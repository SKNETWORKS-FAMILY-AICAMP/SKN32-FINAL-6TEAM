# 도장이 찾은 인계 사항 (2026-09-14)

도장(`acop_dojo/`)은 cs 코드를 실행해 보며 배우는 프로그램이다. 만드는 과정에서 cs 쪽 코드와 문서의
문제를 몇 가지 찾았다. 도장은 원본 저장소를 고치지 않으므로 담당이 따로 있는 일을 여기에 모아 넘긴다.
각 항목에는 처음 보는 사람도 바로 움직일 수 있도록 무엇이 문제인지, 어디에서 어떻게 확인했는지, 무엇을 하면 되는지를 적었다.

용어는 다음과 같이 쓴다.

- 멱등 키: 같은 요청이 두 번 와도 실제 실행은 한 번만 되게 붙이는 표식이다. 같은 키면 두 번째는 저장되지 않는다.
- 기준선 실패: 코드를 일부러 망가뜨리기 전부터 이미 실패하는 테스트다.
- 결정 15: v11 계획서의 결정이다. 값을 모르면 대체 소스에서 가져오고, 그것도 안 되면 치명 결함으로 본다.

## 담당에게 넘기는 일 (5건)

### 9. 멱등 키가 "대상 예약"이 아니라 "Case"로 만들어진다 (담당: 코어 1)

- **무엇이**: 한 Case 안에서 서로 다른 예약을 바꾸는 제안 두 개가 같은 멱등 키를 받는다. 두 번째 제안은 저장되지 않고 사라진다.
- **어디서**: `final_project_cs/app/application/controller.py:374`의 `business_subject=str(case["case_id"])`다.
- **확인**: v11 §4-E 가 "서버가 인자에서 꺼내 확인한 대상 객체 id" 로 바꾸기로 했고, v11 본문도 "아직 코드에 반영되지 않았다" 고 적는다.
  실제 DB 재현 기록: `final_project_cs/wiki/records/reports/debugs/2026-09-11_여행_멱등키_대상충돌.md` (상태: 수정 미적용).
- **하면 되는 것**: 서버 키의 `business_subject` 를 제안 인자에서 꺼낸 대상 id 로 바꾸고, 같은 Case 의 서로 다른 대상 두 제안이 둘 다 저장되는 테스트를 붙인다.
- **도장 쪽 후속**: 고쳐지면 "대상 id 를 빼면 두 제안이 합쳐진다" 결함과 시나리오를 도장에 더한다.

### 10. 결정 15 의 "서버를 끈다" 부분이 아직 없다 (담당: 여행 인프라·감시)

- **무엇이**: 대체 소스 사슬과 치명 판정은 있다(`app/infrastructure/travel/weather_chain.py` · `air_quality.py` · `disruptions.py`, 테스트 `tests/unit/travel/test_kma_weather.py` 등).
  없는 것은 사슬이 전부 실패했을 때 서버를 끄는 판단이다.
- **어디서**: `weather_chain.py` 머리말 8~12행에 적혀 있다. 요청 처리 중에 프로세스를 죽이면 다른 Case 까지 죽으므로
  `all_failed` 수를 보는 감시 쪽 몫이고, 아직 만들어지지 않았다.
- **하면 되는 것**: 감시 쪽에서 `all_failed` 를 읽어 기준을 넘으면 기동을 멈추는 경로를 만든다. 기준(몇 번·몇 분)은 결정이 필요하다.
- 「정정」 도장은 처음에 "결정 15 경로가 cs 에 아예 없다" 고 적었다. 검수 의견을 코드로 확인하지 않고 옮긴 오류였다.

### 11. RAG 통합 테스트 3건이 외부 API 잔액에 달려 있다 (담당: cs)

- **무엇이**: `tests/integration/rag/test_rag_integration.py` 의 3건(`test_search_relevance` 2 · `test_tenant_isolation_and_scope_filter`)이 실행마다 실제 OpenAI 임베딩을 부른다.
  2026-09-14 계정 잔액 소진(`429 insufficient_quota`)으로 3건 모두 실패했다.
- **어디서**: `app/infrastructure/rag/retriever.py:18`이다. 키가 없으면 대체 없이 멈춘다(그 자체는 의도다).
- **하면 되는 것**: 둘 중 하나를 택한다. ① 고정 임베딩을 주입하는 가짜로 돌려 격리·필터 검사를 외부 없이 돌린다. ② 실제 호출이 필요한 부분은 `live` 표식으로 분리한다.
- **도장 쪽**: 지금은 `acop_dojo/acop_dojo/data/known_baseline.json` 에 "알려진 기준선 실패" 로 이유와 날짜를 적어 판정에서 뺀다. 고쳐지면 그 줄을 지운다.

### 12. 디버그 리포트 하나에 지금 상태 표시가 없다 (담당: 해당 리포트 작성자)

- **무엇이**: `tests/unit/core/test_debug_report_status.py` 가 `2026-09-11_여행_멱등키_대상충돌.md` 에서 실패한다.
- **어디서**: 그 테스트는 문서 안에 `## 해결됨` 또는 `## 미해결` 제목이 한 번 나오기를 요구한다. 이 리포트는 표 안에 "수정 미적용" 만 있고 그 제목이 없다.
- **[해결됨 2026-09-21 확인]**: 담당자가 2026-09-14 에 `## 미해결 (2026-09-14 확인 …)` 줄을 얹었다. 테스트 35건 통과.
- ~~하면 되는 것~~ 리포트 위쪽에 `## 미해결` 한 줄을 얹는다. 옛 상태 줄은 지우지 않는다. 테스트 머리말이 "지금 상태를 한 줄 얹는 것만 요구한다" 고 적는다.
- **도장 쪽**: 이 실패는 알려진 목록에 넣지 않았다. 환경 문제가 아니라 문서 무결성 문제라 게이트가 끝날 때 실패로 표시한다.

### 16. 여행 Team 모듈의 공통 가드 두 검사에 우는 테스트가 없다 (담당: 팀 모듈)

- **무엇이**: `app/modules/travel_ops/_base.py` 의 `_guard()` 에서 두 검사를 빼도 전체 테스트가 전부 통과한다.
  - `capability` 검사 — manifest 에 없는 능력을 받아도 그대로 처리한다. `unsupported_capability` 를 보는 테스트가 하나도 없다.
  - `degraded` 검사 — 맥락이 깎였는데도 Team 이 계속 진행한다. Core 쪽 방어(`test_proposal_guard_blocks.py`)가 따로 있어 종단 결과가 같아 보인다.
- **어떻게 확인했나**: 도장 결함 INV-COMMERCE-005 · INV-VOC-002 를 「그 검사만 빼기」로 좁혀 게이트에 걸었다(2026-09-22).
  둘 다 새로 깨뜨린 테스트가 0건이다. 그 전 판(조건 뒤집기)은 각각 32건을 깨뜨렸다. 정상 경로까지 escalate 로 보냈기 때문이며 규칙을 잰 것이 아니다.
- **하면 되는 것**: `tests/unit/travel/` 에 두 가지를 더한다. ① manifest 에 없는 capability 를 준 Task 는 `unsupported_capability` 로 escalate 한다.
  ② `degraded=True` 인 맥락 묶음 ContextPack 을 준 Task 는 Team 단계에서 멈춘다(Core 방어에 기대지 않는다).
- **도장 쪽 후속**: 테스트가 생기면 이 결함 둘이 잡히기 시작한다. 그때 문제로 낼 수 있다.

## 결정이 필요한 것 (2건)

### 14. 중지한 커머스 결함 10건을 어떻게 할까

`[실측 2026-09-14]` 결함마다 겨누던 코드 조각(`old`)이 지금 `app/` 어디에 남아 있는지 찾았다.

| 결함 | 조각이 남은 곳 |
|---|---|
| INV-CLASSIFY-001 · INV-VOC-001 | `app/modules/travel_ops/feedback.py` (인라인 분류가 옮겨 왔다) |
| INV-COMMERCE-002 · INV-VOC-002 · INV-COMMERCE-005 | `app/modules/travel_ops/_base.py` (여행 Team 공통 바탕) |
| INV-TEAM-001 · INV-TEAM-002 · INV-REVIEW-002 · INV-COMMERCE-003 · INV-COMMERCE-004 | 없다 — 커머스 Team 과 함께 사라졌다 |

5/10 = 50% 는 경로만 여행 쪽으로 바꾸면 되살아난다. 선택지는 세 가지다.

1. 다섯을 여행 경로로 옮겨 되살리고 다섯은 폐기한다. 규칙(분류 실패를 넘기지 않는다 · 근거 없는 제안 금지 · manifest 밖 capability 거부 · degraded 면 확정하지 않는다)은 여행에서도 그대로다. 대신 여행 Team 코드가 자주 바뀌어 patch 가 자주 낡는다(`patches` 4초 검사로 잡힌다).
2. 지금처럼 전부 중지하고 여행 Team 트랙을 만들 때 한꺼번에 다시 짠다.
3. 전부 폐기한다. 기록은 git 에 남는다.

`[결정 2026-09-21]` 1번으로 갔다. 조각이 남은 것 중 지금도 정확히 한 번 나오는 넷(INV-CLASSIFY-001 · INV-VOC-001 · INV-VOC-002 · INV-COMMERCE-005)을 `app/modules/travel_ops/` 경로로 옮겨 되살렸다.
규칙은 도메인이 바뀌어도 같다. 잘못된 라벨 거부 · 분류 필드 누락 거부 · 축소됐으면 확정 답변 금지 · manifest 밖 capability 거부다.
INV-COMMERCE-002 는 며칠 사이 조각이 사라져(다시 찾았더니 0곳) 중지로 남겼다. 남은 중지는 6건이다.
여행 Team 코드가 자주 바뀌므로 `patches`(4초) 로 자주 본다. 밀리면 그때 다시 만든다.
