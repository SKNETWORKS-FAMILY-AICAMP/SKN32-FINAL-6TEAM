# 도장 사용법

`acop_dojo/`

`final_project_cs`의 구조와 동작을 실행 증거로 배우는 학습 프로그램이다.

## 명령

`[실측]`

| 명령 | 하는 일 |
|---|---|
| `doctor` | 대상 저장소·파이썬·테스트 수집 점검 |
| `trace [--verify]` | 시나리오 트레이스를 뜬다. `--verify`는 두 번 돌려 같은지 본다 |
| `learn 0` | 해설된 완주. 채점 없음 |
| `learn 1` | 복원 — 빈칸에 들어갈 함수를 고른다 |
| `learn 2` | 대조 — 예상 순서를 세우고 실측과 겹친다 |
| `defect [ID] [--fix 패치]` | 결함 문제. `--fix`를 주면 pytest가 판정한다 |
| `boss [--fix 패치]` | 보스전. 안 배운 코드(검증 엔진)에서 같은 규칙을 찾고 고친다 |
| `tracks` | 학습 트랙 5개 (중지 3개) |

| `review` | 예약된 복습. 같은 규칙을 다른 코드에서 묻는다 |
| `status` | 진행 상황 |

| `patches` | 결함 patch가 아직 유효한지 본다. 4초, 테스트 안 돌림 |
| `defects [--rebuild] [--only ID,ID]` | 결함 카탈로그 등록 게이트. 20분 |
| `stability [--repeats N]` | 결함이 매번 같은 신호를 내는지 |

| `level [쉬움\|보통\|어려움]` | 현재 난이도를 보거나 바꾼다 |
| `build hint <단계>` | 처음부터 쌓기의 단계별 힌트를 한 단계씩 연다 |
| `build steps\|start\|brief N\|check N\|reveal N <파일>` | 처음부터 쌓기. 빈 폴더에서 베이스먼트를 직접 만든다 (대상은 `final_project_sample`) |

`[실측]` 2026-09-06 [README](../README.md)와 대조해 위 다섯을 채웠다. `boss`에는 `--defect ID`·`--force`도 있다. 파이썬 3.12 이상(`sys.monitoring`)이 필요하다. 470개 테스트 중 상당수가 DB를 쓰므로 대상 저장소의 PostgreSQL도 필요하다.

세 명령은 실행 시간이 짧은 순서로 쓴다. `invariants`(0.3초) → `patches`(4초) → `defects`(20분) 순이다. 전체 게이트는 매번 돌리기 어려워 앞의 두 명령을 따로 둔다.

`learn 1`·`learn 2`에서 쉬움은 늘 같은 시나리오와 같은 빈칸을 쓴다. 보통·어려움은 실행 기록이 있는 트랙의 시나리오 가운데 하나를 고르고 빈칸도 실행할 때마다 새로 고르며, `--scenario` 를 주면 그 시나리오를 쓴다.

## 문제 풀기 — 외워서 넘기지 못하게

`python dojo.py quiz` 는 고정 문제 대신 대상 저장소 `app/` 의 함수 전체에서 그때그때 문제를 만든다. 고정 문제는 몇 번 풀면 답을 외우기 때문이다. 기본은 5문제이며 `--count N` 은 1~20, `--family 유형` 은 유형, `--track 트랙` 은 트랙을 고른다. `--seed N` 도 받는다.

유형은 `caller` 누가 부르나, `callee` 무엇을 부르나, `identify` 이름을 가린 코드, `guard_exc` 어떤 예외가 나나, `guard_cond` 검사 조건 채우기, `trace_next` 실행 순서의 여섯이다. 정답은 구문 트리, 곧 코드를 기계가 읽은 구조나 저장된 실행 기록에서 기계로 뽑는다. 언어 모델은 정답을 만들지 않는다.

호출 문제, 곧 누가 부르나·무엇을 부르나는 어느 함수인지 코드로 풀 수 있는 호출만 정답으로 쓴다. 같은 모듈의 함수, `from app… import` 로 가져온 함수와 그 별칭, `self.메서드`, 가져온 모듈의 함수가 대상이다. 안쪽 함수 본문의 호출은 바깥 함수의 직접 호출로 세지 않는다. 이름만 같은 외부 라이브러리 호출은 믿지 않는다. 따라서 동적 호출과 상속으로 부르는 관계는 문제에 나오지 않는다.

직접 쓰기 답은 경로를 떼고 `클래스.메서드` 로 쓴다. 메서드 이름만 써도 되지만, 보기에 같은 메서드 이름이 둘 있으면 클래스까지 써야 한다.

실행 순서 문제는 실행 기록이 거친 파일이 기록을 뜬 뒤 바뀌었으면 그 기록을 쓰지 않는다. 나중에 커밋됐거나 커밋하지 않은 수정이 있는 때가 이에 해당한다. 화면은 몇 개를 뺐는지 알리고 `python dojo.py trace <시나리오>` 로 새 기록을 뜨게 한다. 같은 함수를 연달아 부른 자리나 안쪽 함수가 끼는 자리는 묻지 않는다.

오답은 로컬 Ollama 임베딩, 곧 뜻을 숫자로 나타내는 `bge-m3` 로 골라 뜻이 가까운 함수를 넣는다. 둘째 힌트인 함수 설명은 로컬 언어 모델 `qwen3.5:9b` 가 쓴다. 처음 한 번은 모델을 불러오느라 수십 초 걸릴 수 있다. Ollama가 없으면 멈추지 않고 오답은 단어 빈도(TF-IDF), 설명은 코드의 설명 첫 줄로 대신하며 화면에 사용 방식을 밝힌다. `--no-ollama` 는 오답을 단어 빈도로 고른다. 모델 이름은 `ACOP_DOJO_EMBED_MODEL`·`ACOP_DOJO_LLM_MODEL`, 주소는 `ACOP_DOJO_OLLAMA` 로 바꾼다.

쉬움은 `caller`·`callee`·`guard_exc`·`trace_next` 네 유형을 쓴다. 오답은 다른 층, 곧 다른 폴더 묶음에서 골라 지우기 쉽고 같은 문제가 다시 나올 수 있다. 보통은 여섯 유형을 쓰고 안 본 문제를 먼저 내며, 모자라면 본 문제로 채운다. 뜻이 가까운 스무 개에서 오답을 고른다. 어려움은 가장 가까운 셋을 오답으로 쓰고, 본 문제를 다시 내지 않으며, 한 판 안에서 뜻 묶음인 군집을 겹치지 않는다. 어려움에는 기존 규칙대로 힌트와 보기 전환이 없다.

사전진단 `placement` 도 보통·어려움에서는 1·2번을 생성 문제인 이름 가린 코드와 실행 순서로 내고 3번 결함도 그때그때 고른다. 쉬움은 예전 고정 문제다.

`python dojo.py quiz pool` 은 유형별 대상 수를 보여 준다. `python dojo.py quiz selftest` 는 기본으로 낼 수 있는 자리를 모두 만들어 검사하고, `--count N` 이면 유형마다 N개씩 만든다. `[실측 2026-09-24]` `final_project_cs` 는 색인 함수 642개이며 대상 수는 `caller` 335, `callee` 134, `identify` 575, `guard_exc` 173, `guard_cond` 170, `trace_next` 96이다. 이날 세 난이도를 합쳐 3,992문제를 검사했고 실패는 0이었다. 이 검사는 보기 넷·정답 하나·정답 번호·오답이 정답 조건에 걸리지 않음·가린 이름이 새지 않음을 본다. 정답 쪽 소스에 호출이 실제로 있는지와 실행 기록 원본의 다음 호출과 같은지도 본다. 정적으로 못 푸는 호출로 생기는 관계의 빠짐은 보지 않는다.

색인·임베딩·설명 캐시는 git에 올라가지 않는 `.acop_dojo/quiz/` 에 둔다. 코드가 바뀌면 색인을 다시 만든다. `python dojo.py serve` 또는 `도장 열기.bat` 의 학습 탭에는 「문제 풀기」와 「문제 대상 수 보기」가 있다.

## 막히면 힌트, 모르면 보기

난이도는 쉬움·보통·어려움 셋이다. `python dojo.py level` 은 현재 난이도를 보여 주고, `python dojo.py level 쉬움|보통|어려움` 은 난이도를 바꾼다. 기본은 보통이며 설정은 진행 파일에 남는다. 환경변수 `ACOP_DOJO_LEVEL` 의 `easy`·`normal`·`hard` 값이 있으면 그 값이 앞선다.

쉬움은 보기가 있는 문제를 처음부터 4지선다로 내고 힌트를 허용한다. 보통은 먼저 직접 답하게 하되 `모르겠다` 를 치면 4지선다로 바꾸며 힌트도 허용한다. 어려움은 힌트와 보기 전환이 없다.

어느 질문에서든 `힌트` 를 치면 방향, 좁히기, 거의 답의 순서로 최대 세 단계가 하나씩 열린다. 보기가 넷 이상인 보기 문제는 셋째 단계에서 오답 둘을 지운다. 직접 쓰다가 `모르겠다` 로 보기로 바꿔도 힌트 번호는 이어진다. `?`·`h`·`ㅎ`·`hint` 도 힌트로 읽고, `모름`·`몰라`·`보기`·`pass`·`모르겠어` 도 `모르겠다` 로 읽는다.

문제 기록에는 힌트 수와 보기 전환 여부가 남고 단계 기록에는 합계가 남는다. 보스전에서 배운 규칙을 다른 코드에 옮겨 쓰는 능력은 도움 없이 풀었을 때만 확정된다. `python dojo.py serve` 나 작업 폴더의 `도장 열기.bat` 으로 여는 웹 화면에도 난이도 선택, 「다음 힌트」·「모르겠다」 버튼, 쌓기 힌트 버튼이 있다.

## `--verify`가 두 번 도는 이유

`trace --verify`와 `scenarios --verify-all`은 같은 것을 두 번 떠서 비교한다.

트레이스가 재현되지 않으면 학습 자료로 쓸 수 없다. 매번 다른 것을 보여주면 무엇이 규칙이고 무엇이 우연인지 구분할 수 없다.

## 트랙 5개 (중지 3개)

`[실측 2026-09-14]` 전체 1개와 파트 3개가 돈다. 처음엔 파트 6개였고 커머스 팀 모듈 셋을 중지했다.
이 문서에서 Team은 도메인별 작업을 맡는 팀 모듈을 가리킨다.

경계는 사람이 아니라 디렉터리로 긋는다. `docs/handoff/05_분업_규칙.md`도 같은 이유로 그렇게 한다.

| 트랙 | 담당 | 반드시 설명할 수 있어야 하는 것 |
|---|---|---|
| `all` | 전원 | Case가 만들어지고 라우팅되고 처리된 뒤 닫히는 전 구간. 평가 하네스가 코어를 재는 방식, 값을 모를 때 대체 소스로 넘어가는 규칙(결정 15) |
| `core1` | 코어 1 | 상태는 이벤트를 접은 결과다. `transition_case`만이 상태를 바꾼다. 체크포인트는 업무 상태가 아니다. 바깥함은 tenant 를 모르는 메시지를 내보내지 않는다. Registry 는 선언만 보고 기능을 고른다 |
| `core2` | 코어 2 | 같은 요청을 열 번 보내도 side effect는 한 번. scope 없는 호출은 거부. 원격 Team 이 실패하면 성공으로 추정하지 않고 사람에게 넘긴다. PII 는 DB·API·감사 기록 어디에도 원문으로 남지 않고, 고객을 비운 조회도 tenant 밖으로 안 나간다 |
| `front` | 프론트 | 근거 없는 제안은 화면에서 결정할 수 없어야 한다 |
| `team-travel` | 팀 모듈 | 읽은 것마다 근거가 쌓인다. 분류가 실패하면 조용히 넘기지 않는다 (2026-09-21 신설) |
| ~~`team-voc`~~ · ~~`team-review`~~ · ~~`team-commerce`~~ | 팀 모듈 | 중지 (2026-09-14) |

`[실측 2026-09-10]` 팀 트랙 셋의 대상 코드가 cs 작업 트리에서 지워졌다. 결함 카탈로그 49개 중 10개 = 20%가 `app/modules/customer_ops/*` 를 가리켰다. 해당 결함은 INV-CLASSIFY-001 · INV-COMMERCE-002~005 · INV-REVIEW-002 · INV-TEAM-001·002 · INV-VOC-001·002다.

`[결정 2026-09-14]` 도장은 베이스먼트(도메인을 모르는 코어)만 다룬다. 커머스는 지우지 않고 중지했다. 결함 10은 `catalog.json` 의 `parked`, 시나리오 8은 `scenarios.py` 의 `PARKED_SCENARIO_IDS`, 트랙 3은 `tracks.py` 의 `PARKED_TRACK_IDS`, 원장 규칙 5는 `status: parked`에 남아 있다.

`[결정 2026-09-21]` 여행 Team 트랙(`team-travel`)을 열었다. 시나리오 하나(`travel-team-keeps-every-evidence-v1`, DB 없이 도는 회귀 테스트)로 좁게 시작한다. 중지했던 결함 중 조각이 여행 코드에 남은 넷(INV-CLASSIFY-001 · INV-VOC-001 · INV-VOC-002 · INV-COMMERCE-005)도 `app/modules/travel_ops/` 경로로 옮겼다. 규칙은 도메인이 바뀌어도 같다. 남은 중지는 6건이다. 여행 Team 코드는 자주 바뀌므로 `patches`(4초)로 자주 본다.

`[실측]` 이 표가 "7개"라면서 `front`를 빼고 6개만 적고 있었다(2026-09-06 정정). 트랙마다 자기 시나리오·결함·지도가 붙는다. `--track core2`처럼 지정한다.

`[추정]` 중지한 팀 모듈 3분할은 저장소에 사람 배정 문서가 없어 모듈 성격으로 나눈 것이었다. 여행 Team 트랙을 만들 때 다시 정한다. `acop_dojo/tracks.py`의 `owns`만 고치면 결함·지도·시나리오가 따라온다.

각 트랙의 "설명할 수 있어야 하는 것"이 그대로 불변식이다. → [../../final_project_cs/wiki/quality/invariants.md](../../final_project_cs/wiki/quality/invariants.md)

## 지도는 먼저 그려 보고 대조한다

`map`을 열면 실측 호출 간선이 숨겨져 있다. 요청이 지나갈 모듈을 순서대로 눌러 예상을 만든 다음 "실측과 대조"를 누른다. 그때 간선이 열리고 빠뜨린 것과 없는데 넣은 것이 나온다.

보기만 하는 시각화는 효과가 약하고 조작하거나 답할 때 효과가 난다. [design-review.md](design-review.md) 권고 4(읽기 전용 그래프 → 가설 검증 지도)는 이 원칙을 반영했다.

## 반대 방향으로 처음부터 쌓기

`[2026-09-16 신설]` `learn`·`defect`·`boss` 는 있는 코드를 읽고 고친다. `build` 는 반대로 빈 폴더에서 만든다.

대상은 `final_project_sample` 이다. 코어가 `acop_basement/` 한 패키지에 모여 있고 도메인(`app/`)이 밖에 있어서 "코어만 비우고 다시 쌓기" 가 성립한다. cs 는 둘이 같은 `app/` 안에 섞여 있다.

`[실측 2026-09-16]` 순서는 사람이 정하지 않았다. `acop_basement` 48개 모듈의 import 관계를 AST 로 훑어 층으로 나눴다. 7층이고 순환은 0이다. 그 층을 개발 이야기 단위로 묶어 11단계로 만들었다. 단계마다 붙는 테스트도 짐작이 아니라 실측이다. 단계까지의 모듈만 넣은 폴더를 실제로 만들어 `pytest --co` 로 세었고, 빈 베이스먼트에서 불러오기 실패 63건이 11단계에서 0건이 된다.

한 판은 `build start`(작업 폴더 생성) → `build brief N`(왜 필요한가·만들 파일·이름과 서명) → 직접 작성 → `build check N`(그 단계까지의 코드로 도는 실제 테스트) 순서로 돈다. 통과하면 다음 단계 안내가 바로 뜬다. 막히면 `build reveal N <파일>` 로 참고 구현을 꺼낸다. 꺼낸 사실은 기록에 남는다. 직접 쓴 것과 베낀 것이 섞이면 자기 상태를 읽기 어렵기 때문이다.

그 전에 `python dojo.py build hint <단계>` 를 부르면 단계별 힌트가 하나씩 열린다. 첫째 힌트는 판정 테스트가 가져다 쓰는 이름, 둘째는 각 함수 설명의 첫 줄, 셋째는 몸통이 빈 뼈대 파일이다. 뼈대는 이미 쓴 파일을 덮지 않는다. 힌트 셋을 모두 본 뒤에는 `build reveal` 로 참고 구현을 본다.

명세는 이름과 서명까지만 준다. 테스트가 import 하는 이름을 모르면 시작하지 못하고, 본문을 보여 주면 베끼는 연습이 된다.

`[실측 2026-09-17]` 단계표 테스트 파일 54개를 하나씩 돌렸다. 53개는 통과했다. RAG 검색 1개는 실제 OpenAI 호출이라 잔액이 없으면 누구도 넘을 수 없어 판정에서 뺐다. 「정정」 처음엔 DB 테스트 24개가 실패하거나 무한 대기했다. 원인은 PostgreSQL 이 꺼져 있던 것이었다(재부팅 뒤 안 뜬다. sample `wiki/records/manuals/2026-08-12_1520_환경_기동절차.md`). DB 단계에서 판정이 오래 걸리면 코드보다 DB 부터 본다. `build check` 가 판정 전에 DB 포트를 3초로 먼저 묻고, 안 붙으면 기동 절차를 알려 준다.

`[실측 2026-09-17]` 「정정」 단계별 테스트를 처음엔 불러오기(`pytest --co`)로 정했다. 정답 코드를 순서대로 넣어 돌리니 3·5·8단계가 실패했다. 함수 안에서 뒤 단계 모듈을 읽는 테스트 8개를 불러오기가 못 봤기 때문이다. 그래서 실제로 돌려 처음 통과하는 단계로 다시 정했다. 대부분 9단계로 갔다(조립 루트가 피드백 배치까지 읽는다). 불러오기 성공과 실행 성공은 다르다.

## 보스전이 핵심이다

`boss`는 안 배운 코드에서 같은 규칙을 찾아 고치게 한다.

`learn`과 `defect`가 "이 코드에서 이 규칙"이라면, `boss`는 "규칙을 이해했는가"를 묻는다.

`[실측 2026-09-14]` 보스는 베이스먼트의 검증 엔진 `app/core/verification.py` 다. `engine-serves-another-domain-v1`은 커머스 선언을 물린 엔진이 5만원 주문의 7만원 환불을 거부하는 시나리오다. 트레이스는 12단계, 고유 함수 7개이며 전부 `verification.py` 안에 있다. 역할 셋(입구·수량 검사·숫자 맞춤), 판정, Team 코드가 나오는지, 엔진에 커머스 어휘가 있는지를 묻는다. 마지막 둘은 트레이스와 엔진 파일을 직접 읽어 답을 낸다. 판정 문항은 매번 새로 만든다. 트레이스에도 제품에도 없는 셋째 도메인(수업 예약) 선언과 값을 뽑고, 정답은 대상 저장소의 `verification.py` 를 실제로 돌려 얻는다. 처음 판은 트레이스의 커머스 상황을 그대로 묻고 답을 코드에 박아 재도전하면 외워서 통과할 수 있었다(2026-09-14 codex-alt 검수). `[한계]` 역할 셋과 예/아니오 둘은 여전히 관찰·이름 맞추기에 가깝다. 전이를 가장 직접 재는 것은 판정 문항과 마지막 수리다. 수리 문제는 그 파일의 결함 셋(INV-VERIFY-001 · INV-EVIDENCE-002 · INV-QUANTITY-001)에서 나온다.

`[2026-09-14]` 입장 조건은 0~2단계를 해 보고 3단계를 통과하는 것이다. 0~2단계는 자기 채점이라 통과 표시가 약하고, 3단계는 pytest 가 판정한다. 전엔 기록이 있기만 하면 열려 결함을 못 고친 채로도 들어왔다(codex-alt 지적). `--force` 로 건너뛸 수 있다.

`[2026-09-14]` 진행 기록을 읽을 때 중지한 커머스 결함으로 얻은 보스 통과·능력과 지워진 커머스 Team 함수의 「본 적 있음」을 `archived` 로 옮긴다. 기록은 지우지 않지만 베이스먼트 성과로 세지 않는다.

「변경 이유」 앞의 보스는 커머스 환불 Team(`customer_ops/return_refund.py`)이었다. 도메인 전환으로 파일이 지워져 열리지 않았다. Team 은 도메인이 바뀌면 통째로 바뀌므로 보스는 바뀌지 않는 쪽에 둔다.

같은 규칙을 다른 자리에서 못 찾으면 외운 것이지 안 게 아니다.

`review`도 같은 원리다. 예약된 복습에서 같은 규칙을 다른 코드로 묻는다.

## 정답은 사람이 안 정한다

```
pytest 통과 여부
실측 실행 트레이스
```

둘이 판정한다. 그래서 `defect --fix`에 패치를 주면 채점이 자동이다.
