# A-COP 도장

`final_project_cs` 의 구조와 동작을 실행 증거로 배우는 학습 프로그램이다.
정답은 사람이 아니라 pytest 와 실측 실행 트레이스가 판정한다.

파이썬 3.12 이상이 필요하다(`sys.monitoring`). 전체 424개 테스트 중 상당수가 DB 를 쓰므로
대상 저장소가 사용하는 PostgreSQL 도 연결돼 있어야 한다.

```bash
python dojo.py doctor
```

워크스페이스 루트의 `dojo.py` 는 설치 없이 어디서든 돈다.
정식 설치는 `pip install -e acop_dojo` 로 하고, 그러면 `acop-dojo` 명령이 생긴다.

## 왜 이 형태인가

설계 근거는 [`program/research/학습게임_방법론_조사.md`](../program/research/학습게임_방법론_조사.md)
와 [`학습게임_설계검수_2026-08-30.md`](../program/research/학습게임_설계검수_2026-08-30.md) 에 있다.
요약하면 세 가지다.

예측 퀴즈를 중심에 두지 않는다. prequestion 메타분석에서 물어본 내용에는
효과가 있었지만(g=0.54) 묻지 않은 내용으로는 사실상 전이가 없었다(g=0.04).
"다음 호출은?" 을 반복해 맞히면 그 호출 순서만 남는다. 그래서 예측은 자기설명을
끌어내는 재료로만 쓴다.

먼저 해설된 완주를 보여준다. 처음 보는 사람에게 곧바로 예측을 시키면 탐색
부담이 학습으로 오인된다. 0단계는 채점하지 않는다.

마지막은 안 배운 코드에서 본다. 같은 코드에서 한 번 더 물으면 그 코드를 외웠는지만
알 수 있다. 보스전은 학습 트랙이 한 번도 지나가지 않은 베이스먼트의 검증 엔진
(`app/core/verification.py`)에서 열리고, 엔진에 물리는 선언도 제품 도메인(여행)이 아니라
커머스다. 엔진을 한 줄도 안 고치고 다른 도메인이 도는지를 본다. 기록은
acquisition(처음 성공) · retention(재시도) · transfer(안 배운 코드)로 나눠 남긴다.

## 막히면 힌트, 모르면 보기

난이도는 쉬움·보통·어려움 셋이다. `python dojo.py level` 은 현재 난이도를 보여 주고, `python dojo.py level 쉬움|보통|어려움` 은 난이도를 바꾼다. 기본은 보통이며 선택한 값은 진행 파일에 남는다. 환경변수 `ACOP_DOJO_LEVEL` 에 `easy`·`normal`·`hard` 중 하나가 있으면 그 값이 앞선다.

- 쉬움은 보기가 있는 문제를 처음부터 4지선다로 내고 힌트도 허용한다.
- 보통은 먼저 직접 답하게 한다. 막히면 `모르겠다` 를 쳐서 4지선다로 바꿀 수 있고 힌트도 쓸 수 있다.
- 어려움은 힌트와 보기 전환을 모두 막는다.

어느 질문에서든 `힌트` 를 치면 방향, 좁히기, 거의 답의 순서로 최대 세 단계가 한 단계씩 열린다. 보기 문제의 마지막 힌트는 오답 둘을 지운다. `?`·`h`·`ㅎ`·`hint` 도 `힌트` 와 같고, `모름`·`몰라`·`보기`·`pass`·`모르겠어` 도 `모르겠다` 와 같다.

도움을 받은 사실은 기록에 남는다. 문제마다 힌트 수와 보기 전환 여부를 적고 단계 기록에는 그 합계를 싣는다. 보스전에서 배운 규칙을 다른 코드에 옮겨 쓰는 능력은 도움 없이 풀었을 때만 확정된다.

## 빈 폴더에서 베이스먼트를 처음부터 쌓는다

0~4단계는 있는 코드를 읽고 고치는 과정이다. 이 모드는 반대로 코어를 통째로 비운 작업 폴더에서
시작한다. 한 단계에 모듈 몇 개씩 직접 만들고, 그 저장소의 실제 테스트로 판정한다.

```bash
python dojo.py build steps          # 11단계 목록
python dojo.py build start          # 작업 폴더를 만든다 (원본은 안 건드린다)
python dojo.py build brief 3        # 그 단계의 명세 — 왜 필요한가 · 만들 파일 · 이름과 서명
python dojo.py build check 3        # 판정 — 그 단계까지의 코드로 도는 실제 테스트
python dojo.py build reveal 3 <파일>  # 막히면 참고 구현을 꺼낸다 (기록에 남는다)
```

`python dojo.py build hint <단계>` 는 부를 때마다 그 단계의 힌트를 하나씩 연다. 첫째 힌트는 판정 테스트가 가져다 쓰는 이름, 둘째는 각 함수 설명의 첫 줄, 셋째는 몸통이 빈 뼈대 파일이다. 뼈대 파일은 이미 쓴 파일을 덮지 않는다. 힌트 셋을 모두 본 뒤에는 `build reveal` 로 참고 구현을 볼 수 있다.

대상은 `final_project_sample` 이다. 코어가 `acop_basement/` 한 패키지에 모여 있고 도메인(`app/`)이
그 바깥에 있어서, "코어만 비우고 다시 쌓기" 가 성립한다. cs 는 코어와 도메인이 같은 `app/` 안에 섞여 있다.

순서는 사람이 정하지 않았다. `acop_basement` 의 import 관계를 실측해 층으로 나눴다.
아무것도 안 부르는 층(계약·설정·검증 엔진)부터 API 입구까지 7층이며 순환은 0이다. 그 층을 개발 이야기 단위로 묶어 11단계로 만들었다.

단계마다 테스트가 붙는다. 짐작이 아니라 실측한 결과다. 단계별로 그때까지의 모듈만 넣은 폴더를 만들어
pytest 로 불러 봤다. 빈 베이스먼트에서 63건이던 불러오기 실패가 11단계에서 0건이 된다.

| 단계 | 만드는 것 | 그때 처음 도는 테스트 파일 |
|---|---|---|
| 1 계약 | `core/contracts.py` | 1 |
| 2 이벤트와 상태 | 전이표 · 순수 리듀서 | 2 |
| 3 한 문과 저장소 | `transition_case` · 설정 · DB | 2 |
| 4 멱등성과 검증 | 멱등 키 · 제안 검증 엔진 | 5 |
| 5 Team 을 꽂는 자리 | 선언 · Registry · Port · 읽기 도구 | 3 |
| 6 원격 Team | A2A 실행기 · 전송 · Agent Card | 2 |
| 7 맥락 | Context 예산 · RAG · 그래프 | 3 |
| 8 Controller 한 바퀴와 바깥함 | Controller · outbox · 일꾼 | 1 |

`[실측 2026-09-17]` 이 수는 실제로 돌려서 처음 통과하는 단계다. 처음엔 불러오기(`pytest --co`)만 보고 정했는데,
함수 안에서 뒤 단계 모듈을 읽는 테스트 8개를 놓쳐 정답 코드로도 3·5·8단계가 실패했다. 대부분 9단계로 갔다 —
조립 루트가 피드백 배치까지 읽기 때문이다. 다시 쟀더니 54개 파일 전부 11단계 안에서 통과한다.

`[실측 2026-09-17]` 단계표 테스트 파일 54개를 하나씩 돌려 확인했다. 53개는 통과했고 1개는 판정에서 뺐다.
뺀 것은 `tests/integration/rag/test_rag_integration.py`(7단계)다. 실제 OpenAI 임베딩을 불러서 계정 잔액이 없으면
(429 `insufficient_quota`) 학습자가 무엇을 만들어도 통과할 수 없다.

「정정」 처음엔 DB 를 쓰는 테스트 24개가 실패하거나 끝나지 않았다. 코드 결함이 아니라 PostgreSQL 이 꺼져 있었다
(5433 포트에 아무것도 안 떠 있고 접속이 5초 시간 초과). 그때 "MCP 테스트가 끝나지 않는다" 고 판정에서 뺐다가,
DB 를 띄우고 다시 돌리니 통과해서 되돌렸다. `build check` 가 DB 단계에서 오래 걸리면 먼저 `python dojo.py doctor`
와 sample 매뉴얼(`wiki/records/manuals/2026-08-12_1520_환경_기동절차.md`)의 기동 절차를 본다.

`build start` 는 모듈 48개를 지우고 코드가 든 패키지 `__init__` 12개를 비운다. `app/`·`tests/`·`config/` 는
그대로 둔다. 베이스먼트는 그것들을 모시는 층이라 모실 대상이 없으면 무엇을 만드는지 알 수 없다.

명세는 이름과 서명까지만 준다. 본문은 주지 않는다. 테스트가 import 하는 이름을 모르면 시작하지 못하고,
본문을 보여 주면 베끼는 연습이 된다. `build brief` 는 그 사이의 정보만 제공한다. 참고 구현을 꺼내면(`reveal`) 기록에 남는다.

터미널 없이 한 판을 돌릴 수 있다. 여는 길은 셋이다.

1. 바탕화면의 「A-COP 학습 도장」을 두 번 누른다. 서버가 뜨고 브라우저가 열린다.
2. 워크스페이스 루트의 `도장 열기.bat` 을 두 번 눌러도 같다.
3. 터미널에서 직접:

```bash
python dojo.py serve
```

셋 다 `http://127.0.0.1:8765` 를 연다. 서버가 뜨면 브라우저는 자동으로 열린다(`--no-open` 으로 끈다).
데스크톱 앱의 실행 설정(`.claude/launch.json`)에도 `acop-dojo` 로 등록해 두었다.
창을 닫으면 서버도 닫힌다. 화면은 「서버 연결 끊김」으로 바뀐다.

- 화면에서 동작(사전진단·단계 학습·결함 복구·보스전·쌓기·점검)을 고르고 실행하면 출력이 그대로 흐른다.
- 학습 단계가 문제를 내면 화면 아래 입력창으로 답한다. 답은 CLI 로 들어가고 판정은 pytest 와 실측 트레이스가 한다.
  화면은 점수를 만들지 않는다.
- 돌릴 수 있는 것은 도장 명령 18가지로 제한된다. 인자도 목록에 있는 값이나 작업 폴더 안의 경로만 받는다.
  127.0.0.1 에만 붙는다.
- 서버가 죽으면 화면이 그 사실을 말한다.

`python dojo.py serve` 또는 작업 폴더의 `도장 열기.bat` 으로 여는 웹 화면에도 난이도 선택, 「다음 힌트」·「모르겠다」 버튼, 처음부터 쌓기의 힌트 버튼이 있다.

`[실측 2026-09-22]` 브라우저에서 1단계를 실행해 문제 → 답 전송 → 판정 → 다음 문제까지 확인했다.
`dojo.py map` 이 만드는 정적 지도는 그대로 있다. 그쪽은 서버 없이 파일만으로 열린다.

## 지도는 먼저 그려 보고 대조한다

지도를 열면 실측 호출 간선이 숨겨져 있다. 요청이 지나갈 모듈을 순서대로 눌러
예상을 만든 다음 "실측과 대조"를 누른다. 그때 간선이 열리고 빠뜨린 것과 없는데
넣은 것이 나온다.

보기만 하는 시각화는 효과가 약하고, 조작하거나 답할 때 효과가 난다는 것이
프로그램 시각화 연구의 공통된 결론이다. 그래서 읽기 전용으로 두지 않았다.

## 채점하지 않는 것

서술 답안은 LLM 이 채점하지 않는다. LLM 판정을 단독 합격 기준으로 쓰면 학습자가
모델을 설득해 통과하는 길이 열린다. 대신 `answers` 로 답안과 루브릭을 한 파일에
모아 사람이 본다. 능력 표시도 실행 증거가 있으면 확정, 서술만 있으면 잠정이다.

## 규칙은 원장에 산다

새 규칙이 생긴 것을 기계가 발견하게 하지 않는다. 자연어에서 무엇이 정책이고
무엇이 구현 세부인지 안정적으로 가릴 방법이 없어서, grep 으로 찾겠다는 시도는
오탐과 미탐을 동시에 만든다. 대신 선언을 강제한다.

규칙은 `acop_dojo/data/invariants.json` 에 산다. 결함 카탈로그는 그 규칙을 어기는
방법의 목록이다. `defects` 가 빈 규칙은 "문서에는 있는데 세는 곳이 없다" 는 뜻이고
검사에서 실패한다.

```bash
python dojo.py invariants   # 0.3초
```

`[실측 2026-09-14]` 원장 33개 중 활성 28개, 그 28개 전부에 결함이 하나 이상 붙어 있다(28/28 = 100%).
나머지 5개는 커머스 중지로 `status: parked` 다. R-UNKNOWN-01 은 v11 결정 15(모르는 값은 대체
소스로 채우고, 대체도 실패하면 서버를 끈다)에 맞춰 "모르는 값을 추정값으로 채우지 않는다" 로
좁혔다. 옛 문장 "값을 모르면 비워 둔다" 는 결정 15 가 뒤집었다.

처음 원장을 만들었을 때는 33개 중 9개가
비어 있었고, 그 9개에 결함을 만들어 걸어 보니 5개는 이미 테스트가 잡고 있었고
4개는 잡히지 않았다. 비어 있던 규칙이 잡히는 결함으로 바뀌는 것이 진전이다.
생존한 결함은 무엇을 테스트해야 하는지 알려주지만, 결함이 없는 규칙은 아무것도 알려주지 않는다.

「범위」 "생존 0건" 은 결함이 붙은 규칙에 한한 이야기다. 원장이 그 분모를 드러낸다.

### 두 원장 중 정본은 cs 쪽이다

정본은 cs 의 `final_project_cs/wiki/quality/invariants.md`(INV-CS-*) 다. 이 도장의 R-* 는 결함을 묶으려고
만든 보조 원장이다. 둘은 사람이 문장끼리 짝짓지 않고 실행 증거로 잇는다. 정본 규칙마다 적힌
판정 테스트를, 도장 결함이 실제로 깨뜨렸는지 카탈로그의 실패 목록에서 찾는다. `invariants` 명령과
보고서가 이 대조를 매번 다시 계산한다.

`[실측 2026-09-14]` 정본 52개(자동 판정 49개) 중 도장 결함이 판정 테스트를 깨뜨리는 것은 12개(12/49 = 24%)다.
나머지 37개는 "안전하다" 가 아니라 "도장이 그 규칙을 어기는 결함을 아직 안 만들었다" 는 뜻이다.
반대로 정본 판정 테스트가 아닌 다른 테스트로만 잡히는 도장 결함은 이 대조에 안 나온다.

## patch 는 조용히 낡는다

결함은 unified diff 로 갖고 있어서 `app/` 이 바뀌면 hunk 위치가 밀린다.
실제로 `routes.py` 가 다른 작업으로 14줄 늘면서 `INV-UI-001` 의 patch 가 낡아 있었는데
아무도 몰랐다. 전체 게이트는 20분이라 매번 돌릴 수 없다.

```bash
python dojo.py patches      # 4초
```

두 가지를 나눠 본다. 기준 코드가 바뀐 경우에는 anchor 를 못 찾거나 여러 번 나온다.
이때는 재생성으로 해결되지 않으므로 카탈로그의 `old`/`new` 를 손봐야 한다. patch 만 낡은 경우에는
`defects --rebuild` 로 다시 만들면 된다.

## 안전

원본 저장소는 바꾸지 않는다. 결함은 임시 사본에 적용하고 블록을 벗어나면
지운다. 사본은 `eval/reports`(18MB) 만 빼고 통째로 뜬다. `legacy/` 는 unit
테스트 두 개가 import 하므로 반드시 포함해야 한다.

사본에는 원본의 `.git` 대신 빈 git 저장소를 만든다. `.git` 이 아예 없으면
`git check-ignore` 를 부르는 테스트가 사본에서만 실패한다(2026-09-14 실측).

## 결함 없이도 깨지는 테스트 기준선

공유 저장소는 다른 작업 때문에 늘 몇 건이 깨져 있을 수 있다. 게이트는 결함을 넣기 전에
전체 테스트를 한 번 돌려 그 실패를 기준선으로 적고, 결함이 새로 깨뜨린 테스트만
잡힌 것으로 센다. 수리 판정(`defect --fix`, `boss --fix`)도 같다.

기준선 실패는 둘로 가른다. `acop_dojo/data/known_baseline.json` 에 이유와 날짜를 적어 둔 것(지금은
외부 API 잔액에 달린 RAG 통합 테스트)은 조용히 뺀다. 거기 없는 것도 판정에서는 빼지만 게이트를
실패(exit 1)로 끝내고 보고서에 따로 표시한다. 다른 작업이 깨뜨린 무결성 검사를 환경 탓으로
묻어 두지 않으려고.

대가가 있다. 기준선에서 이미 깨진 테스트만 지키는 규칙은 그 판정에서 보이지 않는다.
그래서 보고서가 기준선 실패를 이름으로 전부 적는다. 전에는 기준선이 하나라도 깨지면
게이트가 멈추고 빈 결과로 카탈로그를 덮어써 기록이 지워졌다. 이제 결과가 비면 덮어쓰지 않는다.
