# 코어 협의 메모 — 같은 장소 판정 · 어순/오타 이름 찾기 (2026-10-19, 활동 팀)

> 활동 팀이 활동 코드 안에서 만든 것과, **코어(공유 파일)에서 정해 주셔야 켜지는 것**을 나눠 적습니다. 코어 파일은 고치지 않았습니다.

## 1. 증상 (테스트하면서 발견)

일정에 「N서울타워」와 관광공사의 「남산서울타워」가 **다른 장소**로 찍혀 같은 곳이 두 번 나온다.

접수 `resolve()` 를 카카오 좌표가 관광공사와 다른 가정으로 돌린 결과(가짜 카카오 · 관광공사 CSV):

| 입력 | 결과 |
|---|---|
| 남산타워 · 남산서울타워 · 서울타워 | 카카오 「N서울타워」 · `content_id=None` (별칭 `SEED_ALIASES` 가 모두 「N서울타워」로 바꾼다) |
| 엔서울타워 | 못 찾음 |

관광공사 정식 제목은 「남산서울타워」(contentid 126535)라 일정 장소가 원장 행과 **연결되지 않는다**. 활동 대체 후보는 원장에서 읽으므로 같은 곳이
다른 이름으로 또 나온다. ※ 카카오 키가 없는 환경이라 실제 카카오 응답의 이름 · 좌표는 확인하지 못했다(가정).

## 2. 활동 팀이 만든 것 (활동 파일만 — 이미 반영)

| 파일 | 내용 |
|---|---|
| `instances/activity/place_identity.py` (신규) | 같은 장소 판정: 규칙(`same`/`different`/`ambiguous`). 확인된 별칭 · 같은 이름만 후보에서 빼고, 애매한 후보는 빼지 않고 경고로 센다. ★LLM 판정은 만들었다가 지웠다(2026-10-19 사용자 결정) |
| `instances/activity/replacement.py` | 「이미 일정에 있는 곳」 제외에 연결(`_drop_same_places`) |
| `instances/activity/name_match.py` (신규) | 어순이 다른 이름 · 오타 비교 도구 (원장 · CSV 이름 찾기가 공용) |
| `db_search/place_by_name.py` · `place_lookup.py` · `csv_places.py` | `fuzzy=True` 로 어순 · 오타도 찾는다. **기본 꺼짐**(결과가 `needs_review`) |

판정 규칙: 같은 contentid · 정규화한 이름이 같음 · 확인된 별칭이면 `same`. 300m 안이고 이름(공통 부분열 ÷ 짧은 이름)이 0.8 이상 닮았는데 이름이 다르면 `ambiguous`(빼지 않음).
그 밖은 `different`. ★이름 유사도만으로는 가를 수 없다(실측: 백화점 입점 매장 22,274쌍이 0.8 이상 · 남산도서관/용산도서관 0.92 = 다른 곳,
남산서울타워/N서울타워 0.80 = 같은 곳). 그래서 이름 유사도는 「같을 수도 있다」는 표시까지만 하고, 같다고 확정하는 것은 별칭이다.

## 2-1. 별칭 표 추가 (2026-10-19, 활동 팀)

이름 유사도만으로는 같은 곳을 못 가르므로(2번 실측) **사람이 확인한 별칭**을 둔다. 배포 뒤에도 이미지를 다시 만들지 않고 고칠 수 있게 DB 표로 둔다.

| 파일 | 내용 |
|---|---|
| `migrations/306_activity_place_alias.sql` | `activity.ac_place_alias(alias_norm, content_id → ac_place, alias, source)`. 활동 300번대 마이그레이션 — 재실행 안전 |
| `data_processing/place_aliases.csv` | **기본 별칭** — 이미지에 실려 배포되므로 **DB 적재 없이도 항상 적용된다**(검토 · 이력은 git). 58곳 · 131개. 대표 시나리오(경복궁 · 광장시장 · 국립중앙박물관 · N서울타워 · 북촌한옥마을 · 인사동 · 창덕궁 · 청계천)는 전부 닿는다 |
| `scripts/activity/load_place_aliases.py` | 시드 → 표 복사(선택 · 원장 `load_places.py` 와 같은 **수동 적재**). 정식 제목이 원장과 다르거나 별칭이 모호하면 넣지 않고 알린다. `--dry-run` · `--prune` |
| `db_search/place_candidates.py` | 후보 풀 결과에 `aliases`(표 전체)를 싣는다. 표가 없으면 `[]` |
| `place_aliases.py` · `place_identity.py` | 시드 파일 + DB 표를 합쳐 읽는다. 별칭이면 `same` — 다만 두 좌표를 다 알고 3km(`ALIAS_MAX_M`)보다 멀면 같은 이름의 다른 곳이라 `different`. 한 별칭이 둘 이상의 장소를 가리키면(시드와 DB 가 어긋나도) 쓰지 않는다 |
| `db_search/place_by_name.py` | 원장 이름 찾기가 못 찾았을 때 별칭으로 한 번 더(`match: alias`) |

★운영 반영: 시드 파일은 배포만으로 적용된다. DB 표는 **추가 별칭**(운영 중 배포 없이 더하기 · 고객이 쓴 말 모으기)용이라 마이그레이션 306(`migrate`)이 돌아야 하고, 비어 있거나 표가 없어도 오류가 아니다. 시드를 표에 복사하려면 `python scripts/activity/load_place_aliases.py --dry-run` 후 적재(선택).
★카카오 응답에서 이름을 뽑아 넣지 않는다(운영정책 제5조). 우리가 정리한 이름과 고객이 쓴 말만 넣는다. 접수(코어)의 `SEED_ALIASES` 가 같은 이름을
「N서울타워」로 바꾸는 문제는 그대로라, 접수가 이 표를 읽거나 `SEED_ALIASES` 를 정식 제목으로 맞추면 접수 단계에서도 풀린다(아래 3-1).

## 3. 코어에서 정해 주실 것 (이 중 하나도 안 해도 기본 동작은 안전하다)

1. **접수 쪽 별칭 값** — `intake/pipeline.py` `SEED_ALIASES` 가 「남산타워 → N서울타워」인데 관광공사 정식 제목은 「남산서울타워」다.
   값을 정식 제목으로 맞추거나, 카카오로 찾은 장소를 **좌표 · 이름이 가까운 원장 행에 잇는** 단계가 필요하다(일정 장소가 `source_content_id` 를 갖게).
   이게 풀리면 일정에 두 항목이 따로 들어가는 문제도 접수 단계에서 사라진다. 활동 쪽 제외 로직은 그 전의 안전망이다.
2. **어순 · 오타 이름 찾기 연결** — 접수의 관광공사 조회(`TourApiPlace.find` · `CatalogNames`)는 정확 일치뿐이다. 활동 원장 조회가
   `fuzzy=True` 를 받으므로 접수에서 못 찾았을 때 한 번 더 부르게 할 수 있다. 결과는 `needs_review` 로 다뤄야 한다.

## 3-2. 장소 정보 채우기 — 활동 원장 먼저 · 웹 검색 · 좌표 (2026-10-19, 활동 팀 구현)

**흐름**: 장소 이름 → 활동 원장 → 있으면 **빈 칸만** 웹 검색 / 없으면 카카오로 **실존만** 확인 → 웹 검색(주소 · 운영시간 · 휴무 · 예약 …) → 주소를 브이월드로 좌표.
읽을 때는 **원장 값 먼저, 비었을 때만 웹 값**(별도 표라 원장 재적재가 덮어쓰지 않는다). 소개글 · 체험 안내는 저장하지 않는다.

| 파일(활동) | 내용 |
|---|---|
| `migrations/307_activity_place_web_info.sql` | `activity.ac_place_web_info` — 출처 · 인용 · URL · 확인 시각 · 만료. 웹 출처는 인용 · URL 필수(검사). 「못 찾음」 표시(`none`, 7일)로 같은 칸을 매번 검색하지 않는다 |
| `geocode.py` | 브이월드 지오코더(주소 → 좌표). 키 `vworld_api_key` 재사용 · 서울 밖은 거부 · 「없음」과 「못 물어봄」을 가른다 |
| `web_info.py` · `db_search/web_info_store.py` | 웹 검색 입력 · 출력 계약 · **검증**(검색한 페이지의 URL · 인용 · 인용에 있는 숫자 · 원문 그대로) · 저장 SQL |
| `place_enrichment.py` | 파이프라인 본체 `enrich_place`. 카카오는 `lookup_place`(있다/없다/못 물어봄만) |
| `enrich_batch.py` · `scripts/activity/enrich_places.py` | 곧 시작하는 활동 일정의 장소를 **미리 채우는 배치**(고객 응답 중에 웹을 부르지 않는다). `--dry-run` · `--limit` |
| `ledger.py` | 운영시간 · 휴무 판정이 웹 값을 합쳐 읽는다(`state` · `state_by_content` · `place_row`). 채운 칸은 `web_info`(출처 · 인용)로 싣는다. 원장 밖 장소도 웹 값이 있으면 판정한다 |

**코어에 요청할 것**
1. `read_tools.ALLOWED_PROMPT_KEYS` 에 `activity_judge.place_info` 추가 + `prompts/activity_judge/place_info.v1.md`(초안: `docs/activity/프롬프트_초안_place_info.v1.md` — 활동이 작성). 등록 전에는 배치가 모든 곳을 `web_error` 로 센다.
2. `place_catalog` 를 없애고 에이전트별 DB 를 읽게 바꿀 때, **접수의 이름 찾기가 활동 원장(`activity.ac_place`)을 먼저** 조회하도록 연결 — 활동 쪽은 `lookup_place`(`place_by_name` — 별칭 · 오타 포함)를 준비해 뒀다. 활동 팀 허용 도구에 `read.place_lookup` 도 없다.
3. 운영시간 판정을 코어의 옛 표(`read.place_hours` → `catalog_hours`)가 아니라 활동 원장 기반 판정(`activity_ledger` 끼움 자리 — `instances/activity/ledger.py`)으로 꽂기. 웹 값 합치기가 그 함수 안에 있다.
4. 배치를 새벽 정기 작업(`jobs.py`)에 올릴지(활동 파일 — 코어 협의 없이 가능하나 비용이 나가므로 켜는 시점을 정해 주세요).
5. 카카오 응답(이름 · 주소 · 좌표)은 이 경로에서 **저장하지 않는다**(운영정책 제5조). 좌표는 브이월드다.

## 4. 확인하지 못한 것

- 실제 카카오 응답(이름 · 좌표). 키가 없어 가짜 카카오로 재현했다.
- 일정 항목(`read.itinerary`)의 장소가 항상 좌표를 갖는지. 좌표가 없으면 이름이 같을 때만 같다고 본다.
