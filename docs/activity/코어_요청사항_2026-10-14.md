## 1. 저장된 운영 상태를 팀이 읽게 연결해 주세요

- **배경**: 임시휴무 · 폐업은 관광공사 정기 운영 정보로는 잡지 못한다. 웹 확인 결과를 배치가 `activity.ac_live_status`(304)에 저장하고,
  고객 요청은 `ActivityTeam.live_lookup` 으로 **읽기만** 한다. 팀은 DB 를 직접 읽지 않으므로 조립이 읽기 함수를 넣어 줘야 한다.
- **요청** — `app/composition.py` `build_registry`, `judge_budget` 을 꽂는 자리 옆:

```python
from app.domains.travel_ops.instances.activity import live_store
...
if hasattr(team, "live_lookup"):
    team.live_lookup = live_store.build_lookup(get_connection)
```

  시험 조립(`tools` 를 주입한 경우)에는 꽂지 않는다 — `judge_llm` 과 같은 이유다.
- **안 꽂으면**: 조용히 꺼지지 않는다(이번에 고침). 로그 `live_status_lookup_not_wired` 경고가 남고 결과는 `unchecked` 가 된다.

## 2. 웹 확인 배치를 작업 실행기에 올려 주세요

- **배경**: 배치는 앞으로 72시간 안에 시작하는 일정 · 예약의 (장소, 날짜)를 한 번씩 웹으로 확인해 저장한다. 활동 스크립트는 저장소 어디에도 등록돼 있지 않다(수동 실행).
- **요청**: `scripts/run_sweepers.py` 에 `catalog_hours`(254행 부근 `run("catalog_hours", ...)`)와 같은 모양으로 `live_status` 작업을 추가하고,
  `scripts/activity/check_live_status.run_once()` 를 하루 한 번(03:00~08:00 창) 호출해 주세요. `--only` 목록(5행)에도 이름을 더한다. `[확인 필요: 코어 실행기가 이 파일이 맞는지]`
- **호출 방식**: 인자 없이 `run_once()`. 창 판단 · 예산 · 한도는 함수 안에서 처리한다.
- **반환값**: `skipped` = `outside_window`(창 밖) · `mode_rule`(설정 꺼짐) · `no_judge_llm`(판정 LLM 없음 — `ACOP_ACTIVITY_JUDGE_MODE` 가 `rule`).
  실행했으면 `checked` · `closed` · `open` · `unknown` · `failed` · `left` 건수.
- **호출 수**: 하루 한 번 기준 같은 (장소, 날짜) 최대 2회. 하루 웹 상한 50회를 넘으면 멈추고 남은 곳은 「미확인」.
- **같이 두면 좋은 것**: `refresh_places` → `read_hours` → `decide_indoor`(지난 회신 9번의 「매일 밤 예약」) — 6번 참고.

## 3. `read.booking` 의 `trip_id` 를 올려 주세요

- **배경**: 대체 후보 순서(LLM)가 취향(테마 · 동행 · 우선순위 · 실내외)을 쓰려면 여행 설문이 필요한데, 예약 성립 판정 Case 는 그 예약이 어느 여행인지 알 방법이 없다.
- **요청**: 회신대로 이미 구현했다고 하셨으니 **푸시하고 커밋 해시를 알려 주세요.** 내용은 `read.booking` 결과에 `trip_id`(그 예약이 든 최신 일정의 여행, 없으면 null) 한 칸 — `app/tools/read_tools.py` `_BOOKING_COLUMNS` · 예약 조회 쿼리.
- **활동이 이어서 할 일**: `[2026-10-15]` 활동 쪽 연결은 끝났다 — `read.itinerary` 는 이미 선언돼 있고(`ITINERARY_TOOLS`), 예약 결과의 `trip_id` 를 받으면 그 여행 일정을 읽어 **대체 후보에서 일정에 있는 장소를 뺀다**(`replacement._itinerary_places`). 설문을 순서 정하기에 넘기는 일만 남았다.

## 4. 확인 화면 · 감시 루프가 `live_status` 칸을 읽어 주세요

- **배경**: 운영 상태가 예약 판정에만 들어가던 것을 원장 판정(`ledger.state`)에 별도 칸으로 실었다. 화면 · 감시가 읽어야 보인다.
- **칸의 모양**

| 칸 | 값 |
|---|---|
| `value` | `open` · `closed` · `unknown` · `unchecked`(아직 안 봄 — 「열었다」가 아니다) |
| `mode` | `shadow` · `llm` |
| `applied` | 판정에 반영됐는지(`llm` 일 때만 true) |
| `checked_at` · `citations` · `visit_date` | 확인 시각 · 인용(url · quote) · 방문 날짜 |

- **주의**: `shadow` 면 `closed` 여도 판정은 안 바뀐다(정확도 재는 기간). 화면에서는 「참고」로 구분해 표시해야 한다.
- **위치**: 원장 판정을 쓰는 끼움 자리(`activity_verdicts`) 및 확인 · 감시 호출부. `[확인 필요: 정확한 파일]`

## 섀도 기간 비용 (고객 효과 없음)

- 섀도(`live_status: shadow`)는 **값만 저장하고 고객 답은 바꾸지 않는다.** 웹 검색은 실제로 호출하므로 비용이 나간다 — 정확도를 재기 위한 비용이다.
- **상한**: 하루 50회(≈ **$1.6/일**) · 월 1,000회(≈ **$32/월**), 호출당 약 $0.032(추정 상한). 넘으면 배치가 멈추고 남은 곳은 「미확인」.
- 실제 호출 수는 「72시간 안 일정 · 예약의 서로 다른 (장소, 날짜) × 최대 2회」다.
- **기간은 미정**이다 — 실시간 운영은 라벨이 없어 사람이 달아야 정확도를 잰다. 기간 · 라벨 담당은 팀에서 정해 공유한다.
