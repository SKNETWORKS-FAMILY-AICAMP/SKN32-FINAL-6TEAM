1. 테스트 개요 및 환경 설정

1.1 테스트 목적 및 범위 정의

이 보고서는 triPilot 멀티 에이전트 시스템 가운데 Activity(활동) 에이전트를 검증한 결과이다. 검증 항목은 다음과 같다. ① 판정 정확성 — 성립·취소·휴무·운영시간·재난·실내외 판정이 규칙대로 나오고 「모름」을 「성립」이나 「휴무 아님」으로 바꾸지 않는다. ② 판정 LLM의 안전성 — shadow로 동작할 때 고객 결과를 바꾸지 않고, llm 모드에서는 조심하는 쪽 값만 받으며 인용·출처 검증을 통과하지 못하면 unknown이 된다. ③ 에이전트 간 협업 — Core(분류·라우팅·Controller)를 거쳐 Activity에 도달하고, 감시 루프의 묶음 재계획에서 식당·이동 항목과 하나의 초안·버전·알림을 만든다. ④ 저장소·RAG 연동 — 활동 원장, 실내외·웹 공지 저장소, shadow 기록 표, 여행 규정 검색이 의도대로 읽고 쓴다. ⑤ 장애 방어 — 외부 소스 실패, LLM 시간 초과·429·스키마 오류, 예산 초과에서 정해진 상태로 끝난다. 범위 밖은 Dining·Mobility의 내부 판정 정확도, 웹 화면, 실제 운영 서버 배포이며, 실제 OpenAI를 부르는 live 시험은 비용 때문에 제외하고 판정 LLM 정확도는 2026-10-12 평가 기록을 인용한다.

1.3 에이전트 구성 개요

Core 인라인 분류기: intent·issue_code를 분류하고 activity_* 접두면 Activity로 보낸다. 분류 어휘와 Team 수신 종류의 정합(라우팅 도달성)을 본다.

Controller: Case 상태 전이, Team 호출, 대기·재개, 승인을 맡는다. 상태 전이, Case당 활성 실행 1개, 재개를 본다.

Activity 에이전트: 성립·취소 판정, 변경 제안, 대체 장소, 일정 관리를 맡는다. 판정 순서, 모름 처리, 고객 질문, 대체 후보를 본다. 부수효과는 실행하지 않고 제안만 반환한다.

Activity 판정 LLM: 지금 화면에 나가는 판정은 규칙이다. LLM은 설정에 따라 휴무·날씨 민감도·재난 영향·실시간 운영 상태·대체안 순서를 백그라운드에서 판정해 규칙과의 차이만 기록한다(shadow, 운영시간은 규칙만). 기록이 쌓여 정확도가 확인되면 LLM 판정으로 교체할 계획이며 인용이 없으면 어느 모드에서도 쓰지 않는다.

Dining · Mobility: 식당·이동 항목을 판정한다. 묶음 재계획에서 Activity와의 협업을 본다.

감시 루프: 외부 사건을 감지해 여행당 Case 1건을 연다. 묶음 재계획 시나리오를 본다.

정책 RAG: 여행 규정 문서를 pgvector로 검색해 고객용 문장을 출처와 함께 싣는다. 검색 정확도, scope·tenant 격리를 본다.

2.3 MCP 및 외부 도구 연동 테스트

3.3 모델 한계 및 개선 방향

한계점: 표본이 작다(라벨 52건 × 3회, 반복은 독립 표본이 아니다). 사람 검토자가 1명이고 1차 라벨을 보고 판단했다(수정 1건). 실시간 운영(웹)은 라벨이 없어 정확도를 모르고 지연이 길다(10-06 측정: p50 15.7초, p95 40.7초, 24회 중 8회 429). sLLM(gemma4:12b)의 판정 정확도는 미측정이다(현재 평가기에 로컬 모델 옵션이 없다). 실운영 정확도·장기 변동은 측정하지 못했다.

개선 방향(결정 D-CS-015 개정 2): 휴무·재난은 규칙을 유지하고 LLM은 shadow(백그라운드로 돌려 규칙과의 차이만 기록)로 쓴다. 운영시간·실내외는 규칙이 먼저 판정하고 모르는 곳만 LLM이 1회 읽어 저장한다. 실시간 운영은 shadow를 유지하고 장소·날짜당 1회 배치로 돌린다. 기록이 쌓여 사람 라벨로 정확도를 확인하면 모드(rule → shadow → llm)를 올려 LLM 판정으로 교체한다. sLLM 전환은 ① 팀 GPU 서버 안정 ② gemma4:12b가 같은 골든셋에서 위험 0건 ③ 호출량 증가를 모두 충족할 때 설정으로 전환한다.

4.3 예외 상황 및 방어 체계 테스트

1차 방어(근거·데이터 누락): 예약·장소·정책을 모르면 확정하지 않고 「모름」·질문·상향으로 끝내며 일반 지식으로 메우지 않는다. 외부 소스가 대체까지 실패하면 fatal_source_failure로 상향한다.

2차 방어(판단 오류·과호출): shadow LLM이 반대 판정을 내도 고객 결과는 불변이고, llm 모드에서도 LLM의 「휴무 아님·괜찮다」는 받지 않는다. 예산 초과·같은 도구 반복·허용 목록 밖 도구는 차단한다.

3차 방어(출력 검수): 인용이 원문에 없거나 웹 출처가 검색 목록에 없으면 버리고 unknown으로 둔다. 대체 순서 LLM이 목록 밖 장소를 내면 코드 순서를 유지하고, Team이 외부 변경을 직접 실행하는 것은 아키텍처 시험으로 금지한다.
