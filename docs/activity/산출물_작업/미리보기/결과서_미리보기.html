1. 구축 목적 및 적용 범위

1.1 문제 정의 및 구축 범위

문제 정의 (Problem Definition): 여행 활동의 취소·변경 문의에서 규정을 기억이나 추정으로 답하면 고객이 손해를 보므로, 서비스가 정한 운영 기준 문서를 근거(출처 포함)로 찾아 인용해야 한다. 질문 표현이 달라지면(위약금·환불·무료 취소 등) 단순 키워드 검색은 맞는 절을 찾지 못해 의미 기반 검색이 필요하며, 근거가 없을 때 답을 지어내지 않도록 검색 실패를 신호로 다룬다.

DB 구축 범위:

벡터 데이터베이스: 서비스 운영 기준 문서(취소·변경 접수, 무료·무예약 판정, 운영 통제, 날씨·재난, 취소 공통 절차, 동행 조건 등) 및 공정거래위원회 국내여행 표준약관·소비자분쟁해결기준(공식 자료 3문서)을 더한 총 19문서·152청크의 임베딩과 유사도 검색 엔진을 PostgreSQL pgvector 로 구축. 활동 에이전트가 쓰는 범위는 4개 scope 14문서·100청크.

그래프 데이터베이스: 활동 에이전트에서는 도입하지 않음(2.2 참고). 장소·예약·일정의 관계는 관계형 DB 와 코드 판정으로 처리.

2.2 그래프 데이터베이스(GraphDB) 설계

도입 여부: 도입하지 않음. 활동 에이전트의 판정 입력(장소·운영시간·예약·재난)은 키로 조회되는 사실 데이터이고, 다단계 관계 탐색이 필요한 질의가 없다.

선택 근거:

장소–예약–일정 항목–여행 관계는 PK/FK 관계형 모델로 충분하며, 판정은 코드 규칙으로 수행하므로 그래프 탐색을 쓰지 않았다.

코어에 GraphStorePort 와 SQL 재귀 CTE 어댑터(SqlGraphAdapter)가 마련되어 있으나 활동 에이전트는 호출하지 않는다.

확장 시 고려:

고객 취향 메모리(과거 여행–선택한 장소 분류 관계)가 쌓이면 사용자–분류 선호 관계를 그래프로 모델링할 수 있다(향후 과제).

도입 전까지 노드·엣지·제약 조건 설계와 성능 지표는 수행하지 않았다(아래 검증 표에서 '해당 없음').

2.3 비정형 데이터 및 메모리 관리 구조

원문 저장소: 청크 본문(content)과 메타데이터(scope, 문서 ID, 절 제목, 버전, 개인정보 등급, 시행일)는 knowledge_chunks 에, 문서 단위 정보(제목·출처 URI·scope·버전)는 knowledge_documents 에 저장한다. 원문 파일은 저장소 knowledge/travel/ 과 knowledge/travel_ext/(공식 자료 정리본) 이며 S3 연동은 없다.

상태 관리 (State Management):

Short-term (Case 상태 기반): required_input_schema·customer_input·customer_input_history 를 팀에 전달해 질문 후 재개 시 이어서 판정한다(LangGraph 미사용).

Long-term (Persisted): 판정 결과·근거(Evidence)·변경 이력은 PostgreSQL 에 영구 저장(일정 버전은 추가만 가능). 고객 취향 프로필(과거 여행 집계)은 미구축 — 향후 과제.

2.2 검색 실패 시 대응(Fallback) 전략

검색 0건: 문서는 있는데 선택한 제공자의 벡터 칸이 비어 있으면 0건으로 돌려주지 않고 예외로 알린다. 0건이면 지어내지 않고 '관련 규정을 찾지 못했다'(모름)로 답하며, 규정 질문은 운영 담당자 인계 경로로 간다.

유사도 임계치: 현재 구현은 top-k(8)만 적용하고 임계치는 두지 않는다. 기본 시험에서 범위 안 1위가 0.495 이상, 범위 밖 최고가 0.333 이었다. 공식 자료를 추가한 뒤 범위 안 1위는 0.461까지 내려갔고 3위 점수는 0.368 까지 있어 0.4 는 경계에 가깝다. 범위 밖 질문은 추가 후 다시 측정하지 않았으므로 임계치는 제안으로만 기록하고 적용은 후속 결정으로 둔다.

Safe Mode: 규정 근거가 없으면 LLM 의 일반 지식으로 답하지 않는다. 답변에는 규정 문서의 고객용 문장을 출처와 함께 싣고, 근거가 부족하면 모름 또는 인계로 전환한다(Graceful Degradation).

3.2 시나리오 기반 데이터 이동 경로 (Workflow)

사용자 요청: "무료로 취소할 수 있는 건 언제까지예요? 위약금이 있나요?"

의도 파악 및 라우팅: 코어 컨트롤러가 요청을 분류하고 활동 팀(activity.itinerary_question 또는 activity.check_cancelable)으로 전달한다.

근거 수집:

규정 검색: read.policy 로 활동 관련 scope(travel_activity·weather·cancellation·access)에서 질문과 가까운 절을 top-k 검색한다.

예약 조건 조회: 예약이 있으면 read.booking_terms 로 취소 기한·위약금율(예약 → 공급자 → 종류 순)을 조회한다. 수치는 RAG 가 아니라 구조화 표에서 온다.

결과 취합: 규정 절의 고객용 문장과 예약 조건 수치를 Evidence 로 결합한다. 근거가 없으면 모름으로 처리해 운영 담당자에게 넘긴다.

답변 구성: 모델이 문장을 짓지 않고 규정 문서에 적힌 고객용 문장을 출처와 함께 싣는다(수치는 예약 조건에서).

응답 및 검수: 팀은 답변·제안만 반환하고 부수효과를 실행하지 않는다. 일정 변경이 필요하면 승인 대기 제안으로 넘긴다.
