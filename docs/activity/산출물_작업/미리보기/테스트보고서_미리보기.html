1. 테스트 개요 및 환경 설정

1.1 테스트 목적 및 범위 정의

본 보고서는 여행 CS의 활동(Activity) 에이전트가 고객의 취소·변경·성립 질문을 근거 있게 판정하는지 검증한 결과이다. 활동 에이전트는 규칙(요일표·재난표·예약 조건)으로 먼저 판정하고, 규정 문장은 RAG 로 찾아 근거로 붙이며, LLM 은 규칙이 읽지 못하는 원문 해석에만 보조로 쓴다. 근거가 없으면 지어내지 않고 「모름」으로 사람에게 넘긴다. 범위는 판정 규칙의 단위 기능, DB 연동, 규정 검색(RAG) 정확도, LLM 보조 판정의 규칙 대비 정확도, 시나리오 통합 시험이다. 자동 시험은 789건을 실행했고(2026-10-14), 자체 sLLM 파인튜닝은 하지 않았다.

1.3 에이전트 구성 개요

코어 컨트롤러: 고객 메시지를 Case 로 만들고 분류(일정 제출·사건 신고·확인 요청·조정 거부)한 뒤 팀 레지스트리를 거쳐 활동 팀에 전달한다. 코어는 팀 내부를 알지 못한다.

활동 팀(ActivityTeam): 취소 가능·성립·변경 제안을 판정하고 제안만 반환한다. 결제·예약 변경 같은 부수효과는 실행하지 않고 승인 대기로 넘긴다.

규정 검색(RAG, read.policy): 질문과 가까운 규정 절을 pgvector 로 찾아 고객용 문장을 출처와 함께 싣는다. 못 찾으면 「모름」으로 인계한다.

LLM 판정 보조(activity_judge): 규칙이 읽지 못하는 원문(휴무·운영시간·재난 문구)만 한 번 해석한다. 기본은 규칙, LLM 은 섀도(기록만)이며 켜도 근거(인용)가 있어야 쓴다.

감시·대체: 웹 공지 확인 배치(check_live_status, 저장 값 조회)와 대체 후보 선정·순서(코드가 후보를 고르고 LLM 은 보여줄 3곳의 순서만 정한다).

2.3 MCP 및 외부 도구 연동 테스트

외부 호출 체계: 외부 호출은 두 가지다 — LLM(웹 검색 포함)과 임베딩. 호출은 CallBudget(DB 집계)으로 일·월 상한을 걸고, 한도에 닿으면 호출하지 않고 「모름」으로 돌아간다. 웹 공지 확인은 요청 경로가 아니라 배치(72시간 창, 6시간 재확인)로 돌려 저장하고, 요청에서는 저장 값만 읽는다. 관련 시험: 호출 실패 격리 7건, 호출 예산 3건, 저장된 확인값 조회 14건, 감시 배치 15건 모두 통과.

장애 방어(Fallback): 호출 실패·시간 초과·근거(인용) 없음이면 같은 호출을 반복하지 않고(재시도 0회) 해당 판정을 「모름」으로 두며, 실패 코드를 기록해 조용히 지나가지 않는다. 규칙 판정은 LLM 이 실패해도 그대로 유지된다. 외부 도구(MCP) 연동은 활동 판정 경로에 없어 시험 대상이 아니다.

3. LLM 보조 판정 평가 결과 (자체 sLLM 파인튜닝은 해당 없음)

3.1 평가 환경 (sLLM 파인튜닝은 수행하지 않음)

평가 대상: 외부 LLM gpt-5.4-nano(reasoning low, 웹 검색 사용)의 판정을 규칙과 비교. 사례 60건 × 3회 반복, 사람 검토 라벨(휴무·재난·운영시간 42사례) 기준.

실행 조건: 데이터셋 SHA-256 ef50c4b7fbc5…, 프롬프트 activity_judge.*.v1, 부트스트랩 10,000회. 소요 260초, 비용 $1.02(전체 180관측).

파인튜닝: 하지 않음. 규칙 먼저, LLM 은 규칙이 읽지 못하는 원문만 보조로 쓰는 구조이며 sLLM 학습 데이터·하이퍼파라미터는 해당 없음.

3.3 한계 및 개선 방향

한계점: 사례가 적고(라벨 42사례) 반복 3회는 같은 사례의 반복이라 독립 표본이 아니다. 위험 오답이 규칙 0건 대비 LLM 5건이므로 LLM 을 판정의 주 경로로 쓰지 않는다. 실운영 정확도·장기 변동은 측정하지 못했다.

개선 방향: LLM 은 규칙이 「모름」일 때와 섀도 기록(규칙과 어긋난 사례 수집)에만 쓰고, 웹 공지는 배치 저장값으로 읽는다. 라벨을 늘려 다시 측정한 뒤 모드(rule → shadow → llm)를 올릴지 정한다.

4. 시나리오 기반 멀티 에이전트 통합 테스트

4.1 워크플로우 실행 검증 (판정 순서와 시나리오 시험 103건)

사용자 요청: "내일 오후 2시에 예약한 야외 체험, 비가 와도 진행되나요? 취소할 수 있나요?"

의도 파악 및 라우팅: 코어 컨트롤러가 요청을 분류해 활동 팀의 취소 가능 판정 또는 성립 판정으로 보낸다.

판정 순서(활동 팀): ① 이미 시작·정원 확인 → ② 재난·날씨(규칙표, 모르는 문구만 LLM) → ③ 휴무·운영시간(요일표) → ④ 저장된 웹 공지 값 → ⑤ 모르면 고객에게 질문 → ⑥ 성립이면 경고와 함께 성립.

근거 수집: 예약이 있으면 예약 조건(취소 기한·위약금율)을 구조화 표에서 읽고, 규정 문장은 RAG 로 찾아 출처와 함께 붙인다. 근거가 없으면 지어내지 않는다.

결과 취합: 판정·근거·경고를 하나의 결과로 묶고, 일정 변경이 필요하면 제안만 만들어 승인 대기로 넘긴다(결제·변경을 실행하지 않는다).

답변 구성: 모델이 문장을 짓지 않고 규칙 판정 문구와 규정 문서의 고객용 문장을 그대로 싣는다.

시나리오 시험: 일정 제출·확인 요청·핀 고정 항목·새벽 점검·감시 배치 등 14개 파일, 103건 — 로컬 DB 를 실제로 쓰며 103건 통과.

4.2 협업 및 라우팅 테스트

Routing 적절성: 일정 제출은 활동 판정이 아니라 여행 접수로, 일정이 정해진 Case 는 일정 관리로 가는지 8건, develop 병합 시 활동 동작 회귀 72건 모두 통과했다.

상태·인계 정합성: 질문 후 재개 시 이전 답과 질문 상태가 이어지는지(고객 답 반영 11건)를 시험했다.

4.3 예외 상황 및 방어 체계 테스트

근거 없음 (1차 방어): 입력·근거가 모자라면 판정하지 않고 「모름」으로 두고 고객에게 질문하거나 사람에게 넘긴다. 모르는 입력 처리 13건을 시험했고, 규정 검색 결과가 없으면 취소 가능·변경 판정은 멈추고 「모름」으로 끝난다(활동 팀 코드 규칙).

외부 호출 실패 (2차 방어): LLM·웹 호출이 실패하거나 인용이 없으면 해당 판정만 「모름」으로 두고 실패 코드를 기록한다(호출 실패 격리 7건, 호출 예산 3건). 재시도는 하지 않는다.

승인 없이 실행하지 않음 (3차 방어): 팀은 제안만 반환하고, 핀 고정·확인 우선 항목은 일정을 바꾸지 않고 질문·안전 알림으로만 처리하는지 8건 시험했다(8건 통과).
