## 1. 저장된 실시간 운영 상태를 팀이 읽게 연결해 주세요

- **배경**: 임시휴무 · 폐업은 관광공사 정기 운영 정보로는 원리상 잡지 못한다(수요일 당일 사고 등). 웹 공지를 봐야 하는데,
  고객 요청마다 부르면 비용이 요청 수에 비례하고 응답이 느리다(p95 40.7초 · 429). 그래서 **장소 · 날짜당 한 번** 배치가 확인해
  `activity.ac_live_status`(마이그레이션 `304`)에 저장하고, 고객 요청은 `ActivityTeam.live_lookup` 으로 **읽기만** 한다.
- **코어에 없는 것**: 읽기 함수를 팀에 꽂는 곳. `develop` · `role-manager` 모두에 연결 코드가 없다(확인함).
- **요청** — `app/composition.py` `build_registry`, `judge_budget` 을 꽂는 자리 옆:

```python
from app.domains.travel_ops.instances.activity import live_store
...
if hasattr(team, "live_lookup"):
    team.live_lookup = live_store.build_lookup(get_connection)
```

  시험 조립(`tools` 를 주입한 경우)에는 꽂지 않는다 — `judge_llm` 과 같은 이유다.

## 2. 웹 확인 배치를 돌릴 곳 · 시간을 정해 주세요

- **배치**: `python scripts/activity/check_live_status.py` — 앞으로 72시간(`live_status_within_hours`) 안에 시작하는 활동의 (장소, 날짜)만
  한 번씩 확인한다. 6시간 안에 확인한 곳은 건너뛰고, 웹 예산(`activity_judge_web`, DB 로 셈)이 차면 멈춰 남은 곳을 출력한다.
  `--dry-run` 은 웹을 부르지 않고 대상만 센다.
- **확인한 것**: `catalog_hours`(03:00~08:00)는 코어 작업인데, 활동 스크립트(`refresh_places` · `read_hours` · `decide_indoor` · `check_live_status`)는
  저장소 어디에도 등록되어 있지 않다(수동 실행). 이미 등록된 것은 없다.
- **요청**: 코어가 작업을 돌리는 방식에 이 스크립트를 올려 주세요. 시간은 15시 정기 점검 직전이 가장 신선하다(안 되면 새벽 창).
  활동 스크립트 셋(`refresh_places` → `read_hours` → `decide_indoor`, 지난 회신 9번의 「매일 밤 예약」)도 같은 자리에 두면 한 번에 정리된다.

## 3. 예약 성립 판정에서 그 여행의 설문을 읽게 해 주세요

- **배경**: 대체 후보 순서(LLM)가 취향(테마 · 동행 · 우선순위 · 실내외)을 쓰려면 여행 설문이 필요하다. 감시 경로에는 여행 정보와 함께 오지만,
  예약 성립 판정 Case 는 예약(`read.booking`)만 보고 **그 예약이 어느 여행인지 알 방법이 없다**(`read.booking` 결과에 `trip_id` 가 없다).
- **요청**(가장 작은 길): `read.booking` 결과에 `trip_id`(그 예약이 든 최신 일정의 여행, 없으면 null) 한 칸.
  주시면 활동이 `read.itinerary(trip_id)` 로 설문을 읽어 순서 정하기에 넘긴다(`allowed_tools` 에 `read.itinerary` 를 더하는 것은 활동 manifest).
  다른 방식(`TEAM_STATE_KEYS` 에 `survey`)을 택하시면 활동은 `current_state["survey"]` 를 이미 읽는다.

## 현재 상태와 검증

- **CI**(수동 실행, `develop` · `main` 두 워크플로): 모두 **성공**. 이 브랜치의 이전 판에서 나던 코어 시험 불일치 2건 · 이동 팀 ruff 2건은 role-manager 를 합치지 않아 없다.
- **LLM 은 아직 꺼져 있다**: 판정 LLM 은 전역 `ACOP_ACTIVITY_JUDGE_MODE=shadow` 여야 팀에 꽂힌다(기본 `rule`). 고객 답은 어느 모드에서도 코드 순서 그대로다.
  `llm`(고객 답에 쓰기)으로 올리는 것은 섀도 기록 · 정확도 라벨을 본 뒤다.
