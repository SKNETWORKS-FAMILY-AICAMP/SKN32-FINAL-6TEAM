## 1. 저장된 실시간 운영 상태를 팀이 읽게 연결해 주세요

- **무엇**: 웹 공지로 확인한 임시휴무 · 폐업은 장소 · 날짜당 한 번 배치가 `activity.ac_live_status`(마이그레이션 `304`)에 저장한다.
  고객 요청은 웹을 부르지 않고 `ActivityTeam.live_lookup` 으로 **읽기만** 한다(요청 수에 비례하던 웹 호출 · p95 40.7초 · 429 를 없애려고).
- **지금 코어에 없는 것**: 이 읽기 함수를 팀에 꽂는 곳. `develop` · `role-manager` 모두에 `live_lookup` · `live_store` 연결 코드가 없다(확인함).
  꽂히지 않으면 이 확인은 **꺼진 채**로 남고 경고도 없다(저장은 되지만 아무도 읽지 않는다).
- **요청**(`judge_budget` 을 꽂는 자리 옆, `app/composition.py` `build_registry`):

```python
from app.domains.travel_ops.instances.activity import live_store
...
if hasattr(team, "live_lookup"):
    team.live_lookup = live_store.build_lookup(get_connection)
```

- 시험 조립(`tools` 를 주입한 경우)에는 꽂지 않는다 — `judge_llm` 과 같은 이유다.
- **켜는 조건**(코어 운영 설정): 전역 `ACOP_ACTIVITY_JUDGE_MODE` 가 `shadow` 여야 판정 LLM 이 꽂힌다(기본 `rule`). 로컬 `.env` 에는 이 변수가 없다(줄 수 0 확인).
  `kind_modes.live_status`(현재 `shadow` — 값만 기록, 고객 답 그대로)를 `llm` 으로 올리는 것은 정확도 라벨을 잰 뒤다.

## 2. 웹 확인 배치를 돌릴 곳 · 시간을 정해 주세요

- **무엇**: `python scripts/activity/check_live_status.py` — 앞으로 72시간(`live_status_within_hours`) 안에 시작하는 활동의 (장소, 날짜)를 한 번씩만 확인해 저장한다.
  6시간 안에 확인한 곳은 건너뛰고, 웹 예산(`activity_judge_web`, DB 로 셈)이 차면 멈춰 남은 곳을 출력한다. `--dry-run` 은 대상만 센다.
- **확인한 것**: 코어의 `catalog_hours`(03:00~08:00)는 코어 작업으로 돌고, **활동 스크립트(`refresh_places` · `read_hours` · `decide_indoor` · 이번 `check_live_status`)는
  저장소 안 어디에도 등록되어 있지 않다**(수동 실행 스크립트). 이미 등록해 둔 것은 없다.
- **요청**: 코어가 작업을 돌리는 방식에 이 스크립트를 같이 올려 주세요. 시간은 15시 정기 점검 직전이 가장 신선하다(안 되면 새벽 창).
  활동 스크립트 셋(`refresh_places` → `read_hours` → `decide_indoor`, 회신 9번의 「매일 밤 예약」)과 같은 자리에 두면 한 번에 정리된다.

## 3. 예약 성립 판정 Case 에서 그 여행의 설문을 읽게 해 주세요

- **무엇**: 대체 후보 순서(LLM)가 취향을 쓰려면 여행 설문(`trips.constraints.survey`)이 필요하다. 감시 경로에는 여행 정보와 함께 오지만,
  예약 성립 판정(`activity.check_feasible`) Case 는 예약(`read.booking`)만 보고 **그 예약이 어느 여행인지 알 방법이 없다**(확인함 —
  `read.booking` 결과에 `trip_id` 가 없고, 팀이 부를 수 있는 `read.itinerary` 는 `trip_id` 를 받아야 한다).
- **요청**(제일 작은 길): `read.booking` 결과에 `trip_id`(그 예약이 든 최신 일정의 여행, 없으면 null) 한 칸.
  주시면 활동이 `read.itinerary(trip_id)` 로 설문을 읽고(`allowed_tools` 에 `read.itinerary` 를 더하는 건 활동 manifest) 순서 정하기에 넘긴다.
  코어가 다른 방식(`TEAM_STATE_KEYS` 에 `survey`)을 택하면 활동은 `current_state["survey"]` 를 이미 읽는다(`replacement._survey`).
- 그 전까지: 이 경로의 순서 정하기는 고객 문장만 쓴다 — 동작에는 지장이 없다.
