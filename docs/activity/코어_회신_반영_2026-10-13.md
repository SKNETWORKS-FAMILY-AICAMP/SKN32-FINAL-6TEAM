## 2. 아직 코어와 맞춰야 하는 것

### 2-1. 고객의 실내 · 야외 답을 저장할 곳 (회신 5 · 9번 관련)

- **지금**: 활동은 재개 때 답을 읽어 **그 Case 안에서만** 쓴다. 팀은 DB 에 쓸 수 없어서(`TEAM_STATE_KEYS` · 읽기 도구만) 저장하지 못한다.
  같은 장소로 다른 Case 가 열리면 다시 묻는다.
- **활동 쪽 준비됨**: `activity.ac_indoor` 에 `decided_by='customer'` 로 쓰는 `indoor_store.record(conn, content_id, outdoor, decided_by)`.
  읽기 우선순위는 operator > customer > llm > class(`ledger.indoor()`).
- **요청**: 팀이 `decisions.indoor = {"value", "source": "customer"}` 로 돌려준 답을 코어가 `indoor_store.record` 로 쓰는 단계(재개 완료 후)가 필요한지 판단해 주세요.
  쓴다면 어느 단계에서 · 누가 쓰는지(코어 단계 / 활동이 받는 쓰기 도구 `write.place_indoor`)는 코어가 정해 주세요. 활동이 쓰기 도구를 가지면 `allowed_tools` · 승인 경계(`CLAUDE.md` 부수효과 규칙)에 걸리므로 코어 몫으로 본다.

### 2-2. 예약 성립 판정 Case 의 여행 설문 (회신 8번)

- 회신의 대안(예약 정보로 그 여행을 찾아 설문을 읽기 → 안 되면 예약 시각으로 찾기 → 안 되면 다시 질의)은 방향이고 **누가 구현할지가 정해지지 않았다.**
- 활동은 `current_state["survey"]` 가 오면 이미 읽는다(`replacement._survey`). 코어가 위 대안으로 그 칸을 채워 주는지 알려 주세요.
- 그 전까지 이 경로는 고객 문장만으로 순서를 정한다(`test_activity_preference_received.py` 의 strict xfail 그대로).

### 2-3. 마이그레이션 번호 `031` 중복

- `031_activity_judge_shadow.sql`(활동)과 `031_web_guard.sql`(develop)이 같은 번호다. 파일 이름 순으로 둘 다 돌아 지금은 동작에 문제가 없다.
- 회신 6번이 말한 「적용된 번호를 기록하는 방식으로 전환 시 SQL 문제」가 이 경우에도 해당한다. 번호 기록 방식으로 바뀌기 전에 활동 쪽 번호를 바꿀지(예: `032_`) 정해 주세요.
  바꾸면 이미 적용된 DB 에는 새 번호로 다시 돌지 않게 `IF NOT EXISTS` 로 되어 있는지 활동이 확인한다.

### 2-4. 웹 검색 판정(`live_status`) — 요청마다가 아니라 장소 · 날짜당 한 번 (회신 9번 + 사용자 결정 10-13)

- **구조 변경**: 전에는 DB 규칙이 「열림」이면 고객 요청마다 웹 검색을 불렀다(요청 수에 비례 · p95 40.7초 · 429). 이제
  **배치가 장소 · 날짜당 한 번 확인해 `activity.ac_live_status`(마이그레이션 304)에 저장하고, 고객 요청은 읽기만 한다.**
  경복궁을 100명이 가도 한 번이다. 임시휴무는 관광공사 정기 운영 정보로는 원리상 못 잡으므로(수요일 당일 사고) 웹이 필요한 범위만 웹으로 본다.
- **활동 쪽 준비됨**: `instances/activity/live_store.py`(읽기 · 쓰기 · 읽기 함수 `build_lookup`) · `scripts/activity/check_live_status.py`(배치) ·
  `ActivityTeam.live_lookup`(읽기 자리 — 없으면 이 확인은 꺼져 있고 경고도 없다) · 시험 `test_activity_live_status_stored.py`.
- **코어에 부탁**
  1. **조립 한 줄** — `judge_budget` 을 꽂는 자리 옆에서 `team.live_lookup = live_store.build_lookup(get_connection)`
     (`from app.domains.travel_ops.instances.activity import live_store`). 꽂기 전에는 이 확인이 꺼져 있다.
  2. **배치를 돌릴 시간** — `scripts/activity/check_live_status.py` 를 코어의 15시 정기 점검 직전(또는 `catalog_hours` 와 같은 새벽 창)에
     돌려 주세요. 앞으로 `live_status_within_hours`(72시간) 안에 시작하는 활동만 본다. 15시 점검이 활동 판정을 부르는 흐름이면
     그 직전 단계로 넣는 편이 가장 신선하다.
  3. **예산** — 웹 줄(`activity_judge_web`)은 이미 DB 로 센다(7번). 배치는 호출마다 그 줄을 확인하고, 넘으면 멈추고 남은 곳을 보고한다.
- **모드**: `kind_modes.live_status` — `rule` 끔 · `shadow` 값만 기록(고객 답 그대로, **지금 기본**) · `llm` 저장된 「닫혔다」(인용 있는 것만)면
  대체 장소를 붙여 변경 제안(승인 대기). 정답 라벨이 없어 `llm` 은 라벨로 정확도를 잰 뒤에 올린다.
- **고객에게 보이는 것**: 확인을 켰는데 값이 없거나 모르면 「정기 운영 정보 기준이다 — 임시휴무 · 폐업은 확인하지 못했다」 경고가 붙는다.
