# 코어 요청 — 액티비티 LLM 순서 기능을 여행 채팅 · 감시 경로에 반영 (2026-10-25, 활동 팀)

> **문제: 액티비티 LLM 순서 기능이 쓰이지 않고 있다.**
> 이 문서는 그 기능을 **실제 여행 채팅 · 감시 경로에 반영하기 위한 계획서**이며, 코어 공용 부품을 건드리므로 **코어 협업이 필요하다.**
> 활동 팀은 코어 파일을 고치지 않았다. 아래 근거는 코드 호출 경로를 읽어 확인한 것이고, 실제 감시 회차를 돌려 확인하지는 않았다.

## 1. 문제 — LLM 순서 기능이 쓰이지 않고 있다

10-21 사용자 결정으로 대체 후보 순서를 `llm` 으로 켰다(`config/guardrails.yaml` `travel.activity_judge.kind_modes.alternative_order: llm`, D-CS-015).
LLM 이 코드가 찾고 검증한 후보 3곳의 **보여 줄 순서와 이유 한 줄**을 정하는 기능이다(지시문 v5 + 이유 문장 검사기, 5회차 평가 통과).

그런데 이 기능은 **예약 하나를 대상으로 연 Case**에서만 돈다. 제품의 주 흐름인 여행 경로에서는 한 번도 불리지 않는다.

| 들어오는 Case | 활동 팀 기능 | 대체 후보를 만드는 곳 | LLM 순서 · 이유 |
|---|---|---|---|
| **감시 루프가 연 Case** (여행 일정 항목) | `activity.itinerary` → `handle_trigger` | `plan_activity_trigger` → `plan_activity_adjustment` (코어 `components/itinerary`) | **안 씀** |
| **여행 채팅 「바꿔 줘」** (여행 Case) | `activity.itinerary` | 같은 코드 경로 · 설문 취향 점수(`similarity`) | **안 씀** |
| 계획 확인 화면 「다른 안 3개」 | (팀 기능 아님) | `team_hooks.activity_alternatives.ranked` | **안 씀** |
| 예약 하나에 대한 Case (개인 AI · API 가 `subject_ref.kind = booking` 으로 지정, 또는 대상 없이 연 Case) | `activity.check_feasible` · `propose_change` | `ReplacementMixin._recommend_alternatives` → `_order_alternatives` | **여기서만 씀** |

### 근거

- `final_project_cs/app/domains/travel_ops/instances/activity/team.py` `select_capability` — 여행이 정해진 Case(`subject_ref.kind == "trip"`)는 `itinerary_route` 로 간다(`instances/_shared/itinerary_team.py` `_wants_itinerary`).
- `final_project_cs/app/domains/travel_ops/components/watch/trip_watch_cases.py` `_open_single` — 감시 Case 의 대상은 여행 일정 항목이다.
- `final_project_cs/app/domains/travel_ops/instances/activity/replacement.py` — LLM 순서(`_order_alternatives`)는 `_recommend_alternatives` 한 곳에서만 불리고, 그 함수는 예약 판정(`team.py` `_closed_place_change`)에서만 불린다.
- 감시 알림 문구(`components/planning/pending.py` `proposal_notice`)는 코드가 계산한 안과 그 설명만 싣는다. LLM 이유 문장 칸이 없다.
- 로컬 DB 에서 예약을 가리키는 Case(`customer_cases.state_json.subject_ref.kind = 'booking'`)는 0건이다.

### 영향

- `alternative_order: llm` 전환의 실제 효과는 예약 기반 Case 뿐이다. 웹 화면 · 감시 · 여행 채팅의 후보 순서는 지금도 코드 순서다.
- 평가의 「감시 경로」(holdout-2 · 3 감시, 5회차 감시 재확인)는 **운영에서 쓰이지 않는 경로**의 품질을 잰 셈이다.
- 운영 판정 기록(표 `activity_llm_decisions`, 308 — 10-24 활동 팀 추가, 커밋 전)도 같은 이유로 예약 기반 Case 에서만 쌓인다.
- 결과서 · `wiki/teams/activity.md` · D-CS-015 의 「고객 요청 · 감시 두 경로 전환」 서술이 실제보다 넓다(활동 팀이 고친다 — 아래 0단계).

## 2. 목표

여행 경로에서 고객이 **후보 3곳을 보고 고르는 자리**에, 이미 평가를 통과한 같은 기능(`alternative_order` — v5 + 이유 문장 검사기)을 거치게 한다.
코드가 고르고 검증한 후보는 그대로 두고, **보여 주는 순서와 이유 한 줄만** 바꾼다. 실패 · 시간 초과 · 예산 초과면 지금처럼 코드 순서다.

## 3. 적용 범위 (제안 — 사용자 결정 필요)

| 여행 경로 자리 | 지금 | 붙일 때 고려할 점 | 제안 |
|---|---|---|---|
| **감시 → 「바꿀까요?」 제안 (안 1 · 2 · 3)** | 코드 순서로 안 3개 | 고객이 3곳을 보고 고른다 — 평가한 구조(3곳 순서)와 같다. 감시는 뒤에서 돌아 응답 지연 부담이 작다 | **1차** |
| **여행 채팅 「바꿔 줘」 → 안 1 · 2 · 3** | 코드 순서 | 고객이 기다린다 — 8초 제한 유지. 고객 문장이 있어 거꾸로 읽기 위험이 있다(검사기가 이유는 막지만 순서는 못 막는다) | **2차** |
| 자동 변경 (설문 「비슷한 곳으로 바꿔줘」) | 코드가 하나를 골라 바로 적용 | LLM 이 고른 곳이 바로 일정이 된다 — 순서가 아니라 선택이 되어 위험이 크다 | 제외 (따로 결정) |
| 계획 확인 화면 「다른 안 3개」 | 코드 순서 | 등록 전이라 취향 단서가 적고, 요청마다 부르면 비용이 크다 | 제외 |

## 4. 코어에 요청하는 것

| # | 요청 | 이유 |
|---|---|---|
| 1 | **팀이 꽂는 자리 하나 추가** — 예: `team_hooks/activity_order.py`. 입력: 원래 장소 · 안 1 · 2 · 3(장소 번호 · 이름 · 분류) · 여행 설문 · 고객 답(있으면). 출력: 순서 · 이유 · 기록. **미등록 · 실패면 `None` → 코어는 코드 순서 그대로** | 코어가 활동 팀 코드를 직접 import 하지 않게(D-CS-013 · DoD-22). 다른 `team_hooks` 와 같은 모양 |
| 2 | 감시 제안(`pending` 의 안 1 · 2 · 3을 만든 직후)에서 그 자리를 부르기 | 1차 범위 |
| 3 | 여행 채팅 「바꿔 줘」의 안 1 · 2 · 3을 만든 직후에서 그 자리를 부르기 | 2차 범위 |
| 4 | 이유 문장을 실을 칸 — 제안 알림 문구(`proposal_notice`)에 붙일지, 안 목록에 `order_reason` 칸을 더할지 정하기 | 고객 화면 · 알림 계약이 바뀐다 — 웹 화면 담당과도 맞춰야 한다 |
| 5 | 새 판정 종류 키 — 예: `kind_modes.alternative_order_trip`, **기본 `shadow`** | 예약 경로(`llm`)와 따로 켜고 끄기 위해 |
| 6 | 묶음 Case(`trip_watch_batch`)에서 항목마다 부를 때의 호출 예산 · 시간 상한 | 한 회차에 여러 항목이 겹치면 LLM 호출이 늘어난다 |

활동 팀이 하는 것: 꽂는 함수(기존 `alternative_order` 를 감쌈) · 후보에 실내외 값(`indoor`) 추가 · 운영 판정 기록(308) 연결 · 평가 · 문서.

## 6. 미리 알아 둘 위험

- **실내외 약점이 옮겨진다.** 설문에만 실내외가 있는 사례에서 LLM 이 맞는 후보를 놓쳤다(5회차 N-40 · 4회차 M-33 · 감시 K-43-W). 여행 감시는 고객 문장 없이 설문만 쓰므로, 후보에 실내외 값을 함께 넘기는 개선을 4단계에 같이 한다.
- **거부 유형 사례는 최종판(v5)으로 재지 못했다.** 5회차에 금지 후보가 있는 사례가 0건이었다. 채팅(2차)을 켜기 전에 6단계에서 거부 · 실내외 함정 사례를 함께 잰다.
- **고객 문구가 바뀐다.** 알림에 이유 문장이 들어가면 알림 문구 계약이 바뀐다.
- **전역 스위치가 먼저다.** 서버 `.env` 의 `ACOP_ACTIVITY_JUDGE_MODE` 가 `rule`(코드 기본값)이면 판정 LLM 이 조립되지 않아 7단계 섀도도 돌지 않는다. 서버 값은 아직 확인하지 않았다.
