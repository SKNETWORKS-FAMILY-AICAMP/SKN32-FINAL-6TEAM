# 코어 연결 요청 — 확인 화면 「다른 곳」 후보에 설문 우선순위 넘기기 (2026-10-22)

활동 쪽 확인 결과와 요청입니다. 활동 쪽은 받을 준비가 되어 있고, **코어가 호출에서 한 줄을 넘기면** 이어집니다.

## 지금 상태 (코드로 확인)

| 경로 | 설문 우선순위(`priority`) → 선호도 | 근거 |
|---|---|---|
| 불가 판정 뒤 대체 (Case) | 이어져 있음 | `replacement._preference` → `rank_alternatives(preference=…)` (Case 상태 → 고객 답 → 설문 순) |
| 확인 화면 「다른 곳」 (등록 전) | **안 이어짐** | `components/intake/candidates.py` `_team_places` 의 `activity_alternatives.ranked(...)` 가 `preference` 를 넘기지 않는다 → 활동 팀 엔진은 `preference=None` 으로 계산 |

`candidates.py` 에는 설문 · `priority` 를 읽는 코드가 없다. 그래서 확인 화면에서는 「이동 1순위」 고객도 설문 무응답과 같은 순위로 후보를 받는다.

## 활동 쪽에서 이미 받을 수 있는 자리

- `team_hooks/activity_alternatives.ranked(conn, tenant_id, content_id, at, *, exclude_content_ids=(), preference=None)` — `preference` 인자가 이미 있다.
- 활동 어댑터 `instances/activity/review_alternatives.rank(..., preference=None)` 도 받아서 `rank_alternatives(preference=…)` 로 넘긴다.
- 값은 `"activity"`(활동 우선) · `"mobility"`(이동 우선) · `None`(무응답). 설문 `priority`(앞이 더 중요) 중 먼저 나오는 `activity` · `mobility` 를 고르는 함수가 `activity/alternatives.preference_from_survey(survey)` 다(`food` 는 이 팀 몫이 아니라 건너뛴다).

## 코어에 부탁하는 것

1. 확인 화면 후보를 만들 때 그 여행(또는 접수)의 설문을 읽어 `preference_from_survey(survey)` 로 값을 만든다.
2. `_team_places` 의 `activity_alternatives.ranked(...)` 호출에 `preference=<그 값>` 을 더한다.
3. 설문이 없으면 `None` 그대로(지금과 같다).

## 연결하면 달라지는 것

활동 우선 고객은 대분류를 고정하고 거리 구간(1~3 · 3~5 · 5~10km) → 소분류 → 중분류 → 나머지 같은 대분류 순으로, 이동 우선 고객은 반경을 넓히며 거리순으로 후보를 받는다. 설문 무응답은 지금처럼 정확한 분류만 화면에 두고 더보기에만 소분류를 푼다.

## 같이 알려 둘 것

- 활동 쪽 후보 엔진은 이 값이 없어도 정상 동작한다(문제가 아니라 **연결 대기**다).
- 확인 화면 경로에도 같은 장소 판정(`place_identity`)을 활동 쪽에서 붙였다(2026-10-22). 원래 장소의 다른 이름 등록본과 일정에 이미 있는 곳의 별칭본을 후보에서 뺀다. 단, 이 부품은 일정 **이름**을 받지 않아 contentid 가 없는 일정 장소(카카오로 찾은 곳)는 못 본다. 코어가 일정 장소 이름을 넘겨 주면 더할 수 있다(요청 아님 — 선택).
