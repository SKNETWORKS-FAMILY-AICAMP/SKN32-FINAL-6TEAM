# 활동 팀 — 같은 장소가 둘로 읽히지 않게 하는 판정 (2026-10-20, develop 0b0dfa1a)

## 한눈에

| 층 | 하는 일 | 서비스 연결 |
|---|---|---|
| ① 이름 → 장소 찾기 | 별칭·어순·오타로 원장 장소를 찾음 | ❌ 함수만 있음 (접수가 안 부름) |
| ② 같은 장소 판정 | 일정에 이미 있는 곳을 대체 후보에서 제외 | ✅ 연결됨 |

- LLM은 안 씀 (만들었다가 지움)
- 같다고 **확정하는 건 별칭뿐**, 이름 유사도는 "같을 수도 있다" 표시까지만

## 배경 — 왜 활동이 직접 만들었나

| 대상 | 접수의 오타·표기 차이 처리 |
|---|---|
| 우리 장소 표 (`places`) | ✅ 있음 (자모 오타 보정) |
| **다이닝 원장** | ✅ 있음 (오타·지점·앞부분·포함 매칭을 다이닝 팀이 만들어 접수에 연결) |
| **활동(관광지)** | ❌ 없음 — 접수의 관광공사 검색·목록 이름 조회는 **정확 일치뿐** |

- 그래서 "남산서울타위"(오타), "명동 올리브영 타운"(어순), "N서울타워"(다른 이름) 같은 관광지 이름은 접수 단계에서 못 잡음
- **활동 팀이 활동 원장용으로 직접 구현** (별칭·어순·오타·같은 장소 판정) → 코어에는 **다이닝처럼 접수에 연결만** 요청

## 별칭 데이터

- **시드 파일** `place_aliases.csv`: 58곳·131개 (남산서울타워 ← 남산타워, N서울타워, 엔서울타워 …). 이미지에 실려 **적재 없이 항상 적용**
- **DB 표** `ac_place_alias`(306): 운영 중 추가용
- 한 별칭이 두 장소를 가리키면 **쓰지 않음**
- 카카오 응답에서 이름을 뽑아 넣지 않음 (약관)

## ① 이름 → 장소 찾기

`find_place_by_name(…, fuzzy=False)` — 앞에서 정해지면 멈춤

| 순서 | 방식 | 결과 |
|---|---|---|
| 1 | 공백·기호 무시 완전 일치 | found |
| 2 | 지점·괄호 뗀 일치 | found / ambiguous |
| 3 | 별칭 | found (확정) |
| 4 | 어순 (`fuzzy=True`만) | found / ambiguous, 확인 필요 |
| 5 | 오타: 자모 거리 0.2 이하, 하나일 때만 (`fuzzy=True`만) | found, 확인 필요 |
| 6 | 없음 | not_found |

`lookup_place`는 위가 못 찾을 때 카카오로 **실존만** 확인 (이름·주소·좌표는 안 싣고 안 저장)

## ② 같은 장소 판정

`verdict(일정 장소, 후보, 별칭표)`

| 조건 | 결과 |
|---|---|
| 같은 contentid | same |
| 별칭 일치 | same (좌표를 알고 **3km 초과**면 ambiguous) |
| 정규화한 이름 같음 | same |
| 300m 안 + 이름 유사도 0.8↑, 이름은 다름 | ambiguous |
| 그 밖 | different |

- **same만 후보에서 뺌**, ambiguous는 남기고 경고 ("같은 장소일 수 있는 후보 N곳 …")
- 이유: 잘못 빼면 좋은 후보를 잃고, 잘못 남기면 한 번 더 나올 뿐

## 한계

1. **①은 서비스에 연결 안 됨**: 접수는 코어 순서를 쓰고, 활동 허용 도구에 `read.place_lookup` 없음
2. 별칭은 **목록에 있는 것만** 잡음 (유명한 곳부터 채우는 중)
3. 이름 유사도로는 같은 곳을 못 가름 (남산도서관/용산도서관 0.92 = 다른 곳, 남산서울타워/N서울타워 0.80 = 같은 곳)
4. 코어 `same_site`와 규칙이 다름 (첫 낱말만 같으면 1.5km까지 같은 곳으로 봐서 다른 갤러리·도서관을 오판)
