## 7. 판정 LLM 호출 예산 — 조립에서 두 줄

```python
# app/composition.py — 판정 LLM 을 팀에 넣는 자리(team.judge_llm = judge_llm) 옆
from app.domains.travel_ops.ports.data_sources.call_budget import CallBudget
from app.domains.travel_ops.instances.activity.judge.modes import budget_caps, budget_meter

budget = CallBudget(connection_factory=get_connection, caps=budget_caps())
team.judge_budget = lambda kind: budget.try_reserve(budget_meter(kind))
```

- 줄: `activity_judge`(원문 해석, 호출당 약 $0.0003) · `activity_judge_web`(웹 검색, 약 $0.032)
- 상한: `guardrails.yaml travel.activity_judge.budget` — text 2,000/일 · 30,000/월, web 50/일 · 1,000/월
- 넘거나 세기 실패 → 활동이 부르지 않고 `skipped`(`budget_exhausted`).
- **꽂기 전에도 웹 검색은 활동이 셉니다**(10-12 오후 추가, `judge/modes.py` `LocalWebBudget`) — 위 web 상한을 프로세스 안에서 셉니다.
  다만 프로세스마다 따로 세고 재기동하면 0 부터라, 서버가 여럿이거나 자주 재기동하면 상한을 넘을 수 있습니다 → 그래서 DB 예산(위 두 줄)이 여전히 필요합니다.
  원문 해석(text)은 꽂기 전에는 세지 않습니다. 기본 모드 `rule` 이면 아무것도 부르지 않아 비용 0 입니다.

## 8. 고객 취향 공통 형식

- 활동은 `current_state["activity_preference"]`(`activity`|`mobility`) → 없으면 `current_state["survey"]["priority"]` 를 읽어 대체 후보 순서를 바꿉니다(`replacement._preference`) — 하지만 `TEAM_STATE_KEYS` 가 넘기지 않아 **실제로는 항상 없음**.
- 팀원 제안과 같은 방향: **코어가 취향을 한 번 정리해 공통 형식으로 넘기고, 활동은 그 값으로 후보를 평가 · 정렬**(에이전트마다 계획서를 읽으면 호출이 늘어남).
- 정해 주셨으면 하는 것: 형식(예 `{"priority": [...], "likes": [...], "avoid": [...], "weights": {"distance": 0.5, "similarity": 0.5}}`) · 넘기는 자리(`TEAM_STATE_KEYS` 한 칸 등).
- 받는 쪽 시험 있음: `tests/unit/travel/activity/test_activity_preference_received.py` — 코어가 넘기기 시작하면 strict xfail 시험이 「예상과 달리 통과」로 알려 줍니다.

## 10. (의견) 여행 중 새 장소 추가 — 넣을지 판단해 주세요

요청이 아니라 **의견**입니다. 새 흐름이라 넣을지부터 코어에서 정해 주세요.

- **역할 정리(10-12 사용자 결정)**: 장소 **이름의 실존 확인은 코어**(접수 `intake/places.resolve` — 우리 목록 → 오타 → 관광공사 → 카카오),
  **활동은 확정된 장소의 운영 · 폐업**(웹 검색 판정, 위 9-3)과 휴무 · 운영시간(원장, 3번)만 봅니다. 활동 팀에 카카오 확인을 따로 두지 않습니다.
- **지금 빈 곳**: 여행 중 「○○ 가고 싶어 / 추가해 줘」는 고객 문장 해석(`components/conversation/trip_intake.py`)의 종류
  (delay · closed · stock_out · change · rollback · question)에 없어 `other` → 사람에게 넘어갑니다. 실존을 확인하는 곳이 없습니다.
  (일정 전체를 다시 내는 경우는 활동이 접수로 돌려보내 `resolve` 가 확인합니다 — `activity.submit_itinerary`.)
- **넣는다면(의견)**: 새 종류(예 `add_place`)로 받아 이름 확인은 접수의 `resolve` 를 그대로 쓰고, 확정된 장소만 활동 성립 판정으로 넘기기.
  활동 쪽 추가 작업은 없습니다(받는 판정은 지금 것 그대로).
- **넣지 않는다면**: 지금처럼 사람에게 넘기되, 「일정을 다시 내 주세요」 안내 문구 정도가 있으면 좋겠습니다.

## 11. 대체 후보 순서 LLM 을 켤 수 있게 두 줄 고쳐 주세요

- **막힌 곳 1 — 프롬프트 허용 목록**: 운영 어댑터는 등록된 프롬프트만 쓴다. `app/tools/read_tools.py` `ALLOWED_PROMPT_KEYS` 에

  `tests/unit/tools/test_prompt_registration.py` 의 기대 목록도 같이.
- **막힌 곳 2 — 모델 인자**: `infrastructure/llm/openai_responses.py` `judge()` 가 모든 판정에 `activity_judge_model`(gpt-5.4-nano) 하나를 쓴다.
