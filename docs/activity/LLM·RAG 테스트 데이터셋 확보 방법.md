# LLM · RAG 테스트 데이터셋 확보 방법

> 작성 2026-10-16 · 상태: **계획**(스크립트 · 자료 미작성)
> 대상 계획서: `대체 후보 3곳 중 최적 장소 판정 — LLM 테스트 계획.md` · `법령 문서 기반 환불·취소 규정 안내 — RAG 테스트 계획.md`
> ★두 계획서의 건수(LLM 60건 · RAG 110건)는 이 문서의 **문서당 120건(dev 40 / holdout 80)** 으로 바꿀 예정이다 — 이유는 §1.

## 0. 한 줄 요약

두 테스트 모두 **기존 자산으로 대부분 만들 수 있다**. 외부 데이터에 기대지 않는다. 핵심은 「정답을 얼마나 싸고 정확하게 붙이느냐」다 — LLM 테스트는 **운영 코드로 실제 후보를 뽑고**, RAG 테스트는 **규정 표로 정답을 계산**한다. 사람 손이 꼭 필요한 곳은 holdout 문장 작성과 2인 라벨링뿐이다.

## 1. 몇 건이 필요한가

95% 신뢰구간 기준으로 계산했다(정확도는 Wilson 구간, 0건 상한은 정확 이항, 기준선 비교는 McNemar · 검정력 80%).

### 1-1. 정확도 85% 가 나왔을 때 실제 범위

| 건수 | 95% 구간 | 오차 |
|---|---|---|
| 20 | 64 ~ 95% | ±15%p |
| 40 | 71 ~ 93% | ±11%p |
| 60 | 74 ~ 92% | ±9%p |
| 100 | 77 ~ 91% | ±7%p |
| 150 | 79 ~ 90% | ±6%p |
| 200 | 79 ~ 89% | ±5%p |

### 1-2. 위험 오답 0건이 나왔을 때 실제 비율의 상한

| 건수 | 상한 |
|---|---|
| 20 | 13.9% |
| 60 | 4.9% |
| 80 | 3.7% |
| 100 | 3.0% |
| 300 | 1.0% |

### 1-3. LLM 이 기준선(코드 순서)보다 낫다고 말하려면

| 개선 폭 | 필요 건수(같은 사례 짝지은 비교) |
|---|---|
| +15%p | 약 85건 |
| +10%p | 약 115~155건 |
| +5%p | 약 310건 |

### 1-4. 정한 건수와 주의점

- **문서당 120건 = dev 40 / holdout 80.** holdout 80건이면 오차 약 ±8%p, 위험 오답 0건일 때 상한 3.7%.
- 기존 계획의 LLM holdout 20건은 0건이 나와도 상한이 13.9% 라 전환 판정에 부족하다. RAG holdout 40건도 부족하다.
- **반복 3회는 건수를 늘리지 않는다.** 같은 사례 3회는 1건이다 — 반복은 일관성(M7)용이다.
- **묶음별 수치는 약하다.** 10건 중 10건이 맞아도 하한은 69%다. 묶음별 결과는 「어디서 틀리는지 찾는 용도」로만 쓰고, 합격 판정은 전체 수치로 한다.

## 3. LLM 테스트(대체 후보 판정) — 120건

### 3-1. 입력 만들기

| 단계 | 방법 | 비용 |
|---|---|---|
| ① 원래 장소 뽑기 | `place_catalog` 에서 분류(NA · HS · VE · LS · EX · EV)와 시간대(아침 개장 경계 · 오후 · 저녁)를 섞어 층화 추출 | 0 |
| ② 후보 3곳 만들기 | 운영 코드 `rank_alternatives` 를 그대로 돌린다. **실제 서비스가 만들 후보와 같아야** 의미가 있다 | 0(DB 읽기만) |
| ③ 취향 붙이기 | 설문 항목(테마 · 동행 · 우선순위 · 실내외)은 조합으로 생성. 고객 문장은 `travel_golden` 의 활동 문장 재사용(dev) 또는 사람 작성(holdout) | 0 |
| ④ 함정 · 범위 이탈(E · F 묶음) | 운영시간 「모름」 후보를 일부러 섞고, 「목록 밖 장소로 해줘」 같은 문장을 사람이 쓴다 | 0 |

### 3-2. 출처별 구성

| 출처 | 건수 | 용도 |
|---|---|---|
| 코드 생성 후보 + 조합 설문 + 템플릿 · 재사용 문장 | 40 | dev |
| 같은 방식 후보 + **사람이 쓴 고객 문장**(규칙 · 프롬프트를 보지 않은 팀원) | 80 | holdout |

LLM 으로 문장 변형을 만드는 것은 **dev 에만** 쓴다. holdout 까지 LLM 이 쓰면 LLM 이 LLM 말투로 시험을 보는 셈이다.

### 3-3. 정답 붙이기

- 라벨러는 **LLM 이 받는 입력만 보고** `acceptable` · `forbidden` 을 붙인다(계획서 1-2절).
- 하드 조건 위반 후보(운영시간 밖 · 일정에 이미 있음)는 코드로 미리 계산해 `forbidden` 초안을 채운다. 사람은 취향 판단만 한다.

### 3-4. 운영 뒤 추가 출처

섀도 기록(`activity_judge_shadow`)은 실제 판정이 쌓이는 곳이라 가장 좋은 출처다. 다만 배치 등록이 아직이라 **10-26 전에는 기대하기 어렵다**. 발표 뒤 재측정용으로 둔다.

## 4. RAG 테스트(환불 · 취소 규정) — 120건

규정이 **표(통보 시점 × 귀책 × 여행 종류 → 비율)** 로 되어 있다는 점이 큰 장점이다. 정답을 사람이 매번 판단하지 않고 **계산으로 만들 수 있다**.

### 4-1. 묶음별 확보 방법

| 묶음 | 확보 방법 | 정답 붙이기 |
|---|---|---|
| A. 직접 질문 | 각 문서 머리말 `customer_answers` 의 키(20개)를 질문으로 바꾼다 | 해당 절 = 정답 |
| C · D. 계산형 · 경계값 | **생성 스크립트** — 출발일 · 취소일 · 당일/숙박 · 귀책을 조합해 문장 템플릿에 넣는다 | 원문 표로 **기대 구간 · 비율을 자동 계산** → 라벨 비용 거의 0 |
| B · E. 고객 말투 · 귀책 구분 | 공개 분쟁 사례(§4-2)를 참고해 사람이 다시 쓴다 | 2인 라벨 |
| F. 여러 절 필요 | 표준약관 제13조 → 분쟁해결기준 비율로 이어지는 질문을 사람이 쓴다 | 2인 라벨 |
| G. 모호 | C 템플릿에서 조건 하나(시점 · 여행 종류 · 귀책)를 일부러 뺀다 | 기대 행동 = 「조건 확인」(자동) |
| H. 범위 밖 | 해외여행 · 항공 · 숙박 업체 약관 · 소송 자문 질문을 쓴다 | 기대 행동 = 「거절」(자동) |
| holdout | `policy_query.py` 규칙을 보지 않은 팀원이 실제 고객처럼 쓴다 | 2인 라벨 |

### 4-2. 고객 말투의 공개 참고 출처(이용 조건 확인 필요)

- 한국소비자원 피해구제 사례
- 소비자분쟁조정위원회 조정결정 사례
- 1372 소비자상담센터 상담 사례

여행 · 공연 · 레저 환불 분쟁이 실제 상황으로 정리돼 있어 시나리오 재료로 좋다. **문장을 그대로 복사하지 않고 상황만 가져와 다시 쓴다.** 사람 이름 · 업체명은 넣지 않는다.

### 4-3. 출처별 구성

| 출처 | 건수 | 용도 |
|---|---|---|
| 생성 스크립트(A · C · D · G · H) | 40 | dev 30 / holdout 10 |
| 사람 작성(B · E · F · holdout) | 80 | holdout 70 / dev 10 |

### 4-4. 계산형 생성 스크립트의 모양(초안)

```text
입력 조합: 여행 종류 {당일, 숙박} × 귀책 {여행자, 여행사, 불가항력} × 통보 시점 {5일 전 … 당일}
           + 공연 {10일 전, 7일 전, 3일 전, 1일 전, 당일, 예매 후 24시간}
→ 문장 템플릿: "{출발 요일} 출발 {여행 종류} 여행인데 {취소 요일}에 {귀책 표현}으로 취소하면요?"
→ 기대값: 원문 표에서 구간 · 비율을 찾아 required_facts 와 gold_sections 를 채운다
```

★생성 문장은 말투가 단조롭다 — dev 와 경계값 확인용이며, 일반화 주장은 사람 작성 holdout 으로만 한다.

## 5. 공통 절차(10-26 최종발표까지)

| 날짜 | 할 일 |
|---|---|
| 10-17 ~ 18 | LLM 후보 추출 스크립트 · RAG 계산형 생성 스크립트 · **규정 자료 원문 대조(RAG 0단계)** |
| 10-19 ~ 20 | 팀원 holdout 문장 작성(문서당 2명, 규칙 · 프롬프트 비공개) |
| 10-21 ~ 22 | `eval/human_review` 로 2인 블라인드 라벨링 → 일치도 확인 → 불일치 합의 |
| 10-23 | 자료 동결 — `manifest.json` 에 건수 · 출처 · sha256 · 라벨러 기록(기존 `eval/activity_judge/manifest.json` 방식) |
| 10-24 ~ 25 | 실행 1회 · 보고서 반영 |

**병목**: 사람이 써야 하는 문장이 문서당 80건, 합쳐 160건이다. 팀원 4명이 나누면 1인당 40건.

## 6. 지킬 규칙

- 쇼핑몰 시절 자료는 쓰지 않는다 — 여행 도메인과 `place_catalog` 만 쓴다.
- AI 가 만든 라벨은 `label_by: "claude-draft"` 처럼 **초안 표시**를 붙인다. 사람 라벨은 `human_review` 도구를 거친 것만 인정한다(도구의 블라인드 규칙).
- 공개 사례에서 개인정보 · 업체명을 빼고, 원문을 그대로 복사하지 않는다.
- OpenAI 실호출은 dev 문장 변형에만 최소로 쓴다. 후보 생성과 정답 계산은 호출 없이 만든다.
- holdout 은 자료 동결 전까지 프롬프트 · 규칙을 고치는 사람이 열지 않는다.

## 7. 근거

- 건수 계산의 통계 방법(묶음 신뢰구간 · 짝지은 비교 · 검정력): Miller, E. (2024). *Adding Error Bars to Evals: A Statistical Approach to Language Model Evaluations.* arXiv:2411.00640 <https://arxiv.org/abs/2411.00640>
- holdout 을 고치는 동안 열지 않는 이유: Dwork, C. 외 (2015). *The reusable holdout: Preserving validity in adaptive data analysis.* Science 349(6248), 636–638. doi:10.1126/science.aaa9375
- 위 1절의 수치는 2026-10-16 Python 으로 직접 계산했다(Wilson 구간, 0/n 의 95% 상한 = 1 − 0.05^(1/n), McNemar 표본 수 공식 · 불일치 비율 15~25% 가정). 불일치 비율은 가정값이라 실제 dev 실행 뒤 다시 계산한다.
