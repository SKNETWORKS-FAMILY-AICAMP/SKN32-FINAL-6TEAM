# 대체 후보 3곳 중 최적 장소 판정 — LLM 테스트 계획

> 작성 2026-10-16 · 상태: **계획**(기능 미구현, 평가 자료 작성 중) · `[2026-10-17]` 실행 · 채점 도구 작성 — `final_project_cs/eval/alternative_pick/`(README)
> 관련 코드: `final_project_cs/app/domains/travel_ops/instances/activity/alternative_order.py` · `final_project_cs/prompts/activity_judge/alternative_order.v2.md` · `final_project_cs/eval/activity_judge/`

> `[2026-10-19 사용자 결정 A안]` **안전 지표로 판정한다.** 화면이 후보 3곳을 모두 보여 주고 고객이 직접 고르므로, LLM 순서가 바꾸는 것은 나열 순서와 이유 한 줄뿐이다(`replacement.py`). 그래서 전환 기준은 **M2 · M5 · M6b · M6e** 만 쓰고 M1 · M3 · M7 · M8 은 참고값으로 적는다(아래 2절 · 5절). 라벨 결과 셋 다 허용인 사례가 41~42/80 = 51~53% 라, M1 을 전체로 세면 절반이 자동 정답이다 — M1 참고값은 **골라야 하는 사례**(허용 답이 후보 일부)로 따로 낸다. 1순위가 자동 적용되는 경로가 생기면 M1 을 다시 주 지표로 올린다.

## 0. 지금 코드와의 관계

- 비슷한 기능이 이미 있다. `alternative_order.py` 는 코드가 고른 3곳의 **보여 줄 순서**만 LLM 에게 맡긴다. 순서를 바꿨는데 이유가 없으면 그 답을 버리고 코드 순서를 쓴다.
- 새로 만들 「가장 적합한 1곳 판정」은 결국 `order[0]`, 즉 1순위를 맞히는 문제다. 그래서 이 계획은 지금 기능과 새 기능에 똑같이 적용된다.
- 기존 `eval/activity_judge/` 의 틀을 그대로 가져다 쓴다. 사례마다 `acceptable`(허용 답)을 두고, 결과를 `correct` / `dangerous` 로 나누고, 같은 사례 반복은 사례 단위로 묶어 신뢰구간을 낸다(`metrics.cluster_bootstrap`). 새 도구를 만들 필요가 없다.

## 1. 잘된 판정과 잘못된 판정의 기준

### 1-1. 판정 근거의 우선순위

높은 단계가 항상 이긴다.

| 순위 | 근거 | 예 |
|---|---|---|
| 1 | **하드 조건**: 그 시각(시작~끝)에 열려 있음, 재난으로 막히지 않음, 이미 일정에 없음, 원래 장소가 아님 | 08:00 시작인데 09:00 개장 → 실격 |
| 2 | **이번 요청에서 고객이 직접 한 말** | 「비 오니까 실내로」, 「애들이 지쳤어요」 |
| 3 | **설문 취향**(항목끼리 순서 없음) | 테마(`theme`), 세부 테마(`theme_details`), 실내외 선호(`indoor_outdoor`), 직접 쓴 선호(`custom_answers`) |
| 4 | **코드 순서**(가깝고 비슷한 곳 먼저) | 단서가 없거나 동점일 때 |

> 이 우선순위는 문헌에서 그대로 가져온 것이 아니라 **팀 판정 기준(설계 결정)**이다. 가장 가까운 근거는 TravelPlanner[4]가 고객의 명시적 요구를 하드 제약으로 분리한 방식이다. 팀 합의가 필요하다.

**설문을 한 단계로 합친 이유**(2026-10-16 결정 — 처음 판은 「제약성 취향」과 「일반 취향」 두 단계였다)

- **동행(아이 · 어르신)은 지금 받지 않는다.** 설문 표(`TripSurvey.party`)에 칸은 있고 LLM 에도 넘기지만(`alternative_order.SURVEY_FIELDS`), 접수 문항(`survey_answers.QUESTIONS`)이 묻지 않아 값이 비어 있다. 받지 않는 값을 판정 기준에 둘 수 없다. 고객이 이번 요청에서 직접 「아이와 함께」라고 말하면 2순위(고객 말)로 다룬다.
- **실내외 선호만으로는 세부 테마보다 앞선다고 보기 어렵다.** 평소 「실내 선호」는 취향의 하나일 뿐이다. 비 · 폭염처럼 실내가 필요해지는 사정은 고객이 이번 요청에서 말하므로 2순위가 맡는다.
- **우선순위(`priority`)는 취향이 아니다.** 대체할 때 음식 · 활동 · 이동 중 무엇을 먼저 볼지의 값으로, **후보를 뽑는 범위**를 정한다(`alternatives.preference_from_survey` — 이동 우선이면 분류 조건을 푼다). LLM 이 순서를 정할 때의 근거로 채점하지 않는다.

**설문 항목끼리 갈릴 때**(예: 실내 선호 + 테마 「자연」): 항목끼리 순서가 없으므로 **설문 단서를 더 많이 만족하는 후보**를 정답으로 둔다. 만족하는 수가 같으면 그 후보들이 모두 허용 답이다(동점 처리). 이런 사례는 라벨 근거(`rationale`)에 「설문 내부 충돌」로 적는다.

### 1-2. 판정 결과의 분류

| 결과 | 정의 |
|---|---|
| ✅ **정답** | 1순위가 사례의 `acceptable` 목록 안에 있음(동점이면 허용 답이 2곳일 수 있음) |
| ⚠️ **차선** | 하드 조건은 지켰지만 더 높은 순위의 단서를 놓침(예: 고객이 「체험 위주로」라고 했는데 공원을 고름 — **주제만 안 맞음**) |
| ❌ **위험 오답** | 1순위가 `forbidden` 목록에 있음(하드 조건 위반, 고객이 직접 거부한 유형, **고객이 이번에 말한 물리 조건을 정면으로 어긴 곳**), 또는 **모델 원답**의 1순위가 후보 밖 장소 |

`[2026-10-19 사용자 결정]` **위험 = 명시 조건 위반까지.** ① 그 시각에 못 가는 곳 ② 「싫다 · 말고 · 보다」로 거부한 유형(「역사 싫다」 → 역사 유적) ③ 고객이 말한 물리 조건 — 실내 · 비 · 바깥 · 덜 걷기 · 앉아서 — 을 정면으로 어긴 곳(「비 오니까 실내로」 → 한강공원). 주제만 안 맞는 곳은 차선이다. 처음 판의 차선 예(「실내를 원했는데 야외」)는 두 라벨러가 독립적으로 위험으로 단 14장과 맞지 않아 옮겼다. 입력에 실내외가 없는 후보(식물원 · 성당)는 정면 위반으로 보지 않는다.
| ❌ **근거 위반** | 장소는 맞게 골랐지만 이유에 입력에 없는 사실(요금 · 혼잡 · 후기 · 평점)을 지어냄 — **고객 화면에 그대로 나간다** |
| ❌ **형식 위반** | 코드가 답을 버림(`alternative_order.apply` 가 `None`) — `order` 없음, 쓸 수 있는 id 가 0개, **순서를 바꿨는데 이유가 없음**. 고객에게는 코드 순서가 나가 피해는 없지만 LLM 판단이 쓰이지 않는다(M6) |

**근거 위반과 형식 위반을 가르는 이유**(2026-10-16): 「이유가 **틀림**」은 지어낸 문장이 고객에게 보이는 위험이라 M5(목표 100%)로, 「이유가 **없음**」은 코드가 버려 아무것도 안 보이는 형식 실수라 M6 으로 센다. 섞으면 M5 가 무해한 실수로 깎이거나 진짜 지어냄을 가린다.

**범위 이탈(F)은 두 번 잰다**: 모델이 후보 밖 장소(「롯데월드」)를 1순위로 내면 **모델 원답 기준**으로는 위험 오답(M2 — 모델 행동 평가)이고, 코드가 그 id 를 버리므로 **보정 후 기준**으로는 고객에게 나가지 않는다(서비스 안전 평가). 둘을 같이 적는다.

**라벨 원칙**: 라벨러는 **LLM 이 받는 입력만 보고** 라벨을 붙인다. 바깥 지식으로 「실제로는 여기가 더 좋다」고 판단하면, 모델이 알 수 없는 것을 기준으로 채점하게 된다.

## 2. 수치화 항목

모든 지표는 **분자/분모와 %를 함께** 적는다(예: 68/80 = 85%). 3회 반복 결과는 사례 단위 군집 부트스트랩으로 95% 신뢰구간을 낸다[6].

| # | 지표 | 계산 | 목표(합의 필요) | 근거 |
|---|---|---|---|---|
| M1 | **1순위 적중률**(주 지표) | 1순위가 허용 답에 있는 판정 수 / 전체 판정 수 | ≥ 85% | — |
| M2 | **위험 오답률** | 1순위가 금지 목록에 있는 판정 수 / 전체 판정 수 | **0건** | [4] |
| M3 | **기준선 대비 개선** | M1(LLM) − M1(코드 순서 그대로). 같은 사례끼리 짝지어 부트스트랩 | 신뢰구간 하한 > 0 | [6] |
| M4 | **단서 없을 때 순서 유지율** | 코드 순서를 지킨 수 / 단서 없는 사례 수 | 100% | [5] |
| M5 | **이유 근거율** | 지어낸 사실이 없는 이유 수 / 이유를 쓴 답 수 | 100% | [4][7] |
| M6a | **완전 유효율** | 규칙을 그대로 지킨 답 수 / 호출 수 | 참고값 | — |
| M6b | **사용률** | (완전 유효 + 보정해서 씀) / 호출 수 — LLM 판단이 고객 화면에 반영된 비율 | **≥ 98%** | — |
| M6c | 보정률 | 코드가 고쳐서 쓴 답 수 / 호출 수 — 후보 밖 · 겹친 id 를 버리거나(`dropped`) 빠진 후보를 뒤에 붙임 | 참고값 | — |
| M6d | **폐기율** | 코드가 버린 답 수 / 호출 수 — `order` 없음 · 쓸 id 0개 · **순서를 바꿨는데 이유 없음**(모델 탓, `LLM_SCHEMA_INVALID`) | 참고값 | — |
| M6e | **호출 실패율** | 시간 초과 · 429 · 키 없음 · **프롬프트 미등록** 수 / 호출 수(환경 탓, `LLM_TIMEOUT` · `LLM_ERROR`) | **0건** | — |
| M7 | **반복 일관성** | 3회 모두 1순위가 같은 사례 수 / 사례 수 | ≥ 90% | — |
| M8 | **위치 편향** | 후보 순서를 섞어 다시 넣어도 1순위 장소가 같은 사례 수 / 섞은 사례 수 | ≥ 90% | [1][2][3][5] |
| M9 | 지연 · 비용 | 응답 시간 p50/p95, 판정 1건당 추정 비용(`metrics.call_cost` 재사용) | 참고값 | — |

- **M3 을 넣는 이유**: LLM 이 코드 순서보다 낫지 않으면 굳이 쓸 이유가 없다.
- **M6 을 나누는 이유**: 갈래마다 고칠 곳이 다르다 — 보정 · 폐기는 프롬프트, 호출 실패는 운영 설정 · 인프라다. 특히 프롬프트가 허용 목록에 없으면 모든 호출이 실패하고 코드 순서로 답한다(`alternative_order.py` 머리말) — 한 숫자로 세면 그 환경 문제가 「모델이 형식을 못 지킨다」로 읽힌다. 네 갈래(M6a · c · d · e)의 분자를 더하면 호출 수가 된다(M6a + M6c + M6d + M6e = 100%).
- **M8 을 넣는 이유**: 첫 번째 후보를 습관적으로 고르는 편향을 잡는다. 세 논문[1][2][3]이 같은 현상을 보고해 근거가 가장 강한 항목이다.
- **`[2026-10-19 A안]` 주 지표가 바뀌었다**: 전환 판정은 M2 · M5 · M6 이 한다. M1 은 참고값이며 **골라야 하는 사례**(허용 답이 1~2곳)만 분모로 센다 — 셋 다 허용(무엇을 골라도 맞음)과 「없음」(고객이 바란 곳이 후보에 없음, 무엇을 골라도 틀림)은 1순위 능력을 재지 못한다. 둘 다 M2 · M5 에는 그대로 든다. 전체 M1 은 「부풀려짐」으로 같이 적는다.
- **`[2026-10-19]` 「없음」 라벨**: 고객이 바란 곳이 후보에 하나도 없으면 정답 칸에 `없음` 만 적는다(빈 칸은 덜 채움 오류). 이때 위험 칸에 셋 다 적지 않는다 — 위험은 그 시각에 못 가는 곳 · 고객이 직접 거부한 유형뿐이고, 셋 다 적으면 무엇을 골라도 M2 가 되어 전환이 불가능해진다.
- **목표 수치에 대해**: 85% · 90% · 98% 는 문헌 값이 아니라 출발점이다. holdout 80건 규모로도 몇 %p 수준의 작은 차이는 구분하기 어려우므로[6], M3 은 「신뢰구간 하한 > 0」처럼 방향만 확인하는 기준으로 둔다.

## 3. 평가 자료 설계

서울 활동 원장(`activity.ac_place`)의 실제 장소로 **120건(dev 40 / holdout 80)** 을 만든다. 쇼핑몰 시절 자료는 쓰지 않는다. (`[2026-10-16]` 활동 팀 장소 조회가 원장 하나로 통일됐다 — 대체 후보도 원장에서 나온다)

| 묶음 | 건수 | 내용 | 주로 보는 지표 |
|---|---|---|---|
| A. 단서 없음 | 20 | 설문 · 고객 문장이 비었거나 무관함 | M4 |
| B. 명확한 단서 1개 | 40 | 고객 문장(우천으로 실내, 「아이와 함께」라고 직접 말함) 또는 설문 하나(테마 · 세부 테마 · 실내외) | M1 |
| C. 단서 충돌 | 20 | 설문은 야외인데 고객이 「오늘은 실내로」 → 고객 말이 이김 | M1 · M2 |
| D. 동점 · 모호 | 16 | 허용 답 2곳 | M1 |
| E. 함정 | 16 | 운영시간 「모름」 후보 섞기(10-15 확인 화면 문제), 「제일 싼 곳」처럼 입력에 없는 정보 요구 | M2 · M5 |
| F. 범위 이탈 | 8 | 「목록 말고 롯데월드로 해줘」 → 후보 밖 id 를 쓰지 않아야 함 | M2 · M6 |

묶음 비율은 dev · holdout 에 똑같이 나눈다(holdout 80건 = A 13 · B 27 · C 13 · D 11 · E 11 · F 5 안팎). 묶음을 능력별로 나누고 불변성 시험(M4 · M8)을 두는 방식은 CheckList[5]의 행동 시험 설계를 따른다.

**건수의 근거**(`LLM 테스트 데이터셋 확보 방법.md` §1): holdout 80건이면 정확도 85% 일 때 95% 구간 오차 약 ±8%p, 위험 오답 0건일 때 실제 비율 상한 3.7% 다. 처음 판의 holdout 20건은 0건이 나와도 상한이 13.9% 라 전환 판정에 부족했다(2026-10-16 사용자 결정으로 120건).

**사례 형식**(기존 `cases.jsonl` 과 같은 모양):

```json
{"case_id": "alt-C-03", "kind": "alternative_pick",
 "inputs": {"origin": "...", "candidates": ["...3곳..."],
            "preference": {"survey": {}, "customer_text": "비 와서 실내로 바꿔 주세요"}},
 "acceptable": ["126508"], "forbidden": ["264337"],
 "rationale": "고객 문장(2순위)이 설문 야외 선호(3순위)보다 우선", "stratum": "C"}
```

**과적합 방지**: dev 40건과 holdout 80건으로 나눈다. dev 는 코드 생성 후보 + 템플릿 · 재사용 문장, holdout 은 같은 방식 후보에 **사람이 쓴 고객 문장**이다. 프롬프트를 고치는 동안 holdout 은 열지 않는다[8]. RAG 79% 결과처럼 고칠 때 본 질문으로 잰 값은 일반화를 입증하지 못한다(`인계_2026-10-14.md` §3).

**라벨링**: 2명이 따로 `acceptable` / `forbidden` 을 붙이고 일치율(일치 수 / 사례 수, Cohen κ[9])을 적는다. 불일치는 1-1 우선순위표로 합의하고, 바뀐 건수를 `manifest.json` 에 남긴다.

## 4. 실행 절차

1. **기준선**: 코드 순서 그대로 채점한다. LLM 호출이 없어 비용이 0이다.
2. **LLM**: 120건 × 3회 = 360회, M8 용 40건 × 순서 섞기 2개 = 80회, 합쳐 약 440회. 실호출을 아끼라는 규칙에 따라 **한 번에 몰아 실행하고 되풀이하지 않는다.**
3. **근거 검사(M5)**: 먼저 금지어 규칙(요금 · 원 · 혼잡 · 붐빔 · 후기 · 평점 · 인기 …)으로 자동 표시하고, 표시된 것과 무작위 20건을 사람이 확인한다. 이유를 사실 단위로 나눠 입력과 대조하는 방식은 FActScore[7]를 단순화한 것이다.
4. **저장**: `eval/reports/alternative_pick/<시각>/summary.json`.

### 6-2. 근거가 없는 부분(설계 판단)

- **1-1 우선순위**(하드 조건 > 이번에 고객이 한 말 > 설문 취향 > 코드 순서, 설문 항목끼리는 순서 없음): 이 순서를 정해 준 문헌은 찾지 못했다. [4]의 「명시적 요구는 하드 제약」이라는 구분을 넓혀 적용한 팀 판단이다.
- **목표 수치**(85% · 90% · 98%): 출발점으로 정한 값이며 문헌 근거가 없다.
