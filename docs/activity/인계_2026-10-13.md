## 3. RAG 에 대해 정리된 사실(결과서에 그대로 쓸 것)

- 활동 에이전트에서 RAG 는 **규정 문장 근거**에만 쓰인다 — 취소 확인 · 변경 제안의 근거(`read.policy`)와 일정 질문(규정 질문)에서 규정 문서의 고객용 문장을 출처와 함께 인용. **성립 점검은 RAG 를 쓰지 않는다**(DB + 규칙).
- 벡터 DB = 별도 서비스가 아니라 **PostgreSQL pgvector**(`knowledge_chunks`, HNSW 코사인, 1,536차원 `embedding` + 1,024차원 `embedding_1024`).
- 임베딩 모델 `text-embedding-3-small`(1,536). Ollama(bge-m3)는 이 환경에 없어 쓰지 않는다. RAG 경로에 생성 모델은 없다(문장을 짓지 않고 인용).
- 문서는 **우리가 작성한 서비스 운영 기준**이다(실제 업체 약관 아님). 법령 · 고시(소비자분쟁해결기준 등) 원문은 조회하지 않아 넣지 않았다 — 한계로 명시. 장소별 취소 조건 수치는 RAG 가 아니라 구조화 표 `cancellation_terms`(예약 → 공급자 → 종류 순)이고 현재 데이터 3행은 전부 시연용(`seed:mock`).
- 그래프 DB: 코어에 `GraphStore`(SQL 재귀 CTE 어댑터)가 있으나 활동 에이전트는 쓰지 않는다.
- 현재 구현에는 유사도 **임계치가 없다**(top-k 만). 시험에서 범위 안 최저 0.43 · 범위 밖 최고 0.33 이라 0.4 안팎이면 가를 수 있다 — 「제안 임계치」로만 쓴다.
- 데이터가 작다(활동 scope 10문서 · 82청크)는 점을 숨기지 않는다. 취지는 「구조를 설계하고 임시 데이터셋으로 동작을 보인다」이고, 실제 장소별 규정 문서는 서비스 확장 과제로 쓴다.
