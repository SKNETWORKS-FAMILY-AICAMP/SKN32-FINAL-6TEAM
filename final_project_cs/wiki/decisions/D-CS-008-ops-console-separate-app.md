# D-CS-008 운영자 콘솔을 별도 앱으로 뗀다 (1단계)

`[결정 2026-09-29 사용자]` 「외부에서 절대 접근 못 하게, 가능한 물리적으로 분리」. Codex 와 1회차에 일치했다(ui 세션 전달).

## 무엇이 문제였나

운영 화면(로그인·Case·승인·위임·바깥함·VOC·관리)과 관리 API(`/admin/limits`·`/admin/reload`), 시나리오 모드가
**고객 API 앱(8042)** 에 같이 붙어 있었다. 고객이 닿는 포트로 운영 화면이 열려 있었고, 막는 것은 로그인 하나였다.
운영 화면은 고객 API 를 **같은 프로세스 안에서**(`ASGITransport(app=request.app)`) 서버 비밀키로 scope 키를 만들어 불렀다.

## 정한 것 (1단계 — 같은 기계의 다른 프로세스)

| | |
|---|---|
| 운영 앱 | `app/ops_entrypoint.py` — `python -m app.ops_entrypoint`, 기본 **127.0.0.1:8070**(`ACOP_OPS_PORT`). 지금 쓰는 번호 3100·3102·3200·3300·8041·8042·8044·8060 과 겹치지 않는다 |
| 이 기계 안에서만 | ① 127.0.0.1·::1·localhost 가 아닌 주소로 띄우기를 **거부** ② 루프백이 아닌 곳에서 온 요청은 **403**(누가 uvicorn 으로 0.0.0.0 에 띄워도). 원격 운영은 SSH 터널 |
| 고객 API 앱 | 운영 경로·관리 API·시나리오가 **0개(404)**. `/admin/reload` 는 **설정 관리용 빌드**(`app.entrypoint:app`)에만 — 반영은 그 프로세스 안에서만 뜻이 있어 운영 앱으로 옮길 수 없다 |
| 운영 → 고객 API | **실제 HTTP**(`ACOP_OPS_API_BASE_URL`, 기본 `http://127.0.0.1:8042`). scope 키는 운영 앱 설정 `ACOP_OPS_API_KEYS` 에만 — **스스로 만들지 않는다**. 시간 초과는 「결과 모름」으로 적고 스스로 다시 부르지 않는다(15초, `security.ops_api_timeout_seconds`). 승인은 고객 API 가 멱등 키로 묶어 두 번 눌러도 한 건 |
| DB 직접 읽기 | 운영 화면의 조회(표 7개)는 **읽기 전용 연결**(`ACOP_OPS_READ_DATABASE_URL` — 계정 만드는 법 `scripts/sql/ops_readonly_role.sql`, 비우면 본 주소). 다음 단계는 API 로 옮기기 |
| 웹 제한값 운영 API | `/admin/limits*` 는 운영 앱. 값은 DB(`runtime_limits`)라 고객 앱이 30초 안에 읽는다 |
| 시나리오 모드 | 스위치(`/ui/scenario`)·시연 화면(`/tripilot`)·입구(`/scenario/*`)가 한 판을 **프로세스 메모리**에 든다 — 셋 다 운영 앱으로 **함께** 옮겼다(나누면 깨진다). 시나리오 모드는 데모 모드다(사용자 결정 2026-09-28) |
| 폼 위조 방지 | 운영 화면의 모든 POST 폼에 확인값(`csrf`) — 로그인 뒤는 로그인 쿠키 서명값, 로그인 폼은 이중 제출 쿠키. 전에는 `SameSite` 쿠키에만 기댔다 |

## 아직 아닌 것 — 2단계 전에는 「물리 분리 완료」라고 쓰지 않는다

- **2단계(배포 때)**: 다른 기계(최소 별도 컨테이너·네트워크) 사설망 + VPN·SSH 터널만.
- 운영 화면의 DB 직접 읽기 → API.
- 개발 콘솔(`final_project_ui`, 8060)의 「반영」 버튼은 대상이 **관리용 빌드**일 때만 된다(고객 릴리즈 빌드에는 `/admin/reload` 가 없다).
- `/introspection`(scope `ops:introspect`, 읽기)은 고객 앱에 남아 있다. `[결정 2026-09-29 사용자]` **계획만 잡고 대기** — 운영 앱이 준비되면 옮긴다(계획: `final_project_ui/README.md` 「대기 중인 일」). 옮길 때 서버 쪽 할 일: ① 고객용 빌드에서 `/introspection` 을 빼고 운영 앱에 둔다 ② `/admin/reload` 도 **같은 주소 뿌리**에서 열리게 맞춘다 — 개발 콘솔은 반영 주소를 조립 정보 주소에서 만든다. 둘이 다른 프로세스를 가리키면 **남의 프로세스를 반영시키는 사고**가 난다.
- 1단계 확인(ui 세션, 2026-09-29): 8042 에서 운영·관리·시나리오 9개 경로 404 · 8070 은 루프백만(네트워크 주소로는 연결 안 됨) · 사용자 웹 실서버 종단 2/2 통과. 개발 콘솔의 반영 404 안내는 「고객용 빌드면 설정 관리용 빌드를 가리켜라」로 고쳤다.

## 다음 순서 — Codex 와 1회차 합의(2026-09-29, 「코덱스의논1」 · gpt-6-luna)

실무 기준(OWASP Database Security · Authorization — 필요한 표·권한만, 결정 로그로 사용자 귀속)으로 **운영 앱의 DB 직접 쓰기를 먼저 없애고**
그 뒤 읽기 전용 계정을 적용한다. 그보다 앞서 **운영자 신원 위조**를 막는다 — 고객 API 는 scope 키만 보고 승인자 이름을 요청 본문
(`approver_id`)에서 그대로 받는다(`cases.py:72·201·238·261·263`). 권고 순서:
1. 운영 앱이 로그인 운영자를 **서명한 짧은 증명**으로 보내고 고객 API 가 확인해 승인자·처리자를 거기서 꺼낸다
2. 시나리오 데모를 운영 앱에서 별도 데모 앱(127.0.0.1)으로 뗀다
3. 제한값 저장은 그 3개 표에만 쓰는 좁은 DB 계정 — ★Codex 는 고객 API 로 옮기자 했으나 사용자 지시(관리 API 는 고객 앱에서 뺀다)와 부딪혀 기각
4. 운영 화면 조회에 읽기 전용 계정(지금 보류)
5. 2단계: 앞단 인증 · 조회를 API 로

## 시험

- `tests/e2e/test_ops_app_two_processes.py`(3): 고객 API 앱을 **다른 프로세스로 띄우고** 운영 앱이 HTTP 로 승인 · 위임 조회 · 폼 확인값 없으면 403·기록 0 · 키 없으면 보내지 않음.
