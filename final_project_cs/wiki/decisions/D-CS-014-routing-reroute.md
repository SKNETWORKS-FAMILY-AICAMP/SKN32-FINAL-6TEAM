# D-CS-014 — 라우팅이 어긋나면 **한 번 더 고른다** (사람에게 넘기지 않는다)

## 승인된 자동 처리·결함 기록 원칙 — 2026-10-12

상주 상담원이 고객 문제를 대신 수정하는 처리 경로는 두지 않습니다. 자동 재조회·대체 자료·재분류를 거친 뒤, 고객이 고칠 수 있는 장소명·주소·날짜만 보완 입력을 요청합니다. 검증된 후보가 있으면 추천 이유와 함께 최대 3개를 제시하고, 후보가 없으면 직접 입력을 받습니다. 외부 자료 장애를 고객 입력 탓으로 돌리지 않습니다.

장소 미매칭·처리 오류·고객 건의는 구분해 저장합니다. 오류 발생 고유 ID·배포 판·정책 판·재현 조건·동일 결함 묶음·영향 고객 연결·발생 건수·해결 판본을 개발자·QA가 사후 조회합니다. 고객 건의·입력은 검증 전 공용 장소 정보에 자동 반영하지 않습니다. 수집량이 커지면 상세 기록은 집계·표본으로 줄일 수 있지만 발생 건수·영향 고객 연결은 보존합니다. 진단 DB 장애에는 마스킹한 영속 대기 파일·용량 상한·유실 지표를 사용하고, 둘 다 실패하면 수집 저하를 드러냅니다.

고객 화면은 완료·입력 필요·변경 보류·처리 불가로 안내합니다. 내부 `escalated`를 상담원 대기라고 번역하지 않습니다. 처리 불가 상태를 감시·개인 AI 경로에서도 안내하고 같은 여행의 상태 전환별 중복 통지를 막습니다. 계정·설정·배포 관리 권한과 고객 여행 직접 수정 권한을 구분합니다. 이 절은 승인된 계약이며 전체 수집·복구·고객 안내 구현은 인수 증거 확보 전까지 미검증입니다.


`[2026-10-06 사용자 지시]` 「사람에게는 지금 절대 넘길 수 없는 구조라서 LLM 도입하는 게 맞다고 본다」

## 무엇이 문제였나

분류가 붙인 대상 종류(`issue_code` 접두)를 받는 팀이 없으면 Case 는 `ROUTING_FAILED` → `escalated`
로 끝났다. 「모르는 것을 아무 팀에나 보내지 않는다」는 맞는 원칙이지만, **이 제품에는 사람 운영자
큐가 없다** — 고객은 알림과 여행계획서 링크만 본다. 그래서 그 Case 는 아무도 받지 않는다.

더 나쁜 것은 **고객이 그 사실조차 모른다**는 점이다. 길에 따라 다르다.

| 들어온 길 | escalated 가 되면 |
|---|---|
| 고객이 웹 · 계획서에서 말을 걸었다 | **답이 바로 화면에 나간다** — 「말씀을 제대로 알아듣지 못해 일정은 바꾸지 않았어요」 + 할 수 있는 일 예시(`conversation/trip_replies.not_understood_reply`). 사람 대기 약속은 하지 않는다(2026-09-28) |
| 감시 루프 · 에이전트 API 가 Case 를 열었다 | **아무 말도 안 나간다** — `ROUTING_FAILED` 는 알림(바깥함)을 만들지 않는다. 운영 화면에만 남는다 |

## 결정

**받는 팀이 없으면 한 번 더 고른다.** 다만 지어내지 않는다.

1. 고를 수 있는 값은 **지금 등록된 팀이 실제로 받는 종류**뿐이다 — 목록은 코어가 넘긴다(어휘를
   재배분기에 적어 두지 않는다. 선언이 바뀌면 목록도 같이 바뀐다).
2. 목록 밖을 내면 **한 번만** 다시 묻는다(`feedback.classify` 와 같은 규칙). 그래도 밖이면 포기.
3. **돌려받은 답도 그대로 믿지 않는다** — 그 종류로 `Registry.resolve` 에 **다시 묻고**, 거기서도
   팀이 안 나오면 포기한다. 모델이 그럴듯한 이름을 내도 통과하지 못한다.
4. **Case 당 한 번만.** 되풀이하면 모르는 Case 하나가 모델 호출을 무한히 쓴다.
5. 포기하면 **종전 그대로** `escalated` 다. 이 결정은 그 길을 없애지 않고 **그리로 가는 수를 줄인다.**
6. 모델이 죽어도 Case 는 종전대로 간다(코어가 감싼다).

## 어디에 있나

| 층 | 무엇 | 파일 |
|---|---|---|
| 코어 | 언제 부르고 · 결과를 어떻게 믿고 · 어느 상태로 보내나 | [controller.py `_reroute_once`](../../app/application/controller.py) |
| 도메인 | 어휘와 프롬프트만 | [core_hooks/reroute.py](../../app/domains/travel_ops/components/core_hooks/reroute.py) |
| 조립 | 꽂는 자리 · 스위치 | [composition.py `build_reroute`](../../app/composition.py) |
| 스위치 | `travel.routing.reroute_enabled`(기본 켬 · 호출 때 읽는다) | `config/guardrails.yaml` |

Controller 는 어느 팀이 무엇을 받는지 **모른다** — 기존 「대조 어휘는 주입받는다」와 같은 경계다.
성공하면 `ROUTED` 이벤트에 `rerouted: {from, to, intent, why, by}` 로 **무엇을 무엇으로 왜 바꿨는지**
남긴다.

## 비용

모델 호출은 **라우팅이 실패한 Case 에만, Case 당 한 번**(목록 밖 답이면 되묻기 1회 포함 최대 2회).
평소 경로에는 호출이 늘지 않는다.

## 아직 안 한 것 (정하실 것)

1. **재배분도 실패하면 고객에게 알릴지.** 지금은 여전히 조용하다 — 「이건 제가 처리하지 못했어요」를
   보낼지 정해야 한다.
2. **멈춘 Case 를 되잡는 장치.** `escalated` 로 선 Case 를 다시 시도하는 sweeper 가 없다
   (`presentation/api/cases.py` 주석이 `routing` 쪽 같은 구멍을 이미 적어 뒀다).
3. **실제 모델로 종단 확인.** 이 PC 는 OpenAI 크레딧이 없고 로컬 Ollama 도 떠 있지 않아 못 했다.
   x600 서버의 cs 프로젝트 서버에 배포한 뒤 확인한다.

## 2026-10-07 정정 — 재배분이 성공한 Case 가 뒤에서 죽던 결함

`[결함 · 내가 만든 것]` 재배분(`_reroute_once`)으로 라우팅이 **성공**하면 Case 는 새 팀으로 `ROUTED` 되는데, 뒤의 `_task` 가 기능을 정하려고 `_capability(case)` 를 다시 불러 **원래 종류**(`other` 등)로 등록부에 물었다. 그 종류는 받는 팀이 없으니 `RegistryError` 가 나서 **재배분이 성공한 Case 가 곧바로 터졌다**(종전에는 `escalated` 로 끝났다). 시험 `tests/scenario/test_case_question.py::test_the_two_reports_stay_what_they_were` 가 이것을 잡았다.
- 고침: ①`run_case` 가 재배분으로 정한 기능을 `_task(capability=…)` 에 그대로 넘긴다 ②`_capability` 는 원래 종류로 못 찾으면 **이미 정해진 담당 팀**(`owner_team_id`)으로 찾는다(재개 때도 같다). 담당이 없으면 종전대로 터진다 — 조용히 아무 팀에나 보내지 않는다.
- 시험: `tests/unit/travel/test_routing_reroute.py` 에 재현 시험 추가, 시나리오 103 · 컨트롤러 통합과 코어 단위 272 통과.
- 왜 늦게 잡혔나: 위 「시나리오 847 통과」는 그날 로컬에 모델이 없어(OpenAI 크레딧 소진 · Ollama 꺼짐) 재배분이 한 번도 팀을 **고르지 못해** 이 길을 안 탔기 때문이다 — 모델이 답하는 환경에서만 드러나는 결함이었다. 이 결함은 환경 의존이라 **모델이 있는 환경(x600 서버)에서는 처음부터 터졌을 수 있다.** **컨트롤러를 건드리면 모델이 있는 환경에서도 시나리오 시험을 돌린다.**
- 영향: 재배분이 켜진 실행(`travel.routing.reroute_enabled`)에서 받는 팀이 없는 Case 가 모델이 고른 팀으로 다시 라우팅되는 경우 — 그 뒤 실행이 터졌다. 반영 전까지 x600 서버에는 이 결함이 있다.
