# D-CS-021 장소 이름 찾기 순서

`[결정 2026-10-22 사용자 지시 · Codex 1회차 합의]` 「우리 검색하는 순서 규칙 있잖아 — db 검색 → 별칭 → 카카오 이 순서 아니었어? 이거 전체 적용되게 해놔야지」 ·
「wiki 에 다 관련된 항목에 다 반영시켜서 다시는 이런 문제 없도록」.

계기는 x600 서버였다. 확인 화면에서 「경복궁」 줄에 `mmca 서울`을 검색하자 우리 목록의 「국립현대미술관 서울」 대신 카카오 결과만 나왔다.
그 이름은 활동 팀 별칭 자료(`MMCA 서울` → 1934593)에 있었다. 하지만 그 별칭을 읽는 곳은 활동 팀 이름 찾기 하나뿐이었다(아래 「경위」).

## 순서 (모든 이름 찾기가 같다)

| 단계 | 무엇 | 어디 |
|---|---|---|
| ① | **그 고객이 고친 별칭** — 확인 화면에서 고객이 고친 말(그 고객에게만, 038). 기본값 5개(`SEED_ALIASES`)도 이 자리에 있다 | `pipeline.load_aliases` → `places.resolve` |
| ② | 대표 장소 정답표 · 숙소 말 — 찾기 **전에** 종류와 가리키는 곳을 정한다 | `intake/landmarks.py` |
| ③ | **우리 자료 정확 일치** — 우리 장소 표(`places`), 확인 화면 검색은 관광공사 목록(`place_catalog`)에 그 이름이 있는 곳 | `resolve` · `candidates._db_places_by_name` |
| ④ | **공용 별칭** — 활동 팀 별칭(시드 CSV `instances/activity/data_processing/place_aliases.csv` + DB 표 `activity.ac_place_alias`, 306). **한 곳만 가리킬 때만** 쓴다. 사람이 확인한 별칭이라 「확인 필요」를 붙이지 않는다 | `team_hooks/place_aliases.py` → `place_by_name.alias_target` |
| ⑤ | 자모 오타 | `resolve` · (활동 팀 찾기는 `fuzzy=True` 일 때만) |
| ⑥ | 관광공사(서울) · 요식 원장 — 식사면 원장 먼저 | `resolve` |
| ⑦ | 카카오 — **원문 전체로만**, 찾은 이름은 관광공사로 다시 확인 | `resolve` · `candidates._kakao_places` |
| ⑧ | 유료(구글 Places 등) — 따로 정한 길에서만 | 결정 D-025 · D-CS-010 |

★확인 화면 검색은 **목록**을 돌려준다. 그래서 ③에서 이름이 정확히 같은 곳이 없으면 ④의 곳을 목록 **맨 앞**(정확 일치와 같은 자리, `match: alias`)에 넣는다.
  같은 곳의 카카오 결과는 겹친 결과 지우기에서 빠진다. 결과의 출처가 `tour_api`(우리 목록)로 보인다.
★④는 바깥을 부르지 않는다. 시드 파일과 DB(활동 원장 · 별칭 표)만 읽는다. 별칭에는 카카오 값을 넣지 않는다(카카오 운영정책 제5조, D-027).
★DB 연결이 없는 길(채팅 지역 기준점의 일부)은 시드 파일만 본다. 계획 읽기는 모델을 기다리는 동안 연결을 잡지 않는다. 그래서 DB 표를 1분 기억한 사본으로 본다(`SNAPSHOT_TTL_S`).
  운영 중에 더한 별칭은 1분 안에 계획 읽기에도 쓰인다.

## 이 순서 밖 (이름 찾기가 아니다)

| 무엇 | 왜 밖인가 |
|---|---|
| 「숙소」 · 「음식점」 · 역(SW8)처럼 **종류 · 근처**를 찾는 카카오 검색 | 이름이 아니라 종류를 찾는다 |
| 채팅의 **지역 기준점**(「홍대」 → 역) | 자체 줄임말 표(`read_tools._LANDMARK_ALIASES`)가 따로 있다. 동네 이름이지 방문할 장소가 아니다 |
| 식당 이름 찾기(요식 에이전트 도구) | 요식 원장이 먼저다. 활동 별칭 자료의 대상이 아니다 |
| 숙소 이름(AD5) | 숙소 팀 길이다. 활동 별칭 자료의 대상이 아니다 |

## 다시 어긋나지 않게

- **구조 시험** `tests/architecture/test_place_name_lookup_order.py`: 카카오를 부르는 파일은 모두 표에 분류돼 있어야 한다. 분류는 이름 찾기 · 이름 찾기 뒤 · 종류 찾기 셋이다.
  이름 찾기 파일에는 별칭 단계가 있어야 한다. **새 파일이 카카오를 부르기 시작하면 실패한다.** 그때는 이름 찾기인지 먼저 정하고 표에 적는다.
- **동작 시험** `tests/unit/travel/test_place_name_lookup_order.py`: 계획 읽기 · 확인 화면 검색에서 「MMCA 서울」 · 「Gyeongbokgung」이 카카오 전에 별칭으로 찾힌다. 정확 일치가 별칭보다 먼저인지, 고객 별칭이 공용 별칭보다 먼저인지도 본다.
- **조립 선언**: 활동 팀 `hooks` 에 `place_aliases`(`config/project.yaml`). 빠지면 조립 검사가 실패한다.
- 보고 규칙: 「배포됨」을 「적용됨」으로 쓰지 않는다. **어느 고객 경로에 연결됐는지**를 같이 적는다(루트 `CLAUDE.md` · `AGENTS.md` 같은 날 절).

## 경위 — 왜 「적용 완료」인데 안 됐나

| 길 | 전에 별칭을 봤나 | 이번에 |
|---|---|---|
| 확인 화면 장소 검색(`candidates.search`) | **안 봤다** — 우리 목록은 이름 포함 검색만 하고 바로 카카오로 갔다 | ④ 추가 |
| 계획 읽기 · 이름 고치기 · 채팅 고치기(`places.resolve`) | 고객 별칭(①)만 봤다. **활동 팀 별칭은 안 봤다** | ④ 추가(연결 · 여는 함수 · 시드) |
| 활동 팀 이름 찾기(`read.place_lookup`) | 봤다(원장 → 별칭 → 카카오). 하지만 **고객 경로에서 부르는 곳이 없다**(`read_tools.py` 주석) | 그대로 |
| 활동 팀 같은 장소 판정(`place_identity` · `replacement`) | 봤다 | 그대로 |

10-22 오전 기록은 「x600 서버에 배포됨 · DB 표 있음」까지만 확인했다. 같은 기록에 「실제 고객 경로 확인: 안 했음」이라고도 적었다.
그런데 이 「배포 완료」가 「적용 완료」로 전해졌다. 문서끼리도 순서가 엇갈렸다. D-025는 「정확 → 별칭」, web-intakes는 「별칭 → 우리 장소 표」였다. 이 결정이 둘을 위 표 하나로 맞춘다.
고객 별칭은 ③보다 먼저이고, 공용 별칭은 ③ 다음이다.

## Codex 검토 (사용자 「내 말이 틀리거나 부족하면 코덱스랑 검토」)

판정 B — **방향은 맞지만 부족하다**(Claude · Codex 1회차 일치, Codex 본계정 gpt-6-sol).
- 맞는 점: 우리 자료와 별칭을 카카오보다 먼저 본다.
- 빠진 점: 자모 오타 · 관광공사 · 요식 원장 · 유료 단계, 그리고 「고객 별칭」과 「공용 별칭」이 다른 자료라는 점.
- 틀린 점: 「전체에 적용돼 있다」는 사실이 아니었다(위 경위). 고객 별칭은 DB보다 먼저다.
- Claude 는 1회차에 「정확 일치 → 별칭」을 권했다. Codex 가 짚은 위험을 받아들여 고객 별칭을 맨 앞에 두었다. 고객이 고친 이름이 같은 글자의 다른 장소에 가려질 수 있다.
검토자는 기계(Codex)다. 사람 검토가 아니다.
