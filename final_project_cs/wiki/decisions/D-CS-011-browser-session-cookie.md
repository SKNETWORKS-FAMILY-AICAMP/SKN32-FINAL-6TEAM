# D-CS-011 브라우저 세션은 HttpOnly 쿠키, 로그인 안 한 게스트는 마지막 사용 7일 뒤 삭제

`[결정 2026-10-04 사용자]` 「로그인하면 어차피 다시 인증할 수 있으니 토큰을 오래 들고 있을 필요가 없다 · 키는 로그인 안 했으니 사용자도 날아가는 걸 받아들인다 · 쿠키보다 나은 방식이 오늘 기준으로 없으면 쿠키로 개발 · 로그인 안 한 세션은 삭제하되 관리자 화면에서 수치를 조절 · 초기값은 조사한 최적값과 공식으로」. 나머지는 이 문서의 제한대로 한다(사용자 「나머지는 니 제한대로」).
계약은 [rest-endpoints.md 「브라우저 세션 쿠키」](../external/rest-endpoints.md). 조사는 코덱스(웹 검색) · 검토 에이전트 둘이 따로 했다.

## 무엇이 바뀌나

| | 전 | 지금 |
|---|---|---|
| 웹의 로그인 상태 | 브라우저 저장소의 긴 키(`X-User-Key`) — 페이지의 모든 스크립트가 읽는다 | **서버가 내려주는 HttpOnly 쿠키** — 스크립트가 못 읽는다 |
| 키를 사용자에게 | 발급 때 한 번 보여 주며 「따로 보관하세요」 | 보여 주지 않는다. 키는 **에이전트(MCP)가 쓸 때만**, 로그인 사용자가 만들 때 한 번 보여 준다(2단계) |
| 키를 잃으면 | 키를 다시 넣어 잇는다 | 게스트는 **복구 없음**(받아들인다). 회원은 구글 로그인으로 다시 연다 |
| 로그인 안 한 사용자의 데이터 | 안 지운다(`idle_key_cleanup_enabled` 꺼짐 — 2026-09-29 「키는 그 사용자를 알아보는 유일한 수단」) | **마지막 사용 뒤 `web.guest_idle_hours`(기본 168시간 = 7일) 지나면 지운다.** 관리 콘솔에서 조절. 위 09-29 결정을 이것이 대신한다 |
| 게스트 한도 | 여행 개수 제한 없음 | 여행 **1개** · 감시 불가 · 계획 기간 상한(아래) |

## 1. 쿠키 — 오늘(2026-10-04) 기준 더 나은 방식은 없다

| 후보 | 상태(조사) | 판단 |
|---|---|---|
| **서버 저장형 불투명 세션 + HttpOnly 쿠키** | OWASP · RFC 10017(BCP, 2026-08)이 브라우저 앱의 최우선 권고(BFF 형태) | **채택** |
| DBSC(기기에 묶는 세션 쿠키) | Chrome 146 **Windows 만** 정식(2026-04-10), macOS 147 점진. Safari 미발표 · Firefox 표준 입장 부정적. W3C 초안 단계. 훔친 쿠키를 **다른 기기에서** 쓰는 것을 막는다(갱신 창 약 10분 제외) | 나중에 **얹는 보강** — 서버 세션 행에 공개키·챌린지 열을 더하면 클라이언트 변경 없이 얹힌다. 지금은 필수가 아니다 |
| DPoP · sender-constrained 토큰 | XSS 에 뚫린 앱에서는 공격자가 자기 키로 새 토큰을 받아 무력(RFC 10017) | 쿠키 세션에는 해당 없음 |
| 패스키 | 로그인 수단이지 세션 보호가 아니다 | 구글 로그인이 있어 지금 불필요 |
| Token Binding | Chrome 에서 제거됨 | 불가 |

- claude.ai 웹은 `sessionKey`(1개월) · `sessionKeyV2`(1시간) 쿠키, ChatGPT 웹은 `next-auth.session-token` 쿠키를 인증 쿠키로 쓴다(공식 쿠키 안내). **둘이 localStorage 에 긴 키를 두는 자료는 못 찾았다.** CLI(Codex · Claude Code)는 브라우저 로그인 뒤 OS 자격 저장소/`~/.codex/auth.json`·`~/.claude/.credentials.json` 에 OAuth 토큰을 두고 자동 갱신한다. `[미확보]` 쿠키의 정확한 속성(HttpOnly · SameSite)은 공식 자료에 없었다.
- **왜 더 안전한가**:

| 공격 | 저장소 키(전) | HttpOnly 쿠키 + 서버 세션(지금) |
|---|---|---|
| 악성 스크립트(XSS · 확장 · 서드파티 SDK)가 자격을 **읽어 가기** | 읽힌다 — 영구 탈취 | **못 읽는다** |
| 악성 스크립트가 사용자 **대신 요청 보내기**(세션 라이딩) | 가능 | 가능 — 이건 못 막는다 |
| 훔친 값을 **다른 기기**에서 쓰기 | 만료·폐기까지 가능 | 만료·거둠까지 가능(DBSC 가 막는 부분) |
| CSRF(다른 사이트가 사용자의 브라우저로 요청) | 해당 없음(자동으로 안 붙는다) | **방어 필요** — `SameSite=Lax` + `Origin` 검사 + 세션에 묶인 토큰 헤더 |
| 서버 DB 유출 | 해시만 저장 | 해시만 저장 |

- 쿠키가 되면서 생기는 일: CSRF 방어 · 개발 PC 의 포트 다른 출처(`127.0.0.1:3100 ↔ :8042` — 출처는 다르고 **사이트는 같다**)를 위한 CORS 자격 허용 · 에이전트 키 헤더와의 공존(**둘이 같이 오면 거부**).
- 수명 기본: 회원(소셜 계정 연결) 유휴 7일 · 절대 30일, 게스트는 아래 7일. OWASP 의 짧은 유휴(15~30분)는 고위험 서비스 기준이고 이 서비스는 구글로 한 번에 다시 로그인되므로 길게 둔다 — `[추정]`, 관리 콘솔에서 조절.

## 2. 게스트 보존 시간 — 초기값 7일(168시간), 마지막 사용 기준

**공식.** 보존 비용은 시간에 비례(`c_h·T`), 손실 비용은 「T 안에 못 돌아온 방문자 비율 × 손실」(`c_l·(1−F(T))`) — 총비용 `C(T)=c_h·T + c_l·(1−F(T))`. 최적은 `f(T*)=ρ`, `ρ=c_h/c_l`(「하루 더 둬서 건지는 재방문 비율이 ρ 보다 크면 연장」). 재방문 간격이 멱법칙 꼬리(하한 `t0`, 지수 `α`)면 `1−F(T)=(T/t0)^−(α−1)` → **`T* = t0·[(α−1)/(ρ·t0)]^(1/α)`**.

| 구분 | 값 |
|---|---|
| 자료에서 읽음 | `α≈1.2±0.1`(뉴스 포털 사용자별 연속 방문 간격 1개월 — Dezsö 2006; 검색 클릭·메일·도서대출은 `α≈1` — Vázquez 2006), `t0=30분`(세션 경계 — Catledge & Pitkow 25.5분에서 유래) |
| 우리가 모름(가정) | `ρ`(정책값 — **근거 없음**), 여행 게스트에도 `α=1.2` · `t0=30분`이 맞는지(위 `α` 는 세션 안 클릭까지 섞였고 관측이 1개월로 잘렸다), 아예 안 돌아오는 비율 |

| T | 재방문 포착률 `F(T)`(`α` 1.1~1.3 범위) | 하루 더 둘 때 건지는 비율 `f(T)` | 이 T 가 최적이 되는 `ρ` |
|---|---|---|---|
| 24시간 | **54%**(32~69) | 9.2%/일 | 9.2%/일 |
| **7일** | **69%**(44~83) | 0.89%/일 | 0.89%/일 |
| 14일 | 73%(48~86) | 0.39%/일 | 0.39%/일 |
| 30일 | 77%(52~89) | 0.16%/일 | 0.16%/일 |

(계산한 값 — 이 세션에서 위 공식으로 직접 다시 계산해 일치. `α`=1.2, `t0`=30분.)
- `ρ=1%/일`이면 `T*=6.4일`, `0.5%`면 11.3일, `0.2%`면 24.3일. **`T*` 는 `α` 에 둔감**(1.1~1.3 → 9.5~11.3일)하고 **`ρ` 에 민감**하다.
- **24시간이 최적이려면 `ρ=9.2%/일`** — 「하루 저장하는 비용이 돌아온 사람의 계획을 잃는 손실의 9%」라는 뜻인데, 게스트 여행 계획은 이메일·이름 없는 몇 KB 라 보존 비용이 그렇게 크지 않다. 하루는 재방문의 절반가량(54%)만 살린다.
- **초기값 7일**: ①`ρ≈1%/일`에서 `T*≈6.4일`을 올림 ②포착률 곡선이 꺾이는 자리 — 1일→7일은 +15%p, 7일→14일은 +4%p, 14일→30일은 +4%p ③Safari 의 7일 저장소 삭제 규칙과 같은 크기(서버 데이터 TTL 은 아니다) ④개인정보 최소 보존(GDPR 5조 1항 e · 한국 개인정보 보호법 2023-09 개정으로 일률 기간 없음 — 목적에 필요한 기간) 안에서 짧은 쪽.
- 다른 조사와의 차이: 코덱스는 **24시간**(CHI 2007 「페이지 재방문」 25명 연구에서 하루 누적 84.6% — **페이지 단위 · 오래된 표본**이라 여행 서비스 복귀율로 보장하지 못한다고 스스로 밝혔고, 포착률 목표 80%는 가정), 검토 에이전트는 **14일**(`T*=11.3일`에서 복구 수단이 없는 비대칭을 반영해 올림). 셋 다 **여행 게스트의 실측이 없다** — 어느 값이든 초기값일 뿐이다.
- 확신도: 「하루는 짧고 꼬리가 무겁다」는 방향은 중간~높음, **7일이라는 숫자는 낮음**(`ρ` 가 정책값이고 `α` 는 뉴스 포털 자료). 사용자의 「하루」로 바꾸려면 관리 콘솔에서 24 로 둔다(범위 1~8760 시간).
- `[못 찾음]` 여행 계획 도메인의 재방문 간격 분포 · 와이블/로그정규 모수 사례 · 여행 앱 리텐션의 원본 수치 · 「일정 시작일까지 자동 삭제를 유예한다」고 명시한 서비스 정책(Airbnb 는 예정된 여행이 있으면 **요청한 계정 삭제**를 보류할 뿐, Google 은 활성 구독이 있으면 비활성 삭제에서 뺀다).
- **미래 일정 예외**(내 제한): 게스트도 일정이 남아 있으면 **마지막 사용 `T` 뒤가 아니라 `일정 종료일 + 3일`까지** 지우지 않는다(몇 주 전에 계획하고 당일에 여는 여행 패턴 — Expedia 는 예약 전 약 45일 조사). 단 **마지막 사용 + 180일**이 상한이다(날짜를 빌미로 영구 보존 금지 — 상한은 지금이 아니라 마지막 사용 기준이라 움직이지 않는다). 설정 `web_guard.guest.trip_grace_days` · `trip_keep_max_days`(가드레일 값 — 관리 콘솔에서 조절하는 것은 `web.guest_idle_hours` · `web.guest_cleanup_enabled` 와 세션 수명 둘이다).
- **「마지막 사용」** = 세션 또는 키로 인증된 요청. 계획서 링크 열람 · 자동 감시 · 외부 호출은 사용이 아니다(링크를 열람한 것이 소유자의 보존을 늘리면 안 된다).
- **관리자가 실측으로 맞추는 법**(`[2단계]`): 요청마다 `now − last_seen` 이 30분을 넘으면 구간(1시간 미만 · 1~6시간 · 6~24시간 · 1~3일 · 3~7일 · 7~14일 · 14~30일 · 30일 이상)에 개수만 센다 → `α̂ = 1 + n / Σ ln(g_i/t0)`(살아 있는 게스트는 우측 중도절단). 손실 신호 = 삭제한 세션 해시를 `1.5T` 동안만 두고 그 쿠키로 다시 오면 「삭제 뒤 복귀」로 센다 · 삭제된 여행의 링크 조회(404). 월 1회 `f̂(T)` 를 구해 `2ρ` 보다 크면 `T×1.25`, `ρ/2` 보다 작으면 `T÷1.25`(범위 3~90일, 에이전트 제안). **이 세션에서는 만들지 않았다** — [open-items](../delivery/open-items.md) 에 올린다.

## 3. 나머지 제한(사용자 「니 제한대로」)

- **게스트 여행 1개 · 동시 생성까지 막는다.** 지금의 「여행 만들기 하루 1건」은 사용자(고객) 단위라 새 게스트를 만들면 우회된다 — 한도와 별개로 「게스트 총 1개」를 행 잠금으로 막는다.
- **게스트는 감시 불가** — 화면 버튼만이 아니라 **감시 대상을 고르는 조회와 실행 직전**에도 막는다. 비용 경로는 감시 말고도 모델 예열 · 대안 조회 · 지도 로드가 있어 서비스 전체 예산은 그대로 둔다.
- **게스트 계획 기간 상한**: 여행 시작일은 오늘부터 365일 이내, 길이는 상품 기준 7일 이내(`[추정]` — 상품은 서울 · 최대 7일 · 4인).
- **삭제 전 유예(소프트 삭제 7일) 없음** — 복구 수단이 없으니 유예가 아무에게도 도움이 안 된다(코덱스 지적). 만료 즉시 접근이 막히고, 정리 작업이 데이터를 지운다.
- **에이전트 키 분리(2단계)**: 로그인 사용자만 · 이름 붙여 만들기 · 만들 때 한 번만 표시 · 90일 만료 · 개별 폐기 · 서버엔 해시만 · **여행 작업 권한만**(계정 연동 · 해제 · 새 키 생성은 브라우저 로그인에서만). 게스트는 키 없음. 지금의 키 인증은 **만료를 검사하지 않고** `rotate` 가 모든 키를 한꺼번에 거둔다 — 브라우저와 에이전트가 같이 끊긴다.
- **소셜 연결 해제**: 마지막 연결을 해제하면 그 사용자는 게스트 규칙을 받고 에이전트 키를 거둔다(안 하면 복구 불가능한 계정에 강한 키만 남는다).
- **게스트 삭제는 「여행 삭제」와 같은 함수**를 쓴다([백엔드 요청서](../records/plans/2026-10-03_1920_웹_실서버_전환_백엔드_요청.md) 구현 지침 8항). 사용자 행을 가리키는 외래키 14개 중 13개가 「가리키면 거부」(서버 DB 조회 2026-10-04)라 사용자 한 줄만 지울 수 없다. 웹 사용자만 대상 — `customers.external_id` 가 `web:` 로 시작하는 행(에이전트 API 로 만든 고객과 시드는 안 건드린다).

## 정정 2026-10-04 — 게스트 쿠키는 브라우저 세션 쿠키, 계획서는 내려받게

`[결정 2026-10-04 사용자]` 「그냥 계획서를 그동안 내려받을 수 있게만 해주고 못하면 어쩔 수 없는 거 아닐까? 코덱스와 같은 방식으로 가도 될 것 같다. 무료 범위에서 기능은 다 해주는 거니까」.
- 근거 조사: **클로드 · 코덱스는 게스트가 없고**(계정이 있어야 사용 — 공식 문서가 계정을 전제), ChatGPT 는 로그아웃 상태를 허용하지만 **현재 브라우저 세션에서만** 이어지고 서버가 안전 점검용으로 30일 보관한다(사용자는 못 봄 — [공식 보관 정책](https://help.openai.com/en/articles/8983778-chat-and-file-retention-policies-in-chatgpt)). 며칠씩 이어 주는 게스트를 둔 곳은 조사한 범위에 없었다(세 서비스뿐 — 일반화 못 함).
- 바뀌는 것: ①**게스트 쿠키는 `Max-Age` 가 없는 브라우저 세션 쿠키**(HttpOnly · Secure · SameSite=Lax 는 그대로) — 창을 닫으면 사라진다. 회원 쿠키만 오래간다. 게스트가 구글 계정을 `link` 하면 같은 값을 오래가는 쿠키로 다시 내린다 ②**계획서 내려받기**(`/plan/{id}?download=1`) — 게스트의 보관 수단 ③서버의 게스트 데이터 보존 시간(`web.guest_idle_hours`, 기본 7일)은 **그대로** — 계획서 링크가 그동안 산다. 앞의 「7일 이어 쓰기」 설명은 이 정정으로 **서버 데이터 보존**의 뜻만 남는다(쿠키가 사라진 게스트는 자기 여행을 못 열고 링크로만 본다).
- 「코덱스와 같은 방식(게스트 없이 로그인 필수)」으로 더 가는 것은 별개 결정이다 — 지금은 게스트를 맛보기(여행 1개 · 감시 불가 · 내려받기)로 남긴다.

## 되돌아보기(이 결정이 뒤집은 것)

- [D-020 · D-021 §4](../records/plans/) 「키를 한 번 보여 주며 보관하게 한다」 — 웹은 더 이상 안 한다(키 안내 화면 제거 — 웹 세션 몫).
- 2026-09-29 「빈 키 정리는 끈다」 — 여행이 있는 게스트까지 포함하는 새 규칙이 대신한다(옛 `idle_key_*` 설정은 걷는다).
- `[못 확인]` Safari 는 **서버가 `Set-Cookie` 한 쿠키**가 7일 규칙의 대상인지 공식 문서에 명시가 없다(스크립트가 쓴 쿠키와 저장소가 대상). 문구상 대상이 아니라는 추론이라 실기기 확인이 필요하다.
