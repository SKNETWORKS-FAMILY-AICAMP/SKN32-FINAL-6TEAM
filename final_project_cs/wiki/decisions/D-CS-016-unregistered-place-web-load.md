# D-CS-016 미등록 장소 — 웹 검색 1회 적재 후 규칙 판정

`[결정 2026-10-14 사용자]` 구현은 `[미구현]`이다. 이 문서는 설계 결정이고, 코드 연결은 별도 작업이다.

## 한 문단 요약

고객 일정의 장소가 우리 DB(`place_catalog` · 활동 원장)에 없을 때, **카카오는 실재 여부만** 판단한다(응답 저장 금지 — 카카오 운영정책 제5조, 그대로 유지). 실재가 확인되면 먼저 **TourAPI 키워드 검색**으로 찾고, 거기에도 없으면 **판정 LLM이 웹 검색으로 정기휴무 · 운영시간 원문과 실내외, 주소를 한 번 찾아**, 근거 검증을 통과한 값만 DB에 적재한다(좌표는 주소를 브이월드 지오코더로 바꿔 얻는다). 그 뒤로 그 장소는 DB에 있는 장소와 같이 **규칙 판정**을 받는다. **재난과 실시간 운영은 적재 대상이 아니다.**

## 무엇이 바뀌나

| 케이스 | 전 (wiki 2.5-E) | 후 (이 결정) |
|---|---|---|
| DB에 없음, 카카오에 실재 | 운영 정보 없음을 밝히고 고객 확인(그대로 진행 / 다른 장소). **적재 안 함** | **TourAPI 키워드 검색 → (없으면) 웹 검색 1회 → 검증 통과분 적재 → 규칙 판정**(아래 「좌표 · 주소 확보 순서」). 웹에서도 근거를 못 찾은 항목만 전과 같이 고객 확인(UC-A1 `2a4`) |
| DB에 없음, 카카오에 없음 | 이름 되묻기(최대 2회) | `[개정 1]` **기준점으로 좌표 확정 → 대체 후보**(아래 「개정 1」) |
| DB에 없음, 여러 곳 | 후보 제시 | 그대로 |
| DB에 없음, 카카오 조회 실패 | 담당자에게 넘김 | `[개정 1]` 한 번 다시 시도 → 실패하면 **기준점으로 좌표 확정 → 대체 후보**. 「없음」으로 단정하지 않는다 |

## 판정별 적용

| 판정 | 적재 | 이후 판정 | 이유 |
|---|---|---|---|
| ① 정기휴무 | 웹에서 찾은 **휴무 원문 문장**을 저장 | 규칙(`closure_rules.read_closure`)이 원문을 읽는다. 규칙이 못 읽으면 기존 판정 LLM 원문 해석 경로(D-CS-015 개정 2) | 관광공사 원문과 같은 방식으로 다룰 수 있다 |
| ② 운영시간 | 웹에서 찾은 **운영시간 원문 문장**을 저장 | 규칙으로 요일표(`hours_week`)로 펴고, 못 펴면 `read_hours.py` 경로. 매일 판정은 코드가 날짜 대입 | 같음 |
| ③ 실내외 | `activity.ac_indoor`에 `decided_by=llm`으로 저장(근거 인용 · 출처 URL · 모델 · 프롬프트 버전) | 저장값을 읽는다. 우선순위 `operator > customer > llm > class` 그대로 | 장소 성격은 잘 바뀌지 않는다 |
| ④ 재난 | **적재하지 않는다** | 매번 지금 발령 중인 문자 확인 | 실시간 사실이다. 장소의 속성이 아니다 |
| ⑤ 실시간 운영 | **이 흐름으로 적재하지 않는다** | 지금처럼 장소 × 날짜 단위 배치(`ac_live_status`) | 날짜마다 답이 달라 1회 적재가 성립하지 않는다 |

## 지키는 것

- **카카오 응답은 어디에도 저장하지 않는다.** 이름 · 좌표 · 주소 · id 모두. 카카오가 내는 것은 「있다 / 없다 / 못 물었다」 판정뿐이다.
- **근거 검증을 통과한 값만 적재한다.** 판정 LLM의 기존 규칙과 같다 — 인용 출처 URL이 그 호출의 실제 검색 출처 목록에 있어야 하고, 게시일이 오래된 근거(`citation_max_age_days`)는 버린다. 원문 인용이 없는 값은 적재하지 않는다.
- **사실 정보만 저장한다.** 운영시간 · 휴무 문장 · 실내외 판정과 출처 URL · 확인 시각. 페이지의 소개글 · 사진 같은 창작물은 저장하지 않는다(D-022와 같은 선).
- **출처를 표시한다.** 웹에서 적재한 값은 관광공사 원문과 구분되는 출처(`web`)와 확인 시각을 갖는다. 그 값으로 판정했으면 고객 답에 「웹에서 찾은 안내를 자동으로 읽어 확인했어요. 방문 전 한 번 더 확인해 주세요」를 붙인다.
- **모르면 모른다.** 웹 검색 실패 · 근거 없음 · 검증 탈락이면 그 항목은 적재하지 않고, 전처럼 운영 정보 없음을 밝히고 고객에게 묻는다.

## 좌표 · 주소 확보 순서 (카카오 제외)

`[결정 2026-10-14 사용자]` 카카오 좌표는 저장할 수 없으므로, 저장이 허용된 소스로 아래 순서대로 확보한다. 재난문자는 장소의 구로 거르고 대체 후보는 반경으로 찾으므로, 좌표 · 주소가 없으면 재난 확인 · 대체 장소가 돌지 않는다.

| 순서 | 소스 | 얻는 것 | 저장 근거 | 이미 있는 것 |
|---|---|---|---|---|
| ① | **TourAPI 키워드 검색**(`searchKeyword2`) | 좌표(`mapx` · `mapy`) · 주소(`addr1`) · `contentid` | 관광공사 사실 정보 저장 허용(`[결정 2026-09-28 사용자]`, 루트 `CLAUDE.md` 「외부 공공데이터 저장」) | `TourApiPlace.find()`(`ports/data_sources/tour_api.py`), 키 `ACOP_TOUR_API_KEY` |
| ② | **웹 검색의 주소 원문 → 브이월드 지오코더** | 도로명/지번 주소 → 좌표 | 국토교통부 공공데이터 — Dining 이 이미 운영 허용 소스로 등록(마이그레이션 227 `vworld_geocoder`) | `scripts/geocode_vworld.py`(도로명 → 지번 순, 서울 범위 밖이면 실패), 키 `ACOP_VWORLD_API_KEY` |
| ③ | 둘 다 실패 | — | — | `[개정 1]` 담당자에게 넘기지 않는다. **기준점으로 좌표를 확정**한다(아래 「개정 1」). 기준점은 그 장소의 좌표로 **적재하지 않는다** — 대체 후보를 찾는 출발점으로만 쓴다 |

- **① 에서 찾으면 웹 검색을 하지 않는다.** `contentid` 로 `detailIntro2` 의 운영시간 · 휴무 원문까지 받아 관광공사 원장(`ac_place`)과 같은 방식으로 적재한다. 웹 판정 비용(호출당 약 $0.04)과 대기(p50 9~16초)를 아낀다. 실내외는 관광공사 분류로 먼저 정하고, 못 정하면 기존 1회 판정 경로(`decide_indoor.py`)로 간다.
- **② 의 주소는 웹 검색 한 번에 휴무 · 운영시간 · 실내외와 함께 받는다.** 주소도 다른 값과 같이 근거 검증(인용 · 출처 URL · 게시일)을 통과해야 지오코딩한다.
- **같은 장소인지 확인한다.** TourAPI 결과는 장소 이름 매칭 규칙(`intake.places._kakao_match` 와 같은 기준 — 이름이 같거나, 질의로 시작하는 곳이 하나뿐)을 통과해야 쓴다. 이름이 비슷한 다른 곳을 받지 않는다.
- **구를 대조한다.** 지오코딩한 좌표의 구와 웹 원문 주소의 구가 다르면 적재하지 않는다.
- **출처를 남긴다.** 좌표 · 주소마다 출처(`tour_api` / `web+vworld_geocoder`) · 확인 시각을 저장한다.
- **쓰지 않는 소스:** Google Places(D-CS-010 새벽 창 한정 · 좌표 저장 안 함, 마이그레이션 200), 네이버 검색(결과 저장 안 함 · 좌표 없음), OSM Nominatim(국내 시설 검색 정확도가 낮아 기본 경로에서 뺀다 — 필요하면 마지막 대체 수단으로 따로 정한다).

## 개정 1 — 장소를 못 찾아도 좌표는 반드시 확정한다

`[결정 2026-10-14 사용자]` 근거: 코어 전달 [`docs/2026-10-14_활동_못찾은장소_대체후보_전달.md`](../../../docs/2026-10-14_활동_못찾은장소_대체후보_전달.md). 구현은 `[미구현]`.

**바뀐 것** — 「카카오에 없음」은 이름을 최대 2회 되묻고, 「카카오 조회 실패」는 담당자에게 넘겼다. 이제 둘 다 **담당자에게 넘기지 않고 기준점으로 좌표를 확정해 대체 후보를 낸다.** 이름을 못 찾았다는 것은 「원래 장소」가 없다는 뜻일 뿐이고, 후보는 종류(활동) · 기준점 · 시각 · 취향으로 만들 수 있다. 지금은 대체 후보 길이 `origin_no_coordinates` 로 끝나 추천이 0건이다.

| 경우 | 처리 |
|---|---|
| ⓐ 카카오에 **이름은 안 맞고 종류가 맞는 결과만 있음** — DB에 없음, 카카오 결과 중 원문과 같거나 원문으로 시작하는 이름이 없음(예: 「한강 카약」 → 카약 업체 5곳) | 되묻지 않는다 → 기준점 좌표 확정(아래 「기준점 순서」) → 원문의 활동 말을 **분류로 바꿔**(아래 「원문 활동 말 → 분류」) 기준점 좌표와 함께 `origin` 에 싣는다 → 대체 후보 |
| ⓑ 카카오에 없음 — **결과 0건**(예: 「성수 끄륵」 · 「한강 끄륵」) | 되묻지 않는다 → 기준점 좌표 확정 → 대체 후보(분류는 비움 — 원문에 분류로 바꿀 말이 있으면 ⓐ 와 같이 채운다) |
| 카카오 조회 실패 | 한 번 다시 시도 → 다시 실패하면 기준점 좌표 확정 → 대체 후보. 「없음」으로 단정하지 않는다 |
| 카카오에 실재, 위 「좌표 · 주소 확보 순서」 ①·② 모두 실패 | 기준점 좌표 확정 → 대체 후보 |

**기준점 순서** — ① 그 줄에 적힌 지역의 중심 → ② 없으면 앞뒤 일정의 가운데 → ③ `[결정 2026-10-14 사용자]` 둘 다 없으면 **고객이 지도에서 좌표를 지정**한다. ①·② 계산과 전달은 코어가 맡는다.

- ③ 은 고객에게 묻는 단계다(`WAIT_FOR_INPUT`). 기준점을 지어내지 않는다 — 서울시청 같은 고정 좌표로 채우지 않는다.
- 지도 창은 확인 화면 「지도에서 장소 고르기」 계획([`2026-09-30_2134_확인화면_장소_지도_고르기_실행계획.md`](../records/plans/2026-09-30_2134_확인화면_장소_지도_고르기_실행계획.md), 초안 · 미구현 — Leaflet + OSM 타일, 서울 범위 제한)을 그대로 쓴다. 그 계획은 「찍은 자리 근처 후보 → 없으면 찍은 자리 확정」이고, 여기서는 찍은 자리를 **기준점**으로 받아 대체 후보를 찾는다.
- 찍은 좌표도 기준점이다 — 그 장소의 좌표로 원장에 적재하지 않는다.
- `[실측 2026-10-14]` 예:
  - ① 「성수 끄륵」 — 줄 해석기가 「성수동」으로 읽는다 → 성수동 중심(37.5436, 127.0532, 반경 1.2km).
  - ② 「한강 끄륵」 — 「한강」은 지명 사전에 없어 지역으로 읽히지 않는다(`line_parts.parse` → `area=None`. 정한 규칙이 아니라 사전에 없어서다). 앞 경복궁 · 뒤 광장시장이면 두 좌표의 가운데(위도 · 경도 평균) 37.5731, 126.9882(종로3가, 두 곳에서 각 1.07km).
  - ③ 지역도 앞뒤 일정도 없는 날이면 고객이 지도에서 지정한다.

**ⓐ 와 ⓑ 의 구분** — `[실측 2026-10-14]` 카카오 결과가 있어도 이름 매칭 규칙(`intake.places._kakao_match` — 같은 이름이 하나뿐이거나, 원문으로 시작하는 이름이 하나뿐)을 통과하지 못하면 「없음」이다. 「한강 카약」은 카카오가 카약 업체 5곳(포시즌카약패들보드윈드서핑 · Koa SUP 카약 · 루나루카약 …)을 돌려주지만 이름이 맞지 않아 「없음」, 「한강 끄륵」은 결과가 0건이라 「없음」이다. 코드(`place_lookup`)는 둘 다 `not_found` 로 돌려주므로 ⓐ · ⓑ 로 나눠 돌려주게 바꾼다. ★「카카오에 있음 · 실재」(`exists_unregistered`, 이름 매칭 통과)는 이 개정이 아니라 위 본문(관광공사 → 웹 1회 적재)을 따른다 — ⓐ 를 「카카오에 있음」으로 부르지 않는다. 카카오 업체 이름 · 좌표는 저장할 수 없으므로(제5조) ⓐ 도 후보는 **관광공사 목록**에서 찾는다 — 카카오 결과는 「종류가 맞는 곳이 있다」는 판정에만 쓴다.

**원문 활동 말 → 분류** `[결정 2026-10-14 사용자]`

- 원문의 활동 말을 관광공사 소분류 코드로 바꾸는 표를 설정(`config/place_terms.yaml`)에 둔다. 예: 카약 · 카누 → `LS020200`, 요트 → `LS020300`, 수상스키 → `LS020100`. 판정 LLM 으로 분류하지 않는다(비용 · 사람 라벨 없음).
- 바꾼 코드는 `origin` 의 분류 칸(`lclsSystm1~3`)에 싣고 **출처를 「고객 원문에서 추정」으로 표시**한다 — 관광공사 값과 섞지 않는다. 표에 없는 말이면 분류를 비운다.
- 분류가 채워지면 활동 팀 대체 후보 규칙(`alternatives.py` `rank_alternatives`)이 그대로 돈다. 순서는 설문 선호에 따라 다르다.
  - 「활동 중요」: 대분류 고정. 같은 소분류를 반경 1→10km 로 찾고, 「더보기」까지 10곳이 안 차면 소분류를 풀어 같은 중분류, 그래도 모자라면 중분류를 풀어 같은 대분류로 넓힌다. 10곳이 차면 멈춘다.
  - 설문 무응답: 화면 3곳은 **같은 소분류만**, 「더보기」에만 소분류를 푼 같은 중분류를 채운다. 대분류로는 넓히지 않는다.
  - 화면 3곳의 순서와 1순위 이유는 판정 LLM(`alternative_order`)이 다시 정할 수 있다. 어떤 3곳인지는 코드가 고정한다.
- `[실측 2026-10-14]` 예 — 「한강 카약」 → `LS020200`, 기준점 종로3가(위 ②), 관광공사 레저(LS) 85곳, 「활동 중요」, 운영시간 정보 없는 행이라 「운영 여부 모름」으로 남긴 채 실행:

  | 순위 | 장소 | 소분류 | 거리 |
  |---|---|---|---|
  | 1 | 세빛섬 튜브스터 | `LS020200` 같은 소분류 | 6.78km |
  | 2 | 송강카누학교 서울분교 | `LS020200` 같은 소분류 | 9.53km |
  | 3 | 용산초등학교 실내수영장 | `LS020700` 같은 중분류 | 4.39km |
  | 4 | 서대문문화체육회관 실내수영장 | `LS020700` | 5.06km |
  | 5 | 리버시티수상스키장 | `LS020100` | 5.61km |
  | 6 | 한강시민공원 잠원수영장(실외) | `LS020700` | 6.19km |
  | 7 | 골든블루마리나 | `LS020300` | 6.78km |
  | 8 | 한강레져스포츠 | `LS021400` | 6.84km |
  | 9 | 한강요트투어 세일링파라다이스 | `LS020300` | 6.94km |
  | 10 | 키즈돌핀 서대문DMC점 | `LS020700` | 7.04km |

  같은 소분류는 2곳이고 3~10위는 같은 중분류 거리순이다. 중분류에서 10곳이 차서 대분류(LS) 단계까지 가지 않았다. 현대요트 서울지점(7.3km)은 10위 밖이다. 설문 무응답이면 화면은 1 · 2위 두 곳뿐이고 3~10위는 「더보기」에만 들어간다.
- 카카오가 돌려준 카약 업체 5곳은 순위에 넣지 않는다(저장 · 표시 불가). `[결정 2026-10-14 사용자]` 업체 이름마다 관광공사 키워드 검색으로 재확인해 넣는 방법은 쓰지 않는다 — 지금 순서를 유지한다.
- 고객 안내는 사실대로 — 같은 소분류: 「'한강 카약'을 찾지 못해 가까운 카누 · 카약장을 골랐어요」, 중분류로 넓힘: 「카약장이 없어 가까운 수상레포츠를 골랐어요」, 다른 활동까지 넓힘: 「카약은 찾지 못했어요」를 붙인다.

**반경 기준 — 활동 팀 기준 하나로** `[결정 2026-10-14 사용자]`

- 이 개정의 대체 후보는 **확인 화면 경로를 포함해 모두 활동 팀 기준**으로 찾는다 — 반경 1km 에서 시작해 1km 씩, 최대 10km(`alternatives.py` `RADIUS_START_KM` · `RADIUS_STEP_KM` · `RADIUS_MAX_KM`), 「더보기」까지 10곳이 차면 멈춘다.
- 확인 화면 경로의 고정 반경 3km(`components/intake/candidates.py` `RADIUS_M = 3000`)는 이 개정의 기준에서 **뺀다.** 그 값은 측정 근거가 없는 「우리가 고른 값」이다 — 2026-09-29 `1c4fb18f`(활동 팀 PR #6 통합) 때 「다른 데로 바꿔 줘」 반경(`itinerary_changes.py` `ALTERNATE_RADII_M`, 주석 「설계 문서의 근거는 없다」)으로 들어왔고, 2026-10-03 `1544265d` 에서 확인 화면이 그대로 따라 썼다. 3km 로는 위 예의 카약 후보(5.6~9.5km)가 하나도 나오지 않는다.
- 코어 파일(`candidates.py`)을 바꾸는 일이라 코어에 요청한다(아래 역할 「코어 ③」). 그 전까지 확인 화면은 3km 로 돈다.

**넘기는 `origin`**(지금 `read.place_candidates` 의 `origin` 과 같은 모양):

| 칸 | 값 |
|---|---|
| `title` | 고객이 적은 원문(예: 「한강 카약」) |
| `mapx` · `mapy` | 기준점 좌표 |
| `lclsSystm1~3` | ⓐ · 원문에 분류로 바꿀 말이 있으면 추정 코드(출처 「고객 원문에서 추정」), 없으면 비움 |
| `contentid` · `lDongSignguCd` · 휴무일 · 운영시간 | 비움(모른다고 표시) |

- 후보는 기준점 둘레의 관광공사 목록 행이다. 후보의 휴무 · 운영시간 · 재난 재확인은 지금과 같다.
- 판정 LLM(`alternative_order`)은 목록 안에서 순서와 이유 한 줄만 정하고 후보를 새로 만들지 않는다. 고객 문장의 의도(「한강 카약」)는 순서 단서로만 쓴다.
- **기준점은 장소 좌표가 아니다.** 원장(`ac_place`)이나 장소 목록에 그 장소의 좌표로 적재하지 않는다.

**역할**

| 쪽 | 할 일 |
|---|---|
| 코어 | ① 이름을 못 찾은 줄의 종류를 `activity` 로 단정하지 않고 「모름」으로 둔다(고객이 직접 정한 종류는 그대로, `components/intake/assemble.py:197`) ② 기준점을 계산해 위 `origin` 으로 넘긴다 ③ 확인 화면 대체 후보(`candidates.py`)의 고정 반경 3km 를 활동 팀 기준(1→10km)으로 바꾼다 |
| 활동 | ① `origin` 에 좌표만 있고 `contentid` · 분류가 비어도 `rank_alternatives` 가 `origin_no_coordinates` 로 끝나지 않게 한다 ② 분류가 비면 분류로 거르지 않고 거리 · 시간 적합도로 순위를 매기는지 확인하고 시험을 더한다 ③ `db_search/place_candidates.py` 가 원래 장소 행이 없어도 기준점 좌표로 후보를 읽게 한다 ④ `place_lookup` 이 카카오 실패 시 한 번 다시 시도하게 한다 ⑤ 「카카오에 없음」을 ⓐ 결과 있음 · ⓑ 결과 0건으로 나눠 돌려주게 한다(카카오 이름 · 좌표는 싣지 않음) ⑥ 원문 활동 말 → 분류 표(`place_terms.yaml`)와 그 시험 |
| 화면 | 기준점 ③ — 고객이 지도에서 좌표를 찍는 창(위 지도 고르기 계획 재사용), 찍은 좌표를 그 줄의 기준점으로 서버에 넘김 |

**`[결정 필요]`**
- 기준점 ③ 을 지도 없는 경로(개인 에이전트 API · MCP)에서 받는 방법 — 좌표 · 주소 · 지명 중 무엇을 받을지.
- ⓑ 처럼 분류 없이 거리순으로 나가는 후보를 고객에게 보일 이유 문구(코어가 활동 팀 판단에 맡김).
- 같은 중분류 안의 결 차이 — 위 예에서 LS02 수상레포츠에 **실내수영장**이 섞여 카약 대체 3위로 올라온다. 분류 규칙으로는 맞지만 고객 의도와 멀다. 중분류 안에서 가까운 소분류(물 위 활동)를 먼저 볼지.
- 원문 활동 말 → 분류 표의 첫 목록(어떤 말을 넣을지).
- 고객 문의로 열린 Case 에서 코어가 기준점(앞뒤 일정 좌표)을 가져다 주는 방법(코어가 정함).
- 코어 확인 요청 1: `alternatives.py` 189행 부근 — 분류 4칸이 모두 비면 `keys` 가 비어 풀 전체가 통과한다는 코어의 읽기가 맞는지, 의도한 동작인지 회신.
