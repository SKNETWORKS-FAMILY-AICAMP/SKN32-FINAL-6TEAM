# D-CS-020 서비스 모드 — 회원 · 게스트 한 시간 한도

`[2026-10-22 사용자 지시]` 「무료 계정은 저 콜수를 시간당으로 제한 걸어놔야 겠네. 옵션에 서비스 모드 스위치 만들고 지금은 서비스 모드 아니니까 그럴 필요 없고
서비스 모드 켜면 무료 계정은 저런 api 들 콜수 다 제한 걸어두고 로그인 안하면 검색같은 것들도 제한 거 빡시게 걸어놔 … 이 양도 다 설정 가능하게 관리자 웹앱에 만들어야 해」.
계기: 수정 화면 장소 검색이 「가까운 순 · 이름이 잘 맞는 순」 두 목록이 되며 카카오 호출이 검색 한 번에 최대 2건이 됐다(카카오 예산 하루 1,000건 `travel.kakao_budget`).

## 정한 것

| 무엇 | 값 |
|---|---|
| 스위치 | 운영 설정 `service.mode_enabled` — 기본 **꺼짐**(지금은 시험 단계). 끄면 한 시간 한도는 세지도 막지도 않는다 |
| 켜면 | ①기존 하루 한도(키 · 주소 · 서비스 전체, `web.limits_enabled` 와 같은 것)가 함께 켜진다 ②사람(키) 한 명 단위 **한 시간** 한도가 더해진다 |
| 등급 | **회원** = 소셜 로그인이 붙은 계정 · **게스트** = 로그인 안 함(`guest_policy.is_guest`). 「무료 계정」은 지금 회원 전체다 — 유료 등급은 위키 · 코드 어디에도 없다 |
| 대상 작업 | 하루 한도와 같은 10개 — 계획 읽기 · 일정 짜기 · 확인 · 여행 만들기 · 채팅 · 모델 예열 · 장소 검색(대체 후보 · 사진 포함) · 위험 점검 2 · 이동 판정 |
| 값 | 관리 콘솔 「운영 설정」 → 「서비스 모드」 칸(작업 × 회원/게스트 표). 이름 `service.<member\|guest>.<작업>.per_hour`, 범위 1~100000, 기본값 가드레일 `web_guard.service_mode.per_hour` |
| 기본값 | **우리가 고른 값**(측정 안 함) — 회원은 수정 화면을 여러 번 열어도 막히지 않을 만큼, 게스트는 맛보기([D-CS-011](D-CS-011-browser-session-cookie.md))만큼. 예: 장소 검색 회원 120 · 게스트 20, 채팅 60 · 10, 계획 읽기 10 · 2 |
| 넘으면 | `429 hourly_limit` · `Retry-After` 다음 정시. 그 사람의 그 작업만 막힌다. 화면은 횟수와 기다릴 시간, 게스트면 「로그인하면 더 쓸 수 있어요」 |
| 예외 | QA 예외 계정(`usage_exempt`)은 등급 한도를 받지 않는다(서비스 전체 하루 한도는 그대로) |

## 고르지 않은 것과 이유

- **카카오 호출 수 자체를 사람마다 세기** — 카카오는 계획 읽기 · 대체 후보 · 검색 등 여러 깊은 곳에서 불린다. 작업 단위로 세는 기존 장치(`web_guard`)에 얹는 쪽이 한 곳에서 막고 관리 콘솔에도 그대로 나온다. 대신 장소 검색 한 번이 카카오 최대 2건이라는 것을 기본값에 반영했다.
- **게스트 0회(아예 막기)** — 범위 최소 1. 「0 = 한도 없음」으로 읽는 칸(채팅 하루 한도)이 이미 있어 0 의 뜻이 갈린다.

## 구현 · 확인 상태 (2026-10-22)

- 로컬 사본 구현: `web_guard.py`(설정 · 세기) · `trip_api._count` 문구 · 웹 `error-text.ts` · `client.ts` · 관리 콘솔 `features/operations/service-mode*.tsx` · `connected.tsx` · 가드레일.
- 시험: 관리 콘솔 단위 39/39 · 고객 웹 1042/1042 · 서버 관련 단위 925 통과(남은 실패 7은 고치기 전 판에서도 같다 — 사본 환경). DB 가 필요한 `tests/e2e/test_web_guard_service_mode.py` 는 commit 세션 시험 DB 에서 돌린다.
- 배포 · x600 서버 확인: 안 함. 켜는 것은 서비스를 시작할 때 사용자가 관리 콘솔에서.
