# D-CS-019 배포 중 서비스 공지

`[2026-10-20 사용자 지시]` 「저거 서버에 새 배포본 올라가는 동안에는 자동으로 알맞는 공지 생성해 놨다가 사용자들에게 제공되게 해봐」.
계기: 같은 날 09bf0dad 판 배포가 DB 이주 단계에서 멈춰 cs 프로젝트 서버가 옛 판에 머물렀고, 고객은 무슨 일인지 알 수 없었다.
설계 세부(아래 표 · 문구 · 시간 기준)는 이 지시를 받은 세션이 정했다 — 사용자 확인 전이라 `draft` 다.

## 한 문단 요약

x600 서버의 자동 배포(`deploy/auto_deploy.sh`)가 단계마다 `deploy/deploy_notice.py` 를 불러 **공지 상태 파일**(`state/service-notice/notice.json`)을 쓴다.
cs 프로젝트 서버(api)는 그 폴더를 읽기 전용으로 붙이고, **이미 있는 고객 공지 경로** `GET /v1/web/support/notices` 가 운영자 공지 맨 앞에
배포 공지 한 건을 **정해 둔 한국어·영어 문구**로 만들어 붙인다(`app/application/deploy_notice.py`). 웹은 운영자 공지와 똑같이 상단 공지 띠 ·
여행 화면 알림 센터에 보인다 — 15초마다 다시 읽고, 읽기에 실패해도 **마지막으로 받은 공지를 그대로 둔다**(기존 동작). 그래서 새 판으로 바꾸느라
api · web 이 함께 내려간 동안에도 열린 화면에는 「곧 바뀌어요 / 바꾸는 중이에요」가 남아 있고, 다시 연결되면 「바뀌었어요」로 바뀐다.
그 사이 화면을 **새로 여는** 사람은 Caddy 점검 응답(아래 「아직 반영 안 한 것」 1)이 맡는다. LLM 은 부르지 않는다.

## 언제 고객 화면이 끊기나 (2026-10-20 스크립트로 확인)

| 배포 단계 | 하는 일 | 고객 화면 | 시간 상한(스크립트) |
|---|---|---|---|
| 받기 · 확인 | role-manager 새 커밋을 받고 배포에 쓰이는 폴더가 바뀌었는지 · 실행 중 구성이 맞는지 본다 | 영향 없음(공지도 안 낸다) | — |
| 빌드 | 새 이미지를 만든다 | 영향 없음(옛 판이 그대로 돈다) | 600초 |
| DB 이주 | 표 구조를 앞으로만 맞춘다(`migration_safe_deploy.py migrate`) | 영향 없음(옛 판이 그대로 돈다) | 180초 |
| 바꾸기 | api · worker · web 세 컨테이너를 한꺼번에 새로 만든다(`rollout`, `up -d --no-deps`) | **끊김** — Caddy 뒤의 api · web 이 둘 다 없는 동안 | 240초 + 지켜보기 30초 |
| 실패 시 되돌리기 | 저장해 둔 옛 이미지로 다시 만든다(`recover`) | **끊김**(되돌리는 동안) | 위와 같음 |

2026-10-14 x600 서버 복원 시험에서 바꾸기 한 번에 1~3분 끊겼다([배포 안내](../../deploy/README.md) 「월별 보존 판으로 되돌리기」).

## 공지 상태 파일 (배포 스크립트 → api)

| 칸 | 뜻 |
|---|---|
| `phase` | `preparing`(빌드 · DB 이주 — 아직 안 끊김) · `switching`(바꾸는 중 — 끊길 수 있음) · `done`(새 판 반영) · `kept_previous`(이번 판 실패, 옛 판 그대로) · `trouble`(바꾸기와 되돌리기가 모두 실패 — 사람이 봐야 함) |
| `step` | 운영용 세부 단계 `build` · `migrate` · `switch` · `recover` |
| `deploy_id` | `<커밋 10자>-<시작 초>` |
| `started_at` · `switch_started_at` · `finished_at` · `updated_at` | 한국 시각(+09:00) 원값 |
| `expected_outage_seconds` | 끊김 예상 — 지난 바꾸기 실측(성공한 최근 5번의 최댓값, 30~300초로 자름, `history.json`). 기록이 없으면 120초 |

- 파일은 임시 파일에 쓴 뒤 바꿔 끼운다(잘린 파일을 읽지 않게). 공지 쓰기가 실패해도 배포는 계속한다(경고 한 줄). 원본 기록은 그대로 `deploy.log` 다.
- `migration_safe_deploy.py` 는 「바꾸기 실패 · 되돌리기 확인」(종료 코드 1)과 「되돌리기도 실패」(종료 코드 3)를 나눠 알린다 — 공지가 `kept_previous` 와 `trouble` 을 가른다.
- 공지는 실행 중 구성 확인(snapshot)이 통과한 **뒤**에 시작한다 — 구성 불일치로 5분마다 멈추는 동안 공지가 켜졌다 꺼졌다 하지 않게.

## 고객에게 보이는 공지 (고정 문구 · 운영자 공지와 같은 모양)

`GET /v1/web/support/notices` 의 `notices[0]` 에 붙는다. `[2026-10-23 사용자 결정 — 추천안]` `id` 는 `deploy:<deploy_id>` — **배포 한 번에 하나**다. 단계가 바뀌어도 같은 건이고(문구만 바뀐다), 앞 단계의 띠를 닫았으면 같은 배포의 다음 단계 띠는 다시 뜨지 않는다.
`startsAt` 은 시작 시각(분까지), `endsAt` 은 `null`.

### 공지사항 게시판에도 한 건 `[2026-10-23 사용자 결정 — 추천안]`

배포 한 번에 **게시판(`GET /v1/web/support/notices/board`)에도 한 건**이 남는다 — 단계마다 새 건을 만들지 않는다.
- 만들고 고치는 곳: `app/application/deploy_notice.py` 의 `sync_board` 를 고객 공지 경로(`/notices`)와 게시판 경로(`/notices/board`)가 읽기 전에 부른다. 상태 파일의 배포 한 건을 운영 공지 기록(`admin_records` 의 `notice`, id `deploy:<deploy_id>`, `source: "deploy"`, 작성자 `auto-deploy`)으로 맞춘다 — 없으면 만들고, 단계가 바뀌었으면 같은 건의 문구를 고친다. 값이 같으면 쓰지 않는다. 호스트의 배포 스크립트는 DB 에 쓰지 않는다(파일만).
- 진행 중(`preparing` · `switching`)에는 `endsAt` = 마지막 갱신 + 30분이라 게시판에서 「게시 중」이다. 배포 프로세스가 죽어 갱신이 끊겨도 그 시각이 지나면 저절로 「종료」가 된다(띠의 30분 기준과 같다).
- 끝나면(`done` · `kept_previous` · `trouble`) `endsAt` 이 끝난 시각이라 「종료」로 보인다. 띠는 5분/30분 뒤 사라지지만 게시판 기록은 남는다. 다음 배포는 새 건이고 앞 건은 「종료」로 남는다.
- 고객 공지 경로의 운영자 공지 목록에서는 `source: "deploy"` 기록을 뺀다 — 띠는 `current_notice` 한 건이 맨 앞에 붙인다(중복 방지).
- 단계별 변화(준비 → 바꾸는 중 → 끝)는 `admin_audit`(`action: deploy-notice`)에만 남는다 — 관리자 앱에서만 본다. 고객 알림(outbox)은 보내지 않는다.
- 한계: 상태 파일은 최신 배포 하나만 가진다. 배포가 시작되고 끝날 때까지 두 경로를 아무도 읽지 않았고 그사이 다음 배포가 시작되면 그 배포의 건은 만들어지지 않는다. 운영자가 이 기록을 지우면 상태 파일이 같은 배포를 가리키는 동안 다음 읽기에서 다시 만들어진다.

| 상태 | 종류(띠 색) | 제목 | 내용(한국어 — 영어는 같은 뜻, 시각 뒤에 `KST`) | 보이는 동안 |
|---|---|---|---|---|
| `preparing` | 점검 예고 | 곧 새 판으로 바뀌어요 | 지금은 그대로 쓰실 수 있어요. {시작 시:분}에 시작한 준비가 끝나면 약 {n}분 동안 연결이 끊길 수 있어요. 저장된 일정은 그대로예요. | 진행 중(30분 넘게 갱신이 없으면 안 보임) |
| `switching` | 점검 예고 | 새 판으로 바꾸는 중이에요 | {바꾸기 시:분}부터 약 {n}분 동안 연결이 끊길 수 있어요. 저장된 일정은 그대로예요. 화면이 안 열리면 잠시 뒤 다시 시도해 주세요. | 위와 같음 |
| `done` | 안내 | 새 판으로 바뀌었어요 | {끝난 시:분}에 끝났어요. 계속 쓰시면 돼요. | 5분 |
| `kept_previous`(바꾸기 전 실패) | 안내 | 이번 업데이트는 미뤘어요 | 새 판 준비가 끝나지 않아 지금 판을 그대로 쓰고 있어요. 이용에는 영향이 없어요. | 5분 |
| `kept_previous`(바꾸다 되돌림) | 안내 | 이번 업데이트는 미뤘어요 | 새 판으로 바꾸지 못해 {시:분}에 원래 판으로 되돌렸어요. 저장된 일정은 그대로예요. | 5분 |
| `trouble` | 기능 차질·장애 | 새 판으로 바꾸다 문제가 생겼어요 | {시:분}부터 일부 기능이 안 될 수 있어요. 안 되면 잠시 뒤 다시 시도해 주세요. | 30분 |

- 웹이 아는 언어는 한국어 · 영어 둘이다(`lib/i18n.ts`, 공지의 `titleEn` · `bodyEn`). 시각은 파일 값의 시:분을 옮길 뿐 다시 만들지 않는다. {n} = 끊김 예상 초를 분으로 올림.
- 파일이 없으면 공지 없음. 읽을 수 없거나 모양이 틀리면 공지 없음 + 경고 기록(조용히 넘기지 않는다).
- 개인 AI(MCP) · 채팅 답변에는 넣지 않는다 — 채팅 화면도 같은 상단 공지 띠를 본다.
- Caddy 가 api 대신 답한 `/v1/*` 거절(`{"error":{"code":"service_updating"}}`, 503)은 웹 오류 문장 표(`lib/live/error-text.ts`)가 「서비스를 새 판으로 바꾸는 중이에요」로 옮긴다.

## 하는 일의 경계

- `deploy/deploy_notice.py` 는 호스트 파이썬 표준 라이브러리만 쓴다(배포 스크립트와 같은 조건).
- `app/application/deploy_notice.py` 는 인증 · DB 없이 파일 하나만 읽는다. 경로는 설정 `service_notice_path`(기본 `var/service-notice/notice.json`).
- compose 는 api 에 `./state/service-notice:/srv/var/service-notice:ro` 를 붙인다 — 환경 파일(`.env`)에는 줄을 더하지 않는다(줄을 더하면 자동 배포가 구성 불일치로 멈춘다).

## 아직 반영 안 한 것 · 사람이 정할 것

1. **Caddy 점검 응답**: 바꾸는 동안 **새로** 화면을 여는 사람은 web 이 없어 Caddy 의 502 를 본다. [`deploy/Caddyfile.tripilot`](../../deploy/Caddyfile.tripilot) 에 `handle_errors` 블록(웹 경로는 20초마다 다시 여는 짧은 안내 쪽, `/v1/*` 는 JSON `service_updating`)을 넣었지만
   x600 서버의 실제 Caddy 설정에 붙이고 다시 읽히는 일은 **사용자 확인 뒤**에 한다(같은 Caddy 를 다른 프로젝트도 쓴다). 이 PC 에는 Caddy 가 없어 `caddy validate` 를 못 했다.
2. **첫 반영의 순서**: 이 변경이 든 판은 x600 서버에 있는 옛 `auto_deploy.sh` 로 배포된다(스크립트는 반영에 성공한 **다음** 회차부터 새 판을 쓴다). 그래서 공지는 **그 다음 배포부터** 나온다.
3. 관리 콘솔 표시는 이번 범위에서 뺐다 — 운영자는 `deploy.log` 와 공지 파일을 본다.
4. 수동 배포(`deploy/server_up.sh`)는 공지를 쓰지 않는다.
