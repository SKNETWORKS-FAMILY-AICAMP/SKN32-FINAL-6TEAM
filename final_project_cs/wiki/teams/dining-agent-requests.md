# Dining — 전달받은 자유문의 식사 조건 확인

2026-10-19 사용자 요청: 코어가 넘긴 일정과 자유문을 다이닝 담당 범위에서 확실하게 판별한다. 앞단 일정 읽기 오류를 다이닝이 고치지 않는다. 초기 작업은 시험 전까지였으며, 후속 「평가해보자」 승인 뒤 [실행 평가](../records/reports/2026-10-19_dining-freeform-evaluation.md)를 진행했다.

## 내부 입력과 책임

기존 `judge_day(plan)`의 날짜·식사 항목·장소·시각은 그대로 사용한다. 고객 자유문 `customer_notes`는 다이닝 안에서 임의로 2,000자까지 자르지 않는다. 여러 날짜를 아우르는 조건의 적용 대상을 판단할 수 있도록 전달받은 전체 일정의 항목 id·날짜·day·종류·제목·시각을 읽기 전용 `itinerary_context`로 함께 보낸다. 코어 일정 값은 생성하거나 고치지 않는다.

LLM이 문장의 뜻을 읽는다. 코드는 문장 키워드·정규식으로 필수·선호·부정·적용 대상을 대신 분류하지 않는다. 기존 도구 호출 턴에서 조건을 정리하고 최종 JSON에 목록을 남기므로 별도 모델 호출을 추가하지 않는다.

## 최종 응답의 조건 목록

고객 문장이 있으면 최종 JSON에 `requests` 배열이 필요하다(조건이 없으면 빈 배열).

각 조건은 `request_id`, `quote`(원문 그대로), `attribute`(`halal|vegetarian|kids|card`), `item_ids`, `required`(boolean), `state`(`active|excluded|unclear`)를 가진다. 같은 속성의 여러 표현이 정정되었으면 최종 뜻을 기준으로 정리하고, 인용에는 정정·부정·선호·적용 범위가 드러나는 문맥을 포함한다.

- active: 실제 요청이며 적용 식사 id를 명시한다. 여러 속성이면 각각 기록한다.
- excluded: 필요 없거나 취소된 조건이다. 해당 조건 검사를 활성화하지 않는다.
- unclear: 적용 대상이나 최종 의도가 모호하다. 임의로 모든 식사에 붙이지 않고 확인 불가로 기록한다.

조건 검사에는 `request_id`와 `required`를 명시한다. 원문 인용·항목 id·조건 속성·필수/선호가 목록과 맞고, 해당 속성의 실제 도구 근거가 검증되어야 반영한다. 할랄과 채식을 한 dietary 결과로 대충 묶지 않고 속성별로 확인한다. 비건·알레르기 등 지원하지 않는 속성을 할랄/채식으로 바꾸어 성공 판정하지 않는다.

인용은 원문에서 연속된 최종 효력 문장을 그대로 복사한다. 멀리 떨어진 최초 요청과 취소문을 줄임표로 합치지 않는다. excluded/unclear 조건은 목록에만 남기고 식사별 조건 검사 결과에 붙이지 않는다. 식당 id가 입력에 있어도 `found` 판정에 필요한 실제 `find_place` 반환 id·호출 근거를 확보한다.

코드는 원문 인용이 실제로 존재하는지, 적용 식사가 입력에 있는지, 그 식사의 조건인지, 각 active 조건이 빠짐없이 검사되었는지 확인한다. 문장이 있는데 목록이 없거나 모호함·누락·검증 실패가 있으면 성공으로 숨기지 않고 기존 `missing`·실패 기록으로 드러낸다. 그 와중에도 별도로 검증된 영업 불가 등은 보존한다.

원문 인용 검사는 문장의 뜻이 옳다는 보증이 아니다. LLM이 조건과 목록을 동시에 놓치는 경우와 잘못된 의미 해석은 별도 자유문 평가로 확인해야 한다. 현재 failed/unknown을 다루는 등록 정책은 바꾸지 않는다.

## 경계

제품 변경은 `instances/dining/` 안으로 제한한다. 공통 intake·trip_api·Controller·Case 상태기계·프런트엔드·DB 스키마·운영 설정·기존 평가 holdout은 변경하지 않는다. 시험·평가 실행기와 wiki 기록을 함께 둔다. 시험 전 단계의 실행 보류는 후속 평가 승인으로 해제됐으며, 실제 실행·미실행 범위는 평가 기록을 따른다. 운영 DB·브라우저·배포 검증은 이번 평가 범위가 아니다.
