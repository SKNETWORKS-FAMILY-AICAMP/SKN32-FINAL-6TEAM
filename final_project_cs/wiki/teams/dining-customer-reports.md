# 고객 실시간 제보

`[2026-10-07]` 기준 코드(`role-dining`)를 읽고 작성했다. `dining-mcp-boundary.md` §6-2 에서 이어진다 — SNS 확인을 뺐으므로 **C6(당일 임시 휴무 · 재료 소진 · 대기)의 출처는 「새벽 3시 구글 확인 + 고객 제보」** 이고, 이 문서는 고객 제보를 늘리는 설계다.

**한 줄 요약 — 고객이 문장을 쓰게 하지 않는다. 시각 · 장소 · 일정 항목이 이미 채워진 버튼을 누르게 하고, 그 한 번의 제보를 같은 날 같은 식당을 가는 다른 여행에도 쓴다. LLM 은 거치지 않는다.**

## 0. 지금 무엇이 있나

| 이미 있는 것 | 위치 | 이 설계에서 |
|---|---|---|
| ② 다음 일정 안내 — 지금 일정이 **시작할 때** 나간다 | `trip_reminders.plan_reminders` · `_payload` (`kind="next_item"`, `dedupe_key=next_item:{item_id}`) | ①의 질문을 **여기에 붙인다** (새 알림을 만들지 않는다) |
| 알림 보기 — 웹이 outbox `trip.notice` 를 읽는다. `options` 칸이 이미 있다 | `GET /v1/web/trips/{id}/notices` | ①의 버튼을 `ask` 칸으로 싣는다 |
| 구조화된 신고 API (에이전트용) — `type: delay · closed · stock_out` | `POST /v1/trips/{id}/reports` (`ReportIn`) | 웹용을 같은 모양으로 만든다 |
| 신고 처리 — 늦음 · 휴무 → 대체 식당 → D-020 | `TripDesk.report_delay` · `report_closed` (`gate=True`) | 그대로 쓴다. 단 **항목을 지정**할 수 있게 한다 |
| 요식 관측 표 — 주제(`closure` · `waiting` · `hours` · `vacancy`) · 예/아니오/모름 · 유효기간 · 누가 | `dining.dn_live_check` (206) · `dining.live_state()` (211) · `v_live_check_fresh` | 고객 제보를 **여기에 적는다** (새 출처 `customer_report`) |
| 같은 방문 같은 말은 한 번 | `dining.dn_notice` UNIQUE (212) | ④의 다른 여행 알림이 두 번 가지 않게 쓴다 |
| 새벽 확인이 안 연다고 하면 — 근처 대체 → D-020 | `dawn_check` → `plan_closed_on_day` → `pending.apply_or_ask` | ④에서 「닫힘 확정」이면 **같은 길**을 탄다 |
| 웹 고객 자유 문장 | `POST /v1/web/trips/{id}/messages` → 분류 LLM → 추출 LLM | 버튼 제보는 **이 길을 타지 않는다** |

★지금 웹에는 **구조화된 제보 경로가 없다** — 웹 고객은 문장으로만 알릴 수 있고, 그 문장은 분류 · 추출 LLM 을 두 번 거친다(2026-10-06 실측에서 모델 연결이 끊기면 전부 사람에게 갔다). 버튼 제보는 이 두 단계를 건너뛴다.

★`dn_live_check` 는 지금 **판정(`open_at_slot`)에 쓰이지 않는다** — `dn_notice` 를 낼지 정할 때(212)만 읽힌다. ④는 여기에 「고객 제보를 판정에 반영」을 더하는 일이다.

## 1. ① 도착 시각 질문

### 1-1. 무엇을

식사 일정이 **시작하는 시각**에 나가는 ② 다음 일정 안내에, 그 식당에 대한 질문 한 줄과 버튼을 붙인다.

```
지금 일정: 을지면옥 점심.
다음 일정: 14:00 국립중앙박물관.

을지면옥, 영업 중인가요?   [영업 중이에요]  [닫혀 있어요]  [대기가 길어요]
```

- **새 알림을 만들지 않는다** — 알림 피로를 늘리지 않고, 질문은 원래 나가던 안내에 붙는다.
- **식사(`kind="dining"`) 일정에만** 붙인다. 하루에 많아야 2~3번이다.
- 그날 마지막 일정이라 ②가 안 나가는 식사(다음 일정이 없음)는 **질문만 따로 한 번** 보낸다(`kind="arrival_check"`, `dedupe_key=arrival_check:{item_id}`).

### 1-2. 붙이지 않는 경우

| 경우 | 이유 |
|---|---|
| 그 항목이 답을 기다리는 중(보류 제안, `waiting`) | 이미 「어떻게 할지 골라 주세요」를 묻고 있다 |
| 오늘 그 식당에 **이미 확정된 「닫힘」**이 있다(§3-2) | 물을 것이 없다 — 이미 바꿨거나 묻고 있다 |
| 같은 여행에서 그 항목에 이미 제보가 있다 | 같은 사람에게 두 번 묻지 않는다 |
| 고객이 알림 질문을 껐다(설정) | 선택권 — §6 결정 2 |

### 1-3. 버튼을 누르면

| 버튼 | 적는 것 (`dn_live_check`) | 이 여행에서 일어나는 일 | 고객에게 보이는 답 |
|---|---|---|---|
| 영업 중이에요 | `closure = no` | 없음 | 「알려 주셔서 고마워요. 맛있게 드세요.」 |
| 닫혀 있어요 | `closure = yes` | 지금의 `report_closed` 와 같다 → 근처 대체 식당 → **D-020**(「먼저 물어봐줘」면 묻고, 아니면 바꾸고 알린다) | 바뀐 일정 또는 고를 안 |
| 대기가 길어요 | `waiting = yes` (팀 수를 고르면 `value_num`) | 없음 (일정을 바꾸지 않는다) | 「대기가 길면 근처 다른 식당을 볼까요?」 + [다른 식당 보기] → 누르면 `closed` 와 같은 대체 계산을 **제안으로만** |

- 처리 경로는 §2 의 제보 API 하나다 — 알림 버튼과 일정 카드 버튼이 같은 곳으로 간다.

### 1-4. 바꿀 곳

| 파일 | 바꿀 것 |
|---|---|
| `trip_reminders._payload` | `next_item` 이고 `current.kind == "dining"` 이고 §1-2 에 안 걸리면 `ask` 칸을 더한다: `{"item_id", "place": 이름, "question": "영업 중인가요?", "options": [{"key": "open"}, {"key": "closed"}, {"key": "waiting"}]}` |
| `trip_reminders.plan_reminders` | 그날 마지막 식사(②가 안 나감)에 `arrival_check` 를 만든다 |
| `GET /v1/web/trips/{id}/notices` | 응답에 `ask` 를 그대로 싣는다 |
| 웹 `trip-attention.tsx` | 알림에 `ask` 가 있으면 버튼을 그린다. 누르면 §2 API |

★문구는 기존 규칙대로 **틀 + 원값**(`Phrase`)으로 만든다 — 식당 이름은 값이라 번역을 타지 않는다.

## 2. ② 일정 카드 제보 버튼

### 2-1. 무엇을

웹 여행 화면의 일정 카드에 버튼을 둔다. **그 일정이 지금 「열려 있을 때」만** 보인다.

| 항목 종류 | 버튼 | 보이는 때 |
|---|---|---|
| 식사 | [늦어요 ▾ 10 · 20 · 30분] [닫혀 있어요] [대기가 길어요] | 시작 60분 전 ~ 끝날 때 |
| 체험 · 관람 | [늦어요 ▾] [닫혀 있어요] | 시작 60분 전 ~ 끝날 때 |
| 그 밖 | 없음 (자유 문장 칸은 그대로) | — |

- 시각 · 장소 · 일정 항목이 **이미 채워져** 있어 고객은 문장을 쓰지 않는다.
- 버튼에 없는 말(「주차장이 없어요」 등)은 지금처럼 자유 문장 칸으로 — 분류 · 추출 LLM 이 읽는다.

### 2-2. 제보 API (웹)

```
POST /v1/web/trips/{trip_id}/items/{item_id}/reports
{
  "request_id": "…",                          // 멱등 — 같은 값이면 같은 결과
  "kind": "open" | "closed" | "waiting" | "delay",
  "minutes": 20,                              // delay 일 때만
  "source": "card" | "arrival_check"          // 어디서 눌렀나 (측정용)
}
```

| 검증 | 실패하면 |
|---|---|
| 그 여행이 이 고객 것인가 (`_web_customer` · `_trip_or_404`) | 404 (있는지도 말하지 않는다) |
| 그 항목이 최신 버전에 있는가 | 409 `stale` — 화면을 새로 고치게 |
| 지금이 그 항목의 **제보 창**(시작 60분 전 ~ 끝) 안인가 | 422 `outside_window` |
| `kind` 가 그 항목 종류에 맞는가 (식사만 `open` · `waiting`) | 422 |
| 같은 고객의 같은 항목 · 같은 `kind` 제보가 이미 있나 | 이전 결과를 돌려준다 (두 번 적지 않는다) |
| 고객당 제보 수 (예: 하루 20건) | 429 |

### 2-3. 처리

```
제보 API
  ├─ dining 항목이면 dn_live_check 에 한 줄 (§3-1) — 「누가」는 해시만
  ├─ kind 별
  │    closed  → TripDesk.report_closed(trip_id, item_id=…)   ← 항목 지정 인자 추가
  │    delay   → TripDesk.report_delay(trip_id, item_id=…, minutes)
  │    waiting → 기록 + 「다른 식당 볼까요?」 답
  │    open    → 기록 + 감사 답
  └─ dining 이고 closed 면 → 공유 작업 예약 (§3-3)
```

★**`report_closed` · `report_delay` 에 `item_id` 를 받게 한다.** 지금은 「그 시각에 걸친 식사」 · 「그 시각 뒤 첫 식사」를 시간으로 고른다(`trip_desk.py`). 카드 버튼은 고객이 **어느 항목인지 이미 가리켰으므로** 시간으로 다시 추측하지 않는다. 인자가 없으면 지금처럼 시간으로 고른다(자유 문장 · 에이전트 API 호환).

★기존 Case 기록은 그대로 남긴다 — 자유 문장 경로와 같은 `TripDesk` 를 타므로 결정 기록 · 통지 · D-020 이 같다. 다른 점은 **분류 · 추출 LLM 을 거치지 않는다**는 것뿐이다.

## 3. ④ 제보 공유 — 한 사람의 「닫혀 있어요」를 다른 여행에

### 3-1. 기록 — `dn_live_check` 에 새 출처

```sql
-- 새 마이그레이션 (예: 228_dining_customer_report.sql — 221 은 이미 221_dining_core_promote.sql 이다, 2026-10-10 기준 마지막은 227)
INSERT INTO dining.dn_source (source_code, display_name, source_kind, storage_mode, production_allowed, note)
VALUES ('customer_report', '고객 현장 제보', 'operator', 'content', true,
        '여행자가 현장에서 누른 버튼. 그날 하루만 유효하다.');
```

| 칸 | 값 |
|---|---|
| `place_uid` | 항목의 `place_id` → `dn_core_place_link` 로 이은 원장 식당. 이어지지 않았으면 **적지 않는다**(공유할 대상이 없다) |
| `topic` · `value_state` | `closure` + `yes`(닫힘) / `no`(영업 중), `waiting` + `yes` |
| `target_at` | 그 일정의 시작 시각 |
| `ttl_seconds` | **그날 끝(KST 24:00)까지** 남은 초 (최소 60) — 오늘의 휴무는 내일의 사실이 아니다 |
| `checked_by` | `sha256(tenant_id + customer_id)` 앞 16자 — **누가 했는지는 남기지 않고, 서로 다른 사람인지만 센다** |
| `outcome` | `ok` |
| `evidence` | `card` / `arrival_check` (어디서 눌렀나) |

### 3-2. 판정 규칙 — 몇 명이 말하면 믿나

같은 식당 · 같은 날의 **유효한** `customer_report` 제보만 센다.

| 「닫힘」 제보 (서로 다른 사람) | 「영업 중」 제보 (가장 최근 「닫힘」 뒤) | 그날 다른 여행의 판정 |
|---|---|---|
| 0 | — | 원장 그대로 |
| 1 | 없음 | **확인 필요** — 일정은 바꾸지 않고 알린다 (§3-3) |
| 1 | 있음 | 원장 그대로 (엇갈림 — 기록만) |
| **2 이상** | 없음 | **불가 (닫힘 확정)** — 새벽 확인이 「안 연다」고 한 것과 같은 길 |
| 2 이상 | 있음 | 확인 필요 |

- ★**제보한 본인의 여행은 1건으로도 바로 처리한다** — 지금 신고 경로와 같다(본인이 현장에서 본 것이다).
- ★**한 사람의 제보로 다른 사람의 일정을 바꾸지 않는다** — 장난 · 잘못 누름을 막는다. 1건이면 「확인 필요」 알림까지만.
- 2명 기준은 시작값이다. 오탐 · 미탐을 보고 조정한다(§5 측정).

**판정에 넣는 자리** — DB 함수(`open_at_slot`)는 건드리지 않고, 파이썬 `ledger.dining_state` 가 원장 판정 뒤에 제보를 읽어 얹는다:

```python
reports = customer_closure(conn, place_uid, day)     # {"closed": 2, "open_after": 0}
if reports["closed"] >= 2 and not reports["open_after"]:
    state["open_at_slot"] = False
    state["source"] = "customer_reports"
elif reports["closed"] >= 1:
    state["needs_check"] = True
    state["customer_report"] = {"closed": reports["closed"], "open_after": reports["open_after"]}
```

이러면 **Team 판정 · 대체 후보 거르기 · 웹 화면 · 플래너가 모두 같은 값**을 본다 — 이미 모두 `dining_state(s)` 를 거친다. 대체 후보에서도 「오늘 2명이 닫혔다고 한 식당」이 자동으로 빠진다.

### 3-3. 다른 여행에 알리기 — 공유 작업

제보 요청 안에서 다른 여행까지 계산하면 제보한 사람의 응답이 느려진다. **스위퍼로 돌린다**(`scripts/run_sweepers.py --only dining_reports`, 다른 스위퍼와 같은 방식).

```
1. 오늘 새로 들어온 closure 제보가 있는 식당(place_uid)을 찾는다
2. 그 식당이 **오늘 아직 시작 전**인 식사 항목을 가진 여행을 찾는다 (dn_core_place_link → 코어 장소 → 일정)
     ★제보한 본인 여행은 뺀다 (이미 처리됐다)
3. 여행마다 §3-2 판정
     확인 필요  → 알림 한 번: 「오늘 ○○식당이 쉰다는 제보가 있어요. 확인 중이에요 — 일정은 그대로예요.」
                  + [다른 식당 보기] (누르면 대체 안을 제안으로)
     닫힘 확정  → plan_closed_on_day → pending.apply_or_ask (D-020) — 새벽 확인과 같은 길
4. 같은 말은 한 번 — dn_notice UNIQUE(place_uid, target_at, kind) + outbox dedupe
```

- 「확인 필요」 알림을 받은 여행은 그 식사 시각이 되면 **①의 도착 질문**을 받는다 — 그 답이 다시 제보가 되어 판정을 확정하거나 뒤집는다. ①과 ④가 서로를 채운다.
- 이미 그 식사가 시작된 여행 · 이미 그 식당을 다른 곳으로 바꾼 여행 · 답을 기다리는 여행은 건너뛴다.

### 3-4. 테넌트 경계 — 결정 필요

`dining.dn_place` 는 테넌트 없이 하나인 원장이다(식당은 공공의 사실). 제보는 **「이 식당이 오늘 닫혔다」는 장소의 사실**이고, 누가 제보했는지는 해시로만 남는다.

| 안 | 장점 | 걱정 |
|---|---|---|
| A. 같은 테넌트 안에서만 공유 | 경계가 단순하다. 보안 규칙(`CLAUDE.md` §1 tenant 범위)과 충돌이 없다 | 테넌트가 작으면 같은 날 같은 식당을 가는 여행이 거의 없다 |
| B. 장소 사실은 테넌트를 넘어 공유, 개인 정보는 공유 안 함 | 공유 효과가 크다 | 「다른 회사 고객의 행동이 우리 판정에 들어온다」 — 정책 결정이 필요하다 |

**제안 — A 로 시작한다.** `checked_by` 해시에 테넌트를 섞어 두면(§3-1) 나중에 B 로 넓힐 때도 표를 바꾸지 않는다.

## 4. 안전장치

| 위험 | 막는 것 |
|---|---|
| 장난 · 잘못 누름 | 다른 사람 일정은 1건으로 바꾸지 않음(§3-2), 제보 창(시작 60분 전 ~ 끝) 밖은 거절, 고객당 하루 상한 |
| 같은 사람이 여러 번 | `checked_by` 로 서로 다른 사람만 셈, 같은 항목 · 같은 `kind` 는 한 번 |
| 오래된 제보 | 그날 24:00 에 만료(`ttl_seconds`) — `v_live_check_fresh` 가 이미 기한을 거른다 |
| 알림 피로 | ①은 새 알림이 아니라 ②에 붙임, 식사에만, 같은 항목에 한 번. ④의 「확인 필요」 알림은 같은 방문에 한 번(`dn_notice`) |
| 고객 선택 무시 | 모든 일정 변경은 D-020 을 지난다 — 「먼저 물어봐줘」 · 「변경 안 할 일정」이면 묻는다 |
| 개인 정보 | 제보 표에 고객 id · 문장을 남기지 않는다(해시만). 다른 여행 알림에 「누가」를 말하지 않는다 |
| 원장 오염 | 제보는 `dn_live_check`(유효기간 있는 관측)에만 적고 영업시간 규칙(`dn_hours_rule`)은 건드리지 않는다 |

## 5. 측정

| 지표 | 뜻 | 어디서 |
|---|---|---|
| 도착 질문 응답률 | ①의 질문에 버튼을 누른 비율 | `evidence = arrival_check` 제보 수 / 질문 붙은 ② 알림 수 |
| 제보 경로 비율 | 버튼(카드 · 질문) vs 자유 문장 | 제보 API vs `/messages` 의 늦음 · 휴무 |
| 자유 문장 LLM 실패 감소 | 버튼으로 옮겨 간 만큼 `report_not_understood` · 모델 오류가 줄었나 | Case `failure_code` |
| 공유로 지킨 여행 | ④에서 「확인 필요」 · 「닫힘 확정」 알림을 받은 여행 수 | 공유 작업 결과 |
| 오탐 | 「닫힘 확정」 뒤 같은 날 「영업 중」 제보가 들어온 비율 | `dn_live_check` |
| 원장 정확도 | 「영업 중이에요」 · 「닫혀 있어요」가 원장 `open_at_slot` 과 맞은 비율 | 제보 × 원장 판정 — **C1~C5 판정의 실측 정확도**가 된다 |

★마지막 지표가 덤으로 생긴다 — 지금은 원장 판정이 현장에서 맞았는지 알 길이 없다. ①의 「영업 중이에요」가 그 답이다(평가 사이클의 정답 데이터).

## 6. 결정이 필요한 것

1. **공유 범위** — §3-4 A(같은 테넌트) / B(테넌트 넘어 장소 사실만). 제안: A.
2. **도착 질문 끄기 설정** — 설문 항목에 넣을까, 웹 설정에 둘까, 처음엔 없이 갈까.
3. **닫힘 확정 기준** — 서로 다른 2명(제안). 테넌트가 작아 2명이 잘 안 모이면 「1명 + 새벽 구글 판정이 모름」을 확정으로 볼지.
4. **「대기가 길어요」의 대기 팀 수** — 버튼만(예/아니오)으로 갈지, [5팀 미만 · 5~10 · 10팀 이상]을 고르게 할지.
5. **체험 · 관람에도 ①을 붙일까** — 이 문서는 식사만. 체험은 Activity 팀 판단.

## 7. 바꿀 곳 · 시험 · 순서

### 7-1. 바꿀 곳

| 구분 | 파일 | 내용 |
|---|---|---|
| DB | `migrations/228_dining_customer_report.sql` (새로 · 만들 때 마지막 번호를 다시 본다) | `dn_source` 에 `customer_report` |
| 원장 | `dining/ledger.py` | `record_report()` · `customer_closure()` · `dining_state` 에 제보 얹기 |
| 신고 | `trip_desk.py` | `report_closed` · `report_delay` 에 `item_id` 인자 (없으면 지금처럼) |
| API | `trip_api.py` | `POST /v1/web/trips/{id}/items/{item_id}/reports`, `notices` 응답에 `ask` |
| 알림 | `trip_reminders.py` | ②에 `ask`, 마지막 식사의 `arrival_check` |
| 공유 | `dining/report_share.py` (새로) + `scripts/run_sweepers.py` | §3-3 |
| 웹 | `features/trip/trip-home.tsx` · `trip-attention.tsx` | 카드 버튼 · 알림 버튼 |

### 7-2. 시험

| # | 시험 |
|---|---|
| R1 | ②가 식사 일정이면 `ask` 가 붙고, 답을 기다리는 항목 · 이미 제보한 항목 · 닫힘 확정 식당에는 안 붙는다 |
| R2 | 그날 마지막 식사는 `arrival_check` 를 한 번만 만든다 (같은 키 두 번 → 한 번) |
| R3 | 제보 API — 남의 여행 404, 낡은 항목 409, 창 밖 422, 같은 `request_id` 는 같은 결과, 상한 429 |
| R4 | `closed` 버튼은 **지정한 항목**을 바꾼다 (같은 시각에 다른 식사가 있어도) — `item_id` 인자 |
| R5 | `open` · `waiting` 은 일정을 바꾸지 않는다 |
| R6 | 판정 규칙 표(§3-2)의 다섯 줄 그대로 — 1명이면 확인 필요, 서로 다른 2명이면 불가, 뒤에 「영업 중」이 오면 내려가지 않음 |
| R7 | 같은 사람이 두 번 눌러도 1명으로 센다 (`checked_by`) |
| R8 | 제보는 그날 24:00 에 만료된다 — 다음 날 판정에 안 들어간다 |
| R9 | 공유 작업이 본인 여행 · 이미 시작한 식사 · 이미 바꾼 여행 · 답을 기다리는 여행을 건너뛴다 |
| R10 | 닫힘 확정 공유도 D-020 을 지난다 — 「먼저 물어봐줘」 여행은 묻고, 「변경 안 할 일정」은 바꾸지 않는다 |
| R11 | 같은 방문에 「확인 필요」 알림은 한 번 (`dn_notice` · outbox dedupe) |
| R12 | 다른 테넌트의 제보는 판정에 들어가지 않는다 (§3-4 A 기준) |
| R13 | 제보 표 · 알림에 고객 id · 이름이 없다 |

### 7-3. 순서

| 단계 | 할 일 | 효과가 보이는 것 |
|---|---|---|
| 1 | 제보 API + `item_id` 인자 + 카드 버튼 (②) | 웹 신고가 LLM 없이 처리된다 |
| 2 | 도착 질문 (①) | 고객이 먼저 말하기 전에 묻는다 · 원장 정확도 데이터가 쌓인다 |
| 3 | 제보 기록 + 판정 반영 (§3-1 · §3-2) | 대체 후보에서 「오늘 닫힌 곳」이 빠진다 |
| 4 | 공유 작업 (§3-3) | 다른 여행이 헛걸음하지 않는다 |
