멘토 확인이 필요하다. P0는 "단일 에이전트 + 읽기 전용 MCP 도구 5개(장소 조회, 운영 정보, 장소 실재, 재난 사실, 대안 검색) + 코드 게이트 + HITL"이다.

### D2. 재난 영향 기준 충돌 `[결정 필요]` — 가장 중요

- 수정본 §8: 산사태 = **지역 위험형** → 해당 구 전체(실내 포함)를 막는다.
- 테스트 ④(종로구 인왕산 등산로 산사태 vs 경복궁): 기대는 LLM `no_effect`.
- EVAL-A4는 "분류별로 채점"이라서 분류표대로 `blocks`가 정답이 되고, 올바른 LLM 답이 오답으로 채점된다.

| 안 | 내용 |
|---|---|
| a | 분류표를 따른다 (LLM 관련성 판단을 끈다) |
| b | LLM 관련성 판단을 따른다 (분류표는 힌트로만) |
| **c (권장 구현)** | 둘 다 기록한다 (분류표 결과 + LLM 결과), 고객 결과는 보수적인 쪽 |

결정은 b 방향을 권한다. 안전 비대칭을 둔다: LLM이 "막지 않음"으로 완화하려면 **인용이 반드시 있어야** 하고, 확신이 낮으면 막는다.

### D3. 정원 초과 `[결정 필요]`
유스케이스는 "판정 항목이 아님"으로, 코드·LLM 계획서는 `problem`으로 본다. 한쪽으로 정리한다. 정원 데이터(capacity)는 TourAPI 추가 컬럼이라 비어 있는 경우가 많다.

### D4. 결과 상태를 계약에 맞추기 `[코어 협의]`

### D5. 종류별 LLM 전환 `[결정 필요]`

### 2.5-B 계획 검증 흐름 (UC-A3, 고객이 일정을 넣을 때)

에이전트가 도구를 부르는 순서가 그림의 가로 흐름이다. 장소 조회에서 DB에 없으면 외부 도구(카카오)로 실재만 확인한다 (응답 저장 금지).

```mermaid
flowchart TD
    A["코어가 일정 전달: 장소, 방문 시각"] --> B["에이전트: 장소 조회 도구 (DB)"]
    B -->|DB에 있음| C{"실내외 값이 있나"}
    B -->|DB에 없음| K["외부 대체 도구: 카카오로 장소 실재 확인"]
    K -->|실재함| U["확인 필요로 응답: 운영 정보 없음, DB에 적재하지 않음"]
    K -->|맞는 이름 없음| N["장소 이름 되묻기 (최대 2회)"]
    K -->|여러 곳| P["후보를 보여 주고 선택"]
    K -->|조회 못 함| E["담당자에게 넘김 (없음으로 단정하지 않음)"]
    C -->|있음| D["운영 정보 조회: TourAPI 원문"]
    C -->|없음| L["LLM 1회 판정"]
    L -->|확정| S["places에 실내외 적재"]
    L -->|확정 못 함| Q["고객에게 실내 또는 실외인지 묻기"]
    Q --> S
    S --> D
    D --> F["코드 게이트: 시작됨, 정원, 정기휴무, 운영시간"]
    F -->|문제 없음| R["재난 사실 확인: 지금 발령 중인 것만"]
```

|---|---|---|
| DB에 있음, 실내외 있음 | 운영 정보 → 게이트 → 재난 확인 | 규칙 판정 (분류표 + 실내외) |
| DB에 있음, 실내외 없음 | LLM 1회 판정 → 적재. 확정 못 하면 **고객에게 묻고** 적재 | **묻지 않음**, 판정 보류 기록 `[결정 필요]` |
| DB에 없음, 카카오에 실재 | 확인 필요 (운영 정보 없음), 적재 안 함 | 해당 없음 (입력 장소는 감시 루프가 DB에서 찾아 줌) |
| DB에 없음, 카카오에 없음 | 이름 되묻기 (최대 2회) | 해당 없음 |
| 여러 곳을 가리킴 | 후보 제시 | 해당 없음 |
| 카카오 조회 실패 | 담당자에게 넘김 | 해당 없음 |
| 운영 원문이 비어 있음 | 휴무 판정 건너뜀. "확인 필요"로 올릴지 미정 | TourAPI 변화 감지 대상에서 제외 |
| 방문이 한참 뒤 | 재난은 **지금 발령 중인 것만** 확인. "미확인" 단서 없음 | 사실 변화가 있을 때만 호출 |
| 지역 위험형 재난 | 구 전체(실내 포함) 영향 | 동일 |
| 야외 위험형 재난 | 실외 장소만 영향 | 동일. 실내외 값 없는 장소는 보류 |
| 재난 해제 | 해당 없음 | 변화로 기록, 앞서 알렸다면 재판정 (해제 알림은 `[미확보]`) |

> 감시 루프의 "판정 보류" 처리는 멘토 메모에 없는 부분이라 내가 채운 안이다. 값이 없는 장소를 영향 있음으로 볼지, 보류로 둘지는 안전 측면에서 정해야 한다.

### 2.5-F 남은 의문

1. 실내외를 일괄 적재(사전)할지, 처음 쓰일 때 적재(지연)할지: 지연 방식은 실제 쓰이는 장소만 비용이 든다. 시연 장소는 미리 데워 두는 것을 권한다.
2. 적재 컬럼은 `places`에 없다. 데이터베이스 설계 문서(`activities`/`tour`/`disaster` 물리 테이블)의 변경이 필요하다. `[코어 협의]`
3. "3시간 창"을 없애면 재난문자 수집은 소스당 3분 주기(WS-3.2)만 남는다. 기존 활동별 5분 감시(3.5)의 퇴역은 그대로 간다.

## 8. 작업자 A · B 분담 `[제안 2026-10-10]`

**한 줄로 나누면:** A는 장소 정보를 모으고 빈칸을 채운다. B는 그 정보로 「이 일정이 되는지」를 판단하는 부분을 만든다.

### 작업자 A — 장소 정보 모으고 채우기

1. **비어 있는 정보가 얼마나 되는지 센다.** 운영시간, 쉬는 날, 정원, 걸리는 시간, 나이 제한, 예약 방법, 실내인지 실외인지를 장소마다 확인한다. 그리고 항목마다 어떻게 채울지 정한다 — 규칙으로 자동 채움 / LLM으로 채움 / 사람이 직접 입력 / 채우지 않음.
2. **실내·실외 값을 저장할 자리를 DB에 만든다.** 지금 DB에는 실내·실외 값만 넣는 칸 하나뿐이라, 「누가 · 언제 · 어떻게 정했는지」까지 남길 칸을 더한다.
3. **AI 기술을 어디에 쓸지 정리한다.** 작은 LLM, 문서 검색(RAG), 모델 추가 학습, 의미 검색용 DB를 각각 쓸 곳이 있는지, 1번 결과와 비용 · 속도를 근거로 판단 자료를 만든다. **쓸 곳이 있다고 정해진 것만** 실제로 데이터를 넣고 검색이 잘 되는지 확인한다.
4. **재난문자를 주기적으로 모으는 기능**을 만든다.

### 작업자 B — 「이 일정이 되는가」 판단 만들기

1. **LLM 판단이 얼마나 정확한지 다시 잰다.** 지금 정답표는 Claude가 만든 것이라, 사람이 먼저 확인한다. 확인된 정답으로 정확도 · 비용 · 걸리는 시간을 다시 재서 A와 함께 본다.
2. **실내·실외를 LLM으로 처음 한 번만 판단하는 기능**을 만든다. 판단 결과는 A가 만든 저장 자리에 넣고, 그 뒤로는 저장된 값을 쓴다.
3. **에이전트가 장소 · 운영 정보를 찾을 때 검색을 쓰게 연결한다.** A가 3번에서 「검색을 쓴다」고 정했을 때만 한다.
4. **답변 결과 모양을 팀 공통 약속에 맞춘다.** 지금 「정보 부족」 같은 값은 공통 약속(계약)에 없는 값이라 정리가 필요하다(D4).
5. **재난 종류별로 어디까지 막을지 정한 표를 판단에 넣는다**(D2).

### 함께

- 마지막에 `develop` 브랜치로 합치고, 문서를 정리한다.

### 시작 전에 알아둘 것

- **A는 정보 수집부터 돌려야 한다.** 정원 · 걸리는 시간 · 나이 제한 · 예약 방법은 모으는 프로그램만 있고 아직 한 번도 안 돌려서 전부 비어 있다. 운영시간 · 쉬는 날은 새벽에 자동으로 읽어 오는 기능이 이미 있는데(새벽 3~8시, 하룻밤 600곳), 내 컴퓨터에서는 아직 안 돌았다. 돌리려면 관광공사 API 키가 필요하다.
- **B의 실내·실외 기능은 팀 결정부터 바꿔야 한다.** 어제 정한 결정(D-CS-015)은 「실내·실외 LLM 판단은 비교용으로만 돌리고 저장하지 않는다」였다. 멘토 의견(처음 한 번 판단해서 저장)대로 하려면 이 결정을 고쳐야 한다.
- **B가 내는 정확도 수치는 정답표 확인이 끝난 뒤에 쓴다.** 지금 숫자는 Claude가 만든 정답 기준이다. 규칙으로 판단한 쪽은 지난번에 다시 쟀고(52건 중 26건 맞음), LLM 쪽은 아직 다시 안 쟀다.
