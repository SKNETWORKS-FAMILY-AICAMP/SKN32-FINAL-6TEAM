# Dining 하이브리드 분류표

`[2026-10-07]` 기준 코드(`role-dining`)를 읽고 작성했다. 설계 문서 `dining-agent-design.md` §2 「MCP 도구로 바꿔 LLM 손에 쥐여 준다」를 **실제로 LLM 이 필요한 곳만 남기도록** 다시 따진 결과다.

**한 줄 요약 — 체크리스트 C1~C5 는 지금처럼 원장으로 코드가 판정한다. LLM 에이전트(MCP 도구)는 「코드 갈래에 맞지 않는 자유 질문」 하나에만 쓴다. 그것도 먼저 빈도를 재고 나서 만든다.**

---

## 0. 왜 이렇게 줄였나

### 0-1. 판단 기준 — 「LLM 이 코드보다 더 알아낼 것이 있나」

LLM 을 붙이면 응답이 밀리초 → 수 초로 느려진다(호출 1회 수 초 × 도구 왕복 2~5회). ★지연 실측값은 아직 없다 — 2026-10-06 gemma4:e4b 실행은 Ollama 연결이 끊겨 성공한 호출이 4건뿐이었다(2.7초 · 3.8초 · 30초 · 33초, 뒤의 둘은 모델 적재 포함). 그 비용을 갚으려면 **코드가 못 얻는 정보나 판단**을 LLM 이 더해야 한다. 처음 판의 호출 조건 넷(H1~H4)을 이 기준으로 다시 봤다.

| 처음 조건 | 세부 | LLM 이 더할 수 있는 것 | 결론 |
|---|---|---|---|
| H1 코드 판정이 「모름」 | 원장에 영업 정보 없음 (`open_at_slot=None`) | 같은 원장을 다시 읽어도 모름. 「가능」으로 올릴 수도 없음 | **뺀다** |
| | 원장에 이어지지 않은 장소 | 읽을 자료 자체가 없음 | **뺀다** |
| | 라스트오더 임박 (`needs_check`) | 「몇 시까지 오면 된다」는 영업시간 · 라스트오더로 **계산**된다 | **뺀다** → 코드 개선(§6) |
| | 명절 규칙 모름 (`needs_holiday_check`) | 공휴일 여부는 원장이 이미 안다. 남는 것은 SNS 공지 찾기뿐 | **뺀다** (SNS 를 뺐으므로, §0-2) |
| H2 자유 질문 | 코드 갈래에 안 맞는 질문 | 여러 체크 항목을 조합해야 하는 열린 질문은 **도구를 골라 쓰는 판단**이 필요하다 | **남긴다 (Q)** — 단 빈도부터 잰다 |
| H3 오늘 · 내일 식당 질문 | 당일 신호(C6) | 구글 실시간은 「부를지」만 정하면 코드가 부른다. 남는 것은 SNS 뿐 | **뺀다** |
| H4 대체 후보 순서 | 동행 조건 반영 | 조건(결제 · 식단)은 이미 코드가 **탈락**으로 거른다. 「좌석 넉넉」 같은 이유를 받칠 데이터가 원장에 없다 — LLM 이 이유를 지어낸다 | **뺀다** → 필요하면 코드 정렬 규칙(§6) |

### 0-2. SNS 확인을 뺀 이유

네이버 검색 키(API HUB 블로그 · 카페글, `core/settings.py` 의 `naver_search_*`)는 있어서 **호출은 가능**하다. 하지만 C6(당일 임시 휴무 · 재료 소진)를 잡는 데는 쓸모가 낮다고 판단했다.

| 문제 | 설명 |
|---|---|
| 공지는 블로그에 없다 | 사장님 공지는 인스타그램 · 네이버 플레이스 「소식」 · 문 앞 안내문에 올라온다. 블로그 · 카페글은 대부분 손님의 **방문 후기**다 |
| 공지가 있는 곳은 쓸 수 없다 | 인스타그램은 남의 계정 글을 찾는 공개 API 가 사실상 없고, 플레이스 소식은 API 가 없으며 수집은 약관 위반이다 |
| 늦다 | 후기는 다녀온 뒤 올라온다. 「오늘 쉰다」가 당일에 검색될 가능성이 낮다 |
| 정확하지 않다 | 같은 이름 다른 지점 · 작년 글 · 광고가 섞이고, 결과는 제목과 짧은 요약뿐이다. 카페글은 날짜도 확인하기 어렵다 |

**C6 는 지금처럼 「새벽 3시 구글 확인(특별 영업시간 포함) + 고객 제보」로 간다.** 고객 제보를 늘리는 방법은 §6-2.

## 1. 흐름과 LLM 호출 조건

### 1-1. 흐름

```
여행자 질문 · 신고 · 새벽 점검
        │
        ▼
 ┌────────────────────────────────┐
 │ ① 코드 경로 (지금 그대로)        │  접수 LLM(분류 · 신고 추출) → 원장 open_at_slot · dining_fits
 │    판정: 가능 / 불가 / 확인 필요   │  → 후보 탈락 규칙 → 답 또는 일정 변경 제안
 └───────────────┬────────────────┘
                 │
         라우터: 코드 갈래에 맞지 않는 자유 질문(Q)인가?
         ├─ 아니오 (대부분) ─────────────────────────▶ ③ 코드 결과로 답 · 적용
         └─ 예
                 ▼
 ┌────────────────────────────────┐
 │ ② LLM 에이전트 (MCP 도구, A 구역만) │  질문에 필요한 체크 항목(C1~C5)을 골라 도구로 확인
 │    (Q 비율을 잰 뒤 만들지 정한다)  │  호출 상한 · 시간 상한 안에서
 └───────────────┬────────────────┘
                 ▼
         가드: 판정 방향(§5) — 코드 판정보다 좋아질 수 없다
                 │       (LLM 실패 · 시간 초과면 ① 결과 그대로 = 지금처럼 사람 상담원)
                 ▼
         ③ 적용 (코드): D-020 판정 문 → 적용 직전 대조 → 일정 새 버전 · 통지
```

### 1-2. 호출 조건 Q — 코드 갈래에 맞지 않는 자유 질문

| 언제 | 코드에서 어떻게 아나 |
|---|---|
| 접수 LLM 이 고객 문장을 신고 갈래(늦음 · 휴무 · 품절 · 재요청 · 질문)로 읽지 못했다 | `failure_code = report_not_understood` |
| 질문 갈래인데 코드가 답하지 못해 사람에게 넘겼다 | `request_type = question` 또는 `capability = dining.itinerary_question`, 그리고 `outcome = escalated` |

**부르지 않는 경우** — 코드가 답한 모든 요청(「가능」 · 「불가」 · 「확인 필요」 포함), 원장이 「모름」인 요청(LLM 도 같은 원장을 읽는다), 예약 · 일정 · 신고 내용이 없는 요청(고객에게 물을 입력이다), 새벽 3시 일괄 점검, 고객이 고른 안 적용 · 되돌리기(실행 경로).

**먼저 잰다 — 새 코드 없이.** Q 에 걸리는 요청은 지금 사람 상담원에게 가고, 그 사유가 이미 `case_events` 에 남는다(`GUARDRAIL_ESCALATED` 의 `guardrail` = `report_not_understood` · `unknown_관련 규정`). 이것을 식당 Case 수로 나누면 **Q 가 전체 요청의 몇 %인지** 나온다. 그 비율을 보고 에이전트를 만들지 정한다. 드물면 지금처럼 사람에게 넘기는 것이 낫다.

★`[2026-10-07]` 처음엔 `DiningTeam.execute` 가 결과의 `decisions` 에 라우터 기록을 붙이게 만들었다가 되돌렸다 — Controller 가 Team 결과의 `decisions` 를 저장하지 않아 운영에서는 기록이 남지 않았고, 같은 수치를 이미 저장되는 사유로 셀 수 있었다. 라우터 · 판정 방향 가드 코드는 에이전트를 실제로 만들 때 넣는다.

**Q 를 줄이는 다른 길** — 자주 나오는 질문 유형이 보이면 에이전트보다 **접수 LLM 의 추출 갈래를 넓히는 것**이 먼저다(예: 「식당 영업 질문」 갈래 + 장소 · 시각 칸 → 답은 코드가 낸다). 에이전트는 갈래로 정리되지 않는 질문에만 남긴다.

## 3. 코드 유지 — LLM 에게 주지 않는 것

가르는 질문 — 하나라도 「예」면 코드에 남긴다.

| # | 질문 | 예 |
|---|---|---|
| Q1 | 상태를 바꾸는가 | 일정 새 버전, 통지, Case 상태 |
| Q2 | 틀리면 되돌릴 수 없거나 고객이 바로 피해를 보는가 | 보낸 알림, 바뀐 일정 |
| Q3 | 고객이 이미 정한 것을 뒤집을 수 있는가 | 설문 15번 「먼저 물어봐줘」, 「변경 안 할 일정」 |
| Q4 | 보안 · 약관 · 비용 경계인가 | tenant 범위, 구글 원값, 호출 예산 |
| Q5 | 정답이 규칙으로 하나로 정해지는가 | 도보 분, 겹침, 버전 대조, 라스트오더 |

- **일정 쓰기 · `settle`** — 기준 버전 대조(`ActionConflict`), 남의 여행 거절, 멱등 키. LLM 은 제안만 하고, 그 제안도 지금 경로(`ActionProposal` → 적용기)를 탄다.
- **D-020** — 고객이 설문 15번으로 정한 것이다. 안전 범주(`SAFETY_CATEGORIES`)도 사용자와 합의한 목록이다. LLM 은 `protected` 칸을 보고 「고정하신 일정이라 여쭙니다」라고 말할 수는 있어도 갈래는 코드가 가른다.
- **범위 · 예산 · 약관** — tenant · customer · case · trip 은 서버가 주입하고 도구 스키마에 칸이 없다. 구글 값은 판정 · 비교 결과만 남긴다 — **LLM 에게 보여 준 값은 답변에 옮겨 쓰여 Case 근거로 저장될 수 있다.**
- **판정 · 탈락 규칙** — 계산이다. 에이전트 경로가 끝난 뒤에도 가드로 한 번 더 돈다.

## 4. A. 사실 조회 도구 — 에이전트(Q)가 고르는 것

공통: 결과에 `source` · `confirmed_at` · `status`(known / unknown). `None` 은 「모름」, 빈 목록은 「없음을 앎」.

| 도구 | LLM 이 채우는 인자 | 서버가 주입 · 검증 | 돌려주는 것 | 빼는 것 · 주의 |
|---|---|---|---|---|
| `itinerary.read` | 없음 | `trip_id` = Case 의 `subject_ref.id` | 버전 · 항목 · 항목별 `protected` | 예약 금액 · 예약번호 원문 |
| `dining.state_at` | `place_id`, `at`, `until?` | `place_id` 허용 집합, `at` 이 여행 기간 안 | `open_at_slot` · `needs_check` · `needs_holiday_check` · 브레이크 · `confirmed_at` · `linked` | — |
| `calendar.holiday` | `date` | — | 공휴일 · 명절 여부 | 「공휴일이다」≠「그 가게가 쉰다」(`answers_whether_the_place_is_closed: false`) |
| `dining.conditions` | `place_id` | 허용 집합 | `met` · `not_met` · `unknown` | `[2026-10-06]` `_conditions` 결함과 같은 실수를 구조로 막는다 |
| `dining.find_place` | `name`, `near?` | — | `found` · `ambiguous` · `exists_unregistered` · `not_found` · `unknown` + 원장 `place_id` | 카카오 응답 원문은 싣지 않는다 |
| `dining.place_status` (새로) | `place_id` | 허용 집합 | 원장의 폐업 · 이전 · 장기 휴업 · 확인 시각 | 실시간 구글 호출 없음 |

**인자 규칙**

| 인자 | 누가 | 이유 |
|---|---|---|
| `tenant_id` · `customer_id` · `case_id` · `trip_id` | 서버 (스키마에 없음) | 다른 고객 · 여행을 읽지 못하게 |
| `place_id` | LLM, 서버가 **허용 집합** 검증 | 허용 집합 = 이 여행 항목의 장소 ∪ 이번 Case 의 `find_place` 결과 |
| `at` · `until` · `date` | LLM, 서버가 여행 기간 안인지 검증 | 「어느 시각을 볼지」가 에이전트 판단의 핵심 |
| 지금 시각 · 코드 판정 | 서버 (프롬프트 입력) | LLM 은 시각을 모른다. 같은 조회를 반복하지 않게 |

## 5. 판정 방향 — 코드 판정 × LLM 판정 → 최종

| 코드 판정 | LLM 판정 | 최종 | 비고 |
|---|---|---|---|
| 무엇이든 | 실패 · 시간 초과 | 코드 판정 그대로 | 지금 동작과 같다 |
| 불가 | 무엇이든 | **불가** | LLM 이 원장을 뒤집지 못한다 |
| 확인 필요 | 가능 | **확인 필요** | LLM 은 올리지 못한다 (경고를 남긴다) |
| 가능 · 확인 필요 | 더 낮음 (확인 시각 붙은 근거 있음) | LLM 판정 | 원장 · DB 사실로 내렸다 |
| 가능 · 확인 필요 | 더 낮음 (근거 없음) | 코드 판정 + 경고 | 참고로만 남긴다 |

**최종 판정은 코드 판정보다 좋아질 수 없다.** (에이전트를 만들 때 코드 가드로 구현한다.)

---

## 6. 코드로 개선할 것 (LLM 대신)

### 6-1. 판정 문구 · 정렬

| 항목 | 지금 | 개선 |
|---|---|---|
| 라스트오더 임박 (`needs_check`) | 경고 「마지막 주문을 확인해야 한다」 | 원장 영업시간 · 라스트오더로 「HH:MM 까지 도착하면 주문할 수 있어요」를 **계산**해 답한다 |
| 명절 규칙 모름 (`needs_holiday_check`) | 경고 「영업시간이 다를 수 있다」 | `holiday_context` 의 확인할 곳(전화 · 공지)을 템플릿으로 안내한다 |
| 동행 조건 순서 | 거리 · 가격 순 | 근거 데이터가 있는 조건(아이 동반 가능 · 식단)만 정렬 키에 더한다. 데이터가 없는 이유로는 정렬하지 않는다 |

### 6-2. 고객 제보 늘리기 (C6)

C6 는 고객 제보가 가장 정확한 출처다. 제보를 늘리는 방법(일정 카드 제보 버튼 등)은 고객에게 보이는 정보량과 함께 나중에 다시 정한다. 어느 안이든 LLM 을 거치지 않는 구조화된 제보를 기본으로 한다.

## 7. 결정이 필요한 것

1. **Q 의 에이전트를 만들까** — `case_events` 로 Q 비율을 잰 뒤 정한다. 기준 예: 식당 Case 의 5% 이상이면 만든다, 아니면 접수 갈래만 넓힌다.
2. **에이전트 시간 상한** — 제안 10초. 고객이 기다리는 웹 채팅 기준.
3. **모델** — gemma4 로컬이면 도구 호출 능력부터 측정한다(2026-10-06 실측은 Ollama 연결 끊김으로 무효).

## 8. 경계 테스트

| # | 테스트 | 막는 것 | 상태 |
