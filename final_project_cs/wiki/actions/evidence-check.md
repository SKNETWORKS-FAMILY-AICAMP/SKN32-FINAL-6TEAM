# 제안 근거 대조

제안이 실제로 확인한 사실·정책과 맞는지 실행 전에 대조합니다. [순수 검증 엔진](../../app/core/verification.py)은 `Facts`·`VerificationPolicy`를 받아 판정하고, DB 재조회는 실행 경계의 `proposal_guard`가 담당합니다.

## 대조 항목과 시점

제안 시점과 승인·실행 직전에 확인합니다. 대기 중 사실이 바뀌면 이전 검증 결과만 믿지 않습니다. 예약 식별자, 고객 범위의 공급자 예약, 예약 금액 상한, 정원, 제안에 인용한 근거 ID를 확인합니다. 확인할 수 없는 식별자·미선언 필드는 무시하지 않고 거부합니다.

## 반드시 유지할 경계

- 대조 대상은 Controller가 만든 Context Pack입니다. Team이 스스로 만든 근거로 자기 제안을 검증하는 순환을 허용하지 않습니다.
- 값이 비정상인 경우 NaN·Infinity 등을 성공이나 처리 오류로 흘리지 않고 검증 실패로 다룹니다. 조회 실패가 뒤따르는 상태 전이의 트랜잭션을 망가뜨리지 않도록 격리합니다.
- 실패한 필드·사유를 기록하고 민감한 원본 값은 hash 등 안전한 형태로 남깁니다. 거부 기록이 오류 응답과 함께 롤백돼 사라지지 않아야 합니다.
- degraded Context의 제안 차단은 Team의 협조에 맡기지 않고 Controller 경계에서도 확인합니다.

## 증거 범위

[여행 예약 검증 시험](../../tests/unit/core/test_proposal_verification.py), [여행 정책 주입 시험](../../tests/architecture/test_engine_accepts_travel_policies.py), [실행 직전 재검증 시험](../../tests/integration/api/test_recheck_before_execution.py)을 구분합니다. 불변식 정의는 [카탈로그](../quality/invariants.md)가 소유하며 여기서 중복 표로 관리하지 않습니다.

검증 통과는 원본 값이나 업체 환급 규정 계산이 정확하다는 보장이 아닙니다. 고객 범위에서 두 식별자를 따로 확인하는 것과 둘의 관계까지 검증하는 것도 다릅니다. 해당 관계를 실제 코드가 확인하는지 별도로 검토합니다. 모든 산업의 범용성을 시험했다고 주장하지 않습니다.

## 과거 기록

[수정 전 문서](../records/commerce_2026-10-11/wiki--actions--evidence-check.md)는 당시 기록입니다. 현재 여행 제품의 사양·평가·시연·완료 증거로 사용하지 않습니다. 원문 바이트는 같은 폴더의 백업에도 보존했습니다.
