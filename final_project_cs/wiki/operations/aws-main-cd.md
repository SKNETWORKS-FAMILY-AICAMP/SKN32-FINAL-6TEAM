# main 검사 성공 뒤 AWS 자동 배포

2026-10-23 사용자 지시: main 검사 통과 후 AWS 자동 배포를 연결하고 최신 main 반영을 실제로 확인한다. 이 문서는 구현 전 확정한 배포 계약이다. 실제 반영 여부는 날짜별 배포 기록으로 확인한다.

## 시작 조건과 같은 판 보장

- 팀 저장소 main의 push 또는 직접 실행한 main 검사 성공이 시작 조건이다. PR·다른 브랜치·다른 저장소의 실행은 배포하지 않는다.
- 현재 main 커밋과 검사한 커밋이 같아야 한다. 경로 조건에 따라 함께 실행된 웹·관리자 검사도 성공할 때까지 기다린다.
- `[2026-10-27 후보]` 이미지 게시는 CI (main) 성공과 현재 main 확인 뒤 바로 시작해 웹·관리자 검사 대기와 겹친다(`gate --main-only`). 이미 끝난 검사가 실패면 게시도 멈춘다. DB 변경·앱 교체는 지금처럼 모든 검사 성공(`gate`) 뒤에만 한다. 게시만 되고 배포되지 않은 `git-<sha>` 이미지는 고객 경로에 쓰이지 않는다.
- 빌드·게시·DB 변경 직전에도 같은 main인지 확인한다. 오래된 실행은 새 main을 덮지 않는다. AWS 배포는 한 번에 하나씩 실행한다.
- GitHub OIDC로 해당 저장소 main에만 단기 AWS 권한을 부여한다. 영구 AWS 키를 GitHub에 등록하지 않는다. 실제 역할·클러스터·주소는 저장소 비공개 설정에만 둔다.
- main 필수 정적 검사에서 배포 파일의 GitHub 표현식을 actionlint로 검증한다. 검증 도구는 고정 버전과 SHA-256을 확인하며, 실행 기계의 임시 경로는 작업이 시작된 단계에서 설정한다.

## 빌드와 보존

API·웹·관리자를 같은 커밋에서 빌드하고 작업 처리 앱은 API와 같은 digest를 쓴다. ECR 이름표는 git 커밋으로 고정하며 실제 배포는 digest를 사용한다. 기존 AWS 이미지의 이동 등 사실 자료와 알림 문구 자료를 보존하고, 이동 자료의 전체 파일 수와 내용 지문이 같아야 게시한다. 웹은 기존 공개 빌드 설정을 유지한다.

운영 앱의 환경변수·Secret 참조·ConfigMap 참조·자원 한도·볼륨·교체 방식은 유지한다. 이미지·배포 판 표시와 관련 주석만 바꾼다. 고객 자료를 GitHub 산출물로 올리지 않는다.

기존 단일 노드에서는 API 두 개와 작업 처리 앱을 동시에 수용할 메모리가 부족하다. DB 변경 성공 후 작업 처리 앱만 잠시 0개로 줄여 종료를 확인하고 API를 무중단 교체한다. 이어 작업 처리 앱을 원래 개수로 복원하고 웹·관리자를 교체한다. 복구할 때도 같은 메모리 확보 순서를 따른다. DB·고객 요청 API를 공간 확보 목적으로 중지하지 않는다.

## DB 변경과 실패

- 기존 RDS의 7일 연속 백업과 최근 20분 안의 실제 복구 가능 시각을 확인한 뒤 현재 SQL을 한 트랜잭션으로 적용한다.
- DB 변경 Job은 자동 재시도하지 않는다. 실패했거나 결과를 모르는 이전 Job이 있으면 다음 배포도 멈춘다.
- `[2026-10-27 후보]` DB 변경은 API가 고객 요청을 받는 중에 돈다. 표 잠금 대기가 뒤 요청을 줄줄이 막지 않도록 잠금 대기 `5s`·문장 실행 `5min`(Job 제한 600초 안)으로 묶고, 서버가 그 값을 받아들였는지 읽어 확인한 뒤에만 적용한다. 넘으면 묶음 전체가 롤백되고 배포는 멈춘다(자동 재시도 없음 — 위 규칙 그대로).
- `[2026-10-27 후보]` DB 변경 결과는 Job 종료 기록(termination message, 4 KiB 이하)에 `committed`·`failed_before_commit`·`commit_unknown`과 오류 종류·SQLSTATE만 남긴다. 컨테이너 로그·행 값은 읽지 않는다. 막힌 다음 배포의 오류 문장에 그 결과가 나온다(`failed_before_commit`이면 반영되지 않은 것, `commit_unknown`·`unknown`이면 DB 확인이 먼저).
- 앱 교체 실패 시 직전 앱 구성을 복구한다. DB 변경을 역실행하지 않는다. 실패와 복구 실패를 구분한다.
- 교체와 복구의 준비 상태는 승인된 앱 이름별 GET으로 확인한다. `kubectl rollout status`가 요구하는 Deployment 목록 권한을 추가하지 않으며, 같은 420초 제한 안에서 관측 세대·갱신 개수·준비 개수·전체 개수가 모두 맞아야 다음 앱으로 넘어간다.

## 완료 조건

API·작업 처리 앱·웹·관리자 모두 현재 커밋의 digest로 실행되고, 준비 상태와 재시작 0을 확인한다. 공개 홈·건강 응답은 배포 점검 클라이언트임을 명시해 확인한 뒤 30초 후 다시 검사한다. 성공 기록에는 커밋·이미지 digest·DB 복구 시각·HTTP 결과·단계별 걸린 초(`timings`)만 남긴다. 실패하면 `aws-deploy-failure.json`에 멈춘 단계·우리 오류 문장(다른 예외는 종류 이름만)·DB 변경 결과·복구 결과·단계별 초를 남겨 산출물로 올린다. 이 조건은 실제 로그인·채팅·알림 전체 기능 시험을 대신하지 않는다.
