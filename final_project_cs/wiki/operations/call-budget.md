# 외부 API 호출 한도 — 어떻게 막고 어떻게 보나

`[2026-10-05 사용자 지시 — 이동 세션 인계]`

**한 줄 요약.** 공공 API 키마다 정한 하루·월 상한을 **DB 에 세서**, 상한이 차면 그 소스를 **호출하지 않고** 「모름」으로 돌린다. 일꾼이 매번 새 프로세스로 떠도 같은 줄을 이어서 센다. 여유는 보고 스크립트로 본다.

## 먼저 답부터

| 궁금한 것 | 답 |
|---|---|
| 한도가 차면 어떻게 되나 | 그 소스는 바깥으로 호출하지 않고 미스 이유 `budget_exhausted` 로 「모름」을 돌려준다. 하루 줄은 **한국 시각 자정**에 열린다 |
| 어디서 세나 | DB 표 `external_call_budget`(소스별 하루 줄 · 월 줄). 모든 프로세스가 같은 줄을 센다 |
| 무엇을 세나 | 사용(`used`) · 실패(`failed` — 부른 뒤 쓸 수 있는 답을 못 받음) · 거절(`rejected` — 한도가 차서 **안 부름**) |
| 어떻게 보나 | `python -m scripts.report_source_budget` — 소스마다 오늘·이번 달 사용/상한(%) · 실패 · 거절 · 단계(정상·경보 80%·위험 95%·찼음) |
| 제공처의 월 한도 숫자는 어디서 보나 | **조회 API 는 없다**(2026-10-05 확인 범위: ITS 공식 OpenAPI 매뉴얼 PDF · 오픈데이터 안내 페이지 — 한도 숫자 없음, 매뉴얼은 「키당 서비스별 하루 트래픽 제한은 현재 없다」고만 적음). ITS 의 월 한도는 **로그인한 포털의 인증키 상세정보**에만 있다(응답 메시지가 그렇게 안내). 그래서 숫자를 추측해 넣지 않고 **제공처가 「한도 초과」(4001)를 알리면 자동으로 멈추고 그때까지 센 값을 `learned_cap` 으로 기록**한다 |
| 한도는 어디서 바꾸나 | 하루 `ACOP_RATE_<이름>_PER_DAY` · 월 `ACOP_RATE_ITS_PER_MONTH`(지금 ITS 만 · 0 = 모름 → 월 줄은 세기만) · 켜기·끄기·대상 `config/guardrails.yaml` 의 `travel.source_budget_*` |

## 아래층 — 동작과 선택

**어디에 걸리나.** `TravelSource._allow` → 제한기 `acquire(이름)` 한 곳. 안쪽(프로세스 안) 제한기를 먼저 통과한 뒤 DB 한 칸을 확보한다(`app/infrastructure/travel/source_budget.py`). 캐시 적중은 바깥으로 안 나가니 한도를 안 쓴다. `TravelSource` 를 거치지 않고 직접 부르는 코드(따릉이 `urllib`)는 `build_gate(settings, ["seoul_bike"])` 로 같은 문을 쓴다.

**제공처가 「한도 초과」를 알릴 때.** ITS 는 월 한도가 차면 HTTP 401 + `resultCode 4001` 로 답한다. 어댑터가 그 숫자 코드를 알아보면(`_quota_signal`) 그 달 줄에 `exhausted_at` · `learned_cap`(그때까지 센 사용 수 = 제공처가 허락한 한도의 **관측값**)을 남기고(마이그레이션 049), **그날 한국 자정까지 그 소스를 부르지 않는다**(한도가 차 있던 날 하루 800~900건을 헛호출하던 것을 막는다 — 9/30 937건 · 10/2 825건). 다음 날 첫 호출이 한 번 시험해 — 여전히 초과면 다시 표시하고, 풀렸으면(한도 증설 · 달 바뀜) 그대로 쓴다. 달이 바뀌면 새 줄이라 자동으로 풀린다. 새 소스의 신호는 어댑터에 `_quota_signal` 한 메서드만 더하면 된다(공급자마다 신호가 다르다).

**월·하루는 함께.** 하루 줄 · 월 줄 중 하나라도 차 있으면 **아무 줄도 올리지 않고** 거절한다(한 트랜잭션). 월 한도를 모르는 소스(ITS 의 `ACOP_RATE_ITS_PER_MONTH=0`)는 월 줄에 세기만 하고 막지 않는다. ★ITS 월 한도의 크기는 국가교통정보센터 로그인 → 인증키 상세정보에서 확인해 넣어야 한다(사용자 몫 — 응답이 「월간 한도 초과」 4001 이다).

**DB 오류 때.** 가드레일 `travel.source_budget_on_db_error` — `allow`(기본: 안쪽 제한기만으로 나간다 — 이 층 도입 전과 같다) · `refuse`(호출하지 않는다 — 한도를 무조건 넘지 않지만 DB 오류 동안 이 목록의 소스가 전부 「모름」 → 도로 사건 감시가 치명으로 번진다). ★**사용자 결정 대기**(2026-10-05). 이 층은 감시 루프와 같은 DB 를 써서 DB 가 아예 죽으면 어차피 감시도 못 돈다 — 차이가 나는 것은 표 누락 · 잠금 시간 초과 같은 부분 장애다.

**여유 단계.** 사용 ≥ 80% 경고 로그(프로세스마다 한 번) · ≥ 95% 위험 — `essential_only(소스)` 가 True 가 돼 비필수 호출(워밍 · 재확인)이 줄일 수 있다. `[미구현]` 지금 이 신호를 읽는 호출자는 없다.

**개발 PC 와 서버가 같은 키를 쓸 때.** 두 곳의 DB 는 **따로**라서 각자 센 합이 키 한도를 넘을 수 있다. 추천: ① 키를 환경별로 따로 받는다 ② 안 되면 **개발 PC 환경 파일의 한도를 훨씬 낮게**(예: 서버 80% · 개발 PC 20%) 둔다. 이 표는 **이 DB 에서 센 만큼**만 보인다.

**실패 수의 뜻.** 부른 뒤 `TravelSource._miss` 가 불린 경우(시간 초과 · 연결 오류 · http 오류 · 응답 모양 이상 …)를 센다 — 서비스 입장의 「못 받음」이다. 한도 때문에 안 부른 것은 실패가 아니라 거절이다. 안쪽(프로세스 안) 제한기가 거절한 것은 DB 에 안 센다(프로세스 안 `refusals` 에만 있다).

**따릉이.** 서울 열린데이터광장 일반 키로 부르는 따릉이 거치 대수의 하루 상한은 `ACOP_RATE_SEOUL_BIKE_PER_DAY`(기본 1,000 — 공식 하루 한도를 못 찾아 **우리가 고른 보수적 값** `[미확인]`). 이동 모듈이 `bike.py` 에서 위 문을 쓰도록 잇는 일은 이동 세션 몫이다.
