# 여행 서비스 상시 운영 점검·복구

고객용 여행 웹·API와 일정 감시·알림 배달이 개발용 터미널 창과 무관하게 지속 실행되는지 확인하는 절차입니다. **이번 작업은 문서·절차 정리이며 서비스 재시작·배포·상시 계측 설치를 수행하지 않았습니다. 현재 배치와 마지막 관측은 [환경별 운영 현황](current-state.md)이 소유합니다.** 2026년 9월 로컬 개발 환경의 수동 실행 장애는 아래 과거 기록에 보존하며 오늘 공개 배포 상태로 사용하지 않습니다.

## 먼저 대상을 구분합니다

| 이름 | 정확한 뜻 | 이 문서에서 하는 일 |
|---|---|---|
| 터미널 창 | PowerShell·WSL 등 명령을 입력하고 출력을 보는 창 | 점검 명령을 실행하는 도구. 창의 존재가 서비스 정상 동작 증거는 아님 |
| 개발자용 진단 웹 화면 | Case·실행 기록·결함·알림 상태를 개발자·QA가 확인하는 화면 | 장애 사후 분석. 고객 대신 문제를 수정하는 상주 상담원 화면으로 운영하지 않음. 고객 문의 답변은 관리자 웹앱의 별도 「문의함」에서 하며 고객 일정은 대신 고치지 않음 ([D-024](../../../wiki/decisions/D-024-inquiry-reply-path.md)) |
| 고객 여행 웹 화면 | 고객이 여행을 제출·조회하고 필요한 정보를 입력하는 웹 | 실제 기능 검사 대상 |

대상 환경은 **로컬 개발 서버 / x600 서버의 cs 프로젝트 서버 공개 배포 / Oracle ARM의 cs 프로젝트 앱 실험 / GPU 서버 연구**로 부릅니다. 명령은 해당 기계의 해당 배포 폴더에서 실행합니다. 개인 접속 주소·SSH 별칭·비밀값은 공용 문서에 적지 않습니다.

## 적용한 방안과 근거

| 안 | 달라지는 것 | 판단 |
|---|---|---|
| A. 기존 Docker Compose 배포를 기준으로 환경별 점검·복구 절차 정리 | 현재 코드의 API·웹·DB·worker와 일치. 상태 관측과 과거 기록을 분리 | **추천·문서 반영**. 실제 배포 변경은 수행하지 않음 |
| B. 로컬 Windows 서비스·작업 스케줄러만 정리 | 개발용 PC의 재부팅·창 종료 문제만 다룸 | 로컬 안내에서 유지. 공개 배포 전체 설명으로 사용하지 않음 |
| C. 새 다중 기계 운영 체계 도입 | 확장·배포 관리 기능과 관리 비용이 함께 증가 | 다중 기계 수요·용량·복구 목표 확인 뒤 별도 검토 |

Docker는 단일 기계의 Compose 운영, 운영 환경별 설정, 재시작 정책을 안내합니다. 이는 현재 배포를 활용하는 근거이며 우리 제품의 가용성을 보증하지 않습니다. [공식 운영 안내](https://docs.docker.com/compose/how-tos/production/).

## 정상 판정을 다섯 단계로 나눕니다

| 단계 | 확인 | 성공으로 확대하면 안 되는 것 |
|---|---|---|
| 구성 | 코드 SHA·이미지 ID·설정 판·자료 판·실행 기계 | 파일이 있다는 이유로 실제 배포 완료라 하지 않음 |
| 프로세스 | 대상 API·웹·DB·worker 실행 상태·재시작 횟수 | `running`만으로 요청 처리 준비 완료라 하지 않음 |
| 준비 | DB 연결·필수 자료·현재 연결 모델·인증 경계 | `/health` 200만으로 여행 기능 정상이라 하지 않음 |
| 고객 기능 | 합성 시험 사용자의 본인 여행 조회·다른 사용자 차단·기대 답변 | HTTP 200인 `decision_failed`를 성공으로 세지 않음 |
| 자동 작업 | 감시 회차 종료·적체·알림 배달 결과·마지막 성공 시각 | 일꾼 프로세스 생존·outbox 비어 있음만으로 주기 실행을 확정하지 않음 |

위 다섯 단계는 점검 절차입니다. 모든 단계의 자동 검사 구현·배포 완료를 뜻하지 않습니다. 현재 [API `/health`](../../app/presentation/api/app.py)는 고정 `status: ok` 응답입니다. DB·모델·알림까지 검사하지 않습니다. [Docker 시작 순서](https://docs.docker.com/compose/how-tos/startup-order/)의 `service_healthy`는 지정된 검사만 기다립니다. 실제 준비 검사를 추가하는 것은 별도 구현 과제입니다.

## 공개 배포를 읽기만 하며 점검합니다

기존 승인된 접속 방법으로 **x600 서버의 해당 Compose 배포 폴더**에 들어간 뒤 실행합니다. 출력에 개인 정보가 있으면 공용 보고에 옮기지 않습니다.

| 순서 | 명령·확인 | 기대 결과 |
|---|---|---|
| 1 | `docker compose ps --all` | `tripilot-db`·`tripilot-api`·`tripilot-worker`·`tripilot-web` 상태와 재시작 여부 확인 |
| 2 | `docker compose exec -T tripilot-db pg_isready` | 연결 수신 가능. 업무 쿼리·자료 최신성은 별도 |
| 3 | `docker compose exec -T tripilot-api curl -fsS http://127.0.0.1:8043/health` | API 프로세스 응답. 준비·여행 기능 통과가 아님 |
| 4 | `docker compose logs --since 15m --tail 200 tripilot-api tripilot-worker` | 오류·회차 지연·배달 실패 조사. **로그 200줄은 제한된 조사 범위** |
| 5 | 승인된 합성 사용자로 고객 웹·여행 조회·권한 경계 검사 | 본인 접근 성공·타인 접근 거부·내용 검사. 실고객 정보로 시험하지 않음 |
| 6 | 감시·배달의 마지막 완료 시각과 오래된 pending·unknown 확인 | 실행 및 결과를 모두 확인. 전용 관측이 없으면 미확인이라고 기록 |

Oracle ARM은 [ARM 앱 배포·검사](arm-develop-cd.md), GPU 서버는 [연구 대기열](gpu-work-queue.md), 로컬 개발 서버는 [로컬 개발 안내](local-setup.md)를 따릅니다. 다른 환경의 명령·성공 기록을 복사해 정상으로 표시하지 않습니다.

## 현재 worker가 보장하는 것과 남은 구현

[공개 배포 worker](../../deploy/worker.sh)는 감시·복구, outbox 배달을 **직접 실행한 뒤 60초 대기**합니다. 시작 간격은 회차 실행 시간 + 60초이며 정확한 1분 고정 주기가 아닙니다. 일일 집계는 지정 시각 뒤 하루 한 번 시도합니다. 실패 exit code는 표준 오류에 남기고 다음 회차를 진행합니다.

로컬 Windows의 `scripts.ops.tick`·`guard`를 통과하는 경로와 다릅니다. 공개 worker가 같은 heartbeat·연속 실패 알림을 남긴다고 가정하지 않습니다. 현재 Compose에서 worker 자체 healthcheck는 꺼져 있습니다. 회차별 시작·종료·성공·실패·건너뜀·처리 건수·지연을 남기는 공통 계측과 종료 시각 기반 점검은 **별도 구현·배포·검증이 남았습니다**. 임계값은 현재 guardrail과 실제 지연 측정으로 정하며 공식 문서가 우리 제품의 주기·시간 상한을 정해준다고 쓰지 않습니다.

Google SRE는 고객 관점 증상과 내부 원인을 구분하고, 지연·트래픽·오류·포화도를 함께 관측하며 신호가 분명한 경보를 권합니다. 이를 적용해 고객 기능 실패·배달 적체와 CPU·메모리·회차 로그를 연결합니다. 새 모니터링 제품 설치를 이번에 완료했다는 뜻은 아닙니다. [Google SRE 원문](https://sre.google/sre-book/monitoring-distributed-systems/).

## 장애 대응과 복구 확인

1. 환경·확인 시각·증상·영향 기능·실행판·최근 변경을 먼저 기록합니다. 로그와 실패 결과를 보존합니다.
2. DB·모델 연결·배포 겹침·필수 자료·worker 진행을 구분해 원인을 확인합니다. 모델 연구 작업을 임의 중단하거나 고객 기능을 연구 결과로 정상 처리하지 않습니다.
3. 해당 환경의 승인된 배포·복구 절차로 필요한 구성요소만 조치합니다. 기존 코드 판 복구가 DB 구조·데이터 복구까지 보장하지 않습니다. 업무 DB 삭제·통째 초기화·무조건 재배달은 복구 절차에 넣지 않습니다.
4. 같은 고객 기능·권한·자동 작업·배달 결과를 다시 검사합니다. 이전 실패와 재검사 결과를 모두 남깁니다. 거래·배달 결과 `unknown`은 [상태 확인 절차](unknown-state.md)를 따라 중복 부수효과를 막습니다.

Docker의 `unless-stopped`는 컨테이너 종료·Docker 재시작에 대한 정책입니다. Docker Engine과 호스트 부팅 준비까지 보증하지 않으며 `unhealthy` 표시만으로 자동 재시작된다고 해석하지 않습니다. 같은 컨테이너를 여러 자동 복구 장치가 경쟁해서 재시작하지 않도록 책임을 정합니다. [Docker 재시작 정책](https://docs.docker.com/engine/containers/start-containers-automatically/).

고객 통지와 개발자·QA 장애 알림은 대상·채널·내용을 구분합니다. 장애 알림을 고객 채널로 대체 전송하는 경로는 권장하지 않습니다. 연속 실패 알림·복구 알림은 중복 방지하고 고객 데이터·접속 정보를 노출하지 않습니다. 이 절은 운영 원칙이며 모든 경로에 구현·배포됐다는 선언이 아닙니다.

## 과거 기록

[수정 전 문서](../records/commerce_2026-10-11/wiki--operations--always-on.md)는 당시 기록입니다. 현재 여행 제품의 사양·평가·시연·완료 증거로 사용하지 않습니다. 원문 바이트는 같은 폴더의 백업에도 보존했습니다.
