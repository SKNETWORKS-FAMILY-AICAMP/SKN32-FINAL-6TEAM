# 도커 이미지 정리와 월별 복원용 보존

배포가 성공할 때마다 오래된 도커 이미지를 지우고, **달마다 하나는 복원용으로 남깁니다.** 정리하지 않으면 이틀에 72GB가 쌓였습니다(`[사용자 보고 2026-10-14]` 10-12 → 10-14, x600 서버 이미지 80 → 191개). 코드는 [image_retention.py](../../deploy/image_retention.py), 복원 시험 도구는 [restore_check.py](../../deploy/restore_check.py), 이번 작업의 근거 기록은 [보고서](../records/reports/2026-10-14_도커이미지_정리규칙과_월별보존.md)입니다.

## 규칙

| 대상 | 남기는 것 | 이유 |
|---|---|---|
| 앱 이미지(`tripilot-api` · `tripilot-web` · `tripilot-admin`) | 최근 3개 · 현재 배포 태그 · 달마다 하나(`keep-YYYY-MM`, 최근 6개월) | 같은 커밋 태그는 저장소가 달라도 함께 남기고 함께 지운다 |
| 복구용 이미지(`tripilot-recovery`) | 최신 2세트 · 2시간 안에 만든 세트 | 배포가 하루 수십 건이라 기간 기준(7일)은 수백 GB가 된다. 직전 이미지는 앱 이미지 「최근 3개」로도 남는다 |
| 복구용 상태 폴더(`state/migration-safety-*`) | 위 복구 세트와 같이 정리 | 풀어 쓴 설정(비밀 포함)이 들어 있다 |
| 빌드 캐시 | x600 서버에서 20GB 상한 | 도커 자동 정리 설정(상한 20GB)만으로는 77GB까지 늘었다 |
| 오라클 서버 `releases/<커밋>` 소스 폴더 | 남은 이미지가 있는 판과 현재·직전 판 | 이미지가 모두 사라진 판의 소스는 지운다 |

- **지우지 않는 것**: `local` · `keep-*` · 손으로 붙인 이름(`*-rollback`, `*-summary-*`, `backup-*`) · 다른 저장소(jikimi 등) · 실행 중(정지된 컨테이너 포함)인 컨테이너가 쓰는 **그 이미지 자체**. 보호는 이미지 단위이고, 같은 커밋 이름표의 다른 저장소 이미지까지 묶음째 지키지 않는다(묶음째 지키면 바뀌지 않는 웹 이미지를 여러 커밋이 공유해 api 이미지가 영영 안 지워진다 — 2026-10-14 수정).
- **달마다 하나 고르는 법**: x600 서버는 `deploy.log` 의 「반영 완료」 중 그달 마지막, 오라클 서버는 `state.json` 의 `history`. 기록이 없으면 이미지를 만든 시각으로 고른다. 빌드만 되고 반영에 실패한 이미지는 후보가 아니다. 달 경계는 서버 지역 시각 기준이다.
- **기본은 계획만 출력**하고 `--apply` 가 있어야 지운다.

## 어디서 도나

| 환경 | 호출 위치 | 첫 실행 확인 |
|---|---|---|
| x600 서버 | `deploy/auto_deploy.sh` 끝(반영 성공 뒤). 정리 실패는 경고만 남기고 반영은 그대로 | `[실측 2026-10-14 16:52]` 자동 배포 후 `deploy.log` 에 「앱 이미지 묶음 4개 중 남김 3 · 지움 3개」 |
| 오라클 서버 | `control/deploy.py` 의 성공 처리 **뒤**. 정리 실패가 배포 실패·이전 판 복구로 번지지 않는다 | `[실측 2026-10-14]` 코드 설치 뒤 배포 2회에서 정리 호출 확인(첫 판의 결함으로 지운 것 0개 → 수정본을 설치해 손으로 돌려 7개 이름표 추가 정리, 처음 손으로 돌린 정리 16개와 합해 이미지 29 → 14개) |

오라클 서버는 저장소 파일이 자동으로 넘어가지 않아 `control/` 에 손으로 설치합니다(이전 파일은 `control/_backup/` 에 보관).

확인 명령(읽기 전용): x600 서버 WSL 안에서 `docker images 'tripilot-*'` 로 태그를 보고 `deploy.log` 끝의 정리 줄을 봅니다. 오라클 서버는 `journalctl -u tripilot-arm-cd.service` 에서 「앱 이미지 묶음」 줄을 봅니다.

## 달별 복원용 보존과 복원

1. **있는 판 보기**: `docker images 'tripilot-*' --format '{{.Repository}}:{{.Tag}}'` 에서 `keep-` 이름표를 찾는다.
2. **먼저 시험하기(운영을 건드리지 않음)**: `python3 deploy/restore_check.py --old-image <옛 이미지> --new-image <현재 이미지> --mobility-dir <이동 자료 폴더>`. 바깥과 연결되지 않는 임시 네트워크에 빈 DB 를 만들어 최신 이미지의 마이그레이션으로 「지금의 DB 구조」를 만들고, 옛 이미지의 마이그레이션 · API 기동 · `/health` · 로그 오류를 확인한 뒤 임시 컨테이너·네트워크·이름표를 항상 지운다. 운영 DB·운영 `.env` 는 읽지 않는다.
3. **되돌리기**: 운영 반영과 같은 안전 절차(`snapshot` → `check` → `rollout`)를 쓴다. 명령은 [Docker 배포 파일 안내](../../deploy/README.md) 「월별 보존 판으로 되돌리기」.

**설정 이름은 걸림돌이 아니다**: 설정(`extra="forbid"`)은 `.env` **파일**에서 읽은 모르는 이름만 거부합니다. 운영은 compose `env_file` 로 값을 컨테이너 환경변수에 넣고 `.env` 를 이미지에 넣지 않으므로(`Dockerfile.api` 주석 · `.dockerignore`), 최신 판에만 있는 설정이 환경 파일에 있어도 옛 이미지는 켜집니다. `[정정 2026-10-14]` 처음에는 반대로 보고했다가 도구의 재현 확인이 실패해 바로잡았습니다.

## WSL 가상 디스크 압축 (x600 서버)

이미지를 지워도 `WSL-Ubuntu.vhdx` 파일 크기는 압축하기 전까지 줄지 않습니다. 압축 스크립트 `C:\ProgramData\WslMaintenance\wsl_maint.ps1`(매주 일요일 05:30 `WslCompactWeekly`, 수동은 `WslMaintenanceFirstRun`)는 건강 확인·복구 절차를 갖추고 있고 11~17분이 걸리며, 그동안 triPilot 과 jikimi 가 같이 멈춥니다. **E 드라이브 여유가 2GiB 미만이면 건너뜁니다.**

`[실측 2026-10-14]` 226.3GiB → 149.7GiB, E 드라이브 여유 1.45GiB → 79.8GiB(15:59~16:10, 컨테이너 건강 확인 통과). 여유가 부족할 때 안전장치 기준을 낮춘 사본으로 실행했으며, 이 변경은 자동 권한 심사가 막아 사용자가 직접 실행했습니다. 사본은 일회용입니다.

## 확인한 것과 못 한 것

| 항목 | 상태 | 근거 |
|---|---|---|
| 정리 규칙 단위 시험 | 통과 | `test_image_retention.py` 23개 · `test_restore_check.py` 12개 · `test_migration_safe_deploy.py` 21개 |
| 월 전환(`keep-2026-11` 생성) | **시험으로만 확인** — 11월이 되기 전에는 실제로 볼 수 없다 | 10월 → 11월, 연말, 6개월 뒤 정리, KST·UTC 시험 |
| 옛 이미지의 격리 복원 시험(x600 서버) | 통과 | 오늘 18:21 판을 최신 DB 구조에 붙여 5개 확인 통과 |
| 운영 컨테이너를 옛 이미지로 바꿨다 되돌리기 | **미시험** | 운영 컨테이너 교체는 자동 권한 심사가 막았다. 사용자가 직접 실행하거나 권한을 열어야 한다. 시험 순서: 현재 → 직전 판 → 월별 이름표 → 오래된 판 → 현재 복귀 |
| 임시 DB 의 한계 | 비어 있어 데이터에 의존하는 동작은 확인하지 못했다 | 운영 DB 를 읽지 않기 위한 선택 |
| 시험한 옛 판의 간격 | 최신보다 2~3시간 앞선 판이라 구조 차이가 작았다 | 월이 지난 판일수록 같은 시험을 다시 돌린다 |
