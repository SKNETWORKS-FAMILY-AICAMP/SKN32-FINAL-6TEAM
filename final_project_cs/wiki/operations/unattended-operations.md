# 자료 조회 정책과 사후 진단

고객 문제는 자동 처리하거나 고객이 보완합니다. 개발자·QA의 설정 변경과 사후 결함 분석은 고객 업무 처리의 대기 조건이 아닙니다. 승인 근거는 [D-CS-014](../decisions/D-CS-014-routing-reroute.md), [낮 휴무 확인](../decisions/D-CS-009-daytime-closure-detection.md), [구글 조회 제한](../decisions/D-CS-010-google-calls-in-dawn-batch-only.md)입니다.

## 자료 선택

후속 접합 계약: 새벽 작업은 요청마다 tenant·고객·여행·장소·방문 구간을 명시합니다. Dining 무료 자료는 운영 허용 출처의 성공한 `closure` 관측 중 방문 시작이 정확히 일치하고 방문 종료까지 유효한 최신 기록만 사용합니다. `yes`는 휴무, `no`는 휴무 아님이며 시간표 확인을 현장 개점 확인으로 승격하지 않습니다. 해당 관측이 없으면 검증 불가입니다. 낮 감시와 Team 재점검도 같은 무료 판정을 사용하며 구글을 호출하지 않습니다.

새벽 구글 첫 HTTP의 기존 공급 예산은 요청 전용 어댑터 사본에서 먼저 확보합니다. 첫 HTTP는 그 허가를 소비하고, 검색 뒤 상세가 필요하면 상세 HTTP 예산을 별도로 확보합니다. 공유 어댑터에 고객·여행 범위를 기록하지 않습니다. 장소 짝 불일치·무료 자료 실패는 검증 불가이며 고객에게 기존 일정 유지와 재확인 상태를 안내합니다. 이 문단은 접합 계약이며 아래 구현·인수 상태가 검증 완료 범위를 구분합니다.

무료 자료를 먼저 조회합니다. 출처·확인 시각·유효기간이 있는 판정만 사용하며 실패·예산 소진·확인 간격 미충족은 `unverifiable`(검증 불가)와 이유 코드로 반환합니다. 조회 실패를 영업 정상으로 바꾸지 않습니다. 조회 자료를 확보한 사실과 실제 개점 확인을 구분하는 책임은 공급 어댑터에 있습니다.

운영 앱 `/admin/api/source-policy`의 GET은 `limits:read`, PATCH는 `limits:write` 권한과 기존 로그인·쓰기 CSRF 검사를 요구합니다. 저장은 tenant별 DB 판본 비교와 감사 기록을 같은 트랜잭션으로 수행합니다. 필드: `allow_paid`(기본 false), `daily_paid_cap`·`trip_paid_cap`(기본 0), `check_interval_seconds`(기본 180). 변경 사유와 `expected_revision`을 받습니다. 상한·범위는 전용 [설정](../../config/operations-policy.yaml)에 둡니다.

유료 재조회는 무료 자료가 검증 불가일 때만 가능합니다. tenant·여행의 하루 예산을 원자적으로 먼저 확보하며 실패해도 반환하지 않습니다. 공급자의 기존 공용 예산 허가 함수도 반드시 통과해야 합니다. 구글은 `dawn` 작업의 한국 시각 03:00~08:00에서만 허용합니다. 운영 화면 설정으로 이 제한이나 기존 공공 API 예산을 늘리지 않습니다. 이 서비스는 Team의 제안·외부 실행 경계를 바꾸지 않으며 읽기 자료 어댑터를 감싸는 접합부입니다.

## 결함 수집과 조회

`place_unmatched`, `processing_error`, `suggestion`을 구분합니다. 발생 UUID, tenant, 고객·여행 UUID, 사건·요청 UUID, 오류 코드, 배포·정책 판본, 재현 조건 코드만 수집합니다. 임의 고객 원문·토큰·접속 주소는 진단 입력 스키마에 없습니다. 기존 마스킹 함수를 재사용하고, 기존 `229_service_improvement.sql`의 동의 기반 합성 자료에는 고객 연결표를 추가하지 않습니다.

같은 발생 UUID의 재전송은 tenant 안에서 한 번만 집계합니다. 동일 결함 묶음은 종류·오류 코드·배포·정책 판본·재현 코드로 결정합니다. 발생 수와 영향 고객 연결은 표본으로 줄이지 않습니다. 고객 연결에는 보존기한을 적용하며 기한 만료 후 영향 고객 수는 보존 기간 내 수라는 뜻입니다. 전체 발생 수는 누적입니다. 재현 상세는 제한된 코드만 남깁니다.

수집은 독립 트랜잭션으로 저장합니다. DB 실패 시 SQLite 영속 대기 파일(WAL·FULL 동기화)에 같은 발생 UUID로 보관합니다. 논리 크기·건수 상한을 검사하고 포화 시 유실 카운터를 기록합니다. 디스크까지 실패하면 반환값과 오류 로그로 `collection_degraded`를 드러냅니다. 재전송은 DB 커밋 확인 후 대기 행을 삭제하며 커밋 뒤 중단되더라도 DB 중복 방지로 집계가 증가하지 않습니다. 로컬 파일은 배포 환경의 비공개 영속 볼륨에 `ACOP_DIAGNOSTIC_SPOOL`로 지정합니다. 파일 접근권한·백업·보존은 배포 인수 항목입니다.

운영 앱 `/admin/api/diagnostics`는 `ops:introspect` 권한으로 tenant별 결함을 페이지 조회합니다. 영향 고객 UUID 및 발생·사건·요청 UUID 조회는 추가로 기존 `case:read` 권한을 요구합니다. 조회 실패는 503이며 빈 정상 목록을 반환하지 않습니다. 해결 판본 기록은 `ops:introspect`·`limits:write`와 변경 사유·감사를 요구하고 고객 여행을 수정하지 않습니다. 이 조회·기록 경로는 전용 운영 화면에도 연결했습니다.

개인 연결과 발생 상세는 기본 30일 보존합니다. 누적 건수와 해결 판본은 유지합니다. 고객 삭제 시 영향 고객 연결은 삭제하고 발생의 고객 참조는 비웁니다. 삭제된 고객·여행을 가리키는 대기 기록은 재전송 때 거부·폐기하며 되살리지 않습니다. 기존 고객 삭제 기능 전체를 새로 구현한 것은 아닙니다. 배포 판본은 `ACOP_DEPLOYMENT_VERSION`에서 받으며 미설정·형식 오류는 `unrecorded`로 명시합니다.

다른 보존 기록의 외래 키 때문에 고객 번호 행만 남기는 정리 경로에서도 OAuth 자격·진단 고객 연결을 제거하고 발생의 고객 참조를 비웁니다. 남은 고객 행의 외부 식별자는 `erased:`와 무작위 고객 UUID로 교체합니다. 진단 재전송은 이 파기 표지를 거부하므로 대기 파일이 개인 연결을 다시 만들지 않습니다. 누적 결함 수와 별도 보존 의무가 있는 기록은 이 정리에서 삭제하지 않습니다.

공개·ARM 배포 정의의 API와 작업 일꾼은 같은 비공개 진단 볼륨을 공유합니다. 공개 운영 앱도 같은 볼륨을 사용합니다. 기존 작업 일꾼은 매 회차에 `replay_operations_diagnostics --prune`을 먼저 실행하며 한 번의 처리 상한은 전용 설정의 `diagnostics.replay_limit`입니다. 재전송·보존 정리·디스크 실패는 각각 실패 결과와 종료 코드로 남고 다음 회차는 계속 실행합니다. POSIX에서는 대기 파일 디렉터리 0700·파일 0600을 요구하며 Windows에서는 파일 시스템의 접근 제어가 별도로 필요합니다. 이 정의의 실제 배포·볼륨 권한·재시작 인수는 아직 하지 않았습니다.

## 구현·인수 경계

최초 고객 분류·분류 되잡기·대화의 분류 실패와 담당 라우팅 실패도 같은 고정 코드 진단 경계를 사용합니다. 새 Case는 생성 커밋 이후 분류하며, 수집은 업무 트랜잭션과 분리합니다. 재배분에 성공한 라우팅은 오류로 세지 않습니다. 고객 원문이나 예외 본문을 진단 콜백에 넘기지 않으며 수집 실패로 원래 업무 결과를 덮지 않습니다. 이 추가 경계의 실행 인수는 후속 기록으로 판정합니다.

최초 담당: operations 세션, 후속 접합: 통합 세션. 최초 로컬 백엔드 51/51, 전용 운영 화면 9/9, 고객 화면 mock 서버 시험 3/3은 원 보고서에 보존합니다. 주기적 재전송은 관련 회귀 27/27·작업 반복 및 볼륨 정의 검사 8/8로 확인했습니다. Team·여행 묶음·감시의 오류 콜백, 여행 삭제 및 실제 PostgreSQL 다중 연결 경쟁·복구 8/8은 [후속 연결 시험](../records/reports/2026-10-12_0520_diagnostic-delete-integration.md)에 있습니다. 새벽·낮 감시·Team의 실제 Dining 읽기 경로와 첫 HTTP 예약 중복 방지는 [장소 정책 접합](../records/reports/2026-10-12_0546_place-status-integration.md)의 새 인수 20/20에서 확인했습니다. [최신 선택 회귀](../records/reports/2026-10-12_0552_privacy-regression-integration.md)는 218통과·11건너뜀입니다. [최초 분류·라우팅 접합](../records/reports/2026-10-12_0603_initial-diagnostics-integration.md)의 관련 회귀268/268과 [추가 DB·고객 화면](../records/reports/2026-10-12_0626_review-support-db-integration.md)의 DB20/20·화면5/5를 후속 확인했습니다. 실제 무료 관측 자료의 대상 장소 충족률, 최신 전체 회귀와 배포 인수는 남아 있으므로 W05·W09는 부분 접합 상태입니다.

전용 SQL 후보 `902_unattended_operations.sql`은 격리 PGlite와 후속 전용 PostgreSQL에 적용했고 업무 DB에는 적용하지 않았습니다. 최초 로컬 격리 시험·화면 반응은 [실행 보고서](../records/reports/2026-10-12-unattended-operations-local-verification.md), 후속 실행은 위 접합 보고서에 기록합니다. 기존 서비스 개선의 동의 기반 합성 자료와 이번 결함 고객 연결은 계속 분리합니다.
