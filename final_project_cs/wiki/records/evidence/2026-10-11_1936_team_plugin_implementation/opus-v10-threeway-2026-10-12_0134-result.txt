## 정적으로 확인한 결합 (실행 재현 아님)
- **resolve는 읽기 질문에만 적용됩니다.** `fact_context.py:34-35`에서 answer_fact + ITEM_FACTS가 아니면 결정을 그대로 돌려줍니다.
  - 그래서 `trip_messages.py:699-709`의 업무 descriptor 대상이나 분류 표지가 바뀌지 않습니다.
  - 변경 업무에 fact focus가 이어지지 않는 경계도 지켜집니다.
- **focus 저장:** 답이 `answered`일 때만 `chat_reply.focus`로 Case에 저장됩니다(`:861-862`, `:872-873`).
  - 같은 요청 재전송 응답에는 choices/choices_title/more/answer_web 네 키만 실립니다(`:326`).
  - `chat_log.recent`의 JOIN은 tenant와 trip 조건으로 묶여 있습니다(`chat_log.py:35-39`).
  - focus에는 item_id/version/at/source만 있어 개인정보가 들어가지 않습니다.
- **TTL과 버전:** 만료 기준은 서버 시각입니다(`:698`). 이전 질문 대상(previous_fact)은 최신 버전과 다르면 다시 고르라고 묻습니다(`:739-742`).
  - 이전 문맥이 없거나 읽을 수 없으면 대상을 비운 채 답합니다(`fact_context.py:63-65`). 이것은 문맥 만료를 치명 결함으로 처리하지 않는다는 약속과 맞습니다.
- **대기 중 업무 보호:** 대기 재개(`resume_pending`)는 결정보다 먼저 돌지만, 명시 연결이 없으면 저장된 선택지·형식에 정확히 맞는 답만 연결합니다(`case_dispatch.py:117-121`, `:321-343`).
  - 그래서 사실 질문이 기존 대기 업무의 토큰이나 메시지를 소비하지 않습니다. `test_web_conversation_isolation.py`의 의미와도 일치합니다.
- **같은 요청 처리:** 같은 request_id의 다른 본문은 SHA로 409를 냅니다(`:312-315`). case.create 멱등 장부도 같은 본문 지문을 씁니다(`case_intake.py:135-145`).
- **guardrails:** newbase 대비 차이는 reliability 키 두 개 추가뿐이고, `focus_ttl_seconds: 1800`은 newbase 값 그대로입니다.
  - v9 대비 차이는 주로 서식입니다. v9에서 따옴표가 빠져 있던 `00:10`, `08:00`, `03:00` 같은 값은 v10에서 따옴표가 복원됐습니다.
- core/application에서 domains를 import하는 곳은 없습니다(직접 grep).

## 지적 사항 (모두 정적 추론, 실행 재현 안 함)
1. **[중간 · 우리 overlay 기존 문제, v10 결합으로 생긴 것 아님 · 경로 확신 높음] 처리 중인 사실 질문 Case를 같은 request_id로 다시 보내면 409가 납니다.**
   - 위치: `trip_messages.py:316-321` → `case_dispatch.py:277-286`
   - 규칙 모드(off/shadow)에서 분류를 응답 뒤로 미룬 경우:
     - 답은 Case를 만들 때 이미 저장되지만, 분류가 끝나기 전에는 상태가 classifying입니다.
     - 이때 같은 요청이 오면 「미완료 요청」 409가 납니다.
     - 코드 주석 `:337-338`의 「분류가 뒤에서 도는 동안 같은 요청이 다시 와도 앞의 답이 나간다」는 약속과 어긋납니다.
   - on 모드에서는:
     - answer_fact가 routing 이후 fact_reply/_place_extras를 처리하는 동안에는 저장된 업무 계획(conversation_dispatch)이 없습니다.
     - 그래서 같은 요청이 오면 「저장된 실행 계획이 없어」 409가 납니다.
     - 이 단계에서 프로세스가 죽으면 그 request_id는 계속 409를 받습니다.
   - v9와 v10에서 이 코드는 바뀌지 않았고, 단위 시험이 classifying 상태의 409를 의도된 동작으로 고정해 두었습니다. 읽기 전용 Case를 업무 Case와 구분하지 않는 문제입니다.

2. **[낮음 · newbase 기존] 이동(mobility) 항목을 고른 채 사실 질문을 하면 「다시 선택」으로 답합니다.**
   - 위치: `fact_context.py:36-38`. 이동 항목을 ID 목록(by_id)에서 빼기 때문입니다.
   - 화면에서 이동 항목을 고를 수 있는지는 확인하지 못했습니다.
