# 게스트 이관 후 Case가 연결된 여행 권한

## 실행

```text
python -m pytest tests/e2e/test_web_auth_guest_transfer.py -q
........ [100%]
8 passed in 18.78s
```

로컬 개발 DB, 실제 cs 프로젝트 서버 라우터, mock 소셜 인증 업체를 사용했다. 외부 업체 요청은 보내지 않았다.

## 확인

`test_transferred_trip_with_open_case_keeps_web_proposal_access`는 공식 `repository.create_case`로 게스트 여행의 열린 Case를 만들고, 같은 여행에 보류 제안을 기록한다. 기존 회원으로 로그인한 뒤 다음 결과를 확인했다.

- 여행 소유자는 기존 회원으로 바뀌고 Case의 발생 당시 고객은 그대로다.
- 현재 회원의 웹 제안 조회는 200, 제안 선택(기존 일정 유지)은 200 `kept`다.
- 별도 게스트로 동일 제안을 조회하면 404다.
- `customer_cases` 직접 UPDATE를 추가하지 않았다.

실제 접근 경로는 `trip_api._proposals`, `_choose`에서 먼저 현재 여행 소유자를 확인한 뒤 `PendingStore`의 tenant+trip 조회를 사용한다. 제안 선택 권한을 Case의 발생 당시 customer_id로 검사하지 않으므로 이번 이관에 Case 소유권 변경은 필요하지 않았다. 여행 신고·대체 요청·메시지도 입구에서 동일한 여행 소유 검사를 거친다.

확인 범위는 여행 웹 입구의 보류 제안 조회·선택과 고객 격리다. 별도 운영자 Case 화면, 이미 실행 중인 모든 Core 업무의 결과, 실제 소셜 업체 인증을 확인했다는 뜻은 아니다.

게스트 정리의 장기 보관 판단은 별개다. 현재 게스트 정리 로직은 원래 고객의 유휴 보존시간이 지난 Case를 정리할 수 있다. 이관을 이유로 기존 보관기간이나 삭제 정책을 임의 변경하지 않았다.
