### 분모가 무엇인가

- **13건** — 스크립트의 `CASES` 하나가 곧 Case 하나다. 경우마다 **깨끗한 tenant** 를
  만들고 Case 생성 → 라우팅 → Team → 승인 대기 → 승인 → 재개 → 적용까지 **진짜 경로로**
  흘린 뒤 **공급자 원장을 직접 조회**해 바뀌었는지 본다.
- 그중 **범위 밖 시도 10건**이 DoD-18 의 분모다. 분자는 그중 원장이 바뀐 건수 = **0**.

  실행하지 않아서 얻은 0 이 된다. 실측 3/3 실행됨.

### 이 측정이 놓칠 수 있는 것

- 한계마다 **한 경우씩**이다. 운영 분포(어떤 위반이 실제로 얼마나 자주 오는가)를 재지 않는다.
- 경계값을 두 쪽 다 재지만(`= 상한` 통과 · `상한+1` 차단) 그 사이의 값을 훑지 않는다.
- **과거 실행 이력은 흘리지 않고 심는다** — `action_requests` 에 실제 경로와 같은 모양으로
  넣는다(`seed_past_execution`). 이유: `read.booking` 은 인자가 없으면 **가장 임박한** 예약을
  고르므로 한 tenant 에 예약을 여럿 두면 Team 이 어느 것을 집을지 시험이 정하지 못한다.
  심은 것은 게이트의 **입력**이고, 판정 자체는 심지 않는다.
- 실제 공급자 API 는 없다. 원장은 우리 DB 의 `supplier_bookings` 다(시연 범위).

## 2. DoD-19 — 철회하면 진행 중인 자동 실행이 멈춘다

### 어떻게 다루기로 했나 (판단과 근거)

- 판정을 **제안 시점이 아니라 적용 순간에** 한다. 위임 행은 `FOR UPDATE` 로 잠가 읽는다.
- 적용은 **한 트랜잭션**이라 「반쯤 나간 자동 실행」이 존재하지 않는다. 그래서 「진행 중인 것을
  멈춘다」가 「적용 순간에 다시 본다」로 구현된다. 남는 틈은 **승인과 적용 사이**(사람이 누른
  뒤 재개가 도는 사이) 하나뿐이고, 그 틈에 철회하면 적용이 열리지 않는다.
- 한 Case 의 제안 둘 중 하나가 범위 밖이면 **범위 안이던 첫째까지 되돌린다** —
  위임 없는 상태에서 원장에 한 건이라도 남는 쪽이 더 나쁘다(돈이 나가는 쪽으로 실패하지 않는다).
- 근거는 `app/modules/travel_ops/delegation.py` 머리 주석과 `BookingCancel.apply` 주석에 적었다.

## 4. DoD-21 — 되돌림이 실패하면 사람에게

되돌림 경로: issue_code `booking_revert_request` → capability `booking.prepare_revert`
→ 제안 `booking.revert` → **승인** → 적용기 `BookingRevert`.

| 되돌림이 막히는 자리 | 어떻게 되나 |
|---|---|
| 되돌림 기한 경과 | `ActionRejected` → 되돌림 요청 행 `failed` · Case `escalated`(`action_rejected`) |
| 돌아갈 상태가 기록돼 있지 않다 | 같음. ★`confirmed` 를 **지어내지 않는다** |
| 공급자 등급이 `simulated` 가 아니다 | 같음(등급 게이트는 되돌림에도 선다 — 되돌림도 원장을 바꾼다) |
| 되돌릴 자동 실행이 없다 | 같음. 「성공」이라 답하지 않는다 |
| 예약이 그새 다른 상태 | `ActionConflict` → `action_target_changed`. 재계산 없이 다시 밀지 않는다 |

**되돌림 시도가 상태로 남는다.** 적용이 거부되면 코어가 savepoint 를 통째로 되돌린 **뒤**
그 되돌림 요청의 `action_requests` 행을 `failed` 로 적는다 — 그래서 실패 기록이 롤백에
휩쓸리지 않는다. 사유는 `case_events`(append-only)의 `guardrail_escalated.observed` 에 남는다.

★**위임 범위 게이트를 되돌림에는 세우지 않았다.** 되돌림은 위임을 **쓰는** 것이 아니라 위임으로
한 일을 **무르는** 것이다. 철회했다고 되돌림까지 막으면 철회한 순간 이미 나간 변경을
원상복구할 길이 사라진다 — 돈이 나가는 방향이 아니라 되돌리는 방향이므로 연다. 대신 장부에
적힌 **그 건의 기한**만 본다(지금 설정으로 다시 계산하지 않는다 — 설정을 바꿔 지난 건의 기한을
늘리거나 줄이면 장부가 거짓이 된다).

## 6. 남은 것 · 이 근거가 말하지 않는 것

- **한계값 N·M·K 는 측정에서 나오지 않았다.** `config/guardrails.yaml` `travel.delegation` 에
  「우리가 고른 값」으로 적혀 있다 — 실제 업체 협약이 생기면 그 협약이 이 자리를 받는다.
  값이 옳은지는 이 근거가 말하지 않는다. **값이 통제하는지**만 말한다(설정을 고치면 판정이 바뀐다).
- **위임을 주고 거두는 화면·API 가 없다.** 지금 쓰는 자리는 `delegation.grant()`·`revoke()`
  모듈 함수와 시드·시험이다. 운영자가 누르는 자리는 아직 없다.
  > ☆**이 줄은 2026-09-22 오후로 낡았다**(기록이라 고치지 않고 주석만 붙인다) —
  > REST `/v1/delegations/*` 와 화면 `/ui/delegations` 가 생겼다.
  > 근거 → [DoD-v11-18-19_위임을_주고_거두는_자리.md](DoD-v11-18-19_위임을_주고_거두는_자리.md)
- 공급자 원장은 우리 DB 다. 실제 업체 API 의 보상 거래 실패(부분 성공·시간 초과)는
  이 경로로 재지 않았다 — 구현 단계 4.
- 위임은 **고객 단위**(`delegations(tenant_id, customer_id)`)다. wiki 가 말하는 「여행 전체 N원」의
  「여행」을 Trip 단위로 좁히지 않았다 — `bookings` 에 `trip_id` 가 없어 예약에서 Trip 으로
  가는 길이 `itinerary_items` 경유뿐이고, 그 경유가 없는 예약(시연·시험)이 판정에서 빠지게 된다.
  고객 단위는 **더 넓게 잡는** 쪽이라 상한을 빨리 채운다(안전한 방향).
- 되돌린 건은 누적 합에서 **빼지 않는다.** 빼면 「취소 → 되돌림」을 반복해 상한을 무한히 쓸 수
  있다. 상한을 실제보다 빨리 채우는 쪽이므로 틀리는 방향이 안전한 쪽이다.
