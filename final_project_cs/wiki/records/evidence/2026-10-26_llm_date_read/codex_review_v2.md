판정: 방향은 맞지만 v1 그대로는 요구를 충족하지 못합니다. 숫자 기반 분류 제거는 타당하나, 근거 누락 때 `month_day`로 바꾸면 명시 과거·상대 과거를 미래로 변조합니다. `dates.py`의 `_relative_for_item(lines, …)`도 원문 해석이므로 이 경로에서 제거해야 합니다.

1. 더 나은 출력 계약
- 작은 모델에는 **완성 날짜 `resolved_date` + 판단 종류 + 근거**를 권합니다. 구성 요소·offset까지 병행하면 출력과 일치 검사가 복잡해집니다.
- enum은 `explicit_year / relative / yearless`가 명확합니다. 날짜 미확정은 `resolved_date=null`로 표현하고, 근거가 있으면 판단 종류는 보존합니다.
- `date_quote`와 nullable `year_quote`를 분리하세요. `2026년 여행` 머리줄과 `3/5`가 떨어진 경우를 표현할 수 있습니다.
- `explicit_year`는 `year_quote` 필수이며 날짜 인용과 겹쳐도 됩니다. `relative`의 연도는 원문 숫자가 아니라 오늘 기준 계산 결과입니다.
- 코드는 인용 존재·출력 날짜의 유효성·필드 간 일관성만 검사합니다. 원문 의미와 머리줄 적용 범위는 모델이 판단합니다.
- `yearless`의 다음 발생일도 모델이 출력하고, 코드는 **모델 날짜의 월·일**을 기준으로 정책 일치만 검증할 수 있습니다. 고객 원문은 파싱하지 않습니다.

2. 질문 네 가지에 대한 답
- **구성 요소 vs 날짜 / 인용:** 완성 날짜와 별도 `year_quote`를 우선 권합니다. 구성 요소는 달력 계산을 코드로 옮기는 것이 허용될 때만 대안이며, offset 표현은 비추천입니다.
- **인용 속 연도 숫자 검사:** 넣지 마세요. 원문 숫자로 의미를 판정하는 규칙이며, 두 자리·문자 연도에서 다시 깨집니다. 인용 존재 확인은 의미적 정확성까지 보장하지 않습니다.
- **`date_form` 누락:** 계약 오류로 처리하세요. 재추론 후에도 실패하면 날짜 미확정·확인 요청으로 보내고, 연도 없는 날짜로 강등하지 마세요. 옛 기록 재생도 버전별로 구분해야 합니다.
- **기존 LoRA에 필드 추가:** 형식은 맞아도 enum 의미·근거 연결이 틀릴 수 있습니다. 실제 모델로 날짜 외 항목까지 회귀 평가하고, 부족하면 새 계약 예제로 추가 학습하세요. 온도 0·스키마 제약은 의미 정확성을 보장하지 않습니다.

3. 8B 모델용 프롬프트
- 권장 출력 순서: `date_quote → year_quote → date_form → resolved_date`. 실제 Ollama 출력에서도 이 순서를 따르는지 확인하세요.
- 날짜 규칙을 한곳에 모으고 KST 기준 오늘·요일·주 시작 기준을 명시하세요. 긴 사고 과정 출력은 요구하지 마세요.
- 대조 예제를 쓰세요: `3/5 + 2026원` / `'26.3.5` / `다음 달 5일` / `작년 크리스마스` / 머리줄 연도 상속.
- 각 예제에 기준일과 정확한 결과를 넣고, 오늘 포함·연말 경계·명시 과거 유지·무관한 숫자 배제를 보여 주세요.
- 기존 전체 JSON 예제에도 새 필드를 넣어 학습된 옛 출력과 충돌을 줄이세요.

4. 위험과 검증
- `_fill_year`는 연도 없는 `2/29`를 다음 윤년까지 찾지 않고 `2/28`로 바꿀 수 있습니다. 날짜를 조용히 보정하면 안 됩니다.
- `03/05`, `26/3/5`, 세기 불명 두 자리 연도는 의미가 모호할 수 있습니다. 확정 불가 시 확인 대상으로 표현하세요.
- 오늘·어제·12/31↔1/1·윤년·지난주 금요일·여러 머리줄·후속 정정·전화번호·예약번호·금액을 시험하세요.
- 최종 날짜뿐 아니라 종류·인용·미확정 처리·과거 보존도 채점하고, 고정 기준일 여러 개로 보지 않은 문장을 평가하세요.
- 접수와 채팅 추가가 같은 날짜 계약을 사용해야 합니다. 날짜 실패를 `fallback_day`로 덮지 말고, 상대 과거도 날짜는 보존한 뒤 추가 가능 여부를 별도로 판단하세요.
