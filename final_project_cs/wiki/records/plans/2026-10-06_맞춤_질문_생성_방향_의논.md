# 로딩 중 질문을 「계획을 본 LLM 이 고르는 맞춤 질문」으로 바꾸는 방향 — 의논 결정 (2026-10-06)

> uiux 세션 + 코덱스(본 계정) 1회차 독립 판단 · 두 쪽 선택이 같다(B). 사용자 아이디어(2026-10-06)를 평가한 기록이다. 검토자: 기계(Claude · Codex 본 계정) — 사람이 봤다고 쓰지 않는다. 사용자 확정은 「지금은 설문 기반으로 만들어 먼저 반영하고, 맞춤 질문은 그 다음 구현」이다.
> 원자료: 질문서 · Claude 1차 의견 · 코덱스 답은 uiux 세션 스크래치패드 `consensus/20261006_adaptive_survey/`(`q.md` · `claude_r1.md` · `r1_main.json`). 코덱스 판단의 모델 지연·품질은 **실측이 아니다**.

## 0. 한 줄 결론
**하이브리드(B)로 간다.** 질문의 「모양」(슬롯 · 닫힌 선택지 · 값의 뜻)은 고정 목록이고, LLM 은 계획을 보고 **어떤 슬롯을 물을지 고르고(최대 3) · 문구를 계획에 맞게 다듬고 · 계획에서 추정한 스타일을 「확인 질문」으로 묻는다.** 질문과 선택지를 처음부터 만드는 완전 자유 생성(C)은 하지 않는다.

| 안 | 내용 | 판정 |
|---|---|---|
| A | 고정 설문 유지 + 점진 개선 | **지금 배포하는 것**(다음 단계의 바탕) |
| B | 슬롯 고정 + LLM 이 고르고 다듬기 + 가설 확인 + 열린 질문 0~1 | **다음 구현** |
| C | 질문·선택지 완전 자유 생성 | 하지 않음(되돌릴 조건은 §6) |

## 1. 왜 B 인가 (두 쪽 일치)
1. 규칙 · 추천 로직이 쓰는 값은 `pace` · `preferred_mobility` · `priority` 같은 **구조화 값**이다. 슬롯 · 선택지 · 값의 뜻이 고정이어야 규칙 · 시험 · 평가가 된다. 자유 질문은 답의 뜻을 질문마다 다시 해석해야 해 경우의 수와 검증 비용이 폭발한다 — 사용자가 걱정한 바로 그 지점.
2. 사용자의 스타일은 **계획에서 추정**한다. 이미 드러난 정보를 다시 묻지 않고, 추천 결과를 크게 바꿀 **불확실성**을 묻는다. ★「질문 수가 줄고 정보량이 는다」는 **아직 가설**이다(실측 전).
3. 에이전트 LLM 에게 줄 정보는 많을수록 좋다 — 구조화 값 + 근거 + **원문 질문 · 답**을 함께 넘긴다(§4).

## 2. 질문을 고르는 규칙
- **최대 3개**(열린 질문 포함). 기준: 추천에 미치는 영향 · 불확실성 · 기존 답과의 중복.
- 순서: ① 안전 · 실행 가능성에 필요한데 모르는 **제약**(식사 제한 · 접근성 — 필요한 실무 제약만, 진단 · 종교 이유는 묻지 않는다) → ② **일정 속도 확인** → ③ 이동 수단 · 대체 장소 우선순위.
- **가설 확인 질문**은 중립 · 닫힌 질문이다: 「둘째 날은 5곳 방문과 이동 약 2시간이 예정되어 있어요. 어느 속도가 편한가요?」 — 여유롭게 · 지금 정도 · 더 알차게 · 아직 모르겠어요(**반대 답과 모름을 동등하게**). ★추정은 **미확인으로 보관**하고 사용자가 **명시적으로 답한 것만** 프로필에 넣는다. 「지금 정도」라는 답도 여행 전체가 packed 성향이라는 일반화로 쓰지 않는다. 외부 에이전트가 만든 계획은 사용자 취향의 증거가 아니라 **확인할 초안**이다.
- 신호 후보: 하루 장소 수 · 체류 시간 · 이동 횟수 · 총 이동 시간 · 식사 · 휴식 시간의 유무 · 실내 · 야외 비율. 장소 수만 보지 않고 시간과 이동 부담을 함께 본다. 운영시간 같은 **계획상의 제약**과 **사용자의 선호**를 구분한다.
- 모름 · 건너뛰기를 허용한다. **로딩 완료를 답변에 종속시키지 않는다**(안 답해도 계획 확인으로 간다).

## 3. 14초 안의 지연 · 실패 설계
- 전체 정리가 끝난 뒤 시작하지 않는다 — **원문 추출이나 최소 계획 요약이 준비되는 즉시** 일정 정리와 질문 선택을 **병렬**로 돌린다.
- 제한 시간은 **실측으로 정한다**(미정). 초과 · 오류 · 스키마 위반이면 **지금의 고정 질문**으로 대체한다(질문 0개로 끝내지 않는다). 사용자가 **답하기 시작한 질문은 늦게 온 생성 결과로 바꾸지 않는다.**
- 로딩 경로에서 LLM 호출은 **한 번**(여러 번 호출 · 재시도 연쇄 금지).

## 4. 다운스트림(에이전트 LLM)에 넘기는 모양
- `profile`: 구조화 값마다 `source`(user_answer · inferred …) · `scope`(trip · day) · `question_id` · 확인 여부.
- `hypotheses`: 추정 + 근거 위치 + **미확인 상태**(프로필과 섞지 않는다).
- 답변 이력: **질문 문구 · 선택지 ID · 라벨 · 자유 답변 · 질문 묶음 버전**을 보존한다.
- 계획 글 · 답 속의 지시문은 **사용자 데이터**다 — 시스템 지시나 도구 실행 · 프로필 변경의 권한으로 쓰지 않는다(프롬프트 주입 경계).

## 5. 개인정보 · 민감정보
- 건강 · 장애 · 종교 등은 계획에서 **추론하지 않는다.**
- 질문 생성에는 연락처 · 예약번호 등을 지운 **최소 계획 정보**만 보낸다. 자체 GPU 모델과 외부 모델 중 **어느 경로로 가는지, 보관 정책**을 사용자에게 밝힌다 — ★외부 전송 정책은 배포 전에 확정해야 한다(미정).
- 쌓일수록 노출과 상충이 늘므로 최소 수집 · 보관 기간 · 삭제 · **최신 명시적 답이 우선**하는 규칙을 정한다.

## 6. 평가와 되돌리는 조건
- 골든 계획 묶음으로 시작: 사람이 슬롯 적합성 · 근거 정확성 · 유도 표현 · 중복 · 값 매핑을 보고, 스키마 성공률 · 지연 · 고정 질문 대체율을 잰다. 그다음 고정 설문과 비교(질문별 답변율 · 전체 응답 수 · 이탈 · 완료 시간 · 실제 수정과 추천의 유용성).
- **A 로 되돌리는 조건**: 제한 시간 안에 유효한 질문을 안정적으로 못 만들거나, 답변율 · 유용성은 안 오르고 이탈만 늘거나, 외부 전송이 막히고 자체 모델이 품질 · 지연 기준을 못 맞출 때.
- **C 를 다시 볼 조건**: 슬롯 밖 자유 질문이 반복해서 중요한 정보를 얻고, 그 답의 구조화 · 안전성 · 지연까지 검증돼 B 보다 뚜렷하게 유용할 때.

## 7. ★지금(설문 기반) 지킬 것 — 다음 단계와 호환되도록
1. **웹은 서버의 `questions[]`(`id · kind · title · why · options[{id,label}] · answer`)만 그린다.** 질문 문구 · 선택지의 뜻을 하드코딩하지 않는다. 모르는 `kind` 는 화면을 깨지 않고 **그 문항만 건너뛴다.** 질문이 0개여도 빈 화면을 만들지 않는다.
2. **문항 ID 와 슬롯 키를 분리**한다. 선택지 ID ↔ 구조화 값의 **매핑은 서버가 소유**한다. 문구를 바꿔도 ID 를 다시 만들지 않고, 같은 선택지 ID 의 뜻을 바꾸지 않는다. 질문 묶음에 **버전**을 둔다.
3. `POST …/survey {answers:{문항id:선택지id}}` 는 유지한다(부분 답 · 덮어쓰기). 서버가 **당시의 질문 묶음과 매핑을 보관해** 답을 해석한다. 자유 답변은 별도 필드나 계약 버전으로 **나중에 더한다.**
4. 지금 **하지 않을 것**: 완전 자유 선택지 생성 · 자유 답변을 무조건 프로필에 반영 · 추정값으로 기존 답 덮어쓰기 · 로딩 경로의 여러 차례 LLM 호출 · 미측정 지연을 전제로 한 구현.

## 8. 남은 일(이 문서가 정하지 않은 것)
- 질문 생성에 쓸 모델(자체 GPU 소형 / 외부)과 **제한 시간**(실측 필요) · 외부 전송 정책 · 슬롯 목록의 확정 · 골든 계획 묶음 만들기 · 서버 계약의 `questions[]` 확장 필드(버전 · 슬롯 키 · 가설 근거) 설계 — 모두 **cs 서버 · RAG 쪽 몫이거나 사용자 결정**이다.
- 실측한 것은 없다: 소형 모델이 선택지 있는 질문을 스키마대로 안정적으로 내는지 · 사용자 이탈 데이터는 모른다.
