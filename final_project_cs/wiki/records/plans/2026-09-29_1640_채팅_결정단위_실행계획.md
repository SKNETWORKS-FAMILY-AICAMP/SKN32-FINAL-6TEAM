## 근본 원인 (Claude · Codex 본 · Codex 보조 셋이 같은 순위)

1. **해석이 여행 상태를 보지 않는다.** 분류기·추출기 모델이 고객 문장만 본다 — 일정 목록·변경 이력·앞 대화·화면 선택을 모른다.
   그래서 「그 식당」「원래대로」「이전에 요청한 거」「첫 식당」의 **대상**을 모델이 정할 수 없었고, 키워드 규칙이 대신 메웠다.
   새 표현이 나올 때마다 규칙이 늘었다(오늘 하루 대상 규칙 셋째 판).
2. **판단이 넷으로 쪼개져 서로 어긋난다** — 사실 질문 낱말 규칙 → 분류기 → 추출기 → 대상 규칙. 식당 요청이 화면 선택된 활동으로,
   장소 정보 요청이 규정 검색으로 떨어졌다.
3. **결과 약속이 없다** — 후보가 없으면 「없어요」로 끝났다(고객이 할 수 있는 것이 없다).
4. **검증 공백** — 채팅 시험은 고정 답변 분류기로만 돈다. 실제 문장 · 실제 모델 재생 시험이 없어 2160 통과 상태에서 실사용 실패가 이어졌다.

## 해결 — 결정 단위 (B)

- 모델 **한 번**의 구조화 호출(Ollama `format` = JSON 스키마, enum). 입력: 일정 목록(짧은 id · 날 · 시각 · 종류 · 이름) · 변경 이력(id) ·
  **서버가 저장한** 최근 대화 · 화면 선택 · 고객 문장. 출력: action · target_item(목록 id|none) · target_change(변경 id|none) · fact · minutes · question.
- **모델은 고르기만 한다.** 서버가 id 존재 · 종류 · 보호 · 버전 · 중복을 확인하고 이미 있는 실행 함수를 부른다. 확정 안 되면 **되묻는다**(clarify).
- ★**모델 실패 · 검증 실패 때 옛 경로로 넘기지 않는다**(Codex 두 계정 지적 — 옛 오처리를 되살린다). 바꾸지 않고 한 가지를 묻는다.
- **대화 기록을 서버에 둔다**(`trip_chat_turns`, 034 — 가린 문장만).
- **결과 약속은 서버에 둔다** — 결과는 늘 「한 일」 또는 「실제로 고를 수 있는 안」. 후보 0이면 조건 풀기(시각 늦추기 · 다음 일정 근처)를
  계산해 묻고, 끝내 없으면 확인된 제약과 고객이 바꿀 수 있는 조건을 말한다.
- Case 에 입력 요약 · 모델 결정 JSON · 검증 결과 · 실행 결과 · 지연을 남긴다.
