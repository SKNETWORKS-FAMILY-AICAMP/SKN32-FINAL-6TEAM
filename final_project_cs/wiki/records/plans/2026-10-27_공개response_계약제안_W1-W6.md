## 1. 무엇을 더하나 (가산형 · 선택 필드)

| 자리 | 지금 | 더하는 것 |
|---|---|---|
| `GET /v1/web/trip-intakes/{id}` · `PATCH …/edits` · `…/restore` 결과 | `status`(reading/review/confirmed/fatal …) · `stage_label` · `check` · `review` | 선택 `response` |
| `POST …/confirm` 결과 | 등록 결과(`trip_id` 등) | 선택 `response` |
| `POST …/plan` (웹 「일정 짜 줘」) · `POST /v1/trips/plan` (에이전트 API) | 초안 · 등록 결과 | 선택 `response` |
| SSE `…/events` 의 `result{state}` | `state` | 바꾸지 않는다(이번 범위 밖 — 같은 `response` 를 실을지는 2차) |

`response` 모양(공개 · 이 네 칸만):

```json
{"answer": "계획서의 읽은 내용을 검토해 주세요. 아직 여행을 등록하지 않았어요.",
 "completion": "complete" | "partial",
 "question_status": ["answered" | "needs_input" | "unsupported" | "failed", ...],
 "execution_status": "reading" | "review_required" | "failed" | "confirmation_recorded" | "registered" | "plan_generated"}
```

- **필수 아님.** 없으면 웹은 지금 화면 그대로(성공을 추정하지 않는다). 기존 `status` · `stage_label` · `check` 의 뜻은 바꾸지 않는다 — `stage_label` 에 문장을 넣는 우회안은 기각(SSE `state` 와 같은 값이라 뜻이 바뀜).
- `execution_status` 는 **서버가 이미 아는 상태의 투영**이다(새 업무 상태 아님). 매핑(제안):

| ID | `execution_status` | 조건(서버 상태) | `answer` |
|---|---|---|---|
| W1 | `reading` | 접수 `status ∈ {reading, checking}` | 계획서를 읽고 있어요. 아직 여행을 등록하지 않았어요. |
| W2 | `review_required` | 접수 `status = review` · `trip_id = null` | 계획서의 읽은 내용을 검토해 주세요. 아직 여행을 등록하지 않았어요. |
| W3 | `failed` | 접수 `status = fatal` 또는 `review_error` · `blocked` 근거 | 계획서 읽기 또는 확인을 마치지 못했어요. … (원인 코드는 기존 `error.code` 그대로, 문장에 원문 · 내부 값 없음) |
| W4 | `confirmation_recorded` | 접수 `status = confirmed` 를 GET 으로 다시 볼 때 | 접수에 등록 상태가 기록되어 있어요. … (지금 여행 상태는 여행 화면이 정본) |
| W5 | `registered` | `confirm` · 등록 `plan` 이 **같은 트랜잭션에서** 여행 생성 · `mark_confirmed` 를 끝낸 뒤 | 여행 등록과 저장을 확인했어요. 계획서에서 일정을 확인해 주세요. |
| W6 | `plan_generated` | `/v1/trips/plan` 이 등록하지 않은 초안만 냈을 때 | 초안 일정을 만들었어요. 아직 여행을 등록하지 않았어요. … |

- W3 은 기존 `review_error` · `blocked` 와 뜻이 겹친다 → **새 상태가 아니라 그 둘의 공개 요약**으로 정의한다(웹은 기존 오류 처리 그대로, 문장만 더한다).
- W5 의 「저장 확인」은 **커밋 뒤 재조회를 하지 않는다**(감시 자동 변경 · 다른 탭이 판을 올리면 등록은 됐는데 500 이 되는 문제 — I행 보고서 3절 기각 사유). 근거는 같은 트랜잭션의 생성 결과 + request_id 멱등이다. 재조회 확인이 필요하면 별도 읽기 API 로 분리(2차).

## 2. 지키는 선

- `response` 에 scope(tenant · customer · trip id) · 원문 · 토큰 · evidence · workflow 를 싣지 않는다(공개는 위 네 칸). 내부 기록(`basis.response`)은 기존 개발 모드 정책 그대로.
- 문장은 서버 고정 문구틀(모델 생성 아님). 언어는 기존 응답 언어 정책 그대로.
- 잘못된 enum 은 웹이 고정 계약 오류로 거부하고 원값을 오류 문장에 싣지 않는다(`web-response-status.md` 초안 규칙 승계).
- `registered` 는 승인 · 업체 거래와 무관하다 — 업체 예약 승인 경계(AGENTS.md) 우회 없음.

## 3. 웹 소비(제안)

- 접수 확인 화면: 기존 「계획 확인 안내」 자리에 `response.answer` 한 줄. `reading` · `review_required` 는 「아직 등록 전」, `confirmation_recorded` 는 「여행 화면에서 지금 상태 확인」, `failed` 는 기존 오류 영역 옆 보조 문장.
- `registered` 는 confirm 결과 또는 서버 확인 상태와 맞을 때만 등록 결과 자리에 보인다. 완료 배지를 새로 만들지 않는다.
- 세션 세대 규칙(`stale_registration_session`)은 초안 그대로 승계 — 늦은 결과를 다른 세션 메모리에 넣지 않는다.
- `final_project_ui` · `frontend` 둘 다 같은 allowlist 를 쓴다(한쪽만 소비하면 화면마다 다르게 보임).
