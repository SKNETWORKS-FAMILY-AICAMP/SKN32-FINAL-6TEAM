# develop 통합 전 작업 방향 (2026-10-05)

`[2026-10-05 사용자 지시]` 오늘은 **develop 브랜치에서 더 작업하지 않는다.** 각자 개인 브랜치에서 마저 고치고, 다 끝난 뒤 사용자가 전체를 한 번에 develop 에 통합해 문제를 잡는다.
`[2026-10-05 사용자 정정]` 방향의 기준은 **우리가 이미 구현해 둔 설계**다. Activity 에이전트를 그 설계에 맞게 **다시 고친다.** 우리 구현을 Activity 쪽 것으로 바꾸지 않는다.

> 앞 판(「Activity 판정을 develop 쪽으로 받는다」)은 방향이 반대였다. 백업: [_backup/](_backup/) 의 `…_develop_통합_작업_방향_앞판` — 이 문서의 앞 판 사본.

## 1. 한 줄 요약

점검(누가 영향받나)은 **코어가 제공하는 공유 점검 도구**가 하고, 판단(영향받은 일정을 어떻게 고치나)은 **에이전트**가 한다. 우리 쪽은 이미 그렇게 돼 있고 그대로 둔다. 바뀌는 것은 Activity 에이전트다 — 이 설계대로 움직이게 맞춘다.

## 2. 설계 (사용자가 정한 것 · Activity 담당에게 이미 전달함)

| 상황 | 동작 |
|---|---|
| 3분 감시 | 공유 점검 도구가 재난 종류별로 **영향받는 에이전트만 걸러낸다** — 비가 와도 영향 없는 식당 에이전트는 부르지 않는다 |
| 첫 계획서 접수 | 에이전트를 **어차피 부른다.** 공유 도구는 에이전트가 별도로 판정할 때 쓴다 |
| 사용자가 지정한 변경 | 위와 같다 — 어차피 부르고, 같은 도구로 별도 판정 |
| 영향받은 에이전트 | 걸러진 뒤에는 자기 일정 사정에 맞춰 **스스로 조정**한다 |

`disruptions.py` 는 코어가 아니라 `app/domains/travel_ops/ports/data_sources/`(2026-10-06 폴더 이동 뒤 경로 — 옛 `app/infrastructure/travel/`) 의 **공유 점검 도구**다(Activity 담당 확인). 코어 격리(INV-CS-ARCH-001)와 부딪히지 않는다.

### 맞추는 순서 (제안 — 코드 착수 전)

1. **대체 장소 두 갈래**(6번)를 읽고 어느 쪽이 우리 설계와 맞는지 가른다 — 영향이 가장 크다.
2. **성립 점검 한 번 호출**(1번) — 우리 `team.py` 가 이미 그렇게 돼 있으므로, 통합 때 develop 쪽 `feasibility.py` 를 가져오지 않는 것이 곧 맞추는 일이다. 시험으로 고정한다(같은 재난 문자 입력에 감시 길과 문의 길이 같은 판정을 내는지).
3. **자체 감시 끄기**(2번) — 호출을 붙이지 않는 것이 곧 맞추는 일이다. 통합 점검표에 적는다.
4. **`insufficient_info` 옮기기**(5번).
