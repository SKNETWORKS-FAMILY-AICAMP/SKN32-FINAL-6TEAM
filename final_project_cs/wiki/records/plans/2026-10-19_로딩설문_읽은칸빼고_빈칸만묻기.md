# 로딩 설문 — 계획서에서 읽은 칸은 빼고, 빈 칸만 묻는다

`[2026-10-19 사용자 지시]` 「로딩 단계에서 설문이 계획에서 못 얻은 내용을 확인하는 걸로 해야 한다. 계획서에서 보이면 반영하고, 없으면 로딩 중에 질문. 우리 설문 7개 만든 거, 항로 지킴이와 겹치는 것(일정이 막힐 때 알아서 짤지 · 내가 고를지) 하나를 빼면 많아야 6개 — 최대 3문항 말고 그건 다 입력받게 해도 된다. 나머지는 이대로 진행.」

이 문서는 10-05 기획 [`2026-10-05_설문_계획서에서_읽고_로딩에서_묻기_기획.md`](2026-10-05_설문_계획서에서_읽고_로딩에서_묻기_기획.md) §1 흐름을 실제로 구현하기 위한 설계다. 10-05 기획의 「최대 3문항」과 「설문 문항은 일단 그대로」는 이 지시로 바뀐다.

## 지금 상태 (2026-10-19 확인)

- 로딩 중 질문은 계획서와 상관없이 **늘 같은 2문항**이다(`intake/survey_answers.py` `QUESTIONS` — 「이동은 주로 어떻게?」 · 「대체할 곳은 무엇을 먼저?」, 상한 `MAX_QUESTIONS = 3`). 질문 목록을 만드는 `intake/pipeline.py`(원격 role-manager 417행)는 고객이 이미 답한 값만 보고, 계획서에서 읽은 성향(`intake/reading_prefs.py`)은 보지 않는다.
- 계획서 읽기는 7칸을 채운다(`reading_prefs.LABELS`): 이동 수단 · 일정 여유 · 식당 취향 · 실내 먼저 · 덜 걷게 · 하루 끝 시각 · 하루 시작 시각.
- 시작 설문 화면(웹 `features/onboarding/model.ts`)은 6문항이다: 여행 테마 · 누구와 · 우선순위(음식 · 활동 · 이동 + 세부) · 실내 · 실외(식당 · 활동) · 일정이 꼬이면 · 여유. 예전 판에는 내국인 여부가 있었다(지금은 묻지 않는다 — 쓰는 곳이 없다).
- 실제 기록(읽기 전용, 최근 6일): 오라클 ARM 에서 계획서에 이동 수단 낱말이 있는 9건 모두 이동 질문을 받았다(9/9). 근거: [10-19 진단 「로딩 설문 점검」](../../../../wiki/records/reports/2026-10-19_chat-intake-secretary-review.md).

## 정한 것

### 1. 로딩에서 물을 수 있는 문항 = 시작 설문에서 「일정이 꼬이면」을 뺀 것

| 문항(시작 설문과 같은 문구 · 선택지) | 계획서에서 읽어 채우는 칸(있으면 묻지 않음) | 담는 곳 |
|---|---|---|
| 여행 테마 | 없음(계획서에서 읽지 않는다) | `survey.theme` |
| 누구와 함께 | 읽은 성향 `kid_friendly` · `elderly_friendly` 는 **힌트로만** 보이고 문항은 묻는다(구성 추정 금지 — 10-05 기획 §7) | `survey.party` |
| 우선순위(음식 · 활동 · 이동 + 세부) | 이동 세부 ← 「이동 수단」, 음식 세부 ← 「식당 취향」 — **세부만** 채우고, 분야 순서는 묻는다 | `survey.priority` · `priority_details` |
| 실내 · 실외(식당 · 활동) | 활동 ← 「비 오면 실내」(읽었으면 활동 칸만 채우고 식당 칸만 묻는다) | `survey.indoor_outdoor` |
| 여유 | 「일정 여유」(`slow_pace` · `late_start`) | `survey.pace` |

- **뺀 것**: 「일정이 꼬이면」(`on_disruption`) — 항로 지킴이 카드가 받는다(지금 그대로 `DIRECT`). 내국인 여부 — 묻지 않는다(쓰는 곳 없음).
- **묻지 않고 읽기만 하는 칸**: 덜 걷게(이동 약자 여부와 이어지는 민감 정보 — 동의 화면에서만 받는다) · 하루 시작 · 끝 시각(문항이 없다 — 계획서에서 읽은 값을 확인 화면에 보인다).
- 지금 로딩의 「이동은 주로 어떻게?」 · 「대체할 곳은 무엇을 먼저?」는 위 「우선순위」 문항의 이동 세부 · 분야 순서로 합친다(문항을 따로 두지 않는다). 묶음 버전 `QUESTION_SET_VERSION` 을 올린다 — 옛 답은 저장 때 해석한 값으로 읽힌다(053 이력).

### 2. 고르는 규칙 — 한 문항마다

1. 고객이 이미 답했다(이번 접수 · 같은 고객의 이전 접수 · 시작 설문 · 등록 요청) → **묻지 않는다.**
2. 계획서 읽기가 그 칸을 채웠다 → **묻지 않는다.** 확인 화면 「이렇게 읽었어요」에 원문 조각과 함께 보이고, 고객이 거기서 고칠 수 있다(고친 답이 이긴다 — 지금 `reading_prefs.status` 규칙 그대로).
3. 둘 다 아니다 → **로딩 중에 묻는다.**
- **상한 3 을 없앤다**(`MAX_QUESTIONS` 삭제). 많아야 5문항이다(표의 다섯).
- 문항 목록은 한 번 정해지면 그 접수에서 흔들리지 않게 한다(화면의 `i / N` — 지금 계약). 단 읽기 결과가 나온 뒤 한 번 다시 정할 수 있다(아래 3).

### 3. 순서 — 읽기 결과가 나와야 빈 칸을 안다

- 질문은 계획서를 읽는 **동안** 뜬다. 그런데 무엇이 비었는지는 이해 단계(`agent_read`)의 결과가 나와야 안다.
- 그래서 두 번에 나눈다:
  - **처음(접수 직후)**: 계획서에서 거의 안 나오는 문항 — 여행 테마 · 누구와 · 우선순위의 분야 순서 — 를 바로 묻는다.
  - **이해 단계 첫 결과가 나온 뒤**: 여유 · 실내 · 실외 · 우선순위 세부 중 **아직 빈 것만** 더한다. 화면은 다음 문항부터 새 목록을 그린다(이미 보인 문항은 지우지 않는다).
- 로딩이 끝날 때까지 못 물은 문항은 10-05 기획대로 확인 화면의 「나중에 답하기」 카드로 잇는다.
- 읽기가 실패하면(`reading_model_failed`) 다섯 문항 중 안 답한 것을 모두 묻는다.

### 4. 읽기 정확도 확인 — 같이 고칠 것

- x600 서버에서 이해 단계가 「택시로 이동」 한 구간을 「여행 내내 택시」(`moves scope all`)로 읽은 사례가 2건 있었다. 이 값으로 이동 질문을 빼면 고객이 엉뚱한 기본값을 갖게 된다.
- 구현 때 **여행 전체 이동 수단은 「다 · 늘 · 주로 · 웬만하면」 같은 말이 원문 조각에 있을 때만** 받는다(코드의 사실 검사 — D-025 「인용은 원문에 글자 그대로」와 같은 자리). 그 밖의 구간 수단은 이동 판정에만 쓰고 질문을 빼는 근거로 쓰지 않는다.

### 5. 접수 입구의 빠른 거름 — 로딩 설문은 거름을 통과한 뒤에만 `[2026-10-19 사용자 결정으로 추가]`

사용자 지시(원문 요지): 「빠른 거름(빈 글 · 분명히 무관한 글은 모델 읽기 전에 바로 입력 화면으로, 로딩 설문은 거름 통과 뒤에만, 애매하면 지금처럼 읽기)을 로딩 설문 구현에 함께. D-025 의 『거절하지 않는다』는 『분명히 무관한 글은 바로 돌려보낸다』로 좁혀.」

- 지금(원격 role-manager): 빈 칸은 서버가 곧바로 확인 상태 · 웹은 일정 0개면 입력 화면으로 되돌림. 여행과 무관한 글은 **모델 읽기를 다 거친 뒤** 이해 에이전트 가드가 확인 질문 한 줄만 붙인다(`fact_check.guard_gaps`). 로딩 설문은 도착하자마자 그려진다(웹 `use-question-flow` `fresh`). 실제 기록: 오라클 ARM 「파이썬 for 루프에 대해서 알려줘」 4초 · 24초, 「편안한 강남여행」 62초 뒤 일정 0개. 근거: [10-19 진단 「접수 입구 거름 점검」](../../../../wiki/records/reports/2026-10-19_chat-intake-secretary-review.md).
- **거름 위치**: 모델 읽기(`agent_read`) 전, 접수를 받은 직후. **규칙만**으로 한다(모델 · 유료 호출 0, 1초 안).
- **바로 돌려보내는 것**(셋 다 아님이 아니라 아래 중 하나):
  1. 글 · 파일이 모두 비었다.
  2. 글만 있고 파일이 없으며, 여행 단서가 **하나도 없다** — 날짜(「10월 3일」 「모레」 「1일차」) · 시각(「10시」 「오후」) · 서울 장소 단서(장소 목록 · 대표 장소 정답표 · 「역 · 궁 · 시장 · 공원 · 박물관 · 호텔 · 식당 · 카페」류 꼬리말) · 여행 낱말(「여행 · 일정 · 숙소 · 관광 · 맛집 · 코스」).
  3. 글이 **분명히 다른 일**이다 — 코드 · 숙제 · 상식 질문 낱말(「파이썬 · 코드 · 함수 · 숙제 · 번역해 줘」 등)이 있고 여행 단서가 없다.
- 돌려보낼 때: 접수를 「일정 없음으로 끝남」(새 상태값은 계약에서 정한다 — 예: `review` + `screened: off_topic|empty`, 또는 `fatal` 이 아닌 별도 코드)으로 남기고, 웹은 지금의 「일정을 찾지 못했어요 …」 문구로 입력 화면에 되돌린다(고객이 쓴 글은 입력칸에 그대로). **로딩 화면 · 로딩 설문을 띄우지 않는다.**
- **애매하면 지금처럼 읽는다** — 여행 단서가 하나라도 있으면(「편안한 강남여행」의 「강남 · 여행」) 거르지 않는다. 잘못 거르는 것보다 늦게 읽는 쪽이 손해가 작다는 판단이다. 거른 접수는 원문 · 걸린 규칙을 남겨 사후에 오판을 셀 수 있게 한다.
- **파일이 붙은 접수는 거르지 않는다**(사진 · PDF 는 받아쓰기 전에는 내용을 모른다).
- **로딩 설문 순서**: 거름을 통과한 접수에만 `questions[]` 를 낸다. 웹은 서버가 「읽는 중」을 알린 뒤에만 설문 단계를 그린다(도착 즉시 그리던 `fresh` 를 거름 통과 뒤로).
- **D-025 를 좁힌다**: 「가드 판정은 거절하지 않고 확인 질문으로만」 → 「**분명히 무관한 글 · 빈 글은 모델 읽기 전에 바로 돌려보낸다. 계획이 섞였거나 애매한 글은 지금처럼 거절하지 않고 확인 질문으로만**」. D-025 본문에 날짜 · 사용자 결정 표시로 덧붙인다(원문은 고치지 않는다).
- 채팅(여행 중 대화)에는 이 거름을 쓰지 않는다 — 채팅의 잡담 · 일반 질문 처리는 지금 그대로다.

## 계약 · 화면

- 계약 `final_project_cs/wiki/external/rest-endpoints.md` 「설문 질문」 — **구현 전에 먼저 고친다**: `questions[]` 상한 없음 · 문항 집합(위 표) · 읽은 칸으로 빠진 문항은 `skipped_by_reading[]`(문항 id · 읽은 값 · 원문 조각)로 따로 싣는다 · 읽기 뒤 목록이 한 번 늘 수 있음 · `questions_version` 올림.
- 웹: 화면은 서버가 보낸 `questions[]` 를 그대로 그리므로 문항 종류가 늘어난 것(여러 개 고르기 · 순서 고르기 · 두 칸 고르기)만 그릴 수 있으면 된다. 시작 설문 화면의 카드 모양을 재사용한다. 화면 담당 세션이 없으면 인계 문서로 남긴다.

## 하지 않는 것

- 식사 제한 · 접근성 · 내국인 여부 · 동행 구성을 추정해 채우기(10-05 기획 §7 그대로).
- 항로 지킴이 카드의 「일정이 꼬이면」을 로딩 질문으로 다시 넣기.
- 시작 설문 화면의 문항 · 선택지 문구 바꾸기(같은 문구를 로딩에서 재사용한다).

## 시험

- 계획서에 「다 지하철로」가 있으면 우선순위 이동 세부는 묻지 않고 `skipped_by_reading` 에 나온다 · 「택시로 이동」 한 구간뿐이면 묻는다.
- 「비 오면 실내」가 있으면 실내 · 실외는 식당 칸만 묻는다.
- 고객이 이전 접수에서 답한 문항은 묻지 않는다(지금 `inherit` 그대로).
- 상한이 없어 다섯 문항이 모두 나올 수 있다 · 읽기 실패면 다섯 문항.
- 읽기 결과 뒤 목록이 한 번만 늘고, 이미 보인 문항은 사라지지 않는다.
- 옛 묶음 버전 답이 새 매핑으로 잘못 읽히지 않는다(053 이력).
- 빠른 거름: 빈 글 · 「파이썬 for 루프에 대해서 알려줘」는 모델을 부르지 않고(호출 0 확인) 바로 「일정 없음」, `questions[]` 없음 · 「편안한 강남여행」 · 「내일 경복궁」은 거르지 않음 · 파일이 붙으면 거르지 않음 · 웹은 거른 접수에서 로딩 설문 단계를 그리지 않고 입력 화면으로(글 보존).
