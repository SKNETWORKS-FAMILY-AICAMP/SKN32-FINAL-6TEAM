# 운영자 정보를 운영 화면에서 입력하기 — 백엔드 요청 (「사업자 전환」 체크)

> 작성 2026-10-05 · uiux 세션 → cs 프로젝트 개발 세션 · 사용자 지시: 「운영자 웹앱에 사업자 전환 체크하는 기능을 만들고, 체크하면 해당 칸을 입력할 수 있게」 · 상태: **요청(서버 미구현)**
> 웹은 이 계약이 생기면 읽어서 약관에 끼운다(아래 「웹이 하는 일」). 그 전까지 웹은 지금처럼 자리표시를 보인다.

## 위층 — 한 번 읽고 알 수 있게

**결론.** 약관의 「누가 운영하나」 6칸(운영 주체 · 대표자 · 소재지 · 문의 연락처 · 개인정보 보호책임자 · 위치정보 관리책임자)을 **코드가 아니라 운영 화면에서 입력해 DB 에 저장**하고, 웹이 그 값을 읽어 약관 글에 끼운다. 지금은 부트캠프 학업용(사업자 아님)이라 대표자 · 소재지는 「해당 없음」이다. 운영 화면에서 **「사업자로 전환」을 체크하면 대표자 · 소재지 · 사업자 상호 입력칸이 열린다.**

**달라지는 것.** 사업 전환 때 약관 코드를 고치고 배포할 필요가 없다. 연락처 같은 개인 정보도 저장소(git)에 남지 않는다.

**서버가 할 일 셋.** ① 운영 정보 저장(표 둘) ② 운영 화면 입력 페이지 ③ 공개 읽기 API 하나. ★값이 바뀌면 약관 버전도 바뀌어야 한다(아래 「약관 버전과의 관계」) — 이것이 이 요청에서 가장 조심할 곳이다.

## 1. 운영 화면 — `/ui/operator`

| 칸 | 언제 입력 | 비고 |
|---|---|---|
| 운영 주체명 | 항상 | 사업자 전환 뒤에는 사업자 상호로 바꾼다 |
| 문의 이메일 · 연락처 | 항상 | 「회원 자료 전체 삭제」 같은 화면에서 못 하는 요청을 받는 창구. 처리방침의 연락처 |
| 개인정보 보호책임자(성명 · 직책 · 연락처) | 항상 | 처리방침 필수 항목. 개인 · 단체도 개인정보처리자라 사업자가 아니어도 둔다(조문 확인 중 — 아래 「확인 못 한 것」) |
| 위치정보 관리책임자(성명 · 직책 · 연락처) | **위치 저장 기능을 켤 때** | 지금은 서버에 그 기능이 없어 비워 둔다 |
| ☐ **사업자로 전환** | 체크하면 아래 열림 | 체크 해제 상태 = 학업용(비영리) |
| └ 대표자 | 체크했을 때만 | 해제 상태에서는 약관에 「해당 없음 (사업자 아님)」으로 나온다 |
| └ 소재지(사업장 주소) | 체크했을 때만 | 해제 상태에서는 「해당 없음 (사업자 아님)」 |

- 입력칸 아래에 한 줄: 「입력한 값은 약관에 그대로 공개돼요. 개인 이메일 · 이름이면 공개되는 것을 감안해 주세요.」
- 저장하면 확인 한 번(「약관 버전이 바뀌어 모든 이용자가 다시 동의해야 해요」) 뒤 저장한다.
- 운영 화면의 기존 로그인 · 감사 방식을 그대로 쓴다(`ui/auth.py`). 누가 언제 무엇을 바꿨는지 남긴다.

## 2. 저장

- `operator_profile`(테넌트당 한 줄): `is_business bool` · `name` · `representative` · `address` · `contact` · `privacy_officer` · `location_officer` · `revision int` · `updated_at` · `updated_by`
- `operator_profile_history`(**추가만** — 동의 증빙 복원용): 저장할 때마다 그 시점의 모든 값과 `revision` 을 한 줄 더한다. 지우지 않는다.
- 값 검사: 길이 제한(칸당 200자 안팎) · 제어문자 금지 · `contact` 는 이메일 또는 전화처럼 보이는 글(느슨하게). 빈 값은 「아직 정하지 않음」이라 약관에 자리표시가 남는다.

## 3. 읽기 API — `GET /v1/web/legal/operator`

로그인 불필요 · 공개 정보만 · 캐시 가능(짧게). 값이 없는 칸은 `null`.

```json
{
  "configured": true,
  "is_business": false,
  "revision": 1,
  "name": "…", "representative": null, "address": null,
  "contact": "…", "privacy_officer": "…", "location_officer": null
}
```

- 아직 한 번도 저장하지 않았으면 `{"configured": false, "revision": 0}`(404 가 아니다). 옛 서버가 404 를 주면 웹은 지금처럼 자리표시를 보인다.

## 4. 약관 버전과의 관계 (★ 조심할 곳)

동의 증빙은 「그때 본 글의 지문(sha256)」이다. 글에 끼워지는 값이 바뀌면 글이 바뀌므로, **같은 버전 이름으로 다른 글에 동의했다는 기록**이 생기지 않게 버전이 따라가야 한다.

- `current_version()` = `consent.terms_version`(지금 `2026-10-05`) + (`revision > 0` 이면 `+op{revision}`). 예: `2026-10-05+op1`.
- 운영 정보를 저장해 **값이 실제로 바뀐 경우에만** `revision` 을 1 올린다 → 모든 이용자가 다시 동의한다(운영 주체가 바뀌는 것은 동의 상대가 바뀌는 일이라 다시 받는 쪽이 안전하다).
- 웹은 같은 문자열(`TERMS_VERSION + "+op" + revision`)을 `POST /v1/web/consents` 의 `version` 으로 보낸다. 서버의 409 `terms_version_changed` 는 그대로 쓴다.
- 증빙 복원: 어떤 동의 기록의 `version`(`…+opN`)과 `text_sha256` 이 오면, 그 버전의 정본 글 + `operator_profile_history` 의 N번째 값으로 글을 다시 만들어 지문을 맞춰 본다.

## 5. 웹이 하는 일 (요청 아님 · 알림)

- 앱이 열릴 때 위 API 를 한 번 읽는다(실패해도 앱은 뜬다).
- 값이 오면 약관 본문의 자리표시(「【확정 필요: …】」)를 값으로 바꾼다. `is_business=false` 이면 대표자 · 소재지는 「해당 없음 (사업자 아님)」으로 쓴다.
- 동의 버전 문자열에 `+op{revision}` 을 붙이고, 지문은 값이 끼워진 한국어 글로 계산한다.
- 약관 상태 표시(「초안」)는 지금처럼 코드의 `TERMS_STATUS` 가 정한다(값을 채워도 변호사 검토 전이면 「초안」).
- 시험: mock 서버(화면 반응)로 하고, 실서버 확인은 서버가 생긴 뒤.
