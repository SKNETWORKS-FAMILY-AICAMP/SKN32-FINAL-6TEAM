# 웹의 데모 화면을 전부 실서버로 바꾼 뒤, 서버에 없어서 넘기는 기능 — 여행 삭제 · 등록한 여행 고치기

작성: ui 세션(웹) · 2026-10-03 · 대상: cs 백엔드 세션 · ★이 문서는 **요청서**다. 서버 코드는 고치지 않았다(웹 쪽에서 한 일은 맨 아래).

## 위층 — 한 번 읽고 알 수 있게

**결론.** 웹의 데모(모방) 화면과 코드를 모두 없앴고, 데모에서만 되던 기능 가운데 **서버에 같은 기능이 없는 것은 둘**이다 — 고객이 자기 **여행을 지우는 것**과, 이미 등록한 **여행의 일정을 고쳐서 다시 확인하는 것**. 앞의 것은 웹이 요청 모양대로 연결해 뒀고(서버가 만들면 바로 동작), 뒤의 것은 서버 설계가 먼저라 웹은 아직 단추를 두지 않았다.

**그래서 무엇이 달라지나.** 지금 고객이 「내 여행」에서 휴지통을 누르면 화면이 **「서버가 아직 여행 삭제를 지원하지 않아요」**라고 솔직하게 말하고 아무것도 지우지 않는다(데모에서는 이 탭 저장소를 지우고 「지웠어요」라고 했다). 서버가 만들면 그 말 대신 실제로 지워진다.

| 기능 | 웹이 하는 일 | 서버에 있나 | 요청 | 급한 정도 |
|---|---|---|---|---|
| **여행 삭제** (목록의 휴지통·선택 삭제) | `POST /v1/web/trips/{id}/delete` 를 부른다 | **없음** — `/v1/web` 경로 28개에 삭제 없음(실행 중인 서버의 `/openapi.json` 으로 확인) | 아래 「1」 | 높음 — 고객이 자기 데이터를 지울 길이 지금 없다 |
| **등록한 여행 고쳐서 다시 확인** (옛 데모의 「일정 수정」·「계획 수정 후 다시 확인」) | 단추를 두지 않았다. 지금은 「새 계획 올리기」(새 여행이 하나 더 생긴다) | **없음** — 접수 수정(`/edits`)은 `confirm` 전까지만 | 아래 「2」 (설계 제안) | 중간 — 삭제가 생기면 「새로 올리고 옛것 지우기」로 대신할 수 있다 |

**정할 것**: ① 삭제가 서버에서 **완전 삭제**인지 **고객 화면에서만 사라지는 숨김**인지(추천: 아래 「1」의 표대로 — 고객이 볼 수 있는 것과 알림은 즉시 없애고, 운영 감사에 꼭 필요한 최소 기록만 남긴다) ② 「2」를 지금 할지, 삭제 뒤로 미룰지. 사용자 결정이 필요한 것은 ①뿐이다.

★**결정(2026-10-04)** — ①은 **즉시 완전 삭제**로 정했다(Claude 와 Codex 가 따로 판단해 1회차에 일치 · 사용자 보고 완료). 숨김(B)·유예 뒤 삭제(C)는 쓰지 않는다. 확인창의 「되돌릴 수 없어요」 약속과 맞고 웹은 바꿀 것이 없다. 운영 감사 줄은 **가리지 않고 그대로 두며, 삭제했다는 한 줄만 덧붙인다**(아래 표 갱신). 구현 지침은 표 아래 「구현 지침(2026-10-04 결정)」.

## 아래층 — 1. 여행 삭제

### 계약(웹이 이미 이 모양으로 부른다)

```
POST /v1/web/trips/{trip_id}/delete          X-User-Key
  요청: 몸통 없음
  200 {"trip_id": "...", "status": "deleted"}
  404 {"error": {"code": "not_found", "message": "resource not found"}}   ← 남의 여행·이미 지운 여행·없는 여행 (있는지도 말하지 않는다 — 다른 웹 경로와 같은 규칙)
  401 unauthenticated · 429 usage_limit(이 호출도 남용 방어 대상이면)
```

- 웹은 **200 이면 지운 것**, **404 `not_found` 도 이미 없는 것**(목록에서 뺀다)으로 읽고, **`{"detail": "Not Found"}` 모양의 404(`HTTP_404`) 나 405 이면 「서버가 아직 지원하지 않아요」**로 읽는다. 그 밖의 오류는 서버 문장을 그대로 보인다.
- 왜 `DELETE` 가 아니라 `POST …/delete` 인가: 서버 CORS 가 `GET`·`POST`·`PUT` 만 연다(`app/presentation/api/app.py:61`). 브라우저의 `DELETE` 는 사전 확인에서 **400 「Disallowed CORS method」** 로 막혀(실서버로 확인) 화면은 서버가 아예 안 닿는 것과 구분할 수 없다. 다른 동작 경로(`/rollback` · `/reports` · `/items/{id}/alternate`)도 `POST` 다. `DELETE /v1/web/trips/{id}` 로 만들고 싶으면 `allow_methods` 에 `DELETE` 를 더해야 하고, 그러면 웹의 한 줄(`src/lib/live/gateway.ts` 의 `removeTrip`)만 바꾸면 된다.
- 멱등: 같은 호출을 다시 보내면 404 `not_found`(웹은 이를 성공으로 본다). 응답 몸통이 비어도(204) 웹은 성공으로 읽는다.

### 서버가 해야 할 일(제안 — 어디까지 지울지는 정해 주세요)

| 대상 | 제안 | 이유 |
|---|---|---|
| 여행 목록·여행 조회 | 즉시 사라진다(`GET /v1/web/trips` 에서 빠지고 `GET …/{id}` 는 404) | 「삭제했어요」가 거짓이 되지 않게 |
| 여행계획서 링크(`plan_url`) | 즉시 닫는다(404 또는 410) | 링크를 가진 사람이 지운 계획을 계속 볼 수 있으면 삭제가 아니다 |
| 감시 루프 · 알림 | 감시 대상에서 빼고, 아직 안 나간 알림(바깥함 대기분)을 취소한다 | 지운 여행의 「출발 시각입니다」가 그 뒤에 나가면 안 된다 |
| 열린 제안(proposals)·열린 Case | 닫는다(`closed: trip_deleted` 같은 이유로) | 고르지 못한 선택이 남아 운영 화면에 떠 있지 않게 |
| 대화 기록(`/chat`)·위치·웹훅이 실린 기록 | 지운다 | 고객이 쓴 문장과 위치는 지우는 쪽이 맞다 |
| 운영 감사 줄·사건 기록 | `[2026-10-04 정정]` **건드리지 않고 두고, 「여행 삭제」 사건 한 줄만 덧붙인다**(고객 문장·위치는 싣지 않는다) | 감사 줄은 고치지도 지우지도 못한다(`case_events` 는 규칙, 한도 변경 줄은 DB 트리거 — [남용 방어](../../external/rest-endpoints.md)). 앞 판의 「가린다」는 UPDATE 가 필요해 규칙과 부딪혀 접었다. Case 와 여행의 연결은 `subject_ref{kind,id=trip_id,part_id}`·`state_json` 이고 감시 Case 의 내용은 여행 번호·장소 이름·`issue_code` 뿐이다 |

### 구현 지침(2026-10-04 결정 — Codex 합의 반영)

1. **한 트랜잭션.** 소유자 확인과 함께 `trips` 행을 잠근다(`FOR UPDATE`). 남의 여행·없는 여행·이미 지운 여행은 모두 같은 404.
2. **외래키가 없어 자동으로 안 지워지는 표는 이름을 대어 지운다**: `trip_chat_turns` · `place_open_checks` · `dining.dn_notice`(trip_id 일치) · `trip_intakes`(trip_id 일치 — 자식은 `ON DELETE CASCADE`). 그다음 `trips`(→ `itinerary_versions` · `itinerary_items` · `pending_changes` 는 CASCADE). **`trip_id` 가 NULL 인 옛 접수·알림은 고객 번호만으로 지우지 않는다**(여행과 연결이 확인된 행만).
3. **운영 쪽**: 그 여행의 열린 Case 를 정상 상태 전이로 닫고(`closed: trip_deleted`) 닫는 사건을 덧붙인다 — `case_events` 는 지우지 않는다. 바깥함(`outbox`)의 대기 알림은 `payload_json` 의 trip_id 로 찾아 취소한다.
4. **경쟁 차단**: 감시 루프·채팅·자동 수정 등 여행을 쓰는 경로가 모두 같은 행 잠금 규칙을 따르고, 보내기 직전에 여행이 있는지 다시 본다. 이미 밖으로 나간 알림은 회수되지 않는다.
5. **계획서 링크**는 토큰 행이 없어(HMAC) 여행이 사라지면 조회에서 404 가 된다. 캐시가 있으면 함께 비운다.
6. **시험**: 지우는 표 목록이 빠짐없는지(새 표가 생기면 걸리는 목록 시험) · 남의 여행이 안 지워지는지 · 삭제와 겹친 쓰기 · 두 번째 호출 404.
7. **MCP 삭제 도구**는 `travel.mcp.write_enabled` 뒤(기본 꺼짐).
8. `[미확인]` 고객이 낸 건의 `case_events.payload_json` 에 마스킹 안 된 고객 문장이 실제로 없는지는 DB 에서 세어 보지 못했다 — 구현할 때 한 번 세어 본다.
- 결정 기록(기계 검토: Codex 본계정 1회차): 이 세션 작업 폴더의 `consensus/20261004_trip_delete/decision.md` — 위 내용이 그 요약이다.
| 접수(`trip-intakes`) | 그 여행으로 만든 접수는 함께 지운다 | 읽은 원문·사진이 남지 않게 |

### 완료 기준(시험 예)

1. 본인 여행 삭제 → 200, 목록에서 빠짐, 조회 404, `plan_url` 404/410.
2. 남의 여행·없는 여행 → 둘 다 같은 404(구별되지 않음). 같은 호출 두 번째 → 404.
3. 열린 제안이 있는 여행 삭제 → 제안이 닫히고 선택 호출은 404.
4. 삭제 뒤 감시 루프가 그 여행을 안 읽고, 대기 중이던 알림이 나가지 않는다.
5. 브라우저 출처에서 `POST` 가 CORS 로 막히지 않는다(사전 확인 통과).
6. MCP 도구로도 열지는 따로 정한다(`travel.mcp.write_enabled` 뒤에 둘 것을 권한다 — 되돌릴 수 없는 쓰기).

### 화면이 보일 것(웹 쪽, 이미 구현)

- 내 여행 → 휴지통/선택 삭제 → 확인창 「서버에 저장된 이 여행과 대화 기록, 여행계획서 링크가 삭제되고 알림도 멈춰요. 삭제한 내용은 되돌릴 수 없어요.」 → 삭제 → 「여행 1개를 삭제했어요.」.
- 서버가 아직 없으면 → 「서버가 아직 여행 삭제를 지원하지 않아요. 지원되면 바로 쓸 수 있어요.」 + 삭제 단추가 꺼진다(그 화면을 다시 열면 한 번 더 묻는다).
- 일부만 실패하면 지워진 것만 빠지고 실패한 여행은 선택된 채 남는다(`삭제하지 못했어요. 다시 시도해 주세요.`).

## 아래층 — 2. 등록한 여행 고쳐서 다시 확인 (설계 제안)

옛 데모에는 여행 화면의 「일정 수정」과 결과 화면의 「계획 수정 후 다시 확인」이 있어서, 등록한 계획의 **원문을 불러와 고친 뒤 다시 확인**할 수 있었다. 실서버에서 등록한 여행은 접수(`trip-intakes`)가 `confirmed` 로 끝나 `/edits` 가 닫히고, 여행 쪽에는 원문이 없다. 지금 웹의 대응은 「새 계획 올리기」(새 접수 → 새 여행)뿐이라 같은 여행이 둘 생긴다.

제안(서버 설계가 먼저 — 웹은 아직 단추를 두지 않았다):

| 단계 | 호출 | 뜻 |
|---|---|---|
| 다시 열기 | `POST /v1/web/trips/{id}/reopen` → `{intake_id, revision}` | 그 여행의 **현재 일정**을 읽은 항목으로 담은 새 접수를 만들어 준다. 여행(번호·대화·계획서 링크)은 그대로 둔다 |
| 고치기 | 기존 `/v1/web/trip-intakes/{id}/edits`·`/candidates`·`/autofix`·`/revalidate` | 새 계획 확인 화면이 그대로 쓴다 |
| 반영 | 기존 `/confirm` 이 `reopened_from` 이 있으면 **새 여행을 만들지 않고 그 여행의 새 버전(version+1)으로 올린다** | 변경 이력·되돌리기(`/rollback`)·알림이 한 여행 안에서 이어진다 |

정할 것: 고친 일정이 **예약이 걸린 항목**을 건드릴 때의 규칙(지금 채팅은 「바꾸기 전에 물어봐요」), 그리고 열린 제안·예정 알림을 새 버전으로 어떻게 넘길지.

## 확인 범위 — 「서버에 없음」이라고 쓴 근거와 놓칠 수 있는 것

- **한 일**: ① `app/` 에서 `/v1/web` 를 찾고(`Grep`) `@router.(get|post|put|patch|delete)` 를 훑었다 — 삭제 경로 없음. ② 실행 중인 로컬 서버(8042)의 **`/openapi.json` 에서 `/v1/web` 경로 28개를 전부 읽었다** — `…/delete`·`…/reopen` 없음, 소셜 로그인 경로(`/v1/web/auth/*`)도 이 서버에는 아직 없음(다른 세션의 일). ③ 같은 서버에 가짜 키로 `POST /v1/web/trips/xxx/delete` → 404 `{"detail":"Not Found"}`, `DELETE`·`PATCH`·`PUT /v1/web/trips/xxx` → 405 `allow: GET`, `OPTIONS`(사전 확인, `Access-Control-Request-Method: DELETE`) → 400 `Disallowed CORS method` 를 받았다(가짜 키라 아무것도 지워지지 않았다).
- **놓칠 수 있는 것**: 이 서버가 **관리용 빌드가 아니라 고객 릴리즈 빌드**라면 관리용 빌드(`management=True`)에만 있는 경로를 못 본다(삭제가 운영 앱(8070)에 있다면 고객 앱에는 없으므로 같은 결론이다). 또 아직 커밋되지 않은 서버 변경(작업 폴더에 수정 중인 `trip_api.py`)이 이 서버 프로세스에 반영되기 전일 수 있다 — 다시 띄운 서버에서는 경로가 있을 수 있다.

## 웹 쪽에서 한 것 — 서버 일이 아니다

- 연결: `src/lib/live/gateway.ts` 의 `deleteTrip`(위 계약), 목록 화면 `src/features/trip/trip-list.tsx`(확인창·실패 알림·「지원 안 함」 처리), 시험용 모방 서버 `tests/live/stub-server.mjs` 가 이 계약대로 흉내 낸다(`tripDelete: "ok" | "unsupported" | "fail"`).
- 이 요청서와 별개로 이미 있는 요청: 「성수 예약 식당」 같은 설명 줄 처리와 `autofix` 의 `dry_run` 은 [장소 해석 개선 요청](2026-10-03_1630_장소_해석_개선_백엔드_요청.md) 에 있다.
- 서버가 고객 디스코드 웹훅으로 **일정 변경 알림**을 보내는 2단계는 여전히 서버에 없다([웹 화면별 연동 상태](../../external/web-screen-api.md)). 화면은 「준비 중」으로 적는다.
