# 오라클 무료 서버 채팅 부하시험 — 계획과 작은 규모부터 (2026-10-15, 승인 대기)

**결론:** 부하시험은 아직 한 번도 실행하지 않았다(전체 채팅 부하시험 0/8 — 계획만). 이 문서는 **실행 순서와 중단 기준**만 정한다. 10-12 에 이 서버에서 점검이 메모리 부족을 일으켜 cs 프로젝트 서버(api)가 꺼진 적이 있어, 아래 0단계(읽기만)부터 사용자 승인을 받고 한 단계씩 간다. **승인 없이 어느 단계도 실행하지 않았다.**

| 단계 | 하는 일 | 서버에 주는 부하 | 상태 | 진행 |
|---|---|---|---|---|
| 0 | 지금 상태 읽기(메모리·CPU·모델 상주·최근 응답 시간) | 없음(읽기) | 승인 대기 | 0/1 = 0% |
| 1 | 질문 1건씩 순서대로 5건(동시 1) | 아주 작음 | 승인 대기 | 0/1 = 0% |
| 2 | 동시 2건 × 5회 | 작음 | 승인 대기 | 0/1 = 0% |
| 3 | 동시 4건 × 3회, 새 일정 첫 질문 비율 10% | 중간 | 승인 대기 | 0/1 = 0% |
| 4 | 전체 채팅 8종 흐름(등록→질문→대안→변경→되돌리기) 한 사람 | 중간 | 승인 대기 | 0/1 = 0% |

(앞 두 문서가 말한 「0/8」은 4단계의 흐름 8종 계획만 있고 실행이 없다는 뜻이다. 아래 단계 번호는 이 문서에서 새로 매긴 것이다.)

## 지금 알려진 것과 모르는 것

- 알려진 것(실측, 모두 이전 보고서 값): 일정 짚기만 재면 하루 약 4,700건이 **계산 상한**이다(새 일정 첫 질문 10% 가정, 슬롯 하나가 쉬지 않고 일한다고 본 값 — 실제 서비스 처리량이 아니다). 근거 [무료 서버 처리량 비교](../reports/2026-10-07_무료서버_처리량과_운영비용_비교.md).
- 채팅 응답은 느리다: 같은 서버의 실제 HTTP 두 질문이 179.5초 · 63.3초였다(CPU 상한 60→90%, 문맥 캐시 64→256MiB 로 올린 뒤에도). 개선은 입증하지 못했다. 근거 [지연 원인 진단](../reports/2026-10-12_0038_arm-latency-root-cause.md).
- 모르는 것: 동시에 여러 명이 물을 때 메모리가 어디까지 가나, 응답이 몇 초까지 늘어나나, 어느 지점에서 api 가 꺼지나. **이것이 이 시험이 알려고 하는 것이고 지금은 값이 없다.**
- 이 서버의 모델은 우리 데이터로 학습하지 않은 Gemma E4B QAT(Q4_0)다. x600 서버의 학습 E4B 와 다르다 — 거기서 잰 속도·정확도를 옮겨 쓰지 않는다.

## 사고에서 가져온 규칙 (10-12 00:26 api 종료)

원인은 api 컨테이너 **안에서** 별도 앱 검사를 돌려 컨테이너 메모리가 찬 것이었다. 그래서:

1. 부하는 **서버 밖(이 PC)** 에서 공개 HTTP 로만 건다. 서버 안에서 시험 프로그램을 돌리지 않는다.
2. 시험용 여행·계정은 따로 만든다(실사용 데이터에 질문하지 않는다). 계정 만들기·약관 동의는 사용자가 직접 하거나 승인 뒤에 한다(제가 임의로 만들지 않는다).
3. 모델 상주를 풀거나 서비스 설정(`.env`·CPU 상한·캐시)을 바꾸지 않는다. 바꾸려면 따로 승인(`.env` 에 줄만 더해도 자동 배포가 멈출 수 있어 재생성과 한 묶음).
4. 한 번에 **한 단계**만. 앞 단계 결과를 사용자에게 보여 주고 다음 단계 승인을 받는다.

## 중단 기준 (하나라도 닿으면 그 자리에서 멈추고 보고)

| 보는 것 | 어디서 | 멈추는 기준 |
|---|---|---|
| 서버 메모리 여유 | 0단계와 같은 읽기 명령(단계마다 시작 전 · 후) | 여유 1GiB 미만 |
| api 컨테이너 상태 | 컨테이너 목록 읽기 | 재시작 횟수가 시험 전보다 늘어남 |
| 응답 시간 | 시험 도구가 건마다 기록 | 한 건이 300초 넘김, 또는 건건이 앞 단계 중앙값의 3배 |
| 오류 | 시험 도구 | HTTP 5xx 또는 연결 거절 2건 연속 |

## 단계별 내용

**0단계 — 상태 읽기(승인 필요 사항: 서버 읽기).** 메모리 총량·사용량·컨테이너별 한도(`docker stats --no-stream`), 모델 프로세스 상주 여부, 최근 한 시간 api 로그의 응답 시간. 읽기만 하고 아무것도 바꾸지 않는다. 결과가 기준(여유 메모리 4GiB 이상)에 못 미치면 1단계로 가지 않고 먼저 보고한다.

**1단계 — 5건 순서대로.** 서로 다른 일정 5개 × 질문 1개씩. 한 건 끝나야 다음 건. 기록: 건별 전체 시간, 서버 메모리 전·후, 답이 정답표와 맞는지(일정 짚기·시간 질문 각 몇 건). 분모는 건수 5 라 **정확도를 말하지 않고 시간 분포만** 본다.

**2단계 — 동시 2.** 앞 보고서에서 동시 2 가 처리량을 늘리지 못했다(Q8, 동시 1 시간당 466건 대 동시 2 282건 — 합성 프롬프트·x86 아닌 같은 서버 실측). 같은 결과인지, 메모리가 어떻게 되는지 본다.

**3단계 — 동시 4, 새 일정 10%.** 중단 기준에 가장 가까워지는 단계. 1·2단계 어느 쪽이든 한 건이 120초를 넘겼으면 3단계는 하지 않는다.

**4단계 — 한 사람의 전체 흐름 8종.** 부하가 아니라 **끝까지 되는지**를 본다. 로그인(게스트)→여행 접수→질문→대안→변경→되돌리기 흐름은 약관 동의가 필요해 사용자 손이 한 번 간다.

## 결과를 쓰는 법

- 분자·분모·조건·횟수를 적는다(예: 「동시 2 × 5회 = 10건 중 응답 10건, 중앙값 N초」). 1회 측정이면 「1회」라고 적고 편차를 말하지 않는다.
- 처리량을 「하루 N건」으로 환산하지 않는다 — 환산은 계산 상한이지 측정이 아니다. 측정은 「이 조건에서 이 시간 안에 이만큼」까지만 쓴다.
- 서버 안 값(메모리·로그)과 밖에서 잰 값(응답 시간)을 따로 적는다. 실서버 확인(서버 응답): 시험을 한 단계만큼만 했다고 적는다.

## 사용자가 정할 것

1. 0단계(읽기) 승인 여부 — 이 서버에 SSH 로 읽기 명령을 실행해도 되는지.
2. 시험용 계정을 누가 만드나(사용자가 직접 / 제가 승인 받고 게스트로).
3. 1단계 이후는 단계마다 확인받는다. 한 번에 승인할 범위를 정하려면 알려 주세요(예: 1·2단계까지).
