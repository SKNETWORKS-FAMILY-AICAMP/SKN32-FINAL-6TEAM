# 계획 확인 화면 — 이동수단 고르기: 서버 계약안 (이동 세션)

작성: 이동 세션 · 2026-10-05 · 상태: **구현됨(2026-10-07 — 사용자 결정 · 사실표는 `wiki/external/rest-endpoints.md` 「이동수단 고르기」).** 짝 문서: [화면 계획서](2026-10-05_이동수단_선택_화면_계획서.md)(ui 세션). 사용자 확인을 받으면 구현한다.

## 위층 — 한 번 읽고 알 수 있게

**결론.** 이동 한 구간마다 「지하철 · 버스 · 택시 · 걸음 각각으로 가면 몇 분·얼마·여유가 얼마인가」를 서버가 계산해 주고(읽기), 고객이 고르면 그 구간만 다시 계산해 확인 결과에 반영한다(쓰기). **여유 안에 닿는 수단만 고를 수 있다** — 서버가 다시 계산해 확인하므로 고른 뒤에 「다시 제출」은 필요 없다.

**왜 되나.** 이동 계산기는 이미 「이 수단들만 써서 후보를 만들라」(`modes`)는 입력을 받고(지하철·버스·걸음·자전거·택시), 구간 하나를 0.2~0.5초(못 닿는 구간은 3~11초)에 답한다. 새로 만드는 것은 ① 수단마다 한 번씩 부르는 읽기 경로 ② 고른 수단을 기억해 다음 계산에도 지키는 쓰기 경로다.

**대가.** 후보 읽기 한 번에 계산이 최대 4번이다(수단 수) — 닿는 구간이면 1~2초, 못 닿는 구간이 섞이면 수 초~십수 초. 그래서 화면 계획서처럼 **구간을 누를 때 한 건씩** 부르고, 서버는 4개를 **동시에** 계산한다.

**정할 것(사용자)**: 아래 「선택지」 — 특히 ⓑ 앞뒤 일정이 바뀌면 고른 수단을 **닿으면 유지, 안 닿으면 추천으로 복귀**로 할지(추천).

## 계약

### 1. 읽기 — 수단별 단일 후보

`GET /v1/web/trip-intakes/{intake_id}/moves/{from}~{to}/options` (사용자 키/쿠키 · 남의 접수 404)

```
200 {
  "intake_id", "revision", "from": "0-0", "to": "0-1",
  "current_mode": "subway",            // 지금 확인 결과의 수단(walk|subway|bus|taxi|transit|estimate)
  "recommended_mode": "subway",        // 계산기가 고른 수단(고객이 바꿔도 안 변함 — 「추천」 꼬리표)
  "options": [                         // 고정 순서: subway · bus · taxi · walk. 못 만든 수단은 줄 자체가 없다
    {"mode": "subway", "label": "지하철 2호선", "minutes": 16, "km": 1.5,
     "fare_krw": 1550, "fare_is_floor": false,
     "depart": "12:00", "arrive": "12:16", "slack_min": 14, "fits": true,
     "basis": "timetable", "grade": "확정"},
    {"mode": "taxi", "label": "택시", "minutes": 12, "fare_krw": 9000, "fare_is_floor": true, "slack_min": 18, "fits": true, "basis": "estimate", "grade": "추정", ...},
    {"mode": "bus", "minutes": 38, "slack_min": -8, "fits": false, "why_not": "버스로는 8분 늦어요 · 다음 일정이 12:30에 시작해요", ...}
  ]
}
404 {code:"not_available"}   // 이동 계산기가 꺼짐 · 그 구간이 계산 대상이 아님(장소 없음·날짜 다름) — 화면이 박스를 안 둔다
```

- `fits` = 앞 일정이 끝난 뒤 떠나 **다음 일정 시작 안에 닿는다**(`slack_min ≥ 0`) **그리고 시간표로 확인했다**(검증 못 한 「끝나는 대로 떠난다」 값은 `fits:false` + 이유).
- `fare_krw`: 지하철은 공표 거리 · 선로 길이 추정(`grade:"추정"`)으로 못 내면 `null`(화면은 「요금 미상」) · 버스는 단일 요금 · 택시는 **하한값**(`fare_is_floor:true`) · 걸음은 `0`.
- `grade`: **`확정` · `추정` · `근거없음`**(기존 근거 등급과 같은 세 값). 시간표 판정으로 성립이 확인된 지하철·버스 = 확정 · 택시·어림·자전거·선로 길이 요금 = 추정.
- `why_not` 는 서버가 완성한 문장이다(화면은 그대로 보여 준다).
- 계산이 오래 걸려 못 끝낸 수단은 `fits:null` + `why_not:"계산이 오래 걸려 확인하지 못했어요"` — 고를 수 없다(지어낸 값 없음).

### 2. 쓰기 — 고른 수단 반영

`POST /v1/web/trip-intakes/{intake_id}/moves/{from}~{to}/mode` body `{"revision": 3, "mode": "taxi"}` (또는 `"recommended"` = 되돌리기)

```
200 {"revision": 4, "review": { …확인 결과 전체(public) — 그 구간이 고른 수단으로 다시 계산돼 있다 }}
409 {code:"stale_revision"}              // 그 사이 판이 바뀜 — 화면이 다시 읽는다(기존 edits 와 같은 규칙)
422 {code:"mode_not_fit", why:"…"}       // 안 닿는 수단 · 계산 못 한 수단 · 알 수 없는 수단
404                                       // 남의 접수 · 없는 구간
```

- 서버는 **고른 수단으로 그 구간을 다시 계산해 닿는지 확인한 뒤에만** 받는다 — 화면이 보낸 `fits` 를 믿지 않는다.
- 저장: **고객의 값**(`intake_claims` 의 고객 값 칸 `moves[{from}~{to}].mode`)으로 새 판(revision+1)에 남는다 — 장소·시간 고치기와 같은 방식이라 앞 판의 근거를 지우지 않는다.
- 응답의 `review.moves[i]` 에 칸 둘이 더해진다: `mode_choice: {"mode":"taxi","state":"kept"|"dropped","why"?}` · `recommended_mode`. (기존 칸은 그대로.)

### 3. 경로선

고른 뒤 `GET …/route-shapes` 를 다시 받는다(이미 있다). 고른 수단이 모양에 반영된다.

## 화면 계획서 ⓐ~ⓔ 에 대한 답

| 물음 | 답 |
|---|---|
| ⓐ 고른 뒤 「다시 제출」이 필요한가 | **아니다 — 서버가 이미 확인했다.** 닿는 수단만 받고, 받을 때 다시 계산했다. 응답의 그 구간 `status` 는 `keep`, 위 `needs` 합계도 다시 계산돼 온다 |
| ⓑ 앞뒤 일정의 장소·시간이 바뀌면 | **고른 수단을 같은 방식으로 다시 시도한다 — 닿으면 유지(`state:"kept"`), 안 닿으면 추천으로 복귀(`state:"dropped"` + 이유)**. 화면은 `dropped` 에 「바뀜」 표시. (제안하신 「무조건 추천으로 복귀」보다 고객의 선택을 덜 잃는다) |
| ⓒ 전체 자동 추천이 고른 수단을 유지하나 | **유지한다.** 자동 추천이 같은 두 일정 사이 구간을 계산할 때 고른 수단으로만 시도하고, 안 닿으면 ⓑ 와 같이 복귀 + 알림. (구현 시 자동 추천 쪽에 고른 수단 표를 넘겨야 한다 — 범위에 포함) |
| ⓓ grade 값 | `확정` · `추정` · `근거없음` 셋 |
| ⓔ 걸음 요금 | `fare_krw: 0`, `fare_is_floor: false`. 걸음 후보는 걸을 만한 거리일 때만 줄이 있다(도보 상한 안) |

| 할 일 | 어디 | 비고 |
|---|---|---|
| 수단 제한 입력 | `mobility/wiring.py` `leg_planner(…, modes=…)` | 이미 계산기가 받는 `modes` 를 밖으로 연다(작다) |
| 수단별 후보 계산 | 새 `intake/move_options.py` | 4 수단을 동시에 계산 · 단일 수단만(혼합 제외) · `fits`·`why_not`·요금 칸 조립 |

| 자동 추천이 유지 | `intake/autofix.py` | 고른 수단 표를 받아 같은 쌍에 적용 |
| 경로 2개 | `trip_api.py` + 계약 문서 `rest-endpoints.md` · API 표면 시험 목록 | |
| 시험 | 단위(가짜 계산기: 닿음/안 닿음/모름/느림) · e2e(소유자만 · 422 · 409 · 되돌리기 · 장소 바뀜 복귀) · 이동 전체층 확인 | 실서버 확인은 서버 반영 뒤 사용자 허락을 받고(여행 하나를 만들어 한 구간) |

## 위험 · 확인하지 못한 것

- 후보 읽기의 **시간**: 못 닿는 구간은 3~11초(2026-10-03 실서버 실측 · 이동 세션이 앞서 알려 준 값). 4개를 동시에 돌려도 가장 느린 것이 전체 시간이다 → 화면의 「찾는 중」 8초 안내가 필요하다. 한 수단이 너무 오래 걸리면 그 줄만 「확인 못 함」으로 두는 상한을 둔다(값은 구현 때 재서 정한다 `[미실측]`).
- **같은 파일을 다른 세션도 고친다**(`review.py` · `trip_api.py` · `autofix.py` — 확인 화면 담당 세션 작업 중). 구현 전에 그 세션 변경과 겹치는지 먼저 본다.
- **택시 후보**는 `modes` 에 택시를 줄 때만 후보로 나온다(설문 택시 선택과 별개로 이 읽기에서는 항상 계산). 요금은 하한값이라 「약 ~원~」 표기가 맞다.
- 동시 계산의 안전성: 판정기는 요청 동시 실행 시험(`test_plan_concurrency_v1`)이 있어 읽기 전용이다 — 새 동시 호출 경로의 시험을 더한다.
- 이 계약은 **한 구간씩 고르기**만 다룬다(여행 전체 일괄 변경은 범위 밖 — 화면 계획서와 같다).
