# 확인 화면 「지도에서 장소 고르기」 — 실행계획 (2026-09-30)

> 상태: **초안 — 사용자 결정 대기**(아래 「정하실 것」). 코덱스 교차검증 전. 구현 전.
> 계약(서버→화면 값)이 바뀌므로 RULE §3.5 에 따라 `wiki/external/rest-endpoints.md` 를 먼저 고치고 화면 세션에 알린다.

## 0. 왜

확인 화면에서 「올리브영 이촌」 · 「호텔」 같은 항목이 「장소를 정하지 못했다 — 고객이 고친다」로 남는다. 지금 고칠 방법은 이름을 다시 적는 것뿐이고,
서버는 이름으로 다시 찾는다(`intake/pipeline.py` `_typed_place`). 이름을 모르는 고객(「호텔」)은 고칠 수 없다.
→ 고객이 **지도에서 위치를 찍으면 근처 후보를 목록으로 주고 고르게** 한다. 후보에 없으면 찍은 자리를 그대로 확정한다.

## 1. 정한 것

### A. 지도

| 결정 | 값 | 이유 |
|---|---|---|
| 지도 그리기 | **기존 Leaflet 1.9.4 + OpenStreetMap 무료 타일**(`features/map/providers/osm.ts`) 그대로 | 이미 붙어 있고 무료·키 없음. 새 라이브러리 없음 |
| 지도 종류 설정이 구글·네이버여도 | **고르기 창은 항상 OSM** | 구글 장소 정보는 구글 지도 위에서만 보일 수 있고(Places 정책, 2026-09-30 확인), 구글 동적 지도는 월 10,000 한도(`map-load` 관문)가 있다. 고르기는 후보 확정이 목적이라 지도 종류와 무관하게 무료 지도로 통일 |
| 열리는 방식 | 항목 카드의 「장소」 줄에 **「지도에서 고르기」 버튼**. 누르면 카드 아래로 지도 패널(높이 360px)이 펼쳐진다. 한 번에 하나만 열림 | 기존 「다른 장소로 고치기」 입력은 그대로 둔다(키보드·이름 아는 고객용 대체 수단) |
| 첫 화면 위치 | 앞뒤 일정 좌표의 평균, 없으면 서울시청(37.5665, 126.978), 확대 14 | `osm.ts` 기존 기본값과 같다 |
| 움직일 수 있는 범위 | **서울 범위로 제한**(위도 37.4~37.72, 경도 126.7~127.3) | 상품이 서울 하나(루트 사실표). 범위 밖 선택을 화면에서 먼저 막는다 |
| 내 위치(GPS) 버튼 | **v1 에서 뺀다** | 위치 권한 요청·개인정보 부담, 필요성 낮음 |
| 후보 핀 | **지도에는 고객이 찍은 핀 하나만.** 후보는 목록으로만 보인다 | 후보 여러 핀은 화면이 복잡하고, 카카오 값을 타 지도에 다수 표시하는 것은 약관 미확인 |

### B. 후보 찾기(서버)

| 결정 | 값 | 이유 |
|---|---|---|
| 새 창구 | `GET /v1/web/place-candidates?q=…&lat=…&lon=…` (웹 고객 인증 `_web_customer`, 읽기 전용) | 기존 웹 API 와 같은 방식 |
| 검색어 `q` | 기본값 = 고객 원문(「올리브영 이촌」). 2자 이상 필수. 고객이 바꿀 수 있다 | 「호텔」 이라고 적었으면 찍은 자리 근처의 호텔을 찾는다 |
| 찾는 순서 | ① 우리 장소 표(공용)에서 반경 안 이름 포함 → ② **관광공사 목록(DB `place_catalog`)** 에서 반경 안 이름 포함 → ③ **카카오 키워드 검색**(찍은 점 중심, 거리순). ①②는 API 를 안 부른다 | API 호출과 한도를 아낀다. 관광공사는 저장이 허용됐다(2026-09-28) |
| 카카오 반경 | 300m → 결과가 3곳 미만이면 1km → 3km(최대) | 정확한 자리를 먼저. `KakaoLocal.search(near=…)` 가 이미 있고 반경은 인자로 바꾸도록 고친다(지금 20km 고정) |
| 돌려주는 것 | 최대 **8곳**: 이름 · 주소 · 분류 · 좌표 · 찍은 점에서의 거리(m) · 출처(우리/관광공사/카카오). 이름에 검색어 말이 모두 들어 있는 곳이 먼저, 그다음 거리순. 이름+100m 로 겹치는 후보는 하나로 | 이름이 맞는 곳을 앞에 |
| 서버 저장 | **후보 조회 결과를 저장하지 않는다**(`cache_ttl_seconds = 0`) | 카카오 약관(공용 표·검색엔진 입력 금지) |
| 호출 횟수 | 새 「세는 작업」 `place_search`(`web_guard.ACTIONS`)를 더한다. 기본 **키당 하루 60 · 주소당 하루 200 · 서비스 전체 하루 500** | 카카오 하루 1,000건은 접수 읽기와 나눠 쓰는 공용 한도라 500 이하로 두어 접수 읽기 몫을 남긴다(접수 하루 5건 × 항목 수 ≈ 수십 건) |
| 화면의 검색 시점 | **지도를 한 번 찍으면 자동으로 1회 검색**(0.6초 기다렸다가). 핀을 30m 안에서 옮기면 다시 검색하지 않는다. 한 패널에서 최대 10회 | 「찍으면 후보가 나온다」를 살리면서 호출을 아낀다. 지도를 끌기만 할 때는 검색하지 않는다 |
| 한도·키 문제 | 후보를 못 찾으면 **「지금은 후보를 찾을 수 없어요 — 찍은 자리를 그대로 확정할 수 있어요」** 를 보이고 직접 확정은 계속 된다. 조용히 빈 목록을 보이지 않는다 | 폴백 금지 원칙(RULE §3.2): 못 찾은 이유를 신호로 남긴다 |

### C. 고르기 동작

| 결정 | 값 |
|---|---|
| 후보를 누르면 | 그 후보의 이름·좌표·출처로 **바로 확정**한다(확인 창 없음). 카드에 「직접 고침」 배지, 「장소를 정하지 못했다」 문구는 사라진다 |
| 후보에 없으면 | 「여기가 맞아요(직접 찍은 곳)」 — 이름 칸(기본 = 고객 원문)을 확인하고 누르면 찍은 좌표 그대로 확정한다 |
| 다시 고르기 | 언제든 같은 흐름으로 다시 고를 수 있다. 「장소 없음」은 그대로 유지한다 |
| 항목 종류(`kind`) | 카드의 기존 종류를 유지한다(후보 분류로 바꾸지 않는다) |
| 문구 | 한국어·영어 둘(`useT`) |

### D. 저장과 안전

| 결정 | 값 | 이유 |
|---|---|---|
| 확정 요청 | 기존 `POST /v1/web/trip-intakes/{id}/edits` 의 `items[n].place` 값 모양을 늘린다: `{name, latitude, longitude, source}`. `source` = `customer_pick`(후보 선택·직접 찍기). 서버는 다시 찾지 않고 검증만 한다 | 후보 조회를 저장하지 않으므로 서버가 다시 확인할 수 없다. 고객이 본 것을 그대로 받는다 |
| 서버 검증(`_checked`) | 이름 1~80자 · 좌표가 숫자이고 **서울 범위 안** · `source` 가 허용 목록 안. 아니면 422(`place_out_of_seoul` · `invalid_value`) | 지어낸 값·범위 밖 좌표를 막는다 |
| ★저장 위치 | **그 여행 전용 장소 행**(`trip_scope`)으로 저장한다. `trip_api.EXTERNAL_PLACE_SOURCES` 와 `intake/assemble._place_in` 에 `customer_pick` 을 더한다 | **빠뜨리면 고객이 찍은 값이 공용 장소 표로 들어가** 다른 고객 검색에 섞인다(코드에서 확인 — 지금은 `tour_api`·`kakao`·`google_places` 만 여행 전용) |
| 요식 식당 | 등록할 때 이름+150m 로 요식 식당과 같으면 요식 행을 자동으로 쓴다(이미 구현, `dining/ledger.py` `ledger_place_for`) | 별도 작업 없음 |
| 별칭 학습 | 후보 선택·직접 찍기는 **별칭(`place_aliases`)에 저장하지 않는다** | 후보 이름은 카카오 값이라 공용 표에 쌓으면 안 된다. 이름을 직접 적은 경로는 예전 그대로 |
| 근거 기록 | `intake_claims` 의 근거에 `picked_from`(우리/관광공사/카카오/직접) · `query` · 카카오 id 를 남긴다 | 틀렸을 때 어디서 온 값인지 안다 |

### E. 시험과 순서

1. **계약 먼저**: `wiki/external/rest-endpoints.md` 에 새 창구와 값 모양을 적고 화면 세션에 알린다(RULE §3.5, 메모리 「웹 계약 바꾸면 ui 세션에 알림」)
2. **서버**: 새 창구(정상 · 범위 밖 · 한도 · 카카오 키 없음 · 관광공사 DB 만으로 충분) · 확정 값 검증 · 등록 뒤 **여행 전용 행이고 공용 표에 안 들어감**을 시험
3. **화면**: Vitest(후보 목록·확정 요청 모양) + 가짜 서버 시험(`tests/live/stub-server.mjs`)
4. **코덱스 교차검증**(`gpt-6-luna`) → 계획·구현 두 번
5. 예상 작업량: 서버 반나절~1일, 화면 1~1.5일(재지 않은 추정)

## 2. 정하실 것 (기본값이 있다)

| 질문 | 기본값 |
|---|---|
| 후보 핀도 지도에 함께 찍을까 | 아니오(목록만) |
| 찍으면 자동 검색할까, 버튼을 눌러야 검색할까 | 자동 1회 |
| 구글 지도 위에서 고르는 것은 나중에 옵션으로 | v1 제외 |
| 서울 밖 선택 | 막는다 |

## 3. 함께 정하면 좋은 작은 고침 (별개 작업)

- 「올리브영 이촌」 이름 비교: 지점 이름(「동부이촌점」)을 떼어서 「이촌」이 사라지는 것 — 이름 전체 말이 모두 든 카카오 결과가 하나뿐이면 고른다
- 관광공사는 DB 목록(`place_catalog`)을 먼저 보고 없을 때만 API 를 부른다(`intake/places.py` `_tour`)
- 서울 밖 좌표(관광공사 목록의 이상한 10행) 걸러내기
