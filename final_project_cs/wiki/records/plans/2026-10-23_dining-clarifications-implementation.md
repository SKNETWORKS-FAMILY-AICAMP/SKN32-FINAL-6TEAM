# Dining 3단계 — 모호한 조건 질문·답변 연결 실행 계획

사용자가 2026-10-23 승인한 [3단계 설계](2026-10-23_dining-agent-completeness-reuse-clarification.md)를 구현한다. 기존 에이전트와 1·2단계는 유지한다.

## 구현 판단

- 원문 검증을 통과한 request_scope_unclear만 질문으로 만든다. 현재 접수의 식사 전체를 선택지로 제공하고 고객이 적용 식사를 복수 선택하거나 조건을 취소한다. 의미를 코드의 키워드로 재분류하지 않는다.
- `intake_reviews.payload.dining_questions`에 질문·원문·구조화 답을 저장한다. 새 표는 만들지 않는다. 같은 판의 답 변경마다 새 run_id를 예약하고 검사 서명에 답을 포함한다.
- 전용 답변 API는 tenant/customer 소유권과 접수 행 잠금을 먼저 확인한다. revision·run_id가 다르거나 검사 중이면 거절한다. 다른 일정·미리보기·등록 완료 접수에는 답을 적용하지 않는다.
- 모델에 구조화 답을 전달하고 원문 목록의 해당 조건에 고객 선택을 우선 적용한다. 모델이 조건 자체를 누락해도 저장된 조건이 검사 대상에서 사라지지 않는다. 조건 취소·대상 정정은 이전 해당 조건 판정 줄을 제거하고 새 검사에 맡긴다. 독립적인 확정 bad는 유지한다.
- 고정 로딩 설문과 구분해 확인 목록 안에서 질문을 표시한다. 저장·오류·재검사 중 상태와 주기 조회를 연결한다. 기존 등록 정책은 유지한다.
- 같은 판의 전체 재검증으로 review를 새로 만들거나 일정 편집으로 판이 바뀌면 기존 질문·답은 자동 재사용하지 않는다. 오래된 질문 응답은 revision/run_id로 거절한다.
