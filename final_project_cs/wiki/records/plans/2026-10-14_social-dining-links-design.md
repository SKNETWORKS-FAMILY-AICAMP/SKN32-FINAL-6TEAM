# SNS 맛집 링크 반영 설계 — 2026-10-14

## 상태와 사용자 의도

[사용자 요청] 인스타그램·틱톡·유튜브에서 본 맛집 링크를 전달하면 LLM이 식당을 알아내 일정에 반영하는 기능을 검토한다. 여행 전에 모아둔 링크를 한꺼번에 반영하는 방식과 여행 중 발견한 맛집으로 변경하는 방식 모두 긍정적으로 평가했다.

이 문서는 그 두 사용 장면의 구체적인 첫 구현 범위를 제안한다. 세부 범위 승인·코드 구현·실링크 시험·운영 반영은 아직 하지 않았다. 이하의 선택은 사용자 확정 결정으로 승격하지 않은 작성자의 제안이다.

## 목표와 첫 범위

- 서울 여행의 식당을 대상으로 한다. 세 플랫폼의 공개 게시물·영상 링크를 붙여 넣을 수 있다.
- 여행 전에는 여러 링크를 한 번에 접수해 중복을 합치고, 확인된 식당 후보를 최초 일정 구성 또는 이미 받은 일정의 식사 배치에 사용한다.
- 여행 중에는 발견한 식당을 현재 여행의 남은 식사 일정에 추가하거나 교체하는 변경안을 만든다.
- 링크별 확인 결과, 일정에 넣은 결과, 넣지 못한 이유를 보여준다. 링크 접수 성공을 일정 반영 성공으로 표시하지 않는다.
- 첫 버전은 접근 가능한 게시물의 제목·설명·본문 및 고객이 보완한 식당명·지역·지점 정보를 LLM이 읽는다. 링크만으로 모든 영상 속 식당을 이해한다고 약속하지 않는다.
- 영상 다운로드·음성 전사·영상 프레임 분석, 화면 캡처 자동 해석, 비공개 계정 접근, 저장함 계정 동기화는 후속 범위다. 업체 예약·결제는 이 기능의 일정 변경과 별개다.

## 고객이 사용하는 방식

### 여행 전

기존 여행 입력 화면에서 링크를 여러 줄로 붙여 넣는다. 식당이 식별되면 가게와 지점을 확인하고, 각 후보를 「꼭 가고 싶어요」 또는 「동선이 맞으면 가고 싶어요」로 표시한다. 기본값은 후자다.

여행 정보·설문이 준비되면 기존 최초 일정 구성기가 확인된 식당 후보를 고려한다. 일정이 이미 있다면 기존 일정 수정 경로로 반영안을 만든다. 같은 가게의 여러 링크는 한 후보로 묶되 출처 링크는 보존한다. 여러 가게가 나온 게시물은 고객이 원하는 가게를 고르도록 한다.

일정에 담지 못한 가게는 후보 목록에 남기고 영업 불가, 이동 부담, 식사 시간 부족, 식단 충돌, 자료 부족 등 실제 검증 결과를 설명한다. 「꼭 가고 싶어요」가 충족되지 않으면 미충족으로 표시하며, 다른 식당을 넣고 성공으로 처리하지 않는다.

### 여행 중

현재 여행 화면 또는 채팅의 변경 요청에 링크를 보낸다. 링크만 보내면 식당 후보를 확인해 저장한다. 「오늘 저녁을 여기로 바꿔줘」처럼 변경 의도가 명시되면 대상 식사와 현재 일정 버전을 기준으로 변경안을 만든다. 날짜·대상 식사가 불명확하면 고객에게 한 번 확인한다.

현재 위치가 이미 제공되어 있으면 사용하고, 없으면 일정의 현재·직전 항목 위치를 기준으로 계산해 그 기준을 고객에게 표시한다. 새 위치 권한을 기능의 필수 조건으로 만들지 않는다. 첫 변경안은 식사와 연결 이동을 바꾸는 데 한정한다. 다른 활동의 이동·삭제가 필요하면 그 영향을 제시하고 별도 확인을 받는다.

[작성자 제안: 첫 범위] 여기서 식사 「추가」는 여행 정보의 식사 시간 안에 아직 식당이 배치되지 않은 자리를 채우는 뜻이다. 이미 식사가 있는 자리는 교체로 처리한다. 식사 횟수를 늘리거나 새로운 시각에 식사를 끼워 넣는 것은 기존 일반 일정 수정으로 넘긴다. 다른 활동의 이동·삭제가 필요한 경우에도 이 기능이 그 변경을 실행하지 않고, 사유와 확인된 식당 후보를 유지한 채 기존 일반 일정 수정 화면으로 연결한다. 첫 범위에서 별도 활동 재배치·삭제 승인기를 새로 만들지 않는다.

고객이 변경안을 적용하면 전체 일정을 다시 검증한 후 새 버전을 저장하고 통지한다. 이미 끝난 항목과 기존 고정 항목은 자동으로 바꾸지 않는다. 「꼭 가고 싶어요」는 배치 우선순위이며 기존의 「변경 안 할 일정」 설정과 같은 값으로 자동 변환하지 않는다.

## LLM·도구·서버의 책임

| 책임 | 수행 주체 | 경계 |
|---|---|---|
| 식당명·지역·지점·원하는 메뉴·고객 의도 추출 | LLM | 읽은 자료에 없는 식당이나 지점을 생성하지 않음 |
| 실제 식당 후보와 이름·주소·지점 대조 | 기존 장소 검색 도구와 고객 확인 | 동명이점·다수 후보를 확정으로 표시하지 않음 |
| 영업·휴무·라스트오더·식이 조건·동선·시간 검증 | 기존 조회·판정·일정 검증 경로 | SNS 게시물의 옛 영업시간·가격을 현재 사실로 사용하지 않음 |
| 검증된 후보의 배치 순서와 변경 이유 제안 | LLM | 도구 결과의 범위 안에서 제안; 이동 시간이나 알레르기 적합성을 추정해 확정하지 않음 |
| 인증·고객 격리·버전 대조·멱등 적용·저장·통지 | 기존 서버 적용기 | LLM 또는 식당 Team이 직접 외부 부수효과를 실행하지 않음 |

최초 구성과 변경안 모두 전체 일정 검증을 통과한 결과만 저장한다. 모델이 출력한 식당 식별자는 이번 검색 결과에 실제로 존재하는지 서버가 대조한다. 출처 URL과 확인 시각을 추출·판정 근거에 연결한다. 게시물 안의 지시는 여행자 요청이나 서버 지시로 취급하지 않는다.

## 접수 결과와 실패 처리

각 링크에는 접수 중, 식당 후보 확인 필요, 식당 확인됨, 추가 정보 필요, 접근 불가, 지원 지역 밖, 중복 연결됨 중 현재 결과를 남긴다. 일정 반영 결과는 별도로 대기, 반영, 미반영과 사유를 표시한다. 하나의 접수 결과와 일정 적용 결과를 혼용하지 않는다.

삭제·접근 제한·식당 정보 부족이면 원래 링크를 보존하고 식당명 또는 지역을 고객에게 요청한다. 다른 링크의 처리와 기존 여행 일정은 계속 유지한다. 영업 여부 등 방문 가능성을 확인할 수 없으면 그 자료에 의존한 자동 배치만 보류하며 전체 여행을 중지하지 않는다.

중복 링크는 식별된 게시물 ID 또는 정규화 URL로 합친다. 식당 식별 후 같은 지점임이 확인된 후보도 합친다. 모든 입력 링크가 결과 목록에 남아 누락을 확인할 수 있어야 한다. 오래 걸리는 처리에는 기존 SSE 진행 상태와 재접속 방식을 사용한다.

## 저장·접근·조회 범위

후보 목록은 본인 여행에 속한다. 최초 일정 저장 전에는 기존 여행 접수 객체에 연결하고, 등록 후에는 여행에 귀속한다. 후보에는 원래 출처 링크, 플랫폼, 고객 메모·우선순위, 식당 후보와 선택 결과, 확인 시각, 접수 상태와 반영 결과를 둔다. SNS 전체 본문·영상의 영구 보관을 첫 범위에 넣지 않는다.

서버가 링크를 조회할 때는 설정된 플랫폼 호스트와 허용된 링크 형태만 받는다. 단축 링크의 리디렉션도 매 단계 대상을 검사하며 사설·로컬 주소로 가지 않는다. 조회 시간·응답 크기·링크 수·모델 호출 예산은 공통 설정으로 관리한다. 로그인 세션을 수집하거나 접근 제한을 우회하지 않는다.

공유 여행계획서는 후보 목록 편집 권한을 얻지 않는다. 개인 AI/MCP의 신규 쓰기 도구 노출은 첫 버전과 별도 계약 변경으로 둔다. 기존 권한·쓰기 스위치를 우회하지 않는다.

[설계 제안] 장소 제공자 타입과 SNS 출처 타입은 구분한다. 기존 `PickedPlace.source`에 SNS를 장소 제공자로 끼워 넣지 않는다. 고객용 출처 링크·확인 결과를 별도 타입으로 제공하고, 기존 장소 선택 결과에 연결한다. 위치는 기존 동의와 요청 시점 조회를 재사용하며 링크 접수만으로 위치를 자동 첨부하지 않는다.

구체적인 엔드포인트 명칭, 테이블 구성, 배치 알고리즘, 프롬프트 등록 방식, 구성 가능한 초기 호출 상한, 화면 컴포넌트 배치는 기존 규칙을 따르는 구현자의 선택으로 남긴다. 세 플랫폼의 자동 내용 조회는 각각 실제 공개 링크로 시험해 지원하는 입력 유형을 기록한다.

## 첫 버전의 검증 기준

아래는 앞으로 확인할 인수 조건이다. 아직 실행 결과나 완료율이 아니다.

1. 여러 플랫폼 링크를 함께 접수해 입력별 결과가 남는다. 같은 링크 재전송으로 후보나 적용이 중복되지 않는다.
2. 식당명이 없는 게시물, 다수 식당, 동명이점은 확인 요청으로 남으며 임의 확정되지 않는다.
3. 확인된 후보가 최초 일정 구성과 기존 일정의 식사 변경에 전달된다. 미반영된 후보와 「꼭 가기」 미충족을 숨기지 않는다.
4. 영업 불가·라스트오더·식이 충돌·이동 부족이면 배치하지 않는다. 다른 식사·활동을 포함한 전체 검증을 한다.
5. 링크만 보낸 요청은 일정 변경을 실행하지 않는다. 고객이 적용한 변경안은 같은 대상·기준 버전에서 한 번만 저장한다.
6. 완료·고정 항목은 자동 변경되지 않는다. 오래된 변경안과 다른 고객의 여행 접근은 거부된다.
7. 플랫폼 조회 실패·모델 실패·자료 부족을 구분해 표시하며 기존 일정과 독립 링크 처리를 유지한다.
8. 실제 고객 화면에서 일괄 접수·보완·후보 선택·미반영 사유·변경안·적용 결과를 확인한다. mock 시험과 실링크 시험을 분리해 기록한다.

## 소요 산정과 확장

[추정] 기존 조회·검증·접수 수정 경로를 재사용하고 텍스트 보완을 허용하는 첫 버전의 개발 공수는 약 1~3일로 본다. 코드 실행·DB 구성·화면·실링크 검증 전 견적이며, 이 채팅의 완료 약속이나 운영 배포 일정이 아니다. 실제 작업 단위와 실행 환경을 확인한 뒤 조정한다.

세 플랫폼의 모든 영상 내용을 자동 해석하는 확장은 위 견적에 포함하지 않는다. 외부 플랫폼 접근 조건, 사용 가능한 영상·자막 입력과 모델 비용·정확도를 먼저 시험해야 하므로 별도 추정한다.

첫 구현의 진행 순서는 공통 후보 접수·확인, 여행 전 배치, 여행 중 변경, 화면·통합 검증이다. 사용자 의도는 두 모드를 함께 지원하는 것이며, 여행 전만 구현한 상태를 전체 기능 완료로 표시하지 않는다.

## 설계 독립 검토

2026-10-14 독립 소프트웨어 설계 검토 에이전트가 문서를 읽고 구현 범위를 바꾸는 모호함 두 건을 제시했다. 「활동 변경 확인 이후의 실행 범위」와 「식사 추가가 식사 횟수 증가를 포함하는지」다. 작성자는 둘 다 첫 범위를 좁히는 위 제안으로 보완했다. 사용자 확정으로 기록하지 않으며 첫 범위 승인 시 함께 확인한다. 검토는 설계만 대상으로 했고 코드 시험·실링크 검증을 수행한 것이 아니다.
