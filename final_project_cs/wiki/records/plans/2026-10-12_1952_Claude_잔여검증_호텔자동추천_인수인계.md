## 사용자 요청과 완료 기준

사용자 지시: “건너뛴 81건이랑 제외한 220건은 왜 안 한 건데? 필요한 자료 확보해서 남은 검증도 진행하고, 호텔 자동추천이 안 바뀌던 문제도 실제로 해결됐는지 확인해. 이거까지 반영한 인수인계 자료 만들어서 클로드에게 이제 작업 넘겨주자.”

성공 수만 늘리거나 skip·마커·허용 오차를 바꿔 통과시키지 않습니다. 원래 301개 nodeid 각각에 실행 결과·자료 해시·명령·실패 원인·후속 수정 결과를 남깁니다. 삭제·대체가 필요하면 원래 항목과 여행 도메인 대체 항목의 대응 및 근거를 보존하며 임의 성공으로 세지 않습니다. 새 자료가 필요하면 다음·네이버·구글 공개 검색·공식 자료를 우선하고 지도 개발자 API 한도는 아낍니다. 기존 40쌍은 굳이 교체하지 말라는 사용자 지시를 유지합니다.

## 호텔 자동추천 — 확인된 코드와 미확인 원인

사용자 사례: 이름이 “호텔”인 확인 필요 일정에서 자동추천이 바뀌지 않았지만 수동 후보 목록에는 효자스테이를 포함한 대체 장소가 나왔고 직접 변경할 수 있었습니다. 화면 기록에는 호텔의 시각 10:00–11:00, 다음 경복궁과 시간 충돌, 수동 변경 뒤 다른 시각 및 잠금 아이콘이 보였습니다. 이 기록만으로 원래 잠금·예약 상태나 후보별 탈락 원인을 확정할 수 없습니다. 고객 접수 식별자는 공용 문서에 복사하지 않으며 필요할 때 기존 사용자 브라우저 문맥에서 읽기 전용으로 확인합니다.

확인한 두 경로:

1. 단일 카드 `frontend/apps/web/src/features/plan-check/use-server-review.ts`의 autoRecommend는 alternativesOf로 후보를 받고 `candidate.fits && pickedPlace(...)`인 첫 후보만 골라 replaceWith로 장소를 바꿉니다. 현재 시간에 맞는 후보가 없으면 no_fitting_place입니다. 수동 replace는 후보를 직접 고를 수 있으므로 수동 변경 성공이 자동의 적합성 통과를 증명하지는 않습니다. 이 차이가 사용자 요구를 만족하는지는 계약·실제 입력으로 판단하고 필요하면 수정합니다.
2. 전체 자동추천은 `/v1/web/trip-intakes/{intake_id}/autofix` → `entry/trip_api.py` → `components/intake/pipeline.py::autofix` → `components/intake/autofix.py::plan` 경로입니다. 장소와 앞뒤 이동·시각을 맞추지만 locked·booked는 보존합니다. 후보 생성은 `components/intake/candidates.py::alternatives`이며 숙박 32·호텔 조식·같은 종류 판정도 확인해야 합니다. 전체 추천의 현재 제약과 단일 카드 정책을 섞어 원인을 단정하지 않습니다.

재현·수정 순서:

1. 같은 좌표·날짜·시각·앞뒤 일정·locked/booked·이동수단·후보 사실값을 합성 재현 입력으로 동결합니다. 효자스테이 자체를 정답으로 하드코딩하지 않습니다. 수동 후보·카드 자동·전체 자동 dry_run의 후보 ID·fits·status·slack·notes·kept 이유를 한 표로 대조합니다.
2. 잠금/예약이 없고 사실·이동 조건을 충족하는 후보는 자동 경로로 실제 제안·적용되는지 확인합니다. 시각 조정으로 해결 가능한 후보는 정책 근거에 맞게 장소·시각·앞뒤 경로를 함께 재계산합니다. 고정·예약 의사를 무시하거나 부적합 후보에 fits=true를 붙이지 않습니다.
3. 테스트는 후보 존재만 검사하지 않습니다. 합성 DB에서 dry_run 무쓰기, 적용 revision 1회 증가, 장소·시각·경로 일치, 되돌리기, 중복 클릭/재전송·오래된 revision·팀 비활성 거절, 잠금·예약 보존까지 확인합니다. UI 실제 Chrome에서 자동추천→변경된 카드→새로고침 보존→되돌리기를 확인합니다.
4. 공개 서비스는 읽기·CSS 확인과 고객 일정 쓰기 검증을 분리합니다. 기존 고객 일정을 실험용으로 바꾸지 않습니다. 별도 시험용 여행으로 수행할 수 있는 범위·환경을 먼저 확인하고, 실행하지 못한 실제 쓰기를 완료라고 보고하지 않습니다.

관련 회귀: `tests/e2e/test_intake_autofix_dry_run.py`, `tests/e2e/test_intake_review.py`, 계획 확인 관련 웹 단위·브라우저 시험. 위 파일들이 이전 백엔드 선택 목록에 전부 들어 있었던 것은 아닙니다. 301건뿐 아니라 이 증상에 직접 필요한 누락 E2E도 실행 범위에 추가해야 합니다.

## 수행 순서·증거·반영 경계

첫 단계는 기준 커밋과 다른 작업자의 변경을 확인하고 301개 명세의 각 입력을 연결하는 것입니다. 기존 자료로 재실행해 드러난 실제 실패를 원인부터 고칩니다. 자료가 정말 부족한 부분만 공식 자료·공개 웹 검색으로 확보하고 출처·관측 시각·해시·좌표·표본 조건을 기록합니다. 논리 결함은 실행일까지의 공식 문서·관련 논문으로 적용 전제를 검토합니다. 개발 표본을 독립 검증으로 부르지 않습니다.

기존 업무 DB·외부 알림·결제와 분리한 작업 소유 PostgreSQL·새 합성 DB를 사용합니다. 모델 원본·datasets 원본은 변경하지 않고 사본/읽기 설정으로 사용합니다. 기존 산출물 변경 전 백업을 남깁니다. Core→Team.execute→ActionProposal 경계·waiting_input 재개·CAS·tenant/customer 격리·멱등·outbox를 유지하며 계산 부품 직접 우회로 되돌리지 않습니다.

후속 변경 뒤 관련 회귀와 계약·보안·DoD·웹 lint/type/build를 수행합니다. 기존 4015 통과를 새 변경 검증으로 재사용하지 않습니다. 실패·건너뜀·선택 제외를 모두 보고하고 301건 표·호텔 전후 재현·자료 해시·실제 실행 환경을 새 dated 보고서에 남깁니다. 다른 작업자의 변경을 덮거나 강제 푸시하지 않습니다. 이전 사용자 승인 범위의 매니저·디벨롭은 origin·team 네 곳에 통합 검증 후 반영하고 실제 해시를 각각 확인합니다. 공용 WSL 종료·다른 프로젝트 폴더 이동·DB/모델 삭제·결제·고객 외부 메시지는 승인 범위가 아닙니다.

## Claude 시작점

Claude 전용 격리 사본의 기준은 위 최종 커밋입니다. 기존 공유 작업 폴더를 직접 수정하지 않습니다. 실제 로컬 위치·전용 실행기·Claude 세션 ID·재개 명령은 Git 밖 인계 폴더의 LOCAL_HANDOFF.md 및 실행 안내에 보존합니다. 구체 파일·로그를 찾지 못하면 임의 대체하지 말고 이 문서와 실제 원문을 대조합니다. 이 문서를 읽었다는 응답·계획은 301건 수행 완료나 호텔 결함 해결이 아닙니다.
