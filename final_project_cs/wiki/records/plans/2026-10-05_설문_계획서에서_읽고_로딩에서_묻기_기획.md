# 설문을 계획서에서 먼저 읽고, 모자란 것만 로딩 화면에서 묻기 — 기획 (2026-10-05)

> 작성: cs 프로젝트 개발 세션 · 출처: 사용자 제안(2026-10-05) · 상태: **기획(서버 구현 전)** — 웹 몫은 uiux 세션에 넘김, 서버 몫은 사용자 확인 뒤 착수.
> 결정 문서 [D-020](../../../../wiki/decisions/D-020-trip-survey-and-ask-first.md) · [D-019](../../../../wiki/decisions/D-019-travel-density.md) 위에 얹는다. 기존 설문 문항과 기본값은 **그대로 둔다**(사용자 지시 「설문은 일단 그대로」).

## ★ 범위 변경 `[2026-10-05 사용자가 목업을 보고 직접 지시 — uiux 세션 전달]`

아래가 이 문서의 나머지 부분보다 **나중이고 우선한다.**

| # | 바뀐 것 | 서버에 미치는 일 |
|---|---|---|
| 1 | 「검증 화면」은 새 화면이 아니라 **기존 계획 확인 화면**이다. 「이렇게 읽었어요」 칸 · 출처 배지 · 「나중에 답하기」 카드는 **만들지 않는다** | `profile_inference` · `defaulted_items` · `given_items` 는 **웹이 쓰지 않는다**(칸이 있어도 무시) — **서버에 새로 만들지 않는다**(2절의 읽기 규칙·3절의 기준은 **보류**, 필요해지면 되살린다). **필요한 것은 `questions[]`(`id` · `title` · `options[]` · `why`)와 설문 답 받는 입구(`POST …/trip-intakes/{id}/survey`)뿐이다** |

| 3 | 「일정이 바뀌면」도 같은 화면에서 고르고 **1번(자동으로 고치기)이 처음부터 골라져 있다** | 그대로 보내면 `survey_answered` 에 `on_disruption` 이 들어가 `auto_on_disruption` 이 참이 된다 → **2026-09-29 「자동 변경은 직접 고른 경우에만」 규칙과 부딪힌다**(`survey.py` 의 `auto_on_disruption`). **사용자 확인 대기**(uiux 세션이 올림) — 답이 오기 전에는 서버 변경 없음. 서버는 웹이 보낸 값을 그대로 「직접 고른 것」으로 기록하므로 규칙을 바꿀지는 제품 결정이다 |
| 4 | 짧은 로딩: 접수 스트림에 예상 남은 시간 칸이 없다(확인함) | 현행(첫 카드 즉시) 유지. 단계별 소요 로그 → `expected_seconds` 는 후속 |

## 위층 — 한 번 읽고 알 수 있게

**결론.** 제안한 모양(계획서에서 먼저 읽고 → 모자란 것만 로딩 화면에서 묻고 → 그래도 없으면 기본 규칙)은 **맞는 방향**이다. 단 「계획서만으로 취향을 안다」고 하면 안 된다 — 계획서가 알려 주는 것은 **그 사람이 이미 정한 여행의 모양**(하루에 몇 시간 쓰는지 · 몇 시에 시작하는지 · 어떤 종류의 장소인지)이고, **취향과 제약**(식사 제한 · 동행 · 일정이 꼬일 때 원하는 방식 · 내국인 여부)은 대부분 계획서에 없다. 그래서 읽을 수 있는 것은 읽고, 읽을 수 없는 것은 **묻는다.**

**지금 제품은 설문 없이도 돈다.** 설문이 없으면 안전한 기본값으로 움직인다(자동 변경은 하지 않고 「바꿀까요?」 제안으로 보낸다 · 밀도 목표 없음). 설문은 **대체안을 그 사람 취향에 맞게** 만드는 용도라서, 첫 사용자에게 설문을 길게 강요할 이유가 없다 — 제안한 방식이 마찰이 가장 작다.

**두 가지를 바로잡는다.**
1. 지금 밀도는 「1/일정 수」로 재지 **않는다.** 하루 점유 = (일정마다 **시작~종료 시간**의 합) ÷ (그날 활동 가능 시간). 종료 시각이 없으면 **고정 기본값**(활동 90분 · 식사 60분)을 채우고, 채운 사실을 기록에 남긴다. 그래서 「사용자가 준 시간」과 「우리가 채운 시간」을 **갈라야** 한다 — 채운 시간으로 사용자의 템포를 추정하면 우리 기본값을 우리가 읽는 꼴이다.
2. 설문 문항 중 **지금 실제로 쓰이는 것**은 일정이 꼬일 때(`on_disruption`) · 여유(`pace`) · 이동 수단 · 내국인 여부 · 활동/이동 우선순위 · 음식 세부다. **테마 · 동행 · 실내외 · 세부 테마는 받기만 하고 쓰는 코드가 없다**(app 전체 검색, 동적 접근은 놓칠 수 있다). 로딩 화면에서는 **쓰이는 문항만** 묻는다.

**사용자가 정할 것(작은 것 둘).** ① 일정 읽기에 **과거 여행 기록**을 쓰려면 개인정보 동의 항목이 필요하다(`[법무 확인 필요]`) — 1단계에서는 **쓰지 않는** 안을 추천 ② 로딩 화면 자동 넘김 시간(아래 표의 30초 + 20초 안을 추천).

## 1. 흐름 (제안)

```
계획서 접수 ─→ [서버] 읽을 수 있는 것을 읽는다 (근거 · 확신도 기록)
                  │
                  ├─ 확신 ≥ 기준 → 「읽은 값」으로 채움 (출처=계획서에서 읽음, 검증 화면에서 고칠 수 있음)
                  └─ 확신 < 기준 / 읽을 수 없는 항목 → 「물을 것」 목록
                                              │
        로딩 화면 ─→ 물을 것만 한 장씩 묻는다(최대 3문항, 한 번 탭)
                       · 처리가 끝나면 「전부 건너뛰기」 활성화
                       · 안 물은 것 → 기본 규칙(대표 수치 · 우리 기본값)
        검증 화면 ─→ 「이렇게 읽었어요」 칸에서 읽은 값 · 답한 값 · 기본값을 구분해 보여 주고 고치게 한다
```

## 2. 제안 항목별 평가

| # | 제안 | 평가 | 보정 |
|---|---|---|---|
| 1 | 「계획 다 짜주기」 선택 시 날짜 옆에 **밀도(여유)** 고르기 | **좋다** — 설문 16번 `pace` 와 같은 값이라 서버 변경이 없다(`constraints.survey.pace`). 안 고르면 지금처럼 하루 활동 2개 | 화면 문구만: 「여유롭게 0.40 · 적당히 0.55 · 꽉 차게 0.70」을 숫자 없이 보여 준다 |
| 2 | 계획서 넘기는 화면에서 **「자동 수정 + 대체안 2개」 vs 「대체안 3개 제안만」** 고르기 | **좋다** — 설문 15번(`replace` · `ask_first`)을 이 화면으로 옮긴다. **계획서에서 읽을 수 없는** 항목이라 반드시 **묻는다** | 건너뛰면 지금 규칙(제안으로 보냄, 자동 변경 없음)이 그대로다 — `auto_on_disruption` 은 **직접 고른 경우에만** 켜진다. 기본값을 몰래 `replace` 로 두지 않는다 |
| 3 | 이동 선호를 계획서에서 읽어 **수치로 정리**, 감정분석 · 사용자 성향 · 에이전트 넘김 · 과거 여행까지 종합 | **일부만 지금 가능** | ㉠ 지금 가능: 계획서에 **이동수단이 적혀 있으면** 읽는다(예: 「택시로」) — 없으면 읽을 것이 없다 ㉡ 감정분석은 **계획서 문장에는 정보가 없다**(계획서는 감정이 아니라 일정이다). 쓸 곳은 일정 변경 **채팅 문장**(「너무 빡빡해요」)이다 ㉢ 에이전트 넘김은 **에이전트가 이미 아는 선호를 구조화해 보내는 칸**을 열면 된다(출처=에이전트, 그대로 믿지 않고 확신도 표시) ㉣ 과거 여행 활용은 동의 항목이 필요해 **1단계에서 뺀다** |
| 4 | 밀도: 사용자가 준 **시간으로 밀도를 재고**, 설문의 어느 단계에 해당하는지 맞춰 **다음 일정도 그 수준으로** | **좋다 — 가장 확실한 항목** | ㉠ 이미 있는 측정(`measure_density`)을 쓴다 — 「1/n」이 아니다 ㉡ **사용자가 준 시간 비율이 기준 이상일 때만** 단계로 옮긴다(아래 표). 기본값(90/60분)으로 채운 항목은 **분모에서 뺀다** ㉢ 가장 가까운 단계로 매핑(0.40 · 0.55 · 0.70 · 0.80), 출처=「계획서에서 읽음」 ㉣ 사용자가 직접 고른 `pace` 가 있으면 **그것이 이긴다** |
| 5 | 장소별 **평균 소요 시간**을 LLM 이 검색해 조사 | **방식을 바꾼다** — 요청 때마다 조사하지 않는다 | 공식 길 안내·장소 API 에 「보통 얼마나 머무는지」 값은 **없다**(우리가 쓰는 관광공사 · 구글 장소 응답에서 확인하지 못함 — 읽은 범위: 우리 어댑터 응답 필드). 요청마다 LLM 검색을 부르면 **느리고 비싸고 매번 달라진다**. 대신 **장소 종류별 표**(궁궐 · 박물관 · 시장 …)를 **미리 한 번 조사해 출처와 함께 저장**하고, 모르는 종류만 기본값(90/60분) + 「추정」 표시 |
| 6 | 요식 등도 같은 방식 — 읽고 → **기준 이상일 때만 반영** → 아니면 로딩 설문 → 아니면 평균·기본 규칙 | **방향 맞다** | 기준과 근거는 아래 3절. **식사 제한(채식 · 할랄 · 알레르기)과 접근성은 절대 추정하지 않는다** — 틀리면 위험하고, 이미 동의 철회 때 지우는 민감 항목이다(`consents.py`). 묻거나 기본값(제한 없음이라고 **가정하지 않고** 「모름」)으로 둔다 |
| 7 | 로딩 화면 설문 — 처리 끝나면 **전부 건너뛰기** 활성화 · **일정 시간 무조작이면 검증 화면으로** · 다 답했으면 오버레이 안내와 함께 넘김 | **좋다** — 단 아래 4절 규칙을 지킨다 | 자동 넘김은 접근성 기준상 **시간 제한**이다 → 끄기 · 연장 수단이 있어야 한다. 답은 **한 문항씩 바로 저장**해서 넘어가도 잃지 않게 한다. 로딩이 짧으면 못 물은 문항은 검증 화면의 **「나중에 답하기」 카드**로 이어 준다 |

### 2-1. 「하루 활동 2곳」이 어느 밀도 단계인가 — 실측 `[2026-10-05]`

시험용 서울 자료(`tests/e2e/test_trip_planner.py`의 후보 · 이틀 · 하루 활동 창 08:00~22:00)에서 곳 수별로 쟀다. 하루에 활동 2곳(+ 식사 2 + 이동)은 밀도 **0.367~0.371**, 3곳은 **0.480~0.487**, 4곳은 **0.593~0.599**(4곳은 닫는 시각 판정에 걸려 채택되지 않았다).
→ 밀도를 안 골랐을 때의 기본 2곳 ≈ **「여유롭게」(0.40) 안쪽**이고, 「적당히」(0.55)와 「꽉 차게」(0.70)는 이 자료에서 둘 다 3곳(0.48)이다. ★이 시험 자료에서 이틀 × 3회만 잰 값이다 — 실제 카탈로그에서는 달라질 수 있고, 화면에 숫자로 약속하지 않는다.
**그래서:** 웹은 밀도를 안 골랐을 때 `pace` 를 **보내지 않는다**(보내면 「직접 답한 값」으로 기록되고 하루가 지금보다 빡빡해진다). 서버가 기본을 「보통」으로 바꾸려면 **제품 결정**이다(출처 `default` 로 서버가 두어야 한다) — 사용자 결정 대기, 추천은 지금 기본 유지.

## 3. 「읽은 값」을 반영하는 기준 (우리가 고른 값 — 아직 측정 안 함)

★**권위 있는 기준을 찾지 못했다**(검색 범위: 추천 시스템 콜드스타트 · 선호 도출 문헌 요약 — 「몇 건 이상이면 믿는다」 같은 표준은 없었다). 아래는 **보수적인 초기값**이고, **정확도를 재서 조정한다**(5절).

| 항목 | 반영 기준 | 이유 |
|---|---|---|
| 하루 여유(`pace`) | 사용자가 준 시간이 있는 일정이 **그날 일정의 60% 이상**이고, 그런 날이 **하루 이상** | 기본값으로 채운 시간이 분자의 대부분이면 우리 기본값을 읽는 것이다 |
| 이동 선호 | 계획서에 이동수단이 **직접 적힌 줄이 2개 이상**이고 **같은 수단이 2/3 이상** | 한 줄로는 취향이 아니라 그날의 사정일 수 있다 |
| 테마 · 활동 종류 | 장소 종류가 **3개 이상**이고 한 갈래가 **2/3 이상** | 일정 하나는 관광지 하나일 뿐이다 |
| 일정이 꼬일 때 · 내국인 여부 · 동행 · 식사 제한 · 접근성 | **읽지 않는다 — 항상 묻는다**(건너뛰면 안전 기본값) | 계획서에 없거나(행동 선호) 틀리면 위험하다(민감 · 신원) |
| 로딩 설문 문항 수 | **최대 3문항**, 한 번 탭으로 답 | 설문 피로를 줄이려는 값 — 근거로 잰 값은 없다 |

모든 값에 **출처**(`asked` 직접 답함 · `inferred_from_plan` 계획서에서 읽음 · `agent` 에이전트가 줌 · `default` 기본값)와 **근거**(어느 일정 · 몇 건)를 남긴다. 「받아 둔 값을 반영했다고 말하지 않는다」(survey.py 원칙)를 그대로 지킨다.

## 4. 로딩 화면 설문 규칙

| 규칙 | 값 | 근거 |
|---|---|---|
| 기다림이 길면 진행 표시를 둔다 | 10초 넘는 처리 | NN/g 응답 시간 한계 — 10초가 주의를 붙들어 두는 한계이고, 그 이상은 진행 표시와 다른 할 일이 필요하다 · [Response Time Limits](https://www.nngroup.com/articles/response-times-3-important-limits/) |
| 「전부 건너뛰기」 | **처리가 끝나면** 활성화, 늘 한 번 탭 | 사용자 지시 |
| 무조작 자동 넘김 | **마지막 조작 후 30초 무조작 → 20초 카운트다운 → 검증 화면** (합 50초) | 카운트다운 20초는 WCAG 2.2.1 의 최소 경고 시간이다 · [Timing Adjustable](https://www.w3.org/WAI/WCAG21/Understanding/timing-adjustable.html). **30초는 우리가 고른 값**(한 문항을 읽고 답하는 시간으로 넉넉하다고 본 것 — 재지 않았다) |
| 연장 · 끄기 | 카운트다운 중 「계속 답할게요」(누를 때마다 연장, 횟수 제한 없음) + 「자동으로 넘어가지 않기」 | 같은 기준 — 시간 제한은 끄기 · 조정 · 연장 중 하나가 필수이고, 연장은 10회 이상 허용해야 한다 |
| 다 답했을 때 | 바로 오버레이 안내 + 검증 화면 | 사용자 지시 |
| 답 저장 | **문항마다 즉시** | 자동 넘김이 답을 잃게 하지 않는다 |

`[미측정]` **실제 로딩 시간 분포**를 먼저 잰다 — 사진 읽기가 들어가면 수십 초일 수 있고 글만이면 몇 초일 수 있다. 몇 초뿐이면 로딩에서 3문항을 다 못 묻는다 → 못 물은 것은 검증 화면 카드로 잇는다.

## 5. 측정 계획 (읽은 값을 믿기 전에)

「LLM 이 지금 그 정도로 발전했나」에는 **우리 자료로 재 보기 전에는 답할 수 없다.** 규칙으로 읽는 것(밀도 · 시작 시각 · 이동수단 문구 · 장소 종류)은 LLM 없이 결정적이다. LLM 은 **모호한 글에서 선호를 뽑을 때만**, **원문 인용을 근거로 달게** 한다.
1. 설문을 **직접 답한** 여행과 그 여행의 계획서 쌍으로 평가 자료를 만든다(건수는 우리 DB 에서 센다 — `[미확인]` 지금 몇 건인지 안 셌다).
2. 「계획서만으로 읽은 값」과 「직접 답한 값」의 일치율을 **문항별로** 잰다 — 표본 크기 · 반복 · 편차를 함께 적고, 편차가 겹치면 「구분되지 않는다」.
3. 일치율이 낮은 문항은 **읽지 않고 묻기만** 한다. 그 전까지 읽은 값은 검증 화면에 **「추정」** 으로 표시한다.

## 7. 위험 · 하지 않는 것

- **하지 않는다:** 식사 제한 · 접근성 · 내국인 여부 · 동행 구성을 추정해 채우기 / 과거 여행 기록 사용(동의 항목 필요) / 설문 문항 바꾸기(사용자 지시 — 그대로 둔다) / 요청마다 LLM 검색으로 소요 시간 조사.
- **위험:** 틀린 추정이 조용히 반영되는 것 → 출처 표시와 검증 화면 수정으로 막는다. 질문이 너무 많아 이탈하는 것 → 최대 3문항 + 건너뛰기. 로딩이 짧아 못 묻는 것 → 검증 화면 카드.
- **확인 못 한 것:** 로딩 시간 분포 · 읽은 값의 정확도 · 설문 직접 답한 여행의 건수 · 문헌의 「질문 2개로 개선」 보고는 검색 요약만 봤고 원문(arXiv 2510.27342)은 열지 않았다 — 우리 문제(여행 일정)와 같은 조건이 아니다.
