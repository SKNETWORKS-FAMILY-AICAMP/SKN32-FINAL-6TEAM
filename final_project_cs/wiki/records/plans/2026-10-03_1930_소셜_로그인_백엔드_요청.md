# 구글·카카오·네이버·디스코드로 로그인하기 — 백엔드 요청 (웹 화면은 이 계약대로 이미 연결해 둠)

작성: ui 세션(웹) · 2026-10-03 · 대상: cs 백엔드 세션 · ★이 문서는 **계획서**다. 서버 코드는 고치지 않았다. 사용자가 「소셜 로그인 도입해봐」(2026-10-03)라고 지시했다.

## 위층 — 한 번 읽고 알 수 있게

**결론.** 지금 서버에는 소셜 로그인이 없다(`rest-api.md`: OAuth2/OIDC는 2단계 · `web-screen-api.md`: 소셜 계정 연결은 검토 중). 웹 화면은 아래 계약대로 **이미 만들었고**, 서버가 이 엔드포인트들을 내놓으면 따로 고치지 않아도 동작한다. 서버가 아직 없으면 화면은 「소셜 로그인은 서버 준비 중이에요」라고만 말한다(가짜 버튼을 두지 않는다).

**무엇이 달라지나(고객 입장).** 지금은 **사용자 키**(`acop_u_…`)를 잃으면 여행을 못 연다(이메일 복구는 뺐다). 소셜 계정을 키에 **연결**해 두면 ① 키를 잃어도 계정으로 같은 키의 여행을 연다 ② 새 기기에서 계정으로 로그인해 그 여행을 연다. 키 자체와 모든 `/v1/web/*` 인증(`X-User-Key`)은 **바뀌지 않는다** — 소셜 로그인은 「키를 받아 오는 또 하나의 길」이다.

| 고객이 하는 일 | 서버가 하는 일 |
|---|---|
| 마이페이지에서 「Google 연결」 | 구글 로그인 화면으로 보냈다가, 돌아오면 그 구글 계정을 **이 키의 사용자**에 붙인다 |
| 새 기기에서 「Google로 로그인」 | 그 구글 계정에 붙은 사용자를 찾아 **그 사용자의 키**를 이 기기에 준다(없으면 새 사용자+새 키) |
| 「연결 해제」 | 붙인 것을 지운다(키와 여행은 그대로) |

**정할 것(사용자)**: ① 제공할 업체 — 웹은 4곳(Google · Kakao · Naver · Discord)을 다룬다. 업체마다 **개발자 콘솔에서 앱을 만들고 클라이언트 ID·비밀값과 리디렉션 주소를 등록하는 일은 사람이 해야 한다**(서버 환경변수에 넣는다). 등록이 안 된 업체는 `GET /auth/providers` 에서 빠지고 화면에도 안 나온다. ② 이메일을 받을지 — 아래 설계는 **받지 않는다**(업체의 고유 번호 `sub`만, 개인정보 최소).

## ★1단계는 구글 하나 (사용자 결정 2026-10-03 — 「가장 쉬운 걸로 하나 먼저」)

- 서버는 **구글만** 구현해도 된다. 웹은 `GET /auth/providers` 가 알려 주는 업체만 단추로 그리므로, 이 목록에 `google` 만 담으면 화면에는 구글만 나온다(웹 추가 작업 없음). 나머지 업체는 같은 계약에 업체 이름만 더하면 되도록 업체별 차이(스코프 · 사용자 번호를 얻는 방법)만 갈라 둔다.
- 구글은 표준 OIDC 다: 스코프 `openid` 하나로 사용자 고유 번호 `sub` 를 ID 토큰에서 얻는다(이메일·이름은 요청하지 않는다). `state` · PKCE(`S256`) · `nonce` 를 쓴다.
- 구글 콘솔은 리디렉션 주소를 **HTTPS** 로 받되 loopback(`127.0.0.1`·`localhost`)은 예외다(구글 OAuth 웹 서버 문서로 확인). 그래서 로컬 시험은 콘솔에 로컬 콜백 주소를 그대로 등록할 수 있고, 운영 주소는 배포가 정해진 뒤 HTTPS 로 더한다.
- 사람이 할 일(구글 클라이언트 만들기)은 아래 「사람이 해야 하는 설정」 Google 줄과 같다. 이 값(클라이언트 ID · 비밀값)은 사용자가 만들어 git 밖 환경 파일에 넣는다 — 웹 세션은 만들지도 입력하지도 않는다.

## 계약 (웹이 호출하는 모양 그대로)

모든 응답 오류는 기존 `{"error": {"code", "message"}}`. 업체 이름은 `google | kakao | naver | discord`.

| 호출 | 키 | 하는 일 |
|---|---|---|
| `GET /v1/web/auth/providers` | 없음 | `{"providers": [{"id": "google"}, …]}` — 서버에 **설정이 끝난 업체만**. 이 호출이 404 면 웹은 「서버 준비 중」으로 둔다 |
| `POST /v1/web/auth/{provider}/start` | 선택 | 본문 `{"mode": "login"\|"link", "client_nonce": "<웹이 만든 무작위 32자 이상>", "turnstile_token"?: "…"}` → `{"authorize_url": "https://…"}`. `link` 는 키 필수(`unauthenticated`). `login` 이고 키가 없으면 새 사용자를 만들 수 있으니 **사람 확인을 요구**해도 된다 → 422 `human_check_required`(웹이 확인 화면을 띄우고 토큰을 실어 다시 부른다). 없는 업체 404 `provider_not_enabled` |
| 업체 로그인 화면 → `GET /v1/web/auth/{provider}/callback?code=…&state=…` | — | **브라우저 이동 전용**(서버가 받는다). 서버가 `state`·PKCE·`nonce`(OIDC)를 검증하고 `code` 를 토큰으로 바꿔 `sub` 를 얻는다. 끝나면 **웹으로 302**: `{WEB_ORIGIN}/auth/done?ticket=<일회용>` 또는 `…/auth/done?error=<코드>`. 코드: `cancelled`(고객이 취소) · `denied` · `already_linked_elsewhere`(이 계정은 다른 사용자에게 이미 붙어 있다) · `failed` |
| `POST /v1/web/auth/exchange` | 없음 | 본문 `{"ticket", "client_nonce"}` → `{"outcome": "signed_in"\|"created"\|"linked", "provider", "user_key"?, "notice"?, "trips": <그 사용자의 여행 수>}`. `signed_in`·`created` 일 때만 `user_key`(이 기기가 쓸 키). `linked` 는 키를 바꾸지 않는다. 만료·재사용·nonce 불일치는 410 `ticket_invalid` |
| `GET /v1/web/auth/links` | 필수 | `{"links": [{"provider", "linked_at"}]}` — 이 키에 붙은 업체. 계정 이름·이메일은 **돌려주지 않는다** |
| `DELETE /v1/web/auth/{provider}` | 필수 | 연결 해제 → 200 `{"links": [...]}`(남은 연결 — 웹의 호출 도우미가 본문 없는 204 를 못 읽는다). 안 붙어 있으면 404 `not_linked` |

**티켓** — 일회용 · 수명 60초 · 서버는 `ticket` 과 `client_nonce` 의 **해시**만 저장하고, 교환할 때 둘이 같은 흐름인지 본다.

## 보안 (필수)

1. **로그인 CSRF 막기** — 공격자가 자기 계정의 `ticket` 이 든 링크를 피해자에게 보내면 피해자 브라우저가 공격자 계정으로 로그인된다. 그래서 `client_nonce` 는 **시작한 브라우저만 안다**(웹이 세션 저장소에 보관) · `exchange` 가 nonce 일치를 요구한다.
2. **`state`** 는 서버가 만들고 서버가 저장한다(수명 10분 · 한 번만). PKCE(`S256`) · OIDC `nonce` 사용. 구글 · 네이버 · 카카오 · 디스코드 각 방식에 맞춘다(카카오 · 네이버는 OIDC 가 아니면 사용자 정보 호출로 `id` 를 얻는다).
3. **리디렉션 주소 허용 목록** — `WEB_ORIGIN` 은 서버 설정(환경변수)이고 요청 값으로 바꿀 수 없다(열린 리디렉션 금지). `return_to` 는 서버가 받지 않는다(웹이 자기 세션 저장소에 둔다).
4. **저장** — 업체 이름과 `sub` 의 **해시**(`HMAC(서버 비밀, provider + ":" + sub)`)만 저장한다. 이메일 · 이름 · 사진은 요청하지도 저장하지도 않는다(스코프: 구글 `openid`, 카카오 `openid`, 네이버 기본, 디스코드 `identify`).
5. **한도** — `start` · `exchange` 에 IP+키 단위 한도, `login` 의 새 사용자 생성에 사람 확인(Turnstile)과 기존 세션 발급 한도(`too_many_sessions`)를 그대로 적용.
6. 한 업체 계정은 **한 사용자에게만** 붙는다. 이미 다른 사용자에게 있으면 `link` 는 실패(`already_linked_elsewhere`) — **합치지 않는다**(여행을 합치는 일은 이번 범위가 아니다).
7. 키 교체(`session/rotate`)를 해도 연결은 남는다. 연결된 계정으로 로그인하면 **현재 유효한 키**를 준다(교체된 옛 키는 아니다).

## 사람이 해야 하는 설정 (서버 코드로 못 한다)

| 업체 | 콘솔에서 할 일 | 서버 설정에 넣을 것 |
|---|---|---|
| Google | Google Cloud 콘솔 → OAuth 동의 화면 + 웹 클라이언트 만들기, 승인된 리디렉션 URI 에 콜백 주소 등록 | 클라이언트 ID · 비밀값 |
| Kakao | Kakao Developers → 앱 만들기 → 카카오 로그인 활성화 · Redirect URI 등록(OpenID Connect 켜면 `sub`) | REST API 키 · (선택) 클라이언트 시크릿 |
| Naver | 네이버 개발자센터 → 애플리케이션 등록(네이버 로그인) · Callback URL 등록 | 클라이언트 ID · 시크릿 |
| Discord | Discord Developer Portal → Application → OAuth2 Redirects 등록 | 클라이언트 ID · 시크릿 |

콜백 주소는 전부 **서버 주소**(`/v1/web/auth/{provider}/callback`)다. 배포 주소가 정해지면 같이 등록한다. **개발용(로컬)과 운영용은 앱을 따로** 만든다. 이 값들은 `.env` 같은 git 밖 파일에만 둔다(저장소·문서·커밋 메시지에 적지 않는다).

## 완료 기준 (시험 예)

- 업체별 가짜 업체 서버(시험용 서버)로 `start → callback → exchange` 한 바퀴: `login` 신규 → `created`+키 · `login` 기존 → `signed_in`+그 사용자의 키 · `link` → `linked`+키 없음.
- 같은 `ticket` 두 번 교환 → 둘째 410. 다른 `client_nonce` → 410. 61초 뒤 → 410.
- 다른 사용자에게 붙은 계정으로 `link` → 콜백이 `error=already_linked_elsewhere`.
- `GET /auth/providers` 는 설정 없는 업체를 뺀다 · 설정이 하나도 없으면 빈 목록(404 가 아니다).
- 이메일 · 이름이 DB 어디에도 없다(저장 열 목록으로 확인).

## 웹(ui) 쪽에서 이미 한 것 — 서버 일이 아니다

- 마이페이지 「소셜 계정」 카드: 업체별 연결 · 해제(`links`, `DELETE`) · 키 없는 브라우저의 로그인. 서버가 `providers` 를 못 주면 「준비 중」만 말한다.
- 메뉴에 「계정 연결 · 로그인」 줄(업체가 하나라도 있을 때만).
- `/auth/done`: 티켓 교환 → 키 저장(로그인일 때만) → 결과 문장. 주소창에서 `ticket` 을 곧바로 지운다.
- 이미 키가 있는 브라우저에서 「로그인」을 누르면 **키가 바뀐다**는 경고를 먼저 보이고 「연결」을 권한다(키를 조용히 바꾸지 않는다 — `client.ts` 의 원칙).

## 확인하지 못한 것

- 카카오 · 네이버가 OIDC `sub` 를 주는 설정이 우리 앱 종류에서 되는지(안 되면 사용자 정보 호출의 `id` 로 대체).
- 운영 배포 주소(콜백 주소 등록에 필요).
