# 고객 제보 · 현장 신호 · 웹 검색 대체 — 계획서 (이동 세션)

작성: 이동 세션 · 2026-10-05 · 상태: **계획서 — 구현 전.** 요청(사용자): 「고객에게 제보를 받고, 막힘·긴 웨이팅 같은 변경 이유를 파악하되 고객이 납득할 수 있게 하고, 제보가 통계적으로 유의미해지면 같은 조건에 놓일 일정을 가진 다른 고객에게 변경을 추천한다. GPS 로 고객 상태도 본다(티맵처럼). API 가 안 돌아도 되게 하고, API 가 다 안 돌면 우리 LLM 에 웹 검색 도구를 줘서 현황을 검색·반영하게 한다」.

## 위층 — 한 번 읽고 알 수 있게

**결론.** 만들 수 있다. 다만 **「API 를 대신한다」가 아니라 「API 가 못 보는 곳을 보태고, API 가 멈췄을 때 이어받는다」** 로 설계해야 맞다. 제보는 고객이 많이 있는 곳·시간에만 모이기 때문이다(규모 문제 — 아래 ③).
**고객 입장에서 달라지는 것.** 일정이 막힐 때 「제보하기」 한 번으로 이유를 남기고(고르기 몇 번), 같은 이유로 일정이 걸릴 다른 고객은 「이 곳에서 대기 40분 제보가 5건 있어요 — 바꿀까요?」를 근거와 함께 받는다. 근거 없는 추천은 없다.
**꼭 정해야 할 것(사용자).** ① **GPS 를 저장할지** — 지금 규칙은 「좌표를 어디에도 남기지 않는다」이고 통계를 내려면 위치가 필요하다. 제안: 좌표 대신 **장소 번호·500m 칸·「근처에 있었음」 표시만** 남긴다. ② **웹 검색 결과를 어디까지 믿을지** — 제안: 「참고 안내」까지만 하고 일정을 **자동으로 바꾸지 않는다**.

## 설계 — 세 층

```
 ① 제보 받기           ② 모아서 판단              ③ 같은 조건 고객에게 추천
 고객이 고르기         장소·구간·이유별로 센다      그 곳을 지날 예정인 다른 고객
 (이유 · 시간 · 위치)  기준을 넘으면 「신호」         근거와 함께 「바꿀까요?」
        │                    │                          ▲
        └──→ 현장 제보 표 ──→ 현장 신호(추정 등급) ──→ 기존 감시 루프 · 동의 · 알림
                                  ▲
 API(UTIC · ITS · 지하철알림)     │  못 읽으면
 웹 검색 대체 소스(참고 안내)  ───┘
```

핵심은 **새 소스를 기존 접점(`route_events.affecting()` 같은 모양)에 끼우는 것**이다 — 그러면 감시 루프 · 동의 · 알림 · 결정 15(못 읽으면 치명)를 새로 만들 필요가 없다.

### ① 제보 받기 — 고객이 납득하는 이유

- **고르기가 먼저, 글은 선택.** 이유 목록: 길이 막힘 · 대중교통이 안 옴/지연/안 섬 · 대기가 길다(○분) · 닫았다/영업 안 함 · 사람이 너무 많다 · 날씨 때문에 · 몸이 힘들다 · 기타. 이유마다 **필요한 값만** 묻는다(대기 = 몇 분, 막힘 = 어느 구간).
- **받자마자 고객에게 돌려준다**: 「제보 고마워요 · 같은 곳에서 최근 N건이 있었어요 · 지금 바꾸면 이런 방법이 있어요(근거: …)」 — 제보가 **내 일정을 바꾸는 데 바로 쓰이는** 구조여야 고객이 납득하고 계속 제보한다.
- **「왜 이 추천인가」를 항상 보인다**: 몇 건 · 몇 분 전 · 어떤 종류(제보/공식 알림/웹 확인) · 확신 정도(`추정`). 추천은 **고객이 거절할 수 있고 거절 이유도 한 번 고르게** 한다(통계에 반영).
- 기존 채팅 제보(`read.customer_report`)와 **같은 이유 목록**을 쓴다 — 말로 한 제보도 표로 들어간다.

### ② 모아서 판단 — 통계 규칙(초안 · 숫자는 정할 값)

- **세는 단위**: (장소 또는 구간 또는 노선 대상 `N호선:역` `도로:이름`) × 이유 × 시간 창(예: 최근 90분). 제보는 **오래 안 간다** — 창이 지나면 사라진다(막힘은 곧 풀린다).
- **「유의미」의 정의(초안)**: ① **서로 다른 고객 k 명 이상**(한 사람이 여러 번 눌러도 1건) ② 같은 시간 창에 모임 ③ 평소(기준선)보다 뚜렷이 많음 — 기준선이 아직 없으면 ①②만. ④ 제보한 사람이 **그 곳 근처에 있었음**(아래 GPS)인 건 가중.
- **k 와 창은 우리가 고르는 값이다(측정 아님).** 처음엔 보수적으로(k 가 크게) 시작해 실제 제보량을 보고 조절한다.
- **남용 방지**: 같은 기기·계정의 반복은 1건 · 제보 빈도 한도 · 「근처에 있었음」 표시가 없으면 약한 가중 · 거짓 제보가 쌓이면 그 고객 가중 하향 · 대량 제보가 한 곳에 몰리는데 **공식 소스는 조용**하면 「신호 있음 — 확인 중」으로만 표시(자동 변경 근거로 쓰지 않음).
- **등급**: 제보 신호는 **`추정`**(공식 알림은 `확정` 등급). 제보만으로 「사건 확정」이라고 말하지 않는다 — 문장은 「제보 N건이 있었어요」.

### ③ 같은 조건의 다른 고객에게 추천

- **누구에게**: 앞으로 N시간 안에 **그 장소·구간·노선·같은 이유 조건**(예: 같은 역 무정차, 같은 길 통제, 같은 장소 긴 대기)에 걸릴 일정 항목이 있는 고객. 기존 `route_targets` · 장소 번호로 찾는다(새 색인은 작다).
- **무엇을**: 기존 「바꿀까요?」 제안(동의 후 적용 · 되돌리기)에 **근거 줄**을 더한다 — 새 변경 로직은 만들지 않는다.
- **GPS(티맵식 상태 확인)**: 추천을 받는 고객이 **앱을 열고 있을 때만** 현재 위치를 읽어(기존 브라우저 위치 방식) 「이미 지나갔는지 · 얼마나 가까운지」를 보고 문구를 고른다. **백그라운드 계속 추적은 하지 않는다**(웹은 신뢰성 있게 못 하고 개인정보 부담이 크다 — 정하실 것).

### 개인정보 — 충돌 1건의 해법(제안)

| 남기는 것 | 안 남기는 것 |
|---|---|
| 장소 번호 · 구간/노선 대상 · **500m 격자 칸 번호** · **「제보 시각에 그 곳 근처(반경 ○m)였음」 true/false** · 제보 시각 · 이유 코드 · 대기 분 · **제보자 가명 번호(되돌릴 수 없는 해시)** | **원 좌표(위도·경도) · 이동 경로 · 정확도 값 · 기기 식별자 원문** |

- 위치는 **제보를 받는 요청 안에서만** 거리 계산에 쓰고 곧바로 버린다(`trip_here` 와 같은 처리) — 저장하는 것은 위 표뿐이다. 그러면 「좌표를 남기지 않는다」 규칙이 **그대로 지켜진다**(격자 칸 번호는 좌표가 아니다 — 시험이 이 구분을 확인한다).
- **동의**: 위치는 고객이 허락한 요청에만 쓴다. 제보 통계에 쓰인다는 사실을 제보 단추 근처에 한 줄로 알린다.
- ★**법적 확인이 필요하다**(`[미확인]`): 개인 위치 정보를 수집·이용하는 서비스에는 법상 동의·신고 의무가 있는 것으로 알려져 있으나 **법 본문을 이번에 읽지 않았다.** 공개 전에 읽고 정한다(학업용이라도 개인 위치를 다루므로). 위 설계는 「원 좌표 비저장」으로 부담을 최소화한 안이다.

### 웹 검색 대체 소스 (API 가 다 멈췄을 때)

- 결정 15 의 「1차가 안 되면 대체로」에 들어가는 **마지막 대체**다. 못 읽은 대상(`affecting()` 이 `None` 이거나 `unsupported`)에만 부른다.
- **LLM 에 검색 도구를 준다**: 검색 → 결과 몇 건 읽기 → 「이 대상에 지금 사건이 있는가」를 **근거 링크와 읽은 시각**과 함께 답하게 한다. 근거 없는 문장은 못 쓴다(원칙 0.1).
- ★**보수적으로만 쓴다**: 결과는 **「참고 안내」(등급 `추정`)** 이고 일정을 **자동으로 바꾸지 않는다**(고객에게 「이런 소식이 있어요 · 출처 · 확인해 보세요」). 이유: 검색 결과는 오래됐거나 틀릴 수 있고, **웹 페이지의 글은 데이터지 지시가 아니다**(페이지에 숨은 지시로 모델이 조종되는 위험 — 도구 결과는 인용으로만 취급하고 모델이 행동을 바꾸지 못하게 막는다).
- 검색 공급자 · 비용 · 약관은 `[미확인]`(후보: 모델 공급자의 내장 검색 도구 · 별도 검색 API) — 정해야 한다. 호출은 **한도를 둔다**(하루 ○건 · 같은 대상은 몇 분 캐시).

## 「API 가 안 돌아도 된다」에 대한 정직한 답

**아니다 — 제보는 API 를 대신하지 못한다.** 이유 셋:
1. **규모**: 통계가 의미를 가지려면 같은 곳·같은 시간에 서로 다른 고객 여럿이 있어야 한다. 고객이 적은 초기에는 신호가 **거의 안 뜬다**(냉시동 문제). k 를 낮추면 거짓 신호가 늘어난다.
2. **사각지대**: 제보는 **고객이 있는 곳에서만** 생긴다. 고객이 없는 구간·새벽·아직 안 간 곳은 아무도 모른다 — 공식 소스가 필요한 이유다.
3. **신뢰**: 제보는 틀리거나 장난일 수 있다. 공식 소스로 **교차 확인**이 되어야 「확정」이 된다.

그래서 **API(확정) → 제보 신호(추정) → 웹 검색(참고)** 의 층으로 쌓는다. 제보가 쌓일수록 API 가 막힌 때의 공백이 줄고, 공식 알림이 안 올리는 현장 사정(긴 웨이팅 · 식당 마감 · 국지 혼잡)을 **보탠다**.

## 단계 제안

1. **개인정보 설계 확정 + 제보 받기(저장만)** — 신호는 아직 안 쓴다. 제보가 실제로 어떤 모양으로 모이는지 본다(통계 값을 짐작이 아니라 **측정**으로 정하려고).
2. **통계 신호 + 「제보 N건」 표시(참고용)** — 일정을 바꾸지 않는다.
3. **같은 조건 고객에게 추천(동의 후 변경)** — 신호가 믿을 만한지 2단계 관찰 뒤.
4. **웹 검색 대체 소스(참고 안내)** — 비용·약관을 정한 뒤.

## 확인하지 못한 것 · 위험

- 개인 위치 정보 관련 **법 본문**(동의 · 신고)을 읽지 않았다 — 공개 전 필수 `[미확인]`.
- 웹 검색 공급자 · 비용 · 약관 · 정확도 `[미확인]`. 이번에 검색 도구를 시험하지 않았다.
- k · 시간 창 · 가중 같은 숫자는 **우리가 정하는 값**이다 — 실제 제보량을 모으기 전에는 맞는 값을 모른다(1단계 이유).
- 제보 신호의 정확도(맞는 제보 비율)는 측정한 적이 없다 — 3단계에 가기 전에 공식 소스와 대조해 재야 한다.
- 이 계획은 **이동 · 감시 쪽**이 중심이다 — 식당 웨이팅 · 휴무 제보(요식 팀 영역)와 같은 표를 쓸지는 요식 담당과 정해야 한다.
