# 여행 대화와 고객 취향 통합 구현 계획

산을 좋아한다는 말을 자연스럽게 받아들이고, 고객이 허용한 취향을 다음 추천에 이어 쓰도록 설계합니다. 현재 일정·이전 일정·채팅·미응답 설문·고객의 일정 선택을 하나의 근거 체계로 모읍니다. **취향 저장과 일정 변경 허가는 별개입니다. “산이 좋아”만으로 현재 일정을 바꾸지 않습니다.**

| 할 일 | 상태 | 진행 |
|---|---|---|
| 다섯 입력 경로 조사 | 문서·코드 조사 완료 | 5/5 = 100% |
| 통합 기능 구현 | 이번 요청 범위 밖 | 0/5 경로 = 0% |
| 운영 반영 | 이번 요청 범위 밖 | 0/1 환경 = 0% |

작성일은 2026-10-12입니다. 독자는 제품 결정 담당과 채팅·추천·고객 웹·데이터 구현 담당입니다. 아래 설계는 **제안**이며 확정 wiki 계약이나 구현 완료 선언이 아닙니다. 담당은 이 채팅의 Codex, 검토는 자체 검토이며 독립 검토는 하지 않았습니다. 구현·SQL 적용·커밋·푸시·배포는 실행하지 않았습니다. 기존 산출물을 덮지 않고 새 파일로 작성했습니다.

## 1. 고객에게 보일 대화

**고객:** 여행 생각하니까 설렌다 ㅋㅋ 너는 바다랑 산 중에 뭐가 더 좋아?

**triPilot:** 여행 앞두면 괜히 들뜨죠 ㅎㅎ 산의 탁 트인 풍경도, 바다를 보며 쉬는 시간도 매력적이에요. 어느 쪽이 더 끌리세요?

이 질문은 여행 관련 잡담입니다. 상담 범위 밖이라고 막지 않습니다. AI가 실제 여행 경험이나 감각을 가진 것처럼 꾸미지 않으면서 대화를 잇습니다. 이때는 **고객 자신의 취향이 아직 밝혀지지 않았으므로 산·바다 선호를 저장하지 않습니다.**

**고객:** 난 산이 좋아.

장기 취향 저장을 켠 고객에게 저장이 성공한 뒤에는 다음처럼 답합니다.

**triPilot:** 산 풍경이 좋으시군요! 다음에 가볼 곳을 추천할 때 참고하도록 기억해 둘게요. 가볍게 경치를 보는 쪽과 걷는 코스 중에는 어느 쪽이 더 끌리세요?

바로 아래에 “기억한 취향: 산 풍경 선호 · 다음 여행에도 사용”과 **수정 / 삭제 / 이번 여행만 사용**을 제공합니다. 추가 질문은 고객이 대화를 이어가는 상황이거나 다음 추천에 답이 필요할 때 하나만 묻습니다. 지금은 등산 강도나 이동 수단을 임의로 채우지 않습니다.

장기 저장이 꺼져 있으면 “산 풍경이 좋으시군요! 이번 대화에서 추천할 때 참고할게요.”로 답합니다. 선택 기능인 “다음 여행에도 기억하기”를 제공하되 켜지 않아도 대화를 계속합니다. 저장 실패 시에는 “산 풍경을 좋아하시는군요. 취향을 저장하지 못했어요. 이번 답변에는 참고할 수 있어요.”라고 하며 기억했다고 약속하지 않습니다.

| 고객 발언 | 기록할 내용 | 기록하지 않을 내용 |
|---|---|---|
| 난 산이 좋아 | 본인 · 산 풍경 · 긍정 · 명시 발언 · 장기 허용 시 고객 범위 | 등산 선호·높은 강도·바다 싫음 |
| 너는 산 좋아? | 대화 질문만 처리 | 고객의 산 선호 |
| 친구가 산 좋아 | 이번 여행 동행인에 대한 전달 정보, 필요한 경우에만 사용 | 본인 취향·친구 계정의 장기 프로필 |
| 산은 좋은데 오늘은 피곤해서 등산 싫어 | 산 풍경 선호 + 오늘 등산 회피를 분리 | 산 선호 삭제·항구적인 등산 혐오 |
| 산 추천해 줘. 오늘 오후 일정은 뭐야? | 추천 요청과 일정 조회를 각각 처리 | 추천 요청을 일정 변경으로 실행 |

이후 고객이 “내일 갈 만한 곳 하나 추천해 줘”라고 하면 먼저 실제로 갈 수 있는 후보를 검증하고, 그 안에서 산 풍경과 맞는 후보를 앞에 둡니다. “산 풍경을 좋아한다고 말씀하셔서 이 후보를 먼저 보여 드렸어요”처럼 실제 사용한 근거만 설명합니다. 후보의 위치·영업·소요·경사 자료가 없으면 그 값을 지어내지 않습니다. **산 풍경 선호는 험한 등산 코스를 선택해도 된다는 허가가 아닙니다.**

## 2. 현재 기능과 추가할 기능

확인 범위는 로컬 작업 폴더의 현재 코드·SQL·고객 웹과 관련 wiki입니다. 미커밋 변경도 포함하므로 원격 커밋이나 배포판과 동일하다고 간주하지 않습니다. 코드 검색 뒤 실제 호출부를 읽어 쓰기→저장→읽기→추천 소비를 추적했습니다. DB 접속·실제 모델 호출·x600 서버 접속은 하지 않았습니다.

| 입력 경로 | 현재 확인한 동작 | 누락되거나 연결이 필요한 부분 |
|---|---|---|
| 현재 여행계획서 | 다른 활동의 분류를 세고 선택적으로 장소 평균 임베딩과 비교합니다. 같은 종류→비슷한 경험 후보가 부족할 때 취향 후보를 보충합니다 | 일정 작성자·자동 생성 여부·개인 선택 이유를 구분하고 고객별 근거로 모으는 경로 |
| 이전 여행계획서 | 고객이 가진 여행을 보관하고 조회할 기반은 있습니다. **같은 고객의 이전 로딩 설문 답 일부는 새 접수에 이어받습니다** | 이전 일정 자체의 취향 추출·중복 제거·만료·동행인 분리·장기 추천 소비 |
| 고객 채팅 | 여러 사실 질문과 잡담 응답을 구조화하는 로컬 코드, 최근 대화·직전 장소 문맥 기록이 있습니다 | 명시 취향을 출처와 범위별로 추출하고 고객별로 저장·정정·삭제·재사용하는 경로 |
| 모르는 부분만 설문 | 접수 답·해석 이력을 저장하고 등록 시 여행 설문으로 합칩니다. 질문 묶음·의미가 같은 이전 답을 이어받고 웹은 첫 미응답부터 보여 줍니다 | 일정·채팅·장기 취향을 함께 확인해 필요한 미지 항목만 질문하는 공통 판정 |
| 고객의 일정 수정·추가·삭제·선택 | 일정 버전·변경 이유가 있고 활동 기록 표도 있습니다. 활동 기록 호출은 조사 범위에서 재난 뒤 재개 선택에 연결돼 있습니다 | 편집 동작 전체를 취향 신호로 변환하고 삭제 이유·행위 주체·추천 노출을 구분하는 경로 |

추가로 마이페이지의 “여행 취향”은 현재 브라우저의 시작 설문 상태를 표시·수정합니다. 등록할 때 여행에 보내며, 다른 기기에서도 통합 취향을 읽는 고객별 DB 프로필과는 다릅니다. DB의 `customer_profiles`는 현재 연락 채널·복구 연락처 중심입니다. **설문 재사용까지 전혀 없다고 결론 내리면 틀립니다.**

현재 확인한 진입점·호출부에서는 다섯 경로를 모으는 통합 저장·수정·추천 경로를 확인하지 못했습니다. 다른 이름의 동적 연결, 실행 중 DB에만 있는 구조, 조사 이후 다른 채팅의 변경은 이 조사에서 놓칠 수 있습니다. 구현 착수 전에 최신 파일·스키마·배포판을 다시 확인합니다.

## 3. 문장 하나를 의미별로 나누는 정책

잡담/여행이라는 단일 라벨로 입력 전체를 버리지 않습니다. **한 문장의 대화 반응, 취향 진술, 사실 조회, 추천 요청, 변경 요청, 기억 관리 요청을 각각 추출**합니다. 특정 문장·장소 이름·키워드 목록을 추가하는 방식으로 해결하지 않습니다.

| 입력 유형 | 응답·기억 정책 | 실행 경계 |
|---|---|---|
| 여행 관련 잡담 | 감정·흥미에 짧게 응답하고 본인 선호가 있으면 근거 후보를 만듭니다 | 잡담만으로 일정 변경 없음 |
| 완전한 비여행 잡담 | 자연스럽게 짧게 응답합니다. 매번 여행으로 억지 전환하지 않습니다 | 영화 취향 등을 여행 취향으로 확대하지 않으며 장기 여행 기억에서 제외 |
| 잡담+일정 질문 | 잡담에 응답한 뒤 요청한 사실을 빠짐없이 답합니다 | 장소 문맥은 질문 부분에서 검증하고 무관한 잡담의 대상은 승계하지 않음 |
| 명시 취향+변경 요청 | 취향과 변경 의도를 분리하고 대상·범위를 확인합니다 | 실제 변경은 기존 일정 변경 경로·버전·권한·승인 규칙 사용 |
| 인용·가정·질문·비꼼 | 단정적 본인 선호로 저장하지 않습니다. 판단이 불명확하면 확인이 필요한 후보로 둡니다 | 불확실한 추출 결과로 쓰기 실행 없음 |
| 현재 질문에 대한 단답 | 직전의 검증된 질문이 본인 취향을 묻는 경우에만 “산” 같은 답을 연결합니다 | 문맥이 만료되거나 질문 대상이 다르면 추측하지 않음 |

추출기는 구조화된 결과를 냅니다. `social`은 짧은 대화 반응, `reads[]`는 각각의 사실 질문, `recommendations[]`는 추천 요청, `actions[]`는 명시 실행 요청, `preference_claims[]`는 취향 근거 후보, `memory_commands[]`는 기억 수정·삭제·거부입니다. 각 항목은 원문 구간과 연결합니다. 현재 `reads`·`social`을 확장하되 기존 단일 변경 계약에 임의로 여러 변경을 밀어 넣지 않습니다. 여러 변경이 섞이면 지원 범위에 따라 순서·대상을 확인합니다.

**모델은 의미를 제안하고 cs 프로젝트 앱이 검증합니다.** 고객·여행·일정 식별자, 동의, 원문 존재, 주체, 범위, 허용 취향 항목을 코드로 확인합니다. 원문에 없는 취향·부정·유효기간을 만들지 못하게 합니다. 다국어는 의미를 정규화하되 부정·주체·시제와 최소 원문 근거를 보존합니다. 신뢰도는 보정되지 않은 모델 확률로 표시하지 않고 `explicit / inferred`와 `high / medium / needs_confirmation`을 구분합니다.

“나는 산이 좋다”에서 산 풍경을 `prefer`로 둘 수 있어도 바다 `avoid`를 만들지 않습니다. “산을 좋아하는 건 아니다”는 선호 부정이지 반드시 산 금지가 아닙니다. “산 말고 바다로 바꿔 줘”는 해당 변경 요청의 선택이며 장기 산 혐오로 일반화하지 않습니다. “전에 산을 좋아했는데 이제 안 좋아”는 같은 취향 항목의 명시 정정입니다.

## 4. 다섯 경로를 하나로 모으기

다섯 경로가 모두 같은 근거 형식으로 들어오고, 저장 가능한 근거만 고객별 취향을 구성합니다. 개인화를 위해 모델 가중치를 학습하는 작업은 하지 않습니다. 고객마다 모델을 재학습하는 대신 확인된 기억을 추천 시 읽습니다.

| 경로 | 수집 시점·내용 | 강도와 오해 방지 |
|---|---|---|
| 현재 계획 | 접수 분석 또는 등록 완료 시 장소의 확인된 분류·경험 속성·고객 선택 여부 추출 | 외부 에이전트·패키지·자동 생성 일정은 약한 제안 근거. 방문 예정과 방문·만족을 구분 |
| 이전 계획 | 장기 사용 허용 후 본인 소유 여행만 작업 큐에서 읽고 현재 유효한 근거로 재구성 | 같은 여행의 여러 버전·같은 장소 반복으로 부풀리지 않음. 여행 종료가 만족 증거는 아님 |
| 채팅 | 인증된 고객 발언을 해석할 때 원문 구간·주체·긍정/부정·기간 확인 | 본인의 명시 발언이 우선. AI 답변과 AI가 만든 요약을 고객의 새 증거로 재수집하지 않음 |
| 미응답 설문 | 추천 소비자가 필요한 항목 중 유효한 명시 답이 없거나 충돌이 큰 항목만 질문 | 기존 답을 미리 채우고 확인·수정 제공. 약한 추정으로 필수 조건·안전 질문 생략 금지 |
| 일정 편집 | 수정·추가·삭제·제안 선택이 실제 저장된 뒤의 이벤트 | 고객 선택과 시스템 자동 교체 구분. 삭제만으로 싫어한다고 저장하지 않음. 이유가 시간·날씨·동행인인지 확인 |

“내가 고른 산책 장소 추가”는 선호 추정 근거지만 화면을 눌러 상세를 본 것은 취향 확정이 아닙니다. 시간만 옮긴 편집으로 장소 선호를 새로 만들지 않습니다. 고객이 추천 후보를 선택하면 어떤 후보들이 노출됐고 무엇을 골랐는지 남겨 선택 제약을 확인할 수 있게 합니다. 자동 추천→자동 채택→강한 취향 강화의 순환을 차단합니다.

## 5. 저장 구조와 우선순위 제안

### 원본 근거와 현재 취향을 분리합니다

기존 연락처 표에 자유 형식 JSON 하나로 모든 것을 섞지 않습니다. 새 저장 구조는 아래 네 역할로 나눕니다. 표·모듈 이름은 제안이며 SQL 번호는 다른 채팅의 변경과 대조한 뒤 배정합니다.

| 저장 역할·제안 이름 | 핵심 데이터 | 책임 |
|---|---|---|
| 근거 `travel_preference_evidence` | tenant·customer·subject·scope, 차원·값·극성, 출처·최소 원문 구간 참조, 시각·유효기간, 강도·상태 | 무엇을 근거로 판단했는지 추적. 일반 갱신은 추가 기록이며 삭제 요청은 실제 삭제·비식별 정책 적용 |
| 현재 취향 `travel_preference_current` | 고객·범위·차원별 선택 값·사용 근거 ID·충돌·revision | 추천이 빠르고 일관되게 읽는 파생 결과. 근거가 지워지면 재계산 |
| 기억 설정 `travel_preference_settings` | 장기 사용 여부·과거 자료 사용 여부·설정 버전·시각·수집 세대 번호 | 거부 이후 지연 작업이 옛 근거를 복원하지 못하게 제어 |
| 처리 상태 `travel_preference_jobs` | 원본 이벤트 키·처리 버전·상태·시도·실패 이유·설정 세대 | 중복 제거·재처리·삭제 경합 제어. 원문 전체를 작업 큐에 복제하지 않음 |

근거에는 최소한 `tenant_id`, `customer_id`, `subject_type`, `subject_ref`, `scope_type`, `trip_id/day/item_id`, `dimension`, `value`, `stance`, `explicitness`, `confidence_level`, `source_type`, `source_id`, `source_version`, `source_span`, `occurred_at`, `ingested_at`, `valid_from`, `expires_at`, `supersedes_id`, `status`, `extractor_version`, `consent_version`, `collection_generation`을 둡니다. 원문 참조가 접근 불가·삭제 상태면 추천 소비에서 제외합니다. 동행인은 이번 여행 내부 식별자로만 다루고 임의의 타인 계정에 연결하지 않습니다.

예를 들어 “난 산이 좋아”는 다음 의미입니다. 아래는 데이터 예시이며 실행 API가 아닙니다.

```json
{
  "subject_type": "self",
  "scope_type": "customer",
  "dimension": "landscape",
  "value": "mountain_scenery",
  "stance": "prefer",
  "explicitness": "explicit",
  "confidence_level": "high",
  "source_type": "chat_customer_turn",
  "source_span": "난 산이 좋아",
  "status": "active"
}
```

실제 저장은 동의와 저장 성공을 확인한 뒤 합니다. “오늘 피곤하다”는 같은 행을 덮지 않고 오늘 범위의 활동 강도·등산 회피 조건으로 별도 기록합니다. 피로를 질병·장애로 확대 추정하지 않습니다.

### 충돌 해결

1. 추천의 안전·운영·고객이 고정한 일정·명시 필수 조건을 먼저 적용합니다. 취향 점수로 통과시키지 않습니다.
2. 요청/일정/하루/여행에 한정된 명시 조건은 해당 범위에서 고객의 장기 선호보다 우선합니다. 범위가 끝나도 장기 선호는 남습니다.
3. 같은 주체·차원·범위에서는 고객의 최신 명시 정정이 이전 명시 값과 모든 추정값보다 우선합니다. 늦게 도착한 옛 자료가 정정을 되돌리지 못하게 원본 발생 시각·정정 연결을 씁니다.
4. 명시가 없으면 현재 고객 선택, 현재 계획, 과거 계획의 약한 신호를 출처와 유효기간에 따라 사용합니다. 약한 신호가 여러 개여도 명시적 반대를 뒤집지 못합니다. 구분이 안 되면 충돌 상태로 두고 필요한 순간에만 확인합니다.

`prefer`, `disprefer`, `avoid`, `neutral`, `unknown`, `forgotten`을 구분합니다. `unknown`은 고객 선호 정보의 부족이며 영업시간·위험 같은 필수 운영값을 모르는 상태와 다릅니다. 취향 정보가 부족하면 검증된 일반 추천을 제공할 수 있습니다. 일정에서 추정한 비선호로 장소를 강제 탈락시키지 않습니다. 고객이 이번 요청에서 명시한 `avoid`만 확인된 속성에 따라 제외합니다.

### 보존·삭제 제안

초기 추천값은 명시 장기 선호 365일 후 재확인, 약한 일정 추정 90일 후 만료, 여행 조건은 여행 종료까지, 오늘 조건은 해당 여행의 현지 날짜 끝까지입니다. **이 기간은 측정이나 확정 약관이 아니라 결정이 필요한 제안값입니다.** 기존 원본 보존기간이 더 짧으면 더 이른 시점을 따르고 사용 중이라는 이유로 기한을 조용히 연장하지 않습니다. 취향이 만료되면 일반 추천으로 돌아갑니다.

고객은 개별 기억 삭제, 특정 취향을 다시 추정하지 않기, 전체 기억 삭제, 장기 저장 끄기를 구분해 선택합니다. 삭제 시 근거·현재 값·요약·벡터·추천 캐시·대기 작업에서 제거합니다. 과거 자료에서 같은 값을 다시 가져오지 않도록 삭제 이전 자료의 재수집 경계를 기록합니다. “다시 추정하지 않기”는 내용 최소의 차단 설정이며 새 명시 입력으로만 해제합니다. 삭제된 취향의 원문을 삭제 감사 기록에 복사하지 않습니다.

여행 삭제 시 해당 여행 근거를 제거하고 고객 취향을 재계산합니다. 채팅·이전 계획이 삭제되어도 파생 취향만 남기는 기본값은 두지 않습니다. 다만 고객이 마이페이지에서 독립적으로 직접 입력한 취향은 그 자체가 원본이므로 여행 삭제와 구분합니다. 회원·게스트 삭제, 계정 연결, 백업 복원 시 삭제 기록 재적용도 구현 범위에 넣습니다.

## 6. 동의와 고객별 격리

[현행 동의 계약](../../external/rest-endpoints/web-auth.md)은 필수 둘과 선택 넷, 총 여섯 항목입니다. `service_improvement`는 서비스 개선용 이용이며 고객 개인화의 장기 기억 허용으로 대신 사용하지 않습니다. `sensitive`·`location`·`alert_channel`도 각각 목적이 다릅니다.

권장안은 **“다음 여행에도 취향 기억하기”를 기본 꺼짐인 독립 설정으로 제공**하는 것입니다. 이번 대화에서 쓰기, 이번 여행 동안 보관, 다음 여행까지 보관을 구분해 표시합니다. 장기 설정을 켜도 과거 여행을 일괄 분석하는 것은 별도 선택으로 둡니다. 실제 약관 항목·목적·기간 변경은 기존 동의 화면·문안·버전 검토 후 확정합니다. 이 계획이 기존 동의를 새 목적의 승인으로 해석하지 않습니다.

식사 제한·종교·건강·접근성 등 민감한 내용은 일반 취향 자동 기억에서 제외하고 기존 민감정보 동의·전용 입력 경로로 연결합니다. 추출 중 민감 내용이 보이면 확인용 대기 근거에도 원문을 복사하지 않습니다. 기존 동의 게이트가 꺼져 있어도 새 장기 기억 쓰기는 실제 허용 상태를 확인합니다. 민감정보 철회는 새로운 근거·파생 값·스냅샷·접수 복사본까지 제거하는 공통 정리기에 연결하고 경합 시험을 합니다. 안전성을 확인할 자료가 없는 음식점에 “안전하다”고 답하지 않습니다.

인증 문맥에서 tenant·customer를 정하고 모델이나 API 본문이 바꾸지 못하게 합니다. 모든 소유권은 읽기·쓰기·작업 실행 때 확인합니다. 여행 토큰을 가진 사람이 고객의 모든 과거 취향을 읽게 하지 않습니다. 게스트 자료를 회원으로 합칠 때도 검증된 기존 계정 연결 절차를 사용하며 이메일 문자열·장소 선택의 유사성으로 사람을 합치지 않습니다. 다른 고객·동행인의 취향은 모델 입력에서도 분리합니다.

## 7. 추천 소비와 일정 변경 경계

공통 `PreferenceContext`(추천 시 필요한 취향 묶음)를 한 번 만들고 일정 생성·재추천·접수 대안·활동/식당/이동 어댑터에 전달합니다. 각 소비자는 사용한 근거와 사용하지 못한 항목을 돌려줍니다. 공유 Core에 여행 도메인 어휘를 넣지 않고 travel_ops 안에서 구성합니다.

| 소비 경로 | 추가 연결 | 유지할 경계 |
|---|---|---|
| 새 일정 생성 | 기존 요청 선호·설문과 유효한 고객 취향을 합칩니다. 현재 키워드 기반 선호 해석은 의미 추출 결과를 받는 어댑터로 교체·이행합니다 | 명시 요청 조건·일정 검증 우선. 모델 정렬 뒤에도 최종 선택의 취향 근거와 제약을 재검증 |
| 접수 대안 후보 | 기존 같은 종류→비슷한 경험→취향 보충의 세 단을 유지하며, 고객 취향은 각 단 안의 허용된 동률·순위 기준과 셋째 단 후보 생성에 연결합니다 | 고객 취향으로 세 단 순서를 뒤집거나 기존 안전·거리·영업 규칙을 건너뛰지 않음 |
| 감시·변경 제안 | 기존 후보 검증·비교 계약을 유지하고 명시된 허용 순위 자리에만 취향 근거를 추가합니다 | 기존 사전식 비교와 충돌하는 변경은 소비자별 계약 검토 없이 넣지 않음 |
| 채팅의 추천 요청 | 권한 확인→현재 조건+취향 읽기→검증된 후보 추천→이유 표시 | “추천”은 실제 일정 적용과 분리 |
| 사실 조회 | 취향을 쓰지 않고 일정·조회 자료로 답합니다 | “몇 시에 가?”의 정답을 선호로 바꾸지 않음 |

초기에는 산 풍경처럼 **후보 자료에서 확인 가능한 속성**부터 연결합니다. 속성이 없는 후보를 LLM 상식만으로 산·힐링·친절함으로 표시하지 않습니다. 분류·장소 설명 임베딩은 후보의 유사성을 보조할 수 있지만 주체·부정·동의·만료를 판정하지 않습니다. 확인되지 않은 속성은 추천 이유에서 빼고 `unsupported_dimensions`로 노출합니다.

응답의 개인화 설명에는 `profile_revision`, `evidence_ids`, `applied_dimensions`, `unsupported_dimensions`, `ranking_version`을 보존합니다. 고객 문장에는 필요한 요약만 보여 줍니다. 개인정보가 섞인 원문이나 동행인의 발언을 이유 카드에 노출하지 않습니다. 실제 순위가 변하지 않았으면 “이 취향으로 더 알맞게 바뀌었다”고 말하지 않습니다.

선호 정정은 다음 추천부터 반영합니다. 이미 진행 중인 생성·선택은 적용 직전에 최신 설정·취향 revision을 확인하고 오래된 결과면 재검증합니다. 명시 변경 요청, 감시 사건, 고객이 직접 누른 선택만 기존 변경 실행 경로로 갑니다. `ask_first`, `customer_pinned`, 업체 거래 승인, CAS(동시 변경 충돌 검사), 멱등 키, outbox 중복 방지를 그대로 적용합니다.

## 8. API와 화면 제안

아래 경로와 필드는 **새 계약 제안**입니다. 현재 API로 호출할 수 있다는 뜻이 아닙니다. 기존 `/profile` 연락처 응답과 최근 채팅 `focus`를 장기 기억 저장소로 재사용하지 않습니다.

| API 제안 | 요청·결과 요지 |
|---|---|
| `GET /v1/web/preferences?scope=…` | 본인 취향·명시/추정·출처 요약·범위·만료·충돌·revision 반환 |
| `POST /v1/web/preferences` | 고객 직접 입력. 허용 차원·값·범위와 요청 ID 검증. 본문 customer_id로 권한 변경 불가 |
| `PATCH /v1/web/preferences/{id}` | 값·극성·범위 수정. `If-Match`로 revision 확인. 정정 근거를 추가하고 현재 값 갱신 |
| `DELETE /v1/web/preferences/{id}` | 개별 삭제와 재수집 방지 처리. 완료 전에는 `deleting`, 읽기·추천에서는 즉시 제외 |
| `GET/PUT /v1/web/preference-settings` | 장기 기억·과거 자료 사용 설정 조회·변경. 끄기와 삭제는 효과를 각각 명시 |
| `POST /v1/web/preferences/forget` | 전체 삭제 또는 다시 추정하지 않을 항목 지정. 확인 화면 이후 실행하고 처리 결과 반환 |
| 기존 `/messages` 응답 확장 | 선택적 `memory_updates[]`에 저장 성공/이번 대화만/확인 필요/저장 실패 표시. 일정 변경 결과와 분리 |
| 기존 접수 조회·설문 확장 | `needed_questions[]`, `known_answers[]`, `question_set_revision`을 추가하고 구형 `questions[]`를 이행 기간 유지 |

요청 ID로 동일 쓰기를 한 번만 처리하며, 충돌은 409, 형식 오류는 422, 타인 대상은 기존 소유권 계약에 맞춘 404를 사용합니다. 동의·기억 설정 변경과 쓰기는 같은 고객 잠금/세대 검사를 사용합니다. 기억 삭제가 실패하면 성공으로 응답하지 않습니다. 장기 저장 장애가 기존 사실 조회를 막지 않게 하되 개인화 미적용 상태를 명확하게 알립니다.

개인 에이전트 API와 MCP는 같은 소유권·저장 정책을 쓰도록 다음 단계에서 계약을 설계합니다. 임의의 고객 취향 읽기 도구를 추가하지 않습니다. 쓰기 도구는 기존 MCP 쓰기 기본 꺼짐을 유지하며 등록·scope·시험을 함께 검토합니다. 웹 API만 먼저 열어 놓고 개인 에이전트가 다른 정책으로 기억하게 하지 않습니다.

화면은 다음 세 곳으로 묶습니다.

1. **채팅:** 자연스러운 답변 아래 저장한 취향 요약과 수정·삭제·범위 변경. 확인 필요 상태는 저장 완료처럼 표시하지 않습니다.
2. **마이페이지:** 내가 말한 취향과 일정에서 추정한 취향을 출처별로 표시하고 범위·최근 시각·만료를 볼 수 있게 합니다. 직접 추가, 정정, 개별·전체 삭제, 장기 저장 거부를 제공합니다. 다른 기기에서도 본인 인증 후 동일하게 읽습니다.
3. **접수·추천 화면:** 아는 답은 미리 보여 주고 부족한 질문만 묻습니다. 질문 목록은 세션 시작에 고정해 진행 숫자가 튀지 않게 하고, 이미 답한 항목을 다시 편집할 수 있게 둡니다. 후보에는 실제 사용한 추천 이유를 붙입니다.

기존 브라우저 설문은 자동으로 장기 기억에 올리지 않습니다. 고객에게 확인받아 항목 의미·범위를 보존하며 가져옵니다. 로컬 설문과 접수 상속 답과 새 기억이 충돌하면 최신 명시 입력을 우선하고 출처를 보여 줍니다. 기억을 지운 뒤 브라우저에 남은 옛 설문이 다음 등록에서 되살리지 않도록 설정 세대·이행 상태를 함께 동기화합니다.

## 9. 구현 순서와 마이그레이션

각 단계는 앞 단계의 수용 기준을 충족한 뒤 켭니다. 소요 일수는 현재 실측 근거가 없어 확정하지 않습니다. 실제 구현 전 다른 채팅의 공유 파일 변경과 SQL 번호를 다시 대조합니다.

| 단계 | 구현 내용 | 완료 증거 |
|---|---|---|
| 1 계약·평가 자료 | 대화 분해·다섯 입력·범위·동의·삭제·소비자 순위 계약 확정, 여행 문장 평가 자료 작성 | 계약 담당 검토 기록, 정답·판정 기준·개발/holdout 분리 |
| 2 저장·수정·삭제 | 근거·현재 값·설정·작업 표와 공통 저장/조회/정리기, 본인 취향 API | 격리·동시 수정·멱등·삭제 경합·SQL 재실행·복구 시험 |
| 3 명시 채팅·설문 | 의미 추출, 저장 결과 응답, 질문 필요 판정, 기존 설문 상속 연동 | 단일·복합·다국어·부정/인용/동행인 시험, 실제 모델 평가 |
| 4 일정·편집 근거 | 현재/이전 일정 어댑터, 고객 편집 이벤트, 과거 자료 선택적 수집 | 버전 중복 제거·자동 변경 제외·삭제 이유·지연 작업 폐기 시험 |
| 5 추천·화면·제한 공개 | 소비자별 취향 읽기와 이유, 마이페이지·채팅·설문 UI, 관측 후 제한 활성화 | 새 여행·새 기기·정정·삭제 후 추천 재생, 화면·실서버 검증 |

마이그레이션은 새 표를 추가하는 방식으로 시작합니다. 기존 연락처·Case·설문 표의 의미를 바꾸거나 삭제하지 않습니다. 복합 tenant/customer 소유권, 범위별 유효 키, 원본 이벤트+추출 버전의 중복 방지 키, 근거 출처 조회 색인을 둡니다. 작업 큐는 쓰기 트랜잭션에서 함께 등록하거나 기존 outbox와 연결해 일정 변경은 성공했는데 신호가 영영 사라지는 간격을 없앱니다.

처음에는 읽기와 쓰기를 각각 설정으로 끄고, 합성 여행 자료에서 저장·정리 경로를 검증합니다. 다음으로 장기 기억을 허용한 고객의 새 명시 입력부터 저장하고, 과거 자료는 별도 허용을 받은 범위에서만 처리합니다. 동의 철회·삭제와 같은 잠금·세대 번호를 확인한 뒤 작업을 반영합니다. 완료된 작업의 재실행은 근거를 늘리지 않습니다.

추천 연결은 사용 근거를 먼저 관측하는 단계와 실제 순위를 바꾸는 단계를 구분합니다. 읽기만 관측하는 단계에서도 허용된 자료만 사용합니다. 활성화 전에 기존 결과와 차이가 어떤 조건에서 생기는지 재생 평가합니다. 문제가 나면 개인화 읽기·수집을 끄고 검증된 일반 추천을 유지하며 새 표를 즉시 지우지 않습니다. 삭제·철회 요청 처리기는 계속 작동해야 합니다. DB 변경의 파괴적 되돌리기는 별도 승인 대상으로 둡니다.

주요 작업 위치는 [대화 구성요소](../../../app/domains/travel_ops/components/conversation/), [고객 구성요소](../../../app/domains/travel_ops/components/customer/), [접수 구성요소](../../../app/domains/travel_ops/components/intake/), [일정·계획 구성요소](../../../app/domains/travel_ops/components/planning/), [고객 웹](../../../frontend/apps/web/src/features/), [DB 변경 파일](../../../app/infrastructure/db/migrations/)입니다. 이름·번호가 확정되지 않은 신규 모듈을 이미 존재하는 파일로 표시하지 않습니다.

## 11. 확정이 필요한 세 가지

사용자에게 즉시 답을 요구하지 않고 구현 전 검토 안건으로 남깁니다. 이 문서 작성의 완료를 막는 항목은 아닙니다.

| 결정 | 권장안 | 선택에 따른 차이 |
