# 텔레그램으로 알림 받기 — 백엔드 요청 (웹 화면은 이 계약대로 연결한다)

작성: ui 세션(웹) · 2026-10-05 · 대상: cs 백엔드 세션 · ★이 문서는 **계획서**다. 서버 코드는 고치지 않았다. 사용자가 「텔레그램만 붙여」(2026-10-05)라고 했고, 범위는 「**알림만 하는 걸로 하자**」(답장으로 수정·소통하는 기능은 이번에 안 한다)로 정했다.

## 위층 — 한 번 읽고 알 수 있게

**결론.** 고객이 마이페이지에서 「텔레그램으로 연결」을 누르면 텔레그램 앱이 열리고, 「시작」을 한 번 누르면 연결된다. 그 뒤 일정이 바뀔 때마다 우리 봇이 그 고객의 텔레그램 대화로 알림을 보낸다. 디스코드 웹훅과 같은 알림 문구·같은 발송 규칙을 쓰고, 바뀌는 것은 「알림이 닿는 길」뿐이다.

**고객이 보는 것(4단계).** ① 마이페이지 「텔레그램으로 연결」 ② 텔레그램이 열려 우리 봇 채팅창이 뜸 ③ 「시작」 한 번 ④ 봇이 「연결됐어요」라고 인사하고, 웹 마이페이지에 「연결됨」이 뜸.

**정한 것(사용자 2026-10-05).**
1. **알림만.** 고객이 봇에게 글을 써도 수정·질문을 처리하지 않는다. 고정 문장으로 「알림 전용이에요, 수정은 웹에서 해 주세요」와 안내를 답한다(모델 호출 없음 — 접점은 둘로 유지하는 2026-09-10 결정과 비용 상한을 지킨다).
2. **알림 받는 곳은 한 번에 한 곳**(디스코드·텔레그램 중 고객이 **마지막에 연결한 곳**). 같은 알림이 두 곳으로 가지 않는다. 기존 디스코드 연결(웹훅 직접 넣기 · 「디스코드로 연결」)도 연결하는 순간 그곳이 알림 받는 곳이 되도록 맞춘다. 고객은 마이페이지에서 다시 바꿀 수 있다.
3. **봇은 운영용 하나 + 시험용 하나**(사람이 만든다 — 아래). 시험 알림이 고객에게 나간 사고(2026-09-22, 8건)를 막으려고 `allowed_tenants` 규칙을 텔레그램에도 똑같이 적용한다.

## 계약 (웹이 호출하는 모양 그대로)

모든 오류는 기존 `{"error": {"code", "message"}}`.

### 프로필 응답에 더하는 칸 (`GET/PUT /v1/web/profile` 과 `…/discord/test` 응답의 `profile` 모두 같은 모양으로)

```
"telegram_connect": {"available": true},
"telegram": {"connected": false, "status": null, "connected_at": null},
"notice_channel": "discord" | "telegram" | null
```
- `telegram_connect.available` — 봇 설정이 서버에 있을 때만 `true`. 없거나 `false` 면 웹은 텔레그램 줄을 **통째로 숨긴다**(가짜 단추 없음).
- `telegram.status` — `ok`(시험 메시지/발송이 닿음) · `untested`(연결만 됨) · `blocked`(고객이 봇을 차단해서 알림이 닿지 않음) · `null`(연결 안 됨).
- `notice_channel` — 지금 알림이 가는 곳. 둘 다 없으면 `null`.
- 이 칸들은 디스코드 칸(`discord_webhook`, `discord_connect`)과 **같은 읽기 함수**로 읽히므로 응답마다 빠짐없이 싣는다.

### 호출

| 호출 | 인증 | 하는 일 |
|---|---|---|
| `POST /v1/web/profile/telegram/connect/start` | 세션 + CSRF | 서버가 **일회용 코드**(무작위 · 사용자에 묶음 · 수명 10분 · 한 번만 · 해시로 저장)를 만들어 `{"link": "https://t.me/<봇 아이디>?start=<코드>", "expires_at": "…"}` 를 준다. 봇 설정이 없으면 404 `not_found`. 한도: 사용자당 시간당 10번(초과 429 `too_many_requests` + `Retry-After`). ★코드는 텔레그램 규칙상 **64자 이하**이고 `A-Z a-z 0-9 _ -` 만 쓴다(공식 문서에서 64자 확인) |
| `POST /v1/telegram/webhook` | **없음**(텔레그램이 부른다) — 헤더 `X-Telegram-Bot-Api-Secret-Token` 이 서버 비밀값과 **같을 때만** 처리(상수 시간 비교), 아니면 401 | 텔레그램이 업데이트를 보내는 곳. 아래 「업데이트 처리」. 처리가 끝나면(실패해도) 빠르게 200 — 텔레그램은 200 이 아니면 같은 업데이트를 다시 보낸다 |
| `POST /v1/web/profile/telegram/test` | 세션 + CSRF | 연결된 대화로 시험 메시지 한 줄. `{"result": "ok"\|"blocked"\|"rate_limited"\|"failed", "profile": {…}}` — 디스코드 시험과 같은 모양. 연결이 없으면 409 `no_telegram`, 너무 자주면 429 `too_soon` |
| `DELETE /v1/web/profile/telegram` | 세션 + CSRF | 연결 풀기: 대화 번호를 지운다 → 200 `{"profile": …}`. 알림 받는 곳이 텔레그램이었으면 디스코드가 있으면 디스코드로, 없으면 `null` |
| `PUT /v1/web/profile` `{"notice_channel": "discord"\|"telegram"}` (기존 호출에 칸 하나) | 세션 + CSRF | 알림 받는 곳 바꾸기. 연결되지 않은 곳이면 422 `channel_not_connected` |

### 업데이트 처리 (`POST /v1/telegram/webhook`)

| 텔레그램이 보낸 것 | 서버가 하는 일 |
|---|---|
| 개인 대화의 `/start <코드>` 메시지 | 코드가 맞고 유효하면 그 사용자에게 **대화 번호(`chat.id`)를 묶고** `notice_channel="telegram"` 으로 하고 `status="untested"`. 봇이 답한다: 「텔레그램이 연결됐어요. 이 채팅은 알림 전용이에요 — 수정은 웹이나 여행계획서 링크에서 해 주세요.」 ★`[2026-10-05 cs 세션 확인]` 지금은 일정 변경 알림이 고객이 저장한 채널로 **나가는 길 자체가 서버에 없어서**(바깥함 일꾼은 운영자 채널 하나로만 보낸다) 인사말에 「앞으로 일정이 바뀌면 알려 드릴게요」 같은 **약속을 넣지 않는다.** 발송 길이 생기면 그때 문장을 더한다 |
| 코드가 틀림 · 만료 · 이미 씀 | 봇이 답한다: 「연결 시간이 지났거나 이미 쓴 링크예요. 웹 마이페이지에서 다시 눌러 주세요.」 |
| 그 텔레그램 대화가 **다른 사용자에게 이미 묶여 있음** | 묶지 않고 답한다: 「이 텔레그램은 이미 다른 계정에 연결돼 있어요. 그 계정에서 연결을 풀고 다시 해 주세요.」(소셜 로그인의 `already_linked_elsewhere` 와 같은 원칙 — 합치지 않는다) |
| 그 밖의 글(`/start` 만, 질문, 사진 …) | 고정 문장으로 답한다: 「알림 전용 봇이에요. 일정 수정과 질문은 웹이나 여행계획서 링크에서 해 주세요.」 ★**모델을 부르지 않는다.** 글 내용은 저장하지도 로그에 남기지도 않는다 |
| `my_chat_member`(고객이 봇을 차단/해제) | 개인 대화에서는 차단·해제할 때만 오는 업데이트다(공식 문서). 차단이면 `status="blocked"` — 발송은 「보낸 것으로 기록하지 않고」 실패로 올린다. 해제면 `untested` |

### 알림 발송

- **같은 알림 문구**(`phrase_of` · 고객 언어로 옮기기 · `[재생]` 표시 · 링크 줄)를 `sendMessage` 로 보낸다. **서식(parse_mode) 없이 평문**으로 보내 특수문자 때문에 깨지지 않게 한다.
- 규칙은 `DiscordWebhook` 과 같다: 전송 성공만 `delivered` · 시간 초과/연결 끊김은 `unknown`(자동 재전송 없음) · 한도(429)는 텔레그램이 알려 준 시각에 다시 · 설정이 없으면 **실패로 올림**(조용한 성공 위장 금지) · 운영 테넌트만(`allowed_tenants`).
- **받는 곳은 `notice_channel` 이 정한다.** 발송기는 알림 한 건을 한 곳으로만 보낸다(여러 곳 동시 발송은 이번 범위가 아니다).
- 한도(공식 FAQ): 한 대화에 **초당 1건 이하**, 한꺼번에 보내도 초당 약 30건. 유료 대량 발송은 쓰지 않는다.

## 보안 (필수)

1. **웹훅 비밀값** — `setWebhook` 의 `secret_token`(1~256자, `A-Z a-z 0-9 _ -`)을 정하고 요청마다 확인한다. 틀리면 아무것도 하지 않는다. 주소 경로에 봇 토큰을 넣지 않는다.
2. **일회용 코드** — 서버가 만들고 해시만 저장 · 10분 · 한 번만. `start` 는 사용자에 묶는다(남의 코드를 써도 코드를 만든 사용자에게 묶일 뿐이라 공격자는 자기 계정에 자기 텔레그램을 묶을 뿐이다 — 디스코드 연결과 같은 이유).
3. **저장하는 것** — 대화 번호(`chat.id`)·연결 시각·상태뿐이다. 텔레그램 이름·사용자명·전화·프로필 사진은 받아도 **저장하지 않는다**. 대화 번호는 웹훅 주소와 같은 방식으로 암호화해 둔다(응답에는 가린 모양도 주지 않는다 — 「연결됨」만).
4. **봇 토큰** — 환경 파일에만 둔다. 로그·오류·응답·문서·커밋에 쓰지 않는다. 새는 일이 있으면 BotFather 에서 폐기하고 새로 받는다.
5. **공개 주소** — 웹훅은 HTTPS 이고 포트는 443·80·88·8443 만 가능하다(공식 문서). 이 문서에는 서버 주소를 적지 않는다.
6. 메시지 본문은 **텔레그램 쪽에 남는다**(고객의 대화 기록). 알림에는 민감한 값(결제 정보 등)이 이미 들어가지 않지만, 변경 사실과 링크만 담는 규칙을 지킨다.

## 사람이 해야 하는 설정 (서버 코드로 못 한다)

텔레그램 앱에서 @BotFather 와 대화해 **봇 두 개(운영 · 시험)** 를 만들고 각 토큰을 서버 환경 파일(git 밖)에 넣는다. 따라 하기 안내: [2026-10-05_텔레그램_봇_만들기_안내.md](2026-10-05_텔레그램_봇_만들기_안내.md). 환경변수 이름은 서버 세션이 정한다(제안: `ACOP_TELEGRAM_BOT_TOKEN` · `ACOP_TELEGRAM_BOT_USERNAME` · `ACOP_TELEGRAM_WEBHOOK_SECRET`). 웹훅 등록(`setWebhook`)은 공개 HTTPS 주소가 있어야 하므로 배포 뒤에 운영 스크립트로 한다. 로컬에서는 공개 주소가 없으니 `getUpdates` 로 받는 시험 도구나 업데이트를 직접 넣는 시험으로 대신한다.

## 완료 기준 (시험 예)

- 한 바퀴: `start` → (시험 도구가 `/start <코드>` 업데이트를 웹훅에 넣음) → 프로필 `telegram.connected=true`, `notice_channel="telegram"`, 봇이 인사말을 보냄(가짜 텔레그램 서버로 확인).
- 같은 코드 두 번 → 둘째는 「이미 쓴 링크」 답 · 11분 뒤 → 만료 · 비밀 헤더가 없거나 틀림 → 401 이고 아무것도 안 바뀜.
- 다른 사용자에게 묶인 대화로 시도 → 묶지 않고 안내 답.
- 알림만: 아무 글이나 → 고정 문장, **모델 호출 0회**, 글 내용이 DB·로그에 없음.
- `my_chat_member` 차단 → `status="blocked"`, 발송은 실패로 올라가고 `delivered` 로 기록되지 않음. 해제 → `untested`.
- 발송: 같은 문구 · 평문 · `[재생]` · 운영 테넌트만 · 429 는 텔레그램이 알린 시각에 다시 · 설정 없으면 실패.
- `DELETE` → 대화 번호 삭제, 알림 받는 곳이 디스코드로(있으면) 또는 `null`. `PUT notice_channel` → 연결 안 된 곳은 422.
- 디스코드를 연결하면 알림 받는 곳이 디스코드로 바뀐다.
- 봇 토큰·대화 번호·일회용 코드 평문이 DB·로그 어디에도 없다.

## 확인하지 못한 것

- 공식 문서 페이지 요약으로 **확인한 것**: `/start` 링크 인자 64자 · 웹훅 포트 4개와 `secret_token` 규칙 · 개인 대화의 `my_chat_member` 는 차단/해제 때만 옴 · 봇 메시지 무료 · 한 대화 초당 1건 · `/newbot` 으로 봇 생성. **확인 못 한 것**: `sendMessage` 본문 길이 한도(흔히 4096자로 알려져 있다 — 구현 때 공식 문서로 확인), 한도 초과(429) 응답의 대기 시간 칸 이름, 차단된 대화로 보낼 때의 정확한 오류 문구(403 이라고 알려져 있다 — 구현 때 확인).
- 「고객이 먼저 시작해야 봇이 메시지를 보낼 수 있다」는 규칙은 흔히 알려져 있으나 이번에 읽은 공식 페이지 요약에서는 확인하지 못했다. 이 설계의 「시작」 단추가 바로 그 행동이다.
- 한국 고객의 텔레그램 사용률은 조사하지 않았다(카카오톡이 더 흔하다 — 알림톡은 사업자 등록·비용이 필요해 이 프로젝트의 「무료」 조건 밖이라고 알고 있으나 이번에 확인하지 않았다).

## 전제 확인 `[2026-10-05 cs 세션]`

서버 세션이 확인한 사실: 바깥함 일꾼(`scripts/run_outbox_worker.py`)은 `trip.notice` 를 **운영자 채널 하나(전역 웹훅)** 로만 보내고, 고객이 저장한 디스코드 웹훅을 읽어 보내는 코드는 없다. 알림 payload 에 고객 번호가 없고 `trip_id` 만 있어 「여행 → 고객 → 알림 받는 곳」을 찾는 길도 새로 필요하다. 그래서 이 요청서의 「같은 발송 규칙 · `notice_channel` 이 정한다」는 **발송 길이 먼저 만들어져야 성립한다.** 범위는 사용자에게 물어 정하는 중이다 — 정해지기 전까지 서버 코드는 시작하지 않고, 웹은 이 계약대로 mock 서버 시험을 유지한다.
웹 화면은 그동안 **알림이 간다고 약속하지 않는다**: 연결·시험 메시지가 닿는지만 말하고, 일정 변경 알림은 「준비 중」이라고 쓴다(디스코드 줄의 기존 안내와 같다).
