# 여행 날짜·시각 오인과 장소 교체 보호

작성일: 2026-10-12 (KST)  
담당·자체 검토: 이 대화의 Codex  
독립 검토: 미실시  
운영 반영: 미확인

## 결론

두 결함이 겹쳤다. 일정 입력 해석기는 “지금 당장”을 접수 시각으로 해석하지 않아 시간이 없는 항목에 하루 첫 일정 기본 시각을 넣을 수 있었다. 채팅 실행 경로는 변경 요청의 대상 범위를 검증하지 않고 모델이 고른 `apply_change`를 장소 교체 실행기로 전달했다. 따라서 “시간을 지금으로 바꿔”가 장소 교체로 분류되면 실제 일정의 장소가 바뀔 수 있었다.

## 확인 범위와 한계

- 코드에서 일정 입력 경로(`pipeline.process` → `read_source` → `label_lines` → 날짜·시각 조립)와 채팅 경로(`decision_unit.decide` → `trip_messages` → `case_dispatch.execute`)를 확인했다.
- 로컬 DB에서 해당 대화에 해당할 만한 남부터미널·소망탑 기록을 찾지 못해 당시 모델의 원 출력·Case 이벤트·변경 전후 일정을 확인하지 못했다. 따라서 사용자가 겪은 구체적인 분류 결과는 로그 증거가 아니라 코드 경로와 설명을 대조한 원인 추정이다.
- 이 수정은 로컬 코드와 단위 시험에만 반영했다. x600 서버의 cs 프로젝트 서버나 고객 화면에서 재현·반영 확인은 하지 않았다.

## 수정

### 1. “지금”을 접수 순간으로 해석

접수 행의 `received_at`을 처리 시작 시 확보해 KST 시점으로 정규화하고, 일정 줄 모델이 “지금·현재·당장”을 시각 조각으로 가리키면 그 시점의 날짜와 시각을 함께 사용한다. 장소 이름과 관계없이 표현의 종류를 처리하며, 후속 처리 대기 시간에 따라 현재 시각이 바뀌지 않도록 접수 시각을 기준으로 삼는다. 해당 해석은 확인 화면에 접수 시각 기준 값으로 표시할 수 있게 근거 메모를 남긴다.

기존에는 이 표현이 날짜·시각 정규식에 없었다. 그래서 시각 없는 일정은 날짜가 잡힌 경우 식사 시각·앞 일정 뒤·하루 첫 시각 등의 기본값으로 채워질 수 있었다. 그 기본값이 “지금”의 해석 결과처럼 보일 수 있는 구조였다.

### 2. 채팅 변경 범위에 실행 차단 추가

모델 출력 계약에 변경 범위(`place`, `time`, `date`, `mixed`, `none`, `unclear`)를 추가했다. 장소 교체·대체 후보 동작은 범위가 `place`인 경우에만 실행기로 전달한다. 시간·날짜·복합·불명확 요청을 장소 교체로 분류하면 서버에서 실행을 중단하고, 일정 변경이 적용되지 않았으며 채팅에서 시각·날짜 수정은 지원하지 않는다고 안내한다.

이는 장소·시간·날짜별 단어를 일정 ID나 특정 문장에 묶어 둔 규칙이 아니라, 모델의 작업 분류와 별도로 변경 대상 차원을 출력하게 하고 서버가 실행 직전에 계약을 검사하는 경계다. 다만 같은 모델이 변경 범위까지 잘못 판단해 `place`라고 내면 이 한 번의 판정만으로 막지 못할 수 있다. 별도 평가에서 오분류가 관측되면 독립 판정 또는 확인 질문 계약을 추가 검토해야 한다.

## 검증

실행 명령:

```powershell
python -m pytest tests/unit/travel/test_intake_resolve.py tests/unit/travel/test_decision_target_guard.py -q
```

집중 시험 결과: **54/54 통과 = 100%**. 접수 시각이 KST 2026-10-12 11:07일 때 “지금 당장”이 같은 날짜와 `11:07`로 해석되는 사례, 시간 변경 요청이 장소 교체 실행에 들어가지 않는 사례를 추가했다. 분모는 두 시험 파일에서 실행된 전체 시험 수다.

확장 시험 명령:

```powershell
python -m pytest tests/unit/travel/test_intake_resolve.py tests/unit/travel/test_decision_target_guard.py tests/unit/travel/test_read_requests.py tests/unit/travel/test_schedule_query.py tests/unit/travel/test_fact_read_recovery.py -q
```

결과: **136/137 통과 = 99%**, 나머지 1건은 시험 자체 실행 전 공통 fixture가 NumPy를 불러오는 과정에서 `MemoryError`로 준비되지 않았다. 실패한 동작 assertion은 없었다. 이후 집중 시험을 다시 실행해 **54/54 통과 = 100%**를 재확인했다. pytest 종료 때 Windows Python 콘솔 정리 경고도 출력됐으나 집중 시험 결과는 성공이었다.
