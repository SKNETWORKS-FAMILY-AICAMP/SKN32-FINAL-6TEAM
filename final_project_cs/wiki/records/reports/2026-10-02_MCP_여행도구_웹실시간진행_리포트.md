# MCP 여행 도구 · 웹 실시간 진행(SSE) 리포트 (2026-10-02)

## 결론

개인 AI(Claude · ChatGPT · Cursor)가 **사용자 본인의 여행**을 다루는 MCP 서버를 새로 만들어 고객 API 앱의 `/mcp/` 에 붙였고,
웹의 오래 걸리는 일(채팅 · 일정 짜기 · 접수 읽기)이 **서버·모델이 멈춰도 사용자에게 상태를 알리도록** 실시간 진행(SSE) 서버 코드를 만들었습니다.
화면(프런트)이 SSE 를 쓰는 부분은 ui 세션 몫이라 아직 안 됐습니다. 외부 AI(Claude · ChatGPT)의 종단 접속 기록은 아직 없습니다.

## 1. MCP

**발견.** 옛 MCP 도구 3개(`app/presentation/api/mcp.py`, 쇼핑몰 Case 도구)는 **띄우는 곳이 한 번도 없었다** — 코드 파일 이력 전체(모든 브랜치)에서
`streamable_http_app` · `sse_app` · `mcp.run(` · `mount("/mcp` · `mcp_app` 모두 0건, sample 저장소 0건, 실행 설정 0건(2026-10-02 실측).
이 방법이 놓칠 수 있는 것: 누가 손으로 `mcp run` 을 띄우고 적지 않은 경우. 그리고 그대로 띄웠다면 **보안 구멍**이었다 — 호출 주체가 고정(`mcp:read`)이고 `customer_id` 를 호출자가 인자로 정해 **남의 문의를 읽을 수 있다.** "안 띄워서 안전한" 상태였다.

**왜 새로 만들었나.** 사용자 지시 「없으면 네가 만들어야 하는 부분 아니냐, 경쟁사 MCP 를 참고해 우리 프로그램에 맞게」. 경쟁 서비스(Wanderlog 31개 · Tripsy · Trvlrr · Trip Planner)는 전부 「AI 가 일정 내용을 편집」하는 CRUD 도구다. 우리는 일정을 **검증하고 지켜보고 틀어지면 고치는** 서비스라 도구도 그 동사다. 코덱스 의논(2회차)은 「결함이냐」에 B(기능 결함 아님, 문서 불일치는 결함)로 합의했지만, 사용자가 만들기로 정해 이 합의는 **만들지 말라는 근거가 아니다** — 합의가 막았던 것은 「호출자 인증 없이 그냥 띄우기」였고 새 설계는 그것을 먼저 푼다.

**설계.** 상세는 [mcp-tools.md](../../external/mcp-tools.md). 핵심만:
- **MCP 는 새 규칙을 만들지 않는다.** 모든 도구가 웹 API(`/v1/web/*`)를 그대로 부르는 얇은 어댑터 — 인증 · 소유 확인 · 멱등 · 남용 방어 · 판정이 한 곳이다.
- **호출자는 사용자 키가 정한다**(`Authorization: Bearer` 또는 `X-User-Key`). 도구 인자에 `customer_id` 가 없다. 키 없음·틀림은 연결 단계에서 401, `mcp` 모듈 토글은 요청마다 보고 끄면 404.
- 읽기 5(여행 목록 · 일정 · 알림 · 제안 · 등록 형식) · 쓰기 7(말 걸기 · 신고 · 다른 안으로 · 제안 고르기 · 되돌리기 · 검증받고 등록 · 서버가 일정 짜기). **쓰기는 `travel.mcp.write_enabled` 가 켜졌을 때만 등록**(기본 꺼짐 — 「MCP 는 read-only」 원칙, CLAUDE.md §0.2). 켜도 바뀌는 것은 일정뿐이고 되돌릴 수 있다.
- 전송 둘: 원격 Streamable HTTP(`/mcp/` · `/mcp`, 무상태, 앱 생명주기에 세션 관리자) · 로컬 stdio 프록시(`python -m app.modules.travel_ops.mcp_server`).
- 웹 쌍둥이 신설: `POST /v1/web/trips/{id}/reports` · `…/items/{item}/alternate` — 에이전트 입구와 **같은 처리**(공용 함수로 뺌), 본인 여행만. MCP 의 구조화 도구가 모델을 안 거치도록.
- 구조: presentation 은 도메인을 import 하지 못해(INV-CS-ARCH-001) 조립이 만든다(`composition.build_mcp_surface`).

**검증.** `tests/e2e/test_mcp_server.py` 15건 — MCP 프로토콜로 **실제 접속**(initialize → 도구 호출). 읽기 전용 기본 · 키 401 · 모듈 끄면 404 · 남의 여행 404 · 웹과 같은 답 · 같은 request_id 중복 방지 · 바꾸기→되돌리기 판 번호 · 키 원문이 오류에 없음. 실제 서버(uvicorn)에도 SDK 클라이언트로 HTTP 접속해 `/mcp/` · `/mcp` 둘 다 열림, 키 없이는 401 을 확인했다(시험용 사용자는 지웠다).

**한계 `[미확보]`.** 외부 개인 AI 의 종단 접속 기록 없음 · OAuth 미구현(헤더 키 방식 — OAuth 만 받는 클라이언트는 못 붙는다) · 쓰기 도구 전용 호출 한도 없음(웹 남용 방어 `message` 를 그대로 씀) · `tripilot_plan_trip` 은 운영에서 사람 확인(Turnstile)이 켜지면 403 으로 막힐 수 있다 · 서버 쪽 SSE 를 MCP 진행 알림으로 잇지 않았다(ASGI 내부 호출은 응답을 모아 돌려준다).

## 2. 웹 실시간 진행(SSE)

**문제.** 채팅 · 일정 짜기는 끝날 때까지 아무것도 안 보이는 호출이라, 원격 모델이 식었거나(첫 채팅 34초) SSH 터널이 끊기면 사용자는 요청이 받아졌는지 · 어디서 기다리는지 · 서버가 죽었는지 알 길이 없었다. 변경 초인종(`trip_events.py`)은 「일정이 바뀜」 신호만 흘려 이 문제를 못 풀었다.

**해법.** 상세는 [rest-endpoints.md](../../external/rest-endpoints.md) 「웹 실시간 진행 (SSE)」. 새 경로를 늘리지 않고 `POST …/messages` · `POST …/trip-intakes/{id}/plan` 에 `Accept: text/event-stream` 을 붙이면 SSE, 안 붙이면 JSON. 접수 읽기만 `GET /v1/web/trip-intakes/{id}/events` 신설. 이벤트 `accepted`(첫 신호) · `stage`(서버가 **실제로** 들어간 단계만 — 지어낸 진행률 없음) · `beat`(3초, **일꾼이 막혀도 이벤트 루프가 낸다**, 모델 대기가 8초 넘으면 `slow`) · `result`(JSON 과 같은 본문) · `error`(시간 초과 · 거절 이유 · `retryable`).
- 연결이 끊겨도 일은 끝까지 돌고 응답 뒤 일(분류 기록)은 **정확히 한 번**(일꾼과 흐름이 서로 누가 끝내는지 모르는 경주를 잠금으로 풀었다). 같은 `request_id` 는 두 번 처리되지 않는다.
- 접수 읽기를 뒤에서 하던 일꾼이 서버 재시작으로 죽으면 갱신이 180초 멈춘 것을 보고 `error{stalled}` — 영원히 「읽는 중」으로 두지 않는다.
- 서버 자체가 죽은 경우는 서버가 알릴 수 없다 → **화면이 `beat` 를 6초(2번) 못 받으면 「연결 끊김」**(ui 몫).

**검증.** `tests/e2e/test_op_stream.py` 21건 — 첫 신호 · 단계 · 막힌 일꾼의 beat · `slow` · 시간 초과 후에도 일꾼 완주 · 거절 이유와 모르는 예외의 원문 숨김 · 끊김 뒤 응답 뒤 일 한 번 · 일정 짜기 SSE 가 JSON 과 같은 본문 · 이미 등록된 판 즉시 · 남의 것 404 · 열린 연결 상한 429 와 반납 · 읽는 일꾼 사망 `stalled`.

- 이 작업 중 **로컬 DB 가 꺼져 있었다**(Windows 메모리 부족으로 보임, 이 작업과 무관) — 다시 켰다. `test_trip_events.py::test_a_change_after_connecting_sends_a_signal_with_no_content` 는 시간에 민감해 3번 중 1번 실패했다(기존 불안정, 이번 변경과 무관 — 연결이 1.6초라 알림 기록이 한 틱 늦으면 놓친다).
