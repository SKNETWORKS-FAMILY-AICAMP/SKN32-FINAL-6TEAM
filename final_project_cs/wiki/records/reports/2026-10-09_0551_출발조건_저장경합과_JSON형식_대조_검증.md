# 출발 안내 계산과 저장 사이 여행 조건 변경을 검출

일정 판이 그대로여도 안내 계산 뒤 인원이나 조건이 달라졌으면 이전 안내를 저장하지 않도록 고쳤습니다. 저장 직전 같은 여행 행 잠금 아래 계산 입력과 현재 입력을 대조합니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 최종 이동 회귀 시험 | 통과 | 823/823 = 100% |
| 포함 관련 조건 | 통과 | 30/30 = 100% |
| 신규 로컬 개발 DB 조건 | 통과 | 8/8 = 100% |

생성 시각: 2026-10-09T05:51:43.200778+09:00. 분모는 최종 코드 판으로 실행한 시험 조건 수입니다. 관련30건·신규8건은823건의 부분집합이며 합산하지 않습니다. 수정 전 소스25개·자료4개는 직전 근거와 일치했습니다. 최종 회귀 시작~출판 사이 변경대상6개 SHA-256이 일치했습니다. 제품 준비율·독립 경로 정확도와 다릅니다.

## 재현과 원인

수정 전 인원/휴식 조건 변경2/2조건에서 문구를 계산한 뒤 별도 DB 연결로 여행 입력만 바꿨습니다. 일정 판은1로 유지됐고 이전 안내가 저장됐습니다. 기존 잠금은 일정 판과 이동 항목만 검사했으므로 최신 조건 대조가 계산 때 성공했더라도 저장 직전 변경을 검출하지 못했습니다.

운영 TripReminders는 최신 여행을 읽고 party_size와 전체 constraints의 분리 사본을 만듭니다. 출발 안내 저장은 이 사본을 선택 인자로 받아 같은 tenant/trip 행을 FOR NO KEY UPDATE로 잠그고 현재 DB 값과 IS NOT DISTINCT FROM으로 비교합니다. 달라지면 StaleDeparture를 반환하고 기존 stale 집계로 셉니다. 사본을 안내 payload나 외부 메시지에 넣지 않습니다. 다른 종류 안내와 사본 없는 저수준 직접 호출은 기존 계약을 유지하므로 모든 호출의 보호를 주장하지 않습니다.

전체 조건 대조이므로 무관한 예산 변경도 한 번 저장을 보류할 수 있습니다. 다음 반복은 최신 여행 입력으로 다시 계산하고, 실제 재경로 필요 여부는 기존 이동 정규화 대조가 맡습니다. 현재 위치/탑승을 추정하지 않았고 경로·시간·요금 상수를 추가하지 않았습니다.

## 중간 결함과 최종 검증

첫 수정은 Python 사전 동등 비교를 써 True와 숫자1을 같게 처리했습니다. 계산 입력 사본의 first_visit=true와 현재 DB 값 first_visit=1을 대조한 추가1/1조건에서 보류가 실패했습니다. 이 형식 시험의 사본은 직접 만든 통제 입력이며 운영 계산기를 거쳐 얻은 값은 아닙니다. 공개 전에 DB JSONB의 형식 구분 비교로 고쳤습니다. 수정 전2건과 중간1건의 실패 로그를 각각 보존하며 중간 회귀와 목표 시험을 최종 통과 수에 합산하지 않습니다.

신규8조건은 계산 뒤 인원/조건 변경2, 분리 사본과 JSON 키 순서2, 실제 두 연결의 잠금 대기2, 다른 안내 종류 호환1, 논리값/숫자 구분1입니다. 두 연결에서 pg_stat_activity의 Lock 대기를 확인했습니다. 조건 갱신이 먼저 커밋되면 옛 안내를 거절하고, 안내 저장이 먼저 커밋되면 이후 조건 갱신이 가능합니다. 저장 후 조건 변경까지 차단하거나 배달 전 재확인한다고 주장하지 않습니다.

모든 DB 조건은 격리된 시험 여행과 통제된 문구 공급을 사용했습니다. 고객 화면·운영 설정 API를 통한 조건 변경, 현재 모델의 실제 운행 정확도 검증은 아닙니다. 인원/조건 변경 뒤 다음 반복의 저장은 확인했으나 새 계산 경로가 정확한지는 직전 별도 조건 대조 시험과 독립 운행 검증을 구분합니다.

## 논문·공식 문서 확인과 적용 전제

[Berenson 등의 SQL 격리 수준 연구](https://www.microsoft.com/en-us/research/publication/a-critique-of-ansi-sql-isolation-levels/)의 공식 초록을 오늘 확인했습니다. 격리 수준 이름만으로 구현의 보장을 단정하지 않고 실제 교대 실행으로 확인한다는 검증 원칙을 적용했습니다. 논문 본문 전체를 검토하거나 우리 구현의 형식적 증명을 한 것으로 부르지 않습니다.

[PostgreSQL 트랜잭션 격리](https://www.postgresql.org/docs/16/transaction-iso.html)와 [행 잠금](https://www.postgresql.org/docs/16/explicit-locking.html)에서 대기 뒤 현재 행을 검사하는 전제를 확인했습니다. [NULL 포함 비교](https://www.postgresql.org/docs/16/functions-comparison.html)와 [JSONB 비교](https://www.postgresql.org/docs/16/functions-json.html)는 형식과 값을 DB에서 비교하는 근거입니다. 이 문서의 잠금 보장을 서울 운행 성능 수치로 바꾸지 않습니다.
