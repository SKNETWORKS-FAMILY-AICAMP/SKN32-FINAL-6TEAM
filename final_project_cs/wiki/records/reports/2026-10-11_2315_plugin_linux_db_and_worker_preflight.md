# 최소 후보 v5의 Linux DB 연결·worker·기존 화면 호환 검증

작성 시각: 2026-10-11 23:15 KST. 시험 대상은 보존된 최소 후보 v5이며, 실제 운영 프로세스 교체는 하지 않았습니다. 독립 검토에서 일정 복원 호출의 인자 불일치가 추가로 발견되어 이미지 제작과 후보 확정을 보류했습니다. 아래 시험 통과는 해당 경로까지 검증한 뜻이 아닙니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| Linux Controller·DB 시험 | 통과 | 10/10 = 100% |
| Linux 채팅 HTTP·DB 시험 | 통과 | 3/3 = 100% |
| 실행 중 필수 담당 불가 후 재시도 | 통과 | 1/1 = 100% |
| API 기준 사본 일치 | 확인 | 404/404 = 100% |
| worker 기준 사본 일치 | 확인 | 404/404 = 100% |

| 운영 새 프로세스 기능 확인 | 미실행 | 0/1 = 0% |

## 실제로 검증한 범위

기존 운영 이미지와 이미 보유한 PostgreSQL 17.11 이미지를 사용해 별도의 일회용 앱·DB를 만들었습니다. 새 내부 전용 Docker 네트워크만 연결했고 호스트 포트를 열지 않았습니다. 운영 DB·환경값·볼륨은 연결하지 않았습니다. 루트 파일은 읽기 전용, 합성 DB와 전달한 소스는 tmpfs에만 저장했습니다. 실행 사용자를 낮추고 CPU·메모리·프로세스 수를 제한했습니다. 이미지 내려받기·패키지 설치·운영 재시작은 하지 않았습니다.

DB에는 보존한 기준 사본의 SQL 85개를 적용했으며, 자료는 합성 여행 일정만 생성했습니다. Controller 경로에서는 답변 원문 전달, 같은 답변의 중복 실행 방지, 담당 중단 시 입력 보존, 재활성 후 한 번 적용, 실행 중 구성 교체 후 이전 요청의 단일 적용을 검사했습니다. 채팅 HTTP 경로에서는 되묻기 후 같은 업무 재개, 일정·적용 기록의 중복 방지, 인증된 기존 화면 요청처럼 토큰·Case ID·예상 버전을 생략한 답변 재개를 검사했습니다.

일반 업무 재개 API의 동적 의존 경계도 별도로 확인했습니다. 담당 자체는 실행 가능하지만 실행 중 다른 필수 담당이 꺼져 있음을 발견하면 HTTP 503을 반환하고 실패 실행을 남깁니다. 이때 답변은 이미 접수됐고 일정은 바뀌지 않았습니다. 필수 담당을 다시 활성화하고 **같은 요청 ID·답변·토큰·예전 예상 버전**으로 재전송하자 저장한 답변으로 완료됐습니다. 다시 전송해도 입력 이벤트 1개, 답변 이력 1개, 일정 변경 1개였습니다. 담당 자체가 실행 전부터 불가하면 기존 관문에서 입력·토큰을 소비하지 않는 경우와 구분합니다. 특정 도메인 사이에 고정 의존성을 추가하지 않았습니다.

고유 시험은 14개입니다. 첫 실행의 Controller 10개와 토크나이저 보완 뒤의 HTTP 3개, 동적 의존 시험 1개를 합했습니다. 같은 시험의 재실행 횟수를 더하지 않았으며 Windows 327개 및 앞선 Linux 175개와 합산해 전체 성능으로 부르지 않습니다.

처음 HTTP 2개는 토크나이저 어휘 파일이 없는 격리 환경에서 외부 다운로드가 차단되어 실패했습니다. 설치된 tiktoken 소스가 지정한 공식 공개 어휘 파일 1개를 별도 취득하고 SHA256 `223921b76ee99bde995b7ff738513eef100fb51d18c93597a113bcffe865b2a7`과 대조했습니다. 이를 명시한 임시 캐시에만 넣고 외부 연결을 다시 닫은 상태로 재검증했습니다. 어림 토큰 계산이나 계산 함수 대역으로 바꾸지 않았습니다. 해당 파일은 패키지·모델 가중치·운영 데이터가 아닙니다.

준비 단계 실패와 최초 HTTP 실패 로그를 보존했습니다. 모든 6회 실행의 임시 컨테이너·네트워크 잔존 수는 0이었습니다. v5 제품 파일 50개와 기준 사본 404개의 SHA256이 그대로임을 재확인했습니다. 신규 동적 의존 시험만 작업 트리에 추가했고 v5 제품 후보는 수정하지 않았습니다.

## 운영 worker와 기존 화면의 읽기 전용 대조

API·worker의 이미지 ID, 기준 파일 404개, 지정 패키지 8개, worker 시작 스크립트 해시, 공개 Team 활성 선언이 일치했습니다. 두 프로세스의 환경변수 **이름** 72개도 일치했습니다. 값은 수집하지 않았습니다. 두 컨테이너의 마운트는 이동 자료 읽기 전용과 운영 산출물 저장 공간이며, 소스·설정의 별도 덮개 마운트는 확인되지 않았습니다. 이 결과는 현재 같은 기준 위에 후보를 적용할 수 있음을 뒷받침하며 새 프로세스 기동 성공을 대신하지 않습니다.

이동 자료 설정은 양쪽 모두 비어 있지 않고 디렉터리가 존재했습니다. 각각 필수 8개 파일이 있고 명세 기반 크기·해시 검사가 통과했습니다. 실제 설정값·자료 경로·키는 내보내지 않았고, 기존 엔진을 다시 적재하거나 지도 API를 호출하지 않았습니다. 따라서 자료 사전 조건은 충족하지만 실제 새 구성의 이동 계산 성공은 반영 후 별도 확인합니다.

운영 화면의 공개 정적·렌더링 빌드 249개를 읽었습니다. `case_status`는 4회, `waiting_input`·`resume_token`·`expected_version`은 각각 0회였습니다. 채팅 코드는 같은 여행의 메시지 API에 `request_id`와 `message`를 다시 보내며 응답의 `answer`를 먼저 표시합니다. 후보의 인증된 자동 재개 시험은 이 요청 형태로 통과했습니다. 필드 출현만으로 화면 전체 동작을 보장하지 않으며, 운영 브라우저에서 실제 고객 답변을 재생한 E2E는 하지 않았습니다.

## 실제 적용과 롤백 절차 — 아직 미실행

1. 독립 검토의 확정 결함을 새 후보에서 해결한 뒤 후보 파일 해시와 제외 목록을 다시 고정합니다. 기존 운영 이미지 ID, API·worker 시작 설정, 기존 두 YAML 파일의 해시와 복구 사본을 함께 보존합니다. 비밀 환경값을 공개 문서나 빌드 문맥에 넣지 않습니다.
2. 검증한 기존 이미지 위에 명시한 후보 변경 파일만 더해 고유 새 이미지로 만듭니다. 패키지·시작 명령·필수 기존 자산 상속과 파일 해시를 확인합니다. API와 worker는 **같은 후보 이미지**를 사용해야 하며 SQL은 변경하지 않습니다. 기존 전체 작업 트리를 복사하지 않습니다.
3. 운영 교체가 별도로 승인되면 API·worker를 함께 새 프로세스로 교체합니다. 구성 버전, 실제 대기·답변 재개, 담당 부재의 거절과 입력 보존, 재활성 후 동일 답변 한 번 적용, worker 다음 회차와 초기화 상태를 확인합니다. 상태 응답 하나만으로 기능 완료라 판단하지 않습니다.
4. 기동·대기 재개·중복 방지·worker 회차 중 하나라도 실패하면 새 요청 유입을 제한하고 API·worker를 기존 이미지로 함께 복구합니다. 두 YAML도 기존 사본으로 함께 되돌립니다. 이번 후보는 SQL 무변경이므로 DB 역변환은 없습니다. 이미 정상 반영된 고객 일정은 무조건 되돌리지 않고 적용 기록을 확인해 별도로 처리합니다.

실제 실행 명령과 운영 위치는 git에서 제외된 비공개 실행계획에만 보존합니다. 위 절차를 적었다는 것이 운영 교체·재시작 승인을 받았거나 실행했다는 뜻은 아닙니다.
