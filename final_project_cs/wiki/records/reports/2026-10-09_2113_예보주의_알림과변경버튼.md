# 예보 주의 알림과 일정 변경 버튼

예보를 주의로 유지하면서 고객에게 주의 문구와 「예보에 맞게 일정 변경」 버튼을 함께 제공하도록 로컬 구현했다. 일정은 후보를 선택한 뒤에만 바뀐다. 운영 배포는 하지 않았다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 처리 흐름·기존 알림·DB 변경 회귀 | 통과 | 88/88 = 100% |
| 기존 감시·예보 판정 | 통과 | 29/29 = 100% |
| mock 서버 화면 시험 | 통과 | 3/3 = 100% |
| 웹 타입 검사 | 통과 | 1/1 = 100% |

## 동작과 범위

- 활동 항목의 예보 강수확률·풍속이 주의 기준에 도달했을 때 알린다. 점검 결과의 `verdict=clear`, `advisories` 분류는 유지한다. 기존 감시 대상 시간 범위도 그대로다. 모든 예보 수치를 경고하는 것은 아니다.
- 안내에는 실제 입력된 강수확률·풍속과 원래 일정이 유지된다는 문장을 넣는다. 같은 트랜잭션에서 빈 후보의 보류 제안을 만든다. 자동 변경을 선택한 고객도 예보 주의만으로 일정을 바꾸지 않는다.
- 변경 버튼은 기존 선택 API에 `key=change`를 전송한다. 동의한 뒤 기존 활동 후보 계산·점검으로 대체안을 보여 주고, 고객이 후보를 고른 뒤 기존 일정 변경 경로로 새 판을 저장한다. 유지·무응답·후보 없음은 원래 일정 유지다.
- 같은 여행·항목·기준 버전의 예보는 한 번만 알린다. 확정 사건이 생기면 열린 예보 제안은 `superseded`로 닫는다. DB 변경 059로 예보와 확정 사건의 중복 방지 범위를 분리했으므로 예보 유지 응답이 뒤의 기상특보·안전 제안을 막지 않는다. 기존 확정 사건 제안이 있으면 예보 제안을 새로 열지 않는다.
- 고객 외부 알림 꺼짐·미연결이면 앱에서 제공한다. 발송 조건을 충족하면 기존 고객 채널로 안내와 여행 링크를 보낸다. 실제 변경 버튼은 앱에서 누른다. 개발용 디스코드는 운영 리포트용이다.
- 식사·이동·숙박의 새 예보 변경 기능, 운영 배포, 운영 알림 재발송은 포함하지 않았다.

## 검증과 재현

mock 서버 시험 3/3 (화면 반응): 예보 주의 문구·버튼 동시 노출, 외부 발송 `skipped` 상태에도 표시, `key=change` 전송과 후보 표시, 후보 선택 후 변경 응답, 기존 실내외 동의·후보 없음 흐름.

실서버 확인 (서버 응답): 안 했음 — x600 서버의 cs 프로젝트 서버에는 배포하지 않았다. 백엔드는 로컬 개발 DB와 재생 점검 입력을 사용하고, API는 시험 클라이언트로 호출했다. 외부 공공 API와 실제 고객 메신저에는 발송하지 않았다.

```powershell
python -m pytest tests/e2e/test_forecast_advisory.py tests/e2e/test_indoor_unknown_consent.py tests/e2e/test_notice_routing.py tests/integration/db/test_migrations_rerun.py -q
```

[원문 로그](../evidence/2026-10-09_2113_forecast_advisory/backend.txt): 88 passed, 98.68초. 새 시험은 예보 안내·동의·선택·반복·유지·확정 특보 우선·조회 실패·실내 활동 제외·기본 감시·무응답 만료를 확인한다. DB 재실행 시험은 임시 DB에서 모든 이유를 가진 행을 보존한 채 반복 적용한다.

[추가 검사 로그](../evidence/2026-10-09_2113_forecast_advisory/adjacent.txt): 기능 시험 29/29 통과. 같은 실행에 포함한 기존 결함 문서 상태 검사 107개 중 96개 통과·11개 실패(표기 누락·중복). 이번 수정 대상 외의 문서이며 해당 파일들은 수정하지 않았다. 이 결과를 기능 시험 통과와 혼동하지 않는다.

화면 시험은 프로젝트 지원 Node 24와 이미 설치된 Edge로 실행했다. 기본 Chromium 설치가 없어 첫 시도가 브라우저 실행 전에 실패했고, 공유 `.next-live` 폴더를 재사용한 시도에서는 실제 브라우저 요청이 별도의 mock 포트로 가는 것을 trace로 확인했다. 시험 실행기의 `LIVE_DIST_DIR` 선택을 추가하고 독립된 빌드 폴더로 다시 빌드하여 검증했다. `tsconfig.json`에 빌드가 자동으로 넣은 이번 작업용 경로 두 줄은 제거했다.

```powershell
$env:STUB_PORT='8149'
$env:LIVE_PORT='3199'
$env:LIVE_DIST_DIR='node_modules/.cache/forecast-live-2113'
$env:PLAYWRIGHT_CHANNEL='msedge'
node node_modules/@playwright/test/cli.js test -c playwright.live.config.ts tests/live/trip.spec.ts -g '예보 주의|실내·야외를 모르는|바꿔 줘.*다른 곳이 없으면'
```

[최종 화면 시험 로그](../evidence/2026-10-09_2113_forecast_advisory/web_isolated.txt): 3 passed, 28.0초. [타입 검사](../evidence/2026-10-09_2113_forecast_advisory/typecheck_after.txt): 종료 코드 0. 최초 타입 검사에서 백업 사본을 소스처럼 읽은 오류는 백업 확장자를 `.bak`로 바꿔 해결했다. 초기 실패 로그도 같은 evidence 폴더에 보존했다.
