# 채팅 실패 읽기 전용 진단

최근 채팅은 요청과 답변이 저장됐지만, 요청을 해석하는 모델 연결이 끊겨 실패 안내가 돌아왔다.

| 확인 | 상태 | 진행 |
|---|---|---|
| 실행 서비스 | 실행 중 | 5/5 = 100% |
| 최근 실제 채팅 | 실패 단계 확인 | 2/2 = 100% |
| 모델 상태 읽기 | 연결 실패 확인 | 2/2 = 100% |

## 근거와 확인 범위

- 사용자가 다른 채팅에서 요청한 공개 채팅 중단의 읽기 전용 진단을 진행했다. 배포 사본 코드 기준은 `bf42b659`다.
- 최근 30분 메시지 POST 200 응답 2건, 대화 GET 200 응답 9건이다. 응답 코드만으로 상담 성공을 판정할 수 없다.
- 최근 2시간 채팅 2건 모두 `escalated`이며 고객 2턴·답변 2턴이 저장됐다. 저장된 답변 2건 모두 해석 모델 응답 오류 안내다.
- cs 프로젝트 서버의 모델 상태 GET `/api/ps`, `/api/tags` 모두 `ReadError`였다. 추가 분류는 `Connection reset by peer`다. 어느 중간 연결이나 모델 프로세스가 끊었는지는 확정하지 않았다.
- 현재 해석 클라이언트는 `OllamaChat`, 모델은 `gemma4:12b`다. 자동 전환 설정은 꺼짐이며 배포용·개인용 대체 API 키는 미설정, 대체 모델 주소는 0개로 확인했다. 키 값이나 연결 주소는 조회 출력에 노출하지 않았다.
- 최근 60분 API·worker 로그의 실제 ERROR·Traceback·실행 실패 검색에서는 해당 오류를 확인하지 못했다. 초기 32건은 정상 집계의 `errored:0`도 포함한 검색 건수여서 오류 건수로 사용하지 않는다.

## 복구 판단

cs 프로젝트 서버에서 GPU 서버까지의 연결·포워딩과 모델 서비스 상태부터 복구해야 한다. 이 근거만으로 프론트엔드 수정이나 새 코드 푸시를 복구 방법으로 정할 수는 없다. 연결 문제만이면 복구·확인까지 10~20분 **예상**이며, GPU 기계나 모델 서비스 자체 장애라면 추가 확인 전에는 완료 시간을 추정하지 않는다.

이번 범위는 점검이다. 실제 고객 메시지 전송·모델 생성 호출·운영 설정 변경·재시작·배포는 하지 않았다. 신규 전송부터 최종 화면까지의 전체 재현은 수행하지 않았다.

mock 서버 시험: 안 했음.

실서버 확인 (서버 응답): 했음 — 실행 상태, 기존 채팅 저장 기록, 읽기 전용 모델 상태 조회.
