# 자동 출발 안내에 현재 관측을 조립하고 로컬 DB 경로를 확인했습니다

저장 당시 소요만 읽던 자동 안내 실행기에 현재 구간 재검증을 연결했습니다. 정확 승차 위치의 버스 도착 소스를 기존 캐시·호출 예산 아래에서 부르고, 현재 일정의 장소와 목표 시각으로 결과를 검증합니다. 실제 배포 고객 안내와 늦음 일정 재조정은 아직 확인하지 않았습니다. 생성 시각 2026-10-09T01:59:05.565589+09:00.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 조립·소스·로컬 DB·기존 구성 시험 | 통과 | 44/44 = 100% |
| 확대 기본 회귀 시험 | 통과 | 649/649 = 100% |
| 기존 웹 원자료 보존 확인 | 일치 | 6/6 = 100% |
| 늦음의 실제 일정 재조정 | 남음 | 0/1 = 0% |

44는 두 번째 실행의 시험 수다. 첫 번째50/50에는 이전 판정기 검사가 함께 들어가 있고 두 번째44는 조립/DB/기존구성으로 범위가 다르다. 확대 실행도 겹치므로 합산하지 않는다. 분모는 해당 실행한 시험 수이며 실운행 정확도·준비율이 아니다. 직전 코드9/9바이트 해시를 먼저 확인한 [기준 확인](../evidence/2026-10-09_0147_출발알림_관측조립/baseline-check.json)과 [원 실행 로그·JUnit·정확 명령·코드/자료 해시](../evidence/2026-10-09_0147_출발알림_관측조립/)를 보존했다.

## 연결과 실패 동작

[조립](../../../app/composition.py)은 기존 이동 기동과 따릉이 호출 한도 문을 하나의 함수로 공유한다. 단독 출발 작업이 이동 계산기를 아직 올리지 않았다면 설정으로 올리고, 이미 올린 상태의 게이트를 다시 덮지 않는다. 원 소스의 boardable_arrival에 캐시나 호출 예산을 우회하는 별도 HTTP를 만들지 않았다. 키가 없어 버스 소스가 없으면 unavailable 근거를 남기고 현재 모델로 다시 검사한다.

[자동 안내 실행기](../../../scripts/run_sweepers.py)가 이 콜백을 TripReminders에 넣는다. [팀 끼움 자리](../../../app/domains/travel_ops/components/team_hooks/legs.py)로 [이동 팀 재검증](../../../app/domains/travel_ops/instances/mobility/wiring.py)을 부르므로 필수 부품이 팀 내부를 직접 import하지 않는다. 공개 TeamTask/TeamResult·core_routes 계약은 그대로다.

[현재 일정 입력 변환](../../../app/domains/travel_ops/components/watch/departure_revalidation.py)은 이동 전후의 비이동 방문 항목과 현재 DB 장소 좌표를 읽는다. 저장 좌표가 바뀌었으면 needs_replan이다. 현재 장소/인접 방문/저장 구간이 빠져도 재경로 대상으로 보류하며 옛 ETA로 성공을 만들지 않는다. 이 좌표는 계획 장소이며 고객의 실제 GPS 위치나 실제 탑승 관측이 아니다. 예외는 유형만 보존한 fatal로 보고하며 비밀을 포함할 수 있는 원 예외 문자열을 고객 근거에 싣지 않는다.

[신선도 설정](../../../config/guardrails.yaml)의 공급나이90초·미래폭2초는 잠정 운영 정책이다. 수신 캐시 상한은 기존30초 설정과 같다. 값이 빠지거나0/음수/문자열/NaN/불리언이면 정책 검사에서 거절한다(미래폭0은 허용). [GTFS 공식 권장](https://gtfs.org/documentation/realtime/realtime-best-practices/)이 내부 자료 나이와 응답 갱신을 구분한다는 원칙을 참고했다. 서울 API의 SLA·예측 오차 보장이 아니며 운영 반복 관측으로 임계값 적합성을 더 확인해야 한다.

## 실행 근거와 확인 범위

실제 SeoulBusArrival 어댑터에 HTTP 응답을 주입해 조립된 콜백을2회 호출했고 동일 노선 응답의 HTTP1회를 확인했다. 실제 노선을 새로 호출한 실험은 아니다. 정확 순번5를 유지하고 첫째3분 차량을 제외해 둘째7분 차량을 선택했다. 접근6+대기1+승차3+이탈2=예상12분인 고정 입력이다. 이 값이 실제 로컬 개발 DB에 저장한 구간→인접 방문 장소→조립된 이동 계산기→바깥함 payload로 이어졌다.

실제 로컬 개발 DB 시험의10회 tick에서는 도착 관측1회·바깥함 발행1회였다. 예측을24분 뒤로 늦춘 입력은 held1·발행0이었다. 첫50/50, 확대 조립·로컬 DB44/44·경고1·6.49초·종료코드0과 최신 확대 회귀 결과를 원문으로 보존했다. live/mobility_full 표시 검사는 이번 확대에서 제외했다. Ruff와 변경 diff 공백 검사 통과다. 일부 실행의 기존 AST 경고·pyreadline 종료 정리 오류는 원문에 남겼다.

mock 서버 시험: 수행하지 않음. 실제 소스 어댑터에 응답을 주입한 시험이며 mock 서버를 띄우지 않았다.
실서버 확인(cs 프로젝트 서버 응답): 안 했음. 로컬 개발 DB 바깥함 확인이며 배포된 cs 프로젝트 서버의 알림 전송을 확인하지 않았다.

이번 추가 외부 교통 API·지도 개발자 API·새 웹 경로 수집·외부 메시지 전송·커밋·푸시·배포는0회다. 새로운 독립 실제 운행 검증 표본은0건이며 기존 원자료6/6은 해시가 같다. 논문의 해외 성능 수치를 우리 성능으로 옮기지 않았다. [직전 문헌 등록부v5](assets/2026-10-09_mobility_research_v5/research-register.json)와 이번 [공식 문서 재확인](../evidence/2026-10-09_0147_출발알림_관측조립/research-check.json)은 읽은 범위와 적용 전제를 구분한다.

## 남은 작업·시각화·백업

[21기능 시각화v11](assets/2026-10-09_mobility_readiness_v11/mobility-readiness.html)에 실제 코드 조립/로컬 DB 검증 범위와 남은 운영 관문을 추가했다. v10을 덮지 않았다. 기능 분류4조건부·9개선필요·8추가검증은 준비율이 아니다. HTML 브라우저 렌더링은 미확인이고 이전 고정 예제 그림은 그대로 보존했다.

다음은 이전 문맥과 직접 도보도 현재 경로로 채우고, needs_replan/held를 실제 Case 재조정으로 넘기는 일이다. 지금의 보류는 낡은 안내를 막지만 새 경로를 만들어 주지는 않는다. 탑승 중 새 지연·후속 환승의 재조회, 회전 제약 탐색 적용, 혼합 운임과 출입점 일치 신규 웹 대조·실제 도착 측정도 남았다. 전체21완료는 선언하지 않는다.
