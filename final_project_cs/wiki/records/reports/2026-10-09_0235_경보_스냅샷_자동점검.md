# 실경보 원본 수집과 대체안 스냅샷 실행기

매일 오전 9시 실경보 원본을 읽어 보관하는 heartbeat를 등록했다. 대체안 화면 점검 코드는 준비했지만 실제 시험 API 연결과 반복 접수 승인이 남아 있다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 실행기 안전 시험 | 통과 | 6/6 = 100% |
| mock 서버 화면 시험 | 통과 | 1/1 = 100% |
| 실제 경보 소스 | 부분 확인 | 5/6 = 83% |
| 실경보 대체안 화면 | 연결 대기 | 0/1 = 0% |
| 매일 원본 수집 예약 | 활성화 | 1/1 = 100% |
| 30분 감시·반복 접수 예약 | 승인 차단 | 0/1 = 0% |

## 목표와 변경

사용자가 다른 uiux 채팅에서 요청한 「당일 실제 경보를 수집하고 영향 일정으로 대체안을 점검해 스냅샷 보관」 중 별도 스냅샷 세션 소유 작업이다. 계획서 v11의 검증·지속관리 범위다. 기존 사용자 여행을 등록·수정하지 않는다.

- [실행기](../../../scripts/capture_alert_scenarios.py): 소스별 원문·캐시 첫 확인 시각·실패를 보관하고 겹친 회차를 막는다. API 404·비활성·근거 부족·대체안 실패를 성공과 구분한다. 원본 보관만 하는 모드는 고객 API와 브라우저를 호출하지 않는다.
- [브라우저 시험](../../../frontend/apps/web/tests/live/alert-snapshots.spec.ts): 새 게스트의 시험 접수에서만 미리 보기를 확인한다. 영향받은 장소의 대체안인지 확인하고 전후 화면을 보관한다. 여행 등록·채팅·알림을 차단한다.
- [운영 문서](../../operations/alert-snapshots.md): 연결 설정·성공 기준·실패 복구·실제 수집 범위와 예약 상태.

개인 접속 명령과 주소는 git 밖 `.tmp/alert-snapshots/`, `var/alert-snapshots/config.json`에만 있다. 다른 세션 소유 입구·pipeline·관리자웹앱·guardrails·설정·run_sweepers는 수정하지 않았다. reset·stash·commit·push·배포를 실행하지 않았다.

## 검증과 남은 것

[실행 증거](../evidence/2026-10-09_경보_스냅샷/verification.md)와 [점검 흐름 그림](../evidence/2026-10-09_경보_스냅샷/flow.html)을 보관했다. TypeScript 검사·시험 파일 ESLint·Python 구문 검사는 통과했다.

mock 서버 시험 1/1 = 100% (화면 반응): 전후 스냅샷 두 장. 실제 경보를 사용한 결과가 아니다.
실서버 확인 (서버 응답): 했음 — x600 서버의 cs 프로젝트 서버 상태 API 200·시험 목록 API 404·실경보 소스 5/6. 실제 대체안 화면 확인은 안 했음.

시험 목록 API가 실제 cs 프로젝트 서버에 배포되고 웹 주소가 확인되면 최신 계약·메타데이터 모양을 대조해 이 세션 소유 파일에 연결해야 한다. 실제 API가 반환하는 장소·시간·실제 영향 근거와 대체 장소의 실경보 재검사가 모두 통과해야 전체 성공이다. 현재 실경보 대체안·화면이 통과했다고 보고하지 않는다.

30분마다 감시하고 원격 시험 접수를 반복하는 heartbeat는 자동 승인 검토가 「반복 주기와 원격 시험 접수의 명시적 승인 부족」을 이유로 거절했다. 사용자에게 승인 범위를 구체적으로 물었으며 답을 기다린다. 허용된 대안인 매일 원본만 수집하는 예약(`tripilot`)을 등록했다. 원본 예약은 계정·접수·여행을 만들지 않는다.
