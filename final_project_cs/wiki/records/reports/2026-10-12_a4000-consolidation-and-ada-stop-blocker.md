# A4000 GPU 작업 통합과 ADA2000 Pod 정지 차단

기존 평가 이력·도구·어댑터를 A4000으로 이전했고 후속 계산을 한 기계에 연결했습니다. ADA2000의 유휴 평가 실행기는 종료했으나, RunPod Pod 자체 정지는 관리 권한과 휘발성 모델 보존이 해결되지 않아 미완료입니다.

| 이전 파일 해시 검증 | 완료 | 1,397/1,397 = 100% |
| 누락 QAT 비교 등록 | 대기열 반영 | 3/3 = 100% |
| 새 비교 실측 | 선행 작업 대기 | 0/144 = 0% |
| ADA2000 Pod 정지 | 관리 권한·보존 차단 | 0/1 = 0% |

## 문제와 실제 환경

[실측] GPU 서버 A는 RTX 2000 Ada이며 등록 196개가 모두 종료 상태였습니다. GPU 서버 B는 RTX A4000이며 기존 HF 앱 출력 완성도·안정성 작업을 계산 중이었습니다. 과거 A/B 양쪽을 계속 채우라는 지시는 사용자의 A4000 통합 지시로 대체했습니다.

## 반영한 내용

- 기존 종료 작업을 재실행하지 않고 1,701,155,373바이트의 원본 결과·실행 조건·평가 입력·어댑터·추론 도구를 A4000으로 직접 이전했습니다. 원본과 복사본의 파일 크기·SHA-256을 대조했습니다. 복사 중 증가한 유휴 로그는 A4000의 `_backup/finish`에 먼저 보존한 뒤 다시 동기화했습니다.
- A4000에 이미 있는 Gemma QAT Q4_0 원본을 재사용했습니다. 우리 데이터로 학습한 cosine seed20261014·oos2r·oos3 어댑터의 아직 누락된 앱 출력 계약 비교만 각 48문항씩 등록했습니다. 같은 고정 입력과 기존 일반 Q4_K_M 비교를 연결했으며 D/E의 새 정확도 개선이나 독립 보류 검증이라고 부르지 않습니다.
- 현재 HF 4작업이 종료 상태이고 선행 프로세스도 종료됐을 때만 단일 평가 실행기가 시작됩니다. 현재 계산을 중단하거나 동시에 새 추론을 띄우지 않았습니다. ADA2000 공급 설정과 기존 로컬 어댑터 feeder는 비활성화했고 기존 두 예약의 공유 지침을 A4000 전용으로 바꿨습니다.

## 검증

[실측] 2026-10-12 12:22:27 KST에 A4000의 기존 HF 비교는 2/4 완료였습니다. FINCH seed20261013의 안정성 작업이 계산 중이며 다음 cosine seed20261013과 새 QAT 3개, 총 후속 4개가 연결돼 있습니다. 표본 GPU 메모리는 10,469MiB, 순간 이용률은 25%였습니다. 새 dispatcher 생존과 선행 대기를 확인했습니다. A4000 디스크 여유는 3,791,228,928바이트로 3GiB 이상입니다.

로컬 feeder 비활성화 확인 1/1 = 100%입니다. 웹 화면 mock 서버 시험은 이번 GPU 운영 변경에 해당하지 않습니다. 실서버 확인(원격 GPU 실행): 했음 — A4000 현재 계산·dispatcher·파일 해시·공간을 확인했습니다.

## 미완료와 필요한 조치

RunPod 공식 관리 API에 기존 인증 헤더를 사용한 조회는 GraphQL `UNAUTHORIZED`, REST `403`이었습니다. 현재 연결된 브라우저에서 RunPod 로그인 세션도 확보하지 못했습니다. 따라서 실제 Pod stop·과금 중지는 확인되지 않았습니다. [공식 stop 안내](https://docs.runpod.io/sdks/graphql/manage-pods)의 볼륨 보존 stop과 terminate를 구분하며 terminate·볼륨 삭제는 실행하지 않았습니다.

URL 쿼리로 API 키를 보내는 공식 문서의 인증 방식은 자동 승인 심사에서 거절됐습니다. 키가 프록시·접속 로그에 남을 위험이라는 사유였으며 이 방식을 우회하거나 반복하지 않았습니다. 관리 권한이 있는 인증 헤더 자격 또는 로그인된 RunPod 관리 화면이 필요합니다.

휘발성 위치의 Valen 원본 3,417,285,852바이트는 아직 별도 보존하지 못했습니다. 기존 지속 네트워크 볼륨은 실제 쓰기에서 `Disk quota exceeded`가 발생했고, A4000에 복사하면 3GiB 여유 기준을 깨며, 로컬 보존은 원본 크기와 512MiB 여유를 합한 사전 검사에서 막혔습니다. 보존 실패 기록을 남겼고 모델·이전 결과를 삭제하지 않았습니다. 실제 Pod 정지 전 이 원본의 저장 여유를 확보해야 합니다.

## Oracle ARM 비공개 원본 보존 검토

Oracle ARM에 10GiB 여유를 남기고, 모델을 기동하지 않으며 1MiB 단위 스트리밍·최저 CPU/IO 우선순위·비공개 접근 권한·원본 SHA-256 검증을 사용하는 보존 스크립트를 준비했습니다. 로컬 대용량 쓰기는 하지 않습니다. 그러나 자동 승인 심사는 Valen 모델을 Oracle ARM으로 보내는 구체적인 사용자 승인이 없다는 이유로 실행을 거절했습니다. 전송은 시작되지 않았고 이 거절을 우회하지 않았습니다. 이 경로로 보존하려면 Valen 원본의 기존 Oracle ARM 비공개 보관 폴더 전송에 대한 사용자 명시 승인이 필요합니다.
