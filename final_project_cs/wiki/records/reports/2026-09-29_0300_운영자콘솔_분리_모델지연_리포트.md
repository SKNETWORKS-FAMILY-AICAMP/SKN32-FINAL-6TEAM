# 운영자 콘솔 분리(1단계) · 모델 첫 호출 지연 — 리포트 (2026-09-29)

## 결론

운영 화면·관리 API·시나리오 모드를 고객 API 앱(8042)에서 빼서 **별도 운영 앱(127.0.0.1:8070)** 으로 옮겼습니다.
고객 서버에 운영 경로는 0개(404)이고, 운영 앱은 이 기계 안에서만 열립니다.
채팅의 사실 질문은 이제 모델 분류를 기다리지 않고 바로 답합니다. 화면이 모델을 미리 깨우는 입구도 만들었습니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 운영 앱 조립 · 고객 앱에서 운영 경로 빼기 | 끝 | 고객 앱 운영 경로 0개 |
| 운영 → 고객 API 실제 HTTP · 키는 설정에만 | 끝 | 호출 3곳 모두 |
| DB 조회 읽기 전용 연결 · 계정 SQL | 끝(계정은 안 만듦) | 표 7개 |
| 폼 위조 방지(CSRF) | 끝 | 모든 POST 폼 |
| 사실 질문 분류 기다리지 않기 · 예열 입구 | 끝 | 시험 통과 |
| 전체 시험 | 통과 | 2301 통과 · 실패 0 |

요청: 사용자 지시(ui 세션 전달 · Codex 합의) — `consensus/20260929_ops_console`, `consensus/20260929_keepalive`(ui 세션 임시 폴더).
결정 기록: [D-CS-008](../../decisions/D-CS-008-ops-console-separate-app.md).

## 1. 운영자 콘솔 분리 (1단계 — 같은 기계의 다른 프로세스)

| 무엇 | 파일 |
|---|---|
| 운영 앱 입구 — 루프백 아닌 요청 403 · 0.0.0.0 띄우기 거부 · 포트 8070 | `app/ops_entrypoint.py` |
| 고객 앱에서 운영 화면 제거 · `/admin/reload` 는 관리용 빌드만(`management=True`) | `app/presentation/api/app.py` · `app/entrypoint.py` |
| 오류 응답 모양 공용(두 앱이 같게) | `app/presentation/errors.py` |
| 운영 앱 도메인 경로(제한값 운영 API · 시나리오 모드) | `app/composition.py::build_ops_routers` |
| 운영 화면 → 고객 API 실제 HTTP · 키는 `ACOP_OPS_API_KEYS` · 시간 초과 「결과 모름」 · 폼 위조 방지 | `app/presentation/ui/routes.py` · `auth.py` |
| 조회 읽기 전용 연결 · 계정 SQL | `app/infrastructure/db/session.py` · `scripts/sql/ops_readonly_role.sql` |
| 설정 넷 · 시간 제한 | `app/core/settings.py` · `config/guardrails.yaml`(`security.ops_api_timeout_seconds`) · `.env.example` |

- **시나리오 모드**: 스위치·시연 화면·입구가 한 판을 프로세스 메모리에 들고 있어, 셋을 **함께** 운영 앱으로 옮겼습니다. 나누면 깨집니다.
- **읽기 전용 계정 SQL**: 한 트랜잭션 안에서 적용해 확인하고(읽기 예·쓰기 아니오) 되돌렸습니다. 실제 계정은 만들지 않았습니다. 비밀번호는 psql 변수로 넘기게 해 두어서 파일·git에 남지 않습니다.
- **실서버 확인**: 8070을 띄워 `/health` 200, `/ui/login` 200, 로그인 전 `/ui/cases` 303, 키 없는 `/admin/limits` 401을 봤습니다. 8042는 옛 코드라 재시작이 필요합니다(ui 세션에 알림).

**2단계 전이라 아직 「물리 분리 완료」가 아닙니다.** 남은 것은 넷입니다.
- 다른 기계·사설망 + VPN·SSH 터널만 열기
- DB 직접 읽기 → API로 옮기기
- `/introspection`을 어디에 둘지 결정
- 개발 콘솔(8060)의 「반영」은 관리용 빌드에서만 된다는 점을 운영 절차에 적기

## 2. 모델 첫 호출 지연

- **(a) 사실 질문은 분류를 기다리지 않습니다** — 웹 입구 한정. 식은 모델에서 34.8·33.5초 걸리던 것(ui 세션 실측)이 규칙 답만으로 끝납니다.
  - 분류·담당·완료 기록은 응답 뒤에서 돕니다. 답은 Case 기록에 처음부터 실려서, 같은 요청을 다시 보내도 답이 나갑니다.
  - 에이전트 입구는 지금처럼 분류까지 기다립니다.
  - 코드: `app/modules/travel_ops/trip_messages.py`(`_finish_fact_case`, `defer`).
- **(b) `POST /v1/web/warmup`**: 응답은 `warm | warming | unavailable`입니다.
  - 1분 안 되풀이는 한 번으로 묶고, 실제로 부를 때만 남용 방어(`warmup`)로 셉니다.
  - 마지막 시도가 실패했으면 이유를 싣습니다.
  - ★정정(같은 날, ui 세션 실측): 모델 서버의 GPU 메모리 부족은 **간헐적**입니다. 두 모델을 동시에 올리려 할 때만 났고, 직후 gemma4:12b 짧은 생성 3회는 모두 HTTP 200, 0.6~0.9초였습니다.
  - 앞서 「식은 모델 34초」로 본 값 일부는 HTTP 상태를 확인하지 않은 측정이라 실패 응답까지 걸린 시간일 수 있습니다. 성공이 확인된 식은 첫 호출은 12b 35.2·37.0초입니다(ui 세션 비교 스크립트).
  - GPU가 부족한 때에는 예열도 효과가 없으므로, 핵심은 (a) 사실 질문이 모델 실패에 붙잡히지 않게 한 것입니다.
  - 코드: `app/modules/travel_ops/model_warmup.py` · `app/infrastructure/ollama_chat.py`(`loaded`·`warm`).
- **keep_alive**: 기본 5분 그대로입니다(합의). 공유 GPU이고 요청 간격 실측이 없기 때문입니다.
- **분류 실패 이유 로그**: `app/application/classification.py`. 원문은 싣지 않습니다.

## 3. 검증

- 분리 기준 `tests/architecture/test_ops_app_is_separate.py` **23/23**
  - 고객 앱 경로 0 · 404 ×14
  - 운영 앱이 고객 앱을 import 하지 않음 · 키를 만들지 않음
  - 바깥 요청 403 · 바깥 주소 띄우기 거부 ×3 · 포트
- 두 프로세스 `tests/e2e/test_ops_app_two_processes.py` **3/3**
  - 고객 API 앱을 uvicorn으로 **따로 띄우고**, 운영 앱이 HTTP로 승인했습니다(승인자 = 로그인 운영자).
  - 폼 확인값이 없으면 403이고 기록 0입니다. 다시 눌러도 기록 1건입니다. 키가 없으면 보내지 않습니다.
  - 조회·위임 화면이 동작합니다.
- 운영 화면 시험 11개 파일을 운영 앱·폼 확인값에 맞게 고쳤습니다: 로그인 24 · 위임 · 승인 실패 · 운영 화면 · 시나리오 8 · 반영 9(고객 릴리즈 404 추가) · API 목록.
  - 시험 도우미: `tests/ops_app.py`(운영 앱과 고객 앱을 HTTP 경계로 잇는다) · `tests/ui_login.py`(`login_csrf`·`csrf`)
- 예열·남용 방어 29/29 · 웹·여행 API 53/53
- **전체 2301 통과 · 실패 0**(6분 38초, 다른 세션의 새 식당 시험 폴더 `tests/integration/dining` 제외 — 그 시험이 쓰는 DB 표가 아직 없다)

## 4. 실제 모델 확인 시험 (2026-09-29, 팀 RunPod GPU 팟)

`tests/live/test_chat_model_live.py` — 실서버가 부르는 것과 **같은 함수**(`trip_intake.extract`·`feedback.classify`)로 채팅 대표 문장 11개를 읽히고, 분류 3개를 해 본다.
- **어디서 돌렸나**: 모델 서버는 다른 세션이 GPU를 쓰는 중이라 팀 RunPod 팟(RTX 2000 Ada 16GB)에 Ollama 0.34.4와 gemma4:12b를 올리고 SSH 터널(로컬 11435)로 불렀다.
- **같은 모델인가**: 모델 지문이 모델 서버와 같다(`4eb23ef187e2`).
- **모델이 올라간 상태: 14/14 통과**, 한 건 1.9~3.1초.
  - 늦음 30분·70분, 휴무, 품절, 2번으로 되돌리기, 다른 식당으로 바꾸기, 위약금·몇 시 질문, 인사, 무관한 말(파이썬·비트코인)을 모두 맞게 읽었다.
  - 분류 3개는 모두 라벨 셋을 냈다.
- **첫 호출(모델이 식은 상태): 1/14 실패**. 60초 시간 제한을 넘었고(`ReadTimeout`), 둘째 호출도 49초 걸렸다.
  - 팟은 모델 파일을 **네트워크 저장소**(`/workspace`)에서 올려서 식은 첫 적재가 1분을 넘는다(모델 서버 로컬 디스크 실측 35~37초보다 느림).
  - 실서버에서 「식은 모델의 첫 채팅이 분류 실패」로 끝나던 것과 같은 모양이다. 사실 질문이 분류를 기다리지 않게 한 것(§2)이 이 경우를 막는다.
