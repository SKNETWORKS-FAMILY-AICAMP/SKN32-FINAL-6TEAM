# 예시 일정의 실행 로직 점검

**새 모델 읽기와 먼저 채우기는 x600 서버의 cs 프로젝트 서버에서 실제로 실행됩니다. 그러나 새 예시의 숙소 자동 채우기·추천 완료 순서·숙소 변경 저장·예약 표시 유지에는 실패가 있어 정상 동작으로 판정하지 않습니다.**

| 할 일 | 상태 | 진행 |
|---|---|---|
| 요청한 동작 점검 | 완료 | 5/5 = 100% |
| 추가 예약 보호 확인 | 누락 재현 | 1/1 = 100% |
| 실행 근거 기록 | 완료 | 1/1 = 100% |

이 표는 점검 작업의 완료율입니다. 기능 시험 통과율이 아닙니다. 관측은 2026-10-17 15:58~16:18 KST이며, 실제 화면 시험은 이번 점검에서 새로 만든 예시 접수 한 건입니다. 다른 고객의 여행·알림 설정을 변경하지 않았고, 기존 자료·코드·배포판을 덮거나 삭제하지 않았습니다.

## 1. 계획과 실제 실행의 대조

기준은 [D-025 결정의 읽기용 사본](../evidence/2026-10-17_live_example_logic_audit/D-025-reference.md)과 현재 제품 범위입니다. 이 사본은 기존 격리 작업 사본의 Git에서 읽어 새 증거 파일로 보존한 것입니다. 원본 문서를 복원하거나 수정하지 않았습니다. D-025의 10-16 당시 “x600 서버 배포 안 함” 문장은 과거 기록이며, 이번에는 실제 실행으로 확인했습니다.

- 실행 코드의 `travel.intake_reader.mode=on`, `prefill=on`을 확인했습니다. 조회한 운영 설정에서 읽기 모드를 덮는 값은 나오지 않았습니다.
- 새 예시의 `reading.agent`에는 `used=true`, 모델 `tripilot-pointer:e4b-ft`, 소요 8.4초가 남았습니다. 가르친 E4B를 사용한 한 번의 관측이며 성능 평균이 아닙니다.
- 식당 팀이 인사동의 빈 식사 자리를 양반댁으로 채웠고 `reading.prefill.filled`에 담당·이유가 남았습니다. 새로고침한 실제 화면에도 “우리가 1곳을 먼저 채웠어요”가 표시됐습니다.
- 숙소 후보를 숙박 분류로 제한하고 여행 전체 방문지와의 평균 직선거리로 정렬하는 개선 코드는 실행판에 있습니다. 실제 화면에서도 호텔 3곳과 숙소 안 식사 3개가 나왔습니다. 후보 제시 성공은 적용 성공과 별개입니다.

실행 API 이미지 식별자는 `sha256:526eadef908f989745d6f79b925b1b95f596a3e43f127bf8511bc13fa904f002`, 웹 이미지는 `sha256:4bcfa5774661f6c4f4065fa1c6c128cce975f3122bdd644d1ad66b8c76d1d08f`였습니다. 배포 상태 파일의 커밋 기록만으로 실행 파일 전체의 일치를 주장하지 않았습니다.

## 2. 실제로 재현한 결함

| 증상 | 직접 관측 | 원인·한계 |
|---|---|---|
| 처음부터 호텔이 채워지지 않음 | 양일 호텔 조식 2/2가 장소 미정. 첫 화면에 숙소 이름을 묻는 질문이 나옴 | 배포된 `prefill.check_gaps`는 미정 숙소까지 `lodging_name → ask_customer`로 보냄. 숙소 후보 조회 개선과 최초 자동 채우기 연결은 별개 |
| 추천 버튼이 갑자기 거절됨 | 새 예시에서 호텔 자동 추천 시 “그 사이 다른 화면에서 고쳤습니다” 표시. 실제 요청 HTTP 409 | `pipeline.process`가 빈칸 채우기 전에 `status=review`로 바꿈. 화면의 실시간 구독은 읽기 완료로 끝나는데 이후 자동 채우기가 새 판을 저장함 |
| 고른 호텔이 적용되지 않음 | 최신 판을 다시 읽고 호텔 조식 후보를 직접 골라도 HTTP 409. “창덕궁 → 청계천” 이동 계산 시간 한도 사유. 최종 판은 2, 두 호텔 장소는 그대로 미정 | 공통 호텔 적용에 따른 시각·이동 재검사에서 `direct_schedule.fit`가 `schedule_check_failed`로 저장을 거절. 실제 실패 화면과 DB 최종 상태를 확인했으며 반복 실패율은 측정하지 않음 |
| “예약 있음”이 사라짐 | 원문 N서울타워에 예약 있음이 있으나 실제 API는 `booked=null`, `locked=false`. 기존 규칙 읽기는 `booked=true` | 새 모델 결과를 옮기는 `_agent_rows`는 예약 값을 `None`으로 넣고 예약 claim을 만들지 않음. 배포 코드의 순수 함수 확인에서도 예약 보존 실패 재현 |

예약 누락은 읽기 결과와 보호 입력의 결함입니다. 이번 점검에서는 예약 항목을 실제로 변경하거나 예약 취소·업체 거래를 실행하지 않았으므로 그 후속 부작용까지 재현했다고 주장하지 않습니다. 모델도 이름이 적힌 예약을 `booked_place_name` 누락 질문으로 분류했으며, 현재 질문이 원문과 맞는지도 보완 대상입니다.

## 3. 길이 보이지 않는 범위

실제 `route-shapes` 응답은 HTTP 200이며, 저장된 같은 날 이동 8개 중 경로선 6개를 반환했습니다. **6/8 = 75%**의 분모는 이 예시의 두 날짜에 있는 인접 일정 간 이동 8개입니다. 길찾기 기능 전체의 성공률이 아닙니다.

빠진 2개는 양일의 호텔→첫 방문지입니다. 호텔 좌표가 정해지지 않아 두 구간의 이동 시간·경로선이 없었습니다. 나머지 6개는 지하철·버스·도보 경로선 응답을 확인했습니다. 대중교통 선은 응답에 적힌 대로 역·정류장을 잇는 근사선이며 실제 선로·도로 형상을 전부 재현한 선이라고 표시하지 않습니다.

예시 원문에는 “호텔 조식” 두 줄이 있고 체크인·체크아웃 숙박 기간은 없습니다. 실제 두 줄의 업무 종류는 `dining`, 장소 분류는 숙박 `32`입니다. 따라서 이 예시만으로 숙박 기간의 등록·체크아웃·숙소 변경 전체를 검증했다고 할 수 없습니다. 현재 숙박 아이콘만 보고 이 구분을 알기는 어렵습니다.

## 4. “관광공사”와 “우리가 채움”의 뜻

| 표시 | 의미 |
|---|---|
| 관광공사 | 호텔·장소 사실 정보를 찾은 출처 `tour_api` |
| 우리 장소 목록 | 서비스 안에 보관된 장소 자료 `places` |
| 우리가 채움 | 에이전트 담당이 빈칸을 채운 행위와 이유 `prefill.filled` |

우리 에이전트가 골랐더라도 사실 정보의 출처가 관광공사일 수 있습니다. 관광공사 표시가 우리 에이전트를 거치지 않았다는 증거는 아닙니다. 반대로 우리 장소 목록이라는 표시만으로 에이전트가 자동으로 골랐다고 판단하면 안 됩니다. 자동 채우기 표시는 따로 확인해야 합니다.

## 5. 다음 수정·검증 범위

동시에 진행 중인 「숙소 추천 위치 로직 수정」 채팅의 16:18 이전 보고에서는 최초 숙소 추천·완료 순서의 수정 시험을 마치고 운영 반영·새 예시 화면 검증을 진행 중이라고 확인했습니다. 이는 해당 채팅의 보고이며, 이번 점검자가 수정판의 배포 완료를 직접 확인한 결과가 아닙니다.

1. 새 예시가 먼저 공통 숙소를 채우고 모든 저장·추천 기록이 끝난 뒤에만 완료를 알리는지 다시 검증합니다. 최종 판 번호와 화면이 쓰는 판 번호가 같아야 합니다.
2. 호텔 선택 뒤 양일 숙소·조식·앞뒤 시각·이동이 실제로 저장돼야 합니다. 이동 시간 한도 실패를 성공으로 바꾸거나 검사를 건너뛰지 않습니다. 동일 조건의 기존 계산 재사용과 영향을 받는 구간·호출 예산을 점검해야 합니다.
3. 새 모델 경로에서도 원문에 명시된 예약 여부·예약번호를 보존하고, 보호되는 항목의 변경 거절을 별도로 확인해야 합니다. 이름이 이미 있는 예약을 이름 미상 질문으로 되돌리지 않아야 합니다.

이번 요청은 현재 동작 확인으로 수행했습니다. 운영 코드 수정·배포·기존 고객 일정 변경은 하지 않았습니다. 점검용 접수는 미등록 상태로 남겼으며 삭제하지 않았습니다.
