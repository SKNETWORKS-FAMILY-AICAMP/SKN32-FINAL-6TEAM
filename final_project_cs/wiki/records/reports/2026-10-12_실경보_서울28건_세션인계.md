## 받는 세션과 새 요청

받는 세션은 [실경보 데이터 수집 목적과 활용 방안](codex://threads/01a12c1b-b182-70f2-ad25-14da99f1b711)이다. 사용자가 이 세션으로 인계 메시지를 보내도록 직접 요청했다. 향후 현황·분석·수집·사례화는 그 세션에서 진행한다. 현재 대화로 회신할 필요가 없다.

새 요청은 “서울에서 수집 기간에 발생한 28건이 실제 여행 일정에 영향 주는 사례인지 확인해서 쓸 수 있는 케이스로 정리. 호출 예산 제한 유지”다. 28건은 확정 영향 사례가 아닌 원본 후보의 수다. 28건 모두에 대해 판정·근거·남은 한계를 남기며 보류·비영향을 분모에서 빼지 않는다.

## 준비한 입력

[서울 후보 28건](../../../var/alert-snapshots/analysis/2026-10-12-handoff-v1/seoul-28-candidates.json)은 새 파일이다. `incidentId`별 최신 저장 행의 `addressJibun`이 서울로 시작하고 `startDate`가 2026-10-09·10·11 중 하나인 기록을 골랐다. 추출 결과는 28개 ID·31개 회차 관측 행이다. 각 후보에 최신 행, 해당 ID의 모든 저장 관측 행, 수집 시각, 원본·수집 결과 파일 위치, 수집 결과 SHA-256을 포함했다. `impact_status=pending`이며 여행 영향은 판정하지 않았다. 같은 ID의 경로·시각 변화가 있으면 전체 관측 행을 확인한다.

서울 주소 기준 필터는 실제 경로 영향의 증명이 아니다. 일부 원문의 시작·종료 시각과 수집 시점이 다를 수 있다. 처음부터 28건 전부를 일정 변경이 필요한 양성 사례로 만들지 않는다.

## 이어서 수행할 일과 완료 기준

1. 현재 wiki 계약·실제 도로 판정 코드·일정 영향 판정 호출부·기존 여행 시험 입력을 먼저 읽는다. [기존 활용안](2026-10-12_실경보_원본_활용안.md)과 후보 28개를 대조한다. 과거 기록을 현재 계약으로 쓰지 않는다.
2. 각 후보의 발생·종료·관측 시각, 좌표·도로·구간·방향·통제 정도, 변경·해제 이력을 정리한다. 도로 가까이에 관광지가 있다는 이유만으로 방문 불가를 단정하지 않는다. 종료된 사건을 지금 조회해 과거 영향의 증거로 대신하지 않는다.
3. 확보된 여행 일정·시험 일정의 방문과 이동 구간을 장소·경로·시간으로 대조한다. 실제 여행 일정이 확보되지 않으면 그 사실을 명시하고, 저장된 실제 사건에 명시적으로 시험용 일정을 결합한 재현 사례를 만든다. 실제 고객 일정에 영향이 확인됐다고 표현하지 않는다. 고객 데이터는 식별정보를 제외하고 읽기 범위만 사용하며 수정하지 않는다.
4. 외부 호출 없는 로컬 재생을 우선한다. 저장 원문·기준 시각·일정 입력·기대 판정·판정 이유를 고정하고, 기존 판정기로 실행한 결과를 남긴다. 영향 중·시간이 다름·다른 도로/방향·해제 후 같은 비교 조건을 활용한다. 재현 시각 이후의 관측을 미리 공급하지 않는다. 의도적으로 만든 시험 일정과 실제 사건 원문을 구분한다.
5. 28건 각각을 사용 가능·비영향·근거 부족 등 근거가 있는 판정으로 정리한다. 사용할 사례에는 원문 참조·해시·시간대·시험 입력·기대값·실제 결과·한계를 묶어 실행 가능한 자료로 만든다. 근거 부족 후보는 필요한 값과 보완 방법을 적는다. 영향 판정과 대체안의 안전성 검증은 별도이며, 실행하지 않은 대체안 검증을 완료로 적지 않는다.

최종 산출물은 28건 전수 판정표, 근거가 충분한 재현 사례 묶음, 이를 재실행할 명령·검증 결과, 보류 이유와 추가 필요 자료다. 분모 28을 유지한 판정 진행표와 실제 실행한 시험 수를 따로 보고한다. 제품 코드가 바뀌면 관련 검증만 수행하고 기존 다른 세션 변경을 덮지 않는다.

## 유지할 예산·행동 경계

개인 설정의 수집 정책은 `shared_stop_ratio=0.2`, `source_daily_attempts=2`, `source_monthly_attempts=62`다. 소스별 공용 하루·알려진 월 사용량이 20%에 닿으면 새 수집을 멈춘다. 수집용 시도는 기존 DB의 `alert_snapshot:<소스>`에서 한국 시각 하루 2회·월 62회를 지키며 실패·공용 예산 거절도 포함한다. 유효 캐시를 우선하고 예산·한도 미확인이나 DB 오류면 새 요청을 하지 않는다. 설정·다른 기능 한도·카운터를 늘리거나 초기화하지 않는다. 사례 분석을 이유로 제한기 밖에서 제공처에 직접 요청하거나 다른 키·경로로 우회하지 않는다.

새 요청은 영향 확인·사례 정리 작업의 승인이다. 30분 감시·원격 시험 접수 자동화에 대한 기존 자동 승인 검토 거절을 해제하는 승인은 아니다. 해당 자동화·고객 계정/접수/여행 쓰기·고객 알림·웹훅·관리자 설정·commit·push·배포는 진행하지 않는다. 로컬 시험용 입력과 재생 자료는 새 이름으로 작성할 수 있다. 기존 산출물 교체 전에는 백업한다. 외부 통신이 꼭 필요하면 먼저 현재 승인 범위와 동일한 제한기를 적용할 수 있는지 확인하며, 사용량·실패를 숨기지 않는다.
