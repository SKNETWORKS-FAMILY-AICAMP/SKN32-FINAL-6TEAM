# 계획 확인 화면 백엔드 리포트 (2026-10-03)

## 결론

고객이 일정을 올리면 서버가 장소·운영시간·휴무·이동 시간을 **읽는 동안 하나씩 검사해 흘려 보내고**, 확인 화면에서 **대체 후보 · 장소 검색 · 사진 · 잠금 · 전체 자동 추천 · 재검증**을 쓸 수 있게 만들었습니다.
목업(`team_branch/sw/2026-10-02_계획확인_스트리밍_대표목업.html`)이 「협의 필요」로 적은 7가지를 모두 서버가 채웠고, 실제 서버(8042)에서 접수부터 자동 추천까지 한 번에 돌려 확인했습니다.
화면(프런트)이 이 주소들을 쓰는 부분은 아직 연결 전입니다 — 이번 지시는 백엔드까지였습니다. 코덱스 적대적 검토는 10회차에서 「높음 이상 새 결함 없음, 합쳐도 된다」가 나왔습니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 목업이 필요로 한 것을 서버가 채움 | 끝 | 7/7 = 100% |
| 코덱스 적대적 검토 → 고치기 반복 | 끝 (10회차 수렴) | 10/10회차 = 100% (1~9회차 지적을 모두 고치거나 근거로 기각) |
| 실제 서버 종단 실측 | 끝 | 1/1 = 100% (접수→검사→후보→검색→사진→자동 추천→재검증) |
| 시험 | 아래 표 | 아래 표 |
| 화면(프런트)이 새 주소를 쓰기 | 다음 단계 | 0/1 = 0% (웹 쪽 몫) |

## 1. 목업이 필요로 한 것 → 서버

| 목업이 필요로 한 것 | 서버 |
|---|---|
| 「장소·운영시간 확인」 단계 | 접수 단계에 `checking` 추가 |
| 장소별 검사 줄 · 이동 · 확인 필요 개수 | 접수 조회 응답의 `review` |
| 이름이 모호한 장소(올리브영) | 앞뒤 일정에 가까운 한 곳을 먼저 채우고 확인 필요로 표시, 다른 지점은 후보 |
| 대체 후보 1~3순위 · 판정 | `GET …/candidates` |
| 장소 검색 · 사진 | `GET …/place-search` · `GET /v1/web/places/photos` |
| 장소·시각 바꾸기 · 삭제 · 되돌리기 · 잠금 | `POST …/edits` 칸 확장 |
| 전체 자동 추천 · 재검증 · 진행 이벤트 | `POST …/autofix` · `POST …/revalidate` · `GET …/events` 내용 이벤트 |

계약 전체(응답 모양 · 오류 코드 · 목업과 다른 점)는 [rest-endpoints.md](../../external/rest-endpoints.md) 의 「확인 화면 검사 · 대체 후보 …」 절이 정본입니다.

## 2. 실측 (2026-10-03, 실제 서버 8042 · 개발 DB)

- 예시 일정(경복궁 → 올리브영 → 광장시장 빈대떡 → N서울타워)을 접수해 **약 5초 만에 확인 화면**(검사 줄 · 이동 포함)이 나왔다. 올리브영은 지점이 여러 곳이라 `인사동점`을 임시로 골랐고 후보 3곳을 함께 냈다.
- 이동은 **시간표 계산기(timetable)** 값이 붙었다(예: 경복궁→올리브영 지하철 3호선 9분, 일정보다 39분 늦어 확인 필요).
- 자동 추천은 한 번에 새 판 1개(올리브영 12:00~13:00으로 이동)를 만들고 **남은 확인 필요 0 · 등록 가능**이 됐다. 재검증도 확인 필요 0.
- 관광공사 사진은 광장시장 빈대떡 쪽에서 8장, 출처 표시 포함. 사진은 저장하지 않는다.
- 운영시간 정보가 없는 곳(카카오로만 찾은 곳)은 「열려 있다」고 지어내지 않고 **`unknown`(모름)** 으로 둔다.

성능(실측): 시간표 계산기는 닿는 구간 0.2~0.5초, 못 닿는 구간의 깊은 탐색은 2.7~10.8초였다. 그래서 **빠른 호출을 먼저** 하고, 비도보 near-miss(15분 이내)에만 깊은 탐색을 하며, 한 요청의 총 계산기 시간에 상한(검사 25초 · 자동 추천 20초)을 둔다. 자동 추천 시험 시나리오가 30초대 → 4.6초가 됐다.

## 3. 코덱스 적대적 검토 (10회차)

| 회차 | 주된 지적 → 조치 |
|---|---|
| 1~3 | 시간표로 확인 못 한 이동을 「닿는다」로 셈 · 겹침이 확인 필요에 안 셈 · 좌표 한 쪽만 같은데 같은 장소로 봄 · 없는 일정이 새로 만들어짐 · 고정과 고치기 혼합 → 모두 고침 |
| 4~5 | 이동 캐시 키 · 수렴 안 하는 시각 이동 · 운영시간 모름을 통과로 받음 · 위조 `content_id` · 항상 참인 단언 → 고침 |
| 6~7 | 읽기 일꾼 이중 실행(선점 없이 두 번) · 이름만으로 후보 제외 · 후보 풀 잘림 · 응답에 내부 `place_id`·`sig` 노출 · 예산 소진 순서 → 고침 |
| 8 | 읽다 멈춘 접수가 영원히 `reading` · 정상 접수 오실패 → 생존 표시(20초)와 정리(`reap_stalled`, 6분 무소식 시 실패 확정) |
| 9 | 정리로 실패 확정된 뒤에도 느린 일꾼이 받아쓴 원본을 저장하고 읽다 만 값을 지움 → 접수 행 잠금(`_hold_reading`)으로 같은 트랜잭션에서 확인 |
| 10 | **높음 이상 새 결함 없음 · 합쳐도 되는가: 예** |

근거로 기각한 것: 「사진을 연달아 불러 관광공사를 남용」 — 어댑터가 응답을 프로세스 메모리에 6시간 들고 있고 몰림 제한을 지나므로 되풀이 호출이 바깥으로 안 나간다(시험으로 확인). 「장소 없음으로 둔 일정의 이동이 `waiting` 이라 등록을 막지 않는다」 — 자유 시간으로 의도한 동작이다.

10회차가 높음 미만으로 남긴 것: 마지막 `review.ensure` 쓰기에는 `reading` 확인이 없다. 실패 확정 뒤 저장된 검사 결과가 화면에 나가거나 접수 상태를 되돌리는 길은 확인되지 않았다(검사는 지워도 다시 계산되는 파생 값).

## 4. 시험

| 묶음 | 결과 |
|---|---|
| 새 시험 — 확인 화면 e2e + 단위 + 접수 API | 87/87 = 100% |
| 관련 e2e · 통합(확인 화면 · 스트림 · 여행 · 웹 · 남용 방어 · OpenAPI 면 · 실행 환경, 12개 파일 순차 실행) | 313/313 = 100% |
| 단위 전체 | **끝내지 못했다** — 9회차 수정 직후의 마지막 두 번째 실행은 별건 1개에서 `-x` 로 멈췄고, 별건을 빼고 다시 돌린 실행은 메모리 부족(가상 메모리 여유 1.3GB)으로 파이썬이 중간에 죽었다. 수정 전 마지막 완전 실행은 1630개 통과 + 별건 1개 실패 |
| 알려진 별건 | `tests/unit/travel/mobility/test_plan_v1.py::test_core_routes_strips_display` — **전체 단위 실행에서만** 실패하고 단독 실행은 통과(이동 담당 영역, 이번 변경과 무관) |

9회차 수정(`_hold_reading`)은 `pipeline.py` 한 곳과 시험 한 줄이라 단위 시험 쪽 영향은 없다고 보지만, **단위 전체를 다시 끝까지 돌린 확인은 아직 없다** — 메모리가 비면 다시 돌린다.

## 5. 사고와 한계

- **개발 DB가 두 번 죽었다**(윈도 커밋 한도 소진 — 큰 병렬 시험 + 여러 세션). 자동 재시작이 없고 사용자가 띄운 `pg_ctl` 프로세스라서, 한 번은 복구를 기다렸고 한 번은 자동 복구됐다. 시험은 이후 **순차 실행**으로 돌렸다.
- 웹 남용 방어의 `place_search` 세기는 **기본이 세기만 하고 막지 않는다**(`web.limits_enabled` 꺼짐). 켜는 것은 운영 결정이다.
- 올리브영 같은 체인은 목업이 「위치 미정」으로 그렸지만 서버는 **가까운 지점을 임시로 골라 확인 필요로 표시**한다(빈칸보다 낫다고 봤다). 화면 문구 정렬은 웹 쪽 몫.
- 위치 고르기(지도) 화면의 실서버 확인은 웹 연결 뒤로 남아 있다.
