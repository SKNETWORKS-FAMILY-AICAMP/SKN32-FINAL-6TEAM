# 일정 생성기 — **v11 §4-A 를 뒤집는다** (2026-09-22)

## 한 줄

요청(도시·날짜·인원·제약·자유 문장)을 받아 **등록 가능한 일정 초안**을 만들고, 그 초안이
**등록이 쓰는 바로 그 판정기**(`check_itinerary`)를 통과해야만 돌려주는 경로
`POST /v1/trips/plan` 을 만들었다. 서울 3일 2인으로 실제로 돌려서 후보 **1,779곳 중 12곳**을
골랐고 판정은 **0회 고침으로 통과**했으며 TourAPI 는 **0회** 불렀다.

---

## ★★0. 이 작업은 기준선을 뒤집는다

| | |
|---|---|
| 기준선이 말한 것 | **v11 §4-A 「계획 생성은 우리 일이 아니다」** — 「계획 생성기를 만들면 트리플·Mindtrip·범용 에이전트와 정면으로 겹친다. 우리 가치는 계획이 현실에서 성립하는지 확인하는 데 있다」 |
| 이 작업이 한 것 | **그 생성기를 만들었다.** 사용자 지시다 |
| 계획서는 | **고치지 않았다.** `program/plan/A-COP_구현계획서_v11.md` 는 읽기 전용이다(`RULE.md` §6 · 루트 `CLAUDE.md` §7). 뒤집힌 사실은 이 리포트와 `wiki/external/rest-endpoints.md`, 그리고 `planner.py` 첫 줄에 적었다 |
| 뒤집히지 **않은** 것 | **판정이 여전히 주인이다.** 생성기는 판정을 우회하는 문이 아니라 판정을 통과하는 입력을 만드는 도구다. §4-A 의 다이어그램에서 왼쪽의 「개인 에이전트·외부 LLM」 자리에 우리가 하나 더 선 것이지, 오른쪽의 「A-COP: 검증」이 약해진 것이 아니다 |

★**누가 이 결정을 되돌리려면 무엇을 보면 되나.** §4-A 의 근거는 「경쟁이 겹친다」는
사업 판단이었지 기술 제약이 아니었다. 그 판단이 유효하면 `POST /v1/trips/plan` 을
라우터에서 빼면 된다 — `trip_api.py` 의 `plan_draft` 하나와 `planner.py` 를 제거하면
나머지 경로는 그대로 돈다. **등록 경로는 이 작업으로 한 줄도 안 바뀌었다**(`create` 의
본문을 `_create_trip` 으로 뽑아낸 것뿐이고 동작은 같다).

### 1-1. 흐름

```
요청 ─ 상품 범위 확인(서울 · 1~7일 · 1~4인)
     ─ 후보 수집  ① places(우리 DB)  ② place_catalog(TourAPI 동기화분)  ③ TourAPI 실시간(②가 빌 때만)
     ─ 선호 반영  키워드 대조 → 싫다고 한 것은 **탈락**, 실내/야외는 순위
     ─ 하루 묶기  같은 구로 모은다(동선이 흩어지지 않게 · 0분 이동 위반을 만들지 않게)
     ─ 모델       **줄 번호 순서만** 받는다
     ─ 시각       서버가 채운다(하루 09:30 시작 · 점심 12:00~ · 저녁 18:00~ · 사이 여유는 도보 환산)
     ─ ★판정      check_itinerary → 위반이면 고치고 다시 판정(최대 3회) → 끝내 안 되면 거절
     ─ (register:true 면) 등록 → **같은 판정기를 한 번 더** 지난다
```

### 1-2. 지키기로 한 것과 그 자리

| 약속 | 코드 |
|---|---|
| **장소를 지어내지 않는다** | `load_candidates()` 가 DB 두 표에서만 읽는다. 좌표를 모르는 장소는 후보에서 뺀다 — 등록 계약(`PlaceIn.lat/lon`)이 필수라서 0 이나 시청 좌표로 채우고 싶어지는 자리다 |
| **모르는 값은 비워 둔다** | 카탈로그 행에는 `hours`·`price_krw` 를 **안 넣는다.** 넣을 값이 없다 |
| **모름을 숨기지 않는다** | `coverage` 가 「영업시간 n/N · 가격 n/N · 구 n/N 만 판정 대상」이라고 분자/분모로 적는다 |
| **가정과 확인을 섞지 않는다** | 문화시설(14)·쇼핑(38)을 실내로 보는 것은 **가정**이라 `attributes.indoor_assumed` 에 따로 싣는다. 판정기(`itinerary_checks`·`replan`)는 `indoor` 만 읽으므로 이 가정이 판정에 새지 않는다 |
| **LLM 은 순서만** | `ORDER_SYSTEM` 이 시각·좌표·가격·이름 출력을 금지하고, `order_with_model()` 이 목록에 없는 값을 버린다 |
| **판정을 건너뛰는 길이 없다** | 초안 쪽은 `plan_trip()` 의 while 루프, 등록 쪽은 `_create_trip()` 안의 `check_itinerary` — **두 경로가 같은 함수를 부른다** |
| **거절은 이유와 완화 조건** | `PlanRefused` 가 `code`·`message`·필요/가진 수·`remedy`·시도한 고침을 들고 나온다. 거절 코드 여섯 — `city_not_supported` · `out_of_product_scope` · `not_enough_candidates` · `plan_infeasible` · `day_overflow` · `plan_short` |
| **조용히 짧아지지 않는다** | 항목 수가 `days × 4` 가 아니면 `plan_short` 로 거절한다. 후보가 모자라 자리를 덜 채운 초안이 「3일 일정」이라며 나가는 것을 막는다 |

### 1-3. 우리가 고른 값 (측정 아님)

`planner.py` 첫머리에 이름 붙여 모아 뒀다 — `replan.py` 와 같은 방식이다.

```
DAY_START 09:30 · ACTIVITY_MIN 90 · MEAL_MIN 60 · LUNCH_FROM 12:00 · DINNER_FROM 18:00
TRANSFER_MIN_MIN 10 · TRANSFER_MAX_MIN 60 · TRANSFER_UNKNOWN_MIN 20 · MAX_REPAIR_ROUNDS 3
DAY_END 21:30   ← ★판정기가 모르는 값이다. `check_itinerary` 는 「하루가 몇 시에 끝나야
                  하는가」를 모른다(그건 우리 상품의 약속이지 일정의 성립 조건이 아니다).
                  고치다 밀려 넘어간 하루는 `day_overflow` 로 **거절**한다
```

항목 사이 여유는 **직선거리 ÷ 도보 80m/분**(`replan.WALK_M_PER_MIN`)이다. 초안의 각 항목
`detail.planner.transfer_basis` 에 「직선 167m ÷ 도보 80m/분 `[추정]`」처럼 **근거와 `[추정]`
표시를 같이** 적는다.

## 2. `register` 를 기본값 `false` 로 둔 근거

`POST /v1/trips` 는 여행을 만들 때 **통지를 바깥함에 넣는다**(`_insert` 의 `enqueue_notice` —
계획서 링크가 처음 나가는 자리, v11 §6-B ①). 즉 등록은 고객에게 말을 거는 행위다.

- 「초안 좀 보자」로 부른 요청이 **조용히 고객 디스코드로 링크를 보내면** 안 된다.
- 그래서 기본은 `false`(아무것도 안 쓴다)이고, 에이전트가 초안을 보고 **명시적으로**
  `register:true` 를 보낼 때만 등록한다.
- 등록까지 가는 경우에도 **판정을 두 번** 지난다 — 생성기가 자기 초안을 통과시켰다는
  주장을 등록이 믿지 않는다.

★**멱등은 등록 경로에서만 강하다.** `register:true` 는 `/v1/trips` 와 **같은 멱등 키**
(`idempotency_key(tenant, request_id, "trip.create", customer_id)` → `trips.request_key`)를
쓰고, 같은 `request_id` 가 다시 오면 **모델도 부르지 않고** 이미 만든 여행을 돌려준다.
반면 **초안만 받는 요청은 서버에 아무것도 남기지 않으므로** 「두 번 만들지 않는다」가 아니라
「두 번 만들어도 아무 흔적이 없다」로 성립한다. 규칙 경로(`mode=rules`)는 결정적이지만,
**모델이 붙으면 같은 요청의 초안이 글자 단위로 같다고 보장하지 않는다.**

## 3. ★이 생성기가 **못 하는 것**

| 못 하는 것 | 왜 |
|---|---|
| **실제 예약** | 업체 예약은 승인 없이 실행하지 않는다(v11 §4-C · `CLAUDE.md` §0.2). 이 경로는 일정만 만든다 |
| **가격 확인** | 카탈로그에 가격 칸이 없다. 실측 실행에서 **가격을 아는 항목 0/12**였다. 예산 제약(`budget_krw`)을 줘도 가격을 아는 항목만 합산된다 — 「예산 안에 든다」고 말할 수 없다 |
| **영업시간 확인** | 같다. 실측에서 **영업시간을 아는 항목 0/12**. TourAPI 의 `usetime`·`restdate` 는 자연어라 boolean 으로 안 바꾼다(`tour_api.py` 의 결정). 즉 **「그 시각에 연다」를 보장하지 않는다** |
| **서울 밖 도시** | `city_not_supported` 로 거절한다. v11 §1 — 커버 못 하는 범위를 상품에 넣지 않는다 |
| **이동 항목(`mobility`)과 경로** | 초안에 이동 항목을 **안 만든다.** 경로 소요(`eta_min`)를 지어내지 않으려는 것이다. 대신 항목 사이에 도보 환산 여유를 둔다. 그래서 「어떻게 가나」(v11 §6-B ③)는 이 초안이 답하지 않는다 |
| **인기·평점 순서** | 순위를 매길 소스가 없다. 카탈로그는 사전식(그리고 종류 우선순위)으로 뽑는다 |
| **요리 종류로 거르기** | 「매운 음식 싫어요」를 **식당 이름으로만** 거른다. 이름에 안 드러나면 못 거른다 |
| **`weather_sensitive` 의 「모름」** | `PlaceIn.weather_sensitive` 가 `bool` 이라 NULL 을 못 담는다. 아는 값만 `True` 로 올리고 모르면 `False` 가 들어간다 — **우리가 「야외가 아니다」라고 단정한 것이 아니다.** DB 칸(`places.weather_sensitive`)은 NULL 을 받으므로 한계는 계약 쪽에 있다 |
| **RAG 근거** | 여행 RAG 는 다른 작업이 동시에 만들고 있다. 붙일 자리(`planner.py` 의 후보 수집)는 열어 뒀고 직접 만들지 않았다 |

★**이것을 요약하면**: 지금 초안이 보장하는 것은 **「시간이 서로 겹치지 않고, 같은 구 안에서
이동 여유가 있고, 상품 범위 안이다」**까지다. 「그 시각에 연다」·「예산 안이다」는
**아는 장소(우리 DB `places`)를 골랐을 때만** 판정된다.

## 5. ★★실측이 잡은 결함 — 조용한 폴백

**처음 실행에서 모델이 낸 값이 하나도 쓰이지 않았는데 결과는 `mode="llm"` 이라고 적혀 있었다.**

- 후보를 `id=tour_126508` 로 보이고 그 **문자열**을 받으려 했는데, `gemma4:12b` 는
  **줄 번호**를 냈다 — 직접 불러 본 원문: `{"activities": [3], "dining": [4, 5]}`.
- 그래서 전부 버려지고 `_merge()` 가 규칙 순위로 채웠다. 초안은 멀쩡했고 판정도 통과했다.
  **아무 신호가 없었다.** 신호 없는 축소는 폴백이다(`RULE.md` §3.2).
- 첫 실행의 실제 값: 모델 호출 3회 · **모델이 낸 값 중 목록에 있는 것 0개**.

고친 것 셋:

1. **번호로 물어본다.** 후보 줄을 `1. activity | 이름 | 구 | indoor` 로 보이고 번호를 받는다.
   우리 후보 키 문자열도 **함께** 받는다(모델이 둘 중 무엇을 내든 통한다).
2. **분자/분모를 센다.** `planner.from_model` / `planner.items` — 일정에 들어간 항목 중
   몇 개를 모델이 골랐나.
3. **하나도 안 쓰였으면 `mode` 가 `rules` 로 내려간다.** `note` 에 「모델을 n회 불렀지만 낸
   값이 하나도 후보 목록에 없어 규칙 순위로 짰다」고 적는다.

고친 뒤 같은 요청: 모델이 낸 값 **21개 중 21개가 목록 안**, 일정 항목 **12/12 를 모델이 골랐다**.

회귀 시험: `tests/e2e/test_trip_planner.py::test_a_model_whose_answers_are_all_unusable_is_reported_as_rules`.
