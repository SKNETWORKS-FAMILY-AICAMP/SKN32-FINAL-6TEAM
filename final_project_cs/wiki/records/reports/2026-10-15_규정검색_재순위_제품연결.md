## 2. 무엇을 연결했나

규정 질문(②)에서 후보를 넓혀 뽑고, 모델이 「질문에 직접 답이 되는 줄」만 고르게 한 뒤(재순위), 고른 줄이 없으면 「못 찾았다」고 답하고(검증), 고른 줄도 점수 문턱을 넘어야 보이게 했다. 코드는 [policy_rerank.py](../../../app/domains/travel_ops/components/conversation/policy_rerank.py) 한 곳이고, 규정 질문에서만 부른다([question_reply](../../../app/domains/travel_ops/components/conversation/trip_replies.py)가 `PolicyRerank` 일 때만). 기능 안내 · 일정 생성기 · 읽기 도구는 지금과 똑같이 검색한다.

**켜고 끄는 스위치** — 가드레일 [guardrails.yaml](../../../config/guardrails.yaml) 의 `travel.question.rerank` (환경 파일 `.env` 줄은 늘리지 않았다 → x600 서버 자동 배포의 환경 어긋남 검사를 건드리지 않는다):

| 값 | 뜻 | 기본 |
|---|---|---|
| `mode` | `"off"` 지금과 똑같음(모델 호출 없음) · `"shadow"` 답은 지금 방식, 뒤에서 재순위를 돌려 로그·세는 값에만 남김(고객 응답 시간 0 추가) · `"on"` 재순위한 줄만 싣는다 | **`"off"`** (켤지는 사용자 결정 대기) |

**호출 예산 · 지연** (정한 값과 이유):
- 규정 질문(`ask_policy`) 한 건당 **모델 호출 최대 1번**. 기본(`local`)은 로컬 모델만 부르고 유료로 넘기지 않는다. `backend="api"` 일 때만 유료이고 그때는 ① 질문 글을 개인정보 가림(`masked`)을 거쳐 보내며 ② 호출 직전에 `external_call_budget` 의 하루 · 한 달 상한을 세고 ③ 상한을 다 썼거나 상한을 세는 장치가 없거나 서버용 키가 없으면 **부르지 않고 지금 방식으로 답한다**(이유를 `plain:budget_exhausted` · `budget_unavailable` · `no_api_key` 로 남긴다).
- 호출 제한시간 `min(timeout_seconds 5초, 남은 시간)`. 남은 시간 = `total_seconds 14초`(고객 응답 15초 − 답 조립 1초) − 요청 해석이 쓴 시간(`llm_failover.current_path()`) − 후보 뽑는 데 쓴 시간. 남은 시간이 `min_remaining_seconds 2초` 보다 적으면 모델을 안 부르고 지금 방식으로 답한다.
- 재순위 호출이 연속 3번 실패하면 60초 동안 건너뛴다(서킷). 고객이 시간 초과를 매번 기다리지 않게.
- 모델을 못 쓴 경우(꺼짐 · 시간 초과 · 형식 오류 · 서킷 · 시간 예산 · 고객 문장 색인 준비 중)는 **조용히 넘기지 않는다**: 답의 근거(Case `basis.rerank.status`)에 `plain:<이유>` 가 남고 로그 경고와 세는 값(`policy_rerank.STATS`)이 오른다. 이유 문장에는 접속 주소를 싣지 않는다.
- 규정 오응답(0.4~0.5%)을 깨지 않는 장치: 고른 줄도 점수 문턱을 넘어야 보이므로, 같은 색인 · 같은 문턱(0.55)이면 「답하는 질문」이 지금보다 늘지 않는다(1등 점수가 문턱 미만이면 둘 다 안 답한다. 예외: 지금은 상위 3개 안에 고객 문장이 없어 못 답하던 질문에서 모델이 더 깊은 줄을 고르면 답이 새로 생길 수 있다). 문턱을 낮추거나 후보 색인을 바꾸면 이 보장이 사라지므로 아래 측정으로 따로 확인한다.

시험: [test_policy_rerank.py](../../../tests/unit/travel/test_policy_rerank.py) 29개(유료 길 6개 포함: 개인정보 가림 · 상한 소진 · 상한 장치 없음 · 키 없음 · 모델 이름 · 설정 검증 / 꺼짐 · 고름 · 빈 판정 · 실패 시 지금 방식 · 서킷 · 시간 예산 · 색인 · 그림자 · 문턱 연결 · 주소 비노출).

- 구조적 천장: 후보 20개 안에 정답이 있는 비율을 정답 번호를 돌려주는 가짜 재순위기로 쟀다 — 지금 색인 B 85.4%(41/48) · H 89.7%, 고객 문장 색인 B 91.7%(44/48) · H 86.8%. 모델이 완벽해도 지금 색인에서는 B 에서 90% 를 못 넘는다.

1. **규정 문서의 고객용 문장 4개가 없다 — 지운 것은 10-12 문서 개정이고, 옛 문장을 되살리면 안 된다.** `t_doc_05#c3`(폭염 구간의 야외 항목) · `t_doc_07#c3`(대신 갈 식당이 동선에서 닿는가) · `t_doc_08#c3`(지연을 여유로 흡수할 수 있나) · `t_doc_08#c8`(출발 안내는 역산해서 만든다). 10-12 개정(`2b5ad163`)이 이 절들의 본문을 다시 썼고(예: 폭염 절은 「12~15시를 앞뒤로 옮기는 안」에서 「모든 여행의 정오~오후 세 시를 자동 이동하는 별도 규칙으로 만들지 않는다」로, 출발 안내 절은 「이동 시작 15분 전 별도 알림 규칙으로 바꾸지 않는다」가 들어감) 옛 고객 문장이 새 본문과 어긋나 빠졌고 새 문장은 안 써졌다. 그래서 이 절이 정답인 질문은 B 4개 · H 3개 · 풀 8개가 「못 찾았어요」가 됐다. **이번에 새 본문만 보고 고객 문장 4개를 새로 썼다**(AI 초안 · 본문에 없는 수치 없음 · 고객 문장 규칙 시험 통과 · 규정 문서 [t05](../../../knowledge/travel/documents/t05_weather_air-heat-quake.md) · [t07](../../../knowledge/travel/documents/t07_dining_alternative.md) · [t08](../../../knowledge/travel/documents/t08_mobility_disruption.md)). 문서 담당의 확인이 필요하고, 이 문장들이 들어간 뒤의 점수는 §4-3 에서 루나로 다시 쟀다(B 상위 3 83.3% → 91.7%). 본문이 안 바뀌어 청크 · 임베딩은 그대로다.
2. **「지금 제품」 기준선이 10-07 보고서와 다르다**: 같은 질문 242개 중 17개에서 보이는 줄이 달라졌다(위 1번 + 문장이 바뀐 절 6개). 이 보고서의 기준선은 오늘 코드 · 오늘 문서로 다시 센 값이다.
3. **가르친 E4B 는 재순위 모델로 약하다.** 같은 지시문 · 같은 방식에서 gemma4:12b 는 H 63/68 = 92.6%(후보 = 색인 E + 예상 질문)였는데 가르친 E4B 는 B 70.8~72.9% · H 70.6~75.0% 다. 후보를 뽑는 색인이 다르다는 점은 감안해야 하지만(10-07 은 예상 질문 6개를 더했다), 빈 판정이 24% 이고 앞 후보 쏠림이 있어 모델 쪽 약점으로 읽는다. 이 모델은 일정 항목 짚기용으로 가르친 것이라 규정 재순위를 가르친 적이 없다.
4. 이 PC 의 로컬 개발 DB 가 시험 중 한 번 내려갔다(가상 메모리 부족 추정) — 앱 관리 실행 설정으로 다시 띄웠다. 시험용으로 만든 복제 DB `acop_rerank_1015` 는 시험 뒤 지웠다.

## 7. 교차 인코더(bge-reranker-v2-m3) — 계속할까 접을까

**결정(사용자 2026-10-15): 이어 학습은 접는다. 제로샷 판은 「12B급을 못 쓰는 환경의 대안」으로 기록만 남긴다.**

근거(10-07 측정, [오응답 보고서 §3](2026-10-07_오응답_실제경로와_Luna_Sol_비교_x600_반영.md)):
- 제로샷은 H Recall@3 52/68 = 76.5%(12B 재순위 63/68 = 92.6%), B 38/48 = 79.2%.
- 우리 규정 자료 6,668쌍(양성 778)으로 2에폭 이어 가르쳐도 **H 76.5% 그대로, B 38 → 35/48, A 95 → 93/100 로 오히려 내려갔다.** 올라간 것은 「점수 문턱으로 정답을 보임」(30.9 → 41.2%)뿐이다. 시드 1개 · 설정 1개라 「이 방식이 안 된다」가 아니라 「이 한 번이 못 이겼다」이고, 10-07 이후 재시도 기록이 없다(그래서 「중단」 상태).
- 이번 측정으로 병목이 모델 하나가 아님이 더 분명해졌다: 후보 천장(§5) · 지워진 고객 문장(§6-1) · 결정 단위가 못 보낸 규정 질문 26% 가 먼저다. 교차 인코더를 더 가르쳐도 이것들은 안 풀린다.
- 학습 자료가 같은 규정 130조각에서 만든 합성 예상 질문이라 평가 질문과 겹칠 위험이 있고(글자 겹침 2건 제거), 평가 세트가 작아(H 68) 10%p 미만의 차이는 구분이 안 된다 — 더 가르쳐도 「좋아졌다」를 증명하기 어렵다.
- 한편 제로샷 교차 인코더(B 79.2% · H 76.5%)는 이번에 잰 가르친 E4B 재순위(B 72.9% · H 70.6~75%)와 비슷하거나 낫고, 0.6B 라 x600 의 12GB GPU 에서 가르친 E4B 와 같이 올라가며 호출이 짧을 것으로 **예상**한다(속도는 이번에 안 쟀다 `[미측정]`). 모델이 병목일 때의 현실적인 대안이다. 다만 후보를 뽑는 1단계가 달라(10-07 은 색인 E + 예상 질문) 숫자를 바로 비교하면 안 된다.

다시 여는 조건: ① 사람이 쓴 질문 300개 이상이 생겨 90% 판정이 의미를 가질 때, ② 12B급 · 유료 루나급 재순위가 지연 · 비용 때문에 거절될 때 — 그때는 이어 학습이 아니라 **제로샷 교차 인코더를 같은 측정 도구로 한 번 재서** 비교한다.
