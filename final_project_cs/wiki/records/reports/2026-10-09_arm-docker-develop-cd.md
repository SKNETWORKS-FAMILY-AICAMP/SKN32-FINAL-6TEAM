# Oracle ARM Docker 배포 준비와 자료 전송 승인 대기

ARM64 앱·웹 이미지 2개와 5분 자동 갱신·30분 실제 HTTP 검사 예약을 만들었다. **앱의 실제 서빙은 아직 완료되지 않았다.** 필수 이동 자료가 없어 기동 검사가 거절했고, 로컬 자료 전송은 자동 승인 심사에서 차단돼 사용자 승인을 요청했다.

## 달라진 구성

Oracle ARM에 Docker 29.1.3·Compose 2.40.3·Buildx 0.30.1을 설치했다. x600 서버의 기존 자동 배포는 실제로 `role-manager`를 따르고 있어 변경하지 않았으며, Oracle ARM만 사용자가 요청한 `develop`를 따른다. 이미지를 외부 레지스트리에 게시하지 않고 기존 ARM 기계에서 직접 빌드했다.

시험용 DB·고객 API·상시 작업·웹·모델 연결기를 별도 Compose 프로젝트로 묶었다. 공개 프록시 설정은 바꾸지 않았고 API·웹·DB 수신은 루프백으로 제한했다. 기존 모델 시험 서비스는 유지했다. 별도 임베딩 프로세스는 이미 보관된 모델을 사용한다.

모델 연결기는 기존 llama.cpp를 이용한다. 앱의 Ollama 계약을 실제 추론 API로 변환하며, vLLM이나 Ollama 엔진 자체를 새로 띄운 것이 아니다. 기존 시험 실행기가 다른 모델로 넘어가면 실제 모델 ID가 다르다는 오류를 내도록 고정했다. `e4bt` 합친 학습판의 정확한 oos 레시피는 이번 작업에서 새로 확정하지 않았다. 같은 엔진을 함께 사용한 기간의 지연은 단독 실행 성능과 구분해야 한다.

## 실패와 보완

첫 실행에서 필수 인증 설정 두 개가 빠져 기계 내부에서 새 값을 생성했다. 다음 실행에서는 이동 자료 6종이 없어 앱이 안전하게 기동을 거부했다. 새 앱의 반복 재시작을 멈췄으며, 기존 추론 작업은 중단하지 않았다. 자료가 없으면 다음 자동 갱신 회차도 빌드·기동을 반복하지 않고 대기한다.

초기 생성 문구 캐시가 객체 형태여서 상시 작업이 거절했다. 목록 형태로 수정한 이미지를 준비했고 최초 실패 이미지는 별도 태그로 보존했다. 관리자 권한 실행 때 저장소 소유권 검사와 홈 경로가 달라진 문제도 해당 경로에 한정해 수정했다. 중간 실패를 성공 시험으로 합산하지 않는다.

자동 승인 심사는 로컬 이동 폴더 전체의 Oracle ARM 전송에 자료·목적지에 대한 명시적 승인이 부족하다는 이유를 제시했다. 전송을 우회하지 않았다. 팀 develop의 해당 데이터 위치에는 `.gitkeep` 1개뿐임을 확인했다. 자료 파일 목록·크기·해시는 로컬에서 준비했으며 실제 고객 자료·비밀키·쇼핑몰 자료는 전송 대상에서 제외한다. 승인을 받기 전 기능을 끄거나 자료 검사를 무력화해 앱을 띄우지 않는다.

현재 웹 이미지의 `npm audit --omit=dev`는 의존성 3건(critical 1·high 2)을 보고했다. 대상은 Next.js·sharp·source-map-js이며 Next.js 수정 후보는 16.4.0으로 표시됐다. 공개 배포 전 검토와 회귀 시험이 필요하다. 개발 브랜치 원본의 의존성을 임의로 강제 갱신하거나 공개 배포 완료로 표시하지 않았다.

## 재개 순서

1. 요청한 이동 자료 전송 승인이 도착하면 준비한 목록대로 기존 Oracle ARM에 복사하고 파일 해시·앱의 자료 검사를 확인한다.
2. 실패 상태·로그를 백업한 뒤 수정된 설정과 캐시 형식으로 같은 SHA를 한 번 재개한다. 앱·웹·상시 작업·DB·모델 연결기 전체 기동을 확인한다.
3. 실제 고객 API로 시험용 여행 등록·본인 접근·다른 사용자 거절·일정 질문·잡담을 검사하고 분모에 실패·미완료를 남긴다. 같은 문항 반복은 독립 정확도 표본으로 합치지 않는다.
4. 원본 결과와 배포 SHA를 회수하고 [운영 절차](../../operations/arm-develop-cd.md) 및 날짜별 기록에 연결한다. 공개 서비스 전환·전체 RAG 품질·실시간 이동 추천·독립 보류 평가를 별도 검증한다.
