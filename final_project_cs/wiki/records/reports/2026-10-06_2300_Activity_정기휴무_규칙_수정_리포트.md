# Activity 정기휴무 규칙 수정 리포트

## 결론

성립 판정과 대체 장소가 함께 쓰는 정기휴무 판정 함수를 새로 만들었다(`closure_rules.read_closure`). CSV 「매주 X」 원문을 놓치는 건수가 307건에서 0건으로 줄었다. **못 읽은 원문은 이제 「휴무 아님」이 아니라 「모름」이다.**
공휴일·명절 조건은 `read.holiday`(한국천문연구원 특일)로 확인하도록 연결했다. 다만 **지금 운영 키가 그 서비스에 등록되어 있지 않아(HTTP 403)** 공휴일 조건은 당분간 「모름」으로 나간다.
브랜치는 `fix/activity-closure-rule`(`origin/develop` 에서 분기)이고, 아직 커밋하지 않았다.

## 바꾼 것

| 파일 | 내용 |
|---|---|
| `app/modules/travel_ops/activity/closure_rules.py` (새 파일) | `read_closure(text, at, holiday)` → 휴무/아님/모름 + 맞은 구절 + 이유 + 단서 필요 여부. 원문을 절 단위로 읽고, 절 안의 요일 · 몇째 주 · 날짜 · 명절 · 공휴일 패턴을 모두 본다. 못 읽은 조각이 남으면 모름. 한국 날짜 기준 |

| `team.py` | 허용 도구에 `read.holiday` |
| 시험 | 새 `tests/unit/travel/activity/test_closure_rules.py`(CSV 재발 방지 · 규칙 · 성립 판정 연결, 34건). 기존 3건은 위험한 기대를 바로잡았다([evidence](../evidence/2026-10-06_정기휴무_규칙_수정_검증.md) §2) |

## 동작이 바뀌는 곳 (고객 쪽)

- 정기휴무일 예약이 「불가」로 나가고 대체 장소를 찾는다. 「매주 월요일」·「토요일~일요일」·「매월 둘째 주 화요일」·「1월 1일」 같은 원문이 여기에 해당한다.
- 「모름」이 늘어난다. 예: 10/12(월) 기준 CSV 휴무 원문 1,659건 중 534건(공휴일 조회가 될 때 219건). 모름이면 사람에게 넘기지 않고 원문을 전하며 「확정하지 않았습니다」라고 말한다.
- 휴무를 **한국 날짜 기준**으로 따진다. 전에는 받은 시각의 요일을 그대로 써서, UTC 15:00(= 다음 날 00:00 KST)이면 하루 어긋났다.
- 「매주 X (단, 공휴일이면 개방)」은 공휴일 여부를 모르면 전처럼 「휴무 + 단서」로 둔다. 공휴일이면 「아님」, 공휴일이 아니면 단서 없이 「휴무」다.

## 공휴일 조회 도구를 붙일 때의 검토

| 항목 | 판단 | 근거 |
|---|---|---|
| **운영 키** | ⚠ 지금은 동작하지 않는다 | 공통 키가 특일 서비스에 미등록(403, 사유 30). data.go.kr 에서 「한국천문연구원_특일 정보」(15012690) 활용신청을 하거나 `ACOP_HOLIDAY_API_KEY` 를 따로 넣어야 한다. 그 전까지는 「모름」으로 안전하게 떨어진다 |
| 도구 예산 | ✅ 문제없음 | 성립 판정은 지금 최대 6회(예약 · 규정 · 장소 · 재난 · 기상 · 대체 후보)를 쓴다. 공휴일은 최대 3회(명절 연휴 조건일 때 그날과 앞뒤)라 합계 9 ≤ `max_steps` 12 |
| 같은 인자 반복(`ToolLoopExceeded`) | ✅ 막았다 | 날짜마다 한 번만 부른다. 시험(`test_feasible_asks_holiday_only_when_needed_and_once`) |
| 지연 | ⚠ 조건부 | 성공하면 월 단위 캐시라 사실상 0이다. 실패는 캐시하지 않아 호출마다 바깥으로 나간다. 403 은 0.1초 안팎이지만, 소스가 멈추면 `travel.source_timeout_seconds`(8초)만큼 기다린다. 첫 날짜에서 모르면 더 묻지 않으므로 최악은 성립 점검 한 번에 +8초. 개선안: `HolidaySource` 에 짧은 실패 캐시 |
| 부르는 조건 | ✅ 좁다 | 휴무 원문에 공휴일·명절·「단, 공휴일이면」 조건이 있을 때만 부른다. CSV 휴무 원문 1,659건 중 약 500건이 해당한다(공휴일·명절·날짜·「단,」 조건 포함 원문 515건 기준, 추정) |
| 의미 | ✅ 원칙에 맞다 | 특일은 「공휴일인가」만 답한다(`answers_whether_the_place_is_closed: False`). 그 장소가 쉬는지는 원문 조건과 합쳐서만 판단한다 |
| 명절 「당일」 | ⚠ 가정이 있다 | 특일 API 가 명절 사흘을 같은 이름(「추석」)으로 준다고 보고 가운데 날을 「당일」로 본다. 키가 403 이라 실측하지 못했다. 가정이 틀리면 「당일」 조건이 「모름」으로 떨어진다(위험한 오답 쪽은 아니다) |
| 캐시 만료 | ⚠ 드문 경우 | 성공한 달은 프로세스가 끝날 때까지 캐시된다. 임시공휴일이 나중에 지정되면 재시작 전까지 반영되지 않는다 |
| 대체 장소 후보 | ⚠ 아직 안 넘긴다 | 후보의 공휴일 조건은 모름 → 후보에서 빼지 않고 남긴다(「명백히 닫힌 곳만 뺀다」 원칙). 같은 날짜 조회 결과를 넘기면 정확해진다 |
| 키 없는 환경(CI) | ✅ | `travel.holiday` 가 없으면 `read.holiday` 는 `None` → 모름. 시험은 가짜 도구를 쓴다 |

## 실험 브랜치(`role-activity-test`)와의 관계

- 실험 브랜치의 `feasibility.py` 도 휴무 판정 지점을 판정 계층으로 바꿨다. 그래서 `develop` 을 실험 브랜치로 합칠 때 `_feasible_operating` 에서 **충돌이 난다.** 손으로 풀어야 한다.
- 실험 브랜치의 `judge/rule.py` 는 `FeasibilityMixin._weekday_closure_match(text, at)` 를 부른다. 감싸개를 남겨 두었으므로 합친 뒤에도 그대로 동작하고, 섀도 비교 기준이 새 규칙으로 바뀐다.
- 결함 리포트는 실험 브랜치 작업 트리(커밋 전)에서 이 브랜치로 옮겼다. 같은 경로의 파일이 두 브랜치에 따로 생겨 합칠 때 막히는 것을 피하려는 것이다.
