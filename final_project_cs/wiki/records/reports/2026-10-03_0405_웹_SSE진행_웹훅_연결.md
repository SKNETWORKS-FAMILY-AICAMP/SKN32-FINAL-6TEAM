## 점검: 서버에 있는데 웹이 쓰지 않던 것

`trip_api.py`의 `/v1/web/*` 경로 25개를 웹 `src/lib/live/*` 호출과 대조했다.

| 서버 | 웹(작업 전) | 이번 처리 |
|---|---|---|
| `POST …/messages` + `Accept: text/event-stream` | JSON 한 번, 최대 180초 대기 | 연결 |
| `POST …/trip-intakes/{id}/plan` + 같은 헤더 | JSON 한 번 | 연결 |

## 수행 내용

### 1. 공통 SSE 클라이언트 — [stream.ts](../../../frontend/apps/web/src/lib/live/stream.ts)

- **`streamApi`(채팅·일정 짜기)**
  - `Accept: text/event-stream`과 `X-User-Key`로 묻는다.
  - `accepted`·`stage`·`beat`를 진행(`OpProgress`: 단계·경과·느림·끊김)으로 넘기고, `result` 본문을 기존 JSON처럼 돌려준다.
  - `error` 이벤트는 그 `code`·`message`를 그대로 담은 오류로 바꾼다.
- **`watchIntake`(접수 읽기)**: 이벤트마다 화면이 접수를 다시 읽게 하고, 끝은 다음 중 하나로 알린다.
  - `done`: 다 읽음
  - `stalled`: 서버의 읽기 작업이 멈춤
  - `gone`: 그런 접수가 없음
  - `unsupported`: 스트림이 없는 서버
  - `lost`: 연결이 끊김
- **연결 감시**: 이벤트가 7초 없으면 끊긴 것으로 본다(명세 「beat 2번 ≈ 6초」에 여유 1초).
  - POST는 같은 본문으로 1·2·4초 뒤 다시 보낸다. 서버가 같은 요청 번호(채팅)나 같은 판(일정 짜기)을 두 번 처리하지 않기 때문이다.
  - 다 실패하면 `connection_lost`를 낸다.
- **스트림이 없는 서버**: 응답 `Content-Type`이 JSON이면 그대로 읽는다. 응답이 시작되기 전에는 기존 시간 한도를 둔다.
- **브라우저 기본 `EventSource`를 쓰지 않은 이유**: 키 헤더를 실을 수 없다. 그래서 기존 초인종(`events.ts`)처럼 `fetch`로 읽고 그 파서를 함께 쓴다.
- **`progressText`**: 서버 단계 이름을 고객 언어 문장으로 바꾼다. 서버 문구는 한국어뿐이라 영어는 웹이 둔다.

### 2. 화면 연결

- **채팅**([trip-home.tsx](../../../frontend/apps/web/src/features/trip/trip-home.tsx), `gateway.ts`): 기다림 줄이 「요청을 이해하는 중이에요… (N초)」, 「· 응답이 느려요 (12초째)」, 「서버와 연결이 끊겼어요 — 다시 연결하는 중이에요…」로 바뀐다.
- **「일정 짜 줘」**(`intake.ts`, `intake-review.tsx`): 「짜는 중」 단추 아래에 서버 단계(짜기 → 조건 확인 → 등록)가 보인다.
- **접수 읽기**([use-intake-events.ts](../../../frontend/apps/web/src/features/intake-review/use-intake-events.ts))
  - 스트림을 따라 다시 읽는다. 끊기면 초인종과 같은 간격(1~30초)으로 다시 붙는다.
  - 스트림이 없으면(404/405·연결 수 상한) 전처럼 1.5초 조회로 바꾼다.
  - 「멈춤」이면 「서버가 이 계획을 끝까지 읽지 못했어요」와 「다시 올리기」를 보인다.
  - 읽는 화면에는 「연결이 끊겼어요」·「읽는 데 시간이 걸리고 있어요」를 보인다.

### 3. 디스코드 웹훅 — [webhook.ts](../../../frontend/apps/web/src/lib/webhook.ts) · [profile/webhook.tsx](../../../frontend/apps/web/src/features/profile/webhook.tsx)

- **온보딩 카드**
  - 키가 있으면 카드를 떠날 때 바로 `PUT`한다.
  - 키가 없으면 **이 페이지 메모리에만** 두었다가, 첫 등록으로 키가 생기면 `ContactSync`가 올린다.
  - 브라우저 저장소에는 쓰지 않는다(비밀값). 빈 칸은 「입력 안 함」이라 저장된 웹훅을 지우지 않는다.
- **마이페이지**
  - 가린 주소와 상태(시험 전·도착·거절)를 보인다.
  - 「시험 메시지 보내기」의 결과 문장을 보인다(ok·invalid·rate_limited·failed, 429 `too_soon`의 서버 문장).
  - 일정 알림 발송(서버 2단계)은 「준비 중」으로 적는다.
- **수정 화면**
  - 새 주소를 넣으면 바뀌고, 비워 두면 그대로 둔다.
  - 「등록된 웹훅 지우기」는 `null`을 보낸다. 등록된 주소는 다시 보여 주지 않는다(서버도 주지 않음).

## 작업 중 바로잡은 것

- **웹훅이 두 번 올라감(시험이 잡음)**
  - 키 발급 때 키 변경 신호가 두 번 온다(키, 안내 문장). 두 번 다 같은 웹훅을 보냈다.
  - 보내는 중이면 같은 요청을 함께 기다리게 고쳤다. 단위 시험도 더했다.
- **키가 있을 때도 웹훅이 두 번 올라감**
  - 온보딩이 약관 카드와 취향 카드로 넘어갈 때마다 연락처 확인을 거친다. 웹훅은 저장된 값을 읽을 수 없어(서버가 돌려주지 않음) 같은 값을 다시 보냈다.
  - 이 화면에서 마지막으로 보낸 값을 기억해 같은 값은 건너뛴다.
- **`watchIntake` 단위 시험이 멈춤**: 연결 감시가 요청만 끊고 읽기를 끝내지 않았다. 읽기도 함께 끝내게 했다(`streamApi`와 같게).
- **live 「멈춤」 시험의 선택자**: Next.js 경로 안내 요소도 `alert`라 2개가 잡혔다. 문장으로 골랐다.
- **demo의 웹훅 안내가 틀림**: 카드에 「첫 여행을 등록하면 서버에 저장돼요」라고 썼는데 demo는 저장하지 않는다. 안내를 모드별로 나눴다(demo는 「실제 서버에 연결됐을 때만 저장돼요」).
- **실서버 확인용 개발 서버 고장**: 몇 시간째 켜져 있던 3100의 내부 작업자가 죽어 `/intakes/…`가 열리지 않았다. 다른 빌드 폴더로 다시 띄웠고, 그때 Next.js가 자동으로 고친 `tsconfig.json`은 되돌렸다.

## 남은 문제·다음 작업

1. **develop 병합 때 계약 시험**
   - develop의 `tests/contract/test_web_client_contract.py`는 웹 호출을 `api(`·`send(` 모양으로만 읽는다.
   - 그래서 `streamApi(…)`와 `fetch(`${API_BASE}/v1/web/…/events`)`(role-manager에 이미 있는 초인종 포함)를 「호출로 읽지 못한 파일」로 실패한다.
   - 시험 안내대로 `_CALL`을 넓혀야 한다. 그 파일은 develop에만 있어 role-manager → develop 병합에서 한다.
2. **웹훅 2단계**: 서버가 고객 웹훅으로 일정 변경 알림을 보내는 부분은 서버에 없다(사용자 확인 뒤 서버 작업).
3. **실서버 시험 메시지**: 디스코드로 바깥 요청이 나가므로 이번에 누르지 않았다. 실제 채널로 확인하려면 사용자가 자기 웹훅으로 한다.
4. **다른 세션이 남긴 미추적 파일**: Codex가 이 작업 트리에 둔 `2026-10-03_0348_웹감사_교차검증` 리포트·근거·history 3개는 이번 변경에 넣지 않았다.
