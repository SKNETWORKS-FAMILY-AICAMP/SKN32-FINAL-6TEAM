# 택시 예산 여유 보정과 시각 일치 검증

서울 중형택시의 예산 여유를 계산 자료로 보정하여 반영했다. 안내 예산은 법정 미터 예상액 + 별도 예산 여유 + 통행료다. 이번 내부 검증에서 목표를 충족했으며 실제 결제액 상한을 보장하는 값은 아니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 보정값 산정 | 완료 | 153/153 = 100% |
| 별도 경로 검증 | 목표 충족 | 38/40 = 95% |
| 코드 시험 | 통과 | 13/13 = 100% |

## 문제와 원인 확인

직전 보고의 154/200 = 77% 낮은 예상액은 당시 조회한 카카오 요금과 우리 낮 10:30 기준 계산을 섞은 집계였다. 원시 값은 변경하지 않고 당시 tool_result의 경로 번호·차량 소요·거리·요금이 최종 원자료와 일치하는 결과에서 조회 완료 시각을 복원했다. 최초 40쌍의 read_at은 그대로 썼으며 원자료를 교체하거나 카카오 API를 새로 호출하지 않았다.

조회 시각은 199/200 = 99.5% 복원했다. 완료 시각 전 90초 범위(최초 40쌍은 기록 시각 전 10초)의 할증률이 변하는 6쌍과 시각 복원 미완료 1쌍을 제외하여 193쌍을 재계산했다. 조회 완료 시각을 출발 시각의 근사로 사용했다. 정확한 실시간 교통의 재현이 아니라 같은 요일형·시간대·심야 할증 조건에 맞춘 로컬 속도 프로파일 계산이다. 경로도 우리 도로망과 카카오 추천 경로가 서로 다르다.

같은 시간대에 기존 10% 여유로 계산하면 카카오보다 낮은 것은 97/193 = 50.3%, 차이율 중앙은 −0.57%였다. 시각 혼합뿐 아니라 예산 여유 부족도 남아 있었다. 따라서 77%라는 값을 요금 산식만의 오류율로 읽거나 그대로 운영할 이유는 없다.

## 계산 방법과 반영

거리층별로 고정 SHA256 순서(seed taxi-budget-20261008)를 정하고 앞 80%를 계산군, 나머지를 검증군으로 분리했다. 합계 계산군 153 · 검증군 40이며 검증군으로 여유율을 다시 튜닝하지 않는다. 모두 이전에 집계한 기존 자료이므로 새로 확보한 미관측 holdout이라고 부르지 않는다.

계산군에서 `(카카오 예상액 − 우리 통행료) / 우리 미터 예상액` 비를 정렬하고 `ceil((n+1) × 0.95)`번째(표본 수를 넘으면 마지막) 값을 사용했다. 그 값 1.3601895734597156에서 1을 빼고 퍼센트점 단위로 올림하여 **37%**로 정했다. 통행료에는 이 비율을 곱하지 않는다.

- 서울 중형: 미터 예상액의 37%와 최소 1,000원 중 큰 값, 100원 단위 올림.
- 대형·모범: 이 자료가 보정 근거가 아니므로 기존 10% 가정을 유지한다. 이를 검증한 값이라고 주장하지 않는다.
- 예: 미터 예상액 10,000원 → 예산 여유 3,700원 → 안내 예산 13,700원. 이는 카카오 원자료의 개별 값을 옮긴 예가 아닌 산식 설명이다.
- 심야 할증은 미터 산식에서 먼저 적용한다. 심야 20/40%를 예산 여유로 다시 중복 적용하지 않는다.

보정값·최소 여유·올림 단위는 이동 규칙 파일 taxi.planning_budget 한 곳에 둔다. CarService가 해당 차종 값을 읽는다. 미터 산식 taxi_fare는 이번 여유율 보정으로 바꾸지 않았다. 기존 화면의 ‘예상 요금’과 실제 결제액 차이 안내도 유지한다.

## 검증 결과와 실용적 한계

| 자료 | 카카오 예상액 이상 | 전체 쌍 | 비율 | 경로별 차이율 중앙 |
|---|---|---|---|---|
| 계산군 | 147 | 153 | 96.1% | +22.7% |
| 계산에 쓰지 않은 검증군 | 38 | 40 | 95.0% | +27.7% |
| 전체 비교 가능 자료 | 185 | 193 | 95.9% | +23.0% |

이상 여부는 안내 예산 ≥ 카카오 예상액, 차이율은 `(안내 예산 − 카카오 예상액)/카카오 예상액 × 100`이다. 전체 수치는 계산군을 포함하므로 별도 검증 수치와 구분한다. 분할 후 검증 목표는 90%로 고정했다. 현재 검증군 40쌍 중 2쌍은 여전히 카카오보다 낮다. 전체 8쌍도 낮은 상태다.

37%는 무작정 붙인 임의 금액이 아니라 계산군의 높은 쪽 오차를 반영한 **잠정 예산 가정**이다. 높게 안내하는 대가로 별도 검증 차이 중앙 +27.7%가 발생한다. 40쌍은 향후 모든 서울 여행에서 95%를 충족한다는 통계 보장을 주지 않는다. 다른 시각·새 경로 및 실제 미터 결제액 검증이 쌓이면 여유율을 재산정해야 한다. 낮은 잔여 사례의 경로 차이 개선은 여유율로 숨기지 않고 다음 정확도 작업의 대상이다.

## 파일과 재현

- 구현: scripts/mobility/calibrate_taxi_budget.py, app/domains/travel_ops/instances/mobility/engine/car.py 및 engine/rules/rules_v0.3.json.
- 시험: tests/unit/travel/mobility/test_taxi_billing_mode.py, test_taxi_budget_calibration.py. 기존 test_car_fare.py의 중형 병산 설명도 현행 산식에 맞췄다.
- 계약: wiki/external/rest-endpoints.md의 예상액 의미를 코드 변경 전에 갱신했다.
- 입력(모두 git 밖): datasets/mobility/raw/kakao_golden/taxi_time_aligned_v1.json. 입력 sha256 ea4a43af9dfe9d2c75f3a43597f1eb93da649c5b4a59f7e764205d9fd8f5db21.
- 결과(모두 git 밖): taxi_budget_calibration_v1.json, taxi_time_aligned_v2.json. 시각 복원 자료 car_read_times_recovered_v2.json, 원시 비교 compare_resume_200_v5.json은 유지했다.

cs 작업 폴더에서:

```powershell
python -m scripts.mobility.calibrate_taxi_budget --aligned ../datasets/mobility/raw/kakao_golden/taxi_time_aligned_v1.json --out ../datasets/mobility/raw/kakao_golden/taxi_budget_calibration_new.json
python -m pytest tests/unit/travel/mobility/test_taxi_billing_mode.py tests/unit/travel/mobility/test_car_fare.py tests/unit/travel/mobility/test_plan_taxi.py -q
python -m pytest tests/unit/travel/mobility/test_taxi_budget_calibration.py -m 'live or not live' -q
```

출력 파일은 이미 존재하면 덮어쓰지 않는다. 개별 경로 자료의 출력은 raw 폴더 밖이면 실패한다. 검증군 값 변경이 산정 계수에 영향을 주지 않는지, 중복·시각 누락을 조용히 건너뛰지 않는지, 실제 설정값과 다시 계산한 계수가 같은지 검사했다. 시험 출력: 10 passed in 28.60s; 3 passed in 2.93s. 변경 파일 Ruff All checks passed. 전 실행에 pyreadline3 종료 처리 경고가 있었지만 pytest 종료 코드는 0이었다.

mock 서버 시험 (화면 반응): 이번 보정에서는 안 했음. 화면 계약을 바꾸지 않았으며 직전 예상액·고지 화면 시험은 1/1 통과했다.
실서버 확인 (서버 응답): 안 했음. 배포 중인 cs 프로젝트 서버에 반영하지 않았다. push도 하지 않았다.

변경 전 사본은 수정 파일 옆 _backup/2026-10-08_택시보정전/*.bak에 보관했다. 이전 10% 판과 비교 원자료를 덮어쓰지 않았다.

외부 Codex 독립 의견을 codex-consensus 스킬로 요청했으나 자동 승인 검토가 내부 계산 자료를 외부 서비스로 전송할 사용자 승인이 확인되지 않았다는 이유로 실행 전에 거부했다. 독립 합의가 성립했다고 보고하지 않는다. 로컬 재계산과 시험을 수행했다.
