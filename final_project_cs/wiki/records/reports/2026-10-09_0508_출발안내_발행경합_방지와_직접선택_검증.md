# 출발 안내 저장과 현재 재탐색 적용을 같은 여행에서 순서대로 처리

## 결함 재현과 변경

실제 로컬 개발 DB에서 문구 계산 뒤 별도 연결로 새 일정 판을 쓰는 순서2조건(이동 항목 유지/교체), 제안 계산 뒤 안내를 저장하는 순서2조건(단일/묶음), 현재 판에 없는 이동1조건을 재현했습니다. 수정 전5/5조건이 기대 안전 조건을 어겼습니다. 이5건은 경로 정확도 표본이 아닙니다.

출발 안내 저장과 자동 출발 재탐색 적용은 tenant/trip 행을 FOR NO KEY UPDATE로 잠급니다. 안내는 현재 버전과 이동 항목을 검사하며 낡았으면 StaleDeparture를 반환하고 반복 결과 stale에 따로 셉니다. 실제 안내 생성기는 반드시 계산한 version을 전달합니다. 이미 있는 안내의 중복은 already이며 낡은 안내와 섞지 않습니다. 잠금은 DB 트랜잭션 끝까지 유지되고 외부 조회는 잠금 전에 실행합니다.

적용기는 단일/묶음 항목의 departure_revalidation 원인을 확인하고, 같은 잠금 아래 이미 안내한 이동이면 ActionConflict를 반환합니다. 기존 코어는 action_target_changed로 처리하며 이 단위는 코어 상태 전이나 알림 배달을 새로 만들지 않았습니다. 고객 직접 선택(customer_request/rollback/customer_choice)은 자동 출발 재탐색 조건을 적용하지 않습니다. 현재 위치가 없어 계획 출발지를 실제 위치로 추정하지 않습니다.

행 잠금은 일반 UPDATE와도 충돌하며 기다린 뒤 갱신된 행을 읽는 동작을 공식 문서로 확인했습니다. 교착 위험을 줄이기 위해 두 경로의 잠금 대상/순서를 동일 여행 행으로 고정했습니다. 근거: [PostgreSQL16 행 잠금](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS). 이 근거는 운행 정확도나 메시지 도착 보장이 아닙니다.
