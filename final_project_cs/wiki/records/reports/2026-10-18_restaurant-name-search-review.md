# 식당 상호 검색 누락의 경로 구분

“레몬그라스 타이”에 대한 카카오 조회는 운영 담당의 제한된 정상 예산 조회에서 성공했습니다. 따라서 실제 사용 화면의 입력·종류 필터와 결과 전달을 먼저 구분해야 합니다. 특정 지점·영업시간·예약 가능성은 확인하지 않았습니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 최초 읽기·수동 검색 경로 | 읽기 확인 | 2/2 = 100% |
| 카카오 실제 조회 | 운영 담당 확인 | 2/2 = 100% |
| 사용한 화면·대상 항목 종류 | 사용자 응답 대기 | 분모 미확정 |
| 제품 수정·배포 | 실행 안 함 | 0/2 = 0% |

확인 시각: 2026-10-18 17:43 KST. 이 담당은 격리 소스만 읽었고 원격·외부 API·고객 변경은0회입니다. 아래 실제 응답은 운영 담당이 실행한 별도 근거입니다.

## 실제 응답과 코드 범위

운영 담당의 오라클 독립 검증에서 원문 “레몬그라스 타이”와 무공백 “레몬그라스타이”가 각각 HTTP200, 서울 음식점(FD6)10개를 반환했습니다. 소요는0.212초·0.137초였고 카카오 일일 운영계수는74→76/100입니다. 사업자 조회가 성공했다는 뜻이며 사용자 화면에서 그 결과를 받은 사실·특정 지점 확정·현재 영업을 입증하지 않습니다. 별도의 SQL 이름 조회에서 공용 장소·관광 목록·요식 원장·인허가4표의 해당 매칭은0건이었습니다.

### 수동 검색

[검색 API](../../../app/domains/travel_ops/entry/trip_api.py)의 `place-search`는 [후보 검색](../../../app/domains/travel_ops/components/intake/candidates.py)의 `search`를 호출합니다.

- DB 이름 조회는 원문 `ILIKE`이므로 “레몬그라스 타이”와 “레몬그라스타이”를 같은 이름으로 찾는 것이 아닙니다. 최종 비교·정렬의 `normalize_full`은 공백을 제거하지만, SQL이 이미 제외한 행을 복구하지 못합니다. 수동 검색은 공용 `places`의 `dining_ledger` 행을 읽고 인허가 표 자체는 읽지 않습니다. 이번 SQL4표에 매칭이 없다는 관측에서는 이 차이만으로 실제 원인이 확정되지는 않습니다.
- 카카오 검색에는 정돈한 원문을1회 전달합니다. 기준점이 있으면 [카카오 어댑터](../../../app/domains/travel_ops/ports/data_sources/kakao_local.py)가 반경20km·거리순·10건 한 페이지를 사용하며, 비었을 때 서울 전체 재조회는 없습니다. 기준점이 없으면 서울 사각과 주소의 서울 여부로 제한합니다. 이번 운영 담당의 전역 조회 성공만으로 사용자의 기준점·반경 조건도 통과했다고 보지는 않습니다.
- FD6·CE7 결과는 `dining`으로 태그한 뒤 원래 항목의 종류와 다른 후보를 제거합니다. **원래 항목이 activity이면 정확 상호의 FD6 결과도 모두 제외**할 수 있고 `notes=no_same_kind`를 반환합니다. 이미 같은 날 일정에 같은 이름·300m 안 장소가 있으면 제외하는 중복 조건도 있습니다.
- 정확 상호 수동 검색에는 실내·우천 안전 대안 전용 검사가 들어가지 않습니다. 운영시간 미확인도 검색 목록에서 즉시 삭제하는 조건이 아닙니다.

### 최초 계획 읽기

[장소 해석](../../../app/domains/travel_ops/components/intake/places.py)은 공백·기호 제거 후 정확 이름·지점·접두·오타를 대조합니다. [접수 처리](../../../app/domains/travel_ops/components/intake/pipeline.py)의 `_place_kind_hint`는 끼니가 명시된 경우 dining, 산책·관람 등 명시된 경우 activity, 그 외에는 None입니다. 일반 상호만 입력했다고 activity를 강제하는 경로는 아닙니다.

이번 카카오 결과에는 지점명이 없는 동일 상호가2개이며 지점명 후보도 여럿입니다. `_kakao_match`는 원문과 같은 하나를 유일하게 정할 수 없으면 임의 확정하지 않습니다. 후보는 앞뒤 일정 기준으로 임시 선택하고 확인을 요구할 수 있습니다. 특정 지점이 미제공인 상황을 “식당이 없다”로 설명하면 안 됩니다. 구체 지점까지 일치한 입력과 지점 미지정 입력을 구분해야 합니다.

### 화면이 사유를 버리는 지점

[웹 검색 연결](../../../frontend/apps/web/src/features/plan-check/use-server-review.ts)의 `search`와 `searchToAdd`는 `found.results`만 변환하고 `found.notes`를 넘기지 않습니다. backend가 결과를0개와 `no_same_kind`·`kakao:timeout`·예산 차단으로 구분해도, 수동 검색 화면에는 일반적인 빈 결과로 표시될 수 있습니다. 이 코드 경로는 사용자 환경 문제를 입증하지 않습니다. 실제 제보가 수동 교체·추가인지, 최초 읽기·검증인지, 채팅인지가 아직 필요합니다.

## 다음 확인과 최소 후보 — 미적용

운영 담당은 이미 사용한2회의 카카오 조회를 반복하지 않습니다. 사용 화면과 대상 항목 종류·같은 날 중복 여부·사용한 검색 기준점을 읽기 확인한 다음, 같은 제공 결과를 재생해 필터 전후 개수와 `notes`를 비교하면 추가 외부 조회 없이 제외 지점을 확인할 수 있습니다.

가능한 최소 수정은 검색 사유를 화면에 전달하고, 고객이 특정 상호를 검색하는 흐름에서 해당 장소의 실제 분류를 보여 준 뒤 종류 변경을 명시적으로 처리하는 것입니다. 산책·관람 대안에 임의 식당을 섞거나 상호만 보고 지점을 확정하지 않습니다. 이 후보는 아직 구현하거나 배포하지 않았습니다.
