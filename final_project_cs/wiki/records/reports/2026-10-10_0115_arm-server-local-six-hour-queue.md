# Oracle ARM 기계 자체의 6시간 시험 공급과 상시 작업자

사용자 지시에 따라 Oracle ARM 기계 안에 6시간분 시험 대기열을 보충하는 타이머와 상시 작업자를 설치했습니다. PC·Codex 예약은 필요하지 않습니다. 기존 자동 배포도 원래 기계 내부 실행이었으며 이를 명확하게 보고하지 못했던 점을 정정합니다. 이번 변경은 옛 30분 단발 검사 방식을 지속 대기열로 바꾼 것입니다.

## 자원 측정과 남은 조건

기존 추론 작업의 5초 간격 61개 표본, 01:10:02~01:15:02 KST 약 300초 구간에서 두 코어 전체 용량 대비 CPU 평균 88.44%였습니다. 표본이 각 직전 구간을 나타내므로 합산 측정 시간은 305.07초입니다. 기계 전체 busy 평균 91.01%, steal 평균 0.19%였습니다. 단기 관측이며 24시간 유지의 증거는 아닙니다. 디스크 사용 55,931,056,128바이트(55.93GB), 여유 46,940,262,400바이트(46.94GB)였습니다. 의미 없는 CPU 소모 작업은 만들지 않았습니다.

앱이 요구하는 이동 자료 67개·203,806,783바이트의 Oracle ARM 전송은 앞선 자동 승인 심사에서 payload/목적지에 대한 구체적 승인 근거 부족으로 거절됐고 승인 대기 중입니다. 이번 지시의 기계 자체 예약 변경만 수행했으며 해당 전송을 우회·반복하지 않았습니다. 이 조건을 무시하거나 이동 기능을 꺼서 앱 검사를 통과시키지 않았습니다. 조건이 해결돼 검증된 배포가 생기면 작업자는 다음 확인 회차에 자동 소비를 시작합니다.

## 변경·복구와 경계

[구현](../../../deploy/arm/serving_queue.py) · [HTTP 검사](../../../deploy/arm/serving_checks.py) · [시험](../../../deploy/arm/test_serving_queue.py) · [운영 정본](../../operations/arm-develop-cd.md).

새 유닛은 `tripilot-arm-refill.timer/.service`, `tripilot-arm-work-queue.service`이며 한국 시간 00·06·12·18시에 공급합니다. 상시 작업자는 실제 완료 시간으로 다음 수량을 보정하고, 소진 전에 중간 보충합니다. 잠금으로 단일 작업자를 보장하고, 한 회차마다 배포와 순서를 나눕니다. 실패 프로필은 같은 SHA에서 격리하며 미실행 분모를 보존합니다.

기존 x600 서버의 기계 내부 fetch→변경 확인→이미지 빌드→건강 검사→실패판 보존 방식을 참고했습니다. x600 서버의 배포 브랜치·프로세스는 바꾸지 않았습니다. 기존 모델·DB·이미지를 삭제하지 않았고 외부 공개·push·새 결제·GPU 임대를 하지 않았습니다.

설치 전 기계 내부 유닛은 제어 도구 `_backup/` 아래 시각별로 보관했습니다. 로컬 문서·스크립트 백업 목록은 [백업 기록](../../../../program/research/daily_rag_slm/arm_queue_backup_2026-10-10.json)에 있습니다. 일일 연구와 6시간 결과 보고는 유지하지만 Oracle ARM 실행 자체의 필수 조건으로 사용하지 않습니다.
