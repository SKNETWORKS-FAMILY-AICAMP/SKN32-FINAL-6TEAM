# 쇼핑 지점끼리 운영시간 · 휴무 옮겨 적기 (2026-10-16)

사용자 지시: 「쇼핑은 같은 브랜드 다른 지점인 경우 운영시간이나 휴무를 동일하게 반영할 수 있는 부분이 있음 — 그 부분 고려한 API 호출 일정」 → 「develop 에서 작업」.

|---|---|
| 쇼핑(38) 전체 행 | 4,679 |

★앞서 대화에서 말한 「쇼핑 3,447건」은 브랜드 행 687건을 포함한 수였다 — 부를 수 있는 것은 위 2,761건이다.

## 왜 입점 매장이 먼저인가 (받은 1,232곳으로 잰 값)

| 묶음 | 2곳 이상 묶음 | 70% 이상 같은 운영시간 |
|---|---|---|
| 입점 매장(백화점 · 아울렛 · 몰) | 40 | 29 / 40 = **72.5%** |
| 입점 밖 단독 지점의 브랜드 | 67 | 22 / 67 = **32.8%** |

입점 매장 휴무는 대부분 「명절」이다(현대아울렛 동대문 33/33, NC 신구로 22/22). 브랜드는 다이소(50/52) · 롯데마트(11/11)는 맞지만 나이키 · 아트박스는 지점마다 다르다.
비교는 `<br>` · 공백 · 「-」/「~」 · 「매일」 차이만 없애고 했다(`sibling_hours.same_text`).

## 만든 것

- `app/domains/travel_ops/instances/activity/data_processing/sibling_hours.py`
  - 묶음: 제목의 입점 매장(`venue:롯데백화점잠실`)이 먼저, 없으면 `brand` 칸(`brand:다이소`). 제목 첫 단어로 브랜드를 짐작하지 않는다.
  - 옮기는 기준: 근거 3곳 이상, 입점 매장은 2/3 이상 · 브랜드는 90% 이상이 같은 값. 근거는 TourAPI 가 직접 준 값뿐(옮긴 값 · 사람 값은 근거가 아니다).
  - 옮기는 칸은 `business_hours` · `closed_days` 둘. 연락처는 옮기지 않는다.
  - 출처 `field_sources`: `{"by": "sibling", "group", "basis": [근거 contentid ≤5], "checked"}`. 다시 돌리면 같은 결과이고, 근거가 더는 맞지 않으면 옮긴 값을 거둔다.
- `fill_tourapi_details.py`
  - `--intro-only` — detailIntro2 만 부른다(장소당 1번). 운영시간 · 휴무 · 문의처(`infocentershopping`)는 이 응답에 있다.
  - `--siblings` — 쇼핑을 **표본 → 혼자인 곳 → 엇갈린 묶음 → 옮겨 적은 곳** 순으로 받고, 받은 뒤 옮겨 적는다. 순서는 실행마다 다시 계산한다(표본을 받아 묶음이 정해지면 그 나머지는 뒤로 간다).
  - `field_sources` 검사가 `by=sibling` 형식(네 키 · 칸 두 개 · basis 숫자 id)을 확인한다. TourAPI 가 그 지점 값을 주면 사람 값과 같은 규칙으로 바뀌고 출처가 지워진다.
- 표시: `place_info.official_web_note` 가 `by=sibling` 칸을 「운영시간: 같은 매장 다른 지점 값(추정)」으로 말한다 — 전에는 이 출처가 「공식 페이지 확인」 · 「직접 확인」으로 보였을 것이다.
  `scripts/enrich_place_catalog_from_csv.py` 의 `hours_read.note` 문구도 추정 값을 포함하도록 고쳤다(출처 이름 `official_web` 은 그대로 — 관광공사 값으로 바뀌는 규칙이 같다).

## 호출 일정 (하루 900회 — 지금 쓰는 `--max-calls`)

```
python -m app.domains.travel_ops.instances.activity.data_processing.fill_tourapi_details --types 38 --intro-only --siblings --max-calls 900
```

| 날 | 받는 것 | 호출 |
|---|---|---|
| 1일차 | 표본 193 + 혼자인 곳 707 → 받은 뒤 바로 옮겨 적기 | 900 |
| 2일차 | 혼자인 곳 나머지 301 + 엇갈린 묶음 최대 599 | ≤ 900 |
| 3일차 | 엇갈린 묶음 나머지(최대 117) | ≤ 117 |
| (선택) 4일차 | 옮겨 적은 곳을 직접 받아 추정을 확인 값으로 바꾼다 | ≤ 844 |

엇갈린 묶음 716 은 지금 근거가 3곳 미만이라 정해지지 않은 묶음을 포함한 **최대값**이다 — 1일차 표본으로 정해지는 묶음은 4번 줄로 내려간다.
지금 방식(장소당 2번 · 5,522회 ≈ 6.1일)과 비교: 필수분 ≈ 1,917회(2.1일), 확인까지 2,761회(3.1일).

## 남은 한계 · 확인 필요

- 하루 1,000회 한도가 상세기능(detailCommon2 · detailIntro2)마다 따로인지 확인하지 못했다(data.go.kr 키 상세에서 본다). 서버 새벽 정기점검이 같은 키를 쓰면 여유를 둔다(`wiki/operations/call-budget.md`).
- 입점 매장 안에서도 지점마다 10:20 / 10:30 처럼 다른 곳이 있다 — 옮긴 값은 추정으로만 표시한다. 판정이 추정 값을 확인 값보다 약하게 다루는지는 이번에 바꾸지 않았다.
- 실제 호출 · CSV 쓰기 · DB 적재(`enrich_place_catalog_from_csv.py`)는 아직 하지 않았다.
