# 여행자 확인 체크리스트 — 서버 코어 쪽 반영 (2026-10-03)

## 위층 (코드를 안 본 사람용)

**결론.** 체크리스트 85가지 중 **서버가 입력·소스 없이 스스로 할 수 있는 8가지**를 코드에 반영했습니다. 전부 로컬 커밋이고(push 안 함), 시험이 돕니다. 나머지는 이유가 있어 못 했습니다(아래).

| 할 일 | 상태 | 진행 |
|---|---|---|
| 반영할 수 있는 항목(입력 연결·소스 필요 제외) | 끝 | 8/8 = 100% |
| 시험 — 새로 만든 것 | 통과 | 28건 + 이어받은 작업 23건 |
| 전체 회귀(`-m "not live"` 전체, 17분): **3,112 통과 · 실패 16.** 그중 1건(감시 시험 — 알림에 원인 코드 이름 `road_closed` 가 새는 것을 못 박고 있었다)은 새 기대로 고쳐 통과시켰다. **남은 15건은 이번 변경 밖이다** — 임베딩 서버가 꺼져 있어 접속이 거절되는 RAG 13건 · UI 쪽 웹훅 모양 시험 문자열을 잡는 보안 검사 1건 · 이동팀 엔진 시험 1건(이 변경을 넣기 전에도 같은 시험이 실패했다). 이 PC 에서만 확인한 결과다.
| 적대 검토(Claude opus — 코덱스 한도 소진) | 끝 — 지적 10건 중 9건 고침 · 1건 한계로 적음 | 9/10 = 90% |
| 체크리스트 문서의 칸 갱신 | 검증 세션이 함 | 1/1 = 100% (검증 세션 보고) |

**고객에게 달라지는 것(예)**
- 외부 AI가 서울 오전 10시를 세계 표준시(새벽 1시)로 적어 보내도 「아직 열기 전」이라고 거절하지 않습니다(H3).
- 「30분 늦어요」라고 하면 점심 식당만 보고 「괜찮아요」라 하지 않고, 점심이 밀려 **뒤 일정이 문 닫는 시각에 걸리거나 예약 시각에 늦으면** 어느 것이 왜 걸리는지 알려 줍니다(L2). 일정은 바꾸지 않습니다.
- 받은 일정에 같은 곳이 두 번 · 점심이 빠짐 · 지도 위를 왔다 갔다 · 22시 넘어 끝남 · 라스트오더 직전 도착이 있으면 「살펴볼 점」으로 알립니다(T7·T8·T9·T13·O4). **거절이 아니라 알림**입니다.
- 시나리오 감시·새벽 확인도 일정을 바꾸기 전에 일정 전체를 다시 확인합니다(T5).
- 필수 칸이 비어 등록이 거절되면 **어느 칸**이 문제인지 알려 줍니다(I1).

**정하실 것.** 없습니다. 아래 「못 한 것」은 입력·데이터가 필요해 다른 세션(ui·intake·이동)이나 사용자 결정이 먼저입니다.

## 적대 검토 결과와 반영 (아래층)

검토는 **Claude opus 에이전트**가 했다(코덱스 한도가 2026-10-04 12:00 까지 소진이라 대신했다 — **코덱스 재검토는 그때 다시 한다**). 코드를 읽고 **실제로 돌려 재현한** 지적만 받았다.
위험이 큰 것부터 고쳤고, 고친 것마다 **고치기 전에 실패하는 시험**을 먼저 만들었다(재현 시험 30개 중 26개가 처음엔 실패).

| 지적(쉬운 말) | 어떻게 틀렸나 | 한 일 |
|---|---|---|
| **장소 값 하나가 비뚤어지면 그 여행 화면이 영구히 500** | 식당의 브레이크 시각이 `"15:00~17:00"` 같은 모양이면 새 품질 점검이 예외를 내고, 여행 화면이 이 점검을 매번 불러 **그 여행은 열 때마다 서버 오류**였다 | 브레이크 시각을 **한 곳에서 관대하게** 읽고(`place_hours.break_span` — 읽을 수 없으면 「모름」), 점검 하나가 죽어도 나머지는 나가며 죽은 점검은 **로그와 `quality_check_skipped` 경고로 센다**(조용히 빼지 않는다) |

**검증 체크리스트(ui) 세션이 짚은 것**(코드를 읽고 본 것): ①재판정 실패 알림에 `closed_on_day` 코드 이름이 그대로 들어감 → **고쳤다**(알려진 코드는 말로 바꾸고 모르는 코드는 안 싣는다) ②MCP 오류 문장 허용 목록에 `fields` 가 없음 → **고쳤다**
③같은 곳 두 번(T8)은 같은 날 안에서만 잡는다 → **한계로 적었다** ④서울로 안 바꾸는 곳 — 대체 식당 판정은 **고쳤다**. 설문 기본 하루 창의 날짜(`trip_api.py`)는 `_seoul` 을 거치지만 **`_seoul` 이 시간대 있는 값을 안 바꾸고 있었다**(이름과 다르게 시간대 없는 값에만 서울을 붙였다) —
검증 세션의 재지적으로 확인해 **고쳤다**: `_seoul` 이 서울로 바꾸고, 끼니 이름표 · 되돌리기 자리 이름 · 채팅 끼니 말 찾기 두 곳 · 변경 알림 문구의 시각 서식 다섯 곳을 서울 시계로 읽게 했다(`test_seoul_hour_readers.py` — UTC 로 온 시각으로 만든 시험, 고치기 전 5개 실패).
검증 세션이 두 번째로 짚은 자리도 같은 방식으로 고쳤다 — 식당 안내 꼬리의 「(HH:MM 입장)」 · 감시가 활동을 바꾼 알림의 「오전/오후」 · 고객 요청 변경 알림의 「(HH:MM 시작)」 · 조건을 푼 안의 「HH:MM으로 늦추면」 ·
변경 링크 화면의 시각 · 일정 응답의 `starts_at`(서울 +09:00 — 지도 날짜 묶음) · 날씨 소스의 예보 칸(서버 PC 시간대가 아니라 서울). 앞 정적 시험이 `객체.starts_at:%` 꼴만 잡아 변수 꼴이 빠져나갔던 것도 넓혔다.
계획서 링크 화면 · MCP 요약은 이번에도 안 건드렸다(MCP 는 웹 응답의 시각을 읽으므로 응답이 서울이 되면서 같이 맞는다).

**안 고친 것**: 고객이 고르는 보류 제안의 **선택지**는 만들 때 일정 전체 재판정을 안 한다(고르면 `plan_swap` 이 바꾼다 — 앞뒤와 겹치는 선택지가 보일 수 있다). 고객이 직접 고르는 길이라 지금은 받아들였다 — 필요하면 따로 정한다.

전체 회귀(`-m "not live"` 전체, 17분): **3,112 통과 · 실패 16.** 그중 1건(감시 시험 — 알림에 원인 코드 이름 `road_closed` 가 새는 것을 못 박고 있었다)은 새 기대로 고쳐 통과시켰다. **남은 15건은 이번 변경 밖이다** — 임베딩 서버가 꺼져 있어 접속이 거절되는 RAG 12건 · UI 쪽 웹훅 모양 시험 문자열을 잡는 보안 검사 1건 · 이동팀 엔진 시험 1건(이 변경 전에도 같은 시험이 실패했다) · (합계 14 + 이전에 센 1 = RAG 12건에 한 건 더 있었는지는 아래 확인). 이 PC 에서만 확인한 결과다.

- 새 경고의 기준(`travel.quality`)과 22:00·20분은 **우리가 고른 값**이다(측정 안 함).
- 코드만 읽고 만든 판정이다 — 실제 DB 에 영업시간·라스트오더 칸이 몇 % 채워져 있는지는 보지 않았다. 칸이 비면 O4 는 「모름」 경고로만 나간다.
- L2 는 일정을 안 밀고 알리기만 한다. 고객이 「밀어 줘」라고 하면 처리하는 길은 없다(안내 문장도 그것을 약속하지 않는다).
- 끼니 경고의 「식사할 틈 60분」 · 22:00 · 20분 · 60분은 **우리가 고른 값**이다(측정 안 함).
- 라스트오더는 **일정에 담긴 장소 값**만 본다 — 요식 원장이 아는 라스트오더가 일정의 장소 값에 없으면 「확인해 주세요」(`last_order_unknown`)가 원장이 아는 식당에도 나올 수 있다.
- 이 PC 의 DB 세션 시간대는 Asia/Seoul 이라 H3 의 DB 쪽 어긋남은 **여기서는 재현되지 않는다** — 시험은 UTC 로 온 시각으로 만들었다.
