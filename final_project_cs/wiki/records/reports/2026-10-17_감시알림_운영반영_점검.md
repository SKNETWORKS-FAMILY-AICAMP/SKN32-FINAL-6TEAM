# 기존 감시와 알림 설계의 공개 배포 반영 점검

**감시·대안 선택·일정 저장·시각 안내 코드는 x600 서버의 cs 프로젝트 서버에 배포돼 있고 실행 기록도 있습니다. 다만 고객 외부 알림은 설정상 꺼져 있으며, 출발 안내의 실제 생성·배달 성공은 확인되지 않았습니다.** 최근 자동 배포도 DB 갱신 단계에서 실패해 이전 배포판이 실행 중입니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 배포 코드·설정 대조 | 완료 | 1/1 = 100% |
| 감시·알림 실행 기록 조회 | 완료 | 1/1 = 100% |
| 선택·안내 연결 확인 | 완료 | 1/1 = 100% |
| 결과와 한계 기록 | 완료 | 1/1 = 100% |

이 표는 점검 작업의 완료율입니다. 제품 기능 전체가 통과했다는 비율이 아닙니다. 점검 시각은 **2026-10-17 00:01~00:13 KST**, 대상은 공개 배포의 API·worker·web·DB입니다. DB 조회는 `SET TRANSACTION READ ONLY`로 제한했고 고객 일정·설정·알림 상태를 바꾸지 않았습니다. 외부 알림을 보내거나 감시를 강제 실행하지 않았습니다.

## 2. 실행판과 설정

실행 중인 API·worker·web·DB 컨테이너는 4/4입니다. API·web·DB health는 정상이고 worker는 별도 healthcheck가 없습니다. API `/health`는 실제 HTTP 200을 반환했지만 이 응답이 외부 자료·고객 알림 성공까지 검사하는 것은 아닙니다.

- 배포 기록 커밋: `ea3e674f425cf7ea1215915f2f66dfd5f62a7201`.
- API·worker 이미지: `sha256:73832fc334d0c68444f2a0b51a6e8a2e833db73fb5278ac63c05aea7d239be68`.
- web 이미지: `sha256:0bba4bfa20cde8c71d9d49e6c06cadecc22fa7aa4dfbe58a18310fd04916076b`.

확인한 배포 코드 16개는 감시 실행·배달 실행·worker·기본 감시·묶음 처리·시각 안내·재난 정지·재개·채널 분기·회차 기록·변경 신호·보류 제안·배달 작업·조립·프로젝트 설정·가드레일입니다. 로컬 작업 폴더와 같은 것은 6/16이며, 로컬에 미커밋 변경이 있고 배포 기록 커밋도 로컬 HEAD와 달라 이 차이를 일괄 미반영 결함으로 분류하지 않았습니다.

## 3. 감시가 돌고 있는지와 실패가 남아 있는지

00:05:31 조회의 최근 24시간 회차는 459개입니다. `completed` 180개, `attention` 279개이며 `failed` 회차는 그 집계에 나타나지 않았습니다. `attention`은 소스 조회 실패·보류 등을 포함하므로 회차가 종료됐다는 사실과 정상 판정을 구분해야 합니다.

같은 조회의 소스 관측에는 재난문자 `ok` 829회·`failed` 745회, 교통 `ok` 164회·`failed` 37회가 있습니다. 이 수는 **확인 기록 수**이며 캐시 재사용과 동일 자료의 반복 관측을 포함합니다. 서로 다른 재난·API 호출 건수나 실서비스 장애율로 해석하지 않습니다.

후속 조회에서는 최근 1시간 감시 18회가 모두 정상 종료했고 재난문자·지진 관측도 정상입니다. 최근 실패 관측은 재난문자 10-16 11:21:12, 교통 10-16 18:30:42입니다. 최근 1시간에는 방문 항목 점검 기록이 없어 교통·장소 상태의 실패까지 해결됐다고 판정할 수 없습니다.

최근 15분 worker 로그 전체 52줄에서 감시 요약 13회·배달 요약 13회가 관측됐습니다. 이 범위의 종료 코드 오류와 확인한 예외 종류는 나오지 않았고 마지막 배달 요약은 처리 0건입니다. 알림 대상이 없는 회차에서 처리 0건은 외부 배달 성공 증거가 아닙니다.

## 4. 일정 안내는 계산되지만 출발 안내의 성공 근거가 부족함

배포된 안내 계산기를 합성 일정·시각으로만 실행했습니다. DB와 외부 채널은 사용하지 않았습니다.

| 합성 입력 | 결과 | 판정 |
|---|---|---|
| 08:00 하루 시작 | 하루 시작 안내 후보 | 통과 |
| 09:20 첫 이동 출발 | 출발 안내 후보 | 통과 |
| 10:00 활동 시작 | 현재와 다음 안내 후보 | 통과 |
| 11:20 다음 이동 출발 | 출발 안내 후보 | 통과 |
| 12:00 마지막 방문 시작 | 안내 후보 없음 | 기존 마지막 항목 제외 규칙과 일치 |

계산 확인은 5/5 = 100%입니다. 이 다섯 결과가 실제 시각에 알림이 저장·배달됐다는 뜻은 아닙니다. 마지막 일정에서 안내가 없는 것은 기존 워크플로에 명시된 동작이며, 마지막 일정·도착·종료까지 안내해 달라는 추가 요구와 구분합니다.

운영 DB의 출발 안내 생성 기록은 0건입니다. 24시간 출발 재확인 기록은 보류 28건·실패 1건이며, 보류 사유는 도착 지연 19건, 보행 도착·여유 부족 6건, 조회 가능한 운행 시각 범위 밖 3건입니다. 안전하지 않거나 이미 늦은 경로를 그대로 권고하지 않는 처리일 수 있지만, **재계획 후 새 이동의 출발 안내가 성공했는지는 이번 기록에서 확인되지 않았습니다.**

## 5. 외부 알림이 나가지 않는 직접 원인

API와 worker 양쪽에서 `travel.notice_per_customer_enabled=false`를 확인했습니다. 배포된 고객별 알림 분기 코드도 이 스위치가 꺼져 있으면 `NoticeSuppressed`로 처리합니다. DB의 `skipped` 198건은 전부 이 사유입니다.

하루 시작·현재와 다음·안전 안내·선택 요청·변경 통지는 DB에 남아 있지만, 현재 설정에서는 고객의 외부 채널로 나가지 않습니다. 앱 안 안내는 외부 발송과 별도로 저장하는 계약입니다. 이번에는 고객으로 로그인해 앱 안내를 열어보는 시험까지 하지는 않았습니다.

`dead_letter` 14건은 10-07~10-12의 실패 기록이며, 최근 발송 건너뜀 198건과 구분합니다. 현재 조회에서 5분 이상 대기·처리 중인 여행 알림과 미해결 `unknown`은 각각 0건입니다. 대기열 적체가 없다는 사실을 알림 전달 정상으로 해석하지 않습니다.

## 6. 새 배포가 멈춘 상태

자동 배포 기록은 다음과 같습니다.

| 시각 KST | 사실 |
|---|---|
| 10-16 12:39:27 | 현재 커밋 `ea3e674f42`의 배포 상태 기록 |
| 10-16 16:20:36 | 새 후보 `2bee4df693` 배포 시작 |
| 10-16 16:22:39 | DB 갱신 실패. 실행 중인 기존 배포판 유지 |

배포 로그에 남은 오류는 `Migration failed; job stopped; DB result must be checked before retry`입니다. 읽은 해당 배포 로그 구간 7줄과 보존 상태 파일에서는 실패한 SQL 이름·직접 원인까지 확보하지 못했습니다. **갱신 작업을 다시 실행하거나 DB를 수정하지 않았습니다.** 현재 DB 상태와 후보의 갱신 파일을 먼저 대조해야 합니다.

두 커밋의 관련 경로 차이에서는 웹 화면·시험 변경이 확인됐고 감시·보류 제안·공개 worker 경로의 차이는 그 범위에서 나오지 않았습니다. 따라서 새 배포 실패를 근거로 기존 감시·알림 전체가 미배포라고 결론내리지 않습니다. 다만 새 웹 변경이 공개 환경에 반영됐다고도 말할 수 없습니다.

## 7. 확인 범위와 다음 조치

이번에 확인한 것은 배포판·설정·실제 DB 이력·작업자 로그·등록된 API 경로·배포 웹 코드·메모리 안 합성 계산입니다. 실제 고객으로 앱에서 대안을 눌러 지도·출발 시각까지 바뀌는 흐름과 외부 알림 수신은 실행하지 않았습니다. p95 5분 목표도 배달 성공·배달 시각의 새 실측이 없어 달성으로 판정하지 않습니다.

- **고객 외부 알림을 사용할 준비:** 꺼짐 설정의 운영 의도를 확인하고 실제 연결·동의·수신 경로를 검증해야 합니다. 점검 요청을 외부 발송 활성화 승인으로 해석하지 않았습니다.
- **출발 안내 확인:** 실제 이동이 성립하는 합성 여행에서 재확인·보류·재계획·새 안내 생성까지 검증해야 합니다. 단순 계산 성공만으로 완료하지 않습니다.
- **배포 실패 확인:** DB 갱신 결과와 새 후보의 갱신 파일을 대조하고 실패 원인을 확보한 뒤 다시 반영 여부를 판단해야 합니다.

GPS 도착·이탈 확인은 기존 감시 설계에 포함됐다는 근거로 취급하지 않았습니다. 이번 검사는 기존 설계의 배포·실행 점검입니다.

mock 서버 시험 (화면 반응): **안 했음**. 배포된 순수 계산기의 합성 입력 확인 5/5와 구분합니다.

실서버 확인 (서버 응답): **했음** — x600 서버의 cs 프로젝트 서버 컨테이너·설정·읽기 전용 DB 집계·API `/health` 200·API 경로·배포 웹 산출물·작업자/배포 로그. 외부 고객 알림 발송·수신과 실제 고객 선택은 안 했습니다.

## 8. 증거와 변경 기록

[비밀값·고객 원문을 제외한 관측 JSON](../evidence/2026-10-17_watch-notification-deployment-audit/observations.json)에 각 조회 시각·집계 범위·실행판·읽기 전용 상태·제약을 남겼습니다. 스냅샷 시각이 달라 24시간 창의 건수도 조금 달라지므로 서로 다른 시점의 숫자를 같은 집계로 합치지 않습니다. 대안 선택 연결은 중복 조인 행 수가 아닌 제안 2개의 존재 관계로 다시 세었습니다.

운영 코드·설정·업무 데이터를 변경하지 않았습니다. 보고서와 증거는 새 파일이며 기존 산출물을 덮지 않았습니다. 운영 현황·변경 기록에 이번 관측 링크를 추가할 때 원본을 각각의 `_backup/`에 보관합니다.
