## 새 규칙 ([image_retention.py](../../../deploy/image_retention.py))
- **앱 이미지**(api · web · admin): 최근 3개 + 현재 배포 태그 + 실행 중 컨테이너가 쓰는 것 + **달마다 하나**(`keep-YYYY-MM` 이름표, 최근 6개월). 같은 커밋은 저장소가 달라도 함께 남기고 함께 지운다.
- **달별 하나의 고르는 법**: x600 서버는 `deploy.log` 의 「반영 완료」 중 그 달 마지막, 오라클은 `state.json` 의 `history`. 기록이 전혀 없으면 만든 시각으로 고른다. 빌드만 되고 실패한 이미지는 후보가 아니다.
- **복구용 이미지**(`tripilot-recovery`): 최신 2세트만. 기간으로 두지 않은 이유 — 배포가 하루 수십 건이라 7일을 두면 수백 GB가 된다. 직전 이미지는 어차피 앱 이미지 「최근 3개」로 남는다.
- 복구용 상태 폴더(`state/migration-safety-*`, 비밀이 든 풀어 쓴 설정 포함)도 이미지와 함께 지운다.
- **안 건드리는 것**: `local` · `keep-*` · 손으로 붙인 이름(`*-rollback`, `*-summary-*`, `backup-*` 등) · 다른 저장소(jikimi 등) · 실행 중(정지된 컨테이너 포함) 컨테이너가 쓰는 **그 이미지 자체**. 보호는 이미지 단위이고, 같은 커밋 이름표의 다른 저장소 이미지까지 묶음째 지키지 않는다.
- ★**2026-10-14 수정(첫 판의 결함)**: 첫 판은 실행 중인 이미지가 하나라도 있으면 같은 커밋 묶음 전체를 보존했다. 웹처럼 바뀌지 않는 이미지는 여러 커밋이 같은 이미지 ID 를 공유해서, 웹이 실행 중이면 그 이후 모든 커밋의 api · admin 이미지가 영영 안 지워진다. 오라클 서버 로그의 「묶음 8개 중 남김 8 · 지움 0개」로 발견했고, 이미지 단위 보호로 고쳐 회귀 시험 2개를 더했다. x600 서버는 옛 정리 때문에 `web` 해시 이름표가 없어서 가려져 있었을 뿐이다.
- 기본은 계획만 출력, `--apply` 가 있어야 지운다. x600 서버는 `auto_deploy.sh` 끝, 오라클은 `deploy.py` 의 성공 처리 **뒤**에서 부른다(정리 실패가 배포 실패로 번지지 않는다).
- 빌드 캐시는 `--builder-keep-gb 20` 으로 상한까지만 남긴다(x600 서버).

## 월 전환과 복원 시험 (같은 날 후속)
- **월 전환**: 10월 마지막 성공 판은 11월이 와도 `keep-2026-10` 에 남고 11월 판은 `keep-2026-11` 이 된다. 이후 배포가 쌓여 10월 판이 「최근 3개」에서 밀려나도 월 보존이 붙든다. 연말 넘김 · 6개월 뒤 정리도 시험했다(`test_image_retention.py` 23개). 로그 시각을 UTC 로 잘못 읽으면 KST 서버의 11월 1일 새벽 배포가 10월로 분류되는 결함을 찾아 서버 지역 시각 기준으로 고쳤고, 리눅스에서 KST · UTC 설정 모두 확인했다.
- **복원 시험 도구** [restore_check.py](../../../deploy/restore_check.py): 운영 DB · 운영 `.env` 를 읽지 않고, 바깥과 연결되지 않는 임시 네트워크 안에서 (1) 최신 이미지로 지금의 DB 구조를 빈 임시 DB 에 만들고 (2) 옛 이미지의 마이그레이션 (3) 옛 이미지 API 의 `/health` 와 로그 오류 (4) 옛 이미지가 모르는 새 설정 이름이 환경변수로 들어와도 켜지는지를 확인한 뒤 임시 자원(컨테이너 · 네트워크 · 이름표)을 **항상** 지운다. 임시 DB 는 이 시험이 도는 동안에만 있다. 단위 시험 12개.
- **실행 결과(x600 서버, 2026-10-14 저녁)**: 오늘 18:21 판(`c172a96e2f`)을 최신 판(`1cf87c084e`)의 DB 구조에 붙여 **5개 확인 모두 통과**했다. 임시 컨테이너 · 네트워크 · 이름표는 남지 않았고 운영 컨테이너는 그대로 정상이었다.
- ★**정정(같은 날 저녁)**: 처음에는 「최신 판에만 있는 설정 `ACOP_JUSO_COORD_API_KEY` · `ACOP_JUSO_SEARCH_API_KEY` 가 운영 `.env.apikeys` 에 있어서 그 전 판으로 되돌리면 `extra="forbid"` 때문에 켜지지 않는다」고 보고하고 README 에 「충돌 줄을 끄는」 단계를 넣었다. **틀린 결론이었다.** 도구에 이를 직접 재현하는 확인을 넣자 실패했다(옛 이미지에 모르는 이름을 환경변수로 줘도 켜진다). `extra="forbid"` 는 `.env` **파일**에서 읽은 모르는 이름만 거부하고, 운영은 compose `env_file` 로 값을 컨테이너 환경변수에 넣으며 `.env` 는 이미지에 없다(`Dockerfile.api` 주석 · `.dockerignore`). 그래서 운영 방식에서는 새 설정 이름이 복원을 막지 않는다. 원인은 「이름이 환경 파일에 있다」는 사실만 보고 「그 파일을 앱이 직접 읽는다」를 확인하지 않은 것이다. README 의 해당 단계를 지웠고, 도구는 환경변수 경로(운영 방식)를 통과 항목으로, 파일 경로를 참고 줄로 바꿨다.
- **확인하지 않은 것**: 실제로 운영 컨테이너를 옛 이미지로 바꿨다가 되돌리는 단계는 시험하지 않았다(2026-10-14 저녁, 운영 컨테이너 교체는 자동 권한 심사가 막았다 — 사용자가 직접 실행하거나 권한을 열어야 한다. README 3·4번 절차가 그 시험 대상이다). 임시 DB 는 비어 있어서(운영 DB 를 읽지 않기 위해) 데이터에 의존하는 동작은 확인하지 못했다. 시험한 옛 판은 최신보다 2~3시간 앞선 것이라 구조 차이가 작았다 — 월이 지난 판일수록 이 시험을 다시 돌려야 한다.
