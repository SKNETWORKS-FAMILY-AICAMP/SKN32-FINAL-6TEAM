# 웹 팀 실행·고객 답변 재개 수정 결과

웹의 팀 실행 우회, 질문을 완료 처리하던 동작, 재개 답변 본문 누락을 로컬 코드에서 수정했다. 등록 Team과 실제 로컬 개발 DB를 사용한 회귀까지 확인했다. 커밋·푸시·운영 배포는 수행하지 않았다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 지적된 결함 수정 | 완료 | 3/3 = 100% |
| 관련 검증 | 통과 | 311/311 = 100% |
| 실제 브라우저 화면 확인 | 미실시 | 0/1 = 0% |

## 바뀐 동작

1. 일정 변경·지연/휴무/품절 신고·되돌림은 등록 Team의 `execute`로 들어간다. Team은 계산·제안만 반환하고, Controller의 적용기가 일정 저장과 알림 예약을 한 번 수행한다. 기존 장소 후보 확보는 Team 실행 전에 유지한다. 단순 사실 조회는 읽기 경로다.
2. 필요한 시간이 없으면 `waiting_input`으로 질문·근거·필수 입력을 저장한다. ‘아직 몰라요’는 재질문하고 ‘30분이요’는 같은 Case의 담당 Team에 전달한다. 원래 요청·최신 답변·답변 이력이 함께 전달된다. 자유 답변의 업무 해석과 대상 선택에 따라 실제 담당 Team도 재배정한다.
3. 웹 JSON/SSE는 대기 Case·토큰·버전을 다음 답변에 연결한다. 새로 고침 뒤에는 인증된 소유권 확인으로 같은 여행의 단일 입력 대기 업무를 재개한다. 여러 업무는 명시적 Case 선택을 요구한다. 잘못된 토큰은 401, 버전·다른 본문으로 요청 번호 재사용은 409, 없는/다른 여행 Case는 404로 처리한다.

대안 목록은 질문으로 남고 번호 선택에서 같은 업무를 재개한다. 적용기에서 보호 조건 때문에 변경 대신 별도 보류 제안만 열었으면 실제 질문을 최종 답변으로 저장해 ‘바꿨다’는 잘못된 안내를 막는다. 이 보류 제안의 수명은 기존 `pending_changes`가 관리한다. 실패 응답에 이전 질문을 성공 안내처럼 재사용하지 않는다.

## 실제 검증과 분모

| 범위 | 통과/실행 | 근거 |
|---|---|---|
| 웹 결정·새 대화·여행 API·식당 상태·신고 추출 | 76/76 = 100% | [전체 로그](../evidence/2026-10-11_conversation_resume_final/web-api.log), [JUnit](../evidence/2026-10-11_conversation_resume_final/web-api.junit.xml) |
| 공통 답변 재개·기존 여행 승인·적용 안내 | 32/32 = 100% | [공통 검증](../evidence/2026-10-11_conversation_resume_core_route_patch/summary.md) |
| 팀 대화·기존 계산 | 65/65 = 100% | [팀·구조 합동 로그](../evidence/2026-10-11_conversation_resume_final/pure.log) |
| 코어 도메인 분리·층 의존·상태도 정합성 | 96/96 = 100% | [팀·구조 JUnit](../evidence/2026-10-11_conversation_resume_final/pure.junit.xml) |
| 웹 gateway·SSE | 42/42 = 100% | [웹 클라이언트 검증·타입·ESLint](../evidence/2026-10-11_0359_conversation_resume_frontend.md) |

각 행은 서로 다른 시험 파일의 실행 수다. 합계는 76+32+65+96+42=311이다. 해석 모델과 외부 공급자 응답은 시험용으로 고정하며, 실제 등록 Team·Controller·적용기·로컬 개발 DB는 실행한다. 이 수치를 모델 정확도나 실제 운영 성능으로 부르지 않는다.

실제 웹 요청에서 같은 Case 재개, 재질문, 토큰·버전·소유권 거부, 초기 요청/답변 재시도, 담당 Team 재배정, 대안 선택, 보호 일정 미변경을 확인했다. 일정 변경 요청은 실제 `agent_runs`와 성공 `action_requests` 각각 1건이며, 세 번 재전송 후에도 일정 버전·변경 알림이 늘지 않는 것을 DB에서 확인했다.

mock 서버 시험(화면 반응): 이번 범위에서 미실시.

실서버 확인(cs 프로젝트 서버 응답): 안 했음. 로컬 개발 DB에 연결한 애플리케이션 내부 HTTP 시험(TestClient)은 했음. 배포된 cs 프로젝트 서버 및 실제 브라우저 화면은 확인하지 않았다.

## 검증 한계와 별도 실패

- 관련 검증 전후 생산 코드 13개 SHA-256이 동일하다. [요약·해시·원문 로그](../evidence/2026-10-11_conversation_resume_final/)에 보존했다. 수정 파일 Ruff, 웹 TypeScript/ESLint, 대상 `git diff --check`도 통과했다.
- 더 넓은 구조 검사에서는 다른 변경 파일 두 곳의 의존 방향으로 `test_travel_ops_cells` 한 시험이 실패했다. 해당 파일은 이번 수정 범위가 아니다. 상태도 불일치는 이번에 추가한 재개 중 재배정 전이를 반영해 생성 파일을 갱신했고 최종 정합성 검사는 통과했다. [초기 구조 검사 출력](../evidence/2026-10-11_conversation_resume_final/broader-architecture-before-generated-sync.log)을 보존했다.
- 앞선 웹 전체 실행은 634/635 통과였고, 수정하지 않은 CSS 직접 색상 사용 검사 한 건이 실패했다. 이번 최종 확인은 gateway/SSE 42건과 타입·대상 ESLint이며 웹 전체 재실행으로 표현하지 않는다.
- 로컬 개발 웹이 실행 중이지 않았고 디스크 여유가 약 150MiB라 새 Next 빌드·화면 기동은 하지 않았다. 검증 시작 시 디스크가 가득 찬 문제는 재생성 가능한 Next 컴파일 캐시만 정리해 진행했다. 소스·사용자 데이터는 삭제하지 않았다.
- Python 3.12.7, 임시 `PYTHONPATH=.tmp/conversation-python`의 tiktoken 0.12.0으로 검증했다. 설치된 0.13.0의 네이티브 실행 중단 때문에 사용한 임시 호환 환경이며 전역 패키지·프로젝트 의존성은 변경하지 않았다. 자동 플러그인 로딩은 끄고 비동기 시험에는 `pytest_asyncio.plugin`을 명시했다. 웹 검증의 Node 26.2.0은 프로젝트 선언 범위 22~24 밖이다.
