# 테스트 계획 기본안 추가와 분류 색

계획 선택에 문제 상황을 의도적으로 넣지 않은 기본안 3개를 추가하고, 문제 분류를 색과 이름으로 표시했다. 기존 test1~test12는 같은 번호·원문을 유지한다. 새 test13~test15는 종료 시각·구체적 장소·방문 간 여유가 있는 기본안이다. 장소 조회·검증 결과를 성공으로 고정하지 않는다.

## 변경과 경계

카탈로그 `seoul-text-v2`에 `category`를 추가했다. 목록·접수 메타데이터에 시험 목적 분류를 보존한다. 기존 DB 구조·인증·활성화 설정은 유지한다. 코드 최대 범위와 관리자 설정 설명은 test15까지 확장했다. 구버전 응답에 분류가 없으면 일반 흐름으로 표시한다. 현재 계약을 구현 전에 수정했으며 변경 담당자가 API·UI 검토를 겸했다. 독립 검토 완료로 표시하지 않는다.

새 기본안은 도심 산책, 박물관·타워 방문, 하루 한 곳씩 방문하는 2일 계획이다. 같은 날 방문 간 여유는 3시간 이상이다. 실제 장소의 운영 상황·날씨·경보가 없다고 보장하거나 검증을 생략하지 않는다.

웹은 기본안부터 묶은 선택 목록을 제공한다. 기본안은 초록, 시간 겹침은 황토, 운영시간·휴무는 붉은색, 장소 미정은 보라, 이동 여유는 파랑, 입력 확인은 청록, 일반 흐름은 회색 계열이다. 색은 분류 이름·시험 코드와 함께 읽는다. 펼친 목록을 화면 안으로 스크롤하고, 44px 이상 누름 영역·Tab·방향키·Home·End·Esc·선택 후 초점 복귀를 제공한다. 직접 코드 입력·원문 미리보기·목록 실패 시 일반 입력을 유지한다.

## 검증 증거

- `python -m pytest tests/unit/travel/test_intake_test_plans.py tests/e2e/test_intake_test_plans.py -q`: 36/36. 단위 29개와 로컬 개발 DB·실제 접수 API 경로 7개다. 장소·이동 제공자는 시험용 mock 제공자다. 새 코드 3개가 읽히고 접수·review에 분류가 보존되는지 확인했다.
- Chrome 생산 빌드 시험: 기존 준비 계획 6개·새 분류 시험 3개 = 9/9. 375px·1280px에서 기본안 우선, 분류 색 7개, 선택·직접 입력, 새 코드 전송, 구버전 응답, 키보드 이동·취소·복귀, 가로 넘침을 확인했다. `chrome-final.json`은 expected9·unexpected0·flaky0·skipped0이다.
- ESLint와 증분 기록을 사용하지 않은 TypeScript 검사가 종료 코드 0/0이다. 분류 배지 7개의 CSS 글자 대비 계산은 최소 5.77:1이다. 이는 전체 화면 접근성 인증을 뜻하지 않는다.
- 별도 웹 시험 사본은 팀 매니저 기준 `d4895eefdaf39db6efd02b24bbda2edd231dbeb3`에 직전 내 위치 작업과 이번 UI 변경만 더한 사본이다. 루트 전체의 다른 작업을 복사하지 않았다. 변경한 UI·시험·fixture 5개가 사본과 같은지 해시로 확인한다.

처음 DB 실행은 로컬 접속 권한 제한으로 4개 시험의 준비 단계가 실패했다. 접속 가능한 실행 환경에서 새 시험까지 포함해 36개를 다시 실행했다. 첫 Chrome 실행은 mock 포트 접속을 확인하지 못해 중단했다. 접속 가능한 첫 실행은 8/9였으며, 모바일 전송 직후 완료 전에 로그를 읽던 시험을 전송 완료 대기로 고쳤다. 키보드 위 방향 시작 위치를 보정한 다음 9/9를 확인했고, 화면 촬영에서 목록이 아래에 가려지는 것을 발견해 화면 안으로 스크롤·여백을 보정한 최종 실행도 9/9였다. 중간 로그와 사진 백업은 보존했다.
