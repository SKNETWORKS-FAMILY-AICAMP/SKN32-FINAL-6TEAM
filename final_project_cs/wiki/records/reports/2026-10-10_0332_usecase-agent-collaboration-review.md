# 여행 사용 사례별 중앙 조합과 에이전트 협업 적용 검토

기준일: 2026-10-10 KST. 판단 성격: 기존 설계 대조와 적용 제안. 제품 정책 변경이나 구현 완료를 선언하는 문서가 아니다.

**triPilot은 중앙에서 일정의 최종 정합성과 변경 권한을 관리하면서, 자유 질문·근거 해석·복구 계획처럼 필요한 곳에만 AI 실행 범위를 넓히는 구성이 적합하다.** 활동·식사·이동의 후보 조합을 개선하는 문제와, 후보를 만들기 위해 새로운 정보를 알아내는 문제를 구분해야 한다. 전자는 제한된 중앙 탐색이 우선이고, 후자는 단일 AI와 도구를 기준으로 제한된 협업의 추가 효과를 비교할 수 있다.

## 먼저 바로잡을 판단

Activity·Dining·Mobility의 다른 영역 영향은 이미 각 Team 위키에서 **후보 제출 → 코어 검증 층의 전체 일정 재검증**으로 정리돼 있다. 이를 새 권고처럼 제시하거나, 병합 함수가 전 조합을 탐색하지 않는다는 사실만으로 직접 협업을 권하는 것은 부정확하다. [Activity 경계](../../teams/activity.md), [Dining 경계](../../teams/dining.md), [Mobility 경계](../../teams/mobility.md).

계획서가 하나라는 사실은 추론 담당자 수를 결정하지 않는다. 여러 담당자가 좋은 입력을 만들더라도 적용된 일정의 정본은 하나여야 한다. 후보 몇 가지를 보여주는 것과 여러 일정을 동시에 적용하는 것도 다르다. 자동 교체·먼저 묻기·고정 항목 보호는 이미 따로 정의돼 있다. [선택 정책](../../../../wiki/decisions/D-020-trip-survey-and-ask-first.md), [최신 API 계약](../../external/rest-endpoints.md).

또한 중앙 **업무 검증 기능**을 확장한다는 말이 범용 Controller에 식사·관광·교통 규칙을 직접 넣는다는 뜻은 아니다. 범용 코어는 실행·버전·권한·변경 확정을 맡고, 여행 도메인의 조합·계산은 등록된 도구와 조립 층으로 연결한다. 기존 주입 구조가 이를 지원한다. [Team 경계](../../teams/team-boundary.md), [조립 구조](../../teams/composition.md).

## 검토 범위와 사실의 수준

루트 wiki와 cs wiki의 Markdown 본문 231개에서 사용 사례·시나리오·협업·전체 일정·조합 관련 문자열을 검색해 관련 문서 73개를 추렸다. 기록·백업·이관 폴더와 변경 이력은 본문 검색에서 제외했다. **231은 검색한 파일 수이며 정독한 파일 수나 구현 완료율이 아니다.** 목록은 [검색 기록](assets/2026-10-10_usecase_agent_fit/wiki-scan.json)에 있다.

관련 본문과 연결된 구현·시험 소스를 대조해 아래 기존 상황 22개와 추가 시험 상황 8개로 묶었다. 이는 문서에 흩어진 사용 사례를 운영 목적별로 통합한 분류이며, 모든 미래 상황을 열거했다는 뜻은 아니다. 시험 함수의 존재는 실행 통과 증거로 사용하지 않았다. 이번 검토에서는 제품 시험, 실제 모델 호출, 운영 배포를 수행하지 않았다.

| 표시 | 의미 |
|---|---|
| 기존 경로 | 현재 wiki/API 또는 코드에 해당 처리 경로가 있다. 운영 환경에서의 전체 성공을 뜻하지 않는다 |
| 설계 초안 | 위키에 있으나 채택·구현·측정이 별도로 필요하다 |
| 이번 제안 | 이번 분석의 적용안이며 승인된 정책이나 측정 결과가 아니다 |

문서의 날짜도 구분했다. 요식팀의 10월 6일 다중 AI·SNS 구상은 10월 7일 경계 문서에서 수정됐다. 현재 검토 기준은 **기본 판정은 코드, 기존 경로로 못 푸는 자유 질문에만 선택적으로 AI**이다. Q 비율 5%와 시간 상한 10초는 그 문서의 제안값이며 확정 운영 정책으로 취급하지 않았다. [수정된 설계](../../teams/dining-mcp-boundary.md).

옛 요식 사용 사례에 있는 ‘사람에게 넘김’도 그대로 채택할 수 없다. 최신 결정은 사람 운영자 대기열을 전제로 하지 않는다. 고객에게 필요한 정보를 다시 묻는 것과 사람 운영자에게 업무를 보내는 것은 다르다. [라우팅 재선택 결정](../../decisions/D-CS-014-routing-reroute.md).

## 구조별로 이득이 생기는 조건

| 방식 | 가장 잘 맞는 일 | 얻는 것 | 지불하는 대가와 경계 |
|---|---|---|---|
| 중앙 코드와 후보 조합 | 필요한 사실과 계산 규칙이 정해진 일정 검증·재배치 | 재현성, 시간 상한, 일관된 변경 확정 | 후보 밖의 새로운 경험·근거를 스스로 알아내지는 못함 |
| 단일 AI와 읽기 도구 | 모호한 문장 해석, 여러 질문을 풀어 도구를 선택하는 일 | 문맥을 한곳에 유지하며 유연하게 처리 | 여러 번의 모델 호출이 필요할 수 있고 수치 판정은 코드로 검증해야 함 |
| 중앙 감독 아래 병렬 담당자 | 서로 독립적인 출처·주제를 조사하는 일 | 조사 범위를 나누고 동시에 진행 | 같은 자료의 중복 조회와 문맥 전달 비용; 단순 병렬 API 호출은 AI 여러 개가 필요하지 않음 |
| 제한된 직접 협업 | 담당자마다 가진 정보가 다르고, 상대의 답에 따라 해석·추가 질문이 달라지는 예외 | 일방향 제출로 빠지는 정보나 의미 충돌을 발견 | 토론이 정답을 보증하지 않음. 참여자·회차·조회·시간의 공통 상한 필요 |
| 독립 외부 에이전트 간 연동 | 개인 AI의 비공개 맥락, 장차 업체별 권한·견적·예약 절차 | 다른 시스템의 독립 지식과 실행 능력 활용 | 인증·권한·기한·중복 실행·부분 실패를 별도 관리해야 함 |

**직접 협업의 채택 조건은 ‘팀이 여러 개다’가 아니라 ‘왕복 질문으로 새로운 결정 관련 정보가 생긴다’이다.** 같은 후보의 시간·거리 점수를 다시 말하는 대화는 중앙 계산 대비 이득을 보여주기 어렵다. 반대로 해석 담당자가 ‘이 공지는 건물 전체 휴관이 아니라 특정 전시실만 해당한다’고 근거를 확인하면 다른 결과를 만들 수 있다.

## 직접 협업을 써본다면 가장 좋은 형태

첫 실험은 활동·식사·이동 전체에 각자 자율 플래너를 주는 방식보다 **근거가 충돌하는 공지 해석**에 ‘해석 담당 + 검토 담당’을 붙이는 방식이 적합하다. 기존 코드는 시간·이동·영업 계산을 계속 맡는다. 두 AI가 주고받는 내용은 일정 전체를 다시 짜라는 요청이 아니라 ‘이 시설이 이 날짜에 실제로 제외 대상인가, 근거는 무엇인가’ 같은 좁은 질문이다.

예를 들어 해석 담당은 ‘미술관 전면 휴관’으로 읽었는데 검토 담당은 공지의 층·전시실 표기가 일정 대상과 다름을 발견한다. 해석 담당이 해당 공식 페이지를 한 번 더 확인해 부분 제한으로 정정하면, 중앙은 불필요한 활동·식사·이동 교체를 하지 않아도 된다. **새 사실이 없고 같은 선호 점수만 반복하면 협업을 끝낸다.** 이 효과는 가설이며 우리 자료로 측정해야 한다.

구조는 다음처럼 닫는다. [방식 선택과 협업 종료 흐름](assets/2026-10-10_usecase_agent_fit/agent-selection.html).

1. 중앙이 일정 판·조회 범위·참여자·공통 예산을 고정한다. 참여자는 추가 팀이나 하위 AI를 생성하지 못한다.
2. 해석 담당이 근거와 구조화된 초안을 만든다. 검토 담당은 틀릴 수 있는 대상·날짜·예외만 질문한다. 필요하면 그 질문에 한정해 읽기 도구를 다시 사용한다.
3. 예시 상한은 담당자 2명, 검토 최대 2회, 세션 전체 모델 호출 최대 6회·외부 조회 최대 6회·30초다. **이번 시험의 제안값**이며 에이전트마다 새 예산을 부여하지 않는다. 별도의 취소·마감 처리가 있어야 실제 상한이 된다.
4. 통과·예산 종료·근거 부족·일정 판 변경 중 하나면 종료한다. 결과는 근거·후보·미해결 항목이며 반영 명령이 아니다. 중앙이 최신 판·보호 항목·시간·예산·권한을 재검증한 뒤 현재 정책에 따라 적용하거나 묻는다.

이 구조는 현재의 Team 간 직접 호출 금지와 양립하게 **Team 내부의 연구·검토 구성** 또는 조립 층에 등록한 별도 읽기 능력으로 시작한다. Activity가 Dining을 직접 호출하는 구현으로 바꾸지 않는다. 현재 Controller의 결과 처리 코드를 확인한 범위에서는 RESPOND·WAIT_INPUT·WAIT_APPROVAL·ESCALATE 경로와 미지원 결과 오류가 있으며, 업무 Team 간 HANDOFF 실행을 이미 제공한다고 가정할 수 없다. 라이브러리를 추가하는 것만으로 이 경계가 해결되지는 않는다. [Controller](../../../app/application/controller.py), [현재 실행 설계](../../runtime/agentic-controller.md).

재난 뒤 복구는 두 번째 실험 접점이다. 이미 있는 복구 요약·위험 조회·이동 판단 도구를 개인 AI가 읽고 고객 조건을 반영한 초안을 제출하게 한다. 먼저 단일 AI로 시험하고, 출처 해석이나 조건 충돌이 남는 사례에만 위 검토 담당을 붙인다. MCP 쓰기 도구는 기본 꺼짐이므로 실제 연결 시험에서는 현재 설정·권한을 확인해야 한다. 이번 분석 때문에 설정을 켜지는 않았다.

## 고객 요청 밖에서 협업이 더 유리한 일

개발·운영 작업도 고객 일정 수정과 분리해서 볼 필요가 있다. 공식 자료의 변경 조사, 추천 실패 사례의 원인 분류, 여행 평가 입력과 반례의 작성은 독립 작업으로 나누기 쉬워 병렬 조사·작성과 별도 검토 담당이 유리할 수 있다. 이 결과는 검증 후 자료·코드·평가에 반영하고, 고객 일정의 온라인 처리 지연에는 넣지 않는다. 추천 품질은 같은 모델 여러 개의 합의보다 별도 정답과 검토로 확인한다.

운영 API 한도·모델 지연·반복 실패의 관측과 경보 조건은 코드로 유지하고, AI는 원인 요약과 개선 초안을 돕게 한다. 또한 고객 원문을 협업 평가 재료로 자동 복사하지 않는다. 최신 [서비스 개선 자료 경계](../../operations/service-improvement.md)는 선택 동의·정해진 수치 추출·승인 전 합성본 이용 차단을 구분한다. 합성본 승인 검토는 고객 장애를 받아 처리하는 사람 운영자 대기열과 다른 절차다.

## 중앙 조합도 현재 상태와 목표를 구분해야 한다

현재 자동 수정 코드는 항목을 순서대로 처리하고 처음 성립하는 후보를 택한다. 묶음 감시 처리도 등록된 계획 함수를 이용해 수정안을 만들고 정합성을 검사한다. 이 경로를 전 조합의 최적해 탐색이라고 부르지 않는다. 그렇다고 기존 구현이 잘못됐다는 결론도 아니다. 일정·응답 시간·개발 범위를 고려한 제한된 방식이다. [자동 수정](../../../app/domains/travel_ops/components/intake/autofix.py), [묶음 감시](../../../app/domains/travel_ops/components/watch/trip_watch_batch.py), [계획 함수 주입](../../../app/domains/travel_ops/components/team_hooks/watch_planners.py).

개선 시험에서는 활동 후보 3개와 식사 후보 3개를 **한 번 제출받아 9쌍**의 시간·이동·비용을 계산하는 식으로 시작할 수 있다. 이동은 각 쌍을 연결하는 계산이므로 독립 후보 점수만 더하지 않는다. 실제 후보 수·호출 상한은 측정해 정한다. 후보가 모두 조건을 어기면 추가 후보 요청을 한 번 허용하거나 필요한 고객 질문을 반환한다. 7일 전체의 후보 곱을 무조건 펼치지 않고 영향 구간·보존할 항목·탐색 상한을 정한다.

영역별 ‘최적안’ 하나만 올리면 전체의 좋은 조합을 놓칠 수 있다. 따라서 추천은 **대표안과 소수의 서로 다른 대안 + 성립 조건을 제출하고 중앙이 비교**하는 방식이다. 이는 에이전트 간 재귀 협상과 다르다. 후보 묶음 안의 최선도 후보 밖까지 포함한 전역 최적을 보장하지 않는다.

현재 발전을 ‘모두 자유롭게 대화하는 방향으로 수렴했다’고 정리할 수 없다. 독립 추론·수명주기가 필요한 영역은 에이전트로 두고, 절차가 정해진 영역은 도구로 줄이며, 상태 복구·권한·평가를 강화하는 흐름도 함께 확인된다. 위 적용 판단은 출처에 대한 **프로젝트 관점의 추론**이다.

## 무엇부터 비교 시험할 것인가

시험 순서는 중앙 조합 개선 → 자유 질문 단일 AI → 근거 충돌의 제한 협업 → 개인 AI 복구 연동을 권한다. 협업의 비교 상대를 약한 순차 병합 하나로만 잡지 않는다.

| 시험군 | 처리 | 비교 목적 |
|---|---|---|
| A | 현재 순차 후보 선택·검증 | 현재 기준선 |
| B | 동일 후보 묶음의 제한된 중앙 조합 | 탐색 개선 효과 |
| C | 단일 AI + 같은 읽기 도구·중앙 검증 | 문장 해석·동적 조회 효과 |
| D | 해석·검토 AI의 제한 협업 + 같은 중앙 검증 | 왕복 검토의 추가 효과 |

조합 시험은 입력 사실·후보 묶음을 같게 고정한다. 새 근거를 찾는 시험은 같은 출처 접근 권한·전체 시간·비용 상한을 주되, 추가로 발견한 사실을 별도 기록한다. 도구가 더 많아서 얻은 효과와 에이전트가 나뉘어서 얻은 효과를 분리한다.

일단 위 표의 30개 상황을 각각 정상·충돌·실패 입력으로 만들어 90개 시험 입력을 구성하는 것을 제안한다. **90개는 아직 생성·실행하지 않은 계획값**이다. 같은 입력을 A/B/C/D 교대 순서로 반복하고 분산·최악 지연도 본다. 계획 성공은 시간·예산·예약 보호·권한 제약을 모두 지킨 적용 가능 결과로 정의한다. 근거 부족 때 원안을 보존하고 정확한 질문으로 끝난 결과도 별도 집계한다.

측정 항목은 실행 가능 일정 비율(적용 가능 결과/적용을 요구한 입력), 보호 조건 위반 건수, 근거 없는 주장 건수, 취향 충족도에 대한 사람 검토, 중앙에서 최종 반영까지 걸린 시간, 전체 모델·조회 비용, 변경 횟수다. 다수 AI의 찬성표를 품질 지표로 쓰지 않는다. 평균만 보지 않고 반복 횟수·편차·지연 분포를 함께 보고 채택한다.

D가 B나 C보다 품질을 높이지 못하면 해당 상황은 더 단순한 경로를 사용한다. D가 근거 해석 오류를 줄이는 상황은 예외 트리거로 제한해 채용한다. 독립 업체 협상은 이미 장기 범위에 있는 Booking Handoff/A2A 논의와 연결하되, 현재 실험의 성공으로 예약·결제 기능까지 채택됐다고 해석하지 않는다.
