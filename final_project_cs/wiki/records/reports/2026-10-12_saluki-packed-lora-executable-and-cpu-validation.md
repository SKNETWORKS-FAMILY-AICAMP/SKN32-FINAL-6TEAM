## 문제와 변경

[앞선 설치판 조사](2026-10-12_saluki-training-runtime-recheck.md)는 표준 GGUF 로더의 `is_trainable=False`와 추론 전용 커널을 확인했습니다. 그것은 표준 학습 지원 여부이며, 동일 packed 가중치를 읽는 별도 미분 계산을 구현할 수 있는지까지 검증한 결과는 아니었습니다. 이번에는 별도 실행기를 구현했습니다.

가중치 전체를 큰 밀집 체크포인트로 풀지 않습니다. 각 선형층의 작은 행 묶음만 필요할 때 원래 값으로 복원해 곱하고, 역전파 때 같은 묶음을 다시 복원하여 입력의 기울기를 구합니다. 원래 packed 본문은 고정하고 LoRA A/B만 갱신합니다. 다른 Qwen 모델을 Saluki로 바꾸어 부르거나 NF4로 재양자화하지 않습니다. 표준 로더의 학습 지원 플래그를 참으로 바꾸지도 않습니다.

## 실제 CPU 검증

- 원본은 26,895,998,464개 파라미터입니다. 파일의 IQ2 표시는 저장 정밀도이며 9B 모델이라는 뜻이 아닙니다.
- 원본의 양자화 11종에서 순전파 최대 절대 오차 2.98e-7, 입력 미분 최대 절대 오차 1.49e-8을 확인했습니다. 종류마다 두 번의 LoRA 업데이트 후 추가 가중치는 달라지고 본문의 바이트 해시는 유지됐습니다. F32 종류 존재 확인을 합친 원본 CPU 결과는 12/12이나, F32를 같은 양자화 미분 시험으로 세지 않습니다.
- 기존 승인 자료 `train_oos2` 2,613문항 전부 정답 시작점이 일치했습니다. 최대 2,237토큰이며 4,096을 넘는 문항은 0/2,613입니다. 512 이하가 0개라 해당 smoke 단계를 제거했습니다. E2 자료는 학습에 사용하지 않습니다.
- 공식 구조 변환에서 양자화 텐서 498/498가 packed 유지 가능했습니다. 별도 작은 구조는 원본 Q8 블록을 사용한 선형층 16개, 선형/전체 attention 두 종류, checkpointing을 연결해 실제 손실·역전파·최적화 2/2회를 통과했습니다. 작은 구조 검증을 27B 전체 학습 성공이나 정확도 측정이라고 해석하면 안 됩니다.
- 수정 중 자료의 필드(`messages` 대신 `prompt/completion`), 토크나이저 반환형, 작은 층 생성자 인자 오류를 실제로 발견했습니다. 수정 전 로그와 수정 뒤 결과를 모두 비공개 근거 폴더에 보존했습니다.

## 대기열 실행 계약

기존 단일 GPU 대기열은 새 실행기 한 건을 실행합니다. 실행 순서는 CUDA의 원본 양자화 블록 11종 미분 검사 → 최대 2,048/4,096토큰 원문 문항 네 개로 네 번 업데이트 → smoke 업데이트 폐기 → 고정 seed로 승인 자료 2,613개 전체 1epoch입니다. 새 GPU worker를 띄우지 않으며 다른 CUDA 프로세스가 있으면 시작하지 않습니다.

본 학습은 rank8·alpha16·dropout0.05·학습률2e-5·cosine·warmup5%·seed20261019·microbatch1·누적16입니다. 정답 부분만 손실을 계산하며 문항을 조용히 자르거나 제외하지 않습니다. 실패는 해당 시도의 `failed.json`에 원인과 traceback을 보존하고 자동 반복하지 않습니다. 실행 제어용 원장 한 건은 학습 정확도 1/1을 뜻하지 않습니다.

언어 선형층 496개에 LoRA 파라미터 58,363,904개가 생겨 float32 어댑터 payload는 233,455,616바이트입니다. 로그 포함 예산은 260MiB로 제한하고 시작 전/저장 후 디스크 3GiB 잔여를 검사합니다. 기존 다른 학습 산출물 예산과 합산해야 합니다. 실제 cgroup 메모리의 남은 용량이 12GiB 미만이면 원인 기록 후 멈춥니다. 메모리에 남은 임시 모델 캐시도 이 값에 포함됩니다. GPU 단계마다 여유 VRAM 1GiB를 확인합니다. 12GiB는 보수적인 시작 조건이며 충분성 증명은 CUDA smoke가 담당합니다.

## 한계와 다음 확인

현재 설치판의 선형 attention이 최적화 커널 대신 PyTorch 참조 계산으로 동작하는 경고를 작은 구조에서 확인했습니다. 이 실행기가 빠르다고 주장하지 않습니다. CUDA smoke에 문항당 걸린 시간과 최대 메모리를 기록합니다. 전체 27B 로딩, CUDA dtype 수치 안정성, 긴 문항의 메모리와 속도는 아직 미측정입니다. 실패할 경우 원인 수정 후 별도 시도를 만들며 학습 성공으로 세지 않습니다.

완성 파일은 custom packed-LoRA A/B 형식입니다. llama.cpp에서 사용할 어댑터 변환, 원본/기존 학습판/보류 자료 재평가는 후속 작업입니다. 학습 완료가 제품 모델 채택이나 실제 서비스 연결 완료를 뜻하지 않습니다.

## 후속 GGUF 변환 구현과 큐 등록

학습 control 작업의 단일 큐 등록을 확인했습니다. 현재 실행 중인 다른 A4000 작업을 끊거나 GPU 모델을 중복 로드하지 않았습니다. 이 보고의 GPU 학습 분자는 여전히 0입니다.

후속 변환은 별도 제어 작업이며 학습의 `completed.json`과 어댑터 해시가 일치할 때만 진행합니다. 본 학습 원본 어댑터는 기존 디스크에 보존하고, PEFT 중간본 및 f16 GGUF는 메모리 기반 임시 저장소에만 만듭니다. 완성 GGUF는 임시 파일에서 원자적으로 교체하고 변환 메타데이터에 해시와 텐서 개수를 기록합니다. 변환 완료와 실제 GPU 로딩 호환 성공은 구분해야 하므로, 최초 로딩 검사를 통과한 뒤 후속 평가에 공급합니다.

공식 변환기로 전체 496개 대상의 rank1 합성 어댑터를 CPU에서 dry-run한 뒤 실제 변환했습니다. 입력 992/992 텐서가 출력에 보존됐고 f16 파일은 14,659,296바이트였습니다. 선형 attention의 출력 열·z 행·a 행·qkv의 V행에 해당하는 네 가지 재배열 결과를 수치로 대조해 4/4가 정확히 일치했습니다. 합성 변환 성공은 학습된 실제 어댑터의 성능이나 GPU 로딩 성공을 증명하지 않습니다.

첫 공식 변환 시도는 학습에 포함하지 않는 MTP(다음 토큰 예측 보조층)를 요구하는 assertion에서 실패했습니다. 기존 변환기 파일은 수정하지 않고, 같은 Qwen3_5ForCausalLM 클래스의 어댑터 전용 `no_mtp=True` 조건을 적용하는 호환 래퍼로 해결했습니다. 실패 로그와 수정 후 원본 결과를 모두 보존합니다. 모델 이름이나 가중치 계보를 다른 모델로 대체한 처리가 아닙니다.

[후속 변환 실행기](../../../../program/scripts/plan_qa_bench/server/saluki_lora_convert_20261012.py)는 기존 큐 Python과 학습 가상환경이 다른 경우 검증된 가상환경으로 실행을 전환합니다. 실제 어댑터의 텐서 수·유한값·완료 기록을 확인합니다. 변환 실패도 자동 반복하지 않습니다. [이 보고서의 변환 근거 추가 전 백업](_backup/2026-10-12_1755_saluki_conversion_proof/)을 보존했습니다.
