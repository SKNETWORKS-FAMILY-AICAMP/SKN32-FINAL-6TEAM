## 1. 실제 문자로 잰 비율

### 세트

- 재료: 전국 재난 문자 2023-09 ~ 2026-10 고유 50,070건 + 서울 2026 고유 760건(`datasets/safety/`, git 밖).
- 후보 600건(문안이 같은 것은 하나만):
  - 무작위 몫 220 — 장소 낱말(궁 · 공원 · 산책로 · 해수욕장 …)과 멈춤 낱말(중단 · 통제 · 금지 · 폐쇄 …)이 함께 있는 2,707건에서 무작위.
  - 닫힘 낱말 몫 180 — 휴관 · 휴장 · 폐쇄 · 운영 중단 · 「문을 닫」 등. ☆후보 조건이 「창문을 닫으세요」 화재 문자까지 잡아 대부분 닫힘이 아니다(오답 시험으로 둔다).
  - 보충 200 — 위 낱말에서 「창문」을 뺀 1,518건에서 무작위.
  - 각 몫을 id 해시로 dev / holdout 반씩.
- 정답: 같은 기준서(`eval/closure/closure_label_guide.md`)와 본문만 보고 두 채점자가 따로 붙였다.
  - Claude 하위 작업 — 규칙 · 코드 · 다른 정답 파일을 보지 않게 했다.
  - Codex `gpt-6.1-sol`.
  - 일치 581/600 = 96.8%, 카파 0.87. **둘이 같다고 한 581건만 정답**으로 쓴다. 갈린 19건은 「생태공원 출입 자제 요청」 · 「위험지역 접근 금지 목록 안의 장소 이름」 같은 경계 사례였다.
- ☆규칙을 쓴 쪽(Claude)과 한 채점자가 같은 회사 모델이다. 그래서 Codex 를 두 번째 채점자로 두고 일치한 것만 썼다.

### 결과 (정답 581건 — 닫힘 72 · 닫힘 아님 509)

| 묶음 | 닫힘 | 감시로 보냄 — 고치기 전 규칙 | 지금 규칙 | 지금 규칙 → 모델 | 닫힘 아님에 「장소 닫힘」 이름표 |
|---|---|---|---|---|---|
| 전체 | 72 | 71/72 = 98.6% | 71/72 = 98.6% | 72/72 = 100% | 0/509 = 0% |
| dev | 36 | 36/36 | 36/36 | 36/36 | 0/252 |
| holdout | 36 | 35/36 = 97.2% | 35/36 = 97.2% | 36/36 = 100% | 0/257 |
| 무작위 몫 | 40 | 40/40 | 40/40 | 40/40 | 0/170 |

- 규칙만으로 놓친 1건: 「야생조류 고병원성 AI 검출 ▲야생조류 서식지(강진만) 폐쇄」(holdout). 시설 이름 목록에 「서식지」가 없다. 모델이 「야외 위험」으로 잡았다.
- **실제 문자의 닫힘은 말투가 다르다.** 10-13 에 넣은 「장소 닫힘」 종류는 「경복궁 임시 휴관」 · 「관람 전면 중단」 같은 문장을 보고 만들었다. 그런데 실제 문자 72건은 거의 다 「산책로 통제」 · 「등산로 입산 통제」 · 「야영장 이용 중단」 · 「공원 전면 통제」 · 「물놀이장 휴장」이다.
  - 72건 모두 다른 종류로 먼저 걸려 감시까지는 간다: 도로 53 · 위험 9 · 야외 위험 6 · 지하철 2 · 인파 1 · 없음 1.
  - 그래서 「장소 닫힘」 이름표가 붙은 닫힘 문자는 **0/72** 다. 고치기 전 규칙과 「보냄」 비율도 같다. 이 세트에서는 10-13 변경이 잡는 건수를 늘리지 않았다.
  - 이름표는 지금 어느 장소에 거는지만 바꾼다: 「야외 위험」이면 날씨 영향 장소에만, 나머지는 그 지역 모든 장소에. 활동 판정은 이름표가 아니라 본문과 장소 이름을 본다. 그래서 실내 장소에 「야외 위험」 닫힘이 안 걸리는 경우만 영향이 있다(6건, 모두 야영장 · 계곡 · 해변처럼 야외 장소 닫힘이었다).
- 활동 팀 예시 같은 궁 · 박물관 휴관 문자는 3년치 전국 문자에 사실상 없었다. 그 말투가 실제로 오는지는 이 데이터로 말할 수 없다.

- 부른 방법: 이 PC → x600 서버 Ollama 로 SSH 터널. 앱의 `NoticeImpactModel` 과 `register_from_settings` 를 그대로 썼다(지시문 · 근거 조각 검사 · 「영향 없음」 처리 모두 앱 코드). 스위치 `travel.notice_impact.mode` = on.
- 운영과 같은 순서로, 규칙이 「영향 없음」이라 한 문자에만 불렀다: 24번 호출 · 오류 0 · 중앙 1.5~1.65초.
- 정답이 있는 규칙-없음 문자 20건(재해구분 「기타」로 넣어 앱의 `disaster_msg.judge` 경로 그대로):

|---|---|---|
| 닫힘(1) | 1 | 0 |
| 닫힘 아님(19) | 15 | 4 |

- 잘못 보낸 15건 중 14건이 「야외 위험」이다 — 물놀이 수칙 · 해안가 접근 금지 · 강풍 시 소각 금지 같은 안전 수칙. 「야외 위험」은 날씨 영향 장소에만 걸린다. 10-13 의 「잘못 보냄 13/28(holdout)」과 같은 경향이다.

## 3. DB 시나리오 · e2e 시험

- 전용 DB `acop_closure_1014` 를 새로 만들고 ci-main 과 같은 순서로 준비했다(표 만들기 → 프롬프트 등록 → 데모 데이터). 다른 세션이 쓰는 개발 DB(`acop_cs`)는 건드리지 않았다.
- 새 시나리오 [test_place_closure_watch.py](../../../tests/scenario/test_place_closure_watch.py) — DB 에 저장한 여행(경복궁 · 국립중앙박물관)을 샘플 CSV 와 같은 열의 「기타」 문자로 점검하고 활동 재판정까지 잇는다: **3/3 통과**.
  - 「경복궁 임시 휴관」 → 경복궁만 이상, 박물관은 활동 판정이 뺀다.
  - 활동 판정이 등록 안 됐으면 두 곳 다 이상(모름을 지우지 않는다).
  - 「하천변 · 해안가 출입금지」는 「장소 닫힘」으로 바뀌지 않는다.
- 기존 DB 시험 — 재난문자 · 감시 · 안전 정지 경로를 지나는 24파일(e2e 11 · 통합 4 · 시나리오 9, 고른 방법: 그 경로의 모듈 이름을 부르는 시험 파일 전부): **통과 348 · 실패 1 → 고친 뒤 349/349**.
  - 실패 1건 `tests/integration/test_watch_monitoring.py::test_safety_first_simulation_keeps_all_six_actual_input_checks` 는 이번 변경과 관계없는 **원래 있던 순서 의존 결함**이었다. 점검 코드는 시험 입력을 연결 자리(`simulation_hook`)에서 꺼내는데, 이 시험은 앱 조립 없이 돌아 그 자리가 비어 있었다(혼자 돌리면 늘 실패, 앞 시험이 조립하면 통과). 원인은 「모니터링 루프 문제 처리」 세션이 찾았다(10-12 병합부터로 추정). 같은 경로를 보는 `test_watch_simulation.py` 와 같은 방식으로 시험 안에서만 자리를 채우는 한 줄을 넣었다 → 그 파일 12/12.
- ☆이 PC 는 남은 가상 메모리가 0.2~2GB 로 오르내린다. 시험 중 로컬 개발 DB(5433)가 메모리 부족으로 세 번 다시 시작해 연결 오류가 났다(다른 세션의 전체 시험과 겹침). 그래서 DB 가 1분 넘게 안정되고 메모리가 남을 때만 파일을 하나씩 돌리고, 연결 오류가 난 파일은 다시 돌렸다. 연결 오류는 코드 실패로 세지 않았다.

### 운영 감시 경로로 한 회차

시나리오 시험은 감시의 두 경로 중 활동 재판정이 붙은 쪽(`TripWatcher`)을 본다. 운영처럼 Case 를 여는 경로(`TripWatchCaseOpener` — 관리자 화면 「감시 현황·로그」에 남는 쪽)도 따로 한 회차 돌렸다. 전용 DB `acop_closure_web_1014`, 테넌트 demo, 데모 데이터의 경복궁 · 국립중앙박물관을 90분 안 일정으로 넣고 「기타」 휴관 문자 한 통을 샘플 CSV 로 줬다. 분류 · 실행 계획은 시나리오 시험과 같은 대역(`fixture_plan`), 날씨는 「맑음」 대역이다.

| 단계 | 결과 |
|---|---|
| 감시 점검(관리자 화면에 남는 기록) | 경복궁 · 국립중앙박물관 **둘 다 「문제 감지」**, 근거 문자 「[국가유산청] 경복궁 임시 휴관합니다」 |
| Case | 여행 하나에 묶음 Case 1개 → 활동 팀 처리 |
| 활동 팀 판정 | 박물관은 영향 없음으로 뺐다. 경복궁만 알림 |
| 고객 알림 | 「⚠️ 안전 알림 — 경복궁 — 기타. 대신 갈 수 있는 곳을 찾지 못해 일정은 그대로 두었어요. 가시기 전에 한 번 확인해 주세요.」 |
| 일정 판 | 바뀌지 않음(판 1 그대로) |

- **Case 를 여는 경로에는 활동 재판정이 없다.** 그래서 이름이 다른 장소(박물관)도 일단 Case 에 들어가고, 활동 팀 안(`plan_activity_trigger` → `_without_cleared_disasters`)에서 빠진다. 고객 알림은 맞게 나가지만, 관리자 화면 기록과 Case 수는 「닫힌 장소」보다 많다.
- **알림 문구에 재해구분 원값 「기타」가 그대로 나온다**(「경복궁 — 기타.」). 고객에게는 무슨 일인지 안 보인다. 본문 요약이나 영향 종류(장소 닫힘)를 써야 한다 — 이 작업 범위 밖이라 고치지 않았다.
- 처음 두 번은 분류 대역을 빼먹어 Case 가 「분류 실패」로 끝났다(시험 준비 실수 — 코드 결함 아님). 날씨 자료원을 안 넣었을 때는 날씨 영향 장소인 경복궁이 「조회 실패」로 가려졌다.

## 4. 웹 화면

**확인하지 못했다.** 관리자 화면(운영자 콘솔)을 실제 연결 모드로 띄워 위 회차를 「감시 현황·로그」에서 보려 했다.

- 한 일: 운영 API(127.0.0.1:8070)를 전용 DB · 이번에 만든 시험용 운영자 계정으로 띄우고, 관리자 화면 개발 서버로 로그인까지 했다(홈 화면 표시 확인).
- 막힌 곳: 「감시 현황·로그」 화면을 컴파일하는 도중 남은 가상 메모리가 0.7GB 로 떨어져 개발 서버가 두 번 꺼졌다(10-14 · 10-15). 공용 DB 가 같이 쓰러질 위험이 있어 멈췄다.
- 안 해 본 것: 미리 빌드한 판(`.next-watch-monitoring-1009`)은 화면 코드가 그 뒤(10-09 23:05) 바뀌어 지금 화면이 아니라 쓰지 않았다. 메모리가 3GB 넘게 남을 때 `next build` 로 새로 빌드해 보는 것, 다른 기계에서 띄우는 것은 해 보지 않았다.
- 대신 확인한 것: 화면이 읽는 API 의 원본(회차 · 점검 기록 표)을 DB 에서 직접 읽어 위 표를 만들었다. 화면 렌더링 자체는 확인하지 않았다.

## 남은 것

- Case 를 여는 감시 경로에도 활동 재판정을 붙일지(지금은 Case 를 연 뒤 활동 팀 안에서 거른다) — 코어 · 활동 팀이 정할 일.
