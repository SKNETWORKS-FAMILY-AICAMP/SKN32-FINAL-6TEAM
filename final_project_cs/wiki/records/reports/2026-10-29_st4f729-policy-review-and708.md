# ST4F-729 보존 규칙 검토와 ST4F-708 독립 시험

2026-10-29 KST. **ST4F-729는 HOLD를 유지합니다.** 기술 판단 위임을 이전 명시적 보존 지시의 폐기로 해석하지 않았습니다. SHA 예외와 검사 범위 변경은 적용하지 않았고, 기존 evidence와 탐지기의 원본 바이트를 보존했습니다. 대신 현재 미배정 ST4F-708의 독립 검증을 새 격리 사본에서 진행했습니다. 담당은 이번 Codex 세션이며 다른 사람·에이전트의 검토 승인을 주장하지 않습니다.

## 대안과 적용 경계

[루트 규칙](../../../../AGENTS.md)의 원본 삭제·일치화 금지, [CS RULE](../../../RULE.md)의 “과거 기록은 추가 기록으로 보완”, “현재 사양을 과거 evidence·history·동결 계획에 소급 반영하지 않습니다”, [문서 표준](../../../../wiki/governance/document-standard.md)의 “자동 생성 문서를 손으로 고치지 않는다”를 적용했습니다. [기존 후속](2026-10-29_st4f729-source-followup.md)은 “보존 형식 변경은 별도 명시적 승인 전까지 하지 않습니다”라고 기록합니다. 이 마지막 문장은 이전 세션의 보류 기록이며 새로운 사용자 지시 자체로 취급하지 않습니다. 이번에는 사용자가 명시적으로 이전 지시를 무시하지 말라고 했고, 기존 기록을 보완하라는 현재 RULE도 남아 있습니다.

| 대안 | 판정과 이유 |
|---|---|
| 특정 SHA의 testcase 이름만 탐지 전 가리기 | 기각. 바이트가 같은 대상에 실제 탐지 예외를 만듭니다. 이번 사용자의 탐지 약화 금지와 양립하지 않습니다. |
| 원시 XML을 로컬에 보관하고 추적 XML을 유효한 가림 XML로 교체 | 기술적으로 가능하지만 적용 보류. 메모리 실험에서 XML 구조와 testcase 수를 유지하며 통과했습니다. 그러나 과거 생성 evidence의 추적 버전을 소급 교체합니다. 단순 기술 위임을 이 보존 규칙의 예외 승인으로 해석하지 않습니다. |
| 원시 XML을 보관소로 옮기고 추적 해제·압축·바이너리 변환 | 기각. 원래 검사하던 텍스트가 검사 대상에서 빠집니다. 별도 백업이 있어도 탐지 범위 보존 조건을 충족하지 않습니다. |
| 가림 파생본을 별도 추가하고 원시 XML도 계속 추적 | 보존은 가능하지만 blocker를 해소하지 못합니다. 원래 XML의 탐지 5건은 그대로 남습니다. 불필요한 파생 파일을 추가하지 않았습니다. |
| 이후 pytest 산출물의 안정된 표본 ID | 기존 생성 원인 수정 후보는 유효합니다. 검사기·표본·assert를 그대로 두면서 향후 정상 실행 XML의 표본 노출을 막습니다. 과거 XML의 실패를 해소하지는 못합니다. 기존 후보를 재통합하지 않았습니다. |

[판단] 현재 확인한 조건을 모두 유지하면서 기존 XML을 GREEN으로 바꾸는 방법은 없습니다. 원본 바이트를 그대로 검사하면 동일한 탐지가 나옵니다. 특정 evidence를 재발행하는 별도 보존 규칙이 명시적으로 정해지기 전에는, 예외 없이 HOLD하고 독립 작업을 진행하는 것이 이번에 적용한 결론입니다. 규칙 파일을 변경하지 않았습니다.

## 독립 보안 검증

[실측] 원본 XML SHA256은 `4139dd065887867094dd053a5e9de007697efe039a57a64b200dd15584bd3a0a`로 동일합니다. 가림 feasibility는 메모리 안에서만 실행했고 가림 XML 파일을 저장하지 않았습니다. 원본·기존 보고서·기존 패치를 수정하거나 이동·삭제하지 않았습니다.

| 이번 실행 | 결과 |
|---|---|
| 로컬 탐지기 사본 독립 probe |31/31 = 100% |
| 최신 커밋의 탐지기 사본 독립 probe |31/31 = 100% |
| 최신 커밋 전체 CS 텍스트 blob 검사 |9,690/9,691 = 99.99%, 실패 파일 1개 · 원시 탐지 5건 |
| 전체 CS blob 분류 |10,888개 중 텍스트 9,691개 · 기존 NUL 휴리스틱상 바이너리 1,197개 |

probe는 독립 조립한 IP·SSH·웹훅·개인키 표본을 testcase 이름·다른 속성·본문·tail에 주입하는 16건, 원시 XML 뒤에 붙이는 4건, 탐지 분기 4개를 각각 메모리에서 끈 반례 확인, 원본·구조·바이트 보존 검사입니다. 보안 분기 변이는 원본 모듈을 쓰지 않고 복사 모듈 상태에만 적용한 뒤 되돌렸습니다. 정상 probe의 성공은 보안 관문 GREEN을 뜻하지 않습니다. 변경하지 않은 탐지기가 기존 XML을 계속 거부하는 것이 예상 결과입니다.

팀 role-manager의 실제 조회 tip은 `fab3da50ab970a7d8c79ed65c1df2e666abc1cd0`입니다. 새 clone의 `git ls-tree`와 `cat-file --batch`로 **sparse checkout에 없는 경로도 포함한 전체 CS blob**을 읽었습니다. 해당 커밋의 탐지기와 기존 허용 목록 1개를 그대로 사용했습니다. 새 허용·경로 제외·SHA 분류 0입니다. 처음 로컬 탐지기를 원격 commit에 적용한 집계는 기존 허용값 차이로 파일 5개를 검출했으므로, 같은 커밋의 탐지기로 바로잡았습니다. 첫 결과도 작업 폴더에 남겼고 최종 판단에 사용하지 않습니다.

이것은 변경하지 않은 raw-text 검사 술어의 전체 commit 검산입니다. RULE의 전체 pytest security·contract·DoD를 이번에 재실행한 결과가 아닙니다. 앞 보고서의 필수 2/3 = 66.7%는 이전 실행 결과이며, 이번 결과로 재기재하지 않습니다. 새 통합·커밋·푸시는 하지 않습니다.

## ST4F-708 격리 진행
