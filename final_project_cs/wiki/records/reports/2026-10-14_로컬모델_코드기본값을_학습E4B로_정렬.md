# 로컬 언어 모델 코드 기본값을 학습 E4B 로 정렬 — 2026-10-14 (Claude, 「코드 기본값 정렬」 작업)

사용자 지시(2026-10-14): 「코드 기본값은 gemma4:12b 이지만 운영 설정이 바꿔 놨다 → 코드 기본값도 우리 학습모델 쓴다고 해놔.」 이어서 「대기 시간도 9초로 올려」.

## 결론

cs 프로젝트 코드의 로컬 모델 기본값이 x600 서버 운영 설정과 같아졌다. 운영은 이미 같은 값이라 서비스 동작은 달라지지 않는다. 어긋나 있던 것은 코드 기본값뿐이었다.

| 설정 | 전 (코드 기본값) | 후 (코드 기본값) | x600 서버 운영 |
|---|---|---|---|
| 로컬 모델 `ollama_model` | `gemma4:12b` (학습 없음) | `tripilot-pointer:e4b-ft` (Ollama `gemma4:e4b` Q4_K_M 에 일정 항목 짚기 자료로 LoRA 학습) | `tripilot-pointer:e4b-ft` |
| 문맥 길이 `ollama_num_ctx` | 8192 (10-14 에 이미 바뀜) | 8192 | 8192 |
| 로컬 대기 `llm_failover_primary_timeout_seconds` | 6초 | 9초 | 9초 |

근거: [채팅 요청 해석 근본 개선 1차](2026-10-14_채팅해석_근본개선_1차.md) 「x600 서버 반영」 절 — 434 문장 재생(채점용 126)에서 할 일 85% · 대상 78%(학습 없는 12B 74% · 72%, 유료 대체 79% · 67%). 학습 E4B 해석 한 건이 5.1~7.3초(x600 서버 실측)라 대기 6초면 8건 중 6건이 유료 대체로 넘어가고, 9초면 8/8 이 로컬로 끝났다. 넘어가도 유료 대체(2~3초)까지 `llm_failover_total_seconds`(15초) 안이다.

## 알고 넘어갈 것

- **개발 PC**: 학습 모델 `tripilot-pointer:e4b-ft` 는 우리가 Ollama 에 올려 둔 곳에만 있다. 로컬 Ollama 에 없으면 호출이 「모델 없음」으로 실패하고, 부르는 쪽이 이전과 같이 「모름」으로 기록한다(넘김 장치는 개발 환경에서 꺼짐). 있는 모델은 `ACOP_OLLAMA_MODEL` 로 지정한다(`.env.example` 에 안내). 모델 이름 문자열만 바뀌었고 오류 처리 경로는 그대로다. 실제 Ollama 가 모델이 없을 때 내는 오류 문구는 확인하지 못했다.
- **일정 짚기 문맥 길이**: 일정 짚기 모델이 기본 모델과 같으면 문맥 길이 8192 를 같이 보내는 기존 코드(`item_pointer.py` `register_from_settings`)가 있다. 두 값이 같게 설정된 환경은 이제 한 모델로 묶여 동작한다(운영은 이미 그렇다).
- **정책 검색 임베딩 대기**: `rag/retriever.py` 가 같은 대기 값(9초)을 쓰므로 함께 9초가 된다(운영은 이미 9초).
- **남긴 12B 언급**: 과거에 12B 로 잰 값을 적은 주석 · 시험 설명 · 보고서(`ollama_chat.py` 의 실측 주석, `planner.py` · `decision_unit.py` · `run_sweepers.py` 의 실측 주석, `wiki/records/` · `eval/` 보고서, `llm-failover.md` 정확도 표의 Gemma 4 12B = 10-07 당시 평소 경로)는 측정 당시 모델이므로 고치지 않았다. 자료 만드는 도구 `ml/label_with_gemma.py` · `ml/synthesize_with_gemma.py` 의 `--model` 기본값도 서비스 설정이 아니라 그대로 뒀다.
