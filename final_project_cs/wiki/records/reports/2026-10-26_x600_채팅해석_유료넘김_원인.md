# 2026-10-26 x600 채팅 해석이 유료로 넘어가는 원인 (읽기 전용 진단)

## 결론
- 최근 해석 기록 17건 중 15건(88%)이 유료로 넘어갔다. 사유는 timeout 11/15(73%), circuit_open 2/15(13%), not_loaded 2/15(13%)다.
- **timeout(주원인)**: 해석 호출이 고정 9초(`ACOP_LLM_FAILOVER_PRIMARY_TIMEOUT_SECONDS=9`) 안에 끝나지 못했다. 합성 여행으로 실측해 보니 프롬프트가 **7,842토큰**이고, 출력이 220토큰이었다. 캐시가 비어 있을 때 전체 12.55초, 캐시를 다시 쓸 때 6.4~7.1초 걸렸다. 로컬 성공 2건도 7.64초·8.84초로 9초 바로 아래였다. 9초는 정상 답도 끊는 값이다.
- **circuit_open**: 원인이 따로 있지 않다. timeout이 3번 이어지면(`llm_failover_failures=3`) 60초 동안(`llm_failover_open_seconds=60`) 로컬을 건너뛴다. 두 건 모두 2.45초·2.98초 만에 유료로 바로 갔다.
- **not_loaded**: 05:11:32에 모델 runner(llama-server pid 19428)가 새로 떴고, 05:12:02·05:12:06 해석은 모델이 아직 올라오는 중이라 `/api/ps`에 보이지 않았다. 스트림 경로는 이때 로컬을 건너뛰기만 하고 모델을 올리지는 않는다(`llm_failover.py` `_streaming`).
  - runner가 내려간 직접 원인은 **Ollama 로그가 남지 않아 확정하지 못했다**. 다만 코드·환경으로 확인된 메커니즘이 하나 있다. 일정 짚기 호출(`OllamaItemPointer`)이 `keep_alive=30m`(`ACOP_OLLAMA_POINTER_KEEP_ALIVE=30m`)를 보내므로, 마지막 요청이 일정 짚기면 30분 뒤 모델이 내려간다.
  - num_ctx가 달라서 다시 뜬 것은 아니다. 모델 파일 기본값이 `num_ctx 8192`라 jikimi(`/v1`, num_ctx 없음)도 8192로 같다.
  - 다른 모델 때문에 밀려난 흔적도 없다. 지금 `/api/ps`에는 tripilot-pointer 하나뿐이다.
- **추가로 발견한 위험 2건(긴급)**:
  1. Ollama를 띄우는 작업 스케줄러 작업 `\Jikimi Ollama serve`의 `ExecutionTimeLimit=PT72H`다. 마지막 시작이 10-23 07:46:17이므로 **10-26 07:46쯤 작업 스케줄러가 ollama.exe를 끝낼 수 있다.** 다시 시작하는 설정도 없다(RestartCount 0, 트리거는 로그온뿐). 그러면 로컬 호출이 전부 연결 실패로 유료로 넘어간다.
  2. RTX 4070 SUPER는 **Thunderbolt(Intel DEV_15EF) 외장 GPU**다. 그 상위 PCIe Root Port 0:3:1(AMD DEV_14EF)에서 WHEA 17(수정된 PCIe AER 오류)이 GPU를 쓸 때마다 대량으로 나온다. 모델이 올라오던 05:11에는 분당 1,777건, 이번 측정 3회 동안에는 10분에 71건에서 579건으로 늘었다. System 로그(20MB 순환)가 이 오류로 차서 **03:46 이전 기록이 모두 밀려났다.**
- 프롬프트 7,842토큰 + `num_predict 400` = 8,242로 `num_ctx 8192`를 넘는다. 이번 답은 220토큰이라 넘지 않았지만, 일정이 많은 여행(이번 합성 여행은 16항목)에서는 앞부분이 잘리거나 문맥이 밀릴 위험이 있다(`--context-shift --keep 4`). 10-14 설정 주석에는 약 4,600토큰으로 적혀 있었다.

## 2. timeout 원인: 실제 해석 호출 크기 재현
- 방법: x600 api 컨테이너 안에서 **배포된 앱 코드**(`decision_unit._prompt` · `_schema` · `SYSTEM+EDIT_SYSTEM`)로 합성 여행(3일 16항목, 변경 1, 직전 대화 2줄, 고객 원문 없음)의 프롬프트를 만들었다. 그 프롬프트로 `OllamaChat._stream`과 같은 옵션(`stream True`, `think False`, `format`=스키마, temperature 0, `num_predict 400`, `num_ctx 8192`, keep_alive 없음)으로 3회 호출했다. 스크립트는 `cache/scratch/x600_decision_probe.py`다.
- 크기: system 14,128자, user 1,711자, schema 6,965자 → prompt_eval_count **7,842토큰**

| 1(캐시 없음) | 5.93초 | **12.55초** | 7,842토큰 4.19초 | 220 / 6.57초(33.5/s) | 0.39초 | 0.84초 | 정상 |

- 실제 기록과 맞춰 보기: 로컬 성공은 7.64초·8.84초였다. timeout 11건은 11.15~12.61초(=로컬 9초 + 유료 2~3초)였다.
- 단일 슬롯(`-np 1`)이라 일정 짚기·계획 읽기·jikimi 요청이 사이에 끼면 KV 캐시가 바뀐다. 그러면 1회처럼 7.8k토큰을 다시 계산해야 하고(4.2초), 9초를 넘는다.
- 생성 속도는 7.8k 문맥에서 33~40토큰/초이고, 짧은 문맥에서는 63토큰/초(부모 실측)다. 220토큰 생성에만 5.6~6.6초가 든다.
- 배포된 스트림 설정 `{first_token 8, stall 5, max 15}`로 계산하면 3/3(100%)이 통과한다. 첫 조각 최대 5.93 < 8, 조각 사이 최대 0.39 < 5, 전체 최대 12.55 < 15다. 다만 05:37 배포 이후 실제 기록은 아직 없다.
