# 채팅 문맥 수정 운영 반영과 실제 화면 확인

x600 서버의 cs 프로젝트 서버에 이번 채팅 문맥 수정을 반영했습니다. 실제 고객 화면에서 N서울타워 질문 뒤 이름 없는 후속 질문이 같은 장소로 이어졌고, 새로고침 뒤에도 대화·선택지가 복구되어 동작했습니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 배포 파일 일치 | 확인 | 8/8 = 100% |
| 실행 구성 교체 | 완료 | 3/3 = 100% |
| 실제 화면 검증 | 통과 | 3/3 = 100% |

분모는 각각 이번 수정 파일 8개, API·worker·고객 웹 3개, 아래 고객 동작 3개입니다. 배포 승인은 이번 대화의 “x600 서버에 이번 채팅 문맥 수정 반영하고, 실제 서비스에서 후속 질문이랑 새로고침까지 확인해 줘” 요청입니다. 커밋·푸시는 수행하지 않았습니다.

## 실제 서비스에서 확인한 것

2026-10-12 01:27~01:29 KST에 기존 로그인된 브라우저에서 등록된 시험 여행을 사용했습니다. 지도에서 고른 일정은 없는 상태였습니다. 실제 모델·운영 DB를 사용했으며 읽기 질문만 보냈습니다.

| 확인 | 입력·동작 | 관측 결과 |
|---|---|---|
| 이름 없는 후속 질문 | “서울 타워 저거 뭐야?” → “자세히 알려줘” | 두 답변 모두 N서울타워. 저장된 후속 답변의 대상 연결 출처가 `previous_fact`이며 직전 대상과 일치 |
| 새로고침 | 브라우저 새로고침 → 채팅 탭 | 새 답변·더 보기·장소별 선택지 3개 복원. 새 답변에 선택지 문장을 중복 표시하지 않음 |
| 복원된 선택지 실행 | “1일차 19:00 N서울타워 다음 일정 알려 줘” 클릭 | N서울타워 다음 일정이 호텔임을 답함. 실제 요청의 `selected_item_id`와 답변의 대상 ID 일치, 접수 `resolved` |

첫 질문은 비교 기준을 만드는 준비 동작이며 3개 확인의 분모에 별도로 더하지 않았습니다. 세 접수 모두 `resolved`였고 여행 일정 버전은 시험 전후 2로 같았습니다. 사실 질문으로 일정을 변경하지 않았습니다.

화면 증거와 상세 접수 식별자는 git 밖 [이번 검증 작업 폴더](../../../../scratch/chat-context-20261011/)에 보존합니다. `production-fixed-followup-20261012.jpg`는 후속 답변, `production-fixed-refresh-20261012.jpg`는 복원된 선택지, `production-fixed-choice-result-20261012.jpg`는 복원된 선택지를 누른 결과입니다. `operating-after-ui.json`과 `production-choice-proof.json`은 해당 여행만 읽은 접수 확인입니다.

## 배포 범위와 검증

실제 실행 컨테이너에서 읽은 소스를 기준으로 다음 부분만 적용했습니다. 작업 폴더 전체 또는 다른 대화의 변경을 복사하지 않았습니다. 기능 안내·목록 조회·팀 실행 변경·위치 동의·최신 대화 이동 버튼은 이번 운영 반영에 넣지 않았습니다.

| 파일 | 반영한 내용 |
|---|---|
| [대상 연결](../../../app/domains/travel_ops/components/conversation/fact_context.py) | 현재 여행의 대상·버전·유효시간 확인 |
| [메시지 처리](../../../app/domains/travel_ops/components/conversation/trip_messages.py) | 답변 대상 연결과 구조화된 기록 보존 |
| [선택지 생성](../../../app/domains/travel_ops/components/conversation/decision_unit.py) | 선택지에 확인된 일정 ID 포함 |
| [대화 읽기](../../../app/domains/travel_ops/components/conversation/chat_log.py) | 해당 여행의 답변·선택지 복원 |
| [운영 제한](../../../config/guardrails.yaml) | 자동 대상 승계 유효시간 1,800초 |
| [웹 대화 자료형](../../../frontend/apps/web/src/features/trip/model.ts) | 선택적 일정 ID |
| [웹 선택지](../../../frontend/apps/web/src/features/trip/trip-chat.tsx) | 클릭한 선택지의 일정 ID 전달 |
| [웹 대화 읽기](../../../frontend/apps/web/src/lib/live/gateway.ts) | 운영 기록에서 선택지·답변 복원 |

운영 후보는 운영 소스 사본 + 위 8개 변경으로 만들었습니다. 시험 준비물은 운영 기준 커밋의 호환되는 준비물을 사용하고 새 회귀 사례를 더했습니다. 로컬 소스 전체의 앞선 검증과 이번 운영 후보 검증은 구분합니다.

- 운영 후보 새 채팅 회귀 시험 **6/6**, 대상 연결·보호 규칙 단위 시험 **39/39** 통과. 기존 회귀를 넓혀 실행하던 도중 로컬 개발 DB 연결이 끊겨 전체 묶음 성공은 선언하지 않습니다. 재실행은 DB 연결 시간 초과였고 로컬 포트 연결 실패도 확인했습니다.
- 후보 API 이미지에서 수정 모듈 import 성공. 후보 웹 이미지의 형식 검사와 운영 빌드 성공.
- 최종 실행 이미지에서 수정 파일 SHA-256 **8/8 일치**. API·고객 웹 `healthy`, worker `running`, 모두 재시작 0회. worker 자체 건강 검사는 정의돼 있지 않으며 이번 확인으로 감시·배달 회차 성공을 주장하지 않습니다.
- mock 서버 시험: 이번 운영 반영 턴에서는 재실행하지 않음. 앞선 로컬 화면 시험 1/1은 [이전 보고](2026-10-12_0015_채팅_후속질문_대상과_기억_검토.md)에 분리 기록.
- 실서버 확인(서버 응답): **했음**. x600 서버의 cs 프로젝트 서버에서 위 실제 질문·새로고침·선택지 동작 3/3과 운영 접수 기록을 확인.

최종 이미지 식별자:

| 실행 구성 | 불변 이미지 ID |
|---|---|
| API·worker | `sha256:a7c6414e5d7ab15fe26ca7d358b754cff73de6c31d31484e2155b3e9d52989b1` |
| 고객 웹 | `sha256:d323b587e59cdfad9f2c53a15d8b6e900827958641f3b575c6da0ec449bdf192` |

`final-audit.json`에 파일별 실제 해시와 실행 상태를 보존했습니다. 운영 Compose는 새 이미지 이름을 명시적으로 가리키며 기존 환경 주입·마운트·네트워크를 유지합니다. API와 worker의 기존 환경 값은 교체 전후 일치했습니다. DB·관리 앱은 교체하지 않았고 기존 컨테이너가 유지됐습니다. DB 구조 변경 명령은 실행하지 않았습니다.

## 실패한 시도와 복구

첫 API 빌드는 Dockerfile의 `FROM`에서 원시 이미지 ID를 이미지 이름처럼 해석해 실패했습니다. 기존 이미지를 별도 이름으로 고정해 다시 빌드했습니다. 이 단계는 실행 중 서비스에 영향을 주지 않았습니다.

첫 웹 후보는 빌드에는 성공했지만 실제 화면에서 접속 설정 누락이 나타났습니다. 기존 최종 이미지에는 원래 빌드 단계의 `NEXT_PUBLIC_*` 환경이 없는데 이를 다시 빌드하면서 주입하지 않은 것이 원인입니다. 웹만 즉시 이전 정상 이미지로 복구했고, 기존 공개 빌드 설정을 명시한 두 번째 웹 이미지로 교체했습니다. 최종 실제 화면 시험은 두 번째 이미지에서 수행했습니다. 처음의 컨테이너 건강 검사 통과를 고객 기능 통과로 기록하지 않습니다.

검증 준비 과정에서 비밀 환경 파일을 추가 사본으로 복사하는 단계가 자동 승인 검토에 거절됐습니다. 해당 복사를 제거하고 시험용 환경 값으로 대체했으며 비밀 환경 파일을 후보·보고서·로컬 운영 백업에 포함하지 않았습니다.

## 백업·복구와 확인 한계

교체 전에 x600 서버에 원래 Compose·변경 대상 소스·원래 불변 이미지 ID를 보존했습니다. API·웹의 원래 이미지는 별도 복구용 이미지 이름으로도 유지합니다. 비밀 환경 파일을 제외한 동일 원본은 [로컬 운영 백업](../../../../scratch/chat-context-20261011/operating-backup/)에도 보존했습니다. 원격 백업 식별 시각은 UTC 2026-10-11 16:23:40이며 KST 2026-10-12 01:23:40입니다.

복구는 보존한 이전 Compose와 API·worker·웹 이미지를 한 묶음으로 사용합니다. DB 삭제·초기화·자료 되감기·전체 프로젝트 종료는 필요하지 않습니다. 배포 잠금을 사용해 자동 반영과 교체가 겹치지 않게 했으며 자동 반영 주기를 끄지 않았습니다. 이후 새 저장소 커밋의 자동 반영은 현재 직접 반영한 이미지를 교체할 수 있습니다. 이번 운영 후보의 파일 해시를 다음 정식 배포 후보와 비교해야 합니다.

이번 결과는 N서울타워 관련 위 문장과 새로고침의 검증입니다. 모든 자연어 표현, 모델 전체 정확도, 외부 장소 정보의 누락·오래된 값, 과거 대화의 표시 문제까지 해결됐다는 뜻은 아닙니다. 앞선 주소 조회에서 같은 장소를 하나로 찾지 못한 문제는 이번 대상 연결 수정의 범위 밖입니다. 독립 검토 없이 구현자가 자체 검증했습니다.
