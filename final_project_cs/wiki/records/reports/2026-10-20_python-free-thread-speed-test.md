# 파이썬 3.14 자유 스레드판 이동 계산 시험 (2026-10-20 · Claude)

결론: **이동 계산 부분만 보면, 놀고 있는 CPU 코어가 여럿 있을 때 자유 스레드판은 스레드를 늘린 만큼 빨라졌다**(GPU 서버 A 기계, CPU 약 5개, 4스레드에서 3.25배). 하지만 **CPU가 2개이고 이미 바쁜 Oracle ARM 서버에서는 빨라지지 않았다**(4스레드 0.98~1.01배). 앱 전체를 자유 스레드판으로 띄우는 시험은 하지 않았다. **운영 판(3.12)은 바꾸지 않았다**(사용자 결정: 「파이썬 버전도 그대로 두고」).

## 1. 무엇을 쟀나

| 항목 | 내용 |
|---|---|
| 계산기 | 이동 계산기(`wiring.leg_planner`) 한 번에 한 구간 |
| 구간 묶음 | 씨앗 고정 24구간(서울 장소 · 직선 1~15 km · 다음 일정 시작 10~20시) |
| 방식 ① | 계산기 하나로 차례로 |
| 방식 ② | 스레드마다 계산기를 따로 두고 2 · 4 · 6스레드로 같이 |
| 결과 대조 | 구간마다 답(출발 · 도착 · 경로 · 후보 · 출발 문맥)의 지문이 차례로 돌린 답과 같은지 |
| 전용 스레드 | 이동 계산 스레드를 뒤에서 계속 돌리는 동안, 고객 요청 흉내(파이썬 계산 약 0.1초)가 얼마나 느려지는지 |
| 판 | 3.12.11 · 3.14.0 · 3.14.0 자유 스레드판 (`uv` 로 설치) |

스크립트: `bench_ft.py`(스레드 수별), `bench_dedicated_thread.py`(전용 스레드). 원자료 17개 · 측정 스크립트는 작업용 임시 폴더의 `handoff5/` 에 있다(이 리포트에 복사하지 않았다).

## 2. 결과 — GPU 서버 A (RTX 2000 Ada 기계, CPU 한도 약 5.1코어, 빈 기계)

판마다 3회. 같은 기계에서 판 순서를 바꿔 가며 쟀다.

| 판 | 차례로 24구간 | 2스레드 | 4스레드 | 6스레드 | 결과 같음 |
|---|---|---|---|---|---|
| 3.12 (운영 판) | 16.5~16.7초 | 0.87~0.92배 | 0.71~0.74배 | 0.62~0.64배 | 216/216 |
| 3.14 보통판 | 15.8~15.9초 | 0.85~0.87배 | 0.72~0.73배 | 0.61배 | 216/216 |
| 3.14 자유 스레드판 | 17.3~17.7초 | 1.81~1.82배 | 3.19~3.30배 | 3.08~3.96배 | 216/216 |

- 보통판(GIL 켜짐)은 스레드를 늘릴수록 느려진다. 한 번에 한 스레드만 파이썬 코드를 돌리기 때문이다.
- 자유 스레드판의 6스레드는 CPU 한도(약 5개)를 넘어서 회차마다 흔들린다.
- 혼자 차례로 돌릴 때는 자유 스레드판이 보통판보다 약 9% 느리다.

전용 스레드(판마다 2회):

| 판 | 고객 요청 흉내 혼자 | 이동 계산 스레드가 도는 동안 | 배율 |
|---|---|---|---|
| 3.12 | 0.105~0.104초 | 0.235~0.249초 | 2.2~2.4배 |
| 3.14 보통판 | 0.078~0.079초 | 0.248~0.271초 | 3.1~3.5배 |
| 3.14 자유 스레드판 | 0.078~0.079초 | 0.079~0.082초 | 1.0배 |

## 3. 결과 — Oracle ARM 서버 (CPU 2개, 메모리 12 GB, 모델 시험 서비스가 같이 돎)

측정 시작 때 평균 부하 1.85, 측정 중 최고 8.5. CPU를 서비스와 다투었으므로 값이 흔들린다.

| 판 | 차례로 24구간 | 2스레드 | 4스레드 | 결과 같음 |
|---|---|---|---|---|
| 3.12 | 20.2~20.6초 | 0.99~1.02배 | 0.88~1.00배 | 48/48 |
| 3.14 보통판 | 20.9~21.0초 | 0.98~1.01배 | 0.96~1.02배 | 48/48 |
| 3.14 자유 스레드판 | 22.9~26.9초 | 0.68~1.13배 | 0.98~1.01배 | 48/48 |

전용 스레드(판마다 2회): 고객 요청 흉내 배율은 3.12 1.7~2.2배, 3.14 보통판 2.0~2.3배, 자유 스레드판 1.2배.

## 3-2. 결과 — AWS 측정 기계 (t3.medium, vCPU 2 · 메모리 4 GiB, 서울 리전, 2026-10-21)

AWS 측정은 2026-10-21 에 따로 했다. 측정 대상은 Oracle 서버의 코드 사본과 이동 자료 사본이고, 같은 씨앗 24구간을 판마다 2번 돌렸다(3.12 → 3.14 자유 스레드판 → 3.14 자유 스레드판 → 3.12 순서). CPU 크레딧 옵션은 `standard`로 두었다.

| 판 | 차례로 24구간 | 2스레드 | 4스레드 | 결과 같음 |
|---|---|---|---|---|
| 3.12 (1회) | 53.7초 | 0.91배 | 0.86배 | 24/24 · 48/48 |
| 3.12 (2회) | 56.5초 | 0.96배 | 0.87배 | 24/24 · 48/48 |
| 3.14 자유 스레드판 (1회) | 53.7초 | 0.62배 | 0.62배 | 24/24 · 48/48 |
| 3.14 자유 스레드판 (2회) | 55.7초 | 0.65배 | 0.67배 | 24/24 · 48/48 |

- 2코어 기계에서는 두 판 모두 스레드를 늘려도 빨라지지 않았다. 3.12는 거의 1배, 자유 스레드판은 오히려 0.6배 수준으로 느려졌다.
- 자유 스레드판이 느려진 원인은 이번 시험으로 가리지 못했다(코어 수, 기계 가상화, 자유 스레드판의 잠금 비용 등). 순서를 바꿔도 같은 결과가 나와서 측정 순서 때문은 아니다.
- AWS 기계 시험에서는 전용 스레드 시험을 하지 않았다.
- 기계는 측정 뒤 종료했다(`i-0cfe1896824074dd1`). 보안 그룹과 키 쌍도 삭제했다.

## 4. 앱 전체 확인 (자유 스레드판, GPU 서버 A 기계, 데이터베이스 없이)

- 3.14 자유 스레드판에 의존성을 설치하려면 라이브러리 여러 개를 바꿔야 했다(`requirements.txt` 판과 다름).
  - 웹 서버(FastAPI): 0.116.1 → 0.118 이상(MCP가 요구하는 새 판과 맞춤)
  - numpy: 1.26.4 → 2.3 이상, pandas · scipy: 새 판 필요
  - cryptography: 43.0.0 → 46 이상(자유 스레드판용 설치 파일 없음, 직접 빌드 실패)
  - psycopg: 빠른 판(binary) → 순수 파이썬 판(설치 파일 없음)
  - orjson: 뺌(LangSmith가 끌고 오는 것이라 설치 파일 없음, 직접 빌드 실패)
- 위 설정으로 앱을 불러오면 GIL은 꺼진 채였다. 웹 서버는 약 20초 만에 떴고 상태 확인 주소가 `{"status":"ok"}` 로 응답했다.
- **확인하지 않은 것**: 데이터베이스에 붙은 실제 요청, 뒤에서 일하는 프로그램(worker), 라이브러리를 바꿔서 생긴 동작 차이, 모델 호출 라이브러리의 GIL 상태.

## 5. 이 세션의 결정과 현재 상태

- 사용자 결정(2026-10-20): 자유 스레드판은 **운영에 적용하지 않는다.** 파이썬 판은 3.12 그대로 둔다. 라이브러리 바꿈도 적용하지 않는다.
- 「미리 계산」(접수 때 대안을 미리 계산해 저장, 바꾸기는 저장분을 바로 씀)은 이미 배포 브랜치(`role-manager`)에 있다(`50d6cdf0` 포함 확인, 읽기 전용 조회). 이 세션에서 새로 적용할 코드는 없다.
- 이동 계산 속도 개선(`139134fdb`)과 바꾸기 응답 줄이기(`fb840cd13`)도 배포 브랜치에 있다.
- 이 세션은 코드를 고치지 않았다. 커밋 · 푸시 · 배포도 하지 않았다.
