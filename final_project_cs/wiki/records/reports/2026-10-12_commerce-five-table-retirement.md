# 이커머스 5표 백업·복원·삭제 — 2026-10-12

## 실제 영향 검증

외부 표에서 옛 5표로 들어오는 FK 0개, 뷰 참조 0개, 검사한 사용자 함수 후보 0개와 운영 Python SQL 참조 후보 0개를 확인했습니다. 실제 DB의 DROP을 트랜잭션 안에서 실행해 여행 핵심 8표의 행 해시가 같은지 검사하고 롤백하는 예행을 통과했습니다. 복원한 격리 DB에서도 삭제 후 현재 SQL 실행기를 2회 실행해 여행 표 유지·옛 표 재생성 부재를 확인했습니다.

승인된 실제 삭제는 표 이름을 public 스키마로 한정하고 FK 순서대로 수행했습니다. CASCADE는 쓰지 않았습니다. 삭제 대상 밖 전체 관계·열·제약·인덱스·트리거 구조가 전후 동일합니다. 여행 관련 trips·itinerary_versions·itinerary_items·bookings·places·place_catalog의 행 수·내용 해시는 두 환경 모두 유지됐습니다. 로컬 customers는 578→579, customer_cases는 645→647로 관측 사이 증가하여 두 표까지 완전 동일하다고 주장하지 않습니다. 증가 원인은 이번 조회만으로 확정하지 않습니다.

## 재생성 방지의 실제 반영

로컬 SQL 실행 계획에서 과거 4파일을 제외합니다. x600에는 실행기·계획 해석기·제외 목록 3파일만 영속 읽기 전용 Compose 마운트로 API·worker에 적용했습니다. 원래 이미지 ID를 확인해 다른 코드 변경을 최종 반영에 포함하지 않았습니다. 첫 Compose 시도는 다른 태그를 선택하고 대기 중 실패하여 원래 이미지로 복구했습니다. 최종 두 컨테이너는 원래 이미지·3파일 마운트·running·재시작 0회이며 API health HTTP 200입니다. worker 회차 전체 성공이나 실고객 거래 검증을 뜻하지 않습니다.

영속 추가 설정은 기본 Compose·기존 기본 자동 배포 명령의 병합 결과에서 유지됩니다. 향후 이미지 선택은 고정하지 않습니다. 별도 -f 목록으로 배포하는 경우 같은 추가 설정을 포함해야 합니다. 자동 배포를 새로 실행하거나 Git에 커밋·push하지 않았습니다. 원격 원본 실행기·Compose·동일 이미지 복원용 추가 설정은 비공개 배포 상태 폴더에 보관했습니다.

## 실패와 한계

최초 삭제 뒤의 중첩 SQL 재실행 시험은 기존 식당 SQL의 명시적 COMMIT 때문에 SAVEPOINT 종료 오류가 났습니다. 삭제는 이미 커밋된 상태였고, 그 호출은 성공 횟수에 넣지 않았습니다. x600은 실제 실행기 독립 호출 2회가 추가로 통과했고 여행 핵심 8표의 해시가 매회 유지됐습니다. 로컬 업무 DB의 추가 전체 SQL 재실행은 자동 승인 검토가 비원자적 변경 위험을 이유로 거절했습니다. 우회하지 않고 격리 DB 재실행 2회와 실제 DB 읽기 전용 검사로 확인했습니다. 전체 SQL 묶음의 원자적 롤백은 현재 보장하지 않습니다.

정확한 옛 5표 이름과 검사 범위에서 잔존은 0개입니다. 다른 이름의 구조·JSON 업무 값·동적 SQL·수동 생성 전부의 부재까지 보증하지 않습니다. 관련 29시험은 통과했으며 전체 시험·실고객 거래를 검증하지 않았습니다. 실제 브라우저 화면 렌더링은 검사하지 않았고 데이터 기반 PNG를 직접 확인했습니다.
