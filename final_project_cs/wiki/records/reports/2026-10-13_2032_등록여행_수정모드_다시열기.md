## 1. 결론

- `[2026-10-13 사용자 결정]` 「일정 수정은 계획 확인 단계의 기능을 그대로 쓴다 · 채팅 변경이 쓰는 반영 길을 그대로 쓴다」. 그래서 **새 「여행 고치기」 API 를 만들지 않고** 등록한 여행을 확인 화면 **접수로 다시 연다**(`POST /v1/web/trips/{id}/reopen`). 시각 · 일정 추가 · 장소 바꾸기 · 삭제 · 자동 추천 · 잠금 · 이동 수단 · 되돌리기 · 재검증은 **기존 접수 경로 그대로**, 「완료」(`/confirm`)만 새 여행 대신 **같은 여행의 새 판**을 쓴다(채팅 변경의 `TripDesk._write` 와 같은 쓰기 — 판 · 변경 이력 · 알림 하나, 낡은 판이면 409).
- 매니저 브랜치(`origin/role-manager`)와 다른 브랜치에 같은 기능이 있는지 먼저 확인했다 — **없었다**. 10-03 백엔드 요청서(`records/plans/2026-10-03_1920_웹_실서버_전환_백엔드_요청.md` §2)의 제안(다시 열기 → 접수 경로 → 확인 때 새 판)과 같은 설계로 사용자 승인을 받고 시작했다.
- 웹: 여행 화면 시트 머리의 글자 「채팅」 단추를 **아이콘 단추 둘(✎ 「일정 수정」 · 💬 「채팅」)** 로 바꿨다(목업 후보 1). ✎ 를 누르면 같은 주소에서 계획 확인 화면이 된다. 카드 · ✎ 수정 페이지(대체 후보 카드) · 시간 · 삭제 모두 계획 확인 그대로이고, `[2026-10-13 사용자 지시]` **마지막 단계도 그대로** — 고치면 둥근 단추가 「다시 제출」, 검증이 끝나면 ✓(이름 「완료」 — 계획 확인의 「여행 등록」 자리)가 되고, 누르면 새 판을 쓰고 여행 화면으로 돌아간다. `[2026-10-13 사용자 지시]` 시트 머리(목업의 「완료」 자리)는 **「✕ 취소」** — 확인 창(「일정 변경을 취소할까요?」 · 「취소하면 변경 내용이 사라져요.」) 뒤 수정 접수를 닫고(`POST /v1/web/trip-intakes/{id}/cancel`) 여행 화면으로 돌아간다. 다음 「일정 수정」은 새로 시작한다.
- 지난 일정(끝 ≤ 지금)은 **접수에 넣지 않는다**(설계 P2). 확인 화면의 어떤 고치기 · 자동 추천 · 되돌리기도 지난 일정에 닿을 길이 처음부터 없고, 「완료」 때 서버가 그대로 다시 붙인다. 화면은 여행 화면의 회색 한 줄로 그 자리에 보인다.

## 2. 설계 — 왜 이렇게 했나

| 정한 것 | 까닭 |
|---|---|
| 다시 열기 = 같은 판으로 열린 수정 접수가 있으면 **그것을 돌려준다** | 새로 고침 · 다시 들어오기에서 고치던 값이 남는다. 판이 바뀐 뒤(채팅 · 감시)에 남은 것은 `closed` 로 닫고 새로 연다 — 옛 판 위에서 고친 값으로 새 판을 쓰지 못하게(마이그레이션 232 의 열린 수정 접수 유일 색인) |
| 접수에 넣는 일정 = 활동 · 식사 중 **아직 끝나지 않았고** 업체 예약 표(`booking_id`)에 묶이지 않고 좌표를 아는 것 | 접수의 항목은 활동 · 식사뿐이다(`assemble._row` 가 종류를 둘로 고친다). 숙소 · 예약 표 일정 · 좌표 없는 장소는 확인 화면이 다룰 수 없어 고정(`frozen_item_ids`)으로 그대로 둔다 |
| 값 줄 방법 `trip`(새 값) | `customer` 로 넣으면 모든 카드가 「고침」(`edited`)으로 보이고, `rule` 은 「규칙으로 채움」이 된다. 등록한 여행에서 가져온 값임을 따로 적는다(마이그레이션 232 가 방법 검사에 더했다). 「장소 없음」 일정은 `trip` + 빈 값을 고객의 「장소 없음」과 같게 읽는다(`assemble` · `review.place_state` 두 줄) |
| 「완료」의 비교 = 원래 일정 id 를 값 줄 근거(`evidence.item_id`)로 따라간다 | 안 바뀐 일정은 **같은 id**(판정 · 감시 · 알림이 같은 일정으로 본다), 바뀐 일정은 새 id 가 `replaces_item_id` 로 원래를 가리킨다 — 채팅 변경(`Item.replaced_by`)과 같다. 끝 시각 없이 등록한 일정은 확인 화면이 규칙으로 끝을 채우므로 끝 칸 값 줄이 없으면 고친 것으로 보지 않는다 |
| 이동 항목은 앞뒤 일정이 **둘 다 그대로이고 여전히 이웃**일 때만 남긴다 | 바뀐 일정 사이의 이동은 낡은 값이다. 확인 화면이 접수에서 이동을 다시 계산해 보여 줬다 |
| 판정 = 채팅 변경과 같은 `introduced_violations`(이번 변경으로 **새로** 생긴 위반만 422) | 감시 루프가 바꾼 여행에는 원래 위반이 있을 수 있다 — 고객이 건드리지 않은 위반으로 「완료」를 막지 않는다 |
| 고객이 고른 곳(후보 · 검색 · 자동 추천)은 **그 이름이 새 판의 일정 이름** | 확인 화면 카드가 고른 곳의 이름을 보인다(`from-review.planItem`). ☆처음엔 원문을 그대로 써서 장소만 바뀌고 여행 화면엔 옛 이름(「덕수궁」 + 창경궁 주소)이 남았다 — 실화면에서 찾아 고쳤다. 원문은 `provenance.title` 에 남고, 이력 · 알림은 「광장시장 → 충신시장」 |
| 바꾼 것이 없으면 판을 쓰지 않는다(`changed: false`) | 들어갔다 그냥 나오면 이력 · 알림이 생기지 않게 |
| 수정 접수에서 `trip.title · party_size · first_day` 고치기 422 · 일정 짜기 409 · 설문 422 | 「완료」가 새 판에 싣지 않는 값을 화면에서 고친 것처럼 보이지 않게. 일정 짜기는 새 여행을 만든다 |
| 수정 취소 = 확인 창 뒤 서버에서 수정 접수를 **닫는다**(`closed`) | `[2026-10-13 사용자 지시]` 「사용자가 수정 모드를 취소하고 싶을 수 있다 — 취소하면 변경 내용이 사라진다고 안내」. 화면만 빠져나오면 같은 판으로 다시 열 때 고치던 값이 되살아나(재사용 규칙) 안내가 거짓이 된다. 닫힌 접수의 값은 지우지 않고 남긴다(기록) |
| 마지막 단계 = 계획 확인의 `registration` 을 같은 모양으로 넘기고 `onRegister` 만 새 판 쓰기로 | `[2026-10-13 사용자 지시]` 「제출 → 검증 → 최종 제출 → 등록 완료 화면」을 그대로 재현 — 처음 판은 둥근 단추를 「다시 제출」만 두고 머리의 「완료」로 끝내게 했는데 계획 확인과 순서가 달랐다. 준비 판단(`review.ready`) · 거절 문장 · 바쁜 표시도 계획 확인과 같다. 앞으로의 일정을 다 빼고 지난 일정만 남은 경우만 준비로 본다(서버도 그때 `no_items` 로 막지 않는다) |
| 웹 수정 모드 = 여행 화면 대신 `PlanCheck` 를 같은 주소에서 그린다 | 「계획 확인의 기능을 그대로」 — 같은 부품 · 같은 서버 호출(`useServerReview`)이라 계획 확인이 바뀌면 수정 모드도 같이 바뀐다. 별도 화면 흐름(`/intakes/[id]`)으로 보내지 않는다(10-12 결정) |

## 4. 검증

## 5. 확인하지 못한 것 · 남은 일

- **화면에서 못 본 기능**: 일정 추가 · 장소 검색 · 자동 추천 — 로컬에 카카오 · 관광공사 검색 키가 없다. 서버 쪽은 시험(공용 장소 재사용 · 추가)으로만 확인했다. 대체 후보로 바꾸기는 화면에서 확인했다.
- **등록 길의 같은 틈(고치지 않음)**: 새 계획을 확인 화면에서 후보로 바꾼 뒤 「여행 등록」하면 일정 이름은 원문(`assemble` 이 적힌 말을 쓴다)이고 장소만 바뀐다 — 수정 모드만 고쳤다. 등록도 맞출지는 따로 정한다.
- **목업과 다르게 둔 것**: 지난 이동 줄과 「출발이 지난 이동」(목업의 「이미 출발한 이동이라 …」)은 그리지 않았다 — 수정 접수의 이동은 앞으로의 일정 사이에서만 다시 계산된다. 지난 일정 줄을 눌러 펼치기는 하지 않고 이유만 말한다. 수정 모드에 들어가면 지도 · 목록이 첫 날에서 시작한다(보기 모드는 오늘).
- **고정 일정의 말**: 아직 끝나지 않은 고정 일정(숙소 · 예약 표 일정)도 같은 회색 줄로 보이고 「지난 일정이라 …」라고 말한다 — MVP 여행에는 거의 없지만 문장이 맞지 않는다.
- `[미정]`(계약에 적음): 재난으로 일정이 정지된 동안 수정을 막을지 · 진행 중 일정의 시작 앞당기기를 서버도 막을지(지금은 화면의 「가능한 시각」만) · 등록한 여행의 이름 · 인원 바꾸기(화면 요청 ①).
