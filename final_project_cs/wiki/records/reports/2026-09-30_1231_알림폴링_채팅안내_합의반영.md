# 알림 1분 폴링과 채팅 오류 안내 합의 반영

## 오류 로그와 서버 담당 범위

오류 로그를 서버에 저장하고 개발자·운영 콘솔에서 확인하는 방향은 사용자 전달 합의다. 현재 확인한 프론트 호출부·백엔드 라우트·API 문서에서 브라우저 오류 수집용 계약을 찾지 못했으므로 임의의 전송 API는 추가하지 않았다. 브라우저 콘솔 기록은 새로고침 후 영구 보존이나 서버 터미널·로그 DB 수집을 보장하지 않는다. HTTP 응답을 받지 못한 연결 오류에는 HTTP 상태가 없다.

다음 작업은 수집 API·인증·허용 필드·보존 정책을 확정하고, 프론트 전송 → 서버 저장 → 개발자/운영 콘솔 조회를 연결하는 것이다. 앱의 개발자 콘솔과 브라우저 개발자 도구 콘솔은 별개다.

새 ID 재전송은 서버 입장에서 별도 요청이다. POST 성공 뒤 GET만 실패했거나 응답이 유실됐다면 이전 요청은 이미 처리됐을 수 있고 같은 내용이 다시 처리될 수 있다. 이번 합의대로 프론트는 안내와 재전송을 제공하며, 중복 판단·최종 Case 및 일정 처리는 서버에서 담당한다. “새 ID이므로 중복 실행이 방지된다”는 보장은 하지 않는다.

## 검증 결과와 한계

- `npm.cmd run check`: 린트·타입·단위·빌드 **4/4 = 100%** 통과. 단위 **109/109 = 100%**, 12개 파일.
- 가짜 서버 live 브라우저: 첫 전체 실행에서 기존 시험 **36/36 = 100%** 통과. 신규 시험의 시간 제어·선택자·초기 요청 횟수 가정을 수정한 뒤 대상 재실행 **8/8 = 100%** 통과. 두 실행에서 확인한 시나리오는 **44/44 = 100%**이며, 최종 전체 단일 실행이 모두 통과했다는 뜻은 아니다.
- 실행 출력·검사별 근거는 [검증 기록](../evidence/2026-09-30_1231_알림폴링_채팅안내_검증.md)에 보존했다.
- 실제 서버·DB·모델·Discord 통합 시험은 실행하지 않았다. 서버 변경 시 알림이 생성되는지, 재전송의 최종 처리 결과, 로그 수집·저장은 실제 서버 공동 확인이 남아 있다.
- 비활성 탭의 주기 조회는 기본 Query 정책에 따라 중단될 수 있다. 알림이 생성되지 않는 변경은 이 방식으로 감지하지 못한다. 활성 탭에서도 네트워크 지연을 포함한 정확한 60초 이내 갱신을 보장하지 않는다.

변경은 로컬 작업 트리에 있으며 커밋·푸시·배포하지 않았다. 과거 리포트의 제안을 소급 수정하지 않고 현재 협의 문서에서 이번 결정으로 대체했다.
