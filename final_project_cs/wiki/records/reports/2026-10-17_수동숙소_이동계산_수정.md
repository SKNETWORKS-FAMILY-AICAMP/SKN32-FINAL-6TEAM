# 수동 공통 숙소 변경의 이동 계산 실패 보완

## 실제 재현과 원인 범위 정정

2026-10-17 숙소 최초 추천 후속 배포 뒤, 기본 예시 새 접수에서 양일 동일 호텔 자동 적용 2/2와 실제 경로선 8/8은 성공했다. 둘째 날 호텔을 다른 호텔의 숙소 안 식사 후보로 직접 바꾸자 북촌한옥마을→양반댁의 계산 상한 때문에 저장을 거절했다. 원래 r3과 양일 호텔은 유지됐다. [실제 실패 근거](../evidence/2026-10-17_qa-usage-exemption/manual-hotel-save-still-refused.png).

정확한 예외 문구를 실제 호출부와 대조하니 실패는 최종 review보다 앞의 `direct_schedule.fit`에서 발생한다. 이전의 review 공유 예산 가설만으로 원인을 확정하지 않는다. review의 이전 판 전달은 이미 구현돼 있다. 직접 재배치는 영향받은 이웃과 시각이 밀린 연쇄 구간을 계산하며, 모든 구간을 무조건 계산하는 것은 아니다.

확인한 직접 재배치의 두 경계: 날짜 루프 밖의 계산 시간 몫 하나를 모든 날짜가 공유한다. 또 계산 결과가 유효한 시간표 구간이어도 호출 후 남은 몫이 소진됐으면 거절한다. 기존 계산기 래퍼에는 이미 동일 입력 캐시가 있으므로 중복 캐시는 추가하지 않는다.

구현 전 [직접 선택 계약](../../external/direct-place-schedule.md)을 작성했다. 코드·시험은 별도 격리 사본에서 진행하며, 다른 숙소 담당의 prefill·pipeline 변경은 수정하지 않는다. 기존 커밋 세션에 경계와 진행을 전달했다.

## 20:12 격리 수정·회귀

날짜별로 기존 20초 계산 몫을 새로 만들고 선택 수단의 계산 몫도 날짜마다 초기화했다. 유효 시간표 결과를 반환한 마지막 계산은 인정하며, 이후 새 계산이 상한 때문에 어림값이 되면 계속 거절한다. 수치·입력·출력·예약·운영시간 경계는 바꾸지 않았다.

네트워크 없는 실제 운영 앱 이미지의 같은 20개 단위 검사: 수정 전 3실패·17통과, 수정 후 **20/20 = 100%**(0.20초). 실패한 세 경우는 추천 수단의 양일 예산, 직접 선택 수단의 양일 예산, 마지막 성공 시간표 결과다. 새 계산 차단·기존 예약/잠금/운영시간 검사도 유지됐다. ruff F·E9 변경 2파일 통과. HTTP 통합·배포·실제 수동 저장은 아직 확인 전이다.

## 20:24 실제 계산 추가 원인·2차 보완

운영과 같은 조립·실제 이동 계산기를 갖춘 별도 프로세스에서 기존 접수 r3은 읽기 전용으로 유지하고 같은 후보 B를 대입했다. 첫 보완만으로는 호텔→경복궁 계산 뒤 경복궁을 5분 미뤄 연쇄 구간을 다시 계산하다 20초 몫을 소진했다. 이 실패를 보존한다. 앞선 준비 오류 2회는 에이전트 팀 연결이 없는 독립 실행 때문이며 기능 성공으로 세지 않았다.

추가 보완: 우리가 규칙·자동 추천으로 채운 호텔 조식 끝만, 최소 체류와 운영시간을 지키면서 이미 계산한 시간표 출발 시각에 맞춰 줄인다. 고객이 쓴 종료 시각·예약·잠금은 줄이지 않는다. 조정 근거는 derived_stay_end로 남기고 다음 수정에서도 고객 입력과 구분한다. 기존 이동 계산 캐시를 그대로 사용하며 추측 경로는 적용하지 않는다.

동일 28개 검사 수정 전 5실패·23통과 → 수정 후 **28/28 = 100%**(0.25초), 변경 Python 4파일 F·E9 통과. HTTP에서 근거 저장까지 확인하는 회귀 1건을 추가했으며 매니저의 격리 DB 실행은 대기다. 별도 Git 사본의 패치 적용 검사도 통과했다.

실제 읽기 전용 재계산은 **1/1 = 100% 성공**(18.995초, 한 번의 기능 확인이며 성능 비교가 아님). 조정은 첫날 조식 끝09:30, 둘째 날 북촌10:05~11:35였고, 첫날 경복궁과 예약 N서울타워는 움직이지 않았다. 실제 일정에는 아직 저장하지 않았다. [실패 계산](../evidence/2026-10-17_manual-stay-save/live-dry-run-r3.json) · [성공 계산](../evidence/2026-10-17_manual-stay-save/live-dry-run-r4.json). 2차 패치는 기존 파일 4개이며 prefill·review는 바꾸지 않았다.

## 20:31 단일 호텔 조식의 HTTP 검증 보완

매니저 격리 DB의 추가 HTTP 시험에서 종료 시각09:50 대신10:00이 반환돼37/38이었다. 한 호텔 조식만 있는 경우 공통 숙소 연결 함수가 숙소 조각 근거를 새 장소에 붙이지 않는 경로를 확인했다. 새로운 추측 분류 대신 기존 원문 조각 판정(line_parts)을 함께 사용하도록 보완했다. 일반 식당 제외 검사도 추가했다. 첫 일반 식당 검사 기대값은 기존 추정 끝10:00을 보존하는 값 줄을 빠뜨려1실패·29통과였으며, 기존 동작을 반영해 종료가 줄지 않는 것과 호텔 조식 표시가 붙지 않는 것을 확인했다. 최종 **30/30 = 100%**(0.22초). 기존28검사와 실제 양일 계산 성공은 보존한다. v3는 전체4파일 패치와 v2 대비2파일 차분을 함께 만들었고 추가 HTTP 재검사는 매니저에 요청한다.
