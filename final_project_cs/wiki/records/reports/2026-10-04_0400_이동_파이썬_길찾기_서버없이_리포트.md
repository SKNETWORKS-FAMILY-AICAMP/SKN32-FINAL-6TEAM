## 2. 서버 없는 파이썬 길찾기 — `engine/graph_router.py`

**무엇**: 이동 담당이 만든 도로 그래프(`road_graph_v1` — 노드 280,065 · 간선 375,651 · gz 16MB)를 읽어 A* 로 최단경로를 구한다.
`GraphHopperClient` 와 **같은 모양**(`route(s, e, profile, via)` → GraphHopper 응답 모양)으로 답해서, 속도 프로파일 계산(`CarGraph.compute`)과
자전거·도보 어댑터(`BikeRouter`)가 고치지 않고 그대로 붙는다. 형상은 이 파일 밖으로 나가지 않는다.

| 프로파일 | 다니는 길 | 비용 | 비고 |
|---|---|---|---|
| car | 차량 간선 · 일방통행 지킴 | 시간(도로급 기본속도, OSM maxspeed 있으면 그것) | 실제 소요는 받는 쪽이 TOPIS 로 다시 잰다. 교차로의 점은 같은 거리쯤의 간선 여럿(≤6)을 출발·도착 후보로 둔다 |
| bike | 자전거 간선 · 자전거 일방 | 거리 × 도로급 계수 | 자전거길 선호 · 간선도로 기피(누그러뜨림) |
| foot | 자동차전용(motorway·trunk) 빼고 양방향 | 거리 | **도로까지 가는 직선 구간도 거리에 더한다** |

### 정확도 (실측)

**걸음·자전거 — GraphHopper 가 같은 pbf 로 낸 거리 기록과 비교** (걸음 16쌍[중복 2쌍 포함] · 자전거 8쌍. 표본이 작아 방향성만 말한다)

| 방법 | 평균 오차 | 중앙 오차 | ±10% 안 | ±30% 안 |
|---|---|---|---|---|
| 지금의 대체식(직선 × 1.40) | 39% | 35% | 4/16 | 6/16 |
| 파이썬 길찾기 | 25% | **9%** | **10/16** | **11/16** |

- 자전거: 우리/GraphHopper 거리 비 평균 1.10, 범위 0.86~1.92(8쌍).
- 크게 틀린 걸음 쌍(비 0.38 · 2.38 등)은 이 그래프에 **보행자 전용 길(계단·샛길)이 자전거 허용일 때만** 들어 있어서다 — 그 길만으로 이어진 구간이 멀게 나오거나, 큰길 쪽 간선으로 붙어 짧게 나온다.

**택시 — 카카오모빌리티 미래 길찾기(실호출)와 비교** (6구간 × 평일 12:30·토요일 23:50 = 12쌍. 우리: 로컬 길찾기 + TOPIS 시각별 속도 + 택시 요금 산식)

| 우리/카카오 | 평균 | 범위 |
|---|---|---|
| 거리 | 0.92 | 0.78 ~ 1.00 |
| 소요 시간 | 1.08 | 0.89 ~ 1.28 |
| 요금 | 0.96 | 0.71 ~ 1.27 |

- 요금 하한은 평일 낮에 카카오보다 12~29% 낮고(우리는 정차·신호·호출료를 안 넣는 **하한**이라 의도된 방향), 토요일 심야엔 우리가 더 높다(심야 할증을 우리가 넣는다).
- 예: 경복궁 → 성수 평일 12:30 — 우리 9.8km · 33분 · 11,700원 / 카카오 10.2km · 35분 · 15,000원.

### 한계 (먼저 적는다)

- v1 그래프는 보행자 전용 길이 빠져 걸음 거리가 **추정**이었다 → 아래 「7. 도보 그래프 v2」로 보완했다. 그래도 근거 문구는 「로컬 도로그래프」 · 등급 추정이다. 「경로 없음」은 「길이 없다」의 근거가 아니다 — `RouterDown` 으로 올려 직선×계수로 간다.
- 회전 금지 제약이 그래프에 없다(README 명시) — 실제보다 짧은 차량 경로가 나올 수 있다.
- 경유지(via)는 지원하지 않는다. 지도 범위(서울+인접 도시+공항 회랑) 밖 좌표는 `out_of_area`.
- 실제 서울 14쌍(고유)으로 본 것이라 모집단 일반화는 못 한다.

### 만들면서 틀렸던 것 (오진 기록)

- 걸음에도 「같은 거리쯤의 간선 여럿」을 출발 후보로 두자 중앙 오차가 9% → 43% 로 나빠졌다 — 큰길에서 길 건너편 간선으로 갈아타 직선에 가깝게 짧아졌다.
  **자동차만** 여럿으로 두고(일방통행 때문에 어느 간선에 붙었느냐가 갈 방향을 가른다) 걸음·자전거는 하나로 되돌렸다.
- 첫 시험에서 교차로 위의 점이 일방통행 간선 하나에만 붙어 나갈 길이 막히는 결함(합성 격자 시험이 잡았다) → 끝점 1 m 안이면 그 끝점을 방향 제약 없이 출발·도착으로 둔다.
- 자전거 계수를 처음에 세게(간선 1.8~2.5배) 줬더니 GraphHopper 보다 약 20% 돌았다 → 1.1~1.6 으로 누그러뜨렸다.

## 3. 서비스에 연결한 것

- 설정 `mobility_local_router`(기본 true · 환경변수 `ACOP_MOBILITY_LOCAL_ROUTER` · [.env.example](../../../.env.example)). GraphHopper 주소(`mobility_gh_url`)가 있으면 그쪽이 먼저고, 없거나 안 닿으면 로컬 길찾기.
- `engine/runtime.py`: 라우터를 정한 뒤 **택시 서비스(`CarService`)를 판정기에 끼운다**. 전에는 서비스 런타임이 그걸 안 끼워 라우터가 떠 있어도 택시는 늘 근거없음이었다.
  속도 프로파일 자료는 처음 택시를 물을 때 올린다(`_LazyCar`).
- `engine/bike.py`: 응답의 `basis`·`source_id` 를 라우터가 정한다 — 근거 문구가 로컬 길찾기를 「GraphHopper」라고 적지 않는다(`osm_road_graph@2026-09-18`).
- `wiring.py`: 서버 기동 때(`configure_from_settings`) 백그라운드로 미리 올린다. 직접 `configure()` 를 부르는 시험은 올리지 않는다.
- `engine/car.py` `make_router`: `local` · `local:<폴더>` 지정 가능.
- `engine/options.py` `TransferCar.load`: 자료 폴더를 `cli_processed()` 로 찾게 고쳤다 — 시험마다 자료 폴더 상태를 초기화하는 공통 설정(`tests/conftest.py`) 뒤에는 초기화된 곳을 가리켜
  표시 칸(`transfer_car`)이 조용히 빠졌다(`test_plan_v1.py::test_core_routes_strips_display` 가 파일 전체를 돌릴 때만 실패하던 순서 의존).

## 9. 용어 — 「모듈」 · 「컴포넌트」 · 「인스턴스」는 표준어다. 다만 층이 다르다

| 말 | 실무에서의 뜻 | 우리 코드에서 가리키는 것 |
|---|---|---|
| 모듈(module) | 코드를 묶는 단위 — 파일·패키지 | `graph_router.py` 파일 · `mobility/` 폴더 |
| 컴포넌트(component) | **같은 약속(인터페이스)을 지켜 갈아 끼울 수 있는 부품** | `GraphRouter` — `route()` 약속을 지켜 `GraphHopperClient` 와 바꿔 낄 수 있다 |
| 인스턴스(instance) | 클래스를 실제로 만든 실행 중 객체 | `GraphRouter.default()` 가 프로세스당 하나 돌려주는 것(공유 인스턴스·싱글턴) |
| 서비스(service) | 따로 떠서 요청을 받는 실행 단위(서버·프로세스) | 지금은 **서비스가 아니다** — 우리 프로그램 안에서 도는 라이브러리(in-process). GraphHopper 서버가 서비스였다 |
| 포트 · 어댑터 | 안쪽이 부르는 약속(포트)과 바깥 도구를 그 약속에 맞추는 부품(어댑터) | 포트 = `route(s, e, profile)` · 어댑터 = `GraphHopperClient` · `GraphRouter` · `FixtureRouter` |
| 엔진(engine) | 계산 핵심 | 길찾기 = routing engine · 이동 판정 = verifier(feasibility checker) |
| 프로바이더(provider) | 같은 일을 하는 교체 가능한 공급원 | routing provider: GraphHopper / 로컬 그래프 / (후보) 카카오 |

- 추천 표기: 에이전트 단위는 **Mobility Team**, 계산 라이브러리는 **Mobility Engine**, 길 찾는 부분은 **Routing Provider**(구현: 로컬 그래프 · GraphHopper), 이동이 성립하는지 보는 부분은 **Verifier**. 연결부(`wiring.py`)는 업계 말로 **composition root(조립 지점)** 다.

## 10. 경로선을 화면에 내려주기 — 우리 계산을 그대로 (2026-10-04 추가)

> 요청(사용자): 「우리 지도도 원본까지 있으니 … 우리가 직접 클라에 쏴줄 수 있다 … 외부 API 가 안 되면 2차 소스로 등록해서 출력되게」.

**지금까지**: 화면은 이동을 구글 지도 **링크**로만 보여 줬다(`trip_api.map_view` — 한국에서 구글은 자동차·도보 길찾기를 안 주고 대중교통은 들를 곳을 못 받아 선을 못 그렸다는 ui 세션 실측이 주석에 있다). 핀만 찍고 선은 없었다.

**했다**: `GET /v1/web/trips/{trip_id}/route-shapes`(사용자 키 · 본인 여행만) — 이동 항목마다 GeoJSON `LineString` 을 우리 도로 그래프와 역 좌표로 만들어 내려준다([route_shape.py](../../../app/modules/travel_ops/mobility/route_shape.py)). 외부 길찾기 API 를 부르지 않는다.

| 계획 수단 | 선을 어떻게 만드나 | source · grade |
|---|---|---|
| 도보 · 자전거 · 택시 | 로컬 도로 그래프 foot · bike · car 경로 | `local_road_graph` · 추정 |
| 지하철 · 혼합 | 탄 역 좌표를 순서대로 잇고 양 끝 걸음은 도로 그래프 foot(실제 선로 곡선은 아님) | `stations` · 추정 |
| 버스 | 정류장 목록이 일정에 없어(노선 번호만) 두 장소 직선 | `straight_line` · 근거없음 |
| 못 구했을 때(길찾기 꺼짐 · 지도 밖 · 경로 없음) | 두 장소 직선 + 이유(note) — **조용히 빼지 않는다** | `straight_line` · 근거없음 |

- 응답에 `attribution`(「지도 데이터 © OpenStreetMap contributors (ODbL)」)이 같이 간다 — 화면은 선을 그릴 때 보여야 한다. 점은 선마다 240개로 솎는다.
- **2차 소스 순서**: 도로 그래프(1차) → 직선(2차). 외부 길찾기 API 는 붙이지 않았다 — 아래 11절의 이유(한도·약관·한국 지원). 붙이려면 `route_shape._route` 앞에 공급원 하나를 끼우면 된다.
- 시험: 가짜 라우터 12개(수단별 모양 · 실패 대체 · 점 상한 · 좌표 없는 장소 건너뜀) + 실제 자료 e2e(계획→등록→경로선, 서울 범위 안 · 추정 등급) — 전부 통과.
- ★**화면은 아직 안 그린다** — 계약만 만들었다. 지도 제공자 셋(osm · google · naver)의 선 그리기는 ui 세션 몫이다(`providers/*.ts` 의 `polyline` 추가).

## 11. 경로를 돌려주는 오픈소스 · 무료 API (조사)

| 이름 | 무엇을 주나 | 무료 조건 | 한국에서 쓸 만한가 |
|---|---|---|---|
| **우리 도로 그래프**(`graph_router.py`) | foot · bike · car 경로 + 형상 | 무제한 · 서버 없음 | OSM 서울+인접 · 걸음은 v2 로 중앙 오차 6% |
| OSRM 공개 데모(`router.project-osrm.org`) | car · bike · foot 경로 + 형상 | 데모 서비스 — 무거운 사용 금지, 초당 1회 안팎 | 서비스용으로는 부적합(약관 · 보장 없음) |

**① 추정 요금 vs ODsay 요금** ([validate_fare_vs_odsay.py](../../../scripts/mobility/validate_fare_vs_odsay.py)) — 9호선·경의선·수인분당선·경춘선·서해선 같은 노선 쌍 28개를 ODsay 에 물었다(한도가 닿아 1~8호선 대조군은 못 돌렸다). **② 관광 구간 소요: 우리 vs 서울 환승경로(15000414)** ([validate_tourist_vs_seoul_transfer.py](../../../scripts/mobility/validate_tourist_vs_seoul_transfer.py)) — 구글 대조와 같은 32쌍 중 31쌍: 우리가 **중앙 +10분 · 1.26배** 느림, ±25% 안 13/31 · ±15% 안 5/31. 이 서비스는 출발 시각을 안 받는 정적 추정이다. 구글 대조(길 기준 접근 걷기에서 +10분 · 1.29배)와 같은 방향이다 — **한국 공공 소스로도 우리가 25% 안팎 보수적**이다. 걷기 속도(1.04m/s)·환승 여유를 보수적으로 잡은 설계의 결과로 읽고, 규칙은 바꾸지 않았다.

한계: 두 대조 모두 서울 24곳·32쌍(또는 28쌍)·평일 한 시각이고, ODsay·환승경로 값은 각 서비스의 가정이라 정답이 아니다. 응답은 숫자만 쓰고 저장하지 않았다.
