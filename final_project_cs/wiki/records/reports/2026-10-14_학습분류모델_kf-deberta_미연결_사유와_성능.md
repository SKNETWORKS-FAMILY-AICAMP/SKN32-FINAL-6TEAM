# 학습 분류 모델(kf-deberta) 이 제품에 연결되지 않은 이유와 제품 모델과의 비교

작성 2026-10-14. 상태: **비교 완료 — 연결하지 않기로 했다.**

## 결론 한 줄

연결하지 않은 것은 의도된 보류가 아니라 **연결 코드 자체가 없어서**였다. 같은 여행 정답 96문장에서 x600 서버가 실제로 쓰는 모델(`tripilot-pointer:e4b-ft`)과 견주니 학습 모델은 낫지 않았다 — 72건에서는 크게 못했고, 따로 둔 24건에서는 구분되지 않았다. 그래서 연결하지 않는다.

## 정정 — 이 비교가 잰 경로는 웹 채팅의 주 경로가 아니다 (같은 날 추가 확인)

위 비교는 `feedback.classify`(모델이 요청 종류·문제 코드를 직접 내는 함수)를 잰 것이다. 코드를 더 읽어 보니 **웹 채팅의 주 경로는 이 함수가 아니다.**

- 기본 설정 `travel.decision_unit.mode: "on"`([guardrails.yaml](../../../config/guardrails.yaml))이면 채팅 한 문장은 **결정 단위**(모델 한 번이 할 일과 대상 일정을 보기 안에서 고름, `decision_unit.py`)로 처리된다. 이때 옛 규칙 경로(사실 낱말·분류기·추출기)는 타지 않는다.
- 요청 종류·문제 코드는 모델이 내지 않는다. 고른 할 일과 대상 일정의 종류에서 **고정 규칙**으로 만든다(`decision_unit.labels()`). 이 규칙이 내는 문제 코드는 `dining_hours`·`dining_other`·`activity_cancel_or_change`·`activity_other`·`mobility_other`·`other` 여섯뿐이다.
- `feedback.classify` 는 설정이 `off`/`shadow` 일 때와 REST 접수(`/v1/cases`) 경로에서 쓰인다.
- 확인하지 않은 것: x600 서버의 운영 설정 `chat.decision_mode`(재기동 없이 바꾸는 값)가 지금 `on` 인지.
- 뜻: 채팅의 정확도는 `feedback.classify` 가 아니라 결정 단위 모델(일정 짚기 시험 A~E·E2 가 재는 것)이 좌우한다. kf-deberta 는 대상 일정을 고르지 못하므로 채팅 경로의 대체가 될 수 없다. 위 「연결하지 않는다」 결론은 `feedback.classify` 경로에 대해서만 유효하다.

## 학습 자료 구성 (`datasets/ml/intent_ko/data/`)

- 실제 문장 6,067건 = **소비자원 민원 제목**(`kca_complaint_title`). 쇼핑 주문이 아니라 소비자 민원이지만 여행 중 채팅 문장이 아니다. 라벨은 gemma4:12b 가 붙였다.
- 합성 문장 875건 = gemma4:12b 가 여행 문장처럼 써 낸 것, 라벨도 같은 gemma4:12b.
- 라벨이 몹시 치우쳤다: 요청 종류에서 `adjust_reject` 46건·`itinerary_submit` 13건, 문제 코드에서 `booking_cancel_request` 3,240건(53%).
- 따라서 **사람이 단 정답이나 실제 여행 고객 문장으로 학습한 분류 모델은 없다.** (우리 데이터로 가르친 모델로는 일정 짚기용 E4B — `tripilot-pointer:e4b-ft` — 가 있고, 이것은 분류가 아니라 「계획의 어느 줄을 가리키는가」 과제다.)

## 실측: 같은 96문장으로 두 모델 비교

- 자료: `eval/datasets/travel_golden.jsonl` 72건, `travel_holdout.jsonl` 24건. 라벨은 **사람 검수 전 초안**(`label_by: claude-draft`). 실패도 분모에 포함. 감정·심각도는 학습 모델이 내지 못해 채점에서 뺐다. 각 모델 1회 실행.
- 학습 모델: 이 PC CPU, 한 문장 p50 약 0.3~0.4초.
- 제품 모델: x600 서버의 cs 프로젝트 서버(api 컨테이너)에서 배포된 `feedback.classify` 를 그대로 호출. 2026-10-14 `/api/ps` 에 `tripilot-pointer:e4b-ft` 적재 확인. 한 문장 p50 1.4초, p95 6.3초.

| 자료·모델 | 요청 종류 | 문제 코드 | 둘 다 맞음 | 팀(접두) 맞음 | 엉뚱한 팀 | 분류 실패 |
|---|---|---|---|---|---|---|
| golden 72 · 학습 모델 | 39/72 = 54.2% | 40/72 = 55.6% | 24/72 = 33.3% | 56/72 = 77.8% | 14 | 0 |
| golden 72 · 제품 모델 | 61/72 = 84.7% | 53/72 = 73.6% | 46/72 = 63.9% | 60/72 = 83.3% | 10 | 2 |
| holdout 24 · 학습 모델 | 16/24 = 66.7% | 16/24 = 66.7% | 12/24 = 50.0% | 18/24 = 75.0% | 6 | 0 |
| holdout 24 · 제품 모델 | 21/24 = 87.5% | 15/24 = 62.5% | 13/24 = 54.2% | 19/24 = 79.2% | 4 | 0 |

읽는 법과 한계:
- golden 에서는 제품 모델이 크게 앞선다. 다만 제품 분류 프롬프트가 golden 을 보며 다듬어졌다(replay 도구 설명) — golden 은 제품 모델에 유리한 자료다.
- holdout 은 프롬프트 조정에 쓰지 않았지만 24건이라 둘 다 맞음 12 대 13, **한 건 차이로 구분되지 않는다.** 문제 코드만 보면 학습 모델이 16 대 15 로 한 건 많다.
- 학습 모델 확신도는 믿을 수 없다 — golden 에서 확신도 0.9 이상 51건 중 둘 다 맞음 18건(35%). 「모르면 LLM 에 넘긴다」 구조가 성립하지 않는다.
- 표본이 작고 한 번씩만 돌렸다. 서비스 전체 성능으로 일반화하지 않는다. 제품 모델 쪽 실행 중 유료 대체 경로로 새지 않았는지는 확인하지 못했다(지연 시간은 로컬 모델 값에 가깝다; 호출 경고 로그만 있고 제공자 표시는 없었다).

## 판단

- 판정 기준(미리 정함): 학습 모델이 제품 모델 이상이어야 연결한다. golden 에서 미달, holdout 에서는 구분 불가, 구조상 이유 6개 중 1~3·6 은 별도 작업이 있어야 해소된다. → **연결하지 않는다.**
- 다시 검토할 조건: 실제 여행 대화 문장을 모아 **사람이 검수한 정답**으로 다시 학습하고(문제 코드 18종, 심각도 포함), 제품 모델과 같은 자료·같은 조건으로 다시 비교해 낫다고 확인될 때.
