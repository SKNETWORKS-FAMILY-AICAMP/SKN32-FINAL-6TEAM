# 길찾기 직선 어림값 · 수정 저장 거절 개선 (Claude, 2026-10-22)

사용자 지적(10-21): 「길찾기가 뭐만 하면 대충 직선거리 예상 시각으로 나온다」 「수정하다가 거리가 안 된다고 거절하는데 다시 제출하면 해결해 줘야 하는 것 아니냐」. 원인 진단은 [2026-10-21 진단](../2026-10-21_leg_estimate_fallback_diagnosis.md)(5절에 정정).

## 왜 이렇게 (사용자 지시와의 관계)

- 10-20 사용자 결정은 「시간 한도에 닿은 것만으로는 거절하지 않는다」였고 「오류 · 자료 없음은 종전대로 거절」이 시험 주석에 적혀 있었다. 이번(10-22) 지시 「개선해서 반영」은 자료 없음까지 거절하지 않는 쪽으로 읽었다 — 몇 번을 제출해도 같은 이유로 막히는데 안내는 「잠시 뒤 다시 시도」였기 때문이다. **이 해석이 틀리면 `direct_schedule.leg` 의 마지막 분기만 되돌리면 된다.**
- 어림으로 저장돼도 같은 판의 검사(`review.build(estimate_needs_review=True)`)가 시간표로 못 구한 구간을 「확인 필요」로 센다. 확인 필요가 남아 있으면 등록되지 않는다(`ready` 거짓).
- 오류만 거절을 남긴 이유: 계산기가 불러지지 않은 것은 「계산이 틀렸다」가 아니라 「모른다」이므로 근거 없는 도착 가능 표시를 만들지 않는다는 기존 원칙(D-018)을 지켰다.

## 하지 않은 것 · 남은 일

1. 어림이 운영에서 실제로 몇 %인지 · 이유 분포(로그 줄 배포 후 x600 서버 로그에서 센다).
2. 「계산 중」표시와 이어서 계산(화면) — 계산 못 한 구간을 직선 어림 대신 「계산 중」으로 보이는 일은 화면 변경이라 안 했다.
3. 구간 결과 DB 저장(요청 · 프로세스 사이 재사용) · 도로 그래프로 잰 시간을 둘째 대체 소스로 쓰기 · 일정 짜기(`planner.add_moves`)가 어림 분만큼 뒤 일정을 미는 것의 제거 · 이동 계산기 잠금 대기가 예산에 잡히는지 확인.
4. cs 프로젝트 서버 실서버 확인: 수정 저장에서 도보 상한 밖 장소(자료 없음)를 넣어 거절 없이 「확인 필요」로 저장되는지.
