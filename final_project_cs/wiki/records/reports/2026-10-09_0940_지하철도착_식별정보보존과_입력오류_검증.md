# 지하철 도착 식별정보 보존과 입력 오류 검증

역·종착역·열차 번호를 버리던 읽기 과정을 고쳤습니다. 잘못된 도착시간과 응답 목록도 정상 결과와 구분합니다. 실제 출발·환승 시각에 지하철 도착정보를 적용한 것은 아닙니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 신규 통제 시험 | 통과 | 43/43 = 100% |
| 기존 동작 포함 관련 시험 | 통과 | 65/65 = 100% |
| 주입 응답 전후 재생 | 검증 | 8/8 = 100% |

생성 2026-10-09T09:40:36.719037+09:00. 신규43건은 관련65건에 포함됩니다. 재생8회는 정상/제곱숫자 2개 통제 입력을 이전·수정·수정·이전 순서로 반복한 것입니다. 새 운행 관측이나 독립 웹 표본8개로 세지 않습니다.

## 원인과 구현

서울 지하철 소스는 도착시간·메시지만 정규화하고 공식 역ID·열차 번호를 버렸습니다. 앞으로 계획 경로에 맞는 열차를 고르는 데 필요한 정보를 잃는 문제입니다. `str(value).isdigit()` 검사도 충분하지 않았습니다. 제곱숫자 U+00B2는 이 검사를 통과하지만 정수 변환이 실패합니다. Python의 긴 숫자 문자열 제한도 동일하게 예외를 냈습니다.

내부 도착 소스 응답 v1.1에 다음8필드를 추가했습니다. 기존 필드를 삭제하거나 Core 계약을 바꾸지 않았습니다.

| 원 응답 | 보존 필드 |
|---|---|
| `subwayId` | `line_id` |
| `statnId` | `station_id` |
| `statnFid` | `previous_station_id` |
| `statnTid` | `next_station_id` |
| `bstatnId` | `terminal_station_id` |
| `bstatnNm` | `terminal_station` |
| `btrainNo` | `train_number` |
| `ordkey` | `arrival_order` |

문자열 식별정보는 선행0까지 그대로 보존합니다. 비음수 정수는 문자열로 바꾸고 논리값·실수·객체·빈 문자열은 None으로 남깁니다. ID를 임의 생성하거나 지도 API를 부르지 않습니다. ETA는 비음수 정수 또는 ASCII 숫자 문자열만 받으며0초는 보존합니다. `eta_status`가 valid/missing/invalid를 구별합니다. 잘못된 목록 또는 잘못된 행은 `malformed_arrivals` 실패로 기록하며 빈 열차 목록으로 위장하지 않습니다. 기존 INFO-200·호선 필터·소스 관측시각·키 가림은 유지합니다.

## 실제 실행 근거

수정 전 신규43/43이 실패했고 수정 후 관련65/65가 통과했습니다. 신규 계약 필드 검사도 포함하므로43개의 실운영 사고로 해석하지 않습니다. [명령·원문 로그](../evidence/2026-10-09_0936_지하철_식별정보_보존/)에 종료코드·JUnit·Ruff 결과를 보존했습니다. [이번 소스 변경](../evidence/2026-10-09_0936_지하철_식별정보_보존/owned-source-diff-v1.patch)과 [신규 시험](../../../tests/unit/travel/test_subway_identity_v1.py)이 재현 근거입니다.

주입한 정상 응답과 잘못된 제곱숫자 응답을 이전·수정·수정·이전 순서로 재생했습니다. 정상 응답의 기존11필드는 전후 동일하며 식별정보가 추가됩니다. 제곱숫자는 이전2/2회 ValueError에서 수정2/2회 `eta_seconds=None, eta_status=invalid`로 바뀝니다. 외부 네트워크 연결을 차단했고 연결 시도0회였습니다. [재생 원문](../evidence/2026-10-09_0936_지하철_식별정보_보존/controlled-replay-v1.json). 실제 공급처에서 같은 오류가 관측됐다고 주장하지 않습니다.

초기 콘솔 점검은 PowerShell 파이프 인코딩 영향을 받을 수 있어 최종 근거로 쓰지 않았습니다. UTF-8 파일에 Unicode escape로 정의한 pytest와 재생 스크립트 결과만 사용했습니다.
