# ST4F-718 크레딧 자동 재생 이력 보존 결함

미배정 ST4F-718의 「이 기기에서 여행마다 한 번」 조건과 달리, 51번째 여행을 기록하면 첫 여행의 재생 이력이 사라지는 결함을 격리 사본에서 수정했습니다. **운영 수락·종결·통합 승인은 아닙니다. ST4F-740과 보안 HOLD는 유지합니다.** 담당·검증은 이번 Codex 세션이며 독립 검토자는 아직 없습니다.

## 선정과 범위

루트·CS AGENTS/CLAUDE·RULE, 양쪽 wiki 입구, 개발 역할, 코드 경로, 지정된 740 독립 검토를 확인했습니다. 실제 Hermes `_coord` NOTICE 60개와 TeamFlow 16분할 GET의 고유 689개를 읽었습니다. 미완료는 103/689 = **14.9%**, ST4F-718은 담당 없음·review입니다. 재확인 NOTICE는 자체 공지를 포함해 61개입니다. 718 숫자가 우연히 포함된 과거 커밋 해시도 본문을 읽어 구분했습니다. 동일 이력 보존 결함의 담당·해결 기록은 찾지 못했습니다. 기존 727·729·731·734 검토나 740 날짜 수정을 반복하지 않았습니다.

작업 사본은 `scratch/teamflow-next-after740-20261029/r`, 기준은 검토된 740 후보 `6573e2067d49787257de22a132a8826ea3aad2e9`입니다. 새 후보는 `cf8d976034b8c559147bd32862b678f98255e5cb`이며 변경은 `ending-credits.ts` 한 표현식과 새 회귀시험 한 파일입니다. 원본 제품 코드는 수정하지 않았습니다.

팀 role-manager tip은 새 GitHub 조회에서 `fab3da50ab970a7d8c79ed65c1df2e666abc1cd0`입니다. 해당 원격 `ending-credits.ts`를 새로 받아 사본의 수정 전 LF 바이트와 일치함을 확인했습니다. **최신 전체 통합 검증을 뜻하지 않습니다.** 보존 bundle에는 부모 740 후보가 포함됩니다. 통합 담당자는 bundle 전체를 그대로 반영하지 말고 두 파일만 담은 `candidate.patch`를 실제 통합 tip에서 검토해야 합니다. 이번 작업은 push·배포·통합 예약을 하지 않았습니다.

## 재현과 변경

`trip-screen.tsx`는 시각이 마지막 일정 끝을 넘을 때 `claimCreditsAutoPlay(trip.id)`가 참이면 자동 크레딧을 엽니다. 기존 함수가 `localStorage` 이력을 `.slice(-50)`으로 자릅니다. 새 여행을 기록하면 이전 여행이 잊히므로 그 여행이 다시 종료 전이를 겪을 때 자동 재생을 다시 허용할 수 있습니다. 이미 종료한 여행에 들어가는 것만으로 즉시 자동 재생된다고 주장하지 않습니다.

52개 합성 여행 ID를 순서대로 기록하고 새로고침한 뒤 다시 확인했습니다. 기존 코드는 저장 이력 50개이며, 앞에서부터 재확인하면 잘림이 연쇄적으로 발생해 52개 모두 다시 허용합니다. 수정본은 저장 이력 52개·재허용 0개입니다. 기존 50개 이력을 넣고 새 여행 하나를 기록하는 경우도 첫 여행 이력 유실을 확인했습니다.

수정은 이력 배열의 50개 제한만 제거합니다. 저장 키·JSON 형식·중복 판정·잘못된 원소 필터·일정 종료 시각 판정은 그대로입니다. 저장소 사용 불가·용량 초과·고객의 브라우저 자료 삭제에 대한 기존 한계는 해결하지 않았습니다. 이력은 기기 브라우저에만 남으며 서버 고객 자료를 만들거나 읽지 않았습니다.

## 실패·보존·인계 중간 기록

첫 새 clone `repo`는 과거 긴 파일 이름 4개 때문에 checkout 실패했고 그대로 보존했습니다. 두 번째 새 clone `r`은 명령에만 `core.longpaths=true`를 주어 성공했습니다. 이후 설정은 새 사본의 독립 `.git`에만 적용했습니다. 공유 원본의 색인·skip-worktree·sparse 설정은 바꾸지 않았습니다.

초기 관문은 연결 불가 포트 1로 시작한 실행이어서 검증 완료로 사용하지 않습니다. 해당 실행의 PID·자식 관계를 확인한 뒤 이 세션의 관문 프로세스만 중단하고 로그를 보존했습니다. 새 PostgreSQL은 `127.0.0.1:56118`, DB `calendar_test`, 자료 폴더 `scratch/teamflow-next-after740-20261029/pgdata`입니다. migration·프롬프트 등록은 전용 DB에서 성공했습니다. 최초 PG 시작 helper의 출력 파이프 대기 문제도 보존하며 별도 명령으로 준비했습니다.

초기 트래커 조회에 과거 740 `query.py`를 재사용해 그 사본의 private 이슈 조회 JSON을 갱신한 실수가 있습니다. 과거 보고서·공개 tracker-summary·시험 로그·XML·스캐너는 수정하지 않았습니다. 이후 모든 조회·로그는 새 경로에 남깁니다. 이 실수를 원본 보존 완료 범위에 숨겨 포함하지 않습니다.

원본 XML·스캐너는 종료 SHA256도 시작값과 2/2 = 100% 일치합니다. 후보 XML도 원본과 바이트가 같습니다. 보안 검사 우회·허용 목록 변경·원문 삭제는 하지 않았습니다. 원본 스캐너와 원격 기준 스캐너의 기존 차이도 유지했습니다. 원본 제품·운영 고객 쓰기·push·배포·삭제·이슈 종결은 모두 0건입니다.

증거는 `scratch/teamflow-next-after740-20261029`에 있으며 원시 tracker/coord JSON은 private로 보존합니다. 공개 증거에는 검증 집계와 패치만 싣습니다.

## 종료 확인과 다음 작업

필수 세 관문 명령은 `python -m pytest tests/contract -q`, `python -m pytest tests/security -q`, `python -m scripts.verify_dod_v11`입니다. 새 관문 로그는 각각 `contract-pg.log`, `security-pg.log`, `dod-pg.log`이며 실제 자식 종료 코드는 0·1·0입니다. Python wrapper 자체 종료 코드만으로 보안 통과를 판단하지 않았습니다. 웹은 `vitest run`, `tsc --noEmit`, 두 변경 파일 대상 eslint를 실행했습니다. Next 전체 빌드는 실행하지 않았습니다.

TeamFlow는 쓰기 직전 단건 전체 객체를 다시 GET하여 저장한 사전 객체와 완전히 같음을 확인했습니다. ST4F-718 설명에 위 결과·제약을 추가한 뒤 별도 GET에서 설명 전체를 정확히 대조했습니다. 바뀐 필드는 `desc`, `updatedAt`뿐이며 review·담당 없음·기존 운영 수락 항목은 유지됩니다. 이후 16분할 GET으로 고유 689개를 다시 읽었고 추가·제거 0, 다른 이슈 688/688 = 100% 불변을 확인했습니다. 미완료는 여전히 103/689 = 14.9%입니다. 740도 변하지 않았습니다.

전용 PG는 data_directory·포트·DB 식별을 다시 확인하고 정지했습니다. 56118 연결 거절을 확인했으며 DB 자료 폴더·사본·실패 로그·시작 helper를 보존했습니다. 최초 helper는 PG 정지 뒤 파이프 대기에서 풀려 후속 createdb 연결 실패로 종료했습니다. 실제 migration·프롬프트 등록·관문은 앞서 별도 명령으로 성공했으며 이 helper 실패를 성공 증거로 사용하지 않았습니다.
