# Activity LLM 3단계 — 판정 계층 리포트

## 결론

판정 계층(규칙 · LLM · 섀도 · LLM 모드)과 판정 프롬프트 다섯 개를 만들었다. 실제 모델로 다섯 종류를 모두 불러 동작을 확인했다.
LLM 판정은 코드가 검증한다. 인용이 원문에 없거나 출처가 검색 목록에 없으면 「모름」으로 내린다. 호출이 실패해도 예외를 던지지 않고 「모름」에 실패 코드를 단다.
Team 은 아직 이 계층을 부르지 않는다(4단계). 그래서 고객 답변은 바뀌지 않았다.
시험 결과는 2000 passed, 73 skipped다. 2단계보다 83건 늘었고 실패는 0건이다.

## 정한 것

- **게시일 없는 웹 근거는 버리지 않는다.** 스파이크에서 3회 중 2회가 비어 있어, 버리면 거의 모두 「모름」이 된다. 대신 `undated_citations` 로 센다.
- **LLM 모드는 호출 실패일 때만 규칙으로 대신한다.** 근거 검증에서 떨어지면 「모름」으로 둔다. LLM 모드를 켠다는 것은 「근거를 못 대면 모른다고 말한다」를 고르는 것이기 때문이다.
- **실패 코드 `llm_error` 를 더했다.** 계획에 없던 코드다. 429·키 없음·네트워크 오류를 시간 초과나 스키마 오류와 구분해 센다.
- **재난문자 0건이면 `no_effect` 에 인용이 필요 없다.** 문자가 없다는 것 자체가 근거다.

## 운영 영향

- 로컬 개발 DB 에 프롬프트 5개를 등록했다(`python -m scripts.register_prompts`, 기존 행은 그대로 두고 추가만 한다). **CI·다른 개발 환경도 같은 명령을 한 번 돌려야** `test_active_prompts_are_the_deployed_set.py` 가 통과한다.
- 섀도 모드가 기본값이다. 다만 Team 이 계층을 부르지 않으므로 아직 LLM 호출이 일어나지 않는다.

## 남은 것 (4단계)

- `_feasible_operating` · `_guess_weather_sensitive` · `_feasible_disaster` 가 `build_judge(...).judge(...)` 를 부르게 한다.
- `_feasible_live_status` 를 추가한다. 실외이거나 시작까지 72시간 안일 때만 부른다.
- `live_status` 의 `address` 를 채울 출처를 정한다. `read.place` 에는 주소가 없고, `csv_places` 행을 쓸지 확인해야 한다.
- 위 판정 4종의 **기존 시험이 섀도 모드에서도 그대로 통과**해야 한다.
