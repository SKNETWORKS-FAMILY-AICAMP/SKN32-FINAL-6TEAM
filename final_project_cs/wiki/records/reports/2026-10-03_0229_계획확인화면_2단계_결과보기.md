## 수행 내용

### 1. 결과 화면 동작 — [plan-check.tsx](../../../frontend/apps/web/src/features/plan-check/plan-check.tsx)

- 카드는 한 번에 하나만 펼쳐진다. 머리는 제목 안의 버튼(`aria-expanded`)이고, 이동 줄도 같은 방식으로 펼친다.
- 카드를 고르면 지도에 그 날과 그 핀이 선택된다. 핀을 누르면 그 카드가 펼쳐지고 목록에서 보이는 자리로 온다.
- 일차 머리를 누르면 지도가 그 날로 바뀐다.
- 손잡이로 목록 높이를 중간 → 높게 → 낮게 순서로 바꾼다.
- 새 자리 두 개를 만들었다: `notice`(화면 맨 위)와 `footer`(결과 목록 맨 아래).
- 배치 CSS는 공통 변수만 쓴다(색 직접 지정 0건).

### 2. 실서버 결과 연결 — [from-intake.ts](../../../frontend/apps/web/src/features/plan-check/from-intake.ts) `resultOf`

- 기존 확인 화면의 `rows`·`placeOf`·`draftOf`·`statusOf`를 같이 써서 서버 데이터를 같은 기준으로 읽는다.
- 일차와 항목: 서버가 준 항목(뺀 항목 제외), 좌표, 여행 제목을 그대로 쓴다.
- 장소: 찾은 장소는 ✓, 문제(`check.problems`)는 ✕, 확인하라는 표시(`needs_review`)는 !로 보인다.
- 시간: 서버가 채운 시각(`check.filled`)은 ✎, 문제·확인 표시는 ✕·!로 보인다.
- 판정: 문제나 확인 표시가 있으면 확인 필요, 서버가 시각을 채웠으면 조정, 아니면 유지다.
- **운영시간·휴무일·이동은 응답에 없어 보이지 않는다.** 서버가 해·날짜를 짐작만 한 것과 고객이 고친 값은 확인 필요로 세지 않는다(기존 화면과 같은 기준).

### 3. 실제 경로 — [intake-review.tsx](../../../frontend/apps/web/src/features/intake-review/intake-review.tsx)

- 읽기가 끝나면 기존 확인 화면 대신 새 결과 화면이 나온다. 이미 읽은 접수를 열어도 결과 화면이다.
- 결과 하단의 임시 버튼(`ResultActions`, 목업의 하단 버튼 줄이 만들어질 때까지)
  - 「여행 등록」: `/confirm`(설문 포함)을 부른다. `check.ready`가 아니면 꺼지고 이유와 서버 문장을 보인다.
  - 「일정 고치기」: 기존 확인 화면(수정)을 연다.
  - 이미 등록한 접수는 「여행 보기」를 보인다.
- 읽은 일정이 없어 일정 짜기가 필요한 접수는 기존 화면으로 바로 간다.
- 처음 방문한 사용자의 키 안내(`KeyNotice`)를 새 화면 맨 위에 보인다. 기존 여정 틀에서 보이던 것과 같다.

### 4. 시험

- 모방 서버에 「등록을 막는 문제」 시나리오(`intake: "blocked"`)를 더했다.
- 도우미 `openEditor`를 더했다.
- 기존 확인 화면을 쓰는 live 시험 9개에 「일정 고치기」 단계를 넣었다. 이 중 1개는 새로고침 뒤에도 다시 연다.
- 첫 방문 시험은 새 결과 화면에서 카드를 펼쳐 서버의 장소를 확인하고 새 「여행 등록」으로 등록하게 바꿨다.
- 새 시험
  - live 2개: 결과 화면과 「일정 고치기」, 막힌 등록
  - demo 3개: 카드·핀, 일차·손잡이, 이동 줄
  - 단위 2개: `resultOf`

## 검증

명령과 출력은 [실행 근거](../evidence/2026-10-03_0229_계획확인화면_2단계_결과보기_검증.md)에 있다.

| 검사 | 결과 |
|---|---|
| 타입 · 린트 | 0건 · 0건 |
| 단위(vitest 전체) | 158/158 = 100% |
| live 빌드 전체(테스트용 모방 서버) | 60/60 = 100% |
| demo 브라우저 — `plan-check.spec.ts` | 8/8 = 100% |
| 실서버(로컬) | 앞 단계에서 올린 접수를 다시 열어 결과 화면을 확인했다 — 키 안내, OSM 지도 핀 3개(「1일차 · 3개 장소 표시」), 「모두 확인했어요」, 카드 3개 「조정」. 경복궁 관람 카드를 펼치면 장소 ✓ 경복궁, 시간 ✎ 「끝 시각이 없어 90분으로 두었다」(서버 문장). 「일정 고치기」·「여행 등록」이 보였다. 등록은 누르지 않았다 |

**live 시험 첫 실행:** 49/58 = 84%가 통과했다. 실패 9개는 모두 읽기 직후 기존 확인 화면의 수정 기능을 바로 누르는 시험이었다. 기본 화면이 바뀐 데서 온 예상된 실패라 「일정 고치기」 단계를 넣어 맞췄다. 새로 쓴 시험 2개의 글자 선택자가 화면 낭독기 상태 문장과 겹친 것도 바로잡았다.

## 남은 문제·다음 작업

1. **3단계 카드 동작**(자동 추천·잠금·삭제·되돌리기)과 **5단계 수정 화면** — 고객이 고친 값의 판정(지금은 유지로 봄)과 수정 계약(`/edits`)을 새 화면으로 옮긴다. 자동 추천·잠금·후보·사진은 서버 API가 없다.
2. **4단계 하단 버튼 줄** — 임시 「일정 고치기」·「여행 등록」을 목업의 「전체 자동 추천 → 재검증 → 여행 등록」으로 바꾼다. 재검증은 서버 API가 없다.
3. **서버 협의** — 확인 단계, 운영시간·휴무일 검사, 이동, 진행 이벤트(인계 문서 §4).
4. **CSS 마감(Codex)** — 지도 칸 크기(공통 지도 최소 높이), 지도 위에 올리는 시트, 선택 핀 색, 뉴트럴 테마.
5. **실서버 시험(`tests/real`)** — 옛 화면 흐름으로 쓰여 있어 「일정 고치기」를 거치게 고쳐야 한다(이번에 실행하지 않음).
