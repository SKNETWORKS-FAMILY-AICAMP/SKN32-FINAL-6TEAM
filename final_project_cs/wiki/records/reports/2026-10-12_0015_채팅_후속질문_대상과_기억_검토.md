# 채팅 후속 질문의 대상 유지와 대화 기억 검토

후속 질문이 가리키는 일정을 선택지와 대화 기록에 함께 보존하도록 로컬 코드를 수정했습니다. 이름을 생략해도 유효한 직전 사실 답변의 대상으로 이어집니다. x600 서버에는 배포·재시작하지 않았고 커밋·푸시도 하지 않았습니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 원인 확인·수정 전 실패 확인 | 완료 | 1/1 = 100% |
| 회귀·계약·보안 시험 | 통과 | 375/375 = 100% |
| 추가 여행 격리·재접속 시험 | 통과 | 6/6 = 100% |
| mock 서버 화면 시험 | 통과 | 1/1 = 100% |

최종 우선순위 보강 뒤 문맥·API 회귀는 68/68 = 100%입니다. 위 375개와 중복되므로 서로 다른 시험 수로 합산하지 않습니다.

작업 시작은 2026-10-11, 마무리 검증은 2026-10-12 한국 시각입니다. 구현·자체 검토는 이 대화의 Codex가 했습니다. 독립 검토를 받았다는 뜻은 아닙니다. 공유 계약은 [후속 질문 계약](../../external/trip-chat-context.md)입니다.

## 무엇이 끊겼나

고객 웹은 `final_project_cs/frontend/apps/web`입니다. 별도 UI 저장소의 개발 콘솔을 조사 대상으로 혼동하지 않았습니다.

| 경로 | 확인한 문제 | 수정 |
|---|---|---|
| 답변 대상 찾기 | 모델이 대상을 생략해도 사실 답변 함수가 문장에서 대상을 다시 찾을 수 있음 | 그 대상을 결정 결과에도 반영 |
| 후속 선택지 만들기 | 선택지는 원래 결정의 대상을 사용하므로 이름 없는 “자세히 알려 줘”가 만들어질 수 있음 | 답변과 동일한 일정 ID를 선택지에 보존 |
| 화면에서 전송 | 선택지 메시지만 보내고 현재 지도 선택을 기본 대상으로 사용할 수 있음 | 선택지 자체 ID 전송, 구형 선택지는 명시적으로 선택 없음 |
| 기록·복원 | 최근 대화는 영속 저장되지만 선택지와 대상이 기록 응답에 없음 | 기존 상담 기록에 허용된 응답 정보만 보존·복원 |

즉, 최근 대화를 더 많이 넣는 것만으로 고칠 문제는 아닙니다. “답변에서 확인한 대상”을 다음 질문까지 같은 식별자로 연결해야 합니다.

확인한 호출 흐름은 [채팅 화면](../../../frontend/apps/web/src/features/trip/trip-chat.tsx) → [웹 연결](../../../frontend/apps/web/src/lib/live/gateway.ts) → [고객 여행 API](../../../app/domains/travel_ops/entry/trip_api.py) → [요청 처리](../../../app/domains/travel_ops/components/conversation/trip_messages.py) → [해석·선택지](../../../app/domains/travel_ops/components/conversation/decision_unit.py)·[사실 답변](../../../app/domains/travel_ops/components/conversation/trip_facts.py) → [대화 기록](../../../app/domains/travel_ops/components/conversation/chat_log.py)입니다.

## 수정의 범위

새 [대상 확인 함수](../../../app/domains/travel_ops/components/conversation/fact_context.py)는 읽기 전용 사실 질문에만 적용합니다. 새 문장의 이름·날짜·시각이 있으면 그 범위를 우선합니다. 명시 선택이 현재 여행에 없으면 다른 일정으로 옮기지 않고 재선택을 안내합니다.

직전 대상의 자동 승계는 같은 여행·같은 일정 버전·유효 시간 안에서만 허용합니다. 유효 시간은 [가드레일 설정](../../../config/guardrails.yaml)의 1,800초이며 제품 운영 정책값입니다. 논문에서 가져온 최적값이 아닙니다. 만료 계산은 고객이 보낸 여행 시각 대신 cs 프로젝트 서버의 현재 시각을 사용합니다. 실제 답변 직전에도 최신 일정 객체를 다시 확인합니다.

이름 없는 짧은 후속 질문에서는 검증된 직전 대상이 모델의 다른 일정 추측보다 우선합니다. 모델이 현재 목록에 있는 ID를 골랐더라도 직전 대상의 버전·시간이 만료됐으면 그 추측으로 만료 검사를 우회하지 못합니다.

기존 요청의 선택적 `item_id`를 그대로 사용하고 응답 선택지에 선택적 `item_id`를 더했습니다. 새 필수 입력·DB 표·모델 호출·외부 메모리 서비스를 추가하지 않았습니다. `chat_reply`에는 선택지·표시용 답·추가 설명·대상 ID·버전·확인 시각만 허용합니다. 전체 상담 상태를 웹에 돌려주지 않습니다.

현재 문맥 기능은 결정 모드가 `on`인 경로를 대상으로 합니다. 구조화 호출이 없는 `off`·`shadow` 경로를 같은 수준으로 확장하지 않았습니다. 기존 선택지는 이름이 포함된 문장으로 동작하지만, 배포 전에 만들어진 대화에 구조화 대상이 소급 생성되지는 않습니다. 같은 여행의 여러 탭은 여행 단위 대화를 공유합니다.

모델 호출이 실패한 경우, 일정 변경·업체 예약·승인 절차에는 자동 대상 승계를 적용하지 않습니다. 기능 안내의 `answer_service`와 안내 지식 작업은 다른 대화의 변경을 보존했습니다. 채팅 맨 아래 이동 버튼도 변경하지 않았습니다.

## 검증 증거와 한계

수정 전 백업의 실행 함수를 메모리에서만 연결해 새 회귀 시험 하나를 실행했습니다. 모델이 대상을 생략한 조건에서 상세 선택지가 `{'label': '자세히 알려 줘', 'message': '자세히 알려 줘'}`로 나왔고 `item_id` 확인에서 실패했습니다. 현재 소스 파일은 이 확인 과정에서 덮어쓰지 않았습니다. 수정 후 같은 시험이 통과했습니다.

각 실행에는 중복 시험이 포함됩니다. 실행별 숫자를 합쳐 서로 다른 시험 수라고 세지 않습니다. 통합 관문의 분모 26은 실행 도구가 정의한 기능 기준이며 실제 모델 정확도의 분모가 아닙니다. 마지막 웹 연결 시험 재실행도 34/34 통과, 1.43초였고 형 검사도 종료 0이었습니다.

mock 서버 시험 1/1 = 100% (화면 반응): 선택지 대상 전송·새로고침 복원.

실서버 확인 (서버 응답): 했음. x600 서버의 cs 프로젝트 서버에서 “서울 타워 저거 뭐야?” → 주소 선택지 → “자세히 알려줘”를 확인했습니다. 이번 확인에서는 세 요청 모두 N서울타워를 가리켰습니다. 신고된 실패를 실제 화면에서 다시 재현했다고 쓰지 않습니다. 운영 코드는 수정 전 상태이며 수정판의 운영 검증은 아직 안 했습니다.

첫 형 검사는 기존 `_backup` 안의 시험 파일 3개에서 상대 경로 import 오류 6개로 실패했습니다. 원본을 백업한 뒤 TypeScript의 `exclude`에 `**/_backup/**`만 더했고 다시 통과했습니다. 첫 화면 시험은 Chromium 실행 파일 버전이 맞지 않아 시작하지 못했습니다. 설치된 Chrome 채널로 다시 실행해 통과했습니다. 초기 DB 시험의 샌드박스 연결 제한은 로컬 DB 접근을 허용한 실행으로 해결했습니다.

실제 서비스 화면에서 질문·답변이 두 번 보이는 현상과 장소 주소 조회 실패도 관찰했습니다. 이 작업에서 새로 생겼다고 확인하지 않았으며 별도 결함 후보입니다. 이번 수정의 통과를 그 문제의 해결로 해석하지 않습니다. 실제 모델의 반복 정확도·응답 지연·비용 변화는 측정하지 않았습니다.

## 대화 기억 연구에서 가져올 것

2026-10-12 확인한 논문 6편과 공식 문서 1개입니다. 아래 날짜는 arXiv 제출·개정일이며 학회 발표일과 같다고 가정하지 않습니다. 논문의 수치를 우리 서비스 성능으로 옮기지 않습니다.

| 출처와 날짜 | 확인한 핵심 | triPilot 적용 판단 |
|---|---|---|
| [LongMemEval](https://arxiv.org/abs/2410.10813), 최초 2024-10-14·v2 2025-03-04 | 추출, 여러 대화의 결합, 시간, 정보 갱신, 답할 수 없는 질문을 나눠 평가 | 오래된 장소·새 선호·서로 다른 여행을 별도 평가군으로 만들기 |
| [Mem0](https://arxiv.org/html/2504.19413v1), 2025-04-28 | 새 대화에서 기억 후보를 추출하고 비슷한 기존 기억과 추가·수정·삭제·유지 판정 | 선호 기억을 도입한다면 출처와 변경 이력을 먼저 설계. 이번 대상 연결에 외부 서비스 도입은 불필요 |
| [EMem](https://arxiv.org/html/2511.17208v1), v1 2025-11-21·최신 초록 v2 2025-12-11 | 사건을 인물·시간·맥락·원문 턴 출처와 함께 저장. 경량 검색과 그래프 검색 비교 | 자유 요약보다 “누가 언제 어떤 여행에서 무엇을 확정했나” 단위가 검증하기 쉬움. 본문 검토는 v1 범위 |
| [When Users Don’t Ask](https://arxiv.org/html/2609.03467v2), 최초 2026-09-03·v2 2026-09-22 | 직접 질문뿐 아니라 암시·틀린 전제·복합 대화 요청에서 검색과 답변 품질을 따로 평가 | “거기 알려줘” 같은 실제 말투와 잘못된 전제도 시험. 검색 성공만으로 답변 성공을 선언하지 않기 |
| [UtilMem](https://arxiv.org/html/2608.30508v1), 2026-08-31 | 필요한 기억을 찾더라도 여러 근거 결합이나 유사한 방해 정보 구분에 실패할 수 있음 | 같은 이름의 다른 날 일정·다른 여행·철회한 선호를 방해 사례로 넣기 |
| [Total Recall at What Cost?](https://arxiv.org/html/2608.11879v1), 2026-08-12 | 기억 구조와 기반 모델에 따라 대화 전체 전송 대비 비용 손익분기점이 달라짐 | 검색 요청 비용뿐 아니라 기억 작성·갱신·임베딩·재순위 비용까지 합산해 실측 |
| [LangChain 공식 메모리 개념](https://docs.langchain.com/oss/python/concepts/memory), 발표일 미표기 | 대화 단기 상태와 대화 간 장기 기억을 분리하고 저장 범위를 명시 | 구조 개념만 참고. triPilot에 LangGraph를 도입하거나 사용한다고 기록하지 않음 |

Mem0의 본문 평가에서는 원 LoCoMo의 답할 수 없는 질문 범주를 제외했다고 설명합니다. 따라서 그 결과만으로 우리 서비스의 불확실한 대상 처리나 안전한 재선택 성능을 보장할 수 없습니다. EMem 본문도 단일 대화의 세밀한 선호 질문에서는 한계를 적습니다. 특정 기억 제품이 모든 평가에서 우세하다는 결론으로 일반화하지 않습니다.

## 방식별 비교와 권장 순서

아래 비용·지연은 구조에 따른 정성적 예상입니다. triPilot에서 잰 수치가 아닙니다.

| 방식 | 해결하는 문제 | 비용·지연 예상 | 주요 한계 | 권장 |
|---|---|---|---|---|
| 최근 대화 원문 | 바로 앞 문맥 | 매 요청 입력량 증가 | 긴 답변 잘림·대상 추측 | 기존 기능 유지 |
| 대상 ID·버전 상태 | “그거”와 클릭 대상 | 작은 DB 조회·기록, 추가 모델 호출 없음 | 복합 주제 전체는 못 보존 | 이번 수정 |
| 선택지의 구조화 값 | 클릭이 가리킨 항목 | 작은 응답 증가 | 옛 선택지의 대상 만료 | 이번 수정 |
| 대화 요약 | 긴 대화 압축 | 요약 호출·갱신 비용 | 시간·부정·철회·예외 누락 | 긴 대화 실패가 관측되면 비교 실험 |
| 장기 기억 검색 | 재방문 선호·과거 결정 | 추출·임베딩·검색·갱신·삭제 비용 | 다른 여행 혼입·낡은 정보·과도한 기억 | 별도 계약과 실측 후 도입 |

추천 순서는 현재 대상의 구조화 → 여행 안의 긴 대화 요약 평가 → 고객이 확인한 선호의 장기 기억입니다. “자세히 알려줘”를 고치기 위해 모든 대화를 벡터 검색하는 구조부터 넣을 이유는 찾지 못했습니다. 이번 확인 범위는 읽기 전용 사실 질문의 대상 연결이며, 장기간 개인화 품질을 평가한 것은 아닙니다.

장기 기억을 도입한다면 저장 단위에 고객·여행 범위, 원문 출처, 기록 시각, 유효 시점, 만료·철회 상태를 붙입니다. 검색 전에 인증된 고객과 여행 범위를 필터링하고, 모델 프롬프트에서만 타 고객 사용을 금지하는 방식에 기대지 않습니다. 확정된 최신 일정이 과거 대화·요약·검색 기억보다 우선합니다. 예를 들어 “이번 여행은 채식 안 해도 돼요”가 들어오면 과거 채식 선호를 현재 여행의 필수 조건으로 강제하지 않습니다.

삭제는 원문뿐 아니라 요약·벡터·캐시·파생 프로필에도 전달하고, 삭제 후 검색 결과와 답변에 다시 나오는지 검증해야 합니다. 기록 보존 기간과 자동 문맥 유효 시간은 별개입니다. 현재 코드는 기존 여행·회원 삭제 정책을 따르는 기존 Case에 대상을 더하며 별도 장기 기억 사본을 만들지 않습니다.

기존 [여행 삭제 구현](../../../app/domains/travel_ops/components/itinerary/trip_delete.py)은 여행 대화 행을 직접 지우고, `retention.case_follows_trip` 설정에 따라 상담 기록과 파생 이벤트를 파기합니다. 이번 범위에서 운영 데이터 삭제는 실행하지 않았습니다.

장기 기억 도입 평가는 여행 문장으로 새로 구성합니다. 이름 생략·여러 날 같은 장소·새 주제로 전환·선호 철회·일정 교체·고객 및 여행 격리·삭제 후 재노출을 나눠 재고, 성공 수/전체 수와 지연·토큰·비용을 함께 기록합니다. 비교할 때 같은 모델과 입력을 고정하고 방식의 실행 순서를 교대로 배치합니다. 이번 로컬 결정 시험은 실제 모델 정확도 평가를 대체하지 않습니다.
