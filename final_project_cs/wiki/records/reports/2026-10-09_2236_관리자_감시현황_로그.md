# 관리자 감시 현황·과거 회차 로그

관리자웹앱에 **감시 현황·로그** 메뉴를 만들었다. 실제 3분 주기 감시의 시작·종료, 확인 대상과 소스별 결과, 후속 처리 이력을 회차별로 저장하고 조회한다. 2026-10-09 사용자 요청에 따른 여행 지속관리 운영 기능이며 운영 환경에는 아직 배포하지 않았다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 회차 기록·조회 | 완료 | 2/2 = 100% |
| 백엔드 회귀 시험 | 통과 | 220/220 = 100% |
| 관리자 브라우저 시험 | 통과 | 2/2 = 100% |

분모는 각 실행에서 수집한 시험 수다. 전체 제품의 완료율이 아니며 중복된 시험 실행을 합산하지 않았다.

## 화면에서 확인하는 것

| 위치 | 볼 수 있는 것 |
|---|---|
| 상단 현재 감시 상태 | 설정 주기, 최근 주기 시작·종료, 다음 예정 시각, 조회 시각, 최근 집계와 상세 보기 |
| 조회 조건 | 한국 시각의 시작·끝, 완료·확인 필요·실행 실패·실행 중, 여행별 필터 |
| 회차 이력 | 주기·수동 실행 구분, 시작 시각·결과·소요 시간, 이전 회차 더 보기 |
| 선택한 회차 상세 | 여행·항목, 재난 안전·방문 일정·이동·출발 확인 결과, 소스별 조회 성공·실패·해당 없음·미연결, 예보 주의와 원인, 생성된 접수·정지·알림 등의 처리 로그 |

관리자웹앱 → **감시 현황·로그** → 기간·여행·상태 선택 → **기간·조건 조회** → **회차 보기** 순서로 사용한다. 최근 회차는 상단 **최근 회차 상세 보기**로 바로 연다. 기록이 더 있으면 **이전 회차 더 보기**를 누른다. 회차 안의 항목 기록도 100개 단위로 더 읽을 수 있다.

이 화면은 10초마다 저장된 DB 기록만 읽는다. 화면을 열거나 새로 읽어도 재난 API를 새로 호출하지 않는다. 외부 API 신규 호출 수와 점검 수를 혼동하지 않도록 캐시가 포함될 수 있다고 안내한다. 강수확률·풍속·기온·지진 규모 등 알려진 수치는 쉬운 말과 단위로 표시하고, 기술 상세는 펼치기로 확인한다.

## 실제 기록 경로

기존 1분 작업 안의 주기 문이 감시를 허용할 때만 회차를 연다. 설정은 180초이고 기존 허용 오차 30초를 유지했다. 기다리는 1분 회차에는 감시 실행 기록이나 외부 호출을 추가하지 않는다. `--only trip_cases` 수동 실행은 별도 회차로 기록하고 주기 시각을 바꾸지 않는다.

재난 안전 확인은 여행마다 재난문자·지진을 먼저 본다. 방문 일정은 기본적으로 앞으로 90분 안에 시작할 항목의 예보·특보·재난문자·교통통제·대기질·지진을 본다. 기존에 추가된 시뮬레이션 현재 항목과 출발 대기 이동 항목도 기존 대상 선정 규칙대로 확인한다. 안전정지 때문에 방문 감시에서 빠진 여행은 안전 점검·정지 기록을 본다.

각 소스 보고서를 회차·여행·항목에 귀속해 저장하므로 정상 결과도 남는다. 시뮬레이션에서 안전정지가 먼저 걸려 방문 점검을 하지 않아도 실제 수행한 6종 전체 입력 점검을 별도 단계로 남긴다. 시작 기록을 먼저 확정하고 항목 결과를 별도로 저장해, 뒤에서 예외가 나도 앞선 항목을 읽을 수 있다. 회차는 실행 중·완료·확인 필요·실행 실패를 구분한다. 최근 주기 실행이 설정 주기의 두 배보다 오래됐으면 지연·중단 여부 확인이 필요하다고 표시한다. 수동 실행이 이를 가리지 않게 최근 주기 실행을 따로 읽는다. 다음 예정 시각은 실행 보장이 아니다.

회차 완료는 감시 처리 종료를 뜻하며 고객 알림의 실제 배달 성공을 뜻하지 않는다. 실행 전에 끝난 회차의 상세 로그는 소급 생성하지 않는다. 기존 주기 문의 마지막 시도 시각만 참고로 표시한다. DB가 준비되지 않았으면 명시적으로 준비 오류를 표시하며 예시 자료로 대체하지 않는다.
