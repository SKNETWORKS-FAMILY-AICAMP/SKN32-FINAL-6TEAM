# 늦어진 일정의 이동 재계산 검증과 시간 계측

N서울타워에서 남대문으로 이동하는 기존 재계산 사례는 통과했습니다. 자료를 이미 올려 둔 뒤 같은 사례를 세 번 계산하면 약 19~21초가 걸렸습니다. 전체층 검증과 다른 작업이 동시에 진행된 조건이므로 서비스 응답 시간 전체나 단독 성능으로 일반화하지 않습니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 기존 재계산 사례 검증 | 통과 | 1/1 = 100% |
| 자료 적재 후 재계산 반복 | 동일 결과 | 3/3 = 100% |
| 전체층 시험 | 별도 실행 중 | 종료 결과 미확정 |

## 기존 값 확인

여행 입력은 N서울타워에서 11:30에 앞 일정이 끝나고, 남대문 도착 목표가 12:13인 사례입니다. 원래 목표는 여유를 포함하면 맞추지 못하고, 버스 01A로 11:30 출발·11:59 예정 도착·여유 포함 목표 12:14를 돌려줘야 합니다. 이 값과 기존 기대값이 일치했습니다.

분리 실행 결과는 `1 passed in 83.57s (0:01:23)`이며, pytest가 표시한 시험 본문 시간은 73.95초였습니다. 시험 본문에는 최초 자료 적재도 들어갑니다. **73.95초를 고객 요청 한 건의 순수 이동 계산 시간으로 해석하면 안 됩니다.** 이 사례는 전체층에 이미 있으므로 1건을 전체층 통과 수에 다시 더하지 않습니다.

## 자료 적재와 계산을 나눈 실측

같은 Runtime을 재사용하고 매번 새 Planner를 만들어 동일 입력을 세 번 호출했습니다. 실측은 다음과 같습니다.

| 측정 | 실측 |
|---|---:|
| 최초 자료 적재 | 46.53초 |
| 계산 1회차 | 21.35초 |
| 계산 2회차 | 19.08초 |
| 계산 3회차 | 19.66초 |
| 계산 중앙값 | 19.66초 |
| 계산 최솟값~최댓값 | 19.08~21.35초 |

세 결과 모두 기존 기대값과 같았습니다. 적재 시간은 별도 프로세스에서 한 번 측정했고, 계산은 그 프로세스에서 연속 세 번 측정했습니다. 비교하는 두 구현이 있는 A/B 시험은 아니며, 다른 작업의 CPU 사용과 캐시 효과가 시간에 영향을 줄 수 있습니다. 따라서 개선율이나 실제 고객 응답 시간의 상한을 만들지 않습니다.
