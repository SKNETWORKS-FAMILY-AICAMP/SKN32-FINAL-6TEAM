# Oracle ARM 실제 2코어 환경 지속 서빙 시험 가동

기존 Oracle ARM 기계에 지속 여행 질의 시험을 등록했고 실제 모델 답안과 CPU 목표 충족을 확인했다. 전체 모델 평가와 장시간 안정성 검증은 계속 진행 중이다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 실제 자원·기존 작업 확인 | 완료 | 1/1 = 100% |
| 최초 시험 설정 등록 | 완료 | 10/10 = 100% |
| mock 서버 시험 | 통과 | 5/5 = 100% |
| 실서버 확인 — Oracle ARM 모델 응답 | 확인 | 1/1 = 100% |
| 최초 문항 평가 | 진행 중 | 1/7254 = 0.01% |

## 목표와 실제 범위

2026-10-08 사용자가 기존 Oracle ARM 기계를 실제 2코어·12GB 무료 서빙 환경으로 쓰며 CPU 사용률20% 이상과 지속적인 작업 할당을 요청했다. 옛 부하시험 계획의 실행 승인 대기는 이번 지시로 해제됐다. 새 자원 임대·결제·모델 삭제·실행 중 작업 중단은 하지 않았다.

개인 SSH 설정과 기존 ARM 시험 스크립트를 대조해 접속했다. 처음에는 사용자가 말한 문자열 별칭만 찾아 접속 이름을 못 찾았으나, 설정의 ARM 별칭과 기존 시험 기록으로 정확한 대상을 확인했다. 공용 문서에는 접속 주소·계정·별칭·키 위치를 기록하지 않는다.

`[실측]` 아키텍처aarch64, CPU2개, 기계 전체 메모리12,503,744,512바이트, 처음 남은 디스크54,433,079,296바이트였다. 모델 추론 작업이 실행 중이지 않은 상태에서 별도 작업 폴더와 시스템 서비스를 만들었다. 기존Caddy·Oracle 에이전트 등 다른 작업은 건드리지 않았다.

## 구현과 예약

- [ARM 실행기](../../../../program/scripts/plan_qa_bench/server/arm_serving_queue.py): 한 작업씩 실행, 파일 잠금, 문항별 답안 저장, 미완료 재개, 자원5초 표본, 실행 시도별 모델·자료·코드 해시와 버전 보관.
- [준비 도구](../../../../program/scripts/plan_qa_bench/server/prepare_arm_serving.py): 기존 보관 모델과 고정D3/MX 자료만 사용해10설정을 등록. 9설정×D3 360문항 + 1설정×MX4014문항 = 7254문항.
- [서비스 등록 도구](../../../../program/scripts/plan_qa_bench/server/install_arm_serving.py): 재부팅 후 실행, 오류 시 재개, 작업 전체CPU1.8코어 상한, 코어0~1, 메모리10GiB 상한·9GiB부터 회수, 스왑0, 추론 스레드2.
- [읽기 전용 관측 도구](../../../../program/scripts/plan_qa_bench/server/observe_arm_serving.py): 실제 HTTP 상태, 슬롯, 서비스, 잠금, 답안 ID와 최근5분 자원 집계.

초기 대상은 기존 합친 Gemma-E4B 학습판Q4_K_M/Q8_0, 원본 Gemma-E4B QAT Q4_0·Gemma-E2B QAT Q4_0·Kanana-2-3B Q8·EXAONE-4.0-1.2B Q8·FrogNano Q8이다. 우리 자료로 학습한 합친 파일의 정확한 레시피는 아직 대조하지 못했으므로 특정oos판으로 이름 붙이거나 원본 모델과 일반 우열을 선언하지 않는다. 원본 배포판도 개발사의 지시/결정/코딩 학습이 있는 모델이며 우리 여행 자료 추가 학습과 구분한다.

동시 접수2·캐시 사용/미사용·MX 혼합 질의 설정을 별도 작업으로 예약했다. 최초 작업이 모두 처리된 뒤 성공 설정을 별도 반복 번호로 돌려 연속 서빙 지연·오류·메모리 안정성을 확인한다. 같은 문항 반복은 독립 정확도 표본으로 합치지 않는다. 실패 작업은 원인 수정 없이 반복하지 않는다.

## 검증과 첫 실측

`[실측 2026-10-08 14시40분 전후]` 모델 엔진은 llama.cpp commit `bed0a856606ee4a24a164066f73d2379447033f5`, build11370, GNU15.2.0/Linux aarch64다. 실제 옵션 지원을 기존 바이너리의 도움말로 확인했다. 실행기·준비·설치 스크립트의 ARM 구문 검사가 통과했다.

mock 서버 시험5/5 통과: 정상 번호·null·해석 실패·HTTP 오류·오류를 분모에 포함하는 집계를 확인했다. 최초 제한 환경에서는 로컬 연결 권한 때문에3개가 실패했고, 허용된 로컬 loopback 시험에서 다시5개를 실행해 통과했다. 이 결과를 ARM 실서버 확인으로 간주하지 않았다.

실서버 확인(서버 응답): Oracle ARM 모델 `/health`가`ok`이고 실제 여행 입력에 `{"item": null}`로 답했다. 첫 문항1/360개 저장, 정답1개·HTTP 오류/해석 실패0개였다. 첫 요청의 실제 지연174.50초, 프롬프트1973토큰·캐시0, 프롬프트 처리11.39토큰/초, 출력6토큰이었다. 한 문항이므로 정확도 우열·일반 서비스 지연·p95를 판단하지 않는다.

`[실측]` 최근300.066초의 시간 가중 CPU 평균은 **두 코어 전체 용량 대비75.68%**였다. 기계 전체 평균76.24%, 가상화CPU 대기0.18%, 작업 그룹 메모리8,791,482,368바이트였다. 작업 그룹 메모리는 모델·실행기뿐 아니라 이 그룹에 청구된 파일 캐시도 포함한다. 첫 파일 해시·모델 준비 구간이 일부 포함된 평균이며 이때20% 이상인 연속 관측은255.06초였다. 하루 유지·24시간 안정성은 아직 확인하지 않았다.

서비스는`active`·`enabled`, 최초작업PID171515, 재시작 횟수0이었다. 현재 프로세스가`FLOCK`을 잡은 것을 읽기 전용으로 확인했다. 시스템 서비스가 재부팅 후 실행되도록 설정했지만 실제 기계를 재부팅해서 확인하지는 않았다. 현재systemd는CPUAccounting 옵션을 무시한다고 알렸으며 CPUQuota와 cgroup의 실제CPU 집계는 별도로 동작함을 확인했다.

두 번째 실행기를 직접 호출하는 중복 방지 시험은 자동 승인 심사에서 거절됐다. 활성 작업과 충돌할 수 있다는 이유였으며 그 호출은 실행되지 않았다. 같은 호출을 우회하지 않고 현재 프로세스의 잠금 보유와 등록 상태를 읽기만 했다.

고정 입력 해시는D3 `4bdeca6aace15d7fa5243985dc9bd66fe0ad81685c32c30f69f5958d1ffca2ea`, MX `124cc9952376a72bb87f284754cbbac3da2127d6a8610d59a430a64dc930c087`다. 원본 자료는[데이터 폴더](../../../../datasets/travel/arm_serving_20261008/)에 보관했다. MX4014는 사용자가 부르는E 혼합2007과 같은 요청의 대조2007을 함께 포함하며 전부 자연 평문 자유질의라고 부르지 않는다.
