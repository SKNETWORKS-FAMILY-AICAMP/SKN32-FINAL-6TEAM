작성: Claude Opus 5.5 하위 작업자(독립 검토). 원저자 파일은 고치지 않았습니다. **학습 0, 모델 적재·추론 0, 유료 API 0, 서버·운영 변경 0, e4b lease 획득 0, 다른 작업자 프로세스 접촉 0.** x600에는 읽기 명령(`ollama show`, `printenv`)만 썼습니다.

## 0. 결론

1. **계획의 큰 틀(원본 보존, RL 제외, 누출 통제, 사실은 검색·DB)은 타당합니다.** 다만 아래 심각 문제 3건 때문에 **지금 형태로 학습 데이터 생성에 들어가면 안 됩니다.**
2. **[심각 1] 구조화 우선 설계가 사용자의 자연어 목표를 밀어낼 수 있습니다.** 배포 채팅 경로는 모델을 **한 번** 부르고, 그 JSON 안에서 사용자에게 보이는 문장(`social`, `general_requests[].answer` 추천+이유, `reads[].advice`)까지 함께 냅니다. 「A=enum JSON만, B=자연어 별도 adapter」로 나누면 서빙 형식과 맞지 않습니다. A 목표에서 이 칸을 비우면 학생이 **답 문장을 생략하도록 학습**될 위험이 있습니다(같은 계열 실패가 이미 기록돼 있습니다: 잡담 재생 100건 = 7.7%가 답을 비워 해석 실패, `decision_unit.py:861` 주석).
3. **[심각 2] 학습 후보 말뭉치 G는 채팅 결정 형식과 0행 대응합니다.** G 학습 18,927행 중 `decision_unit` 표지가 있는 행은 0행이고, 자연어 답 학습행도 0행입니다. 입력도 배포 프롬프트(≈6.8k 토큰 지시문)가 아니라 범용 지시문입니다. 그래서 계획 §12의 7번 항목(매핑)은 「대응표 작성」이 아니라 **새 형식의 합성 말뭉치 생성**이 필요한 일입니다.
4. **[심각 3] 「학습 승인 없음」을 차단 사유로 적은 것은 기록과 맞지 않습니다.** wiki에는 이미 「사용자의 이번 승인에 따라 별도 확인 질문 없이 파인튜닝 대기열에 넣는다」는 기록이 있습니다([slm-model-evaluation](../../quality/slm-model-evaluation.md) 「자동으로 이어갈 학습과 재평가」). 사용자 요청도 실질적으로 가능한 작업은 진행하라는 승인이었습니다. 지금 학습을 막는 것은 **기술 조건**(기준선, 툴체인, 메모리, 형식)입니다. 승인이 필요한 경계는 유료 API, 개인정보 외부 전송, x600 사용·서빙 교체로 좁혀 적어야 합니다.
5. 환경 차이는 **직접 확인했습니다.** x600의 실효 문맥은 **12288**입니다(Modelfile과 API env 모두). 8192는 로컬 복제본 Modelfile(10-20 생성)과 10-26 이전 값입니다. 가중치 blob은 같습니다.
6. 384 표본은 **단일 비율 Wald 정밀도로만** 맞는 값입니다. 계획이 쓰겠다고 한 exact 구간이나 +3%p 짝지은 McNemar 관문의 검정력 근거는 아닙니다(§5).

## 2. 환경 차이 직접 검증 — num_ctx 12288 vs 8192

| 위치 | 확인 방법 | 결과 |
|---|---|---|
| x600 Ollama | `ollama show tripilot-pointer:e4b-ft --modelfile` | FROM `4c27e0f5…`, ADAPTER `f01456d8…`, RENDERER/PARSER gemma4, **num_ctx 12288**, temp 0, top_k 64, top_p 0.95, Ollama 0.31.1, 적재 없음 |
| x600 API 컨테이너 | `docker exec … printenv` | `ACOP_OLLAMA_NUM_CTX=12288`, `ACOP_DEPLOYMENT_VERSION=fab3da50ab`, 해석·짚기 모두 `tripilot-pointer:e4b-ft` |
| 로컬 Ollama | `POST /api/show`(적재 없음) | 같은 FROM·ADAPTER, **num_ctx 8192**(modified 10-20) |
| 배포 코드 `fab3da50a` | 정적 읽기 | 기본값 `ollama_num_ctx=12288`. 10-26 주석: 지시문 6,771 토큰, 16항목·4턴 입력 ≈8,110 토큰 + 답 상한 1,200 > 8,192. 같은 모델을 쓰는 4개 호출 경로가 호출마다 12288을 넘깁니다. `settings.py:87` 주석의 「8192」는 오래된 문구입니다 |

판단: 독립 연구(task-1)의 「ctx 8192」는 로컬 기록 기준입니다. 배포 사실은 12288입니다. 영향은 세 가지입니다.
- 로컬 평가·형식 검증은 `num_ctx=12288`을 **호출마다 명시**해야 합니다. 빠뜨리면 8192가 적용되고, 입력 앞부분이 잘린 상태로 「현행 모델 점수」가 나옵니다.
- 학습 시퀀스 길이는 짚기 파일럿(≈1.9k 토큰)이 아니라 **≈8~9.3k 토큰**입니다. 계획 §7의 시간(3.4초/예제)과 메모리(10.6GB, A4000)는 다른 과제의 실측이라 **옮겨 쓸 수 없습니다**(`[추정]` 이하로 낮춰야 합니다).
- 지시문 해시·스키마 해시·num_ctx·chat template을 manifest 필수 칸으로 고정해야 합니다. 지금 검사기에는 서빙 프롬프트·num_ctx가 일치하는지 보는 검사가 없습니다.

## 3. 실제 GPU/OS 메모리 실패 원인과 학습 설계 종속성

읽기 전용 스냅숏만 찍었습니다. `Win32_OperatingSystem`, `Get-Process`, `nvidia-smi`를 썼고, 적재·probe·lease는 쓰지 않았습니다.

| 관측(03:2x) | 값 |
|---|---|
| Windows 가시 RAM / 여유 | 30.5GB / 1.7GB |
| 커밋 한도 / 여유 | 92.8GB(페이지 파일 62GB 포함) / **1.0GB** |
| GPU(N1X) | 98,240MiB 중 31,705MiB 사용, 사용률 96% |
| Hermes Qwen llama-server(PID 39560) | private **36.7GB**(WS 0.9GB, 대부분 페이지 아웃) |
| 다른 작업자 llama-server(42716) | private 6.4GB(실행 중) |

- **원인**: E4B 적재 실패(HTTP 500, ReadTimeout)는 **Windows 커밋 한도 소진** 때문입니다. GPU 메모리는 원인이 아닙니다. 적재에는 모델 크기와 버퍼만큼의 호스트 커밋이 필요한데, Qwen 서버 하나가 36.7GB를 잡고 있어 여유가 1~8GB 사이를 오갑니다. 다른 작업자(`deleg_f6cad80d`, 골든 실측·memdiag)의 03:12 보호 실행에서도 여유 1.1~1.2GB와 120초 타임아웃이 반복됐습니다. mmap 유무 같은 근본 측정은 그 작업자의 몫이라 겹쳐 하지 않았습니다.
- **readiness 설계 영향**: ① `nvidia-smi`의 남은 MiB는 이 기계에서 준비 신호가 아닙니다. ② R04의 12GB는 **추론 적재** 하한입니다(설정 파일에도 그렇게 적혀 있습니다). 학습 하한으로 쓰면 안 됩니다. ③ 8~9k 토큰 QLoRA는 이 PC에서 지금 공존 상태로는 불가능합니다. 학습 기계 결정(A4000 생존 여부·용량, 또는 다른 장비)이 **모든 학습 일정의 선행 조건**입니다.
- **x600 사용 경계**: x600 Ollama는 운영 중이고 지금 아무것도 적재되지 않은 상태입니다. 평가·학습에 쓰는 것은 운영 영향이 있으므로 사용자 경계로 남깁니다.

## 4. 사용자 자연어 목표와 학습 형식

| 사실(배포 `fab3da50a`) | 근거 |
|---|---|
| 채팅 해석에서 모델 호출은 `decision_unit.decide` 안의 `chat.structured` 1회입니다 | `decision_unit.py:739` |
| 같은 JSON의 필수 칸에 `social`, `general_requests[{question, answer}]`, `reads[].advice`가 있습니다. 「추천을 요청하면 실제 추천 대상을 하나 제시하고 이유를 짧게 답한다」 | `decision_unit.py:168–176, 469–476` |
| 그 밖에 화면에 보이는 문장은 서버가 사실로 조립합니다(`trip_replies`·`read_requests`·`trip_desk`) | 모듈 docstring |
| 「대안+이유」의 이유 누락(0/3)은 서버 조립·저장 결함입니다(`pick_reason` 미저장 등) | 계획 C13 |

판단과 제안:
- **Track A와 B를 adapter로 나누지 말고, 출력 칸으로 나눠 평가하십시오.** 학습 목표는 **배포 JSON 전체**(enum 칸 + 자연어 칸)로 둡니다. 평가는 ① enum 정확도·오지목·스키마 유효와 ② 자연어 칸 rubric(근거 없는 사실 0, 추천+이유, 「모름」 처리)과 ③ 최종 화면 문장 종단 평가로 따로 냅니다. 이렇게 하면 `E_TARGET_TYPE_MIX` 규칙은 「한 manifest는 한 **서빙 호출 계약**」으로 바꿔야 합니다.
- **자연어 개선의 상당 부분은 학습 대상이 아닙니다.** S 분류(이유 미저장·미노출, 일정 밖 지역 질문 경로 없음, 후속 「왜」 계약 없음)는 코드 수정입니다. 그래서 **무학습 대조군 A′**(코드·프롬프트·검색만 고친 판)가 **필수 비교군**입니다. 독립 연구(task-1)도 같은 권고를 했는데, 계획 §8의 비교군 ①~⑤에는 빠져 있습니다.
- 두 adapter를 쓰는 서빙(두 모델 이름)은 x600에서 이중 적재나 재적재를 부르고, 턴당 호출이 2회가 됩니다(15초 스트림 상한). Ollama가 한 모델에 adapter를 여럿 붙이는 것을 지원하는지는 `[미확인]`입니다.

## 5. 실험군·누출·통계 근거

**실험군**: 계획 ①~⑤에 **A′ 무학습 개선판**을 추가하고, 주 비교를 「후보 adapter vs A′」로 두기를 제안합니다(`[제안]`). ④ 교사는 상한 참고용이고 ⑤ 무작위 선별은 학습 내부 대조입니다.

**누출**: 검사기의 family·group·근접 중복·금지 경로 통제는 시험으로 확인됐습니다(24/24). 추가할 점은 세 가지입니다.
- 47 골든 후보의 정답은 **Sonnet 기계 정답**입니다. 교사를 Claude 계열로 고르면 47 보고에도 교사·정답 작성자 동족 편향이 생깁니다. 이때는 `E_HOLDOUT_AUTHOR_TEACHER`와 같은 경고를 47 보고에도 붙여야 합니다.
- 교사 입력 여행 골격이 E2-v2·DU-REAL 장소·골격과 겹치는지 검사해야 합니다(group 키에 장소 id 집합 해시 포함).
- 서빙 프롬프트 해시 고정 칸이 없습니다(§2).

**384 표본**([계산](../../../../program/research/sft_distill_review_2026-10-31/evidence/sample_size_384_check.json)):

| 확인 | 값 |
|---|---|
| Wald n(p=0.9, ±3%p) | 384.16. 표본 크기는 올림이 관례라 385 |
| 계획이 쓰겠다는 exact(Clopper–Pearson), n=384, 346 정답 | [0.867, 0.929]. 아래쪽 폭 3.4%p > 3%p |
| 관문 「+3%p, p<0.05」 짝지은 McNemar, 검정력 80% | 불일치율 5%면 434, 10%면 870, 15%면 1,306쌍 |
| 「정답 선택 ≥95%」 입증 | p̂ 0.97·n=384면 하한 0.946으로 미달 |
| family 군집 | 행 수 ≠ 독립 표본. ICC 0.2·군집 3이면 유효 n≈274 |

→ 384는 「한 비율의 대략적 정밀도」 근거로만 쓰고, 관문별로 필요한 짝 수를 사전 등록에서 따로 계산해야 합니다. 「과제당」이면 사람 검수 수천 행이 필요하므로 실행 가능성도 함께 적어야 합니다. 또 wiki 관문(≥95%, 오지목 ≤1% 등)은 **혼합 선택 평가**(짚기 계열)의 사전 기준입니다. 채팅 결정·자연어 칸에 그대로 적용할 근거는 없습니다.

## 7. 우선순위 다음 순서(제안)
