## 해결한 원인과 남은 연결

`bus_identity.py`의 내부 leg에는 노선ID·승하차 순번과 원문 정류소ID를 보존한다. 직행·혼합·가장 이른 출발·대안 생성, 판정·환승 도보·막차 역산, 요금 유형과 구간 소요 범위가 같은 행을 사용한다. 식별값이 어긋나면 동명 정류장으로 바꾸지 않는다. 순번 없는 옛 입력만 기존 이름 탐색을 유지한다. 공개 `plan/core_routes` 옵션 계약은 그대로여서 실제 안내 소비 연결 완료가 아니다.

`select_boardable_arrival`은 외부 조회 없이 정규화된 실시간 응답과 정확한 노선·정류소ID·순번을 받아 계산한다. 최초 확인 뒤 경과시간만 ETA에서 빼고 접근·준비가 끝난 뒤 도착하는 가장 빠른 예상 차량을 고른다. 접근6분·첫 차량3분·둘째7분이면 둘째와 접근 후 대기1분이다. 공급 mkTm을 메시지 기준시각으로 검증하지 않았으므로 이중 차감하지 않는다. 만차·숫자 ETA 부재·잘못된 시각·오래된 응답은 별도 상태다. 만차가 아니라는 관측도 실제 탑승 보장은 아니다.

공개 저장·소비 연결의 [최소 계약 조사](2026-10-09_0011_버스_실시간_출발안내_연결_최소계약.md)를 기준으로 다음에는 선택 옵션별 구간/접근/대기 문맥을 저장하고 조립→팀 계산 끼움자리→안내 흐름으로 연결한다. 부품에서 이동 팀 내부를 직접 import하지 않는다. 첫 버스만 고치고 후속 환승·늦음 판정을 옛 값으로 두지 않는다.

## 실행 증거

[로그·JUnit·수정 파일 해시](../evidence/2026-10-09_0028_버스_선택정류장과_접근시간_검증/)에 109passed·18deselected·4.77초 실행을 보존했다. 단위 계산은 주입 응답을 사용하며 mock 서버 시험은 수행하지 않았다. 실서버 확인(cs 프로젝트 서버 응답)은 안 했고 외부 알림 전송도 없다. 앞 단계 실제 로컬 개발 DB 안내 시험17/17은 [이전 단계 보고서](2026-10-09_0000_이동_도보시간_안내조회_개선과_연속검증.md)에 있다.

확대 기본시험 v4는 sandbox TEMP 쓰기 오류로 수집 중 멈췄다. TEMP를 workspace 안으로 옮긴 v5에서 식별값이 없는 기존 시험 입력 한 건의 실패를 재현했다. 실제 데이터 형식의 노선ID·순번을 시험 입력에 넣고 원래 도보 상한 주장과 식별값 전달 주장까지 확인한 뒤 위109시험이 통과했다. v5는 완료 로그를 얻지 못해 중단했으며 전체 통과로 세지 않는다. 최신 v6 확대시험은 실행 중 로그이며 완료·종료코드 확인 전 전체 통과를 선언하지 않는다. 회차가 이어지면 `.tmp/mobility_complete_20261008/mobility-default-v6.log/xml`의 완료 결과와 현재 소스 해시를 확인한다.

Ruff와 해당 변경 diff 공백 검사는 통과했다. pytest 종료 후 pyreadline 정리의 WinError 출력과 기존 AST 문자열 SyntaxWarning은 원문에 남겼다. pytest 실행 종료코드0과109통과를 구별해 기록했다.

검색 기준일을 자정 이후 2026-10-09로 갱신한 [논문·공식자료9개 등록부](assets/2026-10-09_mobility_research_v2/research-register.json)를 보존했다. [Dynamic Replanning 연구](https://arxiv.org/html/2505.14193v1) §2.1은 도착+환승 도보≤다음 출발을 성립 조건으로 명시한다. 그 필요조건을 소비 계산에 적용했으며 논문의 전체 알고리즘이나 해외 개선 수치를 구현 성과로 주장하지 않는다. [2026 Early Pruning](https://arxiv.org/abs/2603.12592v4)은 초록·개정이력만 확인한 검토 후보이며 전체 증명·전제가 확인되기 전 적용하지 않았다. 검색은 관련 공개 문헌 조사이며 전수검색은 아니다.
