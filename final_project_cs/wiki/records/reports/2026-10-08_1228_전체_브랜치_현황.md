## 매니저와 UI의 관계

`[실측]` `role-manager → role-eval-ui` 관계는 매니저만 0개, UI만 14개다. UI 브랜치에는 매니저의 현재 커밋이 모두 들어 있으며, 파일 내용 차이는 **160개 파일, +23,584줄 / -948줄**이다. 14개 중 병합 커밋은 2개로, 전부 독립적인 기능 14개라는 뜻은 아니다.

`[실측]` `feat/web-manager-integration → role-eval-ui`도 기능 브랜치만 0개, UI만 20개다. 다만 기능 브랜치와 매니저를 직접 비교하면 매니저만 7개, 기능 브랜치만 1개이므로 기능 브랜치의 현재 tip이 매니저에 전부 포함됐다고 말할 수는 없다.

`[실측]` 매니저·UI와 develop의 공통 조상은 **2026-09-28의 `f98678c`**다. UI와 develop의 웹 파일 내용도 390개 파일에서 다르다(+48,987줄 / -5,837줄). 현재 develop → main PR이 병합되어도 이 별도 계열의 최신 웹 변경이 자동으로 포함되는 것은 아니다.

`[실측: 문서 확인]` UI에 이관된 관리자 앱은 프론트엔드 데모이고, 개발자 콘솔은 명시적 샘플 모드다. 해당 코드가 브랜치에 들어 있다는 사실과 실제 백엔드 연결 완료는 다르다. [관리자 README](../../../frontend/apps/admin/README.md) 3행, [개발자 콘솔 README](../../../frontend/apps/dev-console/README.md) 7행.

## PR과 CI

`[실측]` GitHub 전체 PR 35건 중 열린 PR은 **[#2 develop → main](https://github.com/SKNETWORKS-FAMILY-AICAMP/SKN32-FINAL-6TEAM/pull/2) 하나**다. 현재 head `d85cc7c`, draft 아님, GitHub 병합 상태 `CLEAN`이며 연결된 검사 **7/7개 = 100% 성공**이다. 검사 수는 테스트 사례 수가 아니다.

| 검사 묶음 | 현재 결과 |
|---|---|
| CI develop | ruff, architecture·contract·unit 성공 |
| CI main | ruff, 전체 시험(live 제외), Docker 빌드 성공 |
| CI web | web(check·e2e·live) 성공 |
| CI admin | admin(check·html·e2e·unconfigured) 성공 |

`[실측]` 반면 현재 head 기준 `role-manager`, `role-eval-ui`, `role-activity-test`, `feat/web-manager-integration`에는 GitHub Check Run이 각각 0건이다. 이는 실패 판정이 아니라 **현재 커밋에 연결된 GitHub 검사 결과가 없다는 뜻**이다. 과거 PR의 초록 결과를 이 커밋들의 통과 근거로 쓰지 않는다. 별도 로컬 시험의 실행 여부는 이 API로 판단할 수 없다.

`[실측]` 최신 Dining tip의 PR #35 검사는 2/2개, Activity 본 브랜치 tip의 PR #33 검사는 3/3개, Mobility 현재 tip의 검사는 2/2개 성공이다. 셋 모두 develop에 포함된다. 웹의 `test:live`는 가짜 서버 시험이며 실제 운영 서버 검증이 아니다.

## 통합 전에 확인할 일

1. **웹 CI와 현재 웹 스크립트를 맞춘다.** `[실측]` develop의 `.github/workflows/ci-web.yml:56`은 `npm run test:e2e`를 실행하고 demo 환경을 사용한다. 현재 UI의 `frontend/apps/web/package.json:9` 스크립트 목록에는 `test:e2e`가 없으며, UI tip에는 해당 웹 workflow 파일도 없다. `[추정]` develop workflow와 현재 UI 코드를 그대로 조합하면 없는 스크립트 단계에서 실패한다. 이 불일치는 기존 [웹 설계 검토](2026-10-08_1205_웹_설계검토_브랜치비교_보안.md)에도 기록되어 있으며 이번에 두 ref의 내용을 다시 대조했다.
2. **매니저·UI와 develop의 변경 내용을 맞대어 통합한다.** `[제안]` 스냅숏 이력을 포함하므로 커밋 수만 보고 한쪽을 덮어쓰지 말고, 코어·팀 로직·폴더 구조·웹 계약의 차이를 검토한 통합 브랜치에서 검증한다. 충돌 여부와 최종 병합 결과는 이번 보고에서 시험하지 않았다.
3. **Activity 실험 브랜치의 통합 범위를 정한다.** `[제안]` 9개 미통합 커밋에 실험과 결함 수정이 함께 있으므로 내용을 검토하고 PR로 올릴 범위를 정한다.
4. **main에 보낼 범위를 먼저 확정한다.** `[제안]` PR #2는 현재 develop의 검사 통과를 보여 준다. 최신 매니저·UI까지 릴리스할 목적이면 그 작업을 통합한 결과로 다시 검사해야 한다.

## 수행 내용과 검증 범위

`[실측]` fetch, ref·로그·diff·조상 관계 계산, GitHub PR·Check Run 조회, 연결된 작업 폴더 상태 조회를 수행했다. 애플리케이션 코드를 변경하거나 테스트를 새로 실행하지 않았다. 병합·브랜치 전환·커밋·푸시·배포도 수행하지 않았다.

변경 파일은 이 리포트, [조회 증거](../evidence/2026-10-08_1228_전체_브랜치_현황_검증.md), [wiki 로그](../../log.md) 세 개다. 기록 작성 후 커밋 수와 로컬 링크를 다시 대조하고 공백 오류를 확인했다.
