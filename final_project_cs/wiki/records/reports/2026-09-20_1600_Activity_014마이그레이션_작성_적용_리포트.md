# Activity — activities/tour/disaster 마이그레이션(014) 작성 및 적용

## 1. 작업 목표

`wiki/teams/activity.md`에서 Activity 전용으로 결정한 `activities`·`tour`·`disaster` 제안 스키마(`데이터베이스_저장소_설계_v2.md` 원본)를 실제 마이그레이션 SQL로 작성하고 적용한다.

## 2. 실제 수행 내용

신규 파일: `app/infrastructure/db/migrations/014_activity_tour_disaster.sql`

- `tour`: `contentid`(PK) · `contenttypeid` · `title` · `addr1` · `mapx`/`mapy` · `lclsSystm1`/`2`/`3`(대소문자 보존을 위해 큰따옴표로 인용) · `tenant_id` · `fetched_at`
- `disaster`: `SN`(PK) · `CRT_DT` · `MSG_CN` · `RCPTN_RGN_NM` · `DST_SE_NM` · `EMRG_STEP_NM`(모두 원본 대문자 컬럼명 보존) · `tenant_id` · `fetched_at`
- `activities`: `id`(PK) · `tenant_id` · `name` · `lat`/`lng` · `activity_time` · `address` · `tour_api_content_id`(FK→tour) · `disaster_api_content_id`(FK→disaster)

설계 원본에 없던 `tenant_id`를 세 테이블 모두에 추가했다 — 이 저장소의 모든 도메인 테이블이 tenant 격리를 쓰기 때문이다(FK는 걸지 않음, `places`/`place_catalog`와 같은 패턴). 컬럼 주석에 왜 있는지, 무엇이 미확보로 남는지 각각 적었다.

`wiki/teams/activity.md` 갱신:
- "데이터 저장 — 제안 스키마" → **"데이터 저장 — Activity 전용 스키마"**로 절 제목 변경, 마이그레이션 반영 완료로 정정
- "걸리는 것" 표의 "제안 DB 스키마 vs 실제 마이그레이션" 행을 닫힘으로 갱신. `activities`↔`places` 관계는 여전히 미확보로 남김

## 3. 검증 방법과 결과

```bash
python -m app.infrastructure.db.migrate
# → Applied migrations from .../app/infrastructure/db/migrations
```

두 번 연속 실행해 재실행 안전성(`IF NOT EXISTS`) 확인. `psql -d acop_cs -c "\d tour" -c "\d disaster" -c "\d activities"`로 컬럼·인덱스·FK가 설계대로 생성됐음을 직접 확인 — `activities_tour_api_content_id_fkey`·`activities_disaster_api_content_id_fkey` FK, `tour_tenant_idx`·`disaster_tenant_region_idx`·`activities_tenant_time_idx` 인덱스 모두 존재.

## 4. 미해결 이슈·다음 작업 제안

- `activities.tour_api_content_id`가 `places.source_content_id`와 같은 해소 결과를 가리키는지 — 이 마이그레이션은 그 결정을 선점하지 않았다.
- `disaster.CRT_DT`를 text로 뒀다(설계서 확정값 그대로) — 실제 API 응답 포맷을 확인해 timestamptz 변환 여부를 나중에 정해야 한다.
- 재난문자API 실제 호출 클라이언트는 아직 없다(TourAPI와 달리 코드 0줄, 이전 리포트에서 확인).
