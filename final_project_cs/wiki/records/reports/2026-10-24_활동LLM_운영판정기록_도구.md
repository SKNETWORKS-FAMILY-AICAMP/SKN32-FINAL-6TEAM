# 활동 LLM 운영 판정 기록 — 표 · 기록 지점 · 보고서 도구 (2026-10-24)

사용자 지시 「액티비티 LLM이 운영에서 판정한 결과를 문서로 기록하는 코드 짜줘 — 코드 결과 / LLM 재정의 결과 명확하게」.

## 결론

LLM 을 부른 운영 판정마다 **코드 결과 · LLM 원래 답 · 고객에게 나간 결과**를 표 `activity_llm_decisions`(308)에 한 줄로 남기고,
`scripts/activity/llm_decision_report.py` 가 그 표를 마크다운 문서로 만든다. 로컬 구현 · 로컬 DB 확인까지 했고, 커밋 · 배포 · 서버 확인은 하지 않았다.

## 왜

- 대체 후보 순서는 10-21 부터 `llm` 이라 LLM 답이 고객 화면 순서를 바꾼다. 그런데 운영에서 무엇이 바뀌었는지 남는 곳이 없었다 —
  섀도 표(305)는 규칙 판정 다섯 종류만 받고, 대체 후보 순서는 로그 한 줄뿐이었다(앱에 로깅 설정이 없어 운영에서는 사라진다).
- D-CS-015 의 되돌리는 조건(운영 표본 30건 중 위험 오답 1건 …)을 잴 자료가 없었다.

## 만든 것

| 파일 | 내용 |
|---|---|
| `app/infrastructure/db/migrations/308_activity_llm_decisions.sql` | 새 표. `code_result` · `llm_result`(검사 전 원래 답) · `served_result` · `changed` · `outcome`(`llm_served` · `code_fallback` · `skipped` · `shadow`) · 고객에게 보인 이유 · 검사기 사유 · 실패 · 지연 · 모델. 장소는 번호만, 고객 문장 · 설문 · 좌표는 싣지 않는다 |
| `instances/activity/decision_log.py` | 한 줄 쓰기. `changed` 는 여기서 센다. 쓰기 실패는 고객 답을 막지 않고 `WARNING` 만 |
| `instances/activity/replacement.py` `_order_alternatives` | 대체 후보 순서의 모든 갈래에서 기록 — 사용 · 시간 초과 · 호출 실패 · 쓸 수 없는 답 · 예산 건너뜀 · 섀도 |
| `instances/activity/team.py` `_rule_first` | `kind_modes` 가 `llm` 인 판정 종류에서 규칙이 「모름」일 때 LLM 이 정한 값(지금은 그런 종류가 없다 — 모두 `shadow` · `rule`) |
| `app/composition.py` · `repository.py` | 조립이 판정 LLM 이 있을 때만 기록 함수를 꽂는다(`judge_decision_sink`) |
| `scripts/activity/llm_decision_report.py` | 기간 · 테넌트를 받아 문서로. 요약(종류 · 모드별 n/m = %) → 대체 후보 순서 표(코드 순서 / LLM 원래 답 / 고객에게 나간 순서 / 바뀜 ★) → 다른 판정 → 섀도(305 의 운영 줄) |
