## 1. 왜 했나 — 한 문단

같은 날 오전에 「승인 뒤 공급자 원장을 사람 손 없이 바꾸는 분기」를 막는 **둘째 문**(위임
범위)을 만들었는데, **그 문을 열고 닫는 손잡이가 없었다.** 판정기(`delegation.py`)와
`delegations` 표(019)는 있지만 운영자가 위임을 주려면 DB 에 직접 SQL 을 쳐야 했다.
DoD-19 가 재는 성질이 「철회하면 진행 중인 자동 실행이 멈춘다」인데 **철회할 방법이 사람
손에 없으면** 제품의 약속(「언제든 철회할 수 있다」)은 시험 안에서만 참이다. 그 자리를 만들었다.

## 2. 무엇을 만들었나

### 2-1. REST — `/v1/delegations/*` (도메인 폴더)

`app/modules/travel_ops/delegation_api.py`. 라우터는 **도메인 폴더**에 있고
`composition.build_domain_routers()` 가 앱에 넣는다 — presentation 은 도메인을 import 하지
못한다(INV-CS-ARCH-001). `trip_api.py` 와 같은 모양이다.

| 경로 | scope |
|---|---|
| `GET /v1/delegations` | `delegation:read` |
| `GET /v1/delegations/{customer_id}` | `delegation:read` |
| `POST /v1/delegations/{customer_id}/grant` | `delegation:write` |
| `POST /v1/delegations/{customer_id}/revoke` | `delegation:write` |

### 2-2. ★scope 를 새로 둔 판단과 근거

발주는 `action:approve` 가 적절해 보인다고 했다. **나누는 쪽으로 정했다.**

- **승인은 제안 한 건**에 "이 변경을 해도 된다" 이고, **위임은 서 있는 권한**이다 — 한 번
  주면 거둘 때까지 그 고객의 모든 자동 실행이 한계 안에서 열린다. 같은 사람이 둘 다 해도
  되는지는 운영이 정할 문제이고, 권한 체계가 그것을 **못 나누게 만들면 안 된다.**
- 이 저장소는 이미 **영향 범위가 다르면 scope 를 나눠 왔다** — `composer:admin` 을
  `composer:write` 에서(항목 토글 ≠ 선언 통째 교체), `ops:reload` 를 저장에서
  (저장은 되돌릴 수 있지만 반영은 그 순간 트래픽이 받는 것을 바꾼다). 같은 기준이다.
- 읽기/쓰기도 나눴다(`trip:read`/`trip:write` 와 같은 모양) — 현황을 보는 사람이 문을
  열지는 못한다. 시험이 그것을 고정한다(`test_a_read_key_cannot_grant_or_revoke`).
- 정의는 `config/guardrails.yaml` `security.scopes` 한 곳이다(INV-CS-SEC-007).
  `tests/security/test_scope_contract.py` 의 목록을 함께 갱신했다.

### 2-3. 운영 화면 — `/ui/delegations`

`app/presentation/ui/routes.py`. 기존 화면의 짜임새(`theme.py` 컴포넌트 · 서버 렌더링 ·
POST 뒤 `303`)를 그대로 따랐다. **도메인 SQL 도 `travel.*` 설정도 이 층에서 읽지 않는다** —
같은 프로세스의 `/v1/delegations` 를 불러(승인 화면이 이미 쓰는 ASGI transport 길) 그 응답을
그린다. 한계 값의 이름표까지 도메인이 붙여 주므로, 화면은 `label`/`value` 쌍을 표로 그릴 뿐
그 숫자가 무슨 뜻인지 모른다.

★**승인 화면의 교훈 둘을 그대로 지켰다.**

| 교훈 | 이 화면에서 |
|---|---|
| 실패를 조용히 삼키지 않는다 | 실패는 `303` 이 아니라 **사유가 적힌 화면**이다 — HTTP 코드 + 응답 본문 + 목록으로 돌아가는 링크. 거둘 위임이 없으면 `409 no_live_delegation` 이 그대로 뜬다 |
| 되돌릴 수 없는 행위는 무엇이 바뀌는지 먼저 보여 준다 | 맡기기는 **확인 단계**를 거친다 — 열리는 한계 · 이미 나간 금액 · 남은 여유 · 지금까지 주고 거둔 기록. 그 화면은 아무것도 바꾸지 않는다. **거두기에는 확인 단계를 두지 않았다** — 막는 방향이고, 한 번 더 묻는 사이에 자동 실행이 나갈 수 있다 |

### 2-4. 감사 — 마이그레이션 021

**칸이 없던 것이 아니라, 있는 칸이 덮이고 있었다.** 019 의 `delegations` 는
`granted_by`·`revoked_by`·`granted_at`·`revoked_at` 을 한 행에 한 벌 갖는데, 다시 주기가
`ON CONFLICT … DO UPDATE SET granted_at=now(), revoked_at=NULL, revoked_by=NULL` 이다.
즉 **주기 → 거두기 → 다시 주기** 를 하면 누가 언제 거뒀는지가 사라진다. 019 자신이 「그때는
위임 안에 있었다를 나중에 확인할 수 있어야 한다(감사)」고 적어 둔 것이, 다시 주는 순간
깨지고 있었다.

021 은 `delegation_events`(append-only)를 만든다 — `seq`·`action`(`granted|revoked`,
CHECK)·`actor_id`·`note`·`at`. `case_events` 와 같은 모양이다. 지금 상태는 `delegations` 가,
「어떻게 여기까지 왔나」는 이 표가 답한다. 재실행 안전(`IF NOT EXISTS` · `pg_constraint` 확인),
`pending/` 은 건드리지 않았다.

## 5. 미해결 · 다음 작업 제안

1. ★★**`/ui/*` 에 로그인이 없다.** 운영 화면 전체가 그렇고 승인 버튼도 같은 상태다. 이번에
   **위임을 주는 버튼이 그 위에 올라갔다** — 새로 만든 구멍은 아니지만 넓힌 것은 맞다.
   API 는 scope 로 막히므로 구멍은 화면 층 하나다. 운영 콘솔 인증은 이 작업의 범위를
   넘으므로 여기 적어 둔다.
2. **DoD-18 을 다시 재지 않았다** — `python -m scripts.measure_delegation_scope` 는 오전
   측정 그대로다. 판정기를 부르는 쪽이 안 바뀌어 수가 바뀔 이유는 없지만, **안 쟀다는 것과
   안 바뀌었다는 것은 다르다.**
3. 위임은 여전히 **고객 단위**다(Trip 단위 아님, `bookings` 에 `trip_id` 가 없다).
4. 화면에서 고객을 찾으려면 **UUID 를 손으로 붙여 넣어야 한다.** Case 상세에서 바로 넘어오는
   링크가 있으면 좋겠지만, 고객 식별자를 화면에 더 늘리는 쪽이라 이번에는 하지 않았다.
5. 한계 값(`travel.delegation`)은 **여전히 우리가 고른 값**이다. 화면이 그 값을 보여 준다고
   값이 옳다는 근거가 되지는 않는다.
