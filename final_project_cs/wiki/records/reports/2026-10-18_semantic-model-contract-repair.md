# 시간·근처 식당 요청의 모델 계약과 API 대체 보완

최종 후보: 단위343개와 분리된 실제 DB8개, 합계351개가 모두 통과했다. 실제 모델/API 경로5개도 통과했고 운영 배포와 고객 화면 확인은 하지 않았다.

2026-10-18 12:35 KST. 담당: 일정 변경 오류 조사 대화의 Codex 하위 작업. 구현과 자체 검증을 맡았으며 독립 검토 완료가 아니다. 격리 후보만 수정했고 운영 파일·배포·고객 일정은 변경하지 않았다.

## 확인한 원인과 수정

- 새 `time_edit`·`place_search` 속성은 있었지만 최상위 JSON Schema의 필수 목록에 없어 학습 모델이 생략했다. 새 호출에서는 두 객체를 필수로 하고 none/빈 값을 반환하도록 했다. 과거 저장 결정의 누락 호환성은 유지한다.
- Ollama·API의 구조화 응답은 JSON 객체인지까지만 검사했다. 응답 전체를 JSON Schema로 확인하고, 호출자가 제공하는 현재 문장 인용·대상 별칭 검증도 기존 대체 경로 내부에서 실행한다. 필수 값 누락·형식·원문 근거 오류는 내용 오류다. 기계 장애로 누적하지 않고, 기존 API 호출 예산·시간·개인정보 가림·경로 기록을 유지한다. 예산 초과는 우회하지 않는다.
- 새 시작 시각을 구형 시작 시각 칸으로 무시하지 않고 `time_edit.time`으로 실행한다. 명시한 분만큼 뒤 항목을 옮기는 요청은 기준 항목 다음의 같은 날 미래 항목만 대상으로 삼고 예약·고정·자정·과거 보호를 적용한다. 정확한 시각은 숫자 시각이 든 인용과 기존 시각 재계산기로 대조한다.
- 종료/체류와 다른 날짜를 함께 바꾸는 기능은 이번 후보에서 지원하지 않는다. 그 날짜를 무시하지 않고 명시적으로 거절하며 해당 목표를 후속 요청에 승계하지 않는다. 동일 날짜의 체류 종료와 뒤 일정 재배치는 기존 후보 기능을 유지한다.

공유 계약은 [여행 채팅 문맥](../../external/trip-chat-context.md)의 2026-10-18 절이다. 수정 전 파일은 [_backup](../../../_backup/2026-10-18_122630_semantic-schema-contract/)에 보존했다. `jsonschema==4.23.0`을 직접 의존성으로 기록했다. 로컬 설치판은 4.23.0이며 실제 AWS 별도 프로세스에서도 해당 검증기 import와 호출을 확인했다.

## 실제 모델 검증

합성 여행의 축제·점심·전망대 3항목, 최신 버전과 유효한 미완료 목표를 사용했다. 고객 일정에 쓰지 않았다. 다음 5문장은 개발 회귀 예시이며 서비스 전체 정확도나 별도 holdout 결과가 아니다.

| 요청 | Windows 학습 모델 | AWS 기존 대체 경로 |
|---|---|---|
| 축제에서 5시까지 체류하고 뒤도 맞추기 | 원문에 없는 장소 관계로 거절 | 시간 초과 후 API, 종료17시·뒤 재배치 |

| 직전 실패 뒤 축제 뒤 일정 미루기 | 인용되지 않은 시간 근거로 거절 | 내용 오류 후 API, 유효한 직전 종료 목표 승계 |

Windows의 학습된 `tripilot-pointer:e4b-ft`, context8192를 이미 올라간 상태로 사용했다. 모델을 내리거나 다른 모델을 올리지 않았다. 실제 생성 5요청 중 2/5=40%가 기대 해석을 통과했고 3/5는 안전하게 거절했다. [실제 기록](../../../_local_checks/windows-model-20261018-122709.jsonl). 처음 전송 준비에서는 keep_alive 문자열 형식 오류로 5개 모두 HTTP400을 받았으며 모델 해석 시험으로 세지 않았다. [준비 실패 기록](../../../_local_checks/windows-model-20261018-122657.jsonl).

AWS 기존 cs 앱의 **별도 Python 프로세스**에 후보 모듈을 메모리로만 주입했다. 기존 설정과 실제 `openai_failover` 계량기(일2000/월30000)를 재사용했다. 5/5=100% 기대 해석을 통과했다. API3건(시간초과2, 내용오류1), 기존 모델 경로2건이다. 실제 응답 소요는 각8.49~12.08초다. [실제 기록](../../../_local_checks/aws-model-20261018-123043.jsonl). AWS 구형 모듈의 선택 경로 속성이 없다는 첫 준비 오류는 모델을 호출하기 전에 실패했다. [준비 실패](../../../_local_checks/aws-model-20261018-123032.jsonl).

이후 인용 시각 검증을 강화한 뒤 위 5개의 기록을 새 검증기로 재생했고 5/5를 통과했다. [추가 API 호출 없는 재검증](../../../_local_checks/aws-recorded-validation.json). API가 성공한 답에 스키마 오류 재시도를 추가하지 않으며, 기존 JSON 파싱 오류의 재시도 범위만 유지한다.

## 2026-10-18 12:41 실DB 통합 검증 준비

AWS 담당과 기존 단일 노드 안의 시험 전용 PostgreSQL Pod 1개·emptyDir·CPU100m/500m·RAM64Mi/256Mi·공유 버퍼16MB·연결10개·루프백 포트포워드만 사용하기로 경계를 합의했다. 운영 Secret·환경·고객 DB를 마운트하거나 연결하지 않는다. 스키마의 vector 확장이 필요해 기존 CI와 같은 pgvector/pgvector:pg16을 사용한다. 삭제·기존 리소스 교체·새 노드·EBS·외부 Service는 없다.

시험은 실제 chat_edit→pipeline.edit→reopen_commit→TripStore.append_version 경로를 사용하고 파이프라인·저장 함수를 목업으로 바꾸지 않는다. 미래 항목의 종료17시와 뒤 재배치, 현재 진행 중인 항목의 종료 연장, 뒤 예약/고정 또는 영업 종료 충돌 시 여행 버전·항목·알림 변화 없음, 식사 교체의 요청 기준 반경을 검증한다. 모델 의미 정답과 실제 공공 이동 정보 품질은 앞의 검증과 구분한다.


## 2026-10-18 12:47 상위 코드 검토의 실DB 재현

기존340단위+실DB6개를 한 프로세스에서 합쳐 **346/346=100%**를 확인했다. 이후 상위 검토에서 following의 reflow 표시와 새 시작의 과거 시각을 추가 점검했다. 새 이동 항목·시각 재생성은 기존 코드에서도 확인돼 그 부재를 결함으로 단정하지 않는다. 첫 route_def 단언 실패는 계산기를 꺼 어림 이동(route_def=null)을 얻은 시험 조건 때문이었다. 이동 제공자만 합성 5분 구간으로 명시하고 실제 파이프라인·저장 경로를 유지한 재현에서 이동 재생성은 통과했다.

반면 현재09:00에 미래10:00~12:00 항목을08:30~10:30으로 옮기면 중앙 저장 경로가 이를 받아들이는 결함을 확인했다. 수정 전 재현은 **1/2 통과, 1/2 실패**였으며 [기록](../../../_local_checks/db-test-20261018-124653.log)에 남겼다. 새 시작 분기에 과거 시각 거절을 추가하고, following의 명시 이동에도 reflow=True를 전달해 기존 고정 경계/전방 검증을 거치게 했다. 원래 진행 중인 일정의 종료 연장과 원래 끝난 일정 수정 금지 정책은 바꾸지 않았다. 최종 재검증 결과는 다음 기록에 덧붙인다.


## 2026-10-18 12:49 최종 실DB 결과

최종 단위 **341/341=100%**와 실제 격리 DB **8/8=100%**를 같은 프로세스에서 실행해 **349/349=100%**, 실패0·오류0·건너뜀0, 22.78초를 확인했다. 이전340개의 시험 식별자가 전부 포함됨도 XML로 대조했다. [최종 XML](../../../_local_checks/semantic-db-combined-124755.xml), [실행 기록](../../../_local_checks/db-test-20261018-124755.log). 기존 실제 모델/API 5개 출력도 최종 근거 검증기로 추가 모델 호출 없이 다시 통과했다.

실DB 검증은 미래 종료17시 고정·뒤 재배치, 진행 중 종료 연장, 뒤 고정/예약2경우, 영업종료 충돌, 축제 기준 식당 교체 반경, 기존 이동이 있는 뒤 일정의30분 이동·새 경로 연결, 종료가 미래여도 과거 시작 거절의8개다. 성공 시 버전/알림 각1개, 실패·낡은 판 재실행 시 여행 버전/전체항목/알림 변화0, 원래 버전의 항목 보존을 확인했다. 초기6개는 기존 직선거리 어림 계산 경로다. 추가 이동 시험은 이동 자료 제공자만 합성5분 응답으로 명시했고 파이프라인·검토·커밋·DB 저장기는 실제 코드다. 실제 공공 시간표 정확도 검증이 아니다.

시험용 DB와 합성 자료는 보존했고 로컬 포트포워드는 종료한 뒤 연결이 닫힌 것을 확인했다. [잔여 자원 상태](../../../_local_checks/db-resource-state.json). 기존 노드 안의 RAM64Mi요청/256Mi한도 PostgreSQL Pod1개만 남아 있으며 운영 고객 DB·Secret·외부 알림 채널과 분리돼 있다. 새 노드·EBS·외부 Service·자동화는 만들지 않았다. 데이터/리소스 삭제는 하지 않았다.

고객 화면·실제 고객 여행 변경·알림 배달은 여전히 확인하지 않았고 운영 소스 반영도 하지 않았다. 상위 담당자의 소스 차분 검토와 릴리스 통합 후 최종 고객 경로를 확인해야 한다.

최종 결과는 단위 **343/343=100%**+실DB **8/8=100%**=**351/351=100%**, 실패0·오류0·건너뜀0, 22.74초다. [최종 XML](../../../_local_checks/semantic-db-combined-125021.xml), [실행 기록](../../../_local_checks/db-test-20261018-125021.log). 앞의340개 시험을 모두 포함했고 기존 실제 모델/API5개 기록도 최종 검증기로 다시 통과했다. 포트포워드는 다시 종료하고 루프백 접속이 닫힌 것을 확인했다. 운영 소스·고객 일정은 여전히 변경하지 않았다.
