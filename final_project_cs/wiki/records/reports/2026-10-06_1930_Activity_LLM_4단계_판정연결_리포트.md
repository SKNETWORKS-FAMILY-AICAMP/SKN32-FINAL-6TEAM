# Activity LLM 4단계 — 판정 연결 리포트

## 결론

Activity Team 의 성립 판정(`activity.check_feasible`)이 이제 판정 계층을 거친다. 섀도 모드에서는 고객 결과가 규칙 모드와 완전히 같고, LLM 판정은 백그라운드에서 돌아 차이만 로그로 남는다.
실제 모델로 끝까지 돌려 확인했다. 고객 답변은 0.01초 만에 규칙 결과로 나갔다. 백그라운드 판정 5건은 11초 뒤에 끝났고, 그중 재난문자 판정에서 규칙과 다른 답(다른 지역 → 영향 없음)이 나왔다.
시험 결과는 2016 passed다. 기존 여행 시험 1370건도 그대로 통과했다.

## 바꾼 것

| 파일 | 내용 |

| `app/modules/travel_ops/activity/feasibility.py` | 휴무 · 운영시간 · 재난문자 · 실내외 판정이 `build_judge(...).judge(...)` 를 거친다. 새 단계 `_feasible_live_status`(웹)를 추가했다. 주소는 CSV `addr1`·`addr2` 에서 가져온다. LLM 판정(`source == "llm"`)일 때만 결과에 LLM 칸·근거·문구를 더한다 |

| `app/modules/travel_ops/activity/failure_codes.py` | `live_closed` · `outside_hours` |

## 정한 것

- **주소는 CSV 장소 목록에서 가져온다** (사용자 결정, 2026-10-06).
- **판정 LLM 이 없으면 실시간 운영 상태 단계를 건너뛴다.** 규칙에는 이 판정이 없어서, 불러 봐야 언제나 「모름」이다.
- **LLM 모드에서 재난문자를 판정하지 못하면 등급 기준으로 막는다.** 모름을 「막지 않음」으로 읽지 않는다.
- **LLM 모드의 「웹 공지상 휴무」와 「운영시간 밖」은 장소 때문으로 본다.** 그래서 대체 장소를 찾는다.
- **원문이 없으면 판정을 부르지 않는다.** 휴무 원문이 없을 때, 재난문자가 0건일 때, DB 실내외 값이 있을 때가 여기에 해당한다. 지금 동작과 같고, 헛 호출을 줄인다.

## 찾은 문제

- 실호출 첫 회에서 다섯 판정이 모두 `llm_error` 였다. 시험용 작업의 `run_id` 가 `agent_runs` 에 없어 감사 기록이 외래 키에 걸렸기 때문이다(`AuditWriteError` ← `ForeignKeyViolation`).
- 운영 경로는 Controller 가 `agent_runs` 를 먼저 만들므로 해당하지 않는다. Controller 밖에서 `TeamTask` 를 만드는 곳은 데모 CLI(`activity/__main__.py`)뿐이고, 이 경로는 판정 LLM 을 넣지 않는다.
- 다만 로그만으로는 원인을 알 수 없었다. 그래서 예외 종류를 로그에 남기도록 고쳤다.
