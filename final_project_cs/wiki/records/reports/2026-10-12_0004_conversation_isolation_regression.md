# 대기 업무와 새 문의의 분리·재개 회귀

답변을 기다리는 업무가 새 문의까지 가져가던 경계를 수정했고, 같은 업무 재개·토큰 보호·독립 문의를 함께 확인했습니다. 이 기록은 로컬 개발 DB와 ASGI 처리기 검증이며 운영 배포 완료가 아닙니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 대기·재개·문의 분리 회귀 | 통과 | 16/16 = 100% |
| 계약·보안·구조 관문 | 통과 | 464/464 = 100% |
| 운영 반영 | 미실시 | 0/1 = 0% |

분모 16은 신규 분리 시험 7개와 기존 재개 시험 9개입니다. 464개는 계약·보안·아키텍처 디렉터리의 별도 실행 집합입니다. 다른 실행 기록과 겹치는 시험이 있으므로 전체 고유 시험 수로 합산하지 않습니다.

## 수정한 동작

업무 ID나 재개 토큰을 명시한 답변은 같은 업무로 연결합니다. 명시하지 않은 메시지는 저장된 질문의 숫자·후보 선택·확인 형식에 명확히 맞을 때만 자동 연결합니다. 사실 질문이나 새 변경 요청은 이전 입력 대기를 소비하지 않습니다. 여러 업무에 맞는 답변은 대상을 지정하도록 409로 거절합니다. 자동 연결의 상관관계 판정은 Team의 해석·입력 검증을 대신하지 않습니다.

명시한 토큰의 만료는 기존 401 응답을 유지합니다. 자동 연결한 답변이 만료되면 Controller가 WAIT_EXPIRED를 남긴 뒤 그 메시지를 새 요청으로 처리합니다. 담당 팀이 꺼진 상태의 답변은 기존 업무·토큰을 보존하고 거절하지만, 그 팀과 관계없는 새 문의는 사용할 수 있습니다. [현재 메시지 계약](../../external/rest-endpoints/web-access.md).

최초 접수의 담당 부재 후 같은 요청을 재시도해 같은 업무에서 한 번만 적용하는 시험도 포함합니다. 초기 실행 계획·동시 생성·원문 해시·활성 실행 경합의 전체 검증은 core 담당의 별도 기록과 최종 운영 후보 검증으로 구분합니다. 이번 16개 통과를 그 모든 경계의 증명으로 확대하지 않습니다.

## 실제 재현·실행 기록

- [수정 전 2차 로그](../evidence/2026-10-11_1936_team_plugin_implementation/conversation-isolation-before-v2.log): 6개 실패·1개 통과. 독립 문의 가로채기·자동 연결 만료·담당 부재에 따른 새 문의 차단과 최초 접수 보존 문제를 확인했습니다. 이전 1차 로그의 시험 등록표 복사 오류는 제품 결함 증거로 사용하지 않습니다.
- [분리 기능 1차 통과](../evidence/2026-10-11_1936_team_plugin_implementation/conversation-isolation-after-v1.log): 6개 통과·1개 선택 제외, 208.62초. 실행 중 core 초기 재시도 구현이 바뀌었으므로 최종 소스 일괄 검증으로 부르지 않습니다.
- [최종 묶음 1차](../evidence/2026-10-11_1936_team_plugin_implementation/conversation-final-joint-v1.log): 15개 통과·1개 실패, 123.63초. 아래 시험 집계 가정을 바로잡았습니다.
- [최종 묶음 2차](../evidence/2026-10-11_1936_team_plugin_implementation/conversation-final-joint-v2.log), [JUnit](../evidence/2026-10-11_1936_team_plugin_implementation/conversation-final-joint-v2.xml): 16/16 통과, 70.52초.
- [필수 관문 6차](../evidence/2026-10-11_1936_team_plugin_implementation/required-gates-v6.log), [JUnit](../evidence/2026-10-11_1936_team_plugin_implementation/required-gates-v6.xml): 464/464 통과, 100.85초. 기존 이동 기록 도구의 문서 문자열 invalid escape 경고 6건은 남아 있습니다.

## 업무 생성 기록과 일정 적용을 따로 집계

최종 묶음 1차의 실패는 새 멱등 생성 기록 `case.create`까지 일정 변경 횟수로 세어, 성공 action 총수가 1개라고 기대한 시험 가정 때문이었습니다. 실행 기록과 적용 결과를 대조하면 `agent_runs` 1개, `applied_actions` 1개였으며 일정 중복 적용은 재현되지 않았습니다.

[기존 재개 시험](../../../tests/e2e/test_web_conversation_resume.py)은 성공 action을 종류별로 읽어 `case.create: 1`, `itinerary.apply: 1`을 각각 요구하도록 보정했습니다. 이후 동일 요청 3회 재전송에도 일정 버전 총 2개·변경 알림 1개라는 기존 검증을 유지했습니다. 제품 코드를 이 실패 때문에 수정하지 않았습니다.

## 보존·확인 경계

[구현 전 백업](../../../legacy/team_plugin_lifecycle/2026-10-11_2325_conversation_isolation/), [문서 백업](../../_backup/2026-10-11_2332_conversation_contract/), [재시도 계약 추가 전 백업](../../_backup/2026-10-11_2356_initial_retry_contract/), [시험 집계 보정 전 백업](../../../legacy/team_plugin_lifecycle/2026-10-12_0003_creation_ledger_assertion/)을 보존했습니다. 실패 로그를 삭제하거나 성공 로그로 교체하지 않았습니다.

모델·이동 계산 제공자는 명시적인 합성 시험용입니다. 실제 Controller·Registry·DB·HTTP 처리 경로를 검증하지만 실제 모델 해석 정확도·외부 이동 데이터 정확도·운영 브라우저 화면을 측정하지는 않습니다. 이후 활성 실행 경합 수정과 최소 운영 후보의 이식 검증은 별도 시점의 근거로 남깁니다.

mock 서버 시험(화면 반응): 이 기록 범위에서는 안 했습니다.

실서버 확인(서버 응답): 로컬 개발 DB와 ASGI 처리기로 합성 여행 요청을 검증했습니다. x600 서버의 cs 프로젝트 서버에 새 코드를 반영하거나 재기동하지 않았습니다.
