# 전용 QA 계정 한도 예외와 실제 예약 보존 확인

2026-10-17 사용자 지시로 기존 로그인 계정을 요청하던 단계를 전용 QA 계정 생성으로 바꾼다. 기존 게스트 여행은 삭제·이전하지 않는다.

## 원인 확인·계약

- 기존 게스트 여행 한도는 고객 행 잠금 뒤 총 여행 개수로 검사한다. 관리자 채팅 무제한 예외는 있으나 다른 웹 횟수와 게스트 총 개수에는 적용되지 않는다.
- 구현 전 [QA 예외 계약](../../external/qa-usage-exemption.md)을 작성했다. 일반 고객·인증·소유권·전체 서비스·외부 제공처 예산은 유지한다.
- 원본 코드 대신 최신 매니저 판에서 필요한 파일만 새 격리 사본으로 읽었다. 원본 동기화·삭제는 하지 않았다.
- 구현 담당은 이 세션, 매니저 검토는 기존 커밋 세션에 요청한다. 아직 코드 시험·배포·QA 생성·실제 등록은 미완료다.

## 19:44 격리 구현·검증

- 고객 기록의 엄격한 boolean 예외, 감사 가능한 부여·해제 함수, 웹 고객·주소 횟수 예외, 게스트 총 개수 예외를 구현했다. 전체 서비스 예산·일반 고객·날짜·차단·점검 경계는 유지한다.
- 실제 운영 앱 이미지의 별도 프로세스에서 새 tenant를 만들고 마지막에 롤백했다. 신규 예외 검사 17개와 기존 관리자 정책 11개, 합계 **28/28 = 100%** 통과(1.67초). 제공처 재호출은 하지 않았다.
- 첫 실행은 격리 컨테이너가 DB와 다른 네트워크에 붙어 준비 오류 28건이었다. 공통 네트워크로 수정한 후 위 결과를 얻었다. 이 첫 실패도 보존한다.
- 변경 5개 Python 파일의 ruff F·E9 통과. 계정 생성 도구는 새 자격 파일을 독점 생성하며 기존 파일이 있으면 새 계정을 만들지 않는다. 키 원문은 출력하지 않는다.
- 아직 실제 QA 계정 생성·변경 배포·그 계정의 여행 등록은 하지 않았다. 매니저에 검토·배포를 요청한다.

## 19:51 실제 계정·첫 등록

- 전용 QA 고객 하나를 새로 생성하고 해당 사용자 기록에만 예외를 부여했다. 기존 게스트 고객·여행은 이전·삭제하지 않았다. 자격 파일은 비공개 0600이며 키 원문을 코드·문서·증거에 넣지 않았다. 공개 API의 예외 코드 배포는 아직 대기다.
- 공개 주소의 Python HTTP 요청은 Cloudflare 1010(브라우저 서명 거절)으로 403이었다. 같은 방식 재시도나 보호 설정 변경은 하지 않았다. 이후 x600 서버의 cs 프로젝트 API 컨테이너 안에서 정상 QA 사용자 키로 실제 HTTP를 호출했다. 이 내부 경로의 성공을 공개 프록시 통과로 보고하지 않는다.
- 본인 여행 목록 GET 200, 기존 다른 게스트 접수 GET 404. 예약 일정 읽기→자동 추천→첫 여행 등록→다시 열기→자동 추천→변경 없이 완료를 확인했다. 예약번호 KY-20931·19:00~20:30·예약 표시가 보존됐고 마지막 완료는 changed=false, version=1이었다.
- 고객이 직접 보낸 시각 수정은 허용됐다. 현재 계약은 자동 추천 보호와 고객의 직접 수정을 구분하므로 이를 결함으로 확정하거나 직접 수정을 새로 막지 않았다. 시험에서 바꾼 시각은 원값으로 되돌린 후 등록했다.
- 공개 브라우저에서도 새 QA 여행 계획서의 19:00~20:30 N서울타워와 일정 버전 1을 확인했다. [화면](../evidence/2026-10-17_qa-usage-exemption/qa-registered-plan.png) · [토큰을 제외한 실제 근거](../evidence/2026-10-17_qa-usage-exemption/qa-first-registration-proof.json).
- 남은 일: 예외 코드의 매니저 검토·배포, 두 번째 여행 등록(개수 예외 실증), 숙소 후속 배포 뒤 기본 예시의 숙소·경로·수동 저장 재검증.

## 19:52 적용 전 실제 개수 제한

같은 QA 계정에 두 번째 여행 등록을 요청하자 현재 공개 운영 코드에서는 403 guest_trip_limit(cap=1, existing=1)이었다. 실제 개수 예외가 아직 운영 코드에 적용되지 않았음을 확인했다. 배포 뒤 동일 request_id와 동일 내용으로 다시 요청하여 변화 여부를 비교한다. 기존 첫 여행은 유지한다.
