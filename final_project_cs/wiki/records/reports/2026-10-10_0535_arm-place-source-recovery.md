# Oracle ARM 장소 기준 자료·검색 키 복구

Oracle ARM의 추천 코드는 있었지만 장소·식당 기준 DB가 비어 있어 DB 추천도 후보를 내지 못했다. 사용자 승인에 따라 사실 자료와 검색 키를 복구했고, 기존 일정의 주요 장소 8곳을 찾았다. 별도 활동 추천 결함은 로컬 수정·시험까지 마쳤으며 ARM 코드 반영은 남았다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 주요 장소 좌표 조회 | 실제 조회 성공 | 8/8 = 100% |
| 기존 일정 좌표 | 호텔 이름 두 항목 미정 | 8/10 = 80% |
| 활동 후보 누락 수정 시험 | 로컬 통과, ARM 미반영 | 7/7 = 100% |
| 배포·호출 제한 도구 시험 | 통과 | 3/3 = 100% |

## 문제와 적용 범위

[실측] 이전 진단 당시 Oracle ARM의 `places`·`place_catalog`·`catalog_hours`·`dining.dn_place`·`dining.dn_source_record`는 모두 0행이었다. TourAPI·Kakao 검색 키도 없었다. DB와 모델 연결의 건강 상태가 정상이어도 이 조합에서는 장소를 확정할 수 없다. 키 누락만으로 원인을 설명한 이전 보고는 부족했다.

일정 접수의 이름 조회는 `places`와 외부 검색·식당 자료를 사용하며, Activity 대안 확대는 `place_catalog`와 저장된 운영시간을 사용한다. Dining 대안은 식당 DB를 읽는다. 세 경로의 자료 의존성을 구분했다.

[실측] 적용 실행판은 `210b020067a1e42f2622262adeb60d1f3d371668`이다. 새 모델로 바꾸거나 모델 품질 합격을 선언한 작업이 아니다.

## 복구와 API 한도

[실측] 기존 x600 서버의 여행 사실 자료만 14개 표에 맞춰 추가했다. 고객 여행·접수·대화·키·별칭·사진·소개글은 가져오지 않았다. 기본 테넌트에 맞춰 변환했고 기존 행 삭제나 외래키 우회는 하지 않았다.

| 표 | 적용 후 행 수 | 의미 |
|---|---:|---|
| `places` | 1,247 | 공용 장소 |
| `place_catalog` | 7,996 | 관광정보 목록 |
| `catalog_hours` | 1,248 | 운영시간 자료 |
| `dining.dn_place` | 1,228 | 식당 |
| `dining.dn_source_record` | 1,617 | 식당 출처 기록 |

표끼리 같은 장소가 겹치므로 이 행 수를 더해 고유 장소 수라고 하지 않는다. 식당 인허가 표 `dn_license_shop`은 원본에도 0행으로, 이번 복구 뒤에도 0행이다. 전체 가능한 자료를 모두 복제한 것은 아니다. 압축 전송본 SHA256은 `581b7aa46c6512ac1d18e4f0b8010bc18e78d37e4cd946d223e349ffda595350`이다.

[실측] 검색 키는 Oracle ARM의 비공개 환경 파일에만 넣었다. API별 프로젝트 호출 제한은 다음과 같다.

| 환경 | 하루 상한 | 월 상한 |
|---|---:|---:|
| 로컬 개발 서버 | 450 | 13,000 |
| x600 서버의 cs 프로젝트 서버 | 450 | 13,000 |
| Oracle ARM의 cs 프로젝트 서버 | 100 | 3,000 |
| 알려진 세 앱 합계 | 1,000 | 29,000 |

TourAPI와 Kakao 각각의 상한이다. 제공사 계정 전체의 상한을 변경한 것은 아니며, 직접 실행하는 별도 스크립트·다른 소비자는 이 합계 밖이다. ARM은 API·worker가 DB의 사용량을 공유하고 DB 오류 시 외부 호출을 거절한다. 기존 로컬·x600의 DB 오류 정책은 변경하지 않았다. TourAPI의 일 구분은 한국 시간, Kakao는 UTC다.

[실측 05:33:29 KST] TourAPI 하루 사용 24/100, 월 24/3,000; Kakao 하루 3/100, 월 3/3,000이었다. 이후 실험의 현재 사용량으로 읽지 않는다. 두 API의 해당 관측 실패·한도 거절은 각각 0회였다.

새 develop 이미지에도 제한이 유지되도록 [제한 설정 준비 도구](../../../deploy/arm/prepare_guardrails.py)와 [배포 실행기](../../../deploy/arm/deploy.py)를 연결했다. 새 이미지 원본 설정에서 필요한 제한만 적용하고 이전 설정은 백업한다.

## 실제 확인

[실측] 외부 호출 없이 세 지점의 반경 700m 식당 후보가 각각 18·11·5곳 나왔고 이름 조회도 3/3 성공했다. 이는 후보 보유 확인이며 추천 정확도 평가가 아니다.

[실측] 경복궁·광장시장·국립중앙박물관·N서울타워·북촌한옥마을·인사동·창덕궁·청계천 8/8의 좌표를 실제 검색했다. 경복궁은 저장 DB, N서울타워는 Kakao, 나머지는 TourAPI에서 찾았다.

[실측] 신고된 기존 접수는 원래 판을 보존하고 장소 값만 새 판 2에 저장했다. 날짜·시간·제목·예약 등 다른 값이 변하지 않았음을 비교했다. 05:42:15 KST 별도 제한 컨테이너에서 실제 앱의 확인 결과 계산을 완료했고 오류는 없었다. 좌표 8/10, 확인 필요는 10곳에서 2곳으로 줄었다. 남은 두 항목은 이름이 특정되지 않은 호텔로 임의 숙소를 지정하지 않았다. 이동 8구간 결과의 근거는 시간표와 어림값이 섞인 상태다.

실서버 확인(서버 응답): Oracle ARM DB 후보·실제 검색 8/8·실제 앱 확인 함수 성공·API 건강 응답을 확인했다. 브라우저 화면 재검증은 도구 초기화 오류로 미확인이다. HTTP 정상과 모델 정답을 혼동하지 않는다.

## 활동 후보 누락의 별도 수정

[실측] 가까운 활동을 먼저 자른 뒤 운영시간을 확인하면 뒤쪽의 유효 후보를 놓쳤다. [결함 기록](debugs/2026-10-10_0526_activity-hours-filter-after-limit.md)과 [수정 코드](../../../app/domains/travel_ops/components/places/catalog_pool.py)를 연결한다.

검증 명령: `python -m pytest tests/integration/travel/test_activity_catalog_pool.py tests/integration/travel/test_activity_hours_before_limit.py -q`. 실제 로컬 DB와 시험용 관광정보 응답을 쓰는 통합 시험 7/7 통과. 원래 코드로 새 회귀 시험을 실행하면 1/1 실패해 결함 재현도 확인했다. 첫 10곳의 시간이 없어도 11번째 미술관을 추천하며 고객 요청에서 추가 외부 호출을 하지 않는 시험이다. ARM·x600 코드에는 아직 반영하지 않았다.

배포 도구 검증: `python -m pytest deploy/arm/test_deploy.py deploy/arm/test_prepare_guardrails.py -q`, Linux 환경 3/3 통과. mock 서버 화면 시험은 이번 범위에서 실행하지 않았다.

## 진단 중 API 재시작과 복구

[실측] 05:34:58 KST, 실행 중 API 컨테이너 안에서 전체 앱을 다시 초기화하는 진단을 추가 실행해 1,536MiB 메모리 상한을 넘었다. 커널이 기존 API와 추가 Python을 종료했다. 진단 방식의 잘못이며 정상 단일 API의 메모리 부족으로 일반화하지 않는다. API는 자동 재시작했고 05:42:35 KST 건강 응답 정상·재시작 수 1을 확인했다.

영향받은 질의 회차는 8/11 = 72.73%로 보관했다. 나머지 3개는 연결 종료·접속 오류이며 분모에서 빼지 않았다. 이 회차의 첫 질의는 HTTP200이지만 모델 JSON 오류로 `decision_failed` 응답이었다. 기존 HTTP 계약 검사는 이를 통과로 세므로 8/11은 답변 정확도가 아니다.

추가 진단 프로세스를 제거한 뒤, 해당 장애로 막힌 말투 변경 프로필만 사유·상태 백업을 남기고 다음 대기 작업에서 재개하도록 했다. 기존 실패 회차는 바꾸지 않았다. 그보다 앞서 실패했던 다른 두 프로필은 원인 수정 전 반복하지 않도록 차단을 유지했다. 같은 API 컨테이너 안에서 전체 앱 진단을 다시 띄우지 않는다. 이후 확인 결과 계산은 독립 메모리 1,536MiB·CPU 0.3코어의 일회성 컨테이너에서 성공했다.
