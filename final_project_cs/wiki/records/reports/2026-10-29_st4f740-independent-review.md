# ST4F-740 달력 정합성 독립 검토

후보의 달력 수정은 재현한 결함을 해결합니다. **통합·배포 판정은 HOLD**입니다. 기존 XML 보존과 보안 관문 실패 사이의 충돌을 해소하거나 우회하지 않았습니다. 원본 제품 변경·트래커 변경·push·배포·삭제는 모두 0건입니다.

검토자는 후보 작성과 별도인 이번 Codex 세션입니다. 루트·CS AGENTS, CS RULE, 양쪽 wiki 입구, 개발 역할, 코드 경로, 현재 web-intakes 계약과 실제 Hermes `_coord` NOTICE 60개를 확인했습니다. 기존 담당·EKS·724·734 예약은 인수하지 않았습니다. 이번 검토는 입력·출력 필드, 권한, DB 스키마, 모델·프롬프트를 바꾸지 않습니다.

## 검토 대상과 재현

`scratch/st4f740-review-20261029/repo`를 새로 만들고 후보 **6573e2067d49787257de22a132a8826ea3aad2e9**에 고정했습니다. 기준은 **fab3da50ab970a7d8c79ed65c1df2e666abc1cd0**입니다. 제공 bundle의 prerequisite·형식을 검증하고 새 격리 사본에 fetch하여 bundle HEAD **e96347fd7b222766d89dd83e55c649aea7a58763**가 제품 후보를 포함함을 확인했습니다. 최신 원격 전체 통합을 검증한 결과는 아닙니다.

기준 날짜를 2026-10-29로 고정한 기준판 실행에서 `--02-29`는 2027-02-28, 그 다음 날은 2027-03-01로 왜곡됐습니다. `--04-31`은 2027-04-28, 다음 날은 2027-04-29였습니다. `2026-02-29`는 ValueError였습니다. 3/3 = **100%** 재현했습니다.

후보는 가능한 실제 월·일만 선택하고, 잘못된 명시 날짜는 null/unknown·확인 필요로 둡니다. 유효하지 않은 날짜를 첫날 앵커로 사용하지 않으며, 후속 유효 앵커·출발일 계산은 유지합니다. 조립기의 추가 검증은 원문 머리줄에서 불가능한 날짜가 다시 들어오는 경로를 막습니다. 날짜 해석기만 고치면 충분하지 않다는 점을 조립기 변이 실패로 확인했습니다.

## 의미와 한계

- 해 없는 2월 29일은 오늘을 포함한 다음 실제 윤일입니다. 2028-02-29 당일, 그 다음 날, 2097→2104의 8년 간격과 400년 주기·366개 월일 보존 시험을 확인했습니다. 해를 채운 값은 `year_filled`·확인 필요가 유지됩니다. 명시된 과거의 유효 날짜는 미래로 바꾸지 않습니다.
- 날짜는 서울 여행의 달력 날짜입니다. pipeline은 DB에서 받은 시각을 Asia/Seoul로 변환한 뒤 날짜를 전달합니다. 독립 추가 시험은 UTC 14:59/15:00 경계와 윤일 다음 날을 서울 날짜로 변환해 실제 `read_source`에 전달했습니다. 이 시험은 그 변환을 포함한 실서비스 시계 통합 시험은 아닙니다.
- 규칙 입력은 한국어 월일, ISO 날짜, 월/일 표기입니다. `2/29`를 월/일로 읽는 기존 의미를 유지합니다. 사용자 locale에 따라 일/월로 바꾸거나 모든 언어·시간대를 지원한다고 해석하면 안 됩니다. 조립 몸통의 기존 locale `ko`와 시각 처리에는 변경이 없습니다.
- 명시된 유효 과거 일정 전체는 기존 `all_dates_in_past` fatal 경로에서 막히며, 일부 과거+미래는 review로 갑니다. 새 전용 DB/API에서 기존 두 경로를 재확인했습니다. 날짜 미확정과 해 없는 날짜를 명시된 과거 일정으로 간주하지 않습니다.
- Python 최대 연도에서 다음 윤일이 없으면 null로 안전하게 끝나는 추가 시험도 통과했습니다. 이는 모든 비정상 day offset·최대 날짜 산술의 포괄 검증을 뜻하지 않습니다.

## 새 실행 결과

새 PostgreSQL 데이터 디렉터리는 `scratch/st4f740-review-20261029/pgdata`, 포트는 56140, DB는 calendar_test입니다. migration·프롬프트 등록을 새로 실행했습니다. 실제 FastAPI TestClient와 실제 PostgreSQL을 사용했으며 외부 모델·관광·이동 제공자는 시험 대역입니다. 고객 DB·실서비스·화면·실모델 수락이 아닙니다.

추가 시험 작성 때 PowerShell stdin 인코딩으로 한글이 `?`가 됐습니다. 최초 locale 시험은 2/6 = 33.3% 통과·4실패였고, 최초 독립 confirm의 문장은 의도한 한글 원문이 아니었습니다. 새 시험을 Unicode 이스케이프로 고쳐 위 31건을 재실행했습니다. 최초 로그도 보존하며 제품 결함이나 유효한 한글 confirm 증거로 세지 않습니다. DB 준비 helper의 출력 처리 AttributeError도 보존했고 migration·등록을 별도 명령으로 다시 성공시켰습니다.

## 보존·트래커·인계

역사 XML은 원본·후보 간 바이트가 같습니다. 원본 scanner와 원격 기준 scanner의 allowlist 차이는 그대로이며 두 scanner가 동일하다고 주장하지 않습니다. 원본 scanner와 XML의 시작/종료 SHA256은 각각 일치합니다. 새 보안 실패 원문은 git 밖 scratch에만 두고 이 보고서에는 집계만 기록합니다.

TeamFlow를 상태 4×유형 4의 16분할 GET으로 새 조회했습니다. 중복 없이 **미완료 103/689 = 14.9%**, ST4F-740은 high/review입니다. 작성 세션의 생성 후 689개와 전체 객체를 비교해 추가·제거·변경 각각 0건입니다. 이 세션은 이슈를 닫거나 수정하지 않았습니다.

한 일: 지침·wiki·coord 확인 → 새 격리 사본·bundle 검증 → 기준판 3결함 재현 → 새 PG/API → 등록 거부·과거 일정·locale/서울 경계 추가 시험 → 회귀·계약·보안 → 두 변이와 후보 복구 → 원본 보존·현재 트래커 대조 → 보고·인계입니다. 실행 스크립트·새 시험·원시 로그·DB 데이터는 모두 `scratch/st4f740-review-20261029`에 보존합니다.

다음 담당자는 mandatory HOLD를 유지하고 보존 결정과 보안 검사 실패의 해결 절차를 별도 확정해야 합니다. 이후 실제 통합 대상 tip에서 검증하고 환경별 수락을 확인해야 합니다. 이번 결론을 운영 반영이나 ST4F-740 종결 승인으로 사용하지 않습니다.
