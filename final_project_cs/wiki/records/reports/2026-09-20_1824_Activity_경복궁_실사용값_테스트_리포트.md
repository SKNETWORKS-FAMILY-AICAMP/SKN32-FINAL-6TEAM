# Activity — 경복궁 실사용값으로 TourAPI 대조 테스트 완성

## 1. 작업 목표

사용자가 "1. 임의로 가져온 장소/시간, 2. TourAPI 실제 운영시간을 대조해 성립하는지"를 요청. 사전 확인 결과 사용자가 **현재 원칙(자동 판정 금지) 유지 + 테스트만 추가**를 선택 — `1`·`2`를 나란히 놓고 `feasible`이 그 내용과 무관하게 유지되는지 보는 테스트로 확정. 사용자가 실제 값(경복궁 · 2026-10-03 15시 · "09:00~18:00" / "매주 화요일 휴무")을 제공해 템플릿을 채웠다.

## 2. 실제 수행 내용

변경 파일: `tests/unit/travel/test_activity_tour_operating.py`

- 상단 import에 `datetime`·`timedelta`·`timezone` 추가(고정 시각 KST 구성용)
- `test_a_real_place_and_schedule_stays_informational_only`의 플레이스홀더를 실제 값으로 채움:
  - 1. 요청 장소·시각: `경복궁`, `datetime(2026, 10, 3, 15, tzinfo=KST)` (KST=UTC+9)
  - 2. TourAPI 운영시간 원문: `usetime_text="09:00~18:00"`, `restdate_text="매주 화요일 휴무"`
- 디스크에 남아 있던 중간 편집값(`requested_place_name = "2928947"` — TourAPI contentid로 보이는 값이 장소명 자리에 잘못 들어가 있었다)을 사용자가 준 값으로 덮어썼다.

이 테스트는 **feasible을 계산하지 않는다** — `_show()`로 요청 시각과 TourAPI 원문을 나란히 출력해 사람이 눈으로 대조할 수 있게 할 뿐이고, 자동 판정 금지 원칙이 실사용 값에서도 유지되는지만 assert한다.

## 3. 검증 방법과 결과


## 4. 미해결 이슈·다음 작업 제안

없음 — 사용자가 명시적으로 "자동 판정 로직은 만들지 않는다"를 선택했으므로 이 이상의 구현은 범위 밖이다. 실제 usetime/restdate 자동 대조가 필요해지면 그건 별도의 명시적 결정이 먼저 있어야 한다(자연어 파싱의 위험성은 `tour_api.py` 자체 문서화 참고).
