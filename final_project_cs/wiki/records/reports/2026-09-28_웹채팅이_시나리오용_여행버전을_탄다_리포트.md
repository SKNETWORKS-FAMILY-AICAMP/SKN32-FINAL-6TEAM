# 웹 채팅이 「시나리오용 여행 버전」을 탄다 — 현황과 통합 계획 (2026-09-28)

## 결론

- 웹 화면의 채팅(`POST /v1/web/trips/{id}/messages`)은 **Case 버전이 아니라 시나리오용 여행 버전**(`trip_messages.handle_trip_message` → `TripDesk`)으로 처리된다.
- 에이전트가 `POST /v1/cases`(여행을 가리키는 `subject_ref`)로 같은 말을 하면 **Case 버전**(분류 → Controller → Team `*.itinerary` · `*.itinerary_question`)이 처리한다.
- 그래서 **같은 질문에 대한 답을 만드는 코드가 두 벌**이다.
- 2026-09-28 에 고친 채팅 답(늘 답하기 · 여행 사실 답 · 취소·이동 규정 검색)은 **시나리오용 쪽에만** 들어갔다.
- 방향: **Case 버전으로 합친다.** 웹은 「누구의 어느 여행인가」만 확인하는 입구로 남긴다.

## 두 버전 (이름은 2026-09-15 사용자 지정)

| | Case 버전 | 시나리오용 여행 버전 |
|---|---|---|
| 흐름 | 접수(`open_case`) → 분류 → Controller → Team → 코어가 대조·적용·통지 | `TripDesk` 가 같은 계산(`itinerary_changes.py`)을 Team·Case 처리 없이 바로 적용 |
| 누가 쓰나 | `/v1/cases` · 운영 감시(`run_sweepers` 기본 `trip_cases`, 09-18 부터) | `/v1/trips/{id}/messages` · **`/v1/web/trips/{id}/messages`** · 시나리오 모드 기본값 · `--only trip` |
| v11 설계와 | 맞다(Case 를 Team 이 처리) | 시연용 지름길 |

★09-18 에 운영 감시를 Case 버전으로 옮겼다(`2026-09-18_1500_Case버전_남은작업5건_처리_리포트.md` 3번).
그 뒤 09-24 에 웹 입구(D-020 결정 B)를 만들면서 채팅을 **시나리오용 쪽 함수에 연결**했다. 방향이 거꾸로 됐다.

## 웹 입구를 따로 둔 것 자체는 맞다

- `/v1/cases` · `/v1/trips` 는 **서버용 scope 키**로만 열린다. 이 키는 테넌트 전체 권한이라 브라우저에 둘 수 없다.
- 웹은 **사용자 식별 키**(`X-User-Key`, 마이그레이션 025)로 **그 사용자 본인의 여행만** 연다.
- 입구가 둘인 것은 맞다. 문제는 **입구 안쪽의 처리까지 둘**이라는 것이다.

## 2026-09-28 에 시나리오용 쪽에만 들어간 것

| 무엇 | 파일 |
|---|---|
| 채팅은 어떤 결과든 답 문장(`answer`)을 싣는다. 질문은 일정 사실 + 문턱(0.55)을 넘은 규정 조각, 잡담은 할 수 있는 일 | `trip_replies.py` · `trip_messages.py` |
| 여행 사실 질문(하루 요약 · 일정 상세 · 다음 일정 · 예약 표시 · 주소 · 운영시간 · 이동)은 규정 검색 없이 여행 기록으로 | `trip_facts.py` |
| 규정 질문의 검색 갈래에 취소·이동 추가 | `trip_replies.QUESTION_SCOPES` |
| 실패·사람 확인 전이에도 답을 Case 에 남긴다(중복 요청이 앞 답을 다시 싣는다) | `trip_messages.py` |

Case 버전의 질문 capability(`itinerary_team._answer_question`)는 이것들을 모른다.
- 에이전트가 `/v1/cases` 로 「일정 상세 알려 주세요」라고 하면 옛 규정 검색 답이 나온다.
- 취소 규정 갈래도 빠진 채다.
- (코드 읽기로 확인했다. `/v1/cases` 로 실제로 보내 본 것은 아니다.)

영업시간(`place_hours.py`)은 판정기 · 생성기 · 새벽 확인에 들어갔다. **두 버전이 함께 쓰는 층이라 양쪽에 다 적용된다.**

## 통합 계획

1. **답 규칙을 Case 버전 Team 으로 옮긴다.**
   - `trip_facts` · `trip_replies` 의 규칙을 `itinerary_team` 의 질문 capability 가 부른다.
   - 사실 질문은 Team 이 여행 기록으로 답한다(side effect 없음 — 제안이 아니라 답).
2. **웹 채팅 입구를 Case 버전에 연결한다.**
   - `/v1/web/trips/{id}/messages` 는 키로 고객을 확인하고 본인 여행인지 본다.
   - 그다음 `/v1/cases` 와 **같은 `open_case`(subject_ref = trip)** 로 접수하고, Controller 실행을 **기다린 뒤** Case 의 답을 돌려준다.
   - 응답 모양(`status` · `answer` · `basis` …)은 지금 그대로 둔다 → ui 세션의 화면 · 가짜 서버(`frontend/apps/web/tests/live/stub-server.mjs`)가 바뀌지 않게.
3. **에이전트 입구 `/v1/trips/{id}/messages` 도 같은 방식으로 연결한다.**
4. **`handle_trip_message` 는 시나리오 모드에서만 쓴다.** 이름대로 「시나리오용」으로 남긴다.
5. **증거.** 같은 문장을 웹 · `/v1/cases` 로 보내 같은 답이 나오는지 시험한다(`tests/scenario/test_case_version_day.py` 방식). 화면 문장 기준 시험(`tests/e2e/test_web_api.py`)은 그대로 통과해야 한다.

### 정할 것 · 조심할 것

- `/v1/cases` 는 접수만 먼저 답하고 처리는 뒤에서 돈다. 웹은 **서버가 기다렸다 답하게** 한다(화면 계약 유지). 모델 호출이 길면 응답이 늦어진다 — 지금도 같은 모델 호출을 동기로 한다.
- 시나리오 모드 엔진의 기본값은 시나리오용이다. 바꾸지 않는다(시연 재현성).
