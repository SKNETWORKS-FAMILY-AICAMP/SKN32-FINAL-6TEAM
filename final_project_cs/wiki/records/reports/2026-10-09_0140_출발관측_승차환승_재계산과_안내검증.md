## 원인과 실제 변경

기존 안내는 저장한 planned.eta_min을 읽었다. [고정 입력 재현](../evidence/2026-10-09_0122_출발시점_버스재검증/controlled-comparison.json)에서 저장 시점의 모델은16분이다. 현재 접근6분 이후 탈 수 있는 차량은7분 뒤의 둘째 차량이며, 현재 승차 시각대의 이동 소요는3분에서12분으로 바뀐다. 옛 대기5분을 현재1분으로만 바꾸면12분, 현재 구간 전체를 검증하면21분이다. 이 수치는 고정 시험 프로파일이며 실제 서울 운행 측정이 아니다.

[출발 관측 계산](../../../app/domains/travel_ops/instances/mobility/engine/departure_observer.py)은 현재 양끝 좌표·선택 옵션·내부 구간과 검사 입력·동행 조건·시간표/규칙 판을 검증한다. 현재 시각은 분 올림하고 접근/이탈 걷기를 포함한다. 새벽4시 운행일 경계와 지난/너무 먼 목표를 검사한다. 첫 구간이 정확 ID/순번을 가진 버스일 때 현재 접근 이후 차량의 예측을 내부 인자로 전달한다. 현재 시각을 다른 날짜나 출발 역산에 재사용하지 않는다.

[요청별 판정](../../../app/domains/travel_ops/instances/mobility/engine/runtime.py)과 [버스·환승 판정](../../../app/domains/travel_ops/instances/mobility/engine/verify_time.py)은 해당 승차만 바꾸고 승차 시간대 프로파일·후속 접근/환승·첫차/막차·최악 가정 여유를 다시 계산한다. 후속 미래 버스에는 현재 첫째/둘째 차량을 고정하지 않는다. 지하철이 먼저인 경로는 현재 버스 조회를 생략한다. 예측을 고객 case JSON으로 주입할 수 없으며 요청 복사본에만 둔다.

[안내 소비](../../../app/domains/travel_ops/components/watch/trip_reminders.py)는 선택적으로 주입한 콜백의 realtime/model_revalidated 결과만 사용한다. 원 Item은 바꾸지 않고 출발·도착·소요를 현재 값으로 표시하며 원 관측 근거를 payload에 남긴다. 문맥 변경/늦음은 held, 모델도 값을 못 내면 fatal로 구별해 낡은 안내를 발행하지 않는다. 콜백을 안 꽂은 기존 호출은 기존 동작이다. 운영 조립이 아직 이 콜백을 꽂지 않으므로 배포 고객 알림 연결 완료로 세지 않는다.

## 오늘까지 확인한 문헌과 전제

[GTFS 공식 기준](https://gtfs.org/documentation/realtime/reference/)의 반복 stop_id에 대한 stop_sequence 구분과 예측/관측·불확실성 구분을 다시 확인했다. 서울 API의 시각·정확도를 GTFS가 보장한다는 뜻은 아니다. [동적 재계획 연구](https://arxiv.org/html/2505.14193v1) §2.1/2.2는 선행 도착+환승 시간≤후속 출발을 요구한다. 그 성립 조건에 맞춰 원 구간을 새 시각으로 다시 검증했지만 논문의 전체 후보 최적화·push 알고리즘을 구현한 것은 아니다. 현재 경로 검증과 경로 전체 재계획은 별개다.

[자료 등록부v5](assets/2026-10-09_mobility_research_v5/research-register.json)는 확인 범위와 미적용 전제를 남겼다. 잘못 열린 무관한 논문1개는 근거에서 제외했다. 문헌 전수검색을 주장하지 않는다. 이번 회차의 지도 개발자 API·새 교통 API 호출·신규 웹 경로 표본·커밋·푸시·배포·외부 알림 전송은0회다.
