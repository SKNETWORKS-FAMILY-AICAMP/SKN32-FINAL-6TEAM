# 계획 읽기 실패인데 「계획을 다 읽었어요」·다음 단추가 뜨던 결함 수정 — 2026-10-26

## 사용자 보고

「이거 이렇게 완료가 안 되었는데 다음 화면 뜨는 버그를 같이 수정해서 배포해」 + 모바일 폭 스크린숏:
「계획을 확인하고 있어요」, 막대 6칸 중 「일정 읽기」 1칸, 「8/9줄 · 15초째」, 그런데 「✓ 계획을 다 읽었어요」 ·
「이제 자동으로 넘어가지 않아요.」 · 질문 카드(누구와 1/4, 친구) · 켜진 「읽어 온 계획 확인하기」.

## 원인 (실측)

- x600 DB 읽기 전용 조회(12:5x KST): 보고 시각 직전 접수 `cba8a775…` = `status fatal · stage fatal · fatal_code reading_model_failed`(12:47:54), 검사 저장본 0.
  같은 6시간 안 `reading_model_failed` 3건. 고객 원문은 조회·저장하지 않았다.
- 웹 `intake-review.tsx` 가 질문 흐름에 `loadingDone: status !== "reading"` 만 넘겼다 → **실패(`fatal`)도 「읽기 끝」**으로 보고
  `use-question-flow.ts` 가 phase 를 `done`(손대지 않음) / `late`(답하던 중) 로 올렸다. `done`·`late` 는 `flow.hold` 라
  `if (flow.hold)` 분기가 그 아래의 `view.status === "fatal"` 실패 화면(「이 계획을 읽지 못했어요」 · `fatal.detail` · 「다시 올리기」)보다 먼저 그려졌다.
- 막대는 다른 신호다 — 실시간 진행의 마지막 `progress{reading}` 패킷(8/9줄, `serverProgressOf`)이 남고 `readingOf(fatal)` 의 단계가 `reading` 이라 「일정 읽기 8/9줄 · n초째」가 계속 셌다.
  「다 읽었어요」는 `status` 로 정해졌다. 사용자가 본 「이제 자동으로 넘어가지 않아요.」는 실패 뒤 뜬 `done` 에서 「자동으로 넘어가지 않기」를 누른 결과다.
- 공개 상태 `review+checking → reading`(`pipeline.public_status`)은 원인이 아니다(그 동안 웹은 「읽는 중」).

## 기대 동작 근거

- `wiki/external/rest-endpoints/web-intakes.md` 「접수 읽기 진행」: 끝 상태는 `review` · `confirmed` · `fatal` 의 `result` — `fatal` 은 성공 끝이 아니다.
- 같은 문서 「예상하지 못한 읽기 장애」: 웹은 `fatal.detail` 을 그대로 보인다. 기존 웹 실패 화면이 이 계약의 구현이다.
- 「설문 질문」 「두 번에 정한다」 끝 줄(읽기 실패면 네 문항을 모두 묻는다)은 **서버 질문 목록 구성 규칙**이다. 실패 접수에 저장된 답은 다음 접수가 이어받고(같은 문서, 2026-10-08), 다시 올린 접수에서 안 답한 문항을 다시 묻는다 — 실패 화면으로 바로 가도 답은 잃지 않는다(카드에 고르기만 하고 「다음」을 누르지 않은 값은 저장 전이라 남지 않는다).
- Codex(`codex exec -s read-only`, codex-cli 0.163.0) 검토: 원인 분석 동의. 단 그 끝 줄을 「실패 뒤에도 카드를 남기라」로 읽으면 카드 유지 + 실패 문구 방식이 안전하다는 의견. 이 환경에서 Codex 의 저장소 읽기 명령은 정책으로 막혀 원문 대조는 못 했다. 위와 같이 그 줄은 목록 구성 규칙이고 실패 UI 계약은 별도로 있어 **실패 화면으로 보내는 쪽**으로 정했다(실패 접수는 등록할 수 없어 카드만 남기면 갈 곳이 없다).
