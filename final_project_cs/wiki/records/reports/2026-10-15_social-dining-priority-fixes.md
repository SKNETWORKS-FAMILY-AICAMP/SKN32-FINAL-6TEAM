# SNS 맛집 링크 우선 결함 3건 묶음 수정·검증

2026-10-15 사용자의 “묶어서 수정 검증해줘”에 따라 앞서 정한 우선순위 1~3을 로컬 코드에 반영했습니다. 승인한 수정 **3/3 = 100%**를 완료했으며, 전체 시스템의 모든 결함이 해결됐다는 뜻은 아닙니다. 커밋·푸시·배포는 하지 않았습니다.

## 수정 결과

| 승인한 항목 | 최종 동작 | 상태 |
|---|---|---|
| 식이 조건 보존 | 생성 초안의 `trip.constraints`를 현재 revision claim으로 보관하고 조립·최종 등록에 복원합니다. 부분 설문을 합칠 때 미응답 영역을 유지합니다. SNS preview/apply가 원래 여행·현재 초안·저장 설문의 식이 조건을 확인하고, 필요한 근거가 없으면 해당 배치를 보류합니다. | 1/1 = **100%** |
| 고객의 지점 선택 보호 | 본점/별관·복합 지점명·도로명/건물번호·좌표 충돌을 구분합니다. 지점 없는 결과로 서로 다른 지점이 연결되지 않습니다. 확인된 동일 지점 안에서만 제공자의 검증 정보를 재사용하고, 선택한 ref의 별관을 다른 지점으로 바꾸지 않습니다. | 1/1 = **100%** |
| 이름·지역·지점 검색 분리 | DB 이름검색과 외부 검색문을 분리합니다. 지역 조건과 명시 지점 순위를 DB LIMIT 전에 적용합니다. 이름 지정 원장 검색은 서울 전역을 보며 주변 대체 후보의 반경은 유지합니다. 괄호 속 동명과 상호 본문의 ‘본점’을 구분합니다. 기존 자유 검색은 전체 상호 우선, 실패한 경우에만 사전에 있는 앞/뒤 지역을 나눕니다. | 1/1 = **100%** |

공개 API 요청·응답 모양, tenant/customer 소유 확인, revision 충돌·멱등 처리, 명시적 apply와 최종 confirm 경로는 유지했습니다. DB 스키마·마이그레이션과 v2 프롬프트는 이번 수정에서 바꾸지 않았습니다.

최종 회귀 시험은 기존 `scripts/run_tests_local.ps1`의 **전용 시험 DB `acop_ci_local`과 가짜 모델 설정**으로 실행했습니다. Windows 샌드박스에서 HTTP 시험이 멈추는 문제가 있어 샌드박스 밖에서 실행했습니다. 공통 Starlette/AnyIO 폐기 예정 경고 1건이 있습니다. 두 pytest 묶음은 포함 관계이므로 통과 수를 합산하지 않습니다.

PostgreSQL 검증은 영구 표를 가리는 TEMP `places`·`place_catalog`에서 합성 여행 식당만 사용했습니다. 관광공사·요식원장 각각 ①가까운 다른 지점 40개보다 요청 본점 우선 ②‘본점식당 본점’ ③괄호 속 주교동 ④지역 좌표를 LIMIT 전 필터 ⑤본인/의도된 공용 tenant 허용과 다른 tenant 제외를 확인했습니다. 전부 rollback한 뒤 TEMP 표가 없어졌음을 확인했습니다. 영구 스키마·행 변경과 외부 제공자 호출은 없습니다. ## 실패 재현과 검토 경계

- 식이 조건: 초안 저장에서 유실·부분 설문으로 다른 영역 유실 등 신규 4건의 실패를 먼저 확인하고 수정했습니다. 현재 revision의 조건 읽기와 apply 재검증도 시험했습니다.
- 지점: 같은 건물의 본점/별관, 지점 없는 중간 결과, 비슷한 다른 상호, 멀리 떨어진 좌표, 복합 지점 표기, 동일 상호의 다른 건물번호를 시험했습니다. 지점 단어가 브랜드 안에 있는 경우와 요청한 지점의 부분문자열만 맞는 경우를 구분했습니다. 새 지점·조건 시험은 각각 17건·4건입니다.
- 검색: 실제 ORDER/LIMIT를 수행하는 메모리 DB 대역에서 지역과 지점 후보가 잘리는 실패를 확인했습니다. 후속 독립 검토가 찾은 ‘본점식당’ 경계는 관광공사/원장 2건 모두 RED → GREEN으로 확인했습니다. 새 검색 시험 파일은 28건이고, 기존 검색 3건을 합친 검색 집중 시험은 31/31 = **100%**입니다.
- 기존 ‘병합 성공’ 시험 중 다른 지점 수식어와 먼 좌표까지 합치던 기대는 수정했습니다. 실제 동일 지점 중 더 충분한 검증 결과를 재사용하는 성공 시험은 유지했습니다.

## 먼저 실행한 여행 전체 시험과 남은 이동 실패

최종 코드가 안정되기 전 실행한 여행 전체 단위 시험은 **5,522 통과·18 실패·6 오류·45 건너뜀·356 제외**였습니다. [당시 JUnit 원본](../../../eval/reports/2026-10-15_social_dining_fixes_travel_unit.xml)을 보존했습니다. 시험을 수집한 뒤 수정된 코드가 섞인 실행이므로 최종 회귀 성적표로 사용하지 않습니다. 실패·오류를 숨기지 않고 다음처럼 구분합니다.

- **이동 15건:** 혼잡도 자료 1건, 택시 1건, `test_plan_v1` 5건, 회귀 시나리오 7건, 열차 환승 정밀도 1건입니다. 이번 수정 범위에서 해결하거나 최종 재실행하지 않았습니다. 이 실행만으로 기준 브랜치에서도 같은 실패라고 단정하지 않습니다.
- **공유 캐시 1실패·6오류:** 처음 전체 실행에 앱의 개발 DB `acop_cs` 설정이 사용됐고 `source_response_cache`가 없어 준비/정리 SQL이 실패했습니다. 원본 실행에는 해당 표의 삭제 시도도 포함돼 있어 ‘DB 접근 없음’으로 보고하지 않습니다. 이후 실행은 `acop_ci_local`로 명시적으로 격리했고, 공유 캐시 시험을 포함한 비이동 전체 4,055건이 통과했습니다. 개발 DB에 누락 표를 만들거나 마이그레이션하지 않았습니다.
- **SNS 2건:** 수정 전 수집된 기존 병합 기대를 사용한 실패입니다. 현재 지점 의미에 맞는 회귀 시험으로 고친 뒤 최종 관련 176건과 비이동 전체 실행에서 해소를 확인했습니다.

pytest의 실패와 teardown 오류가 같은 시험에 함께 기록된 경우가 있어 원본 XML의 testcase 노드 수와 고유 시험 수가 다릅니다. 위 원본 결과를 임의로 하나의 성공률로 환산하지 않았습니다.

다음 세 항목은 앞선 검토에서 남겼고 이번 1~3 수정으로 닫지 않았습니다: **head/본문 수집 경계**, **GET에서 저장 제안 복구**, **v2 모델의 유효 식당 누락**. 실제 SNS 플랫폼 접근·실모델 재평가·실서버 화면·운영 배포도 이번 검증의 범위 밖입니다.
