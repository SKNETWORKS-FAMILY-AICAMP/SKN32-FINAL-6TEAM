# 시간 초기화가 일부 일정만 되돌림

## 해결됨 (2026-10-08) — 최신 전체 일정으로 초기화 대상 계산

원래 시간은 최신 완료 일정에서 항목별로 보관하고, 전체 초기화의 대상과 개수도 최신 일정으로 계산한다. 검증 완료 뒤 수정 결과는 `useReveal`에서 즉시 반영하며 내부 상태도 동기화한다. 설문 대기와 최초 검증의 단계별 재생은 유지한다.

**원인 정정:** 아래 발견 기록의 ‘원래 시간 보관 객체를 한 번만 채운다’는 초기 가설이었다. 항목별 보관만으로 바꿔도 같은 시험이 실패했다. 실제 요청을 계측하니 변경 기록은 3곳이지만 표시용 일정은 첫 한 곳만 갱신되어 초기화가 그 한 곳만 보냈다. 화면 재생 지연과 저장된 일정 사이의 차이가 직접 원인이다. [실패 요청 원문](../../evidence/2026-10-08_1750_지도상태와_경로표시/map-status-reset-instrument.log)을 보존한다.

**확인:** 최종 키보드 시험은 모두 되돌리기의 3곳 표시뿐 아니라 `/edits` 본문에 3곳의 원래 시작·끝 총 6개 값이 들어갔는지도 검사한다. 변경 표시가 사라지고 옆 확인 버튼으로 초점이 돌아오는 것도 통과했다. 단위 51/51, 최종 화면 묶음 26/26과 재검증 회귀 1/1. [최종 화면 로그](../../evidence/2026-10-08_1750_지도상태와_경로표시/map-status-ui-complete.log), [작업 리포트](../2026-10-08_1753_지도상태와_경로표시_정리.md).

### 발견 당시 가설과 재현 기록

## 미해결

- 위치: frontend/apps/web/src/features/plan-check/plan-check.tsx의 baseline 보관 효과.
- 재현: 새 map-status-bar.spec.ts의 키보드 변경 메뉴 시험. SSE를 켜고 이미 읽힌 접수를 연 뒤 광장시장 시간을 11:30으로 바꾸면 3곳이 변경됨. 변경 메뉴에서 모두 되돌려도 변경 2곳이 남음.
- 실측: Chrome 화면 시험에서 3곳 중 1곳만 원래 시각으로 복귀. 기본 원래 시간 보관 객체는 비어 있을 때 한 번만 채우므로 완료 화면에 뒤늦게 들어온 일정은 기준 시간이 없음.
- 영향: 고객이 모두 되돌렸다고 생각해도 두 일정의 시간이 수정 상태로 남을 수 있음. 과금·업체 예약 변경은 없음.
- 정정: 폴링 기반 네 일정 시험은 통과했지만 SSE 기반 키보드 시험은 통과하지 못했음. 모든 조건에서 초기화가 된다고 주장하지 않음.
- 수정: 각 일정이 처음 나타날 때 원래 시간을 보관하고 기존 기준은 유지하는 방식으로 보완 예정.
