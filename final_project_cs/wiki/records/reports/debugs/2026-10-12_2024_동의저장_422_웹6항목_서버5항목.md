# 동의 저장이 늘 422 — 웹은 동의 항목 6개를 보내고 서버는 5개만 안다

## 미해결

★`[2026-10-12 임시 조치 · 웹]` 웹이 `service_improvement` 를 보내지 않고 화면에서 「준비 중」으로 둔다 — 아래 「임시 조치」. **서버 수정 전까지 이 리포트는 열려 있다.**

결론: `45ab1efa`(2026-10-12 11:47, role-manager → develop)가 **웹에만** 여섯째 선택 동의 `service_improvement`(서비스 개선용 이용)를 더했다. 웹은 동의를 저장할 때 항목을 늘 전부 보내므로 6개가 가고, 서버는 항목이 5개를 넘으면 거부한다. 그래서 지금 웹의 **모든 동의 저장(`POST /v1/web/consents`)이 422** 로 끝난다.

작성: 2026-10-12 20:24 · Claude · `role-eval-ui` `bb1087b2`(develop `439487e5` 병합본, 백엔드는 develop 과 같다) + 로컬 변경.

## 위치

- 웹 `frontend/apps/web/src/features/consent/consent-model.ts:14` — `CONSENT_CODES` 6개(`service_terms` · `privacy` · `sensitive` · `location` · `alert_channel` · `service_improvement`)
- 웹 `frontend/apps/web/src/features/consent/consent-sync.ts:47` — `choicesOf` 가 `CONSENT_CODES` 전부를 보낸다
- 서버 `app/domains/travel_ops/components/customer/consents.py:33` — `CODES` 5개(`service_improvement` 없음)
- 서버 같은 파일 `:123-124` — `len(items) > len(CODES)` 이면 422 `invalid_items` 「동의 항목이 비었거나 모양이 틀려요」(코드 검사보다 앞이라 `unknown_code` 가 아니라 이 오류가 난다)

```bash
  -X POST http://127.0.0.1:8042/v1/web/consents -d '{"version":"<current_version>","items":[{"code":"service_terms","agreed":true,"text_sha256":"<64자>"}, …]}'
```

## 실측 (2026-10-12)

| 보낸 항목 | 응답 |
|---|---|
| 6개(지금 웹과 같은 모양, `service_improvement` 포함) | **422** `invalid_items` |
| 5개(`service_improvement` 뺌) | **200**, 필수 동의 기록됨 |

브라우저(내장 브라우저, 새 게스트): 필수 약관에 동의한 뒤 `POST /v1/web/consents` 가 422 로 3번 끝났고, 「동의 기록을 확인하지 못했어요 · 다시 확인하기」 카드가 화면 위쪽을 덮어 그 아래 버튼(예: 문의하기의 「문의 작성」)이 눌리지 않았다.

## 시험이 못 잡은 이유

`45ab1efa` 가 웹과 함께 **모방 서버**(`frontend/apps/web/tests/live/stub-server.mjs:233`)도 6개로 바꿨다 — 그래서 `test:live` 는 통과한다. 실제 서버(`consents.py`)와 계약 문서(`wiki/external/rest-endpoints.md:554` 「**항목 다섯**」)는 그대로다. 계약을 먼저 고치는 규칙(`RULE.md` §3.5)이 지켜지지 않았다.

## 위험도

- 새 사용자의 첫 동의(필수 포함)가 **서버에 기록되지 않는다** — 웹 사본에만 남고 「동의 기록을 확인하지 못했어요」가 뜬다.
- 마이페이지 「약관 동의 관리」에서 선택 동의를 켜고 끄는 것도 기록되지 않는다. **철회 효과**(예: `alert_channel` 철회 → 저장한 웹훅 삭제, `rest-endpoints.md:562`)도 서버에서 실행되지 않는다 — 개인정보 철회 미이행 위험.
- 이미 서버에 기록된 사용자는 동의를 바꾸기 전까지는 영향이 없다(그래서 사용자 Chrome 에서는 보이지 않았다).
- 서버의 동의 게이트(`config/guardrails.yaml:768` `gate_enabled`)는 기본 `false` 다. **켜진 환경이면 새 사용자의 거의 모든 호출이 403 `consent_required`** 가 된다. 배포 환경의 이 값은 `[미확인]`.

## 내가 잘못 말했던 것의 정정

2026-10-12 대화에서 「새 게스트에서만 생기는 문제일 수 있다」고 했다. 실제로는 **동의를 새로 저장하거나 바꾸는 모든 사용자**에게 생긴다. 사용자 Chrome 에서 보이지 않은 것은 그 브라우저의 동의가 `45ab1efa` 이전에 이미 서버에 기록돼 있었기 때문이다.

## 서버 쪽에서 함께 빠진 것 — 약관 버전

웹 `terms-content.ts:17` 은 `TERMS_VERSION = "2026-10-10.1"` 이고 주석이 「서비스 개선 선택 동의 추가. cs 프로젝트 서버 `consent.terms_version` 과 함께 변경한다」인데, 서버 `config/guardrails.yaml:766` 은 `2026-10-07.1` 그대로다(실서버 응답도 `current_version: 2026-10-07.1`). 웹은 서버가 준 버전을 쓰므로 409 가 아니라 위의 422 에서 걸린다. 모방 서버(`stub-server.mjs`)의 약관 버전도 웹 값(`2026-10-10.1`)이라 실서버와 다르다 — 이번에는 항목 목록만 맞췄다.
