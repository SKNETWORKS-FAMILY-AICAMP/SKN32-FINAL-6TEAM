# UUID 가 전화번호로 가려져 Case 가 가끔 사람에게 간다 — 「원인 모름 간헐 실패」의 정체

## 해결됨 (2026-09-18)

- 고친 곳: `app/core/redaction.py` — UUID 는 가리지 않고, UUID 사이의 조각만 가린다.
- 시험: `tests/unit/core/test_redaction_rules.py` — 숫자만 이어진 칸이 있는 UUID · 무작위 UUID 5000개 · 같은 문장의 진짜 전화번호·카드번호는 그대로 가림.
- 확인: 고치기 전 `tests/scenario/test_case_version_day.py` 반복에서 30회 중 2회 · 기록 플러그인을 붙여 5회 중 2회 실패(두 번째 실패에서 멈추게 했다) → 고친 뒤 반복 결과는 §6.

- 발견: 2026-09-18 · 남은 작업 「가끔 실패하는 시험 1건, 원인 모름」을 가리다가

## 1. 무엇이 일어나나

Case 버전의 시험이 **가끔**, 그리고 **매번 다른 시험에서** 실패했다. 늦음 신고가 `escalated`, 감시 Case 가 `escalated`, 되돌리기 뒤 버전 수가 하나 모자람. 어제(09-17)는 `test_trip_api.py::test_a_repeated_message_does_not_open_a_second_case` 가 1회 실패(`duplicate` 기대, `still_fits`)하고 재현되지 않아 「원인 미확정」으로 남겼다.

## 2. 원인

`app/core/redaction.py` 의 전화번호 규칙 `(?<!\d)(\d{3})-(\d{4})-(\d{4})(?!\d)` 이 **UUID 안의 숫자 칸**에 걸린다.

```
7da9d588-1234-4253-8b0c-8d09d778ce69   →   7da9d588-****-4253-8b0c-8d09d778ce69
      └ 588-1234-4253 이 010-1234-5678 과 같은 모양
```

`transition_case` 는 이벤트 payload 를, `repository.create_case` 는 `state_json` 을 **통째로** 가린 뒤 저장한다. 그래서 Case 상태 안의 `subject_ref.id`(여행 id)·중복 표식의 `trip_id` 가 가끔 망가진 채 저장됐다.

| 증상 | 경로 |
|---|---|
| Team 이 `unknown_여행 일정` 으로 사람에게 넘김 | 망가진 `trip_id` 로 일정 조회 → `ValueError: invalid literal for int() with base 16: '7da9d588****4253…'` → 「모른다」 |
| 같은 신고를 두 번 처리(`still_fits`) | 중복 표식이 가려진 채 저장돼 `state_json @> {trip_id}` 조회와 안 맞음 |

UUID 가 무작위라 숫자 칸 모양이 맞을 때만 난다 — 그래서 가끔, 매번 다른 시험에서.

## 3. 어떻게 찾았나

1. 그 시험만 25회 → 2회 실패였지만 둘 다 **DB 가 꺼져 있던 때의 연결 시간 초과**였다(아래 §5). 진짜 실패는 아니었다.
2. 원래 조합 12회 → 3회 실패. 그중 2회는 내가 같은 시험 폴더에 새 파일을 쓰던 중이라 무효, 유효 1회(`test_case_version_day` p3 `escalated`). pytest 출력이 잘려 사유가 안 보였다.
3. pytest 밖 탐침 스크립트로 하루 40회 → 0회. 가설 「동시 실행 간섭」 → 두 프로세스 동시에 25회씩 → 0회. **기각이 아니라 이 탐침이 재현을 못 한 것**으로 적어 두고 다른 길로 갔다.
4. pytest 안에서 테넌트를 지우기 직전에 `escalated` Case 의 이벤트를 파일로 떠 두는 플러그인 → 5회 중 2회 실패, 이벤트에 `unknown_여행 일정` 과 위 `ValueError` 가 남았다.

## 4. 위험도

- **고객 답변:** 맞게 고칠 수 있는 신고가 가끔 사람에게 간다(안전한 방향). 같은 신고를 두 번 적용할 수 있었다 — 늦음 70분을 두 번 밀 수 있는 경로다(시나리오용 버전의 중복 표식).
- **감사:** 이벤트 기록의 UUID 가 가려진 채 남는다 — 이미 쌓인 행은 고치지 않는다(append-only).
- 전화번호 가림은 그대로다 — 같은 문장의 진짜 전화번호는 계속 가린다.

## 5. 함께 본 것 — DB 가 기록 없이 꺼진다

`server_5433.log` 에 **정상 종료 기록 없이** 다음 기동이 「not properly shut down」으로 시작하는 일이 셋 있다(09-15 06:47 · 09-17 05:38 이후 · 09-17 15:19 이후). 09-15 는 `WAL writer … terminated by exception 0x40010004` — 바깥에서 프로세스를 끝낸 모양이다. 오늘 13:57 에 누군가 다시 띄웠다(부모 `cmd.exe /C postgres …`, `pg_ctl` 모양). 이 PC 에서 DB 는 서비스가 아니라 셸에서 띄운 프로세스라, 띄운 세션이 끝날 때 같이 죽는다는 가설이 맞아 보이지만 **확인하지 않았다.**

★30회 대 30회로는 차이가 강하지 않다(2/30 과 0/30). 고쳤다고 말하는 근거는 반복 횟수가 아니라 **원인을 직접 봤다**는 것이다 — 가려진 UUID 가 오류 메시지에 그대로 남았고, 같은 UUID 를 가림 함수에 넣으면 같은 결과가 나오며(`masked('7da9d588-1234-4253-…')`), 고친 뒤 무작위 UUID 5000개가 하나도 안 바뀐다.
