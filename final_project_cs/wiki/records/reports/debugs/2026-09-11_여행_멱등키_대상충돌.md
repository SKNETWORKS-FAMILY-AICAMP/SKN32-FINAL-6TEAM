# 디버그 리포트 — 여행 전환 후 서로 다른 예약 제안이 한 건으로 합쳐짐

## 미해결 (2026-09-14 확인 — 아래 판정 요약의 「수정 미적용」 그대로다)

## 0. 판정 요약

| 항목 | 내용 |
|---|---|
| 이슈 | 한 Case 안에서 서로 다른 예약을 바꾸는 두 제안이 같은 멱등 키를 받아 두 번째 제안이 저장되지 않음 |
| 발생 계층 | **Core 저장 경계** — Controller의 서버 키 재계산 + Action Repository의 충돌 처리 |
| 발견일 | 2026-09-10 |
| 상태 | **실제 DB 재현 완료. 수정 미적용.** |
| 위험도 | 높음. 승인·감사·실행 대상이 저장된 행 기준이라 누락된 제안을 뒤에서 복구할 수 없음 |
| 현재 경로 판단 | 여행 Team은 현재 정상 경로에서 제안 하나씩 반환하므로 일반 시나리오에서 항상 발생한다고 단정하지 않음. 다만 `TeamResult.action_proposals`는 복수 제안을 허용하므로 계약상 유효한 입력에서 재현되는 잠재 결함임 |

핵심은 **중복 재시도는 합쳐야 하지만, 같은 Case의 서로 다른 예약은 합치면 안 된다**는 것이다.
커머스 시절에는 Case 하나와 업무 대상 하나가 사실상 같았기 때문에 `case_id`를 대상으로 써도 문제가 드러나지 않았다. 여행에서는 Trip 하나에 요식·이동·액티비티 예약이 여러 개이고, 한 사건이 여러 예약을 동시에 바꿀 수 있어 그 전제가 깨졌다.

## 1. 장애 시나리오

### 입력 조건

하나의 여행 사건에서 다음 두 제안이 만들어졌다고 가정한다.

```json
{
  "case_id": "case-123",
  "request_id": "req-456",
  "action_proposals": [
    {
      "action_type": "booking.change",
      "arguments": {"booking_id": "bk-001", "domain": "dining"}
    },
    {
      "action_type": "booking.change",
      "arguments": {"booking_id": "bk-002", "domain": "mobility"}
    }
  ]
}
```

예시는 경복궁 한옥 투어 일정 변경 때문에 식당 예약과 이동 예약을 함께 조정하는 상황이다. 두 제안은 `action_type`은 같지만 실제로 바꾸는 예약 객체가 다르다.

### 기대 결과

| 제안 | 대상 | 기대 저장 결과 |
|---|---|---|
| 1 | `bk-001` 요식 예약 | `action_requests` 1행 |
| 2 | `bk-002` 이동 예약 | `action_requests` 별도 1행 |

총 **2행**이 저장되고, 승인 화면과 실행 직전 재검증은 각각의 예약을 읽어야 한다.

### 실제 결과

```text
두 제안의 action_id 가 같은가 : True
남은 행 1개
저장된 arguments_json : {"booking_id": "bk-001"}
bk-002 제안 : 저장되지 않음
```

실제 DB에 임시 프로브를 넣어 확인했고, 확인 후 트랜잭션은 롤백했다. 따라서 검증을 위해 운영 데이터나 공유 DB에 잔여 행을 남긴 것은 아니다.

## 2. 재현 절차

### 2.1 재현 조건

다음 네 값이 두 제안에서 동일해야 한다.

```text
tenant_id
request_id
action_type = booking.change
business_subject = case_id
```

`arguments.booking_id`만 `bk-001`과 `bk-002`로 다르게 한다.

### 2.2 현재 코드의 키 계산

Core의 키 함수는 다음 네 요소를 이어 붙여 SHA-256으로 만든다.

```text
sha256(tenant_id + request_id + action_type + business_subject)
```

근거: `final_project_cs/app/core/idempotency.py:8-14`, 계약 문서 `final_project_cs/wiki/teams/team-contract/fields.md:103-109`.

그런데 Controller가 저장 직전에 `business_subject`를 항상 Case ID로 넣는다.

```python
server_key = idempotency_key(
    tenant_id=case["tenant_id"],
    request_id=request_id_for_case(case),
    action_type=proposal.action_type,
    business_subject=str(case["case_id"]),
)
```

근거: `final_project_cs/app/application/controller.py:372-377`.

따라서 두 제안의 실질적인 키 입력은 다음처럼 된다.

```text
제안 1 = (tenant-A, req-456, booking.change, case-123)
제안 2 = (tenant-A, req-456, booking.change, case-123)
```

`booking_id`는 키 계산에 들어가지 않는다. 결과적으로 두 제안은 서로 다른 예약을 가리키는데도 같은 `idempotency_key`를 갖는다.

### 2.3 충돌 시 DB 처리

Repository는 다음 SQL을 사용한다.

```sql
INSERT INTO action_requests (
  tenant_id, case_id, action_type, arguments_json, idempotency_key, status
)
VALUES (...)
ON CONFLICT (tenant_id, idempotency_key)
DO UPDATE SET idempotency_key = EXCLUDED.idempotency_key
RETURNING action_id;
```

근거: `final_project_cs/app/infrastructure/db/repository.py:42-44`.

두 번째 INSERT는 충돌한다. 하지만 `DO NOTHING`이 아니라 기존 행을 대상으로 아무 변화 없는 `DO UPDATE`를 실행하고, 기존 행의 `action_id`를 반환한다.

결과는 다음과 같다.

1. 첫 번째 제안이 `bk-001` 인자로 저장된다.
2. 두 번째 제안의 INSERT가 동일 키와 충돌한다.
3. DB는 기존 `action_id`를 반환한다.
4. Controller는 같은 ID를 `action_ids` 목록에 다시 넣는다.
5. 두 번째 제안의 `arguments_json`은 저장되지 않는다.

즉, 오류를 내지 않고 성공처럼 보이면서 데이터가 줄어드는 **조용한 병합(silent merge)** 이다.

## 3. 원인 분석

### 직접 원인

Core가 서로 다른 업무 대상의 제안을 구분해야 하는 `business_subject`를 `case_id`로 고정했다.

```text
현재: business_subject = case_id
필요: business_subject = 서버가 확인한 대상 객체 ID
```

### 근본 원인

멱등성의 두 목적이 한 저장 규칙에 섞였다.

| 목적 | 합쳐야 하는 것 | 합치면 안 되는 것 |
|---|---|---|
| 재시도 중복 방지 | 같은 요청·같은 작업·같은 대상·같은 인자 | — |
| 여행 일정 변경 | — | 같은 Case 안의 다른 예약·다른 일정 항목 |

기존 산식은 “같은 Case에서 같은 작업을 다시 실행하면 한 번만 저장한다”는 커머스 전제에 맞춰져 있었다. 여행 전환 후에는 Case 하나가 여러 예약을 포함하고, 사건 하나가 요식·이동·액티비티를 함께 바꿀 수 있으므로 `case_id`만으로는 대상의 식별력이 부족하다.

### 초기 분석의 정정

처음에는 `travel_ops/_base.py`의 `booking_id → trip_id → case_id` 폴백이 최종 키를 망친다고 봤다. 그러나 Team이 넣은 키는 최종 저장값이 아니다. Controller가 Team 값을 advisory로 취급하고 서버에서 다시 계산한다.

따라서 `_base.py`의 폴백을 고치는 것만으로는 이 결함이 해결되지 않는다. **수정 위치는 Core의 저장 직전 키 계산부**다.

근거: `final_project_cs/app/application/controller.py:372-377`, `final_project_cs/wiki/teams/dining.md:131-139`.

## 4. 영향 범위

### 데이터 영향

- 서로 다른 예약 두 건이 `action_requests` 한 행으로 축약된다.
- 두 번째 제안의 인자와 대상 ID가 보존되지 않는다.
- 동일한 `action_id`가 `action_ids` 목록에 중복으로 들어갈 수 있다.

### 업무 영향

- 승인자는 식당 예약과 이동 예약이 모두 변경 대상이라고 믿지만 실제 승인 행은 하나일 수 있다.
- 실행 직전 재검증은 저장된 행만 읽으므로 누락된 `bk-002`를 되살리지 못한다.
- 감사 로그에서 “제안 2건”과 “저장·실행 대상 1건”의 불일치가 발생한다.
- 고객에게는 일정 일부만 바뀌거나, 한 예약만 처리된 상태가 정상 완료처럼 보일 수 있다.

### 보안·권한 측면

현재 재현 자체는 다른 테넌트의 데이터를 읽는 문제는 아니다. 다만 대상 소유권 검증 없이 키를 만들면, 향후 잘못된 예약 ID가 들어왔을 때 멱등성뿐 아니라 대상 검증 경계까지 약해질 수 있다. 따라서 키에 넣기 전에 “실재하는가”와 “이 여행의 예약인가”를 함께 확인해야 한다.

## 5. 왜 기존 테스트가 잡지 못했나

기존 멱등성 테스트는 “같은 요청을 여러 번 보냈을 때 `action_requests`가 1행인가”를 확인하는 데 초점이 있다. 이는 정상적인 재시도 중복 방지에는 맞지만, 다음 경우를 검사하지 않는다.

```text
같은 Case
+ 같은 request_id
+ 같은 action_type
+ 서로 다른 business object
→ 두 행이 각각 저장되는가?
```

또한 현재 여행 Team은 제안 하나씩 반환하므로 일반적인 Team 시나리오만 실행하면 충돌 입력 자체가 만들어지지 않는다. 그러나 `TeamResult.action_proposals`가 목록이고, 한 사건이 여러 예약을 바꾸는 여행 업무 규칙을 허용하므로 Core 저장 경계가 이 입력을 안전하게 처리해야 한다.

## 6. 수정안

v11 §4-E의 결정대로 **서버가 인자에서 업무 대상을 추출하고, 실재·소유를 확인한 대상 객체 ID를 최종 키에 넣는다.** 대상을 특정하지 못하면 Case ID로 폴백하지 않고 제안을 거부하거나 `escalate`한다.

### 6.1 대상 추출 규칙

| Action 접두 | 대상 인자 | 키에 넣을 값 |
|---|---|---|
| `activity.*`, `dining.*`, `booking.*` | 예약 변경이면 `booking_id` | 검증된 예약 ID |
| `activity.*`, `dining.*` | 예약 없는 일정 항목이면 `item_id` | 검증된 일정 항목 ID |
| `mobility.*` | `item_id` | 검증된 이동 구간 ID |
| `trip.*` | `trip_id` | 검증된 여행 ID |

### 6.2 수정 후 키

```text
제안 1 = (tenant-A, req-456, booking.change, bk-001)
제안 2 = (tenant-A, req-456, booking.change, bk-002)
```

이제 서로 다른 예약은 서로 다른 `action_requests` 행이 된다. 같은 `bk-001` 제안을 재시도하면 기존 행과 합쳐진다.

### 6.3 Repository 충돌 처리 보강

키가 같더라도 인자가 다른 경우를 다시 조용히 합치면 안 된다. 권장 동작은 다음이다.

1. `ON CONFLICT DO NOTHING RETURNING action_id`로 기존 행을 확인한다.
2. 0행이면 기존 행을 조회한다.
3. 기존 `action_type`, 대상, 정규화한 `arguments_json`을 새 요청과 비교한다.
4. 완전히 같으면 기존 `action_id`를 반환한다.
5. 키는 같은데 인자가 다르면 `IdempotencyConflict`를 발생시키고, 저장·승인 진행을 중단한다.

이 방어선은 키 산정 버그가 다시 생기더라도 “성공처럼 보이는 데이터 손실”을 “명시적인 실패”로 바꾼다.

## 7. 필수 회귀 테스트

| 테스트 | 기대 결과 |
|---|---|
| 같은 예약 `bk-001` 제안 10회 | `action_requests` 1행, `action_id` 동일 |
| 같은 Case의 `bk-001`·`bk-002` 제안 | `action_requests` 2행, `action_id` 서로 다름 |
| 같은 키인데 arguments가 다름 | 명시적 충돌 오류, 두 번째 제안 저장·승인 금지 |
| 존재하지 않는 `booking_id` | 대상 검증 실패, 키 생성 및 실행 금지 |
| 다른 테넌트의 `booking_id` | 소유권 검증 실패, 키 생성 및 실행 금지 |
| 예약 없는 액티비티의 `item_id` | `item_id` 기준 별도 행 생성 |
| `mobility.*`의 서로 다른 `item_id` | 구간별 별도 행 생성 |

최소 재현 테스트의 핵심 단언은 다음과 같다.

```python
assert action_id_1 != action_id_2
assert count_action_requests(case_id=case_id) == 2
assert stored_booking_ids() == {"bk-001", "bk-002"}
```

## 8. 종료 조건

이 이슈는 다음 조건을 모두 만족해야 닫힌다.

- [ ] Controller가 `case_id`를 `business_subject`로 무조건 사용하지 않는다.
- [ ] 서버가 Action 종류별 대상 ID를 인자에서 추출한다.
- [ ] 대상의 실재 여부와 여행 소유권을 확인한다.
- [ ] 대상 미지정 시 `case_id` 폴백 없이 명시적으로 거부한다.
- [ ] 같은 대상·같은 인자는 멱등하게 1행으로 합쳐진다.
- [ ] 같은 Case·같은 Action·다른 대상은 별도 행으로 저장된다.
- [ ] 같은 키·다른 인자는 조용히 병합되지 않고 충돌로 차단된다.
- [ ] 승인 화면과 실행 직전 재검증이 저장된 모든 제안을 읽는다.
- [ ] 요식·이동·액티비티를 포함한 여행 fixture로 회귀 테스트가 통과한다.
