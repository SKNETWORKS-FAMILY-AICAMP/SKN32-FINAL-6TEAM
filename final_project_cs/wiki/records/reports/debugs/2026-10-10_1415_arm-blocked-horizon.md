# Oracle ARM의 실패 대기 작업이 실행 가능 시간을 채우는 결함

## 해결됨 (2026-10-10)

현재 실행판 기준 준비 시간 계산을 수정했고 대기열 회귀15/15 통과, 새 실제 HTTP 회차 시작을 확인했습니다. 원래 실패 프로필의 시간 초과는 별도 미해결이며 재실행하지 않습니다. [실측·원본](../2026-10-10_1400_six-hour-gpu-arm-report.md).

### 발견 당시 상태: 미해결

- 발견: 2026-10-10 14:02 KST.
- 위치: `deploy/arm/serving_queue.py`의 `refill`.
- 재현: 실패 프로필 두 종류의 대기 45건, 성공 프로필 대기 0건인 상태에서 보충 함수를 호출한다.
- 실측: 저장된 남은 추정 21,600초와 달리 현재 배포판에서 실행 가능한 대기는 0건이다. 완료22·실패3·대기45건이며 실패 기록은 보존한다.
- 원인: `select_job`은 실패 프로필을 제외하지만 `refill`은 모두 합산하고 보충 후보에도 실패 프로필을 포함한다.
- 영향: 실제 앱의 자동 질의 시험이 유휴 상태가 된다. 별도 모델 벤치마크는 실행 중이다. 고객 데이터·결제 변경은 없다.
- 정정: 대기 6시간은 준비된 6시간을 뜻하지 않았다. 이후 준비·차단·현재 실행을 분리한다. 시간은 관측 기반 추정이며 실제 6시간 보장이 아니다.
- 수정 계획: 현재 배포판에서 허용된 프로필만 합산·추가하고 막힌 원본과 실패 기록을 보존한다. 잠금과 무실행을 확인한 뒤 유휴 앱 일꾼만 교체한다. 모델 벤치마크는 중단하지 않는다.
- 검증: `python deploy/arm/test_ready_horizon.py` 및 Oracle ARM의 실제 잠금·등록·작업 시작 확인 예정.

- 원격 적용: 배포 잠금 획득·실행 작업0건 확인·직전 백업·유휴 앱 일꾼 교체. 기존 모델 벤치마크와 Docker 앱을 중단하지 않았습니다.
