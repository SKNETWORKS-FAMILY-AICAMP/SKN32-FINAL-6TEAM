# 운영앱 목록 맥락과 차단 확인 상태

## 해결됨 (2026-10-03)

- 발견: 2026-10-03 · Codex · `role-eval-ui` `1ec6111`의 코드 조사.
- 발견 당시 상태: 미수정. 동작 검증과 수정 결과는 후속 절에 기록한다.

## 위치와 재현

1. `frontend/apps/admin/src/components/AdminApp.tsx:111`의 경로별 재마운트와 `src/features/overview/screens.tsx:116`~119의 지역 상태 때문에, 사용자 목록에서 검색·정렬 후 상세로 갔다가 돌아오면 조건이 초기화된다. 문의함도 `src/features/workflows/screens.tsx:69`~71의 필터가 상세 항목 선택으로 초기화된다.
2. `src/features/overview/screens.tsx:139`~152에서 차단 성공 후 확인창·사유를 유지한다. 같은 열린 확인창이 해제 창으로 바뀌어 직전 차단 사유를 그대로 재사용할 수 있다.

재현 환경: admin의 명시적 demo 모드. 사용자 목록에서 검색·정렬 → 상세 → 목록 복귀. 이어 사용자 차단 → 사유 입력 → 확정 후 같은 폼이 남는지 확인한다. 코드에서 확인한 UI 상태 보존 결함 2건이며 실운영 데이터에 대한 영향은 검증하지 않았다.

## 위험과 수정 기준

목록 탐색이 끊기고 반대 동작의 확인에 이전 사유를 사용할 수 있다. 실제 API는 미연결이므로 이번 영향 범위는 데모 업무 흐름이다. 목록 조건은 앱 수명 동안 보존하고 초기화 요청 시 비운다. 차단·해제 성공 후 확인창을 닫고 사유를 비우며 실패하면 입력을 보존한다.

## 수정과 검증

`AdminApp`의 메모리에 목록 조건을 보존하고 사용자·문의 화면에 전달한다. `UserDetail`은 명령 성공 여부를 받아 확인창과 사유를 정리한다. 앱과 단일 HTML의 목록 복귀·문의 항목 선택, 차단 후 재진입·새 사유 요구, 초기화 및 기존 회귀를 검증했다. 단위 23/23 + 브라우저 22/22 = 45/45(100%).

재현 명령은 admin에서 demo를 명시한 `npm run check`, `npm run export:html`, Chrome을 사용하는 `npm run test:e2e`다. [작업 리포트](../2026-10-03_0238_운영앱_관리자앱_화면고도화.md)와 [실행 근거](../../evidence/2026-10-03_0238_운영앱_관리자앱_검증.md)에 최종 출력과 첫 시험 선택자 실패를 구분해 기록했다.
