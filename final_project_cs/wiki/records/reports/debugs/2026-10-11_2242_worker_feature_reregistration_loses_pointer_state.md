# 백그라운드 반복 배선으로 준비된 일정 해석 상태가 사라지는 문제

작성: 2026-10-11 22:42 KST. 해결됨. 범위는 로컬 백그라운드 실행 코드입니다.

독립 정리 회차를 반복해도 준비된 일정 해석 상태를 유지하도록 수정했습니다. 초기화 실패는 다음 회차에 재시도하며, Team 후보 조립과 초기화를 분리했습니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 실제 클래스 상태 소실 재현 | 확인 | 1/1 = 100% |
| 상태 보존·실패 후 재시도 | 통과 | 2/2 = 100% |
| 회차·종료·주기 회귀 | 통과 | 38/38 = 100% |
| 운영 배포 | 미실시 | 0/1 = 0% |

2개 신규 시험은 38개 묶음에 포함됩니다. 서로 더하여 40개로 세지 않습니다.

## 문제와 원인

[기능 배선](../../../../app/composition.py)의 재등록 항목을 확인했습니다. 감시 대상 필터·설정 조회·진행 알림·시뮬레이션은 같은 동작을 다시 연결하지만, 일정 항목을 고르는 모델 연결은 새 `OllamaItemPointer`를 생성합니다. 준비된 응답 캐시를 가진 객체가 새 객체로 바뀌면 같은 질문에서 캐시 결과 대신 규칙 경로가 실행됩니다.

[수정 전 재현](../../evidence/2026-10-11_1936_team_plugin_implementation/feature-reregistration-pointer-state.log)은 실제 클래스를 사용했습니다. 외부 HTTP 대신 시험 응답을 주고 준비 작업을 끝낸 뒤, 두 번째 식당을 고르는 결과를 확인했습니다. 재등록 후 객체가 교체되고 같은 질문이 `NotImplemented`를 반환하여 규칙 경로로 돌아갔습니다. 외부 요청은 0건입니다. 실제 모델 품질을 측정한 시험은 아닙니다.

## 수정

[백그라운드 초기화 함수](../../../../scripts/run_sweepers.py)의 프로세스 안에서 성공한 초기화를 한 번만 기억합니다. 잠금 안에서 성공 여부를 확인하고, 배선이 끝난 뒤에만 성공으로 표시합니다. 실패하면 성공 표시가 남지 않아 다음 회차에서 다시 시도합니다.

`get_settings()`와 가드레일 설정이 프로세스에서 캐시되는 현재 전제에 맞춘 범위입니다. API 앱 생성의 배선 방식이나 Team 후보의 불변 계산 표를 바꾸지 않았습니다. 이전에 보완한 조립 실패·배선 실패의 독립 정리 격리도 유지합니다.

[가용성 계약](../../../teams/team-contract/plugin-availability.md)에 같은 전제를 기록했습니다. [변경 전 백업](../../../../legacy/team_plugin_e2e/2026-10-11_2223/)에는 기존 작업 상태를 포함합니다.
