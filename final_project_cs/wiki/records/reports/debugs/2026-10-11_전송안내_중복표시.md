# 전송 안내 중복 표시

## 해결됨 (2026-10-11)

PlanCheck의 읽기 안내를 단일 소유로 바꾸고 같은 안내가 하나인지 검사하도록 보완했습니다. 보완 후 웹 전체 단위643/643·타입·lint·새 webpack 생산 빌드는 통과했습니다. 최종 mock 서버 Chrome 화면49/49를 같은 새 생산 빌드에서 통과했습니다. 동일 안내가1개인지 명시 검사한 전송3개도 통과했습니다. 최종 결과는 [독립 검증 보고](../2026-10-11_toast_manager_독립검증.md)에 기록합니다.

## 발견 당시 기록

manager 기준과 새 화면 안내 패치를 합친 최초 독립 mock 서버 Chrome 시험에서46/49 통과,3/49 실패했습니다. intake-start.spec.ts의 전송 즉시 진행 화면·게스트 첫 전송·응답 지연 시험에서 같은 전송 안내가 DOM에2개 나타났습니다. 문구 선택이 두 요소에 걸려 strict-mode 검사로 실패했고, 실패 화면에도 같은 토스트 두 개가 남았습니다. 선택자를 완화하지 않았습니다.

## 원인과 고객 영향

src/features/plan-check/plan-check.tsx의 읽기 안내가 useAppToast를 통해 직접 표시되면서 pending에도 보관됐습니다. 같은 화면의 GuardianHeaderControl도 useAppToast를 사용하므로 pending을 회수해 두 번째 ToastView를 표시할 수 있었습니다. 고객에게 안내가 겹치고 읽기 보조 기능에도 중복 전달될 수 있는 화면 결함입니다. backend 응답·과금·고객 격리 변경은 없습니다.

source 공통 코드에는 이 pending 기능이 없어 source의49개 통과만으로 manager 통합 결과를 보증하지 못했습니다. 최초 실패 기록은 보존합니다.

## 수정과 검증 방법

PlanCheck 읽기 안내는 useToastState로 하나만 소유합니다. 읽는 중에만 onToast를 구독하고 안내 표시 effect보다 먼저 구독합니다. 지도 화면의 Checking 구독과 공통 app-toast/toast-bus는 유지합니다. 진행 중 안내는 원래 페이지를 벗어나면 사라지는 inline 안내였으므로 완료 화면으로 새로 이월하지 않습니다.

기존 intake-start.spec.ts 실패3개에 동일 전송 안내가 정확히1개인지 검사하는 toHaveCount(1)을 추가했습니다. 기존 표시·요청 횟수·SSE·화면 이동 검사도 유지합니다. 수정 직전 두 파일은 각 파일 옆 _backup/2026-10-11_single_reading_toast_before/에 .bak로 보존했습니다.
