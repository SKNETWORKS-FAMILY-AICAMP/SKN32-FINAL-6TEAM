# 마이그레이션을 다시 돌리면 보류 변경 제약에서 멈춘다 — 데이터가 있는 DB 에서만

## 해결됨 (2026-10-05)

- 상태: **해결.** 032~035 가 이제 **제약이 이미 자기 값을 허용하면 건드리지 않는다**(좁히지 않는다).
- 확인 방법
  - 운영 개발 DB(`acop_cs`)의 복사본에서 재현 → 고친 뒤 `python -m app.infrastructure.db.migrate` **두 번 연속 통과**, 보류 변경 17행 그대로.
  - 실제 `acop_cs` 에서도 두 번 연속 통과(여행 126 · 일정 2,010 · 보류 변경 17 — 실행 전후 같음).
  - 회귀 시험 `tests/integration/db/test_migrations_rerun.py`(3) — 임시 DB 에서 **이유 여덟 가지마다 행을 넣은 뒤** 두 번 다시 돌린다.
    **고치기 전 파일로는 같은 `CheckViolation` 으로 실패하고**(옛 4개 파일을 넣은 사본으로 확인) 고친 뒤에는 통과한다.
- 수정 지점: `app/infrastructure/db/migrations/032_pending_consent.sql` · `033_pending_relaxed.sql` · `034_trip_chat_turns.sql` ·
  `035_pending_other_options.sql`(각 `DO` 블록) · `app/infrastructure/db/migrate.py`(`apply_all` 로 분리 — 시험이 같은 코드를 돈다).

### 아래는 **고치기 전에 쓴 기록**이다 (그대로 둔다)

★`[2026-10-05 원본]` 요식 데이터를 다시 적재하다 발견했다. 요식과는 무관한 다른 팀(활동·여행 변경)의 마이그레이션 문제다.

## 1. 위치

```
app/infrastructure/db/migrate.py                     모든 *.sql 을 번호 순서로 이어 붙여 한 트랜잭션으로, 매번 전부 다시 돈다
app/infrastructure/db/migrations/032_pending_consent.sql   pending_changes_reason_check 를 5개 값으로 다시 건다
app/infrastructure/db/migrations/033_pending_relaxed.sql   6개 값으로
app/infrastructure/db/migrations/034_trip_chat_turns.sql   7개 값으로
app/infrastructure/db/migrations/035_pending_other_options.sql   8개 값으로(최종)
```

각 파일의 블록은 「제약이 있으면 지우고 → 자기 시점의 값 목록으로 다시 건다」였다.

## 2. 재현

```
ACOP_DATABASE_URL=postgresql+psycopg://postgres@127.0.0.1:5433/<행이 있는 DB> python -m app.infrastructure.db.migrate
→ psycopg.errors.CheckViolation: check constraint "pending_changes_reason_check" of relation "pending_changes" is violated by some row
```

## 3. 실측

- 운영 개발 DB 의 `pending_changes.reason` 분포: other_options 5 · relaxed 4 · requested_options 4 · indoor_unknown 2 · ask_first 1 · indoor_unknown_options 1 (17행).
- 032 가 5개 값짜리 좁은 제약을 다시 걸면 `relaxed` · `requested_options` · `other_options` 행(13건)이 어긴다.
- **빈 DB 에서는 한 번도 안 걸렸다** — 행이 없고, 처음 돌릴 때는 번호 순서대로 넓어지기만 한다. 그래서 시험(빈 임시 DB)이 못 잡았다.
- ☆각 파일 머리말은 「다시 돌려도 안전하다 — 기존 행은 모두 옛 값이라 통과한다」였다. 자기 파일 다음에 값을 더한 마이그레이션이
  생길 수 있다는 것을 계산에 넣지 않은 **틀린 말**이다(032 를 쓸 때는 맞았고, 033~035 가 더해지며 틀려졌다).

## 4. 위험도

- 데이터가 있는 DB 에 마이그레이션을 **다시 돌릴 수 없다** — 새 마이그레이션을 적용하는 일반 절차가 막힌다. 한 번 실패하면 같은 트랜잭션의 뒤쪽
  마이그레이션(요식 220~223 포함)도 전부 적용되지 않는다. 데이터는 잃지 않는다(트랜잭션이 되돌려진다).
- 실제 서버에서 새 배포마다 같은 명령을 돌린다면 배포가 멈춘다.

## 5. 내가 잘못 보고했던 것의 정정

- 9/30 요식 재적재 뒤 「마이그레이션이 한 번 실패했다」고만 알렸고 원인을 요식 쪽이 아니라고 했다 — 맞았다.
  다만 그때는 「뒤쪽 마이그레이션은 시험된 적이 없다」는 점을 몰랐다. 032 를 넘기고 나서 뒤쪽 전체를 복사본에서 두 번 돌려 **새 실패가 없음**을 확인했다.
- 같은 모양(DROP 뒤 ADD CONSTRAINT)이 있는 다른 파일(003 · 038 · 214 · 218)은 이번 두 번 실행에서 걸리지 않았다.
  그러나 시험은 **보류 변경 제약 하나만** 지킨다 — 다른 표에도 같은 일이 생기면 같은 방식으로 시험을 더한다.
