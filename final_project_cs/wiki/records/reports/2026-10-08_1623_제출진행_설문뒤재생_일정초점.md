# 제출 진행·설문 뒤 재생·변경 메뉴·일정 초점

제출을 누르면 진행 화면부터 표시하고 실시간 진행으로 이어지며, 설문을 떠나는 순간부터 검증 결과를 재생한다. 변경 표시와 시간 되돌리기는 한곳에 모으고, 마커로 선택한 일정은 날짜 줄 아래에 놓는다. 공개 배포에는 아직 반영하지 않았다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| mock 서버 화면 시험 | 통과 | 48/48 = 100% |
| 단위 시험 | 통과 | 76/76 = 100% |
| 로컬 개발 DB 통합 시험 | 통과 | 27/27 = 100% |
| 실제 앱 화면 촬영 | 완료 | 8/8 = 100% |
| 사라진 브라우저 수정 복구 | 사용자에게 종류 확인 중 | 분모 모름 |

## 반영한 동작

1. 클라이언트 등록 화면에서 진행 화면을 먼저 그린 뒤 계획을 전송한다. 첫 응답으로 접수 번호를 받으면 전송 화면의 초기 상태를 넘겨 바로 SSE를 연결한다. 첫 조회를 기다리는 동안 빈 조회 화면으로 바뀌지 않는다. 첫 조회와 완료 신호가 겹치면 기존 조회를 기다린 뒤 최신 상태를 한 번 더 읽어 완료 신호가 누락되지 않게 했다.
2. 설문 화면에서는 실시간 결과를 계속 받되 검증 표시 재생을 멈춘다. 설문을 떠나면 같은 재생 상태에서 이어 간다. 완료 결과를 받은 순간이나 유휴 경고가 나오는 순간에 검증 컴포넌트가 다시 만들어져 재생을 소진하지 않게 했다. 이미 저장한 설문 답은 같은 고객의 다음 접수에 이어 쓰며, 첫 미응답 질문부터 표시한다. 질문 종류·뜻·선택지가 달라졌거나 다른 고객의 답은 이어 쓰지 않는다.
3. 필수 동의가 없으면 ‘이용을 위해서는 필수 약관 동의가 필요해요’ 안내와 함께 약관을 바로 연다. 기존 동의를 조회하는 동안의 실시간 단계·오류·재시도와 기존 화면 유지 동작은 보존한다.
4. 지도 아래 ‘! 개수’와 ‘변경 개수’를 같은 그룹에 놓았다. 변경 버튼을 누르면 바뀐 일정으로 걸러 보고, 바로 그 버튼 위에 ‘바꾼 시간 모두 되돌리기’와 ‘전체 일정 보기’를 연다. 시간 되돌리기는 기존 일괄 요청을 사용한다. 시간만 돌리는 기능을 장소 변경까지 취소하는 것처럼 표시하지 않았다. Escape는 메뉴를 닫고 변경 버튼으로 초점을 돌린다.
5. 마커로 선택한 일정은 날짜 선택 줄의 실제 아래 경계를 계산해 그 아래에 맞춘다. 마지막 일정도 올라올 수 있도록 목록 끝에 필요한 스크롤 여유를 둔다. 검증 중에는 추가되는 일정·이동 줄을 목록 가운데로 부드럽게 따라가며, 고객이 직접 스크롤하면 기존 따라가기 중단·복귀 동작을 유지한다.

관련 기능을 그룹으로 모으는 것은 [USWDS 버튼 그룹](https://designsystem.digital.gov/components/button-group/)의 원칙을 따른다. 공간이 부족할 때 보조 동작을 메뉴에서 여는 것은 [Carbon 메뉴 지침](https://www.carbondesignsystem.com/building-blocks/core/components/menu/guidelines)을 참고했다. ‘변경 → 시간 모두 되돌리기’ 배치는 이 화면의 공간과 작업 범위를 고려한 판단이다.

## 검증과 확인 범위

mock 서버 시험 48/48 (화면 반응): 제출·읽는 화면 11건, 약관·설문 34건, 변경 일괄 되돌리기·여러 날짜에서 마지막 일정 위치·검증 중앙 정렬 3건. 같은 시험을 촬영이나 최종 코드로 반복한 것은 총계에 더하지 않았다. 실제 Chrome, 휴대폰 375×812와 기본 1280×720 화면을 사용했다.

실서버 확인 (서버 응답): 안 했음. 공개 서비스에 배포하거나 공개 CS 앱 응답을 확인하지 않았다. 로컬 개발 DB를 쓰는 TestClient 통합 시험은 별도로 27/27 통과했다. 이전 약관 SSE API 검사는 [앞 단계 리포트](2026-10-08_약관확인_실시간진행_화면유지.md)에 있다.

단위 시험 54+15+7=76/76. 수정 파일 ESLint와 타입 검사 통과, 실제 화면 빌드 성공. [실행 근거 폴더](../evidence/2026-10-08_제출설문_일정초점/)에 원문 로그를 보관한다. 화면 검증 최종 명령은 웹 작업 폴더에서 `node node_modules/@playwright/test/cli.js test -c .tmp/consent-progress.config.ts --reporter=line plan-focus.spec.ts plan-check-redesign.spec.ts --grep '마커로 연|검증 중 마지막|바꾼 시간에는'`이다. 시험 전 `STUB_PORT`, `LIVE_PORT`, `PLAYWRIGHT_CHANNEL=chrome`을 지정한다. 시험용 구성은 공개 배포 구성과 분리했다.

검사 과정에서 두 번 정정했다. 초기 중앙 정렬 시험은 첫 조회가 끝나기 전에 결과 조건을 바꿔 재생 과정 자체를 건너뛰었다. 읽는 화면이 실제로 나타난 뒤 조건을 바꾸도록 고쳤다. 초기 마커 위치 시험은 ‘날짜 줄보다 아래’만 확인해 목록 끝에 머무는 경우를 놓쳤다. 날짜 줄 바로 아래에 실제로 도달하는지 상한까지 검사하고, 마지막 일정의 스크롤 여유 부족도 수정했다. 백업 사본의 소스 확장자로 인한 타입 검사 오류는 `.bak` 구분으로 고쳤고, 스크롤 콜백의 기존 React 최적화 검사 오류는 이벤트의 현재 요소를 직접 읽도록 수정했다.

## 사라진 브라우저 수정 — 아직 복구하지 못함

현재 열린 공개 페이지는 새로고침하지 않았다. 현재 페이지의 댓글 입력 UI와 이 대화의 저장된 초안 위치를 확인했지만 사라진 본문은 찾지 못했다. 확인 범위 밖의 다른 탭·다른 대화·브라우저 내부 미리보기 기록에 남아 있을 가능성은 배제하지 않았다. ‘스타일을 직접 조절한 미리보기’, ‘전송 전 댓글’, ‘이미 전송한 댓글’ 중 무엇인지 사용자에게 확인을 요청했다.

[Codex 브라우저 공식 안내](https://learn.chatgpt.com/docs/browser?surface=app)는 요소를 선택해 댓글을 적고 저장한 뒤 대화로 보내는 흐름과, Adjust에서 글자·간격·색을 미리 보는 흐름을 구분한다. 사라진 수정의 종류를 확인하기 전 복구 성공이나 영구 삭제를 단정하지 않는다. 로컬 HTML을 브라우저에 직접 여는 요청은 URL 정책으로 차단되어 우회하지 않았고, 결과 이미지를 대화와 파일 미리보기로 제공했다.
