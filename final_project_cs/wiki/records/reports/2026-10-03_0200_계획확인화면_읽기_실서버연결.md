## 수행 내용

1. **서버 응답 → 화면 데이터(읽기 부분)** — [from-intake.ts](../../../frontend/apps/web/src/features/plan-check/from-intake.ts) `readingOf`
   - 서버 단계: `received` → 받았어요, `transcribing`·`reading` → 일정 읽기
   - 원문 줄: 소스를 이어 번호를 매기고, 읽었는지를 함께 옮긴다.
   - 읽은 줄이 된 일정: 제목·일차·시각을 옮긴다. 서버가 정하지 않은 일차·시각은 비워 둔다. 고객이 뺀 항목은 제외한다.
   - 결과(장소·운영시간 확인, 장소별 검사, 이동)는 서버에 해당 단계·칸이 없어 옮기지 않았다.
2. **실제 경로 연결** — [intake-review.tsx](../../../frontend/apps/web/src/features/intake-review/intake-review.tsx)
   - 서버가 읽는 동안: 기존의 단순 대기 칸 대신 새 화면을 보인다.
   - 읽기가 끝나면: 새 화면이 남은 줄을 그리고 0.8초 머문 뒤 기존 접수 확인 화면이 이어받는다.
   - 화면 갱신은 기존 1.5초 조회 그대로다.
   - 이미 읽기가 끝난 접수와 읽지 못한 접수(`fatal`)는 바로 기존 화면을 보인다.
   - 화면 틀(새 화면 = 휴대폰 틀, 기존 화면 = 여정 틀)은 페이지가 아니라 화면이 고른다([page.tsx](../../../frontend/apps/web/src/app/intakes/%5BintakeId%5D/page.tsx)).
3. **화면 쪽 보강**
   - `PlanCheck`가 휴대폰 틀(`DeviceFrame`)을 품고, 다 그린 뒤 잠깐 머물러 알리는 `onCaughtUp`을 받는다.
   - 찾은 일정의 일차·시각이 없으면 그 부분을 빼고 보인다.
   - 주석의 「연결은 백엔드」 문구를 지금 결정에 맞게 고쳤다.
4. **테스트용 모방 서버** — 실서버처럼 읽는 중에도 원문 줄(읽기 전)을 준다(`tests/live/stub-server.mjs`).
5. **문서** — 인계 문서(분담·§2·§3·§4·§6), [웹 README](../../../frontend/apps/web/README.md) 화면 표, [화면별 연동 상태](../../external/web-screen-api.md), [목업 안내](../../../frontend/apps/web/mockups/README.md)를 갱신했다.

## 작업 중 바로잡은 것

- 새 모방 서버 시험이 처음에 실패했다. 읽기가 끝난 뒤 새 화면이 마지막 줄을 0.28초 만에 그리고 곧바로 넘어가서, 시험이 「읽음」 상태를 잡기 전에 화면이 바뀌었다. 사용자도 마지막 줄을 볼 틈이 없는 셈이었다.
- 다 그린 뒤 **0.8초 머문 다음** 넘어가게 고쳤다.
- 순간적인 상태는 브라우저 시험에서 확인하지 않는다. 줄→찾은 일정 대응은 단위 시험(`from-intake.test.ts`)으로 옮겼다.

## 검증

명령과 출력은 [실행 근거](../evidence/2026-10-03_0200_계획확인화면_읽기_실서버연결_검증.md)에 있다.

| 검사 | 결과 |
|---|---|
| 타입 · 린트 | 0건 · 0건 |
| 단위(vitest 전체) | 156/156 = 100%(새 `from-intake.test.ts` 3개 포함) |
| live 빌드 전체(테스트용 모방 서버) | 58/58 = 100% — 새 시험 「서버가 읽는 동안 새 계획 확인 화면이 서버의 원문 줄을 읽는 중으로 보이고, 읽기가 끝나면 확인 화면으로 넘어간다」 포함. 기존 57개도 새 읽기 화면이 끼어든 뒤 모두 통과 |
| demo 브라우저 — `plan-check.spec.ts` | 5/5 = 100% |
| 실서버(로컬 API 8042 + live 웹 3100) | 계획 4줄을 올림 → 새 화면에 서버의 줄 4개가 「읽는 중 / 기다리는 중」으로 보임 → 읽기가 끝나 기존 확인 화면(일정 3개, 「여행 등록」)으로 넘어감. 서버 로그: 새 키 발급 → `POST /v1/web/trip-intakes` 202 → `GET …/{id}` 200 ×3. 여행 등록은 누르지 않았다 |

**실서버 확인의 한계**
- 앱 내장 브라우저가 화면을 초당 2장만 그리는 상태였다. 그래서 줄이 차례로 「읽음」이 되는 움직임 자체는 눈으로 보지 못했다(이 부분은 단위·모방 서버 시험이 확인한다).
- 같은 브라우저 저장소를 쓰는 사용자 탭에 새 로컬 시험 사용자 키가 생겼고, 앱 언어가 한국어로 바뀌었다(로컬 시험 DB · 브라우저 설정).

## 남은 문제·다음 작업

1. **2단계 결과 보기** — 결과 화면을 실제 데이터로 새 화면에 옮긴다. 장소·좌표·제목·판정은 지금 계약으로 가능하다. 장소별 검사·이동은 협의 필요다.
2. **진행 알림(SSE)** — `GET …/events`로 바꾸면 1.5초 조회보다 빨리 보인다.
3. **서버 협의** — 확인 단계, 장소별 검사, 이동, 진행 이벤트 형식(인계 문서 §4).
4. **백엔드 공유** — 이 화면의 연결은 이쪽이 맡는다는 사실을 백엔드 담당에게 알려야 한다. `role-manager`가 웹 코드를 자주 바꾼다.
