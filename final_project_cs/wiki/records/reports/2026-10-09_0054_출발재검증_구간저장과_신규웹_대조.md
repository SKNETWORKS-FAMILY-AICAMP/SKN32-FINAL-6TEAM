## 저장 변경과 회귀 판정

내부 `detail.departure_context` 버전1은 옵션ID별 선택 구간, 노선·승하차ID/순번, 검증 입력의 접근/이탈/환승 정보, 당시 모델 대기·승차 결과, 장소 좌표, 시간표·규칙 판과 계산 조건을 복사한다. 기존 모델의 분 단위이며 실시간 측정으로 부르지 않는다. 공개 routes/options 허용 칸은 그대로다. plan의 이동 항목·wiring 구간 결과·일정 생성·장소 변경·재경로 저장에 전달했다. 장소 변경 뒤 다시 계산하지 못하는 가까운 유지/추정 경로는 옛 문맥을 제거한다.

확대 v7의487통과는 저장 변경 이전이다. 저장 변경 후 v8은532통과·5실패였다. 실패5개는 기존 고객 값과 새 내부 문맥의 혼합 검사였다. 기존 골든의 경로/시각/요금은 그대로 엄격 비교하고 내부 문맥은 옵션 대응·모델 단위·구간 동일성으로 별도 검사한다. CLI/함수 호출의 내부 계산값도 호출 시각 하나를 제외하고 같아야 한다. 원래 입력 detail의 note·item id 보존도 유지한다. 골든 원문을 다시 맞춰 쓰지 않았다. 해당5검사 통과 뒤 최신 v9에서537통과·220제외·경고1·260.69초를 확인했다. 저장·장소 변경 관련30통과도 별도 로그에 보존했다.

## 신규 웹 대조와 근본 원인 조사

대한문→서울광장을 브라우저에 입력해 네이버101m·2분·횡단보도1회, 다음236m·4분을 얻었다. [원문 보관](../../../../datasets/mobility/raw/kakao_golden/additional_web_2026-10-09_v1/)은 두 조회 시각·장소ID·화면·파일 해시를 보존한다. 시설쌍1개·조회2개이며 독립 구간2개가 아니다. 출입점 좌표·경로 형상 정렬 전이므로 제품 정확도 평가에 편입한 새 표본은0건이다. 지도 개발자 API 직접 호출0회다. 구글 이전 관측은 앞 보고서에 있으며 이번 W03 구글 조회는 아직 하지 않았다.

현재 지도 생성기의 classify_foot는 `area=yes` way를 제외한다. 이는 보행 광장 면 자체를 그래프에 만들지 않는 코드 경계이며, 그 광장에 별도 footway가 하나도 없다는 주장이나 이번 웹 차이의 확정 원인은 아니다. 이 두 문제를 구별한다.

[2015 원문 연구](https://drops.dagstuhl.de/entities/document/10.4230/OASIcs.ATMOS.2015.1)의 §3.1·3.2·4를 읽고 보도/횡단·광장 장애물·진입점 연결을 함께 처리하는 후보를 기록했다. [2026 공개 구현 기록](https://www.openstreetmap.org/user/Paco%20Albacete%20Chicano/diary/409229)은 영역 복원→중심 골격→진입점 연결→가상 보행 간선을 사용하며 알려진 제한도 적었다. 코드·PR 자체 검증 전 후보로 남긴다. [2026 고령자 보행 연구](https://arxiv.org/abs/2607.24795)는 초록·메타만 확인했으며 현장 선호를 우리 정확도로 옮기지 않는다. [등록부12개](assets/2026-10-09_mobility_research_v3/research-register.json)는 검색 기준2026-10-09와 읽은 범위·도입 전제를 보존한다. 관련 공개 조사이며 전수검색이 아니다.

[21개 기능 시각화v8](assets/2026-10-09_mobility_readiness_v8/mobility-readiness.html)에 저장 변경과 새 웹 차이를 추가했다.21행·로컬 링크7개를 정적으로 확인하고 PNG를 직접 확인했다. HTML의 실제 브라우저 렌더링은 미확인이다. v7의 v6 표기 잔존은 v8 새 산출물에서 정정했고 이전 판은 덮지 않았다. 조건부4·개선필요9·추가검증8은 기능 분류이며 준비율이 아니다.
