# Oracle ARM 식사 오연결·검색 자료·질문 분류 복구

식사 요청에 관광지가 연결되던 경로를 고치고 비어 있던 두 검색 표를 채웠습니다. 실제 채팅에서 식사 질문·표현 변경·예약 취소 구분·범위 밖 질문을 확인했습니다. 정확한 장소 이름보다 가까운 부속 장소가 먼저 나오는 정렬도 보완했습니다. 응답 지연과 제품 전체 검증은 완료로 처리하지 않습니다.

| 확인 | 최종 관측 | 범위 |
|---|---|---|
| 장소 검색용 임베딩 | 2,041/2,041 = 100% | 현재 적재 스크립트의 적격 장소; 전체 장소 목록 7,996개의 완성도 아님 |
| 안내 검색 청크 | 11/11 = 100% | 현재 여행 안내 6개 + 기존 서비스 안내 5개 |
| 실제 검색 진단 | 6/6 = 100% | 고정 개발 질문의 해당 문서 top1, 타 고객 검색 결과 없음 |
| 실제 채팅 진단 | 4/4 = 100% | 개발 1건·사전 보류한 표현 3건; 독립 제품 평가셋 아님 |
| 장소·접수·자료 단위 검사 | 71/71 = 100% | 실제 API 시험과 분리한 코드 회귀 |
| 질문·정책·기능 안내 단위 검사 | 146/146 = 100% | 결정 대상 보호 포함 |
| 계약·보안 회귀 | 375/375 = 100% | 최종 장소 정렬 코드 포함 재실행 |
| 기존 기능 관문 | 26/26 = 100% | 관문 명령의 전체 항목; Oracle ARM 전체 기능 인수 아님 |

## 원인과 수정 범위

1. **종류를 확인하기 전 이름 일치로 장소를 확정했습니다.** 식사 요청은 자체 장소·관광공사 자료·카카오 결과 모두 식사 종류가 맞는지 확인합니다. 관광지 좌표를 식당 좌표로 대신 쓰지 않습니다. 기존 시장에서의 식사 추론과 숙소 식사 규칙은 별도입니다.
2. **실제 검색 표가 비어 있었습니다.** 현재 wiki·코드에서 확인한 식사·활동·이동·취소·날씨·접근성 안내를 적재했습니다. 오래된 공통 무료 취소 기한 안내는 적재하지 않았습니다. 장소 임베딩은 이름·분류로 만들며 사진·소개글·주소를 새로 적재하지 않았습니다. 빈 벡터를 정상 자료로 대신 쓰지 않았습니다.
3. **모델이 일반 식사 질문을 `other`로 분류했습니다.** 모델 교체·추가 학습 없이 요청 해석 지침에서 장소 선택 기준·확인 절차도 여행 질문임을 명시했습니다. 검색 결과는 검증된 고객 안내 문장과 연결됩니다. 모델이 웹을 자율 탐색하거나 자유롭게 업체 조건을 만들어 내는 구조로 바꾼 것이 아닙니다.
4. **이름 앞부분 일치와 정확한 이름 일치를 같은 순위로 취급했습니다.** 경복궁 검색에서 가까운 화장실이 먼저 나오던 결과를 재현했습니다. 정확한 이름 → 앞부분 일치 → 그 밖의 순으로 나누고, 각 단계 안의 적합성·거리 정렬은 보존했습니다. 부속 장소를 관광 활동으로 분류하는 문제 전반을 해결했다고 확대하지 않습니다.

## 실제 질의와 지연

| 질의 | 내용·행동 판정 | 응답 시간 |
|---|---|---|
| 식당 이름 없이 한식 점심만 적으면 어떻게 하나요? | 통과 | 68.53초 |
| 식당이 아직 안 정해졌는데, 식사 장소를 정하는 기준은 뭔가요? | 통과 | 65.11초 |
| 일정에서 식당을 빼면 업체 예약도 취소되는 건가요? | 통과 | 67.51초 |
| 오늘 어떤 주식을 사야 돈을 벌까요? | 통과 | 59.80초 |

기존 모델 프로세스가 계속 실행 중인 상태에서 관측했습니다. 첫 모델 적재 시간으로 해석하지 않습니다. 마지막 관측은 `2026-10-11T19:53:52.132172+00:00`이며 모델 PID는 최소 수정 전후 동일했습니다. 실패·미완료를 뺀 정확도 표가 아니라 고정한 네 요청 전체의 진단입니다. 이 표본을 독립 보류 검증이나 제품 채택 근거로 쓰지 않습니다. 이전 판의 식사 질문 실패·취소 질문 성공과 지연도 원본에 보존합니다.

실제 별도 시험 접수에서 경복궁·한식 점심·박물관 3개 항목을 확인했고 식사는 식당 후보와 연결됐습니다. 식당 후보의 위치 확인과 영업시간·예약 완료는 다릅니다. 검색·대체안 네 경로의 HTTP200과 식당/활동 후보 존재를 확인했으며, 후속 이름 검색에서는 경복궁 자체가 첫 결과인지 별도로 판정했습니다. 기존 고객 여행이나 기존 접수의 저장된 오연결을 소급 수정하지 않았습니다.

## 운영 반영과 실패 보존

Oracle ARM의 진행 중 자동 업데이트·모델 시험을 중단하지 않고 잠금과 모델 유휴 상태를 기다려 API만 최소 재시작했습니다. 현재 API 이미지 `tripilot-arm-api:1647e8990df9`는 실행·healthy·OOM 없음이며, 현재 수정 파일 해시와 자동 업데이트 보존 파일 해시가 일치합니다. 자동 업데이트에는 지식 자료 포함과 변경 충돌 감지를 추가했습니다. 이후 develop의 보호 대상 파일이 바뀌면 오래된 코드로 조용히 덮지 않고 재검토를 요구합니다.

적재 시도는 성공 **1/5 = 20%**, 실패 **4/5 = 80%**입니다. 앞의 스크립트 경로·가드레일 마운트·누락 적재 모듈·서비스 자료 준비 실패를 보존했고 각 원인 수정 후 새 시도로 진행했습니다. 이는 모델 정확도 분모가 아닙니다. 최종 적재는 정상 종료했습니다. 첫 검색 시험의 422 네 건은 화면 표시 ID를 UUID로 보낸 시험기 오류이며, 같은 접수에서 올바른 UUID/index로 재확인했습니다. 첫 채팅 검사기의 공개 응답에 없는 내부 출처 ID 요구도 판정 오류로 분리하며, 원문을 지우지 않고 후속 검사는 실제 행동·안내 내용·일정 보존으로 판정했습니다. 장소 정렬 첫 반영은 로컬 CRLF와 Oracle ARM LF의 해시 차이로 변경 전에 중단됐고, 내용 동일성을 확인한 두 번째 시도만 적용했습니다. 최종 상태 수집기의 모델 목록 경로 404도 앱 실패로 합산하지 않았습니다.

질문 지침·검색 정렬 수정 전 코드, 검색 표 덤프와 자동 업데이트 제어 파일은 Oracle ARM에 보존합니다. 초기 장소 해석·안내 코드 원문은 이미 로컬에 보관한 inventory/preflight 실행 기록에도 남아 있습니다. API 내부 백업만으로는 컨테이너 교체 뒤 보존을 보장하지 않으므로 원격 보존 위치를 컨테이너 밖으로 분리했습니다. DB 덤프와 코드 백업의 새 로컬 전송은 자동 승인 심사가 민감 자료와 구체적 전송 승인 부족으로 거절해 수행하지 않았습니다. 같은 기계 안의 백업 보존으로 대체했으며 전송을 우회하지 않았습니다. [로컬 코드 백업](../../../app/domains/travel_ops/components/intake/_backup/)과 이 보고서 갱신 전 문서 백업은 아래 기록에서 찾습니다. 원격 접속 정보·키·환경 파일은 공용 문서에 기록하지 않습니다.

## 남은 범위

- 실제 채팅은 약 60~69초로 여전히 느립니다. 이번 변경을 응답 속도 해결로 보고하지 않습니다.
- 일반 웹검색은 이 Oracle ARM 여행 채팅에 연결하지 않았습니다. [Ollama Web Search](https://docs.ollama.com/capabilities/web-search)는 무료 계정과 API 키가 필요하고, [SearXNG Search API](https://docs.searxng.org/dev/search_api.html)는 자체 운영 검색의 JSON 결과를 제공합니다. 모델 추론 경로와 검색 호출 경로의 비용·외부 전송·시간 상한은 도입 시 따로 정합니다.
- 기존 서비스 안내 자료 적재와 새 `answer_service` 코드의 운영 도달성은 별도입니다. 안전 대피 자료·외부 알림·빠진 외부 키·독립 정확도·전체 제품 배포 완료는 이번 작업의 완료로 포함하지 않습니다.
