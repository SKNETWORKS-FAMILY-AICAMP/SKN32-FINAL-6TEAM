- 고객이 규정(취소·환불·날씨·이동 등)을 물으면 제품이 규정 조각 130개에서 3개를 찾아 고객용 문장을 그대로 싣는다. 이 검색이 얼마나 맞는지 **제품 코드를 그대로 불러** 쟀다(질문 340개 + 섞은 입력 2,340건 + 다국어 480건 + 응답 시간 360호출).

- **근거 정확성은 설계대로 100%**: 답에 실린 규정 문장 334개가 전부 출처 조각의 고객용 문장과 한 글자도 다르지 않다(제품이 모델로 규정 문장을 쓰지 않는다). 근거 없는 규정 문장 발송 0건.

- **개선 시험 하나**: 색인에 쓰는 글을 「직원용 본문」에서 「문서 제목 + 절 제목 + 고객용 문장」으로 바꿔 같은 질문을 다시 쟀다. 정답을 보인 비율이 B 43.8% → 64.6%, A 73.0% → 91.0%. **대가도 있다**: 예약 요청 같은 여행 대화 발화에 규정을 잘못 보이는 비율이 22.3% → 36.7%(라벨 없는 300건).

## 2. 규정 검색 정확도 (기준선)

「정답 줄」 = 질문에 직접 답하는 규정 조각. 답 있음 질문만 센다(A 100문제 · B 48문제).

| 지표 | A | B |
|---|---:|---:|
| Recall@1 = 정답이 맨 위(Precision@1 과 같다) | 0.660 (66/100) | 0.375 (18/48) |
| Recall@3 | 0.820 (82/100) | 0.625 (30/48) |
| Recall@5 | 0.850 (85/100) | 0.667 (32/48) |
| Recall@10 | 0.920 (92/100) | 0.729 (35/48) |
| Precision@3 | 0.273 | 0.208 |
| F1@3(질문별 평균) | 0.410 | 0.312 |
| MRR | 0.750 | 0.509 |
| nDCG@10 | 0.788 | 0.554 |

Precision@k 는 정답 줄이 1~3개뿐이라 k 가 커질수록 구조적으로 낮아진다 — Precision 은 k=1 로, 합격선은 Recall@3 으로 읽는 것이 맞다. B 의 「부분 답」 62문제(관련은 있으나 직접 답은 못 하는 줄)는 따로 세었다: 관련 줄이 상위 3개 안 32/62 = 51.6%.

## 3. 문턱(τ) 0.55 판정

양성 = 답 있음 질문(A 100 · B 48). 음성 = 코퍼스에 없는 질문 + 주제 밖(A 60 · B 50). 「답함」 = 고객용 문장이 하나라도 보이는 것.

| 문턱 | A Precision | A Recall | A F1 | B Precision | B Recall | B F1 |
|---:|---:|---:|---:|---:|---:|---:|
| 0.45 | 0.792 | 0.990 | 0.880 | 0.635 | 0.979 | 0.770 |
| 0.50 | 0.942 | 0.970 | 0.956 | 0.852 | 0.958 | 0.902 |
| **0.55 (운영)** | 0.979 (95/97) | 0.950 (95/100) | 0.964 | 0.975 (39/40) | 0.812 (39/48) | 0.886 |
| 0.60 | 1.000 | 0.770 | 0.870 | 1.000 | 0.500 | 0.667 |
| 0.65 | 1.000 | 0.430 | 0.601 | 1.000 | 0.208 | 0.345 |

- **0.55 가 맞나**: F1 이 가장 높은 문턱은 A 에서 0.55(F1 0.964), B 에서 0.525(F1 0.926)이다 — B 에서 0.55 를 쓰면 F1 0.886 으로 조금 낮다. A 에서 고른 값을 B 에, B 에서 고른 값을 A 에 써도 F1 은 0.886~0.955 라서 **0.55 는 이 두 세트에서 크게 틀린 값이 아니다.** 다만 문턱을 0.60 으로 올리면 B 에서 정답을 절반 놓친다(Recall 0.500). 곡선 전체(문턱 0.30~0.80)는 [rag_metrics_report.txt](../../../../program/scripts/rag_gate/results/rag_metrics_report.txt) 의 「곡선 전체」 표에 있다.
- 같은 세트에서 고른 문턱은 낙관적이다. 문턱을 바꾸려면 세 번째 세트(사람이 쓴 질문)가 먼저 필요하다.
- **「비슷하지만 다른」 질문**은 양성·음성에 넣지 않고 따로 셌다: 규정을 보여 준 비율 A 11/20 = 55.0% · B 41/62 = 66.1%. 이 질문들은 정답이 모호해서 「보여 주면 틀렸다」고 단정하지 않는다.

## 4. 근거 정확성과 환각 방지

### 4-1. 규정 답 경로 (기준선)

| 지표 | 목표 | 현재 값 |
|---|---|---|
| 인용 정확도(답의 규정 문장이 출처 조각의 고객용 문장과 글자 그대로 같음) | 100% | **334/334 = 100%** (규정 문장을 보인 답 189건) |
| 출처 없는 규정 문장 | 0 | **0/334** |
| 근거 없는 규정 문장 발송 | 0 | **0건** (제품이 모델로 규정 문장을 쓰지 않는 구조 + 위 시험) |
| 답 없는 질문(코퍼스에 없음·주제 밖)에 규정을 보임 = 새어 나감 | 0 | **3/110 = 2.7%** (A 2/60 · B 1/50), 거른 것 107/110 |
| 주제 밖(인사·잡담)을 규정 답으로 오인하지 않음 | — | 39/40 = 97.5% |

새어 나간 3건: 「한국 식당에서 팁 줘야 하나요?」 · 「내 다음 일정 몇 시였지?」 · 「한국 식당 팁 줘야 해요?」(점수 0.55~0.60 — 문턱 바로 위).

**한계**: 「100%」는 설계 때문에 나오는 값이다(규정 문장을 모델이 쓰지 않고 저장된 문장을 그대로 싣는다). 이 지표는 **저장된 규정 문장 자체가 맞는지는 말해 주지 않는다**(규정 본문의 사실 검수는 별도). 또 「답에 실린 문장이 질문에 맞는가」는 다른 문제다 — §5 의 「정답 줄을 보인 비율」이 그것이다.

### 4-2. 알림 번역의 숫자 보호 — 실제 모델 호출로 쟀다

제품 번역 함수(`app/infrastructure/notify/translate.py`)는 번역 결과의 숫자를 **출현 횟수까지** 원문과 대조해 어긋나면 번역을 버린다(시각이 틀린 알림이 번역 실패보다 나쁘다는 결정). 이 보호 장치를 실제 모델로 시험했다.

**조건**: 2026-10-06 17:50 · 모델 `gemma4:12b`(제품 기본 번역 모델, x600 서버 Ollama) · 제품 번역 함수와 제품 시스템 지시문을 그대로 사용 · 알림 40개 × 영어·일본어·중국어(간체) = **120호출, 1회** · 알림 40개는 제품 알림 문체를 따라 내가 쓴 **합성 문구**(시각·금액·버전·수 표현 포함, 실제 발송 문구가 아니다) · 번역 지연 p50 2.4초 · p95 3.2초(2개 동시, 원격 왕복 포함).

| 지표 | 목표 | 현재 값 |
|---|---|---|
| 보호 장치가 통과시킨 번역 | — | 115/120 = 95.8% |
| 보호 장치가 거른 번역(한국어 원문으로 대신 발송됨) | — | 5/120 = 4.2% |
| **통과했는데 시각(HH:MM)·쉼표 금액이 어긋난 번역**(내 독립 검사) | 0 | **0/115** |
| **통과했는데 금액의 통화 단위가 바뀐 번역** | 0 | **1건 — 일본어 「35,000원」→「35,000円」**(원→엔). 금액이 든 알림 9개 × 3언어 = 27건 중 일본어 2건이 엔으로 바뀌었고, 1건은 이 보호 장치를 통과했다. 영어·중국어는 0/9 |

- **새어 나간 것은 숫자가 아니라 단위였다.** 제품 보호 장치는 숫자(출현 횟수까지)만 대조한다. 단위(원→엔)는 못 본다 — 금액 숫자는 그대로라 통과한다. 일본어에서 35,000원이 35,000엔으로 가면 약 9배 비싼 값으로 읽힌다.
- **단위 대조를 더하면(제품 코드는 안 고치고 저장된 120건에 가상으로 적용)**: 원문에 「숫자+원」이 있으면 번역에 원/won/ウォン/韩元 중 하나가 있어야 한다는 규칙을 더하면 통과했던 115건 중 **1건(위 35,000円)만 새로 걸리고 오탐은 0건**이다(금액이 든 27건 중 22건 통과·4건은 기존 숫자 대조가 이미 거름·1건 새로 걸림). 일본어 1건·합성 문구 9개라는 작은 표본의 값이다.
- **거른 5건은 모두 안전한 쪽 실패다.** 시각·금액은 맞았고 「1인」 → 「per person」(숫자 1 사라짐), 「5개 중 첫 번째」 → 「1つ目」(1 생김), 「두 곳」 → 「2か所」(2 생김) 같은 **수 표현**이 숫자로 바뀌어 걸렸다. 한국어 원문이 나가므로 틀린 알림은 아니지만 번역 실패율이 4.2% 이다.
- **대괄호 머리표**: 내 합성 문구의 `[변경]` 같은 머리표를 모델이 `[Change]`·`[変更]` 로 번역했다(통과 115건 중 112건). 제품 시스템 지시문은 머리표를 그대로 두라고 하는데 모델이 따르지 않는다. 제품의 `[재생]` 표시는 `discord.py` 의 `_compose` 가 본문에 붙이는데, 번역 앞에서 붙는지 뒤에서 붙는지는 **이번에 확인하지 못했다.**
- **재는 방법의 한계**: 독립 검사는 내가 쓴 정규식(시각 · 쉼표 금액 · 통화 단위 · 머리표)이다. 의미가 바뀐 번역(예: 「앞당겨졌다」→「늦춰졌다」)은 사람이 읽어야 알 수 있어 **측정하지 못했다.** 합성 40문구 × 3언어 1회라 편차는 모른다.
- 단위 테스트(`tests/unit/travel/test_notice_translation.py`): 15개 통과 — 이 시험은 모델을 흉내 낸 입력이라 위 실측과 다른 것을 본다.

### 4-3. 보기 밖 값 반영(일정 변경 초안) — 측정하지 못했다

- **못 한 이유**: 「보기 밖 값」을 막는 곳은 일정 변경 초안을 만드는 체크리스트(planner · decision_unit)이고, 그 경로를 끝까지 재려면 초안을 만드는 모델 호출이 필요하다. 그 경로는 시나리오 러너(`eval/runners/travel_scenarios.py`, multi-agent flow 세션 담당)가 재고 있어 겹치지 않으려고 이번 측정에서 뺐다. 그쪽 참고값: 시나리오 30건 통과 30/30 · 위반 0(모델은 흉내, `eval/reports/arch_metrics_20261006_163909.json`) — 이 값은 **모델을 실제로 부른 값이 아니다.**
- **대신 잰 가까운 지표(같은 종류의 위험)**: 「일정 항목 하나를 고르게 시킨 모델이 목록에 없는 번호를 냈는가」. 한 줄로 이은 시험(835문제, 전문가 모델 호출 502~835회/변형, 변형 10개)에서 **목록 밖 번호 0건**, 형식 오류(JSON 아님) 12건 — 제품 코드는 목록 밖 번호를 「없음」으로 버린다. 이 시험은 항목 짚기 단계이고 초안 만들기가 아니다.

## 5. 응답 시간 · 오류율 (기준선, 색인 개선 후는 안 쟀다)

조건: 이 PC(Windows)에서 제품 코드를 그대로 호출. 임베딩 = x600 서버 Ollama(SSH 포트포워딩 왕복 포함), 벡터 검색 = 이 PC의 로컬 개발 DB(pgvector). 질문 120개(A·B 각 60) × 3회 = 360호출, 호출마다 질문 임베딩 캐시를 비웠다.

| 구간 | 호출 | p50 | p95 | 최대 | 오류 |
|---|---:|---:|---:|---:|---:|
| 질문 임베딩만(Ollama) | 360 | 396ms | 579ms | 884ms | 0/360 |
| 검색(임베딩 + pgvector, top_k 3) | 360 | 435ms | 588ms | 777ms | 0/360 |
| 규정 답 전체(`question_reply`) | 360 | 431ms | 596ms | 890ms | 0/360 |
| pgvector SQL 만 | 300 | 7ms | 10ms | 24ms | 0/300 |

- **응답 시간의 거의 전부가 질문 임베딩이다**(SQL 은 7ms). 운영에서 임베딩이 같은 기계 안에서 돌면 더 빨라질 가능성이 높다 — 「예상」이지 잰 값이 아니다.
- **오류율**: 정확도 패스 680호출 중 오류 0건. 검색 실패 때 고객에게 「오류가 나서 규정에 관한 답은 드리지 못했어요」가 나가는 경로는 코드에 있으나 이 측정에서는 한 번도 일어나지 않아 **그 경로가 실제로 동작하는지는 이 측정이 보여 주지 않는다.**
- 개선 색인(E)의 응답 시간은 재지 않았다. E 는 이번에 제품 코드가 아니라 측정 스크립트가 같은 임베딩 함수로 색인을 만들어 비교한 것이라, 운영 시간을 대표하지 못한다.

## 7. 개선 시험 — 색인에 쓰는 글을 바꾸면 (개선 전 → 후)

- **바꾼 것(하나)**: 규정 조각을 임베딩할 때 쓰는 글. 운영은 직원용 본문을 쓴다. 개선판 E 는 「문서 제목 + 절 제목 + 고객용 문장」을 쓴다(고객이 읽는 문장이 질문과 낱말을 더 공유하므로).
- **바꾸지 않은 것**: 제품 코드 · DB · 문턱 0.55 · top_k 3 · 질문 · 임베딩 모델. 측정 스크립트가 제품과 같은 임베딩 함수로 E 색인을 메모리에 만들어 검색 자리만 바꿔 끼웠다. 같은 질문·같은 `question_reply` 를 불렀다.

### 7-1. 규정 검색 정확도

| 지표 | A 전 → 후 | B 전 → 후 |
|---|---|---|
| Recall@1 | 0.660 → **0.820** | 0.375 → **0.521** |
| Recall@3 | 0.820 → 0.930 | 0.625 → 0.729 |
| Recall@5 | 0.850 → 0.960 | 0.667 → 0.792 |
| MRR | 0.750 → 0.885 | 0.509 → 0.654 |
| nDCG@10 | 0.788 → 0.910 | 0.554 → 0.701 |
| 문턱 0.55 답할 질문 Recall | 0.950 → 0.980 | 0.812 → 0.896 |
| 문턱 0.55 F1 | 0.964 → 0.975 | 0.886 → 0.945 |
| **정답 줄을 보인 비율** | 73/100 → 91/100 | **21/48 → 31/48** |
| 틀린 줄만 보인 비율 | 22/100 → 7/100 | 18/48 → 12/48 |
| 답 없는 질문에 규정을 보임(새어 나감) | 2/60 → 3/60 | 1/50 → **0/50** |
| 「비슷하지만 다른」 질문에 규정을 보임 | 11/20 → 15/20 | 41/62 → 42/62 |

- B 에서 「개선 후에만 맞은 질문 10개 · 개선 전에만 맞은 질문 0개」(정확 검정 p = 0.002). A 는 19개 대 1개(p = 4×10⁻⁵).
- **A 의 개선폭은 부풀려져 있다.** A 의 질문은 고객용 문장을 보고 쓴 것이고 개선판 색인이 바로 그 고객용 문장이라 낱말이 겹친다. **독립 세트 B 의 값(정답 줄을 보인 비율 43.8% → 64.6%)이 판단 근거다.**

### 7-2. 대가 — 규정이 아닌 말에 규정을 보이는 비율

| 입력 | 건수 | 전 → 후 |
|---|---:|---|
| 일상 대화 + 구어체 | 1,300 | 40 → 39 (3.1% → 3.0%, 차이 없음) |
| 관광지 질문 | 400 | 10 → 20 (2.5% → 5.0%) |
| **여행 대화 발화(KLUE-WoS)** | 300 | **67 → 110 (22.3% → 36.7%)** |

색인 개선 뒤 새로 규정이 보인 발화 47개 중 표본 22개를 눈으로 봤다: 「가격은 상관없어요」 · 「일요일 08:44에 2명 예약해 주세요」 · 「택시 전화번호랑 요금은 어떻게 되죠?」처럼 **규정 질문이 아닌 것이 대부분**이다. 즉 개선판은 규정 질문을 더 잘 찾는 대신 **예약·검색 요청 같은 여행 말에 규정을 붙이는 일이 늘었다.** 제품에서는 이런 발화가 먼저 의도 분류를 거쳐 규정 질문일 때만 이 경로로 들어오므로 실제 영향은 분류기 정확도에 달려 있다 — 이 시험은 분류기를 거치지 않았다(**안 한 것**).

## 8. 판단과 고치면 좋을 것

**판단**: 색인 개선은 **규정을 묻는 질문의 정확도를 분명히 올린다**(독립 세트 B 에서 정답을 보인 비율 +20.8%p, 개선 후만 맞은 10개 · 반대 0개). 반면 **규정이 아닌 여행 말에 규정을 붙이는 비율이 늘어난다**(KLUE-WoS 22.3% → 36.7%). 둘의 균형은 제품이 이 경로로 보내는 입력의 분포에 달렸고 이번 시험은 그 분포를 모른다. 따라서 「바로 운영에 넣자」가 아니라 **분류기 뒤에서(규정 질문으로 분류된 입력만 대상으로) 다시 재고 정하자**가 내 의견이다.

**고치면 좋을 것 (제품 코드는 안 고쳤다)**
1. 색인 글을 「문서 제목 + 절 제목 + 고객용 문장」으로 바꾸는 안(위 7절). 바꾼다면 문턱도 같이 다시 정한다(예: 0.575 에서 잡담 오인이 줄어드는지) — 이번에 문턱별 오인 비율은 재지 않았다.
2. 문턱을 정한 근거가 14문제였다(2026-09-28). 이번 340문제로 0.55 가 크게 틀리지 않음은 확인했으나(§3), **사람이 쓴 질문 세트**가 없어 확정 근거는 아니다.
3. 영어 질문에서 「답할 질문을 답함」이 28/48 로 낮다 — 한국어 점수 분포에 맞춘 문턱이 번역 질문에는 높다. 영어 질문은 원문 번역(한국어로 되돌림) 후 검색하는 안을 시험해 볼 만하다(안 해 봤다).
4. 알림 번역 보호 장치에 **통화 단위 대조**를 더하면 좋다(원문에 「원」이 있으면 번역에도 원/won/ウォン/韩元 중 하나가 있어야 함) — 이번 실측에서 일본어 1건이 새어 나갔다(§4-2). 「1인」·「두 곳」 같은 수 표현 때문에 걸러지는 4.2% 는 원문 쪽 숫자 표기를 줄이거나 대조 규칙을 풀어 주는 안을 생각해 볼 만하다.
5. 일정 사실 질문에서 「다른 항목을 짚음」 22.1% — 부정(「~말고」)·대명사에 약하다. 채팅에서는 결정 단위가 짚지만 질문 답 경로의 규칙은 틀린 시각을 말할 수 있다.
