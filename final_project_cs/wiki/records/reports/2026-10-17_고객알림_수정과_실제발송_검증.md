# 고객 외부 알림 수정과 실제 발송 검증

고객 외부 알림을 켜고, 관리자 옵션·배포 실패·출발 안내 누락을 수정했습니다. 지정한 새 디스코드 시험 고객에 생성·제안·변경·다음 일정·하루 시작·출발 안내가 실제 배달됐습니다. **고객 로그인 화면의 대안 버튼 직접 클릭은 미검증**이며, 아래 결과는 실제 업무 함수·운영 DB·최신 계획서 화면·디스코드 공급자 접수에 대한 것입니다.

| 확인 항목 | 결과 | 진행 |
|---|---|---|
| 관리자 두 환경 정상 로그인 | 확인 | 2/2 = 100% |
| 관리자 알림 옵션 끄기·켜기 저장·재조회 | 확인 | 4/4 = 100% |
| 수정 후 시험 고객 알림 배달 | 확인 | 7/7 = 100% |
| 새 회귀 시험 | 통과 | 15/15 = 100% |
| 고객 앱 버튼 직접 클릭 | 미검증 | 0/1 = 0% |

## 환경과 시험 대상

- x600 서버의 cs 프로젝트 서버가 고객 발송 대상입니다. Oracle ARM 관리자 웹앱은 다른 DB·테넌트의 개발 검증 환경입니다. 한 환경의 설정 저장을 다른 환경의 변경으로 보고하지 않았습니다.
- 두 관리자 웹앱의 로그인 계정을 요청값으로 맞추고 정상 비밀번호 로그인 응답을 확인했습니다. 비밀번호와 해시는 이 기록에 보관하지 않습니다.
- DB에서 Google 연결·Discord 연결·생성 순서를 함께 조회해 사용자가 지정한 새 고객을 구분했습니다. 기존 웹훅 고객을 시험 수신자로 지정하지 않았습니다.
- 검증용 표시가 있는 여행 두 개만 추가했습니다. 첫 여행에서 결함을 재현한 뒤 수정 후 여행으로 다시 검증했습니다. 정상적인 이동 계산·고객 동의·일정 재검증·중복 방지를 유지했습니다. 시험 시각을 이용해 실제 발송하지 않았습니다.

## 찾은 원인과 수정

1. **고객 외부 발송이 꺼져 있었습니다.** 기존 운영 한도 API에 `travel.notice_per_customer_enabled`를 등록했습니다. 발송 직전에 테넌트 DB 설정을 다시 읽으므로 관리자 저장 뒤 작업 일꾼 재시작 없이 다음 발송부터 적용됩니다. 고객이 연결하고 동의한 채널로만 보내며 관리자 채널로 우회하지 않습니다. 과거에 건너뛴 알림을 일괄 재전송하지 않습니다.
2. **DB 갱신 재실행이 실패했습니다.** `232_intake_reopen.sql`이 허용 방법을 좁혀, 이후 갱신이 허용한 `llm_agent` 접수 480행과 충돌했습니다. 중간 제약도 같은 방법을 허용하도록 고치고 재실행 회귀를 추가했습니다. 운영 복구 사본에서 관련 72개 시험, 격리된 관문과 실제 DB 갱신·배포 검사를 통과했습니다. 최종 조회에서 같은 방법의 접수 559행을 확인했습니다. 이 숫자는 전체 원본 ID의 행별 대조 결과가 아닙니다.
3. **대안 적용 후 여행 조건이 사라졌습니다.** 장소 교체 후 앞뒤 이동을 다시 만들 때 기본 인원·조건으로 계산해 `party_changed`로 출발이 보류됐습니다. 모든 일정 적용·후보 검증 경로에서 현재 인원과 설문 조건을 전달하도록 고쳤습니다.
4. **출발 시각 직후 재검증이 항상 막혔습니다.** 계획·출발 재검증이 모두 도착 여유 10분을 요구하면서 계획은 마지막 성립 시각을 택했습니다. 정각에는 통과했지만 1초·65초 뒤 분 올림으로 보류됐습니다. 저장할 일정 계산에 발행 지연 여유 2분을 더했고, 출발 재검증의 안전 여유 10분은 유지했습니다. 단순 이동시간 조회는 기존 도착 목표를 유지합니다. 기존 고객 여행을 일괄 변경하지 않았습니다.

## 실제 실행 결과

- 수정 후 실제 대안 처리 함수는 외부 자료 재점검 결과 `clear`를 확인하고 14.894초에 2판을 저장했습니다. 교체 장소와 앞 이동 목적지가 모두 벽천마당으로 바뀌었습니다. 이후 시험 여행 시작 안내 확인을 위해 시작 시각만 조정해 3판을 저장했습니다.
- 정상 계획서 링크를 Chrome에서 열어 HTTP 200·최신 2판·바뀐 장소·바뀐 이동을 확인하고 촬영했습니다. 이는 로그인한 고객 앱에서 버튼을 누른 시험과 구분합니다.
- 수정 후 여행의 알림 7건: 생성, 대안 제안, 대안 선택 변경, 시험 시작 시각 변경, 현재·다음 일정, 하루 시작, 출발. 모두 `delivered`, 시도 1회, 오류 없음입니다.
- 출발 안내는 02:46 예정이었고 실제 반복 작업이 02:46:46.553에 현재 경로를 재검증했습니다. 현재 출발 02:47·도착 02:50으로 안내했고, 고객 Discord 상태 확인은 02:47:03.455였습니다. 정각 즉시 발송을 보장하는 결과가 아닙니다.
- 수정 후 운영 이동 계산기 읽기 전용 경계 검사에서 0초·1초·65초 지연은 안전 여유 10분을 지키며 통과했고, 125초 지연은 그대로 보류했습니다. 이 경계 검사는 외부 알림을 보낸 시험 시나리오가 아닙니다.
- localhost 관리자 화면에서 정상 비밀번호 로그인, 옵션 끄기·켜기 각각 HTTP 200, 새로고침 후 값 유지, 촬영을 확인했습니다. 최종 값은 켜짐입니다. Oracle ARM 화면에서도 같은 두 동작을 확인했습니다.
- 이후 별도 배포가 이어진 최종 실행 이미지에서도 인원 전달·발행 여유·조회 범위·고객 발송 설정 4개를 다시 확인했습니다. API·웹 정상, API·worker 재시작 횟수 0입니다.

## 자동 시험과 범위

격리된 시험 환경: **6,253 통과·132 건너뜀·359 제외**, 실패·오류 0. 실행 대상으로 선택된 6,385개 중 통과는 6,253/6,385 = **97.93%**입니다. 건너뜀은 별도 이동 데이터·수집 스크립트·요식 자료가 없는 환경 때문이며 통과로 세지 않았습니다. 제외 359개는 이 분모 밖입니다. 그중 Git 작업 사본이 필요한 3개는 전체 작업 사본에서 따로 실행해 **3/3 통과**했습니다. 나머지 제외 356개는 이번 실행 범위 밖입니다.

mock 서버 시험: 외부 전송 대역을 쓰는 회귀가 포함되며 위 자동 시험 수치를 실제 고객 배달로 사용하지 않습니다.

실서버 확인(서버 응답): 했음 — x600 서버의 cs 프로젝트 서버·Oracle ARM 관리자 웹앱 실제 로그인·설정 저장, 운영 DB 대안 적용, 실제 Chrome 최신 계획서, 디스코드 공급자 정상 접수를 각각 확인했습니다.

## 남은 범위와 인계

- 고객 앱의 **대안 버튼 직접 클릭**은 시험 브라우저의 고객 로그인 문제로 미검증입니다. 로그인 세션을 만들어 인증을 우회하는 방식은 자동 승인 검토가 거절했고 실행하지 않았습니다. 사용자에게 로그인을 다시 요청하지 않았습니다.
- 디스코드 공급자 정상 접수는 확인했지만 사람이 읽었다는 증거는 아닙니다. 실제 자연재난 발생 상황의 고객 외부 배달도 이번 시험으로 확인하지 않았습니다. 공공자료 6종 점검 응답(일부 캐시 사용)과 실제 도로 통제 감지·대안 재검증 보류는 확인했습니다. 재난 시뮬레이션의 외부 발송 차단은 유지했습니다.
- GPS 미도착·이탈 확인 질문과 별도 도착 체크인은 이번 수정의 구현·인수 결과에 포함하지 않습니다. 기존 안내는 하루 시작·현재와 다음 일정·이동 출발이며, 다음 일정이 없는 마지막 항목의 별도 시작·종료 알림은 이 기록으로 보장하지 않습니다.
- 반복 작업·외부 자료 갱신·외부 공급자 지연 때문에 즉시 전송을 보장하지 않습니다. 새 발행 여유 2분을 넘는 지연이나 실제 이동 불가에서는 보류를 유지합니다. 기존 이동은 정상 재계산부터 새 여유를 사용합니다.
- 첫 고객 설정·DB 갱신 수정은 별도 작업 사본의 `988a7eda1547f31f0d3c19cfe5b023fbf9b5094a`에 있습니다. 추가 출발 수정은 작업 사본에 보존했으며 원격 브랜치 통합·푸시는 하지 않았습니다. 전체 수정 패치를 아래에 보관했습니다. 다음 자동 배포 전에 이 소스 수정을 통합해야 합니다. 기본 작업 폴더의 다른 변경을 덮어쓰지 않습니다.
- 독립 CLI 검토 호출은 내부 설계 전송이라는 이유로 자동 승인 검토에서 거절돼 실행하지 않았습니다. 이를 우회하지 않았으며 재현·회귀·운영 관측으로 수정안을 검증했습니다.
