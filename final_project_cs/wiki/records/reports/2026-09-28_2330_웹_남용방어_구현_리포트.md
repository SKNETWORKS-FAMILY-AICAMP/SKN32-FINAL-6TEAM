# 웹 남용 방어 구현 리포트 (2026-09-28)

## 결론

웹의 비싼 작업(계획 읽기 · 일정 짜기 · 확인 · 여행 만들기 · 채팅)을 **DB 한 곳에서 모든 프로세스가 같이 세는** 장치를 넣었습니다.
- 횟수 제한은 사용자 결정대로 **기본 꺼짐**이고, 꺼져 있어도 세기는 합니다.
- 키 발급 한도를 메모리에서 DB로 옮겼습니다. 재시작해도, 프로세스가 여럿이어도 이어서 셉니다. 주소 원문은 남기지 않습니다.
- **사람 확인(Cloudflare Turnstile) 서버 확인**을 넣었습니다. 실제 Cloudflare에 공개 시험 키로 물어 동작을 확인했습니다.
- **여행을 안 만든 키 정리**(7일)와 **제한값을 바꾸는 운영 API**를 넣었습니다.

## 1. 제안 기본값 계산 `[추정]`

실제 호출 수는 재지 않았습니다. 아래는 코드에서 읽은 구조로 **상한 쪽으로 추정**한 값입니다. 전문은 `config/guardrails.yaml` `web_guard` 주석에 있습니다.

1. **아까운 것은 돈보다 공용 하루 한도**입니다. 모델은 로컬이고 유료 API는 무료 한도 예산(027) 안에서만 씁니다.
   - 관광공사 1,000/일(`[미확인 — 보수적]`), 카카오 1,000/일, 모델 시간 86,400초/일.
2. 웹 몫 = 한도 × 0.5(나머지는 감시 루프·새벽 확인·카탈로그 동기화) × **안전 댐퍼 0.5**
   → 관광공사 250 · 카카오 250 · 모델 21,600초.
3. 1회당 쓰는 양
   - 계획 읽기: 관광공사 15 · 카카오 5 · 모델 50초
   - 일정 짜기: 관광공사 30 · 모델 20초
   - 확인: 외부 호출 0
   - 여행 만들기: 관광공사 15
   - 채팅: 관광공사 1 · 모델 3초
4. 웹 몫을 계획 읽기 30% · 일정 짜기 40% · 여행 만들기 10% · 채팅 20%로 나눕니다.

| 작업 | 키당/일 | 주소당/일 | 서비스 전체/일 |
|---|---|---|---|
| 계획 읽기 | 4 | 5 | 5 |
| 일정 짜기 | 3 | 3 | 3 |
| 확인 | 4 | 5 | 5 |
| 여행 만들기 | 1 | 1 | 1 |
| 채팅 | 50 | 50 | 50 |

★**값이 작게 나온 이유는 관광공사 하루 한도 하나입니다.** 한도를 올리면(운영 계정 신청 등) 같은 비율로 올라갑니다. 그래서 켜기 전에 두 가지를 먼저 합니다.
- ① 꺼 둔 채 쌓인 실제 사용량(`/admin/limits` 의 `usage_today`)을 보고
- ② 관광공사 실제 한도를 확인한 뒤 다시 계산합니다.

**동작 요점**
- **세는 순서**: 한 트랜잭션에서 서비스 → 주소 → 키 순으로 모두 자리가 있을 때만 +1 합니다. 막히면 아무것도 올리지 않습니다.
- **막혔을 때**: 키·주소 한도는 `429 usage_limit`, 서비스 전체 한도는 `503 service_daily_cap`이고, 둘 다 다음 KST 자정까지 `Retry-After`를 줍니다.
- **세지 않는 경우**: 일정 짜기를 같은 판으로 다시 누르면 앞에서 끝나 세지 않습니다. 사람 확인에서 막힌 요청도 세지 않습니다.
- **사람 확인**: 비밀키가 있으면 늘 확인합니다. 실패는 `403 human_check_failed`, Cloudflare 불통은 `503 human_check_unavailable`입니다.
  - 비밀키가 없으면 개발에서는 건너뛰고 `human_check: "skipped"`로 표시합니다. 운영(`ACOP_ENV=prod` 또는 `ACOP_TURNSTILE_REQUIRED=true`)에서는 **서버가 뜨지 않습니다.**
- **빈 키 정리**: 발급 · 마지막 사용 · 마지막 계획 읽기가 모두 7일보다 오래됐고 여행이 0건이면 키를 지웁니다.
  - 사용자 행은 다른 표가 가리키지 않을 때만 지웁니다. 사용자 행을 가리키는 외래키 10개는 전부 「가리키면 거부」라 딸려서 지워지는 데이터가 없습니다(`pg_constraint` 조회).
  - 개발 DB 웹 사용자 56명 중 지금 대상은 **0명**입니다(가장 오래된 키가 2026-09-27 발급 — 읽기만 해서 셌고 실제로 돌리지 않았다).
- **운영 API**: `actor`(운영자 id)와 `reason`이 필수입니다. 옛 판으로 바꾸면 `409`, 범위 밖·모르는 이름·타입 오류는 `422`입니다. 바꾼 값은 다른 프로세스에 최대 30초 늦게 반영됩니다.

## 4. 남은 것 · 다음

1. **켜기 전에 할 것 두 가지**: 실제 사용량 보기, 관광공사 실제 한도 확인 → 기본값 다시 계산(§1).
2. **관리 콘솔**: `[2026-09-29 사용자 결정]` 관리자 웹(`frontend/apps/admin`)은 **보류**다 — 유스케이스를 먼저 논의하고, 화면 설계는 UI 팀 몫이며, 별도 포트의 별도 앱으로 뺀다(ui 세션 전달). `/admin/limits` API 는 그대로 둔다. 그때까지 제한값은 API 를 직접 부르거나 가드레일 기본값으로 바꾼다.
3. **화면(ui 세션)**
   - 키 발급 요청에도 `X-Turnstile-Token`(또는 몸통 `turnstile_token`)을 실어야 합니다.
   - 새 오류 코드 `usage_limit` · `service_daily_cap` · `human_check_failed` · `human_check_unavailable`을 문구로 보여 줘야 합니다.
   - 「7일 안에 여행을 만들지 않으면 키가 사라진다」 안내가 필요합니다.
4. **이번에 안 한 것**
   - 버려진 계획 읽기 원본(고객 글·사진)의 보관 기한은 정하지 않았습니다. 빈 키 정리는 키만 지우고 계획 읽기 행은 둡니다.
   - 여행 한 건당 10,000원 상한도 범위 밖입니다(계획 §7).

## 5. 정정 (2026-09-29) — 빈 키 정리를 끈다

사용자 지적: 지우려던 「키」는 **그 사용자를 알아보는 유일한 식별 토큰**이다. 지우면 그 사람이 사라진다.
- 앞서 「키가 토큰에서의 키 맞지?」라는 확인에 맞다고만 답하고, 지운다는 것이 식별을 없앤다는 뜻임을 짚지 않았다.
- `web_guard.idle_key_cleanup_enabled` 기본을 **false** 로 바꿨다. 켜기 전까지 정리 작업은 아무 키도 지우지 않는다(`{"skipped": "disabled"}`).
- 실제로 지운 키는 없다. 정기 정리 작업을 한 번도 돌리지 않았고, 개발 DB 웹 사용자 56명 그대로다.
- 코드와 켰을 때의 시험은 남긴다(켤지 · 다른 방식으로 할지는 다시 정한다). ui 세션에 「7일 뒤 키가 사라진다」 문구를 붙이지 말라고 알렸다.
