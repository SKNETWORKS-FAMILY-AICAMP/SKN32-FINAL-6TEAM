# triPilot 계획 생성과 AI 협업 구조 비교

자료 기준일은 **2026-10-09, 한국 시간**이다. 결론은 기존 업무 상태 관리와 저장 경계를 유지하고, 계획의 후보 선택·재탐색을 단일 조정 AI와 전문 계산 도구로 먼저 확장해 비교하는 것이다. 하위 AI는 독립 조사 또는 별도 문맥이 필요한 작업에서만 추가 비교한다. 이것은 설계 권고이며 채용 결정이나 MVP 범위 변경을 확정한 기록이 아니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 현재 처리 구조 확인 | 완료 | 1/1 = 100% |
| 최신 공개 근거 조사 | 완료 | 1/1 = 100% |
| 구조 비교와 채용 범위 판단 | 완료 | 1/1 = 100% |

진행률의 분모는 이 검토의 세 작업 단위다. 구현 완료율이나 성능 향상률이 아니다.

## 현재 구조와 컨트롤러의 역할

최초 생성과 이미 등록된 여행의 사건 처리는 다른 경로다. 최초 생성은 업무 Controller를 거치지 않는다. 생성기를 확장하는 것과 기존 변경 업무의 안전 경계를 우회하는 것을 구분해야 한다.

| 경로 | 실제 처리 | 코드 근거 |
|---|---|---|
| 최초 계획 생성 | 후보 조회·순위 → 모델의 후보 순서 → 시간·이동 계산 → 수선과 판정 → 기존 등록 함수 | [계획 생성 입구](../../../app/domains/travel_ops/entry/trip_api.py#L1555), [후보 순서](../../../app/domains/travel_ops/components/planning/planner.py#L603), [생성과 수선](../../../app/domains/travel_ops/components/planning/planner.py#L1299) |
| 여러 여행 문제가 동시에 발생 | 사건 하나 → Controller → 활동 Team 내부 묶음 처리 → 활동·식당·이동의 등록된 계산 함수 → 제안 하나 → 적용 | [감시 사건](../../../app/domains/travel_ops/components/watch/trip_watch_cases.py), [묶음 계산](../../../app/domains/travel_ops/components/watch/trip_watch_batch.py#L166), [계산 함수 연결](../../../app/domains/travel_ops/components/team_hooks/watch_planners.py) |
| 최초 등록 | 참조·경로·일정 판정과 요청 중복 처리 후 저장 | [등록 경계](../../../app/domains/travel_ops/entry/trip_api.py#L754) |
| 기존 일정 변경 | 소유 고객·기준 버전·항목·장소 대조, 해당 자동 변경의 전체 재판정, 버전 기록과 알림 연결 | [변경 적용 경계](../../../app/domains/travel_ops/components/actions/itinerary_actions.py#L125) |

현재 묶음 처리에서 세 Team의 대화가 오가는 것은 아니다. 팀들이 조립 때 등록한 계산을 동일 초안 위에서 순서대로 부른다. 따라서 계산마다 Controller를 왕복하지 않는 방식은 현재에도 존재한다. Controller는 사건의 시작·실행 상태·대기·실패·결과 반영을 관리하며 업무 계산의 내부 과정을 모두 지휘하지 않는다. [Controller 실행 경계](../../../app/application/controller.py#L249)

계획 하나는 출력 개수다. 여러 독립 조사 결과로 하나의 계획을 만들 수도 있고, 단일 AI가 여러 계산 도구를 사용해 만들 수도 있다. 협업의 실익을 가르는 것은 분할 가능성, 필요한 문맥의 크기, 순차 의존성, 목표 품질과 총 실행 비용이다.

## 같은 여행 문제에 적용한 비교

예시 상황은 야외 활동을 바꾸면 식당의 위치·도착 시각·이동까지 바뀌는 여행이다. 아래는 구조 설명용 예시이며 실행 결과가 아니다.

현재 방식은 먼저 활동 대안을 골라 초안에 넣고 식당·이동을 계산한다. 병합 결과가 새 위반을 만들면 가장 뒤의 변경부터 빼서 다시 검증한다. **뒤 결정을 버리는 대신 앞 활동을 두 번째 후보로 바꾸면 전체가 더 좋아질 수 있지만, 해당 병합 함수는 그 조합들을 전역 탐색하지 않는다.** 이것은 해당 함수의 범위로 확인한 한계다. 프로젝트 전체에 어떤 탐색도 없다고 주장하지 않는다. [최종 병합 검사](../../../app/domains/travel_ops/components/watch/trip_watch_batch.py#L244)

| 구조 | 이점 | 부담과 한계 | 권고 |
|---|---|---|---|
| 현재 계산·검증 중심 | 명확한 입력과 결과, 정해진 순서, 기존 상태·중복 방지·검증 경계 | 함수별로 고른 후보가 전체 선호나 조합의 최선은 아닐 수 있음 | 기본 비교군으로 유지 |
| 조정 AI 하나와 전문 계산 도구 | 전체 초안을 한 문맥에서 보며 후보·순서·추가 조회를 조정 가능 | 모델 오류, 반복 호출, 문맥 증가. 기존보다 낫다는 실측은 없음 | 우선 실험군 |
| 조정 AI와 제한된 하위 AI | 독립 자료 탐색, 큰 전용 문맥, 별도 관점 검토를 분리 가능 | 위임·요약 손실, 중복 조회, 토큰 합계와 지연 증가 | 단일 AI가 어려워하는 부분에서 조건부 실험 |
| 계층 없이 여러 AI가 직접 협의·저장 | 자유로운 동적 협의 | 상태·권한·중복·중단 복구·책임 경계를 새로 구축해야 함 | 현재 교체 권고의 근거가 부족함 |

고정된 영업시간, 이동시간, 겹침, 금액 조건은 코드로 계산·검증한다. 고객 문장의 선호 해석과 후보 탐색 방향은 AI가 맡을 수 있다. 여러 조합의 전체 일정 품질을 개선하는 대안으로 제약 최적화 계산도 비교할 수 있다. OR-Tools의 공식 시간창 경로 예제는 이동시간과 방문 가능 시간의 제약을 표현한다. 여행의 활동 선택·선호·식사·예산 모델을 별도로 설계해야 하므로 예제를 그대로 넣어 해결됐다고 볼 수는 없다. [OR-Tools 공식 예제](https://developers.google.com/optimization/routing/vrptw)

정보가 없는 문제는 AI 수를 늘려 해결할 수 있다고 전제하지 않는다. 현재 생성기의 확인 범위는 `coverage`가 표시한다. 새 실험도 동일한 사실 자료와 확인 범위를 사용해야 한다.

### 전문 AI를 전문 절차와 도구로 바꾸는 선택지

Microsoft의 2026-09-16 사례는 별도 전문 모델 대신 조정 AI가 필요한 전문 절차를 로드하고 MCP 업무 도구를 부르게 한다. 전문 업무 서비스와 소유 경계는 유지되며 독립 연구 AI는 남긴 혼합 구조다. 이 사례는 세 쌍의 비교이고 캐시·업무량·실행 환경이 달랐으므로 일반적인 속도·비용 개선 증거로 쓰지 않는다. 모델 호출 수 감소가 전체 토큰 감소를 의미하지 않았다는 점도 중요하다. [공식 비교 사례](https://devblogs.microsoft.com/agent-framework/from-specialist-agents-to-distributed-skills-over-mcp/)

이 방향은 이미 계산 모듈이 분리된 triPilot과 잘 맞는다는 설계 추론이다. 내부 함수 호출에 MCP를 반드시 끼워야 하는 것은 아니다. MCP의 도구·자료 기능만으로 전문 절차의 자동 연결 규약까지 정해지는 것도 아니다.

## 채용 범위와 다음 비교

바깥 업무 흐름은 현재대로 유지한다. 최초 생성의 내부 또는 기존 Team의 `execute()` 안에서 조정 AI를 시험하고, 결과는 기존 생성 결과나 제안 계약으로 반환한다. 내부 실행 단계마다 업무 Controller를 거칠 필요는 없다. 저장·소유·버전·승인·중복 방지·감사는 기존 경계가 담당한다.

단일 조정 AI의 권한은 실제 후보 선택, 읽기 조회, 일정 계산 도구 사용, 검증 실패에 대한 제한된 재탐색까지다. 장소·시간·금액을 임의 생성하거나 직접 저장하는 권한은 주지 않는다. 같은 계획의 변경 주체는 한 곳에 두고 하위 AI는 근거와 구조화된 후보를 반환한다. 독립 조회만 병렬화하고 앞 결정에 따라 입력이 바뀌는 계산은 의존 순서를 지킨다.

| 후보 기능 | 채용 범위 | 다시 판단할 근거 |
|---|---|---|
| 전문 절차·도구의 필요 시 로드, 구조화된 결과, 호출·시간 예산과 추적 | 기존 경계 안에서 우선 설계 가능 | 후보·근거·규칙 대조 성공과 실행 예산 |
| 단일 조정 AI의 전역 후보 재탐색 | 기존 계산과 비교하는 실험 | 규칙을 지키며 고객 선호를 더 충족하는지 |
| 독립 조사 또는 별도 문맥 하위 AI | 단일 AI가 부족한 경우에 추가 비교 | 동일 총 예산에서 단일 AI보다 개선되는지 |
| MAF 또는 LangGraph 기반 실행 저장·중단 복구 | 내부 반복 실행이 길어질 경우 별도 검토 | 현재 실행에서 실제 복구·관찰 문제 발생 건수와 재구축 비용 |

도입 여부는 다음 세 군의 여행 사례 비교로 판단한다: 기존 방식, 단일 조정 AI+동일 도구, 단일 조정 AI+제한된 하위 AI+동일 도구. AI 협업군에만 추가 사실 자료나 더 좋은 검증기를 주지 않는다. 모델 계열·버전·입력·프롬프트·자료 시점·검증기를 기록하고 같은 총 토큰/도구 비용 예산 비교와 실제 지출 비교를 구분한다. 서로 번갈아 반복 실행하며 확인 범위별 성공 건수/전체 건수, 남은 위반, 고객 선호 충족, 변경량, 경과 시간 분포, 전체 모델 호출·토큰·자료 API 비용을 함께 본다. 같은 모델의 자체 동의만으로 품질을 판정하지 않는다.

계산 중심 최적화군을 추가하면 전역 탐색 자체의 이득과 AI 협업의 이득을 분리할 수 있다. 여러 AI가 더 잘한다는 결론은 단일 AI가 같은 예산을 사용한 경우까지 비교한 뒤에만 낸다.

## 수행 범위와 기록

- 코드와 현재 계약을 읽고 공개 공식 자료·논문을 대조했다. 위 코드 링크는 확인한 로컬 작업 트리다.
