# 출발 검증자료 누락과 대안 없음 안내의 구분

출발 직전의 내부 검증자료 누락이 일반 일정 위험으로 안내되고, 재계산이 성립하지 않으면 장소 대안이 없다는 문장으로 끝나는 경로를 확인했습니다. 실제 운행 중단·도로통제 확인과 구분해야 합니다. 17:31의 읽기 진단 뒤 승인된 최소 수정을 진행했으며, 후속 구현·시험 상태는 아래 추가 기록으로 구분합니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 관측·감시·재경로·문장 경로 | 읽기 확인 | 4/4 = 100% |
| 실제 저장자료의 누락 지점 | 원격 담당 조회 대기 | 분모 미확정 |
| 최소 수정 후보 | 정리 | 1/1 = 100% |
| 제품 수정·시험·배포 | 실행 안 함 | 0/3 = 0% |

확인 시각: 2026-10-18 17:31 KST. 개발·운영 담당이 원인과 후속 수정 범위를 판단하기 위한 문제 해결 기록입니다. 실제 고객 식별자·개별 동선·접속 정보는 공개 문서에 옮기지 않습니다.

## 확인한 경로

1. [출발 관측](../../../app/domains/travel_ops/instances/mobility/engine/departure_observer.py)의 `context_missing_or_version`은 저장된 `departure_context`가 dict가 아니거나 `schema_version != 1`인 경우입니다. 여기의 version은 여행 일정의 판 번호가 아닙니다. 도로·운행 API를 읽기 전에 반환할 수 있습니다.
2. [출발 안내 계산](../../../app/domains/travel_ops/components/watch/trip_reminders.py)의 `build_departure`는 관측의 `needs_replan`을 `held`로 보류합니다. [감시](../../../app/domains/travel_ops/components/watch/trip_watch_cases.py)의 `_departure`는 이를 `departure_revalidation` 원인의 Case 대상으로 넘깁니다. 예정 출발 전 운행 사건 점검이 정상이어도, 출발 이후 실행하는 이 검증은 별도로 실패할 수 있습니다.
3. [이동 담당](../../../app/domains/travel_ops/instances/mobility/team.py)은 현재 시각·최신 여행 조건으로 새 경로를 계산합니다. [재경로 계산](../../../app/domains/travel_ops/components/itinerary/itinerary_changes.py)의 `_engine_reroute`는 `got is None`이면 `no_data`만 자료 실패로 구분하고 나머지 계산 사유를 버립니다. 인접 장소·좌표가 없는 경우에도 `None`입니다. `plan_departure_adjustment`는 이 결과를 `unresolved`로 합칩니다.
4. 실제 Case가 `itinerary_unresolved`로 끝나면 감시가 완화 대안을 시도합니다. [완화 대안](../../../app/domains/travel_ops/components/watch/watch_relaxed.py)은 활동·식사만 지원하므로 이동 항목에는 적용되지 않습니다. 이어 [고객 안내](../../../app/domains/travel_ops/components/planning/pending.py)가 공통 `no_alternate` 문장을 사용합니다. 출발 재검증 코드에는 개별 문장이 없어 “일정에 문제가 생겼어요”, 이동에도 “대신 갈 수 있는 곳을 찾지 못해”가 표시됩니다.

다른 실패가 모두 `no_alternate`가 되는 것은 아닙니다. `_after_run`은 자료·실행 실패와 처리 불가를 별도 안내로 나눕니다. 실제 이번 Case의 guardrail은 운영 담당의 전체 기록 조회와 대조해야 합니다. `schedule_action=pinned`는 고정 항목 집계이며 그 자리에서 점검이나 재경로 계산을 중단하지 않습니다.

## 내부 자료가 없는 정상 코드 경로와 미확인 범위

[장소 변경 뒤 이동 갱신](../../../app/domains/travel_ops/components/itinerary/itinerary_changes.py)의 `refresh_moves_around`는 새 경로 계산에 실패하면 `kept_nearby` 또는 `estimate`를 저장하고 옛 `departure_context`를 제거합니다. 옛 장소의 접근·승차 시각을 새 장소의 근거로 재사용하지 않기 위한 기존 계약입니다. [접수 이동 계산](../../../app/domains/travel_ops/components/intake/moves.py)은 원래 출발편을 검증하지 못하고 시작 시각을 추정한 경우 문맥을 넘기지 않습니다. [등록 이동 연결](../../../app/domains/travel_ops/components/intake/registered_moves.py)도 유효한 선택 문맥이 없으면 문맥 없는 수단 경로를 만들 수 있습니다.

따라서 이번 운영 기록의 `detail`에 문맥 키가 없는지, 잘못된 판인지, `route_basis`·`refreshed_for`·`planner.transfer_basis`·`route_def.planned`가 무엇인지와 이전 판 생성 이유를 확인해야 누락 지점을 확정할 수 있습니다. 이 읽기 진단만으로 특정 경로를 실제 원인이라고 단정하지 않습니다. 고객 위치·탑승 상태를 관측한 결과도 아닙니다.

## 최소 수정 후보 — 아직 미적용

- **원인·결과 보존:** 현재 재경로 계산을 유지하되, 인접 장소·좌표·계산 자료 불가를 확인 불가로 분리합니다. 계산이 실제로 실행되어 시간·경로가 성립하지 않은 결과만 미해결로 유지하고, 계산 사유를 Case와 최종 안내에 보존합니다. 알 수 없는 계산 실패를 대안 부재로 바꾸지 않습니다.
- **정확한 안내:** 저장 문맥 누락은 “출발 경로를 다시 확인하는 데 필요한 자료를 확인하지 못했어요”처럼 알리고, 이동의 실제 대안 부재는 “현재 조건에 맞는 다른 이동 경로를 찾지 못했어요”로 장소 대안과 구분합니다. 실제 시간 부족이 입증됐으면 그 사유를 덧붙입니다. 통제·지연·정상 운행을 추정하지 않습니다.
- **범위 유지:** 문맥 누락을 `clear`로 바꾸거나 과거 ETA를 발송하지 않습니다. 옛 문맥 복사·임의 시각 변경·동의 없는 고정 일정 변경도 하지 않습니다. 실제 자료에 따른 재계산이 성공하면 기존 전체 재판정·동의·동시성 검사를 그대로 통과해야 합니다.

## 수정 시 필요한 검증

저장 문맥 누락→현재 재계산 성공, 문맥 누락→자료 불가, 문맥 누락→실제 시간 부족, 인접 좌표 부재를 서로 다른 결과로 시험합니다. 단일·묶음 Case 모두에서 사실 원인을 유지하고, 자료 불가에서는 `no_alternate`를 보내지 않는지 확인해야 합니다. 이동 안내는 장소 대안 문장을 쓰지 않고, 기존 도로 원문·게스트·채널·고정 항목·중복 방지 계약을 유지해야 합니다. 기존 실제 경로 단절 재계산 회귀도 유지합니다.

## 17:43 KST — 실제 저장자료 대조와 로컬 보완

운영 담당의 읽기 전용 SQL 확인에서 이전 판과 현재 판 모두 `departure_context` 키가 없었습니다. 이전 판은 장소 변경 뒤 `kept_nearby`, 현재 판은 `estimate`이며, 직선거리에서 산출한 추정 경로입니다. 해당 이동의 저장 시각은 유지됐고 고정 상태였습니다. 출발 관측 사유와 Case의 `itinerary_unresolved`를 함께 확인해 **문맥 누락→재경로 미해결→공통 no_alternate 안내**까지는 확정했습니다. 당시 재경로 계산의 원래 `why`는 저장되지 않았으므로 실제 도착 불가·어떤 자료 실패였는지는 미확정입니다. SQL 조회는 운영 담당이 실행했으며 이 담당의 원격 실행은0회입니다.

구현 전에 [결과 계약](../../external/departure-revalidation-results.md)을 추가하고 실행 파일3개·기존 시험·이 기록을 각각 부모의 `_backup/2026-10-18_173608_departure-result-guidance/`에 보존했습니다. 로컬 보완은 다음과 같습니다.
