# 일정 0개 완료 시 입력 화면으로 자동 복귀

일정 읽기가 끝났는데 찾은 일정이0개이면 질문 화면에 남지 않고 이전 입력 화면으로 돌아간다. 제출한 글·파일을 복원해 고쳐 다시 보낼 수 있고, 입력 칸에는 복귀 이유를 표시한다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 변경 전 자동 복귀 실패 | 재현 | 1/1 = 100% |
| Chrome 화면 고유 시험 | 통과 | 15/15 = 100% |
| 복원·입력 단위 시험 | 통과 | 19/19 = 100% |
| 타입·문법·새 빌드 | 통과 | 3/3 = 100% |

## 변경과 경계

완료된 빈 결과를 확인하는 분기보다 질문 유지 처리가 먼저 실행되어, 질문에 답하는 동안 「찾은 일정0개」와 확인 버튼이 남을 수 있었다. 이제 접수의 상태가 `review`이고 모든 원문 소스의 일정 배열이 비었을 때 자동 복귀한다. 같은 판단은 질문 유지와 완료 진행 재생보다 먼저 적용한다. 주소를 교체하므로 뒤로 가기로 빈 결과 페이지를 반복해서 밟게 하지 않는다.

읽는 중 임시0개에서는 기다린다. 이미 등록된 여행과, 원문에는 일정이 있었지만 나중에 전부 삭제한 결과는 기존 화면을 유지한다. `fatal`은 읽기 오류 화면을 사용한다. `check.items`나 지도 마커 개수로 판정하지 않고 원문 일정의 개수를 사용한다.

최근 제출 한 건의 글·파일을 현재 탭 메모리에 보관하고, 빈 결과일 때 기존 입력 복원 경로로 전달한다. 정상 완료나 새 제출에서는 파일 참조를 해제한다. 다른 접수의 파일은 섞지 않는다. 직접 연 접수에는 제출 메모리가 없으므로 cs 프로젝트 서버가 돌려준 텍스트 원문을 복원한다. 파일은 같은 탭에서 제출한 직후의 복귀에 한해 복원하며, 새로고침 뒤 잃어버린 파일을 복구한다고 약속하지 않는다. 입력 화면에서 이후 편집한 글의 임시 저장 방식은 유지한다.

빈 결과의 최근 응답도 제거해 고친 접수가 오래된0개 응답을 다시 사용하지 않도록 했다. 자동 재전송·여행 등록·일정 생성 요청은 보내지 않는다. 입력을 고치고 다시 확인을 누를 때만 새 제출을 보낸다.

## 검증

- [변경 전](../evidence/2026-10-11_empty-intake-return/before.json): 375px에서 읽는 중 질문을 건드린 뒤 완료0개로 응답해도5초 안에 입력 화면으로 돌아오지 않았다. 재현1/1이다.
- [첫 수정](../evidence/2026-10-11_empty-intake-return/after.json):15건 중13건 통과. 두 화면 크기의 글 수정·재제출 부분은 최근 빈 결과 응답이 재사용되어 실패했다. mock 서버는 같은 접수 번호를 재사용한다는 조건이 있으며, 이 결과를 실제 공개 cs 프로젝트 서버의 재제출 장애로 일반화하지 않는다.
- [최종 Chrome](../evidence/2026-10-11_empty-intake-return/verified.json): 새 제품 빌드로15/15, 건너뜀0·예상 밖 실패0·재시도 통과0. 신규4건은375px·1280px 각각 질문 유지보다 우선 복귀, 읽는 중 임시0개 대기, 글 수정·재제출, 파일 복원과 자동 재전송 방지를 검사한다. 기존11건은 직접 연 빈 접수의 자동 복귀, 계획 요청 문구가 있는 경우, 일반 결과·등록 완료·모두 삭제한 결과, 제출 거절·전송 중 뒤로 가기·새로고침·게스트 전송·지연 응답을 검사한다.
- [단위 시험](../evidence/2026-10-11_empty-intake-return/unit.json): 신규 복원4건·기존 게스트 오류3건·입력 분기12건, 합계19/19. 도착 표시를 지운 뒤 파일 유지, 다른 접수 파일 격리, 정상 결과에서 제출본 해제, 파일 전용 입력이 기존 글을 덮지 않는 값을 확인한다.
- 변경 파일 ESLint와 타입 검사 각각 종료0. 마지막 제품 변경 후 새 빌드 성공. [빌드·파일 확인값](../evidence/2026-10-11_empty-intake-return/verification.json)을 보존한다.
