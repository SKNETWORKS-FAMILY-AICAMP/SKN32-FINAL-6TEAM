# Oracle ARM 실제 답변 경로 복구

`[실측 2026-10-11 저녁]` 로컬 연결기 개선은 Oracle ARM에 적용했다. 실제 앱 시험에서는 모델 비교 작업이 모델을 바꾸면서 앱의 고정 모델 설정과 충돌하는 별도 결함을 확인했다. 앱 전용 경로와 연결기 준비 확인을 반영했고, 다국어·후속 대화 실제 HTTP22개가 통과했다. 공개 브라우저에서도 직접 입력한 경복궁 일정의 등록과09:00 답변을 확인했다. 반복 시험의 계정 발급 한도와 혼합·복합 요청은 아래 후속 검증 상태를 따른다. 제품 전체 복구나 모델 채택으로 표시하지 않는다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 로컬 연결기 적용 | 완료 | 1/1 = 100% |
| 연결기 회귀 | 통과 | 18/18 = 100% |
| 수정 후 다국어·후속 대화 HTTP | 통과 | 22/22 = 100% |
| 공개 브라우저 네 단계 | 통과 | 4/4 = 100% |

| 계정 수정 후 혼합·복합 HTTP | 실패 보존 | 9/11 = 81.8% |
| 동일 여행 반복 HTTP | 통과 | 22/22 = 100.0% |

## 문제와 원인

- 위치: Oracle ARM 앱의 Ollama 호환 연결기와 모델 비교 실행기의 공유 추론 포트. PostgreSQL 연결·소유권 격리·일정 저장/조회는 실제 HTTP 시험에서 통과했다. 이것을 장소 검색·추천 전체의 정상 동작으로 확대하지 않는다.
- 재현: `language_style`, `context_cache` 각각 11개 검사에서 기본 기능 7개는 통과하고 여행 메시지 4개는 모두 `decision_failed`였다. HTTP 200이어도 답변 실패로 센다. 실행 프로세스의 성공 종료를 답변 통과로 세지 않는다.
- 직접 원인: 앱 연결기는 기존 합친 E4B Q4_K_M 모델을 기대했으나, 공유 실행기는 별도 원본 E4B QAT Q4_0 평가를 수행하고 있었다. 모델 식별 검사가 요청을 차단했다. 식별 검사를 제거하거나 실행 중인 비교 작업을 중단하지 않았다.
- 이전 결함: 로컬 연결기의 `think` 전달과 빈 답·미완료 생성·잘못된 JSON 거부가 운영 연결기에 반영되지 않았다. 수정 후에도 모델 식별 충돌이 남아 있었으므로 연결기 시험 통과를 전체 복구로 보고하지 않는다.
- 위험: 운영 앱의 모델과 모델 비교의 대상이 서로 종속되어 모델 교체 때마다 실제 고객 요청이 실패할 수 있다. 앱의 고정 모델 경로와 평가용 경로를 분리해야 한다.

## 적용·백업·검증

로컬 [연결기](../../../deploy/arm/ollama_adapter.py)를 Oracle ARM 제어 폴더에 적용했다. Oracle ARM에서 [기본 시험](../../../deploy/arm/test_adapter.py)과 [응답 검사 시험](../../../deploy/arm/test_response_guard.py) 18개를 실행했다. 로컬 Windows 실행의 HTTP 시험 한 건은 실행 환경의 루프백 접근 제한으로 실패했고, Oracle ARM Linux 컨테이너에서는 같은 시험 전체가 통과했다.

수정 전 연결기는 Oracle ARM 배포 기준 폴더의 `control/_backup/2026-10-11_103934_answer_repair/`에 보존했다. 적용 시각은 **2026-10-11 19:39:45 KST**다. API·worker·DB·기존 모델 비교 실행기는 재시작하지 않았으며 연결기 컨테이너만 교체했다. 기존 앱 소스 판은 유지됐다.

mock 서버 시험: 연결기의 전체 18개 시험 중 HTTP 응답 검사에 mock 서버를 사용했다. 브라우저 화면 시험은 실시하지 않았다.

실서버 확인(Oracle ARM cs 프로젝트 앱 응답): 실제 HTTP 검사 22/22 실행, 기본 기능 14/14 통과, 여행 답변 0/8 통과. 검사 관측 시각은 **2026-10-11 19:40:32~33 KST**다. 원본과 실패를 모두 분모에 남겼다.

## 앱 전용 경로 시험

기존 보관 모델 **EXAONE-4.0-1.2B Q8(개발사 배포 원본, 우리 자료 추가 학습 없음)**을 별도 내부 경로에서 시험했다. 새 모델 다운로드·결제는 하지 않았다. 이 선택은 제한된 메모리 안에서 앱 경로 분리가 가능한지 확인하기 위한 후보 시험이며, 정확도 우위나 제품 채택을 뜻하지 않는다. 전용 시험의 메모리 상한은 2GiB, CPU 상한은 한 코어 대비 50%(두 코어 전체 대비 25%)다. 실제 속도나 사용률 목표 통과로 표현하지 않는다.

원본 템플릿의 `/apply-template` 실측에서 첫 `system` 메시지의 표식이 사라지고 사용자 표식만 남았다. 해당 실행기의 템플릿 처리에서 첫 역할 분기의 `continue`를 쓰지 않는 별도 템플릿을 만들어 지시문이 정확히 한 번, 앞 대화와 최신 사용자 메시지가 순서대로 보존되는지 확인했다. 2/2 통과했다. 모델 가중치는 바꾸지 않았다. 실행 중인 기존 비교 작업은 그대로 보존했고, 종료된 신규 시험만 새 버전으로 전환했다.

초기 소형 모델 시험은 지시문 누락 상태였다. 첫 문항의 초기 검사기는 할 일·대상만 확인해 통과로 기록했지만 사실 종류를 `time` 대신 `day`로 선택했다. 이 행은 **최종 답변 검증 통과로 사용하지 않는다**. 수정 후 판정에는 사실 종류까지 포함한다. 중국어 질문과 감사 인사도 잘못 해석했으므로 초기 모델을 앱에 연결하지 않았다. 초기 원본은 시험 폴더의 `_backup/template_trial_v1/`에 보존했다.

## 21시 후속 관측 — 출력 설정과 배포 겹침

`[실측 2026-10-11 21:18 KST]` EXAONE 수정 템플릿의 엄격한 판정은 1/3 통과였다. 영어 시작 시각만 맞혔고 중국어 사실 종류와 감사 인사를 잘못 선택해 앱에 적용하지 않았다.

E4B QAT Q4_0 배포 원본(우리 추가 학습 없음)을 별도 내부 경로에서 시험했다. 첫 판은 `--reasoning-format none --reasoning-budget 0`, 추론 스레드 1개였으며 1/3 통과했다. 영어 시간은 맞혔고 중국어·감사 인사 응답은 종료 표식이 `stop`이었지만 JSON 검사에서 실패했다. 실행기의 Gemma4 파서를 확인한 결과 `reasoning-format none`일 때 생각 표식을 최종 본문에 포함할 수 있었다. 다만 해당 실패 응답 원문 확인 시도가 종료 코드137로 끝나 원문을 확보하지 못했으므로 이 원인을 실측 확정으로 표시하지 않는다.

원문 확인 도중 앱 소스가 이전 판에서 후속 develop 판으로 바뀌고 API 컨테이너가 교체된 것을 확인했다. 해당 관측 창의 커널 로그에서는 메모리 부족 종료 기록을 찾지 못했다. 다음 시험은 배포 잠금을 보유해 앱 교체와 겹치지 않게 했다. 기존 ARM 벤치마크의 실행 PID는 유지됐다.

수정 시험은 `--reasoning-format deepseek --reasoning off --reasoning-budget 0`, 스레드2개로 시작했다. 서로 다른 설정·부하이므로 첫 판과 속도 우열을 주장하지 않는다. 같은 가중치 파일을 실행 중 벤치마크와 공유하며 여유 메모리를 함께 관측한다. 세 문항의 할 일·대상·사실 종류가 모두 맞아야 앱 전용 경로를 연결한다. 그 후 실제 HTTP22개를 통과해야 해당 자동 시험 프로필의 차단을 해제한다. 자동 후속 처리는 Oracle ARM 자체 실행 작업이며 PC 예약을 새로 만들지 않았다. 아직 이 관측 시점에는 앱 연결 변경·차단 해제·영구 모델 서비스 설치가 완료되지 않았다.

현재 확인한 기본 답변 복구는 장소 검색·후보 추천·일정 변경·브라우저 전체 동작의 통과를 뜻하지 않는다. 시험과 실패 원본은 별도 이름으로 보존했다.


## 21시30분 — 전용 경로 반영과 준비 확인

`[실측]` E4B QAT Q4_0 원본의 수정 설정은 영어·중국어 시간 질문과 감사 인사3/3을 통과했다. 각각183.27·63.85·47.83초였으며 기존 벤치마크를 함께 실행한 조건이다. 첫 질문의 모델 적재는 이미 끝난 상태였고 입력처리136.77초·출력46.35초였다. 상주 모델의 첫 새 문맥 처리와 초기 모델 적재를 구분한다. vLLM이 아니라 기존 CPU llama.cpp 실행기다.

21:23:30 KST에 재부팅 후 시작하고 실패 시 재시작하는 앱 전용 모델 서비스를 반영했다. 두 스레드·문맥4096·CPU상한 한 코어 대비120%(두 코어 대비60%)·메모리상한6500MiB이며, 기본 출력에서 생각을 분리하고 생각 생성을 끄는 설정이다. 모델 채택 정확도 평가는 별도다. 기존 비교 작업은 같은 PID로 유지했고, 이후 서로 다른 대형 모델의 동시 적재를 피하기 위해 아직 시작하지 않은4작업을 원본 백업 후 manifest의 별도 대기 항목으로 보존했다. 진행 중인 비교의 지연은 추가 추론 부하가 있어 이전 단독 실행과 속도를 공정하게 비교할 수 없다.

연결기 교체 직후 첫 다국어 HTTP 검사7/11에서 네 답변이 연결 거부로 실패했다. 이어진 한국어 대화는11/11(실제 답변4/4)로 통과했다. 따라서 이 첫 회차는18/22이며 실패 네 건을 분모에 남긴다. 한국어 첫 질문156.38초, 점심41.50초, 인사52.36초, 첫 질문 반복47.43초였다. 인사를 업무 변경으로 오지목하지 않는 것까지 확인했고 인사 문구의 자연스러움을 별도 평가로 확대하지 않는다.

[배포 구성](../../../deploy/arm/compose.yml)에 연결기 건강 확인을 추가했다. 모델 식별까지 맞아야 준비 완료가 되며 기존 CD의 Compose `--wait`가 이를 기다린다. 문법 읽기와 Oracle ARM Compose 구성 검사, 실제 연결기 준비 표본3/3을 확인했다. 연결기만 교체했고 API·worker·DB는 이 적용에서 재시작하지 않았다. 수정 전 로컬 구성은 [백업](../../../deploy/arm/_backup/2026-10-11_2126_adapter_readiness/compose.yml)에 보존했다.

준비 확인 이후의 두 프로필22개 검사는 새 폴더에서 실행 중이다. 모두 통과해야 해당 두 프로필의 실패 차단을 잠금 아래 해제한다. 혼합·복합 요청 프로필의 기존 실패는 해제하지 않는다. 내부 기준 통과 뒤 공개 HTTPS의 웹·세션·여행 생성·시간 질문·인사5개를 별도 검증하고, 실시간 진행 이벤트와 최종 답변을 기록한다. 이는 브라우저 클릭 시험이 아니다.


## 21시55분 — 실제 답변 회복과 반복 시험 한도
