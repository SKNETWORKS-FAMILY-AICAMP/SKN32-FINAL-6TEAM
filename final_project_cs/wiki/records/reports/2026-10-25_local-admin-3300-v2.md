# 로컬 관리자 3300 v2 — 독립검토 P1/P2 후속

## 현재 상태

새 격리 `local_admin_3300_v2/repo`에서 검토 tree `91bae429d32d1e362ea98a9f87aa880d71bbb75d`를 고정해 수정했습니다. 기존 예약 OFF·인증·tenant·관리자 프록시 소스와 보호 규칙은 변경하지 않습니다. 실제 서비스·실DB·외부 API·모델·push/배포는 수행하지 않습니다. **실제 3300 로그인·예약 OFF 저장/재읽기는 미검증**입니다.

## 독립검토 실패와 수정

- P1: 기존 7개 시험은 추출 PowerShell만 실행해 전체 cmd 실패를 놓쳤습니다. 실제 전달 LF와 LF 변형은 exit 255, CRLF는 정상인 RED를 먼저 재현했습니다(`red-p1.log`). 단순 chcp 제거도 exit 0/빈 출력으로 실패해 기록을 보존했습니다(`green-p1.log`). bootstrap과 `exit /b`를 첫 ASCII 물리 줄에서 끝내고 UTF-8 본문을 읽는 방식으로 LF·CRLF·실제 전달 바이트가 통과했습니다(`green-p1b.log`). 종료 배치에서도 LF exit 9009를 별도 재현(`red-stop.log`)하고 동일 원칙으로 수정했습니다. pause는 제거해 종료 코드가 호출자에게 직접 반환됩니다.
- P2: 무관 listener 전부 열림이 exit 0인 RED(`red-p2a.log`) → 네 포트 선점 사전검사와 매 시작 직전 충돌 실패. 기존 listener를 소유 기록에 넣거나 종료하지 않습니다.
- P2: 앞선 API가 뒤 앱 시작 중 죽어도 exit 0인 RED(`red-p2b.log`) → 마지막 전체 생존·시작시각·listener 소유권·HTTP 준비 재검사. 마지막 HTTP 검사 중 앞선 프로세스가 죽는 경우도 최종 생존 재검사합니다.
- P2 경계: 뒤늦은 충돌·비소유 listener·HTTP 미준비가 성공하던 반례를 먼저 재현(`red-p2c2.log`) → 준비 실패·충돌은 exit 1, 이미 시작한 소유 기록만 유지합니다. 기존 `180`회·`500ms` poll 값을 재사용하며 새 포트·개인 경로·업무 가드레일 값을 추가하지 않았습니다.
- 준비 계약은 기존 고객 `/health`의 `status=ok`, 운영 `/health`의 추가 `app=ops`, 웹 루트 HTTP 200입니다. 부모/자손 listener 및 시작시각을 확인하고 redirect·비정상 status·잘못된 ops 응답은 준비 실패입니다. 이는 로그인·DB·tenant·예약 설정 확인을 대체하지 않습니다. 개인 starter가 분리한 listener는 소유 증명 실패 시 성공으로 간주하지 않습니다.
- 추가 경계에서 이전 state를 다시 읽을 때 PowerShell 배열 메타데이터가 중첩돼 소유 기록이 훼손되는 것을 RED로 확인(`red-state.log`), 명시적 배열 열거로 보존합니다. 최초 여러 반례를 같은 fixture에 이어 실행한 `red-p2c.log`의 중첩 state 오류도 숨기지 않습니다. 독립 fixture로 바꾼 `red-p2c2.log`는 의도한 3개 실패와 기존 즉시사망 실패 처리를 구분합니다.

## 격리·의존성

- 루트/하위 AGENTS·CLAUDE·RULE, 두 wiki, README 전체 로컬 절·프론트/관리자/웹 README, 기존 실행 계약·handoff, 독립 REVIEW·실제 재현 소스를 읽었습니다. 전역 Codex/Claude 규칙 파일은 없었습니다. 지시파일 수정은 없습니다.
- 관리자 의존성은 v1 후보에서, 고객 웹 의존성은 가용 `C:/_proj/final_workspace`에서 **읽기 복사만** 했습니다. 확장 길이 경로와 12-thread SHA-256 대조로 관리자 26,909개·웹 26,849개 파일을 확인했습니다. source 의존성에는 쓰지 않고 candidate cache만 사용합니다. private env·기존 빌드 산출물은 복사하지 않았습니다. 원본 두 작업 폴더에 코드·설정·Git 쓰기는 하지 않았습니다.
- 실행기: 공유 scratch Python 3.12·공식 Node 24.22.1 ARM64·MinGit. Python 3.14 subprocess Git은 사용하지 않습니다. 기본 Git diff 조회가 60초 timeout인 기록은 환경 조회 실패이며 제품 RED가 아닙니다. MinGit 재조회는 완료했습니다.
- 최초 빌드의 `NEXT_DIST_DIR=.next-v2`가 새 경로를 tsconfig에 추가했습니다. 생성 변경은 보존 백업 후 후보의 tsconfig를 상속 바이트로 되돌리고, 최종 관문은 기본 `.next`로 다시 실행합니다. 원본 tsconfig는 변경하지 않았습니다.

## 최종 검증

첫 `final-gates/` 실행은 wrapper **exit 1**입니다. launcher 18개 중 전체 cmd 음성 시험 1개(전달/LF/CRLF 3 subcase)가 실패했고, 나머지 17개는 통과했습니다. 누락된 필수 파일을 PowerShell이 실패로 출력했지만 인자 없는 단일 줄 `exit /b`가 0으로 반환했습니다. 이전 성공 로그는 이 음성 코드 전파 검사를 넣기 전 12개/16개 시험이므로 동일 범위의 결과가 아닙니다. 이를 환경 오류로 분류하지 않습니다. `&& exit /b 0 || exit /b 1`로 두 bootstrap의 반환을 명시해 동일 음성/양성 시험이 통과했습니다(`green-exitcode.log`).

이 실패 실행에서도 실제 후보 check·admin lint·typegen·tsc 전후·unit 41개·전체 webpack build는 각각 exit 0입니다. wrapper 실패를 이 개별 성공과 혼동하지 않으며, 이 결과를 최종 합격으로 재사용하지 않습니다. 최종 전체 재실행은 새 `final-gates2/`에 보존하고, source/test 입력 해시 전후 동일성과 각 종료 코드를 확인합니다. 최종 수치·전달 검증은 상위 `manifest.json`, `delivery-validation.json`을 따릅니다. 기존 실행과 재실행 수치를 합산하지 않습니다.

최종 `proc_09c49cc8048d` 결과를 회수했습니다: wrapper exit **0**, 아래 개별 관문 **8/8 = 100%** exit 0. 입력 파일 **110개**의 전후 SHA-256은 동일합니다. `final-gates2/execution-results.json`, `inputs-before.json`, `inputs-after.json`을 참조합니다.

P1 증거는 RED LF/전달 255·CRLF 0 → 최종 전달/LF/CRLF check 각각 0, 같은 전체 cmd의 필수 파일 누락은 각각 **1**입니다. P2의 두 독립 반례는 RED 무관 listener/앞선 API 사망 각각 **0(잘못된 성공)** → 최종 대역 경계에서 각각 **1(의도한 실패)**입니다. HTTP 미준비·시작 실패·뒤늦은 충돌·최종 listener/port/HTTP 상실·소유 PID 재사용·종료 실패 유지도 검증했습니다. 실제 socket·서비스·DB·HTTP health 호출은 하지 않았으며 transport/OS effect는 시험 대역입니다. 실제 후보 check 성공은 설정값 유효성·DB 접속·앱 import 성공을 뜻하지 않습니다.

의존성 원본 보존 재검사(`source-preservation-final.json`)는 관리자 26,909개·고객 웹 26,849개 SHA-256 불일치 0, 원본 두 작업 폴더의 기존 선택 10경로씩 동일입니다. 선택 경로·의존성 범위 밖 원본 전체 파일 감사라는 뜻은 아닙니다. v1/예약 후보·보호 규칙·상속 소스 보존과 정역 patch tree는 최종 delivery-validation에서 별도로 확인합니다.

문서 편집 도구가 혼합 줄바꿈 wiki를 정규화한 중간본은 따로 보존하고, v1 원바이트에 새 상태 줄만 삽입해 삽입 외 바이트 동일성을 검증했습니다(`wiki-byte-preservation.json`). 첫 closure 도구는 `update-index --cacheinfo` 이후 갱신되지 않은 stat를 내용 변경으로 오판했습니다(`closure.log`). 실제 나열 11경로의 no-filter blob은 index와 모두 같았습니다. 보호 규칙이나 index를 완화하지 않고 closure를 실제 바이트 blob 대조로 바로잡았습니다. 이 도구 실패는 제품 RED나 시험 실패로 합산하지 않습니다.
