# D-CS-015 (개정 2) 활동 판정 LLM — 규칙 먼저, 규칙이 못 읽는 원문만 LLM

`[결정 2026-10-12]` 사용자 결정 — 아래 제안값 그대로. 개정 1(10-09)은 「개정 이력」에 남긴다. wiki 반영은 문서 일괄 정리 때 한다.

## 한 문단 요약

「09:00~18:00」 · 「매주 화요일」 · 분류 코드 VE03 · 재난 유형 「호우」처럼 **간단하고 정형화된 원문은 규칙(코드)** 이 읽는다 — 빠르고 공짜이고
10-12 재평가에서 한 번도 틀리지 않았다. 「명절이 아닌 금요일은 휴무」 · 「하절기 09~19시, 동절기 09~18시」처럼 **문장이 제각각이라 규칙이 못 읽는
원문만 LLM** 이 읽는다. LLM 은 원문을 **규칙표로 한 번 바꿔 저장**하고, **매일 판정은 저장된 표에 그날 날짜를 대입하는 코드**가 한다 — 원문이 바뀔
때만 다시 읽는다. 휴무 · 재난처럼 틀리면 고객을 닫힌 곳 · 위험한 곳에 보내는 판정에서 LLM 은 **조심하는 쪽(휴무다 · 막는다)으로만** 정한다.

## 판정별 정리

| 판정 | 규칙이 읽는 것 | LLM 몫(규칙이 못 읽는 것) | LLM 이 정할 수 있는 값 | 저장 |
|---|---|---|---|---|
| ① 정기휴무 | 「매주 X요일」 · 「매월 n번째 X요일」 · 「연중무휴」 · 공휴일 조건(공휴일 데이터로) | 제각각인 문장 — 서로 다른 휴무 원문 269개 중 37개(14%) | **휴무다**만. 「휴무 아님」은 확정하지 않는다(모름) | `ac_place` 휴무 규칙표 |
| ② 운영시간 | 「HH:MM~HH:MM」 · 「매주 X요일 휴무」 | 계절 · 요일별 · 입장 마감이 섞인 원문 — 1,932곳 중 1,636곳(85%) | 시간표 전부(원문 인용 검증) | `ac_place.hours_week` · `hours_read` |
| ③ 실내외 | 관광공사 분류(확실한 대 · 중분류) | 분류로 안 정해지는 장소(약 50%) | 실내 · 야외(인용 검증). 그래도 모르면 계획 단계에서 고객에게 | `activity.ac_indoor` |
| ④ 재난문자 | 수정본 §8 분류표 + D2-1 세 규칙 | 분류표에 없는 유형 · 본문을 읽어야 아는 문자 | **막는다 · 실내외를 물어야 한다**만. 「괜찮다」는 확정하지 않는다 | 저장 안 함(실시간 사실) |
| ⑤ 실시간 운영 | — | 웹 공지(임시휴무) | — | 섀도만 |

- ① 공휴일 조건(「공휴일이면 개방」 · 「명절 당일」, 133개)은 LLM 이 아니라 **공휴일 데이터**(`read.holiday`)로 정한다.
  원문에 정보가 없는 것(「홈페이지 참조」 · 「점포별 상이」, 60개)은 누가 읽어도 모름이다.

## 왜 고치나 — 10-12 재평가

근거: `eval/reports/activity_judge/20261012T022514Z/전환리포트.md` (사람 검토 라벨 52건 · gpt-5.4-nano 3회 반복 · 항목 단위 부트스트랩 95% CI).

| 판정 | 규칙 | LLM | LLM − 규칙 | 확정했는데 틀림 (규칙 / LLM) |
|---|---|---|---|---|
| ① 휴무 | 16/16 | 46/48 | −0.04 [−0.13, 0.00] | 0 / 2 |
| ② 운영시간 | 8/14 (나머지 모름) | 42/42 | +0.43 [+0.21, +0.71] | 0 / 0 |
| ③ 실내외 | 5/10 (나머지 모름) | 30/30 | +0.50 [+0.20, +0.80] | 0 / 0 |
| ④ 재난 | 12/12 | 33/36 | −0.08 [−0.25, 0.00] | 0 / 3 |

- 규칙은 한 번도 틀리지 않았다 — 모르는 것만 「모름」이다. 그래서 「규칙을 LLM 으로 바꾸기」가 아니라 **「규칙이 모를 때만 LLM」**.
- LLM 이 틀린 5건은 모두 **풀어 주는 쪽**이었다 — closure-06(규칙 모름 · LLM 「휴무 아님」 · 실제 휴무), disaster-04(LLM 「괜찮다」 · 실제 막아야 함).
  「조심하는 쪽으로만」이었다면 둘 다 모름 · 막음으로 남았다(구현 계획 D2 의 「안전 비대칭」).
- 멘토 피드백(10-08): 실내외는 처음 한 번만 LLM 으로 판정해 저장 · 모르면 계획 단계에서 묻고 감시 루프에서는 묻지 않는다.

## LLM 이 하는 일과 매일 판정은 다르다

| | 무엇을 | 얼마나 자주 | LLM |
|---|---|---|---|
| 원문 읽기 | 원문 문장 → 규칙표(「휴무: 둘째 주 월요일 · 6~8월 09~19시 …」) | **원문이 바뀔 때만** | 규칙이 못 읽을 때만 |
| 매일 판정 | 규칙표에 그날 날짜 · 시각을 대입(「10/13 은 둘째 주 월요일인가」) | 고객 문의 · 계획 검증 · 매일 밤 감시 | **쓰지 않는다** — 코드 계산(`ledger.state` · `verdicts.hours_verdict`) |

- **원문 바뀜 알아채기** `[새로 할 일]`: 지금 활동 원장(`ac_place`)은 CSV 한 번 적재가 전부라 관광공사 원문이 바뀌어도 모른다.
  정기적으로 관광공사 목록의 수정 시각을 비교해 **바뀐 장소만** 원문을 다시 받아 적재한다 → 적재가 그 행의 규칙표를 비우고 → 다시 읽는다.
  주기: **매일 밤** — 코어 새벽 작업(`catalog_hours`)과 같은 창 03:00~08:00. 바뀐 것만이라 호출이 적다.
- **임시휴무는 이 결정의 범위가 아니다** — 관광공사 원문에 없다. 실시간 운영 확인(웹, 섀도) · 고객 · 현장 제보 · 요식의 새벽 확인 같은 다른 경로의 몫이다.

## 모델 — 지금은 API, 조건이 갖춰지면 sLLM

처음에는 「운영시간처럼 비슷한 일을 계속 반복해 부르니, 호출이 공짜인 sLLM 이 효율적」으로 sLLM 을 골랐다. 그 뒤 설계가 **「한 번 읽어 저장」** 으로
바뀌어 반복 호출이 거의 없어졌다(처음 1,636곳 한 번 + 원문이 바뀐 곳만). 그래서 지금은 효율이 아니라 **쓸 수 있나 · 정확도를 아나**로 고른다.

| | sLLM (gemma4:12b) | API LLM (gpt-5.4-nano) |
|---|---|---|
| 지금 쓸 수 있나 | 팀 GPU 서버 주소가 없다 | 된다(키 있음) |
| 정확도 | 재지 않았다 | 운영시간 42/42 · 실내외 30/30 |
| 비용 | 호출은 공짜, **서버를 띄워 두는 비용**(클라우드 GPU 면 켜진 시간만큼 — 대략 시간당 $0.5~$2) | 호출당 약 $0.0003 — 1,636곳 한 번 약 $0.5 |
| 코어와 같은 모델 | 같다(코어 새벽 작업이 gemma) | 다르다 — 결과를 저장해 쓰므로 판정이 갈라지지는 않는다 |
| 데이터가 밖으로 | 안 나간다 | 나간다 — 관광공사 공개 안내문이라 문제없다 |

- **지금: API LLM 으로 읽어 저장한다.**
- **sLLM 으로 바꾸는 조건**(셋 다): ① 팀 GPU 서버가 안정적으로 떠 있다 · ② gemma 로 골든셋을 재서 API 와 같은 기준(확정했는데 틀림 0)을 넘는다 ·
  ③ 호출이 다시 많아진다(요청마다 판정 · 장소 수만 곳).
- 코드는 둘 다 받는다(`place_hours.read_hours` 는 어떤 모델이든 받는다) — 바꾸는 것은 설정이다.
- `[확인 필요]` 팀 GPU 서버가 클라우드(시간 과금)인지 팀원 · 학원 컴퓨터인지.

## 저장 규칙

### ③ 실내외 — `activity.ac_indoor` (활동 스키마 · 코어 표는 바꾸지 않는다)

| 칸 | 뜻 |
|---|---|
| `content_id` | 장소(`ac_place.content_id`) |
| `outdoor` | true 야외 · false 실내 — 모름은 저장하지 않는다(행이 없음) |
| `decided_by` | `class`(관광공사 분류) · `llm` · `customer` · `operator` |
| `model` · `prompt_version` · `quote` | `llm` 일 때 — 어떤 모델 · 프롬프트 · 근거 인용(입력 원문에 실제로 있는 글) |
| `decided_at` · `decided_case_id` | 언제 · 어느 Case 에서 |

- 우선순위: `operator`(사람 수정) > `customer` > `llm` > `class`. 높은 값을 낮은 값으로 덮지 않는다.
- 갱신: 관광공사 분류가 바뀌면 `class` · `llm` 행을 지우고 다시 판정한다. `customer` · `operator` 는 남긴다.
- 순서: 저장값 → 관광공사 분류 → LLM 한 번 → 그래도 모르면 **계획 검증에서만** 고객에게 묻고 저장. **감시 루프에서는 묻지 않고** 판정 보류로 기록한다.

### ① · ② 휴무 · 운영시간 — `ac_place` 의 규칙표

- `hours_week` · `hours_read`(방법 rule|llm · 인용 · 읽은 시각). 휴무 규칙표 칸은 `[새로 할 일]`(지금은 원문을 요청마다 규칙으로 읽는다).
- 원문이 바뀌면 그 행만 비우고 다시 읽는다(`load_places.py` — 원문이 같으면 저장값 유지).

## 고객 안내

LLM 이 읽은 값으로 판정했으면 답에 붙인다. 규칙 · 고객이 정한 값에는 붙이지 않는다.
- 운영시간 · 휴무: 「운영시간은 공개된 안내문을 자동으로 읽어 확인했어요. 방문 전 한 번 더 확인해 주세요.」
- 실내외: 「실내·야외 여부는 자동으로 판단한 결과예요. 다르면 알려 주세요.」 — 고객이 고치면 그 값이 우선한다(저장 규칙)
- 팀원 제안(10-12): 우리 자료로 못 찾아 LLM 이 확인한 경우 「LLM 확인 결과」라고 함께 안내.

## 지키는 것

- 규칙이 아는 값은 LLM 으로 덮지 않는다. LLM 은 규칙이 「모름」일 때만.
- 휴무 · 재난에서 LLM 은 **조심하는 쪽(휴무다 · 막는다 · 물어야 한다)으로만** 정한다. 풀어 주는 쪽(휴무 아님 · 괜찮다)은 「모름」으로 남긴다.
- 인용 검증을 통과한 값만 저장한다 — 원문에 없는 인용 · 시각 · 요일은 버린다. 못 넘으면 모름.
- 모름은 저장하지 않는다. 「열림 · 실내 · 괜찮다」로 바꾸지 않는다.
- 호출 상한 `travel.activity_judge.budget`(원문 해석 2,000/일 · 30,000/월, 웹 50/일 · 1,000/월). 넘으면 부르지 않고 모름.
- 종류별 모드는 `travel.activity_judge.kind_modes` 한 곳 — `llm` 값은 이 개정이 accepted 된 뒤에만 받는다.
- 개정 1 의 「지키는 것」(섀도에서 고객 결과 불변 · 웹 본문 저장 안 함 · 재난 정지 문자는 판정 계층에 보내지 않음)은 그대로.

## 이 결정이 말하지 않는 것

- 대체 장소 고르기에 LLM(팀원 Jev Choice 시험 — 27문제 74.1%) — 따로 정한다.
- 에이전트 구조(구현 계획 D1).
- 코어 감시 경로가 같은 값을 쓰도록 연결하는 일 — 코어 협의(요청 3).
- 임시휴무 확인.

## 되돌리는 조건 (종류별)

하나라도 해당하면 그 종류만 규칙으로 돌리고 저장된 `llm` 값을 쓰지 않는다(행은 남겨 원인을 본다).
- 저장된 `llm` 값 표본 확인에서 오답 — 무작위 **30건** 중 **위험한 오답**(닫혔는데 열림 · 실내인데 야외 등) **1건**이면 끔, 단순 오답은 **2건**까지 허용.
  확인 시점: 처음 켤 때 한 번, 큰 재적재 뒤 한 번.
- 인용 검증 탈락으로 대부분 모름이 된다.
- 비용 · 지연이 상한을 넘는다.

## 구현 순서 (accepted 뒤)

1. 운영시간: `read_hours.py` 가 API 모델을 받게 → 1,636곳 읽어 저장 → 무작위 30곳 사람 확인
2. 휴무 규칙표 저장 칸 · 규칙이 못 읽는 37개만 LLM(휴무다만 확정)
3. `activity.ac_indoor` 마이그레이션 · 우선순위 · 시험 → 실내외 LLM 1회 판정
4. 재난: 분류표에 없는 문자만 LLM(막는다 · 물어야 한다만)
5. 원문 바뀜 알아채기(관광공사 수정 시각 비교 → 바뀐 장소만 재적재)
6. 고객 안내 문구
7. 계획 검증에서 고객 답 저장 — 코어가 재개 때 답을 넘겨야 한다(협의 메모 요청 5)
