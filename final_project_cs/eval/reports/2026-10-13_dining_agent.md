## 4. 측정이 찾은 문제와 고침

| 실측 | 고침 |
|---|---|
| 체크 이름이 도구 이름과 달라 gpt-4o-mini 가 `business` · `attributes` 를 지어 썼다(검증기가 4건 거절) | 체크 이름을 도구에 맞춤(open_at · business …) · 「다른 이름을 만들지 않는다」 |
| `find_place` 결과에 `verdict` 칸이 없는데 `verdict: ok` 를 근거로 적었다(검증기가 거절) | 규칙 도구는 모두 `verdict` 를 낸다(찾음 ok · 확인 필요 unknown · 못 찾음 bad) |
| found 를 「당연하다」며 빼먹음(dev 1판 5건) · 식사 둘인 날 JSON 대신 글로 끝냄(DG-013) | 「시각 있는 식사마다 found · open_at 은 반드시」 · 글로 끝나면 JSON 형식을 강제해 **한 번만** 다시 묻는다 |
| 휴무 규칙이 하나도 없는 가게를 원장 함수(`is_closed_on`)가 「안 쉰다」로 냄 | 도구가 `closure_state` 를 같이 봐서 정보가 없으면 unknown(모름을 없음으로 바꾸지 않는다) |
| `record_status = unknown` 을 「영업 중으로 기록」이라 말함 | 「폐업 기록이 없다(영업 상태를 따로 확인하지는 않았다)」 |

- 프롬프트는 dev 로만 고쳤다(1회). holdout 은 고친 뒤 한 번만 돌렸다.
- 근거 검증(§6)은 의도대로 일했다 — 지어낸 체크 이름 · 없는 경로 인용을 모두 「unknown(검증 실패)」로 돌리고 셌다.

## 5. 한계 · 남은 것

1. 표본이 작다 — dev 41 · holdout 22 체크. 방향은 분명하지만 「100%」는 이 표본에서의 값이다.
2. 기대 판정이 규칙 값이라 **B 의 영업 판정은 구조상 맞을 수밖에 없다** — B 가 재는 것은 「체크 고르기 · 인용 · 형식」이다. 규칙이 unknown 일 때 원문을 해석하는 능력(설계 §3)은 이 자료에 사례가 2건뿐이라 거의 안 쟀다 → 원문만 있는 가게 · 출처가 어긋나는 가게 사례를 넣는다.
3. gemma 는 로컬 e4b(CPU) dev 1판뿐이다 — 서버 12b(GPU)는 재지 않기로 했다(사용자 결정). 운영에 gemma 를 쓸 때는 그 모델로 다시 잰다.
4. 운영 배선 — **했다**(커밋 전): 접수 확인(설계 §1 ①)에 그림자로 붙여 규칙 검사와 나란히 `dining.dn_agent_shadow`(232)에 기록 · 가드레일 `travel.dining.agent_shadow.enabled` 기본 꺼짐 · 셈 `scripts/dining/shadow_report.py`. 새벽 확인에는 쓰지 않는다. 켜는 것과 1주 어긋남 분류는 팀이 정한다.
