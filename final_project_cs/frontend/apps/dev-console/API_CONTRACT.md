# 개발팀 콘솔과 코어·에이전트 연결 계약

작성일: 2026-09-21. **상태: 현재 프론트 표시 계약 + 백엔드 협의안.** 아래 기능의 실제 HTTP API와 에이전트 연결은 구현·검증하지 않았다. 기존 Case API를 이 계약과 동일한 것으로 취급하지 않는다.

## 사용 구조와 담당

```text
개발자 → 콘솔 → 코어의 테스트 실행 API → 선택한 팀
                   ↓                       ↓
                기록 저장 ← 입력·도구 응답·판정·출력 이벤트
                   ↓
                 콘솔 조회
```

| 담당 | 작업 |
|---|---|
| 프론트엔드 | 입력 폼·실행 요청·실행 ID별 조회·단계 상세·A/B 비교 화면, API 어댑터 구현 |
| 코어 | 테스트 실행 생성, 팀 호출, 공통 실행 ID 전파, 기록 저장·조회, 실패·재실행·동시 실행 처리 |
| 액티비티팀 | 활동 장소·시간 조건 조회와 판정, 사용한 원값·기준·근거 참조 기록 |
| 요식업팀 | 식당 이용·예약 조건 조회와 판정, 사용한 값·누락값·근거 참조 기록 |
| 이동팀 | 후보 경로·교통수단·소요 시간·예상 도착, 선택 조건과 출처 기록 |

각 팀이 반드시 별도 서버일 필요는 없다. 코어 내부 모듈이면 함수 호출, 별도 서비스이면 API 호출로 연결한다. 콘솔은 이 차이를 알 필요 없이 코어의 공통 API만 사용한다.

로컬 개발에서는 개발자 PC에서 콘솔·코어를 실행하고 수정 중인 팀 코드를 연결한다. 공용 개발에서는 공용 콘솔과 공용 코어에 연결된 버전을 실행한다. 공용 콘솔이 개발자 PC의 미반영 코드를 자동으로 실행하지 않는다. `localhost`는 해당 프로세스가 실행되는 PC를 가리킨다.

## 현재 어댑터의 메서드

정확한 TypeScript 정의는 [`src/lib/model.ts`](src/lib/model.ts)에 있다. 현재는 `src/lib/demo`가 이를 구현한다.

| 메서드 | 입력 | 결과 |
|---|---|---|
| `createRun` | `TestRequest`, 선택적 `retryOf` | 새 `Run` |
| `getRun` | 실행 ID | 현재 `Run` 스냅샷 |
| `listCases` / `getCase` | 없음 / 사례 ID | 사례 목록 / 사례 |
| `saveCase` | 실행 ID, 사례 이름 | 실행 당시 입력을 저장한 `TestCase` |
| `createComparison` | 사례 ID | 동일 사례로 만든 A/B 실행 ID와 사례 스냅샷 |
| `getComparison` | 비교 ID | 저장된 비교 연결 정보 |

주소·인증·오류 형식은 코어팀과 합의 후 정한다. 위 메서드 이름이 이미 제공되는 HTTP 경로를 의미하지 않는다. 화면에서 임의 서버 주소를 입력하거나 비밀 키를 보관하는 기능은 만들지 않았다.

## 입력과 버전

현재 `TestRequest`는 고정 샘플을 조작하는 범위다.

```json
{
  "target": "activity",
  "version": "B",
  "fixtureMode": "normal",
  "input": { "time": "16:45", "durationMinutes": 60, "transport": "bus" }
}
```

- 대상: `activity`, `dining`, `mobility`, `core`. 사용자 확정 기준은 세 에이전트팀이며 코어는 별도 조율 계층이다.
- 시각: 00:00–23:59. 소요 시간: 정수 1–240분. 교통수단: 버스·도보·택시. 샘플의 장소·시간대는 고정이다.
- `version=A/B`는 실제 코드·모델 ID가 아닌 데모 버전이다. `fixtureMode=tool-error`는 도구 오류 재현용이다.
- 실제 연동에서는 장소 ID·좌표·날짜·시간대·여행 조건, 선택 가능한 팀/코드/프롬프트/모델 버전을 서버가 검증해야 한다. 지금의 단순 샘플 입력을 실제 전체 여행 입력 사양으로 채택하지 않는다.

## 실행 기록에서 필요한 값

| 현재 필드 | 의미와 표시 원칙 |
|---|---|
| `Run.id` | 한 번의 실행 ID. 재실행·A/B는 각각 새 ID |
| `request` | 실행 당시 고정된 입력. 이후 폼 편집과 분리 |
| `status` | 현재 표시 상태 `running`, `completed`, `failed` |
| `createdAt`, `updatedAt`, `completedAt` | ISO 시각. 완료 시각은 종료된 경우만 |
| `retryOf` | 재실행 원본 ID. 기존 기록 보존 |
| `steps[].id`, `owner`, `phase` | 단계 ID, 담당 팀/코어, 샘플 진행 구간. 같은 phase는 병렬일 수 있음 |
| `steps[].status` | `pending`, `running`, `completed`, `failed` |
| `steps[].input` | 단계에 실제 전달된 구조화된 입력 |
| `observations` | 도구에서 가져온 값, 원 출처·응답 참조 |
| `comparisons` | 실제 비교한 값과 기준. 해시만으로 대체하지 않음 |
| `output` | 팀·단계의 반환 결과 |
| `evidenceRefs` | 이 실행에서 사용한 근거를 식별하는 참조 |
| `summary`, `error` | 기록된 결과 요약 또는 오류. UI가 임의로 성공 문구 생성 금지 |
| `result.actual`, `expected`, `matched` | 출력과 기대 결과의 대조. 실행 완료와 구별 |

현재 `FactRow`는 `{label, value, reference?}`의 표시용 행이다. 실제 계측에서는 원본 값·자료형·단위·출처·관측 시각·사용한 규칙/연산자를 서버에 보존하고, 어댑터가 표시용 행으로 변환하는 방식을 권장한다. UI에 없는 원본 필드가 현재 수집되고 있다고 가정하지 않는다.

`phase`는 이번 고정 샘플의 순서를 표현한다. 실제 에이전트는 재시도·동적 분기·병렬·대기가 있으므로 `parentStepId`, `dependsOn`, 시도 번호, 시작/종료 시각, 순서 번호 등을 별도로 합의해야 한다. 실제 서버의 순서 정보를 그대로 사용하고, 단순 화면 순서로 실행 의존성을 추정하지 않는다.

조회 시 실행 ID를 기준으로 기록을 묶는다. 한 여행·Case의 여러 시도 이벤트를 한 실행으로 합치지 않는다. 최종 답변만 보내면 중간 과정은 표시할 수 없다. 숨겨진 모델 사고 과정이 아니라 관측 가능한 도구 응답, 명시적 비교, 반환 결과를 수집한다.

## 진행 조회와 오류

현재는 브라우저가 진행 중인 샘플 실행만 주기 조회한다. 실제 구현에서는 polling API부터 연결하거나 코어가 제공하는 SSE를 별도 어댑터로 연결할 수 있다. 실제 SSE 구현은 없다.

실제 API에는 다음을 합의한다.

- 작업 생성의 중복 요청 방지·멱등 키와 재시도 규칙
- 단계 이벤트의 단조 증가 순서, 중복·누락·재접속 처리
- 대기·중단·시간 초과·취소 등 추가 상태와 화면 매핑
- 존재하지 않는 실행, 권한 없음, 형식 오류, 네트워크·도구 실패의 구분
- 오류 발생 시 진행 기록 유지와 재실행의 새 ID

표시할 데이터가 없으면 미수집·실패·대기 상태를 구분한다. 실제 오류를 데모 데이터나 0비용·0토큰·정상 판정으로 바꾸지 않는다.

## 사례와 평가

사례는 실행 당시 입력의 스냅샷이다. A/B 비교는 버전 외 입력·도구 응답·평가 기준을 고정해야 한다. 실제 비교에는 데이터셋/fixture 버전, 코드·프롬프트·모델 설정, 평가 기준 버전을 함께 기록한다. 현재 모델/프롬프트 선택·배치 평가·토큰·비용 측정은 없다.

현재 기대 결과는 샘플 어댑터가 정한 예시다. 실제 평가의 정답은 별도 검토된 테스트 데이터와 평가 기준에서 받아야 하며 실제 출력에서 그대로 만들어서는 안 된다. 비교 결과에서 각 실행의 원본 기록으로 이동할 수 있어야 한다.

## 실제 연결 순서

1. 코어 담당과 위 표시 계약에 매핑할 실제 API·인증·저장 방식을 확정한다.
2. 코어와 한 팀을 연결해 실행 생성 → 단계 기록 → 결과 조회를 확인한다.
3. 실제 HTTP 어댑터를 추가하고 응답을 스키마 검증한다. 코어 비밀 키를 `NEXT_PUBLIC_*`나 브라우저 저장소에 넣지 않는다.
4. 나머지 두 팀과 통합 실행, 병렬·오류·재실행을 연결한다.
5. 공용 서버의 접근 제어와 기록 보존을 갖춘 뒤 팀원 공동 사용을 검증한다.

사용자 웹의 로그인 없는 MVP 결정은 개발팀 콘솔의 공용 서버 접근 정책을 대신하지 않는다. 현재 앱은 기본적으로 개발자 PC의 loopback 주소에서 실행한다.
