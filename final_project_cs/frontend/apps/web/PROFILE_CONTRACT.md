# 마이페이지 · 사용자 정보 연동 대기 항목

> `[2026-10-03 사용자 결정]` **복구용 이메일은 제품에서 뺐다.** 시작 화면·마이페이지·소개 화면에 이메일 칸이 없고, 웹은 `recovery_email` 을 보내지도
> 읽지도 않는다(서버 호출은 남아 있어도 화면이 쓰지 않는다). 알림은 디스코드 웹훅 하나로 받는다. 아래 이메일 설명은 옛 기록이다.

최신 확인: 2026-09-29 · SKN32 `develop` `fc1ac0a` 코드 기준. 화면별 요구·사용 API·협의와 연결 상태는 [공유 연동 문서](../../../wiki/external/web-screen-api.md)에서 관리한다.

작성일: 2026-09-28 · 상태: 화면·입력 검증까지 구현, **저장·닉네임·복구 이메일은 백엔드 API 없음으로 미연동**.

`[2026-10-03]` **`role-manager`에 복구 이메일·디스코드 웹훅 API가 있다** — `GET`·`PUT /v1/web/profile`, `POST /v1/web/profile/discord/test`([REST 명세](../../../wiki/external/rest-endpoints.md) 「고객 연락처」). 복구 이메일은 백엔드 담당이 `lib/contact.ts`로 온보딩·마이페이지에 이었다(2026-10-01). 디스코드 웹훅은 같은 날 오후 사용자 지시(「서버에서 작업한 것은 프론트가 다 들어가 있어야」)로 이었다 — 온보딩 카드의 저장(`lib/webhook.ts`), 마이페이지의 가린 주소·상태 조회, 수정 화면의 등록·바꾸기·지우기, 시험 메시지. 연결 상태는 [화면별 연동 문서](../../../wiki/external/web-screen-api.md#마이페이지-디스코드-웹훅-mypage--mypageedit). 아래 §1 표는 2026-09-29 `develop` 기준 기록이며 닉네임 API는 여전히 없다.

**계약의 정본은 백엔드다.** 아래는 웹이 쓸 수 있는 것과 없는 것을 코드로 확인한 결과와, 백엔드와 합의할 항목이다. 웹은 없는 API나 필드를 있다고 가정하지 않는다.

## 1. 지금 백엔드가 주는 것 (2026-09-29 확인)

기준 커밋의 `app/` 라우트와 웹 `src/lib/profile.ts`를 대조했다. 닉네임·복구 이메일을 읽고 저장하는 웹 API와 연결을 찾지 못했다. 다른 브랜치 전체나 운영 서버를 이번에 확인했다는 뜻은 아니다.

| 항목 | 백엔드 | 웹 표시 |
|---|---|---|
| 사용자 키(토큰) | `POST /v1/web/session` 이 `customer_id`·`user_key`·`notice` 를 준다. 원문 키는 발급 때 한 번만 나오고 서버에는 해시만 있다(`migrations/025_web_user_keys.sql`) | 실제 연결이 저장한 브라우저 키(`localStorage` `tripilot.web.user-key.v1`)를 가려서 보이고, 보기·복사만 한다. 없으면 「발급된 토큰이 없어요」. 마이페이지를 봐도 새 키를 발급하지 않는다 |
| 닉네임 | 발급 응답에 없다. 저장 칸도 없다 | 「닉네임 미발급」. 웹이 `여행자1` 같은 값을 만들지 않는다 |
| 복구 이메일 | 칸도 API도 없다(`customers.email_hash` 는 해시이고 웹 API로 읽거나 쓰지 않는다) | 「등록된 이메일이 없습니다.」 온보딩 `/start` 의 선택 입력 카드는 같은 항목의 **초안**을 페이지 메모리에만 두고 보내지 않는다(「서버에 저장하지 않아요」 안내). 그래서 마이페이지에는 등록된 것처럼 보이지 않는다 |
| 프로필 저장 | API 없음 | 편집 화면의 `저장` 비활성 + 「프로필 저장 기능은 준비 중이에요.」 |
| 프로필 이미지 | 없음 | 공통 기본 이미지(`Avatar`, `public/images/tripilot-avatar-default.svg`와 같은 모양을 고른 테마 색으로 그린다)만. `이미지 변경` 비활성 |

`useProfile`은 같은 브라우저에 저장된 기존 키를 읽는다(마이페이지를 열어도 키를 새로 발급하지 않는다). 로컬 저장이나 임시 응답으로 저장된 것처럼 보이지 않는다. `[2026-10-03]` 데모 모드는 없앴다.

## 2. 백엔드와 합의할 것

아래는 2026-09-28부터 있던 미합의 항목을 보존한 것이다. 예시 경로를 제공 중인 API로 해석하지 않는다. 이번 개정에서는 새 협의안이나 화면별 API 목록을 추가하지 않는다.

1. **닉네임 발급**: 키를 발급할 때(`POST /v1/web/session`) 초기 닉네임을 서버가 정해 응답에 싣는지, 규칙(예: `여행자N`)과 중복 허용 여부.
2. **사용자 정보 조회**: 키로 여는 조회 API(예: `GET /v1/web/me`)의 응답 필드 — 닉네임, 복구 이메일(등록 여부·표시 형태), 이메일 확인 상태.
3. **사용자 정보 수정**: 수정 API와 받는 필드(닉네임·복구 이메일만, 키는 받지 않음), 닉네임·이메일 길이와 허용 문자, 오류 코드, 동시 수정 처리. 웹은 이것이 정해지면 저장을 연결한다 — 저장 중 중복 요청 막기, 성공하면 조회 화면으로 돌아가 메뉴 닉네임 갱신, 실패하면 입력과 편집 화면 유지.
4. **복구 이메일 확인과 토큰 찾기**(후속): 이메일 소유 확인(인증 메일), 토큰을 잃었을 때 이메일로 되찾는 흐름과 그 화면(마이페이지 밖의 「토큰 찾기」). 키 원문은 서버에 없으므로 「되찾기」가 새 키 발급(`rotate`)인지부터 정해야 한다.
5. **프로필 이미지**(후속): 바꿀 수 있게 할지, 저장 위치와 크기 제한.
6. **온보딩에서 받은 복구 이메일의 저장**: `[2026-10-01 백엔드 담당 구현]` 카드를 떠날 때 `lib/contact.ts`로 저장한다 — 키가 있으면 서버, 없으면 이 브라우저에 두었다가 키가 생기면 서버로 올린다(`components/contact-sync.tsx`). 서버 검사·길이 제한은 백엔드 `customer_profile.py`가 정본이다. 아래는 결정 당시 기록이다. `[결정 2026-09-28 사용자 · 미구현]` 여행을 등록할 때 — 약관 동의와 함께 개별 토큰(사용자 키)을 만드는 그 시점에 — 취향 설문(`constraints.survey`)처럼 한 번에 같이 저장한다. 웹은 그때 온보딩 초안을 실어 보낸다. 백엔드와 합의할 것: 받는 요청과 필드 이름, 서버 쪽 형식 검사·길이 제한, 빈 값은 「등록·변경 요청 없음」(칸을 빼고 보내 기존 값을 지우지 않음). 합의·구현 전까지 웹은 보내지 않는다.

웹이 지금 하는 입력 검사는 닉네임 공백과 이메일 형식뿐이다(`src/features/profile/model.ts` — `checkDraft`, 온보딩과 같이 쓰는 `recoveryEmailProblem`: 앞뒤 공백만 지우고, 비면 미입력, 그 밖에는 이메일 형식). 길이 제한은 3번이 정해질 때 붙인다.

## 3. 현재 구현과 남은 범위

`src/features/account/key-settings.tsx`와 `src/lib/live/client.ts`에 토큰 가져오기·재발급이 구현돼 있고 마이페이지가 live에서 표시한다. 가져오기는 입력한 키로 여행 목록을 조회해 유효성을 확인한 뒤 저장한다. 재발급은 사용자 확인 후 `POST /v1/web/session/rotate`를 호출하고 새 키를 저장·안내한다. 프로필 편집 화면의 토큰 직접 수정과는 별개다.

남은 범위:

- 이메일 인증, 토큰 발송, 마이페이지 밖의 「토큰 찾기」 화면. 이메일을 입력했다고 인증 완료나 복구 설정 완료로 표시하지 않는다.
- 닉네임·이메일 저장, 프로필 이미지 변경. 현재 입력 검증과 비활성 버튼만 구현돼 있다.
