작성일: 2026-09-21. 최초 범위는 로그인·회원가입·서비스 결제 없는 5개 화면이었다. 현재는 소개·온보딩·계획 읽기 확인·여행 목록·마이페이지까지 확장됐다. 이번 문서는 실제 프론트 구현 기준이며, 전체 앱·웹 확장 기획을 대체하지 않는다.

수정일: 2026-09-24. 사용자 지시로 2026-09-23 목업 [`tripilot-intro-animated-nav-switch.html`](mockups/tripilot-intro-animated-nav-switch.html)을 기준선으로 전환했다. 소개·온보딩(약관·여행 취향) 화면과 한/영 전환, 설정 사이드바를 더했고 5개 화면의 디자인을 목업에 맞췄다. 이후 화면 변경은 이 앱에서 한다. 기준선 파일은 원본(11MB)의 내장 이미지를 같은 폴더의 이미지 파일 참조로 바꾼 사본이며 내용은 같다.

목업 위치(2026-09-29): 디자인 기준선과 기존 HTML 시연 파일·공통 리소스 31개는 [`mockups/`](mockups/README.md)에 함께 보존한다. 실행 방법과 과거 목업 검증 기록은 [목업 안내](mockups/README.md)를 따른다. 현재 앱 코드와 `public/images/`의 리소스는 그대로다.

최신 확인: 2026-09-29 · `develop` `fc1ac0a`. 아래 현재 기준은 코드와 대조했고, 뒤의 날짜별 검증 기록은 당시 결과를 보존한다. 화면별 API 협의와 연결 상태는 [공유 연동 문서](../../../wiki/external/web-screen-api.md)를 따른다.

## 기술스택

Next.js 16 App Router + React 19 + TypeScript strict. Node.js 22와 npm을 사용하고 정확한 의존성은 `package-lock.json`으로 고정한다. CSS Modules와 공통 디자인 토큰으로 기존 목업의 색상·간격·배치를 유지한다. TanStack Query가 비동기 여행 데이터·캐시·진행 조회를 소유하고, Zod가 어댑터 데이터와 입력을 검증한다. 로컬 탭·선택·입력 상태는 React로 관리한다. 한 개 입력창을 위해 추가 폼/전역 상태 라이브러리를 도입하지 않는다.

공식 참고: [Next.js 설치](https://nextjs.org/docs/app/getting-started/installation), [TanStack Query 설치](https://tanstack.com/query/latest/docs/framework/react/installation).

## 화면과 개발 순서

1. 공통 레이아웃·버튼·입력·상태 표시와 여행 데이터 계약을 먼저 정의한다.
2. `/`: 소개 3장(스크롤 스냅·등장 모션). 넓은 화면에서는 402px 기기 틀, 720px 이하에서는 전체 화면. 첫 장에는 언어 선택 카드(누르면 아래로 펼쳐지고, 고르면 접힌다)와 최근 여행 3개까지의 내 여행 카드가 있고 하단에는 아래로 가는 안내만 둔다. 둘째 장은 이용 방법 4단계를 앱 화면 캡처와 함께 옆으로 넘기는 카드다.
3. `/start`: 온보딩. 맨 위 선택 입력 `복구용 이메일` 카드(번호 없음, 다른 단계의 조건이 아니다) 아래로 약관·취향 카드. 약관은 끝까지 읽어야 동의할 수 있고, 여행 취향은 설문 안내 카드 뒤에 백엔드 설문(D-020)을 따른 6문항(우선순위는 분야·세부를 누른 순서로 매기는 한 카드)을 좌우로 넘기는 카드다. 답은 여행을 등록할 때 함께 보낸다.
4. `/trips/new`: 텍스트 입력·초안 보존·예시 계획·취향 표시. demo는 시나리오를 선택하고, live는 글·파일 최대 5개를 접수한다. `/intakes/[intakeId]`에서 읽기 상태·원문 근거 확인, 항목 수정·제외, 확인 등록 또는 일정 짜기를 수행한다.
5. `/trips/[tripId]/verification`: demo의 4단계·퍼센트·재시도·결과 이동. live는 별도 검증 단계가 없다는 안내를 표시한다.
6. `/trips/[tripId]/results`: demo의 요약·확인 필요 항목·일차 탭·상세 펼침과 관리 시작 차단. live는 별도 결과 통계를 만들지 않고 여행 화면으로 안내한다.
7. `/trips/[tripId]`: 일정·방문 순서(지도)·채팅을 한 번에 한 칸씩 보여 주고 하단 고정 탭 또는 플로팅 버튼으로 바꾼다.
8. `/trips`: 여행 목록과 demo 개별·선택 삭제(live 삭제 비활성). `/mypage`·`/mypage/edit`: 사용자 키 표시, live 키 가져오기·재발급, 닉네임·이메일 입력 검증. 프로필 저장·이미지 변경은 비활성이다.

디자인 출처는 [2026-09-23 목업](mockups/tripilot-intro-animated-nav-switch.html)이다. 목업의 내비게이션 비교 스위치 대신 오른쪽 위 메뉴(프로필·여행 목록 보기·언어·테마·플로팅 버튼 사용) 사이드바에서 언어, 테마(2026-10-03부터)와 여행 화면 내비게이션(기본 고정 하단 탭)을 고른다. 목업은 실제 지도 대신 방문 순서 개념도를 보이지만, 앱은 지도 제공자 설정을 유지하고 `demo`일 때 개념도를 보인다. 이전 디자인 출처(A-COP `8ed3548`의 `tripilot-intake-wireframe.html`)와 기존 HTML 시연 파일은 보존한다. 상태 오류·실패·없는 여행 안내는 각 화면 내부 상태로 처리한다.

## 코드 경계

- `src/app`: URL·공통 레이아웃·페이지 조합.
- `src/components/ui`, `src/components/layout`: 실제로 재사용되는 UI. `ui`에는 공통 프로필 이미지(`Avatar`), 홈·메뉴가 함께 쓰는 언어 카드(`language-picker`), 메뉴의 테마 카드(`theme-picker`)가, `layout`에는 기기 틀·여정 틀·풍경 배경·메뉴 사이드바가 있다.
- `src/features/intro`, `src/features/onboarding`: 소개 화면과 약관·취향 온보딩.
- `src/lib/i18n.ts`, `src/lib/settings.ts`: 한/영 문구 함수와 언어·내비게이션·테마 설정.
- `src/lib/theme.ts`, `src/styles/tokens.css`: 테마 이름과 첫 화면을 그리기 전에 저장된 테마를 거는 스크립트, 두 테마의 색 역할 변수. 화면 CSS에는 색을 직접 적지 않는다(`src/styles/tokens.test.ts`가 검사).
- `src/lib/profile.ts`, `src/features/profile`: 메뉴·마이페이지가 읽는 사용자 정보와 마이페이지 조회·수정 화면. 연동 상태는 [사용자 정보 연동 대기 항목](PROFILE_CONTRACT.md).
- `src/features/trip-registration`, `src/features/intake-review`: 등록 입력·초안과 live 접수 확인/편집/등록.
- `src/features/account`, `src/features/human-check`: 사용자 키 안내·관리와 선택적 Turnstile 확인.
- `src/features/verification`: 검증 진행과 결과 UI.
- `src/features/trip`: 여행 홈·목록·삭제·화면용 타입·공통 조회·live 제안/알림/이력.
- `src/features/map`: 공통 지도 표시 계약·지도 선택·네이버/Google 지도 컴포넌트.
- `src/lib/gateway.ts`, `src/lib/demo`, `src/lib/live`: 모드 선택, 데모, 실제 사용자 키·접수·여행·상담·제안/알림 연결.
- `src/styles`: 색상·서체와 공통 토큰.

여행 목록·조회·대화는 `TripGateway`, live 접수·확인·계획 생성·제안/알림은 `lib/live`의 별도 함수로 요청한다. 여행 캐시는 ID·화면 언어별로 나눈다. demo 문구는 선택 언어로 생성하지만 live 서버 문장·오류를 자동 번역하지 않는다. 선택 언어는 현재 접수 요청에 전달하지 않으며 서버의 접수 조립·계획 생성은 `locale="ko"`다.

언어(기본 English)·내비게이션(기본 fixed)은 `localStorage`의 `tripilot.web.settings.v1`에 보관한다. 사용자 키와 발급 안내도 `localStorage`, 등록 글 초안과 demo 여행·대화 및 live 대화 표시 이력은 `sessionStorage`를 사용한다. 온보딩 답·약관 동의·복구 이메일 초안은 페이지 메모리에만 있어 새로고침하면 사라진다. 완료한 설문은 demo `createTrip`에서 검사하고, live `/confirm`·`/plan`에서 서버로 보낸다([설문 대응](PREFERENCES_CONTRACT.md)). 이메일 초안은 보내지 않는다.

## 실제 연동 경계

`NEXT_PUBLIC_DATA_MODE=live`는 `NEXT_PUBLIC_API_BASE`의 `/v1/web/*`에 연결한다. 사용자 키 발급·회전, 글/파일 접수·근거 확인·편집·확인 등록/일정 생성, 여행 목록·조회·상담·제안 선택·알림을 구현했다. 서버 기준은 `app/modules/travel_ops/trip_api.py`이며 UI에서 예약 변경·업무 판정·실제 시간 계산을 대신 구현하지 않는다. 실패를 데모 성공으로 바꾸지 않는다.

`Trip`·`TripStop`은 프론트 표시 모델이다. live 어댑터가 서버 `trip_id/items`를 변환하고 서울 시각으로 표시한다. 별도 검증 퍼센트 API나 SSE 구독은 연결하지 않았다. live 등록 시 서버가 판정하며 이후 살펴볼 점·알림·이력은 여행 화면에서 확인한다. demo 진행 조회와 가짜 서버 시험을 실제 운영 검증으로 해석하지 않는다.

미연결: live 여행 삭제, 프로필 저장·이미지 변경·이메일 복구, 선택 언어 전달. 토큰 가져오기·재발급은 연결돼 있다. `POST /v1/web/warmup`은 `fc1ac0a`에서 서버 경로가 추가됐다. 호출 연결과 실제 모델 예열·실패 안내 검증을 구분한다. 상세 실행 조건과 제한은 [README](README.md)를 따른다.

지도 제공자 설정은 데이터 모드와 독립적이다. 유효 좌표와 웹용 키가 있을 때 실제 지도 바탕·핀을 표시하며 길찾기 선·현재 위치는 구현하지 않았다. 서버 좌표 변환과 기존 후속 제안은 [지도 문서](MAP_INTEGRATION.md)에 구분했다. 이번 문서 개정에서 외부 지도 인증이나 운영 API를 재검증하지 않았다.

## 완료 기준

기본 품질 확인은 `npm run check`(lint·typecheck·단위 검사·빌드), demo 브라우저 흐름은 `npm run test:e2e`, live 화면의 요청/실패 처리는 `npm run test:live`(테스트용 모방 서버, 실제 서버 아님)으로 구분한다. `tests/contract/test_web_client_contract.py`는 실제 서버 라우트와 설문 계약을 정적으로 대조한다. `test:real`은 실제 데이터 생성·외부 호출·팀 알림 부작용이 있는 별도 검증이므로 원본 문서 정리에서 실행하지 않는다.

주요 확인 대상은 [현재 화면 목록](README.md)의 소개·온보딩 6문항 및 완료 카드·접수 확인·여행·목록·프로필과 모드별 제한이다. API 연결 코드 존재와 운영 종단 검증 성공은 별도로 기록한다.

이하 날짜별 기록은 해당 작업 당시의 범위·실행 결과다. 옛 「미구현」「미검증」과 테스트 수치를 현재 상태나 이번 재실행 결과로 읽지 않는다.

## 1차 구현 검증 기록

2026-09-21 기준 5/5 화면을 구현했다. 린트·TypeScript 검사·프로덕션 빌드가 통과했고 Vitest 단위 테스트 21/21, Chrome에서 프로덕션 빌드를 실행한 Playwright 시나리오 8/8이 통과했다. 브라우저 검증에는 PC 1440px과 모바일 375px·320px, 지도에서 선택한 일정으로 이동·포커스, 키보드 일차 전환, 저장 실패 후 메시지 재전송을 포함한다. 밝은 화면·어두운 화면의 실제 렌더링도 확인했다. 실제 API 통합과 배포 검증은 포함하지 않는다.

같은 날 지도 모듈 추가 후 단위 검사 40/40(100%), 네이버·Google SDK 대역 브라우저 검사 6/6(100%), 기존 화면 회귀 검사 8/8(100%)가 통과했다. 지도 제공자별 빌드와 기본 데모 빌드도 통과했다. 지도 어댑터는 키 설정 후 사용하며, 실제 계정 인증·지도 타일 검증은 아직 수행하지 않았다. 실행 방법과 검증 경계는 [지도 연동 문서](MAP_INTEGRATION.md)에 기록했다.

## 소개 언어 카드·이용 방법 캡처 기록

## 취향 카드 건너뛰기·다음 버튼 기록

2026-09-28. 사용자 지시(TeamFlow `ST4F-154`)로 여행 취향 9문항의 모든 카드에 `응답하지 않고 넘어가기`를 두고, 건너뛴 질문도 진행 게이지(`00 / 9`)에 센다. 건너뛰면 그 질문의 답을 비우고 `Answers.skipped`에 질문 번호를 남긴다. 그 카드에서 다시 답을 고르면 건너뜀 표시를 거둔다. `다음`(마지막 카드는 `설정 완료`)은 모든 카드에서 선택지를 골라야 켜진다 — 기피 음식·종교 카드도 이제 `해당 없음`·`없음`·`응답하지 않음` 같은 선택이 필요하다. 좌우로 밀기·방향키로 앞으로 넘기는 것도 같은 기준을 따르며, 선택 없이 넘어가는 길은 건너뛰기 버튼뿐이다. 건너뛴 테마·인원은 완료 요약에 `미선택`으로 보이고, 등록 화면은 인원 표시를 뺀다. 모든 질문을 건너뛸 수 있게 되어, 기피 음식·종교 카드 설명 옆에만 있던 `선택` 표시는 사용자 지시로 모든 카드에서 뺐다.

검증: 린트·TypeScript 검사·프로덕션 빌드 통과. Vitest 단위 테스트 49/49(100%). Chrome에서 기본 데모 빌드로 실행한 Playwright 시나리오 12/12(100%) — 네이버 SDK 대역 3건은 별도 빌드 전용이라 건너뛰었다. 온보딩 시나리오에 기피 음식·종교 카드의 다음 버튼 비활성, 건너뛰기 후 게이지 증가, 답을 고른 뒤 건너뛰면 답이 비워지고 다시 돌아와도 다음 버튼이 꺼져 있는 것을 더했다. 개발 서버에서 402px 기기 틀로 9장 모두의 건너뛰기 버튼, 건너뛰기마다 오르는 게이지, 요약의 `미선택`을 눈으로 확인했다. 실제 휴대폰에서 손가락으로 밀어 보는 확인은 하지 않았다.

## 취향 설문 안내 카드·답변 전송 기록

2026-09-28. 사용자 지시(TeamFlow `ST4F-155`).

- 안내 카드: 여행 취향 첫 질문 앞에 설문 안내 카드(`INTRO_STEP`)를 둔다. 추천에 쓸 취향 정보를 모으는 설문이라는 것, 답할수록 더 잘 맞는 후보·결과를 추천받는다는 것, `응답하지 않고 넘어가기`로 건너뛸 수 있다는 것을 알린다. 선택지가 없으므로 `시작하기`는 늘 켜져 있고, `이전`은 약관 카드로 돌아간다. 취향 수정도 이 카드에서 다시 시작한다.
- 전송 형식: 답변은 이미 화면 문구가 아닌 선택지 코드로 들고 있었지만, 그대로는 보내기 어려웠다 — 건너뛴 질문도 초기값(성인 1명 등)이 남아 답과 구분되지 않았고, 직접 입력 예산은 문자열이었고, 필드 이름이 화면 내부용이었다. `toPayload`가 질문별 키·숫자 예산·`skipped` 목록으로 바꾸고 `preferencesPayloadSchema`(Zod)가 형식을 정한다.
- 건너뛴 질문: 화면은 `미선택`, 전송값은 질문별 기본값 표 `skipDefaults`에서 가져온다. 사용자 결정으로 지금은 모두 `"unselected"`이고 질문별 기본값은 추후 정한다.
- 전송: 완료 요약의 `여행 계획 등록하기`(여행이 있으면 `내 여행 이어보기`)가 `TripGateway.submitPreferences`를 부르고, 성공해야 다음 화면으로 간다. 받는 백엔드 API는 없다. 데모 모드는 형식만 검사하고 저장하지 않으며, 그 외 모드는 연결 안 됨 오류로 요약에 머문다. 합의할 항목은 [취향 전송 계약](PREFERENCES_CONTRACT.md)에 적었다.

검증: 린트·TypeScript 검사·프로덕션 빌드 통과. Vitest 단위 테스트 53/53(100%) — 전송 형식 3건(모두 건너뜀 → 기본값·`skipped` 9개, 답한 값의 코드·숫자 변환, `응답하지 않음` 선택과 건너뜀 구분·문구 대신 코드만 허용)과 데모 게이트웨이 1건(형식 검사·저장 없음·잘못된 형식 거절)을 더했다. Chrome에서 기본 데모 빌드로 실행한 Playwright 시나리오 12/12(100%) — 네이버 SDK 대역 3건은 별도 빌드 전용이라 건너뛰었다. 온보딩 시나리오에 안내 카드 문구·게이지 0·`시작하기`·첫 질문에서 `이전`으로 안내 카드 복귀를 더했다. `NEXT_PUBLIC_DATA_MODE=live` 빌드를 따로 띄워 9문항을 건너뛴 뒤 `여행 계획 등록하기`를 눌러, 주소가 `/start`에 머물고 연결 안 됨 오류가 뜨며 버튼이 다시 켜지는 것을 확인했다(확인 뒤 데모 빌드로 되돌림). 개발 서버에서 402px 기기 틀의 안내 카드 배치를 눈으로 확인했다. 실제 백엔드 전송은 API가 없어 확인하지 않았다.

## 내 여행 목록 기록

2026-09-28. 사용자 지시로 `/trips`에 내 여행 목록을 더하고, 같은 날 사용자가 준 요구사항에 따라 첫 화면·메뉴·헤더를 목록으로 들어가는 흐름에 맞춰 정리했다.

- 첫 화면 카드: 소개 첫 장의 언어 카드 아래에 `내 여행` 카드(`RecentTrips`)를 두고 최근 등록 3개까지 보인다. 1~2개면 그 수만, 없으면 `아직 등록한 여행이 없어요.`만 보인다(빈 줄·등록 버튼 없음). 4개 이상일 때만 오른쪽 위에 `전체일정 보기`가 생겨 `/trips`로 간다. 불러오는 중·빈 목록·실패를 카드 안에서 따로 보이고, 실패는 오류 문장과 `다시 불러오기`로 알린다 — 소개 화면 전체를 오류 화면으로 바꾸지 않고, 빈 목록으로 숨기지도 않는다.
- 첫 장 하단: 아래로 가는 안내·버튼만 둔다. `소개 건너뛰기`는 첫 장에서 뺐고 둘째 장에는 그대로 있다. 셋째 장의 `내 일정 시작하기`(→ `/start`)도 그대로다.
- 첫 장 높이: 카드가 들어가도록 언어 카드 위아래 여백(22·14 → 16·10px)과 배지 아래 여백(10 → 6px)을 줄이고, 카드 줄은 46px(터치 44px 이상)로 촘촘하게 했다. 여행 3개일 때 한국어 375×812·390×844·PC 기기 틀(1280×900)에서 첫 장이 넘치지 않는다(각 812/812·844/844·851/851px). 영어 375×812는 제목이 세 줄이라 22px 넘치지만 넘친 부분은 점 내비게이션용 아래 여백이고, 소개와 3개는 한 화면에 보인다. 더 낮은 화면은 내용을 자르지 않고 첫 장 안에서 스크롤된다(목록 안의 별도 스크롤은 없다).
- 메뉴: 오른쪽 위 설정 사이드바를 `메뉴`로 바꾸고(버튼·제목·닫기 이름 포함) 맨 위에 `여행 목록 보기 →`(→ `/trips`, 여행 수와 무관하게 항상)를 두었다. 누르면 메뉴를 닫고 이동하며, 이미 목록 페이지면 닫기만 한다. 링크도 Tab 포커스 순환에 들어가고, Esc로 닫으면 메뉴 버튼으로 포커스가 돌아온다. 언어·여행 화면 내비게이션 설정은 그대로다. 소개·온보딩(기기 틀)과 여정 화면(여정 틀)이 같은 메뉴를 쓴다.
- 헤더: 여정 화면 헤더에는 왼쪽 로고와 오른쪽 메뉴만 둔다(가방·집 버튼을 뺐다). 로고는 모든 화면에서 `/`의 첫 장으로 가고, 소개 화면 안에서는 첫 장으로 스크롤한다. 등록 화면 아래의 `/start` 링크는 단계 이동이라 `홈으로`에서 `이전`으로 이름을 바꿨다(가는 곳은 같다). `/trips`와 그 안의 `새 여행 등록`은 그대로다.
- 한 줄: 제목과 등록 시각(서울 시각)을 보인다. 서버 목록(`GET /v1/web/trips`)이 주는 값이 제목·일정 판·등록 시각뿐이라, 기획서 U02의 여행 날짜·상태·미확인 제안 수는 없다 — 목록 응답에 칸이 생기면 붙인다. 일정 판이 2 이상이면(등록 뒤 새 판이 생겼으면) `바뀐 일정 있음` 배지를 단다. 줄을 누르면 여행 화면으로 가고, 관리 시작 전이면 여행 화면이 검증·결과로 안내한다.
- 게이트웨이·캐시: `TripGateway.listTrips`를 `useTrips` 하나로 불러, 첫 화면 카드와 `/trips`가 같은 조회·정렬·캐시를 쓴다. 여행을 등록하면(데모 등록, 실제 연결의 확인·일정 짜기) 목록 캐시를 지워, 돌아왔을 때 옛 목록을 잠깐 보이지 않고 다시 읽는다. 실제 연결은 저장된 사용자 키가 없으면 서버를 부르지 않고 빈 목록을 보인다 — 부르면 빈 목록을 보이려고 새 사용자 키(서버 사용자)를 만들게 된다. 데모는 이 탭의 `sessionStorage`에서 데모 여행을 모아 최근 등록 순으로 보이고, 제목이 없어 날짜로 이름 붙인다(`2026-09-15 – 2026-09-16 여행`). 등록 시각은 저장 형식의 선택 칸 `createdAt`으로 더했고, 그 전에 저장된 데모 여행은 시각 없이 맨 아래에 온다. 읽을 수 없는 데모 여행이 하나라도 있으면 건너뛰지 않고 목록 전체가 기존 `CORRUPT_STORAGE` 오류를 보인다.

## 메뉴·마이페이지 기록

2026-09-28. 사용자 지시로 사이드바 메뉴를 정리하고 마이페이지 조회·편집 화면을 더했다. 먼저 백엔드를 확인했다 — `develop`·`role-*` 어느 브랜치에도 닉네임·복구 이메일·프로필 조회/수정 API가 없고, 키 발급(`POST /v1/web/session`)은 `customer_id`·`user_key`만 준다. 그래서 **편집 화면·입력 검사까지 만들고 저장은 비활성**으로 두었다. 합의할 항목은 [사용자 정보 연동 대기 항목](PROFILE_CONTRACT.md)에 적었다.

- 메뉴 순서: 프로필(공통 기본 이미지·닉네임·`마이페이지`, 영역 전체가 `/mypage` 링크) → `여행 목록 보기` → 언어 → `플로팅 버튼 사용`. 같은 날 사용자 검토로 네 칸을 따로 떨어진 카드 대신 **흰 판 하나**에 담고 칸 사이는 1px 선으로만 나눴다(목업 비교 뒤 결정). 칸이 판 가장자리에 붙어 링크·버튼의 키보드 포커스 표시는 칸 안쪽에 그린다. 닉네임은 서버가 주지 않아 `닉네임 미발급`으로 보이고, 브라우저를 읽기 전(서버 렌더링)에는 `불러오는 중…`이다. 웹이 `여행자1` 같은 값을 만들지 않는다. 메뉴를 열면 프로필 링크에 포커스가 가고, 링크는 메뉴를 닫고 이동한다.
- 언어: 라디오 토글을 없애고 홈 첫 장의 언어 카드를 공용 부품(`components/ui/language-picker`)으로 옮겨 홈과 메뉴가 같이 쓴다. 메뉴의 언어 칸도 홈 카드와 같은 모양이다 — 작은 `LANGUAGE · 언어` 아래 선택된 언어(사용자 결정: 「왼쪽 언어·오른쪽 선택값」 안 대신 홈 모양). 그래서 메뉴 위에 따로 있던 `언어` 제목은 뺐다. 펼치면 `languages`의 모든 언어가 나오고, 고르면 바로 적용·접힌 뒤 카드로 포커스가 돌아온다. 메뉴 안에서 목록이 펼쳐져 있으면 Esc는 목록만 닫고, 한 번 더 누르면 메뉴를 닫는다. 저장된 언어를 읽는 검사도 `languages` 목록을 기준으로 바꿨다(항목을 더하면 목록과 저장값 검사에 함께 반영). 문구 함수가 한/영 두 인자라 새 언어는 문구도 함께 더해야 한다.
- 내비게이션: 두 라디오를 스위치 하나로 합쳤다. 끄면(기본) `fixed` 고정 하단 탭, 켜면 `floating` 플로팅 버튼 — 기존 설정값·저장 키(`tripilot.web.settings.v1`)를 그대로 써서 기존 사용자의 선택이 유지된다. 바꾸면 바로 적용·저장되고 마이페이지 저장과 무관하다.
- 메뉴 포커스 순환: 링크·버튼·스위치를 모두 넣고, 접힌 언어 목록(`inert`)의 선택지는 뺀다.
- 마이페이지 조회(`/mypage`): `← 마이페이지 / 수정` 머리, 기본 이미지와 그 아래 이름 줄(닉네임, 없으면 `닉네임 미발급`), 발급된 토큰·토큰 복구용 이메일. 이름 줄과 같은 내용을 되풀이하던 `닉네임` 행은 사용자 검토로 뺐다. 토큰은 실제 연결이 저장한 브라우저 키이며 가린 채 시작한다. `보기/숨기기`로 바꾸고, `복사`는 가린 채로도 전체를 복사하며 클립보드 결과대로 성공·실패를 알린다. 키가 없으면 `발급된 토큰이 없어요.`와 함께 보기·복사를 막는다 — 마이페이지를 봐도 새 키를 발급하지 않는다. 이메일은 서버에 칸이 없어 `등록된 이메일이 없습니다.`.
- 프로필 수정(`/mypage/edit`): `취소 / 프로필 수정 / 저장`. 들어올 때 현재 정보를 초안에 복사하고, 초안은 이 화면에만 있어 메뉴·조회 화면에 반영되지 않는다. `취소`는 초안을 버리고 조회로 돌아간다. 닉네임은 따로 된 칸 없이 **이미지 아래 이름 줄이 곧 입력창**이다(사용자 검토) — 가운데 정렬, 비어 있으면 조회 화면과 같은 이름 줄(`닉네임 미발급`)을 흐리게 보이고, 화면에 안 보이는 `닉네임` 라벨로 이름을 붙인다. 이미지 변경 버튼은 비활성(`이미지 변경은 준비 중이에요.`), 토큰은 보기·복사만(`토큰은 수정할 수 없어요.`), 이메일은 선택 입력이다. 입력 검사는 닉네임 공백과 이메일 형식뿐이고(`features/profile/model.ts`), 길이 제한은 백엔드 계약이 정해질 때 붙인다. `저장`은 비활성이며 `프로필 저장 기능은 준비 중이에요.`를 보인다. 이메일을 넣어도 인증·복구 설정이 끝났다고 표시하지 않는다. 이메일 입력란의 14px이 앱 전역 규칙(550px 이하 입력란 16px, 휴대폰에서 누를 때 화면이 확대되지 않게)을 덮고 있어 휴대폰 폭에서는 16px로 되돌렸다(닉네임 입력칸은 17px). 시나리오가 375·320px에서 두 입력란 16px 이상을 확인한다.

검증: 린트·TypeScript 검사·프로덕션 빌드 통과. Vitest 단위 테스트 61/61(100%) — 초안 검사 3건(닉네임 공백, 이메일 선택·형식, 둘 다)을 더했다. Chrome에서 기본 데모 빌드로 실행한 Playwright 시나리오 27/27(100%) — 네이버 SDK 대역 3건은 별도 빌드 전용이라 건너뛰었다. 새 시나리오 8건: 메뉴 순서·네 칸이 한 판에 있음·Tab 순환·Esc(목록 → 메뉴)·포커스 복귀·링크가 메뉴를 닫음, 메뉴 언어 카드의 펼침·선택·접힘과 홈 카드 양방향 동기화, 스위치 기본 OFF·Space로 켜기·새로고침 유지·끄면 고정 탭, 메뉴 프로필 → 조회 → 수정 → 취소(이미지 변경·저장 비활성, 입력칸 2개, 검사 문구, 초안 미반영), 토큰 보기·숨기기·복사 성공(클립보드 값 = 토큰 전체)·다시 열면 가림, 복사 실패 안내, 토큰 없음(보기·복사 막힘, 새 키 없음), 영어와 PC·375×812·320×640에서 메뉴 끝까지 스크롤·긴 토큰·긴 닉네임·긴 이메일 입력의 가로 넘침 없음. 기존 시나리오는 언어 라디오 → 언어 카드(공용 도우미 `pickMenuLanguage`), 내비게이션 라디오 → 스위치로 고쳤고, 옛 메뉴 키보드 시나리오는 새 메뉴 시나리오로 옮겼다. 토큰은 시험용 값만 썼다. 개발 서버 375×812에서 메뉴(한 판·닫힘·언어 펼침)·마이페이지·프로필 수정을, 320×640에서 시험용 토큰을 펼친 마이페이지를 눈으로 확인했다. 긴 닉네임이 **표시되는** 모습은 서버가 닉네임을 주지 않아 확인하지 못했고(입력칸만 확인), 실제 API 저장은 API가 없어 확인하지 않았다.

## 온보딩 복구용 이메일 기록

2026-09-28. 사용자 지시로 온보딩 약관 카드 위에 선택 입력 `복구용 이메일` 카드를 더했다. 이번 범위는 **입력과 형식 검사까지**다 — 인증 메일·인증번호·실재 확인·복구 메일 발송은 하지 않고, 형식이 맞아도 인증 완료나 복구 설정 완료로 표시하지 않는다.

- 카드: 번호 대신 메일 아이콘과 `선택` 표시. 약관 `01`·취향 `02` 번호는 그대로다. 처음엔 접혀 있고 포커스를 가져가지 않는다. 누르면 약관·취향과 같은 펼침(고정 시트)·Esc 접기·포커스 처리·첫 배경(0단계)을 쓴다. 펼치면 설명, `이메일` 라벨의 입력란(`type=email`·`inputmode=email`·`autocomplete=email`), 확인 안내, 저장하지 않는다는 안내, `계속`.
- 완전한 선택: 이메일 카드의 열람·완료가 약관·취향의 조건이 아니다. 카드를 열지 않아도, 비우거나 공백만 넣어도 약관 → 취향 → 여행 등록까지 간다. 기존 약관 동의 조건은 그대로다.
- 검사(`features/profile/model.ts` `recoveryEmailProblem`, 마이페이지와 같은 기준): 앞뒤 공백만 지운 뒤 비었으면 미입력, 그 밖에는 이메일 형식(zod `email`)이어야 한다. 가운데 공백·`name@`·`name@example` 등은 오류이고, 특정 업체만 받는 제한은 없다. 입력하는 동안에는 검사하지 않고, `계속`(Enter 포함)을 누르거나 값이 있는 채로 약관·취향으로 가려 할 때 한 곳(`Onboarding.emailPasses`)에서 검사한다. 오류면 이메일 카드를 열고 입력란에 포커스를 보내며 값을 그대로 두고 두 줄 안내를 보인다(`aria-invalid`·`aria-describedby`). 카드를 접는 것은 되지만 다음 단계로 가면 다시 막힌다. 오류가 한 번 뜬 뒤에는 고치거나 지우는 즉시 사라진다. 통과하면 앞뒤 공백을 지운 값을 둔다.
- 데이터: 마이페이지와 같은 복구 이메일 항목의 **초안**으로 온보딩 상태(`email`, 페이지 메모리)에만 둔다. 여행 취향 설문과 섞지 않고, 새 영구 저장소를 두지 않는다. 백엔드에 저장 API가 없어 보내지 않으며 카드에 「지금은 이 화면에서만 기억하고 서버에 저장하지 않아요」라고 적는다 — 그래서 마이페이지도 계속 「등록된 이메일이 없습니다」다. 저장은 여행 등록 때 약관과 함께 개별 토큰을 만들며 취향 설문처럼 같이 하기로 했다(사용자 결정, 미구현 — API는 백엔드와 합의 뒤, [연동 대기 항목](PROFILE_CONTRACT.md) 6번).

## 내 여행 개별·선택 삭제 기록

2026-09-29. 사용자 지시(TeamFlow `ST4F-163`). `/trips` 목록에서 여행을 하나씩 또는 골라서 지운다. **데모 모드만 실제로 지운다.** 서버에는 여행 삭제 호출이 없어(`trip_api.py`의 `/v1/web/trips`는 GET·POST뿐, `app/` 전체에 delete 라우트 없음) live 모드는 삭제 제어를 끄고 이유를 보인다.

- 선택 모드: `선택 삭제` → 제목 오른쪽이 `취소` · `삭제 (N)`으로 바뀌고 각 행 앞에 네이티브 체크박스가 생긴다. 아무것도 고르지 않은 채 시작하고 0개면 `삭제`가 꺼진다. 행 전체가 체크박스 라벨이라 어디를 눌러도 고르거나 풀고, 여행은 열리지 않는다. 화살표·휴지통과 `새 여행 등록`은 숨긴다. 고른 행은 체크와 옅은 배경·테두리로 보인다. 상단 `취소`는 선택을 비우고 모드를 끝낸다. 선택은 화면 상태에만 있어 다시 들어오면 비어 있다.

## 2026-10-03 — 그린·화이트 테마

사용자 지시: 「메뉴 사이드바에 테마 선택 카드가 생기고, 그 메뉴에서 지금의 녹색 계열이냐 흰색 계열이냐를 고른다.」 처음에는 Codex가 맡기로 했으나 같은 날 사용자가 Claude에게 넘겼다.
- **두 테마**: 그린(기본, 지금까지의 색)과 화이트(`data-theme="neutral"`, [계획 확인 시나리오 목업](mockups/tripilot-plan-check-streaming.html)의 색). 값은 사용자가 확인한 표를 따른다. 글꼴·크기·굵기는 같다.
- **역할 분리**: 버튼(`primary`), 선택(`selected`), 성공(`success`), 조정(`adjusted`), 확인 필요(`warning`), 오류(`error`)를 따로 둔다. 그린에서는 선택색이 기본 버튼색과 같고, 화이트에서는 파랑이다.
- **적용**: 메뉴의 테마 카드 → `lib/settings.ts`의 `theme` → `<html data-theme>`. 새로고침 때는 `<head>`의 짧은 스크립트(`lib/theme.ts`)가 본문보다 먼저 저장된 테마를 걸어 그린이 잠깐 보이지 않는다.
- **색 바꾸기**: 화면 CSS 18개 파일과 지도 핀(`features/map/providers/pin.ts`), 취향 카드 누름 효과의 직접 적은 색을 역할 변수로 바꿨다. 반투명 색은 `color-mix(in srgb, var(--color-…) N%, transparent)`로 같은 투명도를 지킨다. 기본 프로필 이미지는 같은 모양을 역할 색으로 그린다(`Avatar`).
- **장식 배경**: 풍경 그림(`Scene`)과 소개 배경 그림은 그린에만 있다. 화이트에서는 바탕색만 남긴다. 풍경 위의 막·빛 색은 그림에 딸린 것이라 그대로 두었다.
- **앞으로**: 새 화면도 색을 직접 적지 말고 역할 변수만 쓴다. 역할이 모자라면 두 테마에 같은 이름으로 함께 더한다(`tokens.test.ts`가 두 테마의 역할 목록이 같은지 본다).
