# 웹 디자인·시연 목업

이 폴더는 독립 HTML 목업과 공통 CSS·JavaScript·이미지를 보존한다. 현재 Next.js 앱의 실행과 API 연결은 [사용자 웹 안내](../README.md), 개발 기준은 [DEVELOPMENT.md](../DEVELOPMENT.md)를 따른다. 아래 과거 검증 기록은 목업을 만들 당시의 결과이며 현재 서비스의 구현·검증 상태를 뜻하지 않는다.

2026-09-29 앱 루트의 `tripilot-*` 31개를 이 폴더로 옮겼다. 파일 내용은 그대로이며, HTML 12개·JavaScript 8개·CSS 7개·PNG 3개·SVG 1개다. 목업은 같은 폴더의 리소스를 읽으므로 전달할 때 이 폴더를 함께 전달한다. PNG 3개는 앱의 `public/images/`와 내용이 같지만 목업의 독립 실행을 위해 함께 보존한다.

python -m http.server 3102 --bind 127.0.0.1

## 계획 확인 시나리오 목업

작성일: 2026-10-02(개정 7) · 팀 저장소로 옮김: 2026-10-03 · 상태: 계획 확인 화면 구현 기준 / 실제 API 미연결. 원본은 작성자의 개인 작업본이며 이 파일이 팀 공유본이다.

[계획 확인 시나리오](tripilot-plan-check-streaming.html)는 계획 등록(`/trips/new`)에서 「계획 확인하기」를 누른 뒤의 흐름을 휴대폰 화면 하나로 보여 준다. 화면 오른쪽(좁으면 아래)의 시나리오 7개를 단계별로 재생한다.

| 시나리오 | 보이는 것 |
|---|---|
| 1 계획 확인 진행 | ① 올린 원문을 한 줄씩 읽음 → ② 찾은 일정 → ③ 지도 + 아래 시트에서 장소·운영시간·이동을 차례로 검사(지도 핀 갱신) → ④ 끝나면 카드가 접히고 여행 제목 |
| 2 결과 보기 | 일차 머리·카드·이동 줄을 눌러 지도와 함께 보기 |
| 3 자동 추천 | 확인 필요 카드 하나를 검증된 대체 장소로 바꾸고 「조정」 표시 |
| 4 수정 화면 | 검색창, 회색 고정 핀과 후보 핀, 옆으로 넘기는 후보 카드, 시트를 올리면 사진 |
| 5 잠금 | 일정 고정과 막힘 안내 |
| 6 삭제 | 가운데 확인창 → 삭제 → 되돌리기 |
| 7 전체 자동 추천 → 재검증 → 여행 등록 | 결과 화면 맨 아래 버튼 줄의 상태 변화 |

- 단계마다 서버와 주고받을 값을 「지금 계약 · 협의 필요 · 제안 · 화면만」으로 적었다. 「협의 필요」·「제안」은 아직 합의된 API가 아니다.
- 색은 흰색 위주의 **뉴트럴 테마**다. 앱은 공통 변수(`src/styles/tokens.css`)로 구현하고, 기본은 그린 테마다. 글꼴·글자 크기는 앱 기준을 따른다(2026-10-03 사용자 확정).
- 장소·시각·거리·운영시간·사진은 예시 값이고, 지도는 위치 개념도다. 외부 요청이 없어 파일을 브라우저로 바로 열면 된다.
- 구현: 2026-10-03 시나리오 1~7 화면 구현, 서버가 주는 만큼 실제 경로(`/intakes/[intakeId]`)에 연결 — 서버에 없는 자동 추천·잠금·후보·사진·되돌리기·재검증은 「준비 중」. [화면 인계](../PLAN_CHECK_SCREEN.md), 예시 데이터 미리보기 `/preview/plan-check`.

## 등록 후 채팅 배치 비교 목업

작성일: 2026-10-06 · 개정: 2026-10-07(C안 추가) · 상태: 검토용 비교안(A·B·C 중 미결정) / 실제 API 미연결.

[등록 후 채팅 배치 비교](tripilot-registered-chat.html)는 계획 확인 화면에서 「여행 등록」을 누른 뒤 여행 화면(`/trips/[id]`)으로 넘어가지 않고 같은 화면에 머무는 방향을 휴대폰 세 대로 비교한다. 세 안 모두 등록하면 하단 버튼 줄이 사라지고 오른쪽 아래에 채팅 버튼이 뜬다. 차이는 그 버튼을 누른 뒤다.

| 안 | 채팅 버튼을 누르면 |
|---|---|
| A 일정 자리에 채팅 | 아래 시트의 타임라인 자리가 채팅으로 바뀐다. 지도와 일차 칩이 남고, 핀을 누르면 물어볼 일정이 바뀌며, 답의 장소 칩을 누르면 지도에 표시한다. 「‹ 일정」·Esc 로 돌아간다 |
| B 채팅 화면으로 이동 | 채팅 화면이 옆에서 들어와 전체를 덮는다. 뒤로 가면 보던 일차·선택 그대로 돌아오고, 답의 장소 칩(「지도에서 보기」)은 일정 화면으로 돌아가 그 카드를 고른다 |
| C 채팅 막대 + 옆으로 넘기기 | 채팅 버튼이 왼쪽으로 늘어나 입력 막대가 된다 — 일정을 보면서 바로 보내고, 보내면 답을 보러 채팅 칸으로 넘어간다. 시트는 일정 칸 ↔ 채팅 칸을 옆으로 밀어(또는 머리의 「일정 \| 채팅」) 오가며, 채팅 칸에서는 막대가 입력칸이다. 일정으로 돌아오면 쓰던 글이 없을 때 막대가 접힌다. Esc 는 채팅 → 일정, 일정 → 막대 접기 |

- 위쪽 버튼으로 두 휴대폰을 함께 「처음 상태(등록 전) · 등록 완료 · 채팅 연 상태」로 바꾼다. 폭 900px 미만에서는 A·B 중 하나만 보인다.
- 두 안 공통 가정: 받은 알림·변경 이력은 시트 맨 위 한 줄로 접어 두고, 등록 뒤 목록 아래에 채팅 버튼 자리(88px)를 둔다. 카드의 고정·수정·삭제는 지금 등록 뒤처럼 흐리게 둔다.
- 채팅의 빠른 질문 4개(하루 요약·선택 일정·다음 일정·예약 표시)와 입력칸은 지금 여행 화면(`features/trip/trip-home.tsx`)과 같은 구성이다. 답은 미리 적어 둔 예시이며, 자유 입력에는 「목업 응답」으로 답한다.
- 라이브 연결 기준(제안): 지금 계약의 여행 대화(`POST /v1/web/trips/{id}/messages`)·알림(`GET /v1/web/trips/{id}/notices`)을 등록으로 받은 여행 ID로 부른다 — 화면 배치만 바뀌고 새 API는 필요 없다고 보지만 구현 때 확인한다.
- 미정: 여행 화면에만 있는 기능(여행계획서 열기·내려받기, 새 계획 올리기, 일정 펼침 상세, 지도 앱 길찾기)의 자리, 「내 여행」에서 다시 열 때(`/trips/[id]`)도 이 화면으로 열지, B 안의 주소·뒤로 가기 처리. 두 안의 장단점은 목업 아래 메모에 적었다.
- 장소·시각·이동·답변은 예시 값이고 지도는 위치 개념도다. 외부 요청이 없어 파일을 바로 연다.

2026-10-06 브라우저 확인(내장 브라우저 477px·1100px·375px 폭): 두 안 모두 등록 전 하단 버튼 줄, 등록 중 표시, 등록 뒤 버튼 줄 사라짐·「등록 완료」·채팅 버튼·알림 줄·안내, 일차 전환과 핀 선택→카드 강조, 채팅 열기(입력칸 포커스)·빠른 질문 대기와 답·빈 입력 오류·자유 입력 글자 이스케이프·장소 칩 동작·돌아가기·Esc 닫기, 위쪽 일괄 버튼. A 는 채팅 중 지도 핀 4개 유지와 핀으로 선택 변경, B 는 채팅 화면 열림 중 뒤 화면 비활성. 두 안 46개 항목 중 첫 실행에서 입력칸 포커스 2건이 실패해 고친 뒤 통과했다. 1100px 에서 두 휴대폰 나란히·같은 높이, 375px 에서 가로 넘침 없음, 콘솔 오류 없음. 대화 기록 칸 높이는 채팅 연 상태에서 A 239px · B 567px(390×820 기준)로 쟀다. 실제 휴대폰·키보드는 확인하지 않았다.

2026-10-07 C안 추가 뒤 확인(내장 브라우저 375px·437px·1100px·1400px 폭): 등록 전 막대 숨김, 등록 뒤 동그란 버튼과 안내, 막대 펼침(폭 59→354px)·입력칸 포커스·닫기 버튼, 펼쳐도 일정 칸 유지, 짧게 밀면 제자리·180px 밀면 채팅·반대로 밀면 일정(글 없으면 막대 접힘), 세로 움직임은 넘기지 않음, 밀고 난 뒤 카드가 눌리지 않음, 막대로 보내면 채팅 칸으로 넘어가 답과 선택 칩 표시, 빠른 질문 줄이 막대에 가리지 않음, 다른 곳을 눌러 다시 그려도 쓰던 글·입력칸 유지, 쓰던 글이 있으면 일정에서도 막대 유지, Esc 접기, 숨은 칸 비활성, 위쪽 일괄 버튼, A·B 회귀 — 첫 실행은 좁은 창에서 C 휴대폰이 숨겨져 폭 0으로 재져 4건이 실패했고, C 를 보이게 한 재실행에서 19개와 회귀·일괄 6개가 모두 통과했다. 밀기는 스크립트의 포인터 이벤트로 확인했고 실제 손가락 터치는 확인하지 않았다. 1400px 에서 세 휴대폰 한 줄·같은 높이, 1100px 에서 두 줄, 375px 에서 가로 넘침 없음, 콘솔 오류 없음. 채팅 칸의 대화 기록 칸은 221px 다. ★지금 앱의 계획 확인 화면은 일정 목록을 옆으로 밀면 다음 날로 넘어가므로(`use-day-gestures`) C 의 밀기와 겹친다 — 목업 메모에 해결 후보를 적었다.

## 살펴볼 점·알림 배치 아이디어 목업

작성일: 2026-10-06 · 상태: 검토용 아이디어 5가지 + 조합 3가지(미결정) / 실제 API 미연결.

[살펴볼 점·알림 배치 아이디어](tripilot-registered-attention.html)는 지금 여행 화면(`features/trip/trip-attention.tsx`)에 쌓여 있는 살펴볼 점·받은 알림·변경 이력을, 위 「등록 후 채팅 배치 비교」의 등록 뒤 화면(지도 + 아래 시트 + 채팅 버튼)에 넣는 방법을 휴대폰 한 대로 바꿔 가며 보여 준다. 같은 묶음의 재난 정지 패널·자동 변경 되돌리기·「선택이 필요해요」도 함께 다룬다.

| 아이디어 | 놓는 자리 |
|---|---|
| ① 알림 센터 | 머리줄 종 버튼(새 알림 수) → 덮는 화면: 할 일 카드 고정 + 살펴볼 점·받은 알림·변경 이력 탭 |
| ② 시트 머리 숫자 칩 | 시트 머리 ⚠·🔔·🕘 숫자 칩 → 시트 안이 그 목록으로 바뀜, 「‹ 일정」으로 복귀 |
| ③ 일정에 붙이기 | 살펴볼 점은 일차 칩 숫자·일차 머리 노란 띠, 선택 요청·되돌리기는 해당 일정 카드 밑, 알림·이력은 일차 칩 끝 「기록」 |
| ④ 채팅에 합치기 | 알림은 채팅 메시지, 변경 이력은 대화 구분선, 살펴볼 점은 대화 맨 위 고정. 채팅 버튼 숫자 + 미리 보기 말풍선 |

## 등록 후 C안 + 알림 센터 목업

작성일: 2026-10-07 · 개정: 2026-10-07(재난 알림 방식 · 종은 메뉴 옆 · 메뉴는 앱과 같게 · 항로 지킴이는 메뉴 머리 ✕ 옆 · 여행계획서는 B안 제목 펼침 + 공유하기 · 등록 완료 일정 카드 · 상세 보기 · 왼쪽 시각 고정 · 이동 수단은 계획 확인 화면과 같게 · 채팅 버튼은 막대만 펼침) · 상태: 검토용 / 실제 API 미연결.

[등록 후 C안 + 알림 센터](tripilot-registered-c-attention.html)는 위 「등록 후 채팅 배치 비교」의 C안 휴대폰(채팅 막대 펼침 + 일정·채팅 옆으로 넘기기)에 「살펴볼 점·알림 배치 아이디어」의 ① 알림 센터를 얹고, 「여행 등록」 뒤에도 같은 화면에 머물 때의 머리줄·일정 카드·상세 보기를 그렸다. 정해 둔 것(2026-10-07 사용자 결정): 채팅 배치는 C안, 서버가 채팅으로 보내는 알림은 채팅에 두고 나머지 알림은 알림 센터, 급한 알림(재난)은 사라지는 막대 + 시트 머리 표시 + 정지 패널, 종은 메뉴 옆, 메뉴는 지금 앱과 같게 하고 항로 지킴이는 메뉴 머리의 ✕ 옆 아이콘, 여행계획서는 B안(제목 ▾ 펼침), 이동 수단은 기존 페이지와 똑같이.

- 「업체 이름으로 찾기」는 입력칸이 아니라 지도 페이지 검색창으로 가는 버튼이다. 검색과 결과는 지도 페이지 한 곳에서만 한다.
- 추천 후보는 같은 종류의 업체 중 같은 날 앞뒤 일정에서 가까운 3곳을 거리와 함께 보인다. 앞뒤 일정이 없으면 지금 장소를 기준으로 한다. 560px 이하에서는 가로로 넘겨 본다.
- 지도 페이지 검색 결과는 지도 중심(지정 장소 또는 현재 위치)에서 가까운 순이다.
- 방문 날짜·시간이 같은 날 다른 일정과 겹치면 입력칸 아래에 「겹치는 일정이 있습니다」와 겹치는 일정 목록을 보인다. 경고이며 저장은 막지 않는다. 끝 시각이 시작보다 이르면 저장을 막는다.
- 카드를 저장해도 상태는 바로 바뀌지 않고 시각 옆에 「재검사 전」이 붙는다. 상태는 재검사가 정한다 — 목업의 규칙은 라이브 `check`와 같은 수준이라 장소가 없으면 확인 필요, 고친 일정은 유지로 본다. 라이브의 상태 체계와 맞출 때 다시 정한다.
- 라이브 연결 기준: 고친 값은 지금처럼 `POST /v1/web/trip-intakes/{id}/edits`로 보내고 응답의 `check`(문제 목록·`ready`)로 버튼을 정한다. 「여행 등록」은 `POST …/confirm`이며 서버가 다시 조립·판정해 등록한다. 등록 전에 데모처럼 단계별 검증을 돌려 유지·조정 결과를 받는 API는 지금 없다 — 재검사 화면을 실제 판정과 연결하려면 협의가 필요하다.
- 날짜·시간 칸은 어디를 눌러도 브라우저의 선택 창을 연다. 크롬 데스크톱은 원래 칸 오른쪽 작은 아이콘을 눌러야만 열리고, 560px 이하에서는 자리 때문에 그 아이콘을 숨겼다. 키보드 방향키·숫자 입력도 된다.
- 420px 이하에서는 날짜·시간을 한 줄에 넣으려고 그 칸의 글자를 14px로 줄였다. iOS는 16px 미만 입력칸을 누를 때 화면을 확대한다.
- 위쪽 검토 막대에서 검색 결과를 정상·결과 없음·조회 막힘으로 바꿔 볼 수 있고, 「처음 상태로」로 되돌린다. 지도 페이지는 화면 전체를 덮어 검토 막대가 가려지므로 검색 결과 상태는 들어가기 전에 고른다.
- 업체·주소·전화·영업시간·현재 위치는 화면 구성을 보이기 위한 예시 값이다. 지도는 위치 개념도이며 지도 SDK를 쓰지 않는다. 변경은 페이지 메모리에만 남는다.

2026-10-01 브라우저 확인(375px·524px·900px 폭): 접힌 카드 형식, 카드 펼침·접기, 추천 후보 선택과 지도 마커 갱신, 겹침 표시와 해제, 끝 시각 오류와 저장 차단, 저장 후 상태·개수 갱신, 취소, 삭제, 일차 탭, 지도 페이지 진입 두 경로(확대·검색), 현재 위치 새로고침, 검색 결과 선택 후 카드 복귀, 결과 없음·조회 막힘·다시 찾기, 가로 넘침 없음. 같은 날 추가 확인: 상태별 카드·배지 색, 화면 전체 지도와 떠 있는 검색창, 결과 창 끌어 내려 접기·끌어 올려 펼치기·짧게 끌면 제자리·누르기 전환(마우스 끌기로 확인, 실제 터치 기기는 미확인), 결과 창 높이에 맞춰 현재 위치 버튼 이동. 날짜·시간 칸을 눌러 선택 창 열기(창 자체는 캡처되지 않아 화면 확인 필요). 재검사 흐름: 처음엔 재검사 막힘, 저장 후 「재검사 전」·재검사 가능, 계획 읽기 화면(받았어요 → 규칙으로 읽는 중), 통과 시 「여행 등록」으로 전환·등록 완료 화면, 확인 필요가 남으면 다시 막힘, 삭제도 고친 일정으로 셈. 다시 올리기: 입력 화면 열기·입력칸 초점, 빈 입력 오류, 글자 수 갱신, 「이전」 후 다시 들어와도 입력 유지, 계획 확인하기 → 읽기 화면 → 목록.

## 모바일 온보딩 목업

작성일: 2026-09-22 · 상태: 온보딩 홈부터 여행 관리까지 연결한 두 인터랙션 목업 / 실제 서비스 API 미연결.

[기본형 홈 목업](tripilot-mobile-onboarding.html)과 [캐러셀형 홈 목업](tripilot-mobile-onboarding-carousel.html)은 파일을 브라우저에서 직접 열어 실행한다. 외부 라이브러리 없이 같은 폴더의 공통 CSS·JavaScript·이미지를 함께 사용하며, 기존 첫 여행 등록 목업의 초록색·밝은 배경 색상을 유지한다. 홈 기본 폭은 402px이고 더 작은 화면에서는 화면 폭에 맞춰 표시한다.

두 홈 모두 취향 설정을 마친 뒤 `여행 계획 등록하기`를 누르면 기존 Next.js 웹의 흐름을 재구성한 후속 목업으로 이동한다. **계획 등록 → 4단계 검증 → 검증 결과 → 여행 일정·지도·채팅**을 동일한 초록색·둥근 카드 스타일로 연결했다. 후속 화면은 PC에서 넓어져 등록·결과는 2열, 여행 화면은 3열로 표시하며 모바일에서는 일정·지도·채팅 탭으로 전환한다. 실제 Next.js 앱의 소스·라우팅·데이터 연결은 변경하지 않았다.

계획 등록은 날짜·시간·장소 입력 검증과 한영 2일 14개 예시를 제공한다. 홈에서 선택한 언어·취향이 이어지며, 입력 원문·답변·채팅 초안과 대화는 화면 이동 중 유지된다. 상단 홈 버튼으로 온보딩에 돌아가 취향을 수정하거나 관리 중인 여행을 이어 볼 수 있다. 상태는 페이지 메모리에만 유지되므로 새로고침하면 초기화된다.

검증은 준비된 시연 응답이다. 100%가 되어도 자동으로 넘어가지 않고 `결과 확인하기`를 기다리며, 결과의 별도 관리 범위 체크 후 시작한다. 예약 시간은 보존하고 예시의 비예약 일정 2건에 15분 조정을 표시한다. 등록 화면의 `목업 체험 옵션`에서 성공·확인 필요·실패를 선택할 수 있다. 실패는 55%에서 멈추고 원문으로 재시도하며, 미확인 결과는 관리 시작을 막고 다시 검증할 수 있다. 실제 장소·운영시간·이동·예약 조회는 수행하지 않는다.

여행 화면에는 일차별 일정과 펼침 상세, 선택한 장소와 연결된 방문 순서 개념도, 일정 요약·상세·예약 표시를 조회하는 시연 채팅을 제공한다. 개념도는 실제 지도·거리·경로가 아니며 채팅으로 실제 일정·예약 변경을 실행하지 않는다. 일정 수정에는 조정된 목록 대신 입력했던 원문을 다시 표시한다.

후속 화면 파일은 [공통 화면·탐색](tripilot-journey.js), [입력·시연 결과](tripilot-journey-data.js), [일정·개념도·채팅](tripilot-journey-workspace.js), [공통 스타일](tripilot-journey.css)이다. 두 HTML과 아래 배경·진행률 리소스를 전달할 때 이 네 파일도 같은 폴더에 함께 둔다.

연결 후 Chrome 사용자 흐름 **20/20 = 100%**, 기존 선택 기반 진행률 회귀 **24/24 = 100%**, PC·320px 등록/결과/여행 배치 **6/6 = 100%** 통과. 온보딩 완료부터 입력 검증·원문 보존·결과 대기·관리 동의·일정/개념도 선택·채팅·언어 변경·실패 재시도·미확인 차단까지 두 버전에서 확인했으며, 후속 화면과 홈의 모바일·PC 외관을 확인했다. 파일 직접 실행·제출 전 시나리오 변경 시 기존 결과 보존·미확인 재시도·홈에서 언어 변경 후 결과 설명 갱신도 **8/8 = 100%** 통과했다. 실제 서비스 연동·실기기·배포 검수는 포함하지 않는다.

처음에는 언어 카드가 펼쳐진다. 한국어·English를 고르고 계속 버튼 또는 약관 카드를 누르면 약관이 펼쳐지며, 동의 체크 후 선호도 카드로 이동한다. 선호도는 여행 테마, 동행·유아 인원, 음식 제한, 이동수단, 예산, 내국인 여부, 기본 우선순위, 음식·활동·이동의 세부 우선순위, 종교의 9개 질문을 좌우 슬라이드로 보여 준다. 이전 질문 이동과 언어 변경 시 응답을 유지한다.

종교와 음식 제한은 선택 입력이다. 약관은 검토 전 목업 문구이며 실제 서비스 약관이 아니다. 응답은 페이지 메모리에서만 유지되어 새로고침 시 초기화된다.

## 첫 여행 등록 와이어프레임

작성일: 2026-09-14 · 상태: 기존 목업 연결·2일 예시·등록 후 상세/지도/채팅 반영 / 실제 API 미연결.

[첫 여행 등록 클릭형 와이어프레임](tripilot-intake-wireframe.html)은 기존 목업 앞에 필요한 초기 진입 과정을 보여준다. 등록 와이어프레임의 모든 화면에서 제품 헤더에는 로고와 언어 선택만 표시하고, 여행 메뉴·변경 기록·촬영 모드·도움말·사용자 아이콘은 위쪽 `화면 흐름` 영역에 둔다. 첫 화면 중앙에는 소개 문구와 `첫 여행 등록하기` 버튼을 배치하며, 기존 여행 카드와 구분선 이하 안내는 비워 둔다. 두 번째 화면은 사용자 표시 영역에 해당하는 여행 기본정보 입력란·오른쪽 안내 카드·하단 조건 및 취향 입력란을 제거했다. 단계 표시는 `계획 입력 → 검증 → 관리 시작` 세 단계로 표시한다. 두 번째 화면의 이전·검증 버튼과 필수 정보 안내는 화면 맨 아래에 고정하며, 여행 계획 입력창은 그 위의 남는 높이를 채운다. 좁거나 낮은 화면에서도 하단 버튼은 유지하고 입력 영역을 스크롤할 수 있다. 예시 일정 넣기 버튼과 제목 아래 안내 문구는 제거했다. 입력 내용은 홈 왕복과 언어 전환 시 유지된다. `화면 흐름`의 `일정 · 채팅` 메뉴에서 기존 시나리오 목업을 열고, 등록한 여행이 있으면 해당 여행을 연다. 두 목업 모두 왼쪽 위 triPilot 아이콘·제목을 누르면 초기 화면으로 돌아간다. 등록 후 일정·지도·채팅 화면에서도 같은 헤더 구성을 사용한다.

| 화면 | 주요 입력·표시 | 다음 행동 |
|---|---|---|
| 01 · 내 여행 (U02) | 중앙 소개 문구와 새 여행 등록 버튼, 상단 화면 흐름의 여행 메뉴 | 첫 여행 등록 / 일정 · 채팅 열기 |
| 02 · 계획 입력 (U03) | 단계 안내·제목·계획 원문 입력창·이전/다음 버튼 | 내 여행으로 복귀 / 검증 하기 |
| 03 · 관리 시작 (U05/U06) | 시간 조정 전후·예약 보존·관리 범위 | 관리 시작 / 계획 수정 후 재검증 |
| 04 · 첫 진입 (U07~U10) | 일차별 일정 v1·펼치는 장소 상세·지도 핀·채팅 입력 | 일정/지도 선택 · 질문 전송 · 일차 전환 |

시연 순서: `첫 여행 등록하기 → 여행 계획 직접 입력 → 검증 하기 → 관리 시작 화면 → 관리 범위 확인 → 여행 관리 시작`. 내용 분석 중·내용 확인·첫 검증 중 화면은 제거했다. 관리 시작 화면에서는 제목 아래 설명·와이어프레임 안내 배너·일정 버전 배지·브라우저 푸시 안내를 제거했다. 계획 수정은 입력 화면으로 돌아가고, 검증 하기를 누르면 관리 시작 화면으로 다시 이동한다. 별도 날짜 입력란을 제거하여, 날짜는 계획 원문의 일차 제목에 적힌 `YYYY-MM-DD`에서 읽는다. 날짜가 없거나 여행 기간이 7일을 넘으면 입력 화면에서 안내한다. 상단에서 PC·모바일 웹 구성을 바꾸고, 방문한 화면으로 돌아갈 수 있다. 촬영 모드(`F`)는 화면 검토 도구를 숨긴다.

등록 예시는 **2026-09-15~16, 2명, 1·2일차 각 7개씩 총 14개 일정**이다. 1일차는 기존 쇼핑·식도락 계획을 사용하고, 2일차는 호텔 조식 → 국립중앙박물관 → 이촌동 점심 → 이태원 소품숍 → 이촌 한강공원 → 용산 저녁 → 호텔 복귀로 구성한 시연용 계획이다. 날짜가 포함된 일차 제목 또는 `1일차`·`2일차` 제목을 구분하며, 첫 날짜가 주어지면 이후 날짜 없는 일차는 그 날짜부터 계산한다. 실제 운영·예약 가능 여부를 조사한 여행 추천은 아니다.

등록 후 화면의 오른쪽 위 일정 버전·시연 데이터 배지와 맨 아래 안내·버튼 바는 제거했다. 마지막 화면의 여행 개요·상태 안내·일차 탭·패널 제목은 데모와 같은 간격과 글자 크기로 압축했다. PC에서는 제목 옆에 날짜 정보를 표시하며 각 영역 높이는 70px·30px·49px·48px다. 촬영 모드에서는 줄어든 상단 아래의 남는 높이를 일정·지도·채팅 패널이 채운다. 모바일에서는 날짜 정보를 제목 아래에 두고 일차·수정 버튼은 40px로 유지한다. 일차 탭 영역의 오른쪽 끝에 `일정 수정` 버튼을 배치하며, 현재는 버튼 표시만 제공하고 클릭 동작은 연결하지 않았다. 등록 후 화면에 일차 탭을 제공한다. 입력 단계에서 날짜·시각·장소의 필수 정보를 확인하고, 누락이나 잘못된 시각이 있으면 입력 화면에 안내한다. 등록 후에는 선택한 일차에 맞춰 일정 목록·지도 핀·채팅의 현재 일차 안내가 함께 바뀐다. 기존 하루 사건 시나리오는 등록 전 `일정 · 채팅` 메뉴에서 연다.

등록 후 일정 카드를 누르면 예정 시간·위치·예약 상태·첫 검증의 조정 전후·다음 일정·이동 계획·안내를 펼친다. 예시 14개 일정에는 장소별 설명을 제공하며, 직접 입력한 항목은 입력 내용과 확인 전인 정보를 구분한다. `지도에서 보기`와 `이 일정 질문하기`로 같은 장소를 이어서 확인한다.

지도는 방문 순서가 표시된 클릭 가능한 장소 핀과 선택 장소 카드, 확대·축소·원래 크기를 제공한다. 핀을 선택하면 왼쪽의 해당 상세도 열린다. 핀 배치는 위치 개념도이며 실제 좌표나 경로가 아니다. 모바일에서는 일정·지도·채팅 탭으로 같은 동작을 제공한다.

채팅 하단 입력창에서 Enter 또는 `전송`을 누르면 메시지와 로컬 시연 답변이 표시된다. 하루 일정 요약·선택 일정 상세·예약 일정 질문 예시와 다음 이동 질문을 지원한다. 일차를 바꿔도 대화 이력과 입력 중인 문장을 보존한다. 변경 요청은 실제 적용됐다고 표시하지 않으며 실제 AI·예약·일정 변경 서비스는 연결하지 않았다.

일차 제목과 시간으로 시작하는 일정 줄을 구분하는 로컬 미리보기와 필수 입력 검사를 제공한다. 실제 자연어 분석·장소 식별·영업시간/이동시간 검증·저장·감시·예약 실행은 하지 않는다. 예시 결과의 15분 조정은 화면 설명용이며 실제 이동 계산 결과가 아니다. 입력은 페이지 메모리에만 있고 새로고침 또는 다른 HTML로 이동 시 초기화된다. 기존 목업 연결은 별도 고정 시나리오를 열며 입력값을 전달하지 않는다.

설계 제안: 등록 전에는 입력에 집중하고 완료 후 기존 `일정 · 지도 · 채팅` 3열로 합류한다. 원문 확인과 현실 검증을 구분하며 예약은 사용자 입력과 업체 확인을 구분한다. 조정 가능한 일정은 최적안 하나를 반영·안내하는 현재 목업의 방향을 따른다. 검증 실패는 완료로 표시하지 않고 관리 시작을 막는다. 첫 진입에서는 여행 중 사건·실제 위치·출발 여부를 추정하지 않는다.
