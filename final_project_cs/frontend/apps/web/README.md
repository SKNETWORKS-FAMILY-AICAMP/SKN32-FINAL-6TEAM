# 사용자 웹

Next.js 16 App Router + React 19 + TypeScript로 구현한 웹 MVP 1차다. 로그인·회원가입·서비스 결제 없이 다음 5개 화면을 제공한다.

| 화면 | URL | 주요 기능 |
|---|---|---|
| 랜딩 | `/` | 서비스 소개, 여행 등록 진입 |
| 계획 등록 | `/trips/new` | 텍스트 입력·검증·작성 보존, 예시 계획 |
| 검증 중 | `/trips/[tripId]/verification` | 4단계 진행·퍼센트·실패 재시도 |
| 검증 결과 | `/trips/[tripId]/results` | 결과 요약·일차별 목록·변경 전후·미완료 안내·관리 시작 |
| 여행 홈 | `/trips/[tripId]` | 일정·교체 가능한 지도·데모 대화, 모바일 탭 |

기술스택 선택과 컴포넌트·기능·데이터 연결의 책임은 [개발 기준](DEVELOPMENT.md)에 정리했다. 랜딩·등록·결과·홈은 기존 목업을 기준으로 하고 검증 중 화면은 승인한 새 프레임을 사용한다.

## 실행

Node.js 22와 npm을 사용한다. 이 폴더에서 실행한다.

```powershell
npm ci
Copy-Item .env.example .env.local
npm run dev
```

[개발 서버](http://127.0.0.1:3100)를 연다. `.env.local`이 이미 있으면 덮어쓰지 말고 필요한 값을 확인한다. 로컬 예시는 `NEXT_PUBLIC_DATA_MODE=demo`를 명시한다. 프로덕션 빌드에서 이 설정을 생략하면 데이터 연결 오류를 표시하며 데모로 자동 전환하지 않는다.

```powershell
npm run check
npm start
```

`check`는 린트·타입 검사·단위 테스트·프로덕션 빌드를 순서대로 실행한다. `start`는 빌드 결과를 3100 포트에서 제공하므로 개발 서버와 동시에 실행하지 않는다.

## 브라우저 검증

프로덕션 빌드를 만든 뒤 실행한다. Playwright는 테스트 서버를 3101 포트에 띄운다.

```powershell
npx playwright install chromium
npm run test:e2e
```

이미 설치된 Chrome으로 실행할 때는 PowerShell에서 `$env:PLAYWRIGHT_CHANNEL="chrome"`을 설정하고 `npm run test:e2e`를 실행한다. 등록·진행·결과·관리 시작·채팅, 실패 재시도·미완료 차단, 입력 보존·새로고침, 모바일·키보드 동작을 확인한다.

## 데이터 연결 상태

현재 여행 데이터는 **명시적인 데모 어댑터**로 실행한다. 검증 진행·결과·채팅은 시연 데이터이며 실제 에이전트·예약 API에 연결되어 있지 않다. 지도는 기본 `demo`이며 네이버지도·Google Maps 컴포넌트를 선택할 수 있다. 등록 화면의 데모 옵션에서 완료·확인 필요·실패 상황을 선택할 수 있다. 여행 및 대화는 같은 탭의 `sessionStorage`에 보관되므로 새로고침으로 유지되지만 다른 사용자에게 링크를 공유하거나 서버에 영구 보존하는 기능은 없다. 검증 시연 입력 형식은 등록 화면의 예시 계획을 참고한다.

현재 백엔드 Case API와 여행 화면에 필요한 계약이 달라 실제 연결은 후속 작업이다. 화면은 `TripGateway`를 통해 데이터를 요청하므로 계약이 확정되면 이 경계에 실제 어댑터를 구현한다. 실제 API 오류를 데모 성공으로 바꾸거나 백엔드 API 키를 브라우저에 노출하지 않는다.

## 지도 선택과 백엔드 전달

`.env.local`의 `NEXT_PUBLIC_MAP_PROVIDER`를 `naver` 또는 `google`로 지정하고 해당 서비스의 웹용 인증 정보를 설정한다. 개발 서버 재시작/배포 재빌드 후 선택한 지도를 사용한다. 두 지도는 같은 일정 ID·좌표·방문 시간을 받으며 기존 일정 선택 동작을 공유한다.

키 발급·허용 도메인 설정, 필요한 `coordinates` 형식, 이동 경로와의 책임 구분, 데모 좌표 입력 예시는 [지도 연동 · 백엔드 전달 계약](MAP_INTEGRATION.md)에 정리했다. 실제 키 인증은 미검증이며, 좌표가 없는 일정에 임의 핀을 만들거나 지도 오류를 데모로 숨기지 않는다.

## 모바일 온보딩 목업

작성일: 2026-09-22 · 상태: 온보딩 홈부터 여행 관리까지 연결한 두 인터랙션 목업 / 실제 서비스 API 미연결.

[기본형 홈 목업](tripilot-mobile-onboarding.html)과 [캐러셀형 홈 목업](tripilot-mobile-onboarding-carousel.html)은 파일을 브라우저에서 직접 열어 실행한다. 외부 라이브러리 없이 같은 폴더의 공통 CSS·JavaScript·이미지를 함께 사용하며, 기존 첫 여행 등록 목업의 초록색·밝은 배경 색상을 유지한다. 홈 기본 폭은 402px이고 더 작은 화면에서는 화면 폭에 맞춰 표시한다.

두 홈 모두 취향 설정을 마친 뒤 `여행 계획 등록하기`를 누르면 기존 Next.js 웹의 흐름을 재구성한 후속 목업으로 이동한다. **계획 등록 → 4단계 검증 → 검증 결과 → 여행 일정·지도·채팅**을 동일한 초록색·둥근 카드 스타일로 연결했다. 후속 화면은 PC에서 넓어져 등록·결과는 2열, 여행 화면은 3열로 표시하며 모바일에서는 일정·지도·채팅 탭으로 전환한다. 실제 Next.js 앱의 소스·라우팅·데이터 연결은 변경하지 않았다.

계획 등록은 날짜·시간·장소 입력 검증과 한영 2일 14개 예시를 제공한다. 홈에서 선택한 언어·취향이 이어지며, 입력 원문·답변·채팅 초안과 대화는 화면 이동 중 유지된다. 상단 홈 버튼으로 온보딩에 돌아가 취향을 수정하거나 관리 중인 여행을 이어 볼 수 있다. 상태는 페이지 메모리에만 유지되므로 새로고침하면 초기화된다.

검증은 준비된 시연 응답이다. 100%가 되어도 자동으로 넘어가지 않고 `결과 확인하기`를 기다리며, 결과의 별도 관리 범위 체크 후 시작한다. 예약 시간은 보존하고 예시의 비예약 일정 2건에 15분 조정을 표시한다. 등록 화면의 `목업 체험 옵션`에서 성공·확인 필요·실패를 선택할 수 있다. 실패는 55%에서 멈추고 원문으로 재시도하며, 미확인 결과는 관리 시작을 막고 다시 검증할 수 있다. 실제 장소·운영시간·이동·예약 조회는 수행하지 않는다.

여행 화면에는 일차별 일정과 펼침 상세, 선택한 장소와 연결된 방문 순서 개념도, 일정 요약·상세·예약 표시를 조회하는 시연 채팅을 제공한다. 개념도는 실제 지도·거리·경로가 아니며 채팅으로 실제 일정·예약 변경을 실행하지 않는다. 일정 수정에는 조정된 목록 대신 입력했던 원문을 다시 표시한다.

후속 화면 파일은 [공통 화면·탐색](tripilot-journey.js), [입력·시연 결과](tripilot-journey-data.js), [일정·개념도·채팅](tripilot-journey-workspace.js), [공통 스타일](tripilot-journey.css)이다. 두 HTML과 아래 배경·진행률 리소스를 전달할 때 이 네 파일도 같은 폴더에 함께 둔다.

연결 후 Chrome 사용자 흐름 **20/20 = 100%**, 기존 선택 기반 진행률 회귀 **24/24 = 100%**, PC·320px 등록/결과/여행 배치 **6/6 = 100%** 통과. 온보딩 완료부터 입력 검증·원문 보존·결과 대기·관리 동의·일정/개념도 선택·채팅·언어 변경·실패 재시도·미확인 차단까지 두 버전에서 확인했으며, 후속 화면과 홈의 모바일·PC 외관을 확인했다. 파일 직접 실행·제출 전 시나리오 변경 시 기존 결과 보존·미확인 재시도·홈에서 언어 변경 후 결과 설명 갱신도 **8/8 = 100%** 통과했다. 실제 서비스 연동·실기기·배포 검수는 포함하지 않는다.

처음에는 언어 카드가 펼쳐진다. 한국어·English를 고르고 계속 버튼 또는 약관 카드를 누르면 약관이 펼쳐지며, 동의 체크 후 선호도 카드로 이동한다. 선호도는 여행 테마, 동행·유아 인원, 음식 제한, 이동수단, 예산, 내국인 여부, 기본 우선순위, 음식·활동·이동의 세부 우선순위, 종교의 9개 질문을 좌우 슬라이드로 보여 준다. 이전 질문 이동과 언어 변경 시 응답을 유지한다.

종교와 음식 제한은 선택 입력이다. 약관은 검토 전 목업 문구이며 실제 서비스 약관이 아니다. 응답은 페이지 메모리에서만 유지되어 새로고침 시 초기화된다.

검증: JavaScript 구문 검사와 VM 기반 입력·언어·진행 상태 검증 **20/20 = 100%** 통과. 브라우저의 실제 렌더링·320px/402px 배치 검수는 미실시이며, 위 수치에 포함하지 않는다.

별도 비교안인 [카드 캐러셀 목업](tripilot-mobile-onboarding-carousel.html)은 9개 질문을 각각 독립된 카드로 가로 배치한다. 이전·다음 버튼, 좌우 스와이프 또는 방향키로 선호도 카드 영역만 이동하며, 이동 중에는 카드 내용을 교체하지 않고 전체 트랙의 위치만 변경한다. 필수 답변 검증과 이전 답변을 유지하며, 화면 밖 카드는 키보드·스크린 리더 탐색에서 제외한다. 마지막 카드는 설정 완료 버튼으로 마친다.

2026-09-22 질문 축소: 기존 6번 숙박 일정·장소, 7번 도착·출발·예약 정보, 9번 방문 경험을 두 목업에서 제거했다. 남은 질문은 1~9번으로 표시하며, 한영 안내·진행률·여행자 아이콘·배경 이동·완료 조건에 실제 질문 수를 사용한다. 변경 후 Chrome 검사 **20/20 = 100%** 통과: 두 목업의 한영 9개 질문 순서와 필수 검증·선택 건너뛰기, 예산→내국인 여부 전환과 이전 답변 유지, 마지막 진행률 100% 및 320/390/1440px 아이콘 배치, 설정 완료/재수정, 브라우저·리소스 오류를 확인했다. 두 HTML과 공통 배경 JavaScript 구문 검사도 통과했다. 아래 12개 질문 검증 기록은 축소 전 결과다.

캐러셀 검증: JavaScript 구문 및 VM 기반 카드 구조·답변 유지·스와이프 경계·입력 검증 **23/23 = 100%** 통과. 이전의 원본 파일 미변경 검사는 두 목업을 함께 수정하는 요구에 따라 제외했다. 실제 브라우저 렌더링과 물리적 터치 검수는 미실시다.

두 목업 모두 펼쳐진 카드의 제목·화살표를 다시 누르면 접히며, 다시 열면 답변과 현재 문항을 유지한다. 캐러셀에서도 각 질문 카드 상단의 제목·화살표로 접을 수 있다. 수동으로 접으면 예약된 자동 펼치기를 취소하고, 접힌 내용은 키보드·스크린 리더 탐색에서 제외한다. 접기·다시 열기·자동 이동 및 답변 유지에 대한 추가 JavaScript/VM 검사 **17/17 = 100%** 통과. 실제 브라우저 동작은 미검증이다.

두 목업에 탄성 슬라이드, 선택 버튼의 눌림·배경 전환·체크, 답변 상태와 연결된 진행 막대, 약관 및 설정 완료 체크 그리기를 적용했다. 기본형은 질문 내용이, 캐러셀은 카드 트랙이 탄력을 주며 이동한다. 선택 반응은 약 0.22초, 문항 전환은 약 0.36–0.40초이며 카드 최초 등장 효과는 언어·약관 변경 때 반복하지 않는다. 운영체제의 동작 줄이기 설정에서는 CSS/JavaScript 애니메이션을 생략하고 문항 이동을 즉시 완료한다.

모션 검증: JavaScript 구문 및 VM 기반 전환 중 중복 클릭 차단·선택 대상·진행률·동작 줄이기·완료 상태 검사 **21/21 = 100%** 통과. 입력·탐색 회귀 **43/43 = 100%**, 접기 검사 **17/17 = 100%**도 통과했다. 실제 브라우저의 애니메이션 외관·물리적 터치는 미검증이다.

## 첫 여행 등록 와이어프레임

작성일: 2026-09-14 · 상태: 기존 목업 연결·2일 예시·등록 후 상세/지도/채팅 반영 / 실제 API 미연결.

[첫 여행 등록 클릭형 와이어프레임](tripilot-intake-wireframe.html)은 기존 목업 앞에 필요한 초기 진입 과정을 보여준다. 등록 와이어프레임의 모든 화면에서 제품 헤더에는 로고와 언어 선택만 표시하고, 여행 메뉴·변경 기록·촬영 모드·도움말·사용자 아이콘은 위쪽 `화면 흐름` 영역에 둔다. 첫 화면 중앙에는 소개 문구와 `첫 여행 등록하기` 버튼을 배치하며, 기존 여행 카드와 구분선 이하 안내는 비워 둔다. 두 번째 화면은 사용자 표시 영역에 해당하는 여행 기본정보 입력란·오른쪽 안내 카드·하단 조건 및 취향 입력란을 제거했다. 단계 표시는 `계획 입력 → 검증 → 관리 시작` 세 단계로 표시한다. 두 번째 화면의 이전·검증 버튼과 필수 정보 안내는 화면 맨 아래에 고정하며, 여행 계획 입력창은 그 위의 남는 높이를 채운다. 좁거나 낮은 화면에서도 하단 버튼은 유지하고 입력 영역을 스크롤할 수 있다. 예시 일정 넣기 버튼과 제목 아래 안내 문구는 제거했다. 입력 내용은 홈 왕복과 언어 전환 시 유지된다. `화면 흐름`의 `일정 · 채팅` 메뉴에서 기존 시나리오 목업을 열고, 등록한 여행이 있으면 해당 여행을 연다. 두 목업 모두 왼쪽 위 triPilot 아이콘·제목을 누르면 초기 화면으로 돌아간다. 등록 후 일정·지도·채팅 화면에서도 같은 헤더 구성을 사용한다.

| 화면 | 주요 입력·표시 | 다음 행동 |
|---|---|---|
| 01 · 내 여행 (U02) | 중앙 소개 문구와 새 여행 등록 버튼, 상단 화면 흐름의 여행 메뉴 | 첫 여행 등록 / 일정 · 채팅 열기 |
| 02 · 계획 입력 (U03) | 단계 안내·제목·계획 원문 입력창·이전/다음 버튼 | 내 여행으로 복귀 / 검증 하기 |
| 03 · 관리 시작 (U05/U06) | 시간 조정 전후·예약 보존·관리 범위 | 관리 시작 / 계획 수정 후 재검증 |
| 04 · 첫 진입 (U07~U10) | 일차별 일정 v1·펼치는 장소 상세·지도 핀·채팅 입력 | 일정/지도 선택 · 질문 전송 · 일차 전환 |

시연 순서: `첫 여행 등록하기 → 여행 계획 직접 입력 → 검증 하기 → 관리 시작 화면 → 관리 범위 확인 → 여행 관리 시작`. 내용 분석 중·내용 확인·첫 검증 중 화면은 제거했다. 관리 시작 화면에서는 제목 아래 설명·와이어프레임 안내 배너·일정 버전 배지·브라우저 푸시 안내를 제거했다. 계획 수정은 입력 화면으로 돌아가고, 검증 하기를 누르면 관리 시작 화면으로 다시 이동한다. 별도 날짜 입력란을 제거하여, 날짜는 계획 원문의 일차 제목에 적힌 `YYYY-MM-DD`에서 읽는다. 날짜가 없거나 여행 기간이 7일을 넘으면 입력 화면에서 안내한다. 상단에서 PC·모바일 웹 구성을 바꾸고, 방문한 화면으로 돌아갈 수 있다. 촬영 모드(`F`)는 화면 검토 도구를 숨긴다.

등록 예시는 **2026-09-15~16, 2명, 1·2일차 각 7개씩 총 14개 일정**이다. 1일차는 기존 쇼핑·식도락 계획을 사용하고, 2일차는 호텔 조식 → 국립중앙박물관 → 이촌동 점심 → 이태원 소품숍 → 이촌 한강공원 → 용산 저녁 → 호텔 복귀로 구성한 시연용 계획이다. 날짜가 포함된 일차 제목 또는 `1일차`·`2일차` 제목을 구분하며, 첫 날짜가 주어지면 이후 날짜 없는 일차는 그 날짜부터 계산한다. 실제 운영·예약 가능 여부를 조사한 여행 추천은 아니다.

등록 후 화면의 오른쪽 위 일정 버전·시연 데이터 배지와 맨 아래 안내·버튼 바는 제거했다. 마지막 화면의 여행 개요·상태 안내·일차 탭·패널 제목은 데모와 같은 간격과 글자 크기로 압축했다. PC에서는 제목 옆에 날짜 정보를 표시하며 각 영역 높이는 70px·30px·49px·48px다. 촬영 모드에서는 줄어든 상단 아래의 남는 높이를 일정·지도·채팅 패널이 채운다. 모바일에서는 날짜 정보를 제목 아래에 두고 일차·수정 버튼은 40px로 유지한다. 일차 탭 영역의 오른쪽 끝에 `일정 수정` 버튼을 배치하며, 현재는 버튼 표시만 제공하고 클릭 동작은 연결하지 않았다. 등록 후 화면에 일차 탭을 제공한다. 입력 단계에서 날짜·시각·장소의 필수 정보를 확인하고, 누락이나 잘못된 시각이 있으면 입력 화면에 안내한다. 등록 후에는 선택한 일차에 맞춰 일정 목록·지도 핀·채팅의 현재 일차 안내가 함께 바뀐다. 기존 하루 사건 시나리오는 등록 전 `일정 · 채팅` 메뉴에서 연다.
