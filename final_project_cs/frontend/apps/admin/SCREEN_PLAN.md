# 운영자 콘솔 화면 기획 · 1차 개발 계획

작성일: 2026-09-29 · 작성: 최상욱(에이전트 작성) · 상태: **초안 — Codex 1차 검토 반영(2026-09-29), 팀 검토 전**
최신 확인: 2026-09-29 · SKN32 `role-eval-ui` `38cd59d` 코드 기준. `origin/role-manager` `5d7a364`(develop 미반영)는 §5.1·§7에 표시한 부분만 확인했다.

이 문서는 운영자 콘솔(`apps/admin`)에 **무엇을 어떤 화면으로 만들지**와 **이번 단계의 개발 계획**을 정한다. 이번 단계는 **화면만** 만든다. 모든 데이터는 명시적인 데모 데이터이며 실제 API는 부르지 않는다. API 계약은 화면을 팀과 확인한 뒤 따로 만들어 백엔드와 합의한다(§7).

- 화면 구성의 기준은 2026-09-29 와이어프레임 v1.2다(화면 11개). 정적 HTML 사본: [mockups/wireframe-v1.2](mockups/wireframe-v1.2/index.html) · 안내 [mockups/README.md](mockups/README.md).
- 결정은 §2의 **확정**(사용자 결정)·**잠정**·**미정** 표시를 따른다. §3·§4의 화면 구성과 동작은 따로 표시하지 않으면 **구현 제안**(팀 검토 필요)이다. 현재 코드에 대한 사실은 §7·§7.1과 「현재 코드:」로 시작하는 문장에만 적는다.

## 1. 목적과 경계

**확정** 운영자 콘솔은 **실제 운영에 필요한 화면만** 둔다. 사용자·사용량·한도·서버 상태·문의·공지를 다룬다.

| 구분 | 운영자 콘솔 (이 앱) | 개발자 콘솔 (`apps/dev-console`) |
|---|---|---|
| 보는 단위 | 사용자·서비스 전체 | 실행·에이전트 단위 |
| Case | 다루지 않음 | 매니저·에이전트가 Case 흐름을 잘 타는지 |
| 로그·오류 | 사용자에게 영향이 있는 장애만 (연결 상태) | 서버·클라이언트 오류 로그 전부 |
| LLM 호출 | 서비스 전체 사용량·비용 | 호출별 입력·출력·지연 |
| 시스템 구성 | 다루지 않음 | 기존 `/ui/admin` 같은 구성 스냅샷 |

**확정** 제외: AI가 사람에게 넘기는 인계(유스케이스 UC-C13). 지금 없는 기능이다.

## 4. 화면별 내용

모든 화면의 공통 요소(**제안**):

- 왼쪽 메뉴, 위쪽 막대(위치 표시 · 로그인한 운영자 ID · 로그아웃).
- **데모 표시**: 이번 단계의 모든 화면 위쪽에 「데모 데이터 — 서버에 저장되지 않음」을 항상 보인다.
- **설정·권한을 바꾸는 행동은 사유가 필수**다: 차단·해제, 기본·예외 한도, 감시 조절, 운영 상한, 점검 모드 전환, 답변 없이 문의 상태만 바꿀 때, 승인·거절, 위임, 발송 결과 확인. 사유가 비면 저장하지 않는다. 바뀐 내용은 운영 기록(S-10)에 이전 값 → 새 값과 사유로 남는다.
- 답변 보내기와 공지 게시는 본문이 곧 기록이라 사유 칸을 따로 두지 않고, 운영 기록에 본문을 남긴다.
- 화면 상태: 불러오는 중 · 빈 목록 · 불러오기 실패. 이번 단계에서도 세 상태를 데모 데이터로 확인할 수 있게 한다. 실패를 성공처럼 보이게 바꾸지 않는다.

### S-01 로그인

- 운영자 ID·비밀번호 입력. 회원가입 없음 안내, 로그인 실패가 반복되면 잠긴다는 안내.
- 데모 단계에서는 **인증하지 않는다.** 버튼 문구는 「데모로 들어가기 — 인증하지 않음」이고 누르면 홈으로 이동한다. 안내 문구는 「회원가입은 없습니다. 계정은 팀에서 발급합니다.」(사람마다 하나씩은 §2 제안).
- 현재 코드: 백엔드에는 운영자 계정 방식이 이미 있다. 계정은 설정 `ACOP_UI_OPERATORS`에 두고 비밀번호는 해시로만 저장하며, 로그인 실패 잠금이 있다(`app/presentation/ui/auth.py`). 다만 서버가 그리는 `/ui/login` 폼과 쿠키 방식이라 이 앱이 쓸 JSON 경로는 없다(A-01).

### S-02 홈 · 오늘 처리할 일

- 연결 이상 알림 띠(있을 때만) → S-07.
- 카드 6개: 새 문의(접수·처리 중) · 한도에 걸린 사용자(② 채팅만 — ③ 웹은 한도 합의 전까지 제외) · 감시 조절(간격 늘림·멈춤 API 수) · 운영 상한 근접 API(**미정** 기준 [80]%) · 연결 상태 · 승인 대기·발송 미확인(임시).
- 처리할 목록(오래 기다린 순): 종류 · 대상 · 내용 · 기다린 시간 · 이동 링크.
- 오늘 사용량 요약: 외부 API 호출(감시 / 채팅 중 조회), 우리 서버 호출(채팅 / 웹), 유료 사용 예상 비용.
- 「공지 작성」 바로가기 → S-09.
- **미정** 카드의 종류·순서, 처리할 목록에 넣을 일.

### S-03 사용자 목록

- 찾기(사용자 ID 일부), 상태(전체·정상·차단), 빠른 필터(채팅 한도 초과·문의 있음), 정렬(마지막 사용순·오늘 사용량순).
- 열: 사용자 ID · 상태 · ② 채팅 오늘/한도(막대) · ③ 웹 호출 오늘 · 여행 수 · 문의 수 · 마지막 사용 · 상세.
- 현재 코드: 서버는 사용자 키 원문이 아니라 해시만 저장한다(`web_user_keys.key_hash`, 마이그레이션 025). 그래서 화면은 키가 아니라 **사용자 ID로 식별**한다. **미정** 키 끝자리를 보이려면 저장 방식을 바꿔야 한다.

### S-04 사용자 상세

- 요약: 사용자 ID · 상태 · 키 발급일 · 마지막 사용 · 「서버는 키 원문을 보관하지 않음」.
- **차단**: 삭제가 아니라 차단이다. 사유 필수, 해제하면 그대로 돌아온다. **사용자 ID는 키 재발급 뒤에도 유지되며, 운영 차단은 키 폐기와 다르다.** 차단 해제가 재발급으로 폐기된 옛 키를 되살리면 안 된다. 저장·조회·해제 방식은 A-03 계약에서 정한다. **미정** 차단된 사용자의 진행 중 여행 감시를 함께 멈출지.
  - 현재 코드: 키 재발급(`rotate`)이 그 사용자의 살아 있는 키에 `revoked_at`을 적고 새 키를 만든다(`app/modules/travel_ops/web_session.py:57`). 그래서 `revoked_at`을 차단 표시로 다시 쓰면 해제할 때 옛 키까지 살아날 수 있다.
- 사용량 카드: ② 채팅(오늘/한도, 막대, 넘으면 거절과 다시 되는 시각 안내) · ③ 웹 호출(오늘, 자주 부른 경로 3개).
- 이 사용자 여행의 감시(참고): 진행 중 여행 수, 감시 대상 장소 수, 지금 서비스 전체 감시 상태 → S-05. 외부 API는 사용자별로 세지 않는다는 안내.
- 예외 한도: ② 채팅 하루 한도, ③ 웹(**미정**), 적용 기간(오늘만 / 해제할 때까지, **미정**), 사유 필수.
- 여행 목록(여행별 감시 대상 장소 수 — 외부 API 호출 수는 사용자·여행별로 나누지 않는다) · 문의 이력(→ S-08) · 이 사용자에 대한 운영 기록(→ S-10).

### S-05 한도 · 감시 조절

- 사용자별 기본 일일 한도(모든 사용자): ② 채팅 하루 N회(넘으면 요청 거절 + 다시 되는 시각 안내, 사용자 웹에 이미 있는 안내를 쓴다) · ③ 웹 호출(**미정**, 지금은 집계만).
- 감시 조절(서비스 전체, **잠정**): 단계 표. 1단계 「그 API의 운영 상한 소진율 [80]% 이상 → 그 API를 쓰는 감시 간격 × [2]」, 2단계 「운영 상한 도달 → 그 API 호출 멈춤(다음 초기화까지)」. 단계 추가·빼기.
  - 현재 코드: 운영 상한에 닿으면 부르지 않는 동작은 구글·카카오 호출에 이미 있다(`app/infrastructure/travel/call_budget.py`, 표 `external_call_budget`, 마이그레이션 027). 소진율에 따라 **간격을 늘리는 단계는 없다**(A-08). 고정 호출 속도 제한(`app/infrastructure/travel/ratelimit.py`)과는 다른 장치다.
- 지금 상태(API별): API · 운영 상한 소진 막대 · 감시 상태(정상·간격 늘림·멈춤) · 그 API를 쓰는 감시. 운영 상한 조정은 S-06으로 이동.
- 저장 전 영향 미리보기: 이 값으로 저장하면 오늘 기준 채팅 한도 초과 N명 · 간격 늘림 N개 API · 멈춤 N개 API.
- 「사용자에게는 알리지 않음, 기능 차질 시 공지」 안내와 S-09 링크.

### S-06 사용량

### 5.1 기술 기준 (제안)

- 사용자 웹·개발자 콘솔과 같은 판을 쓴다: Next.js 16.3.5 App Router, React 19.3.0, TypeScript 5.9.3 strict, TanStack Query, Zod, CSS Modules, lucide-react. Node.js 22 · npm · 앱별 `package-lock.json`.
- 포트: 개발 **3300**, 브라우저 시험 **3301**. 사용자 웹(3100~3102)·개발자 콘솔(3200~3201)과 겹치지 않게 고른 값이다.
- 데이터 모드: `NEXT_PUBLIC_ADMIN_DATA_MODE=demo`를 명시해야 데모 어댑터가 동작한다. 값이 없거나 다르면 「연결 미설정」 오류를 보인다. 데모로 자동 전환하지 않는다(개발자 콘솔과 같은 방식).
- 화면은 데이터 경계(`AdminGateway`)를 통해서만 데이터를 받는다. 이번 단계에는 데모 구현만 둔다. 실제 연결은 API 계약 합의 뒤 별도 어댑터로 붙인다.
- 실제 연결 때의 제약(지금 구현하지 않음): 운영 API는 권한 범위(scope) 토큰으로 인증하고, 서버의 브라우저 허용 헤더는 `X-User-Key`·`Content-Type`뿐이다(`app/presentation/api/app.py:43-47`). 그래서 운영 API는 **Next 서버 쪽에서** 불러야 하고, 백엔드 키를 `NEXT_PUBLIC_*`나 브라우저 저장소에 두지 않는다. 데모 경계의 모양이 이 방식을 막지 않게 한다.
- 백엔드 매니저 브랜치 `origin/role-manager` `5d7a364`(2026-09-29 16:00, develop 미반영)는 운영 기능을 고객 API 앱(8042)과 다른 프로세스인 **운영 앱**으로 분리했다(`app/ops_entrypoint.py`). 기본 주소 127.0.0.1:8070(설정 `ACOP_OPS_PORT`)이고 루프백이 아닌 요청은 거절하며, 기존 서버 운영 화면(`/ui/*`)과 한도 운영 API를 담는다. 실제 연결 때는 이 앱의 Next 서버 쪽이 같은 기계의 운영 앱을 부른다. 운영 앱과 같은 원칙으로 **이 앱도 루프백(127.0.0.1)에만 열고** 원격 운영은 SSH 터널로 한다(**제안**).
- 화면 폭: PC 우선(1280px 이상 기준). 좁은 화면은 가로 넘침 없이 읽히는 정도만 맞춘다.

## 8. 사용자 웹에 생기는 일 (별도 작업)

운영자 콘솔 기능 중 사용자 웹 화면이 함께 필요한 것이다. 이 문서의 범위가 아니며, 사용자 웹 작업 때 [화면별 연동 문서](../../../wiki/external/web-screen-api.md)에 요구로 올린다.

- 사이드바 「문의함」(토큰 있으면 내 문의와 답변, 없으면 「문의 없음」)과 「문의 작성」 폼. 토큰이 없는 사용자가 문의를 보내면 그때 키가 발급된다 — 새 키 발급 흐름(사람 확인·키 한 번 보여 주기)과 맞춰야 한다(**미정** 세부).
- 공지·점검 배너(한/영).
- 차단된 키로 들어왔을 때의 안내. 한도 초과 안내는 이미 있다.

8. 운영 상한 근접 기준(80%?)과 예상 비용 단가 출처.
9. 문의 유형 분류, 답변 알림 방법.
10. 점검 모드 범위, 공지 한/영 필수 여부.
11. 운영 기록 보관 기간.
12. 예약 승인·위임·발송 확인(S-11)을 이번 범위에 둘지.
13. 서버 이상 알림 방법(홈 표시만 / 디스코드), 배포처.
14. 포트 3300·3301, CI 관문 추가 여부.
15. 운영 앱의 기존 서버 화면(`/ui/*`)을 이 앱으로 대체하고 걷을지, 걷는다면 언제인지. 이 앱에 없는 Case·VOC·시스템 구성 화면을 어디에 둘지. 매니저(백엔드) 담당과 정한다.
16. API별 유료 사용 허용 여부와 운영 상한을 바꿀 수 있는 범위.

20. 여행별 감시 작업 실행 횟수가 필요한지. 필요하면 외부 API 호출과 구분해 집계 단위를 먼저 정한다.
