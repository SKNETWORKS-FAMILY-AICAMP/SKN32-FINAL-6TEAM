# 전용 QA 계정과 예약 보존 검증 — 2026-10-17

사용자 지시: 테스트 계정 하나를 만들고 게스트 여행 1개·채팅 등 이용 횟수 제한을 풀어 실제 검증을 진행한다.

## 완료한 일

- 최신 매니저 판에서 필요한 파일만 격리 사본으로 읽고, QA 고객 기록의 명시적 boolean에만 적용하는 이용 횟수 예외를 구현했다. 공개 HTTP에는 예외 부여 입구를 추가하지 않았다.
- 실제 DB의 별도 tenant에서 신규 17개·기존 관리자 정책 11개, 총 28/28 검사를 통과했다. 이 시험 데이터는 롤백했다. 변경 Python 5파일의 ruff F·E9와 새 격리 Git 사본의 패치 적용 검사를 통과했다.
- 실제 cs 프로젝트 DB에 전용 QA 계정을 하나 생성하고 해당 고객의 예외를 감사 기록으로 남겼다. 키 원문은 비공개 0600 파일에만 보관했다. 기존 게스트 여행은 건드리지 않았다.
- 정상 QA 키로 첫 예약 여행을 등록하고 다시 열었다. 예약번호 KY-20931·19:00~20:30·예약 표시가 보존됐다. 자동 추천 후 변경 없이 완료하면 같은 여행 버전 1을 유지했다. 다른 게스트 접수는 404였다.
- 공개 브라우저에서도 등록된 여행의 계획서와 시각·버전 1을 확인했다. 공개 주소의 명령줄 HTTP는 Cloudflare 1010으로 거절돼 내부 실제 API 확인과 구분했다.
- 패치와 계약·실행 근거를 기존 커밋 세션에 전달했다. 기능 코드의 원본 역복사·색인 변경·삭제는 하지 않았다.

## 진행 중·남은 일

- 한도 예외 코드의 매니저 검토·반영·배포. 현재 배포 전 두 번째 여행 요청은 403 guest_trip_limit(cap=1, existing=1)이다. 배포 뒤 같은 request_id·내용으로 재확인한다.
- 숙소 담당 세션의 후속 배포 뒤 새 기본 예시를 실행해 양일 숙소 자동 적용·경로·수동 장소 저장을 재확인한다. 다른 세션과 중복 구현하지 않는다.
- 일반 고객·인증·소유권·차단·점검·전체 서비스/제공처 예산은 유지한다. 고객이 직접 수정하는 계약과 자동 추천의 예약 보호를 혼동해 직접 수정을 새로 막지 않는다.
