# 장소 API 쿼터와 저장 제약

`[2026-09-22]` 「한 번 부를 때 서울 것을 다 받아서 우리 DB 에 넣어 두면 되지 않나」는 물음에서 시작했다. **구글로는 안 된다. 약관이 막고 산수도 안 맞는다.** 소스마다 조건이 달라 표로 정리한다.

## 한눈에

| 소스 | 호출 한도 | 받은 데이터를 쌓아도 되나 | 우리 용도 |
|---|---|---|---|
| **구글 Places (New)** | **월 1,000건 무료** (채식 필드가 든 Enterprise + Atmosphere 등급) | ★**안 된다.** `place_id` 만 무기한 | 일정 접수 시 그 팀 장소만 1~2회 |
| **카카오 로컬** | **일 100,000건** (키워드·카테고리 검색) | 조건부 — 사용자 환경 개선 목적의 캐시만, 최신 유지 의무 | 좌표·분류 조회 |
| **네이버 지역검색** | `[미확보]` — 같은 계열 블로그 검색이 일 25,000건 | `[미확보]` | 후보 아님(한 번에 5건, 키도 없다) |
| **OSM Overpass** | 동시 2슬롯, 건수 제한은 없으나 공용 서버 배려 | 가능 — **ODbL**(출처 표시, 파생 DB 공개 조건) | 채식 가점 |
| **TourAPI** | 개발계정 일 1,000건 | 별도 제한 못 찾음 `[확인 범위: 서비스 상세 화면]` | 운영시간·휴무 원문 |

## 구글 — 「서울 것을 다 받아 두기」가 안 되는 두 가지 이유

### 1. 약관이 금지한다

`[외부 2026-09-22]` Places API 정책 문서 기준.

| 대상 | 규정 |
|---|---|
| `place_id` | **무기한 저장 가능** |
| 이름·주소·영업시간·속성 | 미리 받기(pre-fetch)·캐시·저장 **금지** (성능을 위한 임시 보관 예외를 빼면) |
| 대량 내려받기, 색인, 검색 가능한 DB 구축 | **금지** |

★**허용되는 임시 보관의 기간은 내가 읽은 범위에 숫자로 없었다** — 「임시」라고만 되어 있다. 기간을 근거로 설계하려면 약관 전문을 다시 읽어야 한다.

### 2. 산수도 안 맞는다

호출 수로 과금되지 장소 수로 과금되지 않는다. **검색(Text Search)은 한 번에 최대 20곳**이다.

★`[확인 2026-09-25, 공식 문서]` 20곳은 **검색 결과**다 — 검색어에 맞는 곳 20개이지, 우리가 고른 장소 20곳을 한 번에 받는 것이 아니다. **장소 상세(Place Details, `places/{id}`)는 한 번에 한 곳**이다. 영업시간(`currentOpeningHours`·`regularOpeningHours`)은 **Enterprise** 등급이라 무료가 **월 1,000건**이다(Pro 5,000 · Essentials 10,000). 새벽 식당 확인은 식당 하나에 상세 1건이 든다.

| | 값 |
|---|---|
| 1회 호출 | 20곳 |
| 월 무료 1,000회 | 최대 20,000곳 |
| 서울 음식점 | **26,555곳** `[실측 — OSM `amenity=restaurant`]` |
| 한 바퀴에 필요한 호출 | 1,300회 이상 |

**월 무료 한도를 다 써도 서울 음식점 한 바퀴를 못 돈다.** 관광지·숙박을 더하면 더 벌어진다.

시간당 1회(월 744회)로 잡으면 한도 안에는 들어오지만 744 × 20 = 14,880곳이라 **한 달 내내 돌려야 서울 음식점 절반**이고, 그렇게 모아도 저장이 금지라 쓸 수 없다.

### 그래서 이렇게 쓴다

「한 번에 많이 받는다」는 원칙은 맞다. **대상이 서울 전체가 아니라 그 팀의 일정**일 뿐이다.

| | 건수 |
|---|---|
| 한 팀 7일 일정의 장소 | 20~40곳 |
| 필요한 호출 | **1~2회** |
| 월 무료 한도로 감당 | **500~1,000팀** |

`place_id` 는 무기한 저장이 허용되므로 **그것만 우리 DB 에 쌓고**, 값이 필요하면 그 id 로 조회한다.

## 카카오 — 여유는 크고 저장은 조건부

`[외부 2026-09-22]` 쿼터는 구글과 자릿수가 다르다.

| API | 일 허용량 |
|---|---|
| 키워드·카테고리 검색 | **100,000건** |
| 주소↔좌표 변환 | 100,000건 |
| 자동차 길찾기 | 10,000건 |
| **대중교통·도보·자전거 경로** | **1,000건** ← 여기만 빡빡하다 |
| 지도 SDK | 300,000건 |
| 전체 월 한도 | 3,000,000건 |

저장 쪽은 운영정책 제5조에 걸린다.

- 20호 — 「앱에서 사용자 환경을 개선하기 위한 목적 **외** 다른 목적으로 카카오에서 받은 데이터를 캐시하거나 캐시 후 **최신 데이터로 유지하지 않는 행위**」를 금지
- 30호 — 얻은 정보를 사전 승낙 없이 복사·복제·변경·제공하는 행위를 금지

→ **구글만큼 딱 잘라 금지하지는 않는다.** 사용자에게 보여 주기 위한 캐시는 되고, 대신 **낡은 채로 두면 안 된다.** 우리가 만드는 것은 지속 관리라 「최신 유지」는 어차피 해야 하는 일이다.

★**다만 「우리 DB 에 서울 장소를 쌓아 두고 그걸로 검색 서비스를 한다」는 30호에 걸린다.** 쿼터가 넉넉하다고 데이터 창고를 만들어도 된다는 뜻은 아니다.

## 네이버 — 지금은 후보가 아니다

- 저장소 어디에도 네이버·NCP 키가 없다 `[실측]`
- 지역 검색은 **한 번에 최대 5건** `[외부]` — 후보를 훑는 용도로 약하다
- 응답 필드에 식이·편의 속성이 없다 `[외부]`
- 쿼터는 확인하지 못했다. `developers.naver.com` 은 이 환경에서 열리지 않는다. 같은 계열 블로그 검색이 일 25,000건이라는 외부 언급만 봤다 `[미확보]`

## 설계에 남는 것

| 언제 | 무엇을 | 어디서 |
|---|---|---|
| 일정 접수 시 1회 | 그 일정의 장소 정보 | 구글 (팀당 1~2회) |
| `[2026-09-25]` **새벽 3시** | 그날 식사 일정이 계획한 시각에 여는가 — 항목당 하루 1회(처음 한 번은 `place_id` 찾기 1회 더) | 구글 — **판정·확인 시각과 `place_id` 만 저장**(D-020, 마이그레이션 026) |
| **3분마다** | 기상·기상청 특보·단기예보·**재난문자**·ITS·UTIC 교통 사건 | **무료 소스만** ([D-017](../decisions/D-017-watch-cadence-golden-time.md)) |
| 항상 | 장소 식별자 | **`place_id` 만 우리 DB 에** |

★`[정정 2026-09-23]` **감시 주기는 2분이 아니라 3분이다.** [D-017](../decisions/D-017-watch-cadence-golden-time.md) 이 정한 값이고, 이 문서 초판은 옛 「2분 폴링」 문구를 그대로 옮겼다. 주기를 정한 식은 이렇다.

```
소스 주기 = max( 목표가 허용하는 주기 , 86,400초 × 한 번 돌 때 호출 수 ÷ 하루 호출 예산 )
```

| 묶음 | 주기 | 하루 호출 / 한도 |
|---|---|---|
| 무료 지역 소스(재난문자 포함) | 3분 | 480 / 1,000 = 48% |
| **에어코리아** — ★**하루 500건짜리** | 3분 | **480 / 500 = 96%** (재시도 여유 20회) |
| 유료 전환 가능 — Google Places | ≈ 90분 | 16 / (1,000÷31) |

★`[정정 2026-09-23]` 앞 판에 「3분을 정한 것은 에어코리아 500건이다」라고 적었다. **틀렸다.** **3분을 정한 것은 이동 사건의 골든타임이다.** 한도는 아래쪽을, 골든타임은 위쪽을 막고 3분은 그 사이에 있다.

| 막는 쪽 | 무엇이 | 어떻게 |
|---|---|---|
| **위 — 더 길게 못 잡는다** | **골든타임 목표 p95 ≤ 5분 · p99 ≤ 10분** | 수집 대기 최대 3분 + 처리 약 1분 + 발송 수 초 = **약 4분 + 원천 게시 지연.** 여유가 1분뿐이라 4분 주기면 목표를 못 지킨다 |
| **아래 — 더 짧게 못 잡는다** | 하루 호출 한도 | 2분이면 하루 720회 — **에어코리아 500건 초과**, 1,000건 소스도 여유 28%. 얻는 것은 1분 |

목표의 끝 시각은 **디스코드가 알림을 수락한 시각(2xx)**이다. 고객이 읽은 시각이 아니다. 예산표의 처리 1분과 원천 지연은 아직 `[예상]`이다 — 여행 경로는 실측 전이다.

에어코리아의 96% 는 3분을 정한 이유가 아니라 **3분이 에어코리아에게 빠듯하다는 결과**다. D-017 은 **에어코리아만 4분(360/500 = 72%)으로 떼는 안**을 대안으로 적어 뒀고, `[결정 2026-09-23]` **3분 그대로 두기로 했다** — 한도 안이고 문제가 난 적이 없다. 한도 거절이 하루 1건이라도 생기면 그때 다시 본다.

★**감시 루프가 구글을 못 쓰는 이유는 비용만이 아니다.** 비용 쪽 근거(자주 부르면 장소 한 곳에 상품가의 몇 배)는 앞서 적어 뒀는데, **약관이 먼저 막는다.** 비용을 감당할 수 있게 되어도 열리지 않는다.
