# D-025 고객 계획은 모델이 통째로 읽고 분류하며, 코드는 사실 검사 · 연결 · 저장만 한다

`[2026-10-16 사용자 결정 — 2026-10-15~16 의논]` 고객이 보낸 계획서와 채팅 수정 요청을 **사람 비서처럼 통째로 이해하고, 고객 성향대로 먼저 채워 보여 주는** 구조로 바꾼다.
뜻을 정하는 일(무엇이 일정이고 무엇이 이동 · 조건 · 성향 · 질문인가)은 모델이 하고, 코드는 모델이 말한 것이 **원문 · 조회 · 범위와 맞는지 검사하고 담당에게 연결하고 저장**만 한다.

## 왜 바꾸나 — 지금 구조가 구조상 못 읽는 것

2026-09-26 설계서 §0 은 「규칙(정규식)이 먼저 읽고, 규칙이 못 읽은 줄만 모델에 넘기되 모델은 **위치만** 가리킨다」였다. 당시 실측(사진 한 장, 모델이 고유명사를 바꿔 적음)으로는 맞는 판단이었다.
그런데 같은 줄에서 규칙이 무엇이든 하나라도 읽으면 **그 줄 전체가 모델에 가지 않는다.** 그래서 문단으로 쓴 자유문, 시각 줄 사이의 「택시로 이동」, 「비 오면 실내」, 「걷기 싫어요」, 「남산타워 말고 롯데타워로」 같은 말은 **구조상 읽을 자리가 없다.**

2026-10-16 시험지 69건(합성 49 · x600 서버 cs 프로젝트 DB 의 실제 접수 20)으로 잰 지금 구조의 점수:

| 칸 | 지금 구조 |
|---|---|
| 일정 항목 찾음 | 217/258 = 84% |
| 문단 자유문의 일정 항목 | 10/22 = 45% |
| 구간별 이동 수단 | 0/28 = 0% |
| 조건(「비 오면 실내」) | 0/9 = 0% |
| 성향(「걷기 싫어」 「애들 데리고」) | 0/18 = 0% |
| 중간 정정 요청 | 0/4 = 0% |
| 값 변조(원문에 없는 글자) | 0/247 = 0% |

근거: [기준선 보고서](../../final_project_cs/wiki/records/reports/2026-10-16_계획읽기_다양한입력_기준선.md) · 시험지 · 채점기 `final_project_cs/eval/intake_diverse/`(commit 117586bf).
같은 날 가르친 E4B 한 번 호출로 통째로 읽게 한 초안은 일정 항목 96% · 이동 수단 57% · 조건 56% · 요청 종류 전부 맞음 86% 였고 값 변조는 0 이었다([초안 측정](../../final_project_cs/wiki/records/reports/2026-10-16_계획읽기_에이전트_초안_측정.md)).
**고유명사를 바꿔 적는 위험은 「원문에 글자 그대로 있는 조각만 받는다」는 코드 검사로 막는다** — 09-26 의 걱정은 구조를 위치 가리키기로 묶지 않고도 막을 수 있다는 것이 초안에서 확인됐다.

웹 조사(2026-10-15, [조사 기록](../../program/research/2026-10-15_계획서이해_구조조사_codex.md))의 요점도 같다: 형식(JSON 틀) 강제만으로는 내용 오류가 줄지 않을 수 있어 **코드 검증이 꼭 있어야 하고**, 긴 입력은 **나눠 읽고**, 기억은 모델이 아니라 **서비스가 가진 장부**로 둔다.

## 무엇을 정했나

### 1. 입구는 하나 — 채팅 수정 요청과 계획서는 같은 흐름

- 글 · 표 · 사진 받아쓰기를 **원래 위치를 붙인 조각**(메시지 n 의 몇째 줄, 시트 · 칸)으로 펼쳐 「고쳐 가는 초안」에 이어 붙인다.
- 입력 모양(표냐 글이냐, 계획서냐 채팅이냐)으로 **미리 갈라서 뜻을 정하지 않는다.**
- 긴 글은 날짜가 아니라 **길이로** 나누고, 앞 조각과 겹치게 하며 **읽은 상태**(지금 몇째 날 · 앞에 나온 장소)를 다음 조각에 넘긴다.

### 2. 이해 · 분류는 가르친 E4B 하나가 한 번에 한다

- 모델: x600 서버의 가르친 E4B(`tripilot-pointer:e4b-ft`, 채팅 · 일정 짚기와 같은 모델). 모델 투표 · 계단식 호출은 쓰지 않는다. 12GB GPU 라 모델 하나에 여러 일을 섞어 가르치는 쪽이 기본이다.
- 한 번 호출에 한 형식(JSON 틀 강제)으로 다음을 낸다.
  - 가드 판정: 여행 이야기인가 · 지시를 바꾸려는 문장인가 · 범위 밖인가. **거절하지 않고 확인 질문으로만** 쓴다.
  - 요청 조각 여러 개: 계획 항목 · 정정 · 질문 · 일정 짜기 요청 · 잡담.
  - 일정 항목: 원문 줄 번호 + 원문 인용.
  - 구간별 이동 수단, 조건(「비 오면 실내」), 성향, 고객만 아는 빠진 값.
- 시간이 9초를 넘으면 지금 채팅 장치대로 유료 대체 모델을 1회 부른다. 그것도 실패하면 **규칙 미리보기 + 못 읽은 조각 표시**로 보여 준다.

### 3. 코드는 사실 검사만 한다

- 인용이 원문에 **글자 그대로** 있나(없으면 버린다) · 시각 다시 계산 · 장소 조회(지금의 장소 찾기) · 서울 · 7일 · 4인 범위.
- 지금의 규칙 읽기(정규식)는 **지우지 않는다.** 대조용과 모델이 실패했을 때의 미리보기로 남긴다.

### 4. 빈칸은 담당에게 연결하고, 담당은 제안만 한다

- 빈칸 목록 = 모델이 분류한 빈칸 + 사실 검사로 찾은 빈칸.
- **분류 이름 → 담당 연결표(코드)** 로 식당 팀 · 활동 팀 · 이동 판정 · 계획 에이전트 · 고객 질문에 보낸다.
- 담당은 **같은 모양의 제안**(후보 1~3 · 이유 · 검사 결과)만 내고 적용하지 않는다.
- 코드가 장소 → 이동 → 시각 순으로 초안에 대 보고 다시 검사한다. 새 충돌이 생기면 **최대 2회까지** 다시 돈다.

### 5. 계획 에이전트는 빈칸 하나를 채운다

- 지금의 일정 생성기는 고객 원문 대신 **정리표 + 선호(설문 · 성향)** 를 받고, 여행 전체가 아니라 **빈칸 하나(하루 · 시간대)** 를 채운다.

### 6. 확인 화면 — 비서처럼 먼저 채우고 등록 한 번

- 읽는 동안 일정을 보여 주되 멈추지 않는다. 우리가 채운 칸에 **「우리가 채움」 + 이유**를 붙이고, 끝에 **등록 한 번**으로 확인한다.
- 영업시간 모름 · 이동 빠듯은 노란 표시만 한다(막지 않는다).
- 예약 일정 · 고객이 고정한 일정 · 재난 규칙은 지금 그대로다.
- 등록 뒤 변경은 [D-020](D-020-trip-survey-and-ask-first.md) 그대로다(항로 지킴이 켜짐이면 적용 후 알림, 꺼짐이면 먼저 묻기).
- 돈(유료 입장 등)은 지금 범위 밖이다.

### 6-A. 읽은 성향 · 조건은 담당이 이미 읽는 열쇠로 넘긴다 `[2026-10-16 후속]`

- 모델이 읽은 성향 · 조건은 **담당이 이미 읽는 설문 · 제약 열쇠**로 옮겨 싣는다. 새 판단 규칙은 만들지 않는다 — 담당은 지금 읽던 열쇠를 그대로 읽는다.
- **고객이 직접 답한 값이 먼저다.** 로딩 중 질문 · 등록 요청의 설문에 이미 있는 자리와 등록 몸통에 이미 있는 열쇠는 덮지 않는다.
- 읽은 값으로 채운 것은 여행의 `constraints.filled_by_reading` 에 원문 인용과 함께 남고(「우리가 채움」), 설문의 「직접 답한 문항」(`survey_answered`)에는 넣지 않는다 —
  항로 지킴이 자동 적용처럼 「고객이 직접 고른 것」만 보는 판단이 읽은 값으로 켜지지 않게.
- 확인 화면 목록 위에 「담당에 넘겨요」로 무엇을 · 어느 담당에 · 「우리가 채움」인지 「고객님 답 그대로」인지 보인다.

| 읽은 것 | 담당이 읽는 열쇠 | 담당 |
|---|---|---|
| 택시 위주 · 대중교통 위주 · 걷기 좋아함, 여행 전체 이동(「다 지하철로」) | `survey.priority_details.mobility` | 이동 판정 · 일정 짜기 |
| 느긋하게 · 늦게 시작 | `survey.pace = relaxed` | 일정 짜기(밀도) |
| 맛집 위주 · 분위기 좋은 식당 + 원문 인용 | `constraints.meal_preference` | 식당 고르기 |
| 비 오면 실내 | `survey.indoor_outdoor.activity = indoor` + 원문(`custom_answers.indoor_outdoor`) | 활동 대안 순서 |
| 걷기 힘듦 · 어르신 · 계단 힘듦 | `constraints.mobility_ease = needs_rest` | 이동 판정(환승 상한) · 일정 밀도 |
| 몇 시까지 끝 · 몇 시 이후 시작 | **새 열쇠** `constraints.day_hours.end` · `.start`(HH:MM) | 일정 짜기 하루 창 · 하루 마감 경고 · 설문 밀도의 하루 창 |

- `day_hours` 는 이번에 새로 만든 열쇠다. 없으면 지금처럼 가드레일 `travel.day_window`(08:00~22:00) 기본값을 쓴다. 시작이 끝보다 늦게 읽히면 둘 다 넘기지 않는다(짐작으로 고르지 않는다).
- 넘기지 않는 것: 아이 · 어르신 동반의 나이 짐작(일정 짜기는 원문 낱말로 이미 본다), 「비 오면 빼기」(감시 루프의 날씨 판정 몫), 채식 · 할랄(민감 정보 — 동의 화면에서만 받는다).

### 7. 고객 선호 장부 — 자리만 두고 구현은 뒤로

- 근거 · 날짜 · 적용 기간을 붙여 두고 고객이 보고 지울 수 있는 장부. 이번에는 **설계에 자리만** 둔다. 구현하면 이 문서 「구현 상태」에 적는다.

## 이전 결정과의 관계

- **뒤집는 것**: 09-26 설계서 §0 의 「모델은 가리키기만 하고, 값은 원문과 조회가 낸다」와 §2-A(규칙이 먼저, 남은 줄만 모델, 모델은 위치만). 설계서는 당시 기록이라 본문을 고치지 않고 §0 에 이 결정을 가리키는 주석만 단다.
- **그대로 두는 것**: 받아쓰기는 비전 모델이 「한 줄씩 그대로」 하는 것(§3-2), 장소 해석 순서(정확 → 별칭 → 자모 오타 → 카카오 · 관광공사 → 유료), 값 변조 금지(원문에 없는 고유명사 · 예약번호를 만들지 않는다), `_create_trip` 한 곳 등록, 2분 감시에 유료 호출 금지.
- [D-020](D-020-trip-survey-and-ask-first.md)(등록 뒤 변경) · [D-018](D-018-decision15-stop-paths.md)(실패한 자료에 기대는 작업만 보류) · 사람 대기 없음 결정은 그대로다.
