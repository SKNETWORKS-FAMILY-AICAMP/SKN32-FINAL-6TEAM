# D-017 감시는 소스별 공유 수집, 주기는 응답 목표와 호출 예산으로 계산한다

`[초안 2026-09-15 · 2판]` 사용자 결정(대화) + codex 검수(「승인 보류」) 반영. 1판 백업: `program/산출물양식/w3/아키텍처/_backup/2026-09-15_0804_D-017초안v1/`.
v11 §7-C(1322줄) 「최소 84초, 기본 2분」과 **다르다** — v11 은 읽기 전용이라 고치지 않고 이 문서가 그 자리를 대신한다.
합의되면 v11 사실표·`wiki/architecture/notifications.md` 에 한 줄로 반영한다.

## 결정

> **감시는 여행 항목별 직접 조회가 아니라 소스별 공유 수집으로 수행하며,
> 주기는 응답시간 목표와 호출 예산을 동시에 만족하도록 소스별로 계산한다.**

```
소스 주기 = max( 목표가 허용하는 주기 , 86,400초 × 한 번 돌 때 호출 수 ÷ 하루 호출 예산 )
하루 호출 예산 = 무료 소스는 무료 한도 · 유료 전환 가능 소스는 무료 한도의 절반
```

지금 값 (한 번 돌 때 소스마다 1회 호출 전제 — 격자·지역을 나눠 부르면 호출 수만큼 주기가 길어진다):

| 묶음 | 소스 | 주기 | 하루 호출 / 한도 |
|---|---|---|---|
| 무료 지역 소스 | 기상(Open-Meteo) · 기상청 특보 · 단기예보 · 재난문자 · ITS · UTIC 교통 사건 | **3분** | 480 / 1,000 (48%) |
| 무료 · 한도 낮음 | 에어코리아 | **3분** — `[결정 2026-09-23]` 그대로 둔다 | 480 / 500 (**96%** — 재시도 여유 20회) |
| 장소 단위 | TourAPI 장소 운영정보 | **3분마다 2곳씩 돌아가며 확인** — 한 장소를 다시 확인하는 간격 ≈ 장소 수 × 86.4초 | ≤ 1,000 (한도 미확인) |
| 유료 전환 가능 | Google Places(영업시간 = Enterprise 등급) · Routes(교통 반영 = Pro 등급) | 무료 한도 절반 — Places ≈ 90분 · Routes ≈ 18분 | 16 · 80 |

에어코리아 대안: **4분 = 360 / 500 (72%)**. 대기질은 이동 사건보다 급하지 않아 4분이 계산식과 맞다.

`[결정 2026-09-23 — 사용자]` **4분으로 떼지 않고 3분 그대로 간다.** 96% 라도 한도 안이고 지금 문제가 난 것은 없다. 미리 바꾸지 않고, **문제가 생기면 그때 다시 점검한다** — 그 신호는 아래 「재검토 조건」의 **한도 거절(`rate_limited`)이 하루 1건 이상**이다. 그때 4분 안을 다시 꺼낸다.
3분은 「무료 지역 소스를 한 주기로 묶는 단순함」을 고른 임시값이다 — 팀원과 정한다.

**함께 정한 흐름** (주기와 떼어 읽으면 주기가 틀리게 읽힌다)

1. 감시 수집기(코어)가 소스마다 가져와 **사실 테이블**에 쓴다 — 값 · 원천 게시 시각 · 처음 본 시각 · 지문(내용 해시)
2. **지문이 바뀐 사실에 걸린 항목만** 해당 에이전트가 판정한다 — **사건 없음**
3. 전부 PASS 면 아무것도 안 한다(사건 0 · 알림 0)
4. 하나라도 FAIL 이면 **여행당 사건 1건** → 코어가 **Activity → Dining → Mobility** 순으로 대안을 받는다(앞 에이전트의 초안을 다음에 넘긴다, 에이전트끼리는 부르지 않는다) → **전체 일정 재검증** → **새 버전 1번 + 알림 1번**
5. 고객 신고(자유 문장)는 폴링과 무관하게 **즉시** 4 로 들어간다

## 맥락

- 그런데 **무료 소스에도 하루 한도가 있다.** 2분이면 하루 720회 — 1,000건 소스는 72%, 에어코리아(500)는 **초과**.
- 지금 코드의 감시는 **항목마다** 「앞으로 90분 안에 시작하는 항목」을 본다(`trip_watch.py:31`). 항목 수에 비례해 호출이 늘어 여행·항목이 수백이 되면 한도를 못 버틴다.
- 「몇 분이면 되나」의 기준이 없었다 — 워크스페이스 계획서·wiki 에서 「골든타임」·감지~통지 목표 표현을 검색해 못 찾았다(가까운 언급은 `wiki/product/scope.md:136` 「통지까지의 총 시간이 상한」 하나). 다른 이름으로 적힌 목표는 놓쳤을 수 있다.

## 응답 목표 — 골든타임에서 거꾸로 정했다

**골든타임 = 고객이 영향받는 항목으로 출발을 결정하는 순간까지 남은 시간.** 확정 시나리오(`team_branch/jh/확정_시나리오.md`)로 추정했다 `[추정]`:

| 사건 | 고객이 결정하는 순간 | 골든타임 |
|---|---|---|
| 역사 화재 무정차 (이동 중) | 지하철에 타기 전 | **5~10분** — 가장 짧다 |
| 도로 행사 통제 (경복궁 → 서울역) | 출발 전 | 10분 안팎 |
| 점심 70분 지연 · 브레이크타임 | 대안 식당으로 걷기 전 | 수십 분 |
| 저녁 식당 당일 임시휴무 | 경복궁을 떠나기 전 | 약 45분 |
| 전망대 기상 악화 | 전망대로 출발하기 전 | 수십 분~몇 시간 (예보) |

**목표 (초안)** — 운영에서 잴 수 있게 정의한다:

| 항목 | 정의 |
|---|---|
| 시작 시각 | 원천 게시 시각(`published_at`)이 있으면 그것, 없으면 우리가 **처음 본 시각**(`first_observed_at`). 둘 다 기록한다 |
| 끝 시각 | **디스코드 API 가 알림을 수락한 시각**(2xx). 고객이 「읽은」 시각이 아니다 |
| 목표 | 이동 사건 **p95 ≤ 5분 · p99 ≤ 10분**, 최근 30일 |
| 모든 구간 | 원천 게시 지연 + 수집 대기(≤ 주기) + 처리(분류 → 판정 → 대안 → 재검증) + 알림 대기열 대기 + 디스코드 호출·재시도 |

시간 예산 `[예상 — 여행 경로 미측정]`:

```
원천 게시 지연  미측정          (교통 사건이 원천에 몇 분 늦게 오르는지 모른다)
수집 대기      최대 3분        (3분 주기)
처리          약 1분          (쇼핑몰 경로 실측 p95 32~51초를 빌린 값)
대기열·발송    수 초           (발송 작업을 상시로 돌린다는 전제)
────────────────────────────
합계          약 4분 + 원천 지연  →  p95 5분 목표의 여유는 약 1분뿐
```

**여유가 1분뿐이다.** 원천 게시 지연이 1분을 넘으면 3분 주기로는 목표를 못 지킨다 — 그래서 아래 재검토 조건에 넣었다.

## 지금 코드와의 차이 — 이 결정이 요구하는 것

이 결정은 **아직 코드에 없다.** 지금 코드는 이렇게 동작한다 `[codex 검수가 짚은 위치 — 줄 번호는 2026-09-15 기준]`:

| 지금 | 이 결정이 요구하는 것 |
|---|---|
| 스케줄러가 **1분마다** `--once` 프로세스를 새로 띄운다(`install_sweeper_task.py:43`, `run_sweepers.py:82`) | 소스별 `다음 호출 시각` 으로 도는 수집기 하나 |
| 호출 제한기가 **프로세스 메모리에서만** 센다(`ratelimit.py:72`) — `--once` 마다 0 으로 돌아가 **하루 한도가 실제로 안 지켜진다** | **영속 호출 예산 카운터** — DB 에 소스별 하루 사용량 |
| 감시가 항목별 90분 창으로 돈다(`trip_watch.py:31`, `:59`) | 소스 단위 수집 → 사실 테이블 → 바뀐 사실에 걸린 항목만 판정 |
| 감시는 **사건을 만들지 않는다**(`trip_watch.py:177`) — 사건은 고객 신고 경로에서만 | 판정 FAIL → 여행당 사건 1건 |
| 사실 테이블 코드·DB 는 **있지만 연결 안 됨**(`watch.py:95`, `:184~259`, 마이그레이션 `012_watch_observations.sql:16`) | 수집기가 쓰고 판정이 읽는다 |
| 알림 발송 작업은 **수동 실행**(`scripts/run_outbox_worker.py`) | 상시 실행 |

실무 폴러가 갖추는 것 (필요 최소):

- 소스 일정 표 — `source_schedule(source, next_due_at, cadence, freshness_slo, failure_count, lease_until)`
- **임대(lease)** — 프로세스가 둘이 되어도 같은 소스를 두 번 부르지 않는다
- 실패 시 **지수 백오프 + 지터**, 원천이 준 `Retry-After` 를 따른다
- **신선도 경보** — 소스의 마지막 성공이 `freshness_slo` 를 넘으면 경보(조용히 멈춘 소스를 찾는다)
- 초기 적재도 같은 예산을 거쳐 여러 날에 나눈다

## 결과

**바뀌는 것**

- 감시가 **항목 단위 → 소스 단위**가 된다
- 설정: `rate_disaster_msg_per_day` 100 → **1,000**(사용자 제공), `rate_google_places_per_day = 16` · `rate_google_routes_per_day = 80` 신설(`app/core/settings.py`, `.env.apikeys.example`). Google 어댑터는 아직 없다
- 발표 그림(`program/산출물양식/w3/아키텍처/svg/절충안/*-v3-*`)이 이 흐름과 지금 코드와의 차이를 세 단계(지금 동작 / 만들어졌지만 연결 안 됨 / 새로 만들 것)로 보여준다

**못 하게 되는 것**

- 시스템이 스스로 알아채는 사건은 **최대 3분 늦게** 잡힌다(2분보다 1분 늦다). 고객 신고는 영향 없다
- 에어코리아를 3분으로 두면 **재시도 여유가 하루 20회**다 — 원천 장애 날에 한도를 먼저 소진할 수 있다
- **장소 단위 소스는 장소가 늘수록 재확인 간격이 길어진다** — 장소 100곳이면 TourAPI 기준 약 2.4시간에 한 번 `[계산]`. **당일 임시휴무를 늦게 잡을 수 있다** — 이 결정의 약점이다
- Places 영업시간 확인은 **하루 16회**가 전부다

**전제 (지켜지지 않으면 근거가 무너진다)**

- 알림 발송 작업이 상시로 돈다
- 호출 예산을 영속 카운터로 센다 — 지금처럼 프로세스 메모리로 세면 한도 계산 전체가 의미 없다

## 확인하지 못한 것 · 다음에 잴 것

- **한도 대부분이 「미확인 — 보수적」 값이다**(`settings.py` 주석). 확인된 것은 Open-Meteo · 기상청 특보 · KHOA · 에어코리아, 사용자 제공 재난문자
- 한 번 돌 때 호출 수 — 단기예보·교통 사건을 격자·지역별로 나눠 부르면 1회가 아니다. 호출 수만큼 주기가 길어진다
- 골든타임 5~10분은 시나리오 시각으로 낸 **추정**이다 — 발표에 쓰려면 근거 자료(도보·배차 간격 등)를 붙인다
- 처리 약 1분은 쇼핑몰 경로 실측을 빌린 값이다 — 여행 경로에서 사건마다 시작·끝 시각을 기록해 p95 를 잰다
- 원천 게시 지연은 안 봤다
- Google Routes 의 대중교통(TRANSIT) 모드가 어느 요금 등급인지 문서에 없다
