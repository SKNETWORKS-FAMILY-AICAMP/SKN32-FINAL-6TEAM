# D-019 여행 밀도 — 관측 경고 + 자동 변경 판단

## ★2026-10-03 개정 — 밀도를 자동 변경 판단에 쓴다 (사용자 지시)

`[결정 2026-10-03 — 사용자: 「밀도 공식 짠 거 적용해서 실제 사용도 하게」]` 아래 「이번 변경은 관측 단계다」를 **감시가 일정을 자동으로 바꿀 때**에 한해 넘어선다. 등록·조회는 그대로 관측만 한다(거절 없음).

**무엇을 보나** — 바꾸기 전과 바꾼 뒤의 하루 밀도를 **같은 함수**(`measure_density`)로 재서 변경이 **나쁘게 만든 날**만 가려낸다(`density.density_regressions`).

| 종류 | 뜻 |
|---|---|
| `new_exceed` | 목표 안이던 날이 목표 밖이 된다 |
| `worse` | 이미 목표 밖이던 날이 **허용 오차보다 더** 밖으로 간다 — 일정 하나 바꿀 때마다 생기는 흔들림은 잡음이라 본다 |
| `unmeasurable` | 잴 수 있던 날을 못 재게 된다 — 값을 모르는 상황을 변경이 만들지 않는다(결정 15) |

바꾸기 전에 못 쟀던 날은 비교할 수 없어 탓하지 않는다. 밀도 목표가 없는 여행은 아무 영향이 없다.

**어떻게 쓰나(soft, 기본)** — 구조 위반(겹침·이동 불가)은 밀도와 상관없이 **늘 막는다**(벽). 밀도는 **선호**라서 벽이 아니다: 밀도를 나쁘게 만드는 안은 순위에서 **뒤로 밀고**, 구조 위반이 없고 밀도도 안 나쁜 안이 있으면 그것을 쓴다. 그런 안이 하나도 없으면 **가장 덜 나쁜 안**(못 재게 되는 날이 적고 → 목표를 덜 넘는 순)을 쓰되 알림에 **무엇이 어떻게 빡빡해졌는지** 적는다. `hard` 로 바꾸면 구조 위반처럼 막는다(`travel.density.gate.mode`).

**왜 벽이 아닌가** — 감시가 일정을 바꾸는 것은 원래 항목이 **고장 났기 때문**이다(닫힘·재난·통제). 하루가 좀 빡빡해지는 것을 이유로 고장 난 항목을 그대로 두면 더 나쁘다. 다만 사용자 지시 원문은 「밀도를 새로 밖으로 밀면 재판정 위반」이라 `hard` 를 한 줄로 켤 수 있게 두었다 — **기본값을 어느 쪽으로 둘지는 사용자 결정 대기.**

**수치(우리가 고른 값 — 측정 안 함)** — 허용 오차 `travel.density.gate.worsen_tolerance` = 0.02(하루 12시간 창에서 약 14분). 목표(0.40·0.55·0.70·0.80)는 아래 연구 보정값 그대로다.

**순위 키로는 안 넣었다** — 후보 순위(`replan.Candidate.rank`)에 「밀도 흔들림」 칸을 더하지 않았다. 같은 시간대 맞바꿈은 하루 점유를 거의 안 바꾸고(분자는 항목 소요 + 이동 + 완충이다), 흔들림의 실제 원천(`shift_minutes` · `changed_items`)은 이미 순위 키에 있다. 목표를 벗어나게 하는 안만 뒤로 민다. 순위 키가 필요하면 `Candidate.rank` 에 한 칸 더하면 된다.

**둘 다 못 하는 곳** — 적용기(`itinerary_actions`)의 마지막 안전망은 구조 위반만 본다. 밀도까지 걸면 soft 가 고른 안을 적용기가 거절한다. 밀도는 Team 이 고를 때(`itinerary_fit.fit_change`)만 본다. 불변식 `INV-CS-ACT-005`.

**한계** — 점유율은 피로·안전 점수가 아니다(아래 근거). 허용 오차는 근거 없이 정한 값이다. 감수한 악화는 알림 문장과 `summary.density` 로 남아 사후 검토할 수 있다.

## 2026-09-22 추가 조사 반영

[근거 조사표와 실측 설계](../../final_project_cs/wiki/records/reports/2026-09-22_2230_여행밀도_근거조사.md)에 문헌·공식 표준별 확인 범위와 수치 적용 한계를 정리했다. 장소 수/점유율 분리, 개인 선호, 대기시간 포함을 근거로 선택 계약 1.1을 구현했다. 사용자 직접 목표와 추정 프리셋을 구별하고 시간 구성·대기 주석 누락 수·정책 식별자를 응답에 추가한다. 점유율을 피로 또는 안전 점수로 해석하지 않는다.

고정 비율·동행자 상한·일률 버퍼를 검증한 수치는 아직 확보하지 못했다. 이번 조사는 관련 근거를 보강했으며 실측 보정을 완료한 것은 아니다. [62/62 테스트 및 변경 리포트](../../final_project_cs/wiki/records/reports/2026-09-22_2240_여행밀도_근거반영_구현.md).

2026-09-22 사용자 구현 요청으로 등록·조회 API에 관측용 밀도를 추가한다. 점유율은 원문 관측값과 그로부터 파생한 운영 구간으로 설정하고, 이동·접근성·예약 여유는 공식 지침값을 사용한다. 등록 거절이나 활동 자동 삭제에는 쓰지 않는다. 최종 수치 근거는 [수치 반영판](../../final_project_cs/wiki/records/reports/2026-09-22_2300_여행밀도_근거자료.md)이다.

분모는 사용자가 명시한 하루 활동 가능 시작~종료 시간이다. 기상 시간이나 첫/마지막 일정으로 추측하지 않는다. 분자는 모든 일정 항목의 예약된 시간 + 항목 밖에 명시한 이동시간 + 별도로 확보할 완충시간이다. 식사·예약·이동 항목을 다시 더하지 않는다. 시간 겹침·창 밖 일정·종료 누락·이동 정보 누락은 측정 불가이며 0으로 채우지 않는다. 장소가 같다는 것은 식별자가 같을 때만 인정한다.

`constraints.density` 및 응답 계약은 [API 계약](../../final_project_cs/wiki/external/travel-density.md)에 있다. 기존 `check_itinerary()`의 위반 목록과 밀도 경고를 분리한다. 밀도 수치 설정은 `config/guardrails.yaml`의 `travel.density` 한 곳에서 읽는다.

## 근거와 적용 한계

- [The Vacation Planning Problem (2022)](https://www.sciencedirect.com/science/article/pii/S0305054822003136): 방문시간·이동시간·하루 시간 예산·시작/종료 위치를 일정 제약으로 다룬다. 시간 기반 계산을 택하는 근거이며 아래 비율의 검증 근거는 아니다.
- [FHWA Travel Time Reliability](https://ops.fhwa.dot.gov/publications/tt_reliability/ttr_report.htm): 이동시간 변동에 대비한 완충시간과 95백분위 기반 buffer index를 설명한다. 서울 관광의 일률적 15% 할증을 정당화하지 않는다.
- 단계별 비율과 동행자별 상한을 검증한 자료는 이번 조사에서 확보하지 못했다. 비율은 [추정] 정책으로 표시하고 동행자 보정·일률 버퍼·자동 재조정은 후속 측정 대상으로 남긴다. 나이·장애·건강 정보는 이 기능의 입력에 포함하지 않는다.
- 등록 시 입력만 확인하는 범위는 [D-018](D-018-decision15-stop-paths.md)의 층별 정책과 현행 `itinerary_checks.py`에 따른다. 밀도 미측정이 감시 루프에서 자동 해소된다고 약속하지 않는다.

후속 적용 조건: 실제 일정의 희망 템포·계획 시간·실제 소요·지연을 수집해 임계값을 검증하고 정책을 별도 확정한 뒤 거절/재조정에 연결한다. ★등록·조회는 여전히 관측 단계다. 감시의 자동 변경만 위 개정(2026-10-03)으로 임계값 없이 **목표 대비 악화 여부**를 본다 — 임계값 검증은 여전히 숙제다.
