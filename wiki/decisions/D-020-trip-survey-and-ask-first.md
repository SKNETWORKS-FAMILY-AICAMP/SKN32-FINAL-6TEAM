# D-020 여행 시작 설문과 「먼저 물어봐줘」

`[결정 2026-09-24 회의]` 사용자 전달. 코드·문서와 부딪히는 곳은 매니저 세션이 대조했다
(코덱스 교차검토 — 첫 판은 사용량 한도로 못 했고, 02:01 에 돌려 아래 「코덱스 교차검토가 짚은 것」에 반영했다).

## 정한 것

### 1. 처음에 UI 화면에서 설문을 받는다
여행 테마 · 여행자 구성 · 선호 이동수단 · 내국인 여부 · 우선순위1(음식·활동·이동) · 우선순위2(영역별 세부) ·
실내/실외(식당·액티비티) · 테마 세부 · **15 일정이 꼬이면** · **16 여유**.

★**우선순위2의 세부 선택지와 세부 테마는 예시다.** 예로 든 「음식 → 맛·친절·청결」, 「활동 → 익스트림·힐링·DIY·쇼핑」,
「이동 → 대중교통·도보·차」의 실제 모양은 **각 담당 팀이 정해서 알려 준다.** 그래서 계약은 그 값들을 목록으로
박지 않고 문자열로 받는다.

### 2. 15번 — 「갑자기 일정이 꼬이면 어떻게 했으면 좋겠어요?」
| 답 | 동작 |
|---|---|
| 🔄 비슷한 곳으로 바꿔줘 (`replace`, 기본) | **지금까지와 같다** — 최고 안을 먼저 적용하고 알린다. 싫으면 다른 안·되돌림 |
| 💬 먼저 물어봐줘 (`ask_first`) | **적용하지 않고** 안(1·2·3)을 보여 주고 **사용자의 선택을 기다린다** |

**무응답 규칙** — 「먼저 물어봐줘」인데 답이 없으면, 해당 일정은 그 시간이 끝나 종료되더라도 **대기**하고,
끝나면 **다음 일정으로 진행**한다(바꾸지 않는다).

### 3. 16번 — 「여행할 때 어느 정도 여유가 좋으세요?」 → 밀도 목표
🐢 여유롭게 = `low` 0.40 · 🙂 적당히 = `normal` 0.55 · ⚡ 꽉 차게 = `high` 0.70
(`config/guardrails.yaml` `travel.survey.pace_to_density_level`). 회의의 「적당 55~60%」는 **0.55 단일값**으로 둔다.

### 4. 하루 활동 시간 기본값 — 08:00 ~ 22:00
사용자가 하루 활동 시간을 주지 않았을 때만 쓴다(`travel.day_window`). 「절반 숙소 나감 10시」는 뜻이 정해지지 않아 **넣지 않았다.**

### 5. 사용자와 주고받는 것은 셋
| | 무엇 | 지금 있는 것 |
|---|---|---|
| ① 알림 | 하루 시작 · 출발 안내 | `trip_reminders.py` |
| ② 사용자가 일정 변경 요청 | 신고 · 자유 문장 · 다른 안 · 되돌리기 | `POST /v1/trips/{id}/reports`·`messages`·`items/{item}/alternate`·`rollback` |
| ③ 시스템이 일정 변경을 통지 | 버전 통지 | 버전 통지(①변경) — **「먼저 물어봐줘」면 통지가 「선택 요청」이 된다** |

## 기준선에서 바뀌는 것

| 기준선 | 지금 |
|---|---|
| 결정 15 「후보가 불확실해도 **하나를 고른다** — 선택지를 나열하지 않는다」 | `replace` 여행에는 그대로. **`ask_first` 여행에는 나열하고 고르게 한다** |
| 접점·통지 모델 「최고 안을 먼저 적용하고 알린다, **알림을 승인 요청으로 쓰지 않는다**」 | `replace` 는 그대로. `ask_first` 는 **통지가 선택 요청**이다. ★「통지가 닿았나」는 여전히 사양 밖 — 그래서 **무응답 = 바꾸지 않음**이 기본이다 |
| D-019 「밀도의 분모는 **사용자가 명시한** 하루 시간, 추측하지 않는다」 | 사용자가 시간을 주지 않고 16번만 답했으면 **팀 기본값 08:00~22:00** 을 쓴다. 추측이 아니라 정한 기본값이고, 채운 사실을 `constraints.derived` 에 남긴다 |

★아래가 「새벽」 표보다 **나중이고 우선한다.**

| A | ★**「돈이 걸렸는지」는 보지 않는다.** 보호 대상은 사용자가 **「변경 안 할 일정」**으로 고른 항목(이미 있는 `customer_pinned` 옵션)뿐이다 — 새벽 표 2번의 「예약·결제가 걸린 항목」·`booking_id` 검사는 뺐다. 고정 항목은 **바꾸지 않고 다른 일정을 바꾸며**, 그 항목 **자체**를 바꿔야 하면 15번 답과 상관없이 **대기(묻는다)** |

### 코덱스 교차검토가 짚은 것 (2026-09-24 02:01, 반영할 것)
- ★**「돈이 걸린」을 알아볼 칸은 이미 있다** — 항목의 `locked`·`booking_id`(`itinerary.py`, 마이그레이션 014). 새 칸(`reserved`·`prepaid`)을 만들 필요가 없다. 다만 등록 API(`ItemIn`)가 두 칸을 **받지 않는다.**
- ★**결함:** `Item.replaced_by()` 가 항목을 바꿀 때 `locked=False`·`booking_id=None` 으로 만든다 — 예약 식당을 자동 교체하면 **예약 연결이 조용히 사라지고** 원 예약·위약금은 살아 있다.
- ★**결함:** 감시는 `customer_pinned` 항목을 **통째로 건너뛴다** — 고정 항목에는 안전 알림도 안 나간다. **감지와 변경을 나눈다**: 고정이면 바꾸지 않되 감지·알림은 계속.
- 알림에 **종류 표시**가 필요하다 — 웹이 가를 수 있게 `guidance`(①②③) · `proposal_request`(선택 요청) · `change_notice` · `safety_alert`.
- 동시에 일행 둘이 고르면 — **먼저 고른 쪽**, 나중 쪽은 409. 선택은 **구조화된 API**로 받고, 자유 문장은 `/messages` 로 따로.

## 지금 판정에 쓰는 것 / 받기만 하는 것
- **쓴다:** 15번(`on_disruption`) · 16번(`pace` → 밀도 목표)
- **받기만 한다:** 나머지 전부. ★판정에 연결되기 전까지 **「반영했다」고 말하지 않는다.**
- ★**맛·친절·청결 같은 평판 값은 뒷받침할 데이터가 없다** — 장소 표(`011_place_catalog.sql`)에 평점 칸이 없고, 관광공사 API 는
  평점을 주지 않으며, 구글 리뷰는 저장이 금지다(`wiki/research/place-api-quota-and-terms.md`). 팀이 세부를 정할 때 **데이터 출처도 함께** 정해야 한다.

## 아직 정하지 않은 것
- 「절반 숙소 나감 10시」의 뜻
- 밀도 산식의 「일정 개수 / n」 — 모르는 소요시간을 남은 시간으로 균등 배분하면 **밀도가 계산 전에 ~100%로 정해진다**
- 「이미 지연됐고 다음 일정이 70% 구간이면 다음 일정 수행」 — `[2026-09-25 사용자]` **70% 는 밀도 이야기다.** 우리 밀도 목표의
  「빡빡」(high = 0.70, `travel.density.targets`)과 같은 자리다. 지연이 났을 때 그 밀도에서 무엇을 하는지(늦은 일정을 줄이나 ·
  다음 일정으로 넘어가나)는 **아직 코드에 넣지 않았다**
- ~~식당 「웨이팅 20분」의 뜻~~ → `[2026-09-25 사용자]` **요식업 팀 몫이다.** 웨이팅을 얻는 방법을 요식업 팀이 고안 중이고,
  그것을 **20분 단위로 조회**하려고 기획 중이다. 코어는 그 값이 들어올 자리만 맞추면 된다 — 방법이 정해지면 받는다
- 새벽 3시 점검의 소스와 저장(구글 약관) — 구글 키가 들어오면 붙인다
