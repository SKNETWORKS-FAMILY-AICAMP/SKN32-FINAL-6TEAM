# 고객 응대 라이팅 에이전트 기존 설계 검토

2026-10-24 21:52 KST. 범위는 로컬 정본 문서와 현재 코드의 정적 검토입니다. 제품 구현·테스트·실모델·DB·고객 화면·운영 배포 검증은 하지 않았습니다. 병렬 독립 조사 2건의 결론을 취합하고 아래 주요 코드 구간을 부모 세션이 직접 대조했습니다. 전체 구현율 분모는 미확정입니다.

## 결론

[실측: 문서·코드] 독립된 ‘라이팅 에이전트’ 확정 계약은 이번 검색 범위에서 찾지 못했습니다. 필요한 자산은 존재하지만 고객 문의·계획 등록 안내·감시 통지가 서로 다른 작성 경로입니다. Composer는 설정·모듈 조립 도구이며 고객 응대 작성기가 아닙니다. 옛 커머스 response_review를 켜는 방식은 채택하지 않습니다.

## 기존 자산과 한계

- [여행 대화·고객 취향 통합 계획](../../../final_project_cs/wiki/records/plans/2026-10-12_여행대화와_고객취향_통합_구현계획.md): 입력의 잡담·취향·사실 조회·추천·변경을 분리하는 제안. 장기 기억의 동의·범위·삭제까지 포함하나 완료 계약이 아닙니다.
- [채팅 문맥 계약](../../../final_project_cs/wiki/external/trip-chat-context.md): 대상·날짜·일정 버전·선택지 보존. 확대 관측의 대상 오승계·복합 질문 누락을 미해결로 기록합니다. 오늘 재현한 결함이라는 뜻은 아닙니다.
- [D-020](../../decisions/D-020-trip-survey-and-ask-first.md): 지킴이 켜짐, 꺼짐/미응답, 고정 항목, 재난 후 명시 재개, 공급자 거래 승인을 구분하는 우선 계약입니다.
- [알림 설계](../../architecture/notifications.md): 변경과 정기 안내를 구분하고 원값·문구틀을 보존합니다. ‘항상 먼저 변경’처럼 오래된 설명은 D-020의 후속 조건과 대조해야 합니다. 모든 안내를 매번 LLM에 보내는 확대는 현재 계약과 다릅니다.

[정적 조사] Controller의 제안 검증을 모든 고객 문장의 사실검사로 간주할 수 없습니다. 채팅의 최근 문맥과 outbox 알림은 별도이며, 감시 알림을 가리키는 후속 질문을 공통 이력으로 해결하는 경계는 조사 범위에서 확인하지 못했습니다. 옛 response_review와 관련 커머스 시험은 여행 제품의 검증 근거로 사용하지 않습니다.

## 개선안 — 미승인 제안

1. **공통 응대 입력 계약:** 입력 종류(계획 접수/문의/감시/후속 답변), 인증된 여행 범위, 일정 버전, 질문 목록, 근거·확인시각·누락, 실제 실행 결과, 승인·대기 상태, 후속 대상과 원인 이벤트를 함께 전달합니다. 새 필드 이름과 모델은 아직 확정하지 않습니다.
2. **업무 판단과 작성 분리:** 기존 전문 팀·검증·저장 경로는 유지합니다. 작성기는 확인된 결과를 설명하고 필요한 질문·선택지를 구성하되 일정 변경·예약·결제를 직접 실행하지 않습니다. 업무 도구가 필요한 경우 기존 권한·예산 경계를 통해 요청합니다.
3. **실행 뒤 최종 응대:** ‘추천’, ‘고객 선택 대기’, ‘저장 완료’, ‘업체 예약 미확정’, ‘실패’를 구분한 결과로 문장을 작성합니다. 작성 결과가 원래 제안·required_input_schema·resume_token·승인 상태를 덮지 않도록 합니다. 정기 안내는 기존 결정론적 문구틀 경로와 공통 사실 계약을 공유하되 모델 호출을 강제하지 않습니다.
4. **후속 대화 연결:** 알림 원인·적용 버전·대기 제안을 채팅에서 참조할 수 있게 합니다. tenant/customer/trip 격리·만료·삭제와 순서 역전·중복 정책을 계약으로 먼저 정합니다. 장기 취향 기억은 별도 동의 과제이며 기본 전제로 넣지 않습니다.
5. **여행용 검증:** 복합 질문 누락, 틀린 대상 승계, 근거 없는 시각/금액/장소, 미저장 완료 표현, 재전송 중복, 변경 뒤 오래된 선택, 감시 알림 후 ‘왜 바꿨어?’를 시험합니다. 실제 모델 평가와 mock/DB/실서버 증거는 분리합니다.

## 작업 순서와 남은 범위

계약·수용 기준 확정 → 문의 한 경로 연결 → 계획서 결과·감시 전달 연결 → 후속 이력·여행 claim 검사 → 실제 모델·종단 검증 순서를 권장합니다. 이 순서는 제안이며 구현 승인·완료를 뜻하지 않습니다. 새 하드코딩·폴백·제품 코드 변경은 없습니다. 저장소에 기존 미커밋 변경이 다수 있으므로 공유 파일 수정 전 개별 비교가 필요합니다.

## 후속 독립 검토 — 최소 수용 기준 제안

[검토 완료: 실행 시험 아님] 새 child 세션의 읽기 전용 독립 검토를 반영합니다. 문장 작성 통합만으로 여행 비서가 되는 것은 아니며, 아래 여섯 책임의 소유자를 계약에서 명시해야 합니다. 신규 기능 확정이나 구현 완료를 뜻하지 않습니다.

1. **질문 완결:** 복합 질문을 개별 추적하고 각각 답변·추가 확인·미지원·실패로 닫습니다. 자연스러운 문장으로 미답변을 숨기지 않습니다.
2. **조회 책임:** 인증된 여행 범위·허용 도구·예산 안에서 조회하고 출처·확인 시각·누락을 전달합니다. 조회 실패를 일반 지식으로 메우지 않습니다.
3. **실행 확인:** 변경 의도·제안·선택·저장·업체 거래를 구분하며 재조회한 결과·버전과 일치할 때만 완료를 표현합니다. timeout·unknown을 성공으로 쓰지 않습니다.
4. **상태 불변:** 작성·검수는 제안·required_input_schema·resume_token·승인/대기 상태를 보존합니다. 작성 실패로 업무를 재실행하지 않습니다.
5. **안내 비용:** 공통 응대 계약이 공통 LLM 호출을 뜻하지 않습니다. 정기 안내의 Case 없는 문구틀·원값 주입과 예산 계약을 보존하며 대기 항목에는 출발을 지시하지 않습니다.
6. **후속 연결:** 원인 이벤트·대상·버전·대기 제안을 권한 확인 후 참조합니다. 오래된 선택·중복·순서 역전을 처리하고 단답을 문맥만으로 변경 승인으로 승격하지 않습니다.

다음 구현 절의 입력은 위 수용 기준과 공통 계약 초안입니다. 현재 사용자 요청의 설계 검토를 넘어 제품 구현·배포를 시작하지 않았습니다.

2026-10-24 사용자 구현 승인 뒤 문의 첫 연결을 구현했으며 부모 격리 unit 재실행 105/105 통과했습니다. 추가 이력 조사에서 후속 문의·계획서 읽기 개편의 로컬 누락을 발견했습니다. 따라서 위 정적 검토를 기존 실제 반영 내용 전수 확인으로 해석하지 않습니다. [변경 묶음·누락·다음 절](../../handoff/2026-10-24_travel-writing-implementation.md).
