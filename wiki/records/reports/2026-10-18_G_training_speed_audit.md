# G 모델 학습 가속 가능성 읽기 전용 점검

현재 학습은 유지했습니다. 코드에서 가속 후보 세 가지를 찾았지만, 이 A4000에서 가속 효과를 비교 측정하거나 적용하지는 않았습니다. 우선 검증 후보는 아직 시작 전인 Gemma-4-E4B-it QAT의 정답 오차 계산 통합입니다. 진행 중인 Winnow-E4B(Jev 계열, 우리 G 자료 학습)에 즉시 적용할 무중단 가속 방법이 검증됐다고 주장하지 않습니다.

## 확인 시각과 범위

- 2026-10-18 00:28 KST: A4000 GPU 상태 5회, 현재 진행 로그, 실행 중인 학습 프로세스, 학습 코드·모델 설정·설치 패키지를 읽었습니다. 처음 조회 스크립트는 문자열 문법 오류로 실행되지 않았고, 수정한 조회는 성공했습니다.
- 00:31 KST: Winnow 프로세스가 유지되고 단계가 2,070에서 2,080으로 진행한 것을 확인했습니다. 최신 2,080/4,620 = 45.0%입니다. E4B는 기존 대기열에 등록되어 있으며 실행을 앞당기거나 수정하지 않았습니다.
- [첫 조회 증거](../../../datasets/core/travel_tasks/20261017_audited_G/e4b_after_winnow_G/speed_audit_20261017_152833_G.json)와 [조사 후 유지 확인](../../../datasets/core/travel_tasks/20261017_audited_G/e4b_after_winnow_G/speed_audit_20261017_152833_G_after_G.json). 학습 코드 2개·로더 1개·모델 설정 2개의 SHA-256이 조사 전후 5/5 일치했습니다. 이는 해당 5파일의 검증이며 전체 데이터셋·모델 가중치를 새로 해시한 결과는 아닙니다.
- 원격 명령은 읽기 전용입니다. 현재 프로세스 정지·재시작·메모리 주입·디버거 연결·추가 GPU 계산·패키지 설치·전력/클럭 변경·모델/데이터 원본 쓰기·작업큐 변경을 수행하지 않았습니다. 로컬에는 새 조회 증거와 이 기록만 만들고 기존 안내 문서는 수정 전 백업했습니다. 예약 생성·재활성화 없음.

## 코드에서 확인한 가속 후보

[Winnow 학습 코드](../../../datasets/core/travel_tasks/20261017_audited_G/scripts/train_winnow_G.py)와 [E4B 학습 코드](../../../datasets/core/travel_tasks/20261017_audited_G/e4b_after_winnow_G/train_e4b_G.py)는 원격 코드와 지문이 일치했습니다. 둘 다 1문항씩 계산하고 8문항의 기울기를 모은 뒤 갱신합니다. BF16 연산·NF4 저장·층별 중간값 재계산과 정답 오차 64토큰 단위 재계산을 이미 사용합니다.

| 우선순위 | 후보 | 확인한 근거 | 적용 전 확인할 것 |
|---|---|---|---|
| 1 | 정답 오차 계산 통합: Fused Linear Cross Entropy/Liger | 어휘 수 262,144의 출력 점수를 만든 뒤 64토큰씩 오차를 따로 계산하고 역전파 때 재계산함. 큰 출력 행렬과 반복 실행을 줄이는 후보 | 실제 Gemma 4 모델 클래스·현재 Transformers 5.18/PEFT/QLoRA 조합 호환, 출력 점수 보정, 정답 토큰 정렬·마스킹, 오차·기울기 대조, 최장 문항 메모리 |
| 2 | 작은 묶음으로 동시 처리 | 현재 1×8을 2×4로 바꾸는 후보. 한 번 갱신에 쓰는 문항 수는 8로 유지 가능 | 원래 문항 순서·그룹·문항별 평균 오차를 유지해야 함. 두 문항을 토큰 수로 합쳐 평균 내면 현재 학습 가중치와 달라짐. 패딩·마스크·위치와 최장 문항 메모리 확인 |
| 3 | 중간값 재계산을 일부 줄임 | 현재 층별 gradient checkpointing과 정답 오차 checkpointing이 메모리를 아끼려고 계산을 반복함 | 먼저 메모리를 절약하고 선택적으로 적용. 현재 약 3.5GiB 순간 여유만으로 전체 해제를 결정하지 않음 |

1번은 [Liger 공식 지원표](https://github.com/linkedin/Liger-Kernel#patching)의 Gemma4 Text/Multimodal 지원과 [Gemma4용 실제 구현](https://github.com/linkedin/Liger-Kernel/blob/main/src/liger_kernel/transformers/model/gemma4.py)을 확인했습니다. 정답 라벨/shift_labels가 있어야 통합 오차 경로로 들어가는 구현이므로 현재 사용자 정의 루프에 단순히 패키지만 설치해도 가속된다고 말할 수 없습니다. 현재 환경의 패키지 메타데이터에는 Liger 설치가 확인되지 않았으며, 설치하지 않았습니다.

2번은 [Hugging Face의 gradient accumulation 안내](https://huggingface.co/docs/transformers/grad_accumulation), 3번은 [PyTorch의 checkpoint 메모리·계산 교환 설명](https://docs.pytorch.org/docs/2.14/checkpoint.html)을 근거로 한 후보입니다. 다른 장비·모델의 홍보 속도 수치를 이 A4000의 개선율로 옮기지 않았습니다.

## 우선 적용 대상으로 삼지 않은 항목

- FlashAttention 강제 전환: 설치된 Gemma4 코드의 SDPA/Flash 지원 선언은 확인했지만, 현재 프로세스의 실제 선택 커널을 계측하지 않았습니다. 별도 FlashAttention 패키지가 나열되지 않는다는 사실만으로 PyTorch 내장 빠른 SDPA도 사용하지 않는다고 판단하지 않습니다. 마스크·슬라이딩 윈도우·역전파 호환을 확인하지 않은 전환은 보류합니다.
- torch.compile: 현재 사용자 정의 루프에 적용되지 않았습니다. [PEFT 공식 안내](https://huggingface.co/docs/peft/developer_guides/torch_compile)는 동적 경로의 그래프 분리와 결과 검증 필요성을 명시합니다. 문항 길이가 달라지는 루프와 NF4·checkpointing 조합의 실제 결과·컴파일 비용 대조가 필요합니다.
- 토큰화·디스크 정리: 현재 코드는 본 학습 반복 전에 토큰을 RAM에 준비합니다. 지금 진행 중인 계산 속도를 높이기 위해 원본 자료나 모델을 정리할 근거로 삼지 않습니다.
- 학습 문항 삭제·긴 문항 자르기·반복 횟수 축소·LoRA 범위 축소: 학습 내용이나 목표가 달라지므로 이번 가속 후보에 포함하지 않습니다.

## 검증 상태와 다음 적용 시점

이번에 완료한 것은 실행 상태 읽기와 코드·공식 근거를 통한 후보 검토입니다. 별도 GPU 가속 비교 시험은 0건이며 속도 개선율·메모리 절감률·정확도 유지가 실측됐다고 주장하지 않습니다. Winnow는 현재 상태로 계속 진행합니다. E4B는 아직 시작 전이므로 새 구현을 검증할 적용 시점이 남아 있지만 이번 요청에서 대기열이나 실행 파일을 교체하지 않았습니다.

후속 구현을 하게 되면 별도 새 코드·새 출력 경로에서 기존 방식과 후보를 같은 문항·조건으로 교대 측정하고, 최장 문항·7과제·오차/기울기·어댑터 저장/재읽기·메모리를 비교해야 합니다. 학습 자료 18,478행·2회 반복·4,620단계·정답만 학습·원본 기반 가중치 고정 조건은 유지 대상입니다. 지금 GPU에서 그 시험을 함께 돌려 현재 학습을 늦추지 않았습니다. 자동 후속 확인을 등록하지 않습니다.
