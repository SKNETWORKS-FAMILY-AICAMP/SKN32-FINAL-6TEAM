# x600 배포 전후 계획 읽기 속도 — 읽기 전용 비교 (2026-10-28 13:45~14:10 KST)

## 결론

| 질문 | 답 | 근거 수준 |
|---|---|---|
| 같은 환경·같은 방식 전후 비교가 가능한가 | **x600 DB 기준(접수→먼저 채우기 claim)으로는 가능**하다. 다만 배포 뒤 표본은 **10건뿐이고 모두 시험 트래픽**이다(배포 직후 묶음 05:23~05:42 8건, 07:25·07:27, 13:38 부모 브라우저 1건). 실제 고객 요청은 0건으로 보인다 | 측정 |
| 실제 서빙 속도가 개선됐나 | **판정 불가.** 전체 p50 은 오히려 23.1 → 33.3초지만 차이는 유의하지 않다(Mann-Whitney p=0.27). 중앙값 차이(뒤−앞) 부트스트랩 95% 구간은 **−4.8 ~ +34.1초**다. 개선과 악화를 모두 배제하지 못한다 | 측정·계산 |
| 정량 한계 | 전 기간 분포에서 모의 실험을 했다(α 0.05, 검정력 0.8). 배포 뒤 **n=10 이면 50% 단축도 못 잡는다.** n=20 이면 약 50%, n=40 이면 약 40%, n=80 이면 약 30% 단축까지 잡을 수 있다. 일정 수·모델 섞임이 다르면 이보다 더 많이 필요하다 | 계산 |
| EKS 80.7초와의 관계 | 다른 서버(EKS main)이고 측정 끝점(브라우저 완료)도 다르다. **이 비교에 쓰지 않는다** | 원칙 |

## 3. 같은 예시 짝(내용에서 숫자·공백을 지운 md5 가 같은 것 — 해시·원문은 출력하지 않음)

|---|---|---|

| A | luna | 7.7 |

- 숫자를 지우면 날짜·시각이 다른 입력도 한 묶음이 된다. 그래서 위험 점검·영업시간 결과는 달라질 수 있다.

## 4. 개선 판정에 필요한 것(제안 — 실행 안 함)

1. 같은 예시를 같은 모델로 고정하고, 전 판 vs 현 판을 **각 20회 이상** 돌린다. 격리 사본 또는 사용자가 승인한 합성 게스트를 쓰고, 동시 부하 없이 간격을 둔다. 측정 지점은 DB claim 시각과 브라우저 완료 둘 다다. 전 판 측정이 x600 에 남아 있지 않으므로, 전 판 이미지(`064208bdd4` 등)를 격리 환경에 띄워야 같은 방식이 된다.
2. 또는 실제 채팅 접수가 **40건 이상** 쌓인 뒤 같은 SQL 로 다시 낸다(약 40% 단축 이상만 판정 가능). 이때 모델별·일정 수별로 나눈다.
3. 13:38 의 25.6초 점검 구간은 api 로그(13:38±2분)로 이동·위험 소스별 소요를 확인한다.

## 5. 지킨 것 · 증거

- SQL 9개는 모두 `BEGIN READ ONLY` · `statement_timeout 30s` · `lock_timeout 2s` · `ROLLBACK` 으로 실행했다. 출력은 집계 · 시각(분 단위) · 일정 수 · 모델 이름 · 소요 숫자만이다. 접수 id · 원문 · 고객 식별자 · 해시는 출력하지 않았다.
- 서버에서 한 일은 `deploy.log` grep, `docker ps`, DB 읽기뿐이다. 서비스 · 설정 · 고객 쓰기는 0이고 새 요청 · 유료 호출도 0이다.
