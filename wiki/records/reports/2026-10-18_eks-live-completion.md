# 2026-10-18 AWS 실제 배포 확인·복구 작업

## 02:07 KST 관측

구구루트(guguroute)의 AWS 배포 상태를 인증된 CloudShell에서 재조회했다. 기존 리소스 식별자는 유지한다.

- PostgreSQL 18.3 관리형 DB: available, 외부 직접 접속 비활성화.
- 웹·관리자 화면·외부 요청 전달 앱·작업 처리 앱: 각 1개 실행 중.
- 서비스 API: 준비 상태 0/1, 모델 제공자 설정 누락으로 CrashLoopBackOff, 재시작 183회 관측.
- 공개 웹 첫 화면: HTTP 200. API·여행 기능 정상 동작을 뜻하지 않는다.
- 작업 처리 로그: 분류 작업 fatal=1. 관광공사 일일 정기점검 관련 조회 연결 누락. 여행·안내 처리 대상 0건인 실행 결과를 실제 고객 경로 성공으로 해석하지 않는다.
- 관리자 화면은 내부 처리 앱을 루프백 주소로 바라보지만 해당 앱이 배치되지 않았다.
- 기존 RunPod GPU 기계의 Ollama 태그 목록에서 학습 모델 `tripilot-pointer:e4b-ft` 등록을 확인했다. AWS에서 도달하는 경로는 아직 연결하지 않았다.

## 02:14 KST 관리자 배치 변경

- 변경 전 관리자 Deployment를 CloudShell 개인 작업 경로에 백업했다. 접속 주소·계정·키 경로는 공용 기록에 싣지 않는다.
- 기존 `tripilot-admin` 컨테이너 정의를 그대로 보존하는 검사를 넣고, `ops` 컨테이너를 같은 Pod에 추가했다.
- `ops`는 기존 API 이미지의 `python -m app.ops_entrypoint`를 실행한다. 관리 화면과 루프백 통신을 유지한다.
- 준비 상태 검사는 내부 `/health`를 호출한다. 교체 전략은 maxUnavailable=0, maxSurge=1이다.
- Kubernetes는 패치 적용 성공을 반환했다. 실행 준비·실제 내부 응답은 후속 확인 중이다.
- 최초 변경안은 자동 승인 검토가 기존 관리자 앱 교체 위험을 이유로 차단했다. 기존 컨테이너 전체 보존 검사와 명시적인 보존 목록을 사용한 수정안이 승인되어 적용됐다.

## 승인 대기·남은 일

- 기존 운영용 외부 API 키·웹훅·관리자 비밀번호 해시·임베딩 키를 현재 AWS 계정의 비공개 보관소로 전송하는 구체적인 승인을 요청했다. 아직 전송하지 않았다.
- 기존 GPU 모델 포트에만 접근할 전용 SSH 연결 승인도 함께 요청했다. 기존 GPU 작업·모델·학습 실행은 변경하지 않았다.
- API 정상화, 관리자 내부 응답, 데이터 준비 범위, 실제 고객 여행 경로, 알림 경로 확인이 남았다.
- 로컬 AWS CLI는 설치돼 있다. 로컬 kubectl과 인증·운영 접속 경로는 추가 준비가 필요하다.
- 새 에이전트 예약·자동화, 제품 CronJob, 커밋·푸시, 원본 자료 삭제는 실행하지 않았다.


## 02:31 KST 재확인·정정

- 관리자 내부 앱 누락이라는 앞선 판단은 틀렸다. 실제 `deploy/Dockerfile.admin`과 `admin_runner.py`가 관리자 화면과 운영 API를 함께 실행한다. 추가한 `ops` 컨테이너 때문에 운영 API 포트가 충돌했다. 이번 추가분을 제거하고 원래 관리자 실행기로 복구했다. Pod 1/1 Running·재시작 0회, 내부 `/health` HTTP 200을 재확인했다.
- 관리자 세션 조회는 `configured=false`다. 내부 응답 성공과 운영자 로그인 가능을 구분한다.
- 로컬 AWS CLI의 전용 프로필 인증과 kubectl 1.34.1 설치·공식 SHA256 대조·EKS 접속을 완료했다.
- 현재 EKS 노드와 AWS 관리 노드가 같은 대상을 가리키며 Online임을 확인했다. 노드 SSH 서비스·임시 공개키 인증 지원도 확인했다.
- 인터넷 SSH 포트를 열지 않고 AWS 관리 통로를 거쳐 SSH로 노드 이름을 조회했다. 공개키는 접속 때 임시 등록하며 비밀키는 이 PC에 남는다. 기존 개인 SSH 설정을 백업한 뒤 새 개인 설정을 Include했다. 새 설정의 Windows 권한도 제한했고, 기본 SSH 설정으로 AWS 노드 접속과 기존 x600 접속 대상 해석을 확인했다.
- GPU 전용 공개키는 기존 GPU 인증 파일을 백업한 뒤 추가했다. 명령 실행은 막고 모델 포트 한 곳의 전달만 허용했다. 로컬 임시 연결로 모델 태그 조회 성공을 확인했으며 이 임시 로컬 연결은 검증 후 종료했다.
- GPU 연결용 소형 이미지를 빌드하고 ECR에 업로드했다. AWS 적용 스크립트는 격리된 개인 작업 경로에 준비했다.
- 자동 승인 검토가 새 GPU 전용 비밀키의 EKS Secret 저장과 연결 Deployment 생성을 구체적인 승인 부족으로 차단했다. 우회하지 않았고 정확한 저장 대상·배포 범위의 승인을 요청했다. 사용자가 전달한 GPU 접속 주소는 연결 대상으로 확인했지만, 외부 운영 키 이전 승인은 별도로 확인 중이다.
- AWS DB의 public 표는 83개다. 장소 목록·영업시간·검색용 지식 문서·지식 조각·여행 표의 실제 행 수는 각각 0건이다. 기존 고객 자료를 옮기지 않았다.
- 로컬 설정에서 관광공사·기상 관련 키가 빈 값임을 확인했다. 키 이전 승인을 받아도 원래 빈 값을 유효한 키로 만들 수는 없다.
- 공개 웹 빌드의 API 주소는 빈 접두어로, 같은 출처의 `/v1` 경로를 사용한다. 로컬 개발 주소를 참조하도록 빌드되지 않았다. 공개 요청 전달 설정도 대조했다.
- 허용 웹 출처를 현재 AWS 공개 요청 전달 주소로 갱신하고 이전 ConfigMap을 개인 경로에 백업했다. 모델 연결 준비 전에는 앱 재시작을 보류했다.
- 공개 접속은 활성 Network Load Balancer다. 현재 DNS 조회 IP는 1개이며 고정 EIP 할당을 확인한 값은 아니다. 실제 주소는 Git 제외 개인 접속 메모에만 보관했다.
- AWS CLI 자격 증명 조회 명령이 출력 제한 인자를 적용하지 않아 임시 자격 증명을 도구 출력에 표시했다. 또한 직접 DB 드라이버에 앱 URL을 넘긴 오류에 연결 문자열이 포함됐다. 이후 조회는 비밀값을 출력하지 않도록 수정했으며 공용 기록에는 값·접속 주소를 복사하지 않았다. 표시된 임시 자격 증명의 만료 시각은 이미 지났다. DB 비밀번호 교체는 아직 하지 않았다.

### 아직 완료되지 않은 범위

1. GPU 전용 키의 EKS 저장·연결 앱 적용에 대한 구체적 승인, 실제 AWS→GPU 모델 호출, 서비스 API 정상화.
2. 외부 운영 키·웹훅·기존 관리자 로그인 해시·임베딩용 키 이전 승인과 적용. 원래 빈 관광공사·기상 키는 별도 확보 필요.
3. 검색용 지식·장소 자료 준비와 실제 고객 여행·알림 경로 검증.
4. 실제 도메인명·DNS 등록·HTTPS. 현재 공개 주소의 IP를 고정 IP로 안내하지 않는다.

새 에이전트 예약·자동화·제품 CronJob·GPU 할당·커밋·푸시·원본 삭제는 수행하지 않았다. 실제 고객 경로 성공·AWS 배포 전체 완료를 선언하지 않는다.


## 02:33 KST 승인 차단 추가

DB 비밀번호 교체·Secrets Manager/EKS 참조 갱신·AWS 앱 3개 재시작을 준비했으나, 자동 승인 검토가 구체적 승인 부족으로 실행을 차단했다. 실행 전 차단되어 DB 비밀번호는 바뀌지 않았다. GPU 연결·기존 운영 키 이전·이번 DB 비밀번호 교체와 앱 재시작의 세 범위를 묶어 명시적 승인을 요청했다. 승인 전 의존 작업은 진행하지 않는다.


## 03:07 KST 승인 적용·실제 응답

- 사용자가 기존 외부 운영 키·관리자 설정 이전과 최초 GPU 전용 키 EKS 저장·배포, DB 비밀번호 교체·AWS 앱 3개 재시작을 명시적으로 승인했다.
- RDS 마스터 비밀번호를 교체했고 새 비밀번호의 DB 접속을 확인했다. Secrets Manager와 Kubernetes 참조를 갱신하고 API·작업 처리·관리자 앱을 재시작했다. 앞서 도구 출력에 표시된 DB 비밀번호를 현재 값으로 재사용하지 않는다.
- 비어 있지 않은 외부 운영 키·웹훅 12개, 기존 관리자 비밀번호 해시, 임베딩용 OpenAI 키를 비공개 보관소에 적용했다. 원래 빈 관광공사·기상 키는 생성하지 않았다. 관리자 계정 설정 1개를 앱에서 확인했다.
- 서비스 API·웹·관리자·작업 처리 앱의 Running/준비 상태를 확인했다. API 내부 `/health`와 모델 태그 조회는 HTTP 200이다.
- AWS 전용 SSH 연결은 기존 RunPod 연결과 별도다. 모델의 내부 Host 제한 때문에 발생한 HTTP 403을 내부 요청 중계로 해결했다. 중계 앱의 모든 임시 폴더를 쓰기 가능한 임시 볼륨으로 옮겨 읽기 전용 파일 시스템 보호를 유지했다.
- AWS에서 학습 모델에 일반 확인 질문 한 건을 보냈고, 완료·비어 있지 않은 답변·「서울」을 확인했다. 응답 소요 12.58초는 이 한 건의 측정값이며 성능 보장이나 반복 측정 결과가 아니다.
- 기존 oracle-arm 기계의 RunPod SSH 프로세스가 같은 상태로 유지되고 모델 태그 조회가 계속 성공함을 재확인했다. 그 SSH 서비스·키·설정·GPU 모델 실행을 중단하거나 재시작하지 않았다.
- x600 기계에는 기존 모델 실행기가 남아 있었지만 Ollama 관리 앱이 꺼져 있었다. 기존 실행기를 중단하지 않고 관리 앱을 SSH 세션과 독립된 숨김 프로세스로 복구했다. SSH 접속 종료 후에도 모델 태그 조회가 유지됐다.
- x600에는 모델 포트 한 곳만 허용하는 별도 공개키를 추가하기 전 기존 인증 파일을 백업했다. 전용 키의 로컬 SSH 연결과 학습 모델 등록을 확인했다. 기존 개인 비밀키는 복사하지 않았다.
- x600 전용 비밀키의 EKS 저장과 자동 전환 중계 앱·Service 적용은 자동 승인 검토가 추가 구체적 승인을 요구해 실행 전에 차단됐다. 준비한 설정을 우회 실행하지 않았다. 별도 승인 질문이 대기 중이다.
- 여행 안내·정책 19문서 141절의 OpenAI 임베딩 전송도 자동 승인 검토가 본문·목적지 승인을 요구해 실행 전 차단했다. 검색용 지식 표는 아직 0건이며, 문서 본문의 OpenAI 전송 승인을 별도 요청했다.
- 공개 장소 원본 CSV 6,334행에서 사실 정보 열 25개만 선별했다. 소개글·체험 설명·예약 설명 등은 제외했다. 기존 로더로 담당 범위와 출처를 지켜 TourAPI 5,451 + 올리브영 368 + 다이소 233 + 아트박스 36 + 무신사 50 = 6,138행을 AWS DB에 적재했고 실제 행 수 6,138을 재확인했다. 고객·여행·시연용 예약 자료는 넣지 않았다.
- 배포용 tenant 행 누락으로 모니터링 루프에 외래키 오류가 있었다. 배포용 tenant 행 1개만 추가한 뒤 해당 작업을 실행해 fatal=0을 확인했다. 고객 여행이 없어 checked=0이며, 실제 고객 일정 변경 검증을 뜻하지 않는다.
- 로컬 개인 키·인증 자료 파일 16개의 허용 ACL을 재조회했고 현재 사용자·시스템·관리자 이외 허용 항목이 없는 16/16을 확인했다. 일부 파일의 ACL 변경 명령은 권한 오류였으므로 명령 성공 수가 아니라 재조회 결과로 구분한다.

### 현재 남은 일

1. x600 전용 비밀키의 EKS 저장·자동 전환 설정 승인 및 적용·장애 전환·기본 경로 복귀 확인.
2. 정책·안내 문서 19개 141절의 OpenAI 임베딩 전송 승인 및 지식 적재·검색 확인.
3. 원래 비어 있는 관광공사·기상 키 확보 여부와 실제 도메인·DNS·HTTPS. 도메인 이름은 아직 전달받지 않았다.
4. 실제 고객 여행 경로와 알림 도착은 검증하지 않았다. 승인 없는 외부 시험 메시지를 보내지 않았다.

새 에이전트 예약·자동화·제품 CronJob·AWS GPU 할당·커밋·푸시·로컬 원본 삭제는 수행하지 않았다. AWS 앱 이미지는 기존 고정 배포 태그 기준이며 다른 세션의 이후 변경 전체가 이 이미지에 포함됐다고 주장하지 않는다.

## 03:18 KST x600 네트워크 보완

- 로컬에서는 x600의 기존 외부 SSH 주소로 접속됐으나, AWS와 oracle-arm에서 같은 주소의 SSH 연결은 각각 시간 초과였다. 이 확인 범위만으로 모든 직접 연결 방식이 불가능하다고 판정하지 않는다.
- AWS에서 oracle-arm SSH는 도달했다. 공개 SSH 포트를 추가로 열지 않고 x600이 oracle-arm으로 먼저 여는 별도 역방향 모델 통로를 준비했다. 기존 RunPod용 통로와 다른 루프백 포트를 사용한다.
- 새 역방향 비밀키는 x600에서 생성했고 x600에 남긴다. oracle-arm의 기존 인증 파일을 백업하고 제한된 전용 공개키만 추가했다. 기존 RunPod SSH 설정이나 프로세스를 교체하지 않았다.
- x600의 새 연결 실행기는 SSH 연결 종료 뒤에도 유지되는 숨김 프로세스이며, 연결이 끊어지면 다시 연결한다. 이것은 요청받은 제품 모델 연결 처리다. 에이전트 예약·작업 스케줄러 등록은 하지 않았다.
- 로컬 전용 키로 새 중계 통로의 x600 학습 모델 등록을 조회해 성공했다. 그 뒤에도 oracle-arm의 기존 RunPod SSH 프로세스가 같은 상태로 유지됨을 확인했다.
- AWS 쪽 새 전용 키 저장은 계속 승인 대기다. 최종 적용 스크립트는 별도 전환 Pod를 더 만들지 않고 기존 모델 연결 Pod 안에 x600 전용 연결을 추가한다. 기존 모델 Service 주소는 유지한다. 이전 세 Deployment 방식 준비 스크립트는 사용하지 않는다.
- 현재 AWS에서 기본 RunPod 추론은 동작하지만, AWS→x600 자동 전환은 아직 적용하지 않았다. 장애 전환 성공으로 보고하지 않는다.
