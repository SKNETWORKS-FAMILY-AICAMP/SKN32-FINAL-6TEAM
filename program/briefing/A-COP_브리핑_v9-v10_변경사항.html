전체 요약 — 한 줄로 가게를 바꾼 게 아니라 파는 물건을 바꿨습니다. 계산대·영수증·환불 규칙(코어)은 그대로 두고 진열대(Team)만 갈아 끼웠습니다. 그게 이 구조가 애초에 주장하던 것이고, 이번 교체가 그 실증입니다. 그래서 아키텍처 그림 5개는 하나도 안 버렸습니다 — 바뀐 건 그 안의 이름과 어휘입니다.

1. 도메인 교체 — 커머스 CS → 여행 CS

2026-09-08 팀 결정. 코어 계약·생명주기·동시성·감사·평가 도구는 승계하고, Team 모듈과 도메인 데이터는 전량 신규다.

v8 — 커머스 CS
  • 주문·결제·배송·반품·응답 검토
  • 검증 쇼핑몰과 연계
  • 고객 문의가 Case 를 만든다
v10 — 여행 CS
  • 일정 검증 · 변화 감지 · 선제 조정
  • 인바운드 외국인 개인·친구 그룹, 1도시, 영어
  • 고객 문의뿐 아니라 시스템이 스스로 Case 를 만든다 (다음 확인 시점이 오면)
DB 19표 중 코어 14표는 손대지 않고 도메인 5표만 갈아낀다 — orders·order_items·products·returns·shipments → trips·itinerary_versions·itinerary_items·bookings·watch_schedule
쉽게 쇼핑몰 고객센터를 만들다가 여행 도우미로 방향을 틀었습니다. 그런데 다시 만든 게 아닙니다. "고객 요청을 받아서 → 규칙에 맞는지 확인하고 → 위험한 건 사람에게 물어보고 → 기록을 남긴다"는 뼈대는 어느 업종이든 같아서, 그 뼈대를 그대로 두고 업종 지식만 바꿔 끼웠습니다.

2. Team 전량 교체 — 그런데 버린 팀은 하나도 없다

여섯 팀이 전부 바뀌었지만 다섯은 기존 팀의 뼈대를 이어받았다. 반대로 코드를 통째로 물려받는 팀도 없다.

v8 — 커머스 6팀
  • Return & Refund
  • Fulfillment & Logistics
  • Procurement + Order & Payment
  • Catalog & Verification (A2A Remote)
  • VOC & Store Manager
  • Response Generation & Review
v10 — 여행 6팀
  • Activity ← Return & Refund 뼈대
    취소 판정 → 접수 → 환급 계산 3단 구조가 같다
  • Mobility ← Fulfillment 뼈대
    움직이는 것을 추적하고 예외를 잡는다
  • Booking Handoff ← Procurement 뼈대
    생성·변경·취소·상태 조회 자리가 같다
  • Dining — 새로 만듦
  • Lodging / Flight — 등록만
  • Response Review 는 각 Team 내부 규칙으로 흡수
MVP 필수는 Activity 와 Booking Handoff 둘이다. 나머지는 일정에 따라 조정된다.
쉽게 "반품 처리팀"이 "액티비티 취소팀"이 됐습니다. 하는 일의 모양이 똑같기 때문입니다 — 취소할 수 있는지 보고, 접수하고, 얼마 돌려줄지 계산합니다. 반품 기한이 취소 기한으로, 배송비 부담이 우천 위약금으로 바뀌었을 뿐입니다.

3. 제품이 하는 일 — 「답한다」에서 「지켜본다」로

가장 큰 변화다. v8 은 고객이 물으면 답했고, v10 은 묻지 않아도 먼저 알린다.

v8 — 물으면 답한다
  • 고객 메시지 → Case → 처리 → 응답
  • Case 가 끝나면 끝난다
v10 — 안 물어도 지켜본다
  • 일정 등록 → 검증 → 감시 시작
  • 변화 감지 → 재계획 → 재검증을 통과해야 통지
  • 고객이 거부하면 이전 일정 버전으로 되돌린다
  • Trip 은 여행이 끝날 때까지 산다 (Case 는 여럿 생겼다 사라진다)
계획을 만드는 것은 우리 일이 아니다(v10 §4-A). 외부 에이전트·LLM 이 만든 일정을 받아 검증하고 지켜보는 것이 제품이다.
쉽게 전에는 "문의하면 답해주는 상담원"이었다면, 지금은 "예약을 대신 지켜봐 주는 비서"입니다. 비가 온다는 예보가 뜨면 고객이 묻기 전에 먼저 찾아내서 "이 액티비티가 취소될 것 같으니 이렇게 바꾸면 어떨까요"를 정리해 보냅니다. 고객이 싫다고 하면 원래대로 되돌립니다. 그 되돌림이 되기 때문에 먼저 나서는 게 위험하지 않습니다.

4. DoD 29 → 22, 일정은 10주 → 7주

항목이 줄어든 게 아니라 다른 것을 재게 됐다. v9 의 29항목은 쇼핑몰 대상이라 그대로 쓰지 않는다.

v8/v9 — 29항목
  • 주문·배송·반품 처리 정확도
  • 10주 · 중간발표 09-15
v10 — 22항목
  • 자동 17 · 아키텍처 테스트 3 · 측정 2
  • 일정 검증 · 되돌림 · 승인 경계 · 자동 실행 차단
  • 7주 · 최종발표 2026-10-26
새로 들어온 판정 넷 — 되돌림이 되는가 · 되돌린 뒤에도 이력이 남는가 · 실제 공급자에는 자동 실행이 안 걸리는가 · 자동 실행 분기가 시연 모드에서만 열리는가

5. 그림은 왜 그대로인가

도메인이 바뀌어도 아키텍처는 안 바뀐다는 것이 이 프로젝트의 주장이고, 그림을 그대로 쓰는 것이 그 증거다.

버렸다면
  • "도메인 바뀌었으니 다 새로 그린다"
  • → 그럼 코어를 승계한다는 주장이 거짓이 된다
v10 — 5개 다 살렸다
  • 파이프라인 → 에이전틱 확장 이유
  • 전체 아키텍처 (Context Broker · Team · Action)
  • 폴더 / 모듈형 Basement
  • ERD — v8 시절 그림이라 낡았다고 표시하고 지금 19표 목록을 붙였다
  • 로드맵 / 간트
바뀐 것은 그림 안의 이름과 어휘다 — Team 라벨, 도메인 팩 이름, 시연 포인트.
쉽게 건물 도면을 다시 그리지 않았습니다. 방 이름표만 바꿔 달았습니다. 전기 배선과 배관(코어)이 그대로라서 가능한 일이고, 그게 원래 이 설계가 노린 것입니다. ERD 그림 하나는 두 도메인 전 것이라 낡았는데, 지우지 않고 "낡았다"고 표시해 뒀습니다 — 지우면 그때 무엇이었는지가 사라지기 때문입니다.
