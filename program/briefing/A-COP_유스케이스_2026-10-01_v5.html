행위자누구무엇으로 들어오나
여행자스스로 계획을 짜는 자유여행자(국적 무관)다. 최대 7일 · 4인, 서울이다. 외국인 첫 방문은 「가장 크게 막히는 사례」로 다룬다(2026-10-01 결정).입구 ① 웹(사용자 식별 키, /v1/web/* — 아래 탭 일정 · 지도 · 채팅) · 여행계획서 링크(로그인 없음) · 디스코드 알림
개인 에이전트입구 ② — 여행자가 쓰는 외부 AI 비서 앱이다. 그 앱이 짠 일정을 받아 여행 내내 지킨다.REST API(외부 요청 인터페이스) /v1/trips/* · A2A(에이전트 간 통신) /a2a/tasks
시계정해진 시각과 주기다.run_sweepers(상시 작업 실행기) — 상시 등록은 1분마다, 외부 감시는 3분 주기(D-017), 새벽 확인(dawn_check)
외부 데이터 소스기상청 · 에어코리아 · TourAPI · ITS/UTIC · 재난문자 등이다.감시 루프가 조회한다.
알림 채널디스코드 웹훅이다. 지금 실제 발송은 서버 설정의 웹훅 하나(팀 시연 채널)로만 간다.바깥함(outbox, 보낼 메시지를 쌓아 두는 표) 일꾼이 발송한다. 사용자별 받을 곳 등록은 서버 1단계만 있다(U-31).

매니저(코어)와 에이전트 — 에이전트로 등록된 것은 요식 · 액티비티 · 이동 셋이다(예약 넘기기 · 숙소 · 항공은 등록만, MVP 밖). 계획 읽기는 에이전트가 아니라 매니저가 계획을 받을 때 거치는 처리 단계다(config/project.yaml teams).

04여행자·개인 에이전트 쪽 유스케이스

A.여행 전

설문 15번 「일정이 꼬이면」은 「비슷한 곳으로 바꿔줘」(replace)가 기본값이지만 활동의 날씨 사건 자동 적용은 이 답을 직접 고른 여행만이며 「먼저 물어봐줘」(ask_first)를 고를 수 있다. 16번 「여유」의 밀도 목표는 0.40 · 0.55 · 0.70이다. 판정에는 이 두 답만 쓰고 나머지는 받기만 한다.

#유스케이스주 행위자경로상태메모
U-01 여행 시작 설문 여행자·에이전트 POST /v1/trips의 constraints.survey · 웹 /v1/web/* 있음 판정에 쓰는 것은 15번 「일정이 꼬이면」·16번 「여유」뿐이다. 직접 답한 문항을 따로 남긴다(survey_answered) — 「일정이 꼬이면」을 직접 「비슷한 곳으로 바꿔줘」로 고른 여행만 자동 적용 대상이다(U-13). 틀린 설문은 422 invalid_survey.
U-02 바뀜 요청으로 일정 초안 만들기 에이전트 POST /v1/trips/plan 있음 첫 활동 09:00 · 마감 22:00(travel.day_window). 이제 이동 항목을 넣는다(출발 = 다음 시작 − 이동 − 여유). 이동 계산기가 꺼져 있으면 직선 어림값. 웹 「일정 짜 줘」(U-30)도 같은 생성기.
U-03 일정 등록·성립 판정 에이전트·여행자 POST /v1/trips · 웹 /v1/web/* 있음 불성립이면 422와 위반·완화 조건으로 답하고 아무것도 저장하지 않는다. 계획 읽기 확인 뒤 등록(U-29)도 같은 등록으로 들어간다.
U-04 바뀜 웹 사용자 식별 키 받기·다시 받기 여행자 POST /v1/web/session · /v1/web/session/rotate 있음 원문은 한 번만 보여 준다(서버는 SHA-256만). 다시 받으면 옛 키는 무효, 내 여행만 열린다. 발급에 사람 확인(Turnstile)과 주소당 시간 한도가 생겼다(늘 켜짐).
U-05 등록 즉시 계획서 링크 통지 시스템 → 여행자 바깥함 → 디스코드 있음 링크가 처음 나가는 자리다(change_notice). 등록 첫 통지에는 type 칸이 없어 웹이 채워 읽는다.
U-28 새로 계획 올리기 — 글 · 사진 · PDF · 워드 · 엑셀 여행자 POST /v1/web/trip-intakes 있음 파일 5개 · 글 20,000자까지. 받아서 뒤에서 읽고 접수 번호를 돌려준다. 사진은 한 줄씩 받아쓰고, 정해진 모양(시각 · 일차 · 예약번호)은 코드가 먼저 읽는다 — 매니저(코어)의 처리 단계다.
U-29 새로 읽은 값 확인 · 고치기 · 등록 여행자 GET /v1/web/trip-intakes/{id} · …/edits · …/confirm 있음 항목마다 근거(원문 줄)를 보여 주고 고치기 · 빼기 뒤 등록한다. 낡은 판을 고치면 409. 등록은 U-03과 같은 길. 이렇게 등록한 여행에는 이동 항목이 없다 — 06.
U-30 새로 「일정 짜 줘」 여행자 POST /v1/web/trip-intakes/{id}/plan 있음 생성기(U-02)로 짜서 등록한다. 읽은 일정은 고정으로 두고 빈 곳만 채우는 선택이 있다.
U-31 새로 알림 받을 곳 · 연락처 등록 여행자 GET · PUT /v1/web/profile · …/profile/discord/test 일부 서버 1단계만 있다 — 받아서 암호화 저장 · 가려서 조회 · 시험 발송. 실제 발송은 여전히 서버 설정의 웹훅 하나로 가고, 웹에는 웹훅 입력칸이 없다(이메일만) — 06.

U-06 ① 하루 시작 안내 시계 → 여행자 run_sweepers(기본 실행에 포함) · trip_reminders.py 있음 시작 시각에 보낸다(없으면 08:00, 첫 일정 60분 전보다 늦지 않게). 어제 이후 바뀐 일정 수·답을 기다리는 일정을 함께 싣는다.
U-07 ② 다음 일정 안내 시계 → 여행자 같은 곳 있음 각 일정 시작 때 「지금 / 다음」과 사이 이동의 출발 시각을 미리 알린다. 마지막 일정엔 없다.
U-08 바뀜 ③ 이동 안내 시계 → 여행자 같은 곳 일부 이동 항목이 시작하는 시각에 보내고 경로는 그때 조회한다. 생성기 일정에는 이제 나간다. 계획을 그대로 등록한 여행은 이동 항목이 없어 안 나간다 — 06.
U-09 답을 기다리는 일정엔 「출발하세요」 대신 대기 안내 시계 → 여행자 같은 곳 있음 답이 없어 닫히면 다음 틱부터 원래대로 안내한다.
U-10 바뀜 새벽 3시 정리 — 식당 영업 확인 시계 run_sweepers(기본 실행에 포함) · dawn_check.py 있음 식당과 활동의 그날 영업을 확인한다. 이름 + 300m로 구글 장소와 맞추고, 판정 · 확인 시각과 place_id만 저장한다(마이그레이션 026). 구글 키가 비면 꺼진다 — 실제 키가 들어 있는지는 확인하지 않았다.

C.여행 중 — 시스템이 먼저

#유스케이스주 행위자경로상태메모
U-11 변화 감지 → 사건(Case) 열기 시계 · 데이터 소스 run_sweepers(기본 = trip_cases) 있음 외부 감시는 3분 주기(D-017), 상시 등록은 1분마다다. 식사 항목도 Case를 연다(09-29). 감시 안에서 3분으로 늦추는 장치는 확인하지 않았다.
U-12 바뀜 「일정이 꼬이면」 답에 따라 가르기 시스템 pending.decide · itinerary_actions.py · trip_desk.py 일부 ①「변경 안 할 일정」 → 묻는다.
②먼저 물어봐줘 + 안전 사건 → 안전 알림만 보낸다.
③먼저 물어봐줘 → 안 1·2·3을 보관하고 묻는다.
④그 외 → 최적 안을 바로 적용한다.
이제 상시 기본 감시 · 고객 신고 · 새벽 확인이 이 판정을 지난다. 남은 것: 답이 없을 때 닫는 만료가 기본 감시에 없고, 기본 감시가 고정 일정을 건너뛴다 — 06.
U-13 바뀜 묶어서 최선의 안 하나 적용(「비슷한 곳으로」) 시스템(Team → 코어) Case → Team 판정 → 코어 적용 일부 자동 적용은 있다. 활동의 날씨 사건은 설문에서 직접 「비슷한 곳으로 바꿔줘」를 고른 여행만 자동이고, 건너뛰었으면 먼저 「바꿀까요?」를 묻는다(auto_on_disruption). 조합 탐색은 확인하지 않았다.
U-14 변경 통지 시스템 → 여행자 디스코드(change_notice) 있음 자동으로 바꾼 통지에는 되돌리기 정보를 싣는다.
U-15 바뀜 선택 요청 시스템 → 여행자 proposal_request 있음 「답이 없으면 원래 일정을 그대로 둡니다」를 반드시 적는다. 상시 기본 감시 경로에서도 나간다. 변형: 안 없이 「바꿀까요?」만 묻기 · 조건을 푼 안(U-33) · 다른 안 고르기(U-32).
U-16 안전 알림 시스템 → 여행자 safety_alert 일부 바꾸지 않고 바로 알린다. 상시 기본 감시는 고정 일정을 건너뛰어 그 일정엔 안전 알림이 안 나간다(--only trip 경로는 점검한다) — 06.
U-17 값을 못 구하면 대체 소스, 그래도 안 되면 서버 중단 시스템 결정 15 일부 기상 · 교통(ITS + UTIC) 대체 사슬이 있다. 서버 중단은 미구현이다.

#유스케이스주 행위자경로상태메모
U-18 계획서 링크로 최신 일정·바뀐 이유 보기 여행자 GET /plan/{trip_id}?t=… 있음 고객 언어 생성(결정 14)은 미구현이다. 지금은 한국어 원문이다.
U-19 보류 제안 보고 고르기(원래대로 두기 포함) 여행자·에이전트 GET /v1/trips/{id}/proposals · POST …/proposals/{pid}/choose · 웹 /v1/web/* 있음 먼저 고른 쪽이 이기고 나중 쪽은 409. 그사이 일정이 바뀌었으면 거절한다. 웹 일정 탭의 「선택이 필요해요」 카드가 이것이다.
U-20 답하지 않음 → 만료, 원래 일정 유지 여행자(아무것도 안 함) 보류 제안 만료 일부 그 일정이 끝나면 expired로 닫고 다음 일정으로 간다. 만료는 여전히 --only trip 경로에서만 돈다 — 06.
U-21 사건 신고(지연·휴무·품절) 여행자·에이전트 POST /v1/trips/{id}/reports 있음 판정(pending.decide)을 지난다 — 설문 답대로 바꾸거나 묻는다.
U-22 자유 문장으로 말하기 → 분류 → 담당 Team 여행자·에이전트 POST /v1/trips/{id}/messages · POST /v1/cases · 웹 /v1/web/trips/{id}/messages · 대화 기록 …/chat 있음 모델 한 번으로 채팅을 해석하는 단계(decision_unit)가 켜져 있다. 대화 기록 조회가 생겼다.
U-23 다른 안으로 바꾸기 여행자·에이전트 POST /v1/trips/{id}/items/{item_id}/alternate 있음 들고 있던 다른 안이 없으면 그 자리에서 찾는다. 그래도 없으면 409 no_alternate.
U-24 되돌리기 여행자·에이전트 POST /v1/trips/{id}/rollback 있음 되살린 항목은 감시가 다시 자동으로 바꾸지 않는다. 웹 되돌리기(/v1/web/trips/{id}/rollback)도 있다.
U-32 새로 직접 바꿔 달라면 바꾸고 다른 안 셋까지 함께 여행자 · 에이전트 채팅 · itinerary_changes.py · trip_desk.py 있음 바꾼 뒤 「다른 곳이 좋으면 고르세요. 답이 없으면 지금대로 둡니다」 제안을 연다. 설문 답과 상관없이 바로 바꾸는 갈래다.
U-33 새로 후보가 없으면 조건을 푼 안을 묻기 시스템 → 여행자 relaxed_options 있음 시각 늦추기 · 다음 일정 근처 · 반경 넓히기 안을 묻는다. 바로 적용하지 않는다.
U-34 새로 여행 화면 탭 — 일정 · 지도 · 채팅 여행자 웹 trip-home · 지도 /v1/web/map-load 있음 순서가 아니라 아래 탭으로 오간다. 「선택이 필요해요」와 받은 알림은 일정 탭 안에 있다. 지도는 무료 지도가 기본이고 구글은 서버가 허락한 뒤.

06공백 — 코드 세션에 넘길 것

  1. ★「먼저 물어봐줘」 — 반쯤 풀렸다. 두 군데가 남았다.

    이제 상시 기본 감시(Case 경로) · 고객 신고 · 새벽 확인이 판정을 지난다(itinerary_actions.py · trip_desk.py · dawn_check.py). 남은 것: ①답이 없을 때 닫는 만료가 기본 감시에 없다(.expire(는 trip_watch.py 한 곳) ②기본 감시가 고정 일정을 건너뛴다(trip_watch_cases.py) — 그래서 고정 일정엔 안전 알림도 안 나간다.

  2. ★계획을 그대로 등록한 여행엔 ③ 이동 안내가 없다.

    생성기 일정은 풀렸다(이동 항목을 넣는다). 계획 읽기 → 등록(U-29)은 이동 항목을 만들지 않아(intake/assemble.py에서 이동 항목 생성 0건) ③이 안 나간다.

  3. ★알림 받을 곳이 실제 발송과 이어지지 않았다.

    사용자 연락처 저장 · 시험 발송은 있지만(U-31) 실제 발송은 서버 설정의 웹훅 하나다. 웹에는 웹훅 입력칸이 없다. 이메일을 알림용으로 쓰려면 저장 여부도 정해야 한다(지금은 복구용으로만 받고 저장하지 않음).

  4. 식당 방문 60 · 20분 전 안내(dining_*)가 상시 작업에 안 붙어 있다.

    시험 · 점검 스크립트만 부른다(dining/tick.py).

풀린 것(앞 판의 공백): 새벽 3시 영업 확인(U-10, 구글 키 필요) · 웹 키 발급 속도 제한(U-04) · 생성기 일정의 ③ 이동 안내(U-02).
