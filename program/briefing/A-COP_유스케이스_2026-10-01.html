운영자는 없다

여행에서는 운영자가 판단해야 하는 상황이 정상 흐름에 없다.

커머스 시절 CS 구조(상담원이 승인·인계받음)를 옮겨 오면 생기는 착시다. 이미 내린 결정으로 보면 전부 다른 주인에게 가거나 버그가 된다.

운영 화면은 2026-09-23부터 로그인한 계정만 들어간다(D-CS-007). 화면이 남아 있다는 것이지 판단할 사람이 필요하다는 뜻은 아니다 — 06 공백 참고.

운영자가 위임을 주고 거둠여행자가 주고 거둔다.위임은 고객의 권한이다.

03알림 ①②③ — 하루가 어떻게 흘러가나

변화가 없어도 때가 되면 말을 건다. 세 알림 모두 Case를 만들지 않고 LLM을 부르지 않는다. 같은 안내는 두 번 보내지 않는다(바깥함 UNIQUE(tenant_id, topic, dedupe_key)).

시점언제무엇을 담나규칙
① 하루 시작 사용자가 정한 그날 시작 시각이다. 없으면 08:00이다. 첫 일정이 더 이르면 첫 일정 60분 전으로 당긴다. 오늘 일정 · 어제 이후 바뀐 일정 수 · 답을 기다리는 일정 전날 20시 안내는 껐다(travel.reminders.eve_hour: null). ①이 그 몫이다.
② 다음 일정 각 일정(이동 제외)이 시작할 때다. 「지금 / 다음」이다. 사이에 이동이 있으면 몇 시에 나서는지 미리 알린다. 그날 마지막 일정에는 보내지 않는다.
③ 이동 이동 항목이 시작하는 시각이다. (앞 판의 「15분 전」은 09-24에 지워졌다.) 어디로 · 언제 나서나 · 어떻게 가나 경로는 보낼 때 조회한다. 경로 사건을 못 읽으면 보내지 않고 fatal로 센다(결정 15). 계획한 수단에 사건이 걸려 있으면 held로 둔다. 이동 항목이 없는 여행(계획을 그대로 등록)에는 ③이 없다 — 06.
★답을 기다리는 일정 ②·③ 시점이다. 「출발하세요」 대신 「답을 기다리는 중 — 답이 없으면 원래 일정대로 진행」을 알린다. 답이 없어 닫히면 다음 틱부터 원래대로 안내한다.

04여행자·개인 에이전트 쪽 유스케이스

A.여행 전

설문 15번 「일정이 꼬이면」은 「비슷한 곳으로 바꿔줘」(replace)가 기본값이지만 활동의 날씨 사건 자동 적용은 이 답을 직접 고른 여행만이며 「먼저 물어봐줘」(ask_first)를 고를 수 있다. 16번 「여유」의 밀도 목표는 0.40 · 0.55 · 0.70이다. 판정에는 이 두 답만 쓰고 나머지는 받기만 한다.

#유스케이스주 행위자경로상태메모
U-01 여행 시작 설문 여행자·에이전트 POST /v1/trips의 constraints.survey · 웹 /v1/web/* 있음 판정에 쓰는 것은 15번 「일정이 꼬이면」·16번 「여유」뿐이다. 직접 답한 문항을 따로 남긴다(survey_answered) — 「일정이 꼬이면」을 직접 「비슷한 곳으로 바꿔줘」로 고른 여행만 자동 적용 대상이다(U-13). 틀린 설문은 422 invalid_survey.
U-02 바뀜 요청으로 일정 초안 만들기 에이전트 POST /v1/trips/plan 있음 첫 활동 09:00 · 마감 22:00(travel.day_window). 이제 이동 항목을 넣는다(출발 = 다음 시작 − 이동 − 여유). 이동 계산기가 꺼져 있으면 직선 어림값. 웹 「일정 짜 줘」(U-30)도 같은 생성기.
U-03 일정 등록·성립 판정 에이전트·여행자 POST /v1/trips · 웹 /v1/web/* 있음 불성립이면 422와 위반·완화 조건으로 답하고 아무것도 저장하지 않는다. 계획 읽기 확인 뒤 등록(U-29)도 같은 등록으로 들어간다.
U-04 바뀜 웹 사용자 식별 키 받기·다시 받기 여행자 POST /v1/web/session · /v1/web/session/rotate 있음 원문은 한 번만 보여 준다(서버는 SHA-256만). 다시 받으면 옛 키는 무효, 내 여행만 열린다. 발급에 사람 확인(Turnstile)과 주소당 시간 한도가 생겼다(늘 켜짐).
U-05 등록 즉시 계획서 링크 통지 시스템 → 여행자 바깥함 → 디스코드 있음 링크가 처음 나가는 자리다(change_notice). 등록 첫 통지에는 type 칸이 없어 웹이 채워 읽는다.
U-28 새로 계획 올리기 — 글 · 사진 · PDF · 워드 · 엑셀 여행자 POST /v1/web/trip-intakes 있음 파일 5개 · 글 20,000자까지. 받아서 뒤에서 읽고 접수 번호를 돌려준다. 사진은 한 줄씩 받아쓰고, 정해진 모양(시각 · 일차 · 예약번호)은 코드가 먼저 읽는다 — 매니저(코어)의 처리 단계다.
U-29 새로 읽은 값 확인 · 고치기 · 등록 여행자 GET /v1/web/trip-intakes/{id} · …/edits · …/confirm 있음 항목마다 근거(원문 줄)를 보여 주고 고치기 · 빼기 뒤 등록한다. 낡은 판을 고치면 409. 등록은 U-03과 같은 길. 이렇게 등록한 여행에는 이동 항목이 없다 — 06.
U-30 새로 「일정 짜 줘」 여행자 POST /v1/web/trip-intakes/{id}/plan 있음 생성기(U-02)로 짜서 등록한다. 읽은 일정은 고정으로 두고 빈 곳만 채우는 선택이 있다.
U-31 새로 알림 받을 곳 · 연락처 등록 여행자 GET · PUT /v1/web/profile · …/profile/discord/test 일부 서버 1단계만 있다 — 받아서 암호화 저장 · 가려서 조회 · 시험 발송. 실제 발송은 여전히 서버 설정의 웹훅 하나로 가고, 웹에는 웹훅 입력칸이 없다(이메일만) — 06.

06공백 — 코드 세션에 넘길 것

  1. ★「먼저 물어봐줘」 — 반쯤 풀렸다. 두 군데가 남았다.

    이제 상시 기본 감시(Case 경로) · 고객 신고 · 새벽 확인이 판정을 지난다(itinerary_actions.py · trip_desk.py · dawn_check.py). 남은 것: ①답이 없을 때 닫는 만료가 기본 감시에 없다(.expire(는 trip_watch.py 한 곳) ②기본 감시가 고정 일정을 건너뛴다(trip_watch_cases.py) — 그래서 고정 일정엔 안전 알림도 안 나간다.

  2. ★계획을 그대로 등록한 여행엔 ③ 이동 안내가 없다.

    생성기 일정은 풀렸다(이동 항목을 넣는다). 계획 읽기 → 등록(U-29)은 이동 항목을 만들지 않아(intake/assemble.py에서 이동 항목 생성 0건) ③이 안 나간다.

  3. ★알림 받을 곳이 실제 발송과 이어지지 않았다.

    사용자 연락처 저장 · 시험 발송은 있지만(U-31) 실제 발송은 서버 설정의 웹훅 하나다. 웹에는 웹훅 입력칸이 없다. 이메일을 알림용으로 쓰려면 저장 여부도 정해야 한다(지금은 복구용으로만 받고 저장하지 않음).

  4. 「서버를 끈다」가 없다.

    그대로다 — fatal을 세고 알리기만 한다. 확인 범위: app·scripts에서 종료 관련 낱말 다섯(os._exit 등) 검색. 다른 이름의 장치는 놓쳤을 수 있다.

  5. /health는 늘 {"status":"ok"}다.

    그대로다(고객 앱 · 운영 앱 둘 다).

  6. 여행자가 위임을 주고 거두는 창구가 없다.

    그대로다(U-27). 웹 src에서만 찾았다.

  7. 운영자용 화면이 남아 있다 — 반쯤 풀렸다.

    승인 · 위임 · 바깥함 화면은 그대로지만, 고객 포트에서 떼어 이 기계 안에서만 여는 운영 앱으로 옮겼다.

  8. 식당 방문 60 · 20분 전 안내(dining_*)가 상시 작업에 안 붙어 있다.
