여행 Team — 무엇을 어디서 읽는가

2026-09-09 · 팀별 데이터 연결 아키텍처 · 모든 수치는 실행·실호출로 잰 값이다

한 줄

여섯 팀은 계약·가드·흐름이 완성돼 있었고 데이터 원본이 하나도 없었다. 이번에 원본 6종 중 4종(67%)이 붙었고, 실 DB + 실 외부 API 로 8건 중 6건(75%)이 고객 답변까지 완주한다.

막고 있던 것은 외부 API 가 아니었다

read.booking·read.place·read.supplier 셋의 원본은 우리 DB다. 그런데 여행 테이블이 하나도 없어서(19테이블 중 0개) 모든 Case 가 첫 도구에서 escalate 했다. 외부 키를 기다릴 이유가 없는 자리였다.

1. 층 구조 — Team 은 HTTP 를 모른다

Team          read.weather 라는 이름 하나만 안다
  ↓           (manifest.allowed_tools 에 적힌 것 밖은 못 부른다)
ReadToolbox   이름 → 함수 표. tenant·customer 범위를 여기서 건다
  ↓           예산(max_steps)·중복·권한을 여기서 본다
app/infrastructure/travel/   HTTP 는 여기서만 난다
  ↓
Open-Meteo / TourAPI / ODsay / 우리 DB

공급자를 갈아끼워도 Team 은 안 바뀐다. 주입은 조립이 한다 — ReadToolbox(travel=...) 의 기본값이 None 이라 안 넣으면 바깥으로 안 나간다. 테스트가 조용히 네트워크를 타는 사고를 구조로 막았다.

3. 팀별 — 무엇을 읽고 무엇을 판정하나

Activity MVP capability 3 204줄 종단 확인됨

활동 그 자체가 대상이다 — 골프 티타임·수상레저뿐 아니라 경복궁 관람처럼 시각이 정해진 활동도 포함한다.

booking ─→ policy ─→ (capability 분기)
                      ├ check_cancelable : 기한·위약금율   ← 계산
                      ├ check_feasible   : 인원·정원 → place → weather
                      └ propose_change   : 제안 (승인 대기)

기상은 「날씨가 판정에 들어가는 활동」에만 본다. place.weather_sensitive 가 참일 때만 부르고, 모르면 안 본다 — 실내 활동에 기상 판정을 걸면 틀린 이유로 판정이 흔들린다.

★날씨로 「불가」를 만들지 않는다

강수확률이 얼마부터 취소·순연인지는 운영 규정이 정할 일이다. 가드레일의 수치(60% / 40km/h)는 판정 기준이 아니라 주의 문구 기준이고, 측정에서 나온 값이 아니라 우리가 고른 값이다. 그걸로 확정 답을 만들면 근거 없는 확정이 된다. 그래서 강수확률 90%여도 판정은 「성립」이고, 답변이 기준 미확인을 스스로 말한다.

실제 답변 (2026-09-09 실행, 실 Open-Meteo)

확인한 범위에서는 성립합니다(시작까지 29.9시간).
예보상 2026-09-11T04:00 기준 강수확률 0%, 풍속 6.3km/h입니다
(예보이며 현장 확인이 아닙니다).

근거: read.booking · read.policy · read.place · read.weather
Booking Handoff MVP 다음 capability 3 94줄 종단 확인됨

이름이 Execution 이 아니라 Handoff 인 것이 핵심이다. 기본 동작은 인계다 — 바꿔야 할 것을 정리해서 넘긴다.

booking ─→ verify        : 공급자 원장과 대조 (read.supplier)
        └→ prepare_*     : 규정 확인 → ActionProposal (WAIT_FOR_APPROVAL)

supplier_bookings 를 일부러 따로 둔 이유. 한 테이블에 두면 대조할 상대가 사라져 booking.verify 가 자기 자신과 비교하는 꼴이 된다. 어긋나는 것이 정상이고, 어긋남을 찾는 것이 이 팀의 일이다.

실행 결과 (BK-GOLF-DRIFT — 우리 confirmed / 공급자 cancelled)
→ "예약 상태가 공급자 기록과 다릅니다. 사람이 확인해야 합니다."
  warnings: 우리 기록과 공급자 기록이 어긋난다
Dining MVP capability 2 83줄 종단 확인됨

「오늘 여는지」가 아니라 「그 일정 시각에 여는지」를 본다.

booking ─→ place ─→ ├ check_open       : open_at_slot (confirmed_at 없으면 「모름」)
                     └ check_conditions : dietary / dietary_absent / 둘 다 아니면 모름

★여기서 결함 하나가 나왔다

이 팀은 read.place 를 case_id 로 부르고 있었다. 장소 조회의 열쇠는 place_id 이고 그건 예약에 들어 있다 — Case 번호로는 어느 장소인지 알 수 없다. 실 DB 종단 실행에서 항상 「모름」으로 떨어져 드러났다. Activity 는 처음부터 맞게 하고 있었다 — 같은 규율이 팀마다 갈렸다.

Mobility MVP capability 3 80줄 종단 미확인 — 키 대기

여유 시간 ≥ 필요 시간인지 계산한다. LLM 을 안 부른다.

route ─→ transit ─→ 여유(gap) vs 필요(duration) 비교 + 막차 확인

문의와 사건을 가른다. _INCIDENT_MARKERS 6개(놓쳤·못 탔·끊겼·지연됐·결항·운행 중단)만 잡고, 신호가 없으면 기본 동작(조회)에 맡긴다. 커머스에서 이 훅이 넓어 "지연 기준이 어떻게 되나요"(문의)까지 사건으로 잡은 적이 있다.

여섯 중 유일하게 종단 실행을 못 했다. read.route·read.transit 둘 다 ODsay 키에 걸려 있다.

Lodging · Flight 등록만 capability 각 1 73줄 (클래스 공유)

조회만 하고 어떤 변경 제안도 만들지 않는다. max_steps=2.

★껍데기 Team 은 혼란을 만든다. 커머스의 voc_store_manager 가 계약만 있고 동작이 없어 "이 팀은 뭘 하나" 를 매번 다시 확인해야 했다. 그래서 첫 줄에 「등록만·로직 없음」을 적어 뒀다.

Lodging 은 실행으로 확인했다(BK-HOTEL → completed, 제안 0건). Flight 는 시드에 없어 확인하지 못했다 — 같은 클래스를 쓰므로 같게 돌 것으로 예상하지만 잰 것이 아니다.

4. 공통 기반 _base.py — 규율을 한 곳에

커머스 6팀은 계약 처리 코드가 315줄 복붙돼 있었고 가드가 팀마다 달랐다:

가드커머스여행
team_id — 남의 일이면 넘긴다1/6 = 17%6/6 = 100%
capability — 못 하는 일은 시작 안 한다4/6 = 67%6/6 = 100%
degraded — 근거가 깎였으면 확정 안 한다5/6 = 83%6/6 = 100%

여기에 둘이 더 붙는다.

  • _read() 가 budget=max_steps 를 항상 넘긴다. 각 팀이 넘기게 두면 빠뜨리는 곳이 생긴다 — max_steps 가 선언만 되고 아무도 안 읽던 커머스와 같은 모양이 된다.
  • _unknown() 이라는 별도 갈래. 도구가 None 을 주면 "없다"가 아니라 "확인 못 했다"이고, failure_code=unknown_<무엇> 으로 escalate 한다. NULL 을 「없음」으로 읽으면 결함이 자리만 옮긴다.

5. 어댑터의 규율 넷

  1. 못 가져오면 None — 기본값·평균값·지난번 값으로 메우지 않는다
  2. 성공하면 confirmed_at·source 를 반드시 함께 준다
  3. HTTP 상태만 보고 성공을 판정하지 않는다
  4. 왜 못 가져왔는지를 센다 — 조용한 스킵을 만들지 않는다

★③ 은 지어낸 걱정이 아니다 (2026-09-09 실측)

ODsay  키 없이 호출 → HTTP 200
       {"error":[{"code":"500","message":"[ApiKeyAuthFailed] ..."}]}

data.go.kr 계열 → HTTP 401 SERVICE_KEY_IS_NULL   (정직하게 답한다)

raise_for_status() 만 믿었다면 인증 실패가 성공으로 지나가 read.transit 이 빈 값을 돌려주고, Team 은 그걸 「확인했다」로 읽는다. 공급자마다 다르므로 본문까지 봐야 한다.

★종단 실행이 잡은 결함 2건 — 단위 테스트가 못 잡았다

① 근거가 덮어써졌다. _evidence() 가 매번 컨텍스트에서 다시 시작해 두 번째 호출이 첫 번째를 지웠다. 근거 4건이 1건으로 줄어 있었다. 있던 검사가 전부 도구를 한 개만 쓰는 경로여서 안 잡혔다 — 하나짜리에서는 덮어써도 결과가 같다.

② Dining 이 장소를 case_id 로 조회. Mock 이 인자를 안 보고 값을 돌려줬기 때문에 단위 테스트가 초록이었다.

★근거 소실은 가벼운 결함이 아니다. 근거 없는 문장은 답변에 넣지 않는다가 이 제품의 첫째 규칙인데, 그 근거가 조용히 사라지고 있었다.
