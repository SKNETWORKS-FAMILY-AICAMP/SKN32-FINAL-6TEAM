1. 팀원에게 먼저 전달할 사항

새 폴더 구조를 포함한 통합본을 기준으로 작업을 이어갑니다. 옛 경로 파일을 다시 만들거나 개별 커밋 몇 개만 골라 합치면 연결 코드가 빠질 수 있습니다.

해야 할 일확인할 결과
작업 중 변경을 별도 커밋 또는 임시 보관한 뒤 최신 develop을 합칩니다.기존 작업이 보존되고 새 구조가 들어옵니다. 충돌은 파일 역할별로 해결합니다.

팀 내부 기능은 팀 폴더에 두고, 공통 부품에서는 등록된 연결 함수를 사용합니다.다른 팀 내부를 직접 import하지 않습니다.
배포 전 DB 변경·조립 코드·화면 코드를 함께 반영합니다.관리자 기능은 226_admin_operations.sql과 별도 운영 앱 설정이 필요합니다.

팀 소스 반영 순서: role-manager → 배포 확인 → develop. 오늘 반영본은 bf42b659이며, 기존 전체 구조 통합 기준은 61cc9221입니다. 다른 진행 세션의 미완료 변경은 이 반영본에 포함하지 않았습니다.

4. 끼움 자리 — 부품이 우리 팀을 부르는 방식이 바뀌었습니다

여기가 이번 변경에서 가장 중요한 대목입니다. 실무에서는 의존성 역전(DIP) · 포트와 어댑터라고 부릅니다.

전 — 부품이 팀 이름을 알았다 
# components/watch/dawn_check.py
from ...instances.dining.ledger \
     import dining_states

states = dining_states(conn, tenant, slots)

요식업 팀을 빼면 감시가 import 단계에서 죽는다

후 — 부품은 자리만 안다 
# components/watch/dawn_check.py
from ...components.team_hooks \
     import dining_ledger

states = dining_ledger.states(conn, tenant, slots)

요식업 팀이 없으면 None(모름) — 안 죽는다

꽂는 쪽은 조립 한 군데 — app/composition.py 
def wire_domain_teams():
    dining_ledger.register(add_nearby=…, states=…, state=…, find_by_name=…)
    legs.register(leg_planner=…, disruptions_from_events=…, walk_limit_m=…)
    similarity.register(score=…, preference_of=…, distance_first=…)
    watch_planners.register("dining", …)   # 엑티비티 · 이동도 같은 모양

자리 일곱

자리부품이 묻는 것꽂는 쪽안 꽂으면
team_hooks/legs이동 시간 · 노선 · 사고 · 도보 상한이동 팀계산기 None(어림값)
team_hooks/dining_ledger근처 식당 · 시간대 영업 판정 · 이름 찾기요식업 팀판정 None(모름)
team_hooks/similarity활동 유사도 · 설문 선호 · 거리 우선엑티비티 팀점수 None(거리만)
team_hooks/watch_planners항목 종류별 감시 판정세 팀None — 그 종류는 안 함

progress_hook진행 알림 포장(SSE)실시간 진행[] — 실시간 화면만 없음
★ 안 꽂혔을 때의 답은 「새로 만든 기본값」이 아닙니다. 일곱 모두 그 팀 · 기능이 조립에 없을 때 부품이 원래 가던 길 그대로입니다. 영업 여부를 모르면서 「열었다」로 답하지 않고, 다른 팀 계산으로 대신하지도 않습니다 — 값을 지어내지 않는다는 규칙 그대로입니다.

미등록 반환값은 구현의 연결 경계 설명입니다. 운영 환경에서 필수 값이 빠져도 괜찮다는 제품 정책을 뜻하지 않습니다. 필요한 기능이 등록되었는지는 조립·통합 시험에서 별도로 확인합니다.

5. 오늘 추가한 실제 기능

영역바뀐 동작팀원이 유지할 경계
관리자 웹앱사용자 차단·채팅 한도와 예외·문의 답변·공지·점검·외부 API 상한 등 13개 명령을 연결했습니다. 기존 설정·보관·접수 근거 화면도 연결했습니다.운영 앱에만 관리자 경로를 등록합니다. 고객 쿠키·사용자 키로 운영자 로그인하지 못합니다.
고객 웹앱본인 문의 작성·답변 조회와 공지·점검 배너를 연결했습니다.문의 조회는 본인 범위만 허용합니다. 연결 실패를 데모 자료로 바꾸지 않습니다.
요식업 추천낮 감시·대체 식당·완화 후보·현재 위치 추천에 기존 앞뒤 동선 검사를 연결했습니다.공통 이동 연결 함수를 사용합니다. 현재 위치→식당은 도보 어림, 먼 다음 일정은 상위 3개 후보 재측정 범위를 유지합니다.

관리자 화면의 CPU·메모리·경로별 지연 등 아직 수집하지 않는 값은 미계측으로 표시합니다. 안전 감시 주기를 비용에 따라 느리게 바꾸는 편집은 비활성화했습니다. 운영 계정과 접속 정보는 이 공유 문서에 싣지 않습니다.

전달하는 내용은 item_id, at, detected, categories와 여러 일정의 항목 목록입니다. 외부 원자료 전체를 담는 계약은 아닙니다. 엑티비티·요식업은 이 정보를 받고 공통 도구로 상태를 재확인한 뒤 대처안을 판단합니다.

3분마다 평가한다는 말은 모든 외부 API나 LLM을 3분마다 부른다는 뜻이 아닙니다. 정상 일정은 담당 팀을 호출하지 않고, 외부 소스별 캐시와 중복 억제를 사용합니다.

식당 영업 확인: 현재 동작과 다음 연결을 구분합니다

새벽 확인은 연결되어 있습니다. 60분·20분 전 확인 부품은 있으나 실제 작업 일꾼 호출·조회 어댑터 연결은 아직 남아 있습니다. 이번 반영에서 유료 자동 조회 주기를 켜지 않았습니다.

추천은 새벽 1회 + 식당으로 출발하기 전 1회 + 휴무 제보·일정 변경 같은 새 사건 때 추가 확인입니다. 예를 들어 식당까지 40분 걸리면 방문 20분 전 확인은 이미 출발한 뒤입니다. 두 번 조회만으로 갑작스러운 휴무를 전부 잡는다고 보장하지 않습니다.

카카오 장소 검색 응답만으로 영업시간·임시휴무를 확인할 수 없습니다. 제공처 응답 범위와 조회 비용은 감시·영업 확인 근거 보고서에 정리했습니다.

7. 합친 뒤 검증하는 순서

  1. 경로·칸 경계 시험을 실행해 팀 간 직접 import와 공통 부품의 팀 내부 접근을 확인합니다.
  2. 조립된 상태에서 단위·보안·계약 시험을 실행합니다. 팀 함수를 대체할 때는 공통 부품의 옛 이름이 아니라 팀 쪽 실제 함수에 적용합니다.
  3. 전용 시험 DB에 스키마와 필요한 시험 자료를 준비한 뒤 통합 시험을 실행합니다. 고객 DB를 시험 초기화 대상으로 사용하지 않습니다.
  4. 고객·관리자 화면 각각 타입·린트·단위·빌드·mock 서버 시험을 실행하고, 배포 후 실제 응답은 따로 확인합니다.

일정 생성기 시험은 공용 식당 자료량에 따라 달라지지 않도록 시험용 후보를 고정합니다. 검색용 여행 코퍼스가 필요한 RAG 통합 시험은 자료와 로컬 임베딩 조건을 별도로 갖춰야 합니다. CI의 해당 제외를 전체 RAG 통과로 읽지 않습니다.

9. 반영 완료 범위와 남은 일

구분상태
팀 소스 통합전체 구조 기준 61cc9221에 이번 관리자·고객 지원·요식업 연결 53개 변경 파일을 bf42b659로 반영했습니다. role-manager와 develop에 같은 커밋을 푸시한 것을 확인했습니다.
배포같은 반영본의 API·고객 웹·작업 일꾼·DB·관리자 컨테이너 5/5 실행을 확인했습니다. 관리자 앱은 고객 앱과 별도 프로세스·컨테이너입니다.
기존 라우팅 재배분등록된 팀이 받는 종류로 한 번 다시 배분하고 실제 등록부로 확인하는 구조를 유지합니다. v2에서는 실제 모델의 재배분 종단 시험을 새로 실행하지 않았습니다.
