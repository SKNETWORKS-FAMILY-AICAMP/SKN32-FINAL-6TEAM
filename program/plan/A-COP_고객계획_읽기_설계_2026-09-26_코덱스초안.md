# guguroute 고객 여행계획 범용 수집·정규화 설계서

기준일: 2026-09-26  
대상: 서울, 최대 7일, 최대 4인  
목표 출시일: 2026-10-26

## 1. 결론 먼저

권장 방식은 **“증거를 보존하는 멀티모달 수집 파이프라인 + 규칙 기반 확정 + 단일 고객 확인 화면”**이다. 채팅·문서·이미지·링크를 먼저 위치 정보가 붙은 텍스트 블록으로 만들고, 개인정보를 토큰화한 뒤 로컬 LLM은 원문에 있는 사실의 구조화에만 사용한다. 날짜·시각·좌표·예약번호·장소명은 원문 복사, 설정된 일정 규칙, 로컬 DB, TourAPI, Places 조회 중 하나에서만 가져온다. 장소는 `정확 일치 → 별칭 → bge-m3 임베딩 → 실시간 TourAPI → 유료 Places` 순서로 하나를 선택하고 근거와 확신도를 남긴다. 불확실해도 후보가 있으면 가장 근거가 강한 하나를 보여주되, 근거가 전혀 없으면 치명 결함으로 중단한다. 고객이 “이렇게 읽었습니다” 화면에서 고친 뒤에만 `CreateTrip`을 만들며, 등록은 현재와 동일하게 `_create_trip` 한 곳을 통과시킨다. `_create_trip`은 이미 참조 검증과 `check_itinerary` 판정을 거쳐 저장하고 알림까지 생성하는 유일한 본문이다(`app/modules/travel_ops/trip_api.py:349-414`, `app/modules/travel_ops/trip_api.py:450-455`).

## 2. 설계 원칙

1. **원본 → 해석 → 확정값을 분리한다.**  
   LLM 출력이 바로 `CreateTrip`이 되면 안 된다. 먼저 원문 위치를 가리키는 `ExtractedClaim`을 만들고, 조회·규칙으로 보완한 `TripDraft`를 거친다.

2. **LLM은 값 생성기가 아니다.**  
   LLM은 문서 구조, 항목 종류, 원문 span 연결을 담당한다. 날짜·시각·금액·예약번호·고유명사는 반드시 원문 span 또는 조회 결과와 일치해야 한다. 기존 `trip_intake.validate`도 숫자와 상품명이 고객 문장에 실제로 존재하는지 재검증한다(`app/modules/travel_ops/trip_intake.py:63-102`). 같은 패턴을 계획 수집으로 확장한다.

3. **RAG와 장소검색을 구분한다.**  
   RAG는 취소·접근성·아동 동반 같은 정책 설명에만 쓴다. 장소명·좌표·가격을 RAG에서 가져오지 않는다. 현행 planner도 RAG는 근거 설명일 뿐 후보 선택을 바꾸지 않는다고 명시한다(`app/modules/travel_ops/planner.py:447-460`).

4. **모든 필수값에는 대체 경로가 있다.**  
   원문 → 같은 제출물의 다른 자료 → 웹 세션/온보딩 → 로컬 DB → 공공 실시간 조회 → 유료 조회 → 고객의 단일 사실 입력 순서다. 끝까지 값이 없으면 `fatal`이고 등록하지 않는다.

5. **등록은 고객 확인 뒤 한 번만 한다.**  
   웹 고객은 별도 에이전트 키 없이 새 intake API를 사용하고, 최종 확정 시 서버 내부에서 `_create_trip`을 호출한다. 현재 `/v1/web/trips`가 고객 ID를 세션에서 주입한 뒤 `CreateTrip`을 검증하고 `_create_trip`을 호출하는 보안 경계는 유지한다(`app/modules/travel_ops/trip_api.py:722-734`).

6. **상태의 정본은 등록 후 여행계획서 링크다.**  
   링크는 열 때마다 최신 버전을 보여주도록 설계돼 있고(`app/modules/travel_ops/plan_link.py:8-10`), 알림에도 자동으로 붙는다(`app/modules/travel_ops/itinerary.py:265-288`).

```mermaid
flowchart LR
    A[채팅·파일·링크] --> B[형식 판별·텍스트화]
    B --> C[PII 토큰화·구조 추출]
    C --> D[장소·날짜·예약 해석]
    D --> E[규칙으로 빈칸 채우기]
    E --> F[동일 판정기 실행]
    F --> G[고객 확인·수정]
    G --> H[_create_trip 단일 등록]
    H --> I[버전·감시·알림]
```

## 3. 입력 분류와 첫 처리

모든 입력은 하나의 `intake_id` 아래 여러 `intake_source`로 묶는다. 여러 파일과 채팅이 섞여도 따로 해석한 뒤 증거 단위로 합친다.

| 입력 | 형식 판별 | 첫 처리 | 실패 시 대체 |
|---|---|---|---|
| 짧은 채팅 요청 | UTF-8 텍스트 | 문장·목록 분리, 수신 시각과 KST를 함께 기록 | LLM 실패 시 날짜·인원·기간·장소 키워드 규칙 추출 |
| 붙여넣은 일정 | 텍스트 | 줄·표·화살표·시간 패턴을 보존한 블록화 | 줄 파서 실패 시 LLM 구조 추출 |
| 텍스트 PDF | MIME과 magic bytes, 페이지별 텍스트 유무 | 글자·페이지·bbox를 함께 추출 | 글자량이 적거나 깨지면 스캔 PDF 경로 |
| 스캔 PDF | PDF 페이지 렌더링 | 페이지별 OCR 후 표·열 순서 복원 | OCR 저신뢰 영역만 vision LLM, 그래도 안 읽히면 고객에게 해당 페이지만 재업로드 요청 |
| DOCX | ZIP/OpenXML 구조 확인 | 문단·표·헤더·푸터·하이퍼링크를 순서대로 추출 | 손상 시 LibreOffice 기반 PDF 변환 후 PDF 경로 `[추정]` |
| XLSX | ZIP/OpenXML 구조 확인 | 시트별 셀 값·병합 영역·행/열·표시 형식 추출. 수식은 저장된 계산 결과를 읽고 원 수식도 증거에 보존 | 계산 결과가 없으면 LibreOffice 재계산 `[추정]`; 실패하면 해당 셀을 치명 결함으로 표시 |
| 이미지·사진·캡처 | 실제 이미지 MIME, EXIF 방향 | 회전·왜곡 보정 → OCR → 레이아웃 블록화 | 저신뢰 블록만 redacted vision 입력 |
| 예약 확인 메일 | `.eml` MIME 또는 붙여넣은 헤더/본문 | 발신자·제목·본문·첨부를 분리하고 예약번호·시각·업체 문구를 원값으로 토큰화 | HTML 본문 실패 시 plain text, 없으면 첨부파일 |
| 바우처 | PDF/이미지 경로 + 예약 문서 분류 | 업체명·예약번호·이용일시·인원·상태를 추출 | 업체명/일시 중 하나도 확보하지 못하면 치명 결함 |
| 공개 블로그 링크 | `http/https`만 허용, DNS/IP 재검증 | HTML 본문과 표·제목·게시 시각 추출 | 브라우저 렌더링 `[추정]` → 실패 시 PDF 저장본/붙여넣기 요청 |
| 공개 Notion 링크 | 공개 여부 확인 | 공개 HTML 또는 export 결과 추출 | 로그인·권한 필요 페이지는 `[미확보]`; 고객에게 export/PDF 요청 |
| 혼합 입력 | 각 source별 독립 판별 | 동일 날짜·장소·예약번호를 연결하되 출처별 증거는 유지 | 충돌 우선순위로 하나 선택하고 확인 화면에 충돌 표시 |

형식은 확장자가 아니라 magic bytes와 MIME으로 결정한다. 파일 크기·페이지·압축 해제 크기 제한은 `[추정]` 초기값으로 파일 20MB, PDF 100쪽, XLSX 20개 시트로 두고 평가 후 조정한다.

웹은 현재 12,000자 textarea만 제공하고(`frontend/apps/web/src/features/trip-registration/trip-registration.tsx:83-96`), live gateway는 아직 연결되지 않았다(`frontend/apps/web/src/lib/gateway.ts:10-27`). 또한 현재 `app/`에는 `UploadFile`, `File(`, `multipart` 사용처가 없다. 따라서 파일 수집 API와 live gateway 구현이 모두 새로 필요하다.

## 4. 단계별 파이프라인

### 4.1 접수·텍스트화

**입력:** 채팅, URL, 파일  
**사용:** 규칙·전용 파서·OCR, 필요한 영역에만 vision LLM  
**출력:** 원본과 위치를 보존한 `SourceBlock[]`

```json
{
  "intake_id": "in_01",
  "received_at": "2026-09-26T14:20:00+09:00",
  "sources": [
    {
      "source_id": "src_pdf_1",
      "kind": "pdf",
      "sha256": "...",
      "mime": "application/pdf"
    }
  ],
  "blocks": [
    {
      "block_id": "b17",
      "source_id": "src_pdf_1",
      "locator": {
        "page": 2,
        "bbox": [83, 214, 492, 251]
      },
      "text_masked": "10:00 경복궁 → 12:00 토속촌",
      "ocr_confidence": 0.96
    }
  ]
}
```

- PDF·이미지는 페이지와 bbox를 보존한다.
- DOCX는 `paragraph_index` 또는 `table,row,column`.
- XLSX는 `sheet`와 `cell_range`.
- HTML은 URL, DOM selector, 문자 offset을 보존한다.
- 텍스트는 줄 번호와 문자 offset을 보존한다.
- 원본 파일은 암호화 저장하고 모델에는 직접 보내지 않는다.

**대체 경로:** 전용 파서 → OCR → redacted vision → 고객 재제출. 모든 경로가 실패하면 `fatal_unreadable_source`.

한국어 사진·손글씨 OCR 정확도는 `[미확보]`다. `gemma4:12b`가 현재 로컬 기본 모델인 것은 확인되지만(`app/core/settings.py:54-64`), 한국어 여행 문서 vision 품질은 평가 전 제품 보장에 넣지 않는다.

### 4.2 개인정보 가림과 구조 추출

OCR 직후 전화번호·이메일·결제 식별자·예약번호·이름 후보를 찾아 안정적인 토큰으로 교체한다.

```json
{
  "masked_text": "예약자 <PERSON_1>, 예약번호 <BOOKING_1>, 10월 3일 15:00",
  "secure_tokens": {
    "<BOOKING_1>": {
      "encrypted_value_ref": "secret_92",
      "source_span": "b31:4-12"
    }
  }
}
```

현재 공통 masking은 API 키·결제 ID·전화번호·카드번호·이메일만 처리한다(`app/core/redaction.py:29-35`). 예약번호·사람 이름·주소와 이미지 영역 가림은 새로 추가해야 한다. 기존 자유문장 신고 추출기는 메시지를 그대로 `chat.json`에 넘기므로(`app/modules/travel_ops/trip_intake.py:105-107`), 이 함수를 계획 수집에 직접 재사용하지 말고 `masked_text`만 전달하는 래퍼를 둔다.

LLM은 다음 중 하나로 입력을 분류하고, 각 값에 `evidence_ids`를 붙인다.

- `plan_request`: “다음 주 금토 서울 일정 짜줘”
- `existing_itinerary`: 이미 순서·날짜·시각이 있는 일정
- `reservation_confirmation`: 메일·바우처
- `reference_material`: 블로그·추천 목록
- `mixed`

```json
{
  "document_role": "mixed",
  "facts": {
    "city": {
      "value": "서울",
      "evidence_ids": ["ev1"],
      "method": "verbatim"
    },
    "party_size": {
      "value": 4,
      "evidence_ids": ["ev2"],
      "method": "phrase_rule"
    }
  },
  "item_mentions": [
    {
      "order": 1,
      "day_label": "첫날",
      "time_text": "10시",
      "place_text": "경복궁",
      "booking_token": null,
      "evidence_ids": ["ev3"]
    }
  ]
}
```

추출 후 규칙 검증은 다음을 강제한다.

- 원문 값은 해당 evidence span에 실제로 존재해야 한다.
- 날짜·시간·금액·인원·예약번호는 원문 정규화 이외의 변환을 금지한다.
- “넷이서”처럼 언어 규칙으로 `4`가 된 값에는 `phrase_rule`을 기록한다.
- LLM이 원문에 없는 고유명사를 반환하면 폐기한다.
- 상충하는 두 값이 있으면 하나를 우선순위로 선택하지만 `conflict=true`를 유지한다.

**대체 경로:** LLM JSON 실패 → 한 번의 JSON repair → 날짜·시각·인원·예약 패턴 파서 → 그래도 구조가 없으면 치명 결함. 근거 없는 LLM 결과로 대체하지 않는다.

### 4.3 날짜·일차·예약 해석

절대 날짜는 다음 우선순위로 하나를 정한다.

1. 고객이 확인 화면에서 직접 수정한 값
2. 예약 확인서의 이용일
3. 일정 본문에 적힌 날짜
4. 같은 intake의 여행 시작일
5. 웹 온보딩/세션에서 확인된 출발일
6. 상대 날짜를 `received_at`의 KST 달력으로 계산
7. 없음: 고객에게 “첫날 날짜” 하나만 입력받고 그 전에는 등록 중단

예를 들어 2026-09-26 KST에 접수된 “다음 주 금토”는 달력 규칙으로 날짜 두 개를 계산하고 다음과 같이 남긴다.

```json
{
  "value": "2026-10-02",
  "method": "relative_date_rule",
  "rule": "next_week_friday",
  "inputs": {
    "received_at": "2026-09-26T14:20:00+09:00",
    "timezone": "Asia/Seoul",
    "source_text": "다음 주 금토"
  }
}
```

“첫날·둘째 날”만 있고 기준 날짜가 전혀 없으면 임의 날짜를 만들지 않는다. 이것은 선택할 후보 자체가 없는 상태이므로 `fatal_missing_date_anchor`다.

예약 문서는 일정보다 우선한다. 동일 장소가 일정표에는 14:00, 바우처에는 15:00이면 15:00을 선택하고 충돌 배지를 보여준다. 예약번호는 토큰 상태로 모델을 통과한 뒤 서버에서 원값으로 복원한다.

### 4.4 장소 해석

상세 알고리즘은 5절에 기술한다. 출력은 후보 목록이 아니라 **선택된 하나**다.

```json
{
  "mention": "그 한강 카약 하는 데",
  "selected": {
    "entity_type": "place_catalog",
    "entity_id": "catalog-...",
    "name": "선택된 실제 업체명",
    "kind": "activity",
    "lat": 37.0,
    "lon": 126.0
  },
  "method": "embedding_then_realtime",
  "confidence": "low",
  "score": 0.81,
  "evidence_ids": ["ev9"],
  "lookup_evidence": {
    "source": "tour_api",
    "content_id": "...",
    "observed_at": "2026-09-26T14:20:08+09:00"
  }
}
```

예시의 이름·좌표 값은 설명용 형식이며 실제 값은 조회 결과만 사용한다.

### 4.5 빈칸 채우기와 초안 생성

두 흐름을 분리한다.

#### A. “일정을 짜줘” 요청

추출된 `city/start_date/days/party_size/constraints/preferences`를 현행 `planner.plan_trip` 서비스 함수에 전달한다. 웹이 에이전트 전용 HTTP 엔드포인트를 호출하는 것이 아니라 동일 프로세스 내부 서비스 계층을 호출해야 한다. 현재 `/v1/trips/plan`은 `trip:write`가 필요하지만(`app/modules/travel_ops/trip_api.py:458-487`), 실제 계획 생성 로직은 `planner.plan_trip`으로 분리돼 있다(`app/modules/travel_ops/planner.py:891-918`).

planner는 서울·7일·4인 범위를 검증한다(`app/modules/travel_ops/planner.py:136-146`). LLM에는 후보 번호만 주고, 후보 밖 이름은 버리는 구조도 그대로 재사용한다(`app/modules/travel_ops/planner.py:495-509`).

#### B. 이미 작성된 일정

고객이 적은 순서·날짜·시각·예약은 보존한다. planner가 전체를 다시 짜지 않는다.

시각이 없는 항목은 다음 순서로 채운다.

1. 같은 항목의 예약 시각
2. 표의 시간 열 또는 주변 문장
3. 앞뒤 항목과 영업시간을 입력으로 한 결정적 scheduler
4. planner의 설정된 하루 창·활동/식사 길이 규칙
5. 배치할 수 없음: `fatal_unschedulable`

현재 planner도 모델이 아닌 코드가 시작·종료 시각을 부여한다(`app/modules/travel_ops/planner.py:574-609`). 활동 90분·식사 60분·이동 여유 등 현재 값은 `app/modules/travel_ops/planner.py:65-82`에 있으나, intake에서 재사용할 때는 하드코딩을 복제하지 말고 guardrail 설정으로 이동한다.

```json
{
  "draft": {
    "title": "서울 2026-10-02 여행",
    "locale": "ko",
    "party_size": 4,
    "constraints": {
      "with_child": true
    },
    "places": [],
    "items": [
      {
        "seq": 1,
        "kind": "activity",
        "title": "경복궁",
        "place": "p1",
        "starts_at": "2026-10-02T10:00:00+09:00",
        "ends_at": null,
        "detail": {
          "provenance": {
            "title": ["ev3"],
            "starts_at": ["ev3"]
          }
        }
      }
    ],
    "routes": {}
  },
  "completion": {
    "title": "rule:city_start_date",
    "party_size": "source:ev2",
    "starts_at": "source:ev3"
  }
}
```

`request_id`는 서버가 생성하고, `customer_id`는 웹 세션에서 주입하며, locale은 세션에서 가져온다. title이 없을 때의 `서울 YYYY-MM-DD 여행`은 조회된 도시·날짜를 조합한 규칙값이지 LLM 생성값이 아니다.

### 4.6 판정

`CreateTrip`으로 바꾸기 전에 현재와 동일한 `check_itinerary`를 실행한다.

```json
{
  "status": "needs_customer_review",
  "violations": [
    {
      "code": "overlap",
      "items": [2, 3],
      "reason": "두 일정의 시간이 겹친다",
      "remedy": "뒤 일정을 앞 일정 종료 뒤로 이동한다"
    }
  ],
  "unknown_checks": [
    {
      "item": 4,
      "field": "opening_hours",
      "reason": "조회 결과 없음"
    }
  ]
}
```

현행 판정기는 다음을 확인한다.

- 종료 시각이 시작보다 빠른지(`app/modules/travel_ops/itinerary_checks.py:85-90`)
- 일정 중첩과 이동시간(`app/modules/travel_ops/itinerary_checks.py:124-148`)
- 영업시간·브레이크타임(`app/modules/travel_ops/itinerary_checks.py:99-120`)
- 결제수단과 예산(`app/modules/travel_ops/itinerary_checks.py:157-175`)

다만 현재 판정기는 값이 없는 항목을 통과시킨다(`app/modules/travel_ops/itinerary_checks.py:8-20`). intake 앞단에서는 이를 “확인 완료”로 표시하면 안 된다. 대신 다음처럼 구분한다.

- `pass`: 필요한 값이 있고 판정 통과
- `unknown_noncritical`: 선택 사항만 모름
- `needs_confirmation`: 선택한 낮은 확신도 값이 있음
- `fatal`: 등록 또는 지속관리에 필수인 값이 없음
- `violation`: 값은 있으나 일정이 불가능함

규칙이 자동으로 고칠 수 있는 위반은 한 번 고치고 다시 판정한다. 예약 시각·고객 고정 항목은 자동 이동하지 않는다.

### 4.7 고객 확인 후 등록

고객 확인 결과는 전체 문서를 다시 추출하는 것이 아니라 field patch로 반영한다.

```json
{
  "intake_id": "in_01",
  "base_revision": 3,
  "confirmed_fields": ["trip.start_date", "items.1.place", "items.1.starts_at"],
  "patches": [
    {
      "path": "items.2.starts_at",
      "value": "2026-10-02T15:00:00+09:00",
      "evidence": {
        "type": "customer_confirmation",
        "confirmed_at": "2026-09-26T14:25:00+09:00"
      }
    }
  ]
}
```

서버는 patch 후 장소 해석과 판정을 다시 실행하고 최종 `CreateTrip`을 생성한다.

```json
{
  "request_id": "intake:in_01:rev4",
  "customer_id": "<웹 세션에서 주입>",
  "title": "서울 2026-10-02 여행",
  "locale": "ko",
  "party_size": 4,
  "constraints": {},
  "places": [],
  "items": [],
  "routes": {}
}
```

최종 호출은 `_create_trip(tenant, CreateTrip.model_validate(body))` 하나다. 계획 API도 이미 같은 방식으로 초안을 `CreateTrip`으로 변환한 뒤 `_create_trip`을 호출한다(`app/modules/travel_ops/trip_api.py:490-495`).

## 5. 장소 해석 상세

### 5.1 검색 대상

통합 장소 인덱스는 다음을 함께 검색한다.

- 테넌트 `places`: 운영시간·가격·결제·식이조건 등 운영 속성
- `place_catalog`: TourAPI 장소명·주소·좌표·관광 타입
- 고객이 확인한 별칭
- 영문명·로마자 표기·띄어쓰기 제거형
- 실시간 TourAPI/Places 결과

현행 planner도 `(이름, 종류)`가 같으면 운영 정보가 더 많은 `places`를 우선한다(`app/modules/travel_ops/planner.py:254-299`). `place_catalog`는 공급자 전체 장소와 우리 운영 장소를 분리하기 위한 표이며(`app/infrastructure/db/migrations/011_place_catalog.sql:9-30`), 현재는 제목 인덱스만 있고 임베딩 칸이 없다(`app/infrastructure/db/migrations/011_place_catalog.sql:33-34`).

### 5.2 선택 순서

1. **정규화 정확 일치**
   - Unicode NFKC
   - 영문 대소문자
   - 공백·괄호·지점 접미어 정규화
   - 주소의 서울 여부와 종류 일치 확인
   - `places`가 `place_catalog`보다 우선

2. **별칭 일치**
   - `경복궁/Gyeongbokgung/Gyeongbok Palace`
   - 공급자 공식 영문명
   - 운영자가 승인한 별칭
   - 고객이 이전 확인 화면에서 승인한 표현
   - 자동 생성 별칭은 바로 신뢰하지 않고 원 장소 ID와 승인 출처를 보존

3. **임베딩 유사도**
   - bge-m3 1024차원
   - 색인 문장: `정식명 | 별칭 | 종류 | 주소 | 구 | TourAPI 타입`
   - 검색 질의에 같은 날의 지역·활동 종류·주변 장소를 함께 넣는다.
   - 현행 RAG도 Ollama/bge-m3 1024차원 경로를 지원한다(`app/infrastructure/rag/retriever.py:14-17`, `app/infrastructure/rag/retriever.py:47-65`). 장소용으로 별도 테이블과 인덱스를 둔다.

4. **TourAPI 실시간**
   - 서울과 A01·A02·A03·A04 범위에서 키워드 조회
   - 무료 원천을 유료보다 먼저 사용
   - 응답의 content ID·종류·주소·좌표를 증거로 저장
   - 현재 planner의 실시간 TourAPI는 카탈로그가 비었을 때만 보충한다(`app/modules/travel_ops/planner.py:918-923`). intake에서는 “해당 mention이 로컬에서 해결되지 않았을 때”로 호출 조건을 좁힌다.

5. **Places 실시간**
   - 마지막 대체 소스
   - 이름·좌표·종류 field mask만 요청
   - 결과 중 하나를 거리·종류·서울 여부로 선택
   - 현행 Google Places 구현에는 Text Search, 최대 5개 결과, 좌표 반경 판정, 호출 예산이 이미 있다(`app/infrastructure/travel/google_places.py:36-42`, `app/infrastructure/travel/google_places.py:71-103`, `app/infrastructure/travel/google_places.py:106-127`).

6. **고객 확인 또는 치명 결함**
   - 하나 이상의 실제 후보가 있으면 최고 점수 하나를 선택해 보여준다.
   - 후보가 전혀 없거나 서울 밖 결과만 있으면 `fatal_place_unresolved`.
   - 고객에게 여러 업체 목록을 던지지 않는다. 선택된 하나와 “다른 장소로 수정” 입력만 제공한다.

### 5.3 표현별 처리

| 표현 | 처리 |
|---|---|
| “광장시장 빈대떡집” | “광장시장”을 지역 앵커, “빈대떡집”을 업종으로 분리한다. 시장 자체를 식당으로 확정하지 않고 내부/인근 업체 검색 결과 중 종류·주소가 맞는 하나를 선택한다. |
| “그 한강 카약 하는 데” | 같은 문서의 “한강”·“카약”·날짜를 묶어 A03 레포츠 후보를 검색한다. 로컬 임베딩이 약하면 TourAPI, 그다음 Places를 호출한다. |
| “Gyeongbokgung” | 별칭/영문명 정확 일치로 `경복궁`에 연결한다. |
| “경복굼” | 문자 유사도는 후보 생성에만 쓰고, 임베딩·주소·종류를 함께 평가한다. |
| “호텔” | 같은 intake의 예약 확인서에 호텔명이 있으면 연결한다. 없으면 monitorable 장소로 확정할 근거가 없으므로 고객에게 호텔명 하나를 요청한다. |
| “자유시간” | 특정 장소가 필요 없는 항목이므로 `place=null`을 허용한다. 장소를 지어내지 않는다. |

### 5.4 확신도

초기 기준은 모두 `[추정]`이며 평가셋으로 보정한다.

- `high`: 정확명/공식 별칭 + 서울·종류 일치
- `medium`: 임베딩 cosine ≥ 0.88이고 2위와 차이 ≥ 0.08
- `low`: 임베딩 기준 미달이지만 실시간 결과에서 서울·종류·문맥이 가장 잘 맞는 실제 후보가 있음
- `fatal`: 후보 0개, 필수 좌표 없음, 서울 밖만 존재, 공급자 응답 실패 후 대체 소스도 실패

낮은 확신도도 하나를 선택하지만 고객 확인 전에는 등록하지 않는다. 확신도 숫자는 사실이 아니라 모델 점수이므로 원문 근거와 같은 색으로 표시하지 않는다.

### 5.5 비용

주어진 단가를 그대로 적용하면 Places 1회는 `$20 / 1,000 = $0.02`다.

- 로컬 정확/별칭/임베딩 해결: 0회
- TourAPI 해결: Places 0회
- 유료 조회가 필요한 고유 장소가 `U`개면: `$0.02 × U`
- 최대 7일 일정에서 유료 조회 10개인 경우: `$0.20` `[추정]`
- 유료 조회 42개인 극단 사례: `$0.84` `[추정]`

환율 기준이 없으므로 원화 환산은 `[미확보]`다. 49,000원 상품에서의 정확한 원가 비중 역시 환율 없이는 확정하지 않는다.

장소 검색은 intake와 새벽 영업 확인에만 사용한다. 2분 감시 루프에서는 Places나 Route Matrix를 호출하지 않는다. 현행 코드도 유료 호출을 DB 예산에서 호출 전에 예약하고, 실패 호출도 사용량으로 센다(`app/infrastructure/db/migrations/027_external_call_budget.sql:3-19`). Places 영업 확인은 당일 새벽 한 번만 수행하도록 별도 기록한다(`app/infrastructure/db/migrations/026_place_open_checks.sql:1-11`, `app/infrastructure/db/migrations/026_place_open_checks.sql:25-39`).

## 6. 근거 보존과 “왜 이렇게 읽었나”

모든 필드는 다음 provenance를 가진다.

```json
{
  "field_path": "items[1].starts_at",
  "value": "2026-10-02T12:00:00+09:00",
  "provenance": [
    {
      "type": "source_span",
      "source_id": "src_pdf_1",
      "page": 2,
      "bbox": [83, 214, 492, 251],
      "quote_masked": "12:00 토속촌",
      "source_sha256": "..."
    }
  ],
  "transform": {
    "type": "combine_date_time",
    "inputs": ["trip.start_date", "12:00"],
    "rule_version": "datetime-ko-v1"
  }
}
```

근거 종류는 세 가지다.

1. **원문 근거:** 파일·페이지·줄·bbox·셀·DOM 위치와 발췌
2. **조회 근거:** provider, content/place ID, 관측 시각, 응답 hash
3. **규칙 근거:** 규칙 ID, 버전, 입력값, 결과

UI에서 각 값 옆에 “근거 보기”를 두고 다음을 제공한다.

- PDF/이미지: 해당 bbox 하이라이트
- DOCX: 문단 또는 표 셀
- XLSX: 시트와 셀
- 텍스트: 줄과 발췌
- 링크: URL과 발췌
- 조회값: “TourAPI에서 좌표 확인, 2026-09-26 14:20”
- 규칙값: “접수일 기준 ‘다음 주 금요일’을 계산”

원본을 수정하거나 재추출하면 revision을 올리고 이전 provenance를 지우지 않는다. 여행 일정 자체도 현재 `itinerary_versions`에 append-only로 쌓이고(`app/infrastructure/db/migrations/014_itinerary.sql:25-53`), `latest_version` 비교로 낡은 쓰기를 거부한다(`app/modules/travel_ops/itinerary.py:213-237`). intake도 같은 방식의 revision/optimistic concurrency를 사용한다.

## 7. 고객 확인 흐름

확인 화면은 세 화면이면 충분하다.

### 화면 1 — “이렇게 읽었습니다”

- 여행 날짜·인원·도시
- 일자별 일정
- 선택된 장소명과 지도 위치
- 원문 시각과 예약 여부
- 각 값의 “근거 보기”
- `원문 그대로`, `규칙으로 배치`, `조회로 확인`, `확인 필요` 배지

후보 목록은 보이지 않는다. 장소마다 선택된 하나만 보여주고 “장소명 수정”을 제공한다.

### 화면 2 — “확인이 필요한 것만”

다음만 모아 보여준다.

- 낮은 확신도의 장소
- 문서 간 충돌
- 규칙으로 채운 시각
- OCR 저신뢰 값
- 예약번호·업체·시각의 불완전 조합
- 판정기가 발견한 일정 위반

고객 수정은 원문보다 높은 우선순위의 새 evidence가 된다. 수정 후 영향받은 장소·날짜·판정만 다시 실행한다.

### 화면 3 — “등록하고 지속관리 시작”

- 최종 일정
- 자동 감시 대상과 감시 불가능한 항목
- 예약 변경·취소는 별도 승인이 필요하다는 문구
- “등록 및 관리 시작” 단일 버튼

현재 프런트도 검증 결과에 미해결 항목이 있으면 여행 시작을 막고(`frontend/apps/web/src/features/verification/verification-results.tsx:79-98`, `frontend/apps/web/src/features/verification/verification-results.tsx:121-126`), 고객이 관리 범위를 확인한 뒤 시작하도록 구성돼 있다(`frontend/apps/web/src/features/verification/verification-results.tsx:105-119`). 이 화면 구조를 실제 intake 결과에 연결한다.

### 되묻는 경우

되묻기는 선택지를 만들기 위한 대화가 아니라 **필수 사실 하나를 얻는 최후의 소스**다.

- 첫날 기준 날짜가 없음
- 인원이 없어 4인 한계를 판정할 수 없음
- 서울인지 확인할 근거가 없음
- 예약 일정의 날짜/시각이 상충하고 우선할 원본이 없음
- 장소 후보가 0개
- 파일 핵심 영역을 어느 추출기도 읽지 못함

질문 예시는 “첫날 날짜를 입력해 주세요”처럼 단일 사실을 요구한다. 장소 후보 A/B/C를 나열하지 않는다. 후보가 하나라도 있으면 먼저 하나를 선택해 보여주고 고객은 자유 입력으로 수정한다.

## 8. 새 API와 데이터 모델

### 8.1 웹 API

| API | 역할 |
|---|---|
| `POST /v1/web/trip-intakes` | 텍스트·URL·파일을 multipart로 접수 |
| `GET /v1/web/trip-intakes/{id}` | 진행 상태·초안·fatal 조회 |
| `PATCH /v1/web/trip-intakes/{id}` | 고객 수정 patch |
| `POST /v1/web/trip-intakes/{id}/confirm` | 재판정 후 `_create_trip` 호출 |
| `DELETE /v1/web/trip-intakes/{id}/sources/{source_id}` | 고객이 원본 삭제 |
| 기존 `POST /v1/web/trips` | 구조화 클라이언트 호환용으로 유지 |

`confirm`은 `base_revision`을 받아 중복 탭의 낡은 확인을 거부한다. 최종 `request_id`는 `intake_id + revision`으로 만들어 현재의 멱등 계약을 사용한다. 등록 요청은 body hash까지 비교하므로 같은 request ID에 다른 본문이 오면 409가 된다(`app/infrastructure/db/migrations/016_trip_request_key.sql:8-13`, `app/modules/travel_ops/trip_api.py:395-408`).

### 8.2 새 표

| 표 | 주요 칸 |
|---|---|
| `trip_intakes` | `intake_id`, tenant/customer, status, revision, received_at, locale, fatal_code, pipeline_version, confirmed_at, trip_id |
| `intake_sources` | source_id, type, filename, MIME, URL, sha256, encrypted_storage_ref, parse_status, retention_until |
| `intake_blocks` | block_id, source_id, page/sheet/cell/DOM/bbox/line, masked_text, OCR confidence, reading_order |
| `intake_secrets` | token, encrypted original, source locator, secret type, key version |
| `intake_claims` | claim_id, field_path, value_json, normalized_value, extraction_method, confidence, status, revision |
| `intake_evidence` | claim_id, source/block ID, quote, offsets/bbox, source hash, observed_at |
| `intake_place_mentions` | 원 표현, 주변 문맥, item 연결 |
| `intake_place_resolutions` | selected entity, method, score, margin, provider evidence, confirmed_by_customer |
| `place_aliases` | place/catalog ID, alias, language, source, approved_at |
| `place_search_index` | entity_type/id, canonical text, `embedding_1024`, model, content hash, embedded_at |
| `intake_jobs` | stage, attempt, status, error, started/finished_at |
| `intake_audit` | revision, actor, action, patch, timestamp |

장소 임베딩은 정책 RAG 표와 섞지 않는다. 정책 청크는 `knowledge_chunks.embedding_1024`를 쓰며(`app/infrastructure/db/migrations/020_local_embedding_column.sql:5-10`), 장소는 수명·갱신 방식과 검색 필터가 다르기 때문이다.

원본 보관기간 30일은 `[추정]` 초기값이다. 고객 확인 후에는 장기 운영에 필요한 최소 evidence와 hash만 남기고 원본 자동삭제 여부를 개인정보 정책 검토로 확정해야 한다 `[미확보]`.

### 8.3 예약 연결

현행 `bookings`에는 예약번호·종류·상태·시각·인원·금액·잠금 여부가 있다(`app/infrastructure/db/migrations/010_domain_travel.sql:38-53`). 하지만 현재 `_insert`는 모든 일정 항목의 `booking_id`를 비워 만든다(`app/modules/travel_ops/trip_api.py:439-444`).

따라서 최상위 `CreateTrip` 모양은 바꾸지 않고 다음을 제안한다.

```json
{
  "detail": {
    "booking": {
      "booking_no_token": "<BOOKING_1>",
      "status": "confirmed",
      "source_evidence_ids": ["ev41"]
    }
  }
}
```

`_create_trip` 트랜잭션 안에서 검증된 `detail.booking`을 `bookings`로 materialize하고 생성된 `booking_id`를 `Item`에 연결한다. 이렇게 해야 예약 변경 감시와 승인 경계가 작동한다. 업체 상태는 별도 `supplier_bookings`와 대조하도록 이미 분리돼 있다(`app/infrastructure/db/migrations/010_domain_travel.sql:59-69`).

## 9. 평가 방법

### 9.1 평가셋

입력 형태마다 `[추정]` 30건씩 만든다.

- 짧은 채팅 요청
- 붙여넣은 일정
- 텍스트 PDF
- 스캔 PDF
- DOCX
- XLSX
- 이미지/캡처
- 예약 메일·바우처
- 공개 링크
- 2개 이상 혼합 입력

총 `[추정]` 300건이며, 그중 최소 `[추정]` 30%는 다음 결함을 포함한다.

- 첫날/둘째 날만 존재
- 일부 시각 없음
- 상대 날짜
- 오탈자·영문명·별칭
- 예약 문서와 일정표 충돌
- 여러 표/다단 PDF
- 저해상도 사진
- 개인정보 포함
- 서울 밖 장소 또는 5인 이상 등 상품 범위 밖

각 사례에는 사람이 다음 gold를 단다.

- 문서 블록과 읽기 순서
- 항목 목록
- 날짜·시각·인원·금액·예약번호
- 정확한 evidence locator
- 정답 장소 ID와 좌표
- 최종 `CreateTrip`
- 예상 판정 결과와 fatal 여부

장소와 evidence는 2인 독립 라벨 후 불일치를 조정한다.

### 9.2 지표

| 영역 | 지표 |
|---|---|
| 텍스트화 | OCR CER/WER, 표 셀 보존율, 읽기 순서 정확도 |
| 항목 추출 | item precision/recall/F1 |
| 값 정확도 | 날짜 exact match, 시각 exact match, 인원·금액·예약번호 exact match |
| 근거 | 값별 evidence recall, bbox/셀/줄 일치율 |
| 환각 방지 | 원문·조회·규칙 근거가 없는 값 비율. 목표 0 |
| 장소 | top-1 장소 정확도, 좌표 허용오차, unresolved recall, confidence calibration |
| 일정 | `CreateTrip` 스키마 통과율, 판정기 위반 검출률 |
| 고객 확인 | 수정률, 잘못된 자동 선택 승인률, 완료 이탈률 |
| 운영 | stage별 p50/p95, GPU peak memory, Places/TourAPI 호출 수, 건당 비용 |
| 개인정보 | 모델 입력에 원 PII가 남은 비율. 목표 0 |
| 지속관리 | 등록 항목 중 감시 가능한 place/route/booking 연결률 |

출시 게이트 제안 `[추정]`:

- 날짜·시각·예약번호 exact match ≥ 99%
- 장소 top-1 정확도 ≥ 95%
- evidence 연결률 ≥ 99%
- 근거 없는 값 0건
- PII 원값 모델 노출 0건
- fatal 사례를 정상 등록한 건 0건

수치는 초기 목표이며 실제 평가 후 확정한다.
