## 1. 코어가 RAG 를 부르는 길

```
Case (subject = 고객 문장)
  → Controller._task()
      policy_required = Team 이 required_context 에 "policy" 를 선언했고
                        그 capability 가 policy_optional_capabilities 에 없다
      필요하면  search_policy(tenant, case.subject, manifest.knowledge_scope)
      예외면    retrieval_failed=True
  → ContextBroker.build()
      정책 청크 → Evidence(source_type="policy")
      degraded = 조회 실패  또는  (필요한데 결과 0건)
  → Team.execute(task)
      Activity·Booking Handoff 는 여기서 read.policy 를 또 부른다
```

`[실측]` 여행 Team 의 RAG 필요 여부 — manifest 를 읽어 셌다.

| Team | RAG 를 켜는 capability | 면제 |
|---|---|---|
| activity | `check_cancelable` · `check_feasible` · `propose_change` | `activity.itinerary` |
| dining | `check_open` · `check_conditions` | `dining.itinerary` |
| mobility | `check_route` · `status` · `exception` | `mobility.itinerary` |
| booking_handoff | `verify` · `prepare_change` · `prepare_cancel` · `prepare_revert` | — |

**12개 capability 가 RAG 를 켠다. 면제는 `*.itinerary` 셋.**

## 2. ★대표 흐름은 RAG 를 안 탄다

`itinerary_team.py:63` — Case 상태에 `subject_ref.kind == "trip"` 이 있으면 `*.itinerary` 로 간다.

```python
return ref.get("kind") == "trip" and bool(ref.get("id"))
```

그리고 `*.itinerary` 는 세 Team 모두 **RAG 면제**다. 즉 **여행을 가리키는 Case 는 규정을
한 번도 안 본다.**

`case_engine.py` (시나리오 모드·하루 대조 시험의 조립)는 이것을 전제로 **도구 경로와
Controller 경로 둘 다에 `_no_policy`(부르면 예외)**를 꽂는다.

```python
tools = ReadToolbox(get_connection, policy_search=_no_policy, …)
self.controller = composition.build_controller(…, policy_search_fn=_no_policy)
```

★**지금은 맞다** — 그 조립이 여는 Case 는 전부 여행 참조라 RAG 가 불릴 일이 없다.
**다만 그래서 시연과 대조 시험은 RAG 를 증명하지 못한다.** 같은 파일 머리말이
"따로 짠 Controller 를 쓰면 대조가 운영을 증명하지 못한다"고 적었는데, RAG 에
한해서는 그 조립이 운영과 다르다.

`[미확보]` 대표 흐름에 **취소 문의**("비 와서 취소되나요")가 들어오면 어느 길로 가나.
여행을 가리키면 `*.itinerary` 라 규정을 안 보고, 안 가리키면 `check_cancelable` 로 간다.
**코퍼스가 가장 잘 답하는 질문이 대표 흐름에서는 규정 없이 처리될 수 있다.**
시나리오에 그 질문을 넣어 어느 capability 로 가는지 확인해야 한다.

## 5. ★점수 문턱이 없다 — 엉뚱한 질문도 근거 8건

검색 SQL 은 `ORDER BY 거리 LIMIT top_k` 뿐이다(`retriever.py`). scope 에 청크가 8개 이상이면
**어떤 질문에도 8건**이 온다.

`[실측 2026-09-25]` activity scope, 질의 6건.

| | 질의 | 건수 | 최고 점수 | 1위 |
|---|---|---:|---:|---|
| 관련 | 비 오면 한강 카약 예약 취소되고 위약금 있나요 | 8 | 0.641 | t_doc_02 |
| 관련 | 공연 당일 취소하면 환불되나요 | 8 | 0.610 | t_doc_01 |
| 관련 | 경복궁 휴관일에 가도 되나요 | 8 | 0.568 | t_doc_03 |
| 무관 | 제 비밀번호를 바꾸고 싶어요 | 8 | 0.510 | t_doc_11 |
| 무관 | 오늘 환율이 얼마예요 | 8 | 0.486 | t_doc_01 |
| 무관 | ㅋㅋㅋ 안녕 | 8 | 0.423 | t_doc_05 |

★**「정책 근거 없음 → degraded」가 사실상 scope 가 비었을 때만 켜진다.** 무관한 질문도
근거 8건을 달고 "근거 있음" 으로 넘어간다. 근거 없는 확정을 막으려고 둔 장치가
**관련성은 안 본다.**

`[미확보]` 문턱을 어디 둘지는 이 6건으로 못 정한다. 관련 최저 0.568 과 무관 최고
0.510 사이가 벌어져 있지만 **표본이 여섯이다.** 질의 묶음을 만들어 재야 한다.
문턱을 넣으면 `degraded` 가 지금보다 자주 켜진다 — 사람에게 가는 비율이 오른다.

## 6. 같은 검색을 두 번 한다

`[실측 — 코드를 읽어]` Activity(`activity.py:143`)·Booking Handoff(`booking_handoff.py:97`)는
`read.policy` 를 부른다. 그 도구는 **ContextPack 의 `knowledge_scope`** 와 **`task.input_text`**
(= `case.subject`)로 검색한다(`read_tools.py:64,107`). **Controller 가 방금 한 검색과 질의·
scope 가 같다.**

- 임베딩 호출은 한 번이다 — `_embed_query` 가 `lru_cache(maxsize=64)` 로 캐시된다
- DB 검색은 두 번이고, 근거가 **같은 청크로 두 벌** 실린다(ContextPack 8 + 도구 8)

`[미확보]` 두 벌이 판정·검증(근거 대조)에서 문제를 일으키는지는 안 돌려 봤다.

## 9. ★대화로 짜고 고치는 흐름은 규정 질문을 못 받는다

`[사용자 질문 2026-09-25]` "일정 대화로 짜는 걸 코어에서 RAG 안 해? 올린 계획서를 수정 가능한
일정으로 관리하는데 RAG 안 하면 어떻게 해?"

### 짜고 고치는 계산은 RAG 가 없어도 된다 — 사실로 한다

`[실측 — 코드를 읽어]`

| 흐름 | 무엇으로 판정하나 | RAG |
|---|---|---|
| 대화로 짜기 `planner.py` | 후보는 우리 `places` · 관광공사 목록 `place_catalog` · TourAPI 실시간에서만. **LLM 은 순서만** 정한다 | 안 씀 |
| 올린 계획서 받기 → 일정 버전 | 항목 `{시작, 끝, 장소, 비용, 잠김}` 로 정규화, 시간 충돌·이동 여유를 **계산** | 안 씀 |
| 고치기 `itinerary_team.py` | `read.itinerary` · `place_catalog` · `disruptions` · `route_events` · `customer_report` | 안 씀 |

★**이건 맞다.** 영업시간·이동 시간·장애는 **지금 값**이라 조회해야 하고, 문서로 들고 있으면 낡는다.
일정 계산을 RAG 로 하면 오히려 틀린다.

### 그런데 대화에는 규정 질문이 섞인다 — 그게 빠진다

여행을 가리키는 Case 는 고객 문장을 신고 **여섯 종류**(`delay`·`closed`·`stock_out`·`change`·
`rollback`·`other`)로만 읽는다(`trip_intake.py`). `other` 면 `report_not_understood` 로
**사람에게 넘긴다**(`itinerary_team.py` `run_itinerary`).

`[실측 2026-09-25]` 실제 추출기(`composition.build_report_extractor()`)에 넣어 봤다.

| 고객 문장 | 뽑힌 종류 | 그 뒤 |
|---|---|---|
| 비 오면 오후 한강 카약 취소돼요? 위약금 있어요? | `other` | **사람에게** — 코퍼스에 답이 있는데 안 본다 |
| 저녁 식당에 아이 데려가도 되나요 | `other` | **사람에게** |
| ★내일 경복궁 휴관 아니에요? | **`closed`** | **질문이 「지금 닫혀 있다」는 신고로 읽혔다** |
| 점심 식당 70분 늦을 것 같아요 | `delay` | 맞다 |
| 다른 식당으로 바꿔줘 | `change` | 맞다 |

★**규정을 묻는 문장 3건 중 규정으로 간 것은 0건이다.** 둘은 사람에게 가고, 하나는
**질문이 상태 신고로 둔갑했다.** `closed` 는 "고객이 있는 곳이 오늘 닫혔다" 는 뜻이라
대체안 계산으로 이어질 수 있다. `[미확보]` 그 Case 가 어느 Team 으로 가서 실제로
일정을 바꾸는지는 끝까지 안 돌렸다.

★표본은 다섯 문장이다. 추출기는 LLM 이라 같은 문장도 매번 같다고 장담 못 한다.

### 무엇이 빠졌나 — 둘

1. **질문을 받을 자리가 없다.** 신고 여섯 종류에 「물어본다」가 없다. 규정 질문은
   `other` 로 버려지거나 가장 가까운 신고로 잘못 들어간다.
2. **바꾼 이유에 근거 문장이 안 붙는다.** 감시가 비를 보고 카약을 실내로 바꿔 통지할 때
   "업체 사정 취소라 위약금이 없다" 는 문장을 붙일 수 없다 — 일정 흐름은 규정을 안 읽는다.
   **근거 없는 문장 금지** 원칙상 그 말을 아예 못 하거나, 근거 없이 하게 된다.

### 제안 — 일정 흐름 안에 「질문」 하나를 더 받는다

| | 무엇 | 대가 |
|---|---|---|
| **① 신고 종류에 `question` 을 더한다** | 추출기가 질문을 따로 뽑고, 그 Case 만 **규정을 읽는 capability**(`*.itinerary_question`, `policy` 필요)로 보낸다. 항목을 짚어 `read.policy` + `read.booking_terms` 로 답하고 근거를 붙인다 | 추출기 프롬프트·규칙 하나, capability 하나. **일정을 안 바꾸는 길**이라 위험이 낮다 |
| ② 기존 `check_cancelable` 로 보낸다 | 이미 있는 RAG capability 재사용 | 그 capability 는 **예약**(`read.booking`)을 전제한다. 무료·무예약 항목(경복궁)은 「모름」으로 끝난다 — v11 결정(판정 입력은 예약이 아니라 **일정 항목**)과 어긋난다 |

★**①을 권한다.** 그리고 **`closed` 와 `question` 을 가르는 규칙**이 같이 필요하다 —
물음표·"아니에요?"·"되나요" 처럼 **묻는 꼴**이면 상태 신고로 받지 않는다. 지금은 그 구분이
없어서 질문이 일정을 바꿀 수 있다.

2번(바꾼 이유의 근거)은 ①이 생기면 같은 도구로 붙인다 — 감시 Case 에서 대체안을 낼 때
`read.policy` 로 이유 문장을 한 번 찾는다.

`[인계]` 코드는 담당 세션 몫이다. 이 문서는 설계·실측만 남긴다.

| 계획 만들기 | `POST /v1/trips/plan` | **정해진 칸** — 도시(기본 서울)·시작일·1~7일·1~4명·조건·선호 문장(`preferences`). 자유 채팅을 바로 받지 않는다 |
| 올린 계획서 등록 | `POST /v1/trips` | **이미 구조화된 JSON** — 장소 목록·항목·경로 |
| 등록 뒤 대화 | `POST /v1/web/trips/{id}/messages` 등 | 자유 문장 → 분류 + 신고 추출 → 일정 관리 |

★**대화에서 칸을 뽑는 일과 계획서 문서를 구조로 바꾸는 일은 우리 쪽에 없다** — 고객 에이전트 몫으로
둔 모양이다. `travel_ops` 에서 함수 이름(`parse`·`extract`·`import`·`normalize`·`paste`·`upload` +
`plan`·`itinerary`·`trip`)으로 찾아 0건이었다. 다른 이름으로 있으면 놓쳤을 수 있다.

### 채팅 임베딩

| | 지금 |
|---|---|
| 고객 문장을 질의로 임베딩 | **한다** — Controller 가 `case.subject` 로 검색할 때 그때그때. 저장하지 않는다 |
| 고객 대화를 쌓아 임베딩해 두기 | **없다.** 임베딩을 만드는 코드는 검색기·코퍼스 적재기뿐이다 |
| 비슷한 과거 사례 | 칸(`similar_cases`)은 있는데 Controller 가 **안 채운다** |

★쌓아서 임베딩하려면 **목적부터 정한다.** 같은 여행의 대화 맥락은 DB 이력을 읽으면 되고 임베딩이
필요 없다. 필요한 것은 **비슷한 과거 사례 찾기**다. 그리고 고객 문장을 저장·임베딩하면
**개인정보 문제**(가리기·보관 기한·동의)가 같이 붙는다.

### 법 규정

`[실측 2026-09-25]` 여행 코퍼스 12문서는 **전부 우리 내부 운영 규정**이다(`source_uri` 가 모두
`internal://…/travel-policy/…`). 본문이 "업체 약관·법령" 을 **일반적으로 언급**하는 줄은 있지만
소비자분쟁해결기준·관광진흥법·개인정보보호법 **이름은 0회**, 법령 조문·출처도 없다.

★09-09 코퍼스 계획이 **소비자분쟁해결기준 원문 조회**를 1순위로 적었는데 안 됐다.

### 「문제없게 대화」는 RAG 만으로는 안 된다

RAG 는 **근거를 가져오는 것**이고, 문제되는 말이 나가지 않게 하는 것은 **답이 나가기 전에 거르는
장치**다. `[실측 — 코드를 읽어]`

| | 지금 |
|---|---|
| 여행 채팅 경로(`trip_messages` · `trip_intake` · `trip_api`)의 개인정보 가리기·답 검수 | **0건** (`mask`·`redact`·`pii` 로 찾음) |
| 신고 추출기 | 고객 문장을 **가리지 않고** 모델에 보낸다. 로컬 Gemma 라 밖으로 나가지는 않는다 |
| 분류기 | 가린다(`composition.py` `masked(message)`) — **두 자리가 다르다** |
| 쇼핑몰 때의 답 검수(개인정보·금지어) | v10 에서 「Team 내부 규칙으로 흡수」로 정했는데 **여행 쪽에 옮겨진 것이 안 보인다** |
