# 고객 계획 읽기 설계 — triPilot 웹 앱

기준일 2026-09-26 · 기준선 v11 · 대상 서울·최대 7일·4인 · 최종발표 2026-10-26

고객이 웹 앱에 무엇을 어떤 모양으로 올리든(채팅 요청, 붙여넣은 일정, PDF, docx, xlsx, 사진·캡처, 링크, 예약 확인서)
그것을 읽어 **지속 관리되는 일정**(`CreateTrip` → `_create_trip` → 감시·알림)으로 만드는 방법을 정한다.

만든 과정: Codex 가 초안을 쓰고([코덱스 초안](A-COP_고객계획_읽기_설계_2026-09-26_코덱스초안.md) — 원본 그대로 보관),
이 세션이 **실물로 재서** 초안의 전제 다섯 개를 뒤집었다. 이 문서가 최종판이다. 둘이 다르면 이 문서를 따른다.

## 0. 결론

> `[2026-10-16 주석]` 이 절의 「모델은 가리키기만 하고, 값은 원문과 조회가 낸다」와 §2-A 는 [D-025](../../wiki/decisions/D-025-plan-reading-model-understands.md) 가 뒤집었다 — 지금은 가르친 E4B 가 통째로 읽고 분류하고, 코드는 인용 · 시각 · 장소 · 범위 검사만 한다. 아래 본문은 당시 기록이라 고치지 않는다.


**모델은 가리키기만 하고, 값은 원문과 조회가 낸다.**

1. **글자로 만든다.** 파일 종류별 전용 파서(PDF·docx·xlsx)를 쓰고, 사진·스캔은 로컬 비전 모델(`gemma4:12b`)에 **"한 줄씩 그대로 받아 적어라"**만 시킨다.
   결과는 **줄 번호가 붙은 글**이다.
2. **규칙이 먼저 읽는다.** 일차 머리줄·날짜·시각 줄·예약번호·인원은 규칙으로 뽑는다. 규칙이 못 읽은 줄만 LLM 에 넘기되,
   LLM 에게는 **값이 아니라 "몇 번째 줄의 몇 번째 글자부터 몇 번째까지가 무엇"**만 받는다. 값은 서버가 원문에서 잘라 낸다.
3. **장소는 찾아서 고른다.** 정확 일치 → 별칭 → **자모 단위 오타 교정** → **무료 실시간 검색**(카카오 키워드 검색·관광공사) →
   유료 Places 순서로 **하나**를 고른다. 임베딩은 확정에 쓰지 않고, 뭉툭한 표현의 후보를 좁히는 보조로만 쓴다.
4. **확인 화면 한 장**에서 "이렇게 읽었습니다"를 근거와 함께 보여 주고, 고객이 고친 뒤 `_create_trip` 한 곳으로 등록한다.

왜 이 모양인지는 §1 의 실측이 말한다. 한 번에 "사진 → JSON"을 시키면 **여섯 항목 중 셋을 잃었고**,
받아 적기만 시키면 **여섯 줄을 다 그대로** 적었다. LLM 에게 구조화를 시키면 고유명사를 **바꿔 적었다**(토속촌 → 토속툰).

### 어디에 무엇을 쓰나

| 도구 | 쓰는 곳 | 안 쓰는 곳 |
|---|---|---|
| **로컬 비전 모델** (`gemma4:12b`) | 사진·스캔 쪽의 **받아쓰기** | 구조화·값 생성 |
| **로컬 LLM** (`gemma4:12b`, 생각 모드 끔) | 규칙이 못 읽은 줄에 역할·위치 붙이기, "일정 짜 줘" 요청을 planner 칸으로 옮기기, 뭉툭한 장소 표현을 **검색어**로 바꾸기 | 시각·날짜·이름·예약번호·좌표 **값**을 내는 것 |
| **임베딩** (`bge-m3`, 1024칸) | "그 한강 카약 하는 데" 같은 표현의 **종류·지역 후보 좁히기**(보조) | 장소 확정. §1 실측 6 — 점수로 맞고 틀림이 안 갈린다 |
| **RAG** (여행 규정 코퍼스) | 확인 화면의 **규정 안내**(취소·아동 동반 등 설명 문장) | 계획 값. 장소·시각·가격을 RAG 에서 가져오지 않는다 |
| **규칙** | 일차·날짜·시각·인원·예약번호 패턴, 상대 날짜 계산, 자모 오타 교정, 빈 시각 배치 | — |
| **조회** | 장소 좌표·종류(카카오·관광공사·Places), 영업시간 | 2분 감시 루프의 유료 호출 |

## 2. Codex 초안과 달라진 것

초안 대부분은 받아들인다 — 원본 → 해석 → 확정값 분리, 값마다 근거 세 종류(원문·조회·규칙), 선택된 하나만 보여 주는 확인 화면,
되묻기는 필수 사실 하나만, `_create_trip` 한 곳 등록, 예약 문서 → `bookings` 연결, 판정기가 모르는 값을 통과시키는 한계를
앞단 검사로 막기, 2분 감시에 유료 호출 금지, 링크 수집의 SSRF 차단. 아래 다섯은 뒤집었다.

| # | 초안 | 최종 | 근거 |
|---|---|---|---|
| A | LLM 이 구조를 뽑고, 실패하면 규칙 | **규칙이 먼저**, 남은 줄만 LLM. LLM 은 **위치만** 반환하고 값은 서버가 원문에서 자른다 | 실측 3·4·5 — LLM 은 1/6 이거나, 6/6 이어도 고유명사를 바꿨다. 규칙은 6/6 |
| B | OCR 먼저, 비전 모델은 저신뢰 영역만 | **비전 모델 받아쓰기가 주 경로.** 누락은 완전성 검사로 잡는다(§3-2). OCR 엔진은 평가 뒤 추가 여부를 정한다 | 실측 10 — OCR 엔진이 없다. 실측 2 — 받아쓰기는 6/6 |
| C | 원본 이미지를 비전 모델에 직접 넘기지 않는다(먼저 가린다) | **로컬 모델이면 원본을 보여 준다.** 가림은 **기계 밖으로 나가는 경로**(외부 LLM·로그·운영 화면)에서 한다. LLM 제공자가 외부로 설정되면 이미지 경로를 막는다 | 개인정보 위치를 찾으려면 먼저 읽어야 한다 — 가리고 읽기는 순서가 돌아간다 |
| D | 정확 → 별칭 → **임베딩** → TourAPI → Places | 정확 → 별칭 → **자모 오타** → **무료 실시간(카카오·관광공사)** → Places. 임베딩은 후보 좁히기 보조 | 실측 6(임베딩 42%, 문턱 0.88 통과 0건) · 7(자모 2/2) · 8(카카오) |
| E | 로컬 카탈로그를 주 후보로 | **카탈로그 수집 필터부터 고친다**(`lDongRegnCd=11`). 고치기 전에는 실시간 검색이 주 경로다 | 실측 9 — 서울의 24.6%, 경복궁 없음 |

규모도 줄였다. 새 표 12개 → **MVP 3개**(§6), 평가셋 300건 → **MVP 60건**(§7) `[추정]`. 4주 안에 초안 범위를 다 만들 수 없다.

## 3. 파이프라인

```
접수 ─▶ 글자로 ─▶ 완전성 검사 ─▶ 규칙 읽기 ─▶ LLM(남은 줄, 위치만) ─▶ 날짜 해석 ─▶ 장소 해석
     ─▶ 빈칸 채우기·판정 ─▶ 확인 화면 ─▶ _create_trip ─▶ 버전·감시·알림
```

### 3-1. 접수

- 웹 세션으로 부르는 새 입구 `POST /v1/web/trip-intakes`(multipart: 글·파일 여러 개·링크). 고객 id 는 **세션에서 주입**한다 —
  지금 `POST /v1/web/trips` 의 경계(`app/modules/travel_ops/trip_api.py:722-734`)와 같다.
- 형식은 확장자가 아니라 **파일 첫 바이트(magic bytes)**로 판별한다.
- 한 번의 접수 = `intake_id` 하나. 파일·글이 여럿이면 각각 따로 읽고 근거 단위로 합친다.
- 처리는 **뒤에서(작업 큐)** 돈다 — 사진 한 쪽 받아쓰기가 약 45초다(실측 2). 화면에는 진행 단계를 보여 준다.
  7일 일정 사진 2~3쪽이면 받아쓰기만 1.5~2.5분 `[추정]`.

### 3-2. 글자로 만들기

| 입력 | 방법 | 근거로 남기는 위치 | 안 되면 |
|---|---|---|---|
| 채팅·붙여넣기 | 그대로 | 줄 번호 | — |
| 글자 있는 PDF | PyMuPDF 로 쪽별 글자(있음) | 쪽 + 줄 | 글자가 없거나 깨진 쪽 → 쪽을 그림으로 → 아래 사진 경로 |
| 스캔 PDF·사진·캡처 | 비전 모델 **받아쓰기** "한 줄씩 그대로, 고치지도 빼지도 말고" | 쪽 + 조각 + 받아쓴 줄 번호 (+ 조각 그림) | 조각을 더 잘게 → 다시 받아쓰기 → 그래도 안 되면 그 쪽만 다시 올려 달라고 한다 |
| docx | python-docx, 문단·표 순서대로(있음) | 문단 번호 / 표·행·열 | 깨진 파일 → 고객에게 PDF 로 |
| xlsx | openpyxl, **계산된 값**(있음) | 시트 + 셀 주소 | 계산 값이 비면 그 셀만 확인 화면에 |
| 공개 링크 | http/https 만, 사설·루프백 주소 차단, 리다이렉트 제한. bs4 로 본문(있음) | URL + 발췌 + 받은 시각 | 로그인 필요 페이지 → 고객에게 PDF·붙여넣기 |
| 예약 메일 | `.eml` 또는 붙여넣기 | 줄 | — |

**완전성 검사**(사진·스캔 경로). 실측 1 처럼 모델이 한 부분을 통째로 빠뜨리는 일을 잡는다.

1. 쪽을 **위·아래 두 조각**(겹침 10%)으로도 받아 적는다.
2. 전체 받아쓰기와 조각 받아쓰기의 **시각 패턴 줄**(`\d{1,2}:\d{2}`, `\d+시`)과 **일차 머리줄**을 맞춰 본다.
3. 한쪽에만 있는 줄은 그 조각을 다시 받아 적어 확정한다. 끝까지 한쪽에만 있으면 **있는 쪽을 채택하고 확인 필요 배지**를 단다.

비용: 한 쪽에 받아쓰기 3회 ≈ 2분 `[추정 — 실측 2의 44.7초 × 3]`. 조각이 전체보다 짧아 더 빠를 수 있다 `[미확보]`.

bbox(글자 상자 좌표) 근거는 OCR 엔진이 있어야 나온다. MVP 는 **쪽·조각·줄 번호**까지만 남긴다.

### 3-3. 규칙 읽기

프런트의 데모 파서(`parse-plan.ts`) 규칙을 **서버로 옮기되, 거절 대신 "읽은 줄 / 남은 줄"로 나눈다.**

| 규칙 | 예 | 결과 |
|---|---|---|
| 일차 머리줄 | `1일차`, `DAY 2`, `첫날`, `둘째 날` | 일차 번호 |
| 날짜 | `2026-10-03`, `10/3(금)`, `10월 3일` | 날짜(연도 없으면 접수일 기준 다음 해당일) |
| 시각 줄 | `10:00 경복궁 관람`, `오후 3시 한강` | 시각 + **줄의 나머지 원문**(제목) |
| 기간·인원 | `2박3일`, `4명`, `넷이서` | 일수·인원(`넷이서`→4 는 `phrase_rule` 로 기록) |
| 예약 | `예약번호 KY-20931`, `예약 4명`, `예약 없음` | 예약번호 **원문**, 예약 여부 |
| 화살표 나열 | `10시 경복궁 → 12시 토속촌` | 줄 안에서 나눠 여러 항목 |

**제목은 규칙이 자른 원문 그대로다.** 「토속촌」이 「토속툰」이 될 길이 없다.

### 3-4. LLM — 남은 줄만, 위치만

규칙이 못 읽은 줄(서술형 블로그 글, 섞인 문장)만 넘긴다. 설정: `gemma4:12b`, **생각 모드 끔**(실측 4b 에서 켜면 1/6), JSON 스키마, 온도 0.

받는 모양:

```json
{"spans": [
  {"line": 14, "start": 0, "end": 5,  "role": "time"},
  {"line": 14, "start": 6, "end": 15, "role": "place"},
  {"line": 15, "start": 3, "end": 11, "role": "booking_ref"}
]}
```

서버가 `원문[line][start:end]` 로 값을 자른다. 잘라 낸 값이 역할의 형식(시각 패턴, 예약번호 패턴)에 안 맞으면 버린다.
**LLM 이 낸 글자를 값으로 쓰는 경로가 아예 없다.**

"일정 짜 줘" 같은 **계획 요청**이면 여기서 planner 칸(`city·start_date·days·party_size·preferences`)을 같은 방식(위치 + 규칙)으로 채우고
**웹 서버 안에서 `planner.plan_trip`을 직접 부른다.** 에이전트 키가 필요한 `POST /v1/trips/plan`(`trip_api.py:458`)을 거치지 않는다.

### 3-5. 날짜 해석

초안 §4.3 을 그대로 쓴다. 우선순위는 이렇다.

1. 고객이 고친 값
2. 예약 확인서의 이용일
3. 본문 날짜
4. 같은 접수의 시작일
5. 웹 세션의 출발일 칸
6. 상대 날짜를 접수 시각(KST)으로 계산

위 여섯이 다 없고 "첫날·둘째 날"만 있으면 날짜를 만들지 않는다. **「첫날 날짜」 하나만** 묻는다. 결정 15 의 「대체 소스」 중 마지막이 고객이다.

### 3-7. 빈칸 채우기·판정

초안 §4.5~4.6 을 받는다. 시각 없는 항목은 예약 시각 → 표의 시간 칸 → 앞뒤 항목과 영업시간으로 규칙 배치 순으로 채운다.
planner 의 활동 90분·식사 60분(`app/modules/travel_ops/planner.py:65-82`)을 **설정으로 옮겨** 같이 쓴다.

좌표 없는 장소, 날짜 없는 항목, 시각 없는 예약은 등록 전에 걸린다.

### 3-8. 확인 화면 → 등록

초안 §7 의 세 화면을 받는다. MVP 는 **한 화면**으로 합친다.

- **일정표.** 항목마다 배지를 단다: `원문 그대로` · `규칙으로 배치` · `조회로 확인` · `확인 필요`.
- **근거 보기.** 받아쓴 줄과 그 조각 그림을 보여 준다.
- **확인 필요 항목**을 위로 올린다.
- 장소는 **고른 하나**만 보인다. 옆에 「다른 장소로 고치기」 입력칸을 둔다. 후보 A/B/C 를 나열하지 않는다.
- 「등록하고 관리 시작」 버튼 하나. 서버가 다시 판정한 뒤 `_create_trip(tenant, CreateTrip)` 을 부른다(`trip_api.py:349`).
- `request_id` 는 `intake_id + revision` 이다. 탭 두 개에서 같은 확인을 눌러도 두 번 등록되지 않는다.

예약번호가 있는 항목은 `detail.booking` 으로 싣는다. `_create_trip` 이 `bookings` 행을 만들어 항목에 연결해야 한다.
지금은 모든 항목의 `booking_id` 가 비어 있다(`trip_api.py:439-444` 확인). 이 연결이 있어야 예약 변경 감시와 승인 경계가 돈다.

## 5. 근거 보존

값마다 근거가 붙는다. 종류는 셋이다(초안 §6 그대로).

- **원문**: 파일·쪽·조각·줄·셀 위치와 발췌
- **조회**: 제공자·장소 id·조회 시각
- **규칙**: 규칙 이름·판·입력

MVP 에서 원문 위치는 **쪽·조각·줄·셀**까지다. bbox 는 OCR 엔진을 들이면 추가한다.

근거는 `ItemIn.detail.provenance` 로 등록까지 들고 간다. 그러면 여행계획서 링크에서도 「왜 이렇게 읽었나」를 보여 줄 수 있다.
고객이 고친 값은 **원문보다 높은 근거**가 되고, 이전 근거는 지우지 않는다(`itinerary_versions` 처럼 쌓는다).

## 11. 채팅 질문이 가리키는 일정 항목 찾기 — 제안 `[2026-09-29 추가 · 확정 대기]`

계획을 읽어 등록한 뒤, 고객이 채팅으로 「궁궐 몇 시에 가요?」처럼 **이름 없이** 물어도 어느 항목인지 알아듣게 하는 방법이다.
지금 코드는 질문 속 단어가 일정 제목에 그대로 있어야 찾는다(`itinerary_team.py` 의 `mentioned_item`).

**실측**: 가상 일정 2개·Codex 가 쓴 질문 90개(보류 묶음)로 모델 20여 종을 재었다. 전체는
[여행일정_질문인식_모델비교_2026-09-29.md](../research/여행일정_질문인식_모델비교_2026-09-29.md) 에 있다.

| 방식 | 맞음(90개) | 엉뚱한 항목으로 답함 |
|---|---:|---:|
| 지금 코드 | 33 = 37% | 10 |
| 규칙 + 임베딩 + 별칭(LLM 없음) | 63 = 70% | — |
| 재평가·임베딩 모델 단독(최신판 포함, 최고) | 73 = 81% | 15 |
| **LLM 이 항목 번호만 고름 (Gemma 4 26B)** | **87 = 97%** | **2** |
| 　└ + 규칙 되확인 | 86 = 96% | **0** |

**제안**

1. LLM 은 일정 목록에서 **번호 하나 또는 「없음」만** 낸다. 시각·장소·가격은 쓰지 않는다 — 답 문장은 지금처럼 DB 값과 문장 틀이다.
2. 질문에 날짜·시간대·시각·종류가 있는데 고른 항목이 그 조건 밖이면 버린다(규칙 되확인).
3. 못 찾으면 「못 찾았다 + 일정 요약」으로 답한다. 답에 「○○ 일정 기준으로 답했어요」를 붙인다.
4. LLM 이 멈추면 규칙 + 임베딩 + 별칭으로 대체한다(결정 15). 임베딩은 「해당 없음」을 못 가르므로 **규칙이 일정 질문으로 본 경우에만** 쓴다.

**확정 전에 남은 것**: 서비스 서버 GPU 에 26B(약 17GB 압축판)가 올라가는지 `[미확보]` · 실제 고객 채팅으로 다시 재기 ·
7일·50항목 규모 `[미확보]`. 이 세 가지가 끝나기 전에는 **제안**이다. 코드 세션에는 아직 넘기지 않았다.

**2026-09-30 갱신 — Codex 합의**: 기본은 위 제안 그대로(**A: 규칙 + 로컬 26B 번호 짚기 + 규칙 되확인**)로 확정 후보를 굳혔고, **Jev(결정 전용 모델)는 시험 후 「재확인·기권 층」으로 추가할지 정한다.** 다중 모델 합의는 이 표본에서 이득이 표본 오차 안이라 채택하지 않는다.
판정은 **오지목 최우선**이며, 「엉뚱한 답 ≤1%」를 말하려면 **약 300문항에서 0건**이어야 한다(0/90 의 95% 상한은 3.3%). 확정 전 실험 순서·판정 기준은
[모델 비교 문서 §13](../research/여행일정_질문인식_모델비교_2026-09-29.md).

## 12. 구조 조회 원칙 — LatWeave 확인 결과의 반영 `[2026-09-30 추가 · 제안 · 코드 세션 인계 전]`

근거·측정은 [`program/research/여행일정_질문인식_모델비교_2026-09-29.md`](../research/여행일정_질문인식_모델비교_2026-09-29.md) §16-A · §25. 9월 논문(LatWeave, arXiv 2609.27225, 프리프린트)의 「답을 낼 때 LLM 을 안 부르고 조건 교집합·순서 비교·구조적 기권으로 처리」하는 방식이 우리 구조와 같은 방향이라, 다음 네 가지를 사양 후보로 둔다. **아직 제안이며 코드 세션에 넘기지 않았다.**

1. **조건 조회의 세 갈래**: 날짜·끼니·종류·순서로 후보를 좁혀 **1개면 확정 · 0개면 모델 없이 「일정에 없음」 · 2~5개면 후보를 보여 주며 되묻기**(단, 모델이 그 후보 안에서 고를 수 있으면 그 답). 6개 이상은 지금처럼 모델 몫.
2. **답의 근거 기록**: 답마다 `{경로, 뽑은 조건, 남은 후보 수, 호출한 전문가, 답}` 을 남긴다 — 고객 질문 → 답을 재현·검토할 수 있고 오답 원인이 바로 읽힌다(연구 문서 §25 표본 176건).
3. **조건 추출은 규칙 우선**: 날·순서·끼니·앞뒤는 규칙(정규식)이 읽고, 규칙이 못 읽는 표현만 모델(질문 계획 1회 호출 후보)에게 맡긴다.
4. **계획서 읽기 단계**: 계획서를 항목으로 뽑을 때 **기준 어휘표로 정규화(장소명·시간대·끼니 표현)하고 중복 항목을 제거**한다. 추출이 빠지면(논문의 성능 저하 원인 90.6%가 추출 범위 부족) 뒤 조회가 아무리 정확해도 답이 없으므로 **추출 범위를 따로 재는 항목**을 §7 평가에 둔다.

한계: 이 규칙들이 작동하는 문제가 우리 시험 세트에 거의 없어 정확도 이득은 측정되지 않았다(176문제 중 1개). 사양의 가치는 안전성(임의로 찍지 않음)과 감사 가능성이다.
