# 여행 일정 — 고객 질문이 가리키는 항목 찾기, 모델 비교 (2026-09-29)

`[실측 2026-09-29]` 고객이 채팅으로 「궁궐 몇 시에 가요?」「강에서 노 젓는 거 취소돼요?」처럼 **일정 항목의 이름을 안 부르고 물어도**
그 항목을 알아듣게 하는 방법을 찾았다. 유료 GPU 서버 1대로 모델 20여 종을 같은 질문으로 재었다.
코드·시험 문제·작은 결과는 [`program/scripts/plan_qa_bench/`](../scripts/plan_qa_bench/README.md) 에 있다.

> `[2026-09-30]` 결론만 모은 한 장 요약은 [`여행일정_질문인식_정리본_2026-09-30.md`](여행일정_질문인식_정리본_2026-09-30.md) 에 있다. 이 문서는 그 근거·표·실패 기록의 원본이다.

## 0. 결론 (먼저)

| | 값 |
|---|---|
| 지금 코드(질문 속 단어가 일정 제목에 그대로 있어야 찾는다) | 90개 중 **33개 = 37%** |
| **가장 좋은 방식** — LLM 이 일정 목록에서 **번호 하나만** 고르고, 규칙으로 되확인 | Gemma 4 26B: **87/90 = 97%**, 되확인을 붙이면 **86/90 = 96%** · 엉뚱한 항목으로 답한 경우 **0건** |

1. **답 문장은 그대로 DB 값과 문장 틀로 만든다.** 모델이 하는 일은 「몇 번 항목인가」를 고르는 것뿐이라, 시각·장소·가격을 지어낼 자리가 없다.
2. 임베딩·재평가 모델은 **「이 질문은 일정에 해당 없음」을 못 가른다.** 어느 항목이든 하나를 고른다. 그래서 단독으로는 못 쓴다.
3. 이 결과는 **가상 일정 2개·Codex 가 쓴 질문 기준**이다. 실제 고객 채팅으로 다시 재기 전에는 확정이 아니다(§7).

## 1. 무엇을 알아보려 했나

- 문제: 질문 한 개 → **일정 항목 번호 하나** 또는 **「해당 없음」**.
- 요구(2026-09-29 사용자): 「사용자가 질문할 때 임베딩해서 여행 계획에 합당한 쪽에 관련된 답변을 잘하게」, 그리고 「LLM 은 할루시네이션이 있는데 뭘 믿고 쓰나 — RAG 로 정확하게 답하니 고객 질의 인식만 잘 받게」.
- 그래서 **모델이 문장을 쓰지 않는 구조**로 한정했다. 규정 답은 규정 원문 문장을 출처와 함께 붙이고, 일정 답은 DB 값을 틀에 넣는다(`app/modules/travel_ops/trip_replies.py`, `itinerary_team.py`). 모델은 **번호만** 낸다.
- 지금 코드가 항목을 찾는 방법은 `itinerary_team.py` 의 `mentioned_item`(제목·장소 이름의 단어가 질문에 나오는지 센다)이다.

## 2. 시험 방법

### 시험 묶음

| 묶음 | 문항 | 누가 썼나 | 쓰임 |
|---|---:|---|---|
| mine38 | 38 | 이 세션(사람이 쓴 것과 같은 방식) | 개발용(기준선 정하기) |
| dev50 | 50 | Codex — 질문 100개의 짝수 번째 | 개발용 |
| **test50** | 50 | Codex — 질문 100개의 홀수 번째 | **판정용(보류)** |
| **hard40** | 40 | Codex — 일정을 보여 주고 **이름 없이 설명만 하는 질문 위주로** 새로 쓰게 함 | **판정용(보류)** |

- **판정은 test50 + hard40 = 90개**로 한다. 기준선(문턱)은 mine38 + dev50 에서만 정했다.
- Codex 에게는 이 세션의 방식을 알려 주지 않았다(시험 문제가 방식에 맞춰지는 것을 막으려고).
- 질문 종류: 직접 이름(12) · 이름 없는 설명(20) · 상대 시간(15) · 영어(10) · 일본어(4) · 중국어(4) · 오타·구어(8) · 순서(7) · 일정 항목에 붙은 규정 질문(10) · **해당 없음(10)**. 새 40개는 지식 기반 설명(14) · 활동 설명(6) · 순서(5) · 영어(5) · 일본어(2) · 중국어(2) · **비슷하지만 일정에 없는 것(6)**.
- 일정: Codex 가 만든 4일·22항목(서울 실제 장소) 1개, 이 세션의 3일·11항목 1개.

### 채점

- **맞음**: 정답 항목을 골랐거나, 해당 없음 질문에 「없음」을 냈다.
- **엉뚱한 답**: 틀린 항목을 골랐거나, 해당 없음 질문에 항목을 골랐다. **고객에게 잘못된 항목의 정보가 나가는 경우**라 가장 나쁘다.
- **못 찾음**: 항목이 있는 질문에 「없음」. 「못 찾았다」고 말하고 끝나므로 상대적으로 덜 나쁘다.

### 방식

| 기호 | 방식 |
|---|---|
| A | **지금 코드**: 제목·장소 이름 단어가 질문에 나오는지 |
| B | 규칙 + 임베딩(bge-m3) + 별칭 색인. 규칙이 날짜·시간대·시각·종류로 후보를 좁힘. LLM 없음 |
| C | **LLM 번호 짚기**: 일정 전체(번호·일차·날짜·시각·종류·제목·장소)를 주고 `{"item": 번호 또는 null}` 만 받음. JSON 스키마 강제, 생각 모드 끔, 온도 0 |
| C+ | C + **규칙 되확인**: 질문에 날짜·시간대·시각·종류가 있는데 고른 항목이 그 조건 밖이면 버림(순서 질문은 제외) |
| D | **재평가 모델**(질문·항목 쌍마다 관련도 점수) — 문턱을 넘는 최고점 항목 |
| E | **임베딩 단독**(질문↔항목 코사인) |

규칙이 읽는 것: 첫날·둘째 날·N일차·마지막 날·요일·오늘·내일·「10월 4일」(영어·일본어·중국어 표현 포함), 아침·점심·오후·저녁, 시각, 식사·숙소·이동, 「다음·전에」 같은 순서 표현.
모델은 모두 **올라마 기본 압축판**(Q4 계열)으로 돌렸다. 원본 정밀도에서는 다를 수 있다 `[미확보]`.

### 3-5. 읽는 법

- **재평가·임베딩은 「해당 없음」을 못 가른다.** 항상 하나를 고르니 엉뚱한 답이 9~27건 났다. Qwen3-Reranker-4B 만 반대로 조심스러워(못 찾음 14) 엉뚱한 답이 9건이었다.
- **규칙으로 후보를 먼저 좁히면** 모든 모델이 크게 오른다(재평가 +5~17개, 임베딩 +31~39개). 규칙이 「둘째 날 저녁」 같은 말을 정확히 읽기 때문이다. 그래도 LLM 방식을 넘지 못했다.
- 이 작업에서 재평가 모델이 약한 이유로 추정하는 것: 이 모델들은 「질문 ↔ 답이 든 긴 문단」으로 학습됐는데 우리 후보는 「10월 11일 09:00 창덕궁 후원 관람」 같은 **짧은 한 줄**이다 `[추정]`.

### 확정 전에 확인해야 할 것

- **서비스 서버의 GPU**: 26B(약 17GB 압축판)를 올릴 수 있는지. 못 올리면 12B(92%)나 서버 메모리 넘김으로 느려짐 `[미확보]`.
- **실제 고객 채팅**으로 다시 재기: 지금 질문은 전부 작성된 것이다. DB 에 쌓인 실제 채팅 질문에 정답을 달아 다시 재야 한다.
- **7일·50항목 규모**: 일정이 길어지면 프롬프트가 길어져 속도·정확도가 달라진다 `[미확보]`.
- 일정이 짧아(11~22항목) 통째로 보여 줄 수 있었다. 항목이 아주 많아지면 후보를 먼저 좁히는 단계(규칙+임베딩)가 필요할 수 있다.

### 교훈 — 다음 실험을 위해

1. **전체를 돌리기 전에 질문 1개로 답이 나오는지 먼저 본다.** Muse 는 40분을 돌려 0/90 이었다.
2. **모델을 받으면 채점 직후 지운다**(저장소 캐시까지). 용량 제한이 있다.
3. **결과 파일은 임시 파일에 쓴 뒤 바꿔치기한다.**
4. **오늘 기준 최신판만 쓴다**(사용자 지시). 이전 판을 섞으면 서버 시간이 낭비된다.
5. **문턱은 개발용 묶음에서만 정하고, 판정은 보류 묶음으로 한다.**
6. **결과는 그날 문서로 옮긴다.** 이번에는 실험이 끝난 뒤에야 문서를 썼고, 그동안 결과가 임시 폴더에만 있었다.

## 8. 제안 설계 (확정 전)

1. 질문에서 규칙으로 날짜·시간대·시각·종류·순서 표현을 읽는다.
2. **LLM 한 번 호출**: 일정 전체를 번호와 함께 주고 항목 번호(또는 null)만 JSON 스키마로 받는다. 생각 끔, 온도 0. **번호 외의 값은 쓰지 않는다.**
3. 규칙 되확인: 조건이 있는 질문인데 고른 항목이 조건 밖이면 버린다.
4. 못 찾으면 지금처럼 「못 찾았다 + 일정 요약」으로 답한다(틀린 항목으로 답하지 않는다).
5. 답에 「○○ 일정 기준으로 답했어요」를 붙여 잘못 짚어도 고객이 알게 한다.
6. LLM 이 멈추면 대체(결정 15): 규칙 + 임베딩 + 별칭(70%)을 쓰되, **규칙이 일정 질문으로 본 경우에만** 쓴다(임베딩은 「해당 없음」을 못 가른다).
7. 답 문장은 지금처럼 DB 값과 문장 틀로 만든다.

## 10. 실제 질의 점검 — 「실제 고객」 질문은 아직 없다 `[실측 2026-09-29 밤]`

이 실험의 97%가 **실제 성능**인지 보려고 DB 에 쌓인 채팅을 세었다. 결론부터: **실제 고객의 질문은 0개**다. 사람이 친 것은 팀원이 웹에서 시험한 문장뿐이다.

| 어디 | 무엇 | 양 | 실제 고객? |
|---|---|---|---|
| 접수 기록(`case_events`), 채널 `mcp` | 부하·시험이 만든 「같은 문의 <번호>」 「배송 문의 <번호>」 — 쇼핑몰 시절 흔적 | 464건(09-06~14) | 아님(자동) |
| 접수 기록, 채널 `trip_message` | 웹 채팅에 팀원이 시험 입력 | 266건 · 서로 다른 문장 **96개**(09-27~29) | 아님(팀) |
| 대화 표(`trip_chat_turns`) | 자동 시험 대화 | 3,512줄 = 1,756쌍 · 고객 문장 **77종**(각 평균 약 23번 반복, 한 번만 나온 문장 0개) · 1,286개 여행 중 여행 표(`trips`)에 실제 있는 것은 18개 | 아님(자동) |
| 그 밖 채널(`system` 10 · `chat` 8 · `test` 2 · `api` 1 · `web` 1) | 감시·수동 시험 | 22건 | 아님 |

- 팀 입력 96개와 자동 시험 77종을 합치면 서로 다른 문장 **132개**(겹침 41개). 정답이 아직 없다 — [`fixtures/team_typed_132.json`](../scripts/plan_qa_bench/fixtures/team_typed_132.json) 에 라벨링 재료로 저장했다.

### 실제 입력의 모습 (132문장, 정규식으로 센 값 — 정확한 분류가 아니라 대략)

| 특징 | 문장 수 | 비율 |
|---|---:|---:|
| 「바꿔·되돌려·다른 데로」 같은 **변경 요청** | 44 | 33% |
| 장소 이름을 직접 부름(「경복궁 주소」) | 34 | 26% |
| 화면 버튼의 **고정 문구**(「하루 일정을 요약해 주세요」 등 4종) | 26 | 20% |
| **앞 대화를 가리키는 말**(「그 식당」「그건」「방금 바꾼」「다음식당」) | 12 | 9% |
| 순서·날짜로 가리킴(「첫 식당」「2일차 첫 식당」) | 8 | 6% |
| 글자 수 중앙값 **13자**, 20자 이하 | 99 | **75%** |

같은 기준으로 이 실험의 시험 문제(Codex 작성 140개)는 **중앙값 26자, 20자 이하 30개(21%)**다. 실제 입력은 훨씬 짧다.

### 시사점

1. **이 실험의 97%를 실제 성능으로 읽으면 안 된다.** 시험 문제는 길고 서술적인데, 실제 입력은 짧고 변경 요청 비중이 크다. 분포가 다르다.
2. **앞 대화 맥락을 안 줬다.** 「그 식당 전화번호 뭐야」「방금 바꾼 걸 원래대로」는 「무엇」이 앞 대화에 있다. 항목 짚기만이 아니라 **직전 2~3턴과 방금 바꾼 항목**을 같이 줘야 하는지는 `[미측정]`.
3. **버튼 문구 20%는 규칙이 이미 정확히 읽는 말**이라(`trip_facts.py`의 사실 질문 분류) 모델에 안 맡겨도 된다.
4. 서비스 공개 전에는 실제 고객 질문을 모을 방법이 없다. 대안: 팀 시험 입력을 늘리고, 지인 시연에서 동의를 받아 수집.

### 더 모아야 하는 것

1. **여행 도메인의 짧은 실제 스타일 질문과 정답** — 수백 개 이상. 정답: 어느 항목 또는 「없음」, 유형(변경·질문·신고…).
2. **다회전 대화**(앞 대화 포함) — 「그 식당」류를 다루려면 필요.
3. **합성 데이터 만드는 파이프라인** — 관광공사 장소 + 일정 + LLM 변형. 우리가 만들 수 있다.
4. 법령 원문(RAG 용).

### 제안 순서

1. **실제 스타일 시험 세트를 만든다**(짧고, 변경 요청·앞 대화 지시 포함, 정답 라벨). 팀 입력 132문장을 사람이 확인한 정답표로 만들고, 같은 스타일의 합성 질문을 더한다.
2. **파인튜닝 없이 최고점을 찾는다**: 프롬프트 변형 · 앞 대화 맥락 넣기 · 두 번 물어 합의 · 두 모델 합의 · 7일·50항목 규모 · 반복(편차).
3. 그래도 모자라거나 서비스 GPU 가 작으면 **작은 모델로 증류**(LoRA).

## 13. yok3x fork 세션 참고 → 적용 (Codex 합의 2026-09-30)

`yok3x : idea (fork)` 세션이 하는 일을 읽고 우리 일정 질문 인식에 적용할 길을 Codex(`gpt-6-sol`)와 따졌다. **1회차에 합의**했다(결정 기록: [`consensus/20260930_jev_apply/decision.md`](../scripts/plan_qa_bench/consensus/20260930_jev_apply/decision.md)). 검토자는 기계(Codex)이며 사람이 본 것이 아니다.

### 그 세션이 하는 일 (읽은 범위: 기록 4,875개 중 마지막 약 70개 + Jev 공개 자료. 그 세션의 문서(33절·17절)는 yok3x 폴더에서 찾지 못함 `[미확인]`)

- **Jev**(TypeSafe AI, 2026-09-15 공개)는 글을 쓰지 않는 **결정 전용 모델**이다. 질문 유형은 choice(선택지별 확률)·score·noul(예/아니오). 도구는 classify(label·probability·margin·confidence·decision `auto`/`review`)·check·score·**rank**·ask. 약 250ms/호출, 입력 100만 토큰당 0.042달러, 입력 한도 약 32k 토큰. 확률은 보정돼 있으나 「집단에 대한 것이지 개별 답의 보장이 아니다」. `[외부 — 개인 측정 gist·저장소 README·LangChain 글을 요약 도구가 읽은 것, 원문 전체는 아님]`
- **실측된 함정**(2026-09-18, 개인 측정): `items[i]` 위치 인덱스는 150개에서 86/320, 25개에서 29/320 오답. **키가 있는 객체**(`items.k137`)나 질문에 항목을 직접 넣으면 320개에서 0/320 오답.

### 오프라인 앙상블 재계산 (저장된 모델 번호, 비용 0) — [`vote_offline.py`](../scripts/plan_qa_bench/vote_offline.py)

같은 90문항(test50 + hard40), 각 1회. **주의: 모델을 이 90문항 성적으로 골랐으므로 낙관적이다.**

| 방식 | 맞음 | 엉뚱한 답 | 못 찾음 |
|---|---:|---:|---:|
| 26B 단독 | 87/90 = 97% | 2 | 1 |
| 26B + 규칙 되확인(A) | 86/90 = 96% | **0** | 4 |
| 26B·12B 가 같을 때만 답 | 85/90 = 94% | **0** | 5 |
| 26B 기본, 다른 둘 중 1개 이상 동의해야 답 | 87/90 = 97% | **0** | 3 |
| 3모델(26B·Qwen3.8·12B) 2표 이상 | 88/90 = 98% | **0** | 2 |
| 3모델 3표 전부 같을 때만 | 80/90 = 89% | 0 | 10 |

- A 가 이미 엉뚱한 답을 0 으로 만든 위에 합의를 얹어도 **맞음 차이가 2문항**이라 표본 오차 안이고, 비용은 2~3배(Qwen3.8 은 이 서버에서 45초/질문)다. 그래서 합의(D)는 채택하지 않는다.

### 결정 (합의) — 확정 후보

1. **기본 = A**: 규칙(버튼 문구·날짜·시간대·종류)이 먼저 읽고, 로컬 Gemma 4 26B 가 **항목 번호만** 고르며, 규칙으로 되확인. 못 찾으면 「못 찾았다 + 일정 요약」. 답 값은 DB 에서만.
2. **Jev = 시험 후 결정.** 통과하면 A 다음 **재확인·기권 층**으로 추가(C). 탈락 조건: 실제 스타일 보류 세트에서 오지목이 늘거나 · 개인정보를 가린 뒤 성능이 떨어지거나 · 약관·보관 조건을 확인 못 하면.
3. 로그확률 기권(E)은 실험 후보로 유지. 증류(F)는 서비스 GPU 에서 지연·비용이 한도를 넘을 때.

- **「이름 없이 설명만으로 항목을 가리키는」 질문(우리 hard40 같은 것)은 132문장 중 0개였다.** 어려운 묶음(지식 설명 14 + 순서 9)은 시험이 일부러 넣은 것이고, 지금 관측된 입력에는 없다.
- 그래서 「무거운 작업」은 큰 모델이 필요한 읽기가 아니라 ① **앞 대화 상태**(방금 바꾼 항목·직전 대화) ② **유형 분류**(변경·되돌리기·신고·질문·범위 밖) ③ **범위 밖 거르기**다. 이 셋은 상태 관리 + 규칙 + 작은 분류기의 몫이다.

### 14-6. 잠정 결론

> `[2026-09-30 정정]` 아래의 「E4B·12B 합의 → 갈릴 때만 26B」(계단식) 구성은 **사용자 결정으로 채택하지 않는다**(합의·투표 방식 금지). 수치는 참고용으로만 남기고, 설계는 §15 의 **파트별 배치**로 간다.

- **관측된 입력 기준으로는 26B 단독이 필요하지 않을 가능성이 크다.** 규칙(버튼 문구·날짜·시간대·종류·이름)이 먼저 읽고, 가벼운 LLM(E4B, 필요하면 12B 합의)이 번호를 고르며, 못 찾으면 「못 찾았다 + 일정 요약」으로 답하는 구조가 엉뚱한 답 0 을 지킨다. 26B 는 **불일치·어려운 질문에만** 부르는 선택 층이다.
- 이 결론은 **실제 스타일 보류 세트로 다시 재기 전에는 잠정**이다. 그 세트가 있어야 「어려운 묶음」이 실제로 얼마나 오는지, 앞 대화 맥락이 얼마나 중요한지 알 수 있다.
- 기본 설계(§13 합의 A)는 그대로 두고, 이 절은 **가벼운 단계형을 대안 후보로 추가**한 것이다. Codex 와의 재합의는 OpenDecider·WeMM 결과까지 나온 뒤에 한다.

### 15-4. 「구조로 푸는」 방식 — 순서·상대 위치만 따로 시험

착안: 「N째 날 · 몇 번째 · ~ 다음/전」은 모델이 추측할 문제가 아니라 일정 항목 사이의 관계를 따라가면 정해진다(그래프의 발상. 항목 51개라 그래프 DB 제품은 불필요, 「다음 항목·같은 날·같은 종류」 관계를 메모리 구조로 두면 된다).
구현: 문장에서 **날(day)·순서(pos)·종류(kind)·끼니(meal)·앞뒤(rel)·기준 항목(anchor)** 을 뽑고 [`slot_lookup.py`](../scripts/plan_qa_bench/slot_lookup.py) 가 일정에서 항목을 확정한다(모델은 값을 만들지 않는다). 뽑는 쪽 세 가지를 비교했다.
- S1: Jev 가 6개 자리표를 모두 뽑는다 ([`jev_slots.py`](../scripts/plan_qa_bench/jev_slots.py))
- S2: **규칙(정규식)이 날·순서·종류·끼니·앞뒤를 읽고** Jev 는 기준 항목만 짚는다 ([`rule_slots.py`](../scripts/plan_qa_bench/rule_slots.py))
- S3: 규칙 우선, 규칙이 못 읽은 칸만 Jev 로 채움

시험 세트 둘: **ord2**(48문제, 개발용 — 결과를 보고 규칙과 조회 코드를 고쳤다) · **ord3**(42문제, 판정용 — 규칙을 쓰기 전에 문장을 써 뒀지만 **완전한 블라인드는 아니다**: 같은 사람이 문장도 규칙도 썼고, 규칙을 쓸 때 ord3 문장의 표현 유형(끝나면·가기 전·둘째 체크인 등)을 알고 있었다). 둘 다 [`eval_ord.py`](../scripts/plan_qa_bench/eval_ord.py) 로 채점, 문장 정의는 [`build_ord2.py`](../scripts/plan_qa_bench/build_ord2.py) · [`build_ord3.py`](../scripts/plan_qa_bench/build_ord3.py).

| 방식 | ord2 (개발용 48) | ord3 (판정용 42) |
|---|---:|---:|
| Jev 직접 짚기 | 19/48 = 40% · 엉뚱 20 | 14/42 = 33% · 엉뚱 17 |
| Codex 루나(정의 명시) | 34/48 = 71% | 28/42 = 67% |
| Codex 솔(정의 명시) | 47/48 = 98% | 42/42 = 100% |
| S1 Jev 자리표 + 코드 | 30/48 = 62% | 33/42 = 79% |
| S3 규칙 우선 + Jev 빈 칸 | 35/48 = 73% | 35/42 = 83% |
| **S2 규칙 자리표 + Jev 기준항목 + 코드** | **46/48 = 96%** (못 정하면 Jev 직접으로 대신 47/48 = 98%) | **42/42 = 100%** (엉뚱 0) |

- **결론: 순서·상대 위치는 모델이 아니라 「규칙으로 자리표를 읽고 코드로 관계를 따라가는」 쪽이 압도적으로 낫다.** Jev 를 자리표까지 뽑게 하면(S1) 「넷째 날 마지막」에서 넷째를 순서로 읽고 「이틀째·이레째」를 못 읽는 오류가 난다. 규칙이 그 부분을 맡으면 Jev 는 기준 항목 짚기(이름 직접 짚기 = 만점 근처)만 하면 된다.
- 이 개선의 절반은 규칙과 조회 코드를 ord2 오류를 보고 고친 결과다. ord3 의 100% 는 **「내가 아는 표현 범위 안에서」의 결과**이고, 실제 고객이 쓰는 표현(예: 「다다음 날」「사흘 뒤」)에서의 성능은 `[미측정]`이다. 규칙이 못 읽으면 「못 정하면 Jev 직접」으로 대신하는 안전망이 있다.
- 중간에 조회 코드를 고치면서(순서와 조건으로 기준 항목을 정하기·기준 항목이 말한 날과 다르면 버리기) S1(모델이 자리표를 다 뽑는 방식)은 오히려 77% → 62% 로 내려갔다. 모델이 내는 잘못된 순서 값에 코드가 더 민감해졌기 때문이다. 규칙이 자리표를 맡는 S2 는 영향이 없었다.
- ord2 의 문제 하나(「브런치 다음 일정」)는 브런치가 두 번 있어 정답이 하나로 안 정해져 **정답 문장을 고쳐 다시 돌렸다**(라벨 결함이지 모델 튜닝이 아니다).

## 16. 결정론적 RAG 관련 논문 확인 `[확인 2026-09-30 — 초록만 읽음]`

사용자 문의: 「아직 출시 안 된 결정론적 RAG 논문이 준비 단계라던데 적용할 만한가」. **공개 전(준비 중) 논문은 볼 수 없다.** 공개된 것 중 「결정론적 검색 + LLM」에 해당하는 것을 찾았다. 전문은 못 열었고(403) 초록·요약만 읽었다.

### 16-A. LatWeave (arXiv 2609.27225, 2026-09-23, 프리프린트) `[확인 2026-09-30 — 초록 + 본문 일부 요약, 코드 공개 여부 미확인]`

[논문](https://arxiv.org/abs/2609.27225): 「Meet, Compare, or Abstain: LatWeave for Deterministic Multi-Hop Question Answering on Knowledge Lattices」.
지식을 여러 차원의 격자(각 차원은 「구체성 순서」를 가진 방향 비순환 그래프)로 만들고, 질문을 세 연산으로 바꿔 **답을 낼 때는 LLM 을 전혀 부르지 않는다**. Meet = 조건 교집합 · Compare = 격자 순서 비교 · Abstain = 구조적 기권(조건 충돌·결과 집합이 빔).

- LLM 이 쓰이는 곳: ①지식 구축(문서에서 사실 추출, Claude · 온도 0 · 질문을 모르는 상태) ②질문 계획(문장 → 자료형 있는 계획, 질문당 LLM 1회).
- 저자 보고 수치: MetaQA 3-hop any-hit 0.9975(39,093문항) · 2WikiMultihopQA EM 0.865(held-out 1,258) · IIRC 기권 정확도 0.971, 누출률 0.029. 검색 p50 18.7ms.
- **붙여 받은 소개글이 「성능저하」로 뭉갠 부분**: HotpotQA EM 0.1687(해결된 것만 0.4545) · MuSiQue EM 0.0248. 저자는 원인을 격자 밖(추출 범위 부족 90.6%, 질문 계획 9.4%)으로 돌린다. 정형 질문(MetaQA·2Wiki)에서만 높고 자유 문장에서는 크게 떨어진다.
- 평가는 벤치마크 문서에서 LLM 이 지식을 뽑은 뒤 같은 문서에 대한 질문으로 한다. 피어리뷰 전 프리프린트다.

**우리에게**: 방향은 우리가 §15 에서 만든 구조(LLM 은 자리표만 뽑고 코드가 조건 교집합·순서·기권을 처리)와 같다. 새 도구를 붙이는 것이 아니라 **우리 구조의 이름과 설계 원칙을 뒷받침**한다.
적용할 것: (1) 항목을 차원(날짜·시간대·끼니·종류·장소 묶음)의 격자로 두고 조건 교집합 후보가 **1개면 확정 · 0개면 구조적 「없음」 · 여러 개면 모델이 찍지 않고 후보를 보여 되묻는** 세 가지 결과로 통일 (현재는 여럿이면 모델 짚기로 넘어간다). (2) 계획(자리표)을 답의 근거로 로그에 남겨 재실행·감사 가능하게. (3) 「고객 계획 읽기」의 추출 단계에 차원 어휘표·정규화·중복 제거 원칙 참고.
적용 못 하는 것: 긴 문서 다단계 추론(우리 일정은 이미 구조화됨), 잡담·범위 밖 판정(격자 문제가 아니라 별도 관문이 필요).

### 19-1. 구조

문장 하나가 들어오면 다음 순서로 처리한다. 앞 단계가 확정하면 뒤 단계는 부르지 않는다.

1. **절 분석**(코드): 「A 말고 B」는 B 가 대상·A 는 제외(또는 기준 항목), 「A 취소하고 B …」(요청 둘)는 **먼저 말한 절 A 가 대상** — 연결어는 명시한 동사+「고」·「그리고」·쉼표·물음표뿐(「끝나고」「먹고」는 자르지 않음).
2. **규칙 자리표 + 관계 조회**(코드): 날·순서·종류·끼니·앞뒤를 정규식으로 읽고 일정 관계를 따라 항목을 확정. 「한 시간 뒤로」 같은 시간 이동은 순서·위치로 읽지 않는다. 앞뒤 관계의 **기준 항목만** 모델(anchor 전문가)에게 묻는다. 모호하면(후보 여럿·기준 항목 불명) 기권해 다음 단계로 넘긴다.
3. **관문 전문가(gate)**: 일정 항목에 대한 문의가 아니면(잡담·요금·시세·날씨·일반 추천) 「없음」.
4. **짚기 전문가(point)**: 대상 절이 가리키는 항목 번호(없으면 null). 앞 대화를 함께 준다.
5. **검증(verify)**: 짚은 항목이 문장과 정말 맞는지 같은 모델이 한 번 더 확인(§18 「검증 관문」 아이디어).

전문가 세 역할에 E4B/12B 중 누구를 쓸지는 **heavy 개발용 44문제의 정확도로만** 골랐다(고른 배치: gate = E4B · anchor = E4B · point+verify = 12B, 개발 44/44 — 동률 중 12B 를 덜 쓰는 쪽). 26B·Jev·투표는 쓰지 않았다.

|---|---|---|---|---|
| 자리표 읽기 · 관계 조회 | 날·순서·끼니·앞뒤를 읽고 항목 확정 | **모델 아님 — 규칙(정규식) + 코드** | 순서·상대 위치에서 Jev 직접 33%·12B 직접 6/8 인 문제를 코드가 100%(판정 ord3 42/42) | 규칙이 아는 표현 범위 안에서만. 「N번째 방문」 등 미구현 |
| 절 분석 | 「말고」·「~하고」로 대상 절 정하기 | **코드** | 요청 둘: 26B 직접 5/8 → 구조 8/8 (mix4) | 「먼저 말한 항목이 대상」이라는 정의에 의존 |
| 관문(gate) | 일정 문의인지 판정, 아니면 「없음」 | **Gemma E4B** | 개발 44문제에서 E4B 와 12B 가 동률(44/44) → 빠르고 가벼운 쪽 | 「삭제해줘」(앞 대화 속 대상)를 잘못 거름. 다른 모델과 비교한 적 없음 |
| 기준 항목(anchor) | 「~ 다음」의 기준이 되는 항목 짚기 | **Gemma E4B** | 위와 같은 동률 → 가벼운 쪽 | mix4 에서 2건 실패(「토속촌」을 항목에 못 이음 · 「먹어」에 끌림). 12B 로 바꿔도 총점은 같았다(81/88) |
| 짚기(point) + 검증(verify) | 대상 절이 가리키는 항목, 맞는지 재확인 | **Gemma 12B** | 개발 44문제: E4B 34/44 대 12B 44/44 (같은 역할 E4B 는 「못 찾음」이 21건으로 무너짐) | 검증이 정확한 이름도 거부하는 오탐(남대문시장 2회) |

- **후보 풀이 사실상 「Gemma 4 계열 두 크기(E4B·12B)」뿐이었다.** 사용자의 목표(여러 모델을 알맞은 곳에)를 절반만 구현한 것이다. 이 구조에서 다른 계열을 역할별로 겨뤄 본 적이 **없다**.
- 다른 모델을 이 구조에 안 넣은 이유는 앞 측정(직접 짚기, 기존 판정 90 · 각 1회)에 근거한다. 다만 **역할별로(관문·검증에서는 다를 수 있다) 재 본 것은 아니다**:

| 후보 | 앞 측정 | 이 구조에 안 넣은 이유 | 다시 볼 가치 |
|---|---|---|---|
| Gemma 4 26B | 직접 92~97% | 「작은 모델로」라는 목표에서 제외(9.8초). 이번 비교 기준선으로만 씀 | 기준선 |
| Qwen3.8 27B | 92%, **45.1초/질문** | 이 서버에서 너무 느림 | 서비스 GPU 가 정해지면 |
| gpt-oss 20B | 78% (엉뚱 1 · 못 찾음 19), 6.4초 | 짚기로는 조심스러워 놓침이 많음 | **관문·검증 역할에는 맞을 수 있다** `[추정]` — 엉뚱한 답이 적은 성향 |
| 카나나-2 3B / 30B(제3자 변환) | 44% / 78% | 짚기 정확도 낮음 | 3B 는 한국어 관문 후보로 빠르다 `[미측정]` |
| 임베딩·재평가(zerank-2, WeMM, KaLM 등) | 69~81%, 「없음」을 못 가림 | 「없음」 판정이 필요한 역할에 부적합 | **기준 항목(이름 잇기) 역할에는 맞을 수 있다** `[미측정]` |
| OpenDecider | 56% (영어 전용) | 한국어 이름을 못 읽음 | 낮음 |
| Jev | 89% (순서만 1/8) | 유료 호출 — 요청 시에만(§17) | 요청이 있을 때 |

- 정리: 지금 구조의 「전문가」는 **규칙·코드(구조 파트) + Gemma E4B(관문·기준 항목) + Gemma 12B(짚기·검증)** 이다. 역할별 모델 경쟁(관문·검증에 gpt-oss·카나나 3B, 기준 항목에 임베딩)은 아직 하지 않았고 다음 단계 후보이다.

### 19-2. 결과 — 개발용으로 다듬은 heavy 와, 처음 보는 mix4

| 방식 | heavy 판정 88 (개발하며 본 세트) | **mix4 판정 88 (처음 보는 세트)** |
|---|---:|---:|
| Gemma E4B 직접 | 75/88 = 85% | 72/88 = 82% (엉뚱 15) |
| Gemma 12B 직접 | 81/88 = 92% | 79/88 = 90% (엉뚱 9) |
| **Gemma 26B 직접** | 85/88 = 97% | **81/88 = 92%** (엉뚱 7 · 못 찾음 0) |
| **전문가 구조 E4B/E4B/12B** | 84/88 = 95% | **81/88 = 92%** (엉뚱 4 · 못 찾음 3) |

- **mix4 에서 26B 와 동점이고 엉뚱한 답은 더 적다(4 대 7).** 88문항에서 1문제 = 1.1%p 라 「동점」이지 「앞섰다」고 말할 수 없다. 배치는 코드를 커밋한 뒤(`9b401a9c`) **한 번만** 재서 고르지 않았다.
- 속도(**추정**): 전문가 구조 평균 약 5초/질문(호출 수와 모델별 호출 시간으로 계산, 서버가 다른 작업과 겹친 시간이 섞여 있어 거칠다) · 26B 9.8초(실측). 12B 단독 2.5초·3.2초에 비해 구조가 느린 이유는 관문·검증 호출이 더해지기 때문이다.
- **개발 세트(heavy) 95% → 처음 보는 세트 92%**: 다듬은 세트의 점수는 낙관적이었다. 26B 도 97% → 92% 로 내려갔으므로 mix4 가 조금 더 어렵거나 heavy 가 쉬웠던 면이 함께 있다.
- 유형별 mix4 (유형당 8, E4B 직접 / 12B 직접 / 26B 직접 / 구조):

| 유형 | E4B | 12B | 26B | 구조 |
|---|---:|---:|---:|---:|
| 앞 대화 지시어 | 7 | 8 | 8 | 8 |
| 같은 장소 두 번 | 6 | 7 | 8 | 7 |
| 비슷한 이름 · 오타 · 설명형 | 8·8·8 | 8·8·8 | 8·8·8 | 8·8·8 |
| **요청이 둘** | 6 | 6 | **5** | **8** |
| 부정·제외(말고) | 6 | 7 | 7 | **5** |
| **일정 밖(잡담·시세·날씨)** | 6 | 6 | **6** | **8** |
| 순서·상대 위치 | 2 | 6 | 7 | 7 |
| 변경 요청 | 7 | 8 | 8 | 7 |
| 없지만 있을 법한 곳 | 8 | 7 | 8 | 7 |

- 26B 가 못 푸는 것(요청 둘 5/8 · 일정 밖 6/8)을 구조가 8/8 로 푼 것이 동점의 원인이고, 반대로 구조가 26B 보다 약한 곳은 **「말고」 문장(5/8 대 7/8)** 이다. 26B 는 「경복궁 취소하고 국립민속박물관 시간」에서 뒤에 말한 항목을 짚는다 — 「먼저 말한 항목이 대상」이라는 이 세트의 정의를 코드로 강제한 것이 이 유형의 이득이다(**정의에 의존한 이득**이라 실제 고객에게서는 「둘 다 필요한」 경우가 남는다).

### 19-3. 구조가 틀린 문제 7개 (mix4, 원인 — 고치지 않고 기록만)

| 문제 | 원인 |
|---|---|
| 「광장시장 두번째 방문 몇 시」 | 「N번째 방문」을 순서로 읽는 규칙이 없다 → 짚기 전문가가 첫 방문을 고름 |
| 「국립중앙박물관 말고 남대문시장 시간」 | **검증 전문가(12B)가 맞는 답을 거부**(정확한 이름인데) — heavy 에서도 「남대문시장 시간」이 같은 이유로 거부됨. 검증이 이름 직접에도 오탐을 낸다 |
| 「토속촌 말고 그 전 일정」 | 기준 항목 전문가(E4B)가 「토속촌」을 항목(삼계탕 점심 @ 토속촌삼계탕)과 못 이었다 → 조회가 기권 |
| 「광장시장 아침 말고 저녁 거 시간」 | 같은 장소의 형제 항목을 고르는 경우를 아직 구현하지 않았다(기록된 한계) |
| 「정동극장 다음에 뭐 먹어?」 | 기준 항목 전문가(E4B)가 「먹어」에 끌려 닭한마리를 짚음 |
| 「삭제해줘」(앞 대화 있음) | 관문이 앞 대화 속 대상을 무시하고 「일정 밖」으로 거름 |
| 「홍대 클럽 언제 가」 | 짚기 전문가가 「홍대」에 끌려 버스킹을 고름, 검증도 통과 |

- 구조의 약점은 **E4B 를 기준 항목·관문에 쓴 것**(3건)과 **검증의 오탐**(1건 + heavy 3건)이다. E4B 를 point+verify 에 쓰면 못 찾음이 20건으로 무너진다(모든 mix4 배치의 E4B point 열 74%).
- 개발 세트에서 고친 규칙(한 시간 뒤로 · 숙소 n번째 = 체크인 · 낮 = 점심)은 mix4 에서 오작동하지 않았다.

### 19-4. 결론과 다음 단계

- **「26B 를 앞지른다」는 아직 증명하지 못했다. 동점이다.** 확인된 것: 규칙 + 작은 모델 전문가 조합(12B 급 주력)이 26B 와 같은 정답 수를 내고 엉뚱한 답이 적다. 확인 안 된 것: 처음 보는 **일정**에서의 성능 · 반복 편차 · 실제 고객 표현 · 유형을 규칙이 아니라 실제 분포로 나눴을 때.
- 다음: ① 검증 전문가 오탐 줄이기(이름이 일치하면 검증을 건너뛰는 코드 규칙) · 관문이 앞 대화 대상을 인정하기 · 기준 항목 전문가를 12B 로 ② 형제 항목·「N번째 방문」 규칙 ③ **새 세트(mix5, 다른 일정 포함)** 를 만들어 코드를 고정한 뒤 한 번 더 판정 ④ Jev 는 요청이 있을 때만 같은 세트로 비교(§17).
- 서버: 이 절의 시험을 위해 Gemma E4B·12B·26B 를 올려 두었다. 앞 15절의 「앞 대화 없음 · 후보 줄이기 · 정의 명시」 3조건은 GPU 경합으로 오류가 21~22건 난 E4B 결과만 있어 **무효로 폐기**하고 재시험하지 않는다(19절 구조가 대신한다).

## 20. 목표 재정의 — 26B 이상 성능에 **파라미터·용량을 줄이는** 것 `[사용자 지시 2026-09-30]`

지시: 문장을 분석해 절로 나누고, 각 조각에 가장 잘 맞는 소형 모델을 배정해 MoE 처럼 돌려서 **26B 보다 잘 나오게 하면서 소모되는 파라미터 수와 용량을 줄인다.** 이 지시에서 「26B」의 비용이 실제로 얼마인지 먼저 확인했다.

| 모델 | 저장 파라미터 | 토큰당 활성 | 양자화·파일 | 출처 |
|---|---:|---:|---|---|
| Gemma 4 26B(A4B) | 25.2B | **3.8B** (전문가 혼합) | Q4_K_M · 18GB | 서버 `ollama show` · [모델 카드](https://ai.google.dev/gemma/docs/core/model_card_4) `[외부]` |
| Gemma 4 12B | 11.9B (밀집) | 11.9B | Q4_K_M · 7.6GB | 서버 `ollama show` |
| Gemma 4 E4B | 8.0B 저장(유효 약 4B) | 약 4B `[외부]` | Q4_K_M · 9.6GB | 서버 `ollama show` |

- **26B 는 이미 「전문가 혼합」이라 토큰당 3.8B 만 쓴다.** 그래서 「파라미터를 줄인다」는 목표는 **호출 하나의 활성 파라미터가 3.8B 미만**이고 **저장이 18GB 미만**이라는 뜻으로 읽어야 한다.
- **§19 의 구조(E4B + 12B)는 이 목표를 아직 달성하지 못했다.** 저장은 9.6 + 7.6 = 17.2GB 로 26B(18GB)와 거의 같고, 질문당 호출은 12B(활성 11.9B)를 최대 2번(짚기·검증) + E4B 를 여러 번 부르므로 활성 파라미터 합이 26B 의 3.8B 보다 **오히려 크다**. 성능이 동점인 것과 별개로 **비용 목표는 미달**이다.
- 실질적으로 줄일 수 있는 것: ① 코드가 확정하는 문제(순서·상대 위치 등)는 모델 호출 0 ② 프롬프트에 항목 51개를 다 싣지 말고 **가벼운 검색 모델로 후보 5개로 줄여** 작은 모델이 고르게 하면 입력 토큰이 크게 준다 ③ 관문·검증에는 가장 작은 모델.
- 사용자가 준 소형 모델 세 개의 저장 용량(참고, 가중치 정밀도에 따라 달라짐 `[추정]`): Qwen3-Reranker-4B(4B, fp16 약 8GB) · WeMM-Embedding-4B(약 5B) · OpenDecider-small(4B) — 셋을 다 두면 26B 의 18GB 를 넘으므로 **용량 목표를 지키려면 모델 수를 줄이거나 더 작은 판(Qwen3-Reranker-0.6B 등)·양자화가 필요**하다.
- 이후 모든 비교표에는 **정답 수 + 질문당 활성 파라미터(호출×모델) + 저장 용량(GB)** 을 함께 적는다.

### 20-1. 두 축으로 재기 — 상주 메모리와 질문당 계산량 `[실측(호출 수)·추정(토큰 환산) 2026-09-30]`

사용자 지적: 26B 는 3.8B 만 활성이라도 **25.2B 전체가 메모리에 올라가 있어야** 한다. 그래서 「활성만」이 아니라 두 축을 같이 잰다. 그리고 우리도 같은 방식(**필요한 전문가만 켜는 것**)으로 활성을 낮출 수 있다.

| 축 | 26B(A4B) | 지금의 구조(E4B + 12B) | 줄이는 방법 |
|---|---|---|---|
| ① 상주 메모리(항상 올려 둠) | 18GB 전부 | E4B 9.6 + 12B 7.6 = 17.2GB 를 둘 다 올릴 때. 12B 를 필요할 때만 올리면 상시 9.6GB + 필요 시 7.6GB | 상시 켜 둘 것은 가장 작은 전문가(검색·관문)만, 큰 것은 필요한 문제에서만 |
| ② 질문당 계산량 = 활성 파라미터 × 입력 토큰 | 3.8B × 약 1.6k 토큰 = **6.0 B·k토큰**(호출 1회) | mix4 88문제 평균 **21.1 B·k토큰**(호출 2.3회, 활성 파라미터 합 20.0B) | 아래 |

- 참고 기준선: 12B 직접 18.9 · E4B 직접 6.4 B·k토큰. 글자 → 토큰은 1.7자 = 1토큰으로 거칠게 환산한 **추정**(전체 일정 프롬프트 약 1,585토큰).
- **구조가 26B 보다 계산량이 약 3.5배 크다.** 이유 둘: (a) 12B(밀집, 활성 11.9B)를 문제의 **75%(66/88)** 에서 부른다 (b) 짚기·관문·기준 항목 호출마다 **일정 51개(약 1.6k 토큰)를 통째로** 싣는다. 코드만으로 끝나는 문제는 13/88 뿐이다.
- 그러므로 「필요한 전문가만 켠다」에서 가장 큰 이득은 **입력 토큰을 줄이는 것**이다. 가벼운 검색 모델이 후보를 5개로 줄이면 짚기 프롬프트가 약 1.6k → 약 0.3k 토큰(**추정**)이라 12B 호출 한 번이 18.9 → 약 3.6 B·k토큰으로 준다. 목표는 **질문당 평균 6.0 B·k토큰 이하 + 상주 18GB 이하 + 정답 수 26B 이상** — 실측으로 확인해야 하는 **가설**이다.

## 21. 경로 분기를 학습형(회귀·강화학습)으로 하면 `[검토 2026-09-30 — 아직 구현 안 함]`

질문: 어떤 전문가를 부를지 정하는 분기를 ML 회귀 모델이나 RL 로 처리하면 되지 않나.

- **가능하고, 할 만한 형태는 「지도학습 분기」다.** 문제마다 `(싼 특징) → 각 전문가가 맞을 확률`을 회귀(로지스틱·작은 트리)로 예측하고, **가장 싼 전문가 중 확률이 목표(예: 95%) 이상인 것**으로 보낸다(신뢰도 기반 보류·위임과 같은 원리). 특징은 이미 공짜로 있다: 규칙이 읽은 신호(날·순서·앞뒤), 검색 모델의 1위 점수·1·2위 차이·엔트로피, 「말고」·앞 대화 유무, 문장 길이, 관문의 확률.
- **정답을 미리 아는 합성 문제를 늘려 학습 자료를 만들 수 있다**(우리가 만든 일정에서 이름·순서·상대 위치 문장을 대량 생성, 정답은 코드가 앎). 지금 라벨이 있는 문제는 기존 178 · heavy 132 · mix4 88 · 순서 세트 90 = 약 490개.
- **RL 은 과하다.** 문제 하나에 전문가 하나를 고르는 **한 단계 결정**이라 맥락 밴딧이면 충분하고, 그것도 보상(정답 여부)이 즉시 알려지는 지도학습으로 풀 수 있다. RL 은 여러 단계 결정이나 실제 서비스 로그로 계속 학습할 때 의미가 있다. (9월 논문 [HybridInfer](https://arxiv.org/abs/2609.30270)는 발열을 반영한 RL 로 온디바이스·엣지·클라우드 층을 배정한다 — 초록만 확인, 정확도 향상이 아니라 자원 제약 배정이 목적으로 보인다. [RSI-Router](https://arxiv.org/abs/2609.34712)는 회귀·RL 이 아니라 경험에서 분기 규칙을 진화시킨다.)
- **위험과 한계**
  1. **합성 문장으로만 학습하면 그 문체를 외운다** — 실제 고객 표현이 다르면 분기가 무너진다(우리 세트도 개발 95% → 처음 보는 세트 92%). 검증은 **유형 하나를 통째로 빼고 학습하는 교차검증**(leave-one-type-out)과 처음 보는 세트로 한다.
  2. **실제 고객 로그가 0개**라 실제 분포로 보정할 수 없다. 서비스가 시작되면 로그로 다시 학습해야 한다.
  3. 전문가끼리의 **일치 여부를 특징으로 쓰면 사실상 투표**가 된다(사용자 결정으로 금지) — 각 전문가 자신의 확신도만 쓴다.
  4. 규칙 분기는 해석 가능하고 무료라 **분기 학습이 규칙보다 얼마나 나은지**를 재야 채택한다. 못 이기면 규칙을 유지한다.
- **순서**: ① 검색 모델 점수가 나오면(진행 중) 1위 확률·차이로 「LLM 을 부를지」를 정하는 **로지스틱 회귀 하나**부터 시험 — 모델 호출을 줄이는 직접 효과가 있고 데이터 요구가 가장 작다 ② 잘 되면 전문가 여럿으로 확장 ③ RL·밴딧은 실제 로그가 생긴 뒤.

- 근거 가설: 재평가 모델은 제로샷 1위 정확도가 69~76% 로 낮지만, **우리 과제(이름·별칭·오타·채팅체·설명·「해당 없음」)에 맞춰 학습하면** 0.6B(약 1.2GB)로 후보 줄이기와 「없음」 판정을 함께 맡을 수 있다 — 26B 가 못 푸는 「일정 밖」 유형과 후보 줄이기에 쓰려는 것.
- **학습 자료 출처 분리**: 장소·문장은 **Codex(gpt-6-sol)가 썼고**(장소 160곳 × 문장 12개 + 일정 무관 문장 180개, 시험 일정 장소와 겹치는 것은 제외 지시 + 코드로 10곳 추가 제거, 원본 [`datasets/travel/plan_qa_bench/train/`](../../datasets/travel/plan_qa_bench/train/) — git 밖), 시험 세트(heavy·mix4)는 Claude 가 썼다. 일정·라벨은 [`gen_train.py`](../scripts/plan_qa_bench/gen_train.py) 가 무작위로 만든다: 일정 60개 × 문제 100개, 쌍 약 6만 4천(정답 4,255). 어려운 오답(글자 겹침 상위 6)+무작위 오답 4. 검증은 **학습에서 뺀 장소 30곳**.
- 학습: [`ft_reranker.py`](../scripts/plan_qa_bench/server/ft_reranker.py), LoRA rank 16, 학습률 1e-4, 1에폭(4,015스텝, 약 55분). 평가 [`eval_ft_pipeline.py`](../scripts/plan_qa_bench/eval_ft_pipeline.py): 문턱은 heavy 개발용으로만 고른다.
- 알려진 한계(미리 적어 둠): ① 모델이 「앞 대화」를 못 읽어 앞 대화 문제는 LLM 몫 ② **재평가(교차) 모델은 항목마다 따로 계산해 질문당 약 7천 토큰 × 0.6B ≈ 4.3 B·k토큰(추정)** 으로 26B(6.0)와 비슷해 계산량 이득은 작다 — 이득은 상주 메모리(약 1.2GB)와 「없음」 판정에서 나온다. 계산량까지 줄이려면 임베딩(양방향 인코더) 판을 학습시키거나 규칙으로 후보를 먼저 줄여야 한다.

### 24-3. 「전용 학습이 의미가 있나」 — 결과를 보기 전에 정한 판정 기준 `[사전 지정 2026-09-30, 학습 결과 나오기 전]`

의문(사용자): 우리 과제 전용으로 학습시키는 것이, 여행용 공개 데이터로 학습시키는 것이 얼마나 의미가 있는지 모르겠다.

- 이 학습이 가르치려는 것은 **여행 지식이 아니라 기술**이다: 「일정 항목 50개 중 이 문장이 가리키는 것을 고르고, 없으면 없다고 하기」. 공개 여행 자료(리뷰·관광 소개·대화 말뭉치)에는 이 「항목 짚기」 라벨이 없다(§12 조사에서도 일정 항목 라벨이 있는 자료는 못 찾음). 공개 자료가 도울 수 있는 것은 **장소 지식**(이름 없이 설명만 하는 문장)뿐인데, 이름 직접·오타·별칭·순서는 12B 가 이미 만점 근처라 병목이 아니다. 관광공사 소개글은 「사진·소개글은 저장하지 않는다」는 결정(2026-09-28)이 있어 학습에 쓰지 않는다.
- **의미가 있는지는 결과로만 판단한다.** 아래 기준을 **학습 결과가 나오기 전에** 적는다(사람이 쓴 시험 세트 heavy 판정·mix4 로만 판정, 학습에는 쓰지 않음):
  1. 후보 재현율@1(정답이 있고 앞 대화가 필요 없는 문제): 제로샷 0.6B(69~71%) → **88% 이상**, 그리고 4B 제로샷(74~76%)을 넘을 것.
  2. 「없음」 판정: 정답이 없는 문제를 **90% 이상** 잡고 맞는 답을 **95% 이상** 지킬 것(제로샷 4B: 74~83% · 91~92%).
  3. 처음 보는 mix4 종단 결과: 정답 수가 26B(81/88) 이상이면서 **LLM 을 부르는 문제가 40% 이하**(기존 구조 75%).
  4. 학습에서 뺀 장소의 검증 정확도가 높은데 위 1·2 가 안 나오면 **합성 자료 과적합**(9월 논문 2609.10750 의 경고)으로 판정하고 이 방법은 접는다.
- 기준을 못 맞추면 「전용 학습은 이 과제에서 효과가 없었다」고 그대로 기록한다. 맞추면 그때 비로소 임베딩 판(계산량 절감)과 사람이 쓴 별도 세트로의 재검증(mix5)으로 간다.

## 26. 우리 과제 전용 소형 재평가 모델 학습 결과와 「학습 없이는 방법이 없나」 `[실측 2026-09-30]`

학습: Qwen3-Reranker-0.6B + LoRA(rank 16), 합성 문제 6천 개(쌍 6.4만), 1에폭 3,719초. 학습에서 뺀 장소의 합성 검증 1위 정확도 **93.9%**. 평가는 사람이 쓴 heavy 판정 88 · mix4 88 로만 한다(학습에 쓰지 않음). 코드 [`gen_train.py`](../scripts/plan_qa_bench/gen_train.py) · [`ft_reranker.py`](../scripts/plan_qa_bench/server/ft_reranker.py) · 채점 [`eval_retrieval.py`](../scripts/plan_qa_bench/eval_retrieval.py) · [`eval_ft_pipeline.py`](../scripts/plan_qa_bench/eval_ft_pipeline.py), 출력 [`eval_retrieval_out.txt`](../scripts/plan_qa_bench/results/eval_retrieval_out.txt) · [`eval_ft_pipeline_out.txt`](../scripts/plan_qa_bench/results/eval_ft_pipeline_out.txt) · [`eval_zeroshot_pipeline_out.txt`](../scripts/plan_qa_bench/results/eval_zeroshot_pipeline_out.txt).

### 26-1. §24-3 에 미리 적은 기준 대로의 판정

| 기준 | 결과 | 판정 |
|---|---|---|
| ① 후보 재현율@1 ≥ 88% (제로샷 0.6B 69~71%) | heavy 72% · mix4 73% (제로샷 0.6B 69%·71%, 4B 74%·76%) | **미달** |
| ② 「없음」 90% 이상 포착 · 맞는 답 95% 이상 유지 | 원 점수 기준 heavy 10/19 · 91%, mix4 12/18 · 95% | **미달** |
| ③ mix4 종단: 정답 ≥ 81/88 이면서 LLM 호출 문제 ≤ 40% | **82/88 = 93%, LLM 14%** | **통과** |
| ④ 합성 검증만 높으면 과적합으로 접는다 | 합성 93.9% 대비 사람이 쓴 세트 재현율 72~73% | 격차가 있다(2609.10750 경고와 같은 방향) |

- **①·②의 지표가 잘못 설계되어 있었다**: 후보 재현율·「없음」 판정을 **구조가 이미 푸는 문제(순서·부정·앞 대화)까지 섞어** 쟀다. 유형별로 보면 순서·상대 위치는 FT 1/16 · 재평가4B 2/16 이지만 그 유형은 앞단 규칙이 푼다. 이름 기반 유형(비슷한 이름·오타·설명·요청·중복·요청 둘 85문제)만 보면 **FT 76/85 = 89%, 제로샷 0.6B 74/85 = 87%, 제로샷 4B 78/85 = 92%** 로 학습 이득은 +2문제다. 사전 기준은 문자 그대로 **미달**로 기록하고, 종단 지표(③)가 실제 의미를 갖는다고 판단한다.
- **채점 결함 정정**: 앞 §23-2 의 「없음」 판정 표는 항목 51개에 걸쳐 정규화한 확률의 1위로 쟀는데 재평가 모델에는 부적절했다(절대 점수가 신호). 원 점수 최고값으로 다시 재면 **재평가4B 는 정답 없음을 heavy 18/19 · mix4 18/18 잡고 맞는 답은 84%·86% 유지**, 재평가0.6B 16/19 · 18/18(유지 67%·71%), FT 0.6B 는 10/19 · 12/18(유지 91%·95%) — FT 는 구조가 푸는 유형의 점수가 없음과 겹쳐 문턱으로 못 가른다. 앞 표의 「재평가4B 14/19」는 이 값으로 바로잡는다.

### 26-2. 종단 결과 — 학습 없는 원본 모델과 나란히 (구조 + 재평가 확신도 분기 + 12B)

분기: 구조(코드)가 확정하면 그 답 · 앞 대화가 있으면 12B · 그 밖에는 재평가 1위 확률이 hi 이상이면 그 항목, lo 미만이면 「없음」, 사이는 12B. lo·hi 는 heavy 개발용 44문제로만 골랐다.

| 방식 | heavy 88 | mix4 88 | 합계 176 | LLM 호출 문제 |
|---|---:|---:|---:|---:|
| Gemma 26B 직접 | 85 | 81 | **166 = 94.3%** | — |
| 기존 구조 E4B/E4B/12B(검증 포함) | 84 | 81 | 165 = 93.8% | 75% |
| **FT 재평가 0.6B** + 구조 + 12B | 79 | 82 | 161 = 91.5% | **12% · 14%** |
| 원본 재평가 4B(학습 없음) + 구조 + 12B | 79 | 82 | 161 = 91.5% | 19% |
| 원본 재평가 0.6B(학습 없음) + 구조 + 12B | 79 | 81 | 160 = 90.9% | 48% · 45% |
| Gemma 12B 직접 | 81 | 79 | 160 = 90.9% | — |

- **미세조정 없이도 같은 수준이 나온다**: 원본 4B 는 82/88(mix4)이고 LLM 호출은 19%다. **학습의 효과는 정확도가 아니라 「확신도가 뚜렷해져 12B 를 덜 부르는 것」(45% → 14%)과 「4B 와 같은 정확도를 0.6B 로」** 이다.
- **두 세트를 합치면 26B(166)를 넘은 조합이 없다**: 가장 가까운 것이 기존 구조 165, FT 구조는 161이다. mix4 에서만 +1(82 대 81)이고 heavy(개발용으로 다듬은 세트)에서는 −6이다. 88문항에서 1문제는 1.1%p 라 통계적 우위라고 하지 못한다. mix4 는 이미 여러 번 본 세트라 「처음 보는 세트」도 아니다.
- **자원**(§20 의 두 축, 추정): FT 구조의 상주 메모리 = 0.6B(fp16 약 1.2GB) + 12B 7.6GB ≈ **8.8GB(26B 18GB 의 약 절반)**, LLM 호출 12~14%. 다만 재평가(교차) 모델은 질문당 항목 51개를 따로 계산해 **0.6B 는 약 4.3 B·k토큰 · 4B 는 약 28 B·k토큰** 으로, 26B(6.0)와 같거나(0.6B) 훨씬 크다(4B). 그래서 **계산량 이득은 없고 메모리 이득만 있다** — 임베딩(양방향) 판 학습을 다시 돌리는 이유다(첫 시도 메모리 부족, 배치를 줄여 재시도 중).

### 26-3. 「미세조정 말고는 소형 조합으로 26B 를 이길 방법이 없나」 — 안 해본 것 목록

- **해본 것(미세조정 외) 여덟 가지**: ① 소형 LLM 직접 짚기(E4B·12B) ② 검색·재평가·OD 를 평균한 조합(76%) ③ 규칙 + 관계 조회 ④ 절 분석(요청 둘·말고) ⑤ 관문·기준 항목·짚기·검증 전문가 분리 ⑥ 검색 모델 후보 재현율 ⑦ 확신도 분기(위) ⑧ LatWeave 식 구조적 기권·되묻기(§25). 이 중 26B 를 이긴 것은 **없다**(동급~1문제 차이, 계산량·메모리는 달라짐).
- **안 해본 것**: (a) 후보를 상위 5·10개로 줄여 12B/E4B 에 **제한된 목록**으로 짚게 하기(정확도 대 입력 토큰) (b) 「질문 계획」 한 번 호출로 조건을 뽑는 LLM 전문가(규칙이 못 읽는 표현용) (c) 임베딩 판(계산량 절감) (d) 검증 전문가 오탐 제거(이름이 맞으면 검증 생략) 등 알려진 실패 원인 수정 후 **처음 보는 세트(mix5)** 재판정 (e) 실제 고객 표현 표본 라벨링 (f) 항목 번호 대신 점수 기반 선택(로그확률 — 올라마 지원 확인 필요) (g) 12B 를 E4B 로 낮춘 종단 시험(자원 이득 확대).
- 결론: **「전혀 없다」고 말할 수 없다.** 다만 지금까지의 실측은 「26B 와 동급 정확도를 더 적은 메모리·LLM 호출로 낸다」까지이고, 「26B 를 이긴다」는 근거는 아직 없다.

## 27. 12B 를 뺀 소형 구성 — 학습 임베딩 판 · 넘김 모델 교체 · Codex 합의 `[실측 2026-09-30]`

### 27-1. 사용자 지적과 Codex 합의(1회차 일치)

지적: 지금 구조가 결국 12B(밀집 11.9B)를 부르니 「소형 조합」이 아니다 — 4B·E4B·코드 정도만으로 26B 급을 내야 의미가 있다. 이 지적은 **맞다**(12B 는 토큰당 11.9B 활성). 기록: [`consensus/20260930_small_only/`](../scripts/plan_qa_bench/consensus/20260930_small_only/) (Claude 의견 → Codex gpt-6-sol 의견 → 결정).
- **결론(둘 다 같음)**: 「26B 를 이긴다」를 목표로 두지 않고 **「활성 4B 이하로 26B −3%p 이내」를 검증 가능한 목표**로 삼는다. ① 알려진 오류(검증 오탐·기준 항목·관문) 수정 → ② **새 독립 세트로 26B 와 12B 뺀 경로를 같은 문제에서 판정**(기존 mix4 는 여러 번 봐서 최종 판정에 못 씀) → ③ 규칙 밖 표현에 질문 계획(D) → ④ E4B 짚기 LoRA(B)는 순개선이 입증될 때만. Codex 는 A·C·E 를 기각(C 재현율 상한, E 목표 불일치). 순서는 Codex 안(D 가 B 앞)을 채택.
- **E4B 에 대한 정직한 표기**: 활성은 약 4B 이지만 저장 8.0B · 파일 9.6GB 로 **12B(7.6GB)보다 파일이 크다**. 「활성 파라미터」 기준으로만 소형이고 상주 메모리 이득은 없다.

| 앞단 검색 전문가(크기) | 넘김 모델 | heavy | mix4 | 합계 | 넘김(LLM) 호출 문제 |

- 학습 임베딩 자체: 합성 검증(학습에서 뺀 장소) 1위 94.2%, 사람이 쓴 세트 후보 재현율@1 67%(heavy)·71%(mix4), @10 84%·85% — **재평가 판(72~73%)보다 낮은 검색 정확도인데도 종단이 더 좋게 나왔다**(mix4 84 대 81). 이유를 규명하지 못했다 `[미규명]` — 문턱을 heavy 개발용 44문제에서 골랐고 표본이 작아 우연일 수 있다.
- 한계: 세트가 합성이고 mix4 는 이미 여러 번 본 세트이며 문턱이 heavy 개발용 44문제로 정해졌다. **새 독립 세트(mix5) 판정 전에는 「26B 급」이라고 주장하지 않는다.**

E4B q8 종단(249)은 **26B 직접(247)을 앞서지만** 용량이 12GB 로 E4B QAT 의 2배라(앞단 더하면 13.2GB) 26B QAT(14GB) 와 거의 같다 — **용량 대비로는 QAT 가 효율 접점**이다.
- **E2B 는 같은 경향이 아니다**: bf16(201)이 Q4(202)와 같고 QAT(211)보다 낮다 — QAT 체크포인트가 원본 bf16 보다 이 과제에서 더 좋다는 뜻인데 이유는 모른다 `[원인 미규명 — QAT 체크포인트가 추가 학습을 거친 판일 수 있다]`. 즉 「양자화가 작은 모델을 해친다」로 일반화할 수 없다.
- **HF 경로(E2B bf16 217)와 올라마 경로(E2B bf16 201)의 16문제 격차는 양자화가 아니다**(같은 bf16). 둘의 차이는 ① HF: 질의문 끝에 「답은 JSON 한 줄로만…」 덧붙임 + 형식 강제 없음(자유 생성 14토큰) + 관대한 파서, ② 올라마: 질의문 그대로 + JSON 스키마 형식 강제 디코딩. 어느 쪽이 원인인지는 **다음 절(변형 실험)** 이 가른다. **만약 형식 강제가 작은 모델을 해치는 것이라면 지금까지의 모든 올라마 수치가 작은 모델에 불리한 측정이었던 것이다** `[가설]`.

### 30-20. ★질의문 끝의 형식 지시가 E2B 를 +13 올린다 — 측정 도구의 타당성 점검 `[실측 2026-10-01 08:40 KST]`

HF 경로(E2B 217)와 올라마 경로(E2B 201~202)의 격차 원인을 가르려고 **같은 올라마·같은 모델(E2B Q4)** 에서 질의문을 바꿨다([`llm_point_var.py`](../scripts/plan_qa_bench/server/llm_point_var.py)): (a) 질의문 끝에 「답은 JSON 한 줄로만: {"item": 번호} 또는 {"item": null}」 덧붙임 + 형식 강제(JSON 스키마) 유지, (b) 같은 덧붙임 + 형식 강제 끄기(자유 생성 14토큰, HF 와 같은 관대한 파서). 채점 [`eval_night_out.txt`](../scripts/plan_qa_bench/results/eval_night_out.txt).

- **원인은 「끝 형식 지시」다.** 형식 강제를 끄든 켜든 같은 215 이고 HF(217)와도 2 차이뿐이라 **디코딩 방식(스키마 강제)은 원인이 아니다.** 작은 모델에게는 질의문 끝에 **출력 형식을 한 번 더 적어 주는 것**(최근 문장이 행동을 정한다)만으로 일정 짚기가 직접 +13(202 → 215), 종단 +8(236 → 244)이다 `[추정 — 지시 문구를 바꿔 끝 위치·내용을 분리하지는 않았다]`.
- **이것은 측정 도구의 한계였다**: 지금까지 모든 올라마 수치(E2B·E4B·12B·26B)는 끝 지시 없이 잰 것이다. 작은 모델은 이 지시로 오르고 **큰 모델은 덜 오를 가능성**이 있어(질의 이해가 이미 충분) 이전 비교가 작은 모델에 불리했을 수 있다. 공정하려면 **기준선(26B)에도 같은 지시를 붙여 다시 재야 한다** — 대기열에서 26B q4_K_M 으로 재는 중이고, E4B QAT 변형도 재는 중이다.
- 이 절의 수치(E2B +13)로 **어떤 구성이 26B 를 넘는다고 주장하지 않는다.** 이미 E4B QAT 종단이 26B 직접과 동급이었고(§30-15), 같은 지시를 기준선에도 주었을 때의 값이 나와야 비교가 성립한다.
