## 어떤 추천 구조를 시험할 것인가

일반적인 추천은 후보를 넓게 찾고, 점수를 매기고, 마지막 순위를 조정하는 단계로 나뉩니다. Google의 공식 추천 교육 자료와 Sentence Transformers의 회수·재정렬 문서가 이 분리를 설명합니다. 여행에서는 ‘방문 가능한가’와 ‘가장 마음에 드는가’를 추가로 나눠야 합니다. [Google 추천 구조](https://developers.google.com/machine-learning/recommendation/overview/types), [회수·재정렬](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

| 단계 | 맡길 일 | 권장 방식 | 별도 확인할 실패 |
|---|---|---|---|
| 고객 요구 정리 | 취향·기피·필수 요구·중요도 정리 | 여행 정보 분석 기능 | 원문에 없는 취향 생성·기피 누락 |
| 후보 회수 | 장소 자료에서 후보 확보 | 분류·거리·텍스트 검색 조합 | 좋은 후보를 처음부터 못 찾음 |
| 필수 조건 | 휴무·시간·예산·이동·재난 제한 확인 | 규칙 계산 | 사실 정보와 시간 계산 오류 |
| 의미 평가 | 취향·원래 활동과의 경험 유사성 | Jev API(유료) 등의 등급 평가 | 좋은 후보를 낮게 평가함 |
| 최종 순위 | 여러 선호의 충돌을 반영해 1·2·3위 제출 | 규칙 계산 또는 nano·Luna | 입력 순서 편향·중요도 무시 |
| 최종 검증 | 후보 ID·필수 조건·근거 다시 확인 | 규칙 계산 | 조건 위반을 그럴듯한 설명으로 감춤 |

**거리와 가중합 계산은 코드로 하고, ‘조용하지만 지루하지 않은 곳’ 같은 의미 판단에 모델을 쓰는 것이 첫 추천입니다.** TypeSafe 공식 소개도 복합 질문을 원자적 요인으로 나누고, 요인별 결과의 계수 결합은 코드에서 하도록 권합니다. 예를 들어 취향 적합성과 기존 활동의 경험 유사성을 별도 Score로 얻고, 거리 점수는 실제 이동값에서 계산합니다. [TypeSafe 원자적 질문](https://docs.typesafe.ai/introduction), [Score와 Noul의 구분](https://docs.typesafe.ai/primitives)

이 제안은 ‘모델이 모든 점수를 만들고 순위도 결정한다’와 다릅니다. 기준 계수와 계산식이 명확하면 코드가 일관되게 최적 순위를 낼 수 있습니다. Luna 재정렬이 가중합보다 실제로 낫다는 증거가 없다면 매번 호출할 이유도 약합니다. 반대로 자연어 취향의 애매함·동행자 요구의 충돌·새로운 경험의 다양성을 비교해야 하면 모델 재정렬의 가치가 커질 수 있습니다. [COMPASS v2 §3.4](https://arxiv.org/html/2510.07043v2#S3.SS4)는 필수 조건을 만족한 답과 효용을 최적화한 답을 구분하고, 규칙 필터와 전수 조합으로 정답을 계산합니다.

## Jev API와 Winnow를 어떻게 구분할 것인가

**Jev API(유료)**는 TypeSafe의 모델과 서비스를 호출하는 경로입니다. **Jev 계열 모델 중 Winnow-E4B(우리 자료 추가 학습 없는 배포 원본)**는 별도 배포 모델이며, Jev API(유료)의 학습 방식·보정·지연·요금 결과를 승계하지 않습니다. 이번 시험에서 어느 쪽을 호출했는지 반환 모델 이름과 함께 남겨야 합니다. [TypeSafe 공식 시작 문서](https://docs.typesafe.ai/introduction/quickstart), [Winnow 호환 범위](https://github.com/EldanRing/winnow-inference/blob/main/docs/API.md)

권장 첫 실험은 고객 맥락을 공유 상태로 넣고 후보마다 ‘취향 적합 등급’을 묻는 방식입니다. 모델이 후보를 평가한 뒤에는 코드가 남길 후보 수를 정합니다. 처음부터 낮은 confidence 후보를 모두 버리지 않습니다. 낮은 확신은 불필요한 후보라는 뜻이 아니기 때문입니다.

특히 Winnow-E4B(Jev 계열)의 호환 구현 문서는 confidence를 선택지 확률 분포의 엔트로피 집중도로 정의하며, 실제 정답률의 보정 보장이 아니라고 밝힙니다. TypeSafe의 공식 confidence 설명도 출력 분포에서 계산한 통계와 업무별 임계값 선택을 설명합니다. 모델이 출력한 0.9를 ‘추천 정답률 90%’로 읽지 말고, 별도 검증 자료에서 **최상위 보존율·관련 후보 보존율**을 직접 확인해야 합니다. [Winnow 확률 계약](https://github.com/EldanRing/winnow-inference/blob/main/docs/API.md), [TypeSafe confidence](https://docs.typesafe.ai/confidence), [확률 보정의 기초 연구](https://arxiv.org/abs/1706.04599)

후속 연구에서는 Jev API(유료)뿐 아니라 전문 CrossEncoder 재정렬 모델도 대조군으로 고려할 수 있습니다. Contextual AI와 ZeroEntropy는 사용자 지시를 받는 전문 재정렬 모델을 제시합니다. 이는 공급자 자체 평가이며 한국어 여행에서의 우위를 보장하지 않습니다. 새 모델을 지금 전부 호출할 필요는 없고, 단일 모델·규칙보다 개선이 있는지부터 봅니다. [Contextual AI v2](https://contextual.ai/blog/rerank-v2), [ZeroEntropy 지시형 재정렬](https://www.zeroentropy.dev/articles/prompting-best-practices-for-instruction-following-rerankers/)

## 사용자 제안에 대한 찬성 근거와 반대 근거

**찬성:** 취향 의미 판단을 작은 모델로 하고 마지막 복합 비교만 큰 모델에 맡기면, 후보가 많을 때 최종 입력을 줄일 수 있습니다. UR4Rec은 후보에 필요한 사용자 선호를 골라 재정렬에 전달하는 접근을 연구했습니다. RankGPT는 제공된 후보를 생성형 모델로 재정렬하는 가능성과 새 지식에서의 평가를 다룹니다. 다만 두 논문 결과가 Jev API(유료)·nano·Luna의 성능 증명은 아닙니다. [UR4Rec](https://aclanthology.org/2025.coling-main.45/), [RankGPT](https://arxiv.org/abs/2304.09542)

**반대:** 후보가 이미 12개 정도로 작고 Luna 직접 호출이 매우 저렴하면, 앞선 선별 요청의 입력 처리·네트워크·실패가 절감보다 클 수 있습니다. FrugalGPT와 RouteLLM의 요지는 업무별 품질·비용 자료로 연쇄나 라우팅을 선택하는 것입니다. 두 모델을 언제나 모두 부르는 것은 라우팅이 아닙니다. [FrugalGPT](https://arxiv.org/abs/2305.05176), [RouteLLM](https://arxiv.org/abs/2406.18665)

**가장 큰 위험:** 앞 단계에서 최고 후보를 버리면 후속 모델이 회복할 수 없습니다. 비용이 싸졌더라도 정답이 입력에 사라졌다면 실서비스 개선이라고 할 수 없습니다. 공급자 기술 글도 회수 실패를 재정렬 지시로 해결할 수 없다고 지적합니다. [지시형 재정렬의 실패 사례](https://www.zeroentropy.dev/articles/prompting-best-practices-for-instruction-following-rerankers/)

**별도 위험:** 상위 후보 정확도와 순위 일관성은 다릅니다. 2026-08 공개된 RecSys 논문은 후보 순열 변화에 따른 쌍별 선호·전체 순위·출력 일관성이 관련도 개선과 엇갈릴 수 있음을 보입니다. 같은 정보의 배열만 바꾸었는데 추천이 바뀌는지 봐야 합니다. [2026 위치 편향 연구](https://arxiv.org/abs/2608.03091), [2025 RISE](https://arxiv.org/abs/2508.02020)

다만 2026 위치 편향 연구는 **고정 입력의 결정적 순위 추출과 20개 후보 순열**을 사용했습니다. API 답변을 반복하면서 후보 순서도 바꾸면 생성 변동과 순서 민감도가 섞입니다. 그 결과는 출력 안정성으로 보고하고, 순서 편향만의 효과로 단정하지 않습니다. 후속 시험에서는 같은 순서 반복과 순서만 바꾸는 반복을 분리합니다. [실험 조건 §4](https://arxiv.org/html/2608.03091v1#S4)

## 비교 시험의 설계

첫 시험은 **규칙 추천, nano 직접 추천, Luna 직접 추천, Jev API(유료) 선별 후 nano, Jev API(유료) 선별 후 Luna**의 다섯 구성을 고정합니다. 직접 추천과 선별 추천에는 같은 고객·장소 속성·중요도를 줍니다. 선별 결과를 nano와 Luna가 공유해야 어느 재정렬 모델이 더 나은지 같은 조건에서 비교할 수 있습니다. Jev API(유료)가 실행되지 못하면 해당 구성은 실제 미실행으로 보고하고 규칙 선별을 그 이름으로 대체하지 않습니다.

**24개 독립 문제·각 12개 이상 후보·3회 반복**은 소액 방향 확인 시험입니다. 24×3=72회는 72개 독립 고객 문제가 아닙니다. 먼저 각 문제의 반복 평균을 구하고, 문제 단위로 짝을 유지해 재표집합니다. 여러 문제에 같은 후보와 같은 원문의 변형을 쓰면 실질적인 독립성은 더 낮아집니다. [paired bootstrap](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html)

| 시험 묶음 | 구별해야 할 능력 | 예시 |
|---|---|---|
| 명시적 취향 | 정리된 선호의 적용 | 사진 선호, 긴 도보 기피 |
| 암묵적 취향 | 자연어와 후보 속성 연결 | 시끌벅적한 곳은 피하되 체험은 원함 |
| 우선순위 충돌 | 필수 조건과 가중치 구분 | 취향은 가장 맞지만 이동 한도 초과 |
| 가중치 반전 | 고객 중요도에 따른 순위 변화 | 이동 우선에서 취향 우선으로 변경 |
| 일정 맥락 | 전후 항목과 연결 | 다음 식사 예약에 맞춰 도착해야 함 |
| 해법 없음·동점 | 억지 추천과 불필요한 오답 처리 방지 | 가능한 후보 0개 또는 동일 효용 |
| 입력 순서 변형 | 순열 편향 | 같은 후보를 3개 순서로 제시 |
| 근거·자료 변경 | 허구 속성과 오래된 정보 방지 | 현재 자료에 없는 가격을 설명에 추가 |

정답표는 실행 전에 고정합니다. 필수 조건과 객관적 점수는 코드로 계산하고, 자연어 의미 태그는 작성자 초안과 독립 검수 상태를 남깁니다. **AI 독립 검수는 사람 검수가 아닙니다.** 모델 입력에는 정답·효용값·사람이 나중에 볼 채점 메모를 넣지 않습니다. 시험 결과를 본 뒤 프롬프트를 고쳤다면 새 판으로 분리하며 기존 시험과 합치지 않습니다. [OpenAI 업무별 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

명시적 속성+계수의 합성 정답은 모델이 계산·조건 적용을 잘하는지 측정합니다. 그것만으로 실제 고객이 더 만족한다는 결론을 낼 수 없습니다. 코드 대조군이 정답표와 같은 속성·계산식을 받으면 완벽에 가까운 점수는 자연스러운 결과이며, 이를 모델 취향 이해의 상한으로 해석하지 않습니다. 후속 실서비스 연구에서는 고객이 직접 작성한 표현과 블라인드 쌍별 선호 평가를 추가해야 합니다. ChinaTravel은 단순 합성 슬롯보다 사람의 열린 요구·암묵적 표현이 훨씬 어려운 평가 대상임을 보여 줍니다. [ChinaTravel v5](https://arxiv.org/abs/2412.13682)

고정된 후보를 주는 이번 시험은 **후보 안에서 좋은 순위를 고르는 능력**을 측정합니다. 최고 후보를 검색 단계에서 놓쳤는지는 별도 시험이 필요합니다. COMPASS v2 §5.2도 회수 범위 부족과 회수한 정보의 처리 실패를 나눕니다. TREK의 사람 검수는 정답 계획의 현실성·실행 가능성을 위한 것이며, 모델이 만든 답의 사람 만족 평가와 실플랫폼 전이는 후속 과제로 남았습니다. 합성 자료의 객관적 정답이 실제 고객 만족까지 보증하지 않습니다. [COMPASS 정보 회수 분석](https://arxiv.org/html/2510.07043v2#S5.SS2), [TREK 정답 검수](https://arxiv.org/html/2607.26977v2#S3.SS5)

|---|---|---|

| 유효 출력 | 스키마·ID·중복 규칙을 지킨 호출 / 전체 호출 | JSON 형식은 내용 정답을 보장하지 않음 |
| 지연 | 전체 경로 p50·p95 및 단계별 지연 | 재시도·선별·후속 모델을 포함 |
| 비용 | 모든 단계·실패·재시도·캐시의 사용량×해당 단가 | API 사용량 기반 추정; 결제 내역과 구분 |

nDCG의 할인·이상 순위와 동점 정의는 표준 구현을 참고합니다. 출력 실패를 정상 답으로 보정하지 않고, 전체 시도 기준 점수와 정상 출력만의 조건부 점수를 함께 보관합니다. McNemar는 같은 문제의 이진 성공 차이에 사용하고, 반복을 독립 사례로 취급하지 않습니다. [nDCG](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.ndcg_score.html), [McNemar](https://www.statsmodels.org/stable/generated/statsmodels.stats.contingency_tables.mcnemar.html), [구조화 출력](https://developers.openai.com/api/docs/guides/structured-outputs)

2026-10-09 확인한 표준 요금에서 nano는 입력 $0.20·캐시 입력 $0.02·출력 $1.25, Luna는 입력 $0.10·캐시 입력 $0.01·캐시 쓰기 $0.125·출력 $0.50입니다. 모두 100만 토큰당이며 짧은 입력 기준입니다. 캐시 쓰기는 해당 입력의 대체 단가이고 추가 요금이 아닙니다. 실제 사용량에 캐시 쓰기 구분이 있으면 이를 적용합니다. [가격표](https://developers.openai.com/api/docs/pricing), [캐시 과금](https://developers.openai.com/api/docs/guides/prompt-caching)

연쇄가 절감하려면 **선별 비용 < 선별로 줄인 후속 입력·출력·재시도 비용**이어야 합니다. 선별로 후보 수가 줄어도 reasoning 출력이 늘거나 호출이 추가되면 총비용은 커질 수 있습니다. 고객에게 보여 줄 이유를 매 단계 길게 생성하지 말고, 우선 짧은 ID·정해진 등급으로 순위를 시험합니다. 답의 길이와 요청 수는 지연에 영향을 주므로 모델 속도만 재지 않습니다. [OpenAI 지연 최적화](https://developers.openai.com/api/docs/guides/latency-optimization), [전문 재정렬과 선택적 LLM 비교](https://www.zeroentropy.dev/articles/should-you-use-llms-for-reranking-a-deep-dive-into-pointwise-listwise-and-cross-encoders/)

## 이전 원문 판정 시험의 가치와 한계

‘휴무·운영시간·실내외·재난 영향’의 원문 해석 시험에는 **좁지만 실제 가치가 있습니다.** API가 반환한 비정형 문구를 구조화 조건으로 옮기는 능력, 모델 연동·스키마·실패 처리, 저장된 원문 답과 사용량의 재계산 가능성을 확인할 수 있습니다. 복잡한 공휴일 예외나 의미가 애매한 활동 설명까지 전부 단순 정규식으로 해결한다고 단정하는 것도 옳지 않습니다.

반면 **그 결과를 취향 추천 모델의 채택 근거로 사용하는 것은 목적이 맞지 않습니다.** 후보 회수·취향 정합·중요도 적용·선별 누락·상위 3위 품질을 측정하지 않았기 때문입니다. 원문 해석이 실서비스의 병목이고 단순 규칙이 그 문장을 충분히 다루지 못한다는 증거가 있으면 필요한 구성 요소 시험입니다. 이미 정리된 값의 계산을 다시 모델에게 시킨 것이라면 비용과 변동성만 추가할 수 있습니다. 정리된 입력과 비정형 원문의 필요성을 분리한 비교가 선행돼야 합니다.

따라서 **‘전혀 장점이 없다’는 평가는 과하고, ‘추천 방향을 증명하지 못한 구성 요소 시험’이라는 평가는 타당합니다.** 기존 시험의 98.7%는 그 채점 조건의 값이며 새 추천 시험의 정확도로 옮겨 쓰지 않습니다. 숫자의 좁은 재현성과 채택 근거로서의 적합성을 구분합니다.

## 2026년 실제 서비스 연구에서 가져올 것

2026년 운영 사례에서는 **언어 의미를 이해하는 회수·순위 모델에, 실제 항목의 자격 확인과 비용 제어를 결합하는 방향**이 반복됩니다. 그러나 범용 대화 API를 바꾸기만 해서 얻은 결과가 아닙니다. 이용 기록과 추천 목표로 학습한 모델·정답 검수·배포 최적화가 함께 들어갑니다. 따라서 지금 제안한 여러 단계 구조의 방향을 뒷받침하지만, Jev API(유료) 선별 뒤 Luna가 반드시 최선이라는 근거는 아닙니다.

| 사례·발표 시점 | 실제 방법 | Activity에 가져올 부분 |
|---|---|---|
| LinkedIn follows · 2026-08-24 | 자연어 프로필을 학습한 회수 임베딩으로 바꾸고 같은 특징을 최종 순위에 사용 | 후보를 찾을 때와 순위를 매길 때 취향 의미가 달라지지 않게 유지 |

[LinkedIn follows](https://www.linkedin.com/blog/engineering/ai/rebuilding-linkedins-follows-recommendations-with-llm-based-semantic-retrieval-and-ranking)는 별도 학습한 회수와 순위의 특징 재사용 사례입니다. [LinkedIn Feed](https://www.linkedin.com/blog/engineering/feed/engineering-the-next-generation-of-linkedins-feed)는 의미와 행동 순서를 함께 다룹니다. 클릭·참여 목표는 여행 취향 효용과 다르므로 그 목적함수를 그대로 쓰지 않습니다. [LinkedIn 검색](https://www.linkedin.com/blog/engineering/search/reimagining-linkedins-search-stack)은 사람의 golden set과 작은 모델 순위·캐시를 결합합니다.

[Spotify 연구](https://research.atspotify.com/2026/8/from-models-to-products-llms-for-recommendation-at-spotify-scale)는 인기 항목으로 recall만 높여도 취향 정합성이 좋아졌다고 볼 수 없다고 설명합니다. 실제 목록·현재 이용 가능성·장단기 맥락·사람 평가를 함께 봅니다. [Meta SilverTorch](https://engineering.fb.com/2026/05/26/ml-applications/silvertorch-index-as-model-new-retrieval-paradigm-recommendation-systems/)의 필터는 실행 자격 규칙이며 의미 평가 모델과 구분됩니다. [Netflix GenRec](https://arxiv.org/abs/2608.10257)은 추천 데이터 후학습과 목록 점수 출력으로 비용을 제어합니다. 이들 대규모 서비스의 이득 수치를 12개 여행 후보나 추가 학습 없는 nano·Luna 성능 예상치로 옮기지 않습니다.

지금 적용할 첫 방법은 **고객 분석 결과를 짧은 정리 형태로 보내고, 실제 후보 ID·현재 사실·필수 조건을 코드로 보장하며, 모델의 추가 비용 대비 취향 개선을 재는 것**입니다. 장기적으로 이용 기록과 사람 선호 자료가 쌓이면 전용 임베딩·CrossEncoder·작은 결정 모델의 추가 학습도 비교할 수 있습니다. 아직 그 자료가 없는 단계에서 대규모 전용 모델 구조를 전부 구현하는 것은 비용 대비 근거가 부족합니다.

Netflix의 prefill-only는 **전용 목록 점수 출력부를 학습한 모델**의 방식입니다. nano·Luna API에 바로 적용할 수 있는 옵션으로 제안하지 않습니다. 논문의 온라인 비교도 batch-compute surfaces에 대한 결과이므로 실시간 여행 요청 지연의 증거로 확대하지 않습니다. 이번 API 시험에서 가져올 부분은 입력 압축과 짧은 출력의 비교 원칙입니다. [GenRec §4.5–§5.1](https://arxiv.org/html/2608.10257v2#S4.SS5)

핵심 주장과 확인한 본문 구절의 대조는 [심화 근거 검수](key_evidence_audit.md)에 별도로 남겼습니다. COMPASS 카탈로그의 최초 발표일은 Apple 소개 시점 대신 논문 초판인 2025-10-08로 바로잡았으며 최신 개정은 2026-04-16입니다.

## 실제 서비스로 넘어가기 전의 연구 순서

첫 단계는 이번 소액 시험으로 모델의 호출 가능성·조건 위반·토큰·연쇄 총비용을 확인하는 것입니다. 두 번째는 사람 표현을 포함한 검수 자료로 선별 임계값과 순위를 보정하고, 문제 수를 늘려 가설을 검증하는 것입니다. 세 번째는 고객 결과에 개입하지 않는 병행 기록으로 현재 코드와 새 추천을 비교합니다. 이후에만 정해진 품질·지연·비용 기준을 통과한 구성을 실제 적용합니다.

지금 규칙으로 고정해야 할 사실은 모델 출력과 독립된 상태여야 합니다. 운영시간·가격·경로의 자료 시점과 변경 이력을 관리하고, 취향·후보 속성·모델 버전·프롬프트 버전이 바뀌면 결과 캐시를 무효화합니다. 모델 판단 캐시와 최신 사실 조회 캐시는 서로 다른 유효기간을 갖습니다. 오래된 정보를 모델이 잘 설명했다고 올바른 추천으로 채점하지 않습니다.

전체 여행계획 벤치마크의 성공률을 서울 활동 대체 추천의 목표치로 가져오지 않습니다. TravelPlanner·TREK·TravelBench·Flex-TravelPlanner에서 가져올 것은 자료 고정, 해법 존재 검증, 조건 변화, 여러 턴 우선순위, 해결 불가 사례를 포함하는 **시험 설계 원칙**입니다. 이번 문제에서 실제로 어떤 구성이 낫다는 답은 동일 조건의 nano·Luna·선별 경로 실측과 후속 고객 검수로 결정합니다. [TREK](https://arxiv.org/abs/2607.26977), [TravelBench](https://arxiv.org/abs/2512.22673), [Flex-TravelPlanner](https://arxiv.org/abs/2506.04649)
