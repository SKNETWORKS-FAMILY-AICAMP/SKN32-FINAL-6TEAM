# Noul 특성 판정과 코드 추천 추가 탐색 기준

Jev API(유료)에 성격 제공 여부만 묻고, 고객 중요도·기피 감점·이동·유사도·반올림·최종 순위는 코드가 계산하는 방법을 추가 비교합니다. Score에 의미 판정과 산술을 함께 맡긴 구성만으로 Jev API(유료)의 단독 추천 가능성을 판단하지 않기 위한 탐색입니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 추가 방법과 기준 고정 | 완료 | 1/1 = 100% |
| 비용 없는 단위 시험 | 통과 | 43/43 = 100% |

이 기준은 **본 eval-v1 실행 중 추가한 탐색이며, Noul 추가 유료 호출 전에 고정**했습니다. 본 평가 시작 전 사전등록이라고 부르지 않습니다. 본 재시험의 개발 자료에서 이미 선택된 nano/Luna `none/none` 설정은 바꾸지 않습니다. 추가 방법은 원문과 과업 정의에 근거하며, 본 eval-v1의 품질 결과로 질문·임계값·가중치를 조정하지 않았습니다. 작성 시 이 추가 방법의 실제 유료 호출은0회입니다.

## 고정하는 방법

1. 동결된 평가48문제에서 기존 `prepare_case`로 사실 상태와 방문 가능 후보를 확인합니다. 상태가 `ready`가 아니면 해당 상태와 빈 순위를 코드로 기록합니다. 가능 후보1개도 코드로 선택하며 유료 호출하지 않습니다.
2. 가능 후보2개 이상이면 후보마다 고객 likes/dislikes의 서로 다른 trait를 한 번씩 질문합니다. `state={}`로 다른 후보나 고객 중요도를 공유하지 않습니다. 질문의 입력은 해당 후보 설명과 trait뿐입니다.
3. 질문은 `type=noul`, `instructions={question,description}`이며 다음 형식을 사용합니다. `이 설명이 [조용함] 성격을 실제 제공함을 말하는가?` true는 실제 제공 확인, false는 부정·단순 인용·명령·광고성 지시·비제공으로 정의합니다. 추가 예시 문장이나 자료별 보정은 이번 고정판에 넣지 않습니다.
4. Noul이0.5 이상이면 제공=true, 미만이면false입니다. 확률 크기를 취향 강도로 사용하지 않습니다. bool에 선호 중요도와 기피 벌점을 적용하고0~1로 제한한 뒤 `floor(x*4+.5)/4`로 가장 가까운0.25 등급을 계산합니다. 중간값은 위 등급으로 갑니다.
5. 이동 점수는 `max(0,1-travel_min/60)`, 유사도는 원래 분류와 같으면1, 복합문화이면0.5, 그 외0입니다. 기존 weights로 합산해 상위 `min(3,가능 후보 수)`를 반환합니다. 동점은 복수 정답을 인정하며 코드 표시 순서는 ID 사전순입니다.

임계값0.5는 이번 탐색의 고정 선택입니다. 보정된 실제 정답 확률이나 최적 임계값이라는 뜻이 아닙니다. 후보 설명이 모순되거나 사실 자체가 틀리면 이 방법도 올바른 추천을 보장하지 않습니다. [TypeSafe Noul과 Score 유형](https://docs.typesafe.ai/primitives)의 구분을 사용하되 해당 문서가 한국어 여행 성능을 증명한다고 해석하지 않습니다.
