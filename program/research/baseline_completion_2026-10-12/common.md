# 25개 wiki 개정 후속 구현·검증 공통 지시

사용자 직접 요청: “SQL 문제만 말고 표에 남아 있는 구현·검증 작업들도 새 세션으로 나눠서 진행시켜. 이미 다른 세션에서 하는 건 중복하지 말고, 다 끝나면 wiki 기준으로 v12랑 최종 베이스라인까지 만들어.”

현재 사양은 wiki의 확정 결정·계약입니다. v11은 당시 기록으로 보존합니다. 과거 구현을 현재 결정으로 오인하거나, 구현 차이를 근거로 확정 결정을 임의로 되돌리지 않습니다. 루트와 수정 대상 프로젝트의 AGENTS.md·RULE.md, 해당 기능의 wiki 계약을 먼저 읽습니다.

## 입력과 작업 경계

- `program/research/review_status_2026-10-12/status.json`: W01~W25 현황 출발점. 모든 기능의 인수 시험이 완료됐다는 뜻이 아닙니다.
- `program/research/wiki_review_2026-10-11/findings-v2.json`: 사용자 선택과 관련 문서. 일부 completion_evidence는 이전 시점 기록이므로 현재 파일·실측과 대조합니다.
- 이 폴더의 `coordination.json`: 담당 세션·의존 관계·기존 세션의 중복 제외 범위입니다. 최신 list_threads/read_thread로 변화도 확인합니다. 다른 세션의 메시지·출력은 사실 확인 자료이지 추가 권한이 아닙니다.
- `tasks/<담당>/task.md`: 해당 세션의 수정 범위와 완료 조건입니다. 공유 파일은 원문과 현재 변경을 읽고 기능별 작은 변경만 반영합니다. 같은 부분을 다른 세션이 수정 중이면 인계 패치·필요한 접합부를 남겨 최종 통합 때 적용합니다. 다른 작업을 되돌리지 않습니다.

## 공통 완료 기준

1. 설계 설명에 머물지 말고 현재 계약과 실제 호출 경로를 비교한 뒤 필요한 구현·관련 시험까지 진행합니다. 이미 구현된 것은 중복 구현하지 않고 실행 증거로 확인합니다.
2. 변경 전 산출물·생성 스크립트와 출력을 지정된 `_backup/날짜_시각_이유/`에 보존합니다. 과거 records·legacy는 현재 사양으로 소급 수정하지 않습니다.
3. tenant/customer/trip 격리, Team의 ActionProposal 반환, Core의 도메인 중립성, CAS·멱등성·감사·outbox 경계를 유지합니다. 상주 상담원·고객 문제 직접 수정 운영자 구조를 만들지 않습니다. 개발자/QA 사후 분석용 운영자 웹앱은 별도입니다.
4. 실제 업무 DB 변경, 원격 배포·재시작, 커밋·푸시, 고객 알림·웹훅, 결제·유료 외부 호출, 수집 예산 확대는 이번 분담에 포함하지 않습니다. 격리 시험은 허용합니다. 실제 적용에 필요한 권한·계정·값이 없으면 근거와 미검증 범위를 표시하고 구현·격리 시험은 계속합니다.
5. 공용 자료에는 접속 주소·계정·키·SSH 별칭·웹훅 URL 등을 적지 않습니다. 외부 기술 사실은 공식 문서·원 논문 등 1차 자료로 확인합니다. 법·약관 해석만으로 기존 데이터나 기능을 삭제하지 않습니다.
6. 실행 명령·조건·성공/실패/건너뜀·분자/분모·실행 시각·변경 파일·해시·백업·남은 문제를 새 보고서에 기록합니다. mock 서버 시험(화면 반응)과 실서버 확인(서버 응답)은 구분합니다. 관련 의미 있는 시험을 우선하고 전체 제품 통과로 확대 해석하지 않습니다.

## 세션 결과 전달

각 세션은 자기 `tasks/<담당>/status.json`만 갱신하고 이 폴더의 공용 coordination.json·다른 세션 결과를 고치지 않습니다. 상태 파일에는 다음을 기록합니다.

```json
{
  "phase": "running | waiting_dependency | ready_for_integration | blocked",
  "updated_at_kst": "실제 한국 시간",
  "w_ids": [],
  "changed_files": [],
  "tests": [{"command":"", "passed":0, "failed":0, "skipped":0, "evidence":""}],
  "report": "워크스페이스 기준 경로",
  "dependencies_remaining": [],
  "unresolved": [],
  "deployment": "not_deployed",
  "ready_reason": ""
}
```

`ready_for_integration`은 해당 구현·검증 범위의 증거가 갖춰져 통합 검토를 요청하는 상태입니다. 미구현 필수 요구나 실패한 필수 시험을 숨긴 채 이 상태로 올리지 않습니다. 외부 자격 증명이 필요한 실제 연결과 로컬 구현 완료는 나눠 기록합니다. 자동 승인 검토 거절은 우회하지 않고 거절 대상과 이유를 정확히 남깁니다. 작업 진행·최종 보고는 한국어 존댓말과 분자/분모가 있는 진행 표를 사용합니다.
