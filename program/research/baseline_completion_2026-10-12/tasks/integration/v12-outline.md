# triPilot v12 안내서 — 검토 준비본

triPilot은 여행 계획이 실제로 가능한지 확인하고 여행 중 변화를 살펴 조정합니다. 이 문서는 후속 구현 결과를 기다리는 작성 골격입니다. 기능 완료·출시 승인·최종 기준선 확정을 뜻하지 않습니다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 요구 추적 항목 작성 | 준비 | 25/25 = 100% |
| 항목별 인수 근거 검토 | 대기 | 0/25 = 0% |
| 최종 안내서·기준선 | 대기 | 0/2 = 0% |

분모 25는 W01~W25 요구 항목 수입니다. 문서만 바뀌는 항목도 포함하므로 제품 기능 수나 시험 수가 아닙니다.

## 1. 이 안내서의 책임과 읽는 순서

읽는 사람은 코드를 처음 보는 팀원입니다. 먼저 고객이 무엇을 할 수 있는지, 그다음 누가 판단하고 실행하는지, 마지막으로 실제 확인한 범위를 읽습니다. 확정 사양의 정본은 [현재 wiki](../../../../../wiki/index.md)입니다. v12는 사양의 위치와 동작을 이해하도록 돕는 안내서입니다. 같은 정책을 별도의 정본으로 유지하지 않습니다.

최종 파일은 `program/plan/triPilot_구현계획서_v12.md`와 같은 내용의 검토용 HTML로 만듭니다. [v11](../../../../plan/A-COP_구현계획서_v11.md)은 2026-09-10 당시 기록으로 보존합니다. 최종 판정 때 보존 전후 해시를 대조합니다.

## 2. 고객이 사용하는 세 경로

[제품 범위](../../../../../wiki/product/scope.md)의 확정 계약을 요약합니다.

| 경로 | 고객이 하는 일 | 접근 범위 |
|---|---|---|
| 고객 웹 앱 | 여행 입력, 최초 일정 구성, 검증 결과 확인, 설정, 변경 요청 | 로그인한 고객의 본인 여행 |
| 개인 AI 연결 | AI를 통해 일정 제출·조회·질의·허용된 변경 요청 | 고객이 허용한 권한과 본인 여행 |
| 공유 계획서 링크 | 최신 일정과 변경 이유 열람 | 공유된 여행의 읽기 범위 |

세 경로는 같은 여행 상태를 봅니다. 최초 일정 구성과 여행 중 재계획은 구분하되, 모두 시간·이동·예산·장소 조건을 검증한 결과만 제시합니다. OAuth 연결의 실제 클라이언트 시험과 웹 로그인 시험은 별개의 증거로 남깁니다.

## 3. 판단하는 에이전트와 실행 장치

[D-017](../../../../../wiki/decisions/D-017-watch-cadence-golden-time.md)과 [팀 경계](../../../../../final_project_cs/wiki/teams/team-boundary.md)를 따릅니다.

분류 에이전트는 질문, 여행 계획, 현재 상황, 고객 성향, 활성 팀 목록을 보고 담당 팀·순서·우선순위·이유·의존 관계를 정합니다. 공통 실행 장치는 등록 여부·권한·예산·순환을 검사한 뒤 승인된 계획을 실행합니다. Activity 에이전트 팀이 다른 팀의 호출 순서를 정하지 않습니다.

Activity는 여행 활동, Dining은 식사, Mobility는 이동을 담당합니다. 각 팀은 허용된 조회 도구로 근거를 얻고 변경 제안을 반환합니다. 일정 저장·고객 알림·예약 거래 등 외부에 영향을 주는 실행은 공통 실행 경계가 맡습니다. Booking Handoff는 다음 단계이며, Lodging·Flight는 현재 잠긴 예약 취급이라는 [제품 범위](../../../../../wiki/product/scope.md)를 유지합니다.

예: 비 때문에 야외 활동을 바꿔야 하면 분류 에이전트가 활동 대안, 식사 시간, 이동 검증의 필요한 순서를 정합니다. 각 팀이 계산한 결과가 합친 일정에서도 성립해야 저장합니다.

최종본에는 목표 계약과 실제 호출 경로의 일치 여부, 비활성 팀·잘못된 계획·예산 초과·도구 권한 위반 시험을 연결합니다. 파일 존재만으로 구현됐다고 적지 않습니다.

## 4. 항로 지킴이와 고정 일정

[현재 설문 결정](../../../../../wiki/decisions/D-020-trip-survey-and-ask-first.md)의 현재 계약을 우선합니다. 옛 `replace`·`ask_first` 값은 호환성 검증 대상이며, 예전 본문만 읽고 현재 동작을 확정하지 않습니다.

| 조건 | 동작 |
|---|---|
| 항로 지킴이 켜짐, 변경 가능 조건 충족 | 검증된 대안 적용 후 변경 이유 안내 |
| 항로 지킴이 꺼짐 | 자동 적용 없이 고객이 선택할 수 있게 안내 |
| 고객이 변경하지 않기로 고정한 항목 | 감지·안내는 계속, 항목 변경은 고객 선택 필요 |
| 고객이 정지한 변경 | 명시적 재개 전까지 정지, 날짜 변경만으로 재개 금지 |
| 업체 예약·결제·환급 | 별도 거래 승인·권한 검사 |

최종본에는 웹 표시값·실제 판정값·알림값·기존 여행 호환성의 같은 규칙 적용 여부를 연결합니다.

## 5. 한 회차의 점검과 알림

모니터링 툴은 외부 자료와 여행 상태를 살펴 문제를 발견합니다. 분류 에이전트가 처리 계획을 정하고 각 팀이 업무 계산을 합니다. 한 회차·한 여행의 문제 묶음과 여행 전체 수명은 다릅니다. 다음 회차를 시작하는 조건도 그림에 따로 씁니다.

3분 점검 간격은 원본 자료의 나이가 3분 이하라는 보장이 아닙니다. 원문 게시, 수집, 캐시, 판정, 통지 시각을 구분합니다. 원문 시각이 없으면 감지 지연을 추정치로 채우지 않습니다. 실제 자료 최신성 측정은 verification 담당 결과를 연결합니다.

알림은 일정 상태를 확인하는 신호이며 최신 계획서·인증된 조회 상태가 근거입니다. 알림 수신·열람과 계획서 열람도 구분합니다. 최종 시점 규칙은 [알림 계약](../../../../../wiki/architecture/notifications.md)을 직접 인용하고, 과거 시점표를 복사하지 않습니다.

## 6. 조회 실패와 무인 운영

[D-018](../../../../../wiki/decisions/D-018-decision15-stop-paths.md)에 따라 실패한 조회에 의존하는 변경만 보류하고 기존 일정·독립 기능을 유지합니다. 대체 자료까지 실패하면 확인 불가 상태·시각·오류를 남기고 고객에게 안내합니다. 자료가 복구되면 최신 고객 설정과 일정으로 재검증합니다.

예: 식당 영업 조회가 실패하면 그 식당의 변경을 보류합니다. 독립적인 활동 변경은 계속할 수 있지만 합친 일정의 시간·이동 검증도 통과해야 합니다.

상주 상담원에게 고객 문제를 넘기는 구조를 두지 않습니다. 고객에게 필요한 입력을 받고, 개발자·QA는 장애·미매칭·영향 고객을 사후 분석합니다. 진단 기록의 마스킹, 영속 대기 파일, 용량 상한, 유실 지표는 [자동 처리·결함 계약](../../../../../final_project_cs/wiki/decisions/D-CS-014-routing-reroute.md)을 따릅니다.

## 7. 인증·자료·모델의 경계

브라우저 로그인, 개인 AI의 OAuth 동의, 공유 링크 읽기를 분리합니다. 고객·여행 격리와 읽기·쓰기 권한, 만료·폐기를 검사합니다. MCP 쓰기는 권한과 기능 스위치가 모두 허용해야 합니다. 개인 AI가 계정 관리나 공급자 거래 승인을 대신하지 않습니다.

무료 자료 우선, 승인된 조회 경로, 호출 예산, 사실 자료와 사진·소개글 정책을 각각 해당 wiki 계약에 연결합니다. 학업용 이미지의 Git 밖 보관 예외를 배포 허용으로 확대하지 않습니다. 쇼핑몰 당시 데이터·평가·시연은 현재 제품에서 사용하지 않습니다. ODsay의 제품 미사용과 별도 연구 검토도 구분합니다.

모델은 정확한 이름, 원본 판본, 우리 데이터 학습 여부, 추론 설정, 자료·프롬프트 해시를 기록합니다. Jev 계열 모델은 정확한 모델 이름과 학습 여부를 적습니다. 실제 채택·환경별 로딩은 verification 담당의 실측 근거가 있어야 채웁니다.

## 8. 구현·검증·환경별 적용

최종본에는 [통합표](integration-table.md)의 항목별 판정과 [원본 해시](current-source-manifest.json)를 연결합니다. 공통·여행 전체 시험, 계약·보안·현재 관문, wiki·생성물 검사 결과의 실패·건너뜀·분모·시각을 그대로 싣습니다. 불변식 목록 수와 시험 통과 수는 별개입니다.

로컬 개발 환경, x600 서버의 cs 프로젝트 서버, 오라클 ARM 환경, GPU 서버는 각각 코드·설정·DB·모델·모니터링 툴의 확인 시각과 적용 근거를 구분합니다. 이 분담에서는 실제 업무 DB 변경·배포·재시작·커밋·푸시·고객 알림을 수행하지 않습니다.

## 9. 남은 요구와 변경 절차

필수 미구현·실패 시험·미실행 외부 연결을 숨기지 않습니다. 외부 자격 증명이 필요한 실제 연결은 로컬 구현 완료와 분리합니다. 확정 사양을 바꾸려면 wiki 결정·계약을 먼저 수정하고 영향받는 구현·시험·환경을 확인한 뒤 새 기준선 판본과 근거 해시를 남깁니다.

최종 기준선은 제품 전체에 하나이며, 하위 에이전트 구축·학습 보고서는 별도 근거로 연결합니다. 최종 표시 전 문서 링크·해시·요구 추적·예시·출처·비밀값 노출을 검사합니다.

## 작성 대기 항목

- auth·orchestration·operations·wiki 담당의 변경 파일과 원본 시험 결과
- verification 담당의 공통·여행 전체 실행과 환경·모델·자료 최신성 대조
- 기존 SQL·화면·채팅·이동·식당·RAG·경보 중 이 요구와 관계있는 결과
- 최종 소스 해시의 고정, 그림·HTML 확인, 문서 재검토와 실패 항목 기록
