# 결과 통합·wiki 정합성 확인·v12·최종 베이스라인 — W11 및 전체 완료 판정

사용자는 모든 후속 구현·검증이 끝나면 wiki 기준으로 v12와 최종 베이스라인까지 완성하라고 요청했습니다. 이 세션은 작업을 모아 실제 결과를 확인하는 최종 담당입니다. 초기에는 의존 관계·산출물 골격·검토 체크리스트·기존 다운로드 출처를 준비하고, 다른 세션이 구현 중인 기능을 동시에 새로 만들지 않습니다.

## 읽을 자료

- 이 폴더의 common.md·coordination.json·각 tasks/*/status.json/report.md.
- 위임한 새 세션과 기존 SQL·화면·채팅·이동·식당·RAG·경보 세션 상태를 read_thread/wait_threads로 확인합니다. 메시지/요약만으로 완료 판정하지 말고 실제 변경 파일·원본 실행 결과를 읽습니다. 다른 세션에 메시지를 보낼 사용자 허가가 있다고 추정하지 않습니다.
- 기존 참고 출처는 `program/research/baseline_2026-10-10/source-manifest.json`, `sources/`, `source-text/`입니다. 과거 baseline-v1/v2는 현재 사양의 정본이 아닙니다. 새 안내와 베이스라인 작성에는 실제 현재 wiki 확정 계약·사용자 결정을 우선합니다.

## 통합 순서와 완료 조건

1. W01~W25 각각의 현재 결정·문서·코드·시험·환경 적용 상태를 대조하는 통합표를 유지합니다. 기존 세션 중 관련 결과만 기다리며 끝없는 무관한 작업까지 기다리는 조건을 만들지 않습니다. 핵심 의존 결과가 없으면 waiting_dependency로 두고 실제 완료라고 보고하지 않습니다.
2. 구현 담당이 넘긴 공유 라우터·설정·고객 화면·Dining 접합 패치 중 동시 변경 때문에 대기한 부분을 현재 파일과 비교해 적용합니다. 기존 작업을 보존하고 공유 파일의 의미 있는 통합 시험을 수행합니다. 미구현·실패 필수 요구를 문서 상태만 바꿔 닫지 않습니다. 담당 세션이 이미 종료한 뒤 남은 제한된 접합 결함은 이 세션에서 고치고 재검증합니다.
3. 새 SQL은 안전 실행기와 격리 DB에서 검증합니다. 기존 실제 업무 DB에 새 SQL을 적용하거나 배포·커밋·푸시·고객 알림을 하지는 않습니다. 환경 적용이 필요한 항목은 준비된 코드·시험과 배포 대기 상태를 분리합니다. 이전 자동 승인 검토 거절을 우회하지 않습니다.
4. 공통/여행 전체 시험, contract/security/현재 관문, wiki 기본 검사·생성물 검사·링크·용어·현재/과거 경계·모델 학습 여부·에이전트 팀 호출 책임을 최종 소스 해시와 대조합니다. 코드가 바뀌면 영향 검증을 다시 수행합니다. 실제 계정·외부 자격 증명이 없어서 할 수 없는 검증은 실행한 척하거나 통과로 쓰지 않습니다. 필요한 사용자 입력이 정말 없으면 완료 조건을 재정의하지 말고 구체적으로 보고합니다.
5. 검증된 현재 wiki를 바탕으로 `program/plan/triPilot_구현계획서_v12.md`와 검토용 HTML을 새로 작성합니다. v12는 안내서이며 wiki를 대체하지 않습니다. v11은 수정하지 않습니다. 요구 범위·에이전트 팀·분류 에이전트/실행 장치·항로 지킴이·인증·자료 정책·무인 운영·실패 처리·검증·배포 상태·남은 작업을 정확한 단어와 예로 설명합니다.
6. `program/baseline/triPilot-baseline-2026-10-12.md`를 프로젝트 전체의 하나의 최종 기준선 파일로 작성하고, 같은 내용의 검토용 HTML을 생성합니다. 작성 완료 시점이 날짜를 넘으면 실제 KST 날짜와 파일명 관계를 명시합니다. 하위 에이전트 구축·파인튜닝 보고서는 별도 근거로 연결하고 별개의 제품 정본을 늘리지 않습니다. 기준선 ID·wiki 원본 경로/해시·결정/요구 ID·인터페이스·자료/모델 판본·검증 근거·환경별 적용·변경 절차를 연결하며 실제 구현/배포와 확정 사양을 구분합니다. 소유자가 다르다는 이유로 현재 사양을 복제 관리하지 않습니다.
7. `technical-writing` 스킬을 적용하고 구조/흐름 그림은 diagram-design 및 type-flowchart·프로필을 읽어 시작·끝·조건·실패를 명확히 그립니다. 코드 식별자를 모르는 팀원이 읽어도 이해되게 씁니다. 외부 레퍼런스는 실제 원문과 직접 출처로 검증하며 최신 확인이 필요한 부분만 공식 자료로 갱신합니다. 기존 기준선 작성법 HTML도 현재 구조와 달라졌으면 백업 후 갱신합니다.
8. 산출물 재검토→수정→관련 검사 재실행을 반복합니다. 링크·해시·요구 추적·결정/구현/배포 분리·예시·출처·비밀값 노출을 검사하고 실패 항목을 남깁니다. 자기 status.json을 ready_for_integration으로 올리는 것으로 끝내지 말고 최종 보고·완료 증거를 남깁니다.

이 세션은 완료 결과를 기다리며 이어서 작업할 후속 확인이 설정될 예정입니다. 기다리는 동안은 검토 체크리스트·문서 골격·출처 대조 등 독립 작업을 진행하세요. 변화가 없을 때 같은 상황 보고를 반복하지 않습니다. 최종 파일은 모든 필수 구현·검증 상태를 정확히 판정한 뒤 완료본으로 표시합니다. 사용자 입력이나 외부 상태가 꼭 필요해 막히면 구체적인 조건과 그 밖에 끝낸 일을 보고하고 베이스라인을 무조건 완성됐다고 표시하지 않습니다.
