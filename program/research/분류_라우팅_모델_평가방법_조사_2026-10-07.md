# 질의를 분석해 알맞은 에이전트에 넘기는 모델 — 논문·실무에서 하는 시험 목록 (2026-10-07 기준 조사)

> 질문(사용자 2026-10-07): 우리 일은 사용자 질의가 어떤 문제인지 파악해 알맞은 에이전트에 넘기는 것이다. 이런 모델을 논문·실무에서는 **어떤 시험으로 성능을 재고, 파인튜닝이 잘 됐다고 판단하나.**
> 전제(사용자 정정 2026-10-07): 이 프로젝트는 **학업 부트캠프용 비상업 프로젝트**이고 경쟁 AI 모델을 만드는 것이 아니다. 아래 약관 항목은 상업으로 전환할 때만 해당한다.
> **근거 등급**: ★원문 읽음 · ◎논문 초록 페이지에서 제목·저자·학회·핵심 확인 · ○검색 요약만 봤음(원문 미확인). 모든 링크는 조사 때 실제로 열린 주소다.

## 한눈에

1. 이런 모델의 시험은 **정확도 하나가 아니라 열 가지 안팎의 검사**로 한다. 아래 표가 그 목록이고, 각 검사마다 **방법 · 지표 · 대표 논문**을 붙였다.
2. 핵심 묶음은 다섯이다: **통계적으로 믿을 수 있는 정확도**(구간 · 짝지은 검정 · 시드) / **범위 밖과 기권** / **보정** / **견고성** / **운영 지표와 문서화**.
3. 2026 년 논문 둘이 우리 설계와 직접 맞닿는다: ★Rodrigues & Vas(2026-06) — 클래스가 배포마다 바뀌면 학습한 분류기는 새 클래스에서 0%이고 스키마를 주는 LLM이 필요, 범위 밖은 LLM이 낫다 / Rabanser 외(2026) — 에이전트 신뢰성을 정확도와 따로 일관성 · 견고성 · 예측가능성 · 안전 4차원 12지표로 잰다.

**모델 종류를 고르는 기준(★Rodrigues & Vas 2026)**: 클래스 고정 · 라벨 많음 · 지연 중요 → 학습한 인코더(ATIS 95.9 대 Claude 제로샷 84.1) / 클래스 많고 라벨 보통 → 동률(CLINC150 89.1 대 88.5, p=0.24) / **배포마다 클래스가 바뀌고 라벨 없음 → 스키마를 프롬프트로 주는 LLM**(학습한 분류기는 새 앱 클래스에서 0%, LLM 은 두 앱 모두 약 94%) / 범위 밖이 중요 → LLM 또는 빠른 분류기 위에 LLM 기권 / 확신이 낮을 때만 LLM 으로 넘기는 혼합이 이득 대부분을 가져간다. 지연은 RoBERTa 2.4 ms 대 LLM API p50 981 ms · p95 1,787 ms. 한계: 영어 · 한 LLM · 한 인코더.

## 1-2. 각 시험을 하는 이유와 우리 프로젝트에 쓴다고 판단한 근거 (사용자 요청 2026-10-07)

판단 표기: **필수** = 하지 않으면 우리 설계의 규칙을 못 지킴 / **권장** = 설계에 쓰는 기능이 있어 같이 재야 함 / **차용** = 방식만 가져옴 / **선택** = 있으면 좋음. 「우리 근거」는 프로젝트 규칙과 이미 잰 값에서 가져왔다.

| # | 검사 | 하는 이유 | 우리 프로젝트에 쓰는 근거 | 판단 |
|---|---|---|---|---|
| 1 | 정확도(분류) | 클래스 빈도가 다르면 평균 정확도가 소수 클래스 실패를 가린다. 거시 F1 · 혼동행렬이 약한 클래스를 찾는다 | 우리 라우팅은 여러 클래스(요청 종류 · 대상 종류 · 긴급도)이고 약한 클래스가 실제로 있다(긴급도 medium 재현율 0.76 · 대상 flight 0.78) — 이 지표로 찾았다 | 필수 |
| 2 | 통계적 유의성(구간 · 짝지은 검정 · 시드) | 시험 문제 수가 적고 학습이 한 번 달라져도 값이 흔들려 점 하나로 「A 가 낫다」를 말할 수 없다 | **실제로 틀릴 뻔했다**: 같은 레시피에서 시드만 바꿔 769문제 748~760(최대 12문제), D 시험 85.6~93.7%. 한 시드 비교(Winnow-E4B 756 대 E4B 750)는 결론이 아니었다. 같은 문장 짝지은 검정으로만 비교 | 필수 |
| 3 | 범위 밖(OOS) | 실제 고객은 잡담 · 다른 장소 · 무관한 말을 보낸다. 이때 항목을 지어내면 잘못된 안내가 나간다 | 서비스 최우선 규칙이 「근거 없으면 확정 답 금지」. D 시험의 오지목이 모델을 갈랐다(가르친 E4B 4.3~16.0% · 학습 없는 12B 17.4% · FrogNano 0.9%) — 모델 선택 근거가 된 검사 | 필수 |
| 4 | 오분류 · 분포 밖 탐지(확신도 AUROC) | 확신도가 틀린 답을 가려내면 별도 필터 없이 거를 수 있다 | 확신도(답 토큰 확률)로 되묻기 · 큰 모델 위임을 설계했다(§89) — 그 확신도의 질을 재는 직접 대응. 아직 AUROC 로는 안 쟀다 | 권장 |
| 5 | 보정(ECE) | 임계값(예: 확신 0.8 미만이면 되묻기)이 뜻을 가지려면 확신도가 실제 정확도와 맞아야 한다 | 임계값 기반 되묻기 · 위임을 쓰는 한 필요. CX 에서 ECE 0.014~0.042 측정, 서비스 실행기(llama.cpp)에서는 미측정 | 필수 |
| 6 | 기권(위험-커버리지 곡선) | 「맞출 수 있는 만큼만 답한다」를 하면 오류율을 목표에 맞출 수 있다 | **사람 대기 없음 결정**(고객 건을 사람에게 넘기지 않음)이라 기권은 사람 인계가 아니라 되묻기 · 「모른다」 안내 — 어느 확신도에서 얼마나 받고 오류가 얼마나 주는지 곡선이 있어야 임계값을 정한다. 아직 곡선은 안 그렸다 | 권장 |
| 7 | 견고성 · 행동 검사 | 실제 말투는 오타 · 구어체 · 생략 · 부정문이라 깨끗한 합성 문장만으로는 놓친다 | 일정 질문 유형 10종(오타 · 속어, 부정, 대명사, 헷갈리는 이름, 이름 없는 설명 …)이 CheckList 의 「능력 × 유형」 표와 같은 구조다 — 유형별로 약점을 찾았다(이름 없는 설명 75문제 중 63). 변형을 묶음으로 만든 말투 시험은 아직 없다 | 필수(유형별은 함) |
| 8 | 종합 평가 축(HELM) | 한 축만 올리다 다른 축이 무너지는 것을 막는다 | 7축 전부는 과하다(공정성 · 독성은 우리 일이 아님). 정확도 · 보정 · 견고성 · 효율 4축만 해당 — 4축 모두 이미 측정 | 차용(4/7) |
| 9 | 도구 호출 · 에이전트(pass^k, 최종 상태) | 같은 일을 시켰을 때 매번 같은 결과가 나와야 고객 서비스를 믿는다 | 결정 단위 재생을 3번 돌려 pass^3 91.3%로 쟀다. τ-bench 의 「DB 최종 상태 비교」는 우리 Team 이 **제안만 하고 실행은 승인**이라 「제안한 대상 · 할 일의 일치」로 바꿔 쓴다 | 필수(pass^k) · 차용(최종 상태) |
| 10 | 에이전트 신뢰성 분해 | 정확도가 올라도 일관성 · 견고성 · 예측가능성 · 안전은 안 오를 수 있다 | 12지표 전체는 안 쓰고 개념만 차용: 일관성=pass^3, 견고성=유형별, 예측가능성=확신도. 안전은 승인 · 근거 규칙 쪽(별도) | 차용 |
| 11 | 라우팅 비교(오라클 · 비용-성능 곡선) | 모델 조합이 비용 대비 이득인지 본다 | 우리 단계 처리(규칙 → ML → 분류 → LLM)가 같은 구조다(호출 절감 · 정확도를 오라클과 비교). RouterBench 자체는 「어느 LLM 에 보내나」 벤치라 그대로는 안 맞고 평가 방식만 차용 | 차용 |
