## 3. 바꿔야 할 점 Top 5

1. **“한 규칙이 잡으면 그 문단은 읽은 것”이라는 처리부터 없애십시오.**  
   규칙이 한 항목을 찾았더라도 나머지 문장에는 이동 수단, 비 오는 날 대안, 선호가 남을 수 있습니다. 원문 줄이나 구간을 모두 보존하고, 추출되지 않은 구간을 따로 넘겨야 누락을 알아챌 수 있습니다.

2. **짧은 채팅과 긴 파일을 다른 경로로 처리하십시오.**  
   짧은 채팅은 한 번 호출에서 “새 계획·변경·질문”과 일정 정보를 함께 추출하면 지연을 덜 늘립니다. 긴 PDF·사진 전사본·산문 계획은 구간별로 읽고 결과를 합쳐야 8k 문맥 한도에서 정보가 잘릴 위험을 줄입니다. 표 파일은 셀 값을 그대로 가져오고, 모르는 열 제목만 모델에 물어보는 현재 방향을 유지하면 됩니다.

3. **출력 JSON에 필드별 근거 위치와 ‘모름’을 넣으십시오.**  
   이동 수단·날씨 조건·선호를 일정과 분리해 표현하고, 각 값이 나온 원문 구간을 함께 저장하십시오. 장소 자동 교정이나 일정 합치기는 코드가 재검증하고, 근거가 모자라면 모델이 빈칸이나 확인 필요를 반환하게 해야 합니다. JSON 형식 제한은 내용 검증을 대신하지 않습니다.

4. **안전·범위 판단은 같은 추출 호출 하나에 맡기지 마십시오.**  
   크기·빈도·도구 허용 범위는 코드로 막고, 사용자 문장은 신뢰할 수 없는 입력 데이터로 취급하십시오. 여행 서비스 범위 판정이 필요하면 한국어 실제 메시지로 별도 분류기를 비교하십시오. 안전 모델을 붙일 때도 지연과 오탐을 측정해야 합니다.

5. **메모리와 모델 학습에 사용자 통제·회귀 확인을 넣으십시오.**  
   고객별 선호를 근거가 달린 레코드로 저장하고, 고객이 확인·수정·삭제하도록 하십시오. E4B를 다시 학습할 때는 다양한 한국어 실제 대화와 합성 입력을 섞고, 시간·장소·교통·조건·분류 능력이 이전보다 나빠지지 않았는지 기존 모델과 비교하십시오. 어댑터를 하나로 합칠지 나눌지는 12GB GPU에서 측정하기 전에는 단정할 수 없습니다.

## 4. 확인하지 못했거나 근거가 약한 점

- **guguroute과 같은 한국어 여행 일정 데이터에서 4B급 E4B, 8k 문맥, 12GB GPU, Ollama를 놓고 단일 호출과 분할 호출을 직접 비교한 공개 연구는 찾지 못했습니다.** 권고는 공개 연구의 일반 결과와 입력 형태를 바탕으로 한 설계 판단입니다.
- 전용 가드 모델을 추가했을 때 guguroute의 5~7초 추론 시간에 실제로 몇 초가 더해지는지는 측정 자료가 없습니다. 추가 호출이 직렬이면 늦어질 수 있다는 것은 구조에서 나온 추론입니다.
- vLLM과 llama.cpp의 어댑터 기능은 공식 문서에서 확인했지만, **현재 Ollama 버전에서 작업별 어댑터를 요청 단위로 선택할 수 있는지**는 확인하지 못했습니다.
