02 처리 건 열기 · 담당 고르기 — 문제를 기록으로 만들고 맞는 담당을 고른다

감시가 찾은 문제나 고객 문장을 처리 건 한 건으로 저장하고, 문제 종류에 맞는 담당 에이전트와 일감 종류를 고르는 기능입니다.
목차로 ← 01 일정 문제 감시 03 작업 지시서 (코어 → 에이전트) →
  • 결론: 문제 한 건을 처리 건(Case) 한 줄로 저장하고, 그 문제 종류를 받을 담당 한 곳을 고릅니다.
  • 입력: 감시 사건(항목 · 원인) 또는 고객 문장. 출력: 처리 건 한 줄(상태 「시작」) · 담당 이름 · 일감 종류.
  • 그래서 달라지는 것: 같은 문제는 한 건으로 모이고, 담당이 없는 문제는 대안을 찾지 않고 닫힙니다.
  • 정할 것 · 한계: 고객 문장을 5개 라벨로 나누는 방식(규칙이냐 모델이냐)은 이 세션에서 확인하지 못했습니다 [미확보]. 접수 창에는 글자 수 상한이 없습니다(03 참조).
  • 근거 범위: 2026-10-12 기준 코드 경로 확인 · 계획 v11 §5-A · §5-B · w5 v7 오버레이 [1]–[3].

1. 명세 머리 — 누가 무엇을 이루려고 하나

범위triPilot 시스템 안의 처리 건 접수 · 라우팅
수준사용자 목표(고객 문의 한 건을 처리 건으로 여는 것) + 시스템 하위 기능
주 액터접수기(코드) — 고객 접수 창 또는 감시 작업이 부른다
보조 액터담당 등록 목록(registry, 코드) · 고객(접수 문장 제공)
사전조건여행 대상이 정해져 있다(감시) 또는 고객이 문장을 보냈다(접수)
트리거감시 사건 발견 · 고객 접수 요청
최소 보장접수는 같은 요청 번호로 두 번 만들어지지 않는다. 실패하면 오류로 기록하고 고객에게 알리지 않는다
성공 보장처리 건 한 줄이 있고, 담당 한 곳과 일감 종류가 기록돼 있다(또는 닫힘 사유가 있다)

2. 주 성공 시나리오

  1. 접수기가 처리 건 한 줄을 만든다(대상 · 시작 주체 · 원문 · 상태 「시작」).
  2. 코어가 문제 종류 이름에서 사건 종류를 읽는다. 예: dining_* 는 식당(dining).
  3. 코어가 사건 종류와 의도(intent)를 받는 담당 등록을 찾는다.
  4. 담당이 정확히 하나면 담당 이름과 일감 종류를 처리 건에 기록한다.
  5. 처리 건을 실행 대기로 넘긴다(03 → 05).

3. 확장 · 예외 — 주 시나리오에서 갈라지는 길

  • 1a 같은 요청 번호의 처리 건이 이미 있음: 새로 만들지 않고 기존 건에 붙는다.
  • 2a 감시 사건: 문제 종류가 이미 붙어 있어 문장 분류를 건너뛴다.
  • 4a 담당이 0개 또는 2개 이상: 담당 배정 실패로 기록한다. 고객에게 알리지 않는다.
  • 4b 「그 밖(other)」 문제: 담당이 없어 바로 닫힌다.

7. 미확정 · 한계 · 정할 것

  • 고객 문장을 5개 라벨(일정 제출 · 사건 신고 · 확인 요청 · 조정 거부 · 그 밖)로 나누는 방식이 규칙인지 모델인지 확인하지 못했습니다 [미확보]. 정하실 것: 이 분류를 어느 방식으로 할지.

  • 접수 창에 글자 수 상한이 없습니다. 상한(12,000자)을 넘는 글은 작업 지시서를 만들다 실패합니다(03 참조).
