## 4. 그대로 교체할 문장

아래 교체는 기존 문서 형식을 바꾸지 않는다. 문구가 반복된 I/O 표·마지막 순환 설명에도 같은 수정 내용을 적용한다.

### ① 첫 요약 문단

> triPilot의 Multi-Agent 구조는 팀 결정상 요식·액티비티 두 에이전트와 공용 이동 판정 툴로 정리합니다. 현재 낮 감시는 문제 항목의 Case를 열고 오케스트레이터가 담당 Team 하나를 실행하며, Team은 허용된 읽기 툴과 계산 코드로 대안을 제안합니다. 고객 채팅은 TripDesk를, 새벽 영업 확인은 별도 점검·반영 경로를 사용하며 일정 계산 함수를 공유합니다. 결과는 필요한 검증·고객 선택·일정 버전 반영과 알림을 거치고, 별도 주기 작업이 다음 항목을 계속 점검합니다.

### ② 사용자 상자

> I: 여행 계획(글·사진·파일), 채팅 질문·신고, 다른 안 선택·새 대안 요청·되돌리기  
> O: 확인 범위가 표시된 일정, 변경 이유·다른 안, 웹 알림·Discord 알림

### ③ 계획 확인 제목과 읽기 설명

> 1. 계획 읽기·확인·등록 — 고객 수정과 확인 후 등록 시 재검사

> 규칙이 먼저 읽고, 남은 줄은 LLM이 원문 인용·줄 번호·역할을 찾는다. 사진·스캔은 비전 받아쓰기를 사용한다.

### ④ 검증 체크리스트 상자

> I: 일정 항목과 제출된 장소·경로·여행 제약  
> O: 확인 가능한 위반 항목·이유·완화 조건; 정보가 없는 항목은 미확인  
> 공통: 시각 순서·겹침·제출 경로의 이동 시간·결제·예산  
> 장소: 값이 있을 때 운영일·영업시간·브레이크·입장/주문 마감  
> 등록 단계에서는 외부 날씨 점검과 요식 원장 전체 재조회가 돌지 않는다  
> 부가 정보: 확인된 주차 등 장소 정보; 등록 검증과 구분

### ⑤ 실패 분기

> 실패·부족 항목: 이유와 완화 조건 표시 → 고객이 수정 → 다시 확인  
> 불가능하거나 필수값이 부족하면 등록 거절(구현)  
> 실패 항목의 자동 채팅 대안 추천은 현재 등록 경로에 없음

`전부 통과?`는 다음으로 바꾼다.

> 확인 가능한 검사에서 위반 없음?

### ⑥ 진행 SSE 상태

> 접수 읽기·일정 생성·채팅 진행 SSE는 서버에 구현되어 있다. 현재 웹 접수 화면은 주기 조회를 사용하므로 화면 연결은 진행 중으로 구분한다. 항목별 검증 체크리스트의 순차 SSE 출력은 별도 미구현이다.

### ⑦ 등록→감시 연결

> 등록된 여행을 별도 감시 작업이 조회한다 — 운영 작업 정의는 1분 주기

### ⑧ 트리거 설명

> 낮 감시: 최신 active 여행에서 앞으로 90분 안에 시작하는 항목  
> 새벽 확인: 03:00 이상~08:00 미만, 그날 남은 식사·활동의 Google 영업 정보  
> 고객 채팅·신고: 별도 TripDesk 처리 경로  
> 외부 성립 점검: 기상·특보·지진·재난문자·교통·대기질의 6범주; 실제 연결·샘플 여부 구분

### ⑨ Supervisor 라우팅

> 규칙 라우팅: 문제 코드 접두를 기본으로, 서버가 확인한 대상 힌트와 capability 선택 규칙을 적용해 담당 하나를 고른다.

> I: 접수·감시가 만든 Case와 문제 원인  
> O: 담당 Team 하나, 할 일·허용 툴·컨텍스트, Team timeout 설정 90초

### ⑩ Worker 공통 흐름

> 낮 감시 Case는 현재 항목을 같은 외부 점검으로 다시 확인한다. clear면 유지, fatal이면 변경하지 않고 실패를 기록한다.

> 후보는 영업·거리·조건과 해당 경로의 외부 재점검으로 거른다. 요식 낮 감시는 순위순 최대 3곳을 재점검하고, 활동 기본 경로는 후보 점검 후 순위를 정한다.

> 최종 반환: 최선 1곳과 다른 안 최대 2개. 읽기 툴은 실행당 최대 12회이며, 90초는 Team timeout 설정이다.

후보 상자의 `+ 이동 판정 툴(앞뒤 구간 제시간?)`은 삭제하고, 반영 상자에 다음을 넣는다.

> 장소가 바뀌면 바로 앞뒤의 이동 항목을 다시 계산한다. 계산기가 꺼졌거나 판정하지 못하면 추정·기존 경로 유지 여부를 표시한다.

### ⑪ 검증·반영

> 고객 소유·Case 버전·여행 기준 버전·항목과 장소 실재를 확인한다. 제시한 근거 ID의 유효성도 검사하지만, 모든 일정 제안에 비어 있지 않은 근거 목록을 강제하는 검사는 아니다.

### ⑫ 묻기 조건

> 보호 일정(고객 고정·잠김·계획의 예약번호)은 먼저 묻는다. 설문이 ‘먼저 물어봐’이면 묻거나 안전 알림을 보내며, 그 밖의 안전 사건은 자동 변경할 수 있다. 액티비티의 날씨 사건만 있는 경우에는 실내외를 모르거나 명시적 자동변경 동의가 없으면 ‘바꿀까요?’를 묻는다.

### ⑬ 알림 상자

> I: 등록·변경·보류 질문·하루 시작·다음 일정·출발 안내 문구  
> O: Discord 웹훅 알림과 최신 계획서 링크  
> 적재 중복은 dedupe key로 막는다. 일반 실패는 최초 발송 포함 최대 3회 시도하며, 타임아웃·연결 오류는 unknown으로 남기고 자동 재전송하지 않는다.

알림 상자 아래에 다음을 추가한다.

> 일정 변경 SSE는 별도 조회 스트림이다. DB 변화 신호를 받은 웹이 일정·알림·제안을 다시 읽으며 Discord 배달과 독립적으로 동작한다.

### ⑭ 툴 상자

> 주요 읽기 툴 예시: read.itinerary, read.disruptions, read.dining_state, read.dining_alternatives, read.place_catalog, read.policy  
> 전체 허용 목록은 Team manifest에 있으며, 이전 버전·고객 문장·예약 관련 툴도 포함한다.  
> 한 실행에서 허용 목록 밖 호출과 동일 툴·동일 인자의 재호출을 거부한다. 두 Worker의 읽기 툴 예산은 최대 12회다.  
> 조회 불능·NULL은 모름으로, 정상 조회의 빈 결과는 실제 없음으로 구분한다.

### ⑮ Data 상자

> PostgreSQL + pgvector: 여행·일정 버전·Case·실행 기록·장소·요식 원장·규정 조각  
> 임베딩 provider는 설정으로 선택하며, 로컬 경로의 기본 모델은 bge-m3:latest이다.

> 외부 데이터 6범주: 기상·특보·지진·재난문자·교통·대기질  
> 기상·대기질은 대체 소스 경로가 있고, ITS·UTIC 교통 자료는 합친다. 모든 범주에 대체 소스가 있는 것은 아니다.

> 이동 자료: 지하철 열차 시간표, 버스 노선·정류장·배차·구간 자료  
> 확인 파일 기준 시간표: 일반 파일 463,326행 / 우선 선택 압축 파일 444,915행  
> 판정 결과와 미확인·추정 상태를 함께 반환한다.

### ⑯ AI 사용 설명

> AI는 계획 원문의 인용·역할 찾기와 사진 받아쓰기, 고객 문장 해석·분류, 일정 후보의 순서 제안, 영업시간 원문 구조화, 문장·번역에 사용한다. 일정 성립·영업·시간 제약과 최종 반영 여부는 코드로 판정한다. 모델은 로컬·API 비교 시험 중이며 최종 선정은 미확정이다.

### ⑰ 마지막 순환 문장

> 시스템 구성도에서는 낮 감시의 대표 순환을 `트리거 → Case → 오케스트레이터 → Worker의 점검·대안 제안 → 검증·묻기·반영 → 알림 → 다음 점검 대기`로 표현합니다. 고객 채팅·새벽 영업 확인·일정 생성·정기 안내는 현재 별도 경로이며, 같은 일정 계산과 버전 저장을 공유합니다. 여행 종료 자동 전이의 구현 여부는 별도로 표시합니다.
