## 사실 (코드 · 팀 결정, 2026-10-02 확인)
- 에이전트는 요식 · 액티비티 둘. 이동은 에이전트가 아니라 공용 판정 툴(팀 결정). 코드에는 아직 이동이 팀으로 등록돼 있음.
- 오케스트레이터(코드 이름은 코어/컨트롤러)가 케이스를 열고 담당 하나를 고른다. 에이전트끼리 직접 부르지 않는다.
- 안쪽 루프: 에이전트가 대체 후보를 순위대로 하나씩 다시 점검(같은 외부 점검) → 통과한 것 모음 → 최대 3곳 · 툴 12회 · 90초. 다 떨어지면 「못 함」.
- 바깥 루프: 감시 1분마다(앞으로 90분 안 항목) · 새벽 03~08시 영업 확인 · 고객 신고 → 여행 끝까지.
- 판정은 코드. AI 모델은 계획서 줄 위치 · 분류 · 문장에만. AI 모델 자체는 시험 중(로컬 · API 비교, 미확정).
- 검증 · 반영: 근거 · 고객 소유 · 케이스 버전 확인 → 새 일정 버전(이전 보존). 설문 「먼저 물어봐」 · 고정 일정 · 안전 경보면 묻기만.
- 알림: 아웃박스 → 워커 → 디스코드. 개인 디스코드 등록 · 시험 발송은 됨, 실제 일정 알림은 팀 채널 하나.
- SSE: 「여행 바뀜 신호」만 구현. 계획 검증 진행 스트림은 미구현.
- 로그인 없음(브라우저 키). CI(GitHub Actions) 있음, AWS 자동 배포 없음.
- 고객 건을 사람에게 넘기지 않는다. 운영자는 오류 알림만.

## 사용자의 과거 지적 (지켜야 할 것)
- 에이전트 흐름은 **반복 루프가 눈에 보여야** 한다(안쪽 = 후보 재시도, 바깥 = 여행 끝까지 지속 관리). v6 는 「명확한 루프가 없다」로 다시 지적받았다.
- 「인풋 · 아웃풋」 낱말은 발표에 그대로 쓰지 않는다(받음 · 냄 등으로).
- 「모듈」 같은 개발 용어 남발 금지. 정하지 않은 것을 확정처럼 쓰지 않는다. 쓰지 않는 내용은 넣지 않는다.

## 해 줄 것
1. **멘토 지적 대조** — `mentor_2to4.txt` 에서 시스템 아키텍처 · 에이전트 플로우에 관한 지적을 빠짐없이 뽑고, 각 지적이 v6 그림에서 (a) 충분히 반영 (b) 부족 (c) 빠짐 중 무엇인지 판정. 근거로 그림의 어느 부분인지 적는다.
2. **루프** — v6_flow 와 v4_flow 를 비교해 루프가 어떻게 약해졌는지, 어떻게 그려야 「한눈에 보이는 루프」가 되는지 구체적으로(어느 상자에서 어느 상자로 되돌아가는 화살표).
3. **한 장으로 읽히는가** — 처음 보는 멘토가 30초 안에 흐름을 읽을 수 있는지. 글이 너무 많은 곳, 시선 흐름이 꼬이는 곳, 같은 말 반복.
4. **구성도(그림 2)** — 참고 구성도 형식과 대조해 빠진 칸 · 어색한 칸 · 화살표 방향 · 이름. 위 「사실」과 다른 표기.
5. **사실 오류** — 위 「사실」과 다르거나 확정처럼 쓴 것.
6. **최종 권고** — v7 에서 고칠 것 목록을 중요도 순으로(무엇을 · 어디서 · 어떻게). 서로 충돌하는 요구(예: 한 장 vs 인풋 · 아웃풋 상세)가 있으면 어떻게 풀지.

결과는 마크다운 하나로. 확인한 것과 추측을 구분해 적는다.
