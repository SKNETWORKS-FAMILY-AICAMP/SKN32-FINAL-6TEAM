# guguroute v6 플로우·시스템 구성도 독립 검토

**판정: v6는 설명 항목은 늘었지만, ‘한눈에 보이는 반복 흐름’은 미완성이다.** v7에서는 글을 더 넣기보다 **후보 재점검 루프, 모든 처리 결과의 감시 복귀, 에이전트와 공용 툴의 호출 관계**를 먼저 고쳐야 한다.

## 검토 범위와 근거 수준

- REVIEW.md 39줄과 mentor_2to4.txt 45줄을 처음부터 끝까지 직접 읽었다.
- v6_flow.png, v6_arch.png, v4_flow.png, ref_fastapi.png, ref_console.png의 파일 원본을 직접 확인했다.
- **[확인]**은 원문·이미지에서 직접 확인한 내용이다. **[제공 사실 대조]**는 REVIEW.md의 ‘코드·팀 결정, 2026-10-02 확인’을 기준으로 한 판정이다. 이 폴더에는 소스 코드가 없으므로 그 사실을 독립적으로 코드 검증한 것은 아니다.
- **[검토 판단]**은 가독성·구조에 대한 판단이다. **[제안]**은 v7 수정안이다. 그림의 수치·기술 이름만으로 실제 구현이나 성능을 확인했다고 보지 않는다.
- 아래 (a) 충분히 반영, (b) 부족, (c) 빠짐은 **그림에 반영된 정도**이다. 예정 기능을 적절하게 표시했더라도 구현 완료로 판정하지 않는다.
- 3회차의 외국인 타겟 유지보다 4회차의 외국인 타겟 제외 방향이 최신이다. 둘을 동시에 만족시키라고 요구하지 않는다. 원문의 과거 프로젝트 주제·팀 이름을 현재 시스템 이름으로 옮길 이유도 없다.

| 일정 실패 리스크의 실제 조사·케이스 포함 | **(c)** | 12:00 식당 예시는 있으나 실제 조사·사례·출처로 제시되지 않았다. 가상 예시와 실제 근거를 구분해야 한다. 이 근거는 별도 기획 장표에 두어도 된다. |
| 각 에이전트를 트리거→받는 것→내보내는 것으로 정의 | **(a)** | 플로우 요식·액티비티 카드에 ‘트리거 / 받음 / 냄’이 각각 있다. 입력의 종류와 결과 형태가 이전 지적보다 구체적이다. |
| 단순 LLM 호출과 에이전트 플로우 구분 | **(b)** | 플로우 우상단 설명과 구성도 모델 칸에 사용 범위를 구분했다. 그러나 재조회·판단·재시도가 도형으로 보이지 않아 설명문에 의존한다. 모델이 판정하지 않는다는 방향은 정확하다. |
| 전체 에이전트 플로우 아키텍처를 발표에 포함·설계 완성 | **(b)** | 두 그림이 전체 구성과 처리 단계를 다룬다. 안쪽 루프와 실패 복귀, 상단 계획 등록→하단 감시 연결이 빠져 전체 흐름을 완성했다고 보기 어렵다. |
| 정량 평가 데이터셋·사전 기준으로 개선 추적 | **(b)** | 요식 87→99/100, 이동 회귀 168건이 있다. 액티비티는 ‘기준 만드는 중’. 데이터셋 조건·판정 기준·평가일이 없어 사전 기준 및 에이전트 전체 성능 고도화까지 입증하지 못한다. |

### 1.2 3회차: 명확한 연결과 용어·평가

출처: ‘3회차 → 에이전트 플로우 / 결정 사항 / 액션 아이템’. 2회차와 반복된 요구도 회차별로 대조했다.

| 멘토 지적·요구 | 판정 | v6의 근거와 남은 문제 |
|---|---|---|
| 에이전트별 받음·냄을 명시 | **(a)** | 플로우 두 에이전트 카드에 식사·활동 항목, 원인·성향과 그대로/대체/못 함 결과가 적혀 있다. |
| ‘일정 사고 문의’처럼 광범위한 트리거를 구체화 | **(a)** | 감시 1분·90분 범위, 새벽 03~08시, 지진·날씨·휴무·늦음·품절 등의 조건을 적었다. 다만 90분은 점검 대상 범위인지 실행 시점인지 문구를 통일해야 한다. |

| 에이전트 평가 지표 정의 | **(b)** | 요식의 영업시간 일치와 이동 회귀 수치를 적었다. 영업시간 정확도가 대체 식당 적합도·복구 성공률을 대변하지는 않는다. 액티비티 지표는 미완성이라고 정직하게 표시했다. |
| 전체 유스케이스·모든 화면의 행위를 합의서로 정의 | **(b)** | 계획 업로드·채팅·신고·알림은 보인다. 사용자 확인 응답, 다른 안 선택, 되돌리기 등은 경로가 없고 기능 명세서도 자료에 없다. 두 그림만으로 명세서 작성 여부를 판정할 수 없다. |
| CI/CD, AWS 자동 배포로 동일 환경 협업 | **(b)** | 구성도 하단에 CI 완료 / CD ‘아직 안 됨’을 구분했다. 현황 표기는 맞지만 멘토의 배포 완료 요구는 충족되지 않았다. |

### 2.2 v7 안쪽 루프: 에이전트 영역 안에 실제 회로를 그릴 것

**[제안] 두 에이전트에 공통인 실행 흐름을 한 번만 그린다.** 요식·액티비티 카드는 그 흐름으로 들어가는 두 선택지이며 서로를 부르지 않는다.

| 출발 상자·분기 | 도착 상자·분기 | 선에 붙일 문구 |
|---|---|---|
| 담당 에이전트 | 현재 일정 재점검 | 일정·원인·허용 툴 |

복귀 선의 출발과 도착을 뚜렷하게 하고, 후보 선택·재점검 아래에 금색으로 짧은 U자 경로를 둔다. 색뿐 아니라 ‘다음 후보’라는 라벨도 쓴다.

‘더 점검할 수 있는가?’ 옆에 **최대 3곳·툴 12회·90초**를 붙인다. 한도에 걸려 확인하지 않은 후보는 통과 후보에 넣지 않는다. REVIEW.md는 최대 3곳이라는 한도를 제시하지만 상세 카운터 구현은 제공하지 않는다. ‘3곳 확인’인지 다른 집계 방식인지까지 코드 확인 없이 새로 확정하지 않는다.

루프의 주체는 **선택된 에이전트**이고, 그 케이스를 열고 담당을 선택하는 주체는 **오케스트레이터**이다. 실패할 때마다 다른 에이전트로 넘기거나 둘을 순차 호출하는 화살표를 추가해서는 안 된다.

### 2.3 v7 바깥 루프: 정상·실패 모두 실제 트리거로 복귀

**[제안] 마지막 처리가 끝나는 지점에 ‘여행이 끝났는가?’를 두고, 아니오일 때 ‘다음 트리거 대기’로 돌아간다.**

| 경로 | 반드시 이어야 할 화살표 |
|---|---|
| 계획 확인 완료 | 계획 등록·현재 일정 저장→감시 시작/다음 트리거 대기 |
| 정상 변경 | 검증 통과→반영(새 버전)→알림→여행 끝? |
| 현재 항목에 영향 없음 | 그대로→여행 끝? |
| 후보 없음·한도 내 해결 불가 | 못 함→일정 유지·사유 기록→여행 끝? |
| 검증에서 거부·실패 | 일정 유지·오류 기록→여행 끝? |
| 확인이 필요한 조건 | 사용자에게 묻기→응답 대기; 응답 시 현재 버전 등 재검증→반영 또는 유지 |
| 여행 끝? → 아니오 | **다음 트리거 대기→감시 1분 / 새벽 03~08시 / 고객 신고→점검·문제 발견→오케스트레이터** |
| 여행 끝? → 예 | 종료 |

검증 실패와 대안 없음은 서로 다른 원인이므로 각각 결과를 낸 뒤 ‘일정 유지’에 합류시킨다. 운영자 오류 알림은 실패 처리에서 갈라지는 보조 경로로 두며 고객 처리의 다음 담당자로 그리지 않는다.

사용자 응답을 기다리는 동안의 다른 항목 감시 정책은 자료에 없다. 그 정책을 새로 확정하지 말고 ‘응답 대기’와 응답 후 재검증 연결만 명시한다. 여행 전체가 사용자 한 명의 응답 때문에 멈춘다는 그림도 피한다.

**현재 v6의 바깥 복귀 선 끝을 ‘제보 공유’에서 ‘다음 트리거 대기’로 옮기는 것이 필수다.** 제보 공유는 검토 중인 추가 기능이고, 구현된 감시가 그 기능을 통과해야 다시 실행되는 구조가 아니다. ‘여행 끝까지’ 문구만으로 종료 판단을 대신할 수 없다.

요식 트리거의 ‘식사 90분 전’과 액티비티 ‘시작 90분 전’은, REVIEW.md의 ‘1분마다 앞으로 90분 안 항목 점검’과 혼동되기 쉽다. **[제안] ‘앞으로 90분 안의 식사/활동에 영향이 발견되면’으로 통일**한다. 정확히 90분 전에 한 번 실행한다는 뜻으로 읽히지 않게 한다.

### 3.2 같은 말이 반복되는 곳

- 플로우 제목 아래, LLM 차이 설명, 하단 두 카드 위, 맨 아래 주석이 모두 ‘AI는 판정하지 않는다 / 다음 트리거를 기다린다’를 반복한다.
- 요식·액티비티 트리거가 좌측 공통 트리거와 각 카드에 중복된다.
- ‘담당 하나 선택’이 플로우 오케스트레이터와 에이전트 영역 제목, 구성도 3·5번에 반복된다.
- 구성도 데이터 수가 툴 안과 하단 데이터 소스에 반복된다.
- 구성도 모델 ‘시험 중’이 4번 제목·설명·하단 인프라에 반복된다.

**[제안] 각 의미를 한 곳에만 적는다.** 공통 감시 조건은 트리거 칸, 실행 반복은 화살표, 유형별 차이는 두 카드, 평가 수치는 작은 하단 표, 모델 사용 범위는 구성도 모델 연결선에 둔다.

### 3.3 ‘한 장’과 화면 크기

원본 크기는 플로우 3600×3200, 구성도 3000×2320이다. 둘 다 일반적인 가로 발표 화면보다 세로 비중이 크다. **[가정에 따른 판단] 1920×1080 화면에 전체를 맞추면** 플로우는 약 1215×1080, 구성도는 약 1397×1080으로 표시되어 양옆 여백이 생기고 작은 주석은 더 읽기 어렵다. 고해상도 파일이라는 사실이 발표 가독성을 보장하지 않는다.

‘한 장’에 모든 체크리스트·평가 방법·기술 세부를 넣는 대신, **한 장의 주 흐름만으로 서비스가 무엇을 하는지 설명하고 상세 정의는 보조 자료로 제공**해야 한다. 그림을 파일 두 개로 나누는 것보다 각 그림의 역할을 분명히 하는 것이 우선이다.

## 4. 구성도: 참고 형식, 상자, 화살표, 이름

### 4.1 참고 구성도에서 가져올 원칙과 가져오지 않을 내용

**[확인]** 두 참고 그림은 사용자→진입 앱→중앙 처리→모델의 상단 구조, 중앙 처리↔툴, 별도 저장소, 검색용 파이프라인, 결과→사용자의 하단 구조를 사용한다. ref_fastapi에는 데이터 소스·인프라·특징·범례가 있고 ref_console에는 하단 특징 띠가 있다. v6_arch는 이 형식의 큰 틀을 따랐다.

차이는 **참고 그림의 중앙 상자가 실행 메커니즘을 설명하는 반면, v6의 중앙 네 칸은 계획 읽기·검증·채팅·담당 선택이라는 업무 기능을 나열한다는 점**이다. 참고의 Agent Loop 아이콘을 그대로 붙이는 대신 guguroute의 실제 후보 재점검을 보여줘야 한다.

System Prompt, LangChain/LangGraph, InMemorySaver, FAISS, OpenAI/Gemini, 예제 API 경로는 참고 시스템의 내용이다. 제공 사실에서 사용을 확인하지 못했으므로 누락이라고 단정하거나 v7에 복사해서는 안 된다. PostgreSQL의 일정·케이스 상태를 참고의 대화 메모리와 동일한 것으로 설명해서도 안 된다. 별도의 ‘Context 통합’ 상자도 그 기능이 실제로 있을 때만 필요하다.

### 4.3 화살표를 고칠 위치

1. **FastAPI↔처리부:** 방향 자체는 요청 오른쪽·결과 왼쪽으로 맞다. 같은 서버 내부 경계에서 함수 호출로 표현한다.
2. **처리부↔모델:** 요청 오른쪽·응답 왼쪽도 맞다. 다만 현재 큰 3번 상자 전체와 연결되어 오케스트레이터 판정도 모델을 경유하는 것처럼 보인다. 실제 모델 사용 지점에 연결하거나 ‘줄 위치·분류·문장에만’이라는 범위 라벨을 붙인다.
3. **처리부→5번:** 네 하향 화살표를 두 에이전트 중 하나를 고르는 분기로 바꾼다. 이동·규정 툴은 에이전트/코어가 부르는 보조 호출로 연결한다.
4. **5번→3번 결과 / 5번→하단 검증:** 동일 결과가 서로 다른 두 수신처로 가는 듯 보인다. 하단 검증을 같은 오케스트레이터의 내부 기능으로 묶고 결과 경로를 하나로 만든다. 업무 결과가 두 번 전달된다는 근거는 없다.
5. **감시→오케스트레이터:** 방향은 감시에서 서버로 맞다. 선의 도착점이 넓은 처리 서버 테두리인 점을 바꾸어 오케스트레이터 ‘케이스 열기’에 직접 꽂는다. ‘깨진 항목→케이스’ 대신 ‘문제 항목·원인’을 전달한다.
6. **고객 신고→오케스트레이터:** 현재 사용자→FastAPI 신고는 있지만 중앙 처리에서 신고가 감시와 같은 문제 접수에 합류하는 선이 없다. 내부 분기 한 줄로 연결한다.
7. **저장소↔감시·반영·알림:** 실행에 필요한 상태의 핵심 읽기·쓰기 관계를 추가한다. 모든 내부 함수에 선을 그릴 필요는 없다.
8. **검증 결과→사용자 확인:** ‘묻기만’ 텍스트에서 실제 사용자로 가는 선이 없다. 확인 요청→웹앱/알림과 사용자 응답→검증·반영을 연결한다.
9. **현재 일정 변경→웹앱:** 구현된 SSE 바뀜 신호가 어디서 발생하는지 표시한다. 검증 진행 스트림과 선·라벨을 분리한다.
10. **오류→운영자:** 고객 건을 운영자에게 인계하는 선으로 보이지 않도록 ‘오류 알림’이라고 명시한다. 현재 방향 자체는 맞다.

### 4.4 권장 이름과 범례

- ‘3. guguroute 처리 서버’ → **‘일정 처리·오케스트레이터(같은 FastAPI 안)’**
- ‘5. 에이전트·툴—담당 하나 선택’ → **‘담당 에이전트 1개 선택’**과 별도의 **‘공용 툴’**
- ‘공유 State’ → **‘공유 저장소’**; 필요하면 아래에 케이스·일정 버전·알림 대기열을 적는다.
- ‘깨진 일정=케이스’ → **‘문제 항목·원인→케이스 열기’**. 일정 항목과 그것을 처리하는 건은 동일한 개념이 아니다.
- ‘태스크+컨텍스트’ → **‘할 일·허용 툴 / 현재 일정·원인’**
- ‘에이전트+이동 판정 툴’ → **‘유형별 검사+이동 가능 여부 검사’**. 계획 검증에서 에이전트 래퍼를 실제로 호출하는지는 자료가 충분하지 않다.

v6_flow의 파란 점선 에이전트 영역은 실제 실행 영역인데, v6_arch의 설명은 ‘점선 회색 상자=예정·검토 중’이다. 두 그림을 함께 보여줄 때 점선의 뜻을 하나로 오해하지 않게 한다. **테두리 색은 역할, 상태는 ‘구현/진행 중/예정/검토 중’ 배지, 선은 흐름 종류**로 분리하면 된다. 두 그림의 금색·주황색 선도 반복/감시라는 다른 의미를 가지므로 각각 명시한다.

### 5.3 사실과 맞으므로 유지할 표기

- 요식·액티비티 두 에이전트, 이동은 공용 툴이라는 팀 결정.
- 오케스트레이터가 담당 하나를 고르며 에이전트끼리 부르지 않는다는 방향.
- 후보 재점검 한도 최대 3곳·툴 12회·90초. 숫자를 루프 종료 조건 옆으로 옮긴다.
- 1분 감시·앞으로 90분 범위, 새벽 03~08시, 고객 신고, 여행 끝까지 관리.
- 판정은 코드, 모델은 줄 위치·분류·문장에만 사용; 로컬·API 비교 중.
- 근거·고객 소유·버전 검증과 새 일정 버전·이전 보존. 플로우에도 검증 기준을 짧게 옮겨 두 그림을 맞춘다.
- 개인 디스코드 등록·시험과 실제 팀 채널 일정 알림을 구분한 주석. ‘알림 구현’만 크게 쓰지 말고 제한을 같은 칸에서 읽히게 한다.
- SSE 변경 신호 구현 / 검증 진행 스트림 예정, CI 있음 / AWS 자동 배포 없음.
- 운영자는 오류 알림만, 고객 건을 사람에게 넘기지 않음.

**코드와 팀 결정의 차이:** REVIEW.md는 ‘코드에는 이동이 아직 팀으로 등록되어 있음’도 명시한다. v6가 이동을 툴로 그린 것은 최신 팀 설계와 맞다. 이를 그림의 오류라고 되돌릴 필요는 없다. 다만 전체가 현행 코드 그대로라는 인상을 주지 않도록 **‘이동: 공용 툴 설계 확정, 코드 팀 등록 정리 필요’**라는 짧은 현황 표시가 필요하다. 이 검토가 코드 등록을 확인하거나 수정한 것은 아니다.

플로우 맨 아래에는 새벽·채팅이 에이전트 래퍼 대신 같은 판단 코드를 직접 부른다는 설명도 있다. **[확인] 그림 제작 쪽의 주석**이며 소스 검증 자료는 아니다. 주 흐름을 팀의 공통 설계로 그릴 때는 ‘직접 호출하는 현재 경로 있음’이라는 작은 현황 메모로 구분하고, 구현이 모두 동일하다고 확대하지 않는다.

### 6.2 서로 충돌하는 요구를 푸는 배치

**한 장 vs 상세 받음·냄:** 주 그림에서 받음·냄을 없애면 멘토 요구를 놓친다. 두 에이전트의 짧은 카드에 **트리거 1줄·받음 1줄·냄 1줄**은 유지한다. 세부 체크리스트·식이 조건·평가 방법은 보조 표로 이동한다. 두 카드에 같은 실행 순서를 중복해서 넣지 않는다.

**전체 흐름 vs LLM 차이 설명:** 플로우는 후보 재시도와 지속 관리의 동작을 보여준다. 구성도는 코드 판정과 제한된 모델 사용 지점을 보여준다. 플로우 상단의 긴 LLM 비교문은 ‘판정은 코드’ 한 줄로 줄이고 공간을 루프에 쓴다.

**참고 구성도 형식 vs 실제 시스템:** 사용자·진입 서버·중앙 처리·모델·툴·저장소·결과라는 배치 원칙을 따른다. guguroute에는 참고의 RAG 파이프라인보다 상시 감시·버전 검증·알림 대기열이 더 중요한 실행 구성요소이므로 그 관계를 크게 둔다. 실제 사용 여부가 불명확한 칸은 참고와 똑같이 채우지 않는다.

**현재 구현 vs 목표 설계:** 메인 경로는 최신 팀 설계를 그리되, 구현 상태 배지와 짧은 차이 메모를 붙인다. 이동의 코드 팀 등록, 검증 스트림 미구현, 로그인 예정, 팀 채널 알림 제한은 이 방식으로 설명한다. 검토 중 제보 공유가 현재 루프의 일부가 되지 않게 별도 영역에 둔다.

**계획 확인 vs 여행 중 지속 관리:** 플로우 상단은 ‘계획→유형별 검사→결과→등록’만 짧게 보여준다. 아래 넓은 영역은 지속 관리에 사용하고, 내부에 작은 후보 재점검 루프를 넣는다. 두 영역 사이에 등록→감시 시작 선을 그리면 서비스의 두 단계가 연결된다.

### 6.3 v7을 다시 검토할 때의 완료 기준

처음 보는 사람이 그림만 보고 다음을 가리킬 수 있어야 한다.

1. 요식·액티비티 **중 하나**를 누가 고르는가.
2. 현재 항목과 대체 후보를 무엇으로 점검하며, 실패한 후보 다음에는 **어느 상자로 돌아가는가**.
3. 통과 후보를 어디에 모으고, 최대 3곳·툴 12회·90초 뒤에 어떤 결과를 내는가.
4. 근거·소유·버전이 맞지 않거나 대안이 없을 때 일정이 유지되고, **어디서 감시가 다시 이어지는가**.
5. 묻기 조건일 때 누가 질문을 받고, 응답이 어느 단계로 들어가는가.
6. 새 일정 저장과 디스코드 알림이 어떻게 나뉘며, 현재 팀 채널 제한은 무엇인가.
7. 여행 종료 분기는 어디에 있는가.
8. 모델 사용 지점과 검증 스트림·로그인의 구현 상태는 무엇인가.

실제 30초 독자 시험은 v7을 만든 뒤 별도로 해야 한다. 루프를 설명문으로 찾아 읽어야 답할 수 있다면 ‘한눈에 보이는 플로우’ 수정은 아직 끝나지 않은 것이다.
