# guguroute 에이전트 흐름 — 계획을 확인받고, 여행 중 문제가 생긴 일정을 고쳐 받기

- guguroute 은 고객의 여행 계획을 검사해 등록하고, 여행 중 식당 · 활동에 문제가 생기면 대안을 찾아 일정을 고칩니다.
- 다음에 무엇을 할지는 언제나 프로그램이 정한 규칙이 정합니다. 언어 모델(LLM)은 계획을 읽을 때와 알림을 번역할 때만 돕습니다.
- 대안을 찾는 일은 요식업 · 액티비티 에이전트 둘이 나눠 맡고, 한 번에 하나만 일합니다.
- 바꾸기 전에 고객에게 물어야 하면 답을 기다리고, 그렇지 않으면 바로 바꾸고 알립니다.
- 아래 두 그림에서 자동으로 되는 일과 고객이 고르는 자리(⏸)를 보시면 됩니다.

## 1. 여행 계획을 확인받는다

고객이 글 · 사진 · 파일로 계획을 올리면 프로그램이 날짜 · 시각 · 장소를 읽습니다. 규칙으로 못 읽은 줄과 사진 글자만 언어 모델이 돕습니다.
고객은 확인 화면에서 읽힌 일정을 고치거나 등록을 요청합니다. 고치면 다시 검사해 확인 화면으로 돌아옵니다.
등록을 요청하면 프로그램이 시간이 겹치는지 · 이동이 가능한지 · 필요한 정보가 다 있는지 검사하고, 통과하면 저장한 뒤 계획서 링크를 알립니다.

**예: 「14:00 경복궁, 14:30 남산타워」처럼 이동이 30분 안에 안 되면 등록되지 않고, 확인 화면에 이유와 고칠 방법이 나옵니다.**

![여행 계획을 확인받는다 — 에이전트 흐름](그림1_계획확인_v20.png)

**끝나는 길 · 예외**

- 읽지 못하면 이유를 보여 주고 다시 올리게 합니다.
- 고객이 연결한 개인 AI 가 일정을 내면 읽기 · 확인 화면 없이 바로 검사하고, 실패하면 문제 목록을 그 AI 에게 돌려줍니다.
- 고친 횟수에 상한이 있는지는 확인되지 않았습니다. 다시 올리기 · 등록 요청은 하루 한도를 둘 수 있게 돼 있지만 지금은 꺼져 있습니다.

## 2. 여행 중 문제가 생긴 일정을 고쳐 받는다

프로그램이 자동으로 곧 시작할 일정을 점검합니다. 날씨 · 특보 · 재난문자 · 교통 · 대기질 · 지진 6종을 동시에 조회해 한 판단으로 합칩니다.
문제가 처음 발견되면 프로그램이 문제 종류에 따라 담당 에이전트 하나를 고릅니다. 같은 점검에서 한 여행에 문제가 둘 이상이면 하나로 묶어 액티비티 에이전트에게 맡기고, 액티비티 에이전트이 조정자가 되어 활동 → 식당 → 이동 순으로 한 초안 위에서 고칩니다(이때 요식업 에이전트는 따로 부르지 않고 식당 계산만 빌려 씁니다).
프로그램이 대안을 확인한 뒤, 고객 허락이 필요하거나 고객이 「먼저 물어봐」를 골랐으면 답을 기다리고, 아니면 일정을 바로 바꿔 알립니다.

**예: 저녁 식당 근처에 재난문자가 오면 요식업 에이전트이 그 시각에 여는 근처 식당을 최대 3곳 다시 확인해 대안을 냅니다. 고객이 「먼저 물어봐」를 골랐다면 대안을 보여 주고 고르기를 기다리고, 아니면 바로 바꾸고 되돌리기 버튼과 함께 알립니다.**

![여행 중 문제가 생긴 일정을 고쳐 받는다 — 에이전트 흐름](그림2_일정고치기_v20.png)

**끝나는 길 · 예외**

- 외부 정보가 대체 소스까지 조회에 실패하면(확인 불가) 그 일정은 이번 점검에서 고치지 못합니다. 점검 작업을 「실패」로 기록하고 3분 뒤 점검에서 다시 확인합니다. 고객과 운영자에게 따로 알리지는 않습니다(현재 한계 — 아래 4절). 같은 문제를 이미 찾았으면 다시 처리하지 않습니다.
- 잠긴 예약 · 예약번호가 있는 일정(보호 일정)은 바꾸기 전에 먼저 묻습니다. 고객이 「바꾸지 말 것」으로 고정한 일정도 점검합니다 — 일정은 바꾸지 않고, 대안이 있으면 보여 주며 위험을 알립니다.
- 자동으로 바꾸기 전에 등록 때와 같은 검사로 일정 전체를 다시 봅니다. 1순위 안이 걸리면(시간 겹침 · 이동 불가 · 영업시간 밖 등) 담당이 뽑아 둔 2 · 3순위 안을 차례로 시험해 되는 첫 안을 적용하고, 알림에 몇 순위 안인지 적습니다. 다 안 맞을 때만 그대로 두고 알립니다.
- 하루 밀도(얼마나 빽빽한지)도 봅니다. 바꾼 탓에 그날이 목표보다 빽빽해지면 그 안은 뒤로 밀리고, 더 나은 안이 없을 때만 그 안을 쓰고 알림에 적습니다.
- 묶음일 때 일정마다 결과가 갈립니다 — 고친 것은 새 일정 하나와 알림 하나로 내고, 못 고친 일정은 같은 알림에 한 줄로 적고, 물어야 하는 일정(보호 · 고정 · 「먼저 물어봐」)은 따로 묻습니다. 하나를 못 풀어도 나머지는 진행합니다.
- 대안을 못 찾으면 일정을 그대로 두고, 그대로 둔 이유를 고객에게 알립니다. 조건을 풀어 비슷한 안(시각 늦추기 · 다음 일정 근처 · 반경 넓히기)을 찾아 보여 주는 기능은 고객이 「다른 곳으로」를 요청할 때만 쓰이고 자동 점검에는 아직 없습니다 — 붙이는 중입니다(2026-10-03). 변경안 확인에서 떨어진 경우는 아직 알리지 않습니다(현재 한계).
- 요식업 · 액티비티 어느 에이전트든 오류로 멈추면 그 일정의 이번 처리만 멈추고 다른 일정은 계속 점검합니다. 외부 조회 실패나 오류로 멈춘 처리는 5분이 지난 뒤 같은 문제가 다시 보이면 최대 3번 다시 시도합니다(고객에게는 알리지 않음).
- 고객이 답하지 않으면 그 일정이 끝날 때 요청을 닫고 일정은 바꾸지 않습니다.

## 3. 역할 요약 — 누가 무엇을 맡나

| 역할 | 맡은 일 | 언제 일하나 | 받는 것 → 내는 것 | 하지 않는 일 |
|---|---|---|---|---|
| 요식업 에이전트 | 문제가 생긴 식사 일정 하나의 대체 식당을 찾는다 | 자동 점검이 식사 문제 하나만 찾았을 때 프로그램이 부른다(같은 여행 문제가 여럿이면 액티비티 에이전트이 식당 계산을 빌려 쓴다) | 할 일 · 일정 · 문제 정보 → 대체 식당 1곳 + 다른 안 최대 2곳, 또는 「바꿀 것 없음」 · 「대안 없음」 | 일정을 직접 바꾸지 않는다 · 고객에게 직접 알리지 않는다 · 언어 모델을 쓰지 않는다 |
| 액티비티 에이전트 | 문제가 생긴 활동 일정 하나의 대체 활동을 찾거나, 먼저 고객에게 물을지 정한다 | 자동 점검이 활동 문제를 찾았을 때, 또는 같은 여행에 문제가 여럿일 때 조정자로 프로그램이 부른다 | 할 일 · 일정 · 문제 정보 · 고객 설문 → 대체 활동 제안(후보 최대 6곳 확인), 또는 「바꿔도 될까요?」 질문, 또는 「바꿀 것 없음」 · 「대안 없음」 중 하나 | 일정을 직접 바꾸지 않는다 · 고객에게 직접 알리지 않는다 · 언어 모델을 쓰지 않는다 |
| 이동 판정기 (공용 도구 · 에이전트 아님) | 바뀐 장소의 바로 앞뒤 이동을 지하철 · 버스 시간표로 다시 판정하고, 이동 일정에 사고가 나면 피하는 새 경로를 찾는다 | 에이전트가 장소를 바꿀 때 · 저장 직전 전체 검사 때 · 이동 일정에 사고가 났을 때 불린다 | 앞뒤 장소 · 시각 → 출발 시각 · 경로 · 소요(시간표로 못 하면 어림값과 그 표시) | 스스로 깨어나지 않는다 · 대안 장소를 고르지 않는다 · 언어 모델을 쓰지 않는다 |
| 계획 읽기 도우미 (언어 모델) | 규칙으로 못 읽은 계획 줄을 짚고, 사진 · 스캔의 글자를 옮겨 적는다 | 고객이 올린 계획에 규칙이 못 읽은 부분이 있을 때 | 원문 줄 · 이미지 → 원문에 실제로 있는 조각 · 옮겨 적은 글 | 원문에 없는 값을 만들지 않는다 · 등록 여부를 정하지 않는다 |
| 알림 번역 도우미 (언어 모델) | 한국어 알림을 고객 언어로 옮긴다 | 외국어 고객에게 알림을 보낼 때 | 한국어 문구 → 번역 문구(실패하면 한국어 원문 그대로) | 시각 · 금액 · 장소 이름 · 예약번호를 바꾸지 않는다 · 보낼지 말지 정하지 않는다 |

## 4. 고객에게 미치는 현재 한계

- 문제 종류에 맞는 담당을 못 정하면 대안을 찾지 않고 일정을 그대로 두며 고객에게 알리지 않습니다. 감시는 요식업 · 액티비티 · 이동 문제로만 처리를 열어 이런 일은 거의 없지만, 숙박 · 항공 같은 다른 종류의 일정은 아예 점검 대상에서 빠집니다.
- 외부 정보가 대체 소스까지 실패해 확인할 수 없는 일정은 고치지 못하고, 고객 · 운영자 누구에게도 바로 알리지 않습니다. 점검 작업이 「실패」로 기록되고 3분마다 다시 확인할 뿐입니다 — 그 사이 일정이 시작되면 고객은 모른 채 나섭니다.
- 변경안 확인에서 떨어지면 일정은 그대로인데, 고객은 그 사실을 알림으로 받지 못합니다.
- 일정을 바꾸면 그 옆 이동이 새로 만들어지는데, 새 이동은 그 구간의 사건(시위 · 통제)을 모른 채 경로를 고릅니다. 다음 점검에서 다시 봅니다.
- 물어야 하는 일정이 둘 이상일 때 하나를 고르면 일정이 바뀌어 나머지 요청은 닫히고, 다시 묻지 않습니다.
- 고객이 일정별 · 여행 전체 알림을 끄는 기능은 없습니다 — 나중에 볼 할 일로 남겼습니다.

고친 것: 대안을 못 찾았을 때 고객에게 원인 알림 · 답 없는 요청을 일정이 끝나면 닫음 · 도구 사용 한도 때문에 점검 전체가 멈추던 문제(2026-10-03, 제품 담당 세션이 이 컴퓨터에서 고쳤고 공유 저장소에는 아직 안 올림). 위 여섯 줄은 아직 남은 한계입니다. 점검 주기 3분 · 고정 일정 점검 · 전체 다시 검사 · 다음 순위 안 · 밀도 판단 · 같은 여행 묶음도 같은 날 만들었습니다. 상세는 부록 C.

## 부록 A. 상세 명세 카드

### 요식업 에이전트 (AG-DINING)

| 항목 | 내용 |
|---|---|
| 책임 (한 문장) | 깨진 식사 항목 하나를 다시 점검하고, 그 시각에 여는 근처 대체 식당을 골라 변경안을 낸다 |
| 하지 않는 일 | 일정에 직접 쓰기 · 고객에게 직접 알리기 · 다른 워커 부르기 · LLM 호출 · 업체 예약 변경 |
| 호출 주체 / 트리거 | 처리 총괄(코드) — 감시가 새로 연 식사 문제 건(문제코드 dining_*) · ⑥-a 단계 |
| 입력 | TeamTask — 처리 건 · 실행 식별자 · 할 일 종류(dining.itinerary) · 처리 건 버전 · 입력 문장 · 근거 묶음(현재 상태 · 트리거: 항목 · 시각 · 원인 범주) · 허용 도구 · 마감 시각 |
| 출력 (스키마) | TeamResult · ActionProposal(Pydantic 계약) — 다음 행동(답 / 중단) · 답 문장 · 결정 · 근거 · 변경 제안 itinerary.apply {trip_id, base_version, reason, causes, notice, summary, replacements[{item_id, item}]} (승인 불요 · 위험 낮음) |
| 모델 / 설정 | 없음 — 규칙 코드(LLM 안 씀) |
| 도구 / 권한 | 읽기만 11개: read.itinerary · read.disruptions · read.place_catalog · read.dining_alternatives · read.dining_state · read.place · read.policy · read.booking · read.booking_terms · read.itinerary_version · read.customer_report |
| 보는 컨텍스트 | 할 일 묶음 + 도구 결과. 다른 워커의 출력은 보지 않는다 |
