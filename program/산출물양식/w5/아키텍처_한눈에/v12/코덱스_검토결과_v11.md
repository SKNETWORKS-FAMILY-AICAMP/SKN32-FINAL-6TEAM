**판정: 고쳐야 함.**

그림은 **낮 감시가 연 식사·활동 Case 한 건의 처리 경로**를 상당 부분 정확하게 그렸다. 그러나 **프로젝트 전체의 실제 멀티에이전트 구조**라고 제시하기에는 범위가 좁고, 일부 문장이 실제 구현보다 강하다.

핵심 문제는 다음과 같다.

- **「날씨만·실내 모름?」은 실제 묻기 조건보다 좁다.**
- **오케스트레이터가 일정 제안의 모든 사실을 검증한다는 인상을 주면 과장이다.**
- 현재 코드는 **항목별 Case**, 기준 계획서와 D-017은 **여행별 묶음 Case**다.
- 외부 계획 작성자, 개인 AI의 MCP 입구, 결정 단위, Booking Handoff, 위임이 빠져 있다.

### 실제 외부 호출 간격

**필요한 항목이 계속 있으면, 기본 감시는 같은 외부 요청을 약 1분마다 다시 내보낼 수 있다.**

이유는 다음과 같다.

1. 매분 새 프로세스를 실행한다.
2. 그 안에서 감시용 소스·캐시·제한기를 새로 만든다.
3. 프로세스가 끝나면 캐시와 호출 이력이 사라진다.
4. 다음 실행은 빈 캐시와 초기 토큰으로 시작한다.

따라서 일반 캐시 5분과 재난문자 캐시 20분은 **다음 감시 회차를 건너뛰게 하지 않는다.** 주로 **동일 소스 객체를 사용하는 한 회차 안의 중복 요청**을 줄인다. 캐시 키는 소스명·URL·요청 인자다. `I/base.py:163–184`

또한 감시와 워커는 소스 객체가 다르므로, 감시가 받은 응답을 워커의 재점검이 그대로 재사용하지 않는다. **문제가 발견된 회차에는 같은 소스를 감시와 워커가 각각 호출할 수 있다.** `R/scripts/run_sweepers.py:237–245`; `A/composition.py:183–185`

**`--interval`로 상주 프로세스만 만들면 해결된다고도 할 수 없다.** 반복문이 매번 `_run_once()`를 호출하고, 그 아래에서 소스 객체를 다시 생성한다. 소스 객체의 수명을 함께 바꾸어야 한다. `R/scripts/run_sweepers.py:325–331`

다만 아래 조건 때문에 **모든 소스를 무조건 매분 호출한다는 뜻은 아니다.**

- 앞으로 90분 안에 시작하는 항목이 없으면 점검하지 않는다.
- 실내 장소에는 일부 기상·대기질 점검을 적용하지 않는다.
- 키가 없는 소스는 연결되지 않는다.
- 같은 소스 객체·같은 요청의 성공 응답은 회차 안에서 재사용한다.
- 외부 제공자가 거절하거나 대체 소스로 넘어갈 수 있다.

근거: `T/itinerary.py:312–324`; `I/disruptions.py:95–134,258–282`; `I/base.py:368–372`

## 2. 실제로 어떤 멀티에이전트 구조인가

### 요식·액티비티가 LLM 에이전트인가

**그림에 나온 감시 Case 경로는 규칙 코드와 허용 툴로 동작한다.**

- `DiningTeam.handle_trigger()`는 재점검하고 `plan_dining_disrupted()`를 호출한다.
- `ActivityTeam.handle_trigger()`는 묻기 조건을 검사하고 `plan_activity_adjustment()`를 호출한다.
- 후보 탈락·순위·최선 선택은 Python 계산이다.
- 기반 클래스가 `self.llm`을 보관하지만, 이 두 워커의 해당 실행 경로에서는 사용하지 않는다.

근거: `T/dining/team.py:99–131`; `T/activity/team.py:94–150`; `T/itinerary_changes.py:379–424,731–781`; `T/replan.py:383–409`; `T/_base.py:43–46`

`activity/team.py` 독스트링의 **「대안 생성만 LLM」**이라는 설명도 현재 실행 코드와 일치하지 않는다. `activity.propose_change`의 `_propose_change()`는 예약 변경 제안을 코드로 만든다. LLM 호출이 없다. `T/activity/team.py:7–9,409–431`

다만 **여행 신고를 처리하는 다른 워커 경로**에서는 `read.customer_report`가 신고 해석 모델을 간접 호출할 수 있다. 그러므로 「두 Team은 어떤 상황에서도 AI를 전혀 쓰지 않는다」도 과도한 표현이다. `T/itinerary_team.py:108–127`; `A/tools/read_tools.py:444–456`; `A/composition.py:152–168`

### AI 모델이 실제 호출되는 자리

| 자리 | 모델이 하는 일 | 모델이 하지 않는 일 | 근거 |
|---|---|---|---|
| 일반 고객 Case 분류 | intent·issue_code·sentiment 등 라벨 추출 | 라우팅·반영 직접 실행 | `T/feedback.py:109–149`; `A/application/classification.py:65–92` |
| 신고 해석 | 자유 문장에서 지연·휴무·변경 등의 구조 추출 | 변경안의 사실·실행 권한 확정 | `T/trip_intake.py:107–108` |
| 채팅 결정 단위 | 일정·변경 이력·대화·화면 선택을 보고 **할 일과 대상 선택** | 새 장소·시각·가격을 만들어 실행 | `T/decision_unit.py:9–12,215–254` |

| 영업시간 읽기 | 자연어 운영시간을 구조화 | 최종 영업·일정 판정 | `T/place_hours.py:200–210,288` |

| 알림 번역 | 한국어 문구틀을 고객 언어로 번역 | 일정 변경 여부 판정 | `A/infrastructure/notify/translate.py:37–45`; `A/infrastructure/notify/discord.py:145–160` |

**한국어 답변·변경 알림 문구가 전부 LLM 생성인 것도 아니다.** 후보 선택과 변경 안내는 코드가 문구를 만들고, 결정 단위의 되묻는 문장도 서버가 만든다. 응답 리뷰 Team은 현재 꺼져 있다. `T/replan.py:412–425`; `T/decision_unit.py:211`; `R/config/project.yaml:43–53`

### 멘토에게 정직하게 설명할 표현

> **triPilot은 중앙 Controller가 역할별 워커를 호출하는 구조입니다. 현재 요식·액티비티의 감시 판정과 대체안 계산은 규칙 코드와 허용 툴로 수행합니다. LLM은 별도의 분류·요청 해석·계획 읽기·후보 순서 제안·번역에 사용합니다. 여러 LLM 에이전트가 자율적으로 협의하는 구조로 구현된 것은 아닙니다.**

에이전트를 **독립된 역할·계약·툴 권한을 가진 작업 단위**로 정의하면 “멀티에이전트 구조”라는 표현을 사용할 여지는 있다. 그러나 **현재의 LLM 기반 다중 에이전트 협업 구현**이라고 설명하면 부정확하다.

그림의 추천 제목은 다음이다.

> **triPilot 역할별 워커 처리 흐름 — 감시 Case 한 건**

“멀티에이전트”를 유지하려면 다음처럼 범위와 구현 방식을 함께 써야 한다.

> **triPilot 멀티에이전트 설계의 감시 Case 처리 경로 — 현재 워커는 규칙 기반**

### 오케스트레이터는 Supervisor인가

**중앙 감독·조정 역할이라는 의미에서는 맞다. LLM Supervisor라는 의미에서는 아니다.**

Controller는 다음 일을 한다.

- Registry로 담당과 capability를 선택한다.
- ContextPack·허용 툴·기준 Case 버전·마감이 담긴 TeamTask를 만든다.
- 워커를 실행한다.
- 결과를 검사하고 제안을 적용기로 보낸다.
- 상태 전이와 실행 기록을 남긴다.

근거: `A/application/controller.py:117–163,235–257,292–318,435–507`

현재 실행기는 **로컬**이고 A2A 실행기는 꺼져 있다. `R/config/project.yaml:6–7,14–17`; `A/core/remote_team/executor.py:22–31`

또한 현재 Controller는 **여러 워커의 초안을 순차 조합하는 Supervisor**가 아니다. 한 Case에 담당 하나를 골라 실행한다. D-017의 Activity→Dining→Mobility 순차 조정과 기준 계획서의 여행별 묶음 조정은 이 경로에서 확인되지 않는다.

### 직접 호출과 HANDOFF

**요식·액티비티가 서로 직접 호출하지 않는다는 설명은 맞다.** 이 경로에서 호출하는 대상은 읽기 툴과 공통 계산 함수다.

그러나 **HANDOFF 자체가 없다고 설명하면 틀린다.**

| 구분 | 확인 결과 | 근거 |

**독스트링은 대체로 실재하는 함수에 연결되지만, 그 함수가 보장하는 범위를 그림에서 확대했다.**

## 6. 중요한 구조 불일치

### 항목별 Case와 여행별 묶음 Case

현재 감시는 due 항목을 반복하면서 **각 항목의 Case를 만든다.** 요청 ID도 여행·항목·원인 지문으로 구성된다. 이후 열린 Case들을 순서대로 실행한다. `T/trip_watch_cases.py:77–114,142`

반면 기준 계획서는 **한 스윕·한 Trip에 Case 하나**, D-017은 여러 원인의 대안을 모아 **전체 일정 재검증·새 버전 하나·알림 하나**를 요구한다. `P/A-COP_구현계획서_v11.md:1014–1026`; `W/D-017-watch-cadence-golden-time.md:40–45`

따라서 현재 그림은 **현재 항목별 구현에는 맞지만, 계획서의 묶음 조정 구조에는 맞지 않는다.**

여러 항목 문제가 같은 여행에서 잡히면 Case·변경·알림이 여러 건이 될 가능성이 있다. 이것은 코드 구조에서 도출한 결과이며, 이번 검토에서 실제 다중 사건 실행을 측정한 것은 아니다.

### 전체 일정 재검증을 거쳤다고 말할 수 없음

등록 시에는 `check_itinerary()`를 호출한다. `T/trip_api.py:590–601`

그러나 그림의 Case 적용기는 소유·기준 버전·항목·장소와 묻기 조건을 검사한다. **갱신된 전체 일정에 등록과 같은 `check_itinerary()`를 다시 적용하는 호출은 이 경로에서 찾지 못했다.** `T/itinerary_actions.py:88–160`

앞뒤 이동을 갱신하는 것과 **전체 일정 성립을 재검증하는 것**은 다르다. 그림의 검증 구역을 후자로 설명하면 안 된다.

### 고정 항목은 기본 감시에서 아예 제외됨

현재 `trip_cases`는 `customer_pinned` 항목을 만나면 점검 전에 건너뛴다. `T/trip_watch_cases.py:78–80`

D-020은 고정 항목도 **감지·안전 알림은 계속**하도록 요구하고, 구현 상태 표에서는 완료라고 설명한다. `W/D-020-trip-survey-and-ask-first.md:86,101`

**현재 기본 감시 경로와 D-020의 완료 설명이 어긋난다.** 그림의 「보호 일정이면 묻는다」만 보면 이 누락을 알 수 없다. 적용기까지 도달한 보호 항목의 처리와, 감시가 보호 항목을 발견하는 문제를 나눠 표시해야 한다.

### 보호 대상 판정도 D-020과 다름

D-020 오전 정정은 「돈이 걸렸는지 보지 않고 customer_pinned만」이라고 적는다. `W/D-020-trip-survey-and-ask-first.md:61`

현재 `protected_reason()`은 `customer_pinned` 외에 `locked`, `detail.booking`도 보호한다. `T/pending.py:49–58`

최신 그림의 「보호 일정」은 모호한 표현이므로, 현재 구현을 보여 줄 때는 이 세 조건을 구체화하고 **결정과 구현의 차이**를 표시해야 한다.

## 8. 지금 형식을 유지하면서 더하고 빼야 할 구조

현재의 다섯 구역·상자·마름모·점선 형식은 유지할 수 있다.

| 구역 | 수정 |
|---|---|
| ① 들어오는 곳 | **외부 계획 작성 에이전트·LLM → 계획 접수·검증·등록 → 여행 저장**을 추가 |
| ① 들어오는 곳 | **개인 AI → MCP**를 별도 상자로 추가. 「기본 조회·쓰기 설정 필요」 표시 |
| ① 들어오는 곳 | 일반 고객 Case와 여행 채팅을 분리 |
| ② 오케스트레이터 | 「규칙 Controller」라고 표시. 여행 채팅 옆에는 **결정 단위(LLM) → Case 기록·TripDesk** 점선 경로 추가 |
| ③ 워커 | 두 워커에 「규칙 코드」 표시. 이동은 아래 공용 툴 상자로 배치 |
| ③ 워커 | `read.dining_state`를 후보 생성·영업 판정 상자로 이동 |
| ③ 워커 | Booking Handoff는 두 워커와 같은 주 에이전트로 늘리기보다 **예약 업무 보조 경로**로 별도 배치. 현재 Team 등록 사실 표시 |
| ④ 검증·반영 | Case 적용기와 TripDesk·pending 직접 처리를 작은 하위 상자로 구분한 뒤 **공통 버전 저장**에서 합침 |
| ④ 검증·반영 | **전체 일정 재검증은 이 변경 경로에서 미확인**이라는 주석 추가 |
| ④ 검증·반영 | apply·ask·safety_alert 세 갈래와 consent 경로 구분 |
| ④ 검증·반영 | 고객 「바꿔 줘」는 **후보 계산 → 다시 묻기**로 돌려보냄. 구체적 안 선택은 선택 처리·저장으로 연결 |
| ④ 보조 경로 | 위임은 **모의 예약 취소 실행 범위 검사**에만 연결. 일반 일정 변경의 필수 문으로 그리지 않음 |
| ⑤ 알림·다음 차례 | outbox 완료에서 감시로 이어지는 실행 화살표를 빼고, **독립 타이머**가 감시를 시작하도록 표시 |
| 그림 바깥 주석 | 내부 생성기는 「현재 코드에 존재·이번 팀 결정상 제품 범위 밖」이라고만 표시 |

**외부 에이전트를 추가하는 것만으로 내부 LLM 멀티에이전트 협업이 구현됐다고 설명해서는 안 된다.** 외부 작성자, 개인 AI 클라이언트, 내부 해석 모델, 규칙 워커, 공용 툴은 서로 다른 참여자다.

최종적으로 이 그림은 **현재 구현의 식사·활동 감시 Case 흐름**으로 범위를 좁히고 위 문장을 수정하면 사용할 수 있다. **프로젝트 전체 구조나 결정이 모두 구현된 구조로는 그대로 사용하면 안 된다.**
