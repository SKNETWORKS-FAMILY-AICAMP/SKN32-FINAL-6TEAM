### S6B: `{}`는 오히려 “먼저 묻기”를 넓힌다

**확인한 조건**은 다음이다.

```text
원인 종류가 예보·기상특보·대기질에만 해당하고 안전 사건은 없음
AND
(
  실내·야외 모름
  OR
  자동 교체를 직접 선택했다는 기록이 없음
)
```

- `needs_consent(report, None)`이면 실내·야외 모름 조건만 본다.
- 실제 활동 워커는 `constraints or {}`를 넘긴다. 따라서 설문이 없어도 `None`이 아니라 `{}`다.
- `{}`에는 직접 답한 기록이 없으므로 `auto_on_disruption({})`는 거짓이다. **실내·야외를 알아도 날씨 관련 사건이면 먼저 묻는다.**
- 실제 일정 읽기 도구는 저장된 `constraints`를 반환한다. 따라서 “워커가 설문을 항상 빈 값으로 받는다”는 반박도 사실이 아니다.
- 자동 교체에는 `survey_answered`에 해당 문항이 있고 답이 `replace`라는 두 조건이 필요하다. 저장된 기본값 `replace`만으로는 부족하다.

근거: [실제 활동 호출부](C:/Users/playdata2/Documents/final_workspace/final_project_cs/app/modules/travel_ops/activity/team.py:111), [동의 함수](C:/Users/playdata2/Documents/final_workspace/final_project_cs/app/modules/travel_ops/pending.py:99), `T/survey.py:117–123`; `A/tools/read_tools.py:385–388`.

**따라서 S6B의 새 조건 자체는 제대로 반영했다.** 다만 그림에는 “날씨·대기질만 / 자동 교체 직접 선택 기록 없음”이라고 풀어 써야 한다.

### S10: 실제 `check`와 호출부

실제 연결은 다음이다.

```text
composition.check_factory
  → DisruptionCheck(외부 소스 묶음).check
  → trip_api._check()가 재사용
  → trip_api._choose()
  → pending.choose(check=_check())
  → plan_swap(check=check)
```

근거: `A/composition.py:317–322`; `T/trip_api.py:525–535,894–906`; `T/pending.py:315–317`.

`plan_swap`은 **장소가 있고 활동 항목이며 `check`가 연결된 경우**에만 해당 점검 함수를 다시 실행한다. 식사에서는 그 함수를 실행하지 않는다. 활동도 점검기가 없으면 재점검을 생략한다. `T/itinerary_changes.py:888–897`.

여기서 두 가지 과장이 남는다.

1. **“식사는 버전·항목만”은 틀림.** 선택지·장소 존재·뒤 이동 조정·다음 장소 일정 충돌도 본다. 영업 여부나 외부 사건을 다시 조회하지 않는다는 뜻으로 고쳐야 한다.
2. **“그 시각 외부 재점검”이 새 HTTP 조회를 보장하지 않음.** 서버는 점검 객체를 재사용하고, 외부 어댑터는 저장해 둔 응답을 재사용할 수 있다. 기본 일반 응답 유지 시간은 5분, 재난문자는 20분이다. `T/trip_api.py:525–531`; `I/base.py:118–127,163–184`; `R/config/guardrails.yaml:432–441`.

**“바꿔 줘”의 6곳도 수정해야 한다.** 600m에서 최대 6곳을 점검하고 실패하면 1.5km에서 다시 최대 6곳을 점검한다. 이 호출 구조에서 총 점검 요청은 최대 12회가 될 수 있다. 이는 두 워커의 12회 도구 예산과 다른 경로다. `T/pending.py:333–367`.

### S10: 무응답 만료는 기본 경로에 연결되지 않았다

**확인:**

- 제안에는 종료 시각, 종료 시각이 없으면 시작 시각을 만료 시각으로 저장한다. `T/pending.py:204–218`.
- 실제 만료 처리는 `PendingStore.expire()`가 한다. `T/pending.py:264–270`.
- `app`·`scripts`에서 확인한 호출부는 `TripWatch.tick()`이다. `T/trip_watch.py:63–70`.
- 기본 작업은 `trip_cases`를 실행하며 `trip`은 `--only trip`일 때만 실행한다. `R/scripts/run_sweepers.py:98–103`.
- `pending.choose()`는 제안 상태·버전 등을 검사하지만 현재 시간이 만료 시각을 지났는지는 검사하지 않는다. `T/pending.py:288–307`.

**추론:** 별도 `trip` 실행이나 외부 정리 작업이 없으면 제안이 종료 시각 뒤에도 `open`으로 남을 수 있다. 버전과 항목이 유지되면 종료 후 선택도 시간만으로 차단되지 않는다. 실제 운영 DB에서 이런 사례가 발생했는지는 확인하지 않았다.

그림의 **“무응답→일정 종료→자동 만료”는 현재 기본 배선으로 그리면 안 된다.**

### S11: 순서는 일부 맞지만 “같은 판정 문”은 다시 틀렸다

기본 설정은 결정 단위 `on`이다. 운영 설정으로 바꿀 수 있다. `R/config/guardrails.yaml:247–250`; `T/trip_messages.py:528–546`.

기본 `on` 경로에서는 다음 순서가 맞다.

```text
모델이 할 일·대상 선택, 반환값 검증
→ Case 생성
→ 결정 결과의 분류 라벨 기록
→ 담당·할 일 기록
→ 요청 종류별 처리
→ 결과와 답변 기록
```

다만 **담당을 기록한 것이 실제 워커 실행을 뜻하지 않는다.** 이후 코드는 TripDesk 또는 질문·위치 답변 등의 함수를 직접 부른다. `T/trip_messages.py:623–738`.

| 요청 종류 | 실제 처리 |
|---|---|
| 사실 질문·위치 질문·되물음 | 답변 또는 추가 질문. 일정 저장 없이 끝날 수 있음 |
| “다른 안으로”, 직접 변경 | `swap_alternate`·`fresh_alternate`. 묻기 정책 우회 |
| “후보 보여 줘” | 선택 요청 열기 |
| 되돌리기·다시 적용 | 옛 내용을 **새 버전으로** 저장하거나 먼저 확인 질문 |
| 지연 신고·현재 식사 휴무 신고 | TripDesk 내부에서 `decide` 판정 후 묻기 또는 저장 |
| 다른 대상의 휴무 신고 | 대상에 따라 `fresh_alternate`로 갈 수 있음 |

근거: `T/trip_messages.py:642–738`; `T/trip_desk.py:97–112,123–156,218–240,243–307`.

**TripDesk는 `apply_or_ask`를 호출하지 않는다.** 일부 신고에서 같은 `decide` 함수를 공유한다. 실제 쓰기는 자체 `_write` 경로다. 더구나 TripDesk 판정은 `report=None`이라 안전 사건 분기를 같은 방식으로 제공하지 않는다. `T/trip_desk.py:256–307`.

이것은 1차 검토의 “공통 규칙이 있어도 적용 경로는 다르다”를 **반영한 척하면서 다시 하나의 문으로 합친 곳**이다. `V1:11`; `V2:81`.

### S7·S8: 그대로, 동의, 안전 알림은 존재하지만 도착 조건이 다르다

| 갈래 | 확인 결과 |
|---|---|
| **그대로→Case 완료** | 존재. 답을 Case에 저장하고 완료하며, 제안이 없으면 알림 목록은 빈 상태다. `A/application/controller.py:435–455`. |
| **“바꿀까요?”→묻기 열기** | 존재. 소유·버전을 확인한 뒤 동의 전용 처리로 가며 일반 교체안 판정을 건너뛴다. 대체안 없이 제안을 연다. `T/itinerary_actions.py:97–103,198–225`. |

**“안전 사건이면 안전 알림은 반드시 간다”는 구조가 아니다.** 대체안 계산이 실패하면 안전 판정 문에 도달하지 못할 수 있다.

### 중단 시 고객은 무엇을 받는가

**확인:** `itinerary_unresolved`·`fatal_source_failure`를 반환한 감시 워커의 중단 경로에는 고객 알림 생성이 없다.

```text
워커 실패 결과
→ Case 실패 상태·사유 기록
→ 일정 유지
→ 이 실패에 대한 고객 알림 없음
```

근거: `T/dining/team.py:112–114`; `T/activity/team.py:106–108`; `T/itinerary_team.py:257–263`; `A/application/controller.py:504–511`. 상태 변경 함수는 전달받은 알림 목록만 적재하며 별도 실패 알림을 만들어 주지 않는다. `A/core/transition.py:195–208`.

또한 다음 감시가 같은 항목·같은 원인 지문을 발견하면 기존 Case로 모이며 **새로 생성된 Case만 실행**한다. 실패 Case가 다음 주기에 자동으로 재실행되는 연결은 아니다. `T/trip_watch_cases.py:55–58,110–114,142–161`.

**그림에 정직한 종점:**

> **변경 중단 — 일정 유지·실패 기록 / 이 중단에 대한 고객 알림 없음**

“고객은 아무것도 못 받는다”는 표현은 너무 넓다. 정기 안내·다른 변경 알림은 별도로 받을 수 있다. 채팅 요청 실패도 사용자에게 반환하는 답변 경로가 있으므로 감시 실패와 구분해야 한다.

“운영자는 오류 대응만”은 팀 결정이다. 코드에는 `escalated` 상태와 사람 인계라는 오래된 설명이 남아 있다. **실제로 운영자가 고객 건을 처리한다거나 자동 복구가 연결되어 있다고 확인한 것은 아니다.** `T/_base.py:134–143`; `W/D-018-decision15-stop-paths.md:24–32,63`.

## 4. 그림 세 장에 필요한 상자·화살표·이름표

아래는 **그림 제작용 목록**이다. 그림 안에는 쉬운 이름을 사용하고 개발 식별자는 검토 문서에만 남긴다.

주체 종류는 요청한 다섯 종류를 사용한다. 워커 내부의 상자는 각각 새로운 에이전트가 아니라 **같은 워커의 처리 단계**다. 외부 정보 조회 상자는 정보 제공자를 에이전트로 세는 것이 아니라 조회하는 규칙 코드를 뜻한다.

세 그림 공통 표기:

- **실선:** 확인한 실행 연결.
- **점선:** 선택적 연결 또는 팀 목표 연결. 반드시 어느 쪽인지 이름표로 구분.

- **그림 밖 연결:** 다른 그림의 상자 번호를 화살표 끝에 표기. 새 상자를 중복 생성하지 않음.
- **Case:** 그림에서는 **문제 처리 건**.
- **pending:** **선택 대기 제안**.
- **버전:** **일정 판**.
- **Supervisor:** **처리 총괄**.

| **S6B 순위** | **필수 조건을 통과한 후보를 일정 변경량·추가 비용·시간과 도보 변화·되돌리기 가능성·경고·비슷함·거리 순으로 비교한다. 설문 선호는 비슷함 계산에 반영한다.** |
| **S7 그대로** | **문제가 없어졌으면 일정은 유지하고 문제 처리 건을 완료한다. 이 결과에 대한 고객 알림은 생성하지 않는다.** |
| **S7 중단** | **변경할 수 없거나 조회·검증이 실패하면 일정은 유지하고 실패 상태·사유를 기록한다. 감시 워커의 이 중단에 대한 고객 알림은 생성하지 않는다.** |
| **S7 검증** | **참조·소유·근거 식별자를 대조하고, 근거를 온전히 구성하지 못한 상태의 자동 제안을 막는다. 교체 내용과 외부 사실 전체를 다시 검증하는 단계는 아니다.** |
| **S8 분기** | **대체안 없는 바꿀까요? 제안은 현재 항목을 확인한 뒤 선택 요청을 연다. 일반 교체안은 보호·설문·안전 조건으로 묻기 또는 변경을 정한다. 고객 직접 선택과 전체 목록 교체는 이 묻기 판정을 우회한다.** |
| **S8 안전** | **보호 항목은 먼저 묻고, 안전 사건이면 안전 표시를 붙인다. 보호 항목이 아니면서 먼저 물어봐와 안전 사건이 함께 있으면 안전 안내를 만든다. 후보 계산이 실패해 적용기에 도달하지 못하면 이 안전 안내도 생성되지 않는다.** |
| **S8 이동** | **장소가 바뀌면 바로 앞뒤 이동을 갱신한다. 계산할 수 있으면 새 경로를 쓰고, 계산할 수 없으면 가까운 교체는 기존 경로를 유지하며 이름을 갱신하고 먼 교체는 어림값 경로로 바꾼다. 전체 일정 재검증은 이 경로에 없다.** |
| **S9 작업** | **정기 안내는 감시·새벽 확인 뒤 같은 점검 작업에서 만들고, 적재된 알림은 별도 1분 작업이 배달한다. 작업 설정이 실제 도착시간을 보장하지는 않는다.** |
| **S9 정기 안내** | **하루 시작에는 그날 일정·최근 변경·답을 기다리는 항목을 안내한다. 현재 장소 일정이 시작하면 다음 장소 일정을 안내하고, 저장된 이동 항목이 시작하면 출발을 안내한다. 대기 중이면 대기 안내로 바꾸며, 경로 확인 실패나 사건 발견으로 출발 안내를 보류할 수 있다.** |
| **S9 발송** | **Discord 발송을 시도하며 계획서 링크를 싣는다. 일반 오류는 첫 시도 포함 최대 3회 시도하고, 시간 초과·연결 오류는 수신 여부 불명으로 기록해 자동 재시도하지 않는다.** |
| **S10 안 선택** | **구체적 안을 고르면 열린 제안·최신 판·항목·선택지·장소·다음 일정 충돌을 확인한다. 활동은 점검기가 연결되어 있으면 외부 변동을 재판정하고, 식사는 영업·외부 사건을 다시 조회하지 않는다. 통과하면 워커를 거치지 않고 새 판을 저장한다.** |

| **S10 무응답** | **무응답이면 자동 변경하지 않는다. 종료 시각 기반 만료 함수는 있으나 기본 감시 경로에 연결되지 않아, 종료 때 자동으로 닫히는 동작은 현재 보장되지 않는다.** |
| **S10 되돌리기** | **되돌리기는 옛 판의 내용을 새 일정 판으로 다시 기록한다. 뒤에 다른 변경이 있으면 그 변경까지 되돌아갈 수 있으므로 채팅 경로에서 먼저 확인할 수 있다.** |
