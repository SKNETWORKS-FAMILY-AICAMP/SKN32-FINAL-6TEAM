# triPilot 멀티에이전트 플로우 — 단계 정의 2판 (Claude · 코덱스 1차 검토 반영 · 2차 적대 검토용)

1판: `플로우_단계정의_초안.md` · 코덱스 1차 검토: `코덱스_검토결과_v11.md`(그림 v11 대상) · 외부 Claude 지적(사용자가 붙여 줌)도 반영.

## 0. 주체 종류 — 그림의 색과 모양이 이것을 가른다

| 표시 | 뜻 | 누가 |
|---|---|---|
| **LLM 에이전트(외부)** | 스스로 다음 행동을 고르는 LLM. 우리 도구를 부른다 | 계획을 짠 외부 에이전트 · 고객의 개인 AI(MCP) |
| **워커 에이전트(규칙)** | 역할 · 허용 툴 · 할 일 계약 · 시간 제한을 받는 작업 주체. **판단은 규칙 코드, LLM 안 씀**(감시 Case 경로 기준) | 요식 · 액티비티 |
| **AI 모델 호출** | 에이전트가 아니다. 한 번 부르고 끝. 정해진 목록에서 고르거나 원문을 옮기기만 | 계획 읽기 · 결정 단위 · 신고 해석 · 분류 · 영업시간 원문 정리 · 알림 번역 |
| **규칙 코드** | 결정적 처리 | 오케스트레이터(규칙 Supervisor) · 적용기 · 감시 · 알림 워커 · 공용 이동 판정 툴 |
| **사람** | 고객(여행자). 운영자는 오류 대응만 | — |

정직하게 쓸 문장(그림 머리 · 발표):
> triPilot 의 멀티에이전트 구조는 **경계의 LLM 에이전트(계획 작성 · 개인 AI)** 와 **안쪽의 규칙 Supervisor + 역할 워커 둘**로 이뤄진다.
> 안쪽 워커는 LLM 루프가 아니라 허용 툴을 부르는 규칙 코드다 — 일정을 실제로 바꾸는 시스템이라 판단을 코드에 뒀다. LLM 은 정해진 자리에서 고르기 · 옮기기만 한다.

## 단계 (처음부터 끝까지)

### S0. 계획을 짠다 — LLM 에이전트(외부)
- 냄: 일정 원문(글 · 사진 · 파일). 웹 또는 개인 AI 의 MCP 로 제출.
- MCP: 읽기 도구는 늘 열림, **쓰기는 `travel.mcp.write_enabled` 를 켤 때만**(기본 꺼짐) — `mcp_server.py` · `guardrails.yaml:271–276`
- 우리 코드에 일정 생성기(`planner.py`)도 있으나 팀 결정상 제품 범위 밖 → 그림 밖 주석.

### S1. 계획 읽기 — 규칙 코드 먼저 + AI 모델(줄 위치 · 사진 받아쓰기)
- 받음: 원문 / 냄: 일정 항목 + 근거 줄. 모델은 원문 조각을 가리키기만(`intake/llm_spans.py:45–87`).

### S2. 등록 판정 — 규칙 코드
- 통과 → 여행 저장 + 계획서 링크 + 알림 / 거절 → 이유 + 고칠 방법(`intake_incomplete` · `itinerary_infeasible`).
- 루프 ① 거절 → 고쳐서 다시 제출 → S1.
- 근거: `trip_api.py:556–621` · `itinerary_checks.py:78`

### S3. 감시 — 규칙 코드 · 독립 타이머
- 결정: 외부 소스 **3분**(D-017 · D-020). **현재 코드: 작업 1분**, 응답 재사용은 실행 1회 안에서만 → 매분 다시 조회할 수 있다(에어코리아 500/일 넘길 위험, 측정은 안 함).
- 받음: **90분 안에 시작할** 항목(고객 고정 항목은 지금 코드에서 건너뜀 — D-020 과 어긋남) + 적용 가능한 외부 범주(기상 · 특보 · 지진 · 재난문자 · 교통 · 대기질, 실내면 일부 생략).
- 냄: 깨진 항목마다 Case 1건(현재 **항목별**, 같은 항목 · 같은 원인은 중복 방지). 식사 `dining_other` · 활동 `activity_…` · 경로 사건 `mobility_…`.
- 계획서 v11 · D-017 은 **여행별 묶음 Case**(전체 재검증 · 새 버전 하나 · 알림 하나) → 미구현.
- 근거: `jobs.py:71–82` · `run_sweepers.py:225–248` · `cache.py` · `trip_watch_cases.py:71–161`

### S4. 배정 — 오케스트레이터(규칙 Supervisor)
- 문제 코드 앞부분(확인된 대상 힌트가 있으면 그것) → 담당 하나. 없거나 여럿이면 멈춤.
- 근거: `routing.py:39–48` · `registry.py:71–85` · `controller.py:245–257`

### S5. 할 일 계약 — 오케스트레이터 → 워커 (화살표 이름표로 「할 일 묶음 →」)
- 할 일 종류 · 지금 상태 · 근거 묶음 · 허용 툴 · 마감 90초(설정값 — 툴 호출이 동기라 강제 중단 보장은 미확인).

### S6A. 요식 워커(규칙)
1. 일정 읽기 `read.itinerary` → 지금 항목 재점검 `read.disruptions`: 문제 없음 → **그대로(답)** · 조회 실패(None · fatal) → **변경 중단**
2. 후보 만들기: 요식 후보 표(`read.dining_alternatives`, 없으면 `read.place_catalog`) + 그 시각 영업 판정(`read.dining_state`) → 순위
3. 앞 순위 후보 **최대 3곳** 외부 재점검 `read.disruptions` (루프 ②) — 못 본 곳은 안 고름
4. 살아남은 후보 중 최선 1 + 다른 안 최대 2 → **변경 제안** / 0곳 → **변경 중단**(`itinerary_unresolved`)

### S6B. 액티비티 워커(규칙)
1. 같은 재점검
2. **원인이 날씨뿐(안전 사건 없음) + (실내 모름 또는 설문에서 자동 교체를 직접 고르지 않음)** → 후보 계산 없이 **「바꿀까요?」 제안**
3. 아니면 후보 재점검(루프 ②) → 최선 + 다른 안 → 변경 제안 / 못 찾음 + 날씨뿐 → 「바꿀까요?」 / 그 밖 → 변경 중단
- 순위: 필수 조건 통과 후 비용 · 경고 · 비슷함(분류 · 구) · 거리 · 설문 선호

툴 규칙(두 워커 공통): 허용 목록 밖 거부 · 같은 툴 + 같은 인자 다시 부르면 거부 · 한 실행 툴 12번. 워커끼리 직접 부르지 않는다. 계약상 HANDOFF 값은 있으나 오케스트레이터가 다시 배정하는 분기는 없다.

### S7. 결과 받기 — 오케스트레이터 (화살표 「← 결과: 그대로 · 제안 · 중단」)
- 그대로 → Case 완료, 일정 안 바뀜 · 중단 → 일정 그대로 + 실패 상세 기록(운영자 오류 대응만)
- 제안 → **참조 · 소유 · 근거 대조**(근거 묶음이 부족하면 자동 실행 금지). 일정 상세값은 적용기가 본다. 실패 → 중단

### S8. 적용기 — 규칙 코드
- 재확인: 고객 소유 · 기준 버전(밀렸으면 충돌 → 중단) · 바꾸는 항목 · 새 장소 실재. **전체 일정 재검증(S2 같은 것)은 이 경로에 없다.**
- 「바꿀까요?」 제안 → 묻기 열기
- 판정(먼저 걸리는 것): 보호 일정(고객 고정 · 잠긴 예약 · 예약번호) → 묻기 / 「먼저 물어봐」+ 안전 사건 → **안전 알림** / 「먼저 물어봐」 → 묻기 / 그 밖 → 적용
- 적용 → 새 일정 버전(이전 판 보존 · 앞뒤 이동 갱신 — 계산 못 하면 기존 유지 · 추정 표시) + 되돌리기 버튼

### S9. 알림 — 규칙 코드 · 독립 타이머(1분)
- 새 버전 알림 · 묻는 알림 · 안전 알림 · 정기 안내(하루 시작 · 다음 일정 · 출발) → Discord + 계획서 링크. 중복 적재 막음 · 첫 발송 포함 최대 3번 시도(시간 초과는 다시 안 보냄).

### S10. 고객 응답 — 사람 · LLM 에이전트(외부)
- 안 고르기 → 그 시각 다시 확인(활동은 외부 재점검, 식사는 버전 · 항목만) → 새 버전 (오케스트레이터 · 워커 안 거침, `pending.choose`)
- 그대로 두기 → 닫음 · 「바꿔 줘」 → 그때 후보 계산(600m → 1.5km, 6곳 재점검) → 안 1 · 2 · 3 으로 **다시 묻기** (루프 ③) · 무응답 → 그 일정이 끝나면 만료(안 바꿈) · 되돌리기 → 이전 버전
- 동시에 누르면 먼저 닫은 쪽이 이김

### S11. 고객 채팅 · 개인 AI 문장 — AI 모델(결정 단위) → 규칙 코드
- 결정 단위(AI 모델): 일정 · 변경 이력 · 대화 · 화면 선택을 보고 **할 일 + 대상을 목록 안에서만** 고름 → 서버 검증 → Case 기록 · 분류 · 라우팅 기록 → TripDesk 계산 → S8 과 같은 판정 문(apply_or_ask) → 버전 저장 → S9
- 일반 `/v1/cases` 는 접수 → 신고 해석 · 분류(AI 모델) → S4 오케스트레이터 경로

### S12. 새벽 영업 확인 — 규칙 코드(03~08시, Google)
- 그날 식사 · 활동 → 닫힌 곳 근처 대체 → `apply_or_ask` → 버전 저장 → S9

### 루프
① 등록 거절 → 다시 제출 · ② 워커의 후보 재점검 · ③ 묻기 → 「바꿔 줘」 → 다시 묻기 · ④ 감시는 독립 타이머로 다시 돈다(알림이 감시를 부르지 않는다).
