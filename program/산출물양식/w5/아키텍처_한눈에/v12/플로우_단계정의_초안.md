# triPilot 멀티에이전트 플로우 — 단계 정의 (초안 1, Claude 작성 · 코덱스 적대 검토 전)

그림을 그리기 전에 **처음부터 한 단계씩** 누가 · 무엇을 받아 · 무엇을 내고 · 어디로 넘기는지 정한다.
각 단계의 **주체 종류**를 셋으로 가른다 — 멘토 지적 「AI 모델 호출과 에이전트를 구분하라」.

| 표시 | 뜻 |
|---|---|
| **[외부 에이전트]** | 우리 밖의 LLM 에이전트 — 계획을 짠 쪽 · 고객의 개인 AI(Claude · ChatGPT 등). 스스로 판단하고 우리 도구를 부른다 |
| **[워커 에이전트]** | 우리 안의 작업 주체(요식 · 액티비티). 자기 권한(허용 툴 목록) · 맥락(할 일 묶음) · 시간 제한을 받는다. **판단은 규칙 코드, AI 모델 안 씀** |
| **[AI 모델]** | 에이전트가 아니라 **한 번 부르고 끝나는 모델 호출**. 정해진 목록 안에서 고르거나 원문을 옮겨 적기만 한다. 값을 만들지 않는다 |
| **[코드]** | 오케스트레이터 · 적용기 · 감시 · 알림 워커 — 결정적 규칙 |

★정직하게 적을 것: 우리 안쪽 구조는 Anthropic 구분으로 **「워크플로 + 도구를 쓰는 작업 주체」**에 가깝다(에이전트가 다음 행동을
스스로 고르는 LLM 루프가 아니다). 일정을 실제로 바꾸는 시스템이라 판단을 코드에 둔 것이 설계 의도다.
**LLM 에이전트끼리의 협업은 경계에서** 일어난다 — 외부 에이전트(계획 · 개인 AI)가 우리 도구(MCP · 웹 API)를 부르고, 우리는 판정 · 감시 · 수정으로 답한다.

---

## 단계

### 0. 계획을 짠다 — [외부 에이전트]
- 받음: 고객의 여행 요청 · 받음 밖(우리 시스템 밖)
- 냄: 일정 원문(글 · 사진 · 파일) — 우리에게 제출
- 근거: 계획 생성은 우리 일이 아니다(루트 CLAUDE.md 사실표). 개인 AI 입구 `modules/travel_ops/mcp_server.py`(조회 · 신고 · 다른 안 · 고르기 · 되돌리기 · 검증받고 등록, 쓰기는 설정으로 켤 때만)

### 1. 계획 읽기 — [코드] 먼저, [AI 모델] 은 보조
- 받음: 일정 원문
- 냄: 일정 항목(날짜 · 시각 · 장소) + 원문 근거 줄
- AI 모델: 원문 줄 위치 찾기 · 사진 받아쓰기 (`intake/llm_spans.py`) — 값은 원문에서 옮긴다
- 다음: 2

### 2. 등록 판정 — [코드]
- 받음: 일정 항목
- 냄: **통과 → 등록 + 계획서 링크** / **거절 → 이유 + 고칠 방법**(필수값 부족 `intake_incomplete` · 수행 불가 `itinerary_infeasible`)
- 보는 것: 시각 순서 · 겹침 · 이동 시간 · 환승 · 결제 · 예산, 값이 있을 때만 휴무 · 영업 전후 · 마지막 입장 · 브레이크. 외부 날씨는 안 본다
- 루프 ①: 거절 → 고객 · 외부 에이전트가 고쳐서 다시 제출 → 1
- 근거: `itinerary_checks.py:78 check_itinerary`

### 3. 감시 — [코드] (작업 1분마다 · 외부 소스는 결정상 3분)
- 받음: 등록된 여행 중 **앞으로 90분 안** 항목 + 외부 6범주(기상 · 기상특보 · 지진 · 재난문자 · 교통 사건 · 대기질)
- 냄: 깨진 항목 1개 → **Case 1건**(식사 `dining_other` · 활동 `activity_weather_risk` / `activity_other`, 경로 사건 `mobility_…`)
- ★주기: 작업은 1분마다(`scripts/ops/jobs.py:76`). 결정(D-017 · D-020)은 외부 소스 3분. 코드의 응답 재사용은 **실행 1회 안에서만** 살아(`travel/cache.py`) 지금은 매분 새로 조회하는 것으로 보인다 — 코덱스 확인 중
- 근거: `trip_watch_cases.py`

### 4. 배정 — 오케스트레이터 [코드]
- 받음: Case(문제 코드)
- 냄: 담당 워커 에이전트 1개 — 문제 코드 앞부분 `dining_` → 요식, `activity_` → 액티비티. 받을 곳이 없으면 멈춤
- 근거: `application/routing.py case_type_of` · `controller.py run_case` A 단계

### 5. 할 일 묶음 — 오케스트레이터 [코드] → 워커 에이전트
- 냄(에이전트에게 주는 계약): 할 일 종류(capability) · 지금 상태 · 근거 묶음(ContextPack) · 허용 툴 목록 · 마감 90초
- 규정 질문일 때만 규정 검색(RAG). 검색 실패면 근거 묶음이 「부족」 표시 → 에이전트는 확정 답을 안 낸다
- 근거: `controller.py _task`

### 6A. 요식 에이전트 — [워커 에이전트]
1. 일정 읽기 `read.itinerary`
2. 지금 항목 재점검 `read.disruptions` → 문제 없음: **그대로(답)** · 확인 불가: **멈춤** · 깨짐: 3
3. 대체 후보 `read.place_catalog` + 요식 후보 표 `read.dining_alternatives` → 순위
4. 후보를 순위순 **한 곳씩** 재점검 `read.disruptions` · 그 시각 영업 `read.dining_state` — 최대 3곳, 못 본 곳은 안 고름 (루프 ②)
5. 결과: 통과 → **변경 제안**(최선 1 + 다른 안 최대 2) · 통과 0곳 → **멈춤**(`NoChange("unresolved")` → `settle` 이 `itinerary_unresolved` 로 멈춤). ★이때 고객에게 알림이 가는지 미확인
- 근거: `dining/team.py handle_trigger` · `itinerary_changes.plan_dining_disrupted`

### 6B. 액티비티 에이전트 — [워커 에이전트]
1. 일정 읽기 · 2. 지금 항목 재점검 (요식과 같다)
3. 원인이 날씨뿐이고 실내 여부를 모름 → 후보 계산 없이 **「바꿀까요?」 묻기 제안**
4. 아니면 후보를 한 곳씩 재점검(비슷한 곳 → 가까운 곳 · 설문 선호) (루프 ②)
5. 결과: 통과 → 변경 제안 · 못 찾았고 날씨뿐 → 「바꿀까요?」 · 그 밖(못 찾음) → **멈춤**(같은 `itinerary_unresolved`)
- 근거: `activity/team.py handle_trigger`

공통 툴 규칙: 목록 밖 거부 · 같은 툴 + 같은 인자 다시 부르면 거부 · 한 실행 12회. 에이전트끼리 직접 부르지 않는다(남의 일이면 HANDOFF 로 돌려준다 — `_base._guard`).

### 7. 결과 받기 · 대조 — 오케스트레이터 [코드]
- 받음: 에이전트 결과 — 그대로(답) / 제안(일정 변경 · 「바꿀까요?」) / 멈춤
- 그대로 → Case 완료(일정 안 바뀜) · 멈춤 → 일정 그대로 + 이유 코드 기록(운영자 개입 없음)
- 제안 → **대조**: 근거 묶음이 부족하면 자동 실행 금지 · 제안 값을 오케스트레이터가 만든 근거와 대조 → 실패면 멈춤
- 근거: `controller.py _event_for_result · _reject_unverified`

### 8. 적용기 재확인 + 묻기 판정 — [코드]
- 재확인: 고객 소유 · 기준 버전(밀렸으면 충돌) · 바꾸는 항목 실재 · 새 장소 실재
- 「바꿀까요?」 제안 → 바로 묻기 열기
- 묻기 판정(위에서 먼저 걸리는 것): 변경 안 할 일정(고객 고정 · 잠긴 예약) → 묻기 / 「먼저 물어봐」 + 안전 사건 → 안전 알림 / 「먼저 물어봐」 → 묻기 / 그 밖 → 적용
- 적용 → **새 일정 버전**(이전 판 보존 · 앞뒤 이동을 이동 판정 툴로 재계산 · 자동 변경엔 되돌리기 버튼)
- 근거: `itinerary_actions.py apply` · `pending.decide`

### 9. 알림 — [코드]
- 받음: 새 버전 알림 · 묻는 알림 · 정기 안내(하루 시작 · 다음 일정 · 출발 — `trip_reminders`)
- 냄: Discord 알림 + 계획서 링크(상태의 정본). 같은 알림 중복 적재 막음 · 보내기 실패 시 첫 발송 포함 최대 3번 시도
- 근거: `infrastructure/messaging/worker.py` · `notify/discord.py`

### 10. 고객 응답 — [사람] · [외부 에이전트]
- 고르기 → 그 시각에 **다시 점검**하고(그 사이 일정이 바뀌었으면 거절) 새 버전 (오케스트레이터 · 에이전트를 안 거친다) — `pending.choose`
- 그대로 두기 → 닫음(kept)
- 「바꿔 줘」 → 그때 후보를 계산해 안 1 · 2 · 3 으로 **다시 묻기**(600m → 1.5km) — `pending._consented` (루프 ③)
- 무응답 → 그 일정이 끝나면 만료, 바꾸지 않음
- 되돌리기 → 이전 버전으로

### 11. 고객 채팅 · 개인 AI 문장 — [AI 모델] 결정 단위 → [코드]
- 받음: 고객 문장(+ 일정 상태 · 변경 이력 · 화면 선택)
- AI 모델: 할 일 + 대상을 **정해진 목록 안에서만** 고른다(일정 id · 변경 id · 할 일 종류) — 값은 안 만든다 (`decision_unit.py`)
- 서버 검증 → 같은 계산(TripDesk) → **8 의 같은 묻기 판정 · 같은 반영** → 9
- 질문은 일정 그대로, 규정 · 일정 사실로 답

### 12. 새벽 영업 확인 — [코드] (03~08시, Google)
- 그날 식사 · 활동 영업 확인 → 닫힌 곳은 근처 대체 → 8 의 묻기 판정 · 반영(`apply_or_ask`) → 9

### 루프 정리
① 등록 거절 → 고쳐서 다시 제출 · ② 에이전트 안 후보 재점검 · ③ 묻기 → 「바꿔 줘」 → 다시 묻기 · ④ 감시: 여행 기간 동안 작업이 1분마다 다시 돈다(알림이 감시를 부르는 것이 아니다)
