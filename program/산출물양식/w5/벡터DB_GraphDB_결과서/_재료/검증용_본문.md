1. 구축 목적 및 적용 범위
guguroute은 여행 정책의 의미 검색에 벡터DB를 사용하고, 이미 정형화된 업무 관계는 PostgreSQL 재귀 질의로 탐색한다. 별도 GraphDB 제품은 구축하지 않았다. 일정 항목 관계와 이동 경로에는 메모리에 읽은 그래프 구조를 사용한다. 이 결과서는 2026-10-06까지의 코드와 측정 기록을 기준으로 각 방식의 쓰임과 한계를 정리한다.
1.1 문제 정의 및 구축 범위
정책 질문은 표현이 달라도 같은 판단 기준을 찾아야 한다. 반면 일정의 날짜·순서·앞뒤 관계나 도로 연결은 문장 유사도만으로 정할 수 없다. 따라서 정책 문장 검색, 업무 관계 조회, 일정 관계 조회, 이동 경로 계산을 각각 알맞은 구조에 맡겼다.
● 벡터DB: PostgreSQL과 pgvector에 여행 정책 문서의 청크와 임베딩을 저장한다. 실제 여행 코퍼스는 bge-m3의 1024차원 벡터로 적재되어 있다.
● SQL 관계 탐색: GraphStorePort의 SqlGraphAdapter가 기존 표의 FK와 필드를 질의 시점에 노드·간선으로 투영한다. 현재 여행 요청 처리 경로에서는 호출하지 않고 관리 화면과 인트로스펙션에서 구현체를 확인한다.
● 일정 관계 구조: 날짜·순서·앞뒤·같은 장소 관계를 메모리에 구성해 항목을 찾는 방식을 실험했다. 이 실험은 GraphDB 제품의 검색 성능 측정이 아니다.
● 이동 그래프: 파일에서 읽은 도로 그래프와 지하철 역 순서 그래프를 공용 이동 판정 도구가 사용한다. 도로 그래프의 최단경로 계산도 별도 GraphDB 서버를 사용하지 않는다.
에이전트는 요식과 액티비티 둘이다. 이동은 두 에이전트가 함께 부르는 공용 판정 도구다. 요식 · 활동 표에는 벡터 열이 없다. 장소 추천을 벡터 검색으로 한다고 적지 않는다.

그림 1. 저장소와 관계 구조의 역할. 실선은 지금 쓰는 길, 점선은 실험 단계이거나 여행 요청 경로 밖인 길이다.
1.3 벡터DB와 그래프는 각각 어디에 쓰는 것이 좋은가
결론: 문장 뜻으로 찾는 일은 벡터 검색이, 순서 · 연결을 따지는 일은 관계 구조가 낫다. 다만 지금 규모에서는 둘 다 PostgreSQL 하나와 프로세스 메모리로 충분해서 별도 그래프DB 제품은 들이지 않았다.

2. 벡터DB/GraphDB 기술 설계 명세
2.1 벡터 데이터베이스 설계
여행 정책 검색은 bge-m3로 적재한 1024차원 열을 사용한다. OpenAI용 1536차원 열도 스키마에 남아 있으나 여행 청크에는 값이 없다. 제공자 설정과 적재된 열이 맞지 않으면 검색기가 오류를 낸다.
항목 | 명세 | 선정 근거 및 한계
저장소 | PostgreSQL + pgvector | 문서·메타데이터·벡터를 같은 DB에서 관리한다.

거리·점수 | 코사인 거리 <=>, 점수 1 - 거리 | 문장 벡터의 유사도를 정렬에 사용한다. 점수는 정답 확률이 아니다.

2.2 그래프 관계 탐색 설계
GraphDB에 해당하는 별도 제품·전용 노드 표·전용 간선 표는 없다. SqlGraphAdapter가 기존 관계형 표를 JOIN하고 WITH RECURSIVE로 순회한다. GraphStorePort는 neighbors, path, subgraph를 제공한다.
구성 | 구현 내용 | 주의 사항
노드 | 고객, 사건, 사건 이벤트, 실행 요청, 승인, 정책 문서·청크 | 기존 행의 식별자를 사용한다. issue와 team은 필드 값을 노드 식별자로 투영한다.
기본 간선 | owns, has_event, proposed, approved, contains, in_document | FK와 JOIN 결과를 질의 시점에 간선으로 구성한다.
이슈 관계 | has_issue, governed_by, handled_by | governed_by는 intent와 scope의 문자열 일치다. 의미적 정책 적합성을 검증하지 않는다.
처리팀 관계 | 이슈와 과거 처리팀 연결 | 담당 선언이 아니라 처리 이력을 나타낸다. 이력이 없으면 관계도 없다.
근거 경로 | has_evidence, references_chunk, references_document | 사건 이벤트의 evidence에서 청크·문서로 연결한다.
제약 | 기존 PK·FK·유일성 제약, 테넌트 필터, 깊이 제한 | neighbors는 깊이로 재귀를 제한한다. path는 방문 경로를 사용해 순환도 제한한다.
호출 범위 | 관리 화면·인트로스펙션에서 구현체 확인 | 여행 요청의 정책 검색이나 일정 변경에 결합된 하이브리드 검색으로 설명하지 않는다.
별도 GraphDB 도입 | 정확도·비용·p95 채택 관문 통과 시 검토 | 수치 문턱과 제품 간 비교 실험은 [미확보].

벡터DB는 정책 근거를 의미로 찾는 데 적합하다. SQL 관계 탐색은 사건과 실행·근거의 연결 이력을 확인하는 데 적합하다. 날짜·순서가 명확한 작은 일정은 메모리 관계 조회로 충분하고, 이동 거리에는 도로 연결을 따르는 최단경로가 적합하다. 이 판단은 과제별 기록에 근거한 배치 판단이며 DB 제품 간 우열 결론이 아니다.
2.3 비정형 데이터 및 메모리 관리 구조
여행 정책 원문은 knowledge/travel의 Markdown과 manifest.json에서 관리한다. DB에는 문서 정보, 청크 본문, 메타데이터와 벡터를 저장한다. 메타데이터에는 문서 식별자, 범위, 버전, 개인정보 등급, 효력 시작일, 절 제목, 청크 번호가 들어간다.
여행별 대화는 PostgreSQL의 trip_chat_turns에 추가 방식으로 저장한다. 고객 문장은 개인정보를 가린 뒤 기록하며, 해석에는 최근 6턴을 조회한다. 프롬프트용 대화 길이 기준은 턴당 160자다. 이 값들은 2026-10-06 확인한 코드 설정값이며 성능 측정값이 아니다.
도로 그래프는 파일에서 프로세스 메모리로 읽는다. 현재 GraphRouter.default는 v2 파일이 있으면 v2를, 없으면 v1을 선택한다. 따라서 코드에 v2 지원이 있다는 사실과 특정 서버에서 v2 자료를 사용한다는 사실을 구분해야 한다.

3. 검색 성능 및 정확도 검증 결과
별도 GraphDB 제품과 벡터DB를 같은 데이터·질의·장비에서 비교한 성능 기록은 없다. 확인한 비교는 정책 벡터 검색의 색인 표현, 일정 항목 판정의 메모리 관계 구조와 임베딩 방식, 도로 그래프와 직선 거리 방식이다. 서로 다른 과제의 정확도와 시간을 한 순위로 합치지 않는다.

3.2 검색 실패 시 대응
● 근거 문턱 미달: 채팅 정책 답은 상위 3개 중 점수 0.55 이상 후보만 사용한다. 맞는 근거와 일정 사실이 없으면 찾지 못했다고 답하고 가능한 요청을 안내한다. 고객 건을 사람의 응답 대기로 넘기는 방식으로 설명하지 않는다.
● 검색 오류: 검색기가 없거나 예외가 나면 질문에 답하지 못한 이유를 알리고 일정을 바꾸지 않는다. 코드의 escalated 상태는 시스템 결함 기록으로 구분한다. 사람은 오류 리포트를 확인하며 고객 답변을 대신 처리하는 역할로 쓰지 않는다.
● 제공자·적재 불일치: 선택한 제공자의 벡터 열이 비어 있으면 검색기가 예외를 낸다. 다른 열로 자동 전환했다고 적지 않는다. 제공자별 적재 상태를 확인해야 한다.
● 현재 값 확보 실패: 결정 15는 1차 소스 실패 시 대체 소스를 쓰고 대체까지 실패하면 서버를 끈다는 원칙이다. 정책 문서나 LLM 지식으로 모르는 값을 채우지 않는다.
값을 끝내 못 얻을 때 서버를 끈다는 원칙 가운데 지금 코드에서 확인한 것은 세 가지다. 시작할 때 조립이 잘못되면 시작을 거부하고, 배치 작업은 실패로 끝내고, 요청 처리 중이면 치명 상태로 기록한다. 요청 처리 중에 서버 프로세스를 끄는 동작은 확인하지 못했다(코드 검색 범위: 결정 적용 경로 실측 기록과 해당 모듈).

4.2 시나리오 기반 데이터 이동 경로
예시 요청은 '비가 와서 야외 활동을 못 하게 됐어요. 다음 식사 장소까지 갈 수 있나요?'다. 정책 근거와 현재 상황을 각각 확인하고, 근거와 값이 확보된 범위에서 답한다.
● 1. 요청 해석: 여행 일정과 최근 대화를 조회해 언급한 활동·식사 항목을 찾고 필요한 판정 작업을 정한다.
● 2. 정책 근거 조회: 문제에 필요한 여행 범위로 search_policy를 호출한다. 날씨·활동·식사·이동 정책의 판단 기준을 찾는다.
● 3. 현재 값 확인: 날씨와 장소 운영 정보 등은 외부 소스에서 확인한다. 정책 문서의 오래된 값으로 대체하지 않는다.
● 4. 분야별 판정: 액티비티는 야외 일정 가능성과 변경 조건을, 요식은 식사 일정의 조건을 판정한다. 두 에이전트는 필요할 때 공용 이동 판정 도구를 호출한다.
● 5. 이동 계산: 이동 도구는 도로·역 순서 그래프와 확보한 운행 정보를 사용한다. 로컬 도로 그래프와 GraphHopper 등 대체 경로는 출처를 구분한다.
● 6. 응답·기록: 근거 출처와 판정 결과를 답에 반영하고 대화·사건 이력을 기록한다. 값을 끝내 못 얻으면 임의로 변경하지 않고 실패 사유를 알린다.
이 흐름에는 SqlGraphAdapter의 관계 탐색이 포함되지 않는다. 업무 관계를 점검하는 SQL 그래프 기능과 실제 여행 요청에서 쓰는 정책 검색·이동 그래프를 구분한다.
시나리오는 코드와 자료의 역할을 설명하기 위한 예시다. 이 문장 전체를 입력한 종단 시험의 결과·성공률은 [미확보].
