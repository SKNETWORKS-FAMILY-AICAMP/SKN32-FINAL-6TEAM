## 사용자 요구
- 오늘까지의 프로젝트 내용으로 쓴다. **벡터DB와 그래프DB를 각각 어디에 쓰는 게 좋은지 점검**한 내용을 넣는다. **그래프DB와 벡터DB 성능 비교 기록**을 넣는다.

## 지켜야 할 사실 · 결정
- 별도 그래프DB 제품(Neo4j · AGE)은 없다. 관계 탐색은 PostgreSQL 재귀 질의(SqlGraphAdapter), 벡터는 pgvector. 그래프DB 제품과 벡터DB를 **제품끼리 비교한 성능 기록은 없다** — 이것을 숨기지 말고, 대신 있는 비교(일정 질문에서 그래프 구조 방식 vs 임베딩 방식 — §15-4 · §41 · §54-2, 도로 그래프 vs 직선 거리, 정책 코퍼스 벡터 검색 · 색인 비교, 검색기 비교 §89-2)를 「무엇을 무엇과 비교했는지」 정확히 적는다. 「그래프」가 DB 가 아니라 메모리 관계 구조인 곳은 그렇게 쓴다.
- SqlGraphAdapter 는 여행 요청 경로에서 부르지 않는다(관리 화면 · 인트로스펙션만) — 사실대로.
- 색인 E 는 코드에 아직 안 들어갔다.
- 쇼핑몰(커머스) 시절 자료 · 숫자는 쓰지 않는다(D-023). 양식 예시 값(K-culture · MySQL · Cypher · 0.89 등)도 쓰지 않는다. LangGraph · S3 · Neo4j 를 쓴다고 적지 않는다.
- 고객 건을 사람에게 넘기지 않는다(사람은 오류 리포트만) — 양식 「Human-in-the-loop」 자리는 이 결정에 맞게(예: 근거가 문턱 미만이면 「모른다」고 답하고 기록, 고객에게 다른 질문을 권함 등 실제 동작만).
- 값을 모를 때는 대체 소스, 대체까지 안 되면 서버를 끈다는 결정(결정 15)이 있다.
- 에이전트는 요식 · 액티비티 둘, 이동은 모두가 부르는 공용 판정 도구.
- 수치는 분자/분모 · 날짜 · 1회 측정 여부를 함께. 낙관적 세트 · 블라인드 세트 구분. 모르는 것은 `[미확보]`.
- 문장은 쉬운 한국어, 결론 먼저. 금지 문자: 줄표(—, –), 별(★☆), 체크(✓✔), 말줄임표(…). 화살표 「→」는 써도 된다.

## 블록 형식
절 다섯 개의 블록 목록. 블록 종류:
- `["h", "1.1 문제 정의 및 구축 범위"]` 소제목
- `["p", "문단"]`
- `["b", "라벨:", "글", 0]` 글머리표(0 또는 1단계)
- `["t", ["머리1","머리2",…], [["칸",…],…], [비율,…]]` 표
- `["fig", "그림ID", "캡션"]` 그림 자리(그림은 Claude 가 만든다 — 아래 figures 에 데이터를 준다)
- `["code", "머리글(파일:줄)", "코드 발췌 원문 10~30줄"]` — 실제 파일에서 그대로 옮긴다
- `["note", "출처 · 주의 작은 글"]`

## 출력 JSON
{"sections": [[블록…], [블록…], [블록…], [블록…], [블록…]],
 "figures": [{"id": "fig_…", "kind": "bar|hbar|table", "title": "…", "data": {...}, "source": "경로"}],
 "doubts": ["확인 못 한 것"]}
그림은 2~4개(예: 검색 재현율 운영 vs 색인 E, 그래프 문지기 vs 임베딩 앞단, 도로 그래프 오차 비교, 저장소 역할 구분도). 「5. 구축 결과」의 캡처 자리는 `["fig","cap_…", "…"]` 로 무엇을 찍으면 좋을지만 적어라(실제 DB 조회 결과 예시 텍스트가 있으면 code 블록으로).
