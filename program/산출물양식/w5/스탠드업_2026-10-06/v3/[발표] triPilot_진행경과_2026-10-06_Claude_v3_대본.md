# guguroute 5주차 스탠드업 v3 대본 (Claude 판)

## 1장

guguroute 5주차 진행 경과를 말씀드리겠습니다. guguroute 은 자유여행자가 이미 짠 여행 계획을 받아서, 여행이 끝날 때까지 문제가 생기지 않는지 지켜보고 바꿔 주는 서비스입니다.

## 2장

오늘은 서비스, 모델, 비용, 검증, 남은 일의 다섯 파트로 말씀드리겠습니다. 장마다 오른쪽 위에 지금 어느 파트인지 표시해 두었습니다.

## 3장

고객이 계획을 올리면 코드가 시간 겹침과 이동 가능 여부를 검사하고 고객이 확인합니다. 등록하면 여행 중 3분마다 휴관, 마감, 날씨 위험을 점검하고, 문제가 생기면 식당 · 활동 담당 AI 가 바꿀 안을 만들어 알립니다. 이 점검과 수정은 여행이 끝날 때까지 되풀이됩니다. 이번 주에는 화면 연결, 실시간 진행 표시와 개인 AI 입구, 고객 말을 일정 항목에 매칭하는 모델을 다뤘습니다.

## 4장

한 주 규모입니다. 모든 브랜치를 합쳐 커밋 531건이었고 10월 3일이 112건으로 가장 많았습니다. 고객 웹 화면 12개를 연결했고, 자동 시험은 4,251개 중 4,245개를 통과했습니다. 일정 항목 매칭 모델은 파인튜닝으로 688개에서 760개까지 맞혔고, 산출물은 6종을 만들었습니다.

## 5장

고객은 계획을 붙여 넣고, 읽는 동안 취향 질문에 답하고, 항로 지킴이를 켤지 고릅니다. 항로 지킴이는 문제가 생기면 서비스가 먼저 바꿔 두고 알릴지, 먼저 물어볼지를 정하는 스위치입니다. 계획을 확인한 뒤 여행 중에는 일정, 지도, 채팅을 쓰고, 재난 문자가 오면 남은 일정을 멈추고 안전 안내를 보여 줍니다. mock 서버로 화면 반응을 확인했고, 실서버 확인은 계획 확인 화면 일부만 했습니다.

## 6장

서버 쪽은 두 가지가 컸습니다. 고객이 평소 쓰는 AI 비서가 guguroute 에 들어와 본인 여행만 읽을 수 있고, 고치는 기능은 기본으로 꺼 두었습니다. 오래 걸리는 일을 하는 동안에는 몇 단계인지와 살아 있다는 신호를 3초마다 보내서, 고객이 멈췄는지 기다리는 중인지 알 수 있게 했습니다.

## 7장

모델이 푸는 문제는 하나입니다. 고객이 한 말이 일정표의 몇 번 항목을 가리키는지 찾습니다. 금요일 전시를 물은 뒤 「뒤에 거 예매해야 돼」라고 하면 정답은 25번 피크닉 전시이고, 일정에 없는 남산타워를 물으면 정답은 없음입니다. 이걸 맞혀야 그 장소의 영업시간이나 예약을 확인하고 바꿀 수 있습니다.

## 8장

약 4B 크기의 Gemma 4 E4B 를 우리 연습문제로 파인튜닝하니 688개에서 750개, 다시 학습하면 760개를 맞혔습니다. 파인튜닝하지 않은 26B, 27B 로컬 모델이 732개, 749개라서, 작은 모델로 큰 모델만큼 맞힌 셈입니다. 다만 같은 방법으로 두 번 학습해도 10문제쯤 흔들리기 때문에 4B 모델끼리 순위는 매기지 않습니다. CPU 만으로도 이어지는 질문은 평균 4.5초에 답합니다.

## 9장

파인튜닝은 이렇게 했습니다. 사람이 처음 문제와 체크리스트를 쓰고, Claude 가 이를 바탕으로 여행자 10명의 일정과 연습문제 1,760개를 만들었습니다. 별도 풀이로 정답이 모두 일치하는지 확인하고, 시험 문제와 같거나 비슷한 122개를 뺀 뒤, 여행자 8명 몫 1,313개로 학습하고 다른 2명 몫 325개로 검증했습니다. Gemma 4 E4B 를 4비트로 올려 QLoRA 로 2 epoch 학습했고, 설정은 평가를 보기 전에 하나로 고정했습니다. 검증 세트에서 265개에서 320개로, 시험지에서 688개에서 750개로 올라 미리 정한 기준을 통과했고, 시드만 바꿔 다시 학습한 760개, CPU 용 8비트 파일로 바꾼 748개도 확인했습니다.

## 10장

시험은 네 가지입니다. A, B, C 는 같은 835문제를 채점 기준만 바꾼 것입니다. 한 문장에 일정 둘을 묻는 질문을, A 는 먼저 말한 항목만, B 는 하나라도 맞으면, C 는 둘 다 맞혀야 정답으로 봅니다. D 는 실제 채팅처럼 일정 질문 사이에 관광지 질문, 일상 대화, 구어체를 섞은 2,735문제입니다. 파인튜닝한 Gemma 4 E4B 는 769문제 750~760개, B 채점 816~826개로 26B, 27B 로컬 모델보다 높았고, C 에서는 항목을 하나만 내는 구조라 상용 모델보다 낮습니다. D 는 지금 우리 모델만 쟀고 다른 모델은 측정을 맡겨 두었습니다.

## 11장

상용 모델 점수는 자기가 낸 문제까지 푼 것이라, Codex 가 쓴 문제에서는 Codex 를, Claude 가 쓴 문제에서는 Claude 를 빼고 다시 셌습니다. 그래도 상용 모델이 가장 높았습니다. 문제는 비용입니다. 서버는 어차피 우리가 확보해야 하는데, 상용 API 를 쓰면 한 달 5~10만원이 더 들고, RunPod 는 24만원 고정입니다. 오라클 무료 서버는 2 CPU, 12GB, 월 10TB 트래픽까지 0원이라, 파인튜닝한 작은 모델을 여기서 얼마나 감당할 수 있는지 지금 재고 있습니다.

## 12장

금액은 이렇게 나왔습니다. API 한 건은 질의 1,700토큰과 답 12토큰에 공개 단가를 곱한 값으로 Luna 0.25원, Sol 4.93원, Astra 24.64원이고, API 를 써도 앱 서버가 필요해 월 5.4만원이 더해집니다. RunPod 은 월 24.5만원 고정에 한 대가 하루 약 4만 건을 처리합니다. 오라클 무료 서버는 0원인데 하루 약 2,500건까지로 예상하고 지금 실제로 재고 있습니다. 그래서 하루 2,500건까지는 무료 서버가 가장 싸고, 그 위로는 Sol 기준 하루 1,300건, Astra 기준 260건부터 GPU 서버가 API 보다 쌉니다.

## 13장

결론입니다. 질문이 적을 때는 무료 서버로 운영하되, 새 일정의 첫 질문은 무료 서버에서 112초나 걸리므로 처음부터 API 로 보냅니다. 하루 7천 건쯤에서 무료 서버가 차면 넘치는 질문도 API 로 보내고, API 비용이 GPU 서버 월세 24.5만원을 넘는 하루 약 3.8만 건에서 RunPod GPU 서버로 넘어갑니다. GPU 한 대가 차는 5.8만 건부터는 다시 API 로 넘치는 몫을 받다가, 9만 건쯤에서 GPU 를 한 대 늘리는 식으로 반복합니다. 품질을 우선해 Sol 을 쓰면 API 단계가 짧아져 하루 7천 건 남짓에서 바로 GPU 로 넘어갑니다.

## 14장

모델을 여러 단계로 이어 붙이면 좋아지는지 실제로 돌려 봤습니다. 835문제를 넣으면 정해 둔 말 패턴의 규칙이 125개를 바로 처리하고, 작은 분류 모델이 잡담 36개를 걸러서 큰 모델은 674번만 부르면 됩니다. 점수는 혼자 풀 때와 같고 호출은 19% 줄었습니다. 파인튜닝하지 않은 Jev 계열 모델을 라우터로 넣으면 697로 떨어졌지만 학습 조건이 달라 공정한 비교는 아닙니다.

## 15장

실제 채팅처럼 잡담, 관광 질문, 구어체를 섞은 2,735문제로 다시 돌렸습니다. 모델의 생각 모드를 끄니 빈 답 81건이 모두 사라지고 정답률이 90.8%에서 93.6%로 올랐습니다. 이 상태에서는 앞단의 규칙과 분류 모델이 정확도를 더 올린다고 말할 수 없었고, 남는 이득은 큰 모델 호출을 23% 줄이는 것입니다. 제품 호출은 이미 생각 모드를 끄고 있다는 것도 실서버에서 확인했습니다.

## 16장

고객 말에는 꼬리표 네 개를 붙입니다. 무엇을 원하는지, 식당인지 활동인지, 감정은 어떤지, 얼마나 급한지입니다. 이 중 긴급도가 가장 어려웠는데, 학습 없이 지시문만 준 모델은 60.9%였고 우리 문장으로 학습한 작은 분류 모델은 88.4%였습니다.

## 17장

규정 검색입니다. 고객이 창덕궁 임시 휴관이면 어쩌죠라고 물으면 운영 중단 규정의 임시 휴관 절을 찾아야 합니다. 지금은 정답 규정이 상위 3개 안에 드는 비율이 62.5%로 목표 90%에 못 미칩니다. 개선안을 두 가지 시험했습니다. 첫째, 규정을 찾을 때 비교하는 글을 고객용 문장으로 바꾸면 정답은 늘지만 예약 요청 같은 말에도 규정을 붙이는 오응답이 22%에서 37%로 늘었습니다. 둘째, 후보 20개를 다시 줄 세우는 재순위는 따로 둔 보류 세트에서 92.6%로 목표를 넘었고, 지금 제품 반영을 준비하고 있습니다.

## 18장

사람이 직접 35행을 검수했습니다. 원문, 답, 근거를 보고 맞다, 중간, 틀리다로 판정했고, 기계 의견은 판단 보조로만 썼습니다. 기계 검사와 사람 판정은 19개 중 18개가 같아서 기계 검사를 믿을 만하다는 것을 확인했습니다. 어긋난 한 건은 답의 앞뒤 문장이 서로 모순되는 결함이었는데, 정답 줄 검사로는 잡을 수 없는 문제라 검수에서 찾아 제품 문구를 고쳤습니다.

## 19장

평가 지표는 공개 벤치마크와 논문 기준에 맞춰 우리 서비스에 맞는 것을 골랐습니다. 규정 검색은 고객에게 실제로 보이는 두 줄 기준의 Hit@2 와 Recall@3, 답할지 거절할지는 선택적 위험, 근거는 문장 일치와 숫자 보존, 분류는 네 꼬리표 동시 정답과 보정, 에이전트는 같은 일을 세 번 모두 맞히는 pass^3, 지연은 p95 로 봅니다. 모든 비율에는 95% 구간을 붙이고, 두 방법 비교는 같은 질문끼리 짝지은 McNemar 검정으로 했습니다.

## 20장

상용화 기준을 정리했습니다. 양식과 계획서에 정해진 기준은 응답 15초, 규정 검색 90%, 결정 단위 95%와 엉뚱한 변경 0건, 지어낸 값 0건입니다. 나머지는 틀렸을 때 고객이 입는 손해를 기준으로 제안했습니다. 일정을 잘못 바꾸거나 금액을 바꾸는 것처럼 되돌리기 어려운 일은 0건, 답의 정확도는 90~95%입니다. 지금 넷은 기준을 넘었고, 규정 검색은 개선안을 제품에 넣으면 넘으며, 여섯은 아직 미달입니다. 그리고 이 모든 값은 사람이 쓴 실제 질문에서, 구간의 아래 끝으로 기준을 넘어야 상용화라고 봅니다.

## 21장

이번 주에 고친 것이 넷입니다. 번역 금액 단위 대조를 제품에 넣었고, 사람 검수로 찾은 문구 모순을 고쳤고, 무료 서버 처리량을 쟀고, 빈 답 문제는 제품 호출이 이미 생각 모드를 끄고 있어 생기지 않는다는 것을 실서버에서 확인했습니다. 남은 다섯은 오응답 실제 경로 측정, 재순위 검색의 제품 반영, 엉뚱한 일정 변경을 막는 안전장치, 계획 읽기의 글자 오독, 그리고 실서버에서 실제 사용자 흐름 확인입니다.
