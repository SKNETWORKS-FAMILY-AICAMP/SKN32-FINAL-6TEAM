# triPilot 5주차 스탠드업 v4 대본 (Claude 판)

## 1장

triPilot 5주차 진행 경과를 말씀드리겠습니다. triPilot 은 자유여행자가 이미 짠 여행 계획을 받아서, 여행이 끝날 때까지 문제가 생기지 않는지 지켜보고 바꿔 주는 서비스입니다.

## 2장

오늘은 서비스, 모델, 비용, 검증, 남은 일의 다섯 파트로 말씀드리겠습니다. 장마다 오른쪽 위에 지금 어느 파트인지 표시해 두었습니다.

## 3장

고객이 계획을 올리면 코드가 시간 겹침과 이동 가능 여부를 검사하고 고객이 확인합니다. 등록하면 여행 중 3분마다 휴관, 마감, 날씨 위험을 점검하고, 문제가 생기면 요식업 · 액티비티 에이전트가 바꿀 안을 만들어 알립니다. 이 점검과 수정은 여행이 끝날 때까지 되풀이됩니다. 이번 주에는 화면 연결, 실시간 진행 표시와 개인 AI 입구, 고객 말을 일정 항목에 매칭하는 모델을 다뤘습니다.

## 4장

유스케이스입니다. 쓰는 사람은 여행자와, 여행자 대신 일하는 개인 AI 비서 앱, 계획서 링크만 보는 동행자, 그리고 3분마다 일정을 점검하는 시간과 장애 알림을 받는 운영자입니다. 고객 목표는 계획으로 여행 등록하기부터 일정 바꾸기, 생긴 문제 알림, 다른 안 고르기까지 12개이고, 여러 유스케이스가 함께 쓰는 하위 기능이 둘 있습니다. 고객 건을 사람 상담원에게 넘기는 유스케이스는 일부러 두지 않았습니다.

## 5장

시스템 구성입니다. 고객은 웹이나 자기 AI 비서로 들어오고, 둘 다 API 하나로 모입니다. API 안에 오케스트레이터와 요식업 · 액티비티 에이전트, 이동 판정이 있습니다. 워커는 3분마다 날씨 · 교통 같은 외부 정보 6종을 확인해 일정이 깨졌는지 보고, 알림을 보냅니다. 모델은 Ollama 의 gemma4:12b 와 임베딩을 쓰고, 저장은 PostgreSQL 과 pgvector 입니다. 이 네 컨테이너가 지금 x600 서버에서 돌고 있습니다.

## 6장

에이전트 구성입니다. 가운데 오케스트레이터는 언어 모델을 쓰지 않는 코드라서 같은 입력이면 늘 같은 순서로 움직입니다. 요식업 에이전트와 액티비티 에이전트는 일정마다 바꿀 초안을 세 개까지 내기만 하고, 그 초안은 다시 오케스트레이터로 돌아와 체크리스트와 이동 판정으로 검증된 뒤에 저장되고 알림이 나갑니다. 이동 판정은 에이전트가 아니라 모두가 부르는 공용 도구입니다.

## 7장

한 주 규모입니다. 모든 브랜치를 합쳐 커밋 531건이었고 10월 3일이 112건으로 가장 많았습니다. 고객 웹 화면 12개를 연결했고, 자동 시험은 4,251개 중 4,245개를 통과했습니다. 일정 항목 매칭 모델은 파인튜닝으로 688개에서 760개까지 맞혔고, 산출물은 6종을 만들었습니다.

## 8장

고객은 계획을 붙여 넣고, 읽는 동안 취향 질문에 답하고, 항로 지킴이를 켤지 고릅니다. 항로 지킴이는 문제가 생기면 서비스가 먼저 바꿔 두고 알릴지, 먼저 물어볼지를 정하는 스위치입니다. 계획을 확인한 뒤 여행 중에는 일정, 지도, 채팅을 쓰고, 재난 문자가 오면 남은 일정을 멈추고 안전 안내를 보여 줍니다. mock 서버로 화면 반응을 확인했고, 10월 7일에 x600 서버에서 서버 응답과 웹 경로 55개, 재난 뒤 패널 문구까지 확인했습니다. 로그인과 여행 만들기 흐름은 아직 확인하지 않았습니다.

## 9장

서버 쪽은 두 가지가 컸습니다. 고객이 평소 쓰는 AI 비서가 triPilot 에 들어와 본인 여행만 읽을 수 있고, 고치는 기능은 기본으로 꺼 두었습니다. 오래 걸리는 일을 하는 동안에는 몇 단계인지와 살아 있다는 신호를 3초마다 보내서, 고객이 멈췄는지 기다리는 중인지 알 수 있게 했습니다.

## 10장

이동 판정은 일정과 일정 사이를 제때 갈 수 있는지 보는 공용 기능입니다. 이번 주에는 앞 일정이 끝난 뒤 출발해서 되는 가장 이른 도착을 계산하게 했고, 지하철과 버스를 섞은 경로를 만들게 했습니다. 실제 길찾기 서비스와 맞춰 보니, 대중교통은 구글보다 중앙값 3.5분 길게 나왔고, 원인은 걷는 속도가 아니라 걷는 거리였습니다. 도로를 따라 재다 보니 출구에서 멀리 돌아가는 경우가 있어, 걷기 거리를 직선의 두 배까지로 막고 다른 출구를 쓰게 했더니 3.0분으로 줄었습니다. 택시는 카카오 미래 길찾기와 12쌍을 비교해 거리 0.92, 시간 1.08, 요금 0.96 배로 거의 맞았습니다. 카카오는 대중교통 공개 API 가 없어서 대중교통은 구글과 비교했습니다.

## 11장

에이전트별로 이번 주 일입니다. 요식업 에이전트는 팀원 작업을 합치면서 서울 음식점 목록을 990곳에서 1,599곳으로 늘렸고, 사업자 등록 자료 15만 곳을 이름 찾기에 쓰게 넣었습니다. 다만 사업자 자료는 실제 폐업과 절반 가까이 어긋나서 폐업 판정에는 쓰지 않습니다. 액티비티 에이전트도 팀 작업 중 나은 것을 반영했고 시험 2,454개를 통과했습니다. 오케스트레이터는 맡을 에이전트가 없을 때 한 번 더 고르게 했고, 그 뒤에 생긴 결함도 고쳤습니다. 계획 읽기는 일정 항목을 빠짐없이 읽는 비율이 97%까지 올랐고, 남은 것은 사진 글자 오독입니다.

## 12장

배포와 서버입니다. 코드를 올리면 GitHub Actions 가 린트와 구조, 단위, 보안 시험을 돌립니다. 배포는 따로 돕니다. x600 서버가 5분마다 팀 저장소의 새 커밋을 확인해서, 바뀐 부분만 새 이미지로 만들고, DB 를 바꾼 뒤 새 판을 띄우고, 30초 동안 지켜봅니다. 컨테이너 넷이 멀쩡하면 성공이고, 아니면 이전 판으로 되돌립니다. 실제로 10월 6일에 DB 변경이 교착으로 실패했지만 서비스는 이전 판으로 계속 돌았고, 고친 커밋으로 다시 반영됐습니다. 서버는 공개 서비스를 돌리는 x600, 무료로 쓰는 오라클 서버, 학습과 채점용 RunPod GPU 세 대, 그리고 IP 에 묶인 도로 통제 API 를 부르기 위한 경유 서버를 확보했습니다. 지금 돌고 있는 서비스는 화면의 주소나 QR 로 바로 열어 보실 수 있습니다.

## 13장

모델이 푸는 문제는 하나입니다. 고객이 한 말이 일정표의 몇 번 항목을 가리키는지 찾습니다. 금요일 전시를 물은 뒤 「뒤에 거 예매해야 돼」라고 하면 정답은 25번 피크닉 전시이고, 일정에 없는 남산타워를 물으면 정답은 없음입니다. 이걸 맞혀야 그 장소의 영업시간이나 예약을 확인하고 바꿀 수 있습니다.

## 14장

약 4B 크기의 Gemma 4 E4B 를 우리 연습문제로 파인튜닝하니 688개에서 750개, 다시 학습하면 760개를 맞혔습니다. 파인튜닝하지 않은 26B, 27B 로컬 모델이 732개, 749개라서, 작은 모델로 큰 모델만큼 맞힌 셈입니다. 다만 같은 방법으로 두 번 학습해도 10문제쯤 흔들리기 때문에 4B 모델끼리 순위는 매기지 않습니다. CPU 만으로도 이어지는 질문은 평균 4.5초에 답합니다.

## 15장

파인튜닝은 이렇게 했습니다. 사람이 처음 문제와 체크리스트를 쓰고, Claude 가 이를 바탕으로 여행자 10명의 일정과 연습문제 1,760개를 만들었습니다. 별도 풀이로 정답이 모두 일치하는지 확인하고, 시험 문제와 같거나 비슷한 122개를 뺀 뒤, 여행자 8명 몫 1,313개로 학습하고 다른 2명 몫 325개로 검증했습니다. Gemma 4 E4B 를 4비트로 올려 QLoRA 로 2 epoch 학습했고, 설정은 평가를 보기 전에 하나로 고정했습니다. 검증 세트에서 265개에서 320개로, 시험지에서 688개에서 750개로 올라 미리 정한 기준을 통과했고, 시드만 바꿔 다시 학습한 760개, CPU 용 8비트 파일로 바꾼 748개도 확인했습니다.

## 16장

시험은 네 가지입니다. A, B, C 는 같은 835문제를 채점 기준만 바꾼 것입니다. 한 문장에 일정 둘을 묻는 질문을, A 는 먼저 말한 항목만, B 는 하나라도 맞으면, C 는 둘 다 맞혀야 정답으로 봅니다. D 는 실제 채팅처럼 일정 질문 사이에 관광지 질문, 일상 대화, 구어체를 섞은 2,735문제입니다. 파인튜닝한 Gemma 4 E4B 는 769문제 750~760개, B 채점 816~826개로 26B, 27B 로컬 모델보다 높았고, C 에서는 항목을 하나만 내는 구조라 상용 모델보다 낮습니다. D 는 지금 우리 모델만 쟀고 다른 모델은 측정을 맡겨 두었습니다.

## 17장

우리가 만든 시험이 제대로 된 것인지 바깥 기준과 대조해 봤습니다. 공개 결정 모델 벤치마크인 JevBench 와 우리 시험에 같이 나오는 원본 모델 14개의 순위를 비교하니 순위상관이 0.92였습니다. 바깥 벤치마크에서 잘하는 모델이 우리 시험에서도 잘했다는 뜻이라, 우리 시험이 엉뚱한 것을 재고 있지 않다는 근거가 됩니다. 다만 점수 크기는 다릅니다. 영어 보드의 4B 상위 모델이 우리 한국어 시험에서는 80% 안팎이라, 보드 점수만 보고 모델을 고르면 안 되고 우리 시험으로 다시 재야 합니다.

## 18장

상용 모델 점수는 자기가 낸 문제까지 푼 것이라, Codex 가 쓴 문제에서는 Codex 를, Claude 가 쓴 문제에서는 Claude 를 빼고 다시 셌습니다. 그래도 상용 모델이 가장 높았습니다. 문제는 비용입니다. 서버는 어차피 우리가 확보해야 하는데, 상용 API 를 쓰면 한 달 5~10만원이 더 들고, RunPod A4000 은 25.6만원 고정입니다. 오라클 무료 서버는 2 CPU, 12GB, 월 10TB 트래픽까지 0원이라, 파인튜닝한 작은 모델을 여기서 얼마나 감당할 수 있는지 지금 재고 있습니다.

## 19장

금액은 이렇게 나왔습니다. API 한 건은 질의 1,700토큰과 답 12토큰에 공개 단가를 곱한 값으로 Luna 0.25원, Sol 4.93원, Astra 24.64원이고, API 를 써도 앱 서버가 필요해 월 5.4만원이 더해집니다. RunPod 은 지금 쓰는 A4000 포드 기준 월 25.6만원 고정이고, 16 vCPU 와 62GB 메모리가 있어 앱 서버까지 같이 올립니다. 3개월이나 6개월을 미리 내면 할인되고, 1년 약정은 RunPod 에 없습니다. 오라클 무료 서버는 0원이고 몰리는 시간 기준 하루 약 700건까지 받습니다. 그 위로는 Sol 기준 하루 약 1,400건, Astra 기준 약 270건부터 GPU 서버가 API 보다 쌉니다.

## 20장

결론입니다. 서버 대수는 하루 평균이 아니라 가장 몰리는 한 시간을 기준으로 정했습니다. 그 한 시간에 하루 질문의 15%가 몰린다고 보고, 그때도 서버를 80%까지만 쓰게 했습니다. 이 기준으로 무료 서버만으로는 하루 약 700건까지 버팁니다. 그 위로는 몰리는 시간에 넘치는 몫만 Luna API 로 보내고, 한가한 시간에는 무료 서버가 다 받습니다. API 비용이 GPU 월세를 넘는 하루 약 4.1만 건에서 GPU 서버를 붙이고, 그 뒤로는 약 10만 건마다 한 대씩 늘립니다. 품질을 우선해 Sol 을 쓰면 하루 5.8천 건에서 바로 GPU 로 넘어갑니다. 서버가 죽었을 때 API 로 넘기는 장치는 cs 개발 세션에 맡겼습니다.

## 21장

모델을 여러 단계로 이어 붙이면 좋아지는지 실제로 돌려 봤습니다. 835문제를 넣으면 정해 둔 말 패턴의 규칙이 125개를 바로 처리하고, 작은 분류 모델이 잡담 36개를 걸러서 큰 모델은 674번만 부르면 됩니다. 점수는 혼자 풀 때와 같고 호출은 19% 줄었습니다. 파인튜닝하지 않은 Jev 계열 모델을 라우터로 넣으면 697로 떨어졌지만 학습 조건이 달라 공정한 비교는 아닙니다.

## 22장

규칙, ML, 임베딩, Jev 계열 모델, 소형 LLM 을 여러 방식으로 조합해 봤습니다. 앞에서 거르기, 자신 없으면 다른 모델로 넘기기, 질문 유형에 따라 전문 모델로 보내기, 학습한 라우터로 고르기까지 여덟 가지입니다. 어느 조합도 단독 최고 모델을 넘지 못했고, 파인튜닝 전 모델을 라우터로 넣은 조합은 오히려 크게 떨어졌습니다. 같은 모델을 시드만 바꿔 다시 학습해도 10문제가 달라지는데, 조합 사이 차이는 그보다 작았습니다. 조합의 이득은 정확도가 아니라 비용입니다. 규칙과 ML 필터가 앞에서 쉬운 문제를 닫아 큰 모델 호출이 19에서 23% 줄었습니다. 그래서 지금 구성은 한 모델에 모두 맡기지 않고, 기능마다 가장 잘하는 것을 붙인 파트별 구성입니다. 고객 말 분류는 학습한 인코더, 항목 매칭은 파인튜닝 Gemma 4 E4B, 규정 검색은 임베딩과 재순위, 잡담은 규칙과 ML 필터입니다. 이 넷을 한 흐름으로 이어 재는 시험은 아직이라 맡겨 두었습니다.

## 23장

실제 채팅처럼 잡담, 관광 질문, 구어체를 섞은 2,735문제로 다시 돌렸습니다. 모델의 생각 모드를 끄니 빈 답 81건이 모두 사라지고 정답률이 90.8%에서 93.6%로 올랐습니다. 다만 이것은 시드 하나의 값입니다. 같은 방법으로 시드만 바꿔 학습한 세 모델은 93.7%, 85.6%, 90.9%로 크게 갈렸고, 갈린 곳은 일정과 무관한 말을 「없음」으로 거르는 부분이었습니다. 이 상태에서는 앞단의 규칙과 분류 모델이 정확도를 더 올린다고 말할 수 없었고, 남는 이득은 큰 모델 호출을 23% 줄이는 것입니다. 제품 호출은 이미 생각 모드를 끄고 있다는 것도 실서버에서 확인했습니다.

## 24장

고객 말에는 꼬리표 네 개를 붙입니다. 무엇을 원하는지, 식당인지 활동인지, 감정은 어떤지, 얼마나 급한지입니다. 이 중 긴급도가 가장 어려웠는데, 학습 없이 지시문만 준 모델은 60.9%였고 우리 문장으로 학습한 작은 분류 모델은 88.4%였습니다.

## 25장

규정 검색입니다. 고객이 창덕궁 임시 휴관이면 어쩌죠라고 물으면 운영 중단 규정의 임시 휴관 절을 찾아야 합니다. 지금은 정답 규정이 상위 3개 안에 드는 비율이 62.5%로 목표 90%에 못 미칩니다. 개선안을 두 가지 시험했습니다. 첫째, 규정을 찾을 때 비교하는 글을 고객용 문장으로 바꾸면 정답은 늘지만 예약 요청 같은 말에도 규정을 붙이는 오응답이 22%에서 37%로 늘었습니다. 둘째, 후보 20개를 다시 줄 세우는 재순위는 따로 둔 보류 세트에서 92.6%로 목표를 넘었고, 지금 제품 반영을 준비하고 있습니다.

## 26장

사람이 직접 35행을 검수했습니다. 원문, 답, 근거를 보고 맞다, 중간, 틀리다로 판정했고, 기계 의견은 판단 보조로만 썼습니다. 기계 검사와 사람 판정은 19개 중 18개가 같아서 기계 검사를 믿을 만하다는 것을 확인했습니다. 어긋난 한 건은 답의 앞뒤 문장이 서로 모순되는 결함이었는데, 정답 줄 검사로는 잡을 수 없는 문제라 검수에서 찾아 제품 문구를 고쳤습니다.

## 27장

평가 지표는 공개 벤치마크와 논문 기준에 맞춰 우리 서비스에 맞는 것을 골랐습니다. 규정 검색은 고객에게 실제로 보이는 두 줄 기준의 Hit@2 와 Recall@3, 답할지 거절할지는 선택적 위험, 근거는 문장 일치와 숫자 보존, 분류는 네 꼬리표 동시 정답과 보정, 에이전트는 같은 일을 세 번 모두 맞히는 pass^3, 지연은 p95 로 봅니다. 모든 비율에는 95% 구간을 붙이고, 두 방법 비교는 같은 질문끼리 짝지은 McNemar 검정으로 했습니다.

## 28장

상용 모델 Luna 와 Sol 을 우리와 같은 문제, 같은 채점으로 재 봤습니다. 고객 말 분류와 결정 단위에서는 Sol 이 앞섰습니다. 별도 평가셋에서 네 꼬리표를 동시에 맞힌 비율이 우리 43.8%, Luna 55.2%, Sol 67.7% 이고, 결정 단위를 세 번 모두 맞힌 비율은 우리 91.3%, Sol 97.1% 입니다. 규정 재순위는 우리와 Luna 가 92.6% 로 같고 Sol 은 86.8% 였습니다. 대신 Sol 은 한 건에 약 5원이 들고 우리 모델은 우리 서버에서 돕니다. 그래서 분류와 결정 단위는 우리 모델을 더 키울 여지가 있다는 뜻으로 읽고 있습니다.

## 29장

상용화 기준을 정리했습니다. 양식과 계획서에 정해진 기준은 응답 15초, 규정 검색 90%, 결정 단위 95%와 엉뚱한 변경 0건, 지어낸 값 0건입니다. 나머지는 틀렸을 때 고객이 입는 손해를 기준으로 제안했습니다. 일정을 잘못 바꾸거나 금액을 바꾸는 것처럼 되돌리기 어려운 일은 0건, 답의 정확도는 90~95%입니다. 합성 시험으로는 넷이 기준을 넘었지만, 사람이 쓴 실제 질문으로 잰 것은 아직 없어서 상용화 통과라고 말하지는 않습니다. 규정 검색은 재순위가 92.6%지만 구간 아래 끝이 84%라 90% 기준에는 못 미치고, 여섯은 미달입니다. 그리고 이 모든 값은 사람이 쓴 실제 질문에서, 구간의 아래 끝으로 기준을 넘어야 상용화라고 봅니다.
