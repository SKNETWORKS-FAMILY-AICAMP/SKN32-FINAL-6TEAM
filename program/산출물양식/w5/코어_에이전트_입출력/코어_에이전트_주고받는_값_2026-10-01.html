guguroute(final_project_cs) 코드를 직접 읽어 정리 · 2026-10-01 · 읽기만 했고 코드는 바꾸지 않았습니다. 경로는 모두 final_project_cs/ 아래입니다.

먼저 알아 두실 것 다섯 가지
  1. 「코어 → 에이전트 → 코어」 경로를 실제로 타는 것은 감시가 연 처리 건뿐입니다. 고객이 채팅으로 보낸 말(POST /v1/trips/{trip_id}/messages)은 처리 건(Case)을 만들고 분류는 하지만, 코어의 Controller와 에이전트를 거치지 않고 TripDesk가 직접 처리합니다. 이 문서의 2~11장은 감시 건 · POST /v1/cases 경로 기준입니다(고객 채팅 경로는 12장).
  2. 「외부 데이터 6종을 3분마다 수집」은 결정(D-017, 초안)만 있고 코드에는 없습니다. 지금 실제로 도는 것은 1분마다, 앞으로 90분 안에 시작하는 일정 항목을 하나씩 점검하는 방식입니다(trip_watch_cases.py:39, scripts/ops/jobs.py:71-83). 발표 자료의 「3분마다」는 「결정된 설계 · 미구현」으로 고쳐야 합니다.
  3. 「사람 대기 없음」 결정(2026-09-28): 고객에게 「사람이 확인하도록 남겨 두었어요」 문구는 빠졌습니다. 하지만 코드의 상태 이름 escalated는 남아 있고, 감시 건이 escalated가 되면 고객에게 아무 알림도 가지 않습니다(11장). 운영 화면 문구에도 「사람에게 옵니다」가 남아 있습니다(14장).
  4. 숫자 대부분은 근거가 적혀 있지 않습니다. 12,000자 · 90초 · 근거 40건 · 재시도 3번 등. 근거가 있는 숫자는 13장에 따로 모았습니다. 많은 숫자의 원 출처로 적힌 「구현계획서 v5」 파일은 워크스페이스에 없습니다.
  5. 코드에서 문제를 여러 개 찾았습니다(14장). 예: 이동 에이전트의 조회 도구 read.route·read.transit은 구현되지 않아 늘 빈 값입니다.

2. 입구 — 처리 건(Case)이 열리는 곳

처리 건(Case)이란: 고객 문의나 시스템이 찾은 사건 한 건입니다. DB 표 customer_cases에 한 줄로 저장되고, 상태(status)가 12종 중 하나로 바뀌어 갑니다. 상태가 바뀔 때마다 case_events에 기록이 쌓입니다(지우지 않음).

입구정확한 이름하는 일코어·에이전트를 거치나
감시trip_watch_cases.py · TripWatchCaseOpener.tick앞으로 90분 안에 시작하는 항목을 점검해, 깨졌으면 open_case(labels=…)로 시스템 처리 건을 열고 run_case를 부릅니다. 무엇이 문제인지 이미 알아서 LLM 분류를 하지 않습니다(분류 값을 고정해 넣음). 같은 여행 · 항목 · 원인이면 같은 처리 건으로 모입니다(요청 id watch:{trip}:{item}:{지문}).예
일반 처리 건 APIPOST /v1/cases (app/presentation/api/cases.py:120)처리 건을 열고, 응답을 먼저 보낸 뒤 뒤에서 run_case를 돌립니다(접수에서 실행까지 실측 20~51초라 기다리게 하지 않으려고).예

주기: 감시와 「멈춘 처리 건 되잡기」(routing_sweeper)는 같은 작업(scripts.run_sweepers --once)으로 1분마다 돕니다(scripts/ops/jobs.py:71-83, 윈도우 작업 스케줄러 /SC MINUTE /MO 1). 근거 있음 「주기는 안전이 아니라 복구 지연을 정한다」(jobs.py:8). 90분 앞을 보는 값은 근거 없음.

되잡기(routing_sweeper): 담당이 정해지지 않은 채(routing) 10분(routing_stuck_after_seconds: 600) 넘게 멈춘 처리 건을 한 번에 최대 50건 다시 돌립니다. 600초는 근거 있음 「실행이 원래 수십 초 걸려 짧게 잡으면 정상 실행을 되잡아 같은 건을 둘이 돌린다」.

5. 근거 묶음 ContextPack과 그것을 만드는 ContextBroker

ContextBroker란: 에이전트에게 줄 상태와 근거를 12,000 토큰 안에 정해진 규칙대로 잘라 묶는 부품입니다(app/core/context.py). 답을 만들지는 않습니다. 코어가 ContextInputs(재료)를 주면 build()가 ContextPack(묶음)을 돌려줍니다.

build()가 하는 일 (context.py:199-280)

  1. 자르면 안 되는 것부터 셉니다: 지시문(system_instruction, 지금은 고정 문장 "Answer using the supplied evidence.")과 처리 건 상태(current_state). 토큰은 tiktoken cl100k_base로 실제로 셉니다(「글자 수 ÷ 4 같은 어림은 예산 초과를 조용히 통과시킨다」). 지시문 1,800 · 상태 2,400 토큰을 넘으면 자르지 않고 오류를 냅니다.
  2. 잘라도 되는 네 칸을 각자 예산에 맞춥니다: 도구 사실(2,400 · 최신순 · 중복 제거) · 규정 조각(3,600 · 점수 높은 순) · 지난 대화(1,200) · 비슷한 사례(600). 뺀 것은 omissions에 이름을 남깁니다.
  3. 규정 조각을 근거로 바꿉니다: Evidence(source_type="policy", source_id="{문서}#c{조각}", confidence=점수). 전체 근거는 40건까지.
  4. 근거가 모자란지 판정(degraded): 규정 검색이 실패했거나, 규정이 필요한 일감인데 0건이면 degraded=True. 여행 일정 관리(*.itinerary)는 규정이 필요 없는 일감으로 정해져 있어 0건이어도 괜찮습니다.

6. 에이전트 안에서 일어나는 일

execute(task)란

에이전트(팀)마다 하나씩 있는 「일감을 받아 결과를 돌려주는 함수」입니다. 부르는 사슬:

  1. Controller.run_case가 asyncio.wait_for(self.team_executor.execute(task), timeout=90)으로 부름(controller.py:299)
  2. LocalTeamExecutor.execute(app/core/remote_team/executor.py:22-31)가 registry.get(team_id)로 에이전트를 찾고, 일감의 도구 목록이 에이전트 등록 범위 안인지 확인한 뒤(ToolScopeViolation) 에이전트의 execute(task)를 부름
  3. 에이전트의 execute: 먼저 _guard로 검사 → 일감 종류가 *.itinerary · *.itinerary_question이면 공통 run_itinerary(task), 아니면 에이전트별 다른 갈래

_guard — 시작 전 검사 세 가지 (_base.py:49-65)

순서검사걸리면
1일감의 team_id가 내 이름이 아님다른 팀으로 넘김(handoff) — 단, 코어는 이 값을 처리하지 못합니다(14장)
2내가 지원하지 않는 capabilityunsupported_capability로 escalated
3근거 묶음이 깎임(degraded)degraded_context로 escalated

run_itinerary(task) — 일정 관리 공통 순서 (itinerary_team.py:88-135)

  1. read.itinerary {trip_id: subject_ref.id}로 지금 일정 판(여행 + 항목 전체)을 읽음. 없으면 unknown_여행 일정
  2. 판단 시각 = 요청 시각 또는 trigger.at, 둘 다 없으면 지금(한국 시각)
  3. trigger_source == "schedule"(감시 건)이면 → handle_trigger()(에이전트별, 8장)
  4. 아니면 신고 종류를 정함: 요청 type → 없으면 interpretation.report.type → 없으면 read.customer_report로 문장에서 뽑음. other면 report_not_understood
  5. 종류별 갈래: question → _answer_question(규정 답) · change → _change(다른 곳으로 바꾸기, plan_swap) · rollback → _rollback(옛 판으로) · 그 밖(delay 늦음 · closed 휴무 · stock_out 품절) → handle_report()(에이전트별)
  6. 계산 결과를 settle()이 결과(TeamResult)로 바꿈(9장)

결과 양식이 스스로 막는 것 (contracts.py:244-295)

  • 답(answer)이 있는데 근거(evidence)가 없으면 거부 — 「근거 없는 답변 금지」
  • 승인이 필요한 제안이 있으면 다음 할 일은 반드시 wait_for_approval — 「에이전트는 승인 없이 실행하지 않는다」
  • 제안의 근거 번호는 같은 결과의 근거 안에 있어야 함
  • respond면 답 필수 · escalate면 이유(failure_code나 warnings) 필수 · wait_for_input이면 받을 모양 필수 · handoff면 넘길 일감 필수

10. 코어가 결과를 반영 — Controller._apply_result() → _event_for_result()

결과 반영은 처리 건 상태 바꾸기 · 기록 · 알림 넣기를 한 묶음(트랜잭션)으로 합니다. 유일한 문은 transition_case()(app/core/transition.py)이고, 판 번호가 맞을 때만 씁니다.

respond + 승인 없는 제안 — 감시 건이 일정을 바꾸는 길

  1. _reject_unverified() — 제안을 사실과 대조. 근거 묶음이 깎였으면 막음(degraded_context_blocks_action). 제안의 값을 고객 번호 조건으로 DB에서 다시 읽어 대조: trip_id → trips, booking_id → bookings, 인원 ≤ 정원 등. 일정 칸(base_version · replacements 등)은 여기서 안 보고 적용기가 적용하는 순간 봄. 어긋나면 action_proposal_verification_failed.
  2. _apply_auto_proposals() — 제안 전부를 한 묶음(savepoint)으로 적용, 하나라도 실패하면 전부 되돌림.
    • 적용기 찾기: action_handlers["itinerary.apply"] = ItineraryApply(auto_apply=True). 없으면 action_handler_missing
    • risk_level이 low가 아니면 action_requires_approval
    • 중복 방지 키를 서버가 다시 계산 → 이미 성공한 키면 다시 적용하지 않음(replayed)
    • ItineraryApply.apply() 실행(아래)
  3. 성공하면 실행 기록(action_requests, succeeded) · 처리 건 COMPLETED → resolved · 알림 메시지를 같은 묶음에 넣음

ItineraryApply.apply() 단계 (itinerary_actions.py:74-160)

  1. TripStore.latest()로 최신 판을 읽음. 없거나 다른 고객의 여행이면 같은 문구로 거부(있는지도 말하지 않음)
  2. 지금 판이 base_version과 다르면 충돌(ActionConflict → action_target_changed)
  3. 「바꿀까요?」 제안(consent)이면 _ask_consent() — 일정은 안 바꾸고 보류 제안을 열고 묻는 알림만 넣음
  4. 새 항목 목록 만들기: full_items면 그대로, 아니면 replacements로 해당 항목만 갈아 끼움(일정에 없는 항목이면 거부)
  5. refresh_moves_around() — 장소가 바뀐 항목의 바로 앞뒤 이동 항목을 다시 만듦. 시간표 판정기가 있으면 다시 판정, 없고 걸어갈 거리(1,200m, 근거 「초속 1.04m 기준 약 19분」) 안이면 이름만 바꿈, 멀면 직선 어림값
  6. 새 장소가 이 여행의 장소 목록에 없으면 거부(지어낸 장소 금지)
  7. 설문 확인 — _ask_instead(): 고객이 직접 고른 변경(customer_request · rollback · customer_choice)이 아니면 pending.decide()로 판정. 위에서부터 먼저 걸리는 것이 이김: ① 바꾸지 않기로 한 일정(고객 고정 · 잠김 · 예약번호 있음) → 묻기 ② 설문 「먼저 물어봐」 + 지진 · 재난문자 · 기상 「경보」 → 안전 알림 ③ 설문 「먼저 물어봐」 → 묻기 ④ 그 밖 → 적용. 묻기면 일정은 안 바꾸고 보류 제안(pending_changes, 그 일정이 끝나면 만료 · 답 없으면 그대로)과 묻는 알림만 넣음
  8. store.append_version() — 새 일정 판 저장. trips.latest_version을 판 번호 조건으로 올리고 itinerary_versions · itinerary_items에 새 판을 씀. 옛 판은 지우지 않음
  9. 알림 메시지 1건: 주제 trip.notice, 중복 방지 "{trip_id}:v{판}", 내용 = 알림 문구 · 여행계획서 링크 · 판 번호(감시가 바꾼 것이면 「되돌리기」 제안 포함)

그 밖의 갈래

  • wait_for_approval: 사실 대조 → 제안마다 action_requests(status="pending_approval") → waiting_approval. 승인 뒤 코어가 직접 실행(_apply_approved), 바깥 응답이 끊기면 unknown으로 두고 다시 실행하지 않음
  • wait_for_input: 재개 표 발급 → waiting_input
  • escalate: GUARDRAIL_ESCALATED → escalated. 알림 메시지가 붙지 않습니다 — 감시 건이면 고객은 아무것도 받지 않고, 여행계획서 링크는 바뀌지 않은 일정을 보여 줍니다. 운영 화면에 빨간색으로 표시
