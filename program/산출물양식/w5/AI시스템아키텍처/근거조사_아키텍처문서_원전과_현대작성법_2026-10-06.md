# 근거 조사 — 아키텍처 문서의 원전과 현대 멀티 에이전트 작성법 (2026-10-06)

조사일 2026-10-06 · 조사 범위는 5절에 적었다 · 판정은 「맞음 / 일부 맞음 / 틀림 / 확인 못 함」, 근거가 하나뿐이면 「근거 1개」, 1차 자료를 못 열었으면 「2차」.

---

## 1. 한 줄 결론

원전(Perry·Wolf → Kruchten → IEEE 1471/ISO 42010 → Clements·Bass → arc42·C4·ADR)이 한목소리로 요구하는 것은 **「누가 무엇을 걱정하는지(이해관계자·관심사)마다 그림을 따로 그리고, 그림마다 범례를 달고, 결정에는 이유를 붙여라」**이고, 현대 에이전트 자료(Anthropic·OpenAI·Azure·Google)는 **「코드가 경로를 정하면 워크플로, 언어 모델이 경로를 정하면 에이전트」**로 가르므로 — 오케스트레이터가 코드이고 두 에이전트가 언어 모델을 안 쓰는 우리 시스템은 문서에 **「코드가 지휘하는 워크플로 + 규칙형 소프트웨어 에이전트 둘 + 언어 모델 호출 지점 4곳」**이라고 정직하게 적는 것이 원전·현대 자료 양쪽과 맞는다.

## 4. 권고 — 부트캠프 양식 6개 절에 무엇을 넣나

### 4-0. 먼저 정할 것 — 「워크플로 vs 에이전트」를 정직하게 적는 법

우리 시스템을 자료별 정의에 대 보면 이렇다.

| 자료의 정의 | 우리 오케스트레이터 (코드·규칙) | 요식업 · 액티비티 에이전트 (규칙 + 읽기 도구 반복, LLM 안 씀) | LLM 호출 4곳 (보기 고르기 · 계획 읽기 · 번역 · 순서 고르기) |
|---|---|---|---|
| Anthropic 2024 | **워크플로** — 라우팅 패턴 (분류를 코드가 함, 원문이 허용) | LLM 에이전트 아님 | 증강 LLM 의 단발 호출 |
| OpenAI 2025 | 결정적 해법 | **에이전트 아님** (LLM 이 흐름을 안 정함) | 단일 호출 = 에이전트 아님 |
| Azure 2026 | 「결정적 라우팅 · 단순 분배기」 — 권장 경우에 해당 | — | 「직접 모델 호출」 단계 |
| Google Cloud · ADK | **사용자 정의 로직 패턴** · 「워크플로 에이전트」라는 이름의 선례 | 결정적 하위 에이전트 | 단발 호출 |
| Wooldridge·Jennings 1995 | — | **약한 의미의 에이전트에 해당** (자율 · 메시지 · 반응 · 목표 지향) | — |

권고 문구(1절 설계 목표나 2.2 표 위에 한 문단):
- 「본 시스템의 지휘는 **코드(규칙)가 한다**. 업계 분류(Anthropic 2024)로는 **워크플로**, 패턴으로는 **라우팅 + 사용자 정의 로직**이다.」
- 「요식업·액티비티 에이전트는 **규칙형 소프트웨어 에이전트**(고전 정의 Wooldridge·Jennings 1995)이며, **언어 모델이 스스로 경로를 정하는 LLM 에이전트는 아니다**.」
- 「언어 모델은 **정해진 4곳에서만, 정해진 보기 안에서** 부른다. 그래서 끝없는 반복·엉뚱한 경로 같은 LLM 에이전트형 실패가 구조상 생기지 않는다(근거: Azure 의 「결정적인 일에 비결정적 패턴을 쓰지 말라」).」
- 왜 이렇게 골랐는지 근거 문장: OpenAI 의 「에이전트가 맞는 세 경우」에 우리 판정(영업시간·휴무·이동 시간)이 해당하지 않는다 — 규칙이 명확하고 값이 정형이다. 반대로 비정형 글(계획 읽기)·언어(번역)·취향(순서 고르기)에는 LLM 을 쓴다.
- ★양식 예시가 「LangGraph · Recursion Limit 20 · Supervisor GPT-4o」 로 되어 있어도 따라 쓰지 않는다. 쓰지 않는 기술을 적으면 안 된다(루트 기준표 「LangGraph 는 쓴다고 적지 않는다」와도 맞다).

### 4-1. 1절 설계 개요
- **이해관계자 · 관심사 표**(ISO 42010 3.10·3.17): 여행자 · 개인 AI(MCP 로 붙는 쪽) · 운영자 · 심사위원 — 각자 걱정하는 것 한 줄. 이 표가 뒤 그림 목록의 「왜 이 그림이 있나」가 된다.
- **품질 목표 3~5개**(arc42 1절): 예 — 「값을 모르는 채로 안내하지 않는다」「같은 안내를 두 번 보내지 않는다」. 각각 5절 지표와 번호로 이어 둔다.
- **워크플로/에이전트 정직 문단**(4-0).

### 4-2. 2.1 아키텍처 그림
- C4 의 **시스템 맥락 → 컨테이너** 두 단계로 나눈다(한 장에 다 넣지 않는다 — Kruchten 서론의 경고).
- 그림마다 **제목 · 범례**(C4 표기법 + ISO 42010:2022 「뷰 구성 요소는 범례로 설명」 — 독립 근거 2개). 범례에 **「LLM 씀 / 안 씀」 표시를 상자 모양이나 색으로** 넣는다. 이것이 정직 문단을 그림으로 보이는 가장 싼 방법이다.
- 화살표엔 「사용」 대신 **무엇이 오가는지**(「일정 제출(HTTPS)」「도구 호출(MCP)」) 이름표.

### 4-3. 2.2 구성 · 역할 표
- 양식의 「에이전트 명 | 기술 스택 | 역할」에 **「경로를 누가 정하나(코드/LLM)」「LLM 호출 여부·횟수 상한」「쓰는 도구(읽기/쓰기)」** 열을 더한다(Anthropic 의 구분 · Azure 「에이전트마다 작업 난이도에 맞는 모델」).
- 요소는 Perry·Wolf 의 세 종류로 묶으면 표가 정리된다: 처리(오케스트레이터 · 두 에이전트 · 이동 판정 모듈) / 데이터(DB · 장소 목록) / 연결(API · MCP · 바깥함 배달).
- 각 행 책임은 「한 줄 · 동사로」(C4 「key responsibilities」).

### 4-4. 2.3 오케스트레이션 · 상태 관리
- 양식의 「LangGraph State 스키마」 자리에 **Case 상태 기계**(상태 목록 + 전이 조건)를 넣는다 — Clements 의 「동작(behavior) 문서」, Kruchten 의 프로세스 뷰에 해당.
- 「무한 루프 차단」은 Recursion Limit 대신 **우리 코드의 실제 상한**(도구 반복 최대 횟수 · 재시도 횟수)을 적는다. 수치는 코드에서 확인해 넣는다 — 이 조사는 코드를 열지 않았다.
- 동시성 · 멱등 · 바깥함 같은 **결정은 ADR 형식(맥락 · 결정 · 결과)으로 짧게** 표 하나에 모은다(Nygard · arc42 9절 · ISO 42010 5.2.12 — 독립 근거 3개).

### 4-5. 2.4 기술 스택 · 연동
- MCP 는 명세 용어로 적는다: 우리 앱 = **MCP 서버**, 개인 AI 쪽 = 호스트·클라이언트, 우리가 내놓는 것 = **도구**(읽기 · 쓰기). 쓰기 도구가 **기본 꺼짐**인 것은 MCP 명세의 「사람이 도구 호출을 거부할 수 있어야 한다」와 이어서 설명하면 근거가 선다.
- 명세 판(**2026-07-28** 현행)을 적고, 우리 구현이 어느 판에 맞췄는지는 코드로 확인해 적는다(이 조사에서는 확인 안 함).
- A2A 는 **안 쓰면 안 쓴다고** 적는다. 쓸 계획이면 Agent Card 의 「기술(skill)」 항목으로 두 에이전트를 소개하는 정도가 명세에 맞는 모양이다.

### 4-6. 3절 Workflow
- 양식 예시처럼 번호 단계 + **시퀀스 그림 한 장**(Kruchten 시나리오 · arc42 6절 런타임 뷰 · C4 동적 그림 — 세 자료가 같은 것을 요구).
- 대표 시나리오 1개(정상) + 실패 시나리오 1개(외부 API 장애). 단계마다 **[코드] / [LLM]** 꼬리표.
- 감시 루프와 배달 루프를 따로 그린다(서로 다른 시점에 도는 일).

### 4-7. 4절 장애 대응 · 신뢰성 (양식 5개 항목)
- **검색 실패**: 양식 예시의 「정보 부족 메시지 · 사람 개입」은 우리 결정과 **반대다**(값을 모르면 대체 소스 → 안 되면 끈다 · 사람에게 넘기지 않는다). 우리 결정을 적고, Azure 의 「단계적 기능 축소 · 오류를 숨기지 말 것」을 근거로 단다.
- **판단 오류**: MAST 의 「검증 없음·부실」「틀린 검증」을 짚고, LLM 출력은 **정해진 보기 안의 값인지 코드가 검사**한다고 적는다(Azure 「다음 단계로 넘기기 전 출력 검증」 · OpenAI 「출력 검증 · 규칙 기반 보호」).
- **무한 반복**: MAST 의 「같은 단계 반복」「끝낼 조건 모름」 두 실패가 LLM 이 경로를 정할 때 생긴다 → 우리는 경로를 코드가 정하므로 구조적으로 막히고, 남는 반복(도구 루프 · 재시도)은 상한이 있다고 적는다(Anthropic 「최대 반복 같은 멈춤 조건」).
- **외부 API 장애**: 타임아웃 · 재시도 · 회로 차단기 · 대체 소스(Azure 신뢰성 목록 · MCP 「클라이언트는 타임아웃」).
- **출력 검수**: 개인정보 · 근거 없는 문장 금지 · 시각/금액/예약번호는 생성하지 않고 원값 — OpenAI 가드레일 목록에 대어 표로.
- 각 항목을 **Bass 품질 속성 시나리오 한 줄**로 쓰면 5절 지표와 바로 이어진다 — 예: 「(자극원) 장소 API 가 (자극) 30초 응답 없음, (환경) 출발 알림 계산 중, (응답) 대체 소스로 전환, (응답 측정) 알림 지연 n분 이내」. n 은 실측해 넣는다.

### 4-8. 5절 평가 지표 · 목표치
- 양식의 RAGAS · SQL 성공률 예시는 우리 구조와 맞지 않는다. **결정적 부분은 코드 채점기(정답 일치)**, **LLM 4곳은 보기 정답률 + pass^k(k번 모두 같은 답인가)** 로 나눈다(Anthropic evals 2026 — 코드 채점기 우선, pass^k 는 「매번 믿을 수 있나」를 잰다).
- **회귀 평가는 거의 100%** 를 목표로, 능력 평가는 낮게 시작해 올라가는 것으로 구분해 적는다(같은 자료).
- 평가 자료는 **실제 실패에서 뽑은 20~50건** + 「해야 할 때 / 하지 말아야 할 때」 양쪽(같은 자료 · 연구 시스템 글의 약 20건).
- 운영 지표: 도구 호출 수 · 도구 오류 · 실행 시간 · 토큰(Anthropic 도구 글) + Sculley 의 **예측 편향**(LLM 이 고른 보기 분포가 갑자기 바뀌는지) · **행동 한도**(하루 알림 수 상한).
- 목표치마다 **분모와 측정 조건**을 붙인다(Bass 「응답 측정」).

### 4-9. 6절 결론
- arc42 11절처럼 **알려진 위험 · 기술 부채**를 숨기지 않고 2~3줄(예: 대상 도시 1곳, MCP 쓰기 도구 꺼짐).
- 「왜 LLM 에이전트로 만들지 않았나」를 한 문단으로 — Cognition(따로 도는 에이전트는 어긋난 가정을 한다)과 Azure(결정적인 일엔 결정적 패턴)를 근거로. 향후 개선에 「LLM 이 경로를 정할 필요가 생기는 조건」을 적어 두면 문을 닫지 않는다.

| 5 | 대표 시나리오 시퀀스(정상 + 장애 1개), 단계마다 [코드]/[LLM] | Kruchten +1 시나리오 · arc42 6절 런타임 · C4 동적 | 세 자료 | 그림4 멀티에이전트워크플로 v1 |
| 6 | 장애 대응 지도 — 장애 종류 × 감지 × 대응 × 상한 | arc42 10·11절 품질 시나리오·위험 · Bass 품질 속성 시나리오 | arc42 · Bass · MAST · Azure | 그림5 장애대응지도 v1 |
| 7 | (선택) 배포도 — 어느 기계에 무엇이 뜨는가 | C4 배포 · Kruchten 물리 뷰 · Clements 할당 뷰 | 세 자료 | 없음 |

그림마다 캡션 첫 줄에 「이 그림은 ○○ 관점 — △△ 를 걱정하는 사람을 위한 것」을 적으면 ISO 42010 의 「관점이 관심사를 틀 짓는다」를 그대로 따르는 셈이다.
