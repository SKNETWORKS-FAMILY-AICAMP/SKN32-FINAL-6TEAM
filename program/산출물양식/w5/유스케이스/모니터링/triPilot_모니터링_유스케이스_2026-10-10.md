# triPilot 모니터링 유스케이스 명세

작성일: 2026-10-10 · 관점: 여행자와 운영자 · 형식: 사용자 목표 중심의 블랙박스 명세

등록한 여행의 문제를 미리 알아채고 대응하는 여행자 목표와, 감시 상태를 파악하고 시험하는 운영자 목표를 명세한다. 내부 구성요소·처리 기술·버튼 조작은 주 성공 시나리오에 넣지 않는다.

현재 로컬 구현을 기준으로 작성했다. 최근 추가한 예보 주의 안내, 고객·운영 알림 분리, 관리자 감시 현황·로그·한도·시뮬레이션의 x600 서버 배포는 아직 이루어지지 않았다. 이 문서는 실제 운영 성공을 인증하는 결과가 아니다.

| 여행 일정의 변경 | 업체 예약의 자동 변경·취소 |

## 2. 액터와 관심사

| 액터 | 역할·관심사 |
|---|---|
| 여행자 | 헛걸음과 위험을 피하고, 변경 여부에 관한 자신의 선택을 지키며, 최신 일정을 알고 싶다. |
| 운영자 | 감시가 실제 수행됐는지, 무엇을 판단했는지, 실패·변경·정지의 경과가 무엇인지 알고 싶다. |
| 시간 | 정해진 감시 시점에 여행자를 대신해 감시를 시작시키는 주 액터다. |
| 외부 정보 서비스 | 날씨·특보·재난문자·도로·대기질·지진 등 일정 판단에 쓰는 정보를 제공하는 보조 액터다. |
| 고객 외부 알림 채널 | 연결·발송 조건을 충족한 여행자의 안내를 전달하는 보조 액터다. |
| 운영 리포트 채널 | 개발용 Discord 등으로 운영 장애·복구 리포트를 전달하는 보조 액터다. |
| 동행자 | 무대 밖 이해관계자다. 공유한 여행계획서에서 최신 일정을 보고 싶다. |

## 3. 액터–목표 목록과 최상위 요약

UC-M01~09는 이 모니터링 명세의 식별자다. 기존 전체 서비스 UC-01~14를 다시 번호 매긴 것이 아니다. 우선순위·릴리스 순서는 이번 요청에서 정하지 않았으며 기존 팀 결정을 새로 만들지 않는다.

|---|---|---|---|

| UC-M02 | 여행자 | 예보를 고려해 일정을 조정한다 | 완전 |

**최상위 요약:** 여행자는 등록한 여행의 감시를 맡긴다. 시스템은 정해진 시점에 상황을 검증해 주의·문제·안전 위험을 구분한다. 여행자는 안내를 받아 일정을 유지하거나 조정하고, 재난으로 정지된 여행은 안전을 확인한 뒤 재개한다. 운영자는 감시 기록과 한도를 파악하고, 재난 시험과 장애·복구 리포트로 운영 상태를 점검한다. 여행이 종료되면 해당 여행의 정상 감시 대상 기간도 끝난다.

### UC-M01 · 일정 문제를 현장에 가기 전에 알아챈다

| 항목 | 내용 |
|---|---|
| 범위 | triPilot의 등록 여행 모니터링 |
| 수준 | 사용자 목표 |
| 주 액터 | 시간(여행자 대신) |
| 보조 액터 | 외부 정보 서비스 |
| 이해관계자와 관심사 | 여행자: 문제를 방문 전에 알고 싶다. 운영자: 조회 실패를 정상으로 오해하지 않고 처리 경과를 알고 싶다. |
| 사전조건 | 등록된 여행과 감시 대상 장소·시각이 있다. 해당 감시가 대상 기간과 처리 범위에 속한다. |

| 성공 보장 | 대상의 점검 결과가 정상·주의·문제로 구분되어 기록되고, 필요한 안내·변경 대응·안전정지 처리가 시작된다. 정상인 일정은 유지된다. |
| 확장점 | 별도 UML 확장 관계는 정의하지 않는다. 발견한 상황에 대한 대응은 아래 확장에 기술한다. |

**주 성공 시나리오 — 문제가 없는 감시 회차**

1. 시간이 등록된 여행의 감시를 시작시킨다.
2. 시스템이 여행 지역의 안전, 다가오는 방문 일정, 이동·출발 점검 대상을 정한다.
3. 시스템이 대상에 필요한 외부 상황 정보를 얻는다.
4. 시스템이 각 상황이 대상 장소·시각·활동·이동에 영향을 주는지 검증한다.
5. 시스템이 정상 결과와 점검 범위를 기록하고 기존 일정을 유지한다. **이번 회차가 성공 종료된다.**

**확장**

- **2a · 이번 회차에 점검할 대상이 없다.**
  - 2a1. 시스템이 대상이 없다는 결과를 기록한다. **별도 정상 종료한다.**
- **3a · 1차 정보원이 응답하지 않고 대체 정보원이 있다.**
  - 3a1. 시스템이 대체 정보원에서 정보를 얻는다. **4단계로 돌아간다.**
- **3b · 필요한 정보를 대체 정보원까지 얻지 못한다.**
  - 3b1. 시스템이 조회 실패와 확인하지 못한 범위를 기록한다.
  - 3b2. 시스템이 조회 실패를 근거로 일정을 변경하거나 재난 정지를 만들지 않는다. **해당 점검이 실패 종료된다.**
- **4a · 예보 주의 기준에 해당한다.**
  - 4a1. 시스템이 관측한 예보 값과 기존 일정 유지 사실을 여행자에게 안내하고 변경 선택을 제공한다.
  - 4a2. 시스템이 주의 결과와 안내를 기록한다. **주의 안내를 완료하고 종료한다.** 여행자가 조정을 요청하면 UC-M02가 시작된다.
- **4b · 실제 상황이 일정 진행에 영향을 준다.**
  - 4b1. 시스템이 문제와 처리 결과를 기록하고 UC-M03의 변경 정책에 따른 대응을 시작한다. **이번 감시 회차는 문제 발견 결과로 종료한다.**
- **4c · 재난 정지 기준에 해당한다.**
  - 4c1. 시스템이 안전정지를 우선 적용하고 안전 안내를 제공한다. **이번 회차는 안전정지 결과로 종료한다.** 이후 재개는 UC-M04에서 처리한다.
- **4d · 소스가 대상에 적용되지 않거나 연결되지 않았다.**
  - 4d1. 시스템이 해당 없음·미연결을 정상과 구분해 기록한다. **판정 가능한 나머지 대상으로 4단계를 계속한다.**

**기술·데이터 변형:** 방문 점검은 현재 기본값으로 90분 안에 시작하는 항목을 대상으로 한다. 여행 안전 확인은 재난문자·지진을 살피며, 이동·출발 점검은 경로와 출발 상황을 살핀다. 유효한 최근 조회 결과를 사용할 수 있어 점검 건수와 신규 외부 호출 횟수는 같지 않다.

**품질·자율성·빈도:** 자동 수행, 설정 주기 3분. 정상·주의·문제·조회 실패·해당 없음·미연결을 구분한다. 설정 주기는 실제 시각마다 성공 실행됐다는 보장이 아니다.

**미결·운영 확인:** 대체까지 실패할 때의 과거 정책과 현재 오류 기록 동작은 차이가 있다. 이번 명세는 현재 구현을 기술하며 cs 프로젝트 서버의 자동 종료를 약속하지 않는다. x600 서버의 실제 주기 수행은 이번 작업에서 확인하지 않았다.

### UC-M02 · 예보를 고려해 일정을 조정한다

| 항목 | 내용 |
|---|---|
| 범위 | triPilot의 예보 주의 대응 |
| 수준 | 사용자 목표 |
| 주 액터 | 여행자 |
| 보조 액터 | 외부 정보 서비스·고객 외부 알림 채널(발송 조건 충족 시) |
| 이해관계자와 관심사 | 여행자: 예보를 실제 재난으로 오해하지 않고 스스로 변경을 결정하고 싶다. 동행자: 확정된 최신 일정을 보고 싶다. |
| 사전조건 | 감시 대상 활동에 유효한 예보 주의 안내와 조정 제안이 있다. |
| 트리거 | 여행자가 예보에 맞는 일정 조정을 요청한다. |
| 최소 보장 | 예보만으로 일정을 자동 변경하지 않는다. 여행자가 대체 후보를 선택하기 전에는 원래 일정을 유지한다. |
| 성공 보장 | 여행자가 선택한 대안이 재검증을 통과해 최신 일정에 반영되고 변경 결과를 안내한다. |
| 확장점 | 별도 UML 확장 관계 없음. |

**주 성공 시나리오**

1. 여행자가 예보 주의와 원래 일정 유지 안내를 받아 조정을 요청한다.
2. 시스템이 요청한 제안이 현재 일정에 유효한지 검증한다.
3. 시스템이 예보와 여행 조건을 고려한 대체 후보를 찾고 검증한다.
4. 시스템이 가능한 대체 후보를 여행자에게 제안한다.
5. 여행자가 대체 후보 하나를 선택한다.
6. 시스템이 선택 시점의 상황과 전체 일정에 대한 적합성을 재검증한다.
7. 시스템이 선택한 대안과 변경 안내를 확정한다.
8. 시스템이 최신 일정과 선택 결과를 제공한다. **성공 종료한다.**

**확장**

- **1a · 여행자가 기존 일정 유지를 선택한다.**
  - 1a1. 시스템이 제안을 닫고 원래 일정을 유지한다. **유지 선택으로 별도 성공 종료한다.**
- **1b · 여행자가 제안의 유효시간까지 응답하지 않는다.**
  - 1b1. 시스템이 제안을 만료 처리하고 원래 일정을 유지한다. **변경 없이 종료한다.**
- **2a · 일정이 이미 바뀌었거나 제안이 이미 처리됐다.**
  - 2a1. 시스템이 옛 제안을 적용하지 않고 현재 상태를 알려준다. **해당 요청을 종료한다.**
- **3a · 적합한 대체 후보를 찾지 못한다.**
  - 3a1. 시스템이 대체 후보가 없음을 알리고 원래 일정을 유지한다. **변경 목표 미달로 종료한다.**
- **3b · 후보 판단에 필요한 정보를 얻지 못한다.**
  - 3b1. 시스템이 근거 없는 후보를 확정하지 않는다. **변경 실패로 종료한다.**
- **5a · 여행자가 기존 일정 유지를 선택하거나 후보를 고르지 않는다.**
  - 5a1. 시스템이 원래 일정을 유지한다. 유지 선택은 **별도 성공 종료**, 무응답은 유효시간이 지나면 **변경 없이 종료**한다.
- **6a · 선택한 대안이 더 이상 적합하지 않거나 일정 기준이 달라졌다.**

**품질·자율성·빈도:** 최근 주기 실행과 별도 수동 실행을 구분한다. 운영자 조회 시 수행한다. 다음 예정 시각은 실행 완료 보장이 아니다.

**기술·데이터 변형:** 여섯 종류는 예보·기상 특보·재난문자·도로 상황·대기질·지진이다. 화면의 종료 시간 선택은 5·15·30·60분이다. 선택하지 않은 종류와 대체 장소의 실제 검증은 유지한다. 시험 중 실제 일정 내용이 바뀔 수 있다.

**품질·자율성·빈도:** 운영자가 시험 입력을 결정하고 기존 고객 선택 정책을 따른다. 수행자·사유·전후 설정을 남긴다. 운영자 시험 요청마다 수행한다.

**미결·운영 확인:** x600 서버 배포 후 실제 감시와 앱 간 연결 확인이 남아 있다. 시험 종료와 상태 복구는 서로 다른 결과다.

### UC-M09 · 감시 운영의 장애와 복구를 알아챈다

| 항목 | 내용 |
|---|---|
| 범위 | triPilot의 반복 운영 작업 장애·복구 보고 |
| 수준 | 사용자 목표 |
| 주 액터 | 운영자 |
| 보조 액터 | 운영 리포트 채널(개발용 Discord 등) |
| 이해관계자와 관심사 | 운영자: 감시·안내 작업이 계속 실패할 때 알아채고 복구도 알고 싶다. 여행자: 자신의 안내가 운영 리포트 채널에 잘못 전달되지 않기를 바란다. |
| 사전조건 | 반복 운영 작업의 성공·실패가 기록된다. 운영 리포트 전달 경로가 설정돼 있다. |
| 트리거 | 운영 작업의 연속 실패가 보고 기준에 도달한다. 현재 기준은 3회다. |
| 최소 보장 | 고객 외부 알림 미연결을 운영 장애로 만들지 않는다. 보고 전달 실패·보낼 곳 없음도 기록하며 성공으로 처리하지 않는다. |
| 성공 보장 | 운영 장애와 이후 복구에 대한 리포트 전달 결과가 기록되고, 전달 성공 시 운영자가 해당 사실을 알 수 있다. 운영자의 실제 열람까지 보장하지 않는다. |
| 확장점 | 별도 UML 확장 관계 없음. |

**주 성공 시나리오**

1. 시스템이 반복 운영 작업의 연속 실패가 기준에 도달한 사실을 감지한다.
2. 시스템이 실패한 작업과 원인을 포함한 운영 리포트를 준비한다.
3. 운영 리포트 채널이 리포트 전달을 수락한다.
4. 시스템이 운영 리포트 전달 결과를 기록한다.
5. 운영자가 전달된 리포트로 장애를 파악한다. **장애 보고 목표를 달성하고 종료한다.**

**확장**

- **1a · 연속 실패가 기준에 도달하지 않았다.**
  - 1a1. 시스템이 실패 상태만 기록하고 기준 보고를 시작하지 않는다. **보고 없이 종료한다.**
- **1b · 이미 보고한 동일 장애가 계속된다.**
  - 1b1. 시스템이 실패 경과를 기록하고 같은 최초 장애 보고를 반복하지 않는다. **중복 보고 없이 종료한다.**
- **1c · 이미 보고한 장애의 작업이 정상으로 돌아왔다.**
  - 1c1. 시스템이 복구 리포트를 준비한다. **3~5단계를 수행하고 복구 보고로 종료한다.**
- **3a · 운영 리포트 목적지가 설정되지 않았다.**
  - 3a1. 시스템이 보낼 곳 없음과 미전달을 기록한다. **전달 실패로 종료한다.**
- **3b · 운영 리포트 채널이 오류를 반환하거나 응답하지 않는다.**
  - 3b1. 시스템이 전달 실패를 기록한다. **전달 실패로 종료한다.** 원래 운영 작업의 결과를 보고 성공으로 바꾸지 않는다.
- **5a · 운영자가 아직 리포트를 열람하지 않았다.**
  - 5a1. 시스템이 열람 완료로 단정하지 않는다. **전달 결과까지만 확정하고 종료한다.**

**기술·데이터 변형:** 현재 반복 작업 실패·복구 알림의 범위를 기술한다. 모든 예외와 버그가 자동으로 리포트된다는 뜻은 아니다. 개발용 Discord는 운영 리포트용이며 고객 여행 안내의 대체 발송처가 아니다.

**품질·자율성·빈도:** 최초 기준 도달 시 한 번, 보고한 장애가 복구되면 한 번 보고한다. 실제 운영 리포트 수신·열람은 이번 작성에서 시험하지 않았다.

**미결·운영 확인:** 버그 종류별 추가 자동 보고 범위는 이 명세에서 확정하지 않는다.
