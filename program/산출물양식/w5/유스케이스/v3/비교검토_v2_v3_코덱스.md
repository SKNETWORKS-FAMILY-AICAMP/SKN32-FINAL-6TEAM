# 유스케이스 v2 · v3 비교 검토 — 코덱스(gpt-6.1-sol) 원문

2026-10-02 · 의뢰서: 이 폴더 REVIEW.md 와 같음 · Claude 의 판단과 합친 결론은 v4 문서 「v2 · v3 비교」 절.

**v3는 v2보다 읽기 쉽지만, 내용이 완전히 같은 그림은 아닙니다. 명세 충실도와 관계 표기의 명확성은 v2가 낫습니다. 최종안은 v3의 배치를 채택하되, v2의 정확한 문구와 명시적인 UML 관계 표기를 복원하는 수정안으로 권합니다. 두 원본 모두 교재 기준으로 그대로 확정하기에는 문제가 있습니다.**

REVIEW.md를 끝까지 읽고, 두 PNG, `v2_make_onepage.py`, `v2_make_usecase.py`, `v3_make_hand.py`, `v2_doc.html`, `교재_유스케이스장.txt`를 직접 대조했습니다. 아래에서 **확인**은 파일에서 확인한 사실이고, **판정**은 그 사실을 명세·교재에 적용한 검토 의견입니다. 실제 서비스 저장소와 실행 결과는 제공되지 않았으므로, “실제 코드와 일치한다”는 제작자의 설명까지 검증한 것은 아닙니다.

**1. 대조 범위와 전체 집계**

v2 한 장의 실제 노드·관계는 `v2_make_onepage.py`의 `band1()`~`band4()`와 구역 사이 선을 그리는 `main()`을 기준으로 셌습니다. `v2_make_usecase.py`에서는 상속받는 `D` 클래스의 도형·관계 구현을 확인했습니다. 그 파일의 개요·개별 그림에만 존재하는 노드를 한 장의 노드로 중복 계산하지 않았습니다.

v3는 `build()` 전체와 `node()`, `actor()`, `path()`, 범례·스타일 정의를 대조했습니다. 일반화는 코드의 텍스트상 화살표 순서가 아니라 **실제로 빈 삼각형이 놓이는 방향**으로 판독했습니다.

| 대조 항목 | v2 | v3 | 확인 결과 |
|---|---:|---:|---|
| UC-01~UC-16 | 16개 | 16개 | ID와 기능 이름 모두 유지 |
| ID 없는 세부 기능·처리 단계 | 24개 | 24개 | 삭제·추가 없음 |
| 다른 구역 UC 참조 상자 | 0개 | 2개 | v3에 `pB`, `pD` 추가. 둘 다 UC-12 참조 |
| 기능 노드의 화면상 표현 수 | 40개 | 42개 | 참조 상자를 포함한 수 |
| 액터의 화면상 표현 수 | 17개 | 15개 | v2 B 구역의 여행자·AI 앱 개별 표현 2개 제거 |
| 연관 관계 | 29개 | 29개 | 대응 종점 유지. 단, B의 요청자 액터 의미 표현은 변경 |

액터 수는 **서로 다른 실제 역할의 수가 아니라 그림에 그려진 표현의 수**입니다. 반복해서 그린 AI 모델·디스코드 등도 각각 계산했습니다. 선 수는 공유 통로의 꺾인 조각 수가 아니라 의미상 관계 수입니다. v2의 `style=invis` 배치용 선은 제외했습니다.

기존 40개 기능 노드 중 **15개에서 제목 또는 주석이 달라졌습니다. 제목 변경은 2개, 주석 변경은 14개**이며, 한 노드에서 둘 다 바뀐 경우가 있습니다. 나머지 25개는 ID·제목·주석이 같습니다. 도형·색·위치는 별도 차이입니다.

**같은 액터를 여러 번 그리는 것**

제공된 교재에는 동일 액터의 반복 표현을 허용하거나 금지하는 명시적 규칙이 없습니다. 따라서 “교재가 허용한다”고 단정할 수는 없습니다. 그렇다고 같은 역할을 여러 위치에서 보여줬다는 이유만으로 관계 규칙 위반이라고 볼 근거도 없습니다.

**검토 판정:** 선을 줄이기 위한 반복 표현은 사용할 수 있습니다. 다만 이름·역할을 통일하고 동일 액터임을 명시해야 합니다. 두 그림의 장소 정보는 `장소 정보`, `장소·영업·교통 정보`, `장소·영업 정보`처럼 이름과 담당 공급자가 달라서, 주석만으로 하나의 액터라고 묶는 것은 정밀하지 않습니다. 공통 역할과 구역별 공급자 차이를 구분해야 합니다.

**UC-12 참조 상자**

v3는 같은 UC-12라는 ID와 C 구역을 표시하므로 사람이 의도를 이해할 수 있습니다. 그러나 `pB`, `pD`, `c`는 생성 코드상 서로 다른 화면 노드이고, 둘과 C를 잇는 모델 관계는 없습니다.

**검토 판정:** 설명용 한 장에서는 유용하지만, 교재에 정의된 정식 관계 표기라고 주장할 수 없습니다. 정식 유스케이스 그림은 실제 UC-12로 선을 연결하는 방식이 가장 분명합니다. 참조를 유지한다면 “UC-12의 반복 표현이며 별도 기능이 아님”을 명시해야 합니다.

**C의 일반화 합류**

v3의 `x1`, `x3` 선은 빈 삼각형이 있는 `x2→a2` 선에 합류합니다. 연결된 선 전체로 보면 세 점검에서 담당 에이전트 점검으로 향하는 일반화 의도는 읽힙니다.

따라서 **이 두 가지를 따로 떼어 “유스케이스끼리 잘못된 연관 실선 2개”라고 세는 것은 적절하지 않습니다.** 다만 v2처럼 세 관계에 각각 삼각형을 두는 편이 더 명확합니다.

더 큰 문제는 두 그림에 공통입니다. 명세는 액티비티·요식·이동이 순서대로 점검하고 초안을 넘기는 **협업 절차**를 설명합니다. 일반화는 기능의 종류를 나타낼 수 있지만, **세 점검을 모두 실행한다는 의미를 보장하지 않습니다.** 이 실행 요구는 시나리오나 활동 다이어그램에 있어야 합니다.

**필수 include와 조건부 실행의 충돌**

v2 문서의 요약은 UC-07·08·10·11이 UC-12를 “반드시” 거친다고 하지만, 상세 명세는 다음과 같이 조건을 둡니다.

| 관계 | 상세 명세에서 확인한 조건 | 판정 |
|---|---|---|
| UC-10→UC-12 | 깨진 항목이 있을 때 조율. 변화가 없으면 사건·알림 0 | **모든 감시 실행에서 필수라고 표현하면 부정확** |
| UC-11→UC-12 | 닫힌 곳이면 조율. 열면 기록만 함 | **모든 새벽 점검에서 필수라고 표현하면 부정확** |
| UC-15→문구틀 번역 | 언어마다 처음 한 번만 번역 | **모든 알림 실행의 필수 번역처럼 보이면 부정확** |
| 계획 읽기→원문 위치 가리키기 | 코드가 읽고 남은 줄만 AI 처리 | 남은 줄이 없는 경우의 실행 여부까지 파일만으로 확정할 수 없음. 무조건 필수 표기는 재검토 필요 |

UC-12의 정상적인 변경 완료 경로에서 UC-14를 포함하는 것은 명세와 맞습니다. 후보 소진 등 예외 경로에서 변경 알림이 생략된다는 사실만으로 그 include를 곧바로 잘못이라고 판단하지는 않습니다.

**내부 단계를 너무 쪼갠 문제**

`계획 읽기`, `소스 수집`, `바뀐 값에 걸린 항목 고르기`, `근거 대조 후 적용` 등은 사용자가 독립적으로 요구하는 서비스보다 내부 구현 단계에 가깝습니다. 특히 v3는 계획 읽기를 직접 “매니저의 처리 단계”라고 적습니다.

교재는 반드시 실행된다는 이유만으로 내부 단계를 전부 include로 분해하라고 하지 않습니다. 재사용과 사용자에게 보이는 기능 단위를 함께 보라고 합니다. 두 그림 모두 그 경계를 넘어 **유스케이스 그림과 처리 구조 설명을 혼합**했습니다.

**9. 기준별 결론과 최종 채택안**

| 기준 | 더 나은 쪽 | 이유 |
|---|---|---|
| 명세 충실도·내용 정확성 | **v2** | 항목·날짜별 점검, 원문 근거, 대조 대상, 원값 보존, Places 등 세부 제약을 더 많이 유지 |
| 교재 표기 준수 | **v2** | 개별 include·extend 라벨, 타원형 기능, 개별 일반화 화살촉이 더 명확. 다만 내부 단계 분해·조건부 include 문제는 공통 |
