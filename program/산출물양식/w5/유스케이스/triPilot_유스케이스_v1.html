2026-10-02 · 표기 기준: 「SW 요구사항 · 아키텍처 설계」 교재 유스케이스 장 · 사실 기준: 실제 API 경로와 코드(final_project_cs) · 그림: 공식 Graphviz 16(로컬)

유스케이스는 16개입니다. 여행자 · 동행자 · AI 비서 앱이 시작하는 일 9개(UC-01~09), 시간 · 외부 데이터가 시작하는 일 3개(UC-10 · 11 · 15), 운영자 1개(UC-16), 그 사이의 공통 기능 3개(UC-12 · 13 · 14)입니다. 그중 바꿔 달라고 하기 · 문제 알리기 · 외부 변화 감시 · 새벽 정기 점검 넷이 일정 조율(UC-12)을 반드시 거칩니다. 조율은 전부 통과할 때까지 반복하고, 끝나면 변경 알리기(UC-14)로 이어집니다. 고객 건을 사람에게 넘기는 유스케이스는 없습니다 — 운영자는 오류 알림만 받습니다.

4. 교재 규칙으로 검산

규칙결과어떻게
실선(연관)은 액터와 유스케이스 사이에만지켰다유스케이스끼리는 실선이 없다
점선(포함 · 확장)은 유스케이스끼리만지켰다액터에 «include»를 걸지 않았다
일반화는 같은 종류끼리만지켰다여행자 → 동행자(액터끼리) 하나
순서를 그리지 않는다(함정 1)지켰다올리기 → 확인 → 등록, 감시 → 조율 → 알림의 순서는 명세에 글로 적었다
로그인을 모든 곳에 include 하지 않는다(함정 2)해당 없음guguroute은 로그인이 없다 — 브라우저 사용자 키 · 링크 토큰
include는 반드시 + 재사용일 때만지켰다일정 조율(UC-12)은 넷(UC-07 · 08 · 10 · 11)이 반드시 쓴다 · 변경 알리기(UC-14)는 조율이 끝나면 반드시
선택적이면 extend지켰다일정 짜 주기(UC-04) · 바꾸기 전에 묻기(UC-13)는 조건이 맞을 때만
너무 묶지도 쪼개지도 않는다(함정 3)판단「바꿔 달라고 하기」와 「문제 알리기」는 나눴다 — 요청과 신고는 처리가 다르다(바로 바꿈 / 늦은 만큼 뒤를 다시 맞춤). 「다른 안 고르기」와 「되돌리기」는 묶었다 — 둘 다 이미 있는 판 중 하나를 고르는 같은 일이다

5. 유스케이스 명세 — 핵심 8개

양식: 1 개요 · 2 관계(개시자 · 지원자 · 사전 · 사후 조건) · 3 기본 흐름 · 4 대안 흐름 · 5 예외 흐름(교재 회원가입 시나리오 양식). 나머지 8개(UC-01 · 03 · 04 · 05 · 06 · 08 · 09 · 16)는 목록의 한 줄 설명이 흐름의 전부에 가깝다.

UC-02 계획 올리기

1. 개요 — 여행자가 쓰던 계획을 그대로 올리면 일정 항목으로 읽어 확인 화면으로 넘긴다.

개시자여행자 · 개인 AI 비서 앱지원자—
사전 조건여행을 시작했다(UC-01).
사후 조건읽힌 항목이 근거(원문 몇째 줄)와 함께 확인 화면에 놓인다.

3. 기본 흐름

  1. 여행자가 글을 붙여 넣거나 파일(사진 · PDF · 워드 · 엑셀)을 고른다.
  2. 시스템이 크기를 확인한다 — 글 20,000자 · 파일 5개 · 파일당 10MB.
  3. 정해진 모양(시각 · 일차 · 날짜 · 예약번호)은 코드가 먼저 읽고, 남은 줄만 AI가 원문 위치를 가리킨다.
  4. 장소를 하나로 정한다 — 우리 표 → 별칭 → 오타 교정 → 카카오 · 관광공사 → Places 순.
  5. 확인 화면(UC-03)으로 넘긴다.

4. 대안 흐름

  • A1 사진이면 먼저 한 줄씩 받아쓰고, 전체 · 반쪽 두 번 대조해 빠진 줄을 찾는다.
  • A2 계획이 비었거나 「일정 짜 줘」를 고르면 UC-04로 확장된다.
  • A3 AI 앱이 올리면 확인 화면 없이 API 응답으로 읽힌 결과를 받는다.

5. 예외 흐름

  • E1 크기를 넘으면 받지 않고 「글은 20,000자까지 받아요」처럼 이유를 알린다.
  • E2 원문에 없는 인용은 버린다 — 근거 없는 값은 만들지 않는다.

UC-07 바꿔 달라고 하기

1. 개요 — 여행자가 일정 하나를 바꿔 달라고 하면 바로 바꾸고 다른 안을 함께 준다.

개시자여행자 · 개인 AI 비서 앱지원자장소 · 영업 정보
사전 조건등록된 여행이 있다.
사후 조건일정이 새 판으로 저장되고, 바꾼 곳 · 다른 안 셋까지가 알림 · 여행계획서에 실린다.

3. 기본 흐름

  1. 여행자가 채팅이나 API로 요청한다 — 「12시 식당 다른 데로 바꿔 줘」.
  2. 시스템이 문장에서 대상 항목과 요청 종류(바꾸기)를 읽는다.
  3. 일정 조율(UC-12)을 포함해 대체 후보를 고르고 앞뒤 이동까지 맞춘다.
  4. 「요청하신 대로 페스타 바이 중후 대신 서울다이닝(으)로 바꿨습니다(12:00 시작). 다른 안: 1) … 2) … 3) …」로 답한다.
  5. 변경 알리기(UC-14).

4. 대안 흐름

  • A1 여행자가 다른 안을 고르면 UC-09. 답이 없으면 바꾼 대로 둔다.

5. 예외 흐름

  • E1 대상 항목을 읽지 못하면 지어내지 않고 무엇을 바꿀지 되묻는다.
  • E2 조건을 다 맞추는 곳이 없으면 바꾸지 않고, 조건을 푼 안(시각 늦추기 · 반경 넓히기)을 「고르시면 바꿀게요. 답이 없으면 원래 일정 그대로」로 묻는다.

UC-10 외부 변화 감시

1. 개요 — 곧 시작할 일정 항목에 걸린 외부 변화를 계속 지켜보고, 깨졌으면 조율을 시작한다.

개시자시간(3분)지원자외부 데이터 6종
사전 조건여행이 진행 중이고 곧 시작할 항목이 있다.
사후 조건변화가 없으면 아무것도 안 한다(사건 0 · 알림 0). 깨졌으면 여행당 사건 1건이 열린다.

3. 기본 흐름

  1. 시간이 감시 작업을 깨운다.
  2. 외부 데이터(날씨 · 특보 · 예보 · 재난문자 · 교통 사건)를 소스마다 한 번 모은다.
  3. 값이 바뀐 것에 걸린 일정 항목만 골라 점검한다 — 장소 항목은 성립 점검, 이동 항목은 구간 사건 점검.
  4. 깨진 항목이 있으면 그 여행에 사건 1건을 열고 일정 조율(UC-12)을 포함한다.

4. 대안 흐름

  • A1 같은 원인으로 이미 연 사건이 있으면 새로 열지 않는다(여행 · 항목 · 원인 지문).

5. 예외 흐름

  • E1 소스와 대체 소스(날씨 Open-Meteo ↔ 기상청 · 교통 ITS ↔ UTIC)까지 실패하면 「괜찮다」로 넘기지 않는다 — 고치지 않고 확인하지 못한 이유를 남기고 오류로 센다.
  • E2 [구현 전] 식당의 낮 임시휴무를 시스템이 스스로 찾는 기능은 결정됐지만 아직 없다 — 지금은 고객 신고(UC-08)로 받는다.

UC-11 새벽 정기 점검

1. 개요 — 그날 식사 · 활동 일정이 계획한 시각에 여는지 새벽에 확인한다.

개시자시간(03:00)지원자장소 · 영업 정보(Google)
사전 조건그날 식사 · 활동 항목이 있다.
사후 조건닫힌 곳은 조율되고, 모은 문제는 하루 시작 알림(UC-15)에 실린다.

3. 기본 흐름

  1. 03:00~08:00 창 안에서 항목 · 날짜마다 한 번 영업시간을 조회한다.
  2. 계획한 시각에 열면 기록만 한다.
  3. 닫혔으면 같은 시각 근처의 대체 장소를 계산해 일정 조율(UC-12)로 보낸다.

4. 대안 흐름

  • A1 「먼저 물어봐」 여행이거나 고정한 일정이면 UC-13으로 묻는다.

5. 예외 흐름

  • E1 조회를 못 했으면(키 오류 · 시간 초과) 「연다」로 적지 않고 창 안에서 다시 부른다.
  • E2 맞는 장소가 없거나 영업시간 칸이 없으면 「모름」으로 기록하고 센다.

UC-12 일정 조율

1. 개요 — 깨졌거나 바꿔야 할 일정을 담당 에이전트들이 전부 통과할 때까지 다시 맞춘다. 네 유스케이스가 반드시 쓴다.

개시자UC-07 · 08 · 10 · 11 (포함)지원자장소 · 영업 정보
사전 조건바꿔야 할 항목과 원인이 정해졌다.
사후 조건통과한 안이 일정 새 판 1번으로 저장된다(먼저 물어봐 여행은 답을 받은 뒤).

3. 기본 흐름

  1. 코어가 영향받는 항목을 추린다 — 바로 다음 · 오늘 남은 일정 · 이후 전부.
  2. 담당 에이전트에게 일감을 준다 — 액티비티 → 요식 → 이동 순서, 앞 에이전트의 초안을 다음에 넘긴다.
  3. 요식 · 액티비티가 영업 · 날씨 · 휴무를 점검하고 대체 후보를 낸다.
  4. 이동이 앞뒤 구간을 시간표로 다시 판정한다.
  5. 「전부 통과?」 — 통과하면 일정 변경 제안을 코어에 돌려주고, 코어가 새 판을 저장한다.
  6. 변경 알리기(UC-14)를 포함한다.

4. 대안 흐름

  • A1 통과하지 못하면 다음 대체 후보로 3단계부터 다시 한다(반복).
  • A2 설문 「먼저 물어봐」 · 고정한 일정 · 안전 경보면 저장 전에 UC-13으로 확장된다.

5. 예외 흐름

  • E1 후보가 다 떨어지면 바꾸지 않고, 「못 맞춤」을 이유와 함께 알린다 — 조건을 푼 안이 있으면 그것을 고르게 한다.
  • E2 조회 소스가 대체까지 실패하면 근거 없이 바꾸지 않고, 이유를 고객에게 알리고 오류로 기록한다(운영자는 오류 알림으로 본다).

UC-13 바꾸기 전에 묻기

1. 개요 — 조건이 맞으면 일정 조율이 바꾸기 직전에 끼어들어 여행자에게 먼저 묻는다.

개시자UC-12 (확장)지원자디스코드
사전 조건통과한 안이 있다. 그리고 설문 「먼저 물어봐」(또는 문항을 건너뜀) · 고정한 일정 · 안전 경보 중 하나다.
사후 조건여행자가 고르면 그 안으로 바뀐다. 답이 없으면 원래 일정 그대로다.

3. 기본 흐름

  1. 바꾸지 않고 「{일정} — {이유}. 어떻게 할까요? 1) … 2) … 답이 없으면 원래 일정을 그대로 둡니다.」를 보낸다.
  2. 여행자가 일정 탭 「선택이 필요해요」에서 고른다(UC-09).
  3. 고른 안으로 새 판을 저장한다.

4. 대안 흐름

  • A1 안전 경보(지진 · 재난)면 일정은 바꾸지 않고 안전 알림으로 보낸다.

5. 예외 흐름

  • E1 그 일정이 끝날 때까지 답이 없으면 묻던 것을 닫고(만료) 원래 일정을 둔다.

UC-14 변경 알리기

1. 개요 — 바뀐 결과를 알리고 여행계획서를 새 판으로 바꾼다.

개시자UC-12 (포함)지원자디스코드 · 여행자
사전 조건일정 새 판이 저장됐다.
사후 조건알림이 나가고 여행계획서 링크가 새 판을 보여 준다.

3. 기본 흐름

  1. 새 판과 같은 트랜잭션으로 알림을 보낼 함에 넣는다.
  2. 배달 일꾼이 디스코드로 보낸다 — 문구틀은 언어마다 처음 한 번만 번역하고, 시각 · 이름 · 금액은 원값을 싣는다.
  3. 여행계획서 링크는 새 판을 바로 보여 준다.

4. 대안 흐름

  • A1 같은 알림은 두 번 보내지 않는다(중복 방지 키).

5. 예외 흐름

  • E1 보내기가 실패하면 3번까지 다시 보내고, 그래도 안 되면 실패 보관함에 둔다.
  • E2 시간 초과로 갔는지 모르면 「보냄」으로 적지 않고 다시 보내지도 않는다 — 같은 알림이 두 번 가는 것도 사고다.
  • E3 [한계] 지금은 팀 시연 채널 하나로만 간다 — 사용자가 받을 곳을 등록하는 화면은 다음 단계다.

UC-15 일정 알림 보내기

1. 개요 — 변화가 없어도 일정에 맞춰 지금 할 일을 알린다.

개시자시간지원자디스코드
사전 조건등록된 여행이 진행 중이다.
사후 조건하루 시작 · 다음 일정 · 출발 알림이 한 번씩 나간다.

3. 기본 흐름

  1. 하루 시작 — 그날 시작 시각(기본 08:00, 첫 항목이 더 이르면 60분 전)에 그날 일정과 새벽 점검에서 모은 문제를 알린다.
  2. 다음 일정 안내를 보낸다.
  3. 출발 시각(다음 일정 시작 − 이동 시간 − 여유)에 어디로 · 어떻게 갈지 알린다. 2 · 3을 반복한다.

4. 대안 흐름

  • A1 이 알림은 사건을 만들지 않고 AI를 부르지 않는다(문구틀 번역만 언어마다 한 번).

5. 예외 흐름

  • E1 보내기 실패 처리는 UC-14와 같다.
