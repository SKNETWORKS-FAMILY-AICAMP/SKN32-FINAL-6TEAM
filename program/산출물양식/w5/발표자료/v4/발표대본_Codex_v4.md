# triPilot 멘토 발표 대본 v4

각 장의 수치는 조사·평가·운영 규칙·예시를 구분해 설명합니다. 사실 정보는 assets/facts.md를 기준으로 합니다.

## 01. triPilot은 여행이 끝날 때까지 기존 계획을 지킵니다

triPilot은 스스로 계획을 짜는 자유여행자가 이미 만든 계획을 여행이 끝날 때까지 관리하는 에이전트입니다. 국적과 관계없이 국내 여행자도 대상입니다. 글이나 파일로 계획을 올리면 문제가 생겼을 때 대안을 검토하고, 허용한 범위에서 적용한 뒤 알려 줍니다. 바꾼 장소를 거쳐 다음 일정에도 제시간에 갈 수 있는지 반복해서 확인합니다. 팀이 정한 현재 서비스 범위는 서울, 최대 7일과 4인입니다. 다음 변화가 생기면 다시 점검하고 여행이 끝날 때까지 관리합니다.

출처: assets/facts.md §0

## 02. 대상은 국적이 아니라 계획 특성으로 나눕니다

대상은 국적보다 계획의 조건으로 나눕니다. 사용자가 알려 주는 할랄이나 채식, 아이 동반 조건을 지켜야 하고, 식당과 활동의 예약 시각을 고정점으로 두고 앞뒤 이동을 확인해야 합니다. 시작 화면에서는 테마와 우선순위, 실내외와 여유를 받습니다. 일정이 꼬이면 바꿔 달라고 할지 먼저 물어봐 달라고 할지도 선택합니다. 이 표는 사실표의 사용자 설문과 에이전트 점검 항목을 연결한 설계 구분입니다. 여행자 유형별 규모를 조사한 수치나 효과 검증 결과는 아닙니다.

출처: assets/facts.md §3

## 03. 여행자는 AI로 계획을 짜도 현장에서 다시 맞춥니다

문체부 외래관광객조사의 2025년 1분기 개별여행 비중은 82.9%입니다. 한국관광공사가 최근 3년 내 방한한 7개국 외국인 2,466명을 조사했을 때, 여행 준비에 생성형 AI를 써 본 비율은 69.9%, 일정이나 동선을 추천받은 비율은 47.5%, 추천 동선대로 실제 이동한 비율은 32.8%였습니다. 그래서 사용자가 쓰는 개인 에이전트 앱을 접속 입구로 둡니다. 같은 관광공사 설문에서 현지 정보 재검색은 96.4%, 일정 변경은 42.5%였습니다. 여행 전 검색·계획 만족 84.6%와 현장 탐색·이용 편의 만족 70.8%의 차이는 13.8%포인트입니다. 만족의 질문이 다르며 인과관계나 동일한 경로를 밟은 사람의 비율은 아닙니다. AI 수치도 기사상 응답자 기준이며 AI 사용자만이 분모인지 확인되지 않았습니다.

## 04. 한국 여행의 불편은 정보에 접근하는 단계에서 드러납니다

야놀자리서치가 레딧 여행 글 3년치 7,260건을 분석한 결과, 불편 경험이 담긴 글의 비율은 한국 11%, 일본 7%였습니다. 여행자 개인의 일정 변경 실패율이 아니라 게시글에서 불편을 언급한 비율입니다. 같은 분석에서 한국 불편 글의 유형은 디지털 27.8%, 관광정보와 안내 16.4%, 교통 13.1%, 결제 12%였습니다. 국가별 글 수와 한국 불편 글 수는 사실표에 없으므로 분자를 만들어 넣지 않았습니다. 한국 여행에서는 예약과 지도, 결제처럼 정보에 접근하는 단계도 확인해야 한다는 근거로 사용합니다.

## 05. triPilot은 여행자가 떠안던 복구 9단계를 대신 수행합니다

팀이 정리한 예시입니다. 일본 여행에서 오후 1시 식당이 임시휴무인데 3시 체험 예약은 지켜야 합니다. 문제 발견, 검색, 번역, 영업 확인에 이어 대안을 찾고 이동을 다시 계산하며 예약 충돌을 확인합니다. 마지막으로 일정 수정과 동행자 공유까지 팀이 아홉 단계로 정리했습니다. 조사에서 나온 단계 수는 아닙니다. triPilot은 담당 에이전트 점검과 대안, 이동 재검증, 최신 계획 반영을 연결합니다. 낮 임시휴무 자동 탐지는 구현 대상이라 현재는 사용자 신고가 필요합니다. 시간 절감 효과는 아직 측정하지 않았습니다.

출처: assets/facts.md §1

## 06. 비교할 가치는 변경 뒤 다음 일정까지 확인하는 데 있습니다

비교할 가치는 변경 뒤 다음 일정까지 성립하는지 확인하는 데 있습니다. 사실표에 정리된 팀 조사에서 TripIt Pro는 항공 변동 알림과 대체 항공편, TripMazer는 감시와 재계획, Tripsy는 일정 편집 연동을 확인했습니다. 토모트래블은 사람이 상담하고 여행을 설계합니다. 오른쪽은 기능이 없다고 단정한 칸이 아니라 공개 자료와 직접 시험에서 확인하지 못한 범위입니다. triPilot은 대안을 검토한 뒤 앞뒤 이동과 전체 일정을 다시 확인합니다. 추천 품질 평가는 더 필요하며, 우월성을 입증한 비교 실험은 아닙니다.

출처: assets/facts.md §2

## 07. 내 계획을 올리고 읽은 내용을 확인하면 관리가 시작됩니다

실제 화면입니다. 첫 화면에서 언어를 고르고 내 여행을 엽니다. 시작할 때 취향과 변경 권한을 선택하고 글을 붙여 넣거나 사진, PDF, 워드, 엑셀 파일을 올립니다. 다음 화면에서는 시스템이 읽은 항목을 사용자가 고치거나 뺍니다. 확인한 계획을 등록하면 관리가 시작됩니다. 현재 이메일은 복구용으로만 받고 저장하지 않습니다. 사용자가 자기 알림 받을 곳을 등록하는 화면도 아직 없습니다. 이후 시작 화면에서 이메일과 함께 디스코드 등 받을 곳을 입력하도록 확장할 계획입니다.

출처: assets/facts.md §3

## 08. 변경 권한에 맞춰 대안을 적용하거나 승인을 요청합니다

변경은 처음 정한 권한에 맞게 처리합니다. 바꿔 줘를 선택하면 허용한 범위에서 검증한 대안을 먼저 적용하고 다른 안도 보여 줍니다. 먼저 물어봐를 선택하면 승인받은 뒤 적용합니다. 사용자가 다른 안을 고르거나 되돌리기를 요청하면 다시 점검과 조율 루프로 들어갑니다. 답이 없으면 현재 상태를 유지합니다. 권한에 따라 이미 반영한 안일 수도 있고 승인 전 일정일 수도 있습니다. 선택 결과는 최신 일정에 반영하며 이전 판도 보존합니다. 캡처의 장소와 시각은 시연 데이터입니다.

출처: assets/facts.md §3

## 09. 알림을 받으면 지도와 채팅에서 최신 일정을 확인합니다

현재 알림은 서버 설정에 넣은 팀 시연용 디스코드 채널 하나로만 갑니다. 사용자가 등록하자마자 자기 디스코드로 받는 구조는 아닙니다. 자기 알림 받을 곳을 입력하는 화면은 없고 복구용 이메일도 저장하지 않습니다. 다음에는 시작 화면에서 이메일과 함께 디스코드 등 받을 경로를 입력하도록 하겠습니다. 웹에서는 받은 알림 이력을 보고 지도와 채팅에서 같은 계획을 확인합니다. 상태의 정본은 로그인 없이 열리는 여행계획서 링크입니다. 알림을 놓쳐도 링크에서 최신 상태를 봅니다. 화면의 시각과 거리는 시연 데이터입니다.

출처: assets/facts.md §3

## 10. 일정 조정은 네 경우에 시작하고 알림은 세 종류로 전달합니다

팀이 정한 운영 구분은 조정 트리거 네 가지와 알림 유형 세 가지입니다. 일정 생성과 변경, 사용자 요청, 새벽 3시 점검, 외부 변화 인터럽트가 조정을 시작합니다. 외부 변화는 사실표의 D-017 수집 규칙에 따라 3분마다 확인합니다. 알림은 시스템 변동, 사용자 요청 변동, 일정 알림으로 구분합니다. 일정 알림은 하루 시작에 이어 다음 일정과 이동 출발 시각을 안내합니다. 팀 운영 규칙의 오전 8시와 밤 10시는 계획의 기준 시각이고 조정 트리거가 아닙니다. 하루 시작 알림은 규칙에 따라 첫 일정 60분 전에 보냅니다.

출처: assets/facts.md §3

## 11. 에이전트는 변경한 일정이 성립할 때까지 확인합니다

LLM을 한 번 호출하면 답변 뒤에 종료됩니다. 에이전트는 일감을 받고 필요한 정보를 조회한 뒤 방문과 이동이 가능한지 확인합니다. 부족하면 다시 조회하고, 안 맞으면 다른 후보를 점검합니다. 코어가 결론과 근거를 모아 일정 판을 남기고 사용자 응답을 받습니다. 그 뒤에도 다음 변화를 기다려 여행이 끝날 때까지 다시 실행합니다. AI는 원문 위치와 분류, 설명을 돕고 시각과 영업 조건은 코드가 판정합니다. 이동은 스스로 깨어나는 에이전트가 아니라 코어가 호출하는 공용 판정기입니다.

출처: assets/facts.md §5

## 12. 조율은 통과할 때까지, 관리는 여행이 끝날 때까지 반복합니다

가장 중요한 두 겹 루프입니다. 주황색 안쪽 루프는 영향받는 항목 추리기, 요식과 액티비티의 점검, 대체 후보 조율, 이동의 앞뒤 재판정입니다. 마름모에서 전체 일정이 전부 통과하는지 확인합니다. 아니면 다음 후보로 교체해서 다시 점검합니다. 후보가 떨어지면 못 맞춘다는 이유를 표시하고 사람에게 넘깁니다. 통과하고 변경 권한도 확인해야 다음 단계로 갑니다. 사실표의 D-017 규칙에 따라 같은 변경은 새 판 한 번, 알림 한 번으로 반영하고 계획서를 갱신합니다. 파란 바깥 루프는 외부 여섯 종류의 3분 감시, 새벽 3시 점검, 사용자 요청, 일정 생성과 변경을 기다립니다. 다른 안 선택과 되돌리기도 요청에 포함합니다. 여행이 끝날 때까지 다시 처음으로 돌아옵니다.

출처: assets/facts.md §4-A

## 13. 계획 읽기는 정해진 값을 먼저 읽고 원문 근거를 남깁니다

계획 읽기는 모양이 정해진 값부터 코드가 읽습니다. 오전 9시 경복궁 관람이라는 팀의 예시에서 코드는 시각을 읽고 AI는 경복궁 관람이라는 표현의 원문 위치를 가리킵니다. 장소를 확인한 뒤 값과 방법, 원문 줄을 함께 저장합니다. 사진은 줄별로 받아쓰고 원문에 없는 인용은 버립니다. 팀의 합성 입력 평가에서는 대조한 값 350개 중 12개가 달라져 값 변조가 3.4% 남았습니다. 그래서 확인이 필요한 줄을 드러내고 사용자가 원문과 대조해 고치게 합니다.

출처: assets/facts.md §6

## 14. 요식은 식사 조건과 앞뒤 이동이 맞을 때까지 후보를 점검합니다

요식은 영업시간과 브레이크, 라스트오더, 할랄과 채식, 아이 동반을 점검합니다. 대체 후보를 고르면 코어가 앞뒤 이동과 전체 일정을 재검증합니다. 안 맞으면 주황 화살표를 따라 다음 후보로 다시 점검하고, 후보가 소진되면 이유를 사람에게 넘깁니다. 팀의 예시에서는 점심이 70분 늦어 브레이크에 걸려 도보 6분 대안 식당을 검토합니다. 팀 식당 데이터 1,225곳은 관광공사 음식점 989곳, 비건 67곳, 할랄 24곳, 미쉐린 신규 145곳을 합한 것입니다. 실시간 웨이팅 API는 없고 낮 임시휴무 자동 탐지는 구현 대상입니다.

출처: assets/facts.md §6

## 15. 액티비티는 활동 목적과 방문 조건이 맞을 때까지 후보를 넓힙니다

액티비티는 활동 목적을 유지하면서 운영일과 휴무, 시간, 예약과 날씨를 점검합니다. 같은 대분류 안에서 소분류만 다른 후보부터 시작해 중분류, 다른 구까지 넓힙니다. 코어의 이동과 전체 일정 검증에서 안 맞으면 다음 후보로 돌아가 다시 점검합니다. 팀이 확보한 후보 805행은 관광공사의 서울 활동 목록 행 수입니다. 전망 활동을 미세먼지와 소나기 때문에 실내 아쿠아리움으로 바꾸는 장면은 자료의 설명용 예시입니다. 추천이 실제 취향에 맞는지는 사람 평가로 검증해야 합니다.

출처: assets/facts.md §6

## 16. 이동은 다른 후보로 바꿔 제시간에 이어지는지 다시 판정합니다

코어가 바뀐 장소의 앞뒤 이동 구간을 요청하면 시간표와 출구, 환승과 도보를 대조합니다. 막힌 역과 노선을 제외하고 제시간 도착을 판정합니다. 성립하면 출발 시각과 경로, 요금을 일정에 채웁니다. 불가면 다른 후보가 있는지 확인하고 후보로 교체한 뒤 다시 판정합니다. 후보가 없으면 못 맞춘다는 이유를 사람에게 넘깁니다. 팀 이동 회귀 시험은 기준 판정 168건 중 168건이 일치했습니다. 현장 여행 성공률은 아닙니다. 모든 답에는 근거 등급과 확인 시각을 남기며 실시간 도착 정보와 택시는 향후 과제입니다.

출처: assets/facts.md §6

## 17. 웹과 개인 AI 앱의 계획을 외부 감시로 계속 관리합니다

접속 입구는 휴대폰 웹과 사용자가 쓰는 개인 에이전트 앱입니다. AI 비서 앱이 우리 API로 계획을 넘깁니다. 사실표의 D-017 결정은 날씨, 기상청 특보, 단기예보, 재난문자, ITS와 UTIC 교통 사건의 여섯 종류를 3분마다 수집하는 것입니다. 3분은 감지부터 알림까지 p95 5분 이하라는 목표에서 수집 대기 최대 3분과 처리 약 1분을 거꾸로 잡은 주기입니다. 하루 480회는 하루의 분 수를 3분으로 나눈 값이고, 소스 한도 1,000회의 48%입니다. 바뀐 값에 걸린 일정만 먼저 판정하고 정상이면 유지합니다. 불가면 코어가 액티비티, 요식, 이동 초안을 이어 받아 전체 일정을 반복 재검증합니다. 맞으면 새 판과 알림을 남깁니다. 외부 감시 3분, 멈춘 사건 되잡기 1분, 알림 배달은 서로 다른 상시 작업입니다.

## 20. 역할별 변경은 기준이 다른 CI 관문을 통과한 뒤 합칩니다

각 역할의 변경은 역할 브랜치를 거쳐 develop과 main으로 합칩니다. 사실표에서 확인한 CI 설정에 따르면 develop push와 PR은 ruff의 최소 버그 규칙, PostgreSQL의 한국 시간대 확인, 표 만들기와 프롬프트 등록 뒤 구조·계약·단위 시험을 합니다. LLM은 가짜입니다. 팀이 2026년 10월 1일 시험 목록을 수집한 값은 구조 159건, 계약 240건, 단위 1,506건이며 실행 통과 결과가 아닙니다. main은 린트와 데모 데이터 뒤 구조를 먼저 시험합니다. 구조는 싸게 확인할 수 있고 늦게 발견하면 되돌리기 비용이 크기 때문입니다. 전체 시험에는 같은 수집 기준으로 통합 350건, e2e 323건, 보안 23건이 포함됩니다. 실제 키·모델이 필요한 LLM 호출과 문서 검색 시험은 제외하고 Docker를 빌드하되 이미지는 올리지 않습니다. 팀의 마지막 실측은 9월 28일 전체 2,309건 통과와 60건 건너뜀입니다. UTC 때문에 시험 43건이 9시간 밀린 사고를 잡아 서버와 DB 시간대를 고정했습니다.

## 21. 관문은 업무 경계·사용자 흐름·웹 화면을 함께 확인합니다

관문이 실제로 무엇을 보는지 예를 들겠습니다. 사실표의 시험 예에서 구조는 코어에 식당이나 주문 같은 업무 단어가 들어오면 실패하게 합니다. 계약은 모든 화면 접근, 중복 요청의 한 번 처리, 수치 하드코딩을 확인합니다. 보안은 권한 없는 요청 거부, 개인정보 가림과 저장소의 서버 주소 노출을 점검합니다. e2e는 계획 올리기 API와 먼저 물어봐, 이동 판정의 흐름을 확인합니다. 웹 관문은 develop과 main에서 웹 폴더가 바뀔 때 npm ci, 린트·타입·단위·빌드, 데모 브라우저 시험, 가짜 서버 브라우저 시험을 순서대로 실행합니다. 웹 시험 건수는 사실표에 없습니다. 현재 자동화는 검증과 빌드까지입니다. 팀 사실표의 현재 운영은 한 대의 PC에 앱과 DB가 상주하는 구성이고 서버 이전은 상시 운영을 약속하는 시점에 진행합니다.
