1 · 무엇인가

유스케이스는 「누가 · 무엇을 이루려고 · 어떻게 하고 · 잘 안 되면 어떻게 되나」 네 가지를 적은 이야기입니다

누가
행위자
시스템을 쓰는 사람(또는 다른 시스템)
예: 여행자
무엇을 이루려고
목표
사용자가 끝에 얻고 싶은 것 하나
예: 문 닫은 식당 대신 갈 곳 정하기
어떻게 하나
주 흐름
잘 될 때 차례로 일어나는 일 3~9단계
예: 알림 → 고르기 → 일정 바뀜
잘 안 되면
예외
중간에 막히는 경우와 그때 할 일
예: 아무것도 안 고르면 → 원래대로
핵심은 기능 이름이 아니라 「사용자 목표」 하나를 기준으로 쓴다는 것입니다.
「검색 기능」「결제 기능」이 아니라 「호텔을 예약한다」처럼 사용자가 하고 싶은 말로 씁니다.
정의: 「외부 행위자의 요청에 시스템이 어떻게 응답해 목표를 이루는지 적은 구조화된 설명」 — 위키백과 「Use case」 항목을 한국어로 줄임.
2 · 왜 만드나

기능 목록만 보면 「사용자가 실제로 뭘 하는지」가 안 보입니다 — 유스케이스는 그걸 보여 주려고 만듭니다

기능 목록으로 보여 주면
  • 계획 읽기 API
  • 3분 감시 작업
  • 대체 후보 계산
  • 알림 발송 일꾼
→ 듣는 사람: 「그래서 사용자는 뭘 하는데?」
→
유스케이스로 보여 주면
여행 중 점심 식당이 문을 닫았다
→ 알림이 온다
→ 대신 갈 식당을 누른다
→ 일정과 이동이 다시 맞춰진다
→ 듣는 사람: 「아, 이렇게 쓰는구나」
멘토 지적(0914): 「유스케이스 — 어떤 경로로 들어와서, 어떤 활동을 하고, 실제로 어떤 화면을 보게 될지」
그리고 「지금 PPT는 너무 개발자용 — 어떤 피처가 있고 얼마나 다른지 어필하는 파트가 필요」
3 · 유명한 예시 ① 위키백과

「글 편집하기」 — 행위자 하나, 주 흐름 5단계, 예외 셋이면 유스케이스 하나가 됩니다

행위자 가입한 회원목표 위키 글 하나를 고친다
1
시스템
편집 칸을 열어 준다
→
2
회원
글을 고친다
→
3
회원
고친 이유를 적고 저장
→
4
시스템
저장하고 기록을 남긴다
→
5
시스템
고친 글을 보여 준다
잘 안 되면 · 다른 길(예외)
2a 저장 전에 보고 싶다미리보기를 보여 주고 2로 돌아간다
2b 무엇이 바뀌었는지 보고 싶다바뀐 부분을 비교해 보여 준다
2c 그만두고 싶다고친 것을 버리고 끝낸다

3 · 유명한 예시 ② 교과서

「웹으로 주식 사기」 — 잘 되면 무엇이 보장되고, 실패하면 무엇이 남는지까지 적습니다

행위자 주식을 사려는 사용자목표 웹 증권사에서 주식을 산다시작 조건 자산관리 프로그램이 열려 있다
1
시스템
어느 증권사 사이트를 쓸지 받는다
→
2
시스템
그 사이트에 연결한다
→
3
사용자
주식을 고르고 산다
→
4
시스템
체결 결과를 받아 내 자산에 반영
→
5
시스템
바뀐 자산을 보여 준다
잘 안 되면(예외)
지원하지 않는 사이트를 원한다다른 사이트를 다시 받거나 그만둔다
연결 중 오류이유를 알리고 앞 단계로 돌아간다
체결 확인이 늦어진다기록해 두고 나중에 사용자에게 결과를 묻는다
끝에 약속하는 것
성공하면: 증권사가 체결을 확인했고, 내 자산이 맞게 바뀌었다
실패해도: 무엇이 잘못됐는지 알 만큼 기록이 남는다
출처: Alistair Cockburn, 『Writing Effective Use Cases』(2001)의 예시를 한국어로 줄여 다시 그림. 유스케이스 작성의 표준 교과서다.
3 · 유명한 예시 ③ 실무 양식

실무에서는 칸을 정해 두고 채웁니다 — 「호텔 방 예약」으로 보면

칸뜻호텔 방 예약이라면
시스템무엇에 대한 이야기인가호텔 예약 웹사이트
행위자누가 쓰나호텔 방을 잡으려는 여행자
목표끝에 얻고 싶은 것원하는 날짜에 방 하나 예약
시작 조건시작 전에 갖춰져 있어야 할 것사이트에 접속해 있다
주 흐름잘 될 때의 차례검색 → 호텔 고르기 → 날짜 · 인원 → 결제 → 예약 완료
예외막힐 때빈 방이 없다 → 다른 날짜 · 다른 호텔 제안 / 결제 실패 → 다시 시도
끝난 뒤 상태끝나면 무엇이 바뀌어 있나예약이 잡히고 확인 메일이 온다
출처: Nulab 「How to create a use case scenario」의 칸 구성을 한국어로 정리 — nulab.com/learn/design-and-ux/
4 · 발표용으로 바꾸기

교과서 유스케이스는 글이고, 발표 유스케이스는 같은 흐름을 「실제 화면 + 화살표」로 보여 줍니다

문서(교과서)
1. 시스템이 알림을 보낸다
2. 여행자가 대체 식당을 고른다
3. 시스템이 일정을 바꾼다
2a. 고르지 않으면 원래대로
→
발표 한 장
누가 · 언제 — 「여행 중, 점심 식당이 임시휴무」
알림 화면→선택 화면→바뀐 일정
결과 — 「버튼 하나로 바뀐다. 안 누르면 원래대로」
발표 한 장 = 위: 누가 · 언제 한 줄 · 가운데: 실제 화면을 화살표로 · 아래: 결과 한 줄.
코드 이름, API 경로, 「있음 · 일부」 같은 개발 상태는 넣지 않습니다.
5 · guguroute 유스케이스 ① 여행 전

쓰던 계획을 올리면 그대로 일정이 되고, 늘 최신인 여행계획서 링크를 받습니다

누가 스스로 계획을 짠 자유여행자(국적 무관)어디로 웹 또는 자기 AI 비서 앱목표 쓰던 계획을 관리받기 시작
① 첫 화면
언어 · 내 여행
→
② 계획 붙여 넣기
글 · 사진 · 파일
→
③ 읽은 값 확인
항목마다 원문 근거 표시
고치기 · 빼기 → 등록
→
④ 등록 완료
로그인 없이 열리는 여행계획서 링크 — 늘 최신
잘 안 되면 일정이 성립하지 않으면(예: 영업시간 밖) 등록하지 않고 무엇을 고치면 되는지 알려 준다 · 계획이 없으면 「일정 짜 줘」
5 · guguroute 유스케이스 ② 여행 중 — 시스템이 먼저

점심 식당이 문을 닫으면 알림이 오고, 일정 탭에서 대신 갈 곳을 누르기만 하면 됩니다

누가 여행 중인 여행자언제 3분 감시나 새벽 3시 점검이 문제를 찾았을 때목표 깨진 일정을 다시 맞추기
점심 식당 임시휴무
감시가 먼저 알아챔
→
알림이 온다
바꾼 안 · 다른 안
→
일정 탭에서 고른다
「선택이 필요해요」
→
일정이 바뀐다
이동도 다시 맞춤
잘 안 되면 · 갈래 설문에서 「바꿔 줘」를 고른 여행은 먼저 바꿔 두고 알림 · 「먼저 물어봐」면 바꾸기 전에 묻는다 · 아무것도 안 고르면 원래 일정 그대로 · 지진 같은 안전 경보는 바꾸지 않고 알리기만
5 · guguroute 유스케이스 ③ 여행 중 — 내가 먼저

채팅으로 「식당 바꿔 줘」라고 하면 바로 바뀌고, 마음에 안 들면 다른 안 셋 중에서 고릅니다

누가 여행 중인 여행자(또는 그의 AI 비서 앱)언제 마음이 바뀌었거나 현장에서 문제를 봤을 때목표 말 한마디로 일정 바꾸기
「점심 식당
다른 데로 바꿔 줘」
채팅 탭에 말한다
→
바로 바꾸고 답한다
이동 시간까지 다시 계산
→
다른 안 3개
마음에 안 들면 고르기 · 되돌리기
실제 문구: 「요청하신 대로 페스타 바이 중후 대신 서울다이닝(으)로 바꿨습니다(12:00 시작). 다른 안: 1) 필동면옥 · 2) 평안도족발집 · 3) 12:30으로 늦추면 송원 — 다른 곳이 좋으면 고르세요. 답이 없으면 지금대로 둡니다.」
잘 안 되면 조건에 맞는 곳이 없으면 「시각 늦추기 · 다음 일정 근처 · 반경 넓히기」 안을 묻는다
6 · 발표에서 말하는 법

장면 하나를 30초로 — 「상황 → 사용자가 하는 일 → 결과 → 그래서 무엇이 달라졌나」

① 상황「여행 중 점심 식당이 갑자기 임시휴무라고 해 보겠습니다.」
② 사용자가 하는 일「사용자는 알림을 하나 받고, 일정 탭에서 대신 갈 식당을 누르기만 하면 됩니다.」
③ 결과「점심 뒤 이동 시간까지 다시 맞춰지고, 여행계획서 링크도 바로 바뀝니다. 아무것도 안 누르면 원래대로 둡니다.」
④ 그래서「앞에서 본 복구 9단계를 혼자 하던 일이, 버튼 하나가 됩니다.」
체크리스트
  • 한 장에 장면 하나
  • 위 한 줄: 누가 · 언제
  • 가운데: 실제 화면을 화살표로
  • 아래 한 줄: 결과
  • 잘 안 될 때 한 줄(예외)
  • 코드 이름 · API · 개발 상태는 빼기
  • 장면은 2~3개면 충분
