# 멘토링에서 받은 지적 (사용자가 정리한 원문 요약, 2026-10-01 전달)

## 발표 자료 전반
- 지금 PPT는 너무 개발자용이다. 어떤 기능이 있고, 얼마나 다르고, 얼마나 대단한지 어필하는 부분이 필요하다.
- 외국인 규모, 일정 관리에 드는 시간, 일정 관리 실패 위험을 조사와 사례로 초반에 다 잡아야 한다. 가치는 개요에서 다 표현한다.
- 현실적인 페르소나: 외국인이 한국에 와서 어려워하는 지점을 구체적으로, 직접 와닿게.
- 기술스택·폴더 구조·ERD는 빼는 게 낫다. 심사위원은 어떤 기능을 어떻게 제공하는지가 궁금하다.
- 아키텍처: 시선이 분산된다. 모르는 사람이 들어도 이해되게, 아예 크게 그린다. 15분에 전부 설명할 수 없다.
- 팀 모듈 대신 에이전트 플로우로. 유기적으로 동작하는 그림. 컨트롤러·라우터는 빼고 전체 구조.
  어떤 트리거로 시작해 어떤 입력·출력이 나오는지. 에이전트 하나하나가 사람이라면? 사람이 하는 서비스를 세분화·벤치마킹.
- 각 모듈: 「어떻게, 무엇이」 동작하는지 의문이 안 생기게. 다른 에이전트와 어떻게 주고받는지(입력·출력).
- 트러블슈팅은 하나만이라도 잘 설명.
- 향후 계획은 에이전트·기능 중심.
- 글자는 적을수록 좋다. 글자가 아니어도 목표를 잘 표현해야 한다.

## 기능·검증
- 범위·기능·시나리오·유스케이스: 어떤 경로로 들어와 어떤 화면을 보고 무엇을 하는가. 첫 화면은 「일정 보기」와 버튼만.
- 추천이 잘 됐다는 것을 수치로 어떻게 보이나(정답이 없는 문제). 정량 평가 루프가 가능해야 한다. 에이전트 평가를 보여 주는 게 가장 좋다.
- 대기시간 확인 가능한 API(캐치테이블 등) 제공 여부 — 들어가 있는지만 알려 줘도 유용.
- 사람이 다 해 주는 서비스와도 비교. 실제 타겟이 겹치는 경쟁사만 비교, 시각적으로 한눈에.
- 리뷰 등 객관적 데이터를 재가공해 쓰는 것은 괜찮다.
- LLM 호출과 에이전트의 차이를 이해하고 설명할 수 있어야 한다.
- 「왜」에 대한 답을 다 할 수 있어야 한다. 데이터 장표로 앞단에서 한 번에 설명.
- 중간 발표 뒤: 협업 방식, CI/CD 구성, 유스케이스, 에이전트 플로우, 에이전트와 LLM 차이.
- 발표는 에이전트1·검증·매니저 3명이 기본.
