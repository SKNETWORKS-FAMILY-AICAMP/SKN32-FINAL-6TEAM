## 3. 사용자 여정과 화면 (실제 캡처: assets/s1~s7)
1. 첫 화면 `/` — 언어 선택 + 「내 여행」 카드(바뀐 일정 있음 배지). 로그인 없음(브라우저에 사용자 키 하나). [s1_home]
2. 온보딩 `/start` — 복구용 이메일(저장 안 함), 약관, 취향 설문 6문항(테마·여행자 구성·우선순위·실내외·일정이 꼬이면 「바꿔 줘 / 먼저 물어봐」·여유).
3. 계획 올리기 `/trips/new` — 글 붙여넣기 + 파일 최대 5개(사진·PDF·워드·엑셀). 3단계 표시(계획 담기 → 함께 확인 → 여행 시작). [s2_upload]
4. 계획 읽기 확인 `/intakes/…` — 항목별 배지, 고치기·빼기, 「등록하고 관리 시작」 또는 「일정 짜 줘」.
5. 여행 화면 `/trips/…` — 「선택이 필요해요」(먼저 바꾼 안 + 다른 안 3개 + 「지금 일정 그대로 두기」, 답 없으면 지금대로), 받은 알림, 변경 이력, 일차별 일정, 「지도 앱에서 길찾기」. [s3_choice, s4_schedule, s5_alerts]
6. 지도 탭(OpenStreetMap, 일차별 번호 핀) [s6_map], 채팅 탭(하루 요약·선택 일정·다음 일정·예약 표시, 이동은 「시간표 판정」으로 출발 시각·노선·소요 표시) [s7_chat].
7. 여행계획서 링크 `/plan/<여행>?t=<토큰>` — 로그인 없이 열리는 「상태의 정본」. 알림을 못 봐도 링크에서 최신을 본다.
8. 알림: 디스코드 웹훅 하나. 지금 규칙 — ① 하루 시작(첫 일정 60분 전, 새벽 3시 확인에서 모은 이슈 포함) → ② 다음 일정 → ③ 이동 시작 시각(출발 = 다음 일정 시작 − 이동 시간 − 여유), ②·③ 반복. 변경 통지는 따로(「먼저 물어봐」 여행이면 선택 요청이 된다).
- 실제 화면 문구 예: 「요청하신 대로 페스타 바이 중후 대신 서울다이닝(으)로 바꿨습니다(12:00 시작). 다른 안: 1) 필동면옥 · 2) 평안도족발집 · 3) 12:30으로 늦추면 송원 — 다른 곳이 좋으면 고르세요. 답이 없으면 지금대로 둡니다.」
- 알림 예: 「17:49 출발 — 엘 샌드위치 → 두가헌 레스토랑(17:49–17:56). 가는 방법: 도보 · 약 7분」.

## 4. 에이전트 전체 흐름 (피그마 「액티비티&요식업 공통플로우」 + 코드)
- 트리거: 하루 시작(08:00) · 하루 종료(22:00) · 일정 생성·변경 직후 · 사용자 요청 · 새벽 3시 정기 확인(관광 정보·식당) · (요식) 방문 전 확인.
- 흐름: 확인 범위 선택(바로 다음 일정 / 오늘 남은 일정 / 이후 모든 일정) → 점검할 식당·장소 추리기 → 에이전트별 점검 항목(영업시간·휴무·예약·날씨 등) → DB 조회 → 조회 실패면 다른 지도 API로 확인, 그래도 안 되면 「확인 필요」 표시·알림 → 예정된 방문에 문제? → 없음: 기존 일정 유지 / 있음: 대체 장소 검토(1순위 유사 장소 · 2순위 선호도 고려 · 3순위 근처) → 대체 장소 선정(대체 이유 포함) → 자동 변경 허용 범위 안이면 적용 · 아니면 사용자 승인 → 사용자 안내 → 응답 반영 → 다시 「일정 변경 직후」로.
- 코어 구조: 감시 루프(1분마다)는 사건(Case)을 만들기만 하고, 판정은 팀 에이전트가 한다. 사건 상태 12종(new → classifying → routing → running → waiting_* → resolved/escalated/failed…), 실패·대기 만료는 조용히 넘기지 않고 사람에게 넘긴다(escalate).
- 분류: 요청 종류 5종(일정 제출·사건 신고·확인 요청·조정 거부·그 외) + 문제 코드(영역 접두 activity·dining·mobility…) → 두 축으로 담당 에이전트를 고른다. 에이전트끼리 직접 부르지 않고 코어를 거친다.
- 배달 루프: 알림은 보낼 함(outbox)에 넣고 일꾼이 보낸다. 3회 재시도 후 실패 보관. 같은 알림 중복 0(키 유일 조건).
- 값을 모를 때: 필요한 값마다 대체 소스(예: 날씨 Open-Meteo ↔ 기상청, 교통 ITS ↔ UTIC). 대체까지 실패하면 조용히 넘기지 않는다(기동 거부 / 사건은 사람에게 / 배치는 실패 종료).
- 원칙: **판정은 코드가 한다 — LLM이 시각·영업시간을 짓지 않는다.** LLM은 원문 위치 가리키기, 분류, 문장 만들기, 대안 후보 설명에 쓴다.

## 5. LLM 호출과 에이전트의 차이 (프로젝트 자료 기준으로 정리)
- LLM 호출: 물어보면 한 번 답하고 끝. 시각을 스스로 모르고, 틀려도 확인하지 않는다.
- 에이전트: ① 스스로 깨어난다(시간·사건·앞 에이전트 변경) ② 일감을 받는다(무슨 일이 생겼나, 지킬 것, 바꿀 수 있는 것, 쓸 도구) ③ 할 일 정하기 → 조회 → 결과 모으기 → 따져 보기를 최대 6단계 반복 ④ 결론·근거·제안·다음 행동으로 돌려주고 일정 새 판을 남긴다(이전 판 보존) ⑤ 알림을 보내고 답을 기다린다.

## 6. 에이전트별
### 계획 읽기(코어)
- 입력: 글·사진·PDF·docx·xlsx(글 20,000자, 파일 5개·10MB). 사진은 Gemma 4 12B가 한 줄씩 받아쓰고, 전체·반쪽 두 번 대조로 빠진 줄 확인.
- 규칙이 먼저 읽고(시각·일차·날짜·예약번호·인원·끼니), 남은 줄만 LLM이 「몇 번째 줄 몇 번째 글자」를 가리킨다. 원문에 없는 인용은 버린다.
- 장소: 우리 표 정확 일치 → 별칭 → 자모 오타 교정 → 카카오·관광공사 → Places 순으로 하나를 고른다.
- 결과: 항목마다 값·방법·근거(원문 줄)를 저장. 합성 평가셋 60건(형식 6종 x 10): 항목 재현율 326/336 = 97.0%(1회차 90.2%), 시각 321/321, 장소 1위 325/326, 근거 없는 값 0/1,828, 값 변조 12/350 = 3.4%(목표 0 미달). 형식별: 붙여넣기·글자 PDF·엑셀 100%, 스캔 95.7%, 섞인 입력 95.6%, 사진 91.2%.
### 요식(Dining)
- 트리거: 영업·휴무 변동, 고객의 지연·휴무 신고, 일정 변경 직후, 새벽 3시 확인.
- 점검: 요일별 영업시간·브레이크·라스트오더·휴무, 할랄·채식·아이 동반. 라스트오더: 알면 「도착+20분」이 넘을 때 탈락, 모르면 식사 종료가 마감 60분 안일 때 경고.
- 데이터: 서울 식당 1,225곳(관광공사 음식점 989 + 비건 67 + 할랄 24 + 미쉐린 신규 145), 코어 장소로 1,219곳 반영. 영업시간 사람 대조 100곳 중 99곳 일치(개선 전 87%). Google은 새벽 창에서만 호출.
- 대체: 덜 밀리는 곳 · 비슷한 곳 · 가까운 곳 축마다 후보 → 하나 먼저 적용, 나머지는 「다른 안」.
- 예시(자료): 점심 70분 지연 → 브레이크타임에 걸림 → 도보 6분 식당으로.
- 한계: 낮 임시휴무를 시스템이 스스로 찾는 기능은 구현 대상(지금은 고객 신고로 대체). **실시간 웨이팅(대기시간) API는 없다** — 캐치테이블 등은 자동 수집 끔, 지도 링크로 확인하게 한다.
### 액티비티(Activity)
- 범위: 여행지에서 하는 활동 그 자체(관광공사 신분류체계 NA 자연관광·HS 역사관광·VE 문화관광·LS 레저스포츠·EX 체험관광·EV 축제·공연·행사·SH 쇼핑), 서울 후보 805행.
- 점검: 운영일·휴무·운영시간, 날씨·대기질 조건, 예약 시간.
- 대체 우선순위(피그마): 공통 고려 칼럼(대분류·중분류·소분류·타입·구·운영시간·휴무일). 같은 대분류를 고정하고 1순위 소분류만 다른 곳 → 2순위 중분류까지 다른 곳 → 3순위 구가 다른 곳.
- 예시(자료): 잠실 스카이타워 전망 → 미세먼지+소나기 경보 → 실내 아쿠아리움.
### 이동(Mobility) — 「모든 에이전트가 쓰는 이동 판정기」(피그마 발표용)
- 트리거: 일정 짜기(처음), 식당을 바꿀 때 앞뒤 이동, 활동을 바꿀 때 앞뒤 이동, 재계획(운행 중단·무정차 사고 뒤).
- 판정: 지하철·버스 시간표 46만 행(판정 대상 444,915행) + 역 출구·환승 도보·따릉이·혼잡으로 「제시간?」 → 성립(이 시각에 나가면 제시간 도착 — 출발 시각·경로·요금을 일정에 채움) / 불가(막차·배차로 못 맞춤, 이유와 함께 → 다른 경로·시간 조정).
- 모든 답에 근거 등급: 확정(시간표 계산) · 추정(어림·통계) · 근거 없음(말하지 않음) + 확인 시각.
- 검증: 판정 회귀 시험 168건 어긋남 0, 자동 생성 점검 사례 12,032건. 학습 모델(HistGradientBoosting)은 근거 부족을 「성립」으로 바꾸는 오류 때문에 채택하지 않았다 — 판정은 코드.
- 예시: 채팅의 「09:04 출발 · 2호선 신대방→을지로3가 → 3호선 을지로3가→경복궁 · 약 62분(시간표 판정)」.

## 7-A. ★사용자 결정(2026-10-01) — 시스템 아키텍처는 이 모양으로 그린다
- **접속 경로 둘: ① 웹(휴대폰 브라우저) ② 개인 에이전트 앱**(사용자가 쓰는 AI 비서 앱이 우리 API로 붙는다 — MCP·A2A·REST).
  받는 쪽: 디스코드 알림 · 로그인 없는 여행계획서 링크.
- **외부 데이터 6종을 3분마다 수집한다**(무료 소스만, 결정 D-017): 날씨(Open-Meteo) · 기상청 특보 · 단기예보 · 재난문자 · ITS 교통 사건 · UTIC 교통 사건.
  3분인 이유: 이동 사건 골든타임 목표(감지~알림 p95 5분 이하)에서 거꾸로 잡았다 — 수집 대기 최대 3분 + 처리 약 1분. 하루 호출 480회 / 한도 1,000회 = 48%.
  그 밖에: 에어코리아 대기질도 3분(480/500), 관광공사 장소는 3분마다 2곳씩 돌아가며, Google 영업시간은 새벽 3시에만.
- **흐름**: 수집한 값이 바뀌면 → 그 값에 걸린 일정 항목만 에이전트가 판정(사건 없음) → 전부 통과면 아무것도 안 함(사건 0·알림 0)
  → 하나라도 불가면 여행당 사건 1건 → 코어가 액티비티 → 요식 → 이동 순으로 대안을 받는다(앞 에이전트 초안을 다음에 넘긴다, 에이전트끼리는 부르지 않는다)
  → **전체 일정 재검증** → 안 맞으면 다음 후보로 다시(반복) → 맞으면 **새 판 1번 + 알림 1번**. 고객 신고는 3분을 기다리지 않고 바로 들어간다.
- 상시 작업: 외부 감시 수집(3분) · 되잡기(1분마다: 분류·라우팅이 멈춘 사건 다시 잡기) · 알림 배달(3회 재시도).
- 즉 **에이전트는 한 번 답하고 끝나지 않고, 여행이 끝날 때까지 계속 돈다.** 이것이 지속 관리이고, 에이전트라고 부르는 이유다.

## 4-A. ★공통 흐름은 반복 루프로 그린다(사용자 지적 2026-10-01)
- 「에이전트가 계획하고 일정 조율을 **반복**하는 루프가 있고, 그게 **다 통과하면 다음으로** 넘어간다. 지속적인 시스템 관리가 없으면 에이전트가 아니다.」

- **여행 중 일정을 바꾼 비율 · 현지 재검색 비율 — 한국인 조사는 찾지 못했다.** 확인 범위: 웹 검색 3회(국민여행조사 기사 · 「국내여행 일정 변경 경험」 · 「날씨 때문에 일정 변경」). 에어비앤비 조사(숙박 문제로 목적지 변경 26.7%)는 여행 **전** 계획 변경이라 같은 고리에 쓰지 않는다.
