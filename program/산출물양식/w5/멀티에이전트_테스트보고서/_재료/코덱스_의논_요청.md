# 의논 요청: 「멀티 에이전트 테스트 계획 및 결과 보고서」에 무엇을 더 넣어야 하나

너는 triPilot 프로젝트(서울 자유여행자의 일정을 받아 여행 내내 지키는 에이전트, 부트캠프 최종 프로젝트)의 산출물 검토자다. 읽기만 한다. 파일을 고치지 않는다.

## 사용자가 이 보고서에 넣으라고 한 것
- 소스코드 포함
- sLLM 파인튜닝 평가 결과
- 구성: 분야별로 성능이 잘 나오는 sLLM 몇 개를 고르고, 규칙 기반 · ML 모델로 선택지를 구성하고, MoE 처럼 상황마다 가장 알맞은 것을 Jev 계열 모델이 골라 배치해 사용자 질의에 답하는 구성 — 이 구성의 성능 평가
- 부족한 sLLM 을 끌어올리는 파인튜닝 후 성능
- 로컬 sLLM · LLM 과 상용 API 모델의 성능 비교
- 기존 A · B · C 채점(요청 둘 66문제의 채점 방식)과 시험 세트 평가
- 「추가로 더 필요한 자료와 내용은 코덱스와 논의해서 채워 넣어라」

## 알아야 할 결정 · 사실 (어기지 마라)
- 고객 건을 사람에게 넘기지 않는다(사람은 오류 리포트만 본다).
- 에이전트는 요식 · 액티비티 둘이고, 이동은 모두가 부르는 공용 판정 도구다(2026-10-02 결정). 코드 등록은 Activity · Dining · Mobility 셋.
- LangGraph 는 쓰지 않는다(양식 4.1 제목에 있어도 쓴다고 적지 않는다). 흐름은 Controller 와 Case 상태기계가 정한다.
- 쇼핑몰(커머스) 시절 자료 · 시험 · 평가는 쓰지 않는다(D-023).
- 가격은 정하지 않았다 — 넣지 않는다.
- 5단계를 끝까지 이은 시험은 없다. 진행 중인 학습(Kanana-2-3B 등)은 결과로 쓰지 않는다.

## 네가 할 일
1. 양식의 각 절(1.1 ~ 5.2)마다: 채울 재료가 이미 있는지 / 어디 있는지(경로) / 비어 있으면 무엇이 필요한지를 표로 낸다.
   특히 모델 평가 말고 **cs 프로젝트 쪽 시험 기록**을 찾아라: `final_project_cs` 의 tests/(architecture · contract · unit · integration · e2e · security · scenario) 건수와 마지막 실행 결과, `wiki/records/evidence/DoD-*.md`, `wiki/quality/*`, 시나리오 재생(replay) 기록, RAG(벡터 검색) 정확도 기록, MCP 도구 시험, DB 연동 시험, 예외 · 방어(대체 소스 · 서버 끄기 · 중복 방지) 시험. 경로와 숫자(분자/분모 · 날짜)를 적는다. 쇼핑몰 시절 기록은 빼고 표시한다.
2. 사용자 요구 대비 **빠진 내용 · 자료** 목록(우선순위 순, 많아야 10개)과, 각각 지금 있는 자료로 채울 수 있는지 / 새로 재야 하는지.
3. 보고서에 넣을 **소스코드 발췌 후보**(파일 · 함수 · 줄 범위, 각 10~40줄) 5~8개 — 조합 단계 · 채점 · 파인튜닝 · 라우팅 · 에이전트 판정이 보이는 것.
4. 보고서에서 **조심해서 써야 할 표현** 목록(공정 비교 아님 · 출제자 편향 · 1회 측정 · 합성 문장 등)과 권하는 문구.
5. 「이 구성이 사용자가 말한 MoE식 배치를 실제로 하는가」에 대한 솔직한 판정 한 문단(이어 붙인 시험이 없다는 점 포함).

결과는 한국어 마크다운 하나로. 모르는 것은 모른다고 쓰고, 찾지 못한 것은 찾아본 범위를 적는다.
