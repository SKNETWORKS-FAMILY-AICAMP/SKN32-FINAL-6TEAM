기획서의 일곱 절은 그대로 유지한다. **1절에서 투자 판단의 전체 논리를 제시하고, 2~3절에서 사업성을 입증하며, 4~6절에서 실현 가능성을 설명하고, 7절에서 실행 책임과 승인 조건을 확정하는 구조로 설계한다.**

아래는 작성할 내용의 명세다. 현재 프로젝트의 사업 내용이나 기술 결정을 채운 문서가 아니다.

분량은 **공백을 제외한 본문·표 안의 글자 수**를 기준으로 한다. 다음 비중은 업계의 공인 기준이 아니라, 이번 경영진 검토용 템플릿의 편집 기준으로 제안한다.

|---|---:|---|
| 1 프로젝트 주제 | 8% | 무엇에 얼마를 투입할지 첫 절에서 판단하게 한다. |

## 2 문제 정의

**이 절이 답하는 질문**

> 어떤 고객이 어떤 상황에서 얼마나 큰 손실을 겪으며, 기존 방식으로 해결되지 않는 원인은 무엇인가?

**반드시 들어가는 것**

- **우선 고객과 발생 상황:** 직업·연령만 적지 않고 실제 업무나 행동, 문제 발생 계기와 제약을 적는다. 같은 사람도 상황에 따라 구매 필요가 달라지기 때문이다.
- **현재 해결 과정:** 고객이 쓰는 도구·인력·우회 방법과 처리 단계를 적는다. 대체할 비용과 행동을 알아야 도입 효과를 계산할 수 있기 때문이다.
- **문제의 빈도·강도·손실:** 시간, 비용, 오류, 포기, 재작업 등 최소 하나를 수치화하거나 측정 계획으로 제시한다. 불편하다는 진술만으로 투자 우선순위를 정할 수 없기 때문이다.
- **증상과 원인의 구분:** 관찰된 현상과 원인 가설을 분리한다. 원인을 잘못 잡으면 기능을 만들어도 손실이 줄지 않기 때문이다.
- **기존 대안의 잔여 공백:** 어느 조건에서 무엇이 해결되지 않는지 적고 3절의 경쟁 근거를 참조한다. 경쟁사가 기능을 제공한다는 사실과 고객 문제가 해결됐다는 사실을 구분하기 위해서다.
- **고객 성과 목표와 우선순위:** 해결 후 달라질 결과, 이번에 해결할 문제, 보류할 문제를 적는다. 기능 목록이 문제 정의를 대체하지 않게 하기 위해서다.

**형태**

현재 과정을 짧은 문단으로 설명하고 다음 표를 둔다. 단계 간 전달 실패가 문제의 원인이면 현재 과정 그림 1개를 추가한다.

| 문제·근거표 | 문제 ID / 대상·발생 상황 / 현재 해결 방식 / 빈도·손실 / 근거·상태·표본 / 원인 가설 / 남는 공백 |
| 성과 목표표 | 문제 ID / 고객 성과 지표 / 현재값 / 목표값 / 측정 방법·기간 / 이번 범위·우선순위 |

인터뷰는 대상 선정 방법과 표본 수를 적고, 고객 진술·관찰·작성자의 해석을 구분한다. 인터뷰 수가 작으면 문제 발견의 근거로 쓰되 전체 고객의 발생률로 확대하지 않는다.

약 **1,900~2,900자, 표 2개**, 필요한 경우 과정 그림 1개로 작성한다. 핵심 문제는 통상 2~4개로 압축하여 뒤의 구현·성과 지표와 연결한다.

**흔한 실패**

## 3 시장조사 및 BM 분석

**이 절이 답하는 질문**

> 도달 가능한 구매자가 기존 대안 대신 비용을 지불할 이유가 있으며, 그들을 확보하고 서비스를 제공한 뒤 이익이 남는가?

**반드시 들어가는 것**

- **시장 경계와 우선 구매자:** 사용자·수혜자·지불자·구매 승인자를 구분하고 지역·상품 범위·분석 기간을 고정한다. 분모가 달라지면 시장·전환율·가격을 연결할 수 없기 때문이다.
- **TAM/SAM/SOM:** 전체 기회에서 제공 가능한 시장, 실제 획득 가능한 규모까지 계산한다. 산업 규모를 곧바로 우리 매출 기회로 제시하지 않기 위해서다.
- **직접 경쟁·인접 대안·현상 유지:** 유료 제품뿐 아니라 수작업·무료 도구·자체 구축도 비교한다. 고객은 구매하지 않는 선택도 하기 때문이다.
- **구매 이유와 전환 장벽:** 기존 대안 대비 개선 결과, 가격 수용 근거, 도입·전환 비용을 적는다. 기능 차이가 구매 이유로 이어지는지 확인하기 위해서다.
- **고객 획득 방식:** 채널별 도달량·전환율·영업 기간·획득비를 적는다. SOM과 매출 목표가 실제 유통 경로에서 나오게 하기 위해서다.
- **가격·원가·기여이익·고정비·손익분기:** 사업을 유지하는 최소 조건을 수치 또는 명시적 추정 범위로 제시한다. 가격과 LLM 비용만으로는 수익성을 판단할 수 없기 때문이다.
- **하방 손익과 자금 소요:** 판매 부진·비용 악화·출시 지연이 손익과 현금에 미치는 영향을 적는다. 정상 운영 흑자가 투자 기간의 자금 부족을 가리지 않게 하기 위해서다.
- **종합 사업 판단:** 시장·경쟁·수익·데이터·구현별 현재 판단과 추가 투자 조건을 적는다. 서로 다른 근거를 하나의 추진 결정으로 연결하기 위해서다.

**시장 규모의 깊이**

| 구분 | 요구하는 계산 | 허용하지 않는 대체 |
|---|---|---|
| TAM | 정의한 문제에 대해 구매 가능한 전체 고객·사용량과 연간 지출 기회를 산정한다. 직접 통계가 없으면 고객 수×구매 빈도×가격 가정으로 추정한다. | 관광 총지출·산업 총매출을 그대로 해당 소프트웨어 시장으로 사용하지 않는다. |

세 단계 모두 **대상 정의·산식·단위·기간·입력 근거**를 요구한다. 숫자는 확인 수준에 맞춰 구간으로 제시할 수 있다. 근거가 없는 정확한 숫자보다 범위를 명시한 추정을 사용한다.

시장 통계가 사람 수이고 과금이 팀·계정·거래 단위라면 환산 가정을 드러낸다. 서로 다른 연도의 누적 이용자·활성 사용자·구매자를 섞지 않는다. SOM은 매출과 함께 제시하되 획득비와 운영 능력이 그 물량을 감당하는지도 확인한다.

사내 개선 프로젝트는 외부 판매시장을 억지로 만들지 않는다. 같은 표에서 전체 적용 가능 업무, 실제 도입 가능한 조직, 기간 내 전환 가능한 업무량을 산정하고 편익·예산으로 연결한다.

**경쟁 분석의 깊이**

직접 경쟁, 인접 대안, 현상 유지를 모두 포함한다. 통상 4~6개 비교 대상을 선정하되, 선정 이유가 분명하면 수 자체를 채우기 위해 늘리지 않는다.

핵심 경쟁 대안 2~3개는 기능 유무를 넘어 **동일한 고객 과제에서 결과·시간·비용·실패 대응**을 비교한다. 직접 시험하지 않았다면 공식 안내와 시험 계획까지만 기록한다. 시험에는 버전·요금제·설정·일시·입력 조건을 붙인다.

“기능을 확인하지 못함”, “시험할 수 없음”, “시험에서 실패함”을 구분한다. 차별화는 현재 우위인지 구현 목표인지 표시한다. 사업 검토서 v3의 Mindtrip 비교가 공식 자료·사용자 관찰·당사 목표를 분리한 방식이 이 기준의 근거다. [경쟁 비교의 확인 범위](C:/Users/playdata2/Documents/final_workspace/team_branch/me/travel-agent-business-review_v3.md:69)

계산 관계는 본문에서 재현할 수 있게 한다.

- `CAC = 정한 획득 지출 ÷ 신규 유료 고객 수`로 정의한다.

- `기여이익Ⅱ = 기여이익Ⅰ − 해당 기간·고객군의 획득비`로 표시한다.
- `기간 손익 = 기간 순매출 − 제공 변동비 − 획득비 − 고정비`로 계산한다.
- 단위와 기간이 일치하고 단위당 기여이익Ⅱ가 양수인 단순 모델에서만 `손익분기 수량 = 고정비 ÷ 단위당 기여이익Ⅱ`를 사용한다.

신규 고객과 재구매 거래를 구분하여 CAC를 매 거래에 중복 부과하지 않는다. 구독형은 고객군별 유지 기간과 누적 기여이익을 이용해 CAC 회수 시점을 계산한다. 유지율이 미확보이면 관측 기간 밖의 LTV를 확정 수익처럼 제시하지 않는다.

고정비가 인력 증원에 따라 계단식으로 증가하면 단순 나눗셈 대신 규모 구간별 손익으로 검토한다. 사내 개선 프로젝트는 가격·CAC의 적용 여부를 밝히고, 도입·전환·교육비를 포함한 편익과 투자 회수를 계산한다.

**별도 문서로 넘기는 기준**

API별 전체 단가표, 월별 계산 원장, 인터뷰 원문, 경쟁 시험 전체 기록은 분리할 수 있다. 다만 **그 내용을 빼면 추진 여부·필요 자금·가격·범위가 달라지는 정보는 본문에 남긴다.** 본문에는 결론, 핵심 산식과 가정, 하방, 상세 문서의 버전·위치를 함께 적는다.

**분량 기준**

약 **5,600~8,400자, 표 8개**로 작성한다. 수익 항목이 복잡하면 단위경제표를 원가표와 기여이익표로 나눈다. 출처 개수를 목표로 삼지 않고 투자 결론을 좌우하는 주장에 근거가 연결됐는지 확인한다.

**흔한 실패**

- 시장 통계·경쟁사 이름·가격 하나를 나열하고 사업성 분석이라고 부른다.
- 사용자 접점을 곧바로 구매자로 간주한다.
- LLM 비용만 차감하여 높은 이익률을 제시한다.
- 미확보가 있다는 이유로 조건부 손익 계산까지 모두 생략한다.
- 다른 고객·상품·운영 조건에서 만든 손익을 현재안으로 옮긴다.

**판정 기준**

검토자가 **시장 규모→도달 고객→유료 고객→매출→기여이익→손익·필요 자금**을 계산으로 따라갈 수 있는지 확인한다. 어느 가정이 바뀌면 추진 결론이 뒤집히는지, 그 가정을 누가 언제 검증하는지도 확인한다.

## 4 시스템 구성 기획

**이 절이 답하는 질문**

> 약속한 고객 결과를 어떤 구성과 운영 방식으로 제공하며, 실패했을 때 어디까지 책임지고 복구하는가?

**반드시 들어가는 것**

- **고객의 전체 이용 흐름:** 시작 조건·입력·핵심 처리·결과·후속 처리를 적는다. 모듈이 존재하는 것과 고객 업무가 완결되는 것을 구분하기 위해서다.
- **시스템 경계와 책임:** 자체 개발, 외부 구매·연동, 고객 수행, 사람 운영을 구분한다. 제공 약속과 통제 가능한 범위를 일치시키기 위해서다.
- **핵심 구성과 선택 이유:** 각 구성요소의 역할, 대안, 선택 이유와 대가를 적는다. 스택 목록만으로는 일정·비용·운영 위험을 판단할 수 없기 때문이다.
- **MVP·출시·확장 범위:** 이번에 검증할 흐름과 실제 판매에 필요한 추가 조건을 구분한다. 시연 성공을 출시 가능성으로 확대하지 않기 위해서다.
- **비기능·운영 조건:** 처리량·지연·가용성·접근 권한·복구·관측·지원 범위를 수치 또는 검증 과제로 적는다. 이러한 조건이 원가와 실제 사용 가능성을 결정하기 때문이다.
- **실패·예외·중단 경로:** 외부 연결 실패, 잘못된 입력, 중복 실행, 데이터 부족, 사람 인계와 복구 원칙을 적는다. 정상 흐름만으로는 운영 가능성을 판단할 수 없기 때문이다.

**형태**

| 형태 | 포함 내용·열 이름 |
|---|---|
| 구성도 1개 | 사용자·외부 시스템·우리 시스템의 경계, 데이터 흐름, 권한·실행 경계를 표시한다. |
| 핵심 흐름 그림 1개 | 정상 처리와 주요 실패·인계·복구 경로를 표시한다. 단순 프로젝트는 구성도와 합친다. |
| 구성·범위표 | 구성요소 / 고객 결과·문제 ID / 역할·입출력 / 자체·외부·사람 구분 / 선택 이유·대가 / 이번 범위·상태 / 선행 조건 |
| 운영 조건표 | 운영 지표·위험 / 목표·상한 / 산정 근거·예상 부하 / 실패 시 처리 / 검증 방법 / 원가 영향·담당 |

상세 함수명·DB 필드·전체 API 명세는 별도 기술 문서로 연결한다. 본문에는 데이터 소유권, 실행 권한, 일관성처럼 제품 약속과 위험을 설명하는 수준을 남긴다.

**분량 기준**

약 **2,100~3,100자, 표 2개, 그림 1~2개**로 작성한다.

**흔한 실패**

- 시스템 구성도를 도구 로고 모음으로 만든다.
- 기술 결정의 경위와 수정 내역이 본문을 차지한다.
- 사람 인계를 적지만 담당 조직·운영 시간·비용은 없다.
- 시연에서 제외한 운영 기능을 판매 조건에서도 제외할 수 있다고 간주한다.

**판정 기준**

핵심 고객 흐름마다 **입력→처리→결과→실패 대응**이 이어지는지 확인한다. 3절의 판매량을 처리할 수 있는지, 그 부하와 지원 수준이 원가에 반영됐는지도 확인한다.

## 5 모델링 계획

**이 절이 답하는 질문**

> 어떤 판단·예측·생성을 어떤 방식으로 수행하며, 기존 대안보다 유효한 결과를 허용 비용 안에서 낸다는 것을 어떻게 검증하는가?

**반드시 들어가는 것**

- **모델링 과제와 입출력:** 분류·예측·추천·최적화·생성 중 수행할 과제와 정답·성공의 정의를 적는다. 모델 이름을 선정하는 것과 문제를 정의하는 것을 구분하기 위해서다.
- **규칙·통계·최적화·AI의 역할:** 어떤 처리를 어느 방식에 맡기는지 적는다. 계산 가능한 조건까지 생성 모델에 맡기거나 필요 없는 AI를 도입하지 않기 위해서다.
- **기준선과 제안 방식:** 현재 업무 방식 또는 단순한 대안과 비교한다. 복잡도를 늘린 대가가 결과 개선으로 돌아오는지 확인하기 위해서다.
- **개발·학습·적용 계획:** 외부 모델 사용, 자체 학습, 검색 결합 등 필요한 방식과 선택 이유를 적는다. 학습이 필요 없으면 그 사실을 명시하여 불필요한 작업을 막는다.
- **평가 설계:** 평가 데이터, 표본 선정, 정답 작성, 분리 방식, 지표·통과선·실패선·비용·지연을 적는다. 평가 결과가 운영 성능을 얼마나 설명하는지 판단하기 위해서다.
- **배포 후 관리:** 성능 저하 감시, 버전 관리, 사람 검토, 기권·대체·복구 기준을 적는다. 최초 시험 통과가 지속 성능을 보장하지 않기 때문이다.

AI를 쓰지 않는 프로젝트도 절을 삭제하지 않는다. 업무 규칙·의사결정 로직·최적화 또는 계산 모델의 설계와 검증을 작성한다.

## 7 역할분담(R&R)

**이 절이 답하는 질문**

> 누가 어떤 결과를 언제까지 책임지고, 무엇을 기준으로 승인하며, 지연·실패·미결정이 발생하면 누가 조정하는가?

**반드시 들어가는 것**

- **산출물 단위의 책임:** 모듈 이름이나 직무가 아니라 검수 가능한 결과로 업무를 정의한다. “백엔드 담당”만으로는 납품과 완료를 판정할 수 없기 때문이다.
- **수행자와 최종 책임자:** 수행 책임 R과 최종 승인·결과 책임 A를 구분한다. 공동 작업에서도 최종 결정을 내릴 사람이 필요하기 때문이다.
- **시장·판매·재무·운영 책임:** 개발 외에 고객 모집, 구매 검증, 가격·원가, 데이터 권한, 출시 후 지원의 책임을 배정한다. 사업 검증이 “전체 담당”으로 남으면 개발 일정에 밀리기 때문이다.
- **마감·공수·가용 인력·의존성:** 담당자의 실제 투입 가능 시간과 선행 작업을 함께 적는다. 사람 이름이 있다는 사실만으로 실행 가능한 일정이 되지 않기 때문이다.
- **단계별 검수와 자원 승인:** 다음 단계에 넘어갈 증거, 승인자, 사용할 예산, 실패 시 조치를 적는다. 기능 완성과 추가 투자 결정을 연결하기 위해서다.
- **미확보·리스크·변경 관리:** 해결 책임자·기한·미해결 시 조치·변경 승인권을 적는다. 미확보 표시가 문제를 방치하는 수단이 되지 않게 하기 위해서다.
- **인수인계와 운영 책임:** 출시 이후 누가 유지·지원·장애 대응을 맡는지 적는다. 프로젝트 종료가 서비스 책임의 공백으로 이어지지 않게 하기 위해서다.

**형태**

| 표 | 열 이름 |
|---|---|
| 책임·실행표 | 산출물·작업 ID / 완료·인수 기준 / 수행자 R / 최종 책임·승인자 A / 협의·인계 대상 / 시작·마감 / 예상 공수·가용 시간 / 선행 작업 / 상태 |
| 단계별 검수표 | 단계·검토일 / 필요한 사업·기술 증거 / 정량 통과·중단 조건 / 승인자 / 다음 단계 예산·인력 / 미충족 시 축소·재검증·중단 |
| 미결정·리스크 관리표 | ID·관련 절 / 미확보·리스크·변경 사항 / 영향·발생 조건 / 해결·검증 방법 / 책임자 / 기한 / 미해결 시 조치 / 결정·완료 근거 |

산출물별 A는 원칙적으로 한 명을 지정한다. 작은 팀은 R과 A를 겸할 수 있으나 책임자를 “전체”로 두지 않는다. 예산·범위 변경의 승인권과 이견을 상위 책임자에게 올리는 조건은 짧은 운영 문단으로 명시한다.

사업 실증과 기술 개발은 필요한 범위에서 병행한다. 핵심 구매 가설을 개발 완료 뒤에야 확인하는 일정이라면 그 순서를 택한 이유와 위험을 적는다.

**흔한 실패**

- 이름 옆에 기술 영역만 적는다.

**판정 기준**

각 필수 산출물에 **수행자·최종 책임자·기한·완료 기준**이 있는지 확인한다. 선행 작업과 가용 시간을 고려해 일정이 성립하는지, 사업·기술 검증 실패 시 누가 자원 투입을 중단하거나 범위를 바꾸는지 확인한다.
