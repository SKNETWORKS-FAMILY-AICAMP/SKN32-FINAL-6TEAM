**2. 작업 하나의 ‘좋은 모양’**

한 행은 **하나의 책임 아래 산출물을 인수할 수 있는 작업 단위**로 작성한다. C셀은 다음 문법을 사용한다. 꺾쇠 안에는 프로젝트별 값을 넣는다.

```text
작업: <대상에 수행할 행동과 도달할 결과>
산출: <결과물 이름·저장 위치·인수할 버전>
완료: <검사 조건·기대 결과·허용 한계>; 검수=<판정자>
연결: REQ=<ID 목록>; DoD=<ID 목록 또는 비적용 사유>
선행: <Task ID / 관계 / 시차 / 받아야 할 결과>; 없으면 <시작점인 이유>
공수: <근거표시> <기준값·범위>인시; 구성=<수행·검증·인계>
기간: <순작업 기간>; 대기=<외부 응답·승인 등과 기간 근거>
경로: <계산 기준일·총여유·임계 여부 또는 미산정 사유>
절삭: <유지 또는 순위·묶음 ID>; 이유=<보존할 약속 또는 제외 영향>
추적: <필요한 상태상세·예상 완료일·실적>; 근거=<C셀 메모의 항목>
```

| 필수 정보 | 작성 규칙과 이유 | 확인 방법 |
|---|---|---|
| **산출물** | 파일뿐 아니라 배포 결과·검증 기록·결정 기록도 허용한다. 회의·조사는 그 결과로 남는 결정이나 근거 묶음을 산출물로 잡는다. 활동했다는 사실만으로 후속 작업이 시작되지는 않기 때문이다. | 후속 담당자가 실제로 받을 대상과 위치가 특정된다. |
| **완료 기준** | `검토 완료` 대신 무엇을 검사해 어떤 결과여야 하는지 적는다. 수치 기준은 분모·대상·허용치까지 연결한다. | 담당자와 검수자가 각각 판정했을 때 결과가 일치한다. |
| **선행** | 작업명 대신 ID와 인수 조건을 적는다. 선행 작업의 상태가 완료여도 필요한 결과가 없으면 착수할 수 없기 때문이다. | 선행 행과 산출물을 따라가 착수 가능 여부를 확인한다. |
| **공수와 기간** | 사람의 투입량과 달력상 경과시간을 분리한다. 외부 응답을 기다리는 3일은 사람의 작업 3일과 다르기 때문이다. | 인시 합계와 시작·마감 사이의 기간을 각각 설명할 수 있다. |
| **담당과 검수** | 책임자 한 명과 완료를 판정할 주체를 명시한다. 자기 확인을 허용하는 업무도 그 규칙을 밝힌다. | 책임자·검수자의 가용시간과 완료 판정 기록이 존재한다. |
| **기한** | 구현·검증·인계가 끝나는 날짜를 잡는다. 산출물이 만들어졌어도 인수하지 못하면 다음 작업은 지연되기 때문이다. | 마지막 검수와 인계가 마감 이전에 배치된다. |

`해당 없음`은 사유와 함께 사용한다. 빈칸이나 `-`로 미확보·비적용·누락을 구분하지 못하게 하지 않는다.

마일스톤도 기존 표의 행으로 기록한다. C셀에 `종류=마일스톤`과 통과 조건을 적고, 시작일과 마감일을 같은 날짜로 둔다. 기간·공수는 0으로 기록하며, 준비·검수에 드는 작업은 실제 작업 행에 배정한다. 행사 날짜에 준비 공수가 묻히는 일을 막기 위한 규칙이다.

**3. 분해 깊이와 중단 기준**

`주요 업무`가 상위 묶음을, 작업 행이 관리 가능한 최하위 단위를 나타내도록 한다. 상위 묶음을 별도의 실행 작업으로 중복 등록해 공수를 다시 합산하지 않는다.

| 상황 | 분해 또는 통합 규칙 | 이유와 판정 기준 |
|---|---|---|
| 한 행 안에서 책임자가 바뀐다. | 인계되는 산출물을 경계로 분리한다. | 누가 어떤 부분을 지연시키는지와 인계 시점을 확인할 수 있어야 한다. |
| 일부 결과가 먼저 후속 작업에 쓰인다. | 먼저 인수할 수 있는 결과를 별도 작업으로 분리한다. | 실제 병렬 수행 기회를 일정에 드러내기 위해서다. |
| 완료 기준·선행 조건·절삭 여부가 다르다. | 서로 다른 조건을 가진 부분을 분리한다. | 한 행의 상태나 우선순위로 서로 다른 판단을 표현할 수 없기 때문이다. |
| 한 번의 진행 점검 주기 안에 객관적 진전을 확인하기 어렵다. | 검증 가능한 중간 산출물을 기준으로 나눈다. | 오랫동안 `진행중`만 반복되는 작업을 줄이기 위해서다. |
| 같은 담당자가 같은 결과를 만들기 위해 짧은 동작을 연속 수행한다. | 체크리스트로 묶는다. 세부 동작은 작업 티켓으로 넘긴다. | 파일 생성·함수 수정 같은 동작마다 WBS 행을 만들면 관리비용과 완료 건수만 늘어나기 때문이다. |
| 범위와 접근 방법을 아직 모른다. | 기간을 제한한 조사 작업을 먼저 만든다. | 모르는 구현을 잘게 나열하면 분해된 것처럼 보일 뿐, 추정 근거는 생기지 않기 때문이다. |
| 기능을 이미 구현했지만 검증하지 않았다. | 남은 검증·인수 작업을 명시한다. | 기존 자산의 존재가 이번 요구사항의 충족을 보증하지 않기 때문이다. |

초기 운영 기준으로 최하위 작업은 **담당자의 유효 작업시간 기준 0.5~5일 정도**를 검토한다. 이는 보편적인 생산성 수치가 아니라, 점검과 인계를 가능하게 하기 위한 시작 규칙이다. 프로젝트의 점검 주기·업무 성격에 맞춰 조정한다.

너무 잘게 쪼갠 WBS는 다음 방식으로 실패한다.

- 사소한 작업의 완료 건수가 늘어 실제 산출물이 없어도 진척률이 높아진다.
- 일정·상태 갱신과 인계에 드는 시간이 작업 자체보다 커진다.
- 개인의 내부 작업 순서까지 선행 관계로 등록해 병렬 수행 가능성을 숨긴다.
- 공통 검증과 통합이 여러 행 사이에서 빠지거나 중복된다.

**분해를 멈추는 조건은 ‘더 작은 행동이 없는가’가 아니라, ‘이 단위로 책임·추정·인수·지연 원인을 관리할 수 있는가’로 정한다.**

**4. 선행 관계와 임계 경로를 기존 칸에 표시하는 방법**

C셀의 `선행`은 다음과 같이 기록한다.

```text
선행: <Task ID> / FS / +0영업일 / <인수할 결과>
```

기본 관계는 선행 완료 후 후행 시작인 `FS`로 둔다. 동시 착수가 필요한 경우에는 `SS`, 종료 시점을 연결하는 경우에는 `FF`를 명시하고 이유를 붙인다. 복잡한 관계가 꼭 필요하지 않으면 중간 인수 작업으로 나눈다. 관계가 짧고 명확해야 일정 오류를 검토하기 쉽기 때문이다.

| 요소 | 기록 위치와 내용 | 필요한 이유 |
|---|---|---|
| 논리적 선행 | 후행 작업 C셀에 선행 ID·관계·시차·받는 결과를 적는다. | 날짜의 선후만으로는 실제 의존 관계를 알 수 없다. |
| 외부 대기 | C셀 `대기`에 응답 주체·기한·근거를 적는다. 별도 책임과 추적이 필요하면 외부 결과 확보 작업으로 등록한다. | 사람을 더 투입해도 줄지 않는 기간을 구별해야 한다. |
| 자원 때문에 생긴 순서 | C셀에 `자원 순서`임을 명시한다. | 담당자가 같아서 순서를 정한 것을 기술적으로 불가피한 의존성으로 오인하지 않게 한다. |
| 경로 계산 결과 | C셀 `경로`에 계산 기준일·잔여 기간·총여유·임계 여부를 적는다. 상세 계산은 메모에 둔다. | 색이나 별표만으로는 임계 판정의 근거를 재현할 수 없다. |
| 미산정 | `경로: [미확보] <부족한 선행·기간·달력 정보>; 확보 담당·기한`으로 적는다. | 계산 입력이 없는 경로를 안전한 일정으로 판단하지 않게 한다. |

계산 방식은 A1 메모에서 고정한다. 기본 FS 관계의 경우, 동일한 작업일 달력으로 다음 값을 계산한다.

```text
빠른 시작 = 선행 작업의 빠른 종료 + 시차 중 최댓값
빠른 종료 = 빠른 시작 + 작업 기간

늦은 종료 = 후행 작업의 늦은 시작 - 시차 중 최솟값
늦은 시작 = 늦은 종료 - 작업 기간

총여유 = 늦은 시작 - 빠른 시작
```

작업일 경계와 시작·종료일 포함 규칙을 함께 명시한다. 날짜를 직접 더하는 방식과 기간을 더하는 방식이 섞여 하루씩 어긋나는 일을 막기 위해서다.

프로젝트의 가장 빠른 종료 시점을 기준으로 역산했을 때 **총여유가 0인 경로를 임계 경로로 표시한다.** 고정 납기 기준 계산에서 음수 여유가 나오면 필요한 단축량을 별도로 표시한다. 임계 경로는 여러 개일 수 있다.

담당자 중복 배정과 외부 대기를 반영하지 않은 계산은 `논리 관계 기준 잠정 경로`라고 표시한다. 변경·실적 반영 후에는 남은 기간으로 다시 계산한다. 오래된 빨간색 표시를 유지하면 현재의 병목을 놓치기 때문이다.

**5. 요구사항·DoD와 연결하는 방법**

요구사항은 **무엇을 충족해야 하는가**, 작업별 완료 기준은 **이 작업을 언제 인수하는가**, 프로젝트 DoD는 **최종 결과를 어떤 조건으로 통과시키는가**를 각각 담당한다.

C셀의 `연결`에는 ID와 역할을 명시한다.

```text
연결: REQ=<ID: 구현 / 검증>; DoD=<ID: 기여 / 판정>
```

단순히 DoD 번호가 등장하는 것으로 충족 처리하지 않는다. 구현 작업과 검증 작업을 구별해야 “시험 계획은 있지만 구현 작업은 없는 경우”를 찾을 수 있기 때문이다.

| 확인 대상 | 확인 방법 | 통과 조건 |
|---|---|---|
| 승인된 요구사항 전체 | 요구사항 기준선의 ID 집합에서 구현·설정·데이터 준비 등 충족 작업과 검증 작업이 연결된 ID를 대조한다. | 설명되지 않은 미연결 요구사항이 없다. 기존 구현을 재사용하면 재사용 근거와 재검증 작업이 있다. |
| 프로젝트 DoD 전체 | 각 DoD에 판정 작업·담당자·판정 방법·기한이 연결되는지 확인한다. | 필요한 판정을 누가 언제 수행하는지 모두 정해져 있다. |
| 요구사항 없는 작업 | 모든 작업을 요구사항 또는 승인된 지원 업무·결정 ID로 역추적한다. | 출처 없이 추가한 범위가 없다. 관리·교육·이관 작업은 필요한 이유가 명시된다. |
| 비기능·운영 요구 | 적용 범위에 들어간 성능·접근 통제·복구·배포·교육·운영 인수 등을 같은 방식으로 대조한다. | 기능 개발에 가려진 필수 작업이 없다. |
| 범위 변경 | 제외·축소 승인 전후의 요구사항 집합을 비교한다. | 삭제한 요구사항과 승인 근거가 남는다. 분모를 조용히 줄여 충족률을 올리지 않는다. |

다음 두 지표를 구분한다.

```text
계획 커버리지 =
충족 작업과 검증 작업이 연결된 고유 요구사항 수
÷ 현재 승인 범위의 고유 요구사항 수

검증 충족률 =
연결된 필수 판정을 모두 통과한 고유 요구사항 수
÷ 현재 승인 범위의 고유 요구사항 수
```

분자·분모의 실제 ID 목록과 기준선 버전을 연결한다. 요구사항 하나가 여러 작업에 등장해도 한 번만 센다. 요구사항 목록 자체가 미확정이면 백분율 대신 **확인한 목록·미연결 목록·분모 미확정 사유**를 적는다.

전체 점검도 기존 표의 실제 작업으로 관리한다. 그 작업의 C셀 메모에 검증 기준선·누락 ID·판정 결과를 기록하므로, 별도 추적표를 양식에 추가하지 않는다.

**6. 일정 지연 시 절삭 계획을 기록하는 방법**

우선순위와 절삭 순위는 구분한다. 늦게 착수해도 되는 필수 작업이 있을 수 있으며, 당장 급한 선택 작업도 있을 수 있기 때문이다.

C셀에는 모든 작업에 `절삭: 유지` 또는 `절삭: <순위·묶음 ID>`를 표시한다. 절삭 후보의 상세는 다음 내용을 포함한다.

| 필수 정보 | 무엇을 적는가 | 왜 필요한가 |
|---|---|---|
| 검토 조건 | 예상 납기 초과·잔여 용량 부족 등 절삭을 검토할 조건과 확인 시점을 적는다. | “밀리면 뺀다”만으로는 실행 시점이 정해지지 않는다. |
| 순위와 묶음 | 어떤 작업 ID들을 함께 제외·축소할지 적는다. | 기능 일부만 빼고 테스트·화면·문서가 남는 불완전한 절삭을 막는다. |
| 잃는 결과 | 영향을 받는 요구사항·DoD·인수 조건을 적는다. | 절삭이 곧 제공 범위 변경임을 확인해야 한다. |
| 반드시 남길 기반 | 다른 필수 작업이 사용하는 공통 산출물과 선행 ID를 적는다. | 선택 기능을 빼면서 필수 기능의 기반까지 제거하는 일을 막는다. |
| 회수 가능량 | 남은 공수 절감량과 납기 단축량을 각각 추정한다. 정리·재검증 비용도 뺀다. | 이미 쓴 공수는 회수되지 않으며, 임계 경로 밖 작업을 빼도 납기는 그대로일 수 있다. |
| 결정과 재진입 | 결정권자·결정 기한·승인 기록·후속 버전 또는 재검토 조건을 적는다. | 일시 연기와 영구 제외를 구별하고 무단 범위 변경을 막는다. |

승인 전까지는 후보로 유지한다. 승인 후에는 행을 삭제하지 않고 C셀에 `범위처리=제외/연기`, 적용 기준선과 결정 근거를 남긴다. 상태를 `완료`로 바꾸지 않는다. 인수 조건 변경이 필요한 절삭은 그 결정까지 하나의 묶음으로 처리한다.

**7. 추정의 정직성과 미확인 정보 표기**

[근거 등급 규칙](</C:/Users/playdata2/Documents/final_workspace/wiki/governance/evidence-grades.md>)을 참고하되, WBS에서는 해당 정보가 **어떤 작업과 기한을 막는지**까지 적는다.

표시는 문서 전체에 한 번 붙이지 않고 **공수·기간·구현 상태 등 해당 주장 바로 옆에** 붙인다. 외부 자료나 실측값을 사용했어도 미래 작업의 예상 공수는 `[추정]`으로 기록한다.

| 표시 | 사용 조건 | 반드시 따라붙는 정보 | 금지하는 사용 |
|---|---|---|---|
| **[실측]** | 직접 확인한 실적·관찰·계산값에 사용한다. | 측정 대상과 범위, 기준일, 환경·버전, 방법, 증거 위치, 단위·표본 수를 붙인다. 계산값이면 산식과 입력값도 적는다. | 파일 존재를 기능 통과로 확장한다. 특정 표본의 실적을 모든 작업의 생산성으로 일반화한다. |
| **[외부]** | 외부 조직의 문서·응답·공개 자료를 인용할 때 사용한다. | 제공 주체, 원문 링크·문서 버전, 발행일·확인일, 적용 조건, 우리 작업에 적용할 수 있는 범위를 붙인다. | 외부 평균 공수를 우리 팀의 확정 공수로 기록한다. 회신 목표를 확정 납품일로 해석한다. |
| **[추정]** | 가정에 따라 예상값을 산정할 때 사용한다. | 추정자·추정일, 기준값·범위, 단위, 산식·유사 작업 근거, 주요 가정, 재추정 조건·시점을 붙인다. | 숫자만 쓰거나 근거 없는 소수점으로 정확한 값처럼 보이게 한다. |
| **[미확보]** | 판단에 필요한 정보·근거·결정이 없을 때 사용한다. | 모르는 대상, 필요한 자료·결정, 확보 방법, 담당자·기한, 영향을 받는 작업, 확보 전 처리 방식을 붙인다. | 빈칸이나 0으로 대체한다. 확인 기한 없이 무기한 남긴다. |
| **[미구현]** | 정한 산출물이나 동작이 아직 구현되지 않았을 때 사용한다. | 미구현 범위, 확인한 환경·버전·일자, 이미 존재하는 부분과의 경계, 구현 작업 ID, 완료 기준을 붙인다. | 계획에 적혀 있다는 이유로 구현됐다고 본다. 시험하지 않은 상태를 구현 부재로 단정한다. |

`[미구현]`은 구현 상태이며, 다른 네 표시는 근거의 성격을 나타낸다. 따라서 같은 작업에 `구현 상태=[미구현]`, `공수=[추정]`, `외부 응답 기간=[미확보]`를 함께 사용할 수 있다.

구현 여부조차 확인하지 못했다면 `[미확보] 구현 상태`로 적는다.

공수 추정에는 다음 규칙을 적용한다.

- **기본 단위는 인시로 통일한다.** 인일을 쓰면 1인일의 시간을 명시한다. 단위가 다르면 담당자별 용량과 비교할 수 없기 때문이다.
- 수행·검증·인계 공수를 구분한다. [기존 추정 기준 문서](</C:/Users/playdata2/Documents/final_workspace/wiki/delivery/estimation-baseline.md>)도 생성·검증·대기의 차이와 표본의 한계를 밝힌다. 코드 생성 속도를 전체 완료 속도로 환산하지 않는다.
- 범위를 정할 근거가 없으면 `공수: [미확보]`로 남기고, 범위를 확인할 조사 작업을 먼저 잡는다.
- 일정 비교용 임시 숫자가 꼭 필요하면 `[추정] 초기 가정·검증 근거 없음`이라고 명시한다. 이를 납기 약속의 근거로 사용하지 않는다.
- 과거 실제 투입량과 앞으로 남은 공수를 분리한다. `남은 공수 = 최초 추정 - 실제 투입`으로 자동 계산하지 않는다. 이미 더 썼어도 남은 일이 줄지 않을 수 있기 때문이다.
- 재추정 시 최초 추정·현재 추정·변경 이유를 C셀 메모에 함께 보존한다. 그래야 추정 오류와 범위 증가를 구분할 수 있다.

**8. 다른 산출물과의 경계**

| 대상 산출물 | WBS에 남기는 것 | 넘기는 것과 이유 |
|---|---|---|
| 기획서·구현계획서 | 승인 범위·기한·결정 ID, 이를 수행할 작업과 변경 영향 | 사업 배경·전략·범위 결정의 전체 논리를 넘긴다. WBS 안에 별도의 범위 정본을 만들지 않기 위해서다. |
| 요구사항 정의서 | 요구사항 ID·버전, 구현/검증 역할, 누락과 제외 상태 | 요구사항 원문·상세 수용 조건을 넘긴다. 원문이 바뀔 때 여러 복사본이 충돌하지 않게 한다. |

상태·일정의 정본을 WBS와 이슈 도구 중 어디에 둘지 A1 메모에 명시한다. 외부 도구가 정본이면 WBS의 반영 기준시각을 함께 표시한다. 두 곳에서 독립적으로 변경하면 같은 작업에 서로 다른 마감일이 생기기 때문이다.

진척률을 제시한다면 산식을 노출한다.

```text
공수 가중 완료율 =
완료한 유효 작업의 기준 공수 합
÷ 현재 승인 범위에 포함된 유효 작업의 기준 공수 합
```

부분 진행률을 근거 없이 50%·90%로 적지 않는다. 객관적인 중간 인수 단위가 있다면 그 단위로 나누어 판정한다. 공수 미확보 작업 때문에 분모가 불완전하면 전체 백분율을 보류하고, 완료·미완료·공수 미확보 작업 수를 제시한다.

최초 기준선과 변경 기준선의 범위·공수 차이도 보존한다. 절삭으로 분모가 줄어 생긴 진척률 상승을 실제 작업 완료로 오인하지 않게 하기 위해서다.
