**공통 작성 규칙**

**1. 근거의 종류와 구현 상태를 분리한다.**

`[실측]`은 근거의 종류이며, ‘운영 적용 완료’라는 상태가 아니다. SQL 파일을 읽은 사실과 운영 DB에서 제약이 활성화된 사실을 구분해야 배포되지 않은 설계가 운영 사실로 읽히지 않는다.

| 표시 | 사용 규칙 | 반드시 따라붙는 정보 | 이렇게 요구하는 이유 |
|---|---|---|---|
| `[실측]` | 직접 읽거나 실행해 확인한 사실에 붙인다. `정적 확인`, `실행 확인`, `운영 관측` 중 확인 방식을 명시한다. | 확인일, 대상 revision·환경, 범위, 명령·조회·검사 방법, 결과 위치, 결과의 한계. 수치에는 단위·표본·측정 구간을 추가한다. | 파일 존재만 확인하고 성능·배포 완료까지 주장하는 일을 막는다. |
| `[외부]` | 공급자 문서·표준·계약 등 외부 자료에서 가져온 조건에 붙인다. | 발행 주체, 문서 제목·URL 또는 계약 식별자, 버전·확인일, 해당 절, 적용 대상·조건 | 다른 버전이나 계약의 조건을 현재 설계에 잘못 적용하지 않도록 한다. |
| `[추정]` | 직접 측정하지 않은 수치·예상 결과에 붙인다. | 입력값별 근거, 산식, 단위·기간, 기준·상한 시나리오, 제외 항목, 재검증 시점·담당 | 결과 숫자보다 가정이 설계 결정을 좌우하므로 재계산할 수 있게 한다. |
| `[미확보]` | 정보·근거·결정이 아직 없는 항목에 붙인다. | 무엇이 없는지, 영향받는 결정, 임시 처리, 확보 방법, 담당, 기한 또는 결정 조건 | ‘나중에 확인’으로 방치하지 않고 진행 가능한 범위를 정한다. |
| `[미구현]` | 설계한 저장 객체·제약·처리 경로가 아직 구현되지 않은 경우에 붙인다. | 설계 ID, 미구현 범위, 확인 기준일·revision, 구현 작업 ID, 담당, 예정 마이그레이션 또는 미배정 표시, 완료 판정 방법 | 의도한 동작과 현재 가능한 동작을 분리한다. |

다음 규칙을 함께 적용한다.

- 하나의 값에 서로 다른 성격이 섞이면 분리한다. 예를 들어 **단가는 `[외부]`, 사용량은 `[추정]`, 둘을 곱한 예산은 `[추정]`**으로 적는다.
- ‘예상 마이그레이션 번호’를 이미 존재하는 번호처럼 적지 않는다. 미배정이면 `마이그레이션 미배정 · 작업 DB-…`로 적는다.
- 설계 선택은 `설계 결정: … · 이유: … · 결정 근거: …`로 적는다. 선택했다는 이유만으로 `[실측]`을 붙이지 않는다.
- 빈칸은 사용하지 않는다. 확인하지 못했으면 `[미확보]`, 적용되지 않으면 `해당 없음 — 이유`로 적는다. **문서의 미확보와 데이터 값의 NULL은 별개**로 정의한다.

**2. 구현 상태는 다음 단계로 기록한다.**

상태는 별도 표를 추가하지 않고 2.1의 `구분`, 3.1의 테이블 이름 문단, 3.2의 해당 행, 변경 이력의 `비고`에 적는다.

| 상태 표현 | 그 상태를 인정하는 최소 근거 |
|---|---|
| 설계만 존재 `[미구현]` | 설계 명세와 미구현 범위 |
| 구현 파일 존재 `[실측·정적 확인]` | revision에 고정된 DDL·설정·코드와 해당 위치 |
| 검증 환경 적용 `[실측·실행 확인]` | 환경, 적용한 마이그레이션 목록·체크섬, 실제 스키마 대조, 관련 검증 결과 |
| 운영 적용 `[실측·운영 확인]` | 운영 환경 식별자, 배포 기록, 적용 이력, 실제 객체·제약 상태 확인 |
| 적용 여부 미확인 `[미확보]` | 확인하지 못한 환경과 확인 작업 |

테이블 전체의 상태와 변경분의 상태를 구분한다. 기존 테이블이 운영 중이어도 새 컬럼·인덱스가 미구현이면 해당 항목에 별도로 표시한다. 또한 **DB 객체 적용과 애플리케이션 연동 검증을 구분**한다. 테이블 생성만으로 그 데이터를 읽고 쓰는 기능까지 완성되지 않기 때문이다.

**3. 다른 산출물과의 경계를 정한다.**

| 겹치는 산출물 | 이 문서에 남기는 것 | 해당 산출물로 넘기는 것·이유 |
|---|---|---|
| 요구사항·사업 기획 | 데이터 구조에 영향을 주는 불변식, 보존·정합성·응답시간 요구와 요구사항 ID | 시장·가격·화면 수·판매 전략의 상세. 저장 구조 결정에 직접 쓰이지 않는 설명은 중복하지 않는다. |

| API·도메인 설계 | 요청 식별자, 멱등 키, 영속 상태, 상태 전이를 강제하는 위치 | 엔드포인트 전체 계약·후보 선택 알고리즘·알림 문구. 저장 불변식에 필요한 부분만 연결한다. |

**4. 근거와 재현 경로를 연결한다.**

각 규칙에는 문서 안에서 변하지 않는 식별자를 부여한다. 예를 들어 엔터티 `E-…`, 관계 `R-…`, 무결성 규칙 `C-…`, 조회 `Q-…`, 변경 `M-…`를 사용한다. 식별자는 기존 셀에 적는다.

연결은 다음 순서를 만족해야 한다.

`요구·결정 근거 → 엔터티·관계 → 컬럼·제약 → 구현 파일·마이그레이션 → 검증 방법·결과 → 적용 환경`

파일 경로만으로 연결을 끝내지 않는다. **revision + 경로 + 객체명·함수명 또는 절**을 함께 적고, 실행 검증에는 준비 데이터·실행 방법·기대 결과·실제 결과 위치를 붙인다. 이는 파일이 바뀐 뒤에도 당시 판단을 재현하기 위함이다.

**표지**

- **이 절이 답하는 질문:** 이 문서는 누가 작성한 어느 저장소 설계의 기준본인가?
- **반드시 들어가는 것:** 작성 책임자, 문서 기준일, 저장소 경로를 기입한다. 문서 버전·대상 환경·revision은 1절의 `도구 :`와 연결한다. 표지의 제출일과 실제 DB 적용일이 다를 수 있기 때문이다.
- **형태:** 기존 표지와 정보 표를 그대로 사용한다. `산출물 단계 / 제출 일자 / 깃허브 경로 / 작성 팀원` 항목을 유지한다.
- **분량 기준:** 기존 칸당 1~2줄로 작성한다.
- **흔한 실패:** 작성일을 운영 반영일처럼 사용하거나 예시 작성자·경로를 남긴다.
- **판정 기준:** 표지만 읽어도 작성 책임과 기준 저장소를 찾고, 1절에서 정확한 revision·환경으로 이어갈 수 있어야 한다.

**1. 모델링 방법**

- **이 절이 답하는 질문:** 무엇을 데이터로 관리하고, 어떤 원칙으로 개념을 논리·물리 구조로 구체화하는가?
- **반드시 들어가는 것:** 저장 범위와 제외 범위, 핵심 업무 개념, 데이터의 정본·소유·생명주기, 정규화 판단, 기술·문서 기준선을 적는다. 이 기준이 없으면 뒤의 표들이 서로 다른 업무 전제와 구현 시점을 가질 수 있기 때문이다.
- **형태:** 기존 세 문단에 다음과 같이 배치한다.

| 기존 문단 | 들어가는 내용과 작성 이유 |
|---|---|
| `모델링 방법 :` | 관리 대상, 핵심 개념의 한 문장 정의, 개념 간 관계, 생성·변경·종료 경계, 정본과 쓰기 책임을 적는다. 예를 들어 ‘현재 상태’와 ‘변경 이력’이 별도 개념인지 먼저 결정해야 이력을 덮어쓰는 구조를 피할 수 있다. |
| `정규화 수준 :` | 목표 정규형과 실제 분리 근거, 자연키·대체키 선택 원칙, 반복 값·다중 값 처리, 비정규화 예외와 동기화 책임을 적는다. `3NF`라는 명칭만으로 데이터 중복과 갱신 이상을 검토할 수는 없다. |
| `도구 :` | DBMS·버전·필수 확장, 스키마·ERD·마이그레이션 도구, 문서 revision·대상 환경, 설계 의도와 구현·배포 사실을 확인할 원본 위치를 적는다. 문서·DDL·실제 DB가 다를 때 무엇을 비교할지 정하기 위함이다. |

- **분량 기준:** 전체 900~1,500자, 기존 세 문단으로 작성한다. 기술 목록보다 개념·결정 이유에 더 많은 분량을 배정한다.
- **흔한 실패:** `개념 → 논리 → 물리`라는 말만 적고 개념을 정의하지 않거나, 화면·사업 설명으로 대부분을 채운다.
- **판정 기준:** 독자가 핵심 개념의 의미·소유·수명과 정규화 예외의 이유를 설명하고, 각 개념이 2.1의 어떤 엔터티로 이어지는지 찾을 수 있어야 한다.

**세 단계의 경계는 다음과 같이 고정한다.**

| 단계 | 여기까지 결정한다 | 다음 단계로 넘긴다 |
|---|---|---|
| 개념 — 1절 | 업무상 무엇이 존재하는지, 서로 어떤 관계인지, 무엇을 같은 대상으로 보는지, 어떤 사실을 보존해야 하는지 | 컬럼 목록, SQL 타입, DB 제약 문법, 인덱스 |
| 논리 — 2.1~2.3 | 엔터티·속성·식별자·도메인, 유일성 범위, 필수·선택 관계, 정규화, 업무 불변식 | DBMS별 타입·기본값·제약 구현·인덱스·파티션 |
| 물리 — 3.1~3.2 | 정확한 저장 객체·컬럼·타입·키, 강제 위치, 트랜잭션·동시성·보존·조회 경로와 용량 | 적용 시점·배포 순서·백필·복구 실행은 마지막 절로 연결한다. |

논리 단계에서 PK·FK라는 표기를 사용할 수 있다. 다만 **논리 식별자·참조 관계를 뜻하며, DB에 해당 제약이 존재한다는 뜻은 아니다.**

**2. 논리 데이터 모델**

- **이 절이 답하는 질문:** 업무 개념을 어떤 엔터티·속성·관계·불변식으로 표현하는가?
- **반드시 들어가는 것:** 2.1의 목록, 2.2의 관계, 2.3의 ERD가 같은 모델을 표현해야 한다. 세 표현이 다르면 개발자마다 다른 구조를 구현할 수 있기 때문이다.
- **형태:** 기존 상위 제목을 유지하고 내용은 세 하위 절에 배치한다.
- **분량 기준:** 상위 제목 아래 중복 설명은 추가하지 않는다.
- **흔한 실패:** 엔터티 목록은 목표 설계, 관계표는 현재 구현, ERD는 과거 버전으로 작성한다.
- **판정 기준:** 모든 엔터티·관계가 동일 식별자와 기준 버전으로 서로 대응해야 한다.

**2.1 엔터티 목록**

- **이 절이 답하는 질문:** 어떤 데이터를 독립된 대상으로 저장하며 각 대상을 무엇으로 식별하는가?
- **반드시 들어가는 것:** 엔터티별 한 문장 정의, **한 건의 단위**, 식별자, 주요 속성의 의미, 유일성 범위, 이력·정본 역할을 적는다. 특히 ‘한 행이 무엇 한 건인가’를 알아야 중복·집계·버전 설계를 판단할 수 있다.
- **형태:** 기존 표 1개를 사용한다.

| 기존 열 | 입력 명세 |
|---|---|
| 구분 | 도메인 또는 역할, 엔터티 ID, 구현 상태를 적는다. 현재 상태·이력·참조·작업 기록 등의 역할을 구별한다. |
| 테이블 | 논리 엔터티명과 대응할 물리명을 적는다. 미정이면 가칭임을 밝힌다. 독립된 엔터티를 `/`로 묶지 않는다. |
| 제약 대상 | 식별 속성 또는 속성 조합을 적는다. ‘고객 정보’처럼 대상을 다시 설명하는 문장은 넣지 않는다. |
| 제약 유형 | 논리 PK, 후보키, 업무상 UNIQUE, 필수·값 범위 등의 규칙과 규칙 ID를 적는다. SQL 강제 여부는 3.2로 연결한다. |
| 주요 속성 | `정의 / 한 건의 단위 / 주요 속성·도메인 / 정본·이력 역할 / 근거` 순서로 적는다. |

한 엔터티에 식별 규칙이 여러 개면 같은 엔터티 ID로 행을 이어 적는다. 엔터티 수와 제약 수가 다르기 때문이다.

- **분량 기준:** 엔터티당 기본 1행, 설명 100~200자와 필요한 규칙 행을 작성한다.
- **흔한 실패:** PK 목록만 작성하거나, 서로 다른 표를 한 행에 묶거나, UUID를 쓴다는 사실만으로 업무상 중복이 방지된다고 판단한다.
- **판정 기준:** 같은 대상의 재입력, 다른 대상, 대상의 새 버전을 구분할 수 있어야 한다. 모든 엔터티는 3.1의 정의 또는 명시한 범위 제외·외부 명세로 연결해야 한다.

**2.2 엔터티 관계**

- **이 절이 답하는 질문:** 엔터티들은 어떤 수량·필수성·소유 규칙으로 연결되는가?
- **반드시 들어가는 것:** 양쪽 엔터티, 최소·최대 수량, 참조 속성, 소유 경계, 관계 해제·부모 삭제 시 의미를 적는다. `1:N`만으로는 부모 없이 생성 가능한지, 부모 삭제 시 이력을 남겨야 하는지 알 수 없기 때문이다.
- **형태:** 기존 표 1개를 사용한다.

| 기존 열 | 입력 명세 |
|---|---|
| 관계명 | 관계 ID와 업무 의미를 적는다. 예: ‘소유한다’, ‘특정 버전에 속한다’, ‘외부 대상을 참조한다’. |
| 주 엔터티 | 2.1의 엔터티 ID·이름과 기준 식별자를 적는다. |
| 종 엔터티 | 2.1의 엔터티 ID·이름과 연결 속성을 적는다. |
| 관계 | 양 끝의 `0..1 / 1 / 0..N / 1..N`, 필수성, 소유·생명주기, 동일 고객·테넌트 조건, 논리 참조 여부, 3.2의 강제 규칙 ID를 적는다. |

N:M은 업무상 의미를 설명하고 이를 해소하는 연결 엔터티로 이어간다. 다형 참조와 외부 ID 연결은 일반 FK와 구별한다. 실제로 DB가 검증하지 못하는 관계를 FK로 오해하지 않도록 하기 위함이다.

- **분량 기준:** 관계당 1행, `관계` 설명 100~200자로 작성한다.
- **흔한 실패:** 선택 관계를 모두 `1:N`으로 적거나, `tenant_id` 컬럼의 존재만으로 테넌트 간 연결이 차단된다고 적는다.
- **판정 기준:** 정상 연결, 부모 없음, 다른 소유자 연결, 부모 삭제라는 네 경우의 허용 여부와 강제 위치를 설명할 수 있어야 한다.

**2.3 ERD**

- **이 절이 답하는 질문:** 엔터티·식별자·관계 전체를 한눈에 대조하면 어떤 구조인가?
- **반드시 들어가는 것:** 엔터티명·ID, 논리 키, 관계 양 끝의 수량·선택성, 연결 엔터티, 논리 참조 범례, 구현 상태 범례, 기준 버전·원본 위치를 넣는다. 그림이 별도 모델이 되지 않도록 목록·관계표와 같은 식별자를 사용한다.
- **형태:** 기존 ERD 영역에 그림과 짧은 범례·출처를 넣는다. 구현 상태는 엔터티의 문자 표식으로, 관계 의미는 선·끝점 범례로 구별한다. 색 하나에 두 의미를 부여하지 않는다.
- **분량 기준:** 기본 1장으로 작성한다. 크면 같은 절 안에서 전체도 1장과 영역별 상세도로 나누되, 관계 연결점이 추적되게 한다. 범례·기준 설명은 150~300자로 작성한다.
- **흔한 실패:** 제목만 남기거나, 모든 관계를 실제 FK처럼 그리거나, 물리 컬럼을 모두 넣어 키와 관계를 읽지 못하게 한다.
- **판정 기준:** 2.1의 대상과 2.2의 관계가 누락 없이 대응하고, 그림에서 고른 관계를 표의 같은 ID로 찾을 수 있어야 한다. 출력 크기에서도 키·수량 표식이 읽혀야 한다.

**3. 물리 데이터 모델**

- **이 절이 답하는 질문:** 논리 모델을 선택한 저장 기술에서 어떤 구조와 강제 장치로 구현하는가?
- **반드시 들어가는 것:** 3.1의 객체·컬럼 명세와 3.2의 강제·운영 규칙을 같은 구현 기준선으로 연결한다. 구조만 있고 쓰기·삭제 방식이 없으면 실제 정합성을 판단할 수 없기 때문이다.
- **형태:** 기존 상위 제목을 유지하고 내용은 두 하위 절에 배치한다.
- **분량 기준:** 상위 제목 아래 중복 설명은 추가하지 않는다.
- **흔한 실패:** ORM 모델·DDL·운영 DB를 구별하지 않고 모두 ‘실제 스키마’라고 부른다.
- **판정 기준:** 어떤 환경의 어떤 구현 상태를 설명하는지 명확하고, 각 물리 규칙이 근거와 적용 상태로 연결되어야 한다.

**3.1 테이블 정의서**

- **이 절이 답하는 질문:** 이 테이블의 각 컬럼에는 정확히 무엇을 어떤 형식과 조건으로 저장하는가?
- **반드시 들어가는 것:** 테이블의 목적·행 단위, 전체 컬럼의 정확한 이름·타입·NULL·기본값·키, 값의 의미, 관련 제약, 구현 상태, 마이그레이션 연결을 적는다. 한 컬럼이라도 누락되면 독자가 정의서만으로 스키마 차이를 판정할 수 없기 때문이다.
- **형태:** 기존 `테이블 : …` 문단과 6열 표를 반복한다.

테이블 이름 문단은 다음 순서로 작성한다.

`테이블 : <schema.name> — <엔터티 ID·한 행의 의미> / 상태: <구현·적용 상태> / 기준: <revision·환경> / 생성: <마이그레이션> / 후속 변경: <목록> / 근거: <정확한 위치>`

| 기존 열 | 입력 명세 |
|---|---|
| 컬럼명 | 실제 컬럼 하나만 적는다. JSON 내부 필드는 해당 컬럼의 설명에서 별도로 식별한다. |
| 타입 | DBMS에서 사용할 정확한 타입과 길이·정밀도·시간대·배열·벡터 차원을 적는다. 필요한 값이 미정이면 표시와 결정 작업을 붙인다. |
| PK | `O / — / 미정`으로 적는다. 복합 PK이면 설명에 전체 컬럼 조합·순서를 명시한다. |
| FK | `O / — / 미정`으로 적는다. `O`이면 참조 스키마·테이블·컬럼 조합과 3.2 규칙 ID를 연결한다. |
| Not Null | `O / — / 미정`으로 적는다. 제안 여부와 실제 적용 여부는 테이블·해당 행의 상태로 구별한다. |
| 제약 조건 설명 | 업무 의미, 단위·허용값, NULL 의미, 기본값과 생성 주체, UNIQUE·CHECK 등 규칙 ID, 민감도·보존 규칙, 변경 마이그레이션을 적는다. |

다음 정보는 해당하는 컬럼에 반드시 포함한다.

- 금액은 통화·단위·정밀도·반올림 기준을 적는다. 같은 숫자라도 원·센트·세전·세후의 의미가 다르기 때문이다.
- 시각은 사건 발생·공급자 수정·수집·저장·효력 시작 중 무엇인지 적는다. 최신성 판단과 처리 순서가 달라지기 때문이다.
- JSON은 스키마 버전·필수 키·검증 주체·크기 한도·호환성 규칙을 적는다. `jsonb`라는 타입만으로 내부 계약이 정의되지 않기 때문이다.
- 외부 저장 참조는 객체 키·버전·체크섬·소유자를 식별하는 방법을 적는다. URL 문자열만으로는 동일 객체와 변경 이력을 확인하기 어렵기 때문이다.

- **분량 기준:** 테이블당 정의 블록 1개, 컬럼당 1행으로 작성한다. 테이블 설명은 150~300자, 컬럼 설명은 대체로 50~150자로 작성한다. 긴 규칙은 3.2로 연결한다.
- **흔한 실패:** `place_id / locked`처럼 FK와 NULL 조건이 다른 컬럼을 합치거나, `VARCHAR`·`numeric`의 필요한 제한을 생략하거나, 주요 열만 보여주고 완전한 정의서처럼 제시한다.
- **판정 기준:** 대상 테이블별 컬럼 집합·타입·NULL·기본값·키가 기준 DDL과 일치해야 한다. 의도적 제외는 범위·이유·완전한 명세의 고정 링크를 명시한다. SQL 구현 확인만으로 운영 적용을 인정하지 않는다.

**3.2 제약 조건 및 무결성 관리**

- **이 절이 답하는 질문:** 잘못된 값·중복·경합·삭제·장애·부하가 발생해도 어떤 규칙을 어디서 어떻게 지키는가?
- **반드시 들어가는 것:** 제약, 주요 조회와 인덱스, 원자적 쓰기, 동시성·멱등·순서, 보존·삭제, 접근 제어, 성능·용량의 결정과 검증 조건을 적는다. 선언한 규칙을 실제로 누가 강제하는지가 이 절의 핵심이다.
- **형태:** 기존 4열 표 하나에 규칙 단위로 작성한다. 아래 구분은 **기존 표에 들어갈 행의 종류**이며 새 하위 절이나 별도 표를 뜻하지 않는다.

| 기존 열 | 입력 명세 |
|---|---|
| 적용 레벨 | DB / 애플리케이션 / 작업자 / 외부 저장소 / 운영 중 실제 책임 주체를 적는다. 공동 책임이면 각각 수행하는 일을 나눈다. |
| 제약 유형 | 규칙 ID와 유형을 적는다. 예: PK, FK, UNIQUE, CHECK, INDEX, 낙관적 잠금, 멱등, 이벤트 순서, 보존·삭제, 성능·용량. |
| 대상 | 정확한 테이블·컬럼 조합·객체·쓰기 작업·조회 ID·소유 범위를 적는다. |
| 설명 및 관리 방안 | `규칙·이유 → 강제 방법 → 실패·예외 처리 → 검증 조건 → 구현·적용 상태·근거` 순서로 적는다. |

**기존 표에 넣을 최소 내용은 다음과 같다.**

| 행의 종류 | 반드시 적는 내용·이유 | 확인 방법 |
|---|---|---|
| PK·UNIQUE | 정확한 컬럼 조합, 업무상 유일성 범위, NULL·대소문자·정규화·삭제된 데이터의 취급을 적는다. 기술 ID의 유일성과 업무 중복 방지가 서로 다르기 때문이다. | 같은 범위의 중복, 다른 범위의 동일 값, NULL·정규화 경계값을 넣었을 때 기대한 결과가 나오는지 확인한다. |
| FK | 참조 컬럼 조합, `ON DELETE`·`ON UPDATE`, 검사 시점, 동일 소유자 조건을 적는다. 다형·외부 참조이면 FK가 없는 이유와 대체 검증을 적는다. | 고아 참조·다른 소유자 참조·부모 삭제·키 변경을 검증한다. |
| CHECK·NOT NULL·도메인 | 정확한 조건식·필수성·NULL 처리, 앱 검증과 DB 검증의 분담을 적는다. 다른 행·표의 상태를 읽어야 하는 규칙은 이를 처리할 트랜잭션·잠금 방식까지 적는다. | 정상값·경계값·NULL·직접 DB 쓰기·동시 변경을 검증한다. |
| 인덱스 | 이름, 방식, 컬럼 순서·정렬, 조건식·포함 컬럼, 유일성 여부, 대응 조회 ID, 기대 효과와 쓰기·용량 부담을 적는다. | 실제 정의와 대표 조회 계획을 대조하고, 추가 전후의 읽기·쓰기 비용을 같은 조건으로 비교한다. |
| 트랜잭션·낙관적 잠금 | 보호 대상, 읽는 버전·개정번호, 함께 커밋할 객체, 격리 수준·조건부 쓰기 또는 잠금, 충돌 판정, 재계산·재시도 한도·소진 처리를 적는다. | 같은 기준 상태를 읽은 두 작업 중 충돌한 쓰기가 거부되고 부분 변경이 남지 않는지 확인한다. |
| 멱등 | 키의 범위·재료·정규화·발급 주체, 대상 실재·소유 확인, 같은 키·다른 본문 처리, 진행 중 요청·결과 보존·만료 후 재요청 처리, 외부 실행 결과 불명 처리를 적는다. | 동일 요청 반복은 하나의 효과가 되고, 다른 대상 요청은 사라지지 않으며, 응답 유실 후에도 중복 실행되지 않는지 확인한다. |
| 이벤트 순서·발행 | 순서를 보장할 범위, 순번 할당, 중복·누락·역순·지연 이벤트 처리, 소비 진행 위치, 재생 기준, 이벤트 스키마 버전을 적는다. | 중복·역순·누락 입력과 소비자 재시작 후 최종 상태·부작용 수를 확인한다. |
| 보존·이력·감사·삭제 | 아래의 데이터 수명 계약을 객체별로 적는다. 오래된 데이터와 지워야 할 데이터가 같은 저장소에 있기 때문이다. | 수정·삭제 권한, 만료 처리, 삭제 전파, 복원 후 재삭제, 이력 조회를 확인한다. |
| 접근 제어·저장소 간 정합성 | 읽기·쓰기 주체, 테넌트·고객 경계, 민감 필드 보호, 정본과 복제·캐시·검색본, 허용 지연, 실패 대조·복구 책임을 적는다. | 다른 소유자 접근, 캐시·검색본 지연, 일부 저장 실패와 재처리를 확인한다. |
| 성능·용량 | 아래의 대표 부하·조회·성장 산식·한계·확장 조건을 적는다. 적재 가능성과 응답 가능성을 구별하기 위함이다. | 계획 수치와 실측을 같은 데이터·부하 조건에서 대조한다. |

제약과 인덱스는 다음 원칙으로 구분한다.

- **논리 단계**에는 ‘같은 소유 범위에서 같은 업무번호가 둘이면 안 된다’처럼 규칙과 이유를 적는다.
- **3.1**에는 해당 컬럼·키 표시와 규칙 ID를 적는다.
- **3.2**에는 정확한 제약·인덱스 정의와 검증 조건을 적는다.
- 일반 인덱스를 정합성 제약처럼 설명하지 않는다. UNIQUE 제약을 지원하는 인덱스는 별도 성능 인덱스와 중복되는지도 확인한다.

DBMS별 차이를 확인할 근거도 연결한다. 예를 들어 PostgreSQL 16에서는 PK·UNIQUE가 인덱스를 생성하지만 FK 선언이 참조하는 쪽 컬럼의 인덱스를 자동 생성하지는 않는다. 또한 CHECK는 NULL 허용 여부를 별도로 검토해야 한다. 따라서 `FK 전체에 INDEX`, `CHECK로 필수값 보장` 같은 일괄 문구를 쓰지 않는다. [PostgreSQL 16 제약 문서](https://www.postgresql.org/docs/16/ddl-constraints.html)

**동시성은 정상 경로와 충돌 경로를 함께 적는다.**

낙관적 잠금을 선택했다면 설명 셀에서 다음 연결을 읽을 수 있어야 한다.

`기준 상태 읽기 → 계산 → 기준 버전·입력 개정 확인을 포함한 조건부 쓰기 → 영향 행 수 확인 → 관련 변경 일괄 커밋`

충돌하면 무엇을 버리고 무엇을 다시 읽을지 적는다. **재시도 횟수만 적지 않고 기존 계산 결과를 재사용해도 되는 조건을 적는다.** 상위 업무 객체를 여러 하위 작업이 함께 변경한다면 어느 객체의 버전을 검사할지도 명시한다.

이벤트 순번에 UNIQUE를 둔 사실만으로 순서 설계를 완료하지 않는다. 해당 제약이 막는 것은 같은 순번의 중복이며, 순번 할당·누락·역순 소비·재생 처리는 별도 계약으로 남긴다. outbox에는 DB 저장과 발행 의도의 원자성을 적고, 외부 전달·수신·처리 완료 각각의 확인 범위를 구분한다.

**보존·이력은 다음 내용을 객체별로 적는다.**

| 내용 | 필수 명세·이유 |
|---|---|
| append-only | 불변 범위, 허용하는 정정 방식, 수정·삭제를 제한하는 권한·장치, 예외 작업과 감사 근거를 적는다. 설명에 ‘수정 금지’라고 적는 것만으로 우회 쓰기가 차단되지 않기 때문이다. |
| 현재 상태와 과거 상태 | 최신 포인터·버전, 과거 상태 조회 기준, 정정·취소·되돌림이 만드는 새 기록을 적는다. 과거 데이터 덮어쓰기로 변경 이유가 사라지지 않게 한다. |
| 감사 로그 | 행위자·대상·행위·시각·요청 ID·결과·변경 전후 값 또는 참조·사유를 적는다. 민감값 마스킹, 조회 권한, 감사 기록 자체의 변경 제한도 적는다. 업무 이벤트만으로 접근·관리자 작업까지 추적할 수 있다고 가정하지 않는다. |
| 보존 기간 | 기산점, 기간, 근거 정책 ID, 활성·보관 저장소, 법적·계약상 보존 예외의 처리 책임을 적는다. 모든 데이터를 동일 기간으로 보존하지 않는다. |
| 삭제 | 논리 삭제·물리 삭제·익명화 중 동작, 실행 주체·주기, 자식 데이터·객체·벡터·캐시·백업의 처리, 완료 증거를 적는다. 논리 삭제만으로 실제 제거가 완료되지 않기 때문이다. |
| 백업·복구 | 허용 데이터 손실 시간인 RPO, 복구 목표 시간인 RTO, 포함 저장소, 복원 검증·삭제 요청 재적용 방법을 적는다. DB만 복구하고 연결된 객체·색인이 누락되는 상황을 방지한다. |

append-only와 보존 종료 후 삭제가 함께 필요하면 **일상 쓰기의 불변성**과 **정책에 따른 수명 종료 절차**를 구분한다. 충돌을 ‘영구 보존’ 한 문장으로 덮지 않는다.

**성능·용량은 다음 수준까지 요구한다.**

- 설계 검토 시점에는 대표 읽기·쓰기 3~5종을 출발점으로 삼고, 핵심 지연 경로와 최대 적재 경로가 모두 포함되게 한다.
- 각 조회는 `Q-ID / 목적 / 필터·조인·정렬·LIMIT / 데이터 규모·분포 / 평균·피크 빈도·동시성 / 목표 지연·처리량 / 인덱스 / 검증 상태`를 설명 셀에 적는다.
- 평균 행 수 외에 버전·이벤트·관측·감사 로그의 증가량, 큰 JSON·객체 크기, 보존 기간을 포함한다. 업무 건수보다 이력 데이터가 빠르게 증가할 수 있기 때문이다.
- 인덱스·파티션·캐시를 채택했다면 해결하려는 조회와 추가 운영 비용을 적는다. 미채택이라면 현재 규모와 재검토 조건을 적는다.
- 모든 조회의 부하 시험을 요구하지는 않는다. 다만 성능을 보장했다고 쓰려면 해당 부하·데이터 분포·환경의 실행 결과가 있어야 한다.

용량 계산에는 최소 다음 산식을 노출한다.

```text
기간 말 행 수 = 초기 행 수 + 기간 중 추가 행 수 − 기간 중 제거 행 수
추가 행 수 = 업무 건수 × 업무당 기록 수
          또는 활성 대상 수 × 대상당 기록 빈도 × 기간

주 저장 용량 = Σ(객체별 행 수 × 저장 행 크기) + 인덱스 용량
필요 공간 = 주 저장 용량 + 로그·임시 작업 공간 + 여유 공간
전체 보유량 = 주 저장소 + 복제본 + 백업 + 외부 객체·검색 저장소
```

각 항의 단위·압축 가정·중복 계산 여부를 밝히고 기준·상한 시나리오를 계산한다. 산출 결과가 저장소 선택, 보존 기간, 파티션 또는 확장 임계값 중 어떤 결정에 쓰이는지도 적는다.

실측에는 환경 사양·DB 설정·데이터 크기·분포·동시성·실행 시간·반복 수·캐시 조건과 p95 등 선택한 지표를 남긴다. 실행 계획의 예상 비용을 실제 밀리초로 해석하지 않는다. [PostgreSQL 16 실행 계획 문서](https://www.postgresql.org/docs/16/using-explain.html)

- **분량 기준:** 기존 표 1개에 독립 규칙당 1행으로 작성한다. 일반 규칙은 100~250자, 동시성·보존·용량처럼 순서가 필요한 규칙은 300~600자를 기준으로 한다. 큰 로그·DDL 원문은 고정 링크로 연결한다.
- **흔한 실패:** DB·앱을 공동 책임으로만 적거나, UNIQUE로 모든 중복 실행·순서가 보장된다고 적거나, 보존 기간·부하 조건 없이 ‘이력 보존·성능 최적화’로 끝낸다.
- **판정 기준:** 각 규칙을 깨뜨리는 입력·경합·실패 사례에 대해 강제 위치, 기대 결과, 검증 자료를 찾을 수 있어야 한다. 미검증 규칙은 계획 상태로 남긴다.

**4. 변경 이력 및 적용 전략**

- **이 절이 답하는 질문:** 설계 변경을 어떤 순서와 검증·복구 조건으로 실제 환경에 적용하는가?
- **반드시 들어가는 것:** 변경 이유·전후 차이, 대상 객체, 마이그레이션·의존성, 기존 데이터 처리, 앱 호환성, 적용·검증·복구 상태를 적는다. 문서를 고친 사실과 DB를 바꾼 사실이 다르기 때문이다.
- **형태:** 기존 5열 표 1개를 사용한다.

| 기존 열 | 입력 명세 |
|---|---|
| 변경일 | 실제 변경일을 적는다. 예정 작업은 `예정: 날짜 또는 조건`으로 구분한다. |
| 변경자 | 작성자뿐 아니라 적용·검증 책임자를 식별할 수 있게 적는다. |
| 변경내용 | 변경 ID, 이유, 전후 차이, 문서 변경인지 DDL·데이터 변경인지, 적용 순서를 적는다. |
| 영향 받는 항목 | 테이블·컬럼·제약·인덱스, 읽기·쓰기 경로, 기존 데이터·외부 저장소를 구체적으로 적는다. |
| 비고 | 마이그레이션 ID·파일·체크섬·revision, 선행 의존성, 환경·적용 상태, 검증 결과, 복구·중단 조건, 작업·승인 기록을 연결한다. |

스키마 변경에는 다음 사항을 포함한다.

- **판정 기준:** 다른 담당자가 해당 행과 연결 자료로 적용 순서·예상 영향·중단 조건·복구 방법을 판단할 수 있어야 한다. 설계 완료·구현 완료·환경 적용 완료를 각각 구별해야 한다.
