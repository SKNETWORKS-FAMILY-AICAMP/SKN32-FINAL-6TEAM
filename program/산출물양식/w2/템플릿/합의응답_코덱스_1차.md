**Q1은 조건부 동의, Q2는 동의, Q3은 조건부 동의, Q4는 동의한다.** G열 병합을 유지하라는 내 처방은 철회한다. 다만 상태 어휘를 통일하면서 구현·적용·검증의 차이를 없애거나, 출력 파일의 ID만 고정하는 방식에는 동의하지 않는다.

파일은 생성·수정하지 않았다. 아래에서 텍스트는 파일·줄로, XLSX·DOCX는 줄 번호가 없으므로 시트·셀 또는 표 위치로 근거를 특정한다.

**Q1. 공통 상태 표시 — 조건부 동의**

기획서의 규칙을 다섯 산출물의 공통 규칙으로 채택한다. 원천 규칙 자체가 근거와 실행을 분리하고, `[결정]`이 사업성 입증을, `[구현]`이 검증 통과를 뜻하지 않는다고 명시한다. 데이터 확보 4단계를 별도 축으로 추가하는 것도 타당하다. [기획서 55–69행][plan55], [수집 데이터 42–50행][data42]

조건은 **공통 표시 아래에 필요한 상세 상태를 보존하는 것**이다.

- DB의 `구현 파일 존재 / 검증 환경 적용 / 운영 적용`은 각각 다른 증거를 요구하므로, 모두 `[구현]`으로만 바꾸면 정보가 손실된다. 공통 표시와 함께 `DB 적용 단계·환경`을 기록해야 한다. [DB 52–64행][db52]
- WBS의 `진행 예정 / 진행중 / 완료`는 작업 진행 상태로 유지하고, 공통 근거·판단·구현 표시는 C열에 기록한다. 작업 완료가 연결된 요구사항 전체의 검증 완료를 자동으로 뜻해서는 안 된다. [WBS 25행][wbs25], [123–133행][wbs123]
- 요구사항의 변경검토·보류·폐기, 시험의 미실행·실패·차단도 상세값으로 남긴다. 공통 어휘만으로 이 차이를 표현할 수 없기 때문이다. [요구사항 269–279행][req269]

**Q2. 요구사항 G열을 행마다 배치 — 동의**

내 템플릿의 “병합을 풀거나 재구성하지 않는다”와 “G16에 세 ID의 비고를 모은다”는 지침을 철회한다. 요구사항별 근거·우선순위·상태는 해당 행의 G셀에 있어야 한다. [요구사항 19–21행][req19]

누락은 직접 확인했다. [백업 생성본][reqbackup]의 `시트1`에서 D17·D18은 REQ-013·014이고, G17·G18은 값이 없는 `MergedCell`이다. 백업 코드도 병합 셀을 만나면 비고 쓰기를 건너뛴다. [백업 코드 319–324행][oldbuild319]

현재는 수정되어 있다. [현재 생성본][reqxlsx]의 G17에는 `v11 §5-B / DoD-23`, G18에는 `v11 §5·§6 / 아키텍처`가 있다. 현재 코드는 G열 본문 병합을 해제하며, 비고 기록 대상이 병합 셀이면 중단한다. [현재 코드 472–487행][reqbuild472], [518–525행][reqbuild518]

다만 검토문의 **“서로 무관한 요구사항 셋”이라는 표현은 과하다.** 세 요구는 Registry·Team·Core 책임에 관한 관련 요구다. 병합을 풀어야 하는 이유는 무관해서가 아니라 **각각 독립된 ID와 판정·추적 단위를 갖기 때문**이다. 또한 빈 원본의 병합만으로 최초 작성자의 예시 의도까지 확정할 수는 없다. 이 두 설명을 정정해도 G열 비병합 결론은 동일하다. [검토문 41–45행][review41], [현재 생성본 D16:G18][reqxlsx]

A~C열은 실제 분류에 맞춰 병합 구간을 구성할 수 있다. 머리글 G3:G4와 본문 G열의 비병합 규칙은 구별한다.

**Q3. 기존 Task ID 열에 안정 ID 기록 — 조건부 동의**

**기존 A열이면 충분하다. 추가 열은 필요 없다.** 이미 내 템플릿도 A열에 고유·불변 ID를 기록하도록 요구한다. [WBS 21행][wbs21]

조건은 **원천 작업 데이터에도 ID를 고정하는 것**이다. 현재 `T`에는 ID가 없고, 출력 시 `enumerate`의 `i - 1`을 A열에 쓴다. 따라서 출력 셀만 수동 수정하면 다음 빌드에서 다시 바뀐다. [WBS 빌드 30–33행][wbsbuild30], [192–200행][wbsbuild192]

작업 데이터에 `task_id`를 저장하고, 행 번호는 출력 위치에만 사용해야 한다. 기존 ID는 유지하며 신규 작업에만 새 ID를 발급한다. 삭제 ID는 재사용하지 않고, 분할·통합은 대체 관계를 남긴다. 검수에는 정렬뿐 아니라 **중간 삽입·재빌드 후 기존 ID 유지와 참조 무결성**을 포함한다.

**Q4. MoSCoW를 비고 앞머리에 표시 — 동의**

각 요구사항 G셀의 첫 토큰을 `[M]`·`[S]`·`[C]`·`[W]` 중 하나로 통일한다. 열을 늘리지 않고도 우선순위를 식별할 수 있다.

다만 **MoSCoW 자체는 기존 템플릿에 이미 있다.** 이번 변경은 새 체계 도입이 아니라 표기 위치와 문법의 확정이다. 현재는 G열 문법 중간에 `우선순위: <M/S/C/W>`가 있고, 릴리스별 판정 기준도 정의되어 있다. [요구사항 201–210행][req201], [233–246행][req233]

`[W]`는 **이번 릴리스에서 이행하지 않기로 한 결정**이며, 영구 폐기나 다음 릴리스 구현 약속이 아니다. 등급 뒤에는 대상 릴리스·선정 이유·결정 근거를 남긴다. G5도 해당 요구의 우선순위로 시작하고, 줄을 바꿔 `문서공통:`을 기록한다. WBS H열의 작업 우선순위와 MoSCoW를 자동 대응시키지는 않는다. [요구사항 242행][req233], [WBS 161–174행][wbs161]

**「합의 안 됨」**
