| **형태** | 기본형은 `REQ-001`과 같은 고정 접두·일련번호로 한다. 여러 프로젝트를 통합 관리하면 `<프로젝트코드>-REQ-001`을 사용한다. 기존 ID 체계가 있으면 유지한다. |
| **분량 기준** | 요구사항 한 행에 ID 하나를 적는다. 범위 표기나 쉼표로 여러 ID를 합치지 않는다. |
| **흔한 실패** | 행 번호를 ID로 사용한다. 분류 변경 때 번호를 다시 매긴다. 삭제된 요구의 ID를 새 요구에 재사용한다. |
| **판정 기준** | 중복 ID가 없어야 한다. 이전 판의 ID가 현재 요구 또는 폐기·대체 기록으로 연결되어야 한다. |

분할·통합 때에는 새 ID를 발급하고 G열에 `분할 원본 / 대체 대상 / 변경 사유 / 승인 기록`을 남긴다. 단순 문구 정정은 ID를 유지하되, **인수조건이 바뀌면 영향받는 시험과 작업을 재검토**한다.

**6. 「소분류(기능설명)」 — E열**

| 작성 항목 | 내용 템플릿 |
|---|---|
| **이 절이 답하는 질문** | “어떤 조건에서 시스템이 무엇을 보장해야 하는가?”에 답한다. |
| **반드시 들어가는 것** | 주체·발생 조건·대상·의무 동작·관찰 가능한 결과를 적는다. 비기능은 적용 대상·품질 속성·목표를 적는다. 독립적으로 합격·불합격을 판정할 의무 하나를 중심으로 작성한다. |
| **형태** | `〈조건〉에서 〈시스템〉은 〈대상〉에 〈동작〉을 수행하고 〈관찰 가능한 결과〉를 보장한다.`로 작성한다. 상세 값과 예외는 F열에 연결한다. |
| **분량 기준** | 1문장, 약 50~150자를 기준으로 한다. 설명이 길어지면 F열로 옮기고, 독립된 의무가 늘어나면 요구사항을 나눈다. |
| **흔한 실패** | “지원한다·최적화한다·안정적으로 처리한다”로 끝낸다. “구현 완료·추후 개발”을 요구 문장에 넣는다. 여러 접점·기능·언어 정책을 한 요구로 묶는다. |
| **판정 기준** | 요구를 위반하는 입력이나 상황을 하나 이상 만들 수 있어야 한다. 검수자가 결과를 관찰해 충족 여부를 판단할 수 있어야 한다. |

“좋은 요구사항 하나”는 **E열의 한 문장과 F·G열의 검증·관리 정보가 결합된 한 행**이다.

| 구성 요소 | 들어갈 위치 | 빠지면 발생하는 문제 |
|---|---|---|
| 지켜야 할 의무 | E | 설명과 요구를 구별할 수 없다. |
| 적용 조건·대상·제외 범위 | F | 어디까지 검수해야 하는지 합의할 수 없다. |
| 관찰 가능한 기대 결과·실패 처리 | F | 성공 경로만 구현해도 완료라고 주장할 수 있다. |
| 인수조건·측정 정의·검증 방법 | F | 담당자마다 합격 판단이 달라진다. |
| 요구 이유·출처·상위 목표 | G | 필요성과 변경 영향을 판단할 수 없다. |
| 우선순위·대상 릴리스·결정 책임 | G | 일정 부족 때 무엇을 남길지 결정할 수 없다. |
| DoD·WBS·시험 연결 | G | 요구가 실제 작업과 검수에서 빠져도 발견하기 어렵다. |
| 요구 확정·구현·검증 상태 | G | 계획을 실적으로 오인한다. |

한 요구에 인수조건이 여러 개 있는 것은 허용한다. 정상·실패·경계 조건이 **같은 의무를 함께 검증**할 수 있기 때문이다. 반면 일부만 별도 출시하거나 별도 책임자가 승인할 수 있는 의무는 분리한다.

**7. 「추가설명」 — F열**

| 작성 항목 | 내용 템플릿 |
|---|---|
| **이 절이 답하는 질문** | “어떤 입력·경계·측정 조건으로 이 요구의 합격을 판정하는가?”에 답한다. |
| **반드시 들어가는 것** | 적용 범위, 전제·입력, 정상 결과, 관련 실패·경계 처리, 인수조건, 검증 방법을 적는다. 수치를 쓰면 단위·집계 대상·측정 구간·산식을 함께 적는다. 판단에 영향을 주는 외부 의존성과 금지 동작도 명시한다. |
| **형태** | 기존 F열 셀 안에 `적용: / 조건: / 인수 AC-01: / 예외: / 검증:`의 줄바꿈 문장으로 작성한다. 그림 대신 상태·인터페이스 설계의 정확한 항목을 참조한다. |
| **분량 기준** | 약 300~700자, 인수조건 2~5개를 기준으로 한다. 모든 자료 구조·시험 절차를 복사하지 않는다. 길이 때문에 핵심 인수조건을 생략하지 않는다. |
| **흔한 실패** | 구현계획서의 문단을 그대로 옮긴다. “시험으로 확인한다”만 적는다. 임계값을 설정 파일로 넘기면서 값의 확정 책임은 남기지 않는다. |
| **판정 기준** | 구현자가 추가로 요구 의미를 결정하지 않고 시험을 설계할 수 있어야 한다. 정상 경로뿐 아니라 해당 요구를 깨뜨리는 실패·경계 조건의 결과가 명시되어야 한다. |

셀의 기본 문법은 다음과 같다.

```text
적용: <대상·접점·환경·제외 범위>
조건: <권한·초기 상태·입력·외부 의존성>
인수 AC-01: <주어진 조건>에서 <사건>이 발생하면 <기대 결과>를 만족한다.
인수 AC-02: <실패·경계 조건>에서는 <거부·복구·유지할 상태>를 보장한다.
측정: <지표·단위·산식·표본·집계 기간·합격값>  ※ 수치 판정에 적용한다.
검증: <시험/분석/검사/시연 중 방법> 및 <재현 절차 참조>
```

`AC-01`은 해당 요구 안에서의 번호다. 다른 문서에서 참조할 때에는 `REQ-001/AC-01`처럼 전체 식별자를 사용한다.

예외가 적용되지 않으면 `예외: 해당 없음 — <이유>`로 적는다. 빈칸은 검토하지 않은 것과 구분할 수 없기 때문이다.

**공통 작성 규칙 — 요구와 사실을 구분하는 방법**

**① 다섯 표시는 같은 상태 목록으로 취급하지 않는다.**

`[실측]·[외부]·[추정]`은 주장이나 값의 근거 성격이며, `[미확보]`는 필요한 정보의 부재다. `[미구현]`은 구현 현황이다. 그러므로 **요구가 확정되어 있으면서 구현은 미구현이고, 성능 실측값은 미확보인 상태**가 가능하다.

| 표시 | 사용 조건 | 반드시 따라붙는 정보 | 기재 위치·이유 |
|---|---|---|---|
| **[실측]** | 직접 관찰·측정·계산한 사실에 사용한다. | 측정일, 대상 버전·환경, 작업 트리/커밋 구분, 측정 방법, 표본·단위, 원자료 위치, 산식 또는 재현 절차, 확인 범위를 붙인다. | 현재 결과는 G열에 적는다. F열의 목표값과 혼동하지 않기 위해서다. 정적 코드 확인이면 실행 검증을 하지 않았음을 밝힌다. |
| **[외부]** | 외부 자료에서 확인한 사실에 사용한다. | 발행 주체, 문서명·URL·항목, 발표·개정일과 확인일, 적용 범위·조건, 1차 출처 확인 여부를 붙인다. | 요구 근거는 G열에 적는다. 외부 제품의 수치나 제공 조건이 우리 시스템의 달성 실적을 뜻하지 않기 때문이다. |
| **[추정]** | 미검증 가정이나 그 가정으로 계산한 값에 사용한다. | 가정한 입력·단위·산식, 입력별 근거, 적용 범위, 결론에 영향을 주는 변동 범위, 검증 담당·시점을 붙인다. | 잠정 인수값이면 F열, 그 선정 근거와 검증 계획은 G열에 적는다. 추정값을 확정 목표로 채택했는지는 별도로 표시한다. |
| **[미확보]** | 판단에 필요한 값·자료·결정·권한 등이 없는 경우 사용한다. | 무엇이 없는지, 영향받는 요구·판정, 확보 방법, 책임자, 기한, 확보 전 처리, 해소 조건을 붙인다. | 요구값이 없으면 F열 해당 위치에, 해소 관리는 G열에 적는다. 빈칸·0·없음으로 대체하면 잘못된 판정을 유발한다. |
| **[미구현]** | 특정 요구 또는 인수조건을 만족하는 구현이 없음을 확인한 경우 사용한다. | 미구현 범위, 확인 시점·버전·방법, 구현 작업 ID, 담당·목표 시점, 완료 후 검증할 인수조건을 붙인다. | G열의 구현 상태에만 적는다. 구현이 없다는 사실이 요구의 필요성·확정 여부를 바꾸지는 않기 때문이다. |

확인하지 않았다는 이유만으로 `[미구현]`을 붙이지 않는다. 구현 증거를 확보하지 못했다면 `구현 상태: 확인불가 / [미확보] 구현 증거 …`로 적는다.

규칙 자체에는 근거 등급을 억지로 붙이지 않는다. 예를 들어 “승인된 요청만 실행한다”는 요구이며, “현재 모든 경로에서 차단된다”는 검증해야 할 사실 주장이다.

**② 우선순위는 미충족의 결과로 정한다.**

MoSCoW를 사용하되, **대상 릴리스 안에서의 의미**를 고정한다.

| 값 | 판정 기준 | G열에 적는 근거 |
|---|---|---|
| **M — Must** | 빠지면 릴리스 목적 또는 확정된 필수 약속을 충족하지 못하고, 수용 가능한 대체수단이 없다. | 연결 목표·약속, 미충족 영향, 대체 불가 이유, 의존 요구를 적는다. |
| **S — Should** | 영향이 크지만 정해진 기간 동안 수용 가능한 우회 처리가 있다. | 우회 방법·담당·비용·허용 기간과 남는 영향을 적는다. |
| **C — Could** | 추가 가치가 있으나 제외해도 핵심 목적과 필수 품질을 유지한다. | 기대 효과와 제외 영향이 제한적이라는 근거를 적는다. |
| **W — Won’t this release** | 이번 릴리스에서는 이행하지 않기로 결정한다. | 제외 이유·승인·대상 릴리스와 재검토 조건을 적는다. 다음 릴리스의 구현 약속으로 쓰지 않는다. |

요청자의 직급이나 구현 난이도를 중요도의 근거로 삼지 않는다. 난이도는 일정·원가의 입력값이며, 요구의 필요성과는 다르다.

Must가 의존하는 선행 요구를 Could로 두었다면 대체수단 또는 우선순위 정정이 필요하다. 시간이 부족하다는 이유만으로 Must를 낮추지 않고, **약속·범위 변경의 승인 기록**을 남긴다.

**③ 추적성은 ID의 나열보다 연결 의미를 우선한다.**

연결은 일대일일 필요가 없다. 공통 보안 요구 하나가 여러 기능·작업·시험에 적용될 수 있고, 시험 하나가 여러 요구를 검증할 수도 있다. 다만 **어느 인수조건을 검증하는지는 식별**되어야 한다.

초안에서는 미확보 연결을 허용하되 담당·기한을 붙인다. 확정 및 릴리스 검토에서는 다음을 확인한다.

- 이번 릴리스의 확정 요구에는 상위 목표와 검증할 인수조건이 존재한다.
- 해당 작업·시험이 준비되어야 하는 시점까지 WBS·시험 연결을 확보한다.
- 완료를 주장하는 요구의 모든 인수조건에는 대상 버전의 통과 근거가 존재한다.
- 제외·보류 항목은 없애지 않고 상태와 결정 기록을 남긴다.
- 작업과 시험에서도 요구사항으로 역추적할 수 있다.

**④ 요구 확정·구현·검증을 따로 관리한다.**

| 축 | 상태 예시 | 판정 근거 |
|---|---|---|
| 요구 상태 | 초안 / 확정 / 변경검토 / 보류 / 폐기 | 요구 내용과 범위에 대한 결정·승인 기록으로 판정한다. |
| 구현 상태 | 미구현 / 부분구현 / 구현됨 / 확인불가 | 지정 버전에서 어떤 인수조건을 수행하는 구현이 존재하는지로 판정한다. |
| 검증 상태 | 미실행 / 통과 / 실패 / 차단 | 지정 환경·버전에서 수행한 인수조건별 결과로 판정한다. |

`확정 + 미구현 + 미실행`은 정상적인 개발 전 요구다. `확정 + 구현됨 + 미실행`은 완료를 입증한 상태가 아니다.

일부만 구현했다면 “70% 완료” 대신 **충족한 AC와 남은 AC**를 적는다. 백분율에는 작업량·기능 수·검수 수가 뒤섞이기 쉽기 때문이다.
