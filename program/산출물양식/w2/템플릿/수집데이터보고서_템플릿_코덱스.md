**공통 작성 규칙 — 데이터 하나의 설명 단위**

데이터에는 문서 전체에서 변하지 않는 ID를 부여한다. 같은 공급자의 데이터라도 권한·갱신 주기·확보 상태가 다르면 별도 ID로 나눈다. 하나의 공급자 이름 아래 서로 다른 사용 조건이 감춰지는 것을 막기 위해서이다.

출처·라이선스·수집 방법·주기·양·품질·개인정보·보관·폐기는 **모두 필수 확인 항목**으로 둔다. 해당하지 않는 항목도 이유를 적는다. 예를 들어 일회성 수집은 “주기 없음—일회성, 재수집 조건 ○○”로 기록한다.

| 필수 정보 | 원본 양식 내 위치 | 반드시 확인하는 내용과 이유 |
|---|---|---|
| 식별·범위·목적 | 개요 | ID, 버전, 관측 단위, 대상 기간·지역·집단, 필요한 기능을 적는다. 다른 모집단의 데이터를 같은 자산으로 오인하지 않게 한다. |
| 출처·라이선스 | 개요의 `출처 / 저작권`, 4절 | 공급자와 권리자, 원문 위치, 허용 행위를 구분한다. 공급자가 데이터를 제공한다는 사실만으로 모든 이용 권한을 판단할 수 없기 때문이다. |
| 수집 방법·주기·비용 | 2.1·2.2 | 실제 경로, 실행 상태, 갱신 주기, 호출량·비용 상한을 적는다. 반복 수집 가능성과 운영 부담을 판단하기 위해서이다. |
| 확보량·품질 | 3.2·5절 | 실제 건수와 통과 건수, 검사 범위·산식을 연결한다. 목표 수량과 사용 가능한 수량의 혼동을 막는다. |
| 개인정보 | 4절, 필드 연결은 3.1 | 포함 필드·처리 근거·보호 조치를 적는다. “공개 자료”나 “합성 자료”라는 분류만으로 포함 여부를 대신 판단하지 않는다. |
| 보관·폐기 | 실행 방법은 3.3, 근거는 4절 | 보관 대상·기간·기산점·삭제 범위·책임자를 적는다. 원본 삭제 후 복제본·청크·백업에 남는 문제를 확인하기 위해서이다. |

각 데이터의 개요에는 다음 세 축을 별도로 적는다.

| 축 | 기록 규칙 |
|---|---|
| **데이터 성격** | 실데이터 / 합성 / Mock / 실응답 재생을 구분한다. API·파일·RAG는 수집·활용 방식이므로 이 축을 대신하지 않는다. |

**2.1 수집 방식 (해당 항목에 체크)**

| 필수 명세 | 내용 |
|---|---|

| 분량 기준 | 기존 표 1개, 선택 셀마다 ID와 상태를 1~3줄로 작성한다. |
| 흔한 실패 | 사용할 생각만 있는 방식을 완료처럼 체크하거나, Mock 응답 시험을 실제 API 수집으로 체크한다. |
| 판정 기준 | 체크된 실제 수집 방식마다 실행 근거가 있고, 개요의 모든 데이터 ID에 수집 경로가 연결되는지 확인한다. |

체크는 **기준일까지 수집 실행이 확인된 방식**에 사용한다. 예정 방식은 체크하지 않고 선택 셀에 `예정: ID, 담당, 목표일`을 적는다. 같은 방식에 실행·예정 데이터가 함께 있으면 ID별로 나눈다.

**2.2 수집 방식 (해당 항목에 체크)**

| 필수 명세 | 내용 |
|---|---|
| 이 절이 답하는 질문 | 누가 어떤 도구·주기·비용·실패 처리 조건으로 수집을 반복하는가? |
| 반드시 들어가는 것 | 실행 도구·버전, 수집 대상 범위, 자동화 상태, 실행 주기, 오류 처리, 호출 제한·비용 통제를 기록한다. 담당자가 바뀌어도 같은 운영 조건을 복원하기 위해서이다. |
| 형태 | 첫 열의 3개 항목명을 보존하고 오른쪽 값 셀에 ID별 내용을 작성한다. |
| 분량 기준 | 데이터 ID당 500~900자로 작성한다. 공통 처리 방식은 한 번 설명하고 해당 ID에서 참조한다. |
| 흔한 실패 | 라이브러리 목록만 쓰거나, 재시도를 무제한으로 두거나, 공급자 쿼터와 내부 예산을 같은 상한으로 취급한다. |
| 판정 기준 | 주기를 실제 호출량·비용으로 환산할 수 있고, 실패·부분 성공·상한 도달 시 동작과 담당을 확인할 수 있는지 검사한다. |

| 원래 항목행 | 오른쪽 값 셀에 넣는 내용 |
|---|---|
| 사용 언어 / 라이브러리 | 언어·핵심 라이브러리 버전, 수집기·설정 파일의 고정 버전, API·파일·수동 입력 경로를 적는다. 인증은 방식과 비밀정보 참조명만 기록한다. |
| 자동화 여부 및 주기 | 수동·반자동·자동, 실제 가동 여부, 최초·증분·재수집 방식, 주기·시간대·대상 범위, 담당을 적는다. 이어서 아래 비용 명세를 `비용:`으로 기록한다. |
| 오류 발생 시 예외 처리 전략 | 타임아웃, 재시도 대상·횟수·대기, 인증·권한 오류 시 중단, 페이지·체크포인트 재개, 중복 방지, 부분 실패 격리, 경보·담당을 적는다. 예산·쿼터 초과 시 처리와 자료가 오래될 때의 대응도 연결한다. |

**비용은 수집 운영을 판단할 수 있는 수준까지 이 셀에 남긴다.**

- 공급자·상품/SKU·요청 옵션, 과금 단위, 통화, 단가 근거·확인일을 적는다. 같은 API도 요청 필드나 처리 단위에 따라 비용이 달라질 수 있기 때문이다.
- 기간별 기본 호출량, 페이지 분할·일괄 처리·재시도·재수집, 호출당 과금 단위 수를 적는다. 업무 요청 1회가 유료 호출 1회와 같다고 가정하지 않는다.
- 무료 할당·구간 할인·정액료의 적용 범위를 적는다. 계정 전체가 공유하는 할당량을 데이터별로 중복 차감하지 않는다.
- 기준 예상액과 상한 시나리오, 내부 예산 상한, 공급자 쿼터, 알림 기준, 실제 차단 장치의 구현 여부를 구분한다. 알림만 설정한 상태를 비용 차단으로 기록하지 않는다.
- API 외 수집에 직접 필요한 전송·저장·문서 추출·외주 수집 비용이 있으면 포함 범위를 적는다. 회사 전체 인건비·손익은 별도 원가 문서로 넘긴다.

산식은 다음 수준으로 노출한다.

> 기간별 과금량 = Σ(실제 과금 대상 호출 × 호출당 과금 단위 수)  
> 예상 비용 = 적용 요금표에 따른 과금량 비용 + 정액·부대비용  
> 원화 환산액 = 외화 비용 × 명시한 환율

재시도·실패 호출의 과금 여부는 공급자 조건을 반영한다. 예를 들어 Routes의 경로 계산과 행렬 계산은 요청·요소라는 과금 단위가 다르므로, 단가 옆에 분모를 반드시 기록한다. [공식 사용량·과금 문서](https://developers.google.com/maps/documentation/routes/usage-and-billing)

단가가 미확보이면 전체 비용도 확정하지 않는다. 확인된 소계와 미산정 항목·해소 조건을 분리한다.

합성 데이터에는 생성기·모델 버전, 프롬프트·설정, 시드, 생성 일시를 적는다. 시드만으로 동일 출력을 보장할 수 없는 생성 방식이면 그 한계와 고정 결과물의 식별값을 함께 적는다. Mock에는 응답 규격·시나리오·기대 동작을, 실응답 재생에는 원래 조회 시각과 재생 시각을 기록한다.

**3.2 데이터 양**

| 필수 명세 | 내용 |
|---|---|
| 이 절이 답하는 질문 | 기준시점까지 몇 건을 확보했고, 그중 몇 건이 명시한 품질 기준을 통과했는가? |
| 반드시 들어가는 것 | ID·버전·집계시점·단위, 실제 확보량, 검사 완료량, 통과·제외·보류량, 집계 근거를 적는다. 목표·공급자 전체 규모·실제 확보량을 구별한다. |
| 형태 | 기존 2개 항목행의 오른쪽 셀에 ID별 수량을 작성한다. 새로운 상태 열을 만들지 않는다. |
| 분량 기준 | 기존 표 1개, ID별로 각 항목행에 2~4줄을 작성한다. |
| 흔한 실패 | 문서·청크·레코드를 합산하거나, 중복 제거 전후 숫자를 섞거나, 미측정을 0건으로 적거나, 표본 통과율을 전체에 적용한다. |
| 판정 기준 | 동일한 버전·분모에서 수량이 맞아떨어지고, 집계 쿼리와 5절의 검사 결과로 수치를 다시 계산할 수 있는지 확인한다. |

- **전체 수집 데이터 건수:** 실제 확보한 원본 건수·용량·범위를 적는다. 실데이터·합성·Mock·재생은 별도 집계한다. 수집 예정량과 공급자 주장 전체량은 별도 문장으로 표시한다.
- **추출된 고품질 데이터 건수 (필터링 후 기준):** 적용 규칙 버전과 검사 모집단, 품질 통과 건수·비율을 적는다. 이어서 **그중 권한·사용 조건까지 충족한 사용 가능 건수**를 별도로 적는다.

동일 단위에서 전수 분류했다면 다음 관계를 확인한다.

> 원본 건수 = 중복으로 제외한 건수 + 그 외 품질 탈락 건수 + 미검사·판정 보류 건수 + 품질 통과 건수

탈락 사유가 중첩되면 합계용 대표 사유를 정하고, 상세 오류 건수는 중복 집계임을 표시한다. 문서를 청크로 변환한 경우에는 단위별 집계를 분리한다.

수집 범위도 함께 적는다. `확보한 대상 수 / 목표 대상 수`를 제시하고, 분모를 모르면 커버리지 역시 `[미확보]`로 둔다.

| 저장 포맷 | 파일·DB 형식, 압축·파티션·버전 식별 방식, 청크·벡터 등 파생물 연결 관계를 적는다. 원본 변경·삭제가 어떤 파생물에 영향을 주는지 추적하기 위해서이다. |
| 인코딩 | 문자 인코딩과 필요한 구분자·개행·직렬화 조건을 적는다. 적용되지 않는 형식이면 사유를 기록한다. |

보관 기간은 임의의 공통 일수로 통일하지 않는다. 계약·이용 목적·관련 보존 의무에 따른 근거를 4절에서 연결한다. 백업에서 즉시 개별 삭제가 어려우면 만료 시점, 접근 제한, 복구 시 재삭제 절차를 적는다.

**4. 법적·윤리적 검토**

| 필수 명세 | 내용 |

| 분량 기준 | 데이터 ID당 약 600~1,000자로 작성한다. 계약·약관 전문은 연결하고 판정과 제한은 본문에 남긴다. |

| 판정 기준 | 예정된 이용 행위마다 적용 근거·판정·조건·검토 책임자가 있고, 미확인 행위가 사용 가능으로 표시되지 않았는지 확인한다. |

| 원래 항목행 | 오른쪽 값 셀에 넣는 내용과 이유 |
|---|---|
| 개인정보 포함 여부 | ID별 포함·미포함·미확인, 검사한 자료·버전·범위를 적는다. 미확인은 어느 쪽도 체크하지 않고 사유를 병기한다. |
| 포함된 경우 필드 | 직접 식별자뿐 아니라 자유서술·위치·시간·행동 조합 등 검토한 필드를 적는다. 각 필드의 수집 필요성과 처리 근거를 연결한다. |
| 비식별화 조치 여부 | 삭제·마스킹·가명처리 등 실제 조치, 적용 시점·범위, 연결키 관리, 검증 결과를 적는다. 조치 이름만으로 재식별 가능성이 해소됐다고 판단하지 않는다. |
| 출처 및 사용권 — 공개 여부 | 원천의 공개 여부와 수집본의 허용 공개 범위를 따로 적는다. 원문이 공개돼 있다는 사실과 수집본의 공개 배포 권한은 다른 판단이기 때문이다. |
| 라이선스 / 약관 검토 여부 | 공급자·권리자, 적용 계약·약관·법령의 판본과 효력일, 조항, 행위별 판정, 표시 의무, 보관·파기 조건을 기록한다. |
| 검토자 | 확인 담당자·역할, 판정 범위, 필요한 추가 검토의 담당자를 적는다. 단순 작성자와 사용 판정 책임자를 구별한다. |
| 검토 일자 | 실제 검토일, 적용 버전, 재검토 조건을 적는다. 약관 변경·용도 확대·외부 제공처 변경 시 이전 판정이 자동 승계되지 않게 한다. |

행위별 권한은 최소한 다음을 판정한다.

> 수집·다운로드 / 일시 캐시 / 장기 저장 / 가공·파생물 생성 / 화면 표시 / 외부 제공·재배포 / RAG·임베딩 / 외부 모델 입력·학습

각 행위에 `허용 / 조건부 / 금지 / 미확인 / 해당 없음`과 근거·조건을 붙인다. 공개 API라도 필드별 저장 예외와 출처 표시 조건이 다를 수 있다. 예를 들어 Places 정책은 콘텐츠 저장 제한과 장소 ID의 예외를 구분한다. 따라서 공급자 전체를 한 번에 “저장 가능”으로 표시하지 않는다. [Places 공식 정책](https://developers.google.com/maps/documentation/places/web-service/policies)

개인정보 처리에는 적용 목적·근거·항목을 기록하고, 목적 달성·보유기간 경과 등 파기 조건과 별도 보존 근거를 확인하도록 한다. 이는 실제 처리 범위와 보관 설정을 대조하기 위한 필수 기록이다. [개인정보 수집·이용 조문](https://law.go.kr/LSW/lsLinkCommonInfo.do?ancYnChk=&chrClsCd=010202&lsJoLnkSeq=1020398481), [개인정보 파기 조문](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1006183947)

합성 데이터도 원천 자료·생성 모델의 이용 조건과 실제 개인 정보의 복제 가능성을 확인한다. Mock의 기능 시험 통과는 실제 공급자 정보의 정확성이나 계약 권한을 입증하지 않는다.

**5. 데이터 품질 및 정합성 관리 방안**

| 필수 명세 | 내용 |
|---|---|
| 이 절이 답하는 질문 | 어떤 검사와 수치로 데이터의 사용 적합성을 판정하며, 실패한 데이터는 어떻게 처리하는가? |
| 반드시 들어가는 것 | 검사 ID·대상·버전, 지표 정의·분모·산식, 기준값·선정 이유, 측정 결과, 탈락·보류 처리, 재검사 조건을 적는다. “정제했다”는 설명을 재검증 가능한 판정으로 바꾸기 위해서이다. |
| 형태 | 기존 4개 항목행을 유지한다. 각 값 셀에 `대상 → 규칙·산식 → 기준 → 결과·근거 → 실패 처리` 순서로 적는다. |
| 분량 기준 | ID당 핵심 규칙 4~6개, 규칙당 약 150~250자로 작성한다. 대량 프로파일 결과는 연결한다. |
| 흔한 실패 | 결측·중복률에 분모가 없거나, 주기만으로 최신성을 보증하거나, 검사하지 않은 값을 통과로 처리하거나, 사용 결과를 본 뒤 통과 기준을 낮춘다. |
| 판정 기준 | 같은 데이터·규칙 버전으로 수치를 다시 계산할 수 있고, 3.2의 통과 건수와 일치하며, 기준 미달 시 사용할 수 없는 범위를 확인할 수 있는지 검사한다. |

| 원래 항목행 | 배치할 내용 |
|---|---|
| 중복 제거 기준 | 동일성 키, 중복으로 보지 않을 정상 반복, 충돌 시 보존 규칙, 중복률·제외 건수, 재실행 시 중복 방지를 적는다. |
| 정합성 검증 방법 | 타입·범위·참조 관계·업무 제약 검사와 최신성 검사를 적는다. 진위·정확성 검사를 했다면 비교 기준과 표본을 별도로 명시한다. |
| Null 처리 및 결측치 전략 | 필수·조건부 필수 필드, 누락·빈 문자열·미상 코드의 정의, 필드별 결측률, 삭제·보류·대체 규칙을 적는다. 대체값에는 표시와 원래 결측 상태를 보존한다. |
| 표준화 전략 | 단위·통화·시간대·코드 체계·문자 규칙, 변환 버전, 정보 손실 검사, 원본 추적 방법을 적는다. 합성·Mock 구분 표식이 변환 중 사라지지 않게 한다. |

최소 지표는 다음과 같이 정의한다. 이 표는 기존 셀에 들어갈 산식의 명세이다.

| 지표 | 산식·필수 조건 | 판정에 필요한 해석 |
|---|---|---|
| 필드별 결측률 | `해당 필드가 필수인 대상 중 결측 건수 ÷ 해당 필드가 필수인 대상 건수 × 100` | Null·빈 문자열·미상 코드의 포함 여부를 정한다. 조건부 필수의 분모와 판정 불가 건수를 따로 기록한다. |
| 중복률 | `중복 판정 가능한 건수에서 고유 키 그룹 수를 뺀 값 ÷ 중복 판정 가능한 건수 × 100` | 키가 없는 건수는 별도 오류·미판정으로 기록한다. 관측 시점이 다른 정상 이력을 삭제하지 않는다. |
| 최신성 충족률 | `허용 경과시간·유효기간 조건을 충족한 건수 ÷ 최신성 관리 대상 건수 × 100` | 기준시점, 시각 필드, 허용 경과시간, 대상 시간대·유효기간을 적는다. 시각 미상·만료 건수도 공개한다. |
| 정합성 위반률 | `규칙 위반 건수 ÷ 해당 규칙의 검사 대상 건수 × 100` | 규칙별로 집계한다. 동일 레코드의 여러 위반을 합쳐 전체 불량 레코드 수로 쓰지 않는다. |
| 품질 통과율 | `명시한 필수 규칙을 모두 통과한 건수 ÷ 해당 평가 모집단 건수 × 100` | 미검사·보류는 통과에서 제외한다. 표본 검사이면 그 표본의 결과로만 보고한다. |

분모가 0이면 0%가 아니라 `산정 불가—대상 0건`으로 적는다.

최신성에서는 **수집 시각, 공급자 갱신 시각, 실제 관측 시각, 데이터가 적용되는 시각**을 구분한다. 방금 재조회한 오래된 자료를 최신 사실로 판단하지 않는다. 공급자 갱신 시각을 알 수 없다면 “조회 경과시간 충족, 내용 최신성 미확인”으로 기록한다.

통과 기준은 업무 용도에서 도출한다. 식별·권한 판단에 필요한 필수값은 결측 허용 여부가 엄격해야 하고, 선택적 설명 필드는 다른 기준을 적용할 수 있다. 기준값마다 해당 기능에서 발생하는 오류의 영향을 적는다. “결측률 5% 이하” 같은 공통 숫자를 근거 없이 적용하지 않는다.

**6. 변경 이력 및 보완 내역**

| 필수 명세 | 내용 |
|---|---|
| 이 절이 답하는 질문 | 무엇이 어떤 근거로 바뀌었고, 남은 데이터 공백을 누가 언제 어떤 조건으로 해소하는가? |
| 반드시 들어가는 것 | 변경일·변경자, 대상 ID·버전, 변경 전후와 이유, 영향받은 수치·권한·기능, 근거를 기록한다. 보완 예정 사항에는 담당·목표일·완료 조건을 붙인다. |
| 형태 | 기존 `변경일 / 변경자 / 변경 내용 / 비고`의 4열을 사용한다. 완료 변경과 보완 예정은 `변경 내용` 셀에서 구분한다. |
| 분량 기준 | 변경·보완 항목당 100~200자로 작성한다. 사소한 문장 수정은 묶고 수치·권한·판정 변경은 개별 기록한다. |
| 흔한 실패 | “수정함”만 적거나, 모든 변경자를 “전체”로 쓰거나, 예정 작업을 완료 이력처럼 적거나, 수치를 바꾸고 기존 사용 판정을 갱신하지 않는다. |
| 판정 기준 | 모든 미확보·미구현 항목에 담당·해소 조건이 연결되고, 완료 항목은 결과 근거와 재판정 내역으로 닫혔는지 확인한다. |

보완 예정 항목의 `변경일`에는 실제 등록일을 적고, `변경 내용`에는 “보완 예정”을 명시한다. 목표일은 `비고`에 둔다. 담당자가 정해지지 않았다면 담당 미배정 사실과 배정 책임·기한을 기록한다.

**독자가 검증할 수 있게 하는 장치**

1. **주장에서 근거까지 연결한다.**  
   각 수치·권한·판정에 근거 ID를 붙인다. 연결 대상은 문서 첫 화면이 아니라 조항·표·로그·쿼리 결과까지 특정한다. 링크가 열린다는 사실과 인용 내용이 주장을 뒷받침한다는 사실을 별도로 확인한다.

2. **같은 버전을 다시 찾게 한다.**  
   데이터 ID·스냅샷·해시 또는 배치 ID, 수집기·검사 규칙 버전을 기록한다. 원문을 보관할 권한이 없으면 허용된 메타데이터와 실행 기록으로 대체하고 재현의 한계를 적는다.

3. **숫자 옆에 계산 조건을 둔다.**  
   단위·기간·분모·필터·산식·반올림 기준을 함께 적는다. 표본은 추출 방식·시드·집단별 수량을 기록한다. 인위적으로 맞춘 표본 비율을 실제 발생 빈도로 해석하지 않는다.

4. **실측의 수준을 제한한다.**  
   코드 정의 확인, 실제 실행 성공, 실제 저장 확인, 품질 통과를 구별한다. 근거가 입증하는 범위를 넘어 “수집 완료”라고 쓰지 않는다.

5. **문서 완결성과 데이터 사용 가능성을 따로 판정한다.**  
   미확보 항목이 있어도 영향·담당·해소 조건이 명확하면 현황 보고는 완결될 수 있다. 사용 가능 판정은 해당 용도의 권한·품질·최신성 조건을 충족해야 한다.
