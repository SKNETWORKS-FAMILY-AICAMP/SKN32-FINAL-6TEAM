## 1. 에이전트 설계 개요

### 1.1 서비스 개요 및 목적

[결정] A-COP은 **가고 싶은 곳과 예약을 주면 전체 여행이 성립하는지 검증하고, 여행이 끝날 때까지 상황 변화를 먼저 감지해 남은 일정을 조정하며, 때가 되면 무엇을 하면 되는지 알려주는 여행 CS 플랫폼**이다. 기준은 v11 §0-1이다.

[결정] 최초 여행계획 생성은 외부 개인 에이전트나 외부 LLM(문장을 이해하고 생성하는 언어 모델)이 담당한다. A-COP은 전달받은 일정을 검증하고, 성립하지 않는 이유와 완화할 조건을 반환하며, 검증을 통과한 여행을 지속 관리한다. 변경이 필요할 때 만드는 대안은 이 지속관리 범위에 포함한다. 근거는 v11 §4-A·§5이다.

[구현] 현재는 Case(요청이나 사건 한 건의 처리 기록)를 접수하고 분류하여 Team(여행 객체 종류별 판정 단위)에 맡긴 뒤 결과를 저장하는 코드가 있다. [미구현] 여행 전체의 일정 버전 저장·자동 재계획·고객 여행계획서 링크·알림 발송까지 연결한 제품 흐름은 완성되지 않았다. 근거는 제공 사실표와 v2 §02·§05·§08이다.

### 1.2 주요 사용자 및 핵심 기능

**주요 사용자:**

| 사용자 | 역할과 접점 |
|---|---|
| 인바운드 여행자 | [결정] 처음 한국에 자유여행을 오는 외국인 개인·친구 그룹을 1순위 고객으로 한다. 서울을 대상으로 하며, 고객은 여행계획서 링크에서 최신 일정과 변경 이유를 보고 재요청한다. [미구현] 고객용 링크 화면은 없다. |
| 개인 에이전트 | [결정] 고객을 대신해 일정·예약·조건·사건을 API(프로그램 사이의 요청·응답 접점)로 전달한다. 한국어 결과를 고객 언어로 옮긴다. [구현] 사건 접수·조회 REST API와 MCP(에이전트가 도구를 호출하는 표준 접점) 도구 선언·함수·시험이 있다. [미구현] 외부 에이전트가 MCP 전송으로 접속하는 문서화된 기동 경로는 없다. [미확보: AI-U-11] MCP 호출자 인증은 확보되지 않았다. [미확보: AI-U-02] 개인 에이전트와의 종단 연동 성공 기록은 확보하지 않았다. |
| 운영자·승인자 | [구현] 사건·실행 추적·승인 대기·바깥함 운영 화면을 사용한다. [결정] 자동 조정 실패와 근거 충돌을 검토하고, 업체 예약 변경의 승인 경계를 관리한다. |

[결정] 고객 접점은 **개인 에이전트 API와 여행계획서 링크 두 가지**이다. 링크·알림은 고객이 고른 언어로 생성하며, 같은 문구틀과 언어는 처음 생성한 뒤 재사용한다. 시각·날짜·금액·고유명사·예약번호는 원값을 유지한다. 대만 고객의 번체 중국어도 이 직접 경로에 포함한다. 근거는 v11 §1·결정 14이다.

**핵심 기능:**

| 기능 | 설계와 현재 범위 |
|---|---|
| 일정 성립 검증 | [결정] 시간 충돌·이동 여유·예산·필수 조건을 코드로 판정한다. [구현] 객체별 판정 코드 일부가 있다. [미구현] 일정 전체를 검증하는 연결과 이동 시간 조회가 남아 있다. |
| 근거 제공 | [구현] 판정 결과에 근거를 담는 계약이 있다. [결정] 모든 판정 근거에 출처와 확인 시각을 붙인다. |
| 선제 감지·조정 | [결정] 여행 종료까지 변화를 감지하여 재계획·재검증 후 통지한다. [구현] 장소 관측·변화 기록이 있다. [미구현] 대표 사건 감지에서 Case 생성으로 이어지는 경로가 없다. |
| 재요청·되돌림 | [결정] 고객 재요청에 따라 이전 일정이나 보존한 다른 안으로 바꾼다. [미구현] 일정 버전 저장과 묶음 단위 되돌림이 없다. |
| 사람 인계 | [구현] Team 결과를 상향 전달 이벤트로 바꾸는 처리가 있다. [미구현] 묶음 탐색 결과·탈락 사유를 포함한 인계 흐름은 없다. |
| 업체 변경 인계 | [결정] 바꿀 항목·대안·차액을 담은 변경 링크로 넘긴다. [구현] 승인 대기 제안 등록과 사람 승인 API가 있다. [미구현] 변경 링크와 승인 이후 실행 연결이 없다. |
| 협약사 시연 | [결정] 위임 범위 안의 자동 실행은 Mock(실제 공급자를 대신하는 시험용 대역) 공급자로만 시연한다. [미구현] 해당 실행 분기와 공급자 종류 제한 게이트가 없다. |
| 일정 안내 | [결정] 생성·변경, 여행·하루 시작, 각 항목 출발 시점에 안내한다. [미구현] 세 시점의 안내 발행·발송 연결이 없다. |

기능 목표의 근거는 v11 §3이며, 구현 범위는 제공 사실표와 v2 §08을 따른다.

### 1.3 에이전트 시스템 설계 목표

[결정] 다음 P1~P5는 **논문 패턴이 아니라 A-COP의 점검 항목**이다. 재설계안 §3에 따라 책임과 검사 지점을 연결한다.

| 점검 항목 | 설계 목표 | 현재 상태 |
|---|---|---|
| P1 역할·능력 | 객체 종류별 담당과 수행 기능을 선언하고, 유효한 요청이 해당 기능에 도달하도록 한다. | [구현] 여섯 Team 등록·두 축 라우팅이 있다. [미구현] 변경·취소 준비 기능으로 이어지는 선택 연결이 남아 있다. |
| P2 도구 권한 | Team이 선언한 읽기 도구만 사용하고 호출 예산을 넘지 않도록 한다. | [구현] 실행기와 도구 호출 경계에서 권한·중복·예산을 검사한다. v2 §03·§07을 따른다. |
| P3 조정·자율 | Controller(사건 실행과 결과 반영을 조정하는 부품)가 Team을 호출하고 상태를 전이한다. 전체 일정 조정은 코어 검증 층에서 수행한다. | [구현] 단일 Team 호출과 결과 반영이 있다. [미구현] 여러 Team을 연결한 묶음 조정이 없다. |
| P4 사람 승인 | 업체 변경 제안을 사실과 대조하고, 승인 경계를 통과한 작업만 실행 대상으로 삼는다. | [구현] 제안 등록 전 대조·승인 시 재대조·승인 기록이 있다. [미구현] 승인 이후 재실행과 공급자 실행 연결이 없다. |
| P5 출력 검증 | 객체 판정, 제안 대조, 승인 시 재대조, 고객 전달 전 검증을 구분한다. | [구현] 앞의 세 검증에 해당하는 코드가 있다. [미구현] 전달 전 검토 Team은 미등록이며 호출 설정은 꺼져 있다. |

### 1.4 설계 시 고려사항

| 고려사항 | 적용 내용 |
|---|---|
| 확장성 | [결정] 도시 확대는 데이터 추가, Team 확대는 객체 종류 추가로 다룬다. Core(공통 실행·계약 계층)는 여행 업무 어휘를 직접 판단하지 않고 선언과 계약으로 연결한다. 근거는 v11 §5·§6이다. |
| 응답 속도 | [구현] REST 접수는 생성 트랜잭션 뒤 분류의 LLM 호출을 응답 전에 수행하고, Controller 실행만 201 응답 뒤 `BackgroundTasks`(응답 후 실행하는 백그라운드 작업)로 분리한다. **분류 대기는 접수 응답 전에 남는다.** MCP 접수는 생성·분류까지만 수행한다. 근거는 정정 사실표의 「접수 후 실행」·「MCP 접수」이다. [미확보: AI-U-02] 종단 응답 시간과 병렬 실행 효과는 측정하지 않았다. |
| 비용 효율성 | [결정] 계산 가능한 판정은 코드가 수행하고, 생성은 대안·설명에 사용한다. 반복 안내는 문구틀·언어별 생성 결과를 재사용한다. [구현] 문맥 토큰 예산과 비용 상한 설정이 있다. [미확보: AI-U-03] 전체 실행의 비용 상한 강제 여부는 확인하지 않았다. |
| 실행 경계 | [결정] 먼저 고치는 대상은 내부 일정 버전이다. 실제 업체 예약은 승인 없이 변경하지 않는다. 비협약사·위임 범위 밖의 건은 변경 링크로 넘기며, 자동 실행 시연은 Mock 공급자로 제한한다. |
| 사실과 생성 | [결정] 시간·금액·이동·필수 조건은 코드와 조회 사실로 판정한다. 제공자 정보의 조회 시각을 현장 확인 시각처럼 표시하지 않는다. |
| 필수 값 누락 | [결정] 결정 15에 따라 필요한 값마다 대체 소스를 둔다. 대체 조회도 실패하면 기동을 거부하거나 서버를 정지한다. [미구현] 현재는 키 없는 소스를 제외하고 앱을 기동하며, Team은 일부 누락을 상향 전달로 처리한다. |
| 코어 변경 범위 | [구현] 공통 계약을 통한 분리는 유지한다. 다만 설정·프로젝트 구성 코드의 변경이 있으므로 ‘코어를 수정하지 않았다’고 기술하지 않는다. 근거는 v2 §01·§11이다. |

### 2.4 기술 스택 및 연동 구조

**Model Context Protocol (MCP):**

[구현] `mcp.enabled: true`이며 FastMCP 객체와 `get_my_cases`(내 사건 목록), `get_case_detail`(사건 상세), `open_support_case`(지원 사건 접수)의 도구 선언·함수·시험이 있다. 셋 모두 `required_scope: mcp:read`이다. 접수 도구도 같은 권한 문자열을 사용한다는 현재 사실을 기록하며, 도구 이름만으로 쓰기 권한이 분리됐다고 해석하지 않는다. 근거는 정정 사실표와 `config/project.yaml:8`이다.

[미구현] 외부 에이전트가 MCP 전송으로 접속하는 문서화된 기동 경로는 없다. 확인 범위에는 앱의 MCP 전송 마운트나 실행 스크립트·기동 설정이 없으며, 시험은 Python 함수를 직접 호출하거나 도구 메타데이터를 확인한다. 따라서 모듈 플래그와 도구 선언을 외부 접속 가능한 MCP 서비스의 가동으로 해석하지 않는다. 근거는 정정 사실표의 「MCP를 띄우는 곳」이다.

[구현] MCP 호출 주체는 외부 호출자를 인증해 얻는 것이 아니라 설정의 tenant와 고정 `mcp:read`로 만든다. [미확보: AI-U-11] 외부 호출자 인증은 확보되지 않았다. 근거는 정정 사실표의 「MCP 호출 주체」이며, 해당 표가 제시한 위치는 `app/presentation/api/cases.py:280~294`이다.

[구현] `open_support_case`는 Case 생성·분류까지만 수행하며 Controller를 호출하지 않는다. [미확보: AI-U-05] 이후 처리는 라우팅 되잡기가 집어야 하나 그 실행은 확인하지 못했다. 근거는 정정 사실표의 「MCP 접수」이며, 해당 표가 제시한 위치는 `app/presentation/api/cases.py:329~366`이다.

## 3. Workflow

[결정] 대표 시나리오는 **대만인 친구 2명의 서울 하루**이다. 호텔 조식 → 잠실 스카이타워 → 성수동 → 경복궁 한복 관람 → 저녁 → 롯데마트 서울역점 순서의 외부 일정을 입력으로 받는다. 사건과 처리 방향은 최신 v11 §8-A를 적용한다.

[결정] 이동-B1과 요식-P3도 통과 후보 중 하나를 고른다. 이전 시나리오 대응 문서의 ‘순위 없이 나란히 제시’는 결정 15로 대체됐다. 동률은 정규화한 후보 식별자로 결정한다.
