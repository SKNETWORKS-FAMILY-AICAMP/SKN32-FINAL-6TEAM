## 1. 전체 서비스 구조 (Service Architecture)

| 질문 칸 | 값 |
|---|---|
| [시스템 구성도 이미지 삽입] | 아래 그림 명세를 사용한다. **실선은 구현 확인, 점선은 미구현·연결 미확인을 뜻한다.** 점선에는 반드시 `[미구현]`, `[미확보]` 또는 ‘구현·비활성’을 글자로 병기한다. 실행 중인지 확인하지 않은 부품을 실선만으로 가동 중이라고 표시하지 않는다. |
| 아키텍처 설계 가이드 | API(Application Programming Interface, 프로그램 간 요청·응답 창구), Controller(사건 처리 조정기), Team(여행 객체 판단 모듈), 저장소와 별도 작업 프로세스를 구분한다. **Team은 상자 하나**로 표현한다. 내부 구조는 v2 §03~04, 계약은 v2 §06을 참조한다. |
| 서비스 설계 목표 및 전략: | [결정] 외부에서 만든 일정을 검증하고, 여행 중 변화에 대응하여 일정을 조정·재검증한 뒤 알린다. 최신 상태는 여행계획서 링크에서 제공한다. [구현] 현재 확인된 중심 실행 구조는 **Controller + Case 상태기계**이다. Case는 접수한 사건 한 건이며, 상태기계는 사건의 진행 상태를 정해진 규칙으로 바꾸는 구조이다. [미구현] 여행 전체의 지속관리 흐름은 아직 연결되지 않았다. 근거는 v11 §1·§6-A·§9-C, 사실표, v2 §05·08이다. |

**상자 명세**

| 위치·상자 | 표시·담는 내용 |
|---|---|
| 로컬 기계 밖 — 고객 | [결정] 개인 에이전트를 통해 요청하거나 여행계획서 링크를 직접 연다. 링크 화면은 [미구현]이다. |
| 로컬 기계 밖 — 개인 에이전트 | [구현] REST(HTTP 기반 요청·응답 방식) 접점을 표시한다. MCP(개인 에이전트가 도구를 호출하는 연결 규약)는 도구 선언이 있으나 외부 접속의 문서화된 기동 경로가 [미구현]이므로 점선 접점으로 표시한다. 특정 개인 에이전트와의 실제 연결 성공은 [미확보]이다. |
| 로컬 기계 밖 — 운영자 | [구현] 사건 조회·추적·승인·바깥함 관리 화면을 사용한다. 근거는 사실표의 운영 UI이다. |
| 로컬 기계 안 — API 서버 | [구현] 접수·조회·입력 재개·승인·운영 화면을 제공한다. 내부에 분류, 라우팅, Controller, 검증, Action(상태 변경·외부 실행을 통제하는 처리 층)을 구분한다. Action의 제안·승인 기록과 공급자 실행은 별도 상태로 표시한다. |
| API 서버 안 — 여행 Team | [구현] 여섯 로컬 Team을 포함한 상자 하나로 그린다. 작업과 판단 결과만 주고받는다. 내부는 v2 §03~04를 참조한다. |
| 로컬 기계 안 — 되잡기 작업 | [구현] 멈춘 분류·라우팅을 재처리하는 작업이다. 여행 감시 되잡기는 별도 점선 상자로 표시한다. |
| 로컬 기계 안 — 바깥함 일꾼 | [구현] outbox(보낼 메시지를 DB에 먼저 기록하는 바깥함)에서 행을 꺼내 발행 함수를 호출한다. 디스코드 발송 함수는 [미구현]이다. |
| 로컬 기계 안 — DB | [구현] PostgreSQL과 pgvector(문서 의미 검색용 벡터 저장 확장)를 표시한다. 사건·실행·승인·바깥함·여행 조회 자료를 저장한다. Trip(여행 전체 상태) 저장 구조는 점선으로 구분한다. |
| 로컬 기계 밖 — 외부 소스 | [구현] 관광정보·기상·공휴일·국가유산 조회 어댑터를 표시한다. 키·설정에 따른 조립 여부와 Team까지의 연결 여부는 2.5에 따른다. |
| 로컬 기계 밖 — LLM API | [구현] LLM(대규모 언어 모델) 호출과 임베딩(문서를 검색용 숫자 벡터로 바꾸는 처리) API를 표시한다. |
| 로컬 기계 밖 — 알림 채널 | [결정] 디스코드 한 채널을 고객 통지에 사용한다. [미구현] 실제 발송 연결은 점선으로 표시한다. |
| 별도 원격 상자 — A2A 에이전트 | [구현·비활성] A2A(에이전트 사이의 원격 작업 위임 규약) 서버와 Place Verification 시뮬레이터를 표시한다. 현재 코어의 원격 호출 연결은 꺼져 있다. |

**화살표 명세**

| 출발 → 도착 | 선·흐르는 것 |
|---|---|
| 개인 에이전트 → REST 접수 | 실선 · [구현] 고객 식별자·메시지·채널·요청 식별자가 흐른다. |
| 개인 에이전트 → MCP 도구 | **점선 · [미구현] 외부 에이전트가 MCP로 접속하는 문서화된 기동 경로가 없다.** 사건 목록·상세 조회·접수 도구 선언은 [구현]이다. 근거는 정정 사실표 「MCP를 띄우는 곳」의 Claude 정적 확인이다. |
| REST 접수 → DB → 분류 | 실선 · [구현] Case 생성·생성 이벤트 기록 후, 생성 트랜잭션 밖에서 메시지를 분류한다. |
| REST 접수 → 호출자 | 실선 · [구현] 분류 후 사건 식별자·상태·버전·조회 주소를 응답한다. |
| 응답 후 작업 → Controller → 여행 Team | 실선 · [구현] BackgroundTasks(응답 뒤 실행할 작업 등록 기능), TeamTask(팀에 위임하는 작업 계약)가 흐른다. |
| 여행 Team → Controller | 실선 · [구현] TeamResult(판단 결과 계약)와 필요 시 ActionProposal(실행 제안)이 흐른다. |
| Controller → 검증 → 승인 저장소 | 실선 · [구현] 제안 사실 대조와 승인 요청 기록이다. 현재 기본 라우팅에서 승인 제안 기능에 도달하지 못하는 한계를 병기한다. v2 §02·08을 참조한다. |
| 운영자 → 승인 API → DB | 실선 · [구현] 승인·거절, 승인 시 재대조, 사건 상태 전이가 흐른다. |
| 승인 완료 → 공급자 실행 | 점선 · [미구현] 승인 뒤 재실행과 공급자 실행 연결이 없다. |
| API 서버 ↔ 외부 소스·LLM API | 실선 · [구현] 조회 인자·조회 결과·분류 입력·모델 출력이 흐른다. 실제 응답 성공은 이 문서에서 검증하지 않았다. |
| 되잡기 작업 ↔ DB·Controller | 실선 · [구현] 멈춘 분류·라우팅 사건을 읽고 재처리한다. |
| 여행 감시 → Case 생성 | 점선 · [미구현] 관측 변화에서 사건을 생성하는 연결이다. |
| 재검증된 일정 → 바깥함 → 일꾼 → 디스코드 | 여행 통지 경로는 점선 · [미구현]이다. DB 바깥함을 읽고 발행 함수를 호출하는 일꾼 부분만 실선으로 표시한다. |
| 고객 ↔ 여행계획서 링크 ↔ Trip 저장소 | 점선 · [결정][미구현] 최신 일정·변경 이유·업체 미확정 상태·재요청이 흐른다. |

**경계선 명세**

| 경계 | 표시 내용 |
|---|---|
| 로컬 기계 경계 | API·관리용 진입점·되잡기 작업·바깥함 일꾼·DB를 둘러싼다. 외부 LLM과 데이터 공급자는 밖에 둔다. |
| 외부 요청의 신뢰 경계 | 외부 입력과 API·MCP 접점 사이에 표시한다. [구현] REST 접수는 `case:write` 권한을 요구하고, 조직 구분값인 `tenant_id`는 요청 본문이 아니라 인증 결과에서 얻는다. `[실측 · 정적 확인] app/presentation/api/cases.py:102~111`. MCP는 2.5의 별도 한계를 표시한다. |
| 실행 권한 경계 | Team 결과와 Action·승인 처리 사이에 둔다. [구현] Team은 제안만 반환한다. v2 §02·06을 참조한다. |
| 외부 데이터 경계 | 공급자 응답은 조회 근거이며 현장 확인과 같지 않음을 표시한다. `[실측 · 정적 확인] app/infrastructure/travel/base.py:200~209`. |

## 2. 시스템 구성 요소 상세 (System Components)

### 2.1 배포 환경 (Deployment)

| 질문 칸 | 값 |
|---|---|
| 클라우드 인프라: | [결정] **로컬 실행 + 외부 LLM API**이다. 클라우드 배포는 이번 MVP 범위에서 제외한다. 누락된 배포 작업으로 분류하지 않는다. 근거는 v11 §9-A이다. |
| 컨테이너화: | [해당 없음] 현재 로컬 실행 범위에는 컨테이너를 사용하지 않는다. **릴리스 대상 `final_project_cs/`에는 Dockerfile·compose가 없다. 참고 구현체 `final_project_sample/`에는 재현용 `Dockerfile`·`Dockerfile.customer`·`docker/compose.yml`이 있다. 이 개발 기계에는 Docker가 설치돼 있지 않다.** 근거는 정정 사실표 「컨테이너」의 Claude 확인이다. |
| 로컬 실행 | [구현] 고객 릴리스 진입점은 `app.presentation.api.app:app`이며 로컬 포트는 8042이다. Uvicorn(파이썬 웹 애플리케이션 실행 서버)으로 실행하는 대상이다. 현재 프로세스 가동 여부는 [미확보]이다. |
| DB 주소 | [구현·설정] `127.0.0.1:5433/acop_cs`를 사용한다. PostgreSQL 직접 실행 환경이다. `[실측 · 정적 확인] .env.example:5~6`. |
| 주기 실행 | [구현] Windows 작업 스케줄러 등록 스크립트 `scripts/install_sweeper_task.py`가 있다. 실제 등록·최근 실행 결과는 [미확보]이다. 근거는 사실표이다. |
| 운영 전환 | [제안] 외부 공개 전에 프로세스 자동 재시작, 안전한 접속 경로, 비밀 보관·교체, DB 백업·복구, 배포·되돌림 절차와 장애 관측을 마련한다. 특정 클라우드나 컨테이너 방식은 확정하지 않는다. |

### 2.2 서버 구성 (Server)

| 질문 칸·프로세스 | 무엇이 띄우나 | 무엇을 하나 | 켜져 있나 |
|---|---|---|---|
| 백엔드 API 서버: 고객 릴리스 | Uvicorn에서 `app.presentation.api.app:app`을 실행한다. 로컬 8042 기준이다. | [구현] Controller를 조립하고 REST·운영 UI를 연결한다. Composer(프로젝트 구성을 편집하는 관리 기능) 쓰기 라우터는 기본 릴리스에 넣지 않는다. | [구현] 진입점 존재. 실제 가동은 [미확보]이다. |
| 관리용 진입점 | `app.entrypoint:app`을 사용한다. 기동 명령·별도 포트는 [미확보]이다. | [구현] Composer 라우터를 주입하는 관리용 진입점이다. 고객 릴리스와 구분한다. | [구현] 사실표에서 확인된 진입점이다. 실제 가동은 [미확보]이다. |
| 되잡기 작업 | `scripts/run_sweepers.py`를 수동 실행하거나 작업 스케줄러로 호출한다. | [구현] 분류·라우팅 되잡기 둘을 실행한다. 기본은 `--once`, `--interval`로 상주 실행한다. | [미확보] 스케줄 등록·가동 상태. 여행 감시 되잡기는 [미구현]이다. |

### 3.2 실시간 요청 처리 흐름

| 질문 칸 | 값 |
|---|---|
| 사용자 요청: | [구현] REST는 고객 식별자·메시지·채널·요청 식별자를 받는다. MCP도 접수 도구를 선언하지만 외부 접속의 문서화된 기동 경로는 [미구현]이며 실행 연결도 다르다. [결정][미구현] 여행계획서 링크의 재요청은 별도 고객 접점이다. |
| 그래프 진입: | [구현] 사건을 만들고 `CREATED`(생성 이벤트)를 기록한다. 실제 조정기는 Controller와 Case 상태기계이다. REST의 생성 트랜잭션이 끝난 뒤 분류하며, **분류 후 응답 → BackgroundTasks → Controller 실행** 순서이다. `[실측 · 정적 확인] app/presentation/api/cases.py:135~168`. |
| 의도 분석 및 라우팅: | [구현] 분류 결과의 `issue_code`(사건 종류 코드)에서 `case_type`(대상 객체 종류)을 구하고, `intent`(요청 종류)와 함께 Team·`capability`(구체적인 수행 기능)를 선택한다. 상세 계약과 현재 기능 선택 한계는 v2 §06·08을 참조한다. |
| MCP 도구 실행: | [구현] MCP에는 외부 사건 조회·접수용 도구 함수가 선언돼 있다. [미구현] 외부 접속의 문서화된 기동 경로가 없다. 내부 Team 조회 도구와 동일한 실행 층으로 취급하지 않는다. MCP 접수 함수는 생성·분류 뒤 반환하며 즉시 Team을 실행하지 않는다. `[실측 · 정적 확인] app/presentation/api/cases.py:329~366`. 기동 경로 부재는 정정 사실표의 Claude 확인을 인용한다. |
| 응답 합성: | [구현] Controller가 Team 결과를 사건 이벤트·상태로 반영한다. 응답 갈래에서는 답변과 근거를 저장한다. [미구현] 경고·구조화 판정·신뢰도 보존과 여행 응답 검토 연결이 남아 있다. v2 §07~08을 참조한다. |
| 제안 → 승인 → Action | [구현] 승인 대기 제안은 문맥 저하 차단과 사실 대조를 거쳐 승인 요청으로 저장한다. 승인 API는 재대조 후 승인 기록·상태 전이를 수행한다. [미구현] 승인 후 사건 재실행과 공급자 실행이 연결되지 않는다. v2 §02·08을 참조한다. |

**현재 실행과 중단 지점**

| 경로 | 처리 순서·상태 |
|---|---|
| REST 기본 경로 | [구현] 인증·입력 검사 → 중복 요청 확인 → Case 생성·생성 이벤트 → 생성 트랜잭션 종료 → 분류 → `routing`(팀 배정 대기)이면 백그라운드 등록 → 201 응답 → Controller → Team → 결과 이벤트·상태 저장 순서이다. 분류 LLM 대기는 접수 응답 전에 남아 있다. `[실측 · 정적 확인] app/presentation/api/cases.py:102~168`. |

[구현] Case 상태는 `new`(신규), `classifying`(분류 중), `routing`(라우팅 대기), `running`(실행 중), `waiting_input`(입력 대기), `waiting_approval`(승인 대기), `waiting_external`(외부 결과 대기), `resuming`(재개 준비), `resolved`(완료), `escalated`(상향 전달), `failed`(실패), `cancelled`(취소)의 12종이다. 이는 **상태 정의**이며 모든 여행 경로가 각 상태까지 구현됐다는 뜻은 아니다. 근거는 사실표이다.
