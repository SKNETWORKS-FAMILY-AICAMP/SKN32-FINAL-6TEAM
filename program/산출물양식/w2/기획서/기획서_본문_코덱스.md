## 프로젝트 주제

**A-COP는 처음 한국을 방문하는 외국인 자유여행자의 서울 일정을 검증하고, 운영 변경을 감지해 남은 일정을 조정하며, 변경 이유와 다음 행동을 한국어로 제공하는 여행 지속관리 서비스다.** 개인 에이전트가 일정 생성과 고객 언어 변환을 담당하고, A-COP는 일정의 성립 여부·근거·최신 상태를 관리한다.

현재 판단은 **제한된 실증 개발을 추진하되, 상용 확장 투자는 보류한다**는 것이다. 여행 수요와 인접 유료 상품은 확인되지만, 현재 대상의 구매자·계약 상대·결제율·여행 원가는 `[미확보]`다. 아래 재산정에서는 건당 기여이익이 양수여도 예상 획득량으로 고정비를 회수하지 못한다.

## 문제 정의

우선 고객은 서울에서 예약한 활동과 자유 방문 일정을 함께 수행하며, 개인 에이전트에 일정 생성을 맡기는 외국인 여행 대표자다. 연령이나 국적만으로 선정하지 않는다. 출발 일정이 확정됐고, 시간을 지켜야 하는 예약이 있으며, 변경 발생 시 스스로 현지 정보를 재확인해야 하는 상황을 모집 조건으로 삼는다.

현재 고객은 생성된 일정과 예약 확인서를 지도·시설 공지·예약처 화면에서 대조한다. 휴관이나 기상 변화가 생기면 이용 가능 여부를 확인하고, 대안을 찾고, 다음 예약까지 도착할 수 있는지 다시 계산한다. 업체 예약을 바꿔야 하면 별도 연락을 진행하고 동행자에게 변경 내용을 전달한다. 이 과정에서 일정표의 변경과 실제 예약의 변경이 서로 다른 상태로 남는다.

이 흐름은 저장소의 제품 정의에서 도출한 **문제 가설**이다. 실제 인바운드 고객의 행동 관찰이나 손실 분포로 검증됐다는 뜻은 아니다. 기존 CS 웹조사는 주로 커머스·금융 상담을 대상으로 하므로, 그 불만 비율을 방한 여행자의 발생률로 옮기지 않는다.

고객 효용은 `줄어든 작업 시간 × 고객이 평가한 시간 가치 + 줄어든 추가 지출 − 서비스 이용료`로 확인한다. 시간 가치와 회피 가능한 손실은 `[미확보]`이므로 현재 금전 편익을 확정하지 않는다. 대신 동일 사건을 기존 방식과 A-COP로 처리하게 하여 시간과 결과를 함께 기록한다.

초기 인터뷰는 구매 여부와 무관하게 최근 여행에서 실제 변경을 겪은 사람을 포함한다. 개인 에이전트 숙련자만 모집하면 연결 장벽이 과소평가되므로, 연결 실패·중도 포기 고객도 기록한다. 소수 인터뷰는 문제 발견에 사용하고 전체 방한객의 비율로 확대하지 않는다.

가족의 복합 돌봄 조건, 긴급 구조, 현장 동행, 장거리 항공 재발권은 이번 검증에서 제외한다. 필수 이동 자료가 없으면 “이동까지 검증 완료”라고 표시하지 않는다. 알림을 발행했거나 최신 링크를 유지했다는 사실만으로 고객이 변경을 인지했다고 판단하지 않는다.

## 시스템 구성 기획

고객은 개인 에이전트가 만든 일정과 예약·필수 조건을 제출한다. A-COP는 식별 가능한 장소와 예약으로 정규화하고, 확인 가능한 근거를 모아 시간·예산·조건을 검사한다. 통과한 일정은 최신 상태로 보관한다. 변화가 생기면 영향을 받는 항목을 묶어 대안을 검증하고, 허용된 범위의 내부 일정만 변경한다. 실제 업체 예약은 미완료 상태를 유지하며 변경 링크로 인계한다.

이 흐름은 목표 구성이다. 현재 여행 관련 표와 팀 코드가 있다는 사실을 전체 지속관리 서비스의 완성으로 표현하지 않는다.

마이그레이션 존재는 생성 SQL이 있다는 뜻이다. 운영 DB에 적용됐거나 실제 공급자와 연결됐다는 뜻은 아니다. 기존 코어 표를 재사용하는 방향은 유지하되 “기존 표 일부만 바꾸면 완료된다”는 요약으로 신규 상태 저장 작업을 누락하지 않는다.

구현은 Python·FastAPI·PostgreSQL·기존 처리 그래프를 기반으로 한다. 별도 메시지 브로커·그래프 저장소는 현재 문제를 해결하는 데 필요한 측정 근거가 있을 때 도입한다. 로컬 실행은 개발 범위이며 상용 가용성의 근거가 아니다. 상용화에는 백업·복구·장애 대응이 추가돼야 한다.

## 모델링 계획

모델링의 목적은 일정 문장을 자연스럽게 만드는 데 그치지 않는다. **필수 조건을 위반하는 안을 걸러내고, 판단할 수 없는 상태를 정확히 남기면서 고객이 실행 가능한 다음 행동에 도달하도록 하는 것**이다. 계산 가능한 제약은 코드가 처리하고, LLM은 요청 해석·대안 생성·설명에 사용한다.

처음부터 자체 모델 학습을 사업의 전제로 두지 않는다. 외부 모델과 규칙 기반 처리로 기준선을 만들고, 학습·경량화는 여행 평가에서 품질·원가 개선이 확인될 때 채택한다. 기존 GPU 학습 실패는 해당 환경·워크로드의 결과이며 여행 추론 가능 여부를 대신하지 않는다.

LLM 채점은 보조 평가로 사용한다. 정책 적용·금액·예약 충돌은 결정론적 검사와 사람 검수로 판정한다. `answer=null`인 결과에 정답 점수를 주는 문제와 모의 실행을 실제 실행으로 혼동하는 문제를 먼저 검사한다.

결과는 평균뿐 아니라 실패 사례, 비용 상위 구간, 지연 상위 구간을 함께 보고한다. 비교 차이에는 여행 단위로 묶은 신뢰구간을 붙인다. 작은 합성 평가에서 위반이 없었다는 사실을 현장 오류율이 없다는 주장으로 확대하지 않는다.

RAG는 수집량을 늘리기 전에 입력 계약을 고친다. 추가 조사 문서는 Activity가 취소 기한·위약금율을 사전 형태로 읽는 반면, 검색 결과는 `PolicyChunk` 객체여서 필요한 수치를 읽지 못할 수 있다고 지적한다. 이는 정적 대조 결과이며 실행 재현은 별도다.

본 기획은 **계산용 구조화 정책과 인용용 원문을 동일 정책 ID·버전으로 묶는 방식**을 제안한다. 수치를 운영 가드레일과 섞지 않고 적용 업체·상품·시행 기간에 연결한다. 산문에서 수치를 추출하더라도 사람 검수 전에는 자동 판정에 사용하지 않는다.
