# 글쓰기 지침: 제출 문서와 발표 자료

triPilot 팀(A-COPilot)이 밖에 내는 글(부트캠프 산출물 문서, 발표 자료, 발표자 노트)을 쓸 때 따른다.
작성 에이전트(Codex)는 **쓰기 전에 이 파일을 끝까지 읽고**, 끝나면 §4 점검을 돌린 결과를 마지막 메시지에 적는다.
§5 는 실제로 검수에서 걸린 사례다. 규칙이 애매하면 사례를 따른다.

---

## 0. 누가 읽나

- **읽는 사람**: 부트캠프 강사·심사자·다른 팀. 우리 코드와 내부 문서를 모른다.
- **그래서**: 우리끼리 쓰는 말(내부 별명, 파일 이름, 함수 이름)을 그대로 쓰면 뜻이 안 전해진다.
  코드 식별자는 **증거로 보여 줄 때만** 쓰고, 그때도 앞에 쉬운 말을 먼저 둔다.
- 발표는 **멀리서 한 번 훑어보는** 글이다. 문서는 **앉아서 끝까지 읽는** 글이다. 둘의 길이 기준이 다르다(§2·§3).

## 1. 공통 문체

### 1-1 문장

1. **평서문 「~다」** 로 끝낸다. 「~함」「~임」「~할 것」 같은 개조식 끝맺음은 쓰지 않는다.
   발표 카드의 짧은 구절은 명사로 끝내도 된다. 다만 **한 장 안에서는 한 가지로** 맞춘다.
2. **한 문장에 사실 하나.** 쉼표로 이어 붙인 문장은 둘로 나눈다.
3. **결론을 먼저** 쓴다. 이유와 근거는 뒤에 둔다.
4. 주어와 동사를 분명히 한다. 「~가 된다」「~되어진다」 같은 피동은 능동으로 바꾼다
   (「검사가 실행된다」 대신 「CI가 검사를 돌린다」).
5. **영문·숫자 뒤의 조사는 붙인다.** 「Case를」「CI에서」「3분마다」로 쓰고, 「Case 를」「CI 에서」로 띄우지 않는다.
   (내부 위키는 띄워 쓰지만 제출물은 표준 맞춤법을 따른다.)
6. **줄표(—)로 문장을 잇지 않는다.** 「A — B」는 번역투로 읽힌다. 두 문장으로 나누거나 쌍점(:)이나 괄호를 쓴다.
7. **기호 사슬로 문장을 대신하지 않는다.** 「문장 → Case → 분류 → 신고 뽑기」처럼 화살표로 이은 글은 읽는 사람이 빈칸을 채워야 한다.
   흐름은 **도형 화살표로 그리고**, 글로 쓸 때는 동사를 넣는다(「받은 문장을 분류해 신고를 뽑는다」).
8. 가운뎃점(·) 나열은 **셋까지**. 넷 이상이면 표나 목록으로 바꾼다.
9. 별표(★·☆), 느낌표, 이모지는 쓰지 않는다.

### 1-2 낱말

1. **이름**: 제품은 **triPilot**, 팀은 **A-COPilot**. 「A-COP」은 옛 이름이라 쓰지 않는다
   (파일 이름에 남은 것은 파일 이름으로만 인용한다).
2. **내부 별명은 풀어 쓴다.** 처음 나올 때 쉬운 말을 앞에 두고, 필요하면 괄호에 원래 이름을 넣는다.

   | 내부에서 부르는 말 | 제출물에서 쓰는 말 |
   |---|---|
   | 되잡기 작업 | 밀린 일을 주기적으로 다시 확인하는 작업 |
   | 바깥함 일꾼(outbox worker) | 알림 발송 작업(보낼 알림을 모아 두었다가 한 번씩만 보낸다) |
   | 판정 문 / 같은 판정 문 | 적용 여부를 정하는 한 곳(변경을 바로 적용할지, 먼저 물을지 정한다) |
   | 코어 1 · 코어 2 | 접수·분류 층 · 실행 층 |
   | Case | 처리 건(Case) |
   | Team | 판정 모듈(Team) |
   | 사실표 · 지시문 · 검수 파일 | **쓰지 않는다.** 실제 출처(코드 경로, 커밋, 측정 날짜)로 바꾼다 |

3. 코드 식별자(`apply_or_ask`, `itinerary_versions`)는 본문 대신 **각주·괄호·발표자 노트**로 보낸다.
4. 같은 것은 문서 끝까지 **같은 이름**으로 부른다. 「대안」과 「후보」와 「안」을 섞지 않는다.
5. 영어 제목과 딱지는 한 자료 안에서 통일한다. 섞을 이유가 없으면 한국어로 쓴다.

### 1-3 숫자와 주장

1. **비율과 건수에는 분모를 적는다.** 「통과 1,015」가 아니라 「1,015건 통과 / 전체 1,400건」으로 쓴다.
   분모가 무엇인지(전체 시험 수인지, live 제외인지) 한 번은 말로 적는다.
2. **잰 값과 예상한 값을 섞지 않는다.** 잰 값에는 **날짜와 횟수(n)** 를 붙이고, 예상에는 「예상」이라고 적는다.
   한 번 잰 값은 「1회 측정」이라고 밝힌다.
3. **상태 낱말의 뜻을 지킨다.** 이 셋만 쓰고, 그 기준으로만 쓴다.
   - **완료**: 코드가 있고, 시험이나 실제 실행으로 확인했다.
   - **부분**: 일부만 있다. 무엇이 빠졌는지 같은 줄에 적는다.
   - **없음**: 코드가 없다. 「찾아봤고 없었다」면 어디를 찾았는지 적는다.
4. **부정과 한계는 확인한 범위와 함께** 쓴다. 「X 없음」 대신 「X를 코드 검색으로 찾았고 나오지 않았다」로 쓴다.
5. **과장하지 않는다.** 「완벽히」「모든」「항상」은 증거가 전부를 덮을 때만 쓴다.
   1회 확인한 것을 「검증 완료」라고 쓰지 않는다.
6. 근거에 없는 숫자는 쓰지 않는다. 숫자를 바꿨으면 어디서 가져왔는지 작업 기록에 남긴다.
7. **근거를 못 찾은 사실을 반대 주장으로 바꾸지 않는다.** 앞 판에 있던 사실의 근거를 못 찾으면 화면에서 빼고 **마지막 메시지에 「근거 못 찾아 뺐다」고 보고**한다.
   「확인이 필요하다」「확인했다고 말할 수 없다」도 주장이다. 근거 없이 쓰면 틀린 말이 될 수 있다.

### 1-4 절대 쓰지 않는 것

- 공인 IP, 서버 호스트, 계정명, SSH 별칭, 키 파일 경로, 웹훅 주소, 실제 API 키
- 로컬 경로(`C:\Users\…`, 작업 임시 폴더)
- 개인 정보(실제 주문·배송지 조각, 팀원 외 실명)
- 내부 작업 파일 이름(사실표, 지시문, 검수 기록)

## 2. 제출 문서(docx)

1. **양식의 순서와 제목을 바꾸지 않는다.** 양식이 세 줄 연속을 기대하는 곳(「모델 유형 / 담당 태스크 / 프레임워크」)에는 사이에 문단을 끼우지 않는다.
   설명 문단은 그 줄들 **뒤에** 둔다.
2. 절의 첫 문장은 **그 절의 결론**이다. 표 앞에는 표가 말하는 것을 한 문장으로 쓴다.
3. 문장은 **60자 안팎**으로 쓴다. 80자를 넘으면 나눈다.
4. 앞 차수와 달라진 점은 「정정한다」「추가했다」처럼 **무엇이 바뀌었는지** 동사로 쓰고, 변경 이력 표에도 한 줄 남긴다.
5. docx 본문에는 줄표(—), 화살표(→), 별표(★)를 넣지 않는다. 빌드 검사(`docxfill.check`)가 막는다.
6. 고칠 때는 **빌드 스크립트를 고쳐 다시 빌드**한다. 결과 docx를 손으로 고치지 않는다.

## 3. 발표 자료(pptx)

### 3-1 이야기 구조

1. **제목은 주제가 아니라 결론 한 문장이다.**
   - 「CI/CD」가 아니라 「코드를 합칠 때마다 CI가 시험 1,400건을 자동으로 돌린다」
   - 「유스케이스 점검」이 아니라 「준비된 유스케이스는 10개 중 5개다」
2. **제목만 이어 읽어도 발표 전체 이야기가 되어야 한다.** 다 쓴 뒤 제목만 뽑아 읽어 보고, 끊기면 고친다.
3. 제목은 **한 줄(약 32자 이내)**. 넘치면 결론이 아직 날카롭지 않은 것이다.
4. **한 장에 할 말 하나.** 두 가지를 말하고 있으면 두 장으로 나눈다.
5. 첫 장 다음에는 **오늘 무엇을 말하는지**(목차 또는 한 줄 요약)가 오고, 마지막 장은 **다음에 할 일과 결정이 필요한 것**이다.

### 3-2 한 장의 글

1. 본문은 **한 장에 150자 안팎**이다(표 장은 예외). 더 필요하면 발표자 노트로 보낸다.
2. 카드 하나의 설명은 **한두 줄**이다. 카드 안 글이 세 줄을 넘으면 카드를 키우지 말고 글을 줄인다.
3. **줄바꿈이 낱말 가운데서 끊기지 않게** 한다. 한 글자나 조사 하나만 다음 줄로 넘어가면(「…알린\n다」) 글을 고친다.
4. 설명 없는 약어는 쓰지 않는다. RAG, A2A 같은 말은 처음 나올 때 풀어 쓰거나 노트에서 설명한다.

### 3-3 그림과 배치

1. 한 장에 **주인공 그림 하나**(도식, 표, 캡처). 나머지 요소는 그 그림을 설명한다.
2. **흐름은 도형과 화살표로 그린다.** 글 속 「→」로 흐름을 대신하지 않는다.
3. 캡처는 **필요한 부분만 잘라** 넣고, 글자가 읽히지 않으면 확대하거나 핵심을 옆에 글로 다시 적는다.
   캡처 아래에 **출처와 날짜**(「팀 FigJam 보드, 2026-09-28 캡처」)를 적는다.
4. 핵심 숫자나 칸은 **색으로 한 곳만 강조**한다. 모두 강조하면 아무것도 강조되지 않는다.
5. 색은 뜻을 가진다: 파랑=기본·진행, 초록=완료·통과, 주황=부분·주의, 빨강=없음·위험, 회색=범위 밖.
   같은 색을 다른 뜻으로 쓰지 않는다.
6. **여백을 고르게** 둔다. 한쪽에 몰리고 반대쪽이 비면 배치를 고친다. 도형끼리 겹치지 않게 한다.
7. 오른쪽 위 딱지(배지)는 **그 장의 내용**을 말한다. 앞 양식에서 딴 그림 딱지를 그대로 쓰지 않는다.
   딱지 폭은 글자 수로 잡되 **한글은 글자당 약 0.16인치(10pt 굵게)** 로 계산한다. 영문 기준으로 잡으면 두 줄로 깨진다.
8. **앞 판의 주인공 그림(단계 흐름, 시간 띠 같은 도식)을 표나 글 한 줄로 바꾸지 않는다.** 글자를 키우느라 자리가 모자라면 그림을 지키고 글을 줄인다.

### 3-4 글자 크기(16:9, 13.33×7.5인치 기준)

| 요소 | 최소 | 보통 |
|---|---|---|
| 제목 | 22pt | 24pt, 굵게 |
| 카드 제목 | 14pt | 14~16pt, 굵게 |
| 본문·카드 설명·표 | **12pt** | 12~14pt |
| 출처·쪽번호·각주 | 10pt | 10pt |

12pt로 안 들어가면 글을 줄인다. 글자를 줄여서 맞추지 않는다.

### 3-5 발표자 노트

표지를 뺀 **모든 장에 노트를 쓴다.** 노트는 **말로 읽을 원고**다.

- 길이: 한 장에 **30~60초 분량(150~300자)**.
- 순서: ①이 장의 결론 한 문장 ②근거 두세 개(숫자는 분모·날짜 포함) ③다음 장으로 넘기는 한 문장.
- 코드 이름, 커밋, 파일 경로처럼 화면에서 뺀 증거는 노트에 둔다. 질문을 받으면 노트를 보고 답할 수 있어야 한다.
- 문체는 **말하는 존댓말**(「~입니다」「~했습니다」)이다. 화면 글(「~다」)과 다르다.

## 4. 끝내기 전 점검

### 4-1 기계 검사

- 발표: `python program/산출물양식/_build/pptx_check.py <덱.pptx> <렌더 폴더>`
  - 실패 0이어야 한다(글자 넘침, 10pt 미만, 금지어, 노트 없음, 장 밖 도형).
  - 경고(12pt 미만 본문, 조사 띄어쓰기)는 하나씩 보고 고치거나, 남긴 이유를 적는다.
  - PowerPoint가 없는 환경이면 넘침 검사와 렌더를 건너뛴다. 그때는 **「건너뛰었다」고 보고**하고 통과라고 쓰지 않는다.
- 문서: 빌드 스크립트의 검사(금지 문자, 양식 예시 잔존, 공개 금지 식별자)

### 4-2 읽어 보는 검사

1. **제목만 이어 읽기**: 이야기가 되나?
2. **숫자마다 근거 대기**: 이 숫자는 어느 파일, 어느 측정에서 왔나? 분모가 적혀 있나?
3. **처음 보는 사람 시험**: 내부 별명이나 코드 이름이 설명 없이 나오나?
4. **렌더 그림 한 장씩 보기**: 넘침, 겹침, 한 글자 줄바꿈, 빈 공간, 읽히지 않는 캡처가 있나?
5. **상태 낱말**: 「완료」라고 쓴 것마다 코드와 확인 근거가 있나?

### 4-3 마지막 메시지에 쓸 것

- 만든 파일 목록
- 기계 검사 결과(실패 n, 경고 n, 건너뛴 것)
- 지시받은 고칠 거리마다 **반영했나 / 못 했으면 왜**
- 근거를 못 찾아 **뺀 내용**과 **확인 못 한 것**
